# GPT-5.6 多轮与工具工作流该怎样选择上下文机制

多轮应用变慢或变贵时，团队常会把持久化推理、提示缓存、程序化工具调用和多智能体混在一起讨论，仿佛它们都是“减少 token 的功能”。结果可能是为了缓存而保留已经失效的推理，为了并行而拆出互相依赖的子任务，或者把需要模型判断的工具链写成固定程序，最终答案反而漏掉证据。

四种机制处理的是四类问题：跨轮推理是否仍相关、稳定提示是否重复、可预测的数据处理是否应交给代码、复杂任务是否能拆成独立工作流。本文按任务形态建立选择顺序，并给出验证每条路线的指标和停止条件。

## 一、四种机制解决的不是同一个问题

先用一张表区分责任：

| 机制 | 主要解决什么 | 不负责什么 |
| --- | --- | --- |
| 持久化推理 | 跨轮复用仍相关的推理项 | 不等于缓存所有输入，也不替代对话目标管理 |
| 提示缓存 | 复用稳定、重复的提示前缀 | 不判断旧内容是否仍有业务意义 |
| Programmatic Tool Calling | 用代码处理大量、可预测的中间结果 | 不适合每一步都需要新语义判断的流程 |
| 多智能体 | 并行执行可独立拆分的工作流并汇总 | 不会自动消除任务依赖、冲突和重复工作 |

因此选择顺序应从问题开始。多轮质量下降，先检查推理相关性；重复系统提示带来大量输入，再看缓存；工具结果过多且处理逻辑固定，才考虑 PTC；任务能够清楚拆成互不依赖的工作流，并行确实能缩短端到端时间，再评估多智能体。

## 二、reasoning.context 负责跨轮推理相关性

OpenAI 当前的 [GPT-5.6 模型指南](https://developers.openai.com/api/docs/guides/latest-model?model=gpt-5.6)说明，GPT-5.6 可以跨轮复用可用的推理项。`reasoning.context` 用来选择早期推理是否继续参与：

- `all_turns` 适合目标、假设和优先级在多轮间保持稳定的任务；
- `current_turn` 适合旧推理不再相关，或当前轮已经改变问题定义的任务；
- 省略该字段或使用 `auto` 时，GPT-5.6 的有效默认值为 `all_turns`，应从响应字段确认实际模式。

用 `previous_response_id` 续接，模型可以访问早期响应中仍可用的推理。一个简化示例是：

```python
first = client.responses.create(
    model="gpt-5.6-sol",
    input="审查发布方案，找出可能导致长时间停机的风险。",
    reasoning={"effort": "high", "context": "all_turns"},
)

second = client.responses.create(
    model="gpt-5.6-sol",
    previous_response_id=first.id,
    input="基于刚才的风险，给出按优先级排序的缓解计划。",
    reasoning={"effort": "high", "context": "all_turns"},
)
```

第二轮延续同一目标，早期推理仍有价值。如果用户突然改成审查另一个系统，或明确推翻之前假设，就应新建任务或测试 `current_turn`，避免模型继续维护过时结论。

验证不能只看回答是否连贯。要检查早期事实是否被正确复用、已撤销假设是否仍出现、错误是否跨轮放大、输入与总 token 如何变化。手工管理历史、使用 `store: false` 或零数据留存时，还要按官方[推理指南](https://developers.openai.com/api/docs/guides/reasoning#preserve-reasoning-across-calls)处理用户输入、响应输出项和加密推理项，不能假定服务器会替应用保存全部状态。

## 三、提示缓存负责复用稳定前缀

提示缓存适合重复出现的系统规则、工具定义、固定参考资料和输出合同。它优化的是相同前缀的重复处理，不判断内容是否正确或仍相关。

GPT-5.6 支持隐式自动缓存，也支持显式标记可复用前缀。官方[提示缓存指南](https://developers.openai.com/api/docs/guides/prompt-caching)及模型指南指出，缓存写入按未缓存输入费率的 1.25 倍计费，缓存读取仍有折扣。评估时要同时查看 `cached_tokens` 和 `cache_write_tokens`，不能只看到读取折扣就认定净成本下降。

适合缓存的内容有三个特征：跨请求稳定、顺序固定、复用次数足够。经常变化的用户材料、每轮更新的任务状态和只使用一次的大段上下文，不应为了命中缓存强行固定。显式模式可以控制缓存断点，`prompt_cache_options.ttl` 用于替代旧的 `prompt_cache_retention`；具体可用值和保留策略应在发布前核对当前文档。

缓存实验至少分三组：不依赖缓存的基线、隐式缓存、显式缓存。记录首个请求成本、后续命中率、写入 token、读取 token、延迟和最终任务成功。若提示频繁变化导致反复写入，显式缓存可能增加成本；如果为了保持前缀不变而保留过期规则，则会损害质量。缓存命中不是业务成功指标。

## 四、PTC 负责可预测的中间数据处理

Programmatic Tool Calling（PTC）允许 GPT-5.6 在托管环境中编写 JavaScript，调用符合条件的工具、传递结果并处理大量中间输出。它适合有边界、工具密集、处理中间数据的规则可以预测，而且不需要模型在每次调用后重新做语义判断的阶段。

典型任务包括过滤、关联、排序、去重、聚合和结构验证。例如要从多个数据源拉取记录，按 ID 关联、去重并统计异常，把所有原始结果逐批送回模型既占上下文，也增加轮次。PTC 可以让程序完成确定性处理，只返回小得多的结构化结果。

调用次数多、存在并行或依赖，并不自动构成使用 PTC 的理由。以下情况更适合直接工具调用：一次调用就能完成；中间结果本来很小；每个结果都会改变模型下一步判断；某个动作需要用户批准；最终答案必须保留原生文件或逐条引用。

路由说明要写清哪一段使用 PTC、允许调用哪些工具、输出结构、证据、并发、重试和停止条件。例如：

```text
在“汇总库存差异”阶段使用 Programmatic Tool Calling。
只允许调用 inventory_snapshot 与 shipment_records。
安全并行读取两个来源，按 sku 关联并去重。
输出 JSON：{missing_skus, quantity_mismatches, source_errors}。
每项保留 source_id；临时错误最多重试 2 次。
不得执行写入，不得重复已成功调用。
缺少必需来源时返回结构化失败，不得猜测。
最终风险判断与证据复核使用直接模型步骤完成。
```

接入时应用还要处理 `program`、程序发起的函数调用与 `program_output`，并保留 `call_id` 和 `caller` 的关联。具体请求与续接结构应以官方 [PTC 指南](https://developers.openai.com/api/docs/guides/tools-programmatic-tool-calling)为准。

## 五、多智能体只适合可独立拆分的工作流

GPT-5.6 的多智能体能力目前在 Responses API 中以 Beta 提供。它让一个实例并行协调多个子智能体并综合结果。合适的任务不是“很复杂”这么宽，而是能够拆成真正独立的工作流。

例如审查一次大型发布，可以分别检查数据库迁移、权限变化、容量风险和回滚方案。四个子任务读取相同输入，但各自有清楚的输出合同，彼此不需要等待对方的中间判断，最后再统一去重与排序。这种形态有机会减少墙上时间。

不适合并行的任务包括：后一步依赖前一步结论；多个子任务会修改同一文件；必须共享不断变化的状态；审批顺序不能打乱；拆分后的协调与重复读取成本超过节省的时间。把这些任务强行并行，容易产生相互矛盾的修改和重复证据。

每个子智能体都要限定输入、问题、输出结构、证据要求和停止条件。汇总者不能只拼接结论，应检查覆盖范围、冲突、重复和证据。由于功能仍是 Beta，生产使用还需准备降级到单智能体或普通并行调用的路线，并关注官方[多智能体指南](https://developers.openai.com/api/docs/guides/responses-multi-agent)的变化。

## 六、决策树、验收指标和失败处理

可以按下面顺序选择：

```text
问题是否来自多轮目标持续存在？
  是 -> 测试 all_turns，并验证旧推理仍相关

是否有大段稳定前缀被重复发送？
  是 -> 比较隐式与显式缓存的净成本和命中

是否有有边界、确定性的中间数据处理？
  是 -> 比较 PTC 与直接工具调用

任务能否拆成独立工作流，并行是否有价值？
  是 -> 小规模测试多智能体与降级路线

以上都不是 -> 保持直接、简单的 Responses API 工作流
```

四种机制都用同一组端到端指标验收：任务成功率、最终答案完整度、必要证据、输入与总 token、缓存写入和读取、p50/p95 延迟、调用次数、轮次、重试、失败恢复和单次成功成本。

组合使用时，日志必须能区分每一层贡献。一次请求至少记录会话或任务标识、响应 ID、有效上下文模式、缓存写入与命中、工具调用路线、子任务数量、最终验收结果和配置版本。只记录总 token 或总耗时，会让团队看到变化却找不到原因。例如延迟上升可能来自 Pro 推理、某个子任务长尾、缓存未命中，也可能来自 PTC 内部重试，处理方式完全不同。

建议按单机制、双机制逐步增加，不要第一次实验就同时开启持久推理、显式缓存、PTC 和多智能体。先验证跨轮状态，再在稳定前缀上测试缓存；工具中间输出确实成为瓶颈后才加入 PTC；独立工作流的墙上时间仍然过长，再评估并行拆分。每增加一层都保存前一层基线，并准备对应的关闭开关。

故障注入比正常请求更能检验边界。可以让一个工具返回临时错误、让一个子任务超时、让缓存前缀发生预期变化，并在后续轮次撤销早期假设。正确结果不是“系统仍然给出一段话”，而是重试没有越过上限、失败被结构化返回、旧结论不再复用、最终答案明确标出缺少的证据。只有这些行为可观察，组合机制才具备生产可维护性。

PTC 的 `program_output` 正确，不代表最终消息一定完整；多智能体的每个子结果正确，也不代表汇总没有漏项；缓存命中高，不代表提示仍然有效；跨轮回答连贯，不代表旧推理没有污染当前任务。验收必须落到最终交付物。

出现质量下降时，按机制回退：持久推理切到 `current_turn` 或新建任务；显式缓存回到隐式或不依赖缓存；PTC 回到直接调用以观察原始结果；多智能体回到单智能体串行基线。一次只撤掉一个机制，保留日志和失败样本，才能定位根因。

## 七、限制与结论

持久化推理管理跨轮相关性，提示缓存复用稳定前缀，PTC 压缩可预测的工具中间处理，多智能体并行独立工作流。它们可以组合，但没有必要因为功能存在就全部启用。

先从最简单、可观察的直接工作流建立基线，再针对明确瓶颈增加一个机制。只有最终答案继续通过质量和证据要求，较少 token、调用或墙上时间才算改进。任务形态变化后重新验证，并始终保留一条更简单的降级路线。
