# Fable 5.2 降价后每任务成本为何可能翻倍：把 effort 与缓存算进账单

Anthropic 在 2026 年 11 月 9 日发布 Fable 5.2 时，给了一个很直接的价格：每百万输入 8 美元、每百万输出 40 美元。上一代 Fable 5.1 是 10 和 50。两项都便宜了 20%，官方同时说输出速度提升最多 30%，看起来是一次标准的"加量减价"。

但第三方评测机构 Artificial Analysis 在它自己的指数任务上量到的结果不是这样：Fable 5.2 每任务 26.54 美元，Fable 5.1 是 12.99 美元，Opus 5.5 是 10.04 美元。单价降了两成，单任务成本翻了一倍。

这两个数字都成立，因为它们量的不是同一个东西。单价只决定每个 token 多少钱；账单还取决于一次任务烧多少 token、多少命中缓存、跑在哪个 effort 档、有没有开 fast mode。本文把这五个变量拆开，给出公式、三个算例和一份月度估算模板。只算钱，不评价模型能力。

## 一、把标价对齐

先列出这一版涉及的所有价格，单位是每百万 token 的美元价。

| 计费项 | Fable 5.2 | Fable 5.1 | Opus 5.5 |
| --- | --- | --- | --- |
| 输入 | $8 | $10 | $4 |
| 输出 | $40 | $50 | $20 |
| 5 分钟缓存写入 | $10 | $12.50 | $5 |
| 1 小时缓存写入 | $16 | $20 | $8 |
| 缓存读取 | $0.20 | $0.25 | $0.20 |
| Batch（五折） | $4 / $20 | $5 / $25 | $2 / $10 |
| fast mode | $16 / $80 | 不提供 | $8 / $40 |

几个容易看漏的点：

- **缓存读取的倍率是 0.025 倍**，比 Opus 5.5 和 Sonnet 5.5 的 0.05 倍更低。
- **1M 上下文按标准价计费**，没有超长上下文加价档（Haiku 5.5 过 10 万 token 会跳价）。
- **数据驻留是 1.1 倍乘数**：指定 `inference_geo: "us"` 时全部计费项乘 1.1，默认全局路由按标准价。
- **Batch 与 fast mode 不能叠加**，走批处理就没有加速通道。

## 二、缓存是这一版最值得先接的东西

缓存在这套价格里不是"打折"，而是换了一种计价方式：写入按 1.25 倍输入价收一次，之后每次命中按 0.025 倍收。所以同一段提示只要被读一次，第二次开始就划算：官方文档的结论是 5 分钟缓存一次读取即回本，1 小时缓存（2 倍写入价）需要两次。

拿 6 万 token 的固定提示算：

| 场景 | 费用 |
| --- | --- |
| 不缓存，每次全价输入 | $0.48 |
| 用 5 分钟缓存写入一次 | $0.60 |
| 用 1 小时缓存写入一次 | $0.96 |
| 之后每次命中缓存 | $0.012 |

结论很朴素：一次性请求不要开缓存，多轮会话、固定系统提示、长文档反复追问才开。1 小时缓存单价高，适合两次以上复用、但间隔超过 5 分钟的会话。

## 三、三个算例

下面的算例按标准速度、不含数据驻留乘数。输入输出比例是假设值，不表示任何真实业务的用量。

**算例 A：单轮请求，6 万输入、8 千输出。**

- Fable 5.2：6 万 × $8 + 8 千 × $40 = $0.48 + $0.32 = **$0.80**
- Fable 5.1：6 万 × $10 + 8 千 × $50 = $0.60 + $0.40 = **$1.00**

这一档确实便宜了 20%，和标价一致。

**算例 B：同样的量，但 5 万 token 是缓存命中。**

- Fable 5.2：1 万 × $8 + 5 万 × $0.20 + 8 千 × $40 = $0.08 + $0.01 + $0.32 = **$0.41**
- Fable 5.1：1 万 × $10 + 5 万 × $0.25 + 8 千 × $50 = $0.10 + $0.0125 + $0.40 = **$0.5125**

**算例 C：十轮 Agent 会话，每轮 10 万输入（其中 9 万命中缓存）、5 千输出。**

- Fable 5.2 每轮：1 万 × $8 + 9 万 × $0.20 + 5 千 × $40 = $0.08 + $0.018 + $0.20 = $0.298，十轮 **$2.98**
- Fable 5.1 每轮：1 万 × $10 + 9 万 × $0.25 + 5 千 × $50 = $0.10 + $0.0225 + $0.25 = $0.3725，十轮 **$3.725**

注意算例 C 里，输出已经占到每轮费用的三分之二。这就是下一个变量重要的原因。

## 四、effort 才是真正的乘数

Fable 5.2 的 adaptive thinking 常开、无法关闭，控制思考深度的唯一旋钮是 `output_config.effort`。五档分别是 low、medium、high、xhigh、max，**Claude API 的默认值是 high**。

这条默认值对账单的影响比单价那 20% 大得多。

最直接的原因是思考 token 按输出 token 计费——官方文档写明，推理花的 token 按输出价计费，即使思考文本没有返回给你，切换 `summarized` 与 `omitted` 也不改变计费。输出价是输入价的 5 倍，思考量翻倍时，账单增幅远大于 token 总数翻倍。

其次，effort 影响所有输出 token，不只是思考：低档位下工具调用更少、更简短，同一句请求可能少好几轮往返。

最后，思考 token 占 `max_tokens`。上限设小了，模型可能在想完之后直接以 `stop_reason: "max_tokens"` 停下，一个字都没输出：钱花了，结果没有。迁移文档专门提醒这一条：以前靠"不要思考，直接回答"压住输出的提示词，在 medium 及以上档位已经不起作用。

从 Opus 5.5 换过来的团队还要额外注意：Opus 5.5 默认 medium，Fable 5.2 默认 high。没写 `effort` 的代码换模型之后自动升一档，请求不会报错，只是每个月多花钱。

改 effort 有两个位置：请求顶层的 `output_config.effort`，和按消息的 per-message effort。前者会让提示缓存失效，后者保留缓存。长会话里要调档，用后者。

## 五、fast mode 的账要单独算

fast mode 是这一版新增支持的可选项（Opus 5.5 也提供），写法是请求里加 `speed: "fast"`，价格翻倍到 $16 / $80，换来最多 2.5 倍的输出 token 速度。

它有几个特性会直接影响核算：

- 提升的是输出 token/秒，不是首 token 时间。对"等第一个字"的交互式场景，帮助有限。
- 有独立的限速池，超出返回 429 并带 `retry-after`，与标准速度的配额不共享。
- **回落标准速度会导致缓存未命中**，因为两种速度不共享缓存前缀。所以"平时 fast、限速时自动降级"这种写法，每次降级都要重新付一次缓存写入。
- 不在 Batch 上提供，二者选一个。

同一个算例 A 走 fast mode 是 $1.60，正好是标准价的两倍。要让这笔钱花得值，得先确认瓶颈真的是生成速度，而不是排队、工具往返或者你自己的后处理。

## 六、第三方数字为什么相反

Artificial Analysis 的页面把三个模型放在同一套任务上测，都是 Max 档、都标为 "Default Fallback"：

| 模型 | 智能指数 | 每任务成本 | 评测中生成 token |
| --- | --- | --- | --- |
| Fable 5.2 | 65 | $26.54 | 275M |
| Fable 5.1 | 49 | $12.99 | 163M |
| Opus 5.5 | 59 | $10.04 | 218M |

从 5.1 到 5.2，生成 token 增长约 69%，单价下降 20%，两者相乘已经解释了大部分涨幅；剩下的部分与输入输出比例、思考占比有关，AA 没有公开逐项拆分，所以**不能**用 275M 这个总数反推单任务 token 结构。

和官方口径的差异也在这里。官方说在 FrontierCode 2.0 上，High 档的 Fable 5.2 与 Max 档的 Opus 5.5 分数接近，单任务成本约为后者一半；在 WANDR 上，Medium 档以约四成成本达到 Opus 5.5 的最高分。AA 测的则是 Max 档、它自己的任务集，得到的是相反的方向。

两个结论可以同时成立，条件不同：

- 任务在 High 或 Medium 档就能达标时，Fable 5.2 更便宜，因为它的中档能力本来就强于上一代的高档。
- 任务必须开到 Max 才能达标时，它会更贵，因为 Max 档不约束 token 消耗，而它的输出单价仍是 Opus 5.5 的两倍。

换句话说，这一版的价格优势来自"用更低的档位做同样的事"，不是"同样的档位更便宜"。核算时必须把 effort 写进假设。

## 七、一份月度估算模板

把上面几节合成一个公式，按请求粒度算，再乘次数：

```
单次成本 = (未缓存输入 × P_in
         + 缓存读取 × P_read
         + 5m 写入 × P_w5
         + 1h 写入 × P_w1h
         + 输出（含思考）× P_out) / 1,000,000
```

`P_in`、`P_out` 等取第一节表里的值；开 fast mode 时换成 $16 / $80，走 Batch 时换成 $4 / $20；要 US 数据驻留就整体乘 1.1。输出要记得包含思考 token，计费口径里它是输出的一部分。

落到月度估算，需要四个输入：

| 输入项 | 从哪来 | 常见偏差 |
| --- | --- | --- |
| 每月请求数 | 现有监控 | 重试与回落请求也算，容易漏 |
| 每次的平均输入输出 | 响应里的 `usage` 对象 | 只统计成功请求，被拒的也可能计费 |
| 缓存命中比例 | `cache_read_input_tokens` / 总输入 | 把写入当成命中 |
| effort 分布 | 请求日志里的 `output_config.effort` | 假设全部默认，但默认已经变了 |

按算例 A 的量级，每 1000 次请求在 Fable 5.2 上是 $800，在 Fable 5.1 上是 $1000。这个线性关系只在"档位相同、缓存比例相同"时成立；一旦 effort 分布变化，两点之间就不再是直线。

还有两个计费细节：被分类器拦下的请求返回 HTTP 200 加 `stop_reason: "refusal"`，是否计费取决于拒绝类别，但照样占限速配额；服务端回落会让新模型重读上下文，那一轮按新模型算。

## 八、如果你通过兼容层调用

很多团队不是直连官方端点，而是走兼容 OpenAI 协议的聚合网关。以 4SAPI 这类中转网关为例，它对外提供 OpenAI 兼容接口，返回的 `usage` 是 `prompt_tokens`、`completion_tokens` 这一套字段，而 Anthropic 原生响应给的是 `input_tokens`、`output_tokens`、`cache_creation_input_tokens`、`cache_read_input_tokens`，fast mode 还会多一个 `speed` 字段。

做成本核算前，先拿一次真实响应确认三件事：缓存命中数有没有透出、思考 token 是否被算进 `completion_tokens`、`usage.speed` 是否保留。这三项缺任何一项，按上面公式算出来的数都会偏低，而且偏得很隐蔽——请求本身完全正常。

## 九、限制与结论

一句话总结：标价比上一代低 20%、缓存命中价更低，但默认 effort 更高、思考量更大，单任务成本完全可能反而上升。单价是常量，token 量是变量，账单是两者的乘积。

三条可以直接用的判断：

- 短请求、固定提示、每次几千 token 输出，换到这一版大概率省钱，幅度接近 20%。
- 长会话 Agent 先在 high 档实测 token 用量，再决定要不要上 xhigh；不要拿 5.1 的设置直接搬。
- 开 fast mode 时把"降级导致缓存未命中"算进去，否则加速的收益会被缓存重写吃掉一部分。

最后提醒：本文算例都是假设值。真实预算应该来自你自己日志里的 `usage` 统计，尤其 effort 分布和缓存命中率——它们对结果的影响比价格表上那 20% 大一个量级。
