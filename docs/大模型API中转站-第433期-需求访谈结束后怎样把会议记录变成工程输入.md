# 需求访谈结束后，怎样把会议记录变成工程输入

客户说“这个工具不好用”，管理者可能在说投入没有产生结果，一线员工可能在说每天多了一次复制粘贴，技术团队则可能担心故障和维护成本。三句话在会议纪要里都可以被缩成“现有工具体验较差”，工程团队却无法据此决定改哪里、由谁确认、完成后怎样验证。

需求访谈的产出不是一份更整齐的逐字稿，而是一组可以追溯、确认和执行的工程输入。本文给出从访谈准备、现场追问到会后整理的完整方法，并提供一套 Markdown 项目记忆模板。AI 可以参与提取和比较，但不能替有权的人确认事实与决定。

## 一、先追过程，不要急着收功能清单

客户通常更容易说出想买什么，而不是问题怎样发生。“做一个 AI 客服”可能对应三种不同问题：客服重复回答相同问题，新制度发布后知识更新太慢，或者用户根本找不到正确入口。

三个问题都能做成聊天窗口，数据来源、权限风险和验收方式却完全不同。访谈需要从功能名退回最近一次真实任务：

```text
谁在什么时候收到什么输入？
他打开了哪个系统？
根据什么信息作判断？
正常结果写到哪里？
遇到例外会找谁？
哪一步最常等待、返工或出错？
```

最好让受访者直接描述“上一次是怎么做的”。标准流程说明应该怎样工作，最近一次任务更容易暴露实际入口、临时表格、群聊确认和人工绕路。

## 二、同一个问题至少要听三种角色

企业流程很少由一个人完整掌握。只访谈管理者，容易得到目标和制度；只访谈一线员工，容易看到操作细节，却不一定知道预算和风险边界；只访谈技术团队，可能把现有系统限制误当成业务规则。

至少要区分三类视角：

| 角色 | 重点追问 | 容易漏掉的内容 |
| --- | --- | --- |
| 管理者 | 为什么现在要改、谁对结果负责、错误代价是什么 | 实际操作中的绕路与额外负担 |
| 一线用户 | 最近一次怎样完成、哪里等待、遇到例外怎么办 | 权限、系统维护和组织决策 |
| 技术团队 | 数据在哪里、接口怎样接、谁维护、怎样发布 | 用户为什么不用、业务上什么叫答对 |

访谈不是用多数票决定事实。不同角色说法不一致时，应把冲突原样保留，并找到有权确认的人。例如，一线员工说库存实时更新，系统负责人说每天同步一次，这不是文案差异，而是会改变方案的工程条件。

## 三、把会议内容拆成五类

会议结束后，先不要直接生成需求文档。把内容拆成事实、判断、假设、决定和待确认项，工程团队才能知道哪些可以依赖，哪些需要验证。

### 1. 事实

事实是有来源、可核对的当前状态。例如“客服在发送回复前需要主管审批”，需要同时记录是谁说明、依据是什么、何时确认。

### 2. 判断

判断是某个角色对现状的解释，例如“主管认为主要问题是知识更新慢”。判断有价值，但不能自动写成所有人的共同结论。

### 3. 假设

假设是尚未验证、但会影响方案的条件，例如“CRM 接口支持目标写入频率”或“扫描 PDF 可以保留表格结构”。假设应该进入验证清单，而不是悄悄变成架构前提。

### 4. 决定

决定是有权的人已经确认的范围、责任或技术选择。例如“第一阶段只生成回复草稿，不自动发送”。决定需要记录确认人、日期和适用条件。

### 5. 待确认项

待确认项是当前无法归类为可靠输入的问题。它必须有负责人和截止时间；否则，“后续确认”很容易在开发过程中被当作默认成立。

可以使用下面的最小表格：

| ID | 类型 | 内容 | 来源 | 状态 | 确认人或负责人 | 截止时间 |
| --- | --- | --- | --- | --- | --- | --- |
| F-01 | 事实 | 当前审批发生在发送前 | 访谈记录 A | 已确认 | 业务负责人 | - |
| H-01 | 假设 | 接口支持所需写入频率 | 技术访谈 B | 待验证 | 系统负责人 | 日期待填 |
| D-01 | 决定 | 第一阶段不自动发送 | 范围评审 C | 生效 | 项目负责人 | - |

表格中的内容只是格式示例，不代表任何真实项目事实。

## 四、把口头描述画成一张可走查的工作图

分类解决“这句话是什么”，流程图解决“工作怎样发生”。一张可用于工程设计的工作图，至少要包含六个要素：角色、触发条件、输入、动作或判断、输出、异常路径。

以“AI 客服”为例，可以先画成文字流程：

```text
用户提交问题
  -> 工单系统完成分类
  -> 客服查看客户与订单上下文
  -> 查找当前有效的政策
  -> 起草回复
  -> 高风险问题交主管确认
  -> 客服发送并记录结果

异常：资料冲突 / 客户身份不明 / 订单数据过期
  -> 暂停生成或转人工处理
```

然后逐步标注系统与责任：工单分类由哪套系统完成，政策的有效版本由谁维护，哪些客户资料当前用户有权查看，主管审批的结果写回哪里。

验证方式是让实际执行这项工作的人沿着图走一遍最近一次任务。只要他说“这里实际不是这样”，就回到原始记录修改，并保留变更来源。流程图通过走查以后，才适合作为接口、权限和页面设计的输入。

## 五、把项目记忆放进可审计的 Markdown 文件

聊天记录和会议录像适合保留原始材料，不适合充当当前决定。项目推进几周后，如果范围、风险和负责人仍散落在群聊里，团队很难判断哪个版本有效。

一种轻量做法是把原始材料与正式项目记忆分开：

```text
project-memory/
  raw/
    2026-08-10-interview-notes.md
  current/
    workflow.md
    decisions.md
    assumptions.md
    risks.md
    owners.md
```

日期和文件名仅为结构示例。`raw/` 保存访谈记录、来源和未经确认的材料；`current/` 只保存已经分类、标明状态的当前信息。原始文件不覆盖修改，正式文件中的每一项都能回到来源。

决定记录可以使用下面的格式：

```markdown
## D-007 第一阶段只生成草稿

- 状态：已确认
- 决定：系统生成回复草稿，由客服确认后发送
- 原因：当前阶段需要保留人工复核
- 不包含：自动退款、自动修改订单、自动发送
- 确认人：业务负责人
- 来源：范围评审记录
- 生效日期：待填写
- 复核条件：进入下一阶段前重新评估
```

这类文件给团队提供了一个当前有效、可追溯的控制面。“让 AI 记住所有事”解决不了责任归属，AI 在这里主要用于加快检索和比较。

## 六、AI 适合做第一轮提取，不适合替人确认

访谈材料较多时，AI 可以参与四项工作：准备角色化问题、从记录中提取五类信息、比较不同角色的说法、为待确认项生成初步清单。

输入 AI 前，应先按项目要求处理个人信息、商业秘密和访问权限。输出以后还要做三项检查：

1. 每条事实能否定位到原始材料，而不是模型补出的常识。
2. 模型有没有把个人判断写成组织决定。
3. 否定、限制、时间和责任人有没有被遗漏。

AI 只能提出对 `current/` 文件的更新建议。事实、决定、风险和负责人正式生效前，应由对应的有权人员确认。模型生成一句“审批已通过”，不构成任何审批证据。

## 七、会后 24 小时内完成一次确认回路

时间越久，参与者越容易用自己的记忆补全会议。会后可以按下面的顺序收口：

1. 保存原始记录，标明时间、参与者和材料来源。
2. 提取事实、判断、假设、决定和待确认项。
3. 更新工作图，标出系统、角色与异常路径。
4. 把冲突和缺口分配给具体负责人。
5. 请有权人员只确认与自己相关的内容。
6. 将确认结果写回正式项目记忆，保留变更记录。

“24 小时”是工作节奏建议，不是适用于所有团队的硬性标准。如果项目有法务审阅、跨时区协作或正式纪要流程，应以组织要求为准。关键是尽快完成来源、状态和责任人的确认，不让未确认信息进入开发。

## 八、怎样判断会议内容已经能进入工程阶段

可以做一次反向检查：工程师没有参加会议，只阅读工作图、五类记录和当前决定，能否回答下面的问题？

```text
系统准备改变哪一步？
真实输入从哪里来？
哪些规则已经确认？
哪些条件仍是假设？
谁可以查看和执行？
发生例外时交给谁？
什么结果算完成？
```

如果答案仍依赖“大家都知道”或“到时候再问”，会议内容还没有变成工程输入。继续开发只会把这些空白固化进代码。

需求访谈的质量不取决于会议开了多久，而取决于会后留下了什么：一张能被真实用户走通的工作图，一组有来源和状态的信息，以及由具体人员确认的决定与风险。做到这一步，沟通才真正进入工程。

## 九、用一个客服场景走完整个转换过程

下面用一个假设的客服回复助手说明转换过程。案例中的角色和内容只用于展示方法，不代表真实客户项目。

访谈中出现了四句话：

```text
客服：查政策太慢，经常要去群里问主管。
主管：大部分问题系统应该可以直接回答。
技术负责人：知识文件每天夜间同步一次。
项目发起人：第一阶段先提高回复效率，不改现有审批。
```

如果把它们直接压成“建设智能客服，提高政策查询效率”，工程信息几乎全部丢失。按五类记录拆开后，可以得到：

| ID | 类型 | 内容 | 还需要什么 |
| --- | --- | --- | --- |
| F-01 | 事实候选 | 客服当前会在群里向主管确认政策 | 用最近工单和一线走查确认 |
| J-01 | 判断 | 主管认为多数问题可以直接回答 | 需要样本分布和风险边界 |
| F-02 | 事实候选 | 知识文件每天夜间同步 | 由系统 Owner 确认同步范围和失败处理 |
| D-01 | 决定 | 第一阶段不改变现有审批 | 由业务负责人确认并写入范围 |

接着把它们放回工作图：工单进入以后，客服先看客户上下文，再搜索政策；不确定时在群里找主管；回复仍要按原审批流程发送。此时可以看出，第一阶段适合改变“查找资料并起草”这一步，群聊确认和正式审批不能被一句“智能回答”直接跳过。

### 从话语到接口条件

“每天夜间同步一次”会继续拆成工程问题：同步成功的时间在哪里记录，失败是否告警，白天更新的政策何时可见，界面是否要显示知识时间。没有这些信息，用户可能把昨天的数据当成当前状态。

### 从角色判断到评测问题

“大部分问题可以直接回答”不能直接成为需求。团队需要从真实工单中抽取经过授权和脱敏的样本，区分普通咨询、资料冲突、权限受限和必须转主管的情况。评测结果再用于判断哪些类别可以生成草稿，哪些类别应该停止。

### 从项目愿望到范围决定

“提高回复效率”需要落到可观察环节。当前等待究竟发生在找资料、写回复还是等审批？如果主要等待来自审批，生成速度变快也未必改变整体处理时间。工作图和基线观察要先找到真正的等待点。

走完这一步，工程团队拿到的已经不再是四句话，而是一组有来源的流程事实、待验证假设、范围决定和评测问题。

## 十、从工程输入继续拆到任务与验收

工程输入确认后，还要转换成可以排期和验收的工作项。每个任务至少关联一个来源、一个负责人和一种完成证据。

| 工程输入 | 可执行任务 | 完成证据 |
| --- | --- | --- |
| 政策资料夜间同步 | 记录同步时间并暴露给查询层 | 固定样本显示正确知识时间 |
| 资料可能存在版本冲突 | 增加版本过滤和冲突分支 | 冲突样本不会直接生成确定答案 |
| 第一阶段保留审批 | 回复只保存为草稿 | 未确认草稿不能进入发送状态 |
| 权限边界待确认 | 建立角色访问测试 | 不同角色只能检索授权资料 |
| 群聊承担异常确认 | 设计明确的转主管状态 | 异常任务可以被主管接收和回写 |

这种拆法可以避免“做知识库”“接模型”“开发管理后台”一类过宽任务。任务名称应该说明要改变或验证什么，完成证据则说明怎样判断它真的完成。

工程实现中如果发现新事实，例如接口没有预期字段，不能只在代码里绕过去。它需要回到假设或风险记录，由系统负责人和业务负责人判断是换接口、改范围还是调整验收。

### 建立需求到证据的追踪关系

可以给事实、假设、决定、任务和测试分别使用稳定 ID：

```text
F-03 资料每天夜间同步
H-04 同步状态可通过接口读取
D-02 第一阶段显示知识更新时间
TASK-12 接入同步状态字段
TEST-08 模拟同步失败并检查页面提示
```

编号只是检索手段，不要求引入复杂的需求管理系统。关键是测试失败时能够回到原假设，范围变化时能够看出影响哪些任务。

## 十一、五个常见误区

### 1. 把会议总结当作需求确认

一份流畅的总结可能同时混有事实和建议。只有对应角色确认的内容才能进入当前决定。

### 2. 用 AI 自动补齐缺失字段

负责人、日期和系统条件缺失时，应写“待确认”。自动补齐会让文档完整，却让责任链失真。

### 3. 只确认正常流程

企业系统的边界常常藏在例外里。资料冲突、审批人不在、接口超时、用户无权访问，都要进入工作图。

### 4. 所有人一起确认整份文档

整份文档群发后很容易得到模糊的“没问题”。更有效的做法是让业务、用户、数据和技术角色分别确认自己负责的段落。

### 5. 范围变化后不更新项目记忆

聊天里同意缩小范围，正式文件仍保留旧版本，后续开发和验收就会各自引用不同依据。任何生效变更都要同步更新决定、任务和测试。
