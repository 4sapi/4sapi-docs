# AI Coding 第三个项目做什么：从单页网页到带登录的小产品

做完计算器或个人介绍页后，很多新手会想直接挑战一个完整平台。

这时最容易踩坑：页面能登录，但数据没有真正保存；用户 A 能看到用户 B 的记录；数据库密码被写进前端；删除按钮看起来成功，数据却仍然留在后台。

从网页到小产品，真正增加的不是几个页面，而是数据、身份、权限和错误处理。

## 一、先选一条完整流程

适合新手的项目包括：

- 客户需求收集器；
- 读书记录工具；
- 带登录的待办事项；
- 简单个人 CRM；
- 私人记账或库存记录工具。

项目只需要跑通一条主流程：

~~~text
用户登录
-> 创建一条数据
-> 保存数据
-> 查看列表
-> 编辑数据
-> 删除数据
-> 处理错误
~~~

不要一开始加入团队协作、复杂权限、支付和实时同步。

## 二、先区分认证和授权

认证解决“你是谁”。

授权解决“你能做什么”。

登录成功，只能证明当前用户是用户 A。

系统还必须判断：用户 A 是否有权读取、修改或删除这条数据。

如果只在前端隐藏按钮，而后端接口不检查权限，用户仍可能通过修改请求参数访问其他人的数据。

## 三、先写产品边界

在让 AI 写代码之前，先写：

~~~text
目标用户：
核心问题：
核心流程：
必须包含：
明确不做：
保存哪些数据：
如何判断完成：
~~~

例如客户需求收集器的第一版可以是：

- 用户注册并登录；
- 创建客户需求；
- 查看自己的需求列表；
- 编辑和删除自己的记录；
- 管理员功能暂不包含；
- 不处理支付和文件上传。

边界越清楚，越不容易让 AI 顺手生成一套你无法验收的系统。

## 四、设计最小数据结构

一张需求表可以先包含：

| 字段 | 说明 |
| --- | --- |
| id | 记录唯一标识 |
| user_id | 所属用户 |
| title | 需求标题 |
| description | 需求描述 |
| status | 当前状态 |
| created_at | 创建时间 |
| updated_at | 更新时间 |

user_id 是权限判断的重要依据。

如果记录没有明确所属用户，后续很难保证数据隔离。

## 五、让 AI 先给方案

可以使用这样的提示：

~~~text
请先不要写代码。
根据以下需求，给出最小数据模型、页面、接口和权限检查点。
请明确：
1. 哪些数据属于用户；
2. 哪些操作需要登录；
3. 哪些操作需要服务端授权；
4. 失败时返回什么；
5. 第一版明确不做什么。
~~~

先审阅方案，再逐步实现。

## 六、数据库不等于自动安全

把数据存进数据库，只解决了长期保存的一部分问题。

你仍然需要检查：

- 查询是否带有当前用户条件；
- 更新是否验证记录归属；
- 删除是否验证记录归属；
- 用户输入是否经过校验；
- 错误信息是否泄露内部细节。

数据库能保存数据，但不会自动替你设计权限。

## 七、前端不要放秘密

数据库密码、支付密钥和服务端 API Key 不能写在公开前端代码里。

前端代码会发送到用户浏览器，任何用户都可能查看。

敏感配置应放在服务端环境变量中，并使用 .env.example 记录变量名称和用途，不放真实值。

## 八、创建流程要验证输入

创建表单至少检查：

- 必填字段是否为空；
- 字符长度是否合理；
- 枚举状态是否在允许范围；
- 字段类型是否正确；
- 用户是否有权限创建。

前端校验可以改善体验，但服务端校验不能省略。

用户可以绕过浏览器直接发送请求。

## 九、列表查询要验证归属

最危险的测试之一，是准备两个用户：

~~~text
用户 A 创建记录 A。
用户 B 创建记录 B。
用户 A 查看列表。
预期：只看到记录 A。
用户 B 查看列表。
预期：只看到记录 B。
~~~

不要只看页面显示。

还要检查接口响应和数据库查询条件。

## 十、编辑和删除要单独测试

很多项目只在列表接口里做了用户过滤，编辑和删除接口却直接按 id 操作。

测试时让用户 A 尝试修改或删除用户 B 的记录，预期应该是拒绝并留下可观察的错误结果。

这是授权测试，不是页面测试。

## 十一、错误状态必须可见

真实产品至少要处理：

- 加载中；
- 没有数据；
- 保存成功；
- 保存失败；
- 网络超时；
- 未登录；
- 没有权限；
- 记录不存在。

如果所有失败都只显示“出错了”，用户和开发者都很难判断下一步。

## 十二、登录流程不要只测成功

登录测试还包括：

- 错误密码；
- 不存在的账号；
- 空输入；
- 过期会话；
- 退出后返回受保护页面；
- 未登录访问接口。

每种情况都应该有明确结果。

## 十三、先做本地和测试环境

不要第一次就把真实客户数据交给新生成的系统。

先使用假数据和测试账号，确认：

- 数据是否保存；
- 用户之间是否隔离；
- 删除是否符合预期；
- 错误日志是否可读；
- 数据库能否备份和恢复。

## 十四、上线前安全清单

~~~text
登录和退出是否正常
服务端是否检查授权
用户 A 是否能访问用户 B 的数据
密钥是否只在服务端
输入是否经过校验
错误信息是否泄露路径或数据库细节
依赖来源和版本是否明确
数据库是否有备份
部署失败是否能回滚
~~~

如果某项无法确认，就标记为“需要人工验证”，不要写成“已经安全”。

## 十五、保留项目文档

每个小产品至少保留：

- README：如何启动；
- PRODUCT：用户、目标和边界；
- ARCHITECTURE：页面、数据和服务如何连接；
- .env.example：环境变量名称；
- KNOWN-ISSUES：已知问题；
- CHANGELOG：重要修改。

这些文件能帮助你和 AI 共享同一份项目背景。

## 十六、结论

从单页网页升级到带登录的小产品，关键不是多写几个页面，而是建立数据保存、身份识别、权限判断和错误处理的完整闭环。

认证解决“你是谁”，授权解决“你能做什么”。

只要涉及用户数据，就要用服务端规则、测试账号和明确的验收步骤验证隔离效果。

AI 可以帮你生成页面、接口和测试，但不能替你确认数据是否安全，更不能把未验证的 Demo 直接当成生产系统。
