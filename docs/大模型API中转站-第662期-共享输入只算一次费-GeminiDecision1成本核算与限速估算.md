# 共享输入只算一次费：Gemini Decision 1 成本核算与限速估算

Gemini Decision 1 的价格表只有一行有效内容：每百万输入 token 0.10 美元，输出 0 元。相对于同门 Gemini 3.5 Flash-Lite 的 0.30 输入、2.50 输出，这个数字看起来便宜了一个量级。

但"0 输出"掩盖了两件事：它按输入计价，而输入是重复的、并且**没有缓存**；它没有 Batch API，也买不到 Priority 推理，所有流量走在线路径。这两条决定账单与吞吐的真实形态。

本文只做三件事：把计费规则讲清、给出可复算的对照算例、算清限速下的吞吐上限。接口结构与阈值设置分别在前面两篇，这里不重复。

价格为 2026-11-12 检索到的官方页面所载，美元计价。

## 一、计费规则：一次共享输入 + 每个问题的附加量

官方定价页对这一段的描述只有两句，但两句都是关键：

- 每次请求对共享输入计费一次，与问题数量无关；
- 每个问题追加自己的 `instructions`、`criteria` 与格式化 token。

合起来看，单次请求的输入 token 量可以写成：

```
总输入 token ≈ 共享输入 token + Σ(每个问题的 instructions + criteria + 格式化 token)
```

响应里的 `usage` 会把这件事摊开：`total_input_tokens`、按模态的 `input_tokens_by_modality`（视频帧与 PDF 页按图像 token 计）、`total_output_tokens` 恒为 0。核对账单的第一步就是拿这三个字段和估算对齐。

几件它明确不支持的事，直接影响成本模型：

| 能力 | 状态 | 对成本的影响 |
| --- | --- | --- |
| 上下文缓存 | 不支持 | 重复的长输入每次按全价重算 |
| Batch API | 不支持 | 拿不到批处理的折扣档 |
| Flex / Priority 推理 | 不支持 | 无法用"慢一点更便宜"或"贵一点更快"来调 |
| 输出 token | 恒为 0 | 计费只跟输入走，不跟回答长度走 |

第四条是它最直观的优势：判断类任务的成本不随"想得多久"波动。你不必担心某条请求突然输出三千 token 把预算吃掉。

## 二、单位价格对照

| 模型 | 输入（每百万 token） | 输出（每百万 token） | 缓存 | Batch |
| --- | --- | --- | --- | --- |
| Gemini Decision 1 | $0.10 | $0（不产生输出） | 不支持 | 不支持 |
| Gemini 3.5 Flash-Lite | $0.30 | $2.50（含思考 token） | 付费档支持，页面标注缓存价 $0.03 / 百万 token，存储 $1.00 / 百万 token / 小时 | 支持 |

这张表已经能看出两边的差异结构：Decision 1 便宜在输入，赢在输出；Flash-Lite 贵在输出，但可以用缓存把重复输入压下来，还能走 Batch 折扣。

**光看单价对比不足以判断谁更省，因为它们的成本曲线形状不同。** Decision 1 的成本只与输入量线性相关；Flash-Lite 的成本里有一块跟输出长度相关，且可以用缓存把它的一部分输入变成缓存命中。

## 三、两个可复算的算例

下面两个算例都是假设值，用来演示算法，不对应任何真实业务的用量。

**算例 A：一条工单、10 个判断，与一次 JSON 生成对比。**

Decision 1 侧：共享输入 4,000 token，10 个问题的 instructions 与 criteria 合计约 500 token（每问 50 token 量级）。

- 总输入 4,500 token → 4,500 × $0.10 / 1,000,000 = **$0.00045**

Flash-Lite 侧：同一段 4,000 token 输入，让模型输出一份含三个字段的 JSON，约 300 token（含思考则更多）。

- 输入 4,000 × $0.30 / 1,000,000 = $0.0012
- 输出 300 × $2.50 / 1,000,000 = $0.00075
- 合计 **$0.00195**

比值约 4.3 倍。这和官方发布稿的说法方向一致——发布稿称在共享基准集上比"Gemini 3.5 Flash-Lite + Interactions API"便宜近 5 倍。但那个倍数没有公开基准集构成、每题 token 量与被比较的具体配置，只能当作厂商口径；上面这个 4.3 倍来自本文的假设，换成别的输入输出比例会得出别的数。

**算例 B：同一份 10 万 token 文档，一天问 1,000 次。**

Decision 1 侧没有缓存，每次全价。

- 每次 100,000 × $0.10 / 1,000,000 = $0.01
- 每天 1,000 次 = **$10**

Flash-Lite 侧：假设启用缓存且命中，按页面标注的缓存价与存储价估算。

- 缓存读取 100,000 × $0.03 / 1,000,000 = $0.003 /次 → 每天 1,000 次 = $3
- 存储 100,000 token 约合 0.1 个"百万 token 单位"，按 $1.00 / 百万 token / 小时算，约 $0.10/小时；一天 24 小时约 $2.4
- 输出按每次 300 token 计：1,000 次 × 300 × $2.50 / 1,000,000 = $0.75
- 合计约 **$6.15 / 天**

结论是方向性的，也很容易被忽略：**当共享输入被高频重复时，"没有缓存"这一条会把 Decision 1 的唯一价格优势吃掉一部分**。上例里它仍然略便宜，但差距从"4 倍多"缩到了"不到 2 倍"，而且这个结论对输入长度极其敏感——输入越短、重复越少，Decision 1 越占优。

存储费按小时计，所以"缓存常挂"和"用一次建一次"是两种成本；调用若零星爆发，缓存可能没被复用几次，反倒要付存储。

## 四、媒体输入会改变量级

Decision 1 的共享输入支持图片、音频、视频和 PDF。文档说明：视频帧与 PDF 页在 `usage` 里按图像 token 计。

这意味着两个变量的乘积决定账单：

- **内容量**：多少帧、多少页、多少秒音频；
- **分辨率档位**：图像与视频块可以设 `low`、`medium`、`high`、`ultra_high`，用来在"看得清"和"花得少"之间取舍；音频与文档块不使用这个设置。

具体的每档 token 换算没有出现在本次核对的页面里，文档指向单独的 media resolution 页。**因此本文不给"一张图等于多少 token"的数字**，那需要按官方那页的分辨率表逐档核对。可控的做法是：先用最低档跑一遍自己的判断任务，看准确率是否够；不够再逐档往上试，同时记录 `input_tokens_by_modality` 的变化。

对视频尤其要小心：一次请求里放一段长视频，帧数会随长度线性增长，而预算里原本按"几百 token 文本"做的估算会瞬间失效。

## 五、限速才是吞吐的真瓶颈

定价页写的"每百万 0.10 美元"很容易让人以为成本是唯一约束。实际先撞上的通常是 TPM。

| 档位 | RPM | TPM | RPD |
| --- | --- | --- | --- |
| Free | 200 | 50,000 | 10,000 |
| Tier 1 | 1,500 | 1,000,000 | 50,000 |
| Tier 2 | 5,000 | 4,000,000 | 不限 |
| Tier 3 | 15,000 | 10,000,000 | 不限 |

拿算例 A 的 4,500 token/请求去算：

- 免费档：50,000 / 4,500 ≈ 每分钟 11 个请求，远低于 200 RPM；TPM 先到顶，实际可用的 RPM 只有名义值的 5%。
- Tier 1：1,000,000 / 4,500 ≈ 每分钟 222 个请求，仍然是 TPM 先绑；RPM 的 1,500 用不满。
- Tier 3：10,000,000 / 4,500 ≈ 每分钟 2,222 个请求，依旧低于 15,000 RPM。

也就是说，在 4.5K token 这个量级上，**四档里的每分钟上限都由 TPM 决定，RPM 那条线一直是富余的**。只有当单次请求的 token 量足够小（比如几百 token 的短文本 + 少量问题）时，RPM 才会先到顶。

这套 API 没有 Batch，也没有 Priority，所以没有"错峰跑"或"加钱提速"的调节旋钮。容量规划只能落在三件事上：压缩共享输入、拆小请求、或申请更高档位。

## 六、如果你的调用经过聚合网关

很多团队不是直连供应商端点，而是把多个模型放在一个兼容层后面统一调用。以 4SAPI 这类 OpenAI 兼容中转网关为例，它对外暴露的是 `/chat/completions` 这类兼容路径，而 Decisions API 走的是 `/v1beta/decisions` 这个独立端点、返回的是概率而不是消息体——这类非 OpenAI 协议的新接口通常不在兼容层的覆写范围内。

这带来两个纯运维的后果：一是这条调用需要直连 Gemini 端点、单独持有一个密钥；二是它不会出现在网关的用量统计里，预算要分两处核算，否则月度对不上账。在决定接入前先用一条真实请求确认路径是否被转发，比事后查账便宜。

## 七、一份月度估算模板

把上面的规则合成一个公式：

```
单次成本 = (共享输入 token + Σ每个问题的附加 token) × P_in / 1,000,000
P_in = 0.10（Decision 1）
```

没有输出项，没有缓存折扣，没有批量折扣，因此这个公式就是全部，不需要额外的修正系数。

落到月度估算，需要四个输入：

| 输入项 | 从哪来 | 常见偏差 |
| --- | --- | --- |
| 每月请求数 | 现有监控 | 重试请求也算，容易被漏掉 |
| 每次共享输入 token | `usage.total_input_tokens` | 只按文本估，忘了媒体块 |
| 每次的问题附加 token | 各问题 criteria 长度求和 | 选项描述写长会明显抬高 |
| 失败与重试率 | 客户端日志 | 安全拦截返回 400 时是否计费未核验 |

最后一行必须注明：本次核对的定价页没有说明被安全过滤拦下的请求是否计费。要确认这件事，只能用自己的账号做一次真实请求并核对用量。

按算例 A 的量级，每 1,000 次请求的成本是 $0.45；100 万次是 $450。这个线性关系只在"共享输入与问题数不变"时成立——问题是，问题数最容易在项目推进中被悄悄加码：从 3 条规则加到 20 条，附加 token 可能翻几倍，而共享输入那一块完全没变。

## 八、三个容易算错的细节

- **不要用生成式的 token 经验来估它。** 判断类任务不需要输出解释，也没有思考 token；用"一问一答大约 500 token"的经验值来套，会严重高估。
- **不要把"0 输出"当成"0 边际成本"。** 多问一个问题的边际成本等于那个问题的 instructions + criteria token × $0.10/百万。加得足够多，它同样会上账单。
- **不要忽略重建成本。** 没有缓存意味着"改一次 criteria 就要全量重跑"是常态。评估阶段的调用量往往比线上还大，这部分也要计入预算。

## 九、限制与结论

Gemini Decision 1 的成本结构非常单一：只按输入计价，没有输出、没有缓存、没有批量折扣。这种单一性既是优点（可预测）也是限制（没有优化空间）。

三条可以直接用的判断：

- 短输入 + 多问题：它的单价优势最明显，因为共享输入只算一次。
- 长输入 + 高频重复：先算缓存那一侧的成本，"没有缓存"这一条可能把差距吃掉大半。
- 有媒体：先把分辨率档位调到最低跑一遍准确率，再决定要不要往上加；每档的具体 token 换算要回到官方分辨率表。

最后一条要提醒的是吞吐而非成本：四档限速里 TPM 几乎总是先到顶，所以"能不能跑得动"取决于单次请求的大小，而不是你买了哪一档。
