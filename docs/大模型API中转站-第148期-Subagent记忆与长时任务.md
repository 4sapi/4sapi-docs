# 【大模型API中转站】第148期 Subagent与记忆 | 长任务少断片

本文是【大模型API中转站】系列的第148篇。本系列致力于用最低的成本、最清晰的方法，帮你打通多模型API的任督二脉。建议先收藏，随用随查。

前两篇讲了 Agent 的基本循环、MCP、Context Engineering 和 Harness。

这一篇进入更容易被高估、但也确实有价值的一层：

```text
Subagent。
Multi-Agent。
Memory。
长时任务。
```

先说结论：

```text
多 Agent 不是把一群模型放在一起聊天。
真正能落地的多 Agent，是任务拆分、权限隔离、并行执行和结果验收。
```

很多团队第一次做多 Agent，会设计成这样：

```text
一个产品经理 Agent。
一个架构师 Agent。
一个程序员 Agent。
一个测试 Agent。
一个老板 Agent。
大家一起开会。
```

看起来很像公司。

但生产里不一定好用。

因为 Agent 不怕“角色不够多”，怕的是：

```text
任务边界不清。
上下文互相污染。
谁都能调高价模型。
谁都能用危险工具。
失败以后没人验收。
日志里看不出哪一步烧钱。
```

所以企业做 Subagent，重点不是拟人化，而是工程化。

## 1. Subagent 的价值：把上下文拆开

单 Agent 的问题，是所有东西都堆在一个上下文里。

需求、代码、日志、搜索结果、执行计划、失败记录、用户补充，全塞进去。

跑几轮之后，模型就容易乱：

```text
忘了最初目标。
误把旧错误当新错误。
重复尝试已经失败的方案。
把不相关文件也改了。
不知道什么时候该停。
```

Subagent 的第一价值，是把任务拆成独立上下文。

例如一个代码任务：

```text
主 Agent：负责理解需求、分配任务、汇总结论。
搜索 Subagent：只负责找相关文件。
实现 Subagent：只负责改指定文件。
测试 Subagent：只负责跑命令和读失败日志。
Review Subagent：只负责找风险和回归问题。
```

每个 Subagent 看到的内容更少，任务更窄，工具更少。

这比把所有能力交给一个大模型更稳。

可以用一张表理解：

| 角色 | 只看什么 | 只做什么 | 不允许做什么 |
| --- | --- | --- | --- |
| Planner | 用户需求、项目规则 | 拆任务、定验收 | 改文件、发请求 |
| Researcher | 文档、搜索、只读仓库 | 找资料、定位文件 | 写代码 |
| Worker | 指定文件、具体任务 | 实现改动 | 改无关模块 |
| Tester | 测试命令、日志 | 验证结果 | 修改业务逻辑 |
| Reviewer | diff、需求、风险清单 | 审查问题 | 自动合并 |

这才是 Subagent 的正确打开方式。

不是“角色扮演”。

是“最小上下文 + 最小权限 + 明确产物”。

## 2. 主从结构比群聊结构更可靠

多 Agent 有很多玩法。

最适合企业落地的，通常不是“大家互相讨论”，而是主从结构：

```text
主 Agent
  -> 分配任务给 Subagent A
  -> 分配任务给 Subagent B
  -> 分配任务给 Subagent C
  -> 收集结果
  -> 判断是否继续
  -> 输出最终结论
```

原因很简单：

```text
群聊结构容易发散。
主从结构容易收敛。
```

企业任务需要的不是热闹，而是交付。

主 Agent 要负责四件事：

```text
拆任务。
给边界。
收结果。
做最终判断。
```

Subagent 要负责一件事：

```text
把自己那一小块干清楚。
```

比如一个 PR Review 任务可以这样拆：

```text
主 Agent：读取 PR 描述和 diff，拆成安全、性能、兼容性三类检查。

安全 Subagent：只查鉴权、权限、敏感信息、注入风险。

性能 Subagent：只查慢查询、循环、缓存、并发问题。

兼容性 Subagent：只查接口变化、字段变化、迁移风险。

主 Agent：汇总三个结果，只输出 P0/P1 风险和建议。
```

这个结构比一个模型从头看到尾更稳。

因为每个 Subagent 都被限制在一个窄问题里。

## 3. 4SAPI 里要按角色拆 Key

Subagent 一多，模型调用也会变多。

如果所有 Subagent 都共用一个 Key，后面会很痛苦。

你不知道：

```text
哪个角色最贵。
哪个任务最容易重试。
哪个 Subagent 在无效搜索。
哪个模型适合做 review。
哪个模型适合做 summary。
```

所以一开始就建议在 4SAPI 里按角色拆 Key 或至少拆调用标签。

最小拆法：

| Key/分组 | 用途 | 推荐策略 |
| --- | --- | --- |
| `agent-planner` | 拆任务、定计划 | 强模型，低额度 |
| `agent-worker` | 执行子任务 | 性价比模型，控制轮数 |
| `agent-reviewer` | 最终审查 | 强模型，只在关键节点用 |
| `agent-summary` | 摘要归档 | 低成本模型 |

更细一点，可以按项目和环境拆：

```text
crm-dev-agent-worker
crm-prod-agent-reviewer
docs-dev-agent-summary
ops-staging-agent-planner
```

这样 4SAPI 日志里就能回答：

```text
这个月哪个项目的 Agent 最贵？
哪个角色最耗 token？
测试环境是不是误用了生产模型？
reviewer 调用是否真的减少了返工？
```

没有这层归因，多 Agent 很容易变成“多账单”。

## 4. 并行不是越多越好

Subagent 的第二个价值，是并行。

一个主 Agent 可以同时派发多个子任务：

```text
一个查文档。
一个读代码。
一个跑测试。
一个写迁移方案。
```

这能减少等待时间。

但并行也会放大成本。

假设一个任务拆成 8 个 Subagent，每个 Subagent 跑 5 轮，每轮都用强模型。

那不是效率提升。

那是账单加速器。

所以并行前要做三件事：

```text
限制并行数量。
限制每个 Subagent 最大轮数。
限制每个角色可用模型。
```

推荐一个保守起步配置：

| 配置项 | 建议值 |
| --- | --- |
| 单任务最大 Subagent 数 | 3 到 5 个 |
| 单 Subagent 最大轮数 | 3 到 6 轮 |
| Planner 模型 | 强模型，少调用 |
| Worker 模型 | 中低成本模型 |
| Reviewer 模型 | 强模型，最后调用 |
| Summary 模型 | 便宜模型 |

只有当日志证明某类任务确实值得并行，再慢慢放开。

不要一开始就把系统设计成“百 Agent 齐飞”。

那种架构看起来很先进，调试起来会很朴素地崩。

## 5. Memory：Agent 为什么会断片

说完 Subagent，再说记忆。

Agent 跟普通聊天最大的差别之一，是它要跨步骤、跨会话干活。

但模型本身没有真正的长期记忆。

每次调用，本质上都是：

```text
给它一段上下文。
它根据这段上下文生成下一步。
```

如果上下文里没有，它就不知道。

这就是为什么很多 Agent 会“断片”：

```text
上午决定了不用 A 方案，下午又建议 A 方案。
昨天说好某个接口不能改，今天又改了。
前面测试已经失败过，后面又重复跑同样路径。
用户明确说不要动某个文件，它过几轮忘了。
```

不是模型故意不听话。

是记忆层没做好。

## 6. Agent 记忆可以分三层

企业里做 Agent Memory，不要上来就搞一个万能记忆库。

先按三层拆：

| 记忆层 | 保存什么 | 常见载体 |
| --- | --- | --- |
| 短期记忆 | 最近对话、最近工具结果 | 当前上下文窗口 |
| 任务记忆 | 当前任务状态、检查点、已尝试方案 | 状态文件、数据库、任务表 |
| 长期记忆 | 项目规则、用户偏好、历史决策 | 知识库、向量库、规则文件 |

短期记忆解决：

```text
刚才发生了什么？
```

任务记忆解决：

```text
这个任务现在做到哪一步？
哪些方案试过？
哪些测试通过了？
```

长期记忆解决：

```text
这个项目一直遵守什么规则？
以前为什么放弃某个方案？
这个团队偏好什么交付格式？
```

三层不要混。

把所有历史对话都塞进向量库，不等于有了好记忆。

记忆的关键是：

```text
该记什么。
什么时候记。
什么时候召回。
召回后怎么压缩。
过期信息怎么更新。
```

## 7. 长时任务一定要有检查点

长时任务最怕跑到一半崩。

比如：

```text
重构一个模块。
迁移一批文档。
整理一套知识库。
批量检查 PR。
连续跑一晚上的数据处理。
```

如果第 80 步失败，不能从第 1 步重来。

所以长任务必须有检查点。

一个简单的检查点可以包含：

```text
task_id
当前目标
已完成步骤
当前状态
已修改文件
已通过验证
失败记录
下一步建议
成本累计
```

可以写成 Markdown：

```text
## 当前任务
修复登录页偶发 500

## 已完成
- 定位到 auth/session.ts
- 复现了 token 过期路径
- 修改了 refreshSession
- 单测已通过

## 失败尝试
- 修改 LoginForm 无效，已回滚
- 延长前端缓存无效，已放弃

## 下一步
- 跑集成测试
- 让 reviewer 检查鉴权边界

## 成本
- planner: 2 次
- worker: 7 次
- reviewer: 0 次
```

也可以写进数据库。

形式不重要。

重要的是 Agent 能从检查点恢复，而不是靠上下文窗口硬撑。

## 8. 长时任务的 4SAPI 成本策略

长任务最容易烧钱。

因为它不是一次调用，而是一串调用：

```text
计划
  -> 搜索
  -> 执行
  -> 失败
  -> 重试
  -> 再搜索
  -> 再执行
  -> review
  -> 总结
```

所以要在 4SAPI 里配合做成本治理。

建议至少记录这些字段：

| 字段 | 作用 |
| --- | --- |
| `task_id` | 把多轮调用归到同一个任务 |
| `agent_role` | 区分 planner、worker、reviewer |
| `project` | 成本归属到项目 |
| `environment` | 区分 dev、staging、prod |
| `model` | 做模型横评 |
| `retry_count` | 找出失败循环 |
| `final_status` | 成本和结果挂钩 |

如果你的调用框架支持 metadata，就把这些信息带进去。

如果暂时不支持，至少在 Key 命名和任务日志里保留。

长任务不要只看“花了多少钱”。

还要看：

```text
花的钱有没有换来可验收结果。
哪些调用是有效推进。
哪些调用只是重复失败。
哪个角色最值得升级强模型。
哪个角色可以降到便宜模型。
```

这才是成本治理。

## 9. 适合先落地的三个场景

如果你想在企业里试 Subagent 和记忆，我建议先从这三个场景开始。

### 场景一：PR Review

拆成：

```text
主 Agent：读取 PR 和需求。
安全 Subagent：查权限和敏感信息。
测试 Subagent：查是否缺测试。
兼容性 Subagent：查接口和数据结构变化。
总结 Agent：输出 P0/P1/P2 风险。
```

好处是边界清楚，结果容易验证。

### 场景二：知识库整理

拆成：

```text
分类 Subagent：按主题归类。
去重 Subagent：找重复内容。
摘要 Subagent：生成短摘要。
引用检查 Subagent：检查来源是否完整。
主 Agent：生成最终目录。
```

好处是写权限可以先限制在草稿目录，不碰生产知识库。

### 场景三：测试失败排查

拆成：

```text
日志 Subagent：只读失败日志。
代码 Subagent：只读相关文件。
历史 Subagent：查最近提交。
主 Agent：汇总可能原因和修复建议。
```

第一阶段只输出建议，不自动改代码。

跑稳以后，再开放有限修改权限。

## 10. 上线检查清单

多 Agent 和记忆系统上线前，至少检查这些：

| 检查项 | 标准 |
| --- | --- |
| 角色边界 | 每个 Subagent 职责一句话说清 |
| 工具权限 | 每个角色只有必要工具 |
| Key 拆分 | 4SAPI 里能按角色和项目看日志 |
| 最大轮数 | 每个角色有独立轮数上限 |
| 并行限制 | 单任务最大并行数明确 |
| 检查点 | 长任务能断点恢复 |
| 失败记录 | 已尝试方案不会反复重做 |
| 记忆更新 | 旧规则能被新决策覆盖 |
| 结果验收 | 最终输出有测试、人工或规则验证 |
| 预算阀门 | 成本超限能停止或降级 |

这张表比“用了几个 Agent”更重要。

Agent 数量不代表能力。

可控的协作结构才代表能力。

## 11. 总结

Subagent 的本质不是拟人化。

它是：

```text
拆任务。
拆上下文。
拆工具权限。
拆模型预算。
拆验收责任。
```

Memory 的本质也不是把历史都存起来。

它是：

```text
让 Agent 在正确的时候想起正确的信息。
```

企业要让长时任务真正跑起来，必须把 4SAPI 这类大模型 API 中转站放进成本和日志链路里。

否则多 Agent 一跑，调用会非常热闹，账单也会非常热闹。

也就是从“Agent 会干活”走到“Agent 能不能放心用”。
