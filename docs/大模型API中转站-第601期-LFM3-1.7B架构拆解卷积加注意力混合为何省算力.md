# LFM3-1.7B 架构拆解：卷积加注意力混合为何能在小模型上省算力

Liquid AI 在 2026 年 10 月 27 日发布 LFM3 时，给 LFM3-1.7B 写了一句很强的话：它用比上一代 LFM2.5-2.6B 少 35% 的参数，在智能体任务上表现更好。参数少反而更强，通常意味着结构或训练配方有实质变化。

本文回答一个问题：LFM3-1.7B 的结构到底改了什么，每处改动想解决什么问题，哪些结论读者可以自己验证。文章只依据官方博客和模型卡，不包含我自己的实测。官方给出的性能数字全部是厂商自报，文中会逐项标明。

信息截止日期为 2026-10-30。模型卡仍在更新，引用前请重新打开原页面。

## 一、先说结论

1. LFM3-1.7B-Base 共 24 层，由三种层混合：13 层门控短卷积、5 层滑窗注意力、6 层全局注意力。
2. 另有三处改动：头级门控注意力、部分 RoPE、sandwich norm。
3. 这套设计的目标是在长上下文下保持推理速度，并让模型更适合量化。
4. 官方的性能对比有明确数字，但都是自报，没有独立复现。
5. 结构上的"省算力"可以从原理上推断，但具体省多少，需要在你的硬件上测。

## 二、官方到底公布了什么

主要来源是 Liquid AI 在 Hugging Face 发布的博客
[Build specialized multimodal models with LFM3](https://huggingface.co/blog/LiquidAI/lfm3)
（2026-10-27，检索于 2026-10-30），以及模型卡
[LiquidAI/LFM3-1.7B](https://huggingface.co/LiquidAI/LFM3-1.7B)（更新于 2026-10-28）。

| 项目 | 官方数值 |
| --- | --- |
| 参数量 | 1.73B（模型卡） |
| 层数 | 24 |
| 上下文长度 | 256K token（输入加输出） |
| 词表 | 128,000 |
| 预训练 token | 22T |
| 中期训练 token | 最后 3.5T，agent 轨迹和工具调用占比更高 |
| 语言 | 16 种，含中文、日语、韩语、阿拉伯语等 |
| 文本模型 4-bit 体积 | 约 1 GB |

LFM3-1.7B-Base 使用的词表与 LFM2.5-8B-A1B 相同，都是 128K。

## 三、24 层是怎么搭的

### 三种层的配比

| 层类型 | 数量 | 关键参数 |
| --- | --- | --- |
| 门控短卷积 | 13 | 卷积核 7（LFM2 为 3） |
| 滑窗注意力（SWA） | 5 | 窗口 256 token |
| 全局注意力 | 6 | 覆盖全部上下文 |

13 加 5 加 6 等于 24。官方没有在博客里给出这三种层的排列顺序，只给了数量。所以下面的分析只依赖数量，不假设排列。

### 为什么要混合

三种层的计算代价随上下文长度的变化不同。以下是通用的结构性质，不是官方原话：

- **短卷积**：每个位置只看固定宽度的邻域，计算量和状态大小不随上下文增长。
- **滑窗注意力**：只看最近 256 个 token，缓存大小有上限。
- **全局注意力**：每个位置看全部历史，缓存随上下文线性增长。

由此可以做一个推断：在 256K 上下文里，随长度增长的缓存主要来自 6 个全局注意力层。如果同样 24 层都是全局注意力，这部分缓存会是 4 倍，前提是每层的头数和维度相同。这个"4 倍"是我基于层数比例的算术推断，没有来自官方，也没有考虑各层实际配置的差异。

## 四、四处结构改动

### 1. 更宽的卷积核

LFM2 的短卷积核是 3，LFM3 提高到 7。卷积核变宽，每层能直接看到的邻近 token 更多，可以承担一部分原本要靠注意力做的局部建模。代价是每层卷积的参数和计算略增。

### 2. 头级门控注意力

官方描述：用一个 sigmoid 门控缩放每个注意力头的输出，让一个头在"没东西可补充"时可以关闭。

官方给出的目的是帮助抑制激活值离群点，这些离群点会损害量化效果。这个说法和量化的常识一致：激活里出现极大值时，低比特量化的误差会变大。但官方没有给出量化前后的对比数字，所以"更适合量化"目前只是设计意图，不是已验证的结论。

### 3. 部分 RoPE

全局注意力层只对每个头里频率最高的一半维度做旋转位置编码，另一半不旋转，因此那一半只按内容匹配，与距离无关。滑窗注意力层仍使用完整 RoPE。

这样做的直觉是：局部层负责"离得近的"，全局层的一半维度负责"内容相似的、不管多远"。官方没有给出消融实验，因此该设计对长上下文检索的实际贡献无法从公开资料判断。

### 4. Sandwich norm

每个模块在输入和输出两端都做归一化，目的是让激活值保持在合适的数值范围。这对低精度推理和长序列训练的稳定性都有帮助，同样没有官方的单项对比数据。

## 五、速度与参数效率的说法

官方在博客里写了三条与速度相关的说法：

- 按每个参数计算，LFM3-1.7B 在边缘设备上的短提示速度与 LFM2-1.2B 持平。
- 上下文里有 8K token 时，约快 25%。
- 架构搜索覆盖 14 种设备与后端的组合，包括手机、树莓派 5、笔记本、云端 CPU、GPU 和高通 Hexagon NPU。

这几条要注意三点：

1. 对比对象是 LFM2-1.2B，不是通用的其他模型。
2. "按每个参数"的表述意味着做了归一化，具体怎么归一化官方没有写。
3. 没有给出具体的 tokens/s、设备型号和量化设置，读者无法复现。

## 六、训练配方里值得注意的部分

| 阶段 | 内容 |
| --- | --- |
| 预训练 | 22T token，词表 128K |
| 中期训练 | 最后 3.5T token，使用精选数据，agent 轨迹和工具调用占比更高 |
| 上下文扩展 | 中期训练期间扩展到 256K |

官方把"智能体任务进步最大"归因于结构和配方两方面，但没有拆分各自的贡献。博客原文只说"新的 tri-hybrid 架构和训练配方"共同使得性能提升。因此，不能从公开资料判断提升有多少来自结构，多少来自中期训练里增加的 agent 数据。

这一点对选型有实际影响。如果主要增益来自 agent 数据，那么换一个类似配方训练的传统注意力模型，也可能得到相近效果。反过来，如果结构是主因，混合架构就有独立价值。目前无法区分。

## 七、官方的性能说法，逐条标注核验状态

| 说法 | 来源 | 状态 |
| --- | --- | --- |
| 比 LFM2.5-2.6B 少 35% 参数 | 博客 | 可由参数量算出：1.73B 对 2.6B，约少 33% 到 35%，与"1.7B 对 2.6B"的取整有关 |
| WebArena-Verified：38.42 对 3.02 | 博客 | 厂商自报，未复现 |
| 长任务上超过 Qwen3.5-9B | 博客 | 厂商自报，未给出具体任务和分数 |
| 8K 上下文约快 25% | 博客 | 厂商自报，设备和量化未写明 |
| 文本模型 4-bit 约 1 GB | 博客 | 可自己验证（见下一节） |

第一行的"约少 33% 到 35%"需要解释：1.73 除以 2.6 约等于 0.665，也就是少约 33.5%。官方说 35%，如果按 1.7B 对 2.6B 算则是 34.6%。两种取整方式略有出入，不影响判断，但引用时建议直接写参数量。

38.42 对 3.02 是一个很大的差距，接近 13 倍。这个跨度本身就值得谨慎：它说明 LFM2.5-2.6B 在这个基准上几乎不可用，而不一定是 LFM3 极强。读这类数字时，要先看基线是否处于"接近零"的区间。

## 八、读者可以自己验证什么

下面几项不需要特殊硬件，普通开发机即可。

### 1. 体积

下载官方的 4-bit 版本，查看文件大小，核对"约 1 GB"。模型卡列出了 GGUF、ONNX、MLX-4bit、FP8 等版本，具体仓库名以模型卡链接为准。

### 2. 上下文增长对速度和内存的影响

用同一台机器、同一个量化版本，分别用 1K、8K、32K 的输入测首 token 时间和生成速度，同时记录内存占用。观察曲线是否平缓，再与你正在使用的同级别纯注意力模型对比。

这是检验"混合结构在长上下文下更省"的最直接方法。官方说 8K 时快 25%，你可以看自己的数据是否接近。

### 3. 采样参数

模型卡给出的采样设置：

- 通用场景（聊天、工具调用、智能体、代码）：`temperature=0.1, top_k=50, repetition_penalty=1.1`
- 数学与 STEM：`temperature=1.0, top_p=0.95, top_k=20`

跑自己的任务时先用这些默认值，不要沿用其他模型的参数。

### 4. 自定义代码

模型卡的 transformers 示例带 `trust_remote_code=True`，这意味着加载模型会执行仓库里的自定义代码。在生产环境使用前，应该先阅读该仓库的建模代码，或者固定到某个具体的提交版本，而不是跟随主分支。

## 九、什么时候这套结构不一定适合你

- **任务以短文本为主。** 混合结构的收益主要体现在长上下文，短提示下与纯注意力模型的差别有限。官方自己的说法也是短提示上"持平"。
- **你依赖某个推理框架的成熟优化。** 卷积层和门控注意力需要框架支持。模型卡列出了 vLLM、SGLang、llama.cpp、ONNX Runtime、MLX 等部署方式。其中工具搜索功能的说明里写明 llama.cpp 需要"兼容 LFM3 的构建"，旧版本能否运行，需要自己确认。
- **你需要更强的通用知识。** 1.7B 的容量有限，官方定位也是"专业化的起点"，不是通用助手。
- **需要严格复现论文级别的结论。** 公开资料没有消融实验，无法确认各改动的单独贡献。

## 十、限制与结论

LFM3-1.7B 的结构是一个有明确设计意图的混合方案：用卷积和滑窗注意力承担大部分局部计算，只保留 6 层全局注意力。这在原理上有利于长上下文的速度和缓存，也符合官方的实测说法。

但从公开资料看，下列事项仍然没有答案：三种层的排列方式、各项改动的消融结果、量化前后的精度对比、速度测试的硬件和设置、增益里结构与训练数据各占多少。

如果你在考虑把它用在端侧智能体上，建议的下一步是：先下载 4-bit 版本，按第八节的方法测自己设备上的长上下文曲线，再用你自己的 20 到 30 个工具调用任务对比现用的小模型。官方数字可以作为起点，但最终判断应该来自你的数据。
