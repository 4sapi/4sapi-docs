# TradingAgents 的多智能体结构：一场辩论如何收敛成一个评级

多智能体系统有一个常见的失败模式：每个角色都说得头头是道，最后拼起来却没有可执行的结论。要么是几份报告并列摆着让人自己判断，要么是最后一步的输出格式飘忽，程序无法读取。

TradingAgents 在这一点上做了一个明确的选择：不管前面多少角色参与，最终必须收敛成五档评级之一；如果读不出来，就输出一个显式的 REVIEW 标记，而不是默认归到中间档。这个设计比它模仿交易公司的角色设定更值得研究。

本文只看结构：角色怎么排、状态里存什么、辩论怎么收敛、评级解析为什么值得单独写一个模块。回测方法另文讨论。项目 README 明确写了不构成财务、投资或交易建议，本文同样不涉及任何标的的判断。信息来自仓库源码与文档，检索日期为 2026-11-01，我没有运行过它。

## 二、角色怎么排

按 README 与目录结构，一次分析的角色分四层：

| 层 | 角色 | 产出 |
| --- | --- | --- |
| 分析层 | 基本面、情绪、新闻、技术四类分析师 | 四份报告 |
| 研究层 | 看多研究员、看空研究员，之后由研究员主管汇总 | 辩论记录与投资计划 |
| 交易层 | 交易员 | 交易提案 |
| 风控与决策层 | 激进、保守、中立三名风险辩手，之后由组合经理拍板 | 最终决策与评级 |

两个执行顺序上的细节值得注意。

第一，四类分析师是同时工作的，各自用自己的工具，全部报告到齐之后才开始研究辩论。这一点和"顺序流水线"不同：新闻分析师慢，不会阻塞技术分析师；但研究层必须等齐所有报告。

第二，风控层是三个人辩论，不是一个人评估。激进、保守、中立三个视角各自留一份历史，最后才到组合经理。

## 三、状态里到底存了什么

源码里的 `AgentState` 把每一步的产物都显式列出，这份字段表比 README 更能说明系统的形状。

| 分组 | 主要字段 |
| --- | --- |
| 运行标识 | company_of_interest、asset_type、instrument_context、trade_date |
| 分析层 | market_report、sentiment_report、news_report、fundamentals_report |
| 研究层 | investment_debate_state（看多历史、看空历史、count）、investment_plan |
| 交易层 | trader_investment_plan |
| 风控层 | risk_debate_state（三个视角各自的历史、latest_speaker、count） |
| 决策层 | final_trade_decision、final_rating |
| 记忆与组合 | past_context、memory_note、portfolio_context |

有三处注释值得单独读：

1. `instrument_context` 标明"在运行开始时确定性解析的标的身分"。也就是说，分析哪家公司不交给模型在对话里确认，而是开工前定好。
2. `trade_date` 标注为"数据以该日期为准"。它不只是一个可选参数，而是数据访问的时间基准。
3. `memory_note` 标注为"本次运行中记忆日志无法结算或读取的内容，给报告用；一切正常时为空"。失败不是静默的，它会写进报告。

第 3 条在小处见功夫。很多系统在后台步骤失败时选择跳过，报告照旧漂亮；这里把失败通道做成了状态里的一个字段。

## 四、辩论如何收敛

### 轮数上限

默认配置里三个与讨论相关的数字：

| 配置项 | 默认值 | 作用 |
| --- | --- | --- |
| max_debate_rounds | 1 | 多空研究辩论轮数 |
| max_risk_discuss_rounds | 1 | 风控三辩手讨论轮数 |
| max_tool_rounds | 20 | 分析师在被要求出报告前，最多做多少轮工具调用 |

默认都是 1 轮。这意味着开箱状态下辩论很浅：多空各说一次，然后进入汇总。想让它"多吵几轮"，要自己调高，代价是调用次数和 token 成倍增长。

按 4 个分析师、每人 20 轮工具调用算，光分析师一层就有最多 80 轮调用（我的算术），还没算辩论、主管、交易员和风控。这也解释了为什么默认把辩论轮数压到 1。

### 收敛点：五档评级

最终输出用一套固定的五档：Buy、Overweight、Hold、Underweight、Sell。这套词表由研究员主管、组合经理和记忆日志三处共用。

为什么值得单独抽一个模块？源码注释给的理由是避免三处各自演进产生漂移。这个问题在多智能体系统里很真实：报告人写"增持"，组合经理写"Overweight"，日志里存成"overweight"，下游一解析就错。

## 五、评级读不出来的时候

这是我认为整个仓库里最有参考价值的一段设计，值得逐条看。

### 原则：读不出来不等于 Hold

解析函数在找不到评级时返回空值，而每个调用方都把它转成一个专门的 REVIEW 标记，绝不落到 Hold。源码注释的理由很直接：读不出评级的决策不是 Hold，把它记成 Hold，下一次运行就会把一次从未做出的判断当作历史引用。

这里的因果值得展开：记忆日志会把过去的决策回灌给组合经理。如果错误地记成 Hold，系统会以为自己当时持中性看法，从而在后续推理里延续一个不存在的立场。一个解析失败被放大成了持续偏置。

### 解析规则里的几个防护

评级解析不是简单正则，源码里能看到这些处理：

| 情况 | 处理 |
| --- | --- |
| 全文用全角标点（如 `Rating：Overweight`） | 先做 NFKC 归一化，再匹配 |
| 结论开头就是评级行 | 直接取这一行 |
| 出现"Consensus rating: Buy"、"Trader's rating: Buy" | 不算本次结论，那是别人的评级 |
| 出现"Rating Scale: Buy, …"这类量表说明 | 视为模型复述了量表，不算结论 |
| 同一结论里出现两个不同评级，且没有任何标记指明哪个是正式判断 | 判为无评级 |
| 正文里出现"not a Sell"这类否定表述 | 不因为出现评级词就当成结论 |

最后一条尤其关键：在自然语言里，评级词经常出现在反对的语境中。如果解析器只做关键词匹配，就会把一个"这不是卖出信号"读成卖出。

### 结果：REVIEW 会落到人身上

REVIEW 是不可交易的标记。它不会变成仓位，而是要求人工处理或重跑。对自动化系统来说，这是把"沉默的错误"换成了"显式的待办"。

## 六、记忆与组合上下文

### 记忆日志始终开启

每次完成的运行都会把决策追加到记忆日志。后续运行进行时，系统会结算那些持仓期已过的历史决策，算出实际收益和相对基准的超额收益，生成一段反思，再交给组合经理参考。

注意这里的顺序：结算发生在"后续运行分析期间"，而不是单独的批处理。README 也说明了，如果结算失败，运行继续，报告会写明。

### 两种上下文不要混

| 字段 | 含义 |
| --- | --- |
| past_context | 记忆日志里同标的的近期决策加其他标的的近期教训 |
| portfolio_context | 调用方传入的持仓与现金 |

默认情况下智能体不知道你持有什么，输出是写给"自己会套用结论的读者"。传了组合之后，交易员、风控和组合经理才会按你的实际账面来。源码特别区分了"传了空持仓列表"和"什么都没传"：前者是空仓，后者不做假设。

## 七、这套结构的代价

以下是基于结构的推断，不是项目自述。

| 设计 | 好处 | 代价 |
| --- | --- | --- |
| 四分析师并行 | 单点延迟低，互不阻塞 | 要等最慢的一个，且成本是四份 |
| 辩论轮数可调但默认 1 | 开箱便宜 | 默认状态下"辩论"更像各自陈述 |
| 五档评级 + REVIEW | 输出可读、下游可算 | REVIEW 需要人工兜底 |
| 记忆日志常开 | 有跨次连续性 | 日志质量直接影响后续判断 |
| 状态里存全部中间产物 | 可追溯 | 状态体积随角色增加 |

第四行的风险需要强调：记忆日志把过去的评级与反思回灌给组合经理。如果早期决策质量不高，这些内容会成为后续运行的先验。系统本身没有"这段记忆可能有害"的过滤机制，至少我没在源码里看到。

## 八、读这个结构时容易误会的两点

1. **它不是真实的交易系统。** README 写明订单送到模拟交易所。角色分工模仿交易公司，但执行环节是模拟。
2. **它不是组合管理系统。** 回测模块的文档说得很清楚：这是评估决策质量的工具，不是组合模拟器，也不应该被扩展成组合模拟器（详见另一篇关于回测的讨论）。

还有一点是论文层面的：arXiv 摘要主张这套框架在累计收益、夏普比率和最大回撤上优于基线。我没有复现这些结果，而且项目 README 自己写着回测结果不保证与任何已公布数字一致。两者放在一起看，论文数字应当当作论文的主张，而不是可以直接套用的结论。

## 九、限制与结论

这个结构的核心不在角色数量，而在收敛设计：中间可以有很多声音，出口只有一个五档评级，读不出来则显式标记为待人工处理。配套的三个选择也一致：标的身分开工前确定性解析、讨论轮数有硬上限、后台失败写进报告而不是静默跳过。

本文的限制：没有运行项目；只读了状态、评级、默认配置、回测与 README，没有读各分析师的实现；辩论轮数与成本的关系是我的算术，不是实测；没有复现论文指标；不构成任何投资建议。

下一步建议：如果你在自己搭多智能体系统，可以只借鉴两件事——把最终输出压成一个可解析的固定词表，以及为"解析失败"设计一个不属于任何正常档位的显式标记。
