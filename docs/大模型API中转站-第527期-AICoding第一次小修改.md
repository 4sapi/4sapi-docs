# AI Coding 新手第一课：先学会控制一次小修改

第一次接触 AI Coding，最容易产生一种错觉：只要把想法说出来，几分钟后就能得到一个完整应用。

这种体验确实很神奇。

但真正开始维护项目后，问题很快会出现：改一个按钮，另一个页面坏了；AI 说“已经完成”，浏览器却仍然报错；你不知道它改了哪些文件，也不知道出了问题该回到哪个版本。

所以新手的第一课，不是让 AI 一次生成更多代码，而是学会控制一次小修改。

## 一、AI Coding 是什么

AI Coding 不是某一个软件名称。

它指的是人在软件开发过程中使用 AI 或 Agent，参与需求分析、代码生成、调试、测试、审查和文档维护等工作。

一个专业开发者让 AI 写测试，也属于 AI Coding。

一个初学者让 AI 解释文件结构，同样属于 AI Coding。

完整流程大致是：

~~~
理解需求
-> 分析项目
-> 制定计划
-> 生成或修改代码
-> 查看差异
-> 运行测试
-> 修复问题
-> 代码审查
-> 发布
-> 观察日志
-> 持续维护
~~~

AI 可以参与其中很多步骤，但目标、边界、判断和最终结果仍然需要人负责。

## 二、第一次练习应该选什么项目

不要从社交网络、在线商城或复杂 SaaS 开始。

第一次练习更适合选择：

- 一个静态个人介绍页；
- 一个单位转换器；
- 一个简单计算器；
- 一个待办事项页面；
- 一个只有单页的意见收集表。

项目越小，越容易知道修改是否成功。

你需要的不是一个看起来很大的项目，而是一个能完成“修改—运行—验证”循环的项目。

## 三、先让 AI 解释项目结构

打开项目后，不要直接说“帮我重构一下”。

先让 AI 阅读项目，并回答：

~~~
请先阅读当前项目，不要修改文件。
请用简单语言说明：
1. 项目从哪里启动；
2. 主要页面和入口文件在哪里；
3. 样式文件和交互代码在哪里；
4. 当前使用了哪些依赖；
5. 运行项目需要什么命令；
6. 你还无法确认的地方是什么。
~~~

这个步骤的目的，是建立共同上下文。

如果 AI 连项目入口都没有找对，后面的修改就不值得直接执行。

## 四、确认启动方式

你至少要知道三件事：

1. 从哪个目录运行命令；
2. 使用什么命令启动开发服务器；
3. 浏览器应该打开哪个地址。

如果项目有 README，先看里面的启动说明。

如果说明缺失，让 AI 根据项目配置进行判断，并明确标注不确定部分。

不要因为 AI 猜了一个命令就直接执行高风险脚本。

## 五、第一次只做低风险修改

适合新手的低风险修改包括：

- 改一个标题文字；
- 增加一个空状态提示；
- 调整按钮间距；
- 给表单增加必填提示；
- 给按钮增加加载状态。

这些修改范围清楚，验证方法也比较简单。

不建议第一次就让 AI 同时改数据库、路由、登录和视觉系统。

任务越大，越难判断到底是哪一处改变导致了问题。

## 六、给任务写清楚三件事

每次修改前，至少写明：

~~~
目标：这次要解决什么问题。
边界：哪些文件或功能不能动。
验收：完成后怎样确认成功。
~~~

例如：

~~~
目标：给待办列表增加空状态提示。
边界：只修改列表组件和相关样式，不改变数据结构和接口。
验收：删除全部任务后显示提示；重新添加任务后提示消失；刷新页面后原有行为不变。
~~~

这比“优化一下待办列表”更容易得到可控结果。

## 七、让 AI 先说准备改什么

在执行前，可以要求 AI 输出：

- 准备修改的文件；
- 每个文件要改的内容；
- 不会修改的文件；
- 可能的风险；
- 验收步骤。

如果计划涉及的文件明显超出任务范围，先缩小任务，而不是让它继续执行。

## 八、查看 diff 是必修课

AI 完成修改后，先看差异，再运行项目。

你不需要立刻读懂每一行代码，但至少检查：

- 是否修改了预期文件；
- 是否出现大量无关格式变化；
- 是否删除了原有逻辑；
- 是否加入了新的依赖；
- 是否写入密钥或私人信息；
- 是否修改了不应该动的配置。

diff 是你和 AI 之间的边界记录。

## 九、一次只验证一个结果

浏览器验证时，按照验收标准操作。

例如空状态提示的验证顺序：

1. 打开页面；
2. 确认已有任务正常显示；
3. 删除全部任务；
4. 检查提示是否出现；
5. 新增一条任务；
6. 检查提示是否消失；
7. 刷新页面，确认原有行为没有改变。

不要只看截图。

页面看起来正常，不代表状态变化和刷新逻辑也正确。

## 十、AI 说完成，不代表完成

“已完成”“已修复”“测试通过”都只是模型输出的文字。

真正的完成标准应该来自：

- 你看到的 diff；
- 你实际运行的命令；
- 浏览器中的操作结果；
- 自动化测试输出；
- 仍未验证的风险。

如果 AI 没有运行测试，就不要把“应该可以”当成“已经通过”。

## 十一、修改前保存版本

每次小修改前，至少保留一个可回退版本。

使用 Git 时，可以先查看当前状态，再创建提交：

~~~text
git status
git add .
git commit -m "before small change"
~~~

命令需要在项目目录中运行。

如果你还不了解 Git，可以先让 AI 解释命令含义，再执行。

不要在不清楚作用时复制删除或重置命令。

## 十二、修改失败怎么处理

先记录：

- 修改前的项目状态；
- 使用的提示词；
- AI 修改了哪些文件；
- 浏览器如何复现；
- 完整错误信息。

然后让 AI 先判断原因，不要立即继续叠加新修改。

连续叠加多个“修复”，会让问题越来越难定位。

## 十三、给 AI 的调试描述模板

~~~text
我遇到了这个问题：【现象】
运行环境：【操作系统、浏览器、启动命令】
复现步骤：
1. ...
2. ...

预期结果：【本来希望发生什么】
实际结果：【实际发生了什么】
错误信息：【完整错误】

请先判断最可能的原因，列出需要检查的文件和证据。
暂时不要修改代码。
~~~

信息越完整，AI 越不需要猜测。

## 十四、第一次练习的通过标准

完成第一次小修改后，你应该能够回答：

- 项目从哪里启动；
- 主要页面在哪里；
- 这次改了哪些文件；
- 哪些文件没有改；
- 用什么步骤验证成功；
- 如果失败，如何回到修改前版本。

如果这些问题都答不上来，说明你只是让 AI 生成了代码，还没有真正控制开发流程。

## 十五、结论

AI Coding 的入门门槛确实降低了，但需求、边界、验证和维护并没有消失。

新手最值得先练习的能力，是把一个模糊想法缩小成一次低风险修改，然后看 diff、运行项目、记录结果并保留回退路径。

当你能稳定完成这个循环，再逐步增加任务规模，学习登录、数据库、部署和自动化测试，会比一开始追求“大而全”的项目更稳。
