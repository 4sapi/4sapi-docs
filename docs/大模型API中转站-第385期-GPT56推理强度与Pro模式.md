# GPT-5.6 推理强度与 Pro 模式应该怎样组合

接入 GPT-5.6 后，很多团队会自然地把推理强度调到 `max`，再打开 Pro 模式，认为两个选项都开到最高就能得到更可靠的答案。实际结果可能是延迟和 token 明显增加，常规任务的通过率却没有变化。另一些团队为了速度一直使用 `none`，遇到复杂工具任务失败时，又把问题归咎于模型。

这两个参数解决的不是同一件事。本文先拆清 `reasoning.effort` 与 `reasoning.mode`，再给出按任务难度建立二维配置矩阵的方法。你会得到一套可以重复运行的实验，而不是一张脱离业务的“推荐档位表”。

## 一、先分清 effort 与 mode

根据 OpenAI 当前的 [GPT-5.6 模型指南](https://developers.openai.com/api/docs/guides/latest-model?model=gpt-5.6)，GPT-5.6 支持六档 `reasoning.effort`：

```text
none
low
medium
high
xhigh
max
```

它控制模型为请求投入的推理强度。提高强度通常意味着允许更多探索和验证，但不保证每类任务都会得到可测量的质量改善。

`reasoning.mode: "pro"` 则是 Responses API 的执行模式。它会在返回一个最终答案前投入更多模型工作，适合质量提升会实质影响结果的困难任务。Pro 不是独立模型名，不需要切换到一个带 `pro` 后缀的模型。推理强度和执行模式彼此独立：同一个模型可以在标准模式或 Pro 模式下分别测试不同 effort。

如果省略 `reasoning.effort`，官方指南说明 GPT-5.6 在标准与 Pro 模式下都默认使用 `medium`。这意味着“只打开 Pro”并不等于自动使用 `max`；同样，设置 `max` 也不等于进入 Pro 模式。记录实验配置时，必须把模型、effort、mode 三项分开。

标准请求可以写成：

```python
response = client.responses.create(
    model="gpt-5.6-sol",
    input=task,
    reasoning={"effort": "medium"},
)
```

Pro 模式使用同一个模型名：

```python
response = client.responses.create(
    model="gpt-5.6-sol",
    input=task,
    reasoning={"effort": "medium", "mode": "pro"},
)
```

具体请求字段、支持范围和计费行为应在发布前从 OpenAI 的[推理指南](https://developers.openai.com/api/docs/guides/reasoning#reasoning-mode)重新核对。

## 二、六档推理强度的条件化起点

档位不是能力排行榜，更合适的理解是实验预算。

### `none`：把它当作延迟基线

适用于直接转换、简单分类、固定格式改写等不需要复杂探索的任务。它的价值是提供一个低推理投入的对照。如果任务需要多步判断、工具选择或冲突证据分析，也应同时测试 `low`，观察少量推理是否显著减少失败。

### `low`：延迟敏感任务的第一档推理

当 `none` 会漏掉简单关系，但业务仍对延迟敏感时，从 `low` 开始。适合规则明确的抽取、短链路工具调用和局部代码修改。验收重点是格式成功率、工具参数正确率和长尾延迟。

### `medium`：平衡基线

官方把 `medium` 作为平衡起点。新的任务还没有历史数据时，可以先用它建立质量与资源基线，再分别向上、向下比较。它不是所有任务的最终答案，只是减少盲目搜索的起点。

### `high` 与 `xhigh`：需要更多推理且收益可测的任务

复杂调试、跨文档分析、带多个约束的规划可能从这两档受益。是否保留，要看关键问题发现率、证据完整度和任务成功率是否提高。输出更长、解释更多，不自动等于质量更高。

### `max`：困难且质量优先的候选

`max` 适合需要更多探索与验证、并且错误代价很高的任务。测试时应与 `xhigh` 在同一组样本上对照。如果二者都能通过验收，而 `max` 只增加延迟和 token，就没有理由把它设成全局默认值。

## 三、什么任务值得测试 Pro 模式

OpenAI 把 Pro 模式描述为质量优先的执行方式，同时明确它会增加延迟，并把额外模型工作产生的 token 汇总进用量。比较时不要只看最终可见文字的长度。

以下任务值得进入 Pro 候选池：

- 数据库迁移、权限变更等高价值代码与方案审查；
- 有明确正确性标准的复杂优化；
- 需要综合多份证据、遗漏会造成严重后果的分析；
- 普通模式在历史样本上反复出现同一类关键漏报；
- 单次任务价值足以覆盖更高延迟与模型工作量。

以下任务通常先保留标准模式：

- 高吞吐分类、格式化和短摘要；
- 用户正在等待、延迟预算很紧的交互；
- 没有明确验收标准的泛化写作；
- 现有评测看不出 Pro 带来稳定收益；
- 超时后重试会放大队列和成本的链路。

不要在提示词里要求模型“进入 Pro”“多想一会儿”或生成多个候选再自选。应在 API 参数中设置执行模式，提示词继续写清目标、上下文、约束、所需证据、成功标准和输出格式。

## 四、建立二维配置矩阵

六档 effort 乘以两种 mode 会产生很多组合，没有必要全部穷举。先根据旧配置和任务难度选一个小矩阵。

例如，一个当前使用 `high` 的代码审查任务，可以测试：

| 编号 | 模式 | effort | 目的 |
| --- | --- | --- | --- |
| A | standard | `high` | 新模型同档基线 |
| B | standard | `medium` | 验证能否降一档保持质量 |
| C | pro | `high` | 判断额外模型工作是否减少关键漏报 |
| D | pro | `medium` | 判断较低 effort 与 Pro 的组合是否更合适 |

只有 A 和 B 都无法通过关键验收时，才继续测试 `xhigh` 或 `max`。如果 A 已经稳定通过，而 C 没有改善关键指标，就停止扩大 Pro 测试。这样可以把实验控制在少量有解释力的组合中。

对延迟敏感的工具任务，可以换成 `none/low/medium` 的标准模式矩阵，只有在失败损失较高时再加入 Pro。任务价值、时间预算和失败损失决定搜索范围，而不是参数名称。

矩阵得出结果后，还要把它变成明确的线上路由规则。例如只有“数据库变更审查”且输入通过完整性校验时才进入 Pro，普通代码解释继续走标准模式；任务标签缺失时回到平衡基线，不允许模型自行升级。每条路由记录命中原因、配置版本和回退目标，避免几个月后只剩一组没人敢改的高参数默认值。

## 五、同一任务怎样做可复现对照

样本集必须固定，并包含正常案例、边界案例和历史失败案例。每组配置至少运行足够多次以观察波动；调用顺序可以随机化，避免某一时段的网络或服务状态只影响单一配置。测试期间保持提示词、工具、输入和解析器不变。

评测表应记录：

| 指标 | 为什么要看 |
| --- | --- |
| 硬性任务成功率 | 判断输出是否真正完成任务 |
| 关键风险发现率 | 防止平均分掩盖严重漏报 |
| 必要证据完整度 | 防止结论与材料脱节 |
| 输出结构成功率 | 判断下游能否稳定解析 |
| 输入、输出与总 token | 观察资源变化而非只看可见文本 |
| p50、p95、超时 | 识别尾部延迟对队列的影响 |
| 重试和人工接管 | 计算隐藏的运行与编辑成本 |
| 单次成功成本 | 把失败、重试纳入成本分母 |

开放式任务也要有量表。例如内容审稿可以检查事实错误、关键问题覆盖、无依据判断、编辑耗时和最终采用率。不能用“更像人”“感觉更深入”这类无法复测的描述替代标准。

## 六、常见误区、降档与停止条件

### 误区一：最高配置一定更可靠

更多模型工作可能提高困难任务的可靠性，也可能只增加延迟和冗长解释。只要关键成功率没有改善，就应停止向上加档。

### 误区二：回答更长代表思考更多

可见输出长度与内部模型工作不是同一个指标。应查看 API 用量、任务结果和证据，而不是按字数判断。

### 误区三：平均分相同就可以降档

平均分可能掩盖少量高损失失败。降档前单独检查关键样本、最差结果和安全场景。对合同风险、数据迁移等任务，一次严重漏报可能比许多普通成功更重要。

### 误区四：所有请求共享一个全局配置

可以按任务路由：常规抽取用低档，复杂判断用中高档，只有经过评测的少量高价值任务进入 Pro。路由必须有明确条件和日志，避免模型自己无边界地升级资源。

当出现以下情况时停止实验并回到基线：硬性成功率下降、关键漏报增加、p95 超过业务上限、超时造成级联重试、成本增加却没有减少人工复核，或者配置与响应无法追踪。回滚要同时恢复模型、effort、mode、提示词和工具版本。

## 七、限制与结论

推理强度决定一次请求允许投入的推理程度，Pro 模式决定采用更重的执行方式，它们可以独立组合。实际选型应从当前配置或 `medium` 基线开始，先比较同档与低一档，再让困难且质量优先的任务测试 Pro。

合理配置的标志不是参数开得多，而是每一档都有进入条件、验收指标和停止条件。任务分布、提示词、工具或模型版本变化后，重新运行固定样本。只有质量收益能够覆盖新增延迟、token 和运维复杂度时，更高投入才值得保留。
