# 如何测量 Agent 预设是否真的提升效率

把 Agent 从标准模式切到极简或 PTC 模式后，任务可能更早完成，也可能只是碰巧少走了几步。只记录“这次用了 23 分钟，另一次用了 33 分钟”，无法分辨差异来自预设、模型随机性、网络、提示词、缓存，还是任务本身。

要回答“某个预设是否更有效率”，需要把它当成一次小型基准测试：固定不参与比较的变量，定义完成标准，记录全过程，并报告结果不能说明什么。下面给出一套适用于 Agent 预设比较的最小方法，既能比较墙钟时间，也不会把单次体验包装成通用结论。

## 先定义要比较的问题

不要从“哪个模式最快”开始。先写出一个可验收的问题，例如：

```text
在固定仓库提交中，实现一个指定接口。
完成条件：新增测试通过，已有测试不新增失败，改动只位于约定目录。
```

这个定义比“做一个 3D 游戏”更适合评测，因为它写清了输入、允许修改范围和可验证结果。任务可以很复杂，但必须在每次运行时保持一致。

预设比较通常包含一个自变量：预设类型。例如标准模式、极简模式和 PTC 模式。不要在同一次对比里同时更换模型、改提示词、扩大工作区或调整权限，否则无法解释结果差异。

## 固定测试条件

开始前，为每个运行填写一份记录。至少固定或记录下面的字段：

| 字段 | 需要记录的内容 |
| --- | --- |
| 测试日期 | 运行的日期和时区 |
| Harness 版本 | 预设配置可能随版本变动，必须记录版本或提交哈希 |
| 模型配置 | 模型名、推理档位、上下文设置和提供方 |
| 环境 | 操作系统、CPU、内存、网络条件和依赖版本 |
| 仓库状态 | Git 提交哈希、是否干净工作树、依赖安装状态 |
| 任务 | 完整提示词、输入文件和验收标准 |
| 权限 | 工作区、联网、Shell、写入和外部系统权限 |
| 执行规则 | 是否允许重试、最大轮数、是否允许人工提示 |

DeepSeek Harness 的内置预设会随发行版本调整。以 `dsh@0.1.1-rc.2` 为例，标准、极简、PTC 和创造模式的工具组合由各自的 `agent.cordis.yml` 定义，因此比较报告应附上版本或配置提交。[官方预设目录](https://github.com/deepseek-ai/DeepSeek-Harness/tree/b150a551b8d465e31e418e1b2eaf5e79bbb7d28e/apps/cli/config/agent-presets)

## 选择指标时，先把质量放在前面

只比较耗时会鼓励 Agent 走捷径。一个更快但改坏测试、超出文件范围或需要大量人工补救的结果，不应算作更高效率。

建议将结果分为三层：

| 层级 | 指标 | 含义 |
| --- | --- | --- |
| 正确性 | 验收通过率、测试结果、人工审阅结论 | 任务是否真正完成 |
| 过程 | 工具调用轮数、错误数、重试数、越界次数 | 执行是否稳定和可控 |
| 资源 | 墙钟耗时、输入 Token、输出 Token、人工修正时间 | 完成任务付出的资源 |

只有先满足正确性，过程和资源指标才有比较意义。对于涉及文件写入的任务，还应保存 Diff；对于外部调用任务，应记录请求数量和副作用。

## 至少运行多次

同一模型和同一任务也可能产生不同轨迹。一次执行结果只能称为一次观察，不能证明某个模式普遍更快。

一个实用的最小方案是：每种预设至少运行 3 次；如果成本允许，运行 5 次以上。每次开始前回到同一 Git 提交和依赖状态，删除由前一次运行产生的临时文件，并确认任务输入不变。

然后分别计算：

```text
通过率 = 通过验收的运行次数 / 总运行次数
中位耗时 = 排序后位于中间位置的墙钟时间
中位输入 Token = 各次输入 Token 的中位数
```

使用中位数能降低一次网络抖动或异常重试的影响，但并不能消除样本很少的问题。报告中仍要写明样本数和所有异常运行。

## 正确计算“提升百分比”

只有在两个结果都通过同一验收标准时，才讨论时间差。

假设基线中位耗时为 `T_base`，候选预设中位耗时为 `T_candidate`：

```text
耗时减少比例 = (T_base - T_candidate) / T_base
速度提升比例 = (T_base / T_candidate - 1)
```

两种说法并不相同。下面仅演示计算口径：若耗时从 33 分钟降到 23 分钟，耗时减少约 30%，而按单位时间完成量计算的速度提升约 43%。因此，报告必须说明使用哪一个口径，不能只给出一个未说明含义的百分比。

更重要的是，这个数字只有在同一任务、同一验收条件和足够样本下才有解释力。若其中一组存在测试失败、人工接手或额外重试，应同时报告，不应只挑最短的一次。

## 让运行顺序不成为隐藏变量

即使仓库、模型和提示词都相同，按“先连续跑完标准模式，再连续跑完极简模式”的顺序仍可能引入时间因素。后半段运行可能碰上不同的网络负载、服务限流、缓存状态或依赖下载情况。尤其是任务持续数十分钟时，这些外部条件足以改变墙钟时间。

一个简单的改进是交错执行：先运行标准模式第 1 次，再运行极简模式第 1 次，随后回到标准模式第 2 次。若比较三种预设，可以预先写下执行顺序，例如：

```text
第 1 轮：标准 -> 极简 -> PTC
第 2 轮：极简 -> PTC -> 标准
第 3 轮：PTC -> 标准 -> 极简
```

这不能消除随机性，却能避免某一种预设总是占用同一时间段。每轮开始前，恢复到相同 Git 提交，清理上一轮生成的构建产物与临时文件，检查依赖没有被 Agent 修改。若必须保留缓存，应让所有预设在相同缓存规则下运行，并在报告中说明。

还应设定失败处理规则。例如，HTTP 超时、模型限流、工具权限拒绝、测试失败和任务越界分别算什么状态，是否允许重试，重试后如何记账。若一组失败后不断人工补充提示，另一组失败就直接结束，两边已不再满足相同的实验条件。

## 选择能区分预设差异的任务

一个任务只覆盖一种工作方式，很难说明预设的适用边界。若要写一篇有解释力的对比，可以准备两到三类任务，但每个任务都要独立验收，而不是把它们的时间简单相加。

| 任务类型 | 例子 | 主要观察点 |
| --- | --- | --- |
| 受控编码 | 修复一个已有最小复现的测试失败 | 通过率、修改范围、人工修正时间 |
| 信息不完整的项目任务 | 找到入口、确认依赖、补充测试 | 搜索与规划是否减少返工、是否遗漏规则 |
| 规则明确的批处理 | 扫描配置并生成缺失字段清单 | 范围是否准确、轮数、结果是否可复核 |

极简模式可能在受控编码任务中减少工具选择带来的变量；标准模式可能在信息不完整任务中因为具备检索和计划能力而少走弯路；PTC 可能更适合第三类任务。这里使用的是待验证的任务假设，不是预先给出的胜负结论。每类任务都应单独写出“为什么选择它”“允许哪些操作”“完成条件是什么”。

如果预算只够测试一个任务，也要在结论中说明它只代表该类任务，不要把它命名成“全面性能对比”。测评的外推范围越小，结论越可信。

## 测量前先确认每个预设实际加载了什么

预设名称不是稳定的能力说明，发行版本更新后，同名预设的工具、提示词和工具呈现方式可能发生变化。因此测评前应从当前 Harness 版本的 `preset.yml` 和 `agent.cordis.yml` 导出或记录配置摘要，而不是只在结果表中填写“标准模式”“极简模式”“PTC 模式”。

以 `dsh@0.1.1-rc.2` 的官方配置为例，极简模式只有固定 persona、持久 Shell 和文件编辑器，且没有上下文压缩；PTC 则是在标准能力上通过 `tool-presentation` 启用 Code Mode。两者的测试结果因此不能解读成“同一工具集在不同开关下的表现”，而是不同工具边界与调用方式共同作用的结果。[极简预设](https://github.com/deepseek-ai/DeepSeek-Harness/blob/b150a551b8d465e31e418e1b2eaf5e79bbb7d28e/apps/cli/config/agent-presets/minimal/agent.cordis.yml)与 [PTC 预设](https://github.com/deepseek-ai/DeepSeek-Harness/blob/b150a551b8d465e31e418e1b2eaf5e79bbb7d28e/apps/cli/config/agent-presets/code/agent.cordis.yml)都应作为报告附件或来源。

一个实用的配置摘要表可包含：

| 项目 | 记录方式 | 为什么需要记录 |
| --- | --- | --- |
| Harness 版本与 commit | CLI 版本、包版本或仓库提交 | 同名预设会随版本调整 |
| persona 与附加指令 | 配置路径、哈希或脱敏摘录 | 提示词本身会改变工作方式 |
| 工具类别 | 文件、终端、Web、计划、子 Agent、Code Mode | 解释任务路径的差异 |
| 上下文策略 | 是否包含快照、压缩和裁剪设置 | 长任务中会影响可见信息 |
| 审批与沙箱策略 | 当前部署的实际设置 | 区分预设差异与权限拒绝 |

没有这张表时，测到的可能只是某个版本的隐含配置差异。它仍然是有价值的观察，但不能被写成跨版本、跨部署的模式结论。

## 分开记录排队时间、执行时间和人工等待

墙钟时间是读者最直观的指标，却经常混入无法归因的等待。一次任务从点击到结束可能包括模型排队、网络传输、工具执行、依赖下载、人工批准和 Agent 自身的思考。若只记录一个总分钟数，后续无法解释两次差异到底来自哪个环节。

建议至少在日志或手工表中标记以下时间点：任务提交、首个模型输出、首个工具调用、最后一个工具完成、最终回答、人工介入开始与结束。对能取得的系统日志，可进一步记录每次工具调用的开始、结束和结果。这样汇总时可以同时给出总墙钟时间、工具执行累计时间与人工等待时间，而不是把环境拥塞误归因给某个预设。

不要求每一次小测都做精确性能剖析。若工具平台无法提供这些时间点，报告只需诚实写“仅记录端到端墙钟时间，无法分离服务端排队与工具时间”。缺少细粒度数据时不要用“模型推理更快”解释总耗时差异。

## Token 数据也需要一致的口径

预设比较常会看到输入 Token 差异，但这个数字可能包含系统提示词、工具说明、历史消息、缓存读取或压缩后的摘要。每次运行应使用同一提供方、同一计数口径和同一历史策略，并记录报告字段来自客户端估算还是 API 的 `usage`。

若极简模式输入 Token 较少，这只说明该运行中被计入上下文的内容较少；它不能单独证明任务更容易、更便宜或最终质量更高。若 PTC 总轮数较少，也要同时检查单次程序是否携带更多输入、是否因重试产生额外调用。把 Token、工具轮数和通过率放在同一张表里，才能避免只挑其中一个有利指标。

## 如何处理不通过、部分完成和人工介入

性能表格中最容易被隐藏的信息，是那些没有成功完成的运行。一个预设可能很快产出一个看似可用的结果，却没通过测试；另一个预设耗时更长，但完成了所有验收。把前者的最短耗时和后者的通过耗时直接比较，没有实际意义。

建议为每次运行使用明确状态：

| 状态 | 含义 | 是否进入耗时比较 |
| --- | --- | --- |
| `PASS` | 通过所有预先定义的完成条件 | 进入主比较 |
| `PARTIAL` | 完成一部分，但存在明确缺口 | 单独报告，不与 PASS 混算 |
| `FAIL` | 未完成、越界或关键测试失败 | 记录原因，不进入通过样本中位数 |
| `INFRA_ERROR` | 网络、服务、权限或环境故障导致无法判断 | 保留原始错误，按预先规则决定是否重跑 |

人工介入也必须量化。可以记录介入次数、每次新增提示的内容类别、人工修正分钟数和是否改变了任务边界。不是所有人工干预都意味着测试无效，但它改变了“Agent 独立完成”的含义。报告中把它写出来，读者才能判断结果适合自动化还是适合人机协作。

## 从原始记录到条件化结论

收集完每次运行的表格后，先检查原始记录完整性：每一行是否有对应的提示词、日志或对话轨迹、Git Diff、验收输出和异常说明。缺少这些材料时，宁可把该行标为不可用，也不要用回忆补数值。

然后按如下顺序汇总：

1. 先报告每种预设的总运行次数与 `PASS` 次数。
2. 只对 `PASS` 样本计算中位耗时、Token 和工具调用轮数。
3. 将 `PARTIAL`、`FAIL`、`INFRA_ERROR` 列为单独表格，并写出原因。
4. 对比 Diff 与人工修正时间，确认更快的样本没有把成本转嫁给人工。
5. 最后再用任务类型和环境限制解释结果，而不是反过来寻找支持某种预设的数字。

这样形成的结论可以既清楚又克制。例如：“在固定版本、相同仓库提交和三次受控编码运行中，极简模式的通过样本中位耗时较标准模式更短；但该任务不涉及搜索、长上下文和外部工具，因此不能外推到信息不完整的项目任务。”它说明了观察到的差异，也没有把一次局部实验包装成通用规律。

## 如何把测评结果转化为团队规则

最后一步不是宣布某种模式永远默认，而是根据证据制定简单的使用条件。比如：已知修改范围且有本地测试的任务允许先试极简模式；需要检索、计划或跨模块排查的任务默认标准模式；输入范围明确的批处理必须先做 PTC 只读试运行；创造模式只用于预设和插件开发。

这些规则应附上复测条件。Harness 版本、模型、工具实现和项目类型变化后，过去的结果可能不再适用。每隔一段时间用相同任务重新运行小样本，或在重大升级后复验关键工作流，比长期依赖一次旧测评更可靠。

## 如何写出不夸大的结果

可以按下面的格式报告：

```text
在 [日期]、[Harness 版本]、[模型与设置]、[仓库提交] 和 [任务描述] 条件下，
[预设 A] 运行 [n] 次，其中 [x] 次通过验收；[预设 B] 运行 [n] 次，其中 [y] 次通过验收。
在通过样本中，A 的中位墙钟耗时为 [a]，B 为 [b]。
这说明在该任务和环境下，B 的耗时较 A [减少/增加] [百分比]。
该结果不代表 B 在其他模型、项目或任务类型中同样有效。
```

这段话保留了结论，也明确了条件和边界。比起一句“极简模式性能暴增”，它更方便其他人复现或指出差异来自哪里。

## 常见测评错误

**只跑一次。** 单次结果应标为单次观察，不应推广成模式结论。

**任务和验收标准不一致。** 两次都“做出了页面”不等于结果可比，必须检查功能、测试和改动范围。

**忽略人工时间。** Agent 少花了 5 分钟，但人工多花 20 分钟修复，整体效率并没有提升。

**将 Token 和成本混为一谈。** Token 用量不等于成本。不同模型的输入、输出、缓存和推理计费规则不同，若要比较成本，必须记录测试时的价格口径。

**把预设和模型混在一起。** 极简模式下的一个模型表现更好，不等于任何模型切到极简模式都会更好。

## 结论

预设测评的核心不是找出一个“最快模式”，而是识别某种工具组合在哪类任务中更合适。固定变量、先验收质量、重复运行、保留原始记录，才能把体感转化为可解释的结论。

在没有完整测试条件和原始记录前，最好把“更快”写成个人观察，而不是通用性能承诺。这样得到的报告更可信，也更能指导下一次模式选择。
