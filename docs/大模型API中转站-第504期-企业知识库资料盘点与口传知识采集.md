# 企业知识库第一步怎么做：资料盘点与口传知识采集

很多知识库项目从“把文件上传进去”开始，最后却卡在回答不准。问题往往不在向量库或模型参数，而在于项目团队并不知道哪些资料真正有效：一份 PDF 可能是旧版本，一张扫描图可能在打印时就有错误，一个关键规则也可能只存在于老员工的经验里。

如果这些问题没有在入库前被发现，系统越准确地检索原文，错误就越稳定地被回答出来。

这篇文章聚焦知识库建设前的资料盘点：文件怎么找、版本怎么判、口传经验怎么采集，以及哪些内容应该暂缓入库。

## 一、先定义“资料盘点”要交付什么

资料盘点不是列一个文件名清单。

一份可交付的盘点结果，至少应该回答：

```text
资料在哪里？
谁负责确认？
哪个版本有效？
哪些内容允许被检索？
哪些内容需要人工复核？
哪些缺口只能通过访谈补齐？
```

建议最终交付四张表：

| 表格 | 作用 |
| --- | --- |
| 资料目录表 | 记录文件、位置、负责人和更新时间 |
| 可信度表 | 记录版本、来源、冲突和复核状态 |
| 知识缺口表 | 记录文档没有覆盖的问题 |
| 访谈问题表 | 记录需要向业务人员确认的事项 |

这四张表比一个“已上传文件数”更能说明项目准备程度。

## 二、不要只找正式文件

第一次盘点时，常见做法是让客户把制度、手册和产品说明打包发来。

这一步有必要，但不够。

还要检查以下位置：

```text
共享盘和个人电脑。
邮件附件和群聊文件。
ERP、OA、CRM 的导出表。
纸质档案和扫描 PDF。
售后工单与维修记录。
销售给客户的非正式说明。
```

正式文件说明“应该怎样做”，工单和聊天记录往往说明“实际怎样做”。

两类资料都要进入盘点范围，但不能自动放在同一可信度等级。

## 三、建立资料目录表

目录表的第一版可以很简单：

| 字段 | 示例 |
| --- | --- |
| asset_id | DOC-001 |
| 文件名 | 产品A安装手册 |
| 来源位置 | 共享盘/研发/产品A |
| 资料类型 | PDF、表格、图片、邮件 |
| 业务域 | 安装、售后、认证 |
| 负责人 | 研发部张某 |
| 创建时间 | 记录原始元数据 |
| 最后更新时间 | 记录文件时间或系统时间 |
| 当前状态 | 待复核、有效、过期、禁止入库 |
| 备注 | 版本冲突或格式问题 |

不要把“文件存在”直接等同于“文件可用”。

状态字段必须允许出现“待复核”。

如果所有文件一导入就标为有效，后续就很难追踪错误来源。

## 四、版本冲突要先登记再处理

同一产品经常有多个版本：

```text
研发版手册。
销售版彩页。
客户定制版说明。
旧项目交付文档。
```

它们可能描述同一个参数，却给出不同答案。

发现冲突时，不要先凭文件名猜“最新版本”。

建议按以下顺序核对：

1. 谁发布了这份资料；
2. 是否有审批或变更记录；
3. 资料对应哪个产品批次；
4. 最后更新时间是否可信；
5. 现场实际执行的是哪一个版本。

如果仍然不能判断，就把冲突交给业务负责人确认，并在知识库中保留“待确认”状态。

## 五、扫描文件要同时检查图像和文字

复杂 PDF 不能只看 OCR 文本。

检查至少包括：

```text
原始页面是否完整。
文字方向是否正确。
小数点和单位是否丢失。
表格列是否错位。
图片中的尺寸标注是否被忽略。
页码和版本号是否仍可追溯。
```

建议保留三个对象：原文件、解析文本和抽检记录。

解析文本用于检索，原文件用于回看，抽检记录用于证明转换没有静默改变内容。

如果图片、尺寸和不规则表格无法稳定解析，人工录入可以是正式方案的一部分。

交付目标是得到可用知识，不是证明每个环节都必须自动化。

## 六、怎样找到只存在于员工脑中的知识

口传知识不会出现在共享盘搜索结果里。

需要通过现场访谈主动找出来。

访谈对象不要只选管理者，还要包括真正处理问题的人：

```text
销售：客户最常问什么？
售后：哪些故障不能按手册处理？
研发：哪些参数在不同批次会变化？
仓储：哪些名称在系统里和现场叫法不同？
质检：哪些异常必须升级处理？
```

每次访谈都要围绕具体案例，而不是泛泛询问“你们有什么经验”。

## 七、用“最近一次出错”打开访谈

员工通常很难一次性讲完整套知识。

但他们往往记得最近一次出错：

```text
上次为什么退货？
哪个参数最容易填错？
哪种客户不能按标准流程处理？
哪个文档看起来正确但不能照做？
```

从错误案例开始，容易追出隐含规则、例外条件和责任边界。

访谈记录不要直接改写成“标准答案”。

先记录原话、案例、适用范围和说话人的岗位，再由业务负责人确认是否可以入库。

## 八、把口传经验转换成可审核条目

一条口传知识至少要拆成五个字段：

| 字段 | 说明 |
| --- | --- |
| 事实 | 发生了什么 |
| 条件 | 在什么情况下成立 |
| 例外 | 哪些情况不能套用 |
| 来源 | 谁提供、来自哪次案例 |
| 审核 | 谁确认可以对外或对内使用 |

例如不要只写：

```text
这个型号不能这样安装。
```

而要追问：

```text
什么型号？
哪种安装方式？
为什么不能这样做？
有没有替代步骤？
谁能确认这条规则？
```

只有条件清楚，检索系统才不会把例外规则误当成普遍规则。

## 九、资料可信度不要用一个总分解决

可以使用分级，而不是假装存在精确的统一分数：

| 等级 | 含义 | 处理方式 |
| --- | --- | --- |
| A | 已审批且近期验证 | 可进入常规检索 |
| B | 来源明确但需要业务复核 | 带复核标记入库 |
| C | 口传经验或历史案例 | 只在限定场景使用 |
| D | 版本冲突或来源不明 | 暂不进入回答 |

等级不是模型的置信度。

它描述的是资料治理状态，必须由业务流程维护。

## 十、先做小范围试点

不要一开始就盘点全公司。

先选择一个业务域，例如某个产品线的售后问题。

试点应包含：

```text
一批正式资料。
一批历史工单。
两到三位业务专家。
一组高频问题。
一次版本冲突处理。
```

试点的目标不是展示页面，而是发现盘点流程本身的缺口。

如果连一个产品线都无法确认资料负责人、有效版本和验收问题，就不适合立刻扩大范围。

## 十一、资料入库前的最小验收

入库前可以设置以下检查点：

```text
文件来源已记录。
负责人已指定。
版本状态已确认。
敏感内容已标记。
解析结果已抽检。
冲突内容已处理或隔离。
口传条目已有审核人。
```

缺少其中任何一项，都不一定意味着项目停止，但必须留下未完成记录。

“暂不入库”比“先上传再说”更容易控制风险。

## 十二、常见失败方式

### 失败一：只接收老板发来的文件

老板能说明目标，但不一定知道一线使用的文件和例外流程。

### 失败二：把文件修改时间当成有效版本

文件被复制、重命名或重新上传后，时间信息可能已经失真。

### 失败三：把员工经验直接写成事实

经验需要限定适用范围，并由责任人确认。

### 失败四：为了自动化比例强行识别复杂 PDF

如果关键字段识别不稳，人工校对往往更适合交付。

## 十三、这项工作怎样写进项目范围

资料盘点和数据治理经常被默认包含在知识库项目里。

实际签订工作范围时，建议明确：

```text
客户需要提供哪些资料。
交付方负责盘点到什么深度。
访谈包含哪些部门和时长。
资料清洗、重印和数字化是否另计范围。
业务审核由谁完成。
缺少前置条件时怎样调整计划。
```

如果进场后发现大量纸质资料和历史错误，不要默默把第二个项目塞进第一个项目。

可以先完成约定的知识库范围，再把数据治理列为新的工作包。

## 十四、结论

企业知识库的第一步不是选模型，而是确认准备交给模型的知识到底是什么。

资料盘点要同时看文件位置、版本、来源、权限和真实使用方式。

口传知识要通过具体案例访谈，再转成带条件、来源和审核人的知识条目。

当一份资料无法证明有效时，保留“待复核”比强行入库更稳妥。

只有先建立这套资料账本，后面的检索、权限、测试和验收才有清晰的输入。
