# 【大模型API中转站】第183期 AI排查慢查询 | Explain索引和N+1

本文是【大模型API中转站】系列的第183篇。本系列致力于用最低的成本、最清晰的方法，帮你打通多模型API的任督二脉。建议先收藏，随用随查。

系统慢，不一定是模型慢。

很多时候是数据库慢。

表现可能是：

```text
接口 504。
页面加载慢。
队列积压。
AI 总结任务卡住。
RAG 检索慢。
后台报表跑很久。
```

慢查询很适合用 AI 分析。

但前提是给证据：

```text
SQL。
Explain。
表结构。
索引。
数据量。
调用频率。
业务场景。
```

不要只说：

```text
数据库慢，怎么优化？
```

## 1. 给 AI 的慢查询排错包

```text
【现象】
- 哪个接口慢：
- 平均耗时：
- P95/P99：
- 影响范围：

【SQL】
- 脱敏 SQL：
- 参数类型：
- 调用频率：

【Explain】
- Explain / Explain Analyze 输出：

【表】
- 表结构：
- 行数：
- 当前索引：
- 关联表：

【业务】
- 是否分页：
- 是否排序：
- 是否模糊搜索：
- 是否多租户过滤：

【边界】
- 不直接删除索引
- 不直接跑生产变更
- 先给只读分析
```

## 2. 常见根因一：缺索引

最常见。

where 条件里用：

```sql
where tenant_id = ? and status = ? and created_at > ?
```

但索引只有：

```text
created_at
```

数据库可能扫描很多行。

AI 可以根据 Explain 判断：

```text
是否全表扫描。
是否使用了错误索引。
是否需要复合索引。
索引字段顺序是否合理。
```

但加索引是生产变更。

要人工确认。

## 3. 常见根因二：N+1 查询

ORM 很容易写出 N+1。

表现：

```text
一个列表接口查 1 次列表。
然后每条记录再查一次用户、标签、评论。
```

AI 要看：

```text
SQL 日志里是否同类查询重复几十次。
代码里是否循环 await。
ORM 是否开启 eager loading。
```

修复：

```text
批量查询。
join。
include。
预加载。
缓存。
```

Fable 5 适合做代码和 SQL 联合审查。

## 4. 常见根因三：深分页

```sql
limit 20 offset 100000
```

offset 越深越慢。

解决：

```text
游标分页。
基于 id 或 created_at 翻页。
避免深 offset。
```

AI 要结合业务判断：

```text
用户是否真的需要跳到第 5000 页。
还是只需要下一页。
```

## 5. 常见根因四：排序和模糊搜索

```sql
order by created_at desc
```

如果没有合适索引，排序会慢。

模糊搜索：

```sql
where name like '%abc%'
```

普通索引可能用不上。

AI 可以建议：

```text
全文索引。
搜索引擎。
前缀搜索。
异步报表。
```

但不要让它盲目加索引。

索引也有写入成本。

## 6. 与 4SAPI 的关系

很多 AI 应用会把模型结果写库。

如果写库慢，会导致：

```text
模型调用成功，但接口超时。
队列积压。
重复提交模型任务。
成本升高。
```

所以日志要串起来：

```text
request_id
model_task_id
db_query_id
duration_ms
```

这样 Fable 5 能判断：

```text
到底是模型慢，还是数据库慢。
```

## 7. 常见根因五：锁等待和连接池

慢不一定是 SQL 本身慢。

也可能是：

```text
锁等待。
连接池耗尽。
长事务占住资源。
后台任务批量写入。
报表任务和在线请求抢库。
```

AI 排查时要看：

```text
当前活跃连接。
等待事件。
事务持续时间。
锁信息。
连接池配置。
```

Postgres 可以看：

```sql
select state, wait_event_type, wait_event, count(*)
from pg_stat_activity
group by state, wait_event_type, wait_event;
```

给 AI 时不要贴敏感 SQL 参数。

只保留结构和等待类型。

## 8. 索引变更要有审查

AI 很容易建议：

```text
加索引。
```

但索引不是免费的。

加索引会影响：

```text
写入速度。
磁盘空间。
迁移时间。
锁表风险。
查询优化器选择。
```

所以让 Fable 5 输出索引建议时，要要求：

```text
为什么需要这个索引。
覆盖哪个查询。
字段顺序依据。
是否有现有索引可复用。
写入成本。
是否需要在线建索引。
回滚方案。
```

Prompt：

```text
请审查这个索引建议是否适合生产。
不要只给 create index 语句。
必须说明收益、风险、验证方式和回滚方式。
```

## 9. 慢查询报告模板

每个慢查询都应该沉淀成一份小报告。

```text
# 慢查询报告

接口：
SQL：
平均耗时：
P95/P99：
调用频率：
Explain 结论：
主要瓶颈：
建议方案：
风险：
验证方式：
回滚方式：
```

如果这个接口会触发模型调用，还要补：

```text
是否影响 4SAPI 调用等待时间。
是否导致任务重试。
是否增加模型成本。
```

这能把数据库优化和 AI 成本治理连起来。

## 10. 不要让 AI 只看单条 SQL

慢查询有时是系统性问题。

比如：

```text
同一页面发 20 个接口。
每个接口 200ms。
页面总耗时 4 秒。
```

单条 SQL 看起来都不慢。

但组合起来就慢。

给 Fable 5 的材料可以包括：

```text
页面请求瀑布图。
多个接口耗时。
每个接口 SQL 数量。
是否存在重复查询。
```

让它判断：

```text
应该优化单条 SQL，还是合并接口、缓存、预加载。
```

## 11. 实战补充：把慢查询和模型任务放进同一条链路

AI 应用里的慢查询，常常会被误判成模型慢。

比如用户点击“生成报告”以后，接口 30 秒才返回。

日志里看到 Fable 5 调用了 20 秒，就以为模型是瓶颈。

但完整链路可能是：

```text
读取用户资料 3 秒。
读取历史记录 6 秒。
调用 4SAPI 20 秒。
写入报告结果 8 秒。
发送通知 1 秒。
```

这时只优化模型没有用。

要做的是给每一段打点：

```text
request_id
db_query_id
model_task_id
queue_job_id
stage
duration_ms
status
```

然后让 AI 分析：

```text
每个阶段耗时占比。
是否存在重复 SQL。
模型等待是否被数据库等待放大。
失败重试是否重复写库。
```

4SAPI 负责模型侧日志，业务系统负责数据库侧日志。

两边用同一个 `request_id` 串起来，Fable 5 才能判断：

```text
该降模型成本。
还是该加索引。
还是该把写库改成异步。
还是该把报表预计算。
```

如果没有链路 ID，AI 只能看到一堆碎片。

有了链路 ID，它就能像做事故复盘一样，把慢查询、模型耗时和用户体验连起来。

## 12. AI Prompt

```text
你是数据库慢查询排查助手。

请根据 SQL、Explain、表结构、索引、数据量、调用频率和业务场景，判断慢查询原因属于：
1. 缺少索引
2. 索引顺序不合理
3. N+1 查询
4. 深分页
5. 排序或模糊搜索慢
6. 锁等待
7. 返回数据过大
8. 应该异步化或预计算

要求：
- 不直接建议生产执行 DDL。
- 给只读验证方法。
- 区分短期止血和长期优化。
- 每个建议说明风险。
```

## 13. 总结

慢查询不要凭感觉优化。

要给 AI：

```text
SQL。
Explain。
索引。
数据量。
调用频率。
业务场景。
```

Fable 5 适合跨代码、ORM、SQL、业务场景做判断。

4SAPI 负责把模型调用耗时和数据库耗时放到同一条链路上。

一句话：

```text
慢查询先 Explain，再谈优化。
```
