# 从 intent.md 到 spec.md：AI 原生开发如何减少需求交接损耗

AI 编码工具让实现速度变快以后，很多团队首先感受到的不是轻松，而是前面的需求流程变慢了：一个小功能几小时就能写出代码，产品负责人却仍要等待排期、需求评审、设计评审和开发澄清。代码生成提速了，需求在交接中丢失的背景和约束却没有自动回来。

一个实用的改法，是把需求交接拆成几个可以提交、审阅和追踪的文件：先用 `intent.md` 捕获意图，再用 `spec.md` 固化需求与设计，最后进入工程计划和代码实现。

这篇文章聚焦一条版本化产物链，说明如何把模糊想法逐步变成工程团队可以执行、审阅和追踪的规格。

## 一、传统交接为什么容易失真

传统流程通常是：

```text
想法 → 需求池 → 用户故事 → 估点 → 设计稿 → 开发任务 → 代码
```

每一次交接都可能发生三种变化：

```text
原始目标被压缩成字段。
背景和约束被留在会议里。
没有人能确认当前版本是否仍然解决原问题。
```

这些流程并不是没有价值。

它们诞生于实现成本高、项目周期长的环境，主要作用是让不同角色提前对齐。

当 Agent 能在几小时内生成大量代码时，原有流程可能变成新的排队点。

## 二、intent.md 记录的不是解决方案

`intent.md` 的作用是保留“为什么做”和“要解决什么”。

它不应该提前写成完整技术设计，也不应该把所有实现细节交给产品负责人猜。

一份最小意图文件可以包含：

```text
想要什么结果。
为什么现在要做。
影响哪些用户和系统。
有哪些明确约束。
目前还没想清楚什么。
什么情况算成功。
```

例如，不要只写：

```text
增加一个导出按钮。
```

可以写成：

```text
销售需要把筛选后的客户列表交给线下团队处理。
当前导出只能复制页面，超过 1000 条记录时会丢失筛选条件。
目标是导出与当前筛选完全一致的数据，并保留导出时间和操作者。
不能导出没有权限查看的字段。
仍需确认：导出文件是否允许包含客户电话。
```

这份文件把目标、问题和开放问题放在同一个可审阅对象里。

## 三、意图文件的边界

`intent.md` 不应该承担以下内容：

```text
具体数据库字段设计。
最终 API 路由和类名。
完整 UI 像素规范。
没有验证过的性能承诺。
把未知问题直接写成确定答案。
```

这些内容应该在设计阶段被补齐，而不是在意图阶段假装已经确定。

好的意图文件要允许不确定性存在。

把“还没想清楚的问题”公开写出来，反而能让下一阶段优先处理真正的风险。

## 四、谁来起草，谁来接受

意图可以由产品、运营、客服或业务负责人用自然语言起草。

Agent 可以帮助整理结构、补充遗漏问题，但不能替负责人决定业务目标。

推荐的责任分工是：

| 角色 | 负责什么 |
| --- | --- |
| 发起人 | 描述问题、用户和期望结果 |
| Agent | 提问、整理和标记不确定项 |
| 产品负责人 | 确认目标、范围和优先级 |
| 技术负责人 | 在高风险技术问题上提供意见 |
| 评审人 | 检查意图是否可进入设计 |

接受动作要留在版本控制里。

可以通过合并、批准 review 或关闭 review 记录“接受”或“拒绝”，不要只在群聊里说“可以了”。

## 五、意图目录怎么组织

如果意图主要服务一个代码仓库，可以放在同一个仓库：

```text
repository/
├── intent/
│   ├── 2026-09-export-filtered-customers.md
│   └── 2026-09-audit-log.md
├── docs/
├── src/
└── tests/
```

这样做的好处是意图、规格、计划和代码距离很近，后续容易追踪。

如果一个意图会同时影响多个仓库，才考虑单独的意图仓库。

否则，单独仓库会增加链接、权限和同步成本。

## 六、从 intent.md 生成 spec.md

设计阶段的输入是已经接受的 `intent.md`。

输出的 `spec.md` 应该回答：

```text
系统要支持哪些行为。
用户看到什么结果。
哪些输入无效或不允许。
需要修改哪些模块。
怎样验证功能完成。
有哪些安全、合规和体验约束。
```

可以把需求和设计放在一次会话里生成，但最终规格仍然要由负责人审阅。

Agent 负责产出候选方案，人负责确认业务和风险。

## 七、spec.md 不等于代码实现计划

规格说明描述“系统应该怎样工作”。

工程计划描述“这次准备怎样修改仓库”。

两者不能混成一份文件，否则设计变化时很难判断是需求变了，还是实现路径变了。

一个简单区分是：

| 文件 | 主要回答的问题 |
| --- | --- |
| intent.md | 为什么做、为谁做、要达成什么 |
| spec.md | 功能和约束应该是什么 |
| plan.md | 具体改哪些文件、按什么顺序做 |
| diff | 实际改了什么 |
| test output | 结果是否通过 |

## 八、规格评审要先处理关注点

Agent 生成 `spec.md` 时，应主动标记：

```text
需求之间的冲突。
缺少业务决定的问题。
高风险数据流。
无法满足的性能或兼容条件。
需要技术负责人确认的方案。
```

产品负责人先处理这些关注点，再让工程团队开始构建。

这样可以把原来开发中途才暴露的争议，提前放到规格评审阶段解决。

## 九、不要把“自动生成”误解成“自动接受”

从意图自动生成规格，可以减少整理和翻译时间。

但生成并不代表批准。

建议保留一个清晰的门：

```text
intent.md 已接受 → 生成 spec.md → 产品负责人审阅 → spec.md 被接受 → 进入工程计划
```

自动化可以负责触发、生成、检查和创建 review。

接受动作仍然应有明确责任人。

## 十、把组织规则作为输入

规格生成不能只读取业务意图。

还需要读取当前有效的：

```text
安全规则。
合规要求。
品牌和 UX 规范。
架构约定。
数据分级规则。
测试和发布条件。
```

这些规则可以保存在项目规则文件、Skill 或模板中。

但规则本身也要版本化，否则同一个意图在不同时间可能生成无法比较的规格。

## 十一、如何判断规格是否足够清楚

可以让一个没有参加前面讨论的工程师只读 `spec.md`，回答以下问题：

```text
要改哪些用户行为？
哪些情况必须拒绝？
数据从哪里来，流向哪里？
怎样证明已经完成？
哪些问题仍需人工决定？
```

如果工程师必须重新翻聊天记录才能开始，说明规格还没有成为独立产物。

## 十二、规格变更怎样留痕

一旦 `spec.md` 被接受，后续变化不要直接覆盖原文。

建议：

```text
提交新的版本。
写明变化原因。
列出受影响的计划和测试。
重新请求对应负责人接受。
```

如果只是拼写修正，可以走轻量 review。

如果改变用户行为、权限或数据范围，就应重新打开设计门。

## 十三、领先指标和滞后指标

产物链的价值之一，是可以从 Git 和 review 记录取得度量。

可以观察：

| 指标 | 说明 |
| --- | --- |
| 意图提交时间 | 从第一次讨论到形成初稿的时间 |
| 规格生成时间 | 接受意图到提交规格的时间 |
| 规格返工次数 | 规格被接受前修改了几次 |
| 构建后需求返工 | 计划提交后规格又改了几次 |
| 接受比例 | 意图进入设计的比例 |

这些指标不能直接证明效率提升，但能帮助定位瓶颈是在表达、决策还是实现。

## 十四、常见失败方式

### 失败一：把意图写成一句口号

“提升体验”没有用户、范围和验收条件，Agent 只能自行猜测。

### 失败二：让 Agent 代替产品负责人做取舍

Agent 可以列出冲突和方案，不能替组织承担业务决定。

### 失败三：规格和计划混为一谈

需求变化后，团队无法区分是目标变了还是实现方式变了。

### 失败四：自动生成后没人接受

文件提交不等于流程通过，必须保留责任人的接受动作。

## 十五、最小落地步骤

小团队可以只做六步：

```text
1. 在仓库建立 intent/ 目录。
2. 用模板记录目标、约束和开放问题。
3. 让 Agent 提问并整理 intent.md。
4. 产品负责人在 review 中接受或拒绝。
5. 根据已接受意图生成 spec.md。
6. 只有 spec.md 被接受后才开始写代码。
```

先让两三个真实需求走通，不要一开始就做复杂的全自动编排。

## 十六、结论

AI 原生开发的第一步，不是让 Agent 更早写代码，而是让原始意图在进入代码前变成一个可读、可审阅、可追踪的产物。

`intent.md` 保留为什么做，`spec.md` 固化应该怎样工作，`plan.md` 再把它翻译成工程动作。

自动化可以减少整理和交接，但接受、范围变化和高风险决定仍然需要明确的人负责。

当每一步都能从版本记录中找到来源，需求就不再只存在于某次会议或某段聊天里。
