# GPT-6.1 Terra 档位怎么选：把返工成本算进每个已解决任务

GPT-6.1 Terra 有六个推理档位：`none`、`low`、`medium`、`high`、`xhigh`、`max`。第三方评测机构测得，家族内每任务成本从 low 档的 $0.05 到 max 档的 $0.40，相差 7.4 倍。

只看这组数字，答案很简单：能用低档就用低档。

但每任务成本只算了一半账。另一半是**错了以后谁来改、改一次要多少钱**。这篇只回答一个问题：怎么把返工成本算进去，再决定档位。

## 先把两组数字放在一起

| 指标 | low 档 | max 档 | 来源 |
| --- | --- | --- | --- |
| 每任务成本 | $0.05 | $0.40 | Artificial Analysis 发布页，2026-10-26 |
| 易错提示错误率 | 16.7% | 4.3% | OpenAI 官方博客，2026-10-26 |
| 对应通过率 | 83.3% | 95.7% | 由错误率换算 |

来源：[Artificial Analysis · GPT-6.1 Terra 发布页](https://artificialanalysis.ai/models/releases/gpt-6-1-terra)、[Introducing GPT-6.1 Terra](https://openai.com/index/introducing-gpt-6-1-terra/)。

需要先说明：这两组数字不是在同一批任务上测的。每任务成本来自第三方的 Intelligence Index，错误率来自官方的"易错提示"内部基准。把它们放在一起只是为了演示算法，不代表任何具体业务的真实数字。

## 第一笔账：只算模型成本

用"每个已解决任务的成本 = 每任务成本 ÷ 通过率"来算：

| 档位 | 每任务成本 | 通过率 | 每个已解决任务成本 |
| --- | --- | --- | --- |
| low | $0.05 | 83.3% | 约 $0.060 |
| max | $0.40 | 95.7% | 约 $0.418 |

只算模型成本，low 档便宜约 7 倍。这也是大多数人直觉上选低档的原因。

## 第二笔账：把返工算进去

现实里，错的那部分不会自己消失。它要么被人改，要么流到下游造成损失。设每个错误的处理成本为 R（人工复核、修改、重跑、客诉），则：

```
每个已解决任务的总成本 = (每任务成本 + 错误率 × R) ÷ 通过率
```

代入两档数据，看 R 取不同值时的结果：

| 每个错误的处理成本 R | low 档总成本 | max 档总成本 | 更便宜的档位 |
| --- | --- | --- | --- |
| $0（错了也无所谓） | $0.060 | $0.418 | low |
| $1 | $0.260 | $0.463 | low |
| $2.5 | $0.561 | $0.530 | **max** |
| $5 | $1.063 | $0.643 | **max** |
| $20 | $4.071 | $1.317 | **max** |

交叉点大约在每个错误 $2.5 左右。也就是说：**只要一个错误需要人花几分钟去处理，max 档就更便宜**。

这个交叉点会随你的真实错误率变化，但结构不会变：错误处理成本越高，低档越不划算。

## 什么样的任务 R 很低

R 接近 0 的任务，才是低档的主场：

| 任务 | 为什么 R 低 |
| --- | --- |
| 草稿生成，后面一定有人改 | 错误本来就会被看到 |
| 内部检索、分类打标 | 错一条影响很小 |
| 有自动校验的抽取 | 校验失败自动重跑，不用人 |
| 批量预处理 | 下一步会再过滤 |

R 很高的任务正好相反：财务字段、合同条款、对外发送的内容、会触发真实操作的 computer use。这些任务上用低档，省下的 token 钱很快就会被返工吃掉。

## 档位不是预算参数，是任务属性

这套算法得出的一个推论是：**档位应该按任务定，而不是按预算定**。

常见的错误做法是把档位做成全局配置（比如环境变量统一设成 medium），然后"预算紧就调低一档"。这样做的问题是，同一个系统里既有 R 很低的任务，也有 R 很高的任务，统一调档会让后者的总成本上升。

正确的做法是在任务层面分档：

| 档位 | 用在哪 | 判定信号 |
| --- | --- | --- |
| `none` / `low` | 抽取、分类、格式化、模板化改写 | 有确定性答案，错了一眼能看出来，或有自动校验 |
| `medium` | 读屏操作、填单、看图说话、跨 App 流程 | 官方主推档，失败可观察 |
| `max` | 难编码、多步判断、账目核对、对外内容 | 错误处理成本高，或需要多轮推理 |

`high` 与 `xhigh` 不是不能用，而是需要你自己测出它们在你的任务上有没有"甜点"。没有数据之前，先用两头。

## 默认档位一定要显式写

档位影响这么大，就不能依赖默认值。默认值会随版本变化，从别的模型迁移过来的代码也可能完全没写这个参数。

```python
payload = {
    "model": "gpt-6.1-terra",
    "reasoning": {"effort": TASK_EFFORT[task_type]},  # 按任务类型取值，不依赖默认
    "input": task_prompt,
}
```

把档位写进日志，每条请求都能看到用的是哪一档。没有这一步，后面所有成本分析都无法复现。

## 用自己的数据算交叉点

上面的表只是演示。真正有用的是用你自己的任务算一遍：

```python
def total_cost_per_solved(runs, rework_cost):
    n = len(runs)
    solved = sum(1 for r in runs if r.passed)
    failed = n - solved
    model_cost = sum(r.cost_usd for r in runs)
    total = model_cost + failed * rework_cost
    return total / max(solved, 1)

for effort in ["low", "medium", "max"]:
    runs = [call_model(task, effort=effort) for task in tasks]
    for R in [0, 1, 5, 20]:
        print(effort, R, round(total_cost_per_solved(runs, R), 3))
```

三步就够：

1. 从真实业务里抽 20～50 条任务，写清每条的判定标准；
2. 用 low、medium、max 各跑一遍，记录通过与否和成本；
3. 估一个你自己的 R（一个错误平均要人花多少时间 × 时薪），代入算交叉点。

如果团队通过统一网关调用多家模型，还要多验证一件事：档位参数有没有被网关透传。以可替换实例来说，若通过 4SAPI 这类聚合入口调用，模型名与档位支持范围以该平台控制台当期显示为准；验证方法是同一条 prompt 在不同档位下对比输出 token 与耗时，如果几乎没有差别，说明档位可能被静默忽略了。

## 三个失败信号

| 现象 | 说明什么 | 动作 |
| --- | --- | --- |
| 日志里看不到档位字段 | 用的是默认值，实验不可复现 | 强制显式传参 |
| 成本降了但人工改动变多 | 你在用人力补低档位的错误 | 把人工成本算进 R 重新评估 |
| 成本降了但重试率上升 | 你在用重试补低档位 | 重试也是成本，直接比较总成本 |

第三条最常见。重试一次，模型成本就翻倍，还会拉长交付时间。如果低档需要靠重试才能过，它就不再是便宜的选项。

## 一个反直觉的推论

按每任务成本看，降档是"渐进式降本"：每降一档，便宜一点。

按每个已解决任务的总成本看，降档可能是"阶梯式涨价"：错误率一旦跨过某个阈值，返工成本会盖过省下的 token 费。

这意味着两件事。第一，不要用"先调低一档观察一周"的方式降本，你看到的可能是质量突然变差，而不是成本慢慢下降。第二，降本应该发生在任务分层上：把 R 很低的任务整类挑出来用低档，而不是把高 R 任务的档位拧小。

## 限制与结论

必须说清的边界：本文演示用的每任务成本与错误率来自两个不同的测试集，不能组合成任何真实业务的结论；官方错误率来自刻意偏难的内部基准，日常错误率会更低；R 的估算高度依赖你的业务，本文表格里的 R 只是示例取值。

可以确定的是方法：每任务成本只是一半的账，另一半是错误处理成本；档位应该按任务的错误处理成本来分，而不是按预算统一调；默认档位必须从代码里赶出去。

下一步很具体：挑 20 条你认为错了最麻烦的任务，用 low、medium、max 各跑一遍，估一个自己的 R，算出三条总成本曲线。交叉点落在哪里，就把对应的任务放到哪一档。
