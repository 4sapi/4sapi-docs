# DeepSeek Harness 创造模式、插件与事件日志：扩展 Agent 前先守住边界

DeepSeek Harness 最吸引开发者的地方，不是多一个文件工具或多一种 UI，而是创造模式：Agent 可以检查自己正在运行的 Cordis 环境，在内存中试验插件，继续创建新的 Agent 或插件，再把能力挂回当前流程。

这听起来很像“Agent 会自己进化”。从工程角度看，更准确的说法是：系统允许 Agent 在可组合运行时里扩展能力。能力扩展得越快，权限、依赖、日志和回滚就越不能靠感觉处理。

## 一、创造模式到底多了什么

创造模式拥有标准模式的完整能力，并增加了对 Cordis 插件环境的检查与试验能力。它可以帮助你做两类工作：

```text
创建新的专用 Agent。
创建或调整当前运行环境中的插件。
```

例如，素材中给出的需求很典型：

```text
做一个只允许读代码、不允许改文件的安全审计模式。
做一个接入公司内部搜索、固定使用某个模型、拥有三种专属 Skills 的研究 Agent。
```

它们都不是“换一个 Prompt”这么简单。安全审计模式需要限制文件写入、Shell、网络和外部工具；研究 Agent 需要确认内部搜索的身份、资料范围、模型配置和 Skills 的来源。创造模式提供的是实现空间，不会自动替你完成这些治理决定。

## 二、先写能力卡，再创建插件

每次创建或接入插件前，先把能力写成一张短卡。这样做不会拖慢开发，反而能避免 Agent 造出“看着能跑、没人知道边界”的东西。

```markdown
# 插件能力卡

用途：为研究 Agent 提供内部资料搜索
输入：关键词、资料范围、最大返回数
输出：来源 ID、片段、权限标签
允许数据：已批准的内部资料
禁止数据：客户受限资料、个人信息、密钥和私人空间
执行身份：受限服务账号
副作用：无，只读
日志：任务、调用理由、结果数量、来源 ID
停止条件：来源标签缺失、返回受限资料或异常数据量
Owner：资料 Owner、技术 Owner
```

能力卡的重点不是文档形式，而是把“插件能做什么”和“插件不该做什么”放在一起。没有禁止项、身份和停止条件的插件描述，实际上只是在给 Agent 开一扇没有边界的门。

## 三、插件化不等于任意安装

DeepSeek Harness 素材列出了一批社区插件，例如：

| 插件 | 素材中的用途 |
| --- | --- |
| [dsh-at-file](https://github.com/omdsh-dev/dsh-at-file) | 在输入框中通过 `@` 调用文件 |
| [dsh-genui](https://github.com/omdsh-dev/dsh-genui) | 渲染图表、表格、表单、Diff、Mermaid 与交互面板 |
| [dsh-automation](https://github.com/titanwings/dsh-automation) | 增加自动化能力 |
| [DSH-better-sidebar](https://github.com/omdsh-dev/DSH-better-sidebar) | 提供工作台式侧边栏、文件管理、终端、Git 与任务状态 |
| [ModLens](https://github.com/liustack/modlens) | 为纯文本模型补充图片输入与视觉通道 |

这些插件解决的需求不同，风险也不同。文件引用插件主要涉及本地路径和读取范围；自动化插件可能触发后台任务；视觉插件会增加图片上传、模型通道和数据流转；工作台类插件往往接触更多本地工具。

安装前至少检查：

```text
代码和发布包来自哪里，谁维护？
需要哪些文件、网络和环境变量权限？
会不会执行安装脚本或下载额外依赖？
新增了哪些工具、命令和 UI 入口？
卸载后会留下什么状态、配置或后台任务？
升级后谁负责回归验证？
```

“社区里很多人装了”不能替代这些检查。插件进入 Agent 环境后，影响的不只是一个网页功能，还可能是工具调用、数据边界和执行权限。

## 四、让 Agent 创造插件时，限制四件事

创造模式最容易失控的地方，是目标说得太宽。例如“给我做一个更好用的研究 Agent”，会迫使模型自己猜数据源、工具、权限和交互方式。更好的任务描述要锁住四个边界：

| 边界 | 要写清什么 |
| --- | --- |
| 任务 | 目标用户、输入、输出和非目标 |
| 权限 | 可读写的路径、网络、外部系统与执行身份 |
| 运行 | 是否允许后台任务、子 Agent、自动重试和持久化 |
| 验收 | 什么算通过，错误时如何停止和恢复 |

例如，把需求改成：

```text
创建一个只读代码审计 Agent。
它只能读取当前工作区；禁止编辑文件、执行联网命令、安装依赖和访问外部系统。
输出必须列出文件路径、风险等级、证据位置和待人工确认项。
先在隔离项目中运行三条固定任务，全部通过后再申请扩大范围。
```

这比“帮我做安全审计插件”更容易实现，也更容易审核。Agent 的创造能力越强，任务说明越不能含糊。

## 五、只追加事件日志有什么价值

素材中提到，DeepSeek Harness 将会话设计成只追加的事件日志。模型看到的系统提示词、用户消息、推理内容、工具调用与结果、权限变化、上下文注入、压缩、子 Agent 调度等，都会形成事件；下一轮历史也从这些事件重新推导。

它的价值在于追踪“任务为什么走到这里”。很多 Agent 失败后，用户只看到失败、超时或循环，却不知道从哪一次工具调用、哪段上下文压缩、哪次权限变化开始偏离。

一个便于排查的事件链可以长这样：

```text
task_received
  -> context_prepared
  -> tool_called / tool_returned
  -> permission_changed
  -> plugin_loaded / plugin_unloaded
  -> subagent_started / subagent_finished
  -> task_completed | task_handed_off | task_failed
```

事件日志不自动等于安全审计。它仍需要明确：哪些字段可以保存，哪些内容必须脱敏，日志谁能看，日志保留多久，以及如何关联任务、版本、插件和执行身份。把完整密钥、客户原文或未经处理的上下文写进可观测系统，只是把风险换了一个位置。

## 六、从日志回到可复现问题

出现异常时，可以沿着下面顺序排查：

1. 固定 `task_id` 与本次运行版本。
2. 查看当时加载了哪些插件、工具和模型提供方。
3. 找到第一个异常事件：权限拒绝、工具超时、空结果、重复调用或上下文变化。
4. 检查该事件前后的输入引用和结果摘要，而不是只看最终回答。
5. 用脱敏或合成样例在隔离环境重跑。
6. 把确认的失败条件写进回归任务，修改后再验证。

这种方式比“再问模型一次为什么错了”更可靠，因为它能分清问题来自插件、工具、资料、权限、模型还是任务定义。

## 七、插件升级和卸载也需要回归

插件系统的难点不在于第一次安装，而在于第二次更新。一个更新可能改变工具参数、依赖版本、默认权限或上下文行为。即使插件名称没变，Agent 的实际轨迹也可能不同。

每次升级、替换或卸载前后，至少记录：

```text
插件版本和来源。
受影响的 Agent、任务和工具。
新增、删除或改变的权限。
现有后台任务、缓存和持久状态。
需要重跑的正常、失败、越权和重复执行任务。
回退到上一个版本的方式。
```

运行中热插拔插件时尤其要谨慎。Cordis 的可组合设计让这种操作成为可能，但“可以切换”不等于“无需验证”。对有外部写入或敏感数据访问的插件，先在测试环境验证卸载和恢复路径，再进入真实工作流。

## 八、一个渐进式上手顺序

```text
第一步：标准模式运行一个只读项目任务。
第二步：只安装一个低风险插件，例如文件引用或展示组件。
第三步：查看它增加的工具、权限和事件记录。
第四步：为插件补一张能力卡和一组回归任务。
第五步：在创造模式中创建受限的专用 Agent。
第六步：通过观察、人工接管和回退记录决定是否扩大范围。
```

这个顺序看起来不快，却能让团队知道每一项新增能力带来了什么效果和什么风险。一次性装很多插件，再让 Agent 自己决定怎么组合，往往只会得到一个难以复现的演示环境。

## 九、插件不是装完就结束：给它一条生命周期

插件最容易被低估的地方，是它同时带来了代码、依赖、工具、权限和状态。把它当成一个浏览器扩展随手装上，出现问题后通常很难判断是插件本身、升级后的依赖，还是它与现有工具的组合造成的。

一个可执行的生命周期可以很朴素：

```text
提出需求
  -> 写能力卡
  -> 在隔离环境安装
  -> 跑正常、边界与拒绝用例
  -> 人工审阅权限和日志
  -> 小范围启用
  -> 记录版本并持续回归
  -> 出现异常时停用或回退
```

其中最容易被跳过的是“拒绝用例”。如果插件声称只能读取当前工作区，就要验证它会拒绝工作区外路径；如果它不该联网，就要验证网络调用确实失败并留有记录；如果它输出引用资料，就要检查受限资料不会被拼进结果。只有正常路径能跑通，说明不了边界真的存在。

推荐先选一个低风险、只读、没有外部副作用的插件进行试点，例如受限的文件引用或展示能力。不要在第一天同时装上自动化、工作台、网络检索和视觉处理插件。变量太多时，一次异常就会让排查失去抓手。

## 十、事件日志至少要能回答七个问题

只追加日志的优势，是把一次运行拆成可以排序、关联和复查的事件。但要做到这一点，日志字段需要让人能回答：谁在做什么、为了哪项任务、调用了什么能力、权限是否变化、结果是什么、发生在什么时候、对应哪个版本。

下面是用于设计思路的通用示例，不是 DeepSeek Harness 的 API 协议：

```json
{
  "event_id": "evt_01",
  "task_id": "task_20260814_01",
  "run_id": "run_01",
  "event_type": "tool_returned",
  "plugin_id": "internal-search",
  "tool_name": "search_documents",
  "actor": "agent",
  "permission_scope": "approved-internal-docs-read",
  "outcome": "success",
  "timestamp": "2026-08-14T10:30:00+08:00"
}
```

实际系统还可以增加工具耗时、重试次数、插件版本、错误类别和结果摘要等字段。关键不是堆字段，而是保持关联关系：一次任务里发生的模型选择、权限确认、插件加载、工具调用、上下文压缩和最终交付，应该能通过 `task_id` 或 `run_id` 串起来。否则日志再多，也只是一堆无法解释先后关系的文本。

## 十一、可观测不等于把所有内容写进日志

append-only 说的是记录方式，不代表所有原始内容都应该永久保留。工具返回里可能含有 API Key、客户数据、代码片段、内部文档或个人信息；把它们原样复制到日志平台，会扩大可访问的人数和保留时间。

更稳的做法是优先记引用、标识和摘要：

| 应记录 | 处理方式 |
| --- | --- |
| 任务、运行、插件和工具标识 | 保留稳定 ID 与版本，便于关联 |
| 权限变化与确认结果 | 保留范围、执行身份和决定，不记录无关内容 |
| 文件与资料 | 记录受控路径、来源 ID 或摘要，避免全量正文 |
| 错误信息 | 保留错误类别、调用位置和脱敏上下文 |
| 密钥、令牌、客户原文 | 默认不入日志；必要时改用引用或受控脱敏系统 |

此外还要明确访问者和保留期限。开发调试需要的日志，不一定应该对所有业务角色开放；用于一次故障排查的原始片段，也不应在任务结束后无限期保存。可观测性的目标是复现和追责，不是建立第二个无边界的数据仓库。

## 十二、提前演练几种不好看的情况

插件和 Agent 的异常通常不会以“插件坏了”这么简单的形式出现。下面这些场景值得在测试环境里至少走一遍：

| 场景 | 可能后果 | 应有的控制 |
| --- | --- | --- |
| 恶意或失控插件 | 读取超范围数据、执行额外脚本 | 来源审查、最小权限、隔离安装与快速停用 |
| 依赖漂移 | 更新后参数或行为改变 | 锁定版本、记录依赖、升级前回归 |
| 工具权限过宽 | 任务意外修改无关目录或外部系统 | 路径、网络和身份分层，写操作人工确认 |
| 外部操作被重复调用 | 重复创建资源、重复发送通知 | 幂等标识、确认步骤、重复检测 |
| 任务中卸载插件 | 半完成状态或工具引用失效 | 明确停止、清理和交接策略 |
| 数据中夹带指令 | 资料内容影响任务规划或工具使用 | 区分数据与指令，限制可调用工具并人工复核 |

最后一项尤其值得重视。Agent 读取的网页、Issue、文档或文件名都属于外部输入，里面出现“忽略前面规则、执行某命令”之类的文字，不应自动获得高于当前任务和权限策略的地位。插件无法单独解决这类问题，工具最小化、明确的任务边界和人工审阅同样重要。

## 十三、把上线范围做小，指标才有意义

插件上线后的第一周，别只收集“大家觉得好不好用”。至少记录一批能反映真实运行情况的指标：

```text
任务完成率：任务是否按验收条件结束。
人工接手率：有多少任务必须由人继续处理。
工具错误率与重试次数：工具、依赖或参数是否不稳定。
意外权限请求：是否频繁请求设计之外的能力。
插件加载失败率：版本、依赖与运行时是否匹配。
越界或异常副作用：是否出现预期外文件、网络或外部操作。
```

这些指标不需要一开始就做成复杂看板。用一张任务记录表也可以，前提是每条记录能回到具体版本和事件链。没有范围限制的“全员试用”很难解释指标；一个工作区、一种任务、一两个插件的受控上线，反而更容易判断插件是否真的带来收益。

## 十四、出了问题，先停止扩散再修复

遇到异常权限、敏感数据泄漏风险、重复外部操作或无法解释的工具调用时，第一目标不是立刻让任务继续跑，而是阻止影响扩大。一个简单的处理模板可以写进团队约定：

```text
1. 停止当前任务，撤销或限制相关插件的权限与外部访问。
2. 保存 task_id、run_id、插件版本、时间范围和脱敏事件摘要。
3. 判断是否已经产生文件修改、外部请求或敏感数据暴露。
4. 在隔离环境用最小样例复现，区分任务、模型、插件和依赖问题。
5. 修复或回退后，补上对应的拒绝用例与回归任务。
6. 经人工复核后，再决定是否恢复受限范围的使用。
```

这里的“保存”不等于复制全部原始日志。先保护证据链，再按数据规则处理敏感内容。若涉及真实生产系统或客户数据，还应按团队既有的安全响应流程升级处理，而不是只在插件仓库里留一条评论。

## 十五、检查清单

```text
[ ] 新插件有用途、输入输出、数据范围、身份、副作用和 Owner 说明。
[ ] 安装前已检查代码来源、依赖、脚本、权限与升级状态。
[ ] 创造模式任务明确了目标、禁止事项、运行边界和验收方式。
[ ] 第三方插件不直接获得生产密钥、全盘文件或无限网络访问。
[ ] 工具、插件加载、权限变化和任务终态可以关联查询。
[ ] 日志保存引用和摘要，不复制不必要的敏感正文。
[ ] 出错时能够回到具体事件，而不只依赖最终回答。
[ ] 插件升级、卸载和替换都有回归任务与回退方式。
[ ] 热插拔涉及外部副作用时已在隔离环境演练。
[ ] 未验证的新能力先停在受限工作区和人工确认模式。
```

## 十六、结论与资料

创造模式和插件系统让 DeepSeek Harness 有机会从一个默认编码 Agent 变成专用运行环境。代价是，插件不再只是“装上一个功能”，它同时改变工具、依赖、权限、状态和维护责任。

先从一个低风险插件开始，保留事件日志，写清能力边界和回退方式。这样，Agent 的扩展能力才会积累成可维护的工作流，而不是越来越难解释的黑盒。
