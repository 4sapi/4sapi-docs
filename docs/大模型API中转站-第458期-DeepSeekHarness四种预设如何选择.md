# DeepSeek Harness 的四种 Agent 预设怎么选

同样是让 Agent 完成一个编码任务，有的会先检索文档、列计划、拆子任务，有的则直接打开终端改文件。差异不一定来自模型，也可能来自当前会话加载的预设。

预设决定了 Agent 在一次会话中能用哪些工具、会收到哪些系统指令，以及工具如何呈现给模型。它不是能力等级，也不是单纯的“快慢开关”。选择预设时，真正要判断的是：当前任务需要多少工具，以及这些工具是否会带来额外的判断和维护成本。

依据 DeepSeek Harness `dsh@0.1.1-rc.2` 的内置配置，说明四种预设分别适合什么任务、缺少什么能力，以及如何用一个小任务验证选择是否合理。文中配置核对日期为 2026 年 8 月 22 日；预设内容可能随版本变化。

## 预设解决的是什么问题

Agent 预设更像会话级的工作边界。

标准模式把文件、Shell、网页检索、Skills、计划、目标、子 Agent 和工作流等能力放进同一会话；极简模式只留下持久 Shell 与文件编辑器；PTC 模式仍保留标准能力，但改用 TypeScript 程序编排工具调用；创造模式则额外提供运行时检查、插件试验和预设创作能力。

这些不是猜测。官方仓库的四份 `preset.yml` 分别给出了预设的名称和设计目标：[内置预设配置](https://github.com/deepseek-ai/DeepSeek-Harness/tree/b150a551b8d465e31e418e1b2eaf5e79bbb7d28e/apps/cli/config/agent-presets)。

工具多的好处是遇到未知问题时有更多路径可走，代价是模型需要在更多工具和规则中选择下一步。工具少时，路径更短，但一旦任务需要检索、压缩长上下文或并行协作，就没有额外能力兜底。

## 四种预设的区别

| 预设 | 关键特征 | 更适合的任务 | 不宜优先选择的任务 |
| --- | --- | --- | --- |
| 标准模式 | 完整编码 Agent 工具集 | 需求复杂、需要搜索或规划的日常开发 | 明确且很小的本地修改 |
| 极简模式 | 持久 Shell 和文件编辑器 | 受控的纯编码任务、模型基准比较 | 依赖网络、长会话和协作的任务 |
| PTC 模式 | 用 TypeScript 组合多步工具调用 | 规则清晰的批处理与自动化流程 | 需要每一步根据新信息探索的任务 |
| 创造模式 | 标准能力加预设、插件运行时操作 | 创建自定义预设、验证 Cordis 组合 | 普通代码修改和低风险日常工作 |

### 标准模式：信息不完整时的默认选项

标准模式适合你还不能完全确定任务路径的情况。例如，先要读项目结构、搜索相关实现、确定测试命令，再决定改哪些文件。它提供的计划、检索和子 Agent 能力都能帮助处理这类不确定性。

第一次使用时，可以在测试仓库中给出一条只读任务：

```text
读取当前项目的目录结构和规则文件，列出入口文件、测试命令与可能受影响的模块。
不要修改文件，也不要调用外部系统。
```

预期结果是 Agent 能列出可复核的文件路径和命令来源，而不是直接改代码。若它连目录与测试命令都无法可靠识别，先检查工作区、模型配置和权限边界，不要急着切换模式。

### 极简模式：减少变量，而不是承诺更快

极简模式的系统提示词固定为 `You are a helpful software engineer assistant.`，并关闭运行时上下文快照和上下文压缩。其组成是持久 Bash 或 PowerShell，以及 `str_replace_editor` 文件编辑器；具体实现可见[极简模式配置](https://github.com/deepseek-ai/DeepSeek-Harness/blob/b150a551b8d465e31e418e1b2eaf5e79bbb7d28e/apps/cli/config/agent-presets/minimal/agent.cordis.yml)。

这使它适合控制变量。比如比较两个模型修复同一个小 Bug 的表现时，可以固定仓库提交、任务描述、权限和验收命令，避免搜索、Skills 或工作流成为额外变量。

它不等于在所有任务中更快。极简模式没有联网搜索、任务规划、Skills、子 Agent 和上下文压缩。需求信息不全或任务持续很久时，这些缺失会让 Agent 更依赖提示词和模型本身的判断。

### PTC 模式：把确定的步骤编排成程序

PTC 是 Programmatic Tool Call。它保留标准模式的能力范围，但把工具以 Code Mode SDK 的形式呈现给模型。模型可写一段 TypeScript 程序，再由 `run_code` 执行，从而把原本多次往返的工具调用组合在一起。[PTC 配置](https://github.com/deepseek-ai/DeepSeek-Harness/blob/b150a551b8d465e31e418e1b2eaf5e79bbb7d28e/apps/cli/config/agent-presets/code/agent.cordis.yml)中明确将其描述为“一个 TypeScript 程序组合多步操作”。

它适合“步骤多，但每一步都已经确定”的任务，例如读取一批配置、按同一规则提取字段、生成汇总表，或批量检查项目中的固定模式。

不要把所有多步骤任务都交给 PTC。若每一步都要根据前一步的新发现调整方案，或者任务会修改不可逆资源，逐步执行通常更容易审查和中止。

### 创造模式：用于修改 Agent 的工作方式

创造模式为自定义 Agent 预设而设计。它除了标准能力外，还提供运行时检查、插件试验和预设创作指导。[创造模式配置](https://github.com/deepseek-ai/DeepSeek-Harness/blob/b150a551b8d465e31e418e1b2eaf5e79bbb7d28e/apps/cli/config/agent-presets/cordis/agent.cordis.yml)提示，其中的运行时挂载能力属于信任边界，应按 Shell 访问的权限级别对待。

因此，它的正确用法不是长期打开，而是在需要创建专用预设或调试 Cordis 组合时临时使用。完成后回到标准或更受限的模式，能让日常工作保持更清晰的权限边界。

## 用任务特征做选择

可以先问四个问题：

1. 任务是否需要搜索外部资料或处理长上下文？需要时先选标准模式。
2. 任务是否是规则明确、可批量执行的重复操作？是则准备一个小样本试验 PTC。
3. 任务是否只是受控的代码修改或模型比较？是则可以尝试极简模式。
4. 任务是否要新增工具、改系统提示词或创建预设？只有这时才进入创造模式。

切换模式后，不要只看“感觉更顺”。应至少检查任务是否完成、改动范围是否符合要求、验证命令是否通过、失败是否有可读轨迹。对耗时和 Token 的比较，还要固定模型、仓库提交、提示词、重试规则和测试日期。

## 从一个任务开始做选择

很多人会先问“哪种模式最厉害”，结果往往是四种都试一遍，再根据某一次顺利的体验下结论。更实用的起点是把手头任务写成四个可回答的问题：

```text
我已经知道需要改哪些文件了吗？
完成过程中需要访问外部资料或多种项目规则吗？
步骤能否在执行前写成固定循环、筛选和汇总规则？
这次是否要改变 Harness 自己的预设、插件或运行时组合？
```

第一个问题决定任务是在探索还是执行；第二个问题决定是否需要完整工具集；第三个问题决定 PTC 是否有机会减少无效往返；第四个问题则是创造模式的准入条件。不要因为任务名称里有“自动化”就选 PTC，也不要因为任务看起来很小就一定选极简模式。真正重要的是执行路径是否清楚，以及失败后有没有足够的观测能力。

下面是三个容易遇到的场景。

**场景一：修一个尚未定位的单元测试失败。** 只知道测试失败，不知道是依赖版本、构造数据、业务逻辑还是测试隔离问题。这时路径尚不明确，需要读代码、查看测试和必要时搜索文档，标准模式通常更合适。即使最终只改一行，前期也需要足够的诊断手段。

**场景二：检查 200 个配置文件是否缺少同一字段。** 输入目录、判断规则、输出格式都能提前写清，结果也能用“已检查数量、缺失文件清单、解析失败数量”复核。先用 PTC 对 5 到 10 个样本做只读试验，确认范围和规则正确后，再扩大到全量。这里的价值不在于把一次运行包装成性能提升，而在于程序化循环比让模型逐个临场决定更容易审查。

**场景三：为团队做一个固定的发布前检查流程。** 如果只是日常执行，先在标准模式里把流程跑稳定；当流程确实成熟后，再把它改造成 PTC 或专用预设。如果需要新增 plugin、调整 preset 的系统约束、验证 Cordis 服务组合，才暂时进入创造模式。把“执行已知流程”和“修改 Agent 工作方式”分给不同预设，权限与失败范围会清楚得多。

## 用小任务验证预设是否匹配

选中预设后，不建议直接交给它一个大需求。应先设计一个能在十几分钟内完成的小任务，验证该预设最关键的边界。四种预设各有不同的验收重点：

| 预设 | 小任务设计 | 需要观察的结果 |
| --- | --- | --- |
| 标准模式 | 只读梳理一个小项目的入口、规则和测试命令 | 是否能引用实际路径，是否把未知信息标为待确认 |
| 极简模式 | 在固定提交上修复一个已有最小复现的 Bug | 是否只使用文件和终端完成修改，测试是否通过 |
| PTC 模式 | 只读扫描少量样本并输出结构化汇总 | 是否限定输入范围，统计是否与人工抽查一致 |
| 创造模式 | 从标准副本创建一个无副作用的用户预设 | 是否创建用户副本，是否完成挂载和显示验证 |

任务结束后至少保留三项材料：用户提示词、改动或输出、验证命令的完整结果。预设切换的优势不应只体现在对话观感上，而应能落实到可检查的任务完成条件。如果没有可验收的输出，即使 Agent 说“已完成”，也很难判断模式是否真的适合。

对于会改文件的任务，建议先让 Agent 列出拟修改路径和验证命令，再允许写入。对于 PTC，先运行只读版本，再把写入交给第二次受控任务；对于创造模式，先检查预设文件内容与挂载结果，再在测试仓库中尝试。这样做会多一个确认步骤，但能避免一个不合适的预设把错误范围扩展到整个工作区。

## 预设切换后容易忽略的变量

同一个任务在不同预设下的结果可能受到很多因素影响。除了模型和预设本身，还要注意当前会话是否已有历史上下文、工作区是否干净、依赖是否已经安装、网络和检索是否可用、是否启用了缓存，以及中途是否追加了人工提示。

如果目标是完成业务任务，这些变量可以按实际情况使用；但如果目标是比较预设，就必须记录下来。一个常见做法是：为每次测试新建会话，回到同一仓库提交，使用完全相同的任务文本和权限范围，运行同一套验收命令。发生失败时不要悄悄补一句提示后只记录最终成功，而要把人工介入次数、原因和最终状态一起写入记录。

同时，预设不是安全边界的替代品。创造模式涉及运行时和插件组合，标准模式也可能具有 Shell 与文件写入能力。无论当前选择哪一种，都应在任务描述里明确允许访问的目录、是否允许联网、是否允许使用凭据、是否允许触及外部系统。预设负责组织能力，权限范围仍需由工作区规则和人工审查控制。

## 极简模式的两项容易误解的限制

极简模式并不只是“少装了一些工具”。在当前官方配置中，它使用完整固定的 persona，关闭运行时上下文快照，并且没有上下文压缩；工具只包括持久 Shell 与 `str_replace_editor`。Shell 工具说明中还明确写明不能通过该工具访问互联网。[极简预设配置](https://github.com/deepseek-ai/DeepSeek-Harness/blob/b150a551b8d465e31e418e1b2eaf5e79bbb7d28e/apps/cli/config/agent-presets/minimal/agent.cordis.yml)

这会直接改变任务设计。若任务需要查询某个库当前的破坏性变更、下载依赖说明、检查线上文档或使用 web 搜索，那么极简模式不能在会话中自行补齐信息。把网址和关键资料作为任务输入，或者改用标准模式，才是可控的做法。不要让 Agent 先在极简模式里猜文档内容，失败后再把猜测当作结论。

上下文压缩缺失也不等于“长任务一定不能做”，而是要求操作者承担更多会话管理工作。长时间排查时，应将已确认的事实、当前 Diff、测试结果和下一步拆成短小的显式摘要，在合适的节点开新会话并重新提供这些材料。否则最早的日志、约束和失败条件可能逐渐不在模型可见范围内，最终看起来像是 Agent 忘了之前的决定。

极简模式的持久 Shell 同样需要边界。状态会跨工具调用和讨论保留，因此临时环境变量、当前目录、后台进程和生成文件可能影响下一步。开始任务前应声明工作目录；结束前检查是否遗留测试服务、临时凭据或未提交文件。它能减少工具目录的复杂度，却不会自动把终端变成一次性的隔离环境。

## 将“能力选择”与“授权选择”分开

标准、PTC 与创造模式的官方配置都复用宿主层提供的沙箱、审批和模型路由；预设决定的是单个会话拿到哪些工具、提示词与工具呈现形式，而不是给该会话另建一套权限系统。换言之，切到 PTC 不会天然扩大文件权限，切到极简也不能代替目录访问控制；创造模式则因为能改运行时组合而需要更严格的人工边界。

实际使用时选择可以拆成两张表。第一张只解决任务能力：是否需要搜索、规划、批处理或预设创作。第二张只解决授权：允许哪些目录、是否允许联网、是否允许启动服务、是否允许访问真实密钥、是否允许产生外部副作用。先确定授权，再挑满足任务能力的最小预设，能避免“为了少一个工具而放宽权限”或“为了有全部工具而遗漏审批”的问题。

一份简短的会话前声明可以是：

```text
工作目录：仅 C:\work\demo
可读范围：仓库文件与已提供的文档
可写范围：src/ 与 tests/
网络：仅标准模式下允许查询指定官方文档
外部副作用：禁止发布、发送消息和修改生产资源
结束验证：npm test 与 git diff --check
```

它不会替代组织的安全策略，但能让预设的实际使用范围变得可审查。任务完成后，将这份声明与实际工具轨迹、测试结果一起检查，也更容易发现“模式选对了、权限却越界”的情况。

## 用递进方式降低工具复杂度

如果仍无法确定初始选择，可以按“先完整、后收敛”的路径试验。首次处理陌生项目时用标准模式进行只读盘点，产出入口、依赖、测试命令和未知项；等路径清楚后，把下一步受控修改交给极简模式；当重复规则稳定后，再将只读收集或批处理交给 PTC。这个顺序不是强制流程，但能使每一次减少工具的决定都有上一步的证据支撑。

反向切换同样应被允许。极简模式中发现需要外部资料，或 PTC 的中间结果暴露出大量非结构化异常时，切回标准模式继续探索并不表示任务失败。真正的失败是明知信息不足，还为了维持某种模式标签继续猜测。记录“为何切换、在哪一步切换、切换后增加了什么验证”，会让团队后续形成更具体的选择经验。

## 一个可复用的选择与复盘模板

每次遇到新类型任务，可以在执行前填写下面这段简短记录：

```text
任务目标：
已知输入与允许范围：
未知信息与是否需要检索：
是否存在可程序化的重复步骤：
是否涉及预设或插件开发：
选择的预设与理由：
完成条件：
失败停止条件：
验证命令或人工抽查方法：
```

执行后再补上实际使用的工具、是否越界、验证结果和下一次是否仍选择该预设。连续积累几次后，团队会得到基于自己项目的选择经验，而不是套用别人在不同模型、不同任务下的结论。

## 结论

标准模式适合作为日常默认值，因为它能处理信息不完整的项目任务；极简模式适合减少变量，不应被理解为普遍性能结论；PTC 面向可程序化的固定流程；创造模式则专门用于改造预设和插件。

预设的价值不在于“功能越多越好”，而在于让会话拥有恰好够用的工具和约束。先用小任务验证工具边界，再把模式用于正式工作，比一开始就为复杂任务打开全部能力更容易定位问题。
