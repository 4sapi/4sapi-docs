# AI 原生 SDLC 如何闭环：从 Eval、PR 评审到生产监控

当 Agent 能连续写代码、运行测试和创建 PR 后，传统流程会遇到一个新问题：人应该在哪里介入，才能看住风险，又不被每个小动作拖住？一种可行的安排，是把人的注意力集中在产物门上。Agent 负责门前的探索、实现、测试和发布准备，人负责接受意图、审阅关键产物、批准生产变化，并处理超出规则的情况。

维护阶段再把生产指标接回意图文件，形成新的任务入口。

这篇文章聚焦测试、部署和维护之间的连接，说明怎样让 Agent 参与闭环，但不能越过责任门。

## 一、先看完整链路

一个最小闭环可以表示为：

```text
意图 → 规格 → 计划 → 实现 → 测试 → PR 评审 → 发布门 → 生产监控 → 新意图
```

每一段都应留下产物或日志。

如果只保留最终代码，团队无法回答：

```text
为什么做这个改动？
Agent 按什么计划实现？
哪些检查真正运行过？
谁批准了发布？
事故发生后如何重新进入流程？
```

## 二、让每个会话先检查自己的工作

传统开发里，反馈可能来自几分钟后的 CI、几天后的测试或几周后的生产。

Agent 产出速度变快以后，反馈太晚会让人一次性检查大量 Diff。

更好的方式是把反馈回路放进当前会话：

```text
修改一小组文件 → 运行验证命令 → 读取失败 → 修正 → 再验证
```

反馈回路贯穿整个任务，而不是只在最后运行一次。

## 三、验证命令必须有明确退出状态

Agent 需要一个可判断的信号。

验证包装脚本应做到：

```text
成功返回 0。
任一关键检查失败返回非零。
输出失败原因和相关文件。
不把警告伪装成通过。
```

例如：

```bash
./scripts/verify-change.sh
```

脚本可以组合格式、类型、单元测试和敏感信息扫描，但要让每一项结果仍然可定位。

## 四、修 Bug 先把问题固定成测试

如果没有回归测试，Agent 可能用“看起来合理”的方式修复，下一次改动又把问题带回来。

推荐顺序：

```text
复现问题 → 写失败测试 → 确认失败原因 → 锁定测试 → 修改实现 → 运行测试
```

锁定测试的意思是：修复阶段不能为了通过而改动它。

这样测试本身就成为一条可审计的验收证据。

## 五、Eval 是配置的回归测试

Agent 的行为不仅由代码决定，还会受到以下内容影响：

```text
模型版本。
系统提示词。
项目规则。
Skill。
Hook。
工具权限。
上下文策略。
```

这些配置发生变化时，即使业务代码没有改，也可能改变输出质量。

因此需要一组真实任务组成的 Eval 套件，对配置变化做回归。

## 六、Eval 题目从真实工作收集

一开始不必设计抽象题目。

可以从近期任务中收集：

```text
已经解决的 Bug。
容易误改的模块。
需要遵守的权限规则。
曾经发生过的安全问题。
真实 PR 的验收条件。
```

每个 Eval 至少包含输入、检查项和可接受结果。

如果只能由人凭印象评价，也要写清评分标准和关键失败条件。

## 七、Eval 套件不是一次性资产

模型和工具变化后，旧题目可能变得过于简单，无法区分不同配置。

维护 Eval 时要：

```text
删除失去区分度的题目。
补充最近发生的事故。
保留高风险边界题。
记录每次题目变化的原因。
```

每次生产事故都可以转化为一个新的回归题，但不能把事故描述直接当成可执行测试。

## 八、PR 评审不要只看代码风格

Agent 参与 PR 评审时，可以按多个 pass 检查：

```text
逻辑错误和边界 Bug。
安全和权限风险。
与 spec.md 的一致性。
与 plan.md 的一致性。
测试是否覆盖新行为。
是否出现无关改动。
```

评审结果需要区分严重级别。

重要问题应阻塞合并，纯风格建议不应制造不必要的队列。

## 九、写代码的 Agent 不能批准自己的 PR

职责分离仍然需要保留。

可以让 Agent 生成 PR、回应评论和补充测试，但批准合并的身份应独立于执行身份。

否则同一个 Agent 既能写代码，又能决定自己的代码通过，审计价值会明显下降。

分支保护和 code owner 规则可以把批准动作放在仓库层面执行。

## 十、人的评审要集中在意图和风险

人不必逐行复述 Agent 已经通过的格式检查。

更值得人工判断的是：

```text
实现是否仍然解决原始意图。
风险是否在业务可接受范围内。
是否改变了数据和权限边界。
是否值得进入生产环境。
回滚路径是否清楚。
```

这不是减少责任，而是把责任放在机器检查无法替代的地方。

## 十一、发布门要与构建门分开

构建阶段适合自动运行安全的内循环。

发布阶段涉及外部后果，应该保留更严格的门：

```text
变更范围已确认。
测试和 Eval 通过。
PR 得到 code owner 批准。
生产凭证和环境匹配。
回滚步骤已验证。
发布负责人已授权。
```

Agent 可以准备发布、生成清单和触发预发布环境，但不能把准备动作当成生产授权。

## 十二、回滚要提前演练

维护闭环依赖回滚。

如果监控发现指标越界，系统可能需要触发现有回滚流水线。

因此回滚不能只写在文档里：

```text
在预发布环境执行。
确认恢复目标版本。
验证数据和依赖状态。
记录耗时和失败点。
定期重新演练。
```

没有验证过的回滚路径，不能成为自动化维护的安全后盾。

## 十三、监控脚本和模型响应要分层

生产监控的检测部分应尽量确定性。

例如由脚本计算滚动均值、标准差和异常规则，模型只在指标越界后参与诊断和行动建议。

这样可以避免让模型自行决定“什么算异常”。

一个简单分级可以是：

| 偏离程度 | 模型可做的事 |
| --- | --- |
| 轻微偏离 | 记录日志 |
| 中度偏离 | 只读分析并生成报告 |
| 严重偏离 | 创建回滚或修复 PR，等待审批 |

具体阈值应由业务和运维共同定义，不应直接照搬示例。

## 十四、事故要回流为新的 intent.md

事故处理不应停在“修好了”。

可以把已确认的问题整理成新的意图文件：

```text
发生了什么。
影响了哪些用户或服务。
根因和证据是什么。
期望改变什么。
哪些约束必须保留。
如何验收修复。
```

新的 `intent.md` 再进入规格、计划、构建和测试阶段。

这样维护工作不再是一条旁路，而是同一条生命周期的循环入口。

## 十五、把流程指标也纳入监控

监控不只看 5xx 和延迟。

还可以观察：

```text
PR 周期是否持续变长。
评审队列是否积压。
失败测试比例是否漂移。
人工返工时间是否增加。
Agent 生成的无效 PR 是否变多。
```

这些指标异常时，可能说明团队流程或 Agent 配置出了问题，而不是单个服务故障。

## 十六、最小闭环可以怎样落地

小团队不需要一次搭完整平台。

可以分四步：

```text
第一步：统一验证命令，所有任务都能得到明确通过或失败。
第二步：建立 20 个左右真实任务的 Eval 集。
第三步：让 Agent 生成 PR，但保留分支保护和人工合并。
第四步：为一个关键服务接入只读监控和事故意图模板。
```

每一步都先手动运行，再固化成脚本或自动触发。

## 十七、常见失败方式

### 失败一：只看 CI 绿不绿

测试通过不代表意图正确、权限安全或范围没有扩大。

### 失败二：Eval 只测模型回答

Agent 的工具、权限和项目规则变化同样需要回归。

### 失败三：让模型直接改生产

准备发布与获得发布授权是两件事。

### 失败四：事故修完就结束

没有回流为 Eval 或新意图，同类问题还会重复出现。

### 失败五：监控让模型自行判断异常

检测应由确定性指标完成，模型负责解释和受约束的响应。

## 十八、结论

AI 原生 SDLC 的重点不是把人从流程里移除，而是把人的注意力集中在真正需要判断的门上。

会话内反馈回路负责尽早发现错误，Eval 负责验证配置变化，PR 和分支保护负责职责分离，发布门负责生产授权，监控和事故意图负责把维护重新接回开发流程。

当测试、评审、发布和维护都留下可回放产物，Agent 才能在受控边界内持续工作，而不是把速度变成新的治理风险。
