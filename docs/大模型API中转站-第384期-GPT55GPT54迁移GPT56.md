# 从 GPT-5.5 或 GPT-5.4 迁移到 GPT-5.6 的稳妥方法

一个已经运行的 GPT-5.5 或 GPT-5.4 应用，通常不适合只改一行模型名就上线。旧请求里可能还有推理强度、对话续接、缓存、工具定义、输出解析和安全标识；新模型的默认行为发生变化后，同样的提示词也可能变得过短或过度执行。接口返回成功，只能证明请求被接受，不能证明迁移完成。

本文把迁移拆成基线冻结、请求更新、参数对照、协议探针、灰度和回滚六个环节。每一步都有可见的验收信号。完成后，你应该能回答三个问题：质量有没有回归，延迟与成本发生了什么变化，出现问题时能否恢复到上一套已知配置。

## 一、迁移不是只替换模型名

OpenAI 的 [GPT-5.6 模型指南](https://developers.openai.com/api/docs/guides/latest-model?model=gpt-5.6)建议，从 GPT-5.5 或 GPT-5.4 迁移时，先保留当前推理强度作为基线，再测试相同档位和低一档配置。这个顺序很重要，因为新模型可能用更少 token 维持质量，但具体收益取决于工作负载。

一次完整迁移至少包含以下对象：

```text
模型名称与别名策略
Responses API 请求结构
reasoning.effort 与 reasoning.context
多轮续接方式
工具定义和工具结果回传
提示缓存策略
响应解析与用量统计
安全标识和日志脱敏
超时、重试、降级与回滚配置
```

如果团队只记录了“旧模型”和“新模型”，却没有保存提示词、参数、工具版本和解析器版本，测试结果就无法复现。迁移开始前，应把整套配置当成一个可发布的工件，而不是散落在控制台、环境变量和代码默认值里的若干开关。

## 二、先冻结旧版本基线

基线不是旧系统某一天的平均响应时间，而是一份能够重放的任务集合。建议从最近的生产请求中抽取并脱敏，至少保留四类样本：日常成功请求、人工修改较多的请求、触发重试或超时的请求、曾造成严重错误的请求。

每条样本都写明预期结果：

- 结构化输出必须通过哪一个 JSON Schema；
- 摘要必须保留哪些事实和数字；
- 代码修改必须通过哪些测试；
- 分析任务必须发现哪些已知风险；
- 哪些请求应拒绝、澄清或转人工；
- 允许的最大延迟、重试次数和人工处理时间。

在旧模型上重新运行一次，记录任务成功率、必填项完整度、事实错误、输入与输出 token、缓存用量、p50/p95 延迟、超时、重试和单次成功成本。这里的“成功成本”比单次请求成本更有用：如果便宜请求经常失败并重跑，总成本可能更高。

冻结基线时也要保存原始响应，而不只保存分数。后续发现评分规则有误，可以重新评分；如果只留下一个总分，便无法判断差异来自模型还是评测器。

## 三、更新 Responses API 请求与状态续接

官方建议使用 [Responses API](https://developers.openai.com/api/docs/guides/migrate-to-responses)处理推理、工具调用和多轮工作流。下面是一个刻意保持精简的 Python 基线请求：

```python
import os
from openai import OpenAI

client = OpenAI(api_key=os.environ["OPENAI_API_KEY"])

response = client.responses.create(
    model="gpt-5.6-sol",
    input="审查这份迁移方案，列出可能导致数据丢失的步骤，并给出证据。",
    reasoning={"effort": "medium"},
    safety_identifier="usr_8f31c2d9a0",
)

print(response.id)
print(response.output_text)
print(response.usage)
```

`safety_identifier` 应是稳定且保护隐私的标识，不要直接发送邮箱、手机号、姓名或内部账号。可以在自己的服务端使用带密钥的哈希或不可逆映射生成标识，并限制谁能反查。面向个人终端用户的应用应参考 OpenAI 的[安全标识指南](https://developers.openai.com/api/docs/guides/safety-best-practices#implement-safety-identifiers)设计这一字段。

多轮对话不要靠拼接一段越来越长的纯文本假装续接。GPT-5.6 支持通过 `reasoning.context` 选择早期推理是否继续相关。官方指南说明，GPT-5.6 的有效默认行为是 `all_turns`；通过 `previous_response_id` 续接时，模型可以使用早期响应中仍可用的推理项。请求后应检查响应中的有效 `reasoning.context`，不要只相信客户端默认值。

```python
follow_up = client.responses.create(
    model="gpt-5.6-sol",
    previous_response_id=response.id,
    input="把刚才的风险按影响和发生可能性排序。",
    reasoning={"effort": "medium", "context": "all_turns"},
    safety_identifier="usr_8f31c2d9a0",
)
```

如果第二轮目标、假设和优先级已经变化，早期推理可能成为负担，此时应测试 `current_turn`。使用 `store: false` 或零数据留存模式时，还要按官方要求管理并重放 API 返回的加密推理项。不要在没有验证数据保留和历史重放逻辑的情况下照搬有状态示例。

### 响应解析器也要作为迁移对象

旧应用常把正文、工具调用和用量字段当成固定结构读取。迁移到 Responses API 后，应先保存一份真实响应样本，逐项确认最终消息、工具调用项、推理相关项、错误对象和用量数据分别从哪里取得。不要用字符串搜索从整段响应里“捞答案”，也不要在字段缺失时静默返回空文本；解析失败应进入明确的错误分支并保留响应标识。

给解析器准备契约测试：普通文本必须得到非空最终消息；工具任务必须保留调用 ID、函数名、参数和结果关联；多轮请求必须保存前一响应 ID；用量统计必须能区分输入、输出和缓存相关字段。SDK 升级前后重放这些样本，可以及时发现字段名、对象类型或序列化方式变化。

流式请求还要验证事件顺序和中断恢复。客户端收到部分文本后连接断开，不能把半份答案标记为成功；工具参数尚未完整时也不能提前执行。为每类终止事件设置状态机，把“模型完成”“用户取消”“网络中断”“服务错误”和“解析错误”分开统计。这样灰度阶段看到失败增加时，才能判断是模型质量、接口行为还是客户端解析造成的回归。

迁移期间可以同时保留旧、新解析器，但必须由配置版本明确选择，不要根据某个字段是否存在临时猜测协议。双解析的目的只是影子比对，确认一致后应删除兼容分支，避免长期维护两套含义不同的成功标准。

## 四、推理强度做同档和低一档对照

迁移时不要同时更换模型、提示词、推理强度和工具集。一次改变太多变量，即使结果变好，也无法知道是哪项调整起作用。

假设旧模型使用 `high`，第一轮至少跑三组：

```text
A：旧模型 + high，作为冻结基线
B：GPT-5.6 + high，只更换模型
C：GPT-5.6 + medium，在同一模型上低一档
```

如果旧模型使用 `none`，保留它作为延迟基线，同时测试 `low`，观察工具调用或复杂判断是否获得可测量的改善。官方指南把 `medium` 作为平衡起点，把 `max` 留给质量优先且确实需要更多探索与验证的任务。不要在迁移第一轮直接把全部请求调到 `max`，也不要因为平均输出变短就认定质量不变。

对照表至少包括：

| 维度 | 验收方式 | 迁移失败信号 |
| --- | --- | --- |
| 任务成功 | 通过预定义硬性断言 | 平均分相同但关键任务失败 |
| 完整性 | 必填字段和证据逐项检查 | 回答更短且漏掉必要内容 |
| 工具调用 | 参数、顺序、结果回传可追踪 | 重复调用或错误工具增加 |
| 总 token | 输入、输出、推理与缓存一起看 | 只看输出 token 得出结论 |
| 延迟 | 统计 p50、p95、超时 | 少量长尾阻塞业务队列 |
| 成本 | 按通过验收的任务归一化 | 重试和人工返工抵消节省 |

## 五、经过兼容网关时增加协议探针

如果旧应用通过 OpenAI-compatible 网关调用模型，迁移需要单独做协议验证。以 4SAPI 作为可替换候选的测试方法为例：先根据当日[模型名称说明](https://4sapi.apifox.cn/8423112m0)与[URL 配置说明](https://4sapi.apifox.cn/8423139m0)核对实际模型名和路径，再使用隔离令牌测试普通响应、流式输出、推理字段、工具调用、错误码和用量日志。不能因为旧型号可调用，就推断 GPT-5.6 型号、`reasoning.context` 或 Pro 模式已经完整透传；只有当前文档与受控响应都能证明的字段，才进入迁移范围。

协议探针应该与质量评测分开。先用最小请求确认请求字段没有被忽略、响应模型可识别、用量可查询，再运行业务样本。如果最小请求已经出现字段丢失，就不要用增加提示词或重试来补救，那会把链路兼容问题伪装成模型质量问题。

## 六、影子流量、灰度和回滚门槛

离线对照通过后，可以把一小部分生产输入复制到新链路进行影子测试，但不要把新结果直接返回给用户。影子流量必须脱敏，并遵守现有数据保留和访问控制。比较旧、新结果时，重点查看生产分布里是否出现离线样本没有覆盖的语言、长度、工具失败和安全场景。

灰度阶段从低损失任务开始。每次扩量前检查一个固定窗口，不要在没有足够样本时因为短期平均值好看就继续。可以把以下项目设为停止条件：

- 关键任务成功率低于旧基线；
- 结构解析错误或工具调用失败超过门槛；
- p95 延迟、超时或队列长度超过业务预算；
- 人工复核工作量上升；
- 响应模型、请求配置或 token 用量无法追踪；
- 安全拒答、误拦截或越权行为出现不可接受变化。

回滚包要包含旧模型名、提示词、推理参数、工具定义、缓存设置、解析器和依赖版本。把它们放在同一个配置版本中，并提前演练一键切回。真正的回滚成功信号，是旧样本和一批实时请求都恢复到已知基线，而不是控制台里模型名看起来已经变回去。

## 七、迁移检查表与结论

上线前逐项确认：

```text
旧版本样本、响应和指标已经冻结
模型名与别名策略有明确记录
Responses API 请求和多轮续接已验证
同档与低一档推理强度完成对照
工具、缓存、安全标识和日志符合要求
兼容网关的字段透传已单独验证
影子流量与灰度停止条件已设定
旧配置能够完整回滚并通过复测
```

从 GPT-5.5 或 GPT-5.4 迁移到 GPT-5.6，核心不是尽快把请求发出去，而是保留一条能比较、能解释、能撤回的路径。先用旧配置建立基线，只改变一个主要变量，再根据任务成功、完整性、延迟、token 和人工成本逐步调整。

当新链路通过同一套验收标准，并在灰度流量中保持稳定，迁移才算完成。后续提示词、工具或任务分布发生明显变化时，应重新运行代表性样本，而不是把第一次迁移结果长期当作默认答案。
