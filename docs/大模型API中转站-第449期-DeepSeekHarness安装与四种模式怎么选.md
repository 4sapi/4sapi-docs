# DeepSeek Harness 安装与四种模式怎么选：先从标准模式跑通

DeepSeek Harness 最容易把新用户劝退的，不是安装命令，而是启动后的选择：模型怎么配，工作区是什么，四种模式有什么区别，为什么看起来每种都像“更高级”的选项。

第一次上手不需要把所有概念弄懂。先把它当作本地 Web 版编码 Agent，限定一个项目目录，使用标准模式完成一个只读任务。等基本链路跑通，再去碰 PTC、极简和创造模式。

## 一、启动前准备什么

素材给出的 Web 启动命令是：

```bash
npx @deepseek-ai/dsh web
```

运行后，命令行会给出一个本地地址，在浏览器中打开即可。实际安装依赖、Node.js 版本、端口和系统兼容性应以当前官方文档为准；如果命令报错，先保留完整错误和环境信息，不要连续更换多个安装方式。

首次启动前建议准备：

| 项目 | 用途 |
| --- | --- |
| Node.js 运行环境 | 执行 `npx @deepseek-ai/dsh web` |
| DeepSeek API 访问凭证 | 让 Harness 调用模型 |
| 测试项目目录 | 验证文件读取、搜索和终端能力 |
| 浏览器 | 打开本地 Web UI |

DeepSeek API 平台入口为 [platform.deepseek.com](https://platform.deepseek.com/)。密钥只应填在受控配置位置，不要放进项目源码、截图、聊天记录或公开 Issue。

## 二、第一次进入 Web UI 先做什么

启动后先完成三件小事：

```text
配置模型访问凭证。
选择一个测试工作区。
使用标准模式执行一条只读任务。
```

工作区不是一个装饰性选项，它定义了 Agent 默认处理的项目目录范围。第一次不要选主力生产仓库，更不要直接给整个个人目录。选一个可恢复的小项目，确认 Agent 的文件搜索、读取和终端行为都符合预期后再扩大范围。

可以从下面这条任务开始：

```text
读取当前项目结构，列出入口文件和测试命令，不修改任何文件，也不执行外部写入。
```

这条任务能验证模型连接、工作区读取和基础工具调用，又不会改动代码或外部系统。

## 三、四种模式不是能力等级

素材中提到的标准、PTC、极简和创造模式，更适合被理解为四套预设插件组合，而不是从低到高的能力等级。四种模式解决的目标不同。

| 模式 | 主要能力 | 适用场景 | 第一次是否推荐 |
| --- | --- | --- | --- |
| 标准模式 | 文件、Shell、搜索、Skills、计划、目标、后台任务、子 Agent、工作流等默认能力 | 日常编码与项目任务 | 推荐 |
| PTC 模式 | 标准能力 + 程序化工具调用 | 多步骤、结构化、可并行工具操作 | 暂不推荐 |
| 极简模式 | 持久 Bash 与文件编辑器等最小能力 | 裸 Agent 能力基准测试 | 不推荐日常使用 |
| 创造模式 | 标准能力 + 检查并试验 Cordis 插件环境 | 创建专用 Agent 或插件 | 有明确目标后再用 |

如果只是想让 Agent 读代码、改文件、跑测试，标准模式已经足够。模式越“特别”，并不表示完成普通任务会越快。

## 四、标准模式：从这里开始

标准模式预置了完整编码 Agent 常用能力，包括文件读取与编辑、Shell、文件和网页搜索、Skills、计划、目标、后台任务、子 Agent 与工作流。

它适合两个场景：第一次熟悉 DeepSeek Harness，以及日常项目任务。先在标准模式里验证下面几件事：

```text
工作区是否正确。
文件读取和搜索是否只落在预期目录。
Shell 命令是否符合你的权限预期。
模型能否解释它准备做什么。
任务失败时，轨迹中能否定位到工具和错误。
```

标准模式的价值在于减少变量。新用户同时换模型、改插件、开创造模式，最后出现问题时很难判断是环境、权限、工具还是模式造成的。

## 五、PTC 模式：程序化调用工具，不是“更强开关”

PTC 模式保留标准模式能力，但改变了工具使用方式。传统 Agent 往往是“调用一个工具，读取结果，再决定下一步”；PTC 会让模型通过 Code Mode SDK 编写一段 TypeScript 程序，在一次 `run_code` 中组合多个工具操作。

```text
传统路径：读取 -> 搜索 -> 筛选 -> 再读取 -> 整理
PTC 路径：写一段 TypeScript，在一次 run_code 中组合这些操作
```

当任务是结构化、多步骤且可并行时，这有机会减少模型和工具之间的往返，也可能降低 token 消耗。但前提是模型能够稳定规划和调试这段程序。程序一旦写错，排查难度会从“看单次工具调用”变成“看程序逻辑、运行环境和工具返回”。

因此，PTC 适合下面情况：

```text
同类工具往返很多。
任务步骤固定，且存在并行空间。
团队能读懂 TypeScript 与 run_code 轨迹。
已经有标准模式基线，可以比较质量、耗时和成本。
```

没有这些条件时，先留在标准模式。不要为了少几次调用，先引入一层自己暂时无法维护的程序化工具逻辑。

## 六、极简模式：用于比较，不用于舒服地干活

极简模式只保留持久 Bash 和文件编辑器等核心能力，并将系统提示词收得很短。素材中将它定位为最小环境下的模型基准测试模式。

它的价值在于控制变量：如果你想比较两个模型的裸 Agent 能力，极简环境能减少 Skills、上下文压缩、工作流和预置工具带来的影响。反过来，它也少了日常项目里最方便的能力。

可以这样使用：

```text
固定同一仓库、同一任务、同一权限。
分别运行模型 A 与模型 B。
记录完成情况、工具次数、错误和人工修改。
不要把结果外推为“谁在所有场景都更强”。
```

日常编码不建议长期停在极简模式。它的目的不是提供完整体验，而是帮你做更干净的比较。

## 七、创造模式：先定义边界，再让 Agent 扩展自己

创造模式拥有标准模式能力，还可以检查正在运行的 Cordis 环境，在内存中试验插件，并帮助创建新的 Agent 和插件。

听起来像“Agent 可以改造自己”，但第一步不该是让它随意安装任何东西。更实用的做法是先写出目标和边界，例如：

```text
做一个只允许读代码、不允许改文件的安全审计模式。
做一个接入内部搜索、固定使用指定模型、携带三种专属 Skills 的研究 Agent。
```

每个目标都应补齐：允许工具、禁止动作、执行身份、资料范围、日志和撤销方式。插件能在运行中被添加，不等于它应该不经审查地获得网络、文件写入或外部系统权限。

## 八、模型和提供方不要被模式限制

素材提到，界面可选择 Flash、Pro 与思考强度，也支持添加目录里的模型提供方，以及自定义提供方、Base URL、协议和模型列表。实际可用模型和字段应以当前版本界面与官方文档为准。

这意味着 DeepSeek Harness 的 Harness 层与模型提供方可以分开评估。你可以先用一个模型跑标准模式基线，再在相同工作区和任务上比较其他提供方，而不是把“使用 Harness”误解为“必须只使用一种模型”。

成本、价格和模型能力变化很快。要比较时，记录当前价目、上下文长度、缓存规则、推理档位、任务样例和实际用量，不要沿用旧截图或单次体感。

## 九、第一次上手检查清单

```text
[ ] 已从当前官方页面核对安装方式和系统要求。
[ ] `npx @deepseek-ai/dsh web` 能启动，并记录报错信息。
[ ] API 凭证没有写入源码或公开日志。
[ ] 首次工作区是可恢复的测试项目，不是生产目录或个人根目录。
[ ] 第一次任务只读，不包含外部写入。
[ ] 使用标准模式跑通文件读取、搜索和一条小任务。
[ ] PTC 模式有可比较的标准模式基线。
[ ] 极简模式只用于受控评测，不替代日常工作流。
[ ] 创造模式的插件目标、权限、日志和撤销方式已经写清。
[ ] 价格和模型支持范围以当前官方文档与控制台为准。
```

## 十、启动失败时，先缩小问题范围

第一次启动出问题很常见，真正容易把人带偏的是同时改 Node.js、换终端、改代理、重装依赖、切模型。这样即使最后能启动，也很难知道问题到底在哪里。更稳的处理方式是一次只验证一个环节：命令能否执行、本地服务能否监听、浏览器能否访问、模型鉴权是否通过、工作区是否可读。

| 现象 | 优先检查 | 处理原则 |
| --- | --- | --- |
| `npx` 或包执行失败 | Node.js 与 npm 是否可用、当前安装说明 | 保留完整报错，不要根据旧教程猜参数 |
| 地址已被占用 | 命令行给出的监听地址、已有本地服务 | 改用当前版本支持的端口配置，或释放明确冲突的服务 |
| 浏览器打不开页面 | 服务进程是否仍在运行、本机防火墙或地址 | 先在同一台机器访问命令行输出的地址 |
| 页面能开但模型不可用 | API 凭证、账户状态、模型名称和提供方配置 | 不要把密钥贴进错误截图或 Issue |
| 文件读取不到 | 工作区路径、启动账号、目录权限 | 用一个普通文本文件验证，不要直接尝试高权限目录 |
| 工具连续失败 | 任务描述、模式、命令依赖和事件轨迹 | 先缩小到一条只读任务再复现 |

这里刻意不写固定报错文案，因为安装包、系统与版本都在变化。提交问题时，给出命令、系统、Node.js 版本、脱敏后的报错和最小复现步骤，比一句“打不开”更容易得到有效帮助。

## 十一、工作区是第一道安全边界

工作区不只是 Agent 找文件的起点，也是你把“它可以碰哪里”落到本地目录上的第一层限制。首次试用可以专门建一个小仓库，里面放一段能运行的示例代码、几条测试和一个可提交的 Git 历史。这样，Agent 即使做出不符合预期的修改，也容易检查和撤销。

建议把目录分成三类：

| 目录类型 | 是否适合首次授权 | 原因 |
| --- | --- | --- |
| 独立测试仓库 | 适合 | 范围小、可恢复、容易观察全部改动 |
| 日常开发仓库副本 | 谨慎 | 可以验证真实任务，但仍需要先看 Git 状态与密钥文件 |
| 生产目录、个人根目录、同步盘根目录 | 不适合 | 文件范围太宽，常混有凭证、私有资料和无关项目 |

开始一条可能写文件的任务前，先看工作树状态。已有未提交改动时，要么先提交或暂存，要么明确记录它们；否则人和 Agent 的改动混在一起，后续几乎无法判断哪一部分该保留。不要用“让它不要碰别的文件”替代目录边界，这只是提示，不是权限控制。

## 十二、标准模式的第一轮工作流

真正的首轮使用不该是“修完一个复杂 Bug”。它应当验证 Agent 在受限环境中的基本行为是否可信。下面这个顺序比直接给大任务更有信息量：

```text
1. 只读盘点：列出目录、入口、依赖和测试命令，不执行修改。
2. 运行基线：只运行已有测试或静态检查，记录当前通过与失败。
3. 有限修改：要求只修改一个指定文件，解决一个明确的小问题。
4. 审阅 diff：逐行看改动，确认没有顺手重写无关文件或配置。
5. 再跑验证：运行和基线相同的检查，区分原有失败与新增失败。
6. 结束或回退：通过才提交；不通过就保留日志和 diff，撤回试验改动。
```

这六步看上去保守，却能快速回答几个关键问题：它有没有正确理解工作区、会不会胡乱扩大修改范围、命令执行是否透明、失败时能不能停住。等这些都没问题，再把任务规模放大，比让 Agent 一开始就在复杂仓库里“自由探索”更划算。

## 十三、什么时候该用 PTC，什么时候不该用

PTC 的重点不是让模型写代码，而是把原本多轮的工具交互收进一段可执行的程序里。它适合重复、规则相近、结果可以结构化汇总的操作，例如在一组文件里查询固定模式、读取若干配置后生成对照表、对多个独立目标做同一种检查。

但它不适合所有多步骤任务。下列情况先不要用：

```text
任务定义还在变化，模型需要频繁和人确认。
每一步都依赖前一步的语义判断，几乎没有并行空间。
运行内容会修改生产资源、调用付费接口或执行不可逆操作。
团队无法审阅 TypeScript、run_code 轨迹或工具权限。
标准模式都还没有稳定基线。
```

把一次 PTC 试验当作一段普通代码来对待：确认输入范围，限制可调用工具，准备小样本，保留失败输出，并在运行后核对实际副作用。它可能减少工具往返，但不会自动减少错误；错误只会更集中地出现在程序逻辑和一次执行的权限范围里。

## 十四、比较模型与提供方，要固定变量

Harness 能接不同模型或提供方时，很容易出现“换个模型试试看”的随机试用。这样的结果很难解释，因为工作区、上下文、模式、权限、提示词和任务难度可能一起变了。要得到有参考价值的结论，至少固定下面这些条件：

| 应固定的项 | 记录内容 |
| --- | --- |
| 任务 | 同一份任务描述、验收条件和输入数据 |
| 环境 | 同一提交版本、依赖状态、工作区与权限 |
| 模式 | 标准或 PTC 只能一次换一个变量 |
| 执行规则 | 是否允许重试、最大尝试次数、是否人工提示 |
| 结果 | 完成状态、diff、测试结果、工具错误和人工接手时间 |
| 成本信息 | 当时的用量、价格口径和推理设置，而不是旧截图 |

同一任务可以运行不止一次，因为模型输出存在波动。重点不是挑出最漂亮的一次，而是看失败时是否可解释、平均需要多少人工修正、有没有越过权限边界。模型能力和价格变化很快，比较报告也应标出日期与配置，而不是写成永久结论。

## 十五、密钥与外部副作用的底线

API 凭证只是最直观的一种敏感信息。初次使用时还应留意 `.env`、部署配置、浏览器会话、私有包令牌、数据库连接串和云端命令。它们不一定在源码里，却很可能出现在工作区、终端历史或工具返回内容中。

建议把第一轮试用的规则写得足够具体：

```text
不读取或展示真实密钥、访问令牌和客户数据。
不把密钥写入代码、日志、截图、提示词或公开问题反馈。
不执行部署、发送消息、修改生产数据或触发付费外部操作。
涉及写文件、联网和外部系统时，先由人确认范围。
发现疑似敏感内容时，停止扩散并改用脱敏样例复现。
```

这些限制不是否定 Agent 的价值。相反，它们让你能在一个可控环境里验证工具、模型和模式本身，而不是把一次试用变成权限事故。

## 十六、首轮验收与排障清单

```text
[ ] 已在当前官方资料中核对启动命令、系统要求和模型配置字段。
[ ] 服务启动、浏览器访问、模型鉴权和工作区读取已分别验证。
[ ] 报错记录不包含 API Key、路径中的私人信息或业务数据。
[ ] 首次工作区是可恢复的测试仓库，且 Git 工作树状态清楚。
[ ] 已完成一次只读盘点和一次基线测试。
[ ] 有限修改只涉及约定文件，diff 已由人审阅。
[ ] 验证命令在修改后重新执行，原有失败与新增失败已区分。
[ ] PTC 只在任务固定、工具受限且能审阅 `run_code` 时试用。
[ ] 比较模型时固定了任务、环境、模式和重试规则。
[ ] 没有在首轮试用中接入生产密钥或不可逆外部写入。
[ ] 失败时能拿到最小复现、工具轨迹和人工接手点。
```

## 十七、结论与资料

第一次使用 DeepSeek Harness，最稳的路线是“标准模式 + 测试工作区 + 只读任务”。先确认本地 Web UI、模型访问、文件边界和工具轨迹都正常，再决定要不要用 PTC 做程序化工具调用，或者进入创造模式做专用插件。

四种模式的差别不在于谁更高级，而在于谁替你预置了多少能力、又让你承担多少维护成本。下一篇会继续讨论创造模式、插件和事件日志，重点放在如何扩展而不失去可观测性与权限边界。
