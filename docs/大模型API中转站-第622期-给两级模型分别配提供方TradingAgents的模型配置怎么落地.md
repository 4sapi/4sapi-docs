# 给两级模型分别配提供方：TradingAgents 的模型配置怎么落地

一套多阶段系统里，不同阶段对模型的要求不一样。四类分析师各写一份报告，需要的是吞吐和稳定；研究员主管和组合经理要做最终判断，需要的是推理深度。全程用一个模型，要么前面浪费预算，要么后面不够用。

TradingAgents 把这件事做成了配置：模型分成快速与深度两档，每一档可以各自指定提供方，甚至各自指定接口地址。本文讲这套配置怎么落地，以及落地时容易踩的五个坑。

范围限定在配置层面，不涉及它的判断质量。项目 README 写明不构成财务、投资或交易建议。信息来自仓库的默认配置文件与 README，检索日期为 2026-11-01，我没有运行过它。

## 一、两档模型各干什么

| 档位 | 配置键 | 默认值 | 服务哪些角色 |
| --- | --- | --- | --- |
| 快速 | quick_think_llm | gpt-6-luna | 四类分析师、多空研究员、风险辩手、交易员 |
| 深度 | deep_think_llm | gpt-6-sol | 研究员主管、组合经理 |

从表里能看出分配逻辑：所有"收集与表达"的环节走快速档，两个"拍板"的环节走深度档。默认配置里 `max_debate_rounds` 和 `max_risk_discuss_rounds` 都是 1，说明开箱状态下调用次数的大头确实在快速档。

## 二、配置从哪来，谁覆盖谁

配置有三个来源，优先级从低到高：

1. `tradingagents/default_config.py` 里的默认值。
2. 环境变量 `TRADINGAGENTS_*`。
3. Python 里传入 `config` 字典，或 CLI 的逐次提问与命令行参数。

环境变量的映射表在源码里是一张显式的字典，例如 `TRADINGAGENTS_QUICK_THINK_LLM` 对应 `quick_think_llm`，`TRADINGAGENTS_DEEP_THINK_PROVIDER` 对应 `deep_think_provider`。

### 类型是严格的

源码里的转换逻辑有一处值得抄的做法：按默认值的类型来转换环境变量，类型不对就**抛错**，而不是回落到默认值。注释给的理由是，拼错的布尔值（例如把 true 写成 treu）应该在启动时报错，而不是让一次无人值守的运行静默跑在错误配置上。

这一点对定时任务尤其重要。静默回落意味着你可能跑了几周才发现辩论轮数一直是 1。

## 三、每档接自己的提供方与端点

默认情况下两档共用一个提供方和端点。要分开，用这四个键：

| 键 | 作用 |
| --- | --- |
| quick_think_provider | 快速档的提供方 |
| deep_think_provider | 深度档的提供方 |
| quick_think_backend_url | 快速档的接口地址 |
| deep_think_backend_url | 深度档的接口地址 |

源码注释写明了用途：想让管理层跑在 Claude 上、其余跑在 OpenAI 上，只设 `deep_think_provider` 和对应的模型名即可；某一档用了自己的提供方，就用那个提供方自己的密钥和默认端点，需要改地址时才设对应的 `backend_url`。

### 接一个 OpenAI 兼容端点

如果两档要走不同的中转，写法是给对应档位同时指定提供方和地址。下面是一个结构示例，地址和密钥用占位符：

```python
from tradingagents.graph.trading_graph import TradingAgentsGraph
from tradingagents.default_config import DEFAULT_CONFIG

config = DEFAULT_CONFIG.copy()
# 快速档走一个 OpenAI 兼容的中转端点
config["quick_think_provider"] = "openai_compatible"
config["quick_think_backend_url"] = "https://<your-relay-endpoint>/v1"
config["quick_think_llm"] = "<model-id>"

# 深度档留在默认提供方
config["deep_think_provider"] = None
config["deep_think_backend_url"] = None

ta = TradingAgentsGraph(config=config)
```

README 说明 `openai_compatible` 覆盖任何 OpenAI 兼容端点（vLLM、LM Studio、llama.cpp 以及自定义中转）。像 4SAPI 这类中转站就是这种端点的一个实例：把它的接口地址填进 `backend_url`，两档就能分别指向不同的上游。换别的中转或本地服务，改的只是这一行的地址，模型键和其余配置不用动。

这个写法的技术价值在于隔离：地址被收在一个键里，而不是散落在各角色的代码中。

## 四、五个容易踩的坑

### 坑 1：`backend_url` 该留空时留空

默认值是 `None`，注释解释得很清楚：留空时各家的客户端用它自己的默认端点（OpenAI 的 api.openai.com、Gemini 的 generativelanguage.googleapis.com），CLI 在你选提供方时会覆盖它。

注释还记录了历史教训：曾经把 OpenAI 的 `/v1` 写进这个字段，结果切到 Gemini 时被一并转发，产生了格式错误的请求地址。

实践含义：全局的 `backend_url` 只在这套配置的所有模型都走同一个端点时才设；否则用每档的 `*_backend_url`，其余留空。

### 坑 2：环境变量拼错不会静默

前面说了类型转换会抛错。反过来也要注意：名字拼错（例如把 `TRADINGAGENTS_MAX_TOKENS` 写成 `TRADINGAGENT_MAX_TOKENS`）不会被发现，因为系统不认识这个变量，只会忽略。所以配置完建议回读一次生效值，而不是相信自己的输入。

### 坑 3：本地端点不需要密钥，但不是所有端点都不需要

README 说明本地服务不需要密钥，而需要密钥的端点用 `OPENAI_COMPATIBLE_API_KEY`。这与 `OPENAI_API_KEY` 是两个变量，混用会得到认证失败，而不是一个明确的报错。

### 坑 4：推理模型基本忽略温度

想把运行做得更可复现，本能反应是把 temperature 设成 0。README 直接写了：当前默认的推理模型基本忽略温度设置，想要更稳定就换成非推理模型。

源码注释补了一句更根本的：没有任何设置能让 LLM 输出逐字节一致。所以调温度只能减少波动，不能消除波动。

### 坑 5：超时和重试要单独配

两个键和网关有关：

| 键 | 作用 |
| --- | --- |
| llm_max_retries | 传给每家客户端 SDK 的重试预算，用于扛过突发 429 |
| max_tokens | 输出 token 上限，用于限制停不下来的模型，避免撞上网关的空闲超时 |

源码注释举了具体场景：限流环境下不要因为一次 429 就整轮中止；某些部署会输出无界推理，需要靠 `max_tokens` 截住。

如果你是经中转或网关接入，这两个键比在模型侧调参更能解决"跑一半挂住"的问题。

## 五、数据供应商也有同样的思路

模型之外，数据源也是一张显式的链：

| 键 | 作用 |
| --- | --- |
| data_vendors | 类目级配置，例如核心行情、技术指标、财报、新闻、宏观、预测市场 |
| tool_vendors | 工具级配置，优先级高于类目级 |

源码注释里两句值得记住：

1. 配置的值是"确切的供应商链"，请求不会被静默路由到你没选的供应商。
2. 需要有序回退时，用逗号列出多个，例如 `yfinance,alpha_vantage`。

默认里财报类目写的是 `sec_edgar,yfinance`：先按申报原样读美国公司财报，失败再退到 Yahoo。

这个设计对排查很有用：数据"看起来不对"时，先确认当前走的到底是哪一家，而不是猜。

## 六、怎么确认配置真的生效

配置错了不会报错的地方，靠自己验证：

1. **跑一次最小网格。** 用 CLI 指定一个标的、一天、只开两类分析师，观察耗时与调用量是否符合两档分配的预期。
2. **看报告里的设置。** README 提到 v0.5.2 起运行设置会记录在每份报告里，可以拿它核对实际生效的模型与轮数。
3. **故意制造一次错误配置。** 把某个整数键写成非法值，确认启动时报错而不是静默继续。这能验证你理解的是不是真的那套规则。
4. **分档对照。** 让两档指向不同端点，各跑一次同一标的同一日期，比较输出与耗时；如果两档结果完全同源，说明你的每档配置没有生效。

第 4 条最直接：分档配置的意义就是让两档不一样，如果看不出差别，先怀疑配置被全局值覆盖了。

## 七、这套配置设计的可借鉴之处

| 做法 | 为什么值得抄 |
| --- | --- |
| 把"快"和"深"拆成两档，而不是逐角色配 | 配置项少，心智负担低 |
| 每档可单独指定提供方与端点 | 换上游只动一处 |
| 环境变量按默认值类型严格转换 | 拼错立刻失败，适合无人值守 |
| 端点留空表示用各家默认 | 避免把一个家的路径拼到另一个家 |
| 数据源用"确切链"而非模糊路由 | 排查时能说清走的是哪家 |

第二条是这套配置的关键。很多项目把模型名和端点混在一起，导致换端点要改模型名；把两者分开之后，端点只是一个地址。

## 八、限制与结论

配置层的结论可以概括成三条：两档分工对应"收集与表达"和"拍板"两类工作；每档的提供方与地址都能独立指定，因此可以把不同阶段接到不同上游；类型与留空规则是刻意设计的，为的是让错误在启动时暴露。

本文的限制：没有运行项目，示例代码是结构示意而非可执行验证；没有验证经中转时的实际鉴权与限流行为；没有测过两档分属不同提供方时的成本与延迟差异；`OPENAI_COMPATIBLE_API_KEY` 等变量名以 README 为准，未逐个实测；不构成任何投资建议。

下一步建议：先用默认配置跑通一次，再把快速档换到你自己的端点，用第六节第 4 条的分档对照确认真的生效，最后才去调轮数与超时。
