# 多 Agent 审稿怎么拆：避免写初稿的模型自我打分

让同一个 Agent 写完初稿，再问它“请检查有没有问题”，通常只能得到一份礼貌的自评。它熟悉自己刚刚采用的结构，会把遗漏解释成取舍，把身份越界当成合理补充，把过于工整的句子当成清晰。审稿轮次增加了，盲点却可能没有变化。

多 Agent 的价值不在于把一篇文章复制给更多模型，而在于把审稿责任拆开。本文将审稿分成任务完成度、作者一致性、AI 腔与禁忌三轮，每轮拥有独立输入、规则和输出格式；最后由作者决定哪些建议进入正文。目标是让问题可追踪，而不是把最终判断交给一组自动评分。

## 一、初稿与审稿职责要隔离

写初稿的 Agent 可以负责理解选题、组织材料和形成段落，但不应同时拥有“证明自己已经完成”的职责。审稿 Agent 读取初稿、任务合同、对应规则和来源材料，却不读取写作 Agent 的自评，不根据“上一轮说没有问题”跳过检查。

三轮审稿共享文章版本号，但职责不同：

| 轮次 | 只回答的问题 | 不负责什么 |
| --- | --- | --- |
| 任务审稿 | 读者问题、结构、材料和证据是否完成 | 不判断像不像作者 |
| 作者审稿 | 身份、事实边界、文体和读者关系是否成立 | 不替作者做最终价值选择 |
| 表达审稿 | 模板腔、禁忌、空话和越界是否存在 | 不为了顺口改写事实 |

如果三轮都让模型自由“整体优化”，职责又会重新混在一起。每轮只提交问题、证据和候选建议；接受、拒绝或保留原句由作者或编辑决定。

## 二、第一轮只看任务完成度

第一轮的输入是任务合同、文章大纲、原始材料和初稿。它需要检查主线是否清楚、章节是否服务同一个读者问题、关键材料是否被正确使用、结论是否回应开头，以及每个数字、引用和操作步骤是否有支持。

可以给第一轮一个明确的结果结构：

```json
{
  "stage": "task",
  "findings": [
    {
      "severity": "high",
      "quote": "原文中的具体句子",
      "rule_ref": "TASK-EVIDENCE-02",
      "evidence": "材料中没有支持该结论的段落",
      "suggestion": "删除结论或补充可核验来源"
    }
  ],
  "passed_checks": ["主线清楚", "结尾回应问题"]
}
```

`quote` 必须引用原文，不允许只写“第二段有问题”；`rule_ref` 让建议能回到规则；`evidence` 说明为什么命中；`suggestion` 是候选动作，不是自动修改命令。第一轮结束后，先解决高严重度的缺证据、结构跑偏和硬性遗漏，再进入作者审稿。

## 三、第二轮检查是不是这个作者会写

第二轮重新加载作者事实边界和文体规则。它检查第一人称是否有依据，外部材料是否被误写成亲历，教程、观点文或复盘是否使用了对应结构，文章与目标读者的关系是否合适。

常见发现包括：

- 一句“我们已经验证”没有对应作者事实条目；
- 观点文使用了没有反例的绝对判断；
- 复盘把事后知道的结果倒灌进最初决策；
- 教程省略了版本、权限或失败回滚；
- 文章为了显得权威，使用了作者没有资格承担的口吻。

这一轮不能把所有句子改成同一个“个人风格”。如果作者事实文件没有决定某个价值判断，审稿器应标记为需要作者决定，而不是生成一条更坚定的结论。作者审稿的成功信号，是每个身份和文体问题都有证据或明确的人工待决状态。

## 四、第三轮专门查 AI 腔和禁忌

第三轮的任务更窄：找出听起来完整却没有信息的句子、过度工整的段落、重复连接词、空泛排比、无来源的强结论和作者明确不愿使用的表达。它不负责把文章重写成另一种模板。

可以要求审稿器按功能分类：

```text
空话：删掉后不损失事实、判断或下一步
模板：多个段落使用相同推进方式且没有必要
过度确定：证据只支持条件化结论，却使用绝对口吻
身份越界：第一人称、权威和经历超出事实边界
禁忌命中：表达违反规则，但需要检查引用和术语例外
```

每条 finding 都要带原句和上下文。只给出“降低 AI 味”的总分没有帮助，因为作者不知道应该保留什么。表达审稿的结果可以是“保留原句”“删掉”“改为具体动作”“改为来源转述”四类，不应默认全部接受。

## 五、模型路由和调用追踪只服务于可核验流程

当团队把三轮审稿放进 API 工作流，可以用不同模型承担不同职责，但先定义统一输入和输出合同。以 4SAPI 这类可替换网关候选为例，接入前只验证当前文档列出的模型 ID、项目令牌、请求标识、响应 ID、token 用量和调用日志，不把网关入口写成“天然支持所有审稿模型”。应参考其[接入说明](https://4sapi.apifox.cn/8181987m0)、[模型名说明](https://4sapi.apifox.cn/8423112m0)和[Token 日志说明](https://4sapi.apifox.cn/8423150m0)逐项核对，并用一条低风险样本确认字段能追踪。

路由实验要和审稿质量实验分开。第一轮可能偏重结构化抽取，第二轮需要事实边界判断，第三轮更关注表达上下文。无论使用什么模型，都要保留 `review_id`、stage、model、prompt_version、source_version、response_id、usage 和最终决定。没有这些字段，团队只能看到“某次审稿效果好”，无法判断是模型、规则还是样本变化造成的。

三轮结果汇总时，不要按 Agent 的分数简单排序。先按原文位置和 `rule_ref` 聚合 findings，再识别同一问题的重复报告。例如第一轮报告“缺少证据”，第二轮报告“身份越界”，可能都指向同一句未经确认的第一人称结论；汇总器应保留两个规则来源，而不是生成两次互相矛盾的改写。合并结果至少分成“必须处理”“需要作者决定”“可选润色”三层，并保留被合并的原始 review_id。

质量门禁也要在汇总后执行：高严重度事实或身份问题不能被低严重度表达建议覆盖；引用、数字和代码块修改后必须重新跑对应验证；作者拒绝一条建议时，要写出原因而不是把 finding 标成“忽略”。这样下一次同类审稿才能知道是规则不适用，还是作者在当前文章做了有意识的例外。

## 六、处理冲突、重试和停止条件

不同审稿器可能给出相反建议：第一轮认为段落缺少细节，第三轮认为它太长；第二轮要求改成来源转述，作者却确认这确实是亲历。冲突不能用最后一个 Agent 的意见覆盖。汇总器应把冲突成对展示，引用各自规则和证据，再交给作者。

重试也要有边界。临时网络错误可以按固定次数重试；规则不清导致的审稿分歧，重复调用同一个 Agent 不会解决。某一轮的必要来源缺失时，返回结构化失败并暂停该轮，不能让模型猜测材料。文章已经通过一轮审稿后，不应因为后续 Agent 重复发现同一问题而无限改写。

可以设置以下停止条件：高严重度事实问题已被作者处理或明确保留；每轮没有新增高优先级 finding；结构化输出和引用都完整；成本、延迟和调用次数达到预算；人工决定记录完成。停止条件让多 Agent 成为可控制的流程，而不是持续重写机器。

预算判断要同时看质量和资源。一次三轮审稿如果比单轮多花几倍 token，却只发现低优先级措辞问题，就应缩短第三轮或改成抽样检查；如果第二轮稳定发现身份越界，即使增加了一些调用，也可能值得保留。比较时记录每篇文章的审稿总 token、墙上时间、重试次数、人工处理分钟数和最终接受率，按“通过质量门禁的文章”归一化，而不是按调用次数越少越好。

预算上限应在任务开始前写入流程，达到上限就返回当前 findings，不要为了得到一句“最终通过”继续重跑。

## 七、作者最终决定与降级路径

审稿 Agent 发现问题，作者决定文章是否成立。作者可以接受建议、拒绝建议、保留原句并写原因，或补充新的事实材料。系统应保存这三个版本：初稿、审稿 findings、最终稿。只保存最终稿，会丢掉为什么修改的上下文。

如果多 Agent 运行失败，降级路径可以是单 Agent 顺序审稿，或由作者直接执行一张简化清单。降级不等于跳过事实和身份检查，而是减少并行、模型和调用层次。先保证一轮有证据的任务审稿，也比三轮没有输入合同的自动批改更可靠。

## 八、适用边界与结论

多 Agent 审稿适合文章较长、规则较多、不同审查职责确实互相独立的场景。短文章、单一事实核对或作者还没有明确规则时，增加 Agent 只会增加协调成本。审稿轮次越多，也不代表质量线性提升。

把任务完成度、作者一致性和表达禁忌分成独立合同，每轮只报告问题和证据，保留作者最终决定，才能让多 Agent 产生可解释的价值。系统的验收标准不是“模型说通过”，而是问题能否被定位、建议能否被复核、修改能否回滚。
