# Vibe Coding 页面结构怎么设计：从首屏到完整叙事

网页做出来以后，用户不知道先看什么；Hero 很大，下面却没有清晰内容；项目卡片很好看，点进去又没有详情；FAQ 和 Footer 只是为了“把页面填满”。这些问题通常不是 CSS 写错，而是页面结构没有先设计。

布局回答“内容怎么排”，页面结构回答“用户先看到什么、接着看到什么、最后完成什么”。如果没有结构，Agent 往往会从一张漂亮的 Hero 开始，然后按照常见模板顺手添加 About、Features 和 Contact，结果页面看起来完整，却没有明确的阅读路径。

本文从用户目标、内容规模、页面生命周期和主要行动四个角度，拆解 10 种页面结构和叙事模块，并给出一份可以直接交给 Vibe Coding Agent 的页面规划方法。

## 1. 先画用户路径，再列区块

在写页面提示词之前，先回答：

```text
用户为什么来到这个页面？
他第一眼必须理解什么？
他需要哪些证据才会继续？
他最终要点击、阅读、联系还是完成任务？
如果不行动，他还可以去哪里？
```

例如个人作品集的路径可能是：

```text
确认身份和方向
  -> 查看代表项目
  -> 了解项目过程和能力
  -> 阅读文章或经历
  -> 发起联系
```

AI 工具落地页的路径可能是：

```text
理解问题
  -> 看到产品如何解决
  -> 查看工作流程和限制
  -> 处理常见疑问
  -> 开始试用或联系团队
```

页面结构应该服务于这条路径，而不是把所有区块平均排列。

## 2. Single-page Website：内容少、路径短

单页网站把主要内容放在一个页面里，用户通过滚动或锚点浏览。

### 适合什么

```text
个人名片。
轻量作品集。
活动页。
内容量不大的服务介绍。
早期产品首页。
```

### 可复制提示词

```text
创建一个单页个人作品网站。
页面顺序固定为 Hero、About、Selected Work、Writing、Contact 和 Footer。
顶部导航使用 Anchor Links 跳转到对应区块，每个区块设置唯一 id 和语义化标题。
移动端保持自然纵向阅读，不把每个区块压成过小的卡片。
```

### 验收重点

检查滚动顺序是否符合用户目标、锚点是否能正确定位、Sticky Header 是否遮挡标题，以及页面变长后是否仍有回到顶部的路径。平滑滚动要尊重 `prefers-reduced-motion`，不能只追求动画效果。

## 3. Multi-page Website：内容需要独立增长

多页网站让首页、作品列表、项目详情、关于、文章和联系拥有独立 URL。它适合长期维护和内容持续增加的网站。

### 适合什么

```text
成熟作品集。
博客和内容站。
企业官网。
项目较多的产品站。
需要独立分享和搜索的页面。
```

### 可复制提示词

```text
把网站设计为多页结构：Home、Work、Project Detail、About、Journal、Article 和 Contact。
所有页面共享统一 Header 与 Footer。
每个页面有清晰的 active 导航状态。
作品卡片点击后进入独立项目详情页，文章列表点击后进入独立文章页。
请先输出路由和页面关系，再开始实现。
```

### 验收重点

页面是否有真实 URL，刷新和直接打开详情页是否正常，返回和分享是否符合预期，公共 Header/Footer 是否一致，当前页面是否能被用户识别。不要把多页网站做成一个页面加几个隐藏区块。

## 4. Landing Page：围绕一个行动组织内容

落地页不是“首页加更多区块”，而是围绕一个主要行动组织内容。这个行动可以是预约、下载、试用、订阅或联系，但一页最好只有一个主目标。

### 页面顺序

```text
Hero：用户是谁、产品解决什么问题。
痛点：为什么现在需要处理。
价值：产品或服务如何解决。
流程：用户接下来会经历什么。
案例：为什么应该相信。
FAQ：消除关键疑虑。
最终 CTA：完成主要行动。
```

### 可复制提示词

```text
为一个 AI 设计服务创建 Landing Page。
唯一主目标是预约一次咨询。
页面包含 Hero、问题、服务价值、工作流程、三个案例、客户评价、FAQ 和最终 CTA。
所有主要按钮使用同一行动文案，不加入与预约目标无关的复杂导航。
请明确每个区块如何推动用户理解或行动，不要为了凑长度添加区块。
```

### 验收重点

如果用户在首屏和页面底部看到两个不同的主行动，说明目标没有收敛。CTA 也不能替代事实：案例需要真实来源，评价不能由模型凭空生成。

## 5. Case Study Page：讲清问题如何被解决

案例研究页和普通项目详情页的区别，是它不仅展示最终效果，还解释背景、问题、过程、关键决策、方案、结果和复盘。

### 适合什么

```text
设计师作品集。
开发者项目。
产品项目。
品牌案例。
求职作品集。
```

### 可复制提示词

```text
创建一个项目案例研究页。
内容顺序为 Overview、Problem、Role、Process、Key Decisions、Solution、Outcome 和 Reflection。
顶部使用项目封面，正文保持窄阅读宽度，过程图片可以全宽穿插。
桌面端右侧提供 Sticky Table of Contents，手机端改为顶部目录按钮。
每个关键决策都说明背景、选项、选择理由和验证证据。
```

### 验收重点

检查读者能否只看标题就理解项目过程，图片是否有说明，结果数据是否有来源，作者负责的部分是否和团队成果分开。没有证据的“提升了体验”不应写成结论。

## 6. Hero Section：回答首屏四个问题

Hero 是用户打开页面最先看到的区域，它至少要回答：

```text
你是谁？
你做什么？
为什么值得继续看？
下一步应该点哪里？
```

Hero 不是一张巨大的装饰图。它需要有可读的标题、补充说明、主要行动和与主题相关的视觉。移动端要确保标题、说明和按钮仍然在首屏形成清晰层级。

### 可复制提示词

```text
创建一个个人作品集 Hero。
主标题明确表达身份和工作方向，副标题控制在两到三行内。
提供 View Work 和 Contact 两个层级明确的按钮。
视觉内容与网站主题相关，不使用无关的办公桌、家居产品或商业图库人物。
桌面端和 390px 移动端都要验证标题、按钮和视觉的排列。
```

## 7. Feature Grid：并列解释能力

Feature Grid 用 3 到 6 个并列模块介绍能力、服务或产品功能。它适合同一级信息，不适合承载长篇案例。

```text
Design：负责视觉和交互方向。
Frontend：负责页面实现和响应式。
AI Prototyping：负责 Agent 辅助的快速验证。
Writing：负责研究、叙事和内容交付。
```

### 验收重点

每个模块的标题和说明长度要接近，图标只是辅助识别，不要用夸张图标替代文字。桌面端可以四列，平板两列，手机单列；不要为了保留四列而让文字无法阅读。

## 8. Sticky Storytelling：让过程随着滚动展开

Sticky Storytelling 一侧固定当前阶段，另一侧随着滚动展示阶段内容，适合产品故事、项目过程和复杂功能解释。

### 可复制提示词

```text
设计一个 Sticky Storytelling Section。
桌面端左侧约 38% 区域保持 sticky，展示当前阶段标题和说明。
右侧依次展示 Discover、Design、Build 三个面板。
当某个面板进入视口时，更新左侧当前阶段。
手机端取消 sticky，改为正常纵向排列，并在每个面板内重复阶段标题。
```

### 验收重点

滚动到某个阶段时，左侧状态是否更新，键盘用户是否能阅读完整内容，手机端取消 sticky 后信息是否仍然完整。不要让左侧固定区域挡住正文，也不要只在桌面端验证。

## 9. Timeline：按时间表达经历和进展

Timeline 使用节点和时间顺序展示经历、版本、里程碑或学习路径。它适合有明确时间关系的内容，不适合把没有顺序的能力列表硬排成时间线。

### 可复制提示词

```text
在 About 页面添加 Vertical Timeline。
每个节点包含年份、事件标题和两行说明。
桌面端内容位于时间线右侧，手机端保持单列。
时间线使用清晰的文本和节点，不要做成复杂路线地图。
```

### 验收重点

日期格式是否统一，节点是否按真实时间排序，未来计划是否和已完成经历区分，长说明是否会压缩节点。时间线的视觉线条不能成为唯一信息，屏幕阅读器仍需要读到顺序和日期。

## 10. FAQ 和 Footer：处理疑问与收尾

FAQ 通常放在页面末段，用于回答会阻碍下一步行动的问题。Footer 则承担站点导航、社交链接、联系方式、版权和隐私信息。

### FAQ 提示词

```text
在 Contact 之前添加 FAQ。
问题围绕合作范围、交付周期、是否提供开发和如何开始合作。
答案默认折叠，同一时间只展开一个项目。
每个标题使用原生 button，正确设置 aria-expanded 和 aria-controls。
```

### Footer 提示词

```text
创建完整 Footer。
左侧放 Logo 和一句简介，中间分为 Explore、Connect、Elsewhere 三组链接。
右侧放邮箱和订阅入口，底部放版权与隐私链接。
Footer 颜色与主体形成清晰收尾，链接使用真实目标，不放无法验证的社交账号。
```

FAQ 的答案不能凭空补充业务承诺。Footer 也不能只是“版权 2026”，要确保用户可以继续浏览和找到联系方式。

## 11. 页面类型和区块的组合

| 页面目标 | 推荐结构 | 关键区块 | 不要做什么 |
| --- | --- | --- | --- |
| 个人名片 | Single-page | Hero、About、Work、Contact | 塞入过多项目细节 |
| 成熟作品集 | Multi-page | Work、Detail、Journal、About | 用隐藏区块伪装多页 |
| 单一转化目标 | Landing Page | Hero、价值、案例、FAQ、CTA | 放多个互相竞争的行动 |
| 展示解决过程 | Case Study | Problem、Role、Process、Outcome | 只有成品图没有决策 |
| 产品后台 | 多页应用结构 | Sidebar、Dashboard、表格、设置 | 只做默认有数据状态 |
| 个人经历 | About + Timeline | Timeline、能力、经历、联系 | 把能力列表伪装成经历 |
```

## 12. 用提示词先生成结构，不要先生成样式

一个更可靠的页面结构提示词可以这样写：

```text
目标：设计一个个人 AI 产品作品集网站。
受众：希望了解项目能力和合作方式的潜在客户。
主要路径：理解身份 -> 查看代表项目 -> 阅读案例 -> 发起联系。
页面：Home、Work、Project Detail、About、Journal、Contact。
Home 顺序：Hero、Selected Work、Capabilities、Writing、Contact、Footer。
Project Detail 顺序：Overview、Problem、Role、Process、Decisions、Outcome、Reflection。
约束：每个页面只保留服务于主要路径的区块，移动端重新排序，不把桌面布局缩小。
输出：先给出页面树、区块顺序、每个区块的目标和验收条件，不要直接写代码。
```

计划确认后再让 Agent 实现，可以显著减少“做了一整页但顺序不对”的返工。

## 13. 模型怎么参与页面结构工作

页面结构任务可以分成“信息架构整理、文案草拟、代码实现、截图评审”几个阶段；如果使用 4SAPI 作为可替换模型入口，可以让不同阶段使用适合文本、代码或视觉检查的模型，但具体模型名和参数应以当前配置和实际任务验证为准。

截图评审至少检查：

```text
首屏是否说明身份和目标？
区块顺序是否对应用户路径？
每个区块是否有明确作用？
页面是否在中途提供证据？
FAQ 和 Footer 是否真的解决疑问和收尾？
```

## 14. 常见失败

### 首屏很大，内容很少

Hero 占据了大量空间，却没有说明身份、价值和下一步。修复方法是先补目标和行动层级，不是继续放大标题。

### 所有页面都有相同区块

首页、案例页和文章页都使用同一套 Hero、Feature Grid 和 CTA，用户无法区分页面任务。每个页面要有自己的主要问题。

### 过程被压缩成装饰

Case Study 只有图片和结果，没有背景、决策和证据。增加“过程”两个字不够，需要补真实内容和来源。

### 移动端丢失结构

Sticky Storytelling、侧边目录和多列 Feature Grid 在手机端如果不降级，用户会被固定区域和横向滚动阻塞。每个桌面模式都要定义移动端替代结构。

## 15. 结论与限制

页面结构的任务是组织阅读和行动，不是把词典里的模块全部放上去。单页适合短路径，多页适合内容增长，Landing Page 服务一个主要行动，Case Study 解释问题如何被解决；Hero、Feature Grid、Timeline、FAQ 和 Footer 则分别承担首屏、并列说明、时间顺序、疑问处理和站点收尾。

Vibe Coding 时，先写用户路径和页面树，再写视觉风格和组件。结构确认后，Agent 才知道每个区块为什么存在，也更容易在截图和人工审阅中发现问题。具体行业内容、数据和行动承诺仍需由项目负责人核对，模板本身不能替代真实信息。
