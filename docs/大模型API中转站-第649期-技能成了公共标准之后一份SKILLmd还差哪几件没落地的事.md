# 技能成了公共标准之后，一份 SKILL.md 还差哪几件没落地的事

十月的公告里有两句话，常被合起来读成终局：标准捐给了基金会；自 2025 年 12 月起有七十多个平台接入。

捐是捐了。2026 年 10 月 22 日，Anthropic 把 Agent Skills 这个"开放标准"交给 Agentic AI Foundation（AAIF）——Linux Foundation 下的基金会，前一年由 Anthropic、Block、OpenAI 共同创立，MCP 也捐在那里。捐出的具体物件是名称与标志、GitHub 组织、agentskills.io 域名。

但"标准统一"这四个字，落到实处是一个很小的问题：**统一的是哪一层？**

我把公告和规范页都读了一遍，下面说清楚它统一了什么、没统一什么，以及现在能拿来做什么。

## 一、它统一的东西小得有点意外

目录布局上的硬约定只有一条：必须有 SKILL.md。开头这段目录树说完了布局：

```
skill-name/
├── SKILL.md      # 必需：元数据 + 指令
├── scripts/      # 可选：可执行代码
├── references/   # 可选：文档
├── assets/       # 可选：模板、资源
└── ...           # 任意其他文件或目录
```

SKILL.md 本身是 YAML frontmatter 加 Markdown 正文。

就这些。规范不定义运行时协议、RPC、注册中心和 schema 版本号。我判断这是它在十个月左右被七十个平台接进去的一个原因，也是它管不到质量的原因。

对比一下 MCP 就清楚了：MCP 规定的是**进程之间怎么说话**，所以需要传输层、握手、能力协商。技能规定的是**给智能体的一份说明书长什么样**，所以只需要一个文件名和几个字段。前者是接口，后者是文档格式。

## 二、六个字段里，只有两个是必填

规范给出的字段表，完整但克制：

| 字段 | 必填 | 约束 |
| --- | --- | --- |
| `name` | 是 | ≤64 字符，仅小写字母、数字与连字符；不能以连字符开头或结尾；不能有连续连字符；**必须与父目录名一致** |
| `description` | 是 | ≤1024 字符，非空，要写清"做什么"和"何时用" |
| `license` | 否 | 许可证名称，或指向随附许可证文件的引用 |
| `compatibility` | 否 | ≤500 字符，写环境要求（目标产品、系统依赖、网络访问等） |
| `metadata` | 否 | 任意字符串键值映射 |
| `allowed-tools` | 否 | 空格分隔的预批准工具列表，**标注为实验性** |

必填只有两个。这个选择背后有个判断：**一个技能能不能被找到，取决于 name 能不能寻址、description 能不能匹配意图**，其余都是附加信息。

`name` 那条"必须与父目录名一致"看着像洁癖，其实是把"技能的身份"绑到了文件系统路径上。好处是客户端可以靠目录名定位、去重、报错；代价是你没法在不改目录名的前提下重命名一个技能。

`description` 的约束更值得抄。规范给的差评示例是"Helps with PDFs."，好评示例是：

> Extracts text and tables from PDF files, fills PDF forms, and merges multiple PDFs. Use when working with PDF documents or when the user mentions PDFs, forms, or document extraction.

差别不在文采，在**可匹配性**。技能是否被激活，第一道关就是这句话跟用户那句话有多像。写不清"何时用"，技能就等于不存在。

## 三、正文一次全载，所以它逼你分层

规范里有一句需要注意的话：智能体一旦决定激活某个技能，就会**加载整个 SKILL.md**。

这解释了三层加载（元数据、正文、资源）的设计意图。既然正文会被整份塞进上下文，那正文就该短、就该只放流程；细节放 `references/`，代码放 `scripts/`，模板放 `assets/`，正文里用相对路径引用。

官方推荐的正文结构也很朴素：分步指令、输入输出示例、常见边界情况。规范明确说"没有格式限制"——这句话是给创作者的自由，也是给审计者的提醒：**你能约束的只有字段，正文里写什么全凭作者自觉。**

## 四、标准化的收益在哪一层

公告把收益叫"互操作"：自 2025 年 12 月标准发布以来，70 多个 agent 平台接入，点名了 ChatGPT、Cursor、GitHub Copilot、VS Code。按规范的设计意图，同一个技能文件夹换个客户端应该能被读到——这句是意图，不是我实测的结果。

我判断这层收益是真的，但它有上限。用一个具体场景说明：

- **能跨平台的部分**：目录结构、frontmatter 字段、正文的加载时机。
- **不能跨平台的部分**：技能会不会被触发（各家的检索与匹配策略不同）、脚本能不能跑（各家执行环境不同）、`allowed-tools` 认不认（规范自己标了实验性，支持程度因实现而异）。

所以"一份 SKILL.md 到处跑"这句话，准确版本是"一份 SKILL.md 到处能被读到"。读到之后行为一致不一致，取决于客户端，不取决于标准。

## 五、数字要看清口径

公告给了一组很响的数字：**100 万个技能已发布，安装量接近 2.8 亿次。**

先说这组数字能支持什么：它说明生态规模起来了，不是几个示例仓库自娱自乐。这在这类标准的早期是关键信号——没有内容的标准很难被采用。

再说它不能支持什么：

1. **不能说明质量。** 一百万个技能里有多少是可用的、有多少是同一模板批量生成的，公告没说。
2. **不能说明复用。** "安装"是一个动作，不等于长期使用。2.8 亿次安装摊到 100 万个技能上，平均每个不到 300 次，这个分布大概率极不均匀。
3. **口径未公开。** 什么算一次安装、重复安装怎么计，公告没有说明。

这些数字我照抄，但不当成质量证据用。

## 六、捐给基金会，变的是什么

公告的措辞是把标准放进一个"中立之家"，"确保社区对技能标准往哪走有发言权"。**我把它读作控制权的转移——这是我的解读，不是公告用词。**

具体捐了三样：名称与标志、GitHub 组织、agentskills.io 域名。公告同时写明一句很关键的话：**不加入 AAIF 也可以继续使用或贡献这个标准。** 也就是说，加入基金会不是使用许可的前提。

维护方式也写明了：来自 Anthropic、Google、OpenAI 等公司的工程师以**个人身份**维护，设两名牵头维护者。这个安排值得注意——是"个人身份"，不是"公司席位"。前者更接近开源项目的维护者模式，后者接近标准组织的代表制。两者在决策出分歧时表现完全不同。

## 七、还没落地的三件事

公告里"下一步"那一段是提议，不是既成事实。提议三件事：

| 提议 | 现状 | 意味着什么 |
| --- | --- | --- |
| 版本化发布 | 提议中 | 现在没有版本号约定，两份 SKILL.md 是否兼容无法从文件判断 |
| 正式提案流程 | 提议中 | 目前只有公开讨论渠道，没有成文的提案流程 |
| 安全指引 | 提议中 | 面向"写技能的人"和"装技能的人"的规范还没有，只有零散的实践建议 |

第一条对使用者影响最大。技能会被安装、被复制、被改，但没有版本字段可读——`metadata` 里可以自己塞一个 `version`，但那是约定，不是标准。我在自己的仓库里就这么干过：写了个 `version: "1.0"`，客户端不认识，只有我自己认。

官方的创作者文档补的是写法、描述优化、评估和脚本，不涉及版本化；而且那是**指南**，不是**标准条款**。指南教你怎么做好，标准只规定什么算合法。

## 八、现在能拿它做什么

我的判断分三层。

**当格式用，现在就能用。** 一个文件夹、一个 SKILL.md、两个必填字段。这个约定足够简单，简单到你今天就能把自己团队的三五个流程写成技能，不用等任何人的批准。

**当兼容性承诺用，要谨慎。** 跨平台能"读"，不等于跨平台能"跑得一样"。上线前必须在目标客户端里各跑一遍，别信"支持 Agent Skills"这句话。

**当治理框架用，还太早。** 版本化、提案流程、安全指引都在提议阶段。现在依赖它做合规论证，会缺一条腿。

## 九、三种会被误读的说法

围绕这次捐赠的讨论里，有三句话我反复看到。每一句都对了一半。

**"技能已经有正式标准了。"** 格式有，治理还没有。规范的条款是成文的，但版本化发布、提案流程、安全指引三项都在提议阶段。拿它当合规依据，等于只引用了格式那一半。

**"捐给基金会就等于中立了。"** 控制权挪了位置，维护者还是同一批公司的工程师，只是以个人身份参与。中立性更多来自"个人身份加公开讨论"这套机制，不是来自基金会这块牌子。

**"一份技能能在所有客户端里跑。"** 能读到，不一定跑得一样。触发策略、执行环境、`allowed-tools` 的支持范围都在客户端那一侧，标准管不到。

三句话的共同点：把"格式统一"当成了"行为统一"。这两件事之间隔着一整个实现层。

## 十、结论与边界

标准化的价值不在它规定了多少，而在它**只规定了很少**。一个文件夹加一份说明书，上手成本很低，这是它能扩散的真正原因。

代价同样来自"规定得少"：质量、安全、版本、行为一致性，全在下游各自解决。捐给基金会解决的是"谁说了算"，不解决"怎么保证"。

本文的限制：只读了公告与规范页，没有在 Cursor、Copilot、VS Code 里实际安装对比；70 个平台、100 万技能、2.8 亿安装均为公告自述；`allowed-tools` 的实际支持范围未测；路线图三项均为提议，未生效。

下一步如果只做一件事：挑一个你每周都要重复的流程，写成带 `scripts/` 的技能，在两个不同客户端里各跑一次，把两次的差异记下来——那份差异清单，就是这个标准目前真正覆盖的范围。
