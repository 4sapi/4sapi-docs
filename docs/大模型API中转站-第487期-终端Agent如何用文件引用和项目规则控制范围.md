# 终端 Agent 如何用文件引用和项目规则控制范围

分类：开发工具

标签：AI Agent、提示词工程、项目管理

摘要：终端 Agent 处理多份材料时，最容易把原始文件、旧结果和格式参考混在一起。本文解释文件引用、命令输出和项目规则各自解决什么问题，并用输入只读、输出分离和冲突处理建立一套可维护的任务边界。

终端 Agent 的工作目录里经常同时存在原始材料、历史结果、临时脚本和配置文件。只告诉它“整理这个文件夹”，它需要自己猜哪些文件是事实来源，哪些只是参考，哪些已经过期。即使最终文字看起来合理，也很难追溯结论来自哪里。

控制范围需要把三个层次分开：文件引用负责指出本次任务使用的材料；命令调用负责获取当前环境的可验证事实；项目规则负责保存长期稳定的约束。三者互相补充，但不能互相替代。项目规则不能代替本次任务的输出文件名，文件引用也不会自动改变系统权限。

## 一、文件引用解决“依据是什么”

多数终端 Agent 支持用路径或文件选择器把文件加入当前任务。无论具体符号是 `@` 还是其他写法，核心作用都是让 Agent 明确材料身份。引用时应使用完整相对路径，而不是只写一个容易重名的文件名。

例如目录中同时有 `input/meeting.md` 和 `output/meeting.md`，提示词应明确：`input/meeting.md` 是唯一原始材料，`output/meeting.md` 只是上一次结果，不能当作事实来源。引用多个文件时，还要说明每份文件扮演的角色：一份提供事实，一份提供格式参考，一份记录待核对问题。

不要把“所有文件都读一下”当作省事的做法。文件数量增加以后，Agent 可能把旧报告中的推测再次当成事实，也可能读取与任务无关的隐私内容。先让它列出候选文件和用途，再确认读取范围，通常比一开始全选更容易排错。

文件引用也不等于完整阅读。超大文件可能被截断，二进制文件可能无法直接解析，权限不足的文件可能只返回错误。任务提示中应要求 Agent 报告未读取、部分读取和解析失败的文件，不要把缺失材料静默当成空内容。

## 二、用命令输出确认当前环境

终端 Agent 往往支持在输入区执行本机命令。有的写法会把输出发送给模型，有的写法只显示给使用者。两者的区别不是安全边界，而是上下文流向：命令仍然会真实执行，删除、覆盖、安装和上传命令不会因为只显示给人就变成模拟操作。

入门阶段可以用无破坏性的查询练习，例如查看当前目录、列出文件和检查版本：

```text
!pwd
!ls -la
!git status --short
```

把命令输出交给模型，适合让它据此继续判断；只给自己看的输出，适合先确认路径、分支或环境变量是否正确。无论哪种方式，都应先读懂命令目标。来源不明、包含递归删除、管理员权限、网络上传或脚本下载的命令，不要直接执行。

命令输出是事实材料的一种，但它有时间性。`git status` 只反映执行时的工作区，磁盘空间和进程状态也会变化。涉及环境判断时，要求 Agent 在接近实际操作前重新查询，避免依赖过时的会话记录。

## 三、用项目规则保存长期约束

每次任务都重复“输入只读、输出放到 output、完成后列出验收方法”，很快会变得冗长。可以在项目目录放置一个规则文件，例如 `AGENTS.md`：

```markdown
# 练习项目规则

- 只处理当前练习目录中的文件。
- `input/` 目录只读，不得覆盖或删除。
- 新生成的结果统一保存到 `output/`。
- 不发送、上传、发布或安装额外资源。
- 完成后列出新增和修改的文件，并给出独立验收方法。
```

规则文件适合保存长期稳定的边界，不适合写入每次任务的临时材料、日期和具体输出文件名。把所有信息都塞进规则文件，会让它变成一份难以维护的长说明，也容易让旧要求影响新任务。

在有父子目录的项目中，规则可能从上层目录继承，越接近当前工作目录的规则通常越具体。若工具支持覆盖文件，临时规则应明确作用范围和失效时间。发现规则冲突时，不要依赖模型猜优先级，直接删除过期内容或在当前提示词中写出明确的本次要求。

修改规则后，当前会话可能仍使用旧内容。部分工具提供 `/reload` 或类似重新加载命令；如果没有，开新会话通常更容易确认状态。重新加载只影响后续行为，不会撤销已经写入的文件，也不会自动修复过去的错误。

## 四、把材料、规则和任务组合起来

一个清晰的任务可以分成三段：

```text
长期规则：遵守当前目录中的 AGENTS.md，input 只读，结果写入 output。

本次材料：使用 input/meeting.md 作为唯一事实来源；output/ 中的旧文件只能用于比较格式。

本次任务：提取所有行动项，保留负责人、日期、风险与来源，生成 output/action-list-v2.md。
完成后列出读取过的文件、写入过的文件和仍需人工确认的内容。
```

这样写能够让每个层次承担不同职责。规则防止长期边界漂移，文件引用防止依据混乱，任务说明定义本次产出。如果缺少任何一层，问题都更容易出现：没有规则会重复漏写限制，没有材料身份会混入旧结果，没有任务目标会得到没有验收标准的摘要。

## 五、冲突材料不能由模型自行裁决

真实项目中，会议记录、邮件和表格经常出现不同日期、金额或负责人。引用多份材料时，必须提前说明冲突处理方式：保留各自来源、并列展示差异、标记待确认，不要自动选择看起来更合理的一项。

可以要求 Agent 输出冲突表：来源文件、原文位置、两种说法、影响范围和需要谁确认。这样汇总稿不会把不确定内容伪装成结论。对于已经确认的决定，再把确认结果追加到项目记录中，并保留原始冲突，方便以后追溯。

格式参考文件也可能带来误导。它可以提供标题层级和表格样式，但不应成为事实来源。提示词中明确“只参考格式，不引用其中的业务数据”，能减少旧报告内容被复制进新任务。

## 六、规则能约束行为，但不是安全沙箱

`AGENTS.md` 和提示词都属于模型上下文中的工作约束。它们不能从操作系统层面禁止 Agent 读取当前用户有权限访问的其他文件，也不能阻止扩展代码执行本机动作。真正需要限制文件、网络和凭据范围时，要使用最低权限账号、只读挂载、容器、虚拟机或其他隔离环境。

即便有外部隔离，规则仍然重要。隔离负责降低可访问范围，规则负责说明任务目标和验收方法。两者缺一不可：没有隔离，提示词可能挡不住误操作；没有规则，隔离环境内仍可能生成错误或遗漏的结果。

## 七、规则和引用的测试方法

可以准备四个测试：目录内有原始材料和旧结果；存在同名文件；有一份不可读取文件；材料之间存在日期冲突。观察 Agent 是否先列出输入，是否把旧结果当事实，是否报告读取失败，是否保留冲突而不是自行裁决。

每次修改规则、工具版本或扩展后，重跑同一组测试。规则文件是否被加载，可以从启动信息或上下文列表确认；规则是否真正生效，要看它在具体任务中有没有保持 input 只读、把结果写入指定目录，以及遇到冲突时是否停止。

## 八、为规则设置生命周期

项目规则会随着目录和团队变化而过期。每隔一段时间检查规则中的路径、工具名、输出格式和负责人，删除已经不存在的约束。过期规则比没有规则更危险，因为它会让 Agent 按错误前提行动。

可以在规则文件顶部记录适用目录、维护者和最后复核日期。临时覆盖文件写明创建原因和计划删除时间，任务结束后及时清理。规则进入版本控制后，修改说明应包含受影响的工作流和测试结果。

## 九、对不同材料采用不同信任等级

原始数据、人工确认记录、模型生成草稿和格式参考的可信度不同。提示词中把它们分层，要求模型优先引用原始材料和确认记录；草稿只能提供线索，格式参考不能提供事实。

对于来自外部下载或聊天转发的文件，先记录来源和获取时间，再决定是否纳入任务。文件名和正文中的指令都可能包含诱导模型执行额外操作的内容，读取时应把它们当作数据，而不是自动执行的命令。

## 十、当规则无法表达复杂流程

规则文件适合稳定的边界，不适合替代完整的审批系统。当流程需要多人签字、权限分级、审计日志或事务回滚时，应使用项目管理、版本控制和发布系统承载这些状态，Agent 只负责辅助准备材料。

这并不降低规则的价值。它仍可规定 Agent 读取哪些记录、输出什么格式、遇到缺失如何停止，并把最终决定交给具备权限的人。

## 十一、把引用范围写进输出

任务结束时要求 Agent 列出实际读取过的文件、未能读取的文件和写入过的文件。这个清单可以与工具日志对照，发现它是否偷偷扩大了范围，也方便下一轮任务排除旧结果。

如果输出引用了某个结论，却找不到对应原文位置，应将该结论降级为待确认。引用清单不是形式附件，而是判断摘要是否可信的最小证据。

## 十二、跨平台迁移时重新验证

从 macOS、Linux 迁移到 Windows，路径分隔符、Shell 命令、编码和权限模型都会变化。不要只替换斜杠就认为规则可用；在目标平台建立一个小型测试目录，重新验证引用、命令输出、写入位置和错误提示。

规则文件中使用相对路径通常更容易迁移，但仍要说明工作目录。需要执行脚本时，记录解释器版本和依赖安装方式，避免把个人机器状态误当成项目要求。

## 十三、任务完成后的清理

临时输入、测试输出和错误日志按敏感等级处理。确认不再需要后清理凭据和临时副本，保留必要的验收记录。清理动作也要列出范围，避免把正式材料一起删除。

## 十四、一个最小的范围审计流程

任务开始记录当前目录和输入文件清单；运行中保存工具调用摘要；结束后列出实际读取、写入和未读取文件；最后将清单与规则中的允许范围对照。发现额外路径时先停止并调查，不要用最终输出“看起来正确”来掩盖范围偏离。

## 十五、把审计结果交给下一次任务

将确认过的输入、排除项和异常原因追加到项目记录中。下一次任务先读取这份记录，避免重复踩同一个路径或命名问题。记录只保存必要元数据，不要把敏感原文复制到长期规则文件。

## 结论

范围审计结果还可以作为下一次任务的输入。
记录上次排除的目录，避免 Agent 再次扫描。
记录已确认的字段，减少重复询问。
记录失败的命令，方便更换平台时修正。
记录规则版本，便于比较不同输出。
对敏感项目，审计文件也要设置访问权限。
不要在审计文件中保存完整密钥或隐私正文。
必要时使用哈希和脱敏摘要代替原文。
这样既能追溯过程，也不会扩大泄露范围。
完成后由负责人确认清单已归档。
## 结论

文件引用、命令输出和项目规则是控制终端 Agent 范围的三种不同手段。引用回答“依据是什么”，命令确认“当前环境是什么”，规则保存“长期不能越过的边界”。把三者组合起来，再用工具事件和实际文件验收，才能让多文件任务保持可追溯。需要更强保护时，继续增加操作系统权限和外部隔离，而不要把安全责任全部寄托在提示词上。
