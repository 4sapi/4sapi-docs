# 字段抽取模型的两种请求方式：开放与指定 schema 的取舍与代价

发票、化验单、身份证、银行流水——这些文档的共同点不是"需要读全文"，而是"只需要几个字段进系统"。用 OCR 拿到全文之后，仍然要有人写代码把每个值映射到正确的字段，这一步长期靠正则和人力。

Dharma-AI 在 2026 年 11 月 4 日的[官方博客](https://huggingface.co/blog/Dharma-AI/dharma-field-extractor)里发布了一个专门做这件事的模型：原文称 2B 参数，输入文档图像，输出结构化 JSON，声称在自建基准上超过所测的全部通用前沿模型，成本低 6 到 147 倍（检索日期 2026-11-05）。

这些数字值得认真读，但它们有前提。本文按"两种请求方式 → 指标怎么算 → 数字怎么读 → 成本口径 → 一个硬边界"的顺序拆开。0.834 等分数是厂商自测，我没有复现；文中我会逐处标明哪些是原文、哪些是我的推断。

## 一、它到底接受什么、返回什么

按博客原文，这个模型有两种请求方式：

| 方式 | 输入 | 输出 | 适用场景 |
| --- | --- | --- | --- |
| Open | 文档图像，不给 schema | 模型自行判断哪些是"标签+值"或"表头+列"，返回键值对 | 你先不知道文档里有什么 |
| Schema-directed | 文档图像 + 精确 schema（每个字段带 string/number/boolean 类型） | 严格按 schema 返回，键名与你给的一致，文档里没有的返回 null | 下游系统的字段结构已经固定 |

几个细节值得单独记：

1. **同一检查点覆盖所有文档类型**，不做按类型的微调。原文的原话是"同一个检查点处理所有这些，无需按类型微调"。
2. **幽灵字段不编造**。原文明确：如果请求的字段文档上没有，返回 `null` 而不是编一个值。
3. **嵌套跟随文档结构**。发票的每一行明细作为有序列表返回，每行有自己的数量和金额，与总计并列。
4. **原文称返回严格贴合 schema**：键名一致、不多字段。这条我只在原文的示例层面看到（发票与表单两个例子），没有做独立验证；它是否普遍成立，取决于你自己的文档，见第三节与下一篇的验收方法。

第三、四点是它与"让通用模型按提示词输出 JSON"的区别：后者不是做不到，而是**每次都要重新确认形状**。

## 二、它是怎么训练出来的

原文给的训练信息比一般发布稿具体：

| 项目 | 内容 |
| --- | --- |
| 基座 | 原文写 DharmaOCR-LITE v1.1，**2B 参数**（已用监督微调与 DPO 专门做过 OCR）。但这个"2B"跟另外两处公开信息对不上：论**文**版的 DharmaOCR-LITE 是 3B；HF 上同名仓库（2026 年 3 月，v1.0）的 safetensors 元数据把 BF16 1.29B 与 FP8 2.77B 相加得 4.07B——同一套权重的两种精度不能直接当参数量。三处口径并列，我不判断哪个对 |
| 增量训练 | 在基座上训练一个 LoRA 适配器 |
| 训练样本 | 43,384 条，覆盖两种请求模式 |
| 数据流 | 英文多领域（公开网页收集）、巴西葡语真实文档（内部来源）、少量其他欧亚语言 |
| 标注粒度 | 字段级 |

数据混合是刻意跨领域的：收据、商业发票、表单、银行流水、身份证件与合成文档，而不是单一单据类型。这一点对"能不能直接用"影响很大——如果你的业务只有一种单据，专用模型的跨域优势未必用得上；反过来，如果一个月里发票、化验单、身份证都会来，跨域训练才有意义。

## 三、指标怎么算：三个因子相乘

原文的评分不是单一准确率，而是三项相乘：

```text
分数 = 字段级 F1 × 匹配值的 Levenshtein 相似度 × 合法 JSON 的比例
```

拆开看：

| 因子 | 算什么 | 影响 |
| --- | --- | --- |
| 字段级 F1 | 按**路径**匹配（包括表格内的位置） | 少抽、多抽、抽错位置都会扣分 |
| 值相似度 | 只对匹配上的字段算 Levenshtein 相似度 | 字段对但值有小差异，按比例扣分 |
| 合法 JSON 占比 | 输出能否解析 | 格式崩了，乘数直接把整页拉低 |

三个因子相乘意味着：**任何一项差，总分都会被压下来**。这和"字段准确率 90%"这种单一口径不是一回事。

基准规模是 546 份文档 × 3 种场景 = 1,638 个用例（我复算 546×3=1,638，一致）。三种场景是：

1. 不给 schema，抽出全部字段；
2. 给一个只点名真实字段的部分 schema；
3. 给一个**包含有意不存在的字段**的 schema。

第三种是这套基准里最值得抄的设计。它专门测"模型会不会为了满足 schema 而编造"。我在验收方法那篇里会展开怎么用。

## 四、0.834 与 0.816 的差距意味着什么

原文的对照结果：

| 模型 | 分数 | 与本模型的差 |
| --- | --- | --- |
| 本模型 | 0.834 | — |
| Claude Opus 5 | 0.816 | 1.8 个百分点 |
| GPT-5.6 Luna | 0.741 | 9.3 个百分点 |

表中只列了两个对照，原文其实测了**四个**通用前沿配置——另外两个的分数原文没有逐个给出，我无法补。另外两个设置会同时影响分数与成本，容易漏：**所有前沿模型都以 low 推理强度运行**；**Claude Opus 5 用的是自适应努力**，简单页可以跳过推理，也就是说它的每页 token 与延迟天然更低。这两条意味着：那 6 到 147 倍的成本差，是在"通用模型压低推理"的条件下算出来的，不是各家默认档位的对比。

（差值由我相减得到：0.834−0.816=0.018，0.834−0.741=0.093。）

三个读法要一起成立：

1. **对最接近的对手只领先 1.8 个百分点。** 在一个三项相乘的指标上，1.8 个百分点不是压倒性优势。原文自己也说"最接近"。
2. **对最远的对手领先 9.3 个百分点。** 差距的大小取决于你原本打算用哪家。
3. **这是厂商自测。** 基准、prompt、评分脚本都是他们自己搭的；测试集里虽然包含两个公开数据集（SROIE、FUNSD，原文声明未用于训练），但整体结论仍是自测口径。

第 3 条是读取规则而非怀疑：**自测分数能说明"这条路可行"，不能决定"我该换"。** 换不换看第五节的口径和你自己的数据。

## 五、6 到 147 倍成本：四项条件必须同时读

原文的成本结论很抓人，但它旁边就写着限定条件，这四条必须一起引用：

| 前提 | 原文的意思 |
| --- | --- |
| 对比对象不同计费 | 通用模型按 token 计费（每页平均输入/输出 token，含思考 token，对照各家公开标价）；本模型按**单张 L40S 每小时 $2.24 的 GPU 时间**折算 |
| 不是售价 | 原文明确"这不是销售价格"；自托管成本取决于硬件、用量与所需延迟 |
| 目的是说明替代路径 | 原文说这个对比是为了说明"自托管的专用小模型是前沿 API 的现实替代" |
| 通用侧压低了推理 | 原文写明**所有前沿模型都以 low 推理强度运行**，Opus 5 还用自适应努力（简单页可跳过推理）；所以 6–147 倍不是默认档位的对比 |

把这几条放在一起，能得出的结论是有限的：**在"单张 L40S 跑满、且你有量"的假设下，单位抽取成本可以显著低于按 token 计费的通用模型。** 得不出"任何情况下都便宜 147 倍"。

容易漏的一点：6 倍对的是 GPT-5.6 Luna、147 倍对的是 GPT-5.6 Sol——上下界来自**不同的对照对象**，不是同一模型的浮动范围。

### 自己算一遍的量级

按 $2.24/小时 折算，若一台 L40S 每小时处理 100 页，单页约 $0.0224（我的算术）。能不能打取决于真实吞吐、峰值并发（跑不满就摊不平）与是否已有卡。

这三项里有任何一项不成立，"自托管更便宜"在你这里就不成立——你还得先买或租卡。

## 六、一个硬边界：能给的是服务，给不了的是权重

原文没写、但决定"能不能用"的一条。

**获取路径存在，但是账号制的。** 博客里"可以在这里试用"的链接指向的是 `ocr-portal.prd-us-east-2.dharma-ai.com/login` 这个登录门户，不是官网首页；portal 需要注册账号才能进。我没有注册，所以门户里的价格、额度与条款我没有核验。

**权重没有公开。** 我去 Hugging Face 查了这个组织（[组织页](https://huggingface.co/Dharma-AI)）：`Dharma-AI` 名下当时只有一个模型 [`Dharma-OCR-LITE`](https://huggingface.co/Dharma-AI/Dharma-OCR-LITE)（2026 年 3 月创建），**没有这个 Field Extractor 的仓库**。其许可证标签是 `other`，名称 `dharmaocr-lite-license`，能否外推到 Field Extractor 我不知道。

这两条合起来意味着：

- 上面那句"自托管成本"目前是**测算前提**，不是现状——你拿不到权重，就谈不上自托管。
- 验证它短期只能走注册后的服务入口，属于"用服务"而不是"部署模型"。
- 如果你的决策前提是"能自己部署"，那现在应当把它当"待观察"，而不是"可采购"。

顺便说一句原话的用处：原文把成本写成"不是售价"，是因为它描述的是一种部署形态的测算，而不是一个能立刻买到的价格。这话本身是对的——但它不改变"权重未发布"这个事实。

## 七、什么时候这类模型值得考虑

| 你的情况 | 判断 |
| --- | --- |
| 单据类型多、字段固定、量大 | 方向匹配：跨域训练 + schema-directed 正好对上 |
| 下游字段结构已经固定 | 匹配：schema 模式的"多余字段为零"能省掉一层清洗 |
| 只在一种单据上做、量很小 | 不一定划算：自托管的固定成本摊不平 |
| 需要今天就自己部署 | 不匹配：权重未公开 |
| 对字段级差异极敏感（金额、编号） | 要自己测：总分 0.834 不代表你关心的那几个字段也 0.83 |

最后一行是本文的核心提醒。字段级 F1 是平均值，而你最在意的可能是"总金额"和"发票号"这两三个字段。平均值高，不代表关键字段不出错——这一点和我在别的评测文章里反复说的是同一件事：**先看你的关键字段，再看总分。**

## 八、限制与结论

这个模型的方向是清楚的：把"读完整页再映射字段"的两步压成一步，用 schema-directed 模式的严格输出换掉下游的清洗代码；用小参数基座加 LoRA 的路线，把成本从按 token 计费转到按 GPU 时间计费（参数量的三处口径并不一致，见第二节）。原文给的指标定义比多数发布稿具体，也自己写了成本限定的四条（含"通用侧压低推理"这一条）。

但可用性有一条硬约束：能拿到的是账号制服务（试用链接指向需注册的门户），拿不到的是权重；所以"自托管"目前是测算而非现状。

本文的限制：没有调用模型、没有复现任何分数；0.834 等数字全部来自厂商自测；成本换算里的"每小时 100 页"只是我举的量级，实际吞吐未知；博客的试用链接指向需注册的登录门户，我没有注册，因此门户内的价格、额度与条款未核验；权重与授权则确认不可得（HF 组织页只有 Dharma-OCR-LITE）。

下一步建议：先用他们提供的试用入口，拿你自己的 20 到 30 份文档试一遍，重点看你最在意的那几个字段的逐字段准确率（而不是总分）。验收怎么设计，见另一篇关于字段级自建评测的说明。
