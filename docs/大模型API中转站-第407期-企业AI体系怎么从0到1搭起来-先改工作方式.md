# 企业 AI 体系怎么从 0 到 1 搭起来：先改工作方式

很多企业谈 AI，第一反应是购买模型、开通几个工具、给员工安排一次培训，然后等待效率自然提升。几个月以后，常见结果是：员工偶尔用 AI 写总结，几个部门各自做了一个 Demo，真正进入日常流程的项目却很少。

问题通常不是模型不够强，而是落地顺序反了。企业真正要建设的不是一个更大的聊天框，而是一条可以被使用、检查、修改和持续运行的工作流。业务场景提出问题，企业知识提供依据，模型负责理解和生成，工作流负责推进，员工负责判断和承担结果，治理机制负责规定边界。

本文不比较具体产品，而是给出一套从 0 到 1 选择场景、建设试点和检查价值的方法。读完以后，你应该能回答：第一个 AI 项目选什么，哪些事情先不要做，以及怎样证明它不是一次演示。

## 1. 先理解 AI 体系的五个层面

一套能进入企业日常工作的 AI 体系，至少包含下面五层。它们不是五个孤立的软件模块，而是一条从问题到结果的责任链。

### 第一层：业务场景

AI 到底要解决什么问题？谁在什么时候使用？输入是什么，输出是什么，最终由谁判断？

例如：

```text
市场团队：汇总行业信息并生成带来源的周报。
内容团队：把资料整理成不同平台的初稿。
销售团队：根据客户资料生成跟进建议。
客服团队：检索有效政策并起草回复。
产品团队：去重、分类和归纳用户反馈。
管理层：把分散数据整理成经营分析材料。
```

场景层决定项目是否有真实用户和明确边界。无法说明谁用、何时用和怎样判断结果的项目，很容易变成展示页面。

### 第二层：模型与工具

这一层包括通用模型、专业模型、搜索工具、文档工具、自动化平台和企业内部系统。模型负责理解、抽取、分类和生成，但它不会自动知道公司的规则、资料版本和责任边界。

如果调用链通过 4SAPI 这类可替换入口接入模型，建议把入口、实际模型标识、配置版本和调用日志放在配置与观测层，不要让业务流程依赖某个固定模型名称；具体可用模型和参数仍需按当前项目配置逐项核验。

### 第三层：企业知识

产品资料、服务标准、销售话术、合同模板、品牌规范、历史项目经验和部门流程，往往散落在文档、聊天记录、会议纪要和员工经验中。

这些资料没有治理之前，直接接入模型只会把混乱放大。知识需要有负责人、版本、生效时间、适用范围和权限，才能成为可引用的业务依据。

### 第四层：提示词、技能与 Agent

提示词解决一次任务怎么做，技能解决一类任务按照什么标准反复做，Agent 负责在多个技能和工具之间推进复杂任务。

让 AI 写一篇文章是一次对话；把资料核对、受众判断、结构生成、事实检查、语气修改和平台适配固定下来，才是一项可以复用的技能。多个技能再按条件连接起来，才形成 Agent 工作流。

### 第五层：工作流与治理

工作流决定 AI 什么时候被触发、调用哪些系统、结果写回哪里、何时交给人。治理决定什么数据可以进入模型，哪些结果必须人工确认，谁对最终结果负责，如何记录错误和回滚。

没有工作流，AI 只是员工需要主动打开的工具；没有治理，AI 越深入业务，错误越难追踪。

## 2. 不要先买工具，先做场景盘点

第一步不是让每个部门提交“想要一个什么 AI”，而是让他们记录正在发生的工作。场景盘点至少要包含这些字段：

| 字段 | 要记录什么 | 为什么重要 |
| --- | --- | --- |
| 场景名称 | 任务的具体名称 | 避免写成“全面智能化” |
| 使用者 | 哪个岗位、多少人使用 | 判断是否有真实用户 |
| 触发条件 | 什么时候开始 | 判断能否接入流程 |
| 输入 | 文件、字段、对话或系统数据 | 判断数据是否可取得 |
| 输出 | 回复、报告、分类、建议或动作 | 判断结果如何验收 |
| 当前耗时 | 单次和每周大致时间 | 建立基线 |
| 当前痛点 | 重复、等待、遗漏还是经验依赖 | 选择自动化方向 |
| 风险 | 数据、权限、金额、对外承诺 | 确定人工介入点 |
| 负责人 | 谁维护规则和接受结果 | 避免项目无人负责 |

场景描述越接近真实动作，越容易判断是否适合 AI。相比“做一个销售 Agent”，“每天把会议记录整理成客户跟进事项，并由销售确认后写回 CRM”就是更可执行的任务。

## 3. 用四个条件筛选第一个试点

第一批项目不应该追求影响面最大，而应该追求能在较短周期内得到真实反馈。优先考虑下面四类任务：

```text
高频发生：每周或每天重复出现。
重复性强：步骤相似，输入和输出结构相对稳定。
标准较清楚：有样例、规则或专家可以解释什么是合格结果。
容易复核：出错后能及时发现并由人修正。
```

比较适合作为试点的任务包括会议纪要整理、用户反馈归类、周报初稿、公开资料汇总和客服回复草稿。

合同审批、财务付款、医疗诊断、重大人事决策和没有回退路径的外部动作，不适合直接作为第一个全自动项目。它们可以从辅助分析或草稿开始，但不能因为模型能生成内容，就默认它能承担最终责任。

可以使用一个内部排序公式：

```text
场景优先级 = 业务价值 × 使用频率 × 标准化程度 ÷ 实施难度
```

这不是行业通用指标，而是一种帮助团队对话的工具。每个维度都要说明依据，不能用主观分数包装一个已经决定的项目。

## 4. 先选一个小而真的试点

一个合格的试点通常有三个条件：员工原来确实在做，使用前后的变化可以记录，第一版不需要打通整个公司。

以产品团队整理用户反馈为例，原流程可能是：

```text
收集反馈 -> 人工去重 -> 分类 -> 判断严重程度
-> 提取高频需求 -> 整理周报 -> 产品经理决定后续动作
```

第一版可以改成：

```text
系统汇总反馈
  -> AI 清洗和去重
  -> AI 按功能、问题类型和情绪分类
  -> AI 提取高频问题和典型原话
  -> 生成周报初稿
  -> 产品经理审核并决定行动
```

这里 AI 替代的是整理工作，不是产品经理的判断。试点开始前要记录每周反馈数量、人工处理时间、分类修改情况、重要问题遗漏和周报完成周期。没有基线，试点结束后的“感觉变快了”不能证明业务价值。

## 5. 知识库先做小，不要一开始追求大而全

知识库建设最容易犯的错误，是把公司所有文件一次性上传，然后期待模型自己区分新旧版本和部门权限。

在试点范围内，先整理一组有限且明确的资料，并给每份资料补齐：

```text
文件名称和来源
所属部门与内容负责人
发布时间和当前版本
生效、失效时间
适用产品或业务范围
保密级别与访问权限
关键词和可检索标题
更新频率与复核方式
```

如果同一规则有多个版本，先确定哪个版本有效，再接入检索。资料互相矛盾、没有日期或找不到负责人时，正确的动作是标记待治理，而不是让模型自行选择一份。

## 6. 让 AI 进入工作流，而不是停在聊天窗口

单个技能只提高一个环节的效率，完整工作流才能改变业务流程。一个内容团队的工作流可以是：

```text
选题 -> 资料搜集 -> 来源核对 -> 文章初稿
-> 事实和敏感词检查 -> 人工审核 -> 视觉制作
-> 多平台改写 -> 发布 -> 数据复盘
```

每个节点都要定义输入、输出和失败处理。低风险、重复性工作可以自动推进；对外发布的内容需要人工审核；涉及金额、合同、承诺和敏感信息，必须由负责人确认；重大决策只能让 AI 提供分析材料，不能让它替代责任人。

工作流设计也要把确定性代码和模型判断分开。日期校验、金额计算、权限检查、状态机和幂等控制，应尽量由普通代码负责；模型更适合处理非结构化文本、分类、摘要和带依据的候选解释。

## 7. 建立一支小型推进团队

AI 体系不能完全交给技术部门，也不能只交给一个热心员工。资源有限时一个人可以承担多个角色，但以下职责不能缺失：

| 角色 | 主要责任 |
| --- | --- |
| 业务负责人 | 提出真实问题，判断结果是否可用 |
| AI 产品负责人 | 梳理需求、流程、优先级和验收 |
| 技术负责人 | 模型接入、系统连接、权限、部署和恢复 |
| 知识负责人 | 整理资料、维护版本和处理冲突 |
| 安全与合规负责人 | 数据边界、敏感信息和审计要求 |
| 一线使用者 | 实际使用、反馈问题和参与评估 |

一线员工应该从设计阶段就参与。如果他们只在最后被要求“试用一下”，很多流程阻力会等到上线后才暴露。

## 8. 一套从 0 到 1 的执行路线

### 第 1—2 周：业务盘点

访谈部门，建立场景清单，选出一到三个候选任务，记录现有耗时、质量和风险。

### 第 3—4 周：流程与资料整理

画出输入、判断、输出和人工节点，整理小型知识库，删除过期版本，确定数据权限和负责人。

### 第 5—6 周：最小可用版本

先使用已有模型、文档工具、表格和自动化能力跑通一条流程，不急着开发全公司平台。保存输入、输出、人工动作和失败原因。

### 第 7—8 周：小范围使用

让真实用户处理真实但风险可控的任务，记录耗时、修改、拒绝、错误和回到旧流程的原因。

### 第 9—10 周：标准化

把有效方法整理成技能、操作说明、知识维护规则和审核清单，修复最常见的失败路径。

### 第 11—12 周：评估与决定

对比试点前后的效率、质量、采用情况和维护成本。有效的场景继续扩展，没有价值或无法治理的场景及时暂停。

## 9. 可复制的 AI 场景盘点 Prompt

```text
请不要先推荐模型或工具，先帮我盘点部门中适合 AI 改造的真实工作。

对每个候选场景输出：
1. 使用岗位和触发条件；
2. 当前输入、步骤、输出和负责人；
3. 单次耗时、每周频率和当前返工点；
4. 哪些步骤是确定性规则，哪些步骤依赖经验或语言理解；
5. 需要访问哪些系统和资料，资料是否有版本、负责人和权限；
6. 出错后能否被人工发现和修正；
7. 是否会产生金额、合同、客户承诺或其他外部副作用；
8. 第一版可以只做什么，明确不做什么；
9. 如何记录试点前基线和试点后的变化；
10. 按业务价值、频率、标准化程度和实施难度给出排序理由。

不要把“做一个全能 Agent”当成场景，也不要把模型输出直接等同于业务结果。
```

## 10. 常见误区

### 把买工具当成 AI 转型

工具只是基础设施。员工是否愿意使用，流程是否减少重复工作，结果是否能被验证，才决定项目有没有价值。

### 一开始就建设大平台

全公司知识库、统一 Agent 平台和自动化中心都可能有长期价值，但不适合作为没有试点证据时的第一步。

### 只做培训，不改流程

员工会写提示词，不代表 AI 已经进入业务。真正的落地需要触发条件、输入、输出、审核、记录和回退路径。

### 只看生成效果，不看业务结果

文章写得顺不等于内容有效，报告看起来完整不等于决策变好了。必须回到耗时、修改、错误、采用和业务结果。

## 11. 结论与限制

从 0 到 1 搭建企业 AI 体系，顺序比工具清单更重要：先找到真实问题，再选择小试点；先整理企业知识，再固定任务方法；先跑通一条工作流，再扩展平台和自动化；先证明业务价值，再增加复杂度。

这套方法适合企业早期探索和 FDE 推进。涉及财务、法律、医疗、重大人事和自动外部动作时，需要更严格的权限、审计、人工确认和回滚设计。具体模型、工具和接入方式都应依据当前配置与真实验收结果决定，不能用工具数量替代工作方式的改变。
