# 审一个技能包：从六个字段到脚本的七条设计准则

你在别人仓库里点开一个技能文件夹，看到 `SKILL.md`、一个 `scripts/`、若干 markdown。装不装？

大部分人的判断依据是 README 写得好不好看。但技能不是文档，它会在你的环境里被执行：读文件、跑脚本、调工具。所以审它的顺序应该反过来——先看它会做什么，再看它说得好不好。

下面是按规范条款整理的一份审查顺序。条款来自 agentskills.io 的规范页与创作者文档（检索日期 2026-11-06），我没有实际跑过任何一个第三方技能。

## 一、先看两个必填字段

frontmatter 有六个字段，只有两个必填。这两个恰好也是最该先查的。

| 字段 | 约束 | 审查要点 |
| --- | --- | --- |
| `name` | ≤64 字符，仅小写字母、数字、连字符；不能以连字符开头结尾；不能有连续连字符；**必须与父目录名一致** | 不一致的包，说明作者没按规范做，后面几项大概率也松散 |
| `description` | ≤1024 字符，非空，要写清"做什么"和"何时用" | 只写"处理数据"这类，等于这个技能永远不会被正确触发 |

`description` 值得单独说。规范给的差评示例是"Helps with PDFs."，好评示例写清了动作和触发场景：

> Extracts text and tables from PDF files, fills PDF forms, and merges multiple PDFs. Use when working with PDF documents or when the user mentions PDFs, forms, or document extraction.

这不是措辞偏好。`name` 和 `description` 是启动时唯一常驻的部分，客户端靠这段文字判断是否相关——原文的说法是要包含能帮 agent 识别相关任务的关键词。实现上大概率是语义匹配，这一步我没验证。所以审一个包时，我把它当接口看：**它声明了什么条件下该用，那个条件是否足够具体。**

## 二、再看许可，别默认开源

这一点很容易漏。以 anthropics/skills 这个官方示例仓库为例，README 写明部分技能是 Apache-2.0，但 docx、pdf、pptx、xlsx 四个是 "source-available, not open source"。

也就是说，一个技能文件夹能下载、能读、能改，不等于能商用、能再分发。frontmatter 里的 `license` 字段是可选的，缺失时按顺序找：仓库根目录的 LICENSE、技能目录里自带的 LICENSE，都没有再问作者。

我的做法是三步：看 `license` 字段 → 看仓库根目录的许可证 → 看这个技能目录里有没有独立的 LICENSE。三者不一致时，以最严格的那个为准。

## 三、正文长度：一次全载意味着成本

规范里有一句容易被跳过的话：智能体一旦决定激活技能，会**加载整个 SKILL.md**。

这句话把正文长度从"写作风格"变成了"运行成本"。一个 2000 行的 SKILL.md，每次激活都要进一次上下文。

规范给的对策是分层：正文只放流程，细节放 `references/`，代码放 `scripts/`，模板放 `assets/`，正文里用相对路径引用。

所以审查时数一下 `SKILL.md` 的行数，再看它有没有把长内容推到 `references/` 里。规范给的具体阈值是：正文建议 5000 token 以内，`SKILL.md` 控制在 500 行以内。**超过这个数的包，要么作者没分层，要么这个技能的职责太宽。**

官方建议的正文结构很简单：分步指令、输入输出示例、常见边界情况。看到正文里塞满背景科普，基本可以判断作者没考虑加载成本。

## 四、scripts 目录：七条准则，只有一条是硬要求

这是最该细看的地方。这些条款里只有一条被创作者文档（using-scripts 那一页）明确称为硬要求，其余是同页给出的设计准则，它们来自同一个前提：**智能体在非交互 shell 里运行。**

| # | 规则 | 不遵守会怎样 |
| --- | --- | --- |
| 1 | **硬要求**：不得有交互式提示（密码框、确认菜单、TTY 输入） | 永久挂起，任务卡死 |
| 2 | 建议提供 `--help`，写清参数与示例 | 智能体只能靠试错猜接口，浪费轮次 |
| 3 | 建议错误信息说明期望值与可选值 | "Error: invalid input" 让它下一轮还是错 |
| 4 | 建议结构化数据走 stdout，进度与警告走 stderr | 输出混在一起，解析失败 |
| 5 | 建议幂等（"不存在才创建"） | 重试时重复写入 |
| 6 | 建议使用有意义的退出码，并写进 `--help` | 无法区分"没找到"和"参数错" |
| 7 | 建议限制输出体积 | 很多 harness 在约 1 万到 3 万字符处截断，可能丢掉关键信息 |

第 7 条最容易被低估。创作者文档原文提到，不少 agent harness 会自动截断超过阈值（例如 1 万到 3 万字符）的工具输出。一个把全表打成 JSON 的脚本，看起来信息完整，实际到智能体手上可能只剩一部分——原文的说法是"可能丢失关键信息"，没说保留的是开头。

另外两条实践建议也值得看：破坏性操作提供 `--dry-run`；一次性命令锁定版本（如 `npx eslint@9.0.0`），或者把复杂命令移进 `scripts/`。

审包时，我会挑一个脚本读三处：参数怎么解析、错误怎么报、输出往哪写。三处都规矩，剩下的基本可以放心。

## 五、allowed-tools 不是权限边界

frontmatter 里有个 `allowed-tools` 字段，看起来像沙箱配置：空格分隔的预批准工具列表。

但规范自己标了 Experimental（实验性），并注明"支持程度因实现而异"。

这句话的实际含义是：**你不能拿它当安全边界用。** 一个客户端可能读它、可能忽略它、可能只认其中一部分语法。指望这个字段拦住危险操作，等于把安全托付给一个还没有实现的约定。

真正的边界在客户端和执行环境那一侧。审包时能做的是反向检查：这个技能声明要用的工具，跟它正文里实际让你跑的命令，是不是同一批。声明 `Read` 却在正文里让你执行 shell 的包，值得警惕。

## 六、评估：带与不带跑两遍

评估指南（evaluating-skills 那一页）给了一套完整方法，值得抄。核心不是"跑一下看看行不行"，而是**对照**。

- 测试用例存在技能目录的 `evals/evals.json`，每条含 `prompt`、`expected_output`，可选 `files`。
- 每条用例跑两遍：带技能存 `with_skill/`，不带技能存 `without_skill/`；改进旧版本时基线存 `old_skill/`。结果放在 `iteration-N/` 下，每个 run 有 `outputs/`、`timing.json`、`grading.json`。
- 记录 `timing.json`（tokens 与耗时），最后汇总成 `benchmark.json`，给出通过率与成本的 delta。

几个细节能看出这套方法的设计意图：

1. **断言在看到第一轮输出后再写。** 因为跑之前你不知道"好"长什么样。
2. **PASS 必须有具体证据。** 评估指南明确说不要给"benefit of the doubt"——输出里有个"Summary"标题但只有一句话，算 FAIL。
3. **断言本身也要审。** 永远通过的断言没有信息量，永远失败的断言可能是写错了。
4. **delta 要同时看两边。** 通过率涨 50 个点、耗时涨 13 秒，可能值得；token 翻倍换 2 个点，多半不值得。

这套东西的价值在于它把"这技能好不好用"变成了可比较的问题。审第三方技能时，如果作者没提供 evals 目录，可以借这套结构自己补两三条用例跑一遍。

## 七、一张可打印的审查表

把上面几节压成表，按顺序过：

| # | 检查项 | 不合格的信号 |
| --- | --- | --- |
| 1 | `name` 与目录名一致，格式合规 | 大写字母、连续连字符 |
| 2 | `description` 写清"做什么 + 何时用" | 只有"帮助处理 X" |
| 3 | 许可证明确，且不是 source-available 却被当开源用 | 只有 README 一句话 |
| 4 | 正文分层，长内容在 `references/` | 单个 SKILL.md 上千行 |
| 5 | 脚本非交互、有 `--help`、错误可读 | 出现 `input()`、`read`、确认菜单 |
| 6 | stdout 只放结构化数据 | 日志和 JSON 混在一起 |
| 7 | 输出有上限或支持分页 | 一次性打印全量 |
| 8 | `allowed-tools` 声明与实际命令一致 | 声明只读，正文却让执行 shell |
| 9 | 有 `evals/`，或你自己能补两条 | 只有"我试过，好用" |
| 10 | 有人维护（提交记录、issue 响应） | 一年没动、issue 无人回 |

第 3 行来自官方仓库 README，第 8、9 行是审查启发式，第 10 行是经验项；1 到 7 行对应规范与创作者文档。技能会随客户端升级失效，一个没人管的包，半年后可能连 frontmatter 都过不了校验。

## 八、自己写的时候，把顺序倒过来

审查是给别人挑毛病，写的时候同一份清单可以当验收标准，只是顺序不同：

1. 先定 `description`。它是触发条件，不是简介。
2. 再定边界——这个技能不做什么，写进正文比写进 README 有用。
3. 把能跑的东西写成脚本，别让智能体每次现场拼命令。
4. 正文只留流程，细节推给 `references/`。
5. 写两条 eval，带与不带各跑一遍，把差异记下来。
6. 断言先留着位置，等看到第一轮输出再填。

第 2 条是我自己的经验。技能最常见的失败不是做错，是做得太宽——一个"写作助手"技能，最后什么都管一点，什么都管不好。

第 6 条容易被忽略，但评估指南写得很清楚：第一次跑之前，你并不知道"好"是什么样，硬写出来的断言往往要么恒真、要么恒假。先把用例和期望结果写下来，跑一轮，再对照着补断言。

## 九、结论与边界

审一个技能包，实质是审三件事：**它声明了什么（字段）、它会做什么（脚本）、它值不值得（评估）。**

我的判断是：字段和脚本可以按规范逐条查，我的经验是十几分钟能过一遍；评估最难，因为它要求你先知道"好"是什么样。所以真正决定装不装的，往往是第三步——而这个公众号里的多数讨论恰好跳过了它。

限制：本文条款来自 agentskills.io 规范页与创作者文档，检索日期 2026-11-06；我没有实际安装或运行任何第三方技能，脚本规则的后果是创作者文档的描述加我的推断；`allowed-tools` 的具体支持情况未测；评估流程未实跑。

如果只做一件事：挑你已经在用的一个技能，打开它的 `evals/` 目录（如果存在），数一下有几条用例。零条的话，你对它"好用"的判断，目前没有证据。
