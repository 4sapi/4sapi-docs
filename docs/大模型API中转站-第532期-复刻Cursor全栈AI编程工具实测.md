# 复刻 Cursor 的难点在哪里：一次全栈 AI 编程工具生成实测

分类：软件开发

标签：AI 编程、全栈开发、代码生成

摘要：本文整理一次让大模型复刻 Cursor 类 AI 编程工具的实测，重点分析 Agent Window、Editor Window、文件树、终端、Git 和代码补全等功能如何验收，并解释为什么“界面像”不等于“工具完成”。

> 说明：本文基于提供的实测原文改写。文中关于模型名称、耗时、代码量和功能完成情况属于原始测试记录，正式发布前应补充源码、运行日志、测试环境和可核验版本信息。

## 这不是普通的页面仿制

复刻 Cursor 类工具，难点不在于画出一个相似的界面。

真正困难的是把多个工作流连接起来。

用户需要在编辑器里查看文件。

需要在终端里运行命令。

需要让 Agent 读取项目并修改代码。

还需要查看变更、接受或拒绝修改，并继续迭代。

如果页面只有输入框和几个按钮，它更像一个演示页面。

一个可用的 AI 编程工具必须形成闭环。

这个闭环可以概括为：选择项目、提出任务、调用工具、修改文件、运行验证、查看差异。

因此，这次任务适合测试模型的长程规划能力。

## 测试目标和约束

原始任务要求克隆 VS Code 的开源代码。

在此基础上，生成一个 Web 版 AI 编程工具。

工具需要包含两种主要窗口。

一种是 Editor Window。

另一种是 Agents Window。

两种窗口需要能够来回切换。

内置 AI 接口使用指定模型。

原记录还要求模型自行完成项目，而不是由人工逐个补功能。

这类约束很有价值。

如果只要求“做一个像 Cursor 的页面”，模型可以用静态数据完成视觉效果。

如果要求真实读取项目并执行任务，就必须实现更多底层能力。

## 验收清单应该包含什么

第一项是编辑器是否能打开文件。

第二项是代码高亮是否正常。

第三项是是否有基础代码补全。

第四项是 Agent 是否能接收任务。

第五项是 Agent 是否能读取工作区。

第六项是 Agent 是否能调用终端或文件工具。

第七项是修改是否能反映到编辑器。

第八项是用户是否能查看变更。

第九项是 Git 面板是否展示真实状态。

第十项是布局切换和侧边栏是否有效。

这些项目需要逐项验证。

不能因为首页看起来像，就默认所有功能都已经实现。

## Opus 5.5 的交付方式

据原始记录，Opus 5.5 用时约 53 分钟。

打开网站后，默认进入 Agents Window。

左侧显示按工作区分组的 Agent 列表。

中间区域提供任务输入框。

下方还有推荐任务。

这种布局和目标产品的 Agents Window 比较接近。

但视觉相似只是第一层验收。

接下来需要打开文件查看器、终端和 Agent 侧边栏。

原记录称这些区域都能够正常使用。

例如，在终端中运行 tree 命令后，可以看到项目结构。

再向 Agent 询问源码文件数量，Agent 会调用工具列出目录。

如果 Agent 返回的文件数量与终端结果一致，说明它至少读取了真实项目内容。

这比在页面上写死一个数字更有意义。

## Editor Window 应该怎样检查

切换到编辑器模式后，需要确认文件能否打开。

打开后，语法高亮应该与文件类型匹配。

修改代码时，编辑器内容应该真正变化。

如果有代码补全，补全内容应该来自当前语言和上下文。

不能把一组固定的提示词当作通用补全。

还要检查编辑器和 Agent 是否共享同一个工作区状态。

如果 Agent 修改了文件，编辑器是否立即反映？

如果用户在编辑器中手动保存，Agent 是否能读取最新内容？

如果两边各自维护一份假数据，工具就没有形成闭环。

## Git 面板为什么是关键功能

AI 编程工具经常会修改多个文件。

用户需要知道模型改了什么。

Git 面板至少应当展示修改文件列表。

更完整的实现还应提供差异查看。

如果支持提交记录，还要确认记录来自真实仓库。

仅仅显示“已修改 3 个文件”不够。

用户需要定位具体行，判断修改是否合理。

如果工具支持接受或拒绝单个改动，验收时要分别操作。

拒绝某个文件的修改后，实际文件是否恢复？

接受修改后，差异是否从列表中消失？

这些动作比静态截图更能说明功能是否完成。

## GPT-6 Sol 的实现路径

原始记录显示，GPT-6 Sol 用时约 27 分钟。

它的交付速度约为 Opus 5.5 的一半。

项目默认进入 Editor Window。

页面支持代码高亮和自动补全。

Agents 面板也提供了任务输入区域。

从页面结构看，它完成了基本工作台。

但原记录指出，部分按钮不可用。

项目不支持搜索、Git 和终端等能力。

这类结果很常见。

模型可能优先实现最容易展示的界面。

功能越依赖系统调用、文件状态和异步流程，实现成本越高。

因此，评测时要把“有入口”和“能完成动作”分开记录。

## 源码结构能说明什么

根据原始记录，GPT-6 Sol 没有真正使用克隆的 VS Code 源码。

它在旁边使用 Monaco Editor 和 React 重新拼出了一个工作台。

记录中称该项目源码只有 600 多行。

Opus 5.5 生成的代码则超过 3600 行。

代码量不能直接代表质量。

更大的代码库可能包含重复实现，也可能带来更多维护负担。

但在这个任务里，代码量差异提示了实现路径不同。

一个项目偏向功能性原型。

另一个项目更接近完整工作流。

验收时应继续检查实际依赖和调用链。

不能只用行数推断完成度。

## 如何识别“AI 味”的界面

原记录认为 GPT-6 Sol 的 Agent 界面有明显的模板感。

这种评价属于主观感受。

如果要把它写成可复核结论，需要拆成具体指标。

例如，任务状态是否清晰。

工具调用是否能追踪。

错误信息是否可定位。

等待状态是否区分“模型思考”和“工具执行”。

失败后是否提供下一步操作。

按钮名称是否对应实际动作。

这些指标比“看起来像 AI”更容易被不同测试者复核。

界面设计不是单纯的配色问题。

它还关系到用户能否理解系统正在做什么。

## 长程任务为什么容易失败

复刻 Cursor 需要同时管理多个目标。

模型要理解原产品的布局。

还要规划前端组件和状态管理。

还要处理文件系统、终端和模型调用。

任何一个环节使用假数据，都可能导致最终工具无法工作。

长程任务还需要在中途自检。

例如，完成编辑器后，模型应立即打开并测试文件切换。

完成 Agent 后，应让 Agent 读取一个真实项目。

完成 Git 面板后，应制造一次真实修改再查看差异。

如果模型直到最后才检查，很容易留下大量不可用按钮。

## 一个可复现的验收流程

先准备一个包含多个源码文件的示例项目。

项目至少应包含前端文件、配置文件和一个可运行脚本。

然后启动被测工具。

在 Editor Window 中打开任意源码文件。

确认高亮和文件切换。

再切换到 Agents Window。

要求 Agent 列出项目文件。

把 Agent 返回的列表与终端结果对照。

接着让 Agent 修改一个简单函数。

回到编辑器，确认代码发生变化。

打开差异面板，确认修改范围。

最后运行项目测试或启动命令。

如果测试失败，记录失败发生在哪一层。

这样可以区分界面问题、工具调用问题和代码问题。

## 测试记录应该保存什么

保存完整提示词。

保存模型和工具版本。

保存每次运行的开始和结束时间。

保存生成的源码快照。

保存终端输出和浏览器控制台日志。

保存关键操作的屏幕录像或截图。

保存人工干预的时间点和内容。

如果模型中途修改了提示词，也要单独记录。

没有这些材料，读者只能看到最终截图。

最终截图无法证明中间过程是如何完成的。

## 速度、功能和维护成本

GPT-6 Sol 的交付时间更短。

这对快速原型有吸引力。

但如果缺少终端、搜索和 Git，后续人工补功能可能需要更多时间。

Opus 5.5 用时更长。

如果它确实完成了更多真实工作流，额外等待可能换来更少返工。

这是一种项目层面的取舍。

不能只比较模型首次交付时间。

还应计算从初版到可用版本的总时间。

总时间包括模型运行时间、人工排错时间和重新生成时间。

在真实开发中，后两项经常比首轮生成更昂贵。

## 结论

复刻 Cursor 类工具，核心不是做出相似页面。

核心是把编辑器、Agent、文件系统、终端和版本控制连接成一个可验证的工作流。

从提供的实测记录看，Opus 5.5 的项目完成度更高，但耗时更长。

GPT-6 Sol 更快，更像一个功能较少的工作台原型。

这个结论只适用于给定提示词、工具和测试环境。

如果你要评估自己的模型，建议先做一套十分钟内可以完成的最小验收。

确认文件读取、修改、差异查看和运行验证都有效后，再扩大任务范围。

这样得到的结果，比单独比较截图或代码行数更可靠。
