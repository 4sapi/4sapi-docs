# 企业知识如何变成 AI 技能：从个人经验到工作流

很多企业做知识库时，第一步是把文件集中上传；做 AI 助手时，第一步是写一段很长的提示词。两种做法都可能很快得到一个能回答问题的 Demo，却很难让结果稳定复用。

原因在于，文件不等于知识，提示词也不等于能力。真正有价值的企业知识，应该能够被找到、判断版本、确认权限，并在具体任务中转化为稳定的执行方法。一个优秀员工脑中的经验，也不应该只被复制成几句口号，而要拆成输入、步骤、判断标准、异常处理和输出格式。

本文解决一个具体问题：如何把散落的企业资料和个人经验，整理成可以被 Agent 重复调用、人工检查和持续更新的 AI 技能，并把多个技能连接成一条工作流。

## 1. 先区分文件、知识、技能和 Agent

这四个概念经常被混在一起，但它们解决的问题不同。

### 文件

文件是原始载体，可能是产品文档、合同模板、会议纪要、聊天记录或表格。文件可以保存信息，但不一定适合直接检索和执行。

### 知识

知识是经过整理、标注和确认的内容。它应该知道来源、版本、生效时间、适用范围和负责人。

### 技能

技能是一类任务的执行方法。它不仅告诉 AI“输出什么”，还规定输入如何准备、步骤如何进行、结果怎样检查、失败时交给谁。

### Agent

Agent 是能够在多个技能、工具和状态之间推进任务的执行者。它可以先检索资料，再调用分类技能，接着生成草稿，最后等待人工确认。

可以用一句话区分：

```text
文件保存材料，知识提供依据，技能规定方法，Agent 推进流程。
```

## 2. 知识库不是文件仓库

企业资料常见的问题包括：同一制度有多个版本，文件没有生效日期，部门说法互相冲突，重要经验只存在聊天记录中，访问权限没有和业务角色对应。

因此，知识治理要先于知识检索。对每份核心资料，建议至少补齐：

```text
名称与来源
所属部门与内容负责人
创建时间与当前版本
生效时间、失效时间和复核周期
适用产品、地区、客户类型或流程
保密级别和访问角色
关键词、摘要和相关术语
替代文件与冲突说明
```

如果一份退款政策已经过期，系统应该把它标记为不可用于当前决策，而不是因为它包含关键词就继续召回。资料找不到负责人时，应该进入待治理清单，而不是自动成为企业知识。

## 3. 从一个业务场景开始治理资料

知识库不适合一开始就追求“大而全”。正确的切入方式是先选一个试点场景，再反向列出这个场景需要哪些资料。

例如建设客服回复助手，第一批资料可以是：

```text
当前有效的产品说明
常见问题与标准处理流程
退款、换货和升级规则
不同客户类型的服务边界
需要转人工的异常条件
已经确认过的高质量回复样例
```

然后逐份检查：它是否能支持一次具体判断，是否能被用户访问，是否有版本和有效期，是否需要在回答中引用来源。与其导入几千份无法解释的文档，不如先治理几十份真的会被用到的资料。

### 知识单元要能独立理解

一段适合检索的知识单元，不应该只有“按规定处理”这种缺乏上下文的句子。它至少要包含：

```text
适用对象：什么产品、客户或场景
规则内容：允许做什么、不允许做什么
前置条件：需要先确认哪些事实
生效范围：从何时起、由谁维护
例外情况：哪些情况必须升级人工
来源信息：来自哪份文档的哪个版本
```

这样 Agent 返回答案时，才有机会同时给出结论、条件和依据。

## 4. 把优秀员工的经验拆成技能

经验沉淀不是让专家写一篇“工作心得”，而是让他把一次任务完整演示出来，再把判断动作拆开。

假设要把产品经理整理用户反馈的方法变成技能，可以先记录：

```text
输入：反馈原文、来源、产品版本、时间和用户类型。
第一步：删除无意义的寒暄，保留原始事实和上下文。
第二步：合并描述同一问题的反馈，但保留代表性原话。
第三步：按功能、问题类型和影响范围分类。
第四步：区分事实、用户推测和产品团队判断。
第五步：统计频次，同时标记高风险但低频的问题。
第六步：输出问题摘要、证据、待确认信息和建议动作。
审核：产品经理确认分类、优先级和原话是否被误解。
```

这里的关键不是步骤数量，而是把“为什么这样判断”写出来。模型可以根据规则生成候选结果，但无法替团队自动决定哪些业务目标最重要。

## 5. 一份可复用的 AI 技能规格

一个技能至少需要下面八部分：

| 部分 | 要写清什么 |
| --- | --- |
| 名称 | 技能解决哪一类任务 |
| 适用范围 | 什么情况可以调用，什么情况不能调用 |
| 输入契约 | 必填字段、格式、来源和权限 |
| 执行步骤 | 检索、判断、生成、校验的顺序 |
| 工具 | 可以调用哪些查询、计算和写入能力 |
| 输出契约 | 字段、格式、来源和缺失值处理 |
| 质量检查 | 哪些条件必须通过，哪些情况转人工 |
| 版本记录 | 规则、资料、提示词和代码何时变化 |

### 技能模板

```markdown
# 用户反馈归类技能

## 目标
将一批脱敏用户反馈归并为可供产品评审的结构化摘要。

## 必须输入
- feedback_id
- 原始反馈
- 来源渠道
- 产品版本
- 用户类型

## 不负责
- 不判断商业优先级
- 不修改线上产品状态
- 不删除原始反馈

## 执行步骤
1. 校验输入字段和权限。
2. 保留原始事实，标记推测性内容。
3. 查找当前产品术语和版本资料。
4. 生成分类、摘要、代表性原话和缺失信息。
5. 检查重复、冲突和无法判断的项目。

## 输出
返回结构化 JSON，并附每项来源 feedback_id。

## 人工确认
产品经理确认分类、优先级和代表性原话。

## 失败处理
输入不完整、版本未知或资料冲突时，停止自动归类并输出待确认清单。
```

如果需要校验结构，可以使用 JSON Schema 这类明确的输出约束；[JSON Schema 官方入门文档](https://json-schema.org/learn/getting-started-step-by-step)可用于核对字段、类型和必填条件。结构校验不能证明内容正确，但能先阻止字段缺失和格式错误进入下游。

## 6. 提示词、技能和 Agent 的边界

### 只有提示词

适合一次性任务和探索。它通常依赖当前对话上下文，版本、输入和验收方式容易丢失。

### 固定技能

适合重复任务。技能把输入、步骤、输出和检查标准写下来，用户可以重复调用，团队也能讨论版本变化。

### Agent 工作流

适合需要多个工具和条件分支的任务。例如处理一条售后工单：

```text
读取工单 -> 查询订单 -> 检索当前政策 -> 生成建议
-> 判断是否需要人工 -> 等待确认 -> 写回结果
```

这里不是每一步都要交给模型。订单查询、权限检查、状态流转和写回操作应由确定性代码控制；模型负责理解非结构化描述、生成候选建议和说明依据。

## 7. 从技能连接成工作流

工作流要先画出状态和责任，再决定使用哪些工具。以内容团队为例：

```text
选题技能：根据目标受众和内容目标提出候选主题。
资料技能：收集资料，记录来源和版本。
写作技能：按平台规范生成初稿。
事实检查技能：标出无法核实的数字和结论。
审核流程：负责人确认内容后，才允许发布或改写。
复盘技能：整理阅读、修改和拒绝原因。
```

每个节点都应该有明确输入和输出。上一步失败时，是重试、换路径、转人工还是停止？如果没有定义，Agent 只会继续猜测。

### 人工确认点怎么放

```text
低风险的资料整理：可以自动执行。
对外发布的正文：必须人工确认。
金额、合同、客户承诺：由明确负责人确认。
权限、删除和外部写入：按风险配置审批。
重大决策：AI 只提供分析，不替代责任人。
```

人工审核不是把“同意”按钮放到最后，而是要让人看见输入依据、模型建议、缺失信息和可能风险。

## 8. 版本管理比“记住一切”更重要

技能结果发生变化时，至少要能查到：

```text
技能版本
规则版本
知识文档版本
提示词版本
模型配置版本
输入数据的来源和时间
人工修改与最终采用结果
```

如果调用链通过 4SAPI 这类兼容入口接入不同模型，建议把实际模型标识和配置版本写入每次技能执行记录；入口名称只能说明调用路径，不能替代输出快照和人工确认记录。

版本记录的价值不是为了保存所有历史，而是为了回答：这次结果为什么和上次不同，变化来自资料、规则、提示词、模型还是人工修改。

## 9. 一份可复制的知识与技能审计 Prompt

```text
请先不要修改项目，帮我把一个真实业务流程整理成可复用 AI 技能。

调查顺序：
1. 找到这个流程使用的文档、表格、系统字段和人工输入。
2. 标记每份资料的来源、负责人、版本、生效时间、权限和冲突。
3. 请一位熟悉流程的员工逐步描述一次正常任务和一次异常任务。
4. 区分确定性规则、需要检索的事实、需要模型理解的内容和必须人工判断的内容。
5. 输出技能规格：适用范围、输入契约、步骤、工具、输出契约、质量检查和失败处理。
6. 为每个输出字段提供来源或证据要求。
7. 设计至少三个正常样例、三个边界样例和三个失败样例。
8. 指出哪些步骤可以自动执行，哪些步骤必须等待人工确认。
9. 给出版本字段和发布前验收清单。

不要把缺少来源的经验写成确定事实，不要把模型生成的摘要当成原始证据，也不要在没有人工确认的情况下连接外部写入动作。
```

## 10. 如何验收一项技能

一项技能至少要通过四类测试：

```text
输入测试：缺字段、错格式、过期版本和越权数据会怎样？
内容测试：正常任务的结果是否完整，来源是否可追溯？
边界测试：资料冲突、信息不足和用户要求超出范围时是否停止或转人工？
回归测试：技能、知识、提示词或模型版本变化后，关键样例是否仍符合预期？
```

验收不要只看一段示例输出。要检查原始资料是否被保留，输出字段是否稳定，无法判断的内容是否明确标记，人工是否能修改和拒绝，以及失败后能否回到原流程。

## 11. 常见错误

### 把所有文件都塞进知识库

文件越多不等于知识越可靠。过期版本、重复文档和权限混乱会增加错误依据，应先治理核心资料。

### 只保存一段很长的系统提示词

提示词隐藏了输入条件、工具边界和失败处理，换个人就无法维护。技能需要独立的规格和验收样例。

### 把专家结论当成固定规则

专家有时是在信息不足时做经验判断。技能要标出适用条件和不确定性，不能把一次判断包装成所有场景都适用的规则。

### 让模型负责状态流转

模型可以建议下一步，但任务是否完成、是否进入人工、是否允许写回，应由明确的业务状态和代码控制。

### 没有失败样例

只用正常案例训练出来的技能，遇到资料冲突和越权请求时最容易产生危险的自信答案。失败样例是技能边界的一部分。

## 12. 结论与限制

企业知识沉淀的终点不是拥有一个更大的文件库，而是让正确资料能够在正确任务中被找到、解释和复用。优秀员工的经验也不应停留在口头传承，而要被拆成输入、步骤、判断标准、输出契约和异常处理。

提示词适合探索，技能适合重复，Agent 适合推进多步骤流程。真正上线前，必须保留来源、版本、权限和人工确认，并用正常、边界和失败样例持续回归。

这套方法不能自动解决资料质量、组织协作和责任划分问题。知识负责人、业务负责人和技术负责人仍然需要共同维护边界；当资料冲突、权限不清或风险超过审核能力时，停止自动执行往往比生成一个完整答案更可靠。
