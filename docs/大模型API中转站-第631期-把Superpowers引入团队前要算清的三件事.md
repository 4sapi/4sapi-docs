# 把 Superpowers 引入团队前要算清的三件事：安装、成本与验证

一个三十万星的开源方法论，最容易的失败方式是"装上了，就以为团队有了流程"。实际上装完只是把它放进了你的 harness，能不能按流程走取决于三件事：装在哪个入口、每次任务花掉多少调用、以及你怎么知道它真的在按流程走而不是看起来很听话。

本文按这三件事组织，并给一个增量引入的顺序。信息来自仓库 README 与相关技能文件，检索日期为 2026-11-02。我没有安装或运行过它。

## 一、第一件：装在哪

README 列了十六个 harness 的安装方式。这不是炫技，而是它的实际形态：技能本身是 Markdown，需要由各家的插件机制加载。

| harness | 安装方式（摘要） |
| --- | --- |
| Claude Code | `/plugin install superpowers@claude-plugins-official`，或先注册项目方的独立 marketplace 仓库再装 |
| Antigravity | `agy plugin install https://github.com/obra/superpowers`，重装即更新 |
| Codex App | 侧栏 Plugins 里在 Coding 分类下点 `+` |
| Codex CLI | `/plugins` 搜索后安装 |
| Cursor | `/add-plugin superpowers` |
| Devin CLI | `devin plugins install obra/superpowers` |
| Factory Droid | 注册 marketplace 后安装 |
| Gemini CLI | `gemini extensions install https://github.com/obra/superpowers` |
| GitHub Copilot CLI | 注册 marketplace 后安装 |
| Grok Build CLI | `grok plugin install superpowers@xai-official --trust` |
| Kimi Code | 插件市场的 Marketplace 里安装，或从仓库直接装 |
| OpenCode | 让它按仓库里的 `.opencode/INSTALL.md` 执行安装 |
| Pi | `pi install git:github.com/obra/superpowers` |
| Qwen Code | `qwen extensions install obra/superpowers` |
| Hermes Agent | `hermes plugins install obra/superpowers --enable` |
| Muse | 本地检出后 `muse plugins install ./`，再 `muse plugins approve superpowers` |

两条容易踩的：

1. **用多个 harness 就要分别装。** README 明确写了这一点。团队里既有用 Claude Code 的、又有用 Codex 的，就装两遍。
2. **部分平台的安装需要额外确认。** 例如 Muse 要 `plugins approve`，Grok 的命令带 `--trust`。这类确认在自动化部署里容易漏。

### 平台能力差异会改变方法论

这是引入前最该查的一件事。README 自己给了两个例子：

- **Hermes** 没有压缩后钩子，所以很长会话在首轮之后发生压缩会丢掉引导；症状是技能突然不再触发，官方建议是开新会话。
- **Pi** 有原生技能，不需要兼容用的工具；但**子代理与任务清单工具是可选的伴随包**。也就是说，在 Pi 上如果没装那些包，子代理驱动开发这条路径走不通，要退回 executing-plans 或手工执行。

第二点很关键：方法论里第四条有两种执行方式，能不能用"每个任务一个全新子代理"，取决于平台装了什么。引入时不能假设所有同事的配置一样。

## 二、装完怎么确认它真的生效

README 在 Muse 一节给了一个很具体的验收动作：开一个新会话，输入一句"做个 react todo 列表"，如果安装成功，它会在写任何代码之前自动触发 brainstorming。（这一条写在 Muse 小节里，其他平台可以借用同一手法，但属于我的一搬。）

这一步值得做成团队的检查项，因为触发失败时的表现很隐蔽：agent 看起来在正常工作，只是没走流程。

三个常见失效原因：

| 症状 | 可能原因 |
| --- | --- |
| 技能完全不触发 | 装错了 harness；或装完没重启会话（README 要求 Hermes 与 Muse 装后重启） |
| 一开始触发，长会话后不触发 | 平台缺少压缩后钩子（如 Hermes） |
| 技能能手动用，但不会自动进入流程 | 引导钩子未批准（Muse 类平台要求先 approve；未批准时技能本身仍然生效） |
| 子代理那一步走不动 | 平台未安装子代理伴随包（如 Pi） |

第二行的诊断要花点时间：你看到的现象是"它忽然不守流程了"，而实际原因是引导在压缩时被丢了。知道这一点，处置办法是开新会话，而不是怀疑模型。

## 三、第二件：成本

这套方法论的成本结构与多数"加提示词"的方案不同，因为它会主动增加调用次数。

### 两种执行模式的成本

| 模式 | 做法 | 成本口径 |
| --- | --- | --- |
| 子代理驱动 | 每个任务一个新实现子代理；任务后评审（规格符合性 + 代码质量）；最后整分支评审 | 每任务一个上下文，每次评审一个上下文 |
| 内联执行 | 一个上下文做完所有任务；最后只做一次整分支评审 | 一个上下文加一个最终评审者 |

按这个口径折算：十个任务在子代理模式下是 10 个实现 + 10 个任务评审 + 1 次整分支评审 = 约 21 个上下文（技能里还有最多三轮 fix loop，实际可能更高）；内联模式是 1 个上下文加 1 个最终评审 = 2 个。技能文档自己也承认这个差别是"每任务每评审各占一个全新上下文"。

### 派发的字符量

同一份技能里还有一条实测感受：一次派发曾经达到 4.2 万字符，其中 99% 是粘贴的历史。它给出的规则是：全新子代理只需要它的任务、它涉及的接口和全局约束，别的都不要。

这条对成本的影响往往比模型选择更大。很多人第一次用子代理模式时会把手上的对话历史整段塞进任务描述，结果每个子代理都在读无关内容。按这条规则的写法，派发应该很短。

### 所以怎么定

| 情形 | 倾向 |
| --- | --- |
| 改动跨多个模块、错一步代价高 | 子代理驱动，接受调用数增加 |
| 改动集中在一个小范围、你自己盯着 | 内联执行，最后统一评审 |
| 任务数很多但每项很小 | 内联；子代理的固定开销会把收益吃掉 |
| 需要并行推进多条线 | 参考 dispatching-parallel-agents，但要先算清并发数 |

## 四、第三件：验证

"它看起来在按流程走"和"它确实走了"是两件事。可用的验证手段有三层。

### 层一：行为验收

就是第二节那个动作：新会话里给一句构建类请求，看它是否先问需求。这一层最快，覆盖"装没装上"。

### 层二：审计判据

方法论本身给了几条可核对的标准，可以直接拿来做抽查：

| 判据 | 怎么查 |
| --- | --- |
| 计划是否有固定头部 | 看计划文件开头有没有那段含 REQUIRED SUB-SKILL 的头部 |
| 全局约束是否抄自规格 | 对照规格文件逐条比，看计划里是否原样带过来 |
| 是否先写测试 | 看提交历史里测试文件与实现文件的先后 |
| 完成声明是否有证据 | 看它给结论时有没有贴测试命令输出 |
| 计划存在约定位置 | 默认是 `docs/superpowers/plans/YYYY-MM-DD-<feature>.md`（用户偏好可覆盖） |

第三行需要一点技巧：如果一次提交里同时有测试和实现，就无法证明顺序。所以要么约定测试单独提交，要么接受这条查不了。

### 层三：项目自带的自诊断

有一个专门的技能叫 diagnosing-superpowers：当某个会话行为异常（技能该触发没触发、agent 无视计划、重复劳动、token 消耗超出预期），可以让它读会话记录，逐行给证据；它还能打包一份脱敏后的材料用于报缺陷。

这一项的价值在于把"感觉不对"变成"定位到第几行"。它同时说明项目把自身故障也当作可诊断对象。

### 还有一个上游手段

README 提到技能行为测试用的是外部的 drill eval 框架，克隆到 `evals/` 目录；插件基础设施的测试在 `tests/` 下，用相应的脚本跑。如果你要自己改技能，这是现成的回归手段。对普通使用者，知道有这层就够。

## 五、增量引入的顺序

一次性全开的问题是你无法判断哪一条带来了收益。按约束强度从不痛到痛排：

1. **先只用完成前验证。** 要求"声称完成必须带测试输出"。这一条不改变工作方式，只改变汇报方式，阻力最小。
2. **再引入计划技能。** 让改动先出计划，哪怕只有半页。观察任务切分是否落在"评审者能分别接受"的位置。
3. **然后引入 TDD 技能。** 这一条最痛，因为它要求删掉先写的代码。建议先在一个新模块上试，不要在遗留代码上开。
4. **最后才开子代理驱动。** 成本最高，且依赖平台支持；先用内联模式跑顺，再考虑换。
5. **全程保留 diagnosing 这条退路。** 出现"不守流程"时先诊断，不要先改提示词。

## 六、与既有流程的冲突点

| 冲突 | 说明 |
| --- | --- |
| 评审门 | 方法论要求任务之间评审、严重问题阻塞进度；团队的评审节奏如果是每周一次，就会卡住 |
| 提交粒度 | 每个任务一次提交，与"一个功能一次提交"的习惯不同 |
| 计划文件位置 | 默认在仓库里的 `docs/superpowers/plans/`，需要决定是否纳入版本控制 |
| 工作区隔离 | 使用 git worktree，团队若有强制的分支命名或目录结构，要提前对齐 |
| 平台差异 | 同事用不同 harness 时，实际可用能力不同（见第一节） |

第二行和第四行最容易和现有规范打架，引入前先说清楚，比事后解释便宜。

## 七、合规与默认行为

README 最后一节说明了遥测：brainstorming 的可视化伴侣里，一个 logo 默认从维护方网站加载，请求带当前版本号，不含项目、提示或 agent 的信息；可用 `SUPERPOWERS_DISABLE_TELEMETRY` 关闭，也遵从 Claude Code 的 `DISABLE_TELEMETRY` 与 `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC`。

对个人使用无所谓，对有出网白名单或需申报外部请求的环境，这是一条部署前要处理掉的默认项。

另外，README 说明项目通常不接受新技能的贡献，且对技能的任何修改必须在它支持的所有 agent 上都能工作。这条对你意味着：**别指望把它改成团队专用版还长期跟上游同步**，定制要放在自己的技能里。

## 八、三类不适合引入的情形

| 情形 | 原因 |
| --- | --- |
| 团队日常改动多为一行修改 | 完整流程的固定开销大于收益 |
| 无法接受"先写测试、否则删代码" | 这一条是它最硬的规则，不接受就不该开 TDD 技能 |
| 同事的 harness 五花八门且无法统一 | 平台差异会让同一套方法论在不同人身上表现不同 |

## 九、限制与结论

引入这套方法论要算的三件事，本质上是三个问题：装在哪、花多少、怎么证明它在按流程走。其中第二件最容易被低估——它主动增加上下文数量，而派发内容的膨胀会让成本进一步放大。

本文的限制：没有安装或运行；只读了 README 与五个技能文件；没有核验各平台钩子的实际注入时机；计划文件位置、评审门等与流程的冲突点是我根据文档推断的，未在真实团队中验证；星标数为检索当天快照。

下一步建议：先只推"完成必须带证据"这一条，跑两周，记录它拦下过几次过早的完成声明。这个数字能告诉你团队是否值得进入下一步。
