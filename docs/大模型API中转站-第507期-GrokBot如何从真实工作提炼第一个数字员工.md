# Grok Bot 如何从真实工作提炼第一个数字员工

第一次接触 Grok Bot 时，很多人会先创建一组很大的职位：营销总监、产品总监、财务总监、运营总监。职位名称看起来完整，真正派任务时却很快发现，岗位负责的结果太宽，工作方法没有定义，最后只得到一批会聊天、却不知道每天该交付什么的 Bot。更适合落地的起点，是一项已经存在、而且能够验收的真实工作。

这篇文章聚焦第一个 Bot 的提炼过程：从岗位卡、第一项任务到反馈规则，逐步把一项真实工作变成可复用的数字员工岗位。

## 一、先判断这项工作是否适合长期交给 Bot

不是所有任务都适合创建独立 Bot。

可以先检查五个条件：

```text
结果是否会重复出现？
输入来源是否相对稳定？
工作步骤是否能逐步说清？
结果是否能够验收？
哪些动作需要人工批准，是否可以提前划出？
```

例如“每天整理过去 24 小时的 AI 新闻”比“负责公司的增长”更适合做成岗位。

前者有固定时间、来源、输出和停止条件。

后者包含太多不同职责，无法判断 Bot 到底有没有完成工作。

## 二、不要先设计组织架构

数字员工不是现实公司的职位名称搬运器。

现实公司的“运营总监”可能管理预算、人员、渠道和供应商。

如果把这个名称直接交给 Bot，它并不知道当前最重要的结果是什么。

建议把岗位名称改成结果名称：

| 模糊职位 | 可执行岗位 |
| --- | --- |
| 营销总监 | 每周筛选并解释 10 个选题 |
| 情报总监 | 每天核验 AI 行业变化并生成简报 |
| 运营总监 | 每天读取经营表并列出异常事项 |
| 财务总监 | 每周检查现金流表并标记异常 |

岗位名称越接近固定交付物，越容易写出边界。

## 三、先写一份岗位卡

创建 Bot 前，先写一页岗位卡。

岗位卡不需要描述所有未来能力，只需要写清当前长期有效的部分：

```text
岗位名称：
负责结果：
长期数据源：
工作步骤：
固定交付物：
验收标准：
禁止动作：
人工审批点：
失败时如何处理：
```

这张卡可以帮助你区分岗位说明和临时任务。

长期职责放岗位卡。

今天要研究什么、使用哪段时间范围、交付给谁，放进当次消息。

## 四、岗位说明示例：情报研究员

下面是一份最小可用的岗位说明：

```text
你是公司情报研究员。

负责结果：
持续整理可验证的 AI 新闻、工具教程和产品变化，帮助团队决定哪些主题值得继续研究。

长期数据源：
官方文档、官方公告、公开技术文章、X 上的公开帖子和视频说明。

工作步骤：
先确定时间范围，再收集一手来源，区分事实与作者判断，最后整理为结构化简报。

固定交付物：
标题、来源、发布时间、核心事实、适用人群、待核验事项和下一步建议。

验收标准：
每条重要事实都有来源；无法取得原始数据时明确说明；不猜测曝光量、价格和性能数字。

禁止动作：
不发布内容，不代表公司回复，不发送私信，不修改生产数据。

人工审批点：
对外发布、付款、删除资料和需要登录验证的操作必须等待确认。

失败处理：
来源打不开或数据过期时记录失败原因，不用旧资料假装完成。
```

这份说明没有要求 Bot “变得专业”或“主动完成一切”。

它把岗位限制在可以观察和验收的范围内。

## 五、第一项任务要写清五件事

岗位创建完成后，不要只发送“帮我研究一下”。

第一项任务至少要写清：

1. 最终要交付什么；
2. 去哪些来源寻找；
3. 哪些内容不能猜；
4. 使用什么格式交付；
5. 何时必须回来请求人工确认。

示例：

```text
请整理过去 7 天公开讨论 Grok Bot 使用方法的资料。

范围：
- 区分 X Article、普通帖子和教程视频；
- 优先使用原作者页面、官方资料和公开可访问链接；
- 记录作者、发布时间、主题、可见数据和原文链接；
- 取不到曝光数据时写“未取得”，不要估算；
- 输出 Markdown 表格，并在末尾列出需要人工核对的项目；
- 不发布、不联系作者、不点赞或转发。
```

这条任务同时定义了输入范围、工作动作、交付格式和权限边界。

## 六、第一次交付重点看什么

第一次不要急着判断 Bot 是否“聪明”。

先看它有没有遵守工作协议：

```text
是否真的访问了指定来源？
是否把不同内容类型分开？
是否区分事实和判断？
是否对缺失数据保持空缺？
是否留下了原文链接？
是否执行了未经授权的外部动作？
```

如果结果缺少作者、时间或来源，不要只说“写得不够好”。

应该把缺口改写成以后可以重复检查的规则。

## 七、用具体反馈修正岗位

有效反馈通常包含三部分：

```text
哪一项结果不符合要求。
为什么不符合。
下次固定采用什么规则。
```

例如：

```text
你把 X Article 和视频帖放在同一组了。
以后按内容载体分组，并为每组增加“可见数据”字段；取不到时写未取得，不要用互动数替代曝光量。
```

这比“以后认真一点”更容易沉淀成岗位规则或 Skill。

## 八、什么时候该把规则放进岗位说明

不是所有反馈都要立刻写进长期岗位。

可以按下面的判断：

| 情况 | 放置位置 |
| --- | --- |
| 只适用于今天的主题 | 当次任务 |
| 每次都要遵守的来源规则 | 岗位说明 |
| 已经跑通的完整步骤 | Skill |
| 某个项目的临时背景 | 项目文件或任务上下文 |

过早把临时要求写进岗位，可能让 Bot 越来越臃肿。

岗位说明只保留跨任务稳定的约束。

## 九、从聊天结果变成交付物

长期岗位不能只依赖对话历史。

建议每次交付都包含固定字段：

```text
本次任务：
数据时间：
实际读取范围：
已完成：
未完成：
失败原因：
需要确认：
来源清单：
```

即使没有发现任何有效资料，也要输出“已检查范围”和“没有发现的原因”。

这样下一次运行才不会重复同一轮无效搜索。

## 十、何时创建第二个 Bot

不要因为第一个 Bot 运行成功，就马上复制十个岗位。

第二个 Bot 应该在工作中出现稳定分工后再创建。

例如情报研究员负责收集资料，后来持续出现另一项工作：根据读者、业务目标和写作方向判断哪些选题值得继续。

这时可以创建内容筛选员。

两个岗位分别负责：

```text
情报研究员：找材料、核来源、补数据。
内容筛选员：评估价值、排序选题、提出补充问题。
```

如果第二个 Bot 只是把第一个 Bot 的结果再复述一遍，就还没有形成真正分工。

## 十一、与代码 Agent 的边界

Grok Bot 适合围绕岗位、跨软件任务和长期交付组织工作。

Codex 或 Claude Code 更适合围绕代码仓库、终端、构建、测试和 Git 组织工作。

两类工具能力会重叠，但选择时应看主要工作对象：

| 工作对象 | 更适合的组织方式 |
| --- | --- |
| 资料、网页、跨软件事务 | 岗位型 Bot |
| 代码、测试、提交和发布 | 项目型 Coding Agent |
| 混合任务 | 由岗位 Bot 负责协调，代码 Agent 负责仓库变更 |

不要因为一个工具能调用终端，就把所有工程任务都交给它。

工作对象和验收方式仍然决定工具是否合适。

## 十二、上线前的最小检查

第一个 Bot 真正长期运行前，至少检查：

```text
岗位说明没有模糊的无限责任。
每项任务都有清晰交付格式。
来源和数据时间会被记录。
失败时不会用旧数据冒充新结果。
外部发布、付款和删除动作需要审批。
结果可以由人快速抽查。
```

如果这些条件还不满足，可以先保持手动触发，不要急着设置定时运行。

## 十三、结论

第一个 Grok Bot 不应该从一张理想组织架构图里生成，而应该从一项真实、重复、可验收的工作里提炼出来。

先写岗位卡，再派一项有明确结果的任务；根据实际缺口修正规则；等方法稳定后，再把它沉淀为 Skill 或创建第二个专业岗位。

数字员工的价值不在职位名称有多大，而在它是否长期负责一类清楚的结果，并且能在失败时把问题交回给人。
