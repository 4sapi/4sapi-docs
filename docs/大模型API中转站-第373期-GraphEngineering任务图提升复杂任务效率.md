# Graph Engineering：AI复杂任务的任务图设计

很多人使用 AI 完成复杂任务时，习惯采用一条直线流程：

```text
找资料 → 分析资料 → 写文章 → 检查文章 → 完成
```

任务比较小时，这样做没有问题。但当任务变大，例如要分析几十份资料、检查几百个文件、调查多个方向时，这条直线就会越来越慢。

原因并不一定是 AI 变慢了，而是很多本来可以同时进行的工作，被人为安排成了先后顺序。只要前面一个任务没有完成，后面的所有任务就只能等待。

Graph Engineering 要解决的就是这个问题：在让一个 AI 按顺序完成所有事情之前，先画清楚任务之间的关系，再让可以同时进行的工作并行执行。

Graph Engineering 可以翻译成智能体图工程、AI 工作流图设计或多智能体流程设计。这里的 Graph，指的是一张任务关系图。它不是为了让流程看起来更复杂，而是为了把任务之间真实存在的并行关系和依赖关系表达出来。

## 一、先把一条直线变成一张图

假设你要研究一个问题：

> AI 会不会取代普通人的工作？

如果按照传统方式处理，可能是先搜索资料，分析资料，再写文章，最后检查。这个过程很容易变成长时间等待。

但实际上，前面的研究工作可以拆开：

```text
节点 A：研究 AI 对重复性工作的影响
节点 B：研究 AI 对专业岗位的影响
节点 C：研究就业数据和行业报告
节点 D：收集真实职业案例
节点 E：整理支持和反对观点
        ↓
节点 F：统一汇总和写作
        ↓
节点 G：事实与逻辑检查
```

节点 A、B、C、D 不需要互相等待，因此可以同时进行。节点 E 需要等前面的资料到齐，节点 F 又要等 E 完成，节点 G 则要等文章初稿完成。

这就是一张简单的智能体工作图。

图中的重点不是“开了几个 AI”，而是要回答两个问题：哪些任务可以并行，哪些任务必须等待前置结果。

## 二、Graph 中最重要的两个概念

### 1. Node：任务节点

Node 就是一个相对独立的任务。它可以由 AI 完成，也可以由程序或人工完成。

一个节点可以是：

- 一段固定程序；
- 一个搜索工具；
- 一个文件扫描任务；
- 一个模型分析步骤；
- 一个格式转换步骤；
- 一次人工审核；
- 一个最终发布动作。

节点不一定等于一个 Agent。一个 Agent 可以连续执行多个简单动作，一个复杂节点也可以由多个子任务组成。

划分节点时，重点看它能否独立描述输入、输出和完成条件。例如“研究公司风险”太宽泛，可以拆成：

```text
收集财务数据
收集监管处罚信息
检查行业环境
分析客户和供应商依赖
汇总风险证据
```

每个节点都应该有自己的范围。如果一个节点什么都负责，它就很难并行，也很难验证。

### 2. Edge：依赖边

Edge 表示两个任务之间存在依赖。

例如：写文章必须使用收集到的资料，所以写作节点要等待资料收集完成。这是一条真实的依赖关系。

但“查找支持观点”和“查找反对观点”之间没有必要互相等待，因此可以并行运行。

判断两个任务能否并行，只需要问一个问题：

> 后面的任务是否必须读取前面任务的结果？

如果答案是“必须”，就存在依赖；如果答案是“不必须”，通常就可以考虑并行。

当然，还要额外检查两个任务是否会修改同一个文件、占用同一个端口、写入同一份数据库，或者消耗同一个不可共享资源。逻辑上可以并行，不代表运行环境一定允许它们同时执行。

## 三、要点一：把直线变成图，执行多任务并行

假设你要分析 20 家 AI 公司。

如果一个 AI 按顺序处理：

```text
公司 1 → 公司 2 → 公司 3 → …… → 公司 20
```

每家公司需要两分钟，理论上就需要大约 40 分钟，还没有计算中途失败、重试和上下文切换的时间。

如果把任务分给多个智能体，就可以变成：

```text
Worker A：公司 1 - 公司 5
Worker B：公司 6 - 公司 10
Worker C：公司 11 - 公司 15
Worker D：公司 16 - 公司 20
        ↓
统一汇总
```

这在技术上叫并行处理，Parallel Processing。

并行处理不能让单个 AI 变得更聪明，但可以让整个系统拥有更大的处理宽度。任务数量多、彼此独立时，整体完成时间通常会缩短。

不过，理论上的并行时间不能直接等同于实际时间。实际效果还会受到并发额度、机器资源、网络、模型响应速度、任务分配是否均衡和汇总节点速度的影响。

如果公司 1 只需要一分钟，公司 2 需要十分钟，那么负责公司 2 的 Worker 就可能成为整个流程的瓶颈。任务拆分时，应该尽量让各个节点的工作量接近，而不是机械地按照数量平均分配。

## 四、要点二：并行之后必须有汇总节点

多个 AI 同时工作，会产生很多独立结果。这些结果如果散落在不同对话里，最终仍然很难使用。

这时需要一个汇总节点，将它们统一处理：

- 去重；
- 统一格式；
- 处理冲突；
- 按重要程度排序；
- 标记不确定内容；
- 生成最终结论。

在技术上，这个过程叫 Fan-out and Fan-in，也就是扇出与汇合。

Fan-out 是把一个大任务分散出去：

```text
总任务
  ├── 研究方向 A
  ├── 研究方向 B
  ├── 研究方向 C
  └── 研究方向 D
```

Fan-in 是把多个结果重新收回来：

```text
研究方向 A ─┐
研究方向 B ─┤
研究方向 C ─┼──> 汇总节点
研究方向 D ─┘
```

汇总节点不能只是把四份结果拼接在一起。它还要判断哪些内容重复、哪些结论矛盾、哪些资料缺少来源。

例如三个 Agent 都说“这家公司收入下降”，汇总节点需要继续检查：

```text
三个 Agent 使用的是不是同一份数据？
比较的是不是同一个年度？
说的是收入下降，还是利润下降？
它们是否把同一条新闻重复计算了三次？
```

如果没有这个汇总环节，多个 AI 的数量优势可能只是制造更多重复内容。

## 五、统一每个节点的输出格式

并行任务最容易出现的问题，是每个 AI 返回的格式不同。

一个 AI 写了一篇长文，另一个 AI 返回一张表，第三个 AI 只给出一句结论。汇总节点收到这些结果以后，还要重新判断每份内容是什么，处理成本会非常高。

因此，每个节点都应该提前规定输出格式。

例如研究节点可以要求：

```text
请输出以下五项：
1. 一句话结论；
2. 支持结论的三条证据；
3. 每条证据的来源位置；
4. 可能推翻结论的条件；
5. 仍然缺少的资料。
```

也可以使用结构化格式：

```json
{
  "topic": "目标公司的收入变化",
  "conclusion": "待判断",
  "evidence": [
    {
      "source": "年度报告",
      "location": "第 42 页",
      "quote": "营业收入为……"
    }
  ],
  "confidence": "medium",
  "uncertainties": [
    "尚未确认是否剔除汇率影响"
  ],
  "next_action": "检查上一年度同期口径"
}
```

格式不一定非要使用 JSON，Markdown 表格也可以。关键在于字段固定，后续节点能够稳定读取。

至少应包含：

```text
结论
证据
来源
不确定性
下一步动作
```

不要只要求 Agent 返回“分析结果”。这个词太宽泛，不同 Agent 对它的理解完全不同。

## 六、要点三：加入相对独立的验证节点

多个 Agent 并行完成以后，不能直接把它们的结论当作事实，还需要验证节点。

验证者要保持相对独立。

假设第一个 AI 已经写了一大段分析：

> 我认为这家公司存在严重经营风险，理由如下……

如果验证者完整看到这段推理，它很容易沿着前一个 AI 的方向继续思考。这可能导致确认偏误：因为前面已经认为有问题，所以后面只寻找支持这个结论的证据。

更好的做法是，只给验证者：

- 原始资料；
- 需要验证的结论；
- 明确判断标准。

例如：

```text
待验证结论：该公司 2025 年出现明显收入下降。

请检查：
1. 是否有原始财务数据；
2. 下降的是收入还是利润；
3. 对比周期是否一致；
4. 数据是否经过汇率或会计口径调整；
5. “明显下降”是否有明确判断依据。
```

验证者应该重新检查证据，而不是评价前一个 AI 的结论看起来是否可信。

### 验证节点应该放在哪里

验证不应该只放在整张图的最后。更合理的做法是分层验证。

节点级验证：

```text
输出格式是否正确？
是否有来源？
来源是否真实存在？
是否超出了负责范围？
```

汇总级验证：

```text
是否存在重复资料？
不同节点是否使用了相同数据？
是否存在互相矛盾的结论？
是否把推测写成了事实？
```

最终结果验证：

```text
是否回答了最初的问题？
关键结论是否可以追溯？
是否遗漏重要反方证据？
是否存在明显的逻辑跳跃？
```

分层验证可以让问题更早暴露，避免最后才发现基础资料错误，导致前面的分析和写作全部返工。

## 七、要点四：Graph 中也可以有 Loop Engineering

Graph 负责整张路线图，Loop 则是路线图的一部分。

例如：

```text
Graph：
资料收集 → 初步分析 → 交叉验证 → 写作 → 发布前审核

Loop：
初步分析 → 发现证据不足 → 继续搜索 → 再次分析
```

从 Prompt 到 Context，再到 Harness、Loop，最后发展到 Graph，并不是毫无关联的几个概念，而是在一步步迭代：

```text
Prompt：告诉模型要做什么
Context：提供模型需要知道的背景
Harness：提供工具、权限和运行环境
Loop：让局部任务反复执行和修正
Graph：管理整张任务路线图和节点依赖
```

Loop 适合处理一个节点内部的不确定性，Graph 负责管理多个节点之间的关系。

但 Loop 也有一个明显缺点：如果没有停止条件，任务可能一直运行。

因此要提前规定：

```text
最多搜索几轮
最多重试几次
最多调用多少个工具
最多运行多少分钟
最高消耗多少预算
什么情况必须交给人工
```

局部问题不确定时使用 Loop，任务关系复杂时使用 Graph，二者可以组合，但不要把所有任务都放进无限循环。

## 八、这套模式常见的四个问题

### 1. 重复工作

两个 AI 可能搜索到同样的资料，浪费 Token 和时间。

解决方法是提前划分研究方向：

```text
节点 A：只研究财务数据
节点 B：只研究监管信息
节点 C：只研究用户反馈
节点 D：只研究行业趋势
```

汇总时再做去重，不能让每个节点都从相同的宽泛问题开始。

### 2. 结果格式不统一

一个 AI 写长文，一个 AI 返回表格，另一个只给结论，汇总会非常困难。

解决方式是在节点启动前规定统一输出格式，并在汇总前增加格式验证节点。

### 3. 多个 AI 修改同一份内容

例如两个 AI 同时修改同一篇文章，可能互相覆盖，最后连谁改了什么都说不清楚。

更好的方法是让每个 AI 修改独立副本：

```text
原始文件
  ├── Worker A 副本
  ├── Worker B 副本
  └── Worker C 副本
        ↓
统一比较差异
        ↓
合并节点决定最终版本
```

代码任务可以使用不同的 Git Worktree，文档任务可以使用不同的输出文件。最后由一个合并节点统一处理，不要让多个 Agent 直接写同一个文件。

### 4. 无限重试

如果任务一直失败，但系统没有停止条件，Graph 可能变成一个不断消耗资源的 Loop。

因此每个节点都要记录：

```text
尝试次数
最近一次错误
是否允许重试
下一步应该重试、换模型还是人工处理
```

连续使用同一提示词重试，通常不会得到不同结果。遇到输入错误、权限错误或逻辑冲突时，应该修改条件或交给人工，而不是继续重复执行。

## 九、Graph 中要保存状态

如果任务很短，依赖聊天记录也许够用。但当 Graph 包含几十个节点时，不能只靠翻对话判断进度。

最简单可以使用一张状态表：

| 节点 | 状态 | 依赖 | 产物 | 下一步 |
| --- | --- | --- | --- | --- |
| 资料收集 A | 已完成 | 无 | research-a.md | 等待汇总 |
| 资料收集 B | 运行中 | 无 | - | 继续执行 |
| 观点验证 | 等待中 | A、B、C | - | 等待资料齐全 |
| 初稿写作 | 等待中 | 观点验证 | - | 不可启动 |
| 最终审核 | 等待中 | 初稿 | - | 不可启动 |

状态至少应区分：

```text
pending：等待启动
running：正在执行
blocked：被依赖或权限阻塞
review：等待验证
done：完成并通过检查
failed：执行失败
needs_decision：需要人工决定
```

“Agent 说自己完成了”不等于任务完成。只有产物存在、格式正确、验证通过以后，节点才应该进入 `done`。

## 十、一个完整的研究型 Graph 示例

假设最终目标是写一篇关于“AI 是否会取代普通人工作”的文章，可以设计成：

```text
节点 A：收集支持“部分工作会被替代”的资料
节点 B：收集反对“普通人会被全面替代”的资料
节点 C：收集就业数据和行业报告
节点 D：收集真实职业案例
节点 E：检查 A、B、C、D 的来源和时间
节点 F：汇总主要观点和争议
节点 G：设计文章结构
节点 H：完成初稿
节点 I：独立检查事实和逻辑
节点 J：人工确认最终结论
```

依赖关系：

```text
A ─┐
B ─┤
C ─┼─> E ─> F ─> G ─> H ─> I ─> J
D ─┘
```

A、B、C、D 可以并行，E 必须等待四项研究完成。F 只能读取通过验证的资料，不能直接使用未经检查的原始结论。I 不应该只检查错别字，还要检查有没有把“岗位变化”写成“职业消失”，有没有把个别案例写成普遍趋势。

J 则负责最终判断：文章是否符合作者立场，哪些地方需要保留不确定性，哪些结论必须删掉。

## 十一、Graph Engineering 的成本问题

并行不等于免费。

每增加一个节点，就可能增加：

- 模型调用次数；
- Token 消耗；
- 中间文件数量；
- 汇总成本；
- 失败和重试概率；
- 权限和日志管理成本。

因此要区分“必须拆分”和“可以合并”。

例如：

```text
读取一个文件
提取三个字段
写入一行表格
```

这几个动作完全可以交给一个 Agent 一次完成。强行拆成三个节点，只会增加通信成本。

而下面这种任务更适合拆分：

```text
读取 1000 个文件
分别提取不同字段
对结果进行独立验证
最后生成汇总报告
```

拆分的意义在于扩大处理宽度，而不是把每个动作都包装成一个 Agent。

可以用一个简单公式做初步估算：

```text
总成本 ≈ 节点数量 × 平均调用成本
        + 汇总成本
        + 验证成本
        + 重试成本
```

真实结果还会受到缓存命中、上下文长度、模型选择和并发限制影响，但这个公式足以提醒我们：不要为了显得先进而盲目增加节点。

## 十二、什么时候不用 Graph

以下任务通常不需要 Graph：

```text
总结一篇短文章
修改一个配置文件
解释一个报错
生成一个简单脚本
翻译一段文字
```

这些任务的依赖关系很简单，直接让一个 AI 完成即可。

以下情况可以考虑 Graph：

```text
需要同时研究多个方向
需要处理大量文件
需要多个独立观点
需要不同角色进行验证
需要跨项目或跨机器执行
需要失败后重新调度
```

简单任务使用轻量模型，复杂任务使用更强的 Agent 或 Graph，不是因为某个工具永远更好，而是不同工具适合不同任务规模。

## 十三、一个适合小白的 Graph 设计模板

刚开始设计时，不需要先学习复杂框架。只要回答下面七个问题，一张基本的任务图就形成了：

### 1. 最终目标是什么

最后需要得到什么，是一篇文章、一份报告、一组修改后的文件，还是一个可以运行的程序？

### 2. 任务可以拆成哪些小任务

列出所有必要步骤，但不要一上来就决定由几个 Agent 执行。

### 3. 哪些任务可以并行

找出互相不需要读取结果的节点，并确认它们不会修改同一份资源。

### 4. 哪些任务必须等待

把真实的前置条件画出来，不要因为“看起来顺序合理”就强行增加依赖。

### 5. 谁负责验证

重要结论由谁检查？根据什么证据检查？验证者是否独立于生成者？

### 6. 多个结果如何汇总

结果是否需要去重、排序、冲突处理和格式统一？最终由哪个节点负责？

### 7. 什么条件下停止

最多执行多少任务、多少轮、多少分钟，或者消耗多少预算？什么情况需要人工接管？

如果这七个问题都能回答清楚，就已经完成了 Graph 设计的第一版。

## 结语

Graph Engineering 的核心不是画一张漂亮的流程图，而是把任务之间真实存在的依赖关系表达出来。

节点负责一个相对独立的工作，边负责表示依赖关系；可以并行的任务同时执行，必须等待的任务按顺序推进；多个结果通过汇合节点统一整理，重要结论交给相对独立的验证节点检查。

从 Prompt 到 Context，再到 Harness、Loop，最后发展到 Graph，并不是几个互不相关的概念。Prompt 决定单次指令，Context 提供任务背景，Harness 负责工具和运行环境，Loop 处理局部重试，Graph 则负责管理整张任务路线图。

但复杂度也要和任务规模匹配。简单任务不要强行使用 Loop 和 Graph，复杂任务也不要继续用一条直线硬撑。先判断任务之间有没有真实的并行关系和依赖关系，再决定要不要画图、拆节点和增加验证。这样使用 AI，效率和成本才能同时得到控制。
