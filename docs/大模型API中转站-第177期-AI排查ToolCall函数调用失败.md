# 【大模型API中转站】第177期 AI排查Tool Call失败 | 参数和权限

本文是【大模型API中转站】系列的第177篇。本系列致力于用最低的成本、最清晰的方法，帮你打通多模型API的任督二脉。建议先收藏，随用随查。

Agent 工作流里，最难排的一类问题是：

```text
Tool Call 失败。
```

模型回答本身没问题。

但一调用工具就挂：

```text
参数不合法。
工具不存在。
权限不足。
返回值太大。
调用顺序错。
模型选错工具。
工具执行成功但模型理解错返回。
```

这类问题特别适合 Fable 5。

因为它要同时看：

```text
用户目标。
模型计划。
工具 schema。
实际参数。
工具返回。
权限边界。
后续模型反应。
```

## 1. Tool Call 失败先分层

| 层级 | 常见问题 |
| --- | --- |
| 工具发现 | 模型不知道有哪些工具 |
| 工具选择 | 模型选错工具 |
| 参数生成 | 参数缺字段、类型错 |
| 权限 | 工具没权限、Key 不允许 |
| 执行 | 工具内部报错 |
| 返回 | 返回太长、格式不稳定 |
| 后处理 | 模型误读工具结果 |

不要只说：

```text
工具调用失败了。
```

要告诉 AI 失败在哪一层。

## 2. 给 AI 的 Tool Call 排错包

```text
【任务目标】
- 用户原始请求：
- Agent 计划摘要：

【工具】
- 工具名称：
- 工具用途：
- 参数 schema：
- 权限范围：

【调用】
- 模型选择的工具：
- 实际参数：
- 工具返回：
- 错误信息：

【上下文】
- 调用前模型看到的信息：
- 调用后模型怎么解释结果：

【边界】
- 不扩大工具权限
- 不输出真实 Key
- 不执行危险动作
- 先判断失败层级
```

工具参数和返回值可以脱敏。

尤其是文件路径、用户数据、内部 URL、Key。

## 3. 常见根因一：Schema 太模糊

工具参数写得像：

```json
{
  "query": "string"
}
```

模型不知道 query 应该是什么。

更好的 schema：

```json
{
  "project_id": "string",
  "date_from": "YYYY-MM-DD",
  "date_to": "YYYY-MM-DD",
  "error_type": "enum: api_401 | api_429 | timeout | json_parse"
}
```

AI 可以审查：

```text
这个工具 schema 是否足够明确。
哪些字段需要枚举。
哪些字段需要示例。
哪些字段不该让模型自由填。
```

## 4. 常见根因二：工具权限不匹配

模型想做：

```text
读取生产日志。
重启服务。
修改 DNS。
发送工单。
```

但当前工具没有权限。

这不是 bug。

这是权限边界。

AI 排查时要区分：

```text
工具确实缺必要只读权限。
还是模型试图执行越权动作。
```

对于生产环境，建议：

```text
读权限和写权限分开。
只读工具默认可用。
写工具必须人工确认。
高风险工具不暴露给普通 Agent。
```

## 5. 常见根因三：返回值太长

工具一次返回：

```text
几万行日志。
全量数据库结果。
完整网页 HTML。
巨大 JSON。
```

模型后续处理容易失败。

解决：

```text
工具支持分页。
工具支持 filter。
工具只返回摘要和证据编号。
长结果先由辅助模型压缩。
```

4SAPI 里也要记录：

```text
tool_result_tokens
```

很多 Agent 成本高，不是模型想太多。

是工具返回太大。

## 6. 常见根因四：模型误选工具

比如：

```text
应该查 4SAPI 调用日志，却去查业务数据库。
应该读 Nginx error.log，却去读 access.log。
应该用只读工具，却调用写入工具。
```

解决方式：

```text
工具描述写清适用场景。
工具名不要太抽象。
给模型工具选择规则。
高风险工具加确认。
```

Fable 5 可以帮你审查工具目录：

```text
请审查这组 Agent 工具定义，找出命名不清、权限过大、参数模糊、容易误选的工具。
```

## 7. AI Prompt

```text
你是 Agent Tool Call 排查助手。

请根据用户目标、工具 schema、模型选择、实际参数、工具错误和返回值，判断失败发生在哪一层：
1. 工具发现
2. 工具选择
3. 参数生成
4. 权限不足
5. 工具内部错误
6. 返回值过长或格式不稳定
7. 模型误读返回

要求：
- 不建议扩大权限作为第一方案。
- 涉及写操作、生产、发送、删除时标注人工确认。
- 给 schema、工具描述和错误处理的最小修改建议。
```

## 8. 4SAPI 和工具审计

模型调用日志只记录模型请求还不够。

Agent 要记录工具调用：

```text
agent_id
task_id
model
tool_name
tool_args_schema_version
tool_args_valid
tool_status
tool_duration_ms
tool_result_size
risk_level
human_confirmed
```

这样你才能复盘：

```text
哪个工具最容易失败。
哪个模型最容易填错参数。
哪个工具返回太大。
哪些失败来自权限边界。
哪些工具应该拆分。
```

## 9. 工具错误要结构化返回

很多 Tool Call 难排，是因为工具返回：

```text
失败了。
error。
something went wrong。
```

模型看不懂，人也看不懂。

工具应该返回结构化错误：

```json
{
  "ok": false,
  "error_type": "permission_denied",
  "message": "当前 Key 无权读取生产日志",
  "retryable": false,
  "needs_human": true
}
```

这样模型才知道：

```text
不要重试。
不要换参数乱撞。
应该请求人工确认。
```

如果是可重试错误，也要写清：

```json
{
  "ok": false,
  "error_type": "rate_limited",
  "retryable": true,
  "retry_after_seconds": 30
}
```

这比把异常堆栈整个丢回模型稳定得多。

## 10. 工具目录也需要 Review

Agent 工具越多，越容易乱。

建议每隔一段时间让 Fable 5 审查工具目录：

```text
请审查这批工具定义。
找出：
1. 名称相似、容易误选的工具
2. 参数过宽的工具
3. 权限过大的工具
4. 返回值过长的工具
5. 缺少错误类型的工具
6. 应该拆成只读/写入两个工具的工具
```

这类审查很重要。

因为 Agent 的可靠性，不只取决于模型。

也取决于你给它的工具是否清楚、窄口、可审计。

## 11. 实战补充：给工具加风险等级

Tool Call 做到后面，一定要给工具分级。

不要所有工具都长一个样。

我一般建议分四类：

```text
L0：纯查询工具，只读、无副作用。
L1：低风险写入工具，只影响草稿、测试环境、个人设置。
L2：生产写入工具，会影响真实用户或真实数据。
L3：高风险工具，涉及删除、扣费、发消息、改 DNS、改权限。
```

然后给每类工具配不同规则：

| 风险等级 | 是否可自动调用 | 要不要人工确认 | 日志要求 |
| --- | --- | --- | --- |
| L0 | 可以 | 不需要 | 记录 task_id |
| L1 | 可以有限调用 | 视场景 | 记录参数摘要 |
| L2 | 不建议自动执行 | 需要确认 | 记录审批人 |
| L3 | 默认禁止 | 必须确认 | 完整审计 |

这件事看起来像权限治理，其实会直接提升 Agent 成功率。

因为模型知道边界以后，就不会在一个简单排查任务里乱调用高风险工具。

给 Fable 5 的审查 Prompt 可以这样写：

```text
请审查这组工具，并给每个工具标注 L0-L3 风险等级。
判断依据包括：是否写入生产、是否发送外部消息、是否修改权限、是否产生费用、是否可逆。
对 L2/L3 工具，请补充人工确认条件和审计字段。
```

如果走 4SAPI，建议把工具风险也写进调用链：

```text
task_id
model
tool_name
tool_risk_level
human_confirmed
approval_id
tool_status
```

这样复盘时你能回答：

```text
哪个模型最常请求高风险工具？
哪些工具经常因为权限被拦？
哪些失败其实是边界设计正确？
```

这句话很关键：

```text
工具被拒绝，不一定是失败，有时是系统救了你。
```

## 12. 总结

Tool Call 失败，不要只怪模型笨。

很多时候是：

```text
工具定义不清。
参数 schema 太松。
权限设计混乱。
返回值太长。
错误处理不够结构化。
```

Fable 5 适合审查工具设计。

辅助模型适合整理工具日志。

4SAPI 负责模型调用和成本日志。

工具层则要自己记录审计。

一句话：

```text
Agent 能不能干活，取决于模型，也取决于工具是否像工具。
```
