# GPT-6 Luna Decisions 是什么：决策接口的定位、接口形态与适用边界

以 **2026 年 10 月 14 日**核验的官方文档为准，OpenAI 的 Decisions 接口用于评估文本、图像或两者的组合，返回**类型化的答案**，官方描述其速度约为 Responses API 的十倍。它回答的是三类问题：某个条件成立的概率、从固定选项里选一个、或者按评分标准给一个分。官方明确表示该接口处于公开测试（public beta）阶段，并计划在接下来几周内正式可用。[Decisions 文档](https://developers.openai.com/api/docs/guides/decisions)

需要先澄清一个常见的命名混淆：**官方文档里的模型标识是 `gpt-6-luna`**，而不是某些第三方追踪站写的 `gpt-6-luna-decisions`。官方说明当前只有 `gpt-6-luna` 这一个模型可用于该接口，请求走专用的 `POST /v1/decisions` 端点。

本文只回答一个问题：**Decisions 接口是用来做什么的，什么任务应该用它，什么任务不该用它。**

## 一、先把命名和接口形态对齐

先把三件事说清楚，避免在选型和编码时走偏：

1. **模型标识**：官方文档写的是 `gpt-6-luna`。
2. **端点**：专用端点 `POST /v1/decisions`，不是 `/v1/responses`，也不是 `/v1/chat/completions`。
3. **接口用途**：评估输入并返回类型化答案，不生成自然语言正文。

第三方聚合站可能把它标成“GPT-6 Luna Decisions”，并按自己的命名展示。**以官方文档的模型标识和端点为准**，否则代码里拼错标识会直接报错。

## 二、一次请求由三部分组成

官方文档把请求拆成三块，理解这三块就理解了整个接口：

| 字段 | 作用 |
| --- | --- |
| `model` | 执行评估的模型，目前仅支持 `gpt-6-luna` |
| `input` | 共享证据：一段文本字符串，或包含文本与图像的用户消息 |
| `questions` | 要评估的问题，包含每个问题的类型、说明，以及允许的选项或评分档 |

响应里是 `answers` 数组。每个问题要给它一个**唯一的 `name`**，响应会把这个名字回传，用来对应“哪个答案属于哪个问题”。这一点很关键：一次请求可以同时问多个问题，靠 `name` 配对。

## 三、三类问题决定返回什么

官方把问题分成三种类型，各自的返回字段不同：

| 类型 | 用途 | 主要结果 |
| --- | --- | --- |
| `predicate` | 判断某个条件是否成立，比如有无破损、段落是否相关 | `probability`，0 到 1 的估计 |
| `choice` | 从固定选项里选一个，比如部门、内容分类 | `choice`，你提供的某个取值 |
| `score` | 按有序档位给分，比如严重程度 | `score`，档位序号的概率加权平均 |

两点必须记住：

- `choice` 和 `score` 都会返回**离散选项上的概率分布**。
- `score` 取的是档位序号的**概率加权平均**，所以结果可能落在两档之间，不是整数。

因此，`choice` 用于**无顺序**的类别（部门、标签），`score` 用于**有顺序**的档位（严重程度、优先级）。选错类型会得到看起来能用、实际口径不对的结果。

## 四、什么时候该用它，什么时候不该用

官方给了一条清晰的选型线：

- 需要上面三类答案之一 → 用 Decisions。
- 需要**按自己的 JSON schema 生成对象**（比如抽取字段、生成解释） → 用 Responses API 的 Structured Outputs。
- 需要**模型发起工具调用并带参数** → 用 function calling。

这条线很实用。很多人把“让模型输出 JSON”当成一件事，其实分成两种：

1. **输出是判定结果**（是/否、哪一类、几分）→ Decisions 更贴合，还附带概率。
2. **输出是自定义结构的内容**（字段、正文、解释）→ Structured Outputs 更合适。

把判定类任务硬塞进 Structured Outputs，会得到没有概率的字符串结果；把内容生成硬塞进 Decisions，会得到一堆你还需要二次拼装的判定。

## 五、适合它的任务

按官方形态，下列任务天然贴合：

- **内容分类与打标**：给定文本或图像，输出类别与置信度。
- **请求路由**：判断工单该进哪个队列，输出选项和概率。
- **质量打分**：对回复、描述、图片给一个有序档位。
- **二值判定**：合规与否、垃圾与否、需要人工复核与否。
- **批量筛选**：对大量条目做初筛，把低置信度样本转人工。
- **图像条件检查**：官方文档给出的示例就是检查商品图片是否可见破损。

这些任务的共同点是：**判定维度明确、答案空间有限、且需要概率来设定阈值**。

## 六、什么时候不该用它

下列场景通常不适合：

1. **需要产出自然语言**：文章、邮件、代码解释，应交给生成式模型。
2. **答案空间开放**：没有预定义选项或评分标准时，无从下手。
3. **需要带论证过程**：它给结论和概率，不给推理链。
4. **自定义结构输出**：应按官方建议改用 Structured Outputs。
5. **极简判定**：几行确定性规则就能写完的逻辑，引入模型只增加成本与不确定性。
6. **合规要求可解释到规则级**：概率型判定在审计上不如显式规则直观。

## 七、和 GPT-6 Luna 本体是什么关系

同一个模型，两种用法：

| 维度 | GPT-6 Luna（生成式） | Decisions 接口（判定式） |
| --- | --- | --- |
| 端点 | Responses / Chat Completions | `POST /v1/decisions` |
| 输出 | 自然语言文本 | 类型化答案与概率 |
| 参数量级上的开销 | 输入与输出都计费 | 以输入为主 |

GPT-6 Luna 本体是 OpenAI 面向高并发、聚焦型任务的高效模型：上下文 1,050,000 tokens，最大输入 922,000 tokens，最大输出 128,000 tokens，支持 `none` 到 `max` 的多档推理强度，知识截止为 2026 年 5 月 18 日。它同时支持文本与图像输入、结构化输出、函数调用、文件检索、联网搜索和提示缓存。[GPT-6 Luna 模型页](https://developers.openai.com/api/docs/models/gpt-6-luna)

所以这不是两个模型，而是**同一个模型的两种对外形态**：要生成文本就用常规接口，要拿判定和概率就用 Decisions 接口。

## 八、放进 OpenAI 家族里看它的位置

官方文档对当前主力模型的定位写得很直白：

- **GPT-6 Astra**：旗舰，面向复杂推理与编码。
- **GPT-6.1 Sol**：在智能与成本之间取平衡。
- **GPT-6 Luna**：面向成本敏感、高并发的任务。

Decisions 接口目前只在 Luna 这一档上提供，这也符合它的定位——**大量、重复、单次简单的判定**，而不是少量、复杂的推理。理解这一点，就不会期待它去做 Astra 擅长的事。[模型目录](https://developers.openai.com/api/docs/models)

## 九、成本结构上的一点提醒

Luna 本体的标准价是每百万输入 0.10 美元、每百万输出 0.50 美元，缓存输入 0.01 美元；超过 272K 输入后，整个请求按输入 2 倍、输出 1.5 倍计费。Decisions 接口以输入为主，输出占比很低，所以账单几乎完全由输入长度和判定条数决定。[定价页](https://developers.openai.com/api/docs/pricing)

这意味着两件事：

- 把规则、样例塞进输入会直接抬高成本。
- 越过 272K 的分档线后，单位价格翻倍，超长输入拆成多次短请求通常更划算。

## 十、验证与限制

要确认它是否适合自己的任务，建议按下面的最小步骤验证：

1. 取 30 至 50 条**已有人工标注**的样本，覆盖各个类别。
2. 用固定的 `questions` 定义跑一遍，记录答案与概率。
3. 计算在高置信度子集上的准确率，而不是整体准确率。
4. 观察低置信度样本是否集中在真正困难的类别上。
5. 设一个阈值，统计自动处理比例与人工比例。

需要明确的限制：

- 官方文档明确该接口处于**公开测试**阶段，正式可用时间以官方公告为准。
- 当前仅支持 `gpt-6-luna` 一个模型。
- 概率不等于校准良好的置信度，直接当阈值用之前要检查分布。
- 本文的价格、上下文与端点均以 2026 年 10 月 14 日的官方文档为准，属于可变事实。

## 十一、常见误解

- **“模型叫 `gpt-6-luna-decisions`”**：官方文档写的是 `gpt-6-luna`。
- **“它和普通对话接口是同一套参数”**：它用的是 `input` + `questions`，返回 `answers`。
- **“它比结构化输出更通用”**：官方把两者的边界写得很清楚，判定用 Decisions，自定义结构用 Structured Outputs。
- **“概率可以直接当准确率”**：概率需要先验证校准程度。

## 十二、调用前置：SDK 版本与端点

官方文档给出了运行示例所需的 SDK 最低版本，低于这些版本会缺少对应的接口封装：

```text
Python      3.26.0 或更高
JavaScript  7.30.0 或更高
Go          3.73.0 或更高
Ruby        0.101.0 或更高
Java        4.78.0 或更高
```

调用形式有两种：

- **直接用 HTTP**：`POST https://api.openai.com/v1/decisions`，带 `Authorization: Bearer <key>` 与 `Content-Type: application/json`。
- **用 SDK**：更新到上表版本后，通过 `decisions` 相关方法调用。

如果你的项目使用固定版本的 SDK，先确认版本满足要求再写代码，否则会出现“接口存在但 SDK 里没有这个方法”的情况。

## 十三、一次请求问多个问题

`questions` 是数组，意味着**一次请求可以提交多个问题**，它们共享同一份 `input`。这对降低成本很有意义：证据只发一次，问题问多个。

实践要点：

1. **给每个问题唯一的 `name`**，响应按 `name` 回传，靠它配对。
2. **问题之间不要语义重叠**，否则相当于重复付费。
3. **类型可以混用**：同一份输入既可以问“是否有破损”（predicate），也可以问“属于哪一类”（choice）。
4. **控制问题数量**：问题越多，指令越容易被稀释，先从小批量验证。

举例来说，一张商品图可以同时问三件事：是否存在可见破损（predicate）、属于哪个品类（choice）、成色如何（score）。三次判定共享一次输入，比三次独立请求更省。

## 十四、图像判定的注意点

官方示例用 predicate 检查商品照片是否有可见破损，并在指令里明确“忽略阴影和包装上的破损”。这提示了图像判定的三个要点：

1. **在 instructions 里写清排除条件**。图像判定最容易出的问题是把无关因素算进来，比如反光、阴影、包装。
2. **图像会转成输入 token**，分辨率越高越贵；大批量场景应先统一尺寸。
3. **准备带标注的样本**。图像判定的准确率无法靠肉眼抽查几张小样本判断，必须有覆盖各类缺陷的标注集。

如果任务同时涉及文本与图像，把它们放进同一个 `input` 的用户消息里，让模型看到同一份证据，而不是拆成两次请求。

## 十五、常见失败模式

| 现象 | 可能原因 | 处理方向 |
| --- | --- | --- |
| 400 报错 | 模型标识或端点写错 | 用 `gpt-6-luna` 与 `/v1/decisions` |
| 答案对不上问题 | 问题没给唯一 `name` | 为每个问题补 `name` |
| 分数不符合预期 | 用 choice 代替了 score | 有序档位改用 score |
| 判定口径漂移 | instructions 写得含糊 | 在指令里写清排除条件 |
| 成本超预期 | 输入里塞了大量样例 | 精简样例、拆分长输入 |

这些失败模式大多和“接口不会用”无关，而是**问题定义不清**。Decisions 接口的成败，八成取决于你能否把判定维度和排除条件写清楚。
## 限制与结论

Decisions 接口把“判定类任务”单独做成一个入口：输出类型化、带概率、速度按官方描述约为 Responses API 的十倍。它适合分类、路由、打分和二值判定，不适合需要生成自然语言、开放答案或自定义 JSON 结构的场景。

选型时先用一批带标注的样本做小规模验证，重点看高置信度子集的准确率和低置信度样本的分布，再决定阈值和自动处理比例。模型标识、端点、价格与状态请在上线前回到官方文档重新核对。
