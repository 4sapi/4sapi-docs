# 给自己的文档做字段级验收：幽灵字段、路径匹配与可跑脚本

一个字段抽取模型发布时给了 0.834 的总分。这个数字能说明"它整体不错"，但回答不了你真正要问的问题：我这几类单据、我最在意的这几个字段，它到底行不行。

要回答这个，只能自己造一套验收。而这套验收里有两个坑，几乎所有人第一次都会踩：一是只算准确率、不区分"漏抽"和"多抽"；二是只抽真实字段、不测"文档里没有的东西它会不会编"。

本文给一套最小可跑的做法，配一个我本机验证过的评分脚本。指标定义参考 Dharma-AI 在 2026 年 11 月 4 日发布的 Field Extractor 博客（[原文](https://huggingface.co/blog/Dharma-AI/dharma-field-extractor)，检索日期 2026-11-05），脚本是我自己写的，不是官方代码；我没有调用过那个模型。

## 一、先承认：总分不能直接迁移

原文的 0.834 是在他们自己的基准上算的：546 份文档 × 3 种场景 = 1,638 个用例（我复算一致）。规模不算小，但要注意两件事：一是**这 546 份文档的分布原文没有披露**（它只列了参考数据集清单，其中 SROIE 与 FUNSD 是留出不训练的）；二是原文那句"收据、商业发票、表单、银行流水、身份证件与合成文档"说的是**训练数据的混合**，不是评测集的构成。这两个别混。

你的分布大概率不是这个混合：可能 90% 是供应商发票，也可能一半是手写化验单。**在混合分布上算出来的平均分，不能按比例搬到你的单峰分布上。**

所以第一步不是拿模型来跑，而是先把验收设计好。

## 二、三种场景，一个都不能少

原文的基准分三种请求，这个设计可以直接抄：

| 场景 | 请求 | 在测什么 |
| --- | --- | --- |
| A 开放抽取 | 不给 schema，要它抽出全部字段 | 覆盖能力：它能不能发现你没点名的字段 |
| B 部分 schema | 只点名文档上真实存在的字段 | 命中能力：你知道要什么时，它准不准 |
| C 含幽灵字段 | schema 里掺入文档上**不存在**的字段 | 诚实性：它会不会为了填满 schema 而编造 |

C 是最容易被跳过的一种，也是最该测的一种。原因是：A、B 两种场景里，模型编造都能"看起来对"——你没法从输出上分辨一个值是读出来的还是猜出来的。只有在 C 里，正确答案明确是 `null`，编造才会暴露。

三种场景要用**同一批文档**，这样差异才只来自请求方式。这一点和我在别处讲过的"同序列对照"是同一个道理。

## 三、指标：三项相乘，而不是一个准确率

原文的分数定义是三个因子相乘：

```text
分数 = 字段级 F1（按路径匹配）× 匹配值的 Levenshtein 相似度 × 合法 JSON 的比例
```

为什么相乘而不是加权平均？因为这三项是**串联的**：路径没对上，值再对也没意义；JSON 解析不了，整页都是废的。相乘等于"任何一环崩了，总分就崩"。

三个因子各自的陷阱：

| 因子 | 陷阱 |
| --- | --- |
| 路径 F1 | 表格必须把**位置**算进路径，否则"第 3 行金额"跑到第 5 行也会被算对 |
| 值相似度 | 金额、编号这类字段，一个字符之差就是错，不该按 0.9 的相似度给分 |
| 合法 JSON 占比 | 分母是"页数"还是"请求数"，要在报告里写清 |

第二行是我要特别提醒的：Levenshtein 相似度对文本字段合理，对数字与编号不合理。`1240.50` 和 `1240.05` 的相似度很高，但业务上完全错。所以**数字与编号类字段应当用精确匹配**，脚本里留了 `exact` 参数专门处理这件事。实测对比很直观：`1240.5` 与 `1240.05` 按相似度算得 **0.98**（几乎是满分，等于把"小数点错位"当成对），把 `total` 列进 `exact` 后该字段直接得 **0**。

## 四、一个可跑的评分脚本

下面这段我自己写过并跑过，不依赖任何第三方库。它做三件事：把嵌套结构展平成"路径 → 值"、按路径交集算 precision/recall/F1、对交集里的值算相似度。

```python
import json

def flatten(obj, prefix=""):
    """把嵌套 dict/list 展平成 {路径: 值}，列表用下标表示位置"""
    out = {}
    if isinstance(obj, dict):
        for k, v in obj.items():
            p = f"{prefix}.{k}" if prefix else str(k)
            out.update(flatten(v, p))
    elif isinstance(obj, list):
        for i, v in enumerate(obj):
            out.update(flatten(v, f"{prefix}[{i}]"))
    else:
        out[prefix] = obj
    return out

def lev(a, b):
    a, b = str(a), str(b)
    d = [[0]*(len(b)+1) for _ in range(len(a)+1)]
    for i in range(len(a)+1): d[i][0] = i
    for j in range(len(b)+1): d[0][j] = j
    for i in range(1, len(a)+1):
        for j in range(1, len(b)+1):
            cost = 0 if a[i-1] == b[j-1] else 1
            d[i][j] = min(d[i-1][j]+1, d[i][j-1]+1, d[i-1][j-1]+cost)
    return d[len(a)][len(b)]

def sim(a, b):
    a, b = str(a), str(b); m = max(len(a), len(b))
    return 1.0 if m == 0 else 1 - lev(a, b)/m

def field_scores(gold, pred, exact=(), valid_json=True):
    """exact: 需精确匹配的字段名（金额、编号类）；valid_json: 该页输出是否可解析"""
    g, p = flatten(gold), flatten(pred)
    gl, pl = set(g), set(p); tp = gl & pl
    prec = len(tp)/len(pl) if pl else (1.0 if not gl else 0.0)
    rec  = len(tp)/len(gl) if gl else (1.0 if not pl else 0.0)
    f1 = 2*prec*rec/(prec+rec) if prec+rec else 0.0
    def one(k):
        name = k.split(".")[-1].split("[")[0]
        if str(g[k]) == str(p[k]): return 1.0
        return 0.0 if name in exact else sim(g[k], p[k])
    v = sum(one(k) for k in tp)/len(tp) if tp else 0.0
    share = 1.0 if valid_json else 0.0
    return {"paths": len(gl), "f1_path": round(f1,3), "value_sim": round(v,3),
            "valid_json": share, "score": round(f1*v*share,3),
            "extra": sorted(pl-gl), "missing": sorted(gl-pl)}
```

我在本机用一份手造的金标准跑过四种预测。金标准是发票号、供应商、到期日、总额四个标量，加一条含描述/数量/单价三个字段的明细——展平后是 **7 条路径**（列表容器本身不产生路径，这一点我自己先算错过一次）。结果如下：

| 预测 | 路径 F1 | 值相似度 | 综合分 | 被列出的差异 |
| --- | --- | --- | --- | --- |
| 完全正确 | 1.000 | 1.000 | 1.000 | — |
| 漏掉"总额" | 0.923 | 1.000 | 0.923 | missing: total |
| 多一个幽灵字段 | 0.933 | 1.000 | 0.933 | extra: planted_field |
| 供应商名写法不同（Acme Ltda → Acme Limitada） | 1.000 | 0.956 | 0.956 | — |

这张表最值得看的是第三行与第四行的对比。**同一个字段换了种写法（值相似度 0.956）比凭空多编一个字段（0.933）扣得还少**——这正好说明为什么"幽灵字段率"必须单独统计。

## 五、脚本测出来的一个特性：幽灵字段会被总分吸收

按上面的结果，多一个不存在的字段，综合分只从 1.000 掉到 0.933，掉 7%。原因是路径 F1 是集合平均：多一条错路径，在 7 条路径的池子里就是掉 6.7%；路径越少，稀释效应越弱、扣分越重。

但业务上，"编造了一个字段"和"少抽一个字段"不是一个量级的错误：前者会让下游系统多出一条假数据，后者通常只是缺失。所以必须单独算一个比率：

```text
幽灵字段率 = 输出里不存在于文档、也不在金标准里的字段数 ÷ 该页金标准字段数
```

计算方法很简单：把 `extra` 里那些**在文档上确实不存在**的路径挑出来（注意区分"模型多抽但文档上真有"和"模型编造"），除以金标准字段数。这个数在报告里应当与综合分并列，而不是被平均掉。

这也是我在另一篇讲长文档评测时强调的同一条原则：**关键失败要单独计数，不要让它在平均分里消失。**

## 六、怎么攒最小测试集

不需要几百份。20 到 40 份就能跑出可用结论，但要满足四个条件：

| 条件 | 做法 |
| --- | --- |
| 覆盖最难的类型 | 手写、扫描件倾斜、表格跨页、印章遮挡，各至少 3 份 |
| 覆盖业务主力 | 你 80% 的量来自哪类单据，就占样本的一半 |
| 金标准两人独立标注 | 字段级标注的分歧比想象中大，尤其日期格式与金额单位 |
| 固定 schema 版本 | schema 一改，历史分数不可比；把 schema 版本写进报告 |

第三条最容易忽略。两个人标同一张发票，"due_date" 一个写 `2026-11-30`、一个写 `30/11/2026`，脚本会判为值不匹配——这不是模型错，是标注规范没定。所以先定格式约定，再开始标。

## 七、关键字段单独统计

综合分是平均，你最在意的字段可能正好是错得最多的。做法是给每个字段单列一行。下面这张表里的百分比是我编的**示意值**，用来说明表格结构，不是任何模型的测试结果：

| 字段 | 精确匹配率（示意值） | 备注 |
| --- | --- | --- |
| 发票号 | 96% | 数字类，用精确匹配 |
| 总金额 | 91% | 小数点错位会算成"高相似度"，必须精确匹配 |
| 供应商名 | 88% | 文本类，可用相似度，但要设阈值 |
| 到期日 | 84% | 格式差异是主要错因 |

数字类字段用精确匹配，文本类可用相似度但要在报告里注明阈值——否则读者会以为 0.9 相似度就是对的。

## 八、怎么读结果并做决策

| 现象 | 含义 | 动作 |
| --- | --- | --- |
| A 高、B 低 | 能发现字段，但按 schema 就位时出错 | 检查 schema 命名与嵌套是否与文档结构冲突 |
| B 高、C 低 | 会为了填满 schema 而编造 | 下游必须加"非空校验"，或改用开放模式 |
| 三个场景都随页数变差 | 可能是分辨率/版面问题，不是字段理解问题 | 先调图像预处理 |
| 综合分高但关键字段低 | 平均值掩盖了它们 | 按字段决策，不看总分 |

第二行是这类系统上线后最常见的事故来源：总分红，但偶尔在空字段上编一个看起来合理的值。

## 九、限制与结论

验收的要点只有三条：三种场景一起测（尤其是幽灵字段）、指标按路径算并单独统计关键失败、关键字段单列精确率。脚本不到 50 行，一次能跑完。

本文的限制：脚本是我写的，只用一份手造金标准测过四种情形，没有在真实文档上验证；指标定义沿用了 Dharma-AI 博客的口径，但他们的评分脚本我没有看到，实现细节可能不同；"20 到 40 份够用"是我的经验判断，没有统计依据；没有调用任何字段抽取模型，文中没有模型分数。

脚本还有两个已知的粗糙处：一是展平不为空的容器本身生成路径，所以"整张明细表没抽"这类失败在空列表上不会扣分；二是 `round` 用的是银行家舍入，`.xx5` 边界会向下取整。用之前先补这两点。

下一步建议：先拿 10 份自己的文档，把金标准按第二节的三种场景各标一遍，跑一次脚本。这一轮就能告诉你两件事：你的字段定义清不清楚，以及候选模型会不会编。
