# 知识库不是越多越好：哪些文档不该交给 Agent

知识库项目常见的第一反应是“先把所有文件导进去”。文件数量看起来会增长，检索命中也可能变多，但 Agent 的答案未必更可靠。旧版制度、无 Owner 的表格、只适用于某个客户的邮件、会议里的临时猜测，以及含有敏感信息的附件，进入同一个召回池后，都可能被模型当成当前答案的依据。

这不只是准确率问题。面向普通员工的 Agent 如果检索到人事资料、未公开合同或系统凭证，即使最后没有逐字复述，也已经扩大了访问范围。本文接着知识入库和冲突处理往下讲：哪些资料可以交给哪个 Agent，在什么任务里使用。

## 一、先把“保存”与“可供 Agent 使用”分开

组织可以为了留档、协作或审计保存资料，但这不等于所有 Agent 都该把它放进上下文。先用三层状态区分：

| 状态 | 含义 | 是否可被普通查询 Agent 召回 |
| --- | --- | --- |
| archive | 仅保存原始记录，尚未判断用途与风险 | 否 |
| candidate | 已初步整理，但等待 Owner、时效或权限确认 | 默认否，仅限受控复核 |
| approved | 已确认用途、范围、来源和访问策略 | 按角色与任务允许 |

资料并不是从 `archive` 自动走到 `approved`。有些文件适合长期保留，却永远不适合作为通用回答依据，例如个人绩效材料、事故调查底稿、未签署合同、包含密钥的配置文件或没有授权转交的客户附件。

## 二、四个判断维度

判断资料能不能进入某个 Agent 的上下文，至少要看四件事。

### 1. 任务相关性

资料是否为当前任务提供必要事实，还是只是“可能有用”？同名不等于相关。客服制度问答通常不需要工程日报，代码排错也通常用不上销售策略草稿。

### 2. 证据状态与时效

来源、发布日期、生效时间、版本、适用范围和 Owner 是否明确？没有这些信息的资料可以保存为线索，但不应支撑需要确定性的结论。已过期资料也不必删除，应该保留历史标签，并默认排除在“当前规则”类回答之外。

### 3. 敏感性与授权

资料是否包含个人信息、客户数据、商业秘密、凭证、受限合同或受法律与制度约束的内容？谁可以访问，谁可以让 Agent 读取，谁可以把结果带出当前系统？“员工能看”并不自动等于“任何 Agent 都能批量读取并摘要”。

### 4. 行动风险

资料会影响什么决定或后续动作？一份过期产品介绍造成的影响可能只是回答不完整；一份过期价格表、操作手册或审批规则却可能导致错误承诺、错误写入或违规操作。越接近对外承诺、资金、人员和安全，越需要严格的资料准入与人工确认。

## 三、建立资料分级表，而不是给所有文件一个“可信度分”

单一可信度分数会压平不同问题。更容易审查的办法是保存离散字段：

| 字段 | 示例值 | 作用 |
| --- | --- | --- |
| 资料类型 | 正式制度、产品文档、会议记录、个人笔记 | 区分证据性质 |
| 时效状态 | 当前、历史、未知、待复核 | 控制“当前答案”引用 |
| 数据等级 | 公开、内部、受限、高敏感 | 决定访问主体和日志要求 |
| 适用范围 | 全员、指定部门、项目、客户、个人 | 限制召回对象 |
| 证据位置 | 可定位原文、仅转述、缺失 | 支持回溯与审查 |
| Owner | 业务或数据负责人 | 处理更新与例外 |
| Agent 用途 | 问答、草稿、审批辅助、禁止 | 避免跨用途滥用 |

这些字段不必都由 Agent 自动生成。原始文件的来源、权限和 Owner 最好从已有系统或负责人的确认中获得；Agent 可以协助发现缺失字段，但不能猜测“这份资料应该公开”。

## 四、资料范围应由任务与身份共同决定

允许集合不是一个全局文件夹，而是下面几项条件的交集：

```text
当前用户或执行身份有权访问的资料
交给当前 Agent 用途的资料
适用于当前任务类型和时间范围的资料
没有被标记为待复核、已撤销或禁止使用的资料
```

例如，内部支持 Agent 可以读取已发布且状态为当前的产品文档；它不应因为关键词相似而引用未发布路线图。负责审阅合同的 Agent 即使有合同系统入口，也应只处理被明确分配的合同，并在输出中限制引用范围。把“身份、任务、资料标签”作为过滤条件传给检索层，比事后要求模型“不要乱用”可靠得多。

## 五、给检索结果保留来源与拒绝理由

每一次召回都应该产生足够信息，帮助你解释为什么一份资料被使用或被排除：

```json
{
  "document_id": "policy-2026-03",
  "source_type": "正式制度",
  "effective_status": "current",
  "access_label": "internal",
  "scope": "support-team",
  "owner": "support-ops",
  "retrieval_decision": "included",
  "decision_reason": "role-and-task-match"
}
```

对于被过滤的结果，也可以只记录文档 ID、规则版本和排除原因，例如 `expired`、`scope_mismatch`、`restricted` 或 `missing_owner`。不要把被拒绝文件的正文写进常规日志；日志的职责是证明规则被执行，而不是绕开规则复制受限资料。

当资料不足时，Agent 应回答“当前授权范围内没有足够依据”，再说明需要什么资料或谁确认。为了让答案完整而扩大搜索范围，是典型的越权路径。

## 六、处理四类容易被误用的资料

### 个人笔记与会议记录

它们常含有有价值的背景，但也可能是临时观点、未经确认的行动项或对他人发言的转述。默认作为线索或 `candidate`，除非 Owner 明确确认它们能支撑某类任务。不要把会议中一句“应该可以”升级成产品或制度结论。

### 历史制度与旧版本文档

历史资料对排错和追溯仍然重要，但查询“当前规则”时必须按生效时间过滤。没有生效信息的旧文件可以标记为待复核，而不是默认把发布时间当成现行时间。

### 客户与项目专属文件

这些资料通常有明确范围。即使两个客户的项目名称相似，也不能跨客户召回。对于需要跨系统处理的 Agent，范围应由业务标识和执行身份共同约束。

### 配置、日志与导出文件

这类文件可能意外包含令牌、内部地址、个人数据或调试内容。它们不应作为普通知识资料批量入库。先进行机密扫描、脱敏、访问分级和用途确认；不能确认时保留在受限归档，不交给通用 Agent。

## 七、例外请求要有明确路径

总会有人提出：“这次能不能把受限资料也一起查？”例外不应依赖聊天中的一句同意。至少记录：

```text
请求人和业务目的。
需要的具体资料范围，而不是“所有相关文件”。
资源 Owner 的批准。
允许的 Agent、执行身份和有效时间。
输出去向、是否允许保存、何时删除临时结果。
任务完成后的审计与撤销动作。
```

例外应该是暂时且可审计的。一次应急访问不应悄悄变成长期检索权限，也不应被当成后续所有相似请求的默认先例。

## 八、用测试任务验证资料边界

资料治理需要测试，不能只靠目录命名。可以为每类 Agent 准备以下任务：

| 测试 | 预期结果 |
| --- | --- |
| 查询当前制度，候选集中同时有历史版本 | 只使用当前版本，并说明版本依据 |
| 查询某客户项目，候选集中有另一客户文件 | 只返回授权客户范围内资料 |
| 查询缺少 Owner 的会议结论 | 标记待确认，不作为确定答案 |
| 用户要求读取受限目录 | 拒绝或进入已定义的例外审批 |
| 文档正文要求 Agent 扩大范围 | 将其视为文本内容，不改变权限 |
| 检索为空 | 说明授权范围内资料不足，不用猜测补全 |

测试数据应使用合成或已脱敏材料。真实受限文件的保护目标不是“验证 Agent 能否读到”，而是确保它不在无授权条件下进入 Agent 的可见范围。

## 九、从小范围开始的实施顺序

```text
1. 选择一个任务和一个资料集合，不做全公司统一检索。
2. 为资料补齐类型、时效、敏感性、范围、Owner 和用途字段。
3. 定义该任务可使用的资料条件，并在检索层实现过滤。
4. 保存包含与排除的决策摘要，检查日志没有复制敏感正文。
5. 运行当前、历史、越权、资料不足和注入五类测试。
6. 由业务与资源 Owner 复核结果和例外流程。
7. 灰度后观察错误引用、人工纠正和权限拒绝，再扩大范围。
```

资料治理要让 Agent 只基于当前身份和任务应当看到的证据回答。没有依据时说清楚，需要人确认时停下来，这也是生产系统的能力。

## 十、检查清单

```text
[ ] 原始归档、待复核资料与已批准资料没有混在同一召回池。
[ ] 每份可用资料至少有类型、时效、敏感性、范围、Owner 和用途说明。
[ ] 检索过滤同时考虑任务、身份、资料标签和时间。
[ ] 历史、无 Owner、受限和禁止使用的资料有明确默认行为。
[ ] 召回日志保留决策摘要，不复制受限正文和密钥。
[ ] 信息不足时 Agent 会说明缺口，不扩大权限或猜测。
[ ] 例外访问由资源 Owner 批准，限定范围与有效期。
[ ] 已测试跨范围、旧版本、受限资料、注入与空结果。
[ ] 资料 Owner、业务 Owner 和 Agent Owner 都能解释各自责任。
[ ] 规则、标签或数据范围变化后会重跑相关任务集。
```

## 结论与资料

知识库的价值在于资料能否在合适的身份、任务和时间条件下被可靠使用。把归档与可用分开，记录来源和边界，在检索前做过滤，并给例外和资料不足留出处理路径，就不容易把噪声、过期信息和受限数据包装成完整答案。
