# 迁移 GPT-5.6 时怎样精简提示词又不损失约束

很多生产提示词不是一次设计出来的，而是在一次次故障后补出来的。模型漏了证据，就加一条“必须引用”；工具调用越权，就在三个位置重复“先询问”；回答太长，再叠一条“务必简短”。迁移到 GPT-5.6 后，这些旧补丁可能互相冲突，让模型在安全操作前频繁停下，也可能把本来需要完整证据的回答压得过短。

精简提示词不是把长提示改成短提示，更不是一次删掉所有规则。本文给出一套可回滚的减法流程：先识别不能丢的业务合同，再按组删除重复内容，用固定任务复测，最后把响应长度、语气和审批边界放到正确的位置。

## 一、旧提示词为什么会在迁移后变成负担

提示词随系统增长，常见的不是单纯“太长”，而是四种结构问题。

第一，规则重复。同一条“不要修改文件”可能出现在角色、工具说明、工作流和结尾提醒中。模型看到的不是更强约束，而是多个可能略有差异的版本。

第二，抽象要求过多。“专业、自然、友好、简洁、详细、全面”放在一起没有明确优先级。遇到复杂任务时，模型不知道应该保留证据还是优先缩短回答。

第三，工具暴露过量。一个只需要读取文档的任务，却同时提供部署、删除、支付和消息发送工具。模型不仅要处理更长的工具描述，还要判断大量不相关选择。

第四，历史补丁失去原因。团队记得“必须保留这句话”，却不知道它当初修复了什么失败。迁移时无法判断这条规则仍然必要，还是已经被 API 参数、权限层或新模型行为替代。

OpenAI 当前的 [GPT-5.6 提示指南](https://developers.openai.com/api/docs/guides/latest-model?model=gpt-5.6#prompting-best-practices)建议删除重复指令和示例、简化工具描述，并一次只移除一组内容后重跑相同评测。官方给出的内部编码智能体样本显示，精简配置在那组评测中同时改善了分数、token 和成本，但文档也明确说明结果因工作负载而异。业务迁移只能把它当作实验方向，不能照抄成固定收益承诺。

## 二、先标记必须保留的约束

开始删减前，把现有提示词拆成不同类型，并给每条规则写出存在理由。

| 类型 | 例子 | 迁移处理 |
| --- | --- | --- |
| 业务目标 | 输出数据库迁移审查报告 | 必须保留，写成可验收结果 |
| 硬性约束 | 不得执行外部写入 | 必须保留，集中表达一次 |
| 成功标准 | 每个风险引用方案步骤 | 必须保留，可由评测验证 |
| 输出合同 | 返回固定 JSON 字段 | 必须保留，并由 Schema 校验 |
| 风格偏好 | 直接给结论，省略寒暄 | 保留有效部分，避免抽象堆叠 |
| 示例 | 一个正确报告样例 | 只有修复可测差距时保留 |
| 历史补丁 | “再次提醒不要……” | 找到原因后合并或删除 |
| 工具说明 | 所有后台工具完整手册 | 只暴露当前任务相关部分 |

不能丢的不是每一句旧文字，而是它背后的行为合同。例如旧提示词在四处写了“删除前必须询问”，真正需要保留的是：哪些动作属于破坏性操作、何时必须确认、哪些读取和本地验证可以直接执行。把合同写清楚一次，比重复四遍模糊提醒更稳定。

为每条关键规则附上一个测试。若规则要求引用证据，测试就检查每个结论是否关联输入材料；若规则禁止外部写入，测试就检查模拟执行日志中没有写操作。没有对应测试的规则很容易在删减时靠争论决定，最后又被加回去。

## 三、一次只删除一组内容

不要把精简当作一次重写。先在旧提示词和工具集上建立基线，然后按组做实验：

```text
第 0 轮：旧提示词、旧工具集，冻结结果
第 1 轮：合并重复指令，不改示例和工具
第 2 轮：删除无测量依据的风格形容词
第 3 轮：移除与任务无关的工具及说明
第 4 轮：逐个删除不能修复当前差距的示例
第 5 轮：把长度默认值移到 text.verbosity
```

每轮只改变一组，运行同一批正常案例、边界案例和历史失败案例。记录任务成功、关键事实、结构合法性、授权行为、token、延迟和人工修改量。某一轮出现回归时，可以准确知道应恢复哪一组，而不是把整份旧提示词全部复制回来。

下面是一个迁移前的典型片段：

```text
你是一个专业、友好、严谨、全面、简洁的技术助手。
任何时候都必须先询问用户，不得擅自采取行动。
一定要保持简短，但必须详细解释所有步骤。
再次提醒：修改任何内容前都要询问。
请主动完成任务，不要中途停下。
```

它同时要求“任何时候先问”和“主动完成”，也同时要求“简短”和“详细解释所有步骤”。精简后可以改成：

```text
回答、解释、审查、诊断或规划请求：读取相关材料并报告结果；除非请求同时要求修改，否则不实施更改。

修改、构建或修复请求：完成请求范围内的本地更改，并直接运行相关的非破坏性验证。

外部写入、破坏性操作、购买或实质扩大范围：执行前要求确认。

回答先给结论，保留支持结论所需的证据、重大限制和下一步；优先删除重复背景与寒暄。
```

后一版不是为了追求短，而是把授权、行为和输出优先级变成可判断的条件。

示例也要按同样方法处理。保留示例的理由应该是它纠正了稳定出现的差距，例如模型总把风险等级与证据混在一个字段，或者某种文体必须遵守固定格式。若示例只是重复规则，换个任务就失效，可以先移除。确实需要保留时，只展示决定性部分，并同时说明输入条件与错误边界，避免模型把案例中的姓名、数字和结论当成每次都要复用的内容。

可以做一次反向验证：删除示例后，模型仍能在边界样本上满足结构与质量要求，说明规则已经足够清楚；删除后只在某一类任务回归，就把该示例放进对应任务模板，不要重新塞回所有请求共享的系统提示。这样既保留教学价值，也避免少数案例长期占用每次调用的上下文。

## 四、把自主性和审批边界集中表达

GPT-5.6 更能从上下文推断用户目标，并能持续执行多步骤任务。提示词因此更需要清楚说明授权边界，而不是在每个步骤前加一句“先问我”。

可以把动作分成三层：

- 只读分析：读取文件、查看日志、比较配置、报告结论；
- 范围内本地工作：用户明确要求修改后，编辑相关文件并运行非破坏性测试；
- 外部或高影响动作：发消息、上传文件、删除数据、购买、改权限、扩大范围。

前两层在授权范围内可以继续，第三层在动作发生前确认。还要写清哪些动作看似本地却有外部影响，例如执行部署脚本、推送分支、提交表单。规则集中在一个位置，工具说明只补充自身的输入、输出、错误和副作用，不再重复全局审批政策。

验证时专门构造相邻案例：用户让模型“分析故障”时不应修改；用户让模型“修复并测试”时不应在每次读取前停下；用户让模型“修好后发布”时，本地修复可以完成，但外部发布前应确认。只有同时通过这些案例，边界才算写清楚。

## 五、用 text.verbosity 管默认长度

GPT-5.6 默认比 GPT-5.5 更简洁。旧提示词里的“保持简短”“不要展开”可能让迁移后的回答丢掉证据或必要步骤。官方建议使用 `text.verbosity` 设置请求的默认详细程度，再在提示词中写任务特有的长度和内容要求。

```python
response = client.responses.create(
    model="gpt-5.6-terra",
    input=task,
    text={"verbosity": "medium"},
)
```

当前支持 `low`、`medium` 和 `high`。默认级别只控制整体详细程度，不替代输出合同。一个简短风险审查仍应明确要求保留风险、证据、影响、缓解措施和重大限制；可以省略的是背景铺垫、重复解释和无关示例。

语气也不要只写“友好、有同理心”。更可执行的规则是：直接陈述答案；用户报告问题时，先确认具体问题再给下一步；只在相关时使用安抚；不写泛泛赞美和多余结束语。通过可观察的写作选择定义语气，才能在回归评测中判断是否执行。

## 六、回归评测、失败信号和恢复

精简后的提示词至少要通过四类评测：

| 评测 | 检查内容 |
| --- | --- |
| 任务完成 | 目标、必填项、结构和证据是否齐全 |
| 边界执行 | 是否在该继续时继续、该确认时确认 |
| 工具行为 | 是否只选相关工具，参数和停止条件是否正确 |
| 表达质量 | 是否直接、无重复，同时保留必要限制 |

还要记录输入 token、总 token、p95 延迟、工具调用次数、人工返工时间和失败原因。token 减少但任务失败，不是优化；输出更短却需要人工补全，也不是优化。

出现以下信号时恢复上一版：关键事实或证据遗漏、结构错误增加、危险动作未确认、正常本地工作频繁停顿、工具选择错误、人工修改量明显增加。恢复后只把造成回归的那组规则加回，并重写成更清楚的单条合同，不要把旧提示词整体覆盖回来。

提示词和评测集都要有版本。每次删减记录假设、改动、样本、结果和决定。新故障出现时，先判断是样本缺失、规则不清、工具接口问题还是模型能力问题，不要下意识继续往系统提示末尾追加一句。

## 七、限制与结论

提示词减法的目标是减少冲突和无关负担，不是追求最短字符数。业务目标、事实边界、授权规则、成功标准和输出合同必须保留；重复提醒、无测量依据的形容词、不相关工具和失去作用的示例才是优先删除对象。

最稳妥的迁移方式，是一次只删一组，用同一批任务复测，并保存可回滚版本。随着任务和模型变化，提示词应继续维护，但每一条新增规则都要说明修复了什么问题、如何验证、何时可以删除。这样得到的是可演进的行为合同，而不是越积越长的历史补丁。
