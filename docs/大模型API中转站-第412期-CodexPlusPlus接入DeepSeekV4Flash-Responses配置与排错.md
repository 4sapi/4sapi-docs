# Codex++ 接入 DeepSeek V4-Flash：Responses 配置与排错

很多旧教程会告诉你：DeepSeek 接 Codex++ 时，上游协议必须选 Chat Completions，选 Responses 就会 404。这个结论只适用于 DeepSeek 尚未提供 Responses 端点的旧阶段。现在真正需要确认的是：当前 DeepSeek 模型是否支持 Codex 所需的 Responses 协议，Codex++ 是否把 Base URL 和后缀拼接正确，以及桌面端启动的到底是哪份配置。

本文按附件中的 Codex++ 配置流程整理，重点不是某个固定版本的按钮位置，而是把配置项、启动方式、路由证据和 Agent 验收串起来。第三方工具版本会变化，文中版本号只作为附件测试参考，使用前应先查看当前发布说明。

## 1. 先理解旧教程为什么会失效

旧教程中的“选 Chat Completions”通常来自一个真实限制：当上游没有 Responses 端点时，Codex 通过 Chat 协议发送请求，或者依靠本地代理翻译协议。

现在如果 DeepSeek 官方文档已经为当前模型提供 Responses 接入，继续照搬旧配置会造成：

```text
协议与上游端点不一致。
Codex 期待 Responses 事件，上游只返回 Chat 格式。
工具循环的字段无法解析。
流式响应的结束事件不一致。
```

因此不要把“旧教程能用”当成当前配置依据。先查 [DeepSeek 官方 Codex 接入文档](https://api-docs.deepseek.com/zh-cn/quick_start/agent_integrations/codex)，确认当前模型、Base URL 和协议，再在 Codex++ 中逐项填写。

## 2. 公共准备工作

开始前准备：

```text
Codex 桌面端已经安装并能以默认配置启动。
准备 DeepSeek API Key。
准备一个无敏感数据、可回滚的测试仓库。
记录当前 Codex 配置和原有供应商，必要时备份 ~/.codex。
确认当前 Codex++ 版本和系统平台。
```

先保持 Codex 桌面端的默认状态，不要同时运行官方脚本、CC Switch 和 Codex++ 去修改同一份配置。多个工具同时写用户级配置，会让你无法判断最终生效的是哪一份设置。

OpenAI 官方配置参考说明，Codex 的用户级配置位于 `~/.codex/config.toml`；模型提供方属于用户级机器配置，项目级配置不能覆盖它。配置发生变化后，需要让实际使用的客户端重新读取文件，不能只看第三方工具提示“保存成功”。

## 3. 在 Codex++ 中创建供应商

按照当前界面中相近的菜单完成：

```text
1. 安装并打开 Codex++。
2. 进入“管理工具 / 供应商管理”。
3. 新增供应商。
4. 接入模式选择纯 API。
5. Base URL 填入 https://api.deepseek.com。
6. 模型填入 deepseek-v4-flash。
7. 上游协议选择 Responses。
8. 填写 API Key，保存后测试连接。
9. 按工具提示启用页面增强或相关插件入口。
10. 使用 Codex++ 提供的桌面图标启动 Codex。
```

这里最容易错的是 Base URL。不要在没有看到工具要求的情况下自行拼接 `/v1`、`/responses` 或完整接口路径。第三方工具可能会根据上游协议自动拼接路径，多写一层就会出现重复路径和 404。以工具的“测试连接”显示的实际请求地址为准。

附件测试使用了 Codex++ v1.2.44，但版本号会变化。不要把某个界面的菜单路径当成稳定 API；如果新版本把“页面增强”改成其他名称，先确认它解决的是哪一个权限或入口问题，再决定是否开启。

## 4. 如果使用兼容网关

如果通过 4SAPI 这类网关作为模型入口，Codex++ 的配置只能说明客户端愿意按 Responses 发请求，不能证明网关已经正确映射 DeepSeek 模型。需要单独确认：

```text
网关 Base URL 是否需要 /v1 或其他路径。
网关是否支持 Responses，而不是只兼容 Chat Completions。
deepseek-v4-flash 是否映射到实际可用模型。
流式事件和结束事件是否被原样转发。
工具调用、错误码和 usage 字段是否保持可解析。
```

不要把直连 DeepSeek 的 Base URL 和网关 Base URL 混用。遇到 404 时，先用测试工具记录实际请求地址和响应，再决定是路径、模型映射还是协议问题。

## 5. 配置成功的证据是什么

### 证据一：连接测试通过

连接测试只能证明某个请求得到响应。检查它是否显示实际 URL、模型、协议和响应状态；如果界面只显示“成功”，仍然需要继续验证。

### 证据二：模型路由可追踪

桌面端模型选择器可能显示模型名，也可能显示“自定义”。两种显示都不能单独证明路由。更可靠的证据包括：

```text
上游平台的用量记录出现请求。
请求日志中的模型和提供方正确。
Codex 启动信息显示目标提供方。
测试任务的响应元数据符合预期。
```

不要直接问模型“你是什么模型”。Codex 的系统提示词可能要求模型以 Codex 身份回答，这个回答和实际网络路由不是一回事。

### 证据三：完成一个连续工具任务

不要只发送“你好”。在测试仓库中执行：

```text
先搜索项目入口，再读取一个文件，最后修改 README 中的一行说明。
修改前说明计划，完成后运行一个已有检查，不要访问仓库外的敏感文件。
```

你要观察的是：模型能否正确选择工具，能否处理工具返回，能否连续完成多步，失败后能否停止或修正，以及 Codex++ 的工具入口是否真的参与了请求。

## 6. 不要把“文本输入限制”理解成“不能处理文件”

模型目录可能声明当前模型只接受文本输入。这通常意味着模型本身不能把截图、设计稿或照片当成视觉输入理解，并不等于 Codex 不能操作文件。

文件处理可能由 Codex 的命令行工具完成：识别文件、调用本地转换器、运行 Python 统计或读取文本结果，模型负责指挥这些工具。两条路径要分开验证：

```text
图片视觉理解：需要模型支持图片输入。
文件转换和统计：可能由本地命令行工具完成。
```

因此，拖入一个表格并让 Codex 调用本地工具，不足以证明模型支持表格视觉理解；同样，图片无法被模型直接分析，也不代表本地文件工具全部不可用。

## 7. MCP 和 Skills 要看真实日志

第三方接入后，模型能否看到 Codex 的全部工具不能只听模型口头描述。尤其是 MCP 场景，要区分三层：

```text
MCP 连接是否启动。
工具是否进入模型可见的工具清单。
模型是否真正发起了工具调用并拿到结果。
```

一个 MCP server 能返回资源模板，不代表某个工具已经被模型调用。模型也可能自己写脚本连接 stdio server，最终得到正确结果，但那不是 Codex 原生工具调用链。验证时应查看会话日志、工具事件和实际命令，而不是只看最终回答。

Skills 也应检查当前模型目录和客户端是否注入了技能说明。配置里出现 Skills 入口，不等于模型一定收到了完整的技能指引。先用一个无副作用的技能任务查看加载日志，再判断问题来自模型目录、客户端还是第三方工具。

## 8. 常见报错速查

| 现象 | 优先排查 |
| --- | --- |
| 404 | Base URL 是否多拼 `/v1` 或完整路径，上游协议是否选错 |
| 普通请求成功但工具循环失败 | Responses 事件、工具 schema、后续结果回传是否兼容 |
| 一直加载 | API Key、余额、网络、超时和流式结束事件 |
| 模型列表没有 DeepSeek | 模型目录未加载、客户端未重启或提供方未启用 |
| 显示“自定义” | 不要先判定失败，用日志或上游用量确认 |
| MCP 工具没有被调用 | 工具是否进入模型清单，是否实际产生工具事件 |
| 图片任务失败 | 当前模型可能只有文本输入，区分视觉输入和本地文件处理 |
| 只回答“我是 Codex” | 不用身份回答验证路由，改查请求日志和上游记录 |

## 9. 回滚方法

第三方工具接入失败时，优先回到已知可用配置：

```text
退出 Codex++ 和 Codex 桌面端。
恢复 ~/.codex 的配置备份，或关闭第三方提供方。
重新启动原来的 Codex 入口。
执行一次只读任务确认原模型、MCP 和项目设置正常。
```

不要为了清理第三方配置直接删除整个 `.codex` 目录，也不要只恢复模型名却忘记恢复认证、模型目录和 profile。回滚之后必须重新启动客户端，已经打开的会话可能仍然持有旧配置。

## 10. 一份可复制的 Agent 接入验收 Prompt

```text
请在一个测试仓库中验收当前 Codex 的自定义模型接入。

先不要修改业务代码，按顺序执行：
1. 说明当前用户级 Codex 配置、模型、提供方和协议来源，但不要输出 API Key。
2. 只读检查项目入口、测试命令和一个小文件。
3. 执行一个需要连续工具调用的安全任务：搜索、读取、修改 README 一行并运行检查。
4. 记录每一步使用的工具、返回状态和最终结果。
5. 检查流式响应是否正常结束，失败时是否能识别失败状态。
6. 如果配置了 MCP，区分连接建立、工具可见和真实工具调用，并引用日志证据。
7. 如果任务失败，判断问题更可能来自模型、协议、Base URL、工具清单、网络还是权限。
8. 不要因为最终文字看起来正确，就声称模型或 MCP 已经按预期工作。
```

## 11. 按请求链路分层排错

遇到“能连上但不能干活”，不要继续随机修改配置。可以沿请求链路从外到内排查：

```text
第一层：Codex++ 是否启动了正确的 Codex 进程？
第二层：客户端是否读取了预期的用户级 config.toml？
第三层：Base URL 是否被重复拼接或被工具改写？
第四层：上游是否识别 deepseek-v4-flash 和 Responses 协议？
第五层：响应事件是否被 Codex++ 正确解析和收口？
第六层：工具声明是否进入模型可见清单？
第七层：工具结果是否被回传到下一轮模型请求？
第八层：文件权限、网络、Key 和余额是否允许任务继续？
```

每一层都要留下一个证据。例如，连接测试能证明上游返回响应，但不能证明工具清单正确；模型选择器能证明界面加载了提供方，但不能证明实际请求没有被另一个进程接管；最终回答能证明任务产生了结果，但不能证明 MCP 工具是由模型原生调用的。

## 12. 设计三个最小回归任务

接入后不要只使用一个综合任务。用三个短任务分离问题来源：

### 文本任务

```text
读取一个小文件，提取其中的三个标题，不修改任何内容。
```

它主要验证模型路由、文本输出、文件读取和基本工具调用。

### 补丁任务

```text
在测试仓库 README 最后一行增加“接入测试完成”，先展示补丁，确认后再写入，并运行一个格式检查。
```

它验证补丁工具、写入权限、审批和工具结果回传。任务必须在测试仓库中执行，避免把首次验证直接放到生产项目。

### 失败任务

```text
读取一个不存在的文件，不要自行创建它；说明失败原因和下一步建议。
```

它验证模型是否能识别工具错误、停止无意义重试，并把失败状态交给用户。一个只能在成功路径上工作的接入，不适合直接扩大权限。

## 13. MCP 验收要区分三种“通了”

MCP 问题不能用一句“我已经调用了工具”结束。至少区分：

| 层次 | 要验证什么 | 证据 |
| --- | --- | --- |
| 连接层 | server 启动、握手和资源发现 | 启动日志、连接事件 |
| 清单层 | 工具是否进入模型可见工具列表 | 请求中的工具声明 |
| 执行层 | 模型是否发起调用并收到结果 | tool call、返回值和后续请求 |

如果只有连接层通过，模型仍可能看不到工具；如果最终结果正确，也可能是模型自己写脚本访问本地进程，而不是走 Codex 原生 MCP 链路。重度依赖 MCP 的项目必须保存一次真实工具调用日志，并在升级模型或第三方工具后重新验证。

## 14. 文件、图片与 Skills 的边界

建议把能力写成一张边界表：

| 任务 | 可能使用的路径 | 不能直接推出的结论 |
| --- | --- | --- |
| 读取文本文件 | Codex 文件工具或命令行 | 不代表模型支持图片 |
| 统计表格 | 转换器、Python、命令行 | 不代表模型理解表格视觉布局 |
| 查看截图 | 模型图片输入能力 | 文本模型通常不能直接理解像素 |
| 调用 MCP | Codex 工具清单和 MCP 链路 | 连接成功不代表模型可见 |
| 使用 Skills | 客户端加载说明和模型目录 | 有入口不代表指引已注入 |

这张表能避免把“系统最终完成了任务”误写成“模型原生支持所有输入”。在排错报告中，要写清哪一层完成了工作：模型、Codex 工具、本地命令、第三方桥接还是人工操作。

## 16. 结论与限制

Codex++ 接入 DeepSeek 的关键不是照搬旧教程选择 Chat，而是根据当前上游能力选择 Responses，并确保 Base URL、模型、工具和流式事件都在同一条兼容链路上。配置完成后，模型选择器、连接测试和一句问候都不够，必须通过真实的连续工具任务和日志验证。

第三方工具会改变配置管理、桌面启动和插件入口，也可能增加模型目录或协议适配层。遇到问题时先缩小变量：直连还是网关、模型还是协议、文本还是工具、连接还是可见清单。每次只改一层，才能把排错结果变成下一次可复用的配置经验。
