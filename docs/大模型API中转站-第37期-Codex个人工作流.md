# 【大模型API中转站】第37期 Codex个人工作流 | 4个高频场景

本文是【大模型API中转站】系列的第37篇。本系列致力于用最低的成本、最清晰的方法，帮你打通多模型API的任督二脉。建议先收藏，随用随查。

很多人第一次用 Codex，都会自然地把它放进“写代码”这个盒子里。

这当然没错。Codex 最强的能力之一，就是读项目、改文件、跑命令、看报错、再修复。

但如果只用它写代码，其实有点亏。

我现在更愿意把 Codex 理解成一个“能进入工作现场的执行入口”。它不只是回答问题，而是可以读取文件、调用 Skill、生成页面、整理资料、运行命令，并把结果落到本地文件或工具系统里。

这一篇先不讲团队协作，也不讲复杂业务系统，只讲个人每天都可能遇到的 4 个场景：

| 场景 | 传统做法 | Codex 做法 |
| --- | --- | --- |
| 配图 | 找模板、找设计工具、反复改图 | 先读文章，再生成可修改的 HTML 配图或调用 Skill |
| 长文转 Slides | 手动摘重点、自己做 PPT | 先抽主线，再生成 HTML Slides |
| 微信读书摘录 | 记得看过，但找不到在哪 | 按主题检索划线和摘录，变成写作素材 |
| 磁盘整理 | 看哪个目录大，却不知道能不能删 | 先扫描、归类、判断风险，再由人确认清理 |

这 4 件事共同的特点是：它们不难，但碎、烦、容易拖延。

Codex 的价值不是替你“想一个答案”，而是把这些琐碎步骤变成一条可重复的流程。

## 1. 配图：先做信息结构，再考虑图片模型

很多文章配图不需要一上来就调用图片模型。

如果目标是解释概念、呈现流程、做方案对比，HTML、CSS、表格、线条和简单图形反而更稳。因为这种图的重点不是“好看”，而是让读者更快看懂。

一个更实用的流程是：

```text
文章全文
  -> Codex 判断哪里适合配图
  -> 先输出配图结构草案
  -> 人确认图的目的和信息层级
  -> Codex 生成 HTML 页面
  -> 浏览器截图或导出 PNG
```

好处很明显：图里的文字、颜色、布局和比例都可以继续改，不需要每次从头生成整张图。

适合做成信息型配图的内容：

| 内容类型 | 推荐图形 |
| --- | --- |
| 工作方法 | 步骤图、闭环图、清单图 |
| 工具对比 | 对照表、象限图、雷达图 |
| 系统关系 | 架构图、模块图、流程图 |
| 项目复盘 | 时间线、指标卡、漏斗图 |
| 观点总结 | 金字塔、三段式卡片、因果链 |

可以这样提示 Codex：

```markdown
请通读下面这篇文章，判断哪些位置适合做信息型配图。

要求：
1. 先列出 3 个候选配图点。
2. 每个点说明配图目的：解释概念、呈现流程、对比方案或总结观点。
3. 先给结构草案，不要直接出最终图。
4. 确认后生成单文件 HTML，适合公众号正文插入。
5. 图中文字要少，优先让结构说话。
```

如果需要手绘风流程图，可以先让 Codex 拆节点和关系，再调用 Excalidraw Diagram Skill。

Skill 地址：

[https://github.com/coleam00/excalidraw-diagram-skill](https://github.com/coleam00/excalidraw-diagram-skill)

更稳的提示词是：

```markdown
请把下面这段内容拆成适合画成 Excalidraw 流程图的结构。

请输出：
1. 节点列表
2. 节点之间的关系
3. 推荐布局：从左到右、从上到下、循环或分层
4. 哪些信息不适合放进图里
5. 一版极简图结构

先不要生成最终图片，等我确认结构。
```

如果是 PPT 章节页、过渡页或抽象概念解释页，可以用更强手绘风格的插图 Skill。

Skill 地址：

[https://github.com/helloianneo/ian-xiaohei-illustrations/tree/main](https://github.com/helloianneo/ian-xiaohei-illustrations/tree/main)

这里的关键是：不要只说“画一张好看的图”，而要描述场景。

```markdown
请把“Codex 从编程工具变成工作流入口”转换成一张适合 PPT 章节页的手绘风插图。

要求：
1. 画面里要有具体工作场景。
2. 可以出现电脑、文件、表格、流程箭头、工具箱等元素。
3. 表达“一个入口连接多个工作任务”。
4. 风格轻松、有故事感，但不要幼稚。
5. 先输出画面布局和提示词，不要直接生成。
```

配图的成本控制也很重要。不要让高价图片模型承担所有试错。

| 步骤 | 推荐模型策略 |
| --- | --- |
| 找配图点 | 低成本或中等文本模型 |
| 设计结构 | 中等模型 |
| 生成 HTML | 代码模型 |
| 生成最终插图 | 图片模型 |
| 检查文字和遮挡 | 视觉模型或人工审图 |

如果通过 4SAPI 统一模型入口，就可以把“文章分析、HTML 生成、图片生成”拆到不同模型上，既能省钱，也方便看每篇文章到底花了多少成本。

## 2. 长文转 Slides：给大脑做二次索引

长文阅读最难的地方，不是读完，而是过几天之后还能想起来。

很多深度文章第一次读时很有感觉，但如果没有二次整理，很快就只剩一个模糊印象。

我更推荐把长文转成一份 HTML Slides。它不一定要像正式演讲 PPT 那样精致，重点是重新整理文章脉络：

```text
作者在回答什么问题？
核心观点是什么？
关键论据有哪些？
哪些例子最有代表性？
哪些假设没有明说？
我能把它用在哪些场景？
```

Skill 地址：

[https://github.com/gainubi/note-slides](https://github.com/gainubi/note-slides)

一个实用流程：

```text
长文 / PDF / 访谈稿
  -> Codex 抽取主线
  -> 生成 8-10 页 HTML Slides
  -> 人工补充自己的理解
  -> 保存到知识库
```

可复制指令：

```markdown
请把下面这篇长文整理成一份 10 页左右的 HTML Slides。

要求：
1. 不要逐段摘要，要抓文章主线。
2. 第 1 页写一句话结论。
3. 第 2-3 页讲背景和问题。
4. 第 4-7 页讲核心观点和关键论据。
5. 第 8 页讲作者的隐含假设。
6. 第 9 页讲我可以如何应用。
7. 第 10 页列出 5 个值得继续追问的问题。
8. 每页只保留少量文字，适合二次回顾。
```

如果是技术文章，可以补一句：

```markdown
如果文章涉及架构、流程或对比，请优先生成图表页，不要堆文字。
```

这类任务也适合用 4SAPI 控成本：先用便宜模型做章节切分和初步摘要，再用更强模型提炼观点和设计页面结构。不要把整篇长文从头到尾都交给最贵模型。

## 3. 微信读书摘录：让读过的内容重新可调用

写文章时经常会遇到一种情况：

```text
我记得某本书里有个观点特别适合这里，
但就是想不起来在哪一章。
```

以前只能自己翻。接入微信读书或整理本地读书摘录后，Codex 可以把“读过但沉睡的内容”重新调出来。

尤其是工具书、商业书、心理学、管理学、技术随笔这类内容，并不一定要从第一页读到最后一页。很多有价值的观点本来就集中在少数章节和少数段落里。

热门划线也很有参考价值。它相当于很多读者已经帮你筛过一轮：

```text
哪些句子最容易引发共鸣
哪些观点最能代表这本书
哪些概念值得反复思考
哪些段落适合二次写作
```

可复制指令：

```markdown
请围绕“个人知识管理”这个主题，从我的读书摘录和热门划线里筛选相关内容。

请输出：
1. 相关书籍和章节
2. 每本书的核心观点
3. 可以转述的段落摘要
4. 不同作者之间的共同概念
5. 角度不同或互相冲突的观点
6. 适合写成文章的 5 个选题

要求：
不要编造书名、作者和原文。
如果需要引用原文，请标明来源，不要大段复制。
```

这个场景的价值不是让 Codex 替你读书，而是降低知识调用成本。

书里的内容没有变多，但你能更快把它们用到文章、分享、方案和决策里。

要注意两点：

| 风险 | 建议 |
| --- | --- |
| 版权 | 不要大段公开复制书中原文 |
| 准确性 | 重要观点回到原书确认，不只看模型转述 |

## 4. 磁盘整理：先判断，再删除

电脑空间不够时，很多人会直接找清理软件。

但真实问题往往不是“不知道哪个目录大”，而是“不知道这个目录能不能删”。

尤其是频繁试用 AI 工具、Agent 产品、CLI、Docker、Node、Python 环境之后，电脑里很容易留下：

```text
缓存目录
日志文件
模型缓存
插件目录
包管理缓存
已卸载软件残留
Docker 镜像和 volume
```

Codex 适合做这件事，是因为它可以帮你把目录和风险解释清楚。

建议流程是：

```text
第 1 轮：扫描目录，只列清单
第 2 轮：按工具归类
第 3 轮：判断缓存、配置、项目文件和高风险文件
第 4 轮：人确认可清理项
第 5 轮：再执行清理命令
```

不要让 Codex 一上来直接删除。

可复制指令：

```markdown
请帮我检查这台电脑里可能残留的 AI 工具、开发环境和缓存目录。

要求：
1. 只扫描并列清单，不要删除任何文件。
2. 按工具归类：Codex、Claude、Cursor、Node、Python、Docker、浏览器缓存等。
3. 标出目录大小、最近修改时间、可能用途。
4. 把清理建议分成三类：
   - 可安全删除的缓存
   - 删除前需要确认的软件残留
   - 不建议碰的配置或项目文件
5. 给出下一步人工确认清单。
```

清理建议可以按这个标准判断：

| 类型 | 建议 |
| --- | --- |
| 构建缓存、下载缓存、日志 | 通常可以清理，但先确认路径 |
| npm、pnpm、pip、conda 缓存 | 优先用官方命令清理 |
| Docker 镜像和 volume | 先确认没有重要数据 |
| AppData 配置 | 谨慎，可能包含登录状态和偏好 |
| Git 仓库、数据库文件、项目目录 | 默认不要自动删 |

这个工作流的核心原则是：Codex 做判断和整理，人做最终确认。

## 5. 小结：先从一个高频场景开始

这 4 个个人工作流，看起来不像编程，但都很适合 Codex：

```text
配图：把视觉生产变成可修改流程
长文转 Slides：把阅读变成二次索引
微信读书摘录：降低知识调用成本
磁盘整理：先判断风险，再清理空间
```

它们共同的特点是：

```text
输入材料散
处理步骤碎
人工不难但容易拖
结果最好能落成文件
```

这正是 Codex 比普通聊天工具更有价值的地方。

普通 AI 对话给你一个回答；Codex 可以读文件、跑命令、调用 Skill，并把结果落到 HTML、Markdown、PNG、清单或本地目录里。

如果你已经有 4SAPI 这类大模型API中转站，建议给个人工作流单独建一个 Key，只开放常用模型，并设置预算。这样配图、长文整理、读书摘录和磁盘分析的调用都能被统计，不会月底才发现 Token 花在了哪里。

一句话总结：

```text
不要只问 Codex 问题，要把它放进你的日常工作流里。
```
