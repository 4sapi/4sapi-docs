# 模型 API 是否降级怎么测：一套可复现的验真方法

当接口标注为某个高能力模型，实际回答却明显偏弱时，直接问“你是什么模型”几乎没有证据价值。模型可能沿用系统提示中的身份，响应里的 `model` 字段也由服务端生成。更可靠的办法，是把问题改成可测量的工程问题：这个端点在固定条件下，是否持续满足它宣称的工具调用、结构化输出、上下文处理和任务正确率；它与可信对照端点之间是否存在稳定差异。

本文方法用于发现能力降级、动态路由或模型错配的迹象，不能单凭行为测试给模型做密码学意义上的身份认证。

## 1. 先定义“掺水”具体指什么

口语里的“掺水”可能对应多种情况：

| 待验证假设 | 可观察信号 | 不能单独作为证据的内容 |
| --- | --- | --- |
| 路由到了其他模型 | 能力画像与可信对照长期偏离 | 模型自报身份 |
| 高峰期动态降级 | 同一时段正确率、格式率明显变化 | 一次回答变差 |
| 上下文被截断 | 随机证据在特定位置持续丢失 | 回答风格变短 |
| 工具调用未透传 | `tools` 请求稳定返回普通文本 | 某一次未调用工具 |
| 参数或输出上限缩水 | 达到某长度后稳定截断或报错 | 单次超时 |
| 只是采样波动 | 多次结果分布重叠 | 两次措辞不同 |

测试前要选定其中一个假设。把所有异常都叫“假模型”，最后很难形成可以复核的结论。

## 2. 建立测试环境记录

每次运行至少保存：

```text
测试日期、时间和时区
供应商与 endpoint
请求中的 model 字段
完整请求参数
非敏感响应头与请求 ID
原始响应体
usage
首字节时间与总耗时
HTTP 状态码和重试次数
测试脚本版本
```

API Key、Authorization 头和用户敏感数据必须排除在公开记录之外。仅保存整理后的分数不够，因为出现异常时还需要检查原始 `tool_calls`、截断位置和错误信息。

## 3. 第一组：工具调用与 Schema 遵循

工具调用适合做客观测试，因为结果可以由程序校验。以下请求要求模型把 90 分钟换算成秒，并生成符合 Schema 的缓存参数：

```json
{
  "model": "moonshotai/Kimi-K3",
  "messages": [
    {
      "role": "user",
      "content": "给 user_123 创建缓存，内容是 {\"level\":8}，有效期90分钟。只允许通过工具完成。"
    }
  ],
  "tools": [
    {
      "type": "function",
      "function": {
        "name": "cache_set",
        "description": "创建缓存",
        "parameters": {
          "type": "object",
          "properties": {
            "key": {"type": "string", "pattern": "^user:"},
            "value": {
              "type": "object",
              "properties": {
                "level": {"type": "integer"}
              },
              "required": ["level"],
              "additionalProperties": false
            },
            "ttl": {"type": "integer", "minimum": 1}
          },
          "required": ["key", "value", "ttl"],
          "additionalProperties": false
        }
      }
    }
  ],
  "tool_choice": {
    "type": "function",
    "function": {"name": "cache_set"}
  },
  "temperature": 0
}
```

程序应检查：

```json
{
  "key": "user:user_123",
  "value": {"level": 8},
  "ttl": 5400
}
```

评分项可以直接定义为布尔值：是否返回 `tool_calls`、工具名是否正确、arguments 是否为合法 JSON、是否通过 Schema、TTL 是否为 5400。不要根据“看起来差不多”人工给分。

这个测试的前置条件是目标模型和供应商明确支持 Function Calling。若官方未声明支持，失败只能说明测试前提不成立，不能说明模型被替换。

## 4. 第二组：随机化长上下文取证

长上下文测试不要固定使用网上流传的“针尖测试”文本。每次运行时生成新的随机标识，并分别放在开头、中间和结尾：

```text
开头证据：A7Q9-K2PX
中间证据：M4TV-81CZ
结尾证据：R6WN-3JFD
```

随后要求模型只返回三个证据及其位置。测试脚本按目标供应商宣称的上下文范围逐级增加输入，并记录：

```text
请求是否被接受
三个证据是否逐字匹配
错误最先出现在哪个输入规模
遗漏是否集中在固定位置
usage 是否与请求规模一致
```

每轮都生成新的证据，避免服务端缓存、训练记忆或手工特判影响结果。增加输入时只改变填充文本长度，其他参数保持一致；否则无法判断是哪个变量导致失败。

## 5. 第三组：结构化输出与多约束任务

再准备一组不依赖主观文风的任务，例如：

```text
读取给定材料，只输出合法 JSON。
字段严格为 result、evidence、confidence。
result 必须是整数。
evidence 必须逐字引用材料。
材料不足时 confidence 必须小于 0.5。
禁止输出 Markdown。
```

程序分别检查 JSON 可解析性、字段集合、字段类型、引用是否真的存在于输入，以及置信度条件。这样的任务可以发现模型是否持续漏约束，也能区分“答案事实错误”和“输出格式错误”。

题目应由本地生成器现场组合，例如随机数字、随机规则和随机证据位置。公开 benchmark 可以作为补充，但公开题可能已进入训练材料，不能成为唯一依据。

## 6. 设计可信对照组

同一批请求至少发送到三个端点：

```text
A：待测 API
B：可信官方接口或已验证供应商
C：一个明确标注的较小模型
```

三组使用相同的用户输入、system 提示、温度、输出上限和工具 Schema。隐藏端点名称后再评分，避免人工评分者先入为主。

本文建议每个测试单元先运行 20 次，用于观察分布而不是只看单次结果。20 次是一个起步方案，不是统计学上的通用充分样本；任务方差较大或差异较小时，需要增加样本并报告置信区间。

对比指标包括：

| 指标 | 计算方式 |
| --- | --- |
| 任务正确率 | 通过全部客观断言的样本数 / 总样本数 |
| JSON 合法率 | 可成功解析的响应数 / 总响应数 |
| 工具成功率 | 工具选择、参数解析和 Schema 均通过的比例 |
| 上下文取证率 | 三个随机证据全部逐字返回的比例 |
| 截断率 | 输出因长度或异常提前结束的比例 |
| 延迟分布 | 分别记录中位数和高分位，不只报平均值 |
| 错误率 | 按 HTTP 状态码、超时和解析失败分类 |

运行测试前先写下判定门槛，测试后再临时调整门槛会放大确认偏差。

## 7. 跨时段重复，寻找动态路由迹象

如果怀疑高峰期降级，应在多个固定时段重复同一测试集，并保持请求量符合供应商限流要求。记录北京时间的同时保存 UTC 时间，便于与供应商事件和日志对齐。

需要关注的是分布变化：

- 某些时段工具调用突然从结构化参数变成普通文本；
- 长上下文只在高峰期出现集中遗漏；
- 正确率下降同时延迟分布发生明显变化；
- 相同模型 ID 在不同时间出现两组稳定的错误模式；
- 待测端点长期更接近小模型对照组，而不是可信同名模型。

这些信号支持“存在路由异常或能力不一致”的判断，但仍不能直接指出后台究竟使用了哪个模型。还要排除供应商版本更新、系统提示变化、限流、内容安全策略和客户端重试等因素。

## 8. 哪些证据强，哪些证据弱

证据强度可以这样排序：

```text
供应商可核验的模型证明或审计记录
持续、可复现的跨端点能力差异
多个正交任务上的一致异常
单项行为指纹
响应里的 model 字段
模型自报身份
```

`system_fingerprint`、`model`、usage 和请求 ID 都值得保存，但它们属于服务端返回的元数据，不能脱离供应商信任单独证明身份。响应措辞、口头禅和“自我介绍”更容易受提示词与采样影响，只适合做弱信号。

## 9. 报告结论应该怎么写

一份稳妥的报告应描述条件和观察，不直接写无法证明的后台事实。例如：

```text
在 2026-08-10 的三组测试中，待测端点在工具 Schema、
随机长上下文和结构化输出任务上的通过率持续低于可信对照。
当前结果支持“该端点能力与对照不一致”，但不能仅凭行为测试确认
其实际后台模型。需要供应商提供路由日志或模型证明继续核验。
```

同时附上脱敏原始记录、测试脚本版本、失败样本和未控制变量。只有成功案例而没有失败样本，其他人无法复查结论。

## 10. 结论与限制

检测模型 API 是否降级，重点不是设计一道“只有真模型会答”的谜题，而是建立随机化任务、客观断言、可信对照、重复样本和跨时段记录。工具调用、结构化输出和长上下文分别覆盖不同能力，组合起来比单一提示词更难被偶然结果误导。

这套方法能发现能力不一致和路由异常的迹象，不能替代供应商侧的模型证明。模型版本、系统提示、安全策略和服务配置变化也会改变结果，报告必须注明测试日期、端点、参数和限制。
