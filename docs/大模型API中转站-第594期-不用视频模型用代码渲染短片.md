# 不用视频生成模型：让编程 Agent 用代码逐帧渲染一支短片

用视频生成模型做短片，最常见的问题不是"画得不好看"，而是"控制不住"：同一个角色每个镜头长得不一样，字幕和口型对不上，想让第 12 秒的切点正好落在鼓点上几乎做不到。

另一条路线是让编程 Agent 直接写代码画画面。代码画出来的东西可以精确到帧，改一个参数就能重渲染，任何一帧都能单独复现。

开源项目 [lemo-opuscar](https://github.com/lemomo-ai/lemo-opuscar)（MIT 协议，检索 2026-10-29 时约 9,100 星）就是这条路线的一个完整样本：66 种风格，每种都附一支完全用代码做成的样片，不用视频生成，也不用素材库画面。本文只拆它的渲染流水线，说明这种做法怎么运作、适合什么、不适合什么。

## 整条流水线长什么样

项目的技术文档把整个流程画成了一张图，核心只有一句话：**时间线是唯一的事实来源**。

```
时间线（唯一事实来源）
   ├─► 画面：带 render(t) 的网页 ──► 无头 Chrome 逐帧截图 ──► video.mp4
   ├─► 配音：逐句 TTS ──► 语音识别回检 ──► 词级时间戳
   ├─► 音乐：按同一条时间线写谱（采样 + 合成）──► 分轨
   ├─► 音效：在事件时间点程序化生成
   └─► 字幕：.srt + 烧录字幕
混音（压缩、侧链压低、平衡）──► ffmpeg 封装，两遍响度标准化到 −14 LUFS ──► 成片
```

来源：[TECHNIQUE.md](https://github.com/lemomo-ai/lemo-opuscar/blob/main/TECHNIQUE.md)。

这张图里最关键的不是哪个工具，而是"所有东西读同一份数字"。画面在第几秒做什么、音乐在第几拍、字幕什么时候出现，全部从同一个时间线文件里取。

## 画面是时间的函数

每支片子是一个文件夹，里面有一个 `index.html`，这个页面只需要对外暴露几个变量：

```js
window.DUR = 54.2;                 // 片长，单位秒
window.render = (t) => { ... };    // 画出第 t 秒的那一帧，必须是确定性的
window.READY = true;               // 字体和图片都加载完后置为 true
window.EV = [{t, type, ...}];      // 可选：声音与节拍事件，给混音器用
window.TEXTS = (t) => [...];       // 可选：第 t 秒画面上所有文字，给可读性检查用
```

这就是整个渲染系统的"接口合同"。渲染器不关心页面里用的是 Canvas 2D、three.js 还是 WebGL 着色器，只管反复调用 `render(t)` 然后截图。

这个设计带来的好处很直接：

| 好处 | 原因 |
| --- | --- |
| 任意一帧可单独渲染 | `render(t)` 只依赖 t，不依赖上一帧 |
| 可以多进程并行 | 每个 worker 负责一段时间，互不干扰 |
| 改一处只重渲一段 | 不需要从头跑整条片子 |
| 结果可复现 | 同样的代码、同样的 t，永远得到同样的画面 |

## 确定性是硬约束

要让上面这些好处成立，页面代码必须严格遵守确定性规则：

| 规则 | 为什么 |
| --- | --- |
| 不用 `Date.now()` | 每次渲染时间不同，画面会变 |
| 不用不带种子的 `Math.random()` | 随机数要用固定种子的生成器（项目里提供了 `mulberry` 和 `hash`） |
| 不保留上一帧的状态 | 否则并行渲染时各 worker 结果不一致 |
| 跟随主体的特效走同一个坐标变换函数 | 镜头一动，手写的屏幕坐标就会错位 |

第三条最容易被违反。写动画的直觉是"每帧在上一帧的基础上加一点"，但在这套系统里，粒子、角色、笔触都必须能从 t 直接算出来。比如一个下落的物体，要写成 `y = y0 + v*t + 0.5*g*t*t`，而不是每帧 `y += v`。

## 为什么渲染能快

逐帧截图听起来很慢。文档给出了三个提速手段：

| 手段 | 效果 |
| --- | --- |
| 截 JPEG 而不是 PNG | 编码快、文件小 |
| 每个 worker 一个浏览器实例 | 多进程并行，互不抢资源 |
| 胶片颗粒放到 ffmpeg 里加 | 页面里画颗粒会让每帧都无法压缩，拖慢整条管线 |

第三条值得单独记住。颗粒是随机噪点，在页面里画就意味着每一帧都完全不同，截图、编码、写盘都会变慢。放到最后由 ffmpeg 统一叠加，前面的流程就能保持轻量。

## 一条时间线驱动所有东西

段落、速度、节拍、关键点，全部写在一个 `timeline.js` 里：

```js
export const SECS = [{ id: 'chase', t: 12.0, bpm: 144, beats: 12 }, ...];
export const HIT  = { pratfall: ['chase', 6], ... };   // 第几段的第几拍
```

导出成 JSON 之后，配乐、混音、字幕、检查脚本都读这份数字。项目里有的样片带一个 `cuecheck.py`，专门比对"画面上的击打点"和"音乐上应该落的那一拍"，目标误差是 0 毫秒。

这就是代码出片相对生成模型最大的优势：**节拍可以被验证**。生成模型能做出"有节奏感"的画面，但很难保证第 17.5 秒那一刀正好切在鼓点上。

## 声音这一半怎么做

画面之外，声音分三层，全部也是代码生成：

| 层 | 做法 |
| --- | --- |
| 配音 | 英文默认用本地 TTS（Kokoro）；中文默认用联网的 edge-tts；用户自带录音时直接用录音 |
| 配音回检 | 用 faster-whisper 把每句配音转回文字，与脚本逐字比对，不一致就重生成 |
| 配乐 | 用免费采样库按事件写谱；拨弦乐器用物理建模合成；芯片音乐用 numpy 直接合成 |
| 音效 | 程序化合成点击、风声、落地、纸张等，挂在 `window.EV` 的事件时间点上 |
| 母带 | ffmpeg 两遍响度标准化到 −14 LUFS，带真峰值限制 |

配音回检这一步很实用。TTS 偶尔会吞字或读错多音字，用语音识别转回来一比对，问题当场就能发现。文档也提醒：中文短句里识别错一个字很常见，要先听一遍，确认是识别的问题而不是配音的问题，再放行。

## 适合与不适合

这条路线不是视频生成的替代品，而是另一类工具。适用面差别很大：

| 适合 | 原因 |
| --- | --- |
| 数据叙事、信息图动画 | 数字、图表、标注都要精确 |
| 产品发布、界面演示 | 画面元素可控，品牌色和字体可以严格遵守 |
| 风格化短片（版画、剪纸、像素、水墨） | 风格规则可以写进代码，每帧一致 |
| 需要严格卡节拍的片子 | 时间线可验证 |

| 不太适合 | 原因 |
| --- | --- |
| 写实人物表演 | 代码画的角色动作有限，很难做到真人质感 |
| 自然场景的照片级还原 | 程序化画面和实拍差距明显 |
| 赶时间的一次性内容 | 每支片子 Agent 大约要做 30 到 60 分钟，token 消耗不小 |

## 常见失败

文档里列出了最常见的几类问题，可以当成上线前的自查表：

| 失败 | 根因 | 怎么防 |
| --- | --- | --- |
| 并行渲染出来的帧前后跳 | 页面保留了上一帧的状态 | 所有画面都从 t 直接算 |
| 镜头移动后特效对不上主体 | 手写了屏幕坐标 | 统一走一个世界坐标到屏幕坐标的函数 |
| 渲染越来越慢、成片很大 | 在页面里画了颗粒 | 颗粒交给 ffmpeg |
| 3D 景深突然失效 | 正交相机套用了透视相机的深度计算 | 按相机类型换对应的深度函数 |
| 音乐低频糊成一片 | 合成配乐低音太重 | 按频段量能量，20–120 Hz 控制在约 −3 dB |

## 运行环境

系统层面需要 Node 20 以上、ffmpeg、Python 3.11 以上（或 uv）。文档说明开发环境是 macOS（Apple 芯片），Linux 应该可用，**Windows 需要通过 WSL 运行**；3D 和重着色器的风格需要 GPU。其余依赖按需分层安装，核心层约 350 MB，配音层约 0.55 GB 外加一个 Whisper 模型。

## 限制与结论

需要说明的边界：项目的风格是针对特定模型调出来的，README 明确写了"其他模型适配度不高"；每支片子耗时与 token 用量都不低；Windows 用户必须先装好 WSL。

可以确定的是方法本身：把画面写成时间的确定性函数、让一条时间线驱动画面与声音、在最后一步统一做颗粒与响度，这三条是代码出片能做到"精确到帧"的根本原因。它们不依赖某个具体项目，任何想用 Agent 写代码出片的人都可以照这个结构搭自己的管线。

如果只想先试一下，最小的验证是：写一个只暴露 `DUR` 和 `render(t)` 的页面，让它画一个按时间移动的方块，用无头浏览器截 48 帧拼成 2 秒视频。这一步跑通了，后面加声音、加时间线都只是在同一个结构上叠东西。
