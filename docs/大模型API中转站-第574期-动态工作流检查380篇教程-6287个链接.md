# 用动态工作流检查 380 篇教程：6287 个链接背后的脚本化协作

检查十几篇文章的链接，人工还能做。
检查 380 篇文章、6000 多个链接，问题就变了：不是“能不能看完”，而是“怎样保证每一篇都按同一套标准看完，并且能说清哪条结论来自哪一步”。

普通的 AI 对话也能开多个子 Agent，但分工往往是在执行过程中临时决定的。
任务一长，容易出现三个问题：分组漏了、结果格式不一致、失败后不知道从哪继续。

ZCode 的动态工作流换了一个思路：先把“怎么干”写成脚本，再让一支子 Agent 小队照着脚本执行。
这篇文章用一组公开演示记录，说明这套方式适合什么任务、成本大概在哪里、验收应该看什么。

## 先理解它和普通多 Agent 对话的区别

官方规格对动态工作流的定义很直接：主 Agent 通过写程序来指挥多个子 Agent，而不是通过对话。

脚本是一段普通的 TypeScript，调用一组受控接口：

- `agent()` 创建一个子 Agent。
- `.ask<T>()` 给子 Agent 一个任务，并返回带类型的结果。
- `files.*`、`git.*`、`world.run` 读取和探测工作区。
- `phase()` 给阶段命名。
- `report` 流式输出发现。
- `artifact.*` 发布交付物。
- `log` 记录过程。

其他部分就是普通 TypeScript：`await`、`Promise.all`、`for`、`while`、`if`、`try/catch`、辅助函数和 `.map`。
来源：[Dynamic Workflow 规格](https://github.com/zai-org/ZCode/blob/3c5b227649371507ddc4eb46ac5133afe6db1cab/docs/dynamic-workflow.md?plain=1)，访问日期：2026-10-20。

这段定义里有两个关键词：程序和受控接口。

“程序”意味着分工是显式的。
哪个阶段先跑、哪些任务可以并行、结果怎样汇总、失败后重试哪一步，都写在脚本里。
“受控接口”意味着子 Agent 不是随便调用系统命令，而是通过工作流提供的能力读写文件、访问 Git、提交结果。

官方编写说明还提到，脚本会经过 TypeScript 编译器类型检查，每个 `.ask<T>()` 会根据 `T` 合成 JSON Schema，子 Agent 的回答要按 Schema 校验。
工作流的依赖图、控制流图和交接图会在运行前分析出来。
每次执行都会写入 journal，恢复时重新运行同一段脚本，由 journal 回答哪些步骤已经完成。
来源：[Dynamic Workflow 编写说明](https://github.com/zai-org/ZCode/blob/3c5b227649371507ddc4eb46ac5133afe6db1cab/docs/dynamic-workflow/authoring.md?plain=1)，访问日期：2026-10-20。

这解决了长任务里的一个老问题：失败后只能靠聊天记录猜进度。
脚本加 journal，至少让“哪些阶段完成了、哪些结果已经落盘”变成可检查的状态。

## 这次任务为什么适合工作流

这组演示记录里的任务是检查一套免费开源的《AI 编程零基础教程》。
中文内容有 380 篇文章，去重后有 6287 个链接。

任务要求包括：

- 每个链接真实访问一遍，找出失效链接。
- 每条模型和价格信息联网核实，找出过时内容。
- 跨文章比对，找出前后矛盾的说法。
- 把问题按严重程度整理成 Excel，方便逐条修复。

这三点决定了它不适合纯对话：

第一，输入是“宽”的。
380 篇文章不是一条深度推理链，而是几百个相似但不完全相同的检查单元。
第二，流程是固定的。
先盘点，再分组，再检查链接，再核实信息，再复核，最后比对矛盾。
第三，结果要可追溯。
每条问题都要能回到具体文章、具体链接或具体说法。

工作流脚本正好适合这种“宽而结构化”的任务。
如果任务只是改一篇文章的标题，写脚本反而多余。

## 运行前先做三件准备

演示记录里，主 Agent 没有一上来就开跑，而是先做了三步准备。

### 1. 盘点仓库，建立输入清单

先检查仓库结构，统计出 3 个目录一共有 380 篇文章。
再去重链接，得到 6287 个唯一链接。

这一步很重要。
如果连“总共有多少篇文章、多少个链接”都没有确认，后面的分组覆盖率和进度都无法判断。
验收时也无法回答“是不是每一篇都检查了”。

### 2. 先写一个链接检测脚本试跑

在写工作流之前，先写一个单独的链接检测脚本，跑一小批样本。
这样可以提前知道：

- 链接检测大概要多久。
- 哪些站点会超时或返回异常状态。
- 结果字段长什么样。
- 失败重试要不要单独处理。

先跑确定性脚本，再让子 Agent 做判断，是一个很实用的顺序。
死链检测本身不需要语言模型，脚本更快、更便宜、也更容易复现。
子 Agent 应该把精力放在“这个异常是不是误报”“这条信息是否过时”上。

### 3. 用片段工具验证分组覆盖

演示记录提到，主 Agent 用 `EvalWorkflowSnippet` 提前验证了文章分组。
二十多个分组刚好覆盖全部 380 篇文章，一篇都没有遗漏。

这一步相当于在正式运行前做一次“排练”。
工作流一旦跑起来，可能要消耗大量 Token；提前验证分组，比跑完再发现漏了一组便宜得多。

## 工作流分成 6 个阶段

演示记录把工作流画成了一张流程图，确认后才开始运行。
流程大致分成 6 个阶段：

| 阶段 | 主要工作 | 产出 |
| --- | --- | --- |
| 1 | 脚本批量检测链接 | 原始状态码、超时、重定向记录 |
| 2 | 链接分诊员复核疑似死链 | 确认死链与误报清单 |
| 3 | 扫描员分组通读文章 | 每篇文章的过时信息和疑点 |
| 4 | 核实员联网核实 | 模型、价格、版本等事实核对结果 |
| 5 | 复核员二次确认 | 降低误报，补充证据 |
| 6 | 矛盾交叉比对员找冲突 | 文章之间的前后矛盾清单 |

这套分工有两个值得借鉴的地方。

第一，确定性工作和判断性工作分开。
链接状态用脚本批量拿，疑似死链再交给子 Agent 复核。
这样不会让每个子 Agent 都从零开始访问网页，也不会把明显的 404 当成需要推理的问题。

第二，关键结论有二次确认。
核实员查到的信息，再由复核员确认一次。
这不是说二次确认一定正确，而是把“单次判断”变成“可以对照的判断”。

## 105 个子代理怎样协作

演示记录显示，这次任务一共调度了 105 个子代理，消耗了 4000 多万 Token，跑了很久才完成。

105 个子代理不是同时启动的。
工作流有并发上限，子 Agent 按阶段和依赖关系分批执行。
有的负责扫描文章，有的负责查链接，有的负责复核，有的负责比对矛盾。
主 Agent 不直接做所有判断，而是维护脚本、汇总结果和处理异常。

从验收角度看，子 Agent 数量本身不是成绩。
真正有意义的是：

- 每个子 Agent 的输入范围是否明确。
- 输出是否有固定字段。
- 失败时是否记录原因。
- 结果是否能合并、去重、排序。
- 能不能从最终清单回到原始证据。

如果只是“开了很多 Agent”，但结果是一堆自然语言段落，后面仍然要人工重新整理。
工作流的价值在于把结果变成可合并的结构。

## 219 个问题，数字要怎样看

演示记录给出的结果是：体检出 219 个问题，其中高严重度 35 个。
按类型分，有 106 个失效链接、91 条过时信息、26 处前后矛盾。

这里有一个需要说明的口径问题：
106 + 91 + 26 = 223，与 219 不完全一致。
可能是分类之间存在重叠，也可能是统计口径不同。
本文保留原始记录，但不把这组数字当成精确的分类总数。

可以确认的是，最终结果按严重程度排序写进了 Excel，方便逐条修复。
对使用者来说，比“总共多少个”更重要的是：

| 字段 | 用途 |
| --- | --- |
| 问题类型 | 决定修复方式：换链接、改信息、统一说法 |
| 严重程度 | 决定先修哪些 |
| 文章位置 | 快速定位原文 |
| 证据 | 链接、截图、引用或核实来源 |
| 建议动作 | 删除、替换、补充或待确认 |

如果 Excel 只有“问题描述”，没有文章位置和证据，修复成本会很高。
工作流应该把“发现问题”和“支持修复”一起交付。

## 成本为什么高，怎样控制

4000 多万 Token 是一个很直观的提醒：动态工作流不是免费魔法。

成本主要来自三部分：

1. 380 篇文章要通读，输入上下文很大。
2. 6287 个链接要检查，脚本请求和异常复核都不少。
3. 105 个子代理各自有系统提示、任务说明和结果汇总。

控制成本可以从六个地方入手。

### 1. 先抽样

不要第一次就拿全量跑。
先选 10 到 20 篇文章，覆盖不同目录、不同链接类型、不同内容主题。
用小样本验证分组、字段、误报率和耗时，再决定要不要全量。

### 2. 先跑确定性脚本

链接状态、文件数量、重复项、格式检查，这些不需要语言模型。
脚本先做一遍，子 Agent 只处理脚本无法判断的部分。

### 3. 限制并发

并发不是越高越好。
并发太高会触发供应商限流，也会让失败重试变多。
工作流支持设置并发上限，应该根据账号配额和任务紧急程度调整。

### 4. 设置预算和停止条件

在开始前明确：

- 最多允许多少 Token。
- 最多跑多长时间。
- 什么情况下停止。
- 停止后保留哪些中间结果。

没有预算的长任务，容易在“再检查一遍”里失控。

### 5. 保存工作流

工作流可以保存下来，下次教程更新后直接复跑。
这比每次重新描述需求更省时间，也更适合做周期检查。

### 6. 分级处理

不是所有问题都值得用同样的模型和同样的复核次数。
失效链接可以脚本加轻量复核；价格和版本信息需要联网核实；前后矛盾需要更强的阅读和比对。
把资源放在高严重度问题上，比平均用力更划算。

## 怎样设计一个可复现的工作流

如果你也想把类似任务做成工作流，可以按下面五步设计。

### 第一步：定义范围和验收

先写清楚：

```text
输入：哪些目录、哪些文件类型、总共多少份
输出：一张什么格式的清单，包含哪些字段
验收：抽样多少条、由谁复核、什么算通过
```

范围不清楚，工作流只会更快地产生一堆无法验收的结果。

### 第二步：建立清单

先扫描文件，去重，统计数量。
把清单作为工作流的输入，而不是让每个子 Agent 自己再去遍历目录。
这样分组覆盖和进度才有依据。

### 第三步：拆分确定性步骤和判断步骤

确定性步骤包括：

- 文件枚举。
- 链接状态请求。
- 重复项检测。
- 格式和字段校验。
- 结果合并、排序、去重。

判断步骤包括：

- 这个链接是不是真的失效。
- 这条价格信息是否过时。
- 两篇文章的说法是否矛盾。
- 这个问题应该归为哪一类。

两类步骤分开，脚本和子 Agent 各做擅长的事。

### 第四步：先验证片段，再全量运行

用少量样本验证：

- 分组是否覆盖全部输入。
- 输出 Schema 是否稳定。
- 子 Agent 是否能按字段提交。
- 失败和重试是否被记录。
- 结果能否合并。

验证通过后再全量跑，避免把错误的分组复制到几百个任务里。

### 第五步：保留证据和复跑能力

最终清单至少保留：

- 原始文件路径。
- 问题所在位置。
- 证据链接或引用。
- 判断理由。
- 置信度或待确认标记。

工作流保存后，下一次只需要替换输入目录和日期。
但要注意，外部链接和价格会变化，复跑结果不会和上一次完全一致。

## 什么情况下不值得用工作流

动态工作流适合“宽而结构化”的任务，不适合所有任务。

不建议使用的情况包括：

- 只有几份文件，人工半小时能做完。
- 任务目标模糊，连输出字段都定不下来。
- 需要真实付款、发消息、提交表单等不可逆动作，却没有审批机制。
- 资料包含大量敏感信息，尚未脱敏。
- 只需要一次，之后不会重复。
- 失败代价很高，但没有人工复核环节。

工作流会把任务放大：流程设计得好，它放大的是效率；流程设计得差，它放大的是错误和成本。

## 结论

这次 380 篇教程、6287 个链接的检查，展示了动态工作流适合的任务形态：

- 输入很多，但可以分组。
- 流程固定，可以写成阶段。
- 结果需要结构化，方便合并和排序。
- 任务会重复，值得保存和复跑。

它也暴露了成本边界：105 个子代理、4000 多万 Token、较长运行时间，都不是随手可用的量级。
所以正确顺序是：先抽样，再验证分组，再跑确定性脚本，最后才全量调度子 Agent。

下一步验证建议：选一个 20 到 30 篇文档的小目录，按“清单、脚本、分组、抽样、复核”的顺序跑一遍。
先记录误报率、漏报率和人工修正时间，再决定是否扩大到全量。
