# 把十几个工具塞进一个系统：双向图、CRDT 与频道提及怎么配合

事情往往是从"工具不够用"开始变味的。Slack 聊需求、Linear 记任务、Notion 写文档、HubSpot 管客户、Superhuman 收发邮件——每个单看都好，合起来就是：为了搞清楚一个客户提了什么，你得在五个标签页之间翻，最后还得去问当事人。

Macro 的理由写得很直白：上一家公司做到约 20 人时，每个团队有了自己的工具，公司靠 MCP 和 Zapier 粘一起，"不可计算"。它的做法是把这些面放进一个界面，共用一个后端。

这套东西能不能成，取决于三个机制：交叉引用怎么存、并发编辑怎么合、可见性怎么算。下面逐个看，然后说代价。事实来自仓库 README 与官方文档（检索日期 2026-11-06），英文引文为译文；未部署。

## 一、先看它长什么样

按 README，Macro 由 12 个 block 组成：邮件、消息、任务、文档、画布、智能体、通话、文件、Pull Request、CRM、数据库、日历。技术上自称用 SolidJS 和 Rust 构建，"为速度与可靠性"。

README 里有一句话，是整套设计的支点（译文）：

> 每个界面都是为它自己的工作专门构建的，而不是由通用积木拼成——但它们共享同一个后端，跨引用（文档与任务之间、频道消息与邮件之间）原生存储为**双向图**。

这句话解释了为什么"多工具拼接"和"单一系统"不是程度差别。拼起来的工具之间，关系存在谁的库里？通常是一边存个外链，另一边什么都不知道。双向图的意思是：你在消息里提及某个公司记录，两边都知道彼此，之后从哪一头都能走回来。

## 二、交叉引用：为什么必须是双向的

工具之间最常见的粘合方式是链接和同步，两者都只在一个方向上是真的。

- 你在任务里贴上邮件的链接，任务知道邮件；邮件不知道任务。
- 你用 Zapier 把表单同步到 CRM，CRM 有了记录；但那条记录来龙去脉在哪儿，没人知道。

Macro 的做法是把关系也存进数据模型。README 说，在可能的情况下任务会与来源双向链接，于是从"我们为什么做这件事"到任务、到智能体、到合并请求，整条链可审计。

价值不在方便，在可审计。**一份工作从对话开始、经过智能体、落到合并请求，能沿链接倒着走回去，才可能回答"这个改动是谁让做的"。** 多数团队的链是断的。

代价也在这里：每次链接都是一次写操作，图和业务表一起变。做得好顺手，做不好就是"改一条状态，三处都在动"。

## 三、CRDT：人和智能体改同一份文档

文档这块他们选了 CRDT（无冲突复制数据类型），配合 Cloudflare 的 durable objects，支持离线编辑与合并，还有历史回看与分叉。

CRDT 在协作文档里不新鲜。有意思的是把智能体放进同一套机制里。README 两句原文（译文，合并自两处）：

> 原生智能体编辑，由**成群的智能体**驱动，它们在 CRDT 协作系统中作为同级参与者运行，**像人类协作者一样**。
>
> 智能体可以编辑打开或关闭的文档。

"像人类协作者"是重点。多数做法是人走协作通道、智能体走 API 通道，两边靠版本号或锁协调，冲突报错或后写覆盖。塞进同一套 CRDT，等于共享同一份冲突解决规则。

README 举的例子很日常：一个每天运行的任务，扫描各频道看谁赢了办公室台球赛，更新那份 markdown 文档；有人改过它就跳过；冲突交给 CRDT。

风险同样清楚：CRDT 保证"合并不冲突"，不保证"合并结果正确"。同一段文字各改一版，合并出来可能语法通顺、语义打架。那个例子安全，是因为更新幂等（"谁赢了"是事实），不是需要协商的措辞。

## 四、可见性：三条来源，不是一张表

README 有一句听起来很大胆的概括：在频道里提及的任何东西自动共享给频道成员，加入就获得访问，离开就失去。

但官方 permissions 页写得更细：谁能打开一个 block，来自 **Share、在频道中提及，以及若干团队默认值**。三条路并存：

| 来源 | 细节 |
| --- | --- |
| Share 面板 | 指定人或群组，带权限级别（如 Can view）；链接三档：仅限已有权限的人 / 任何拿到链接的人（含没有账号的人）/ 本团队成员拿到链接即可（其他人仍需被单独添加） |
| 频道提及 | 在频道消息里提及文档、任务或文件，即共享给该频道成员 |
| 团队默认 | 任务、从频道发起的通话等，默认对团队可见，可关 |

同一页还有两个细节：正文里的提及不通知、也不给访问（只在评论或频道消息里才算）；邮件默认留在会话内，"Email Sync 打开的公司"是例外。

所以"频道即权限"只是其中一条。更准确的版本反而更好用，它意味着三件事：

1. **回溯可见。** 官方原话是：后加入的人会看到全部历史和所有被提及的内容。临时拉人处理一次故障，等于把该频道的历史一次开给他。
2. **离开即失去**，对交接不友好：人一走，历史里那些被提及的上下文对他关闭。
3. **三个入口就有三套口径。** Share 面板的链接范围、频道的 Team/Private、团队默认值，任一处没对齐，实际可见范围就和主管以为的不一样。

## 五、记忆：每晚刷新的背景资料

智能体要"知道团队在干什么"，靠记忆。官方文档说得比猜测更具体：

> 每晚，Macro 从当天的活动中刷新这份记忆。……夜间摘要已经是一天前的，它会漏掉任何你会临时去查的东西。

边界也写清楚了：记忆是背景，是智能体"知道"的较小那部分；找当前事实靠工具调用——搜索邮件、消息、任务、文档与通话记录，再打开读到的那条，结果是最新的。

记忆还分两层：每人有自己的个人记忆；团队另有一份共享记忆，任务默认进入，从频道发起的通话默认录制共享，可关。

这套分工值得抄：**背景用批处理，事实用检索。** 反过来（指望记忆回答"刚刚那通电话说了什么"）会失望；只做检索，则每次都要重新摸索你喜欢怎么工作。

## 六、智能体怎么接进来

README 给了三种内置接法，外部编码智能体另有一节：

| 接法 | 说明 |
| --- | --- |
| 用平台自带模型 | 私聊智能体、在频道里提及、或给它指派任务（这三种是调用方式，不是模型来源） |
| 接 Cursor | 用你自己的 API key |
| 本机智能体 | 通过 `macrod` 接进工作区 |
| 外部编码智能体 | 走 MCP：`claude mcp add --transport http macro https://mcp-server.macro.com/mcp` |

每种接法的验证点不一样：

| 通道 | 要验的点 |
| --- | --- |
| 平台自带模型 | 它能读到哪些上下文，读不到哪些 |
| 自有 key 接 Cursor | key 与用量算在谁头上，出错时去哪看日志 |
| `macrod` 本机 agent | 本机权限与工作区权限如何叠加 |
| MCP 外部客户端 | 能看到频道历史，还是只能看单条任务 |

最后一行有官方入口：README 指向 MCP setup 文档；那份文档我这次没抓，工具清单未核。

## 七、这套设计的代价

统一系统的收益好讲，代价少有人写。按这套架构，至少有四处要提前想清楚：

| 代价 | 具体是什么 |
| --- | --- |
| 单点 | 一个后端承载邮件、文档、任务、CRM。它挂了，工作全停；以前是某个工具挂了还能换别的干 |
| 迁移 | 数据和关系都在一张图里。迁出去不只是导出文档，还要处理"谁提及了谁" |
| 可见范围 | 拉人进频道等于把该频道全部历史一次开给他；离开后按官方说法即收回，但"临时拉一下"的次数越多，曾经看到的人越多 |
| 智能体写坏的成本更高 | 智能体能改文档、改记录、开 PR；在单一系统里，一次错误的波及面比"只能改一个工具"更大 |

第四行值得多说。README 写了对模型提供方的承诺：不留存、不用客户数据训练，另有 SOC 2 Type II。这些解决不了"智能体在内部改错东西"的问题。后者要靠权限与审计，而三个可见性入口并存时，谁在什么时候看到了什么，不容易讲清。

## 八、四种会先出问题的情形

这套架构在真实团队里最先坏的地方，我猜是四种。前两条对应到某个机制，后两条是从机制往外推的延伸。

**关系图膨胀。** 双向图的好处是每条关系能走回去，坏处是越积越多。用了一年的工作区，可能某条任务链着四十条消息、七份文档和三封邮件——打开它要的是摘要，不是全图。README 没说有没有上限或折叠策略。

**合并出一段说不通的话。** CRDT 保证不冲突，不保证语义对。人和智能体各改一版，机械合并可能前后矛盾。台球赛那个例子安全，是因为更新幂等；换成"改写这段需求描述"就没这么好运。

**背景记忆带着旧结论。** 夜间摘要本身就是一天前的。某个决定后来被推翻，旧决定还会在记忆里待一阵，智能体引用它，还会引用得很自信。这条可以测：改一个决定，看记忆多久跟上。

**可见性被"临时拉一下"摊薄。** 每次临时协作都把一批历史开出去。团队越大、次数越多，实际可见范围与主管以为的差距越大。

共同点：**都不是 bug，是设计的自然结果。** 出问题时没有报错，只有"怎么又有这个""为什么它说的是上个月的结论"。

## 九、如果我要验它

1. **链路可走通**：拿一封真实邮件生成任务，交给智能体产出 PR，再从客户记录一路点回去，看链条是否完整。官方写的是 where possible，断链不一定是 bug——先看邮件转任务那一步有没有生成链接；也要先确认账号有没有接 GitHub 的权限。
2. **并发合并**：人和智能体同时改同一段，看合并结果是否需要人工收拾。
3. **可见性边界**：让一个人临时加入频道，确认他看到全部历史还是部分；离开后是否收回；再对照 Share 面板的链接范围。
4. **记忆延迟**：当天发生的事，多久能被智能体引用——这条至少要跨一个夜间刷新周期；再删一条记录，看记忆里是否还留着。

四条都不用读代码，但第 1 条依赖集成权限，第 4 条依赖时间。**如果第一条走不通，后面三条都没意义**——那条链正是它区别于"再做一个 Notion"的地方。

## 十、结论与边界

核心不是"功能多"，是**让关系成为数据的一部分**：交叉引用进双向图、并发编辑进 CRDT、可见性由 Share 与频道提及共同决定。目标只有一个——工作状态可查询，不用散在各处等人问。

我的判断：对 10 到 50 人、工具已在拖慢协作的团队，这个方向值得试；对合规要求严格、或离不开既有工具生态的团队，先解决审计与可见性口径再说。

限制：没有部署，没验证任何机制；上文描述来自 README 与官方 permissions、unified-memory 文档，属项目自述；第八节后两条是我的推断；SOC 2 Type II 与 ISO 27001 徽章未核实。

下一步建议很小：先只验第九节的第一条。那条链走通了，再谈别的。
