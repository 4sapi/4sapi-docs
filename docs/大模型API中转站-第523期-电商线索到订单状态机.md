# 电商自动化怎么接起来：用一套状态机管理线索到订单

很多电商团队已经在使用 AI：一个脚本负责找客户，一个脚本负责查资料，另一个脚本生成邮件，还有工具处理客服和订单。

问题是，这些工具往往各自保存状态。

采集脚本不知道客户是否已经联系过，客服系统不知道报价进行到哪一步，订单表也不知道这条线索最初来自哪里。

结果就是重复触达、漏掉回复、报价过期，最后没人能说清楚一笔订单是怎样来的。

解决办法不是再增加一个聊天窗口，而是先把客户从线索到订单的路径写成状态机。

## 一、先画出完整路径

一条最小的跨境电商路径可以是：

```text
发现信号
-> 待清洗
-> 已去重
-> 待调研
-> 待评分
-> 待审核
-> 待触达
-> 已联系
-> 等待回复
-> 需求确认
-> 报价中
-> 已报价
-> 成交
-> 交付中
-> 已完成
-> 复购跟进
```

每个状态都要有进入条件、下一步动作、负责人和失败处理。

如果只有“进行中”和“已完成”两个状态，系统无法知道下一步该做什么。

## 二、线索记录至少保存什么

一条线索不是一个公司名称和邮箱地址。

建议至少保存：

| 字段 | 用途 |
| --- | --- |
| lead_id | 线索唯一标识 |
| company_name | 公司名称 |
| website | 来源网站 |
| source | 发现渠道 |
| discovered_at | 发现时间 |
| evidence | 需求证据原文或链接 |
| contact | 联系方式 |
| status | 当前状态 |
| score | 排序分数 |
| next_action_at | 下一步时间 |
| owner | 负责人 |
| last_contact_at | 最近触达时间 |
| opt_out | 是否退订或拒绝 |

其中最容易被忽略的是 `evidence` 和 `next_action_at`。

没有证据的线索不能直接进入高优先级队列。

没有下一步时间的线索，过几天就会从团队视野里消失。

## 三、采集和去重必须分开

采集任务只负责发现信号，不负责判断客户一定会买。

它应该保存来源、时间和原文片段，然后把记录交给清洗任务。

清洗任务再检查公司名称、网站、邮箱和历史互动，判断是不是重复记录。

同一家公司出现新的需求信号时，不要新建一条完全独立的客户。

更合理的做法是把新信号挂到原有客户记录下面：

```text
company_id
  ├── signal_001：新增产品页
  ├── signal_002：招聘采购岗位
  └── signal_003：参加行业展会
```

这样既保留了历史，也避免重复触达。

## 四、调研任务要输出固定字段

客户调研不能只让 AI 写一段介绍。

建议固定输出：

- 公司主营产品；
- 目标市场；
- 可能的采购需求；
- 联系人和职位；
- 需求证据；
- 最近活动；
- 可能的匹配产品；
- 信息来源；
- 未确认的推测；
- 建议的下一步。

“信息来源”和“未确认的推测”必须分开。

如果模型无法确认联系人是否负责采购，就应该写“待确认”，而不是把职位推断成采购决策权。

## 五、评分只负责排序

评分 Worker 可以根据需求信号、产品匹配、联系人可触达程度、市场潜力和时间窗口打分。

分数的作用是帮助人先看更值得看的客户。

它不能替代最终判断，也不应该直接触发高风险动作。

例如可以设置：

```text
0-39：暂不处理
40-69：进入补充调研
70-84：进入人工审核
85-100：优先处理，但仍需审核
```

阈值只是示例，实际数值要根据历史数据调整。

不要把分数写成“成交概率”，除非你有足够样本进行校准。

## 六、触达前必须经过审核

首触草稿可以由模型生成，但发送前应检查：

- 邮件是否引用了真实证据；
- 产品描述是否与产品卡一致；
- 是否包含未经确认的价格和交期；
- 是否出现夸大承诺；
- 客户是否已经退订或明确拒绝；
- 联系人和公司是否匹配。

只要客户已经回复，自动跟进就应该暂停。

回复代表状态发生变化，系统要把任务转交给人工或新的判断流程。

## 七、把回复做成状态转换

客户回复后，不要只把邮件存进聊天记录。

系统需要识别回复类型，并转换状态：

| 回复类型 | 状态变化 | 下一步 |
| --- | --- | --- |
| 索要报价 | 已联系 -> 需求确认 | 补齐规格和数量 |
| 询问交期 | 已联系 -> 交期确认 | 查询产品卡和供应链 |
| 明确拒绝 | 已联系 -> 已拒绝 | 停止自动触达 |
| 要求退订 | 任意状态 -> 已退订 | 永久停止营销触达 |
| 暂不确定 | 已联系 -> 待跟进 | 设定下一次时间 |
| 无法识别 | 已联系 -> 人工复核 | 不自动发送 |

无法识别的回复，不应该被强行归类成“有兴趣”。

## 八、报价要绑定产品卡

产品卡至少应包括：

- 采购成本；
- 建议售价；
- 最低可接受价格；
- 毛利底线；
- 交付时间；
- 可用库存；
- 供应商和替代方案；
- 常见问题；
- 不能承诺的内容。

模型可以根据这些字段生成报价草稿，但低于毛利底线、超出库存或无法确认交期时，必须转人工。

价格、库存、认证和售后承诺不能由模型自由编造。

## 九、订单状态接住前面的结果

订单创建后，客户不应重新从头录入一次。

订单应该关联：

```text
lead_id
company_id
quote_id
product_id
owner
payment_status
fulfillment_status
refund_status
```

这样可以回看客户来源、报价版本和成交条件。

付款、备货、发货、签收、售后和复购提醒，都应该是订单状态的后续转换。

## 十、哪些动作不能自动放行

下面这些动作建议保留人工审核：

1. 首次批量发送；
2. 改变价格和折扣；
3. 承诺交期和认证；
4. 修改库存或正式订单；
5. 处理高金额退款；
6. 删除客户和订单数据；
7. 重新激活已退订客户。

频率高、规则清楚、风险低的动作，才适合自动执行。

## 十一、失败必须留下原因

任务失败后不能只显示红色图标。

至少记录：

```text
task_id
lead_id
attempt
failed_at
error_type
error_message
retryable
next_retry_at
owner
```

网络超时、接口限流、数据缺失和规则拒绝，处理方式不一样。

可重试错误可以进入有限重试队列。

数据缺失需要补充资料。

规则拒绝则应该转人工，而不是不断重试。

## 十二、上线前先干跑

第一次上线不要直接处理全部客户。

拿一小批历史线索做干跑：不发送、不改库存、不写入正式订单，只检查采集、去重、评分和任务生成。

重点看四件事：

- 同一家公司是否被识别成多个客户；
- 推测是否被写成事实；
- 已经联系过的客户是否重新进入首触队列；
- 空字段是否让整个流程中断。

确认这些问题解决后，再开放草稿生成。

最后才是小批量发送，并持续观察送达、回复、退订和投诉。

## 十三、用指标判断流程是否健康

建议每天查看：

- 有效线索率；
- 调研完成率；
- 首触审核通过率；
- 有效回复率；
- 报价转化率；
- 成交率；
- 退订率和投诉率；
- 平均跟进时长；
- 任务失败率；
- 人工介入时间。

线索量增加，不等于业务变好。

如果有效线索率下降、退订率上升，说明自动化可能正在放大噪声。

## 十四、从一个产品和一种客户开始

最小版本只需要：

1. 一种产品；
2. 一类客户；
3. 一张产品卡；
4. 一张线索表；
5. 一个稳定数据源；
6. 一个调研任务；
7. 一个首触审核队列；
8. 一套跟进状态机。

先让这条小链路连续运行，再增加更多国家、品类和来源。

## 结论

电商自动化的难点，不是让 AI 多生成几百条内容，而是让每条线索都能找到下一步，让每次回复都能改变状态，让报价和订单接得上。

状态机、固定字段、人工审核和失败记录，构成了从线索到订单的最小骨架。

当系统能够回答“客户从哪里来、现在在哪一步、下一步什么时候做、失败后谁处理”，自动化才真正开始产生经营价值。
