# 【大模型API中转站】第188期 AI会议纪要 | 决策转工单

本文是【大模型API中转站】系列的第188篇。本系列致力于用最低的成本、最清晰的方法，帮你打通多模型API的任督二脉。建议先收藏，随用随查。

AI 特别适合处理会议纪要。

但目标不是：

```text
把大家说的话复述一遍。
```

真正有用的是：

```text
决策是什么。
谁负责。
什么时候完成。
还有什么没定。
哪些要变成工单。
```

很多会议开完没有结果，不是因为没人说。

而是没有沉淀成行动。

## 1. 会议纪要要输出五样东西

```text
结论。
行动项。
负责人。
截止时间。
未决问题。
```

如果是技术会议，再加：

```text
风险。
依赖。
验收标准。
相关系统。
```

如果涉及 4SAPI 或模型接入，再加：

```text
模型。
Key 权限。
预算。
日志字段。
合规边界。
```

## 2. 模型分工

| 阶段 | 模型 |
| --- | --- |
| 语音转文字后清洗 | 低成本模型 |
| 纪要整理 | 低成本模型 |
| 决策冲突识别 | Fable 5 |
| 工单生成 | 中等模型 |
| 高风险决策复核 | Fable 5 |

Fable 5 不必处理每场普通例会。

但产品、架构、成本、权限相关会议，值得用。

## 3. 会议纪要模板

```text
# 会议纪要

会议主题：
时间：
参会人：

一句话结论：

已确认决策：

行动项：
| 事项 | 负责人 | 截止时间 | 验收标准 |

未决问题：

风险：

需要创建的工单：
```

这个格式比长篇流水账更好。

## 4. 转工单模板

```text
标题：
背景：
目标：
范围：
验收标准：
负责人：
截止时间：
依赖：
风险：
需要确认：
```

让 AI 输出工单草稿后，人再确认。

不要让 AI 自动创建高风险工单并分配人。

## 5. 区分“讨论”和“决策”

会议纪要最容易出错的是：

```text
把讨论中的想法写成已经决定。
```

所以 Prompt 里要明确：

```text
只有明确达成共识、有人确认、或主持人总结过的内容，才写入“已确认决策”。
其他内容放到“讨论观点”或“待确认”。
```

这条很重要。

尤其是涉及：

```text
预算。
人员安排。
客户承诺。
上线时间。
模型供应商选择。
4SAPI Key 权限开放。
```

AI 不能替团队拍板。

它只能整理已经发生的决策。

## 6. 自动建工单的边界

AI 可以生成工单草稿。

但不建议默认自动创建所有工单。

可以分级：

```text
低风险文档任务：可自动创建草稿。
普通研发任务：创建草稿，等待负责人确认。
生产、权限、预算、客户承诺相关：只生成建议，不自动创建。
```

如果要接 Jira、飞书、Linear、GitHub Issues，建议用 4SAPI 单独设置一个会议助手 Key。

并记录：

```text
meeting_id
model
ticket_count
human_confirmed
```

## 7. Prompt

```text
你是会议纪要和工单整理助手。

请根据会议文字，输出：
1. 一句话结论
2. 已确认决策
3. 行动项表格
4. 未决问题
5. 风险
6. 可创建工单草稿

规则：
- 不确定负责人或截止时间，标注待确认。
- 不把讨论中的想法写成已决策。
- 涉及 4SAPI、模型调用、API Key、预算和权限时，必须标注审计和人工确认点。
```

## 8. 4SAPI 治理

会议内容可能包含敏感信息。

建议：

```text
普通会议用低成本模型。
敏感会议先脱敏。
高价值决策用 Fable 5。
所有调用按 meeting_id 记录。
纪要生成后人工确认。
```

## 9. 示例：架构会转工单

会议原话可能是：

```text
我们最近 429 有点多，应该把批量任务和实时任务拆开。
客服那边不能被内容批处理影响。
预算也要分开看。
```

AI 应该整理成：

```text
已确认决策：
批量模型任务和实时客服任务需要拆分 Key 与队列。

行动项：
1. 新增 batch-key 和 realtime-key。
2. 将内容批处理任务迁移到 batch-key。
3. 为 realtime-key 设置更高优先级和独立预算。
4. 在 4SAPI 日志中增加 task_type。

工单草稿：
标题：拆分模型调用 Key 与队列，避免批量任务影响客服实时请求
验收标准：
- 客服请求不再使用 batch-key。
- batch-key 429 不影响 realtime-key。
- 日报能按 key_group 区分成本。
```

这就把会议里的“应该”变成了能执行的任务。

## 10. 会议纪要质量检查

让 AI 自检：

```text
是否把讨论误写成决策？
是否每个行动项都有负责人？
是否每个行动项有验收标准？
是否标注待确认事项？
是否涉及预算、权限、客户承诺？
是否需要人工复核？
```

会议纪要不是越长越好。

越能推动行动越好。

## 11. 会后追踪才是闭环

会议纪要生成以后，真正重要的是追踪。

可以让 AI 每天或每周检查：

```text
哪些行动项到期未完成。
哪些负责人没有确认。
哪些工单缺验收标准。
哪些未决问题超过 7 天没有推进。
哪些涉及 4SAPI 权限、预算或 Key 的任务还没审批。
```

输出不要写成抱怨。

写成工作清单：

```text
待确认负责人：
即将到期：
已逾期：
阻塞原因：
需要升级处理：
```

如果接入飞书、Jira、Linear 或 GitHub Issues，会议助手要有边界：

```text
可以创建草稿。
可以评论提醒。
可以汇总状态。
不自动改截止时间。
不自动关闭高风险工单。
不自动承诺客户。
```

4SAPI 记录会议助手的模型调用成本后，你还可以知道：

```text
会议纪要生成花了多少钱。
创建了多少有效工单。
多少行动项按时关闭。
哪些会议长期没有产出。
```

这时 AI 就不只是会议秘书。

它会变成团队执行力的放大器。

## 12. 示例：成本复盘会纪要

假设会议讨论的是：

```text
上周 Fable 5 成本突然上涨。
```

AI 纪要不应该只写“大家讨论了成本问题”。

它应该落成：

```text
已确认决策：
1. article_review 任务改为先用低成本模型摘要，再由 Fable 5 做最终审查。
2. Fable 5 单任务上下文上限设为 20k。
3. 429 重试最多 1 次，仍失败转人工。

行动项：
| 事项 | 负责人 | 截止时间 | 验收标准 |
| 调整 4SAPI 路由规则 | 后端负责人 | 周三 | article_review 默认不直连 Fable 5 |
| 增加成本告警 | 运维负责人 | 周四 | 单日预算 80% 触发通知 |
| 更新 SOP | 产品负责人 | 周五 | SOP 写明升级模型条件 |
```

这就是会议纪要的标准。

每个结论都能被验证。

每个行动都能被追踪。

## 13. 总结

AI 会议纪要的价值，不是“写得像纪要”。

而是让会议变成：

```text
决策。
工单。
负责人。
截止时间。
验收标准。
```

一句话：

```text
没有行动项的会议纪要，只是聊天记录。
```
