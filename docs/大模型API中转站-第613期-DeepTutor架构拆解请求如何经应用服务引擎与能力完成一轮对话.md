# DeepTutor 架构拆解：请求如何经应用服务、引擎与能力完成一轮对话

DeepTutor 是 HKUDS 开源的个性化辅导平台，仓库的星标已经超过五万。它有对话、测验、研究、解题、沉浸阅读等一长串功能，README 的功能清单读起来像一个大杂烩。要二次开发或评估它，先要弄清一件事：这些功能是各自为政，还是共用一条执行路径。

本文依据仓库 docs-for-dev 里的架构文档，回答这个问题：一次请求怎么进来、经过哪些组件、结果怎么回到界面；工具、能力、模块、插件这几个词各指什么；文档没有说清的地方有哪些。文章没有运行过这个项目，所有描述来自文档。

信息截止日期为 2026-10-30。项目更新很快，README 记录 v1.7.0 发布于 2026-10-28，引用前请重新打开原文件。

## 一、项目概况

| 项目 | 内容 |
| --- | --- |
| 仓库 | [HKUDS/DeepTutor](https://github.com/HKUDS/DeepTutor)（检索于 2026-10-30） |
| 协议 | Apache-2.0 |
| 创建 | 2025-12-28 |
| 最近推送 | 2026-10-29 |
| 语言 | Python（后端），Next.js（前端） |
| Star 数 | 50,277（检索当天） |

架构文档的第一句话把整体形态说得很清楚：这是一个源码仓库，里面有可以独立打包的 Python 模块。CLI、WebSocket 和 Python SDK 三个入口，在执行任何能力之前，都汇入同一个持久化的应用服务。

## 二、一次请求的路径

按文档的流程图，请求依次经过：

| 步骤 | 组件 | 职责（文档原意） |
| --- | --- | --- |
| 1 | 入口：Typer CLI、WebSocket 适配器、DeepTutorApp SDK | 把外部调用转成应用请求 |
| 2 | TurnApplicationService | 持久化的准入、执行与回放 |
| 3 | 会话存储与运行时协调器 | 保存会话和轮次；管理工作进程租约和通知 |
| 4 | TurnEngine | 较低层的执行 |
| 5 | ChatOrchestrator | 根据上下文把请求路由到某个能力 |
| 6 | 被选中的能力 | 拥有完整的一轮 |
| 7 | 代理循环或阶段流水线 | 能力内部的执行方式 |
| 8 | 授权的工具注册表 | 提供本轮允许调用的工具 |
| 9 | 每轮一个 StreamBus | 承载本轮的流式事件 |
| 10 | 存储，再经适配器回放给消费者 | 让断线重连或多个消费者看到同样的事件 |

文档对源码位置给了一张对照表，例如：CLI 解析在 deeptutor_cli/main.py，应用服务在 app/service.py，WebSocket 适配在 unified_ws.py，轮次引擎在 runtime/turn_engine.py，编排器在 runtime/orchestrator.py，能力和工具注册在 runtime/registry/。执行上下文是 core/context.py 里的 UnifiedContext。

### 一条硬规则

文档写道：入口应当使用应用服务，而不是自己实例化一个编排器去绕过持久化状态。持久化、提交身份、回放、取消和恢复，都属于共享的应用与运行时路径。

这条规则解释了为什么 CLI、网页和 SDK 的行为可以保持一致，也解释了 README 发布记录里反复出现的"可恢复的会话流""聊天恢复"。设计上，一轮对话不是一次性的 HTTP 请求，而是一个有身份、可重放的持久对象。

这是我从文档得出的理解，没有读代码验证。

## 三、四个容易混淆的词

### 工具与能力

文档的定义很短：

- **工具**是模型选择的一个操作。
- **能力**拥有一整轮，可以运行共享的循环，也可以运行多阶段流水线。

chat 是默认能力。README 列出的"对话、提问、测验、研究、可视化、解题、掌握路径、沉浸阅读、音频概览"，按文档的说法共享同一个能力运行时和会话上下文，同时保留各自专用的循环或流水线。

每个能力都输出统一的结果信封，其中包括用量成本。这一点对评估运行成本有用：不同模式的花费有统一的统计口径。

### 官方模块与第三方插件

| 概念 | 文档说法 |
| --- | --- |
| 官方模块 | 模块清单负责包路径、依赖、能力、路由、CLI 组、导航和生命周期回调 |
| 模块状态 | installed、enabled、ready 是三个独立的状态 |
| 元数据 | 必须能在不导入不可用功能包的情况下读取 |
| 第三方插件 | 有自己的评审和生命周期规则，与官方模块的包不是一回事 |

"已安装、已启用、已就绪"分开，意味着一个功能可以装了但没启用，或启用了但依赖没就绪。README 里的"模块化安装"（v1.7.0 的发布说明）与此对应。排查"功能不可用"时，先看是哪个状态没满足。

## 四、配置与隔离

文档在这一节有几条对部署者很重要的结论：

1. 运行时设置放在 data/user/settings/ 下，.env 不是应用配置的来源。很多人习惯改 .env，在这个项目里不会生效。
2. **账号授权和工作区选择是两次分开的检查。** 路径和服务通过 services/workspace/ 与 services/path_service.py 解析。
3. 被选中的工作区数据、账号凭据和共享资源授权，生命周期不同。碰迁移和缓存之前，文档要求先看存储文档和工作区契约。

第 2 点是理解多用户隔离的关键：能登录，不等于能访问某个工作区；两道门各自检查。

## 五、前端的边界

| 位置 | 内容 |
| --- | --- |
| web/app/ | Next.js App Router，组合页面 |
| web/features/ | 按领域划分的领域、状态和传输切片 |
| web/shared/ | 可复用的界面和传输原语 |
| web/contracts/ | 生成的 API 与轮次契约 |

依赖规则（配置在 .dependency-cruiser.cjs）禁止四类情况：循环依赖、导入路由的 page.tsx、共享层向上依赖、渲染层导入功能域/状态/传输代码（设置状态是命名的例外）。文档还建议优先使用现有的传输和状态所有者，不要在组件里自己实现 WebSocket、重试或持久化。

web/proxy.ts 把 API 和 WebSocket 流量转发给后端。文档特别强调，浏览器设置和运行时服务器配置是两条边界，部署地址和密钥不应写进客户端代码。

这条对自建部署有直接含义：反向代理只要指向前端端口即可，后端地址在服务端解析，浏览器看不到。具体见部署相关的容器化文档。

## 六、实验性的引擎路径

文档有一节专门讲"实验性引擎路径"：

- Python 调度器仍是默认。
- 环境变量 DEEPTUTOR_CHAT_ENGINE 可以选择实验性的 TypeScript 实现，代码在 packages/chat-engine/ 和 runtime/ts_engine/。
- 原生路径有兼容性检查，也有与 Python 的集成点。
- 文档明确写道：旧的迁移计划不能证明整个后端已经迁到 TypeScript。
- 改动这里必须保持应用服务、存储和公开事件契约不变。

对读者的含义：如果你在源码里看到 TypeScript 的引擎代码，不要据此判断后端语言。默认路径是 Python。

## 七、这套设计的权衡

下面是我基于文档结构的分析，属于推断，不是项目自述。

| 设计选择 | 好处 | 代价 |
| --- | --- | --- |
| 所有入口汇入持久化应用服务 | 行为一致，重连和回放统一 | 每个入口都多一层，调试链路更长 |
| 能力拥有整轮，工具只是一次操作 | 不同学习模式可以有各自的流程 | 能力数量多时，行为差异难以全部测试 |
| 模块清单、三态 | 可选安装，避免硬依赖 | 状态组合变多，排错要多一步 |
| 账号授权与工作区选择分离 | 隔离更细 | 配置时要理解两层概念 |
| 默认 SQLite 加文件 | 部署简单，一个目录即可备份 | 并发和扩展能力有限（见数据存储文档） |

最后一行的"有限"是推断。文档只说明 SQLite 是受支持的本地后端，没有受支持的 PostgreSQL 或 MySQL 连接设置，没有给出并发上限。

## 八、文档没有回答的问题

读完架构文档，我想知道但没有找到答案的事：

- 一轮对话的延迟里，应用服务、编排器、能力各占多少。
- StreamBus 的回放保留多久，容量上限是多少。
- 工作进程租约在节点崩溃时的恢复时间。
- 能力数量增加后，工具注册表的授权判断开销。
- 实验性 TypeScript 引擎与 Python 引擎的行为差异清单。
- 第三方插件的评审规则具体是什么（文档只说"有自己的规则"）。

这些问题要么要读更多文档（MODULES.md、PLUGINS.md、EVENTS_AND_PROGRESS.md、TESTING.md，架构文档里有链接），要么要自己测。

## 九、如果你要二次开发

文档给出的几条隐含要求，可以当作开工前的检查清单：

1. **新入口走应用服务**，不要自己组装编排器。
2. **新功能先判断它是工具还是能力。** 只是一次操作，做成工具；要完整的一轮和自己的流程，做成能力。
3. **新能力要输出统一的结果信封**，包括用量成本。
4. **官方功能走模块清单**；第三方扩展走插件，遵守插件的评审规则。
5. **改流式行为之前先读事件文档**（EVENTS_AND_PROGRESS.md）。
6. **前端遵守依赖规则**，不要在组件里自己实现传输。
7. **动存储、迁移或缓存之前先读存储与工作区文档。**
8. **不要把部署地址或密钥写进客户端代码。**

## 十、限制与结论

DeepTutor 的架构可以概括为：多个入口、一个持久化的应用服务、一个按上下文路由的编排器、若干拥有整轮的能力，加上统一的工具注册表和可回放的事件流。这套结构解释了为什么功能很多却能共用会话、成本统计和恢复机制。

本文的限制：没有安装或运行项目；没有读代码，只读了架构文档和存储、容器化文档；文档里链接的模块、插件、事件、测试文档没有读；星标数和版本是检索当天的快照；第七节的权衡是我的推断。

下一步建议：如果你打算基于它开发，先读 EVENTS_AND_PROGRESS.md 和 MODULES.md，再用最小的一个自定义能力走通"入口、应用服务、能力、回放"这条路径，确认文档描述与代码一致。
