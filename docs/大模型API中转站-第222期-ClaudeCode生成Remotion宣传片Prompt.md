# 把视频需求写成 Remotion 任务书的七个字段

“做一个有科技感的片头”没有说明素材从哪里来、文字是否允许改写、每段何时出现、代码能改到哪里，也没有可执行的验收标准。编码代理只能自行补齐这些空白，结果往往是画面能预览，却不符合交付比例、事实文本或项目结构。本文把视频需求拆成七个字段，并提供一份可替换占位符的 Remotion 任务书，目标是让每项视觉与代码决定都能在 Diff 和预览中检查。

## 字段一：任务范围

先说明这是新项目还是已有项目中的修改，并限制本次交付物：

```text
在现有 Remotion 项目中新增一个 Composition。
不要重新生成项目，不升级依赖，不修改其他 Composition。
先阅读项目中的约定和现有代码，再列出计划修改的文件。
```

如果是新项目，应先按官方流程完成空白项目和开发预览验收，再开始业务画面。环境安装与画面生成混在一个任务中，会让失败难以归因。

## 字段二：内容来源与事实边界

把允许使用的文案、数据、Logo 和媒体文件列出来。没有来源的产品数字、客户名称、价格、能力和比较结论不得由代理补写。

```text
主标题只能使用：{已确认标题}
副标题只能使用：{已确认副标题}
素材仅来自：{仓库内素材目录}
缺少文案或素材时停止并列出缺口，不从网络下载，不生成事实性替代内容。
```

对于示意数据，要在画面和任务书中明确它是占位内容。品牌名称、商标和字体授权也需要由素材提供方确认，编码代理不能替代授权判断。

## 字段三：视频规格

规格必须来自交付渠道或现有 Composition，而不是随意选择：

```text
Composition ID：{唯一标识}
宽度：{像素}
高度：{像素}
帧率：{fps}
总帧数：{durationInFrames}
音频：{无 / 指定本地文件}
```

时长与总帧数要一致。任务书可以直接给出总帧数，避免代理根据小数秒自行取整。需要横屏和竖屏时，分别定义 Composition 和验收边界，不要假定同一布局自动适配所有比例。

## 字段四：按帧描述时间线

把故事板写成不重叠且可检查的帧区间：

| 帧区间 | 内容 | 进入方式 | 退出方式 | 必须保持 |
| --- | --- | --- | --- | --- |
| `{开始}-{结束}` | `{标题或画面}` | `{动画}` | `{动画}` | `{可见信息}` |
| `{开始}-{结束}` | `{第二段内容}` | `{动画}` | `{动画}` | `{可见信息}` |

避免“稍后”“停一会儿”“节奏快一点”等相对描述。若片段需要重叠，明确重叠帧和层级。所有关键文字至少要有一段稳定可读区间，而不是始终处于运动和模糊状态。

## 字段五：视觉规则与禁用项

视觉要求应转化为可观察属性：

```text
背景色：{颜色值或现有设计令牌}
文字色：{颜色值或现有设计令牌}
字体：只使用项目已经包含且授权明确的字体
对齐：{左 / 中 / 右}
安全边距：{项目定义}
禁用：外部网络素材、随机粒子、不可读的强模糊、与设计系统无关的渐变
```

“高级”“大气”“有冲击力”无法单独验收。保留这些方向词时，还要提供参考素材或具体的颜色、密度、运动幅度和排版规则。

## 字段六：代码约束

Remotion 的当前 API 和推荐写法应以 [官方文档](https://www.remotion.dev/docs/) 以及项目已经安装的版本为准。任务书只指定完成目标必需的约束：

```text
使用项目现有 TypeScript、样式和组件约定。
优先复用仓库已有组件，不新增依赖。
动画由当前帧和 Composition 配置决定，不读取系统时间。
不发起网络请求，不在代码中写入本机绝对路径。
所有延迟动画在开始前保持确定状态。
修改后展示完整文件列表和 Diff。
```

不要要求代理机械拆出固定数量的组件。组件边界应由复用、职责和测试需要决定，而不是为了让目录看起来复杂。

## 字段七：验收与停止条件

验收必须区分静态检查、开发预览和实际渲染：

```text
使用 package.json 中已有命令完成类型或代码检查。
在开发界面检查指定 Composition 的开头、中间、转场和结尾帧。
确认所有文字在画面内，素材加载没有错误，其他 Composition 未改变。
如项目已有渲染命令，按仓库说明执行并记录实际输出。
没有现成命令或渲染依赖不满足时停止，不要编造成功结果。
```

编码代理应报告实际运行的命令、退出状态和未验证项。预览可见不等于交付文件已生成，渲染命令执行也不等于画面内容经过人工验收。

## 可复用的任务书模板

```text
先阅读仓库说明、Remotion Skills、package.json 和现有 Composition，不修改文件。
根据下面任务列出计划、候选文件和需要确认的缺口，得到确认后再执行。

【范围】
在现有项目新增 {Composition ID}；不升级依赖，不修改其他 Composition。

【内容来源】
文案：{已确认文案}
素材：{仓库相对路径}
不得补写数字、价格、客户、能力或比较结论；缺失时停止。

【规格】
宽度 {宽度}，高度 {高度}，帧率 {fps}，总帧数 {总帧数}。

【时间线】
{帧区间、内容、进入、退出、稳定状态}

【视觉】
{颜色、字体、排版、安全边距、参考与禁用项}

【代码】
遵循项目现有约定，不新增依赖，不请求网络，不使用本机绝对路径。

【验收】
运行仓库已有检查；检查关键帧和文字边界；按现有流程验证渲染。
展示 Diff、实际命令结果、未验证项和剩余风险。
```

## 如何评审生成结果

先审代理的计划，确认文件范围、素材来源和时间线没有被改写。生成后按三层检查：

1. 事实层：所有文案和数据是否来自已批准输入。
2. 画面层：关键帧、可读性、层级和边距是否符合任务书。
3. 工程层：依赖、路径、组件边界和验证命令是否符合仓库约定。

反馈也使用可检查语言，例如“第 `{帧}` 帧副标题越过右侧安全边距”，而不是“再克制一点”。如果需求本身变化，先更新任务书，再要求修改代码。

## 结论与限制

可执行的 Remotion 提示词更接近一份小型任务书：范围限定改动，来源约束事实，规格和时间线定义画面，视觉和代码规则控制实现，验收说明怎样证明完成。七个字段共同减少代理自行补全需求的空间。

任务书不能替代视觉判断、素材授权和目标环境渲染。最终画面仍需人工逐帧抽查，交付文件仍需在实际播放器和发布渠道中验证。
