# GPT-6.1 Terra 的成本结构：$0.05 缓存输入与六档推理强度怎么算

GPT-6.1 Terra 的输入价是 $1 / MTok，缓存输入价 $0.05 / MTok——**折扣 95%**。这个比例比多数人预期的狠，也最容易算错：缓存不是按次数打折，而是按前缀是否被复用；推理档位不是免费的开关，而是直接改写 token 数量。

这篇只做一件事：把 Terra 的价目表拆到能算单任务成本的程度，并给出两种复算方法。价格引自 OpenAI 官方定价页，检索 2026-10-27。

## 一张表看全三套价格

每 MTok，Terra 的官方价目如下：

| 计费项 | 标准 | Batch（5 折） | Fast |
| --- | --- | --- | --- |
| 输入 | $1.00 | $0.50 | $2.00 |
| 缓存输入 | $0.05 | $0.025 | $0.10 |
| 输出 | $5.00 | $2.50 | $10.00 |
| 缓存写入 30m | $1.25 | $0.625 | $2.50 |
| 缓存写入 12h | $2.50 | $1.25 | $5.00 |

来源：[OpenAI 定价页](https://platform.openai.com/docs/pricing)，检索 2026-10-27。

三点读法。

**缓存输入是输入价的 5%。** $0.05 对 $1.00。这不是"打折"，是数量级的差异：一个稳定前缀每次重发的成本几乎可以忽略，前提是它真的命中。

**Batch 是全线五折。** 输入、输出、缓存、写入同步减半，适合离线批处理。代价是时效性，官方把它与标准档并列而不是并列可选。

**Fast 是全线双倍。** 注意缓存价也翻倍（$0.05 → $0.10）。如果你因为"要快"而整体切到 Fast，缓存带来的节省同样被削半，别只算输入输出的两倍。

另有一条容易被忽略的加价规则：2026-03-05 及之后发布的模型，Regional processing（数据驻留）与 FedRAMP 端点统一加价 10%。Terra 属于这一批。

## 缓存写入为什么要分两档

Terra 的缓存写入按存活时长分 30 分钟与 12 小时两档，价格分别是 $1.25 与 $2.50 每 MTok。这是"保留这份前缀"的一次性成本，不是每次命中都收。

| 场景 | 建议档位 | 判断依据 |
| --- | --- | --- |
| 一个会话内连续追问 | 30m | 命中会续期，间隔短时 12h 白贵一倍 |
| 人工介入、间隔可能超过半小时 | 12h | 避免反复重写 |
| 每天只跑一批离线任务 | 12h 或干脆不缓存 | 命中次数不足以摊薄写入费 |

判断门槛可以照这个算式：**多付的写入费 ÷ 单次命中省下的差价 = 需要的命中次数**。按 Terra 的数：12h 比 30m 多付 $1.25，每次命中省 $0.95（$1.00 − $0.05），所以 **12h 至少要在有效期内命中 2 次才比 30m 划算**（1.25 ÷ 0.95 ≈ 1.32，取整 2）。命中越多越赚。

## 算例一：10 万 token 前缀，100 次请求

假设固定前缀 100k tokens（产品文档 + 系统提示），每次追加 1k 的用户输入、输出 2k tokens，共 100 次请求，全部在缓存有效期内完成。

| 方案 | 计算 | 成本 |
| --- | --- | --- |
| 不缓存 | 100 × (100k × $1 + 1k × $1 + 2k × $5) ÷ 1e6 | $11.10 |
| 30m 缓存 | 写入 100k × $1.25 ÷ 1e6 = $0.125；99 次 × (100k × $0.05 + 1k × $1 + 2k × $5) ÷ 1e6 | 约 $1.32 |
| Batch + 缓存 | 上述各项按五折 | 约 $0.72 |

差额接近一个数量级，但结论不是"一定要开缓存"，而是：**这段前缀本来就是重复内容，不复用等于重复付费**。如果前缀每天只被复用一次，写入费反而变成纯支出。

## 算例二：推理档位才是最大变量

Terra 有六档 `reasoning.effort`：`none` / `low` / `medium` / `high` / `xhigh` / `max`。档位对成本的影响不是线性的，因为推理 token 计入输出计费，而输出是 $5 / MTok。

官方给了一组可以当锚点的数据：在内部"易错提示"基准上，低档错误率从 GPT-5.6 Terra 的 53.6% 降到 Terra 的 16.7%，max 档再降到 4.3%。也就是说，**从 low 升到 max，错误率降了 12.4 个百分点，但推理 token 会增加**。这两个方向必须一起看。

第三方评测给了另一个视角：Artificial Analysis 在 Intelligence Index 上测得 Terra（max）累计输出 130M tokens，而同类中位数是 81M，评价是"somewhat verbose"。同一页面给出的每任务成本是 **$0.40**，缓存折扣 95%，与官方价目一致。

结论很简单：**档位该按任务的容错度选，不该一律用 max**。抽取字段、格式转换、分类打标用 `none` 或 `low`；需要解释判断依据时上 `medium`；只有当前两档明显判错、且错的代价高于 token 差价时才上 `max`。

六个档位的适用面与风险写在一起更好用：

| 档位 | 适用 | 风险 |
| --- | --- | --- |
| `none` | 抽取、分类、格式化、模板化改写 | 需要判断时容易编 |
| `low` | 短问答、简单多步操作 | 复杂因果链会断 |
| `medium` | 读屏操作、填单、图文问答（官方基准的主推档） | 成本开始上升 |
| `high` | 需要解释依据的分析类任务 | 延迟明显 |
| `xhigh` | 长链代理、多层判断 | token 消耗难预估 |
| `max` | 容错度极低的高价值任务 | 单任务成本可达低档的数倍 |

## 复算模板

拿到一次响应后，用下面这段把成本算出来，比看账单快得多：

```python
PRICE = {
    "standard": {"in": 1.00, "cached": 0.05, "out": 5.00, "write30m": 1.25, "write12h": 2.50},
    "batch":    {"in": 0.50, "cached": 0.025, "out": 2.50, "write30m": 0.625, "write12h": 1.25},
    "fast":     {"in": 2.00, "cached": 0.10, "out": 10.00, "write30m": 2.50, "write12h": 5.00},
}

def cost(tier, in_tok, cached_tok, out_tok):
    p = PRICE[tier]
    return (in_tok * p["in"] + cached_tok * p["cached"] + out_tok * p["out"]) / 1e6
```

其中 `in_tok` 只填未命中部分。缓存读取与未命中在 `usage` 里是两块，加错了会系统性高估成本。

## Batch 与 Fast 的适用边界

| 档位 | 适用 | 不适用 |
| --- | --- | --- |
| Batch（五折） | 离线分类、历史数据回填、批量生成 | 对话、computer use、任何需要即时反馈的链路 |
| 标准 | 绝大多数在线请求 | — |
| Fast（双倍） | 延迟直接影响转化的前端交互 | 后台任务（花了钱也感知不到） |

还有一个组合容易被忽略：Batch + 缓存。官方定价页把两列并列，数值可以叠乘（输入 $0.50、缓存 $0.025、输出 $2.50）。离线回填历史数据时这是最便宜的一档，但它同时也把“命中后立即重试”这类交互式补救排除在外了。

## 怎么确认缓存真的命中了

省不省钱取决于命中，而命中取决于前缀是否逐字节一致。三件事按顺序检查：

1. 看响应里的 usage 明细，确认 cached tokens 是否大于 0（Responses API 的字段名以当期文档为准）。
2. 对比同一前缀连续两次请求的 usage，命中部分应从第二次开始明显上升。
3. 若命中始终为 0，回到请求体检查前缀有没有被迫变化。

前缀被迫变化的常见原因，按出现频率排：

| 原因 | 表现 | 修法 |
| --- | --- | --- |
| 前缀里塞了时间戳、随机 ID、请求序号 | 每次都算首次写入 | 动态字段移到用户消息里 |
| 每轮重排工具定义或文档顺序 | 内容相同但前缀不同 | 固定顺序 |
| 把用户信息拼进 system prompt | 每个用户一套前缀 | 用户信息放输入末尾 |
| 在历史中间删改消息 | 变更点之后全部失效 | 从最老轮次整段删 |
| 写入存活期设短于复用间隔 | 命中前就过期 | 改 12h 档 |

## 五个成本坑

**1. 把 Fast 当"同样的东西快一点"。** Fast 是全线双倍，包括缓存价。只在延迟真的影响转化时用。

**2. 只算输入输出，不算推理 token。** 推理 token 按输出计费，高档位的成本上涨主要来自这里，而不是用户可见的答案。

**3. 忽略冗长。** 第三方测得这代模型输出偏多（130M vs 中位数 81M）。输出单价是输入的五倍，冗长对小任务尤其致命。

**4. 把 Batch 用在交互链路上。** 五折是真的，时效性也是真的。对话、computer use 这类需要即时反馈的场景不要用。

**5. 忘记地区加价。** 数据驻留与 FedRAMP 端点 +10%，如果业务需要，预算要按 1.1 倍而不是标准价算。

## 限制与结论

可以确定的是三套价格的相对关系（标准 : Batch : Fast = 1 : 0.5 : 2）、缓存输入为输入价 5%、写入分 30m/12h 两档，以及官方那组错误率与档位的关系。

不能确定的是你的实际命中率与推理 token 占比——这两个只能自己测。官方没有给出各档位对应的 token 消耗倍数，第三方的 verbosity 也只是 Index 任务上的统计。

可执行的做法：先固定前缀、固定档位，跑同一批任务两遍（一遍不缓存、一遍缓存），把 usage 里的三段数字记下来，换算成每任务成本；然后只调整档位再跑一遍。三步之后，你手上会有自己的三条曲线，比任何价目表都准。
