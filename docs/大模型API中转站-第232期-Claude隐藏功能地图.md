# Claude Projects、Chrome、Cowork 与 Code 怎么选

Claude Projects、Chrome、Cowork 与 Code 都能参与复杂任务，但它们负责的工作表面不同。Projects 组织长期主题的资料与指令，Chrome 面向当前浏览器页面，Cowork 面向文件和通用知识工作，Code 面向代码库、终端与测试。本文只解决四个入口之间的选择：先定位输入实际存放在哪里，再判断允许模型读取还是修改，最后写清交付物和验收方式。选择结果不是功能强弱排名，而是让任务使用足够且不过量的权限，并把首次验证限定在真实工作表面。

入口选错时，常见问题不是回答质量，而是上下文反复搬运、授权范围扩大，或结果无法在原工作环境中验证。

## 1. 先回答四个问题

不要先比较产品名称。先把任务写成四个可检查的问题：

```text
1. 资料要不要围绕同一主题长期保存？
2. 任务是否必须读取或操作当前网页？
3. 主要对象是普通文件，还是可运行的代码库？
4. 完成标准是生成一份成果，还是通过测试和版本差异验证修改？
```

四个入口分别对应不同的主要职责：

| 入口 | 主要工作表面 | 典型交付物 | 首要边界 |
| --- | --- | --- | --- |
| Projects | 同一主题的资料、指令和对话 | 有连续背景的分析或草稿 | 只放当前项目需要的资料 |
| Claude for Chrome | 已打开的网页与页面控件 | 页面采集结果或待确认表单 | 提交、发送、删除前人工确认 |
| Claude Cowork | 授权目录中的文档、表格和其他文件 | 汇总稿、整理后的文件或工作清单 | 限定读写目录并保留原件 |
| Claude Code | 代码库、终端、测试和版本控制 | 可审查的代码差异与测试结果 | 限定仓库、命令和修改范围 |

表格描述的是选型起点，不是永久能力承诺。实际入口和权限仍要按当前官方文档与账号界面复核。

## 2. 四个入口分别解决什么问题

### Projects

当同一主题会持续多次对话，并且每次都需要引用相同资料和固定指令时，先考虑 Projects。它适合一个产品、一个客户或一个研究专题，而不是把所有工作文件混在同一容器中。

Projects 解决的是上下文组织，不负责替你操作网页、批量改文件或运行代码。项目资料包含敏感内容时，仍需按来源、权限和保留期限管理。

### Claude for Chrome

当信息只存在于当前网页，或者任务必须在页面中导航、读取控件和预填表单时，Chrome 才是直接入口。只需分析已导出的文件时，不必额外授予浏览器访问。

浏览器页面可能包含不可信内容。第一次执行应从只读采集开始；发送、付款、删除、发布和权限修改不进入默认自动流程。

### Claude Cowork

当任务围绕授权目录中的文档、表格和其他普通文件展开，并需要跨文件汇总、整理或生成成果时，可以考虑 Cowork。任务书应明确输入目录、允许写入的位置、文件命名和失败时的保留方式。

Cowork 不等于代码验证环境。遇到需要依赖安装、测试命令、版本差异或代码审查的任务，应切换到 Code，而不是把工程验收省略掉。

### Claude Code

当任务对象是实际代码库，并且结论必须由搜索、修改、测试和版本差异证明时，选择 Code。它适合定位缺陷、修改实现、运行仓库规定的检查以及交付可审查的补丁。

如果任务只需要整理一组文档，代码工作台会扩大不必要的终端和仓库权限。使用前应写明允许修改的目录、禁止命令、测试入口和停止条件。

## 3. 最容易混淆的选择

### Projects 还是 Cowork

Projects 适合让多次对话共享同一主题背景；Cowork 适合对授权文件执行多步工作。

```text
问题是“下次对话还要引用哪些背景”，优先 Projects。
问题是“这批文件要怎样读取、整理和交付”，优先 Cowork。
```

### Chrome 还是 Cowork

数据仍在网页中且不能可靠导出时，先用 Chrome 做受控采集。数据已经导出为文件后，后续整理通常不再需要浏览器权限，可以交给 Cowork。

不要让 Chrome 一边采集一边直接做高风险提交。采集结果、分析结果和提交动作应分开验收。

### Cowork 还是 Code

两者都可能处理文件，区别在于验收证据。文档任务通常检查来源、结构和内容；代码任务还要检查依赖、类型、测试和版本差异。

只要完成条件包含“测试通过”“补丁可审查”或“仓库状态不受污染”，就应优先使用 Code。

### Chrome 还是 Code

页面故障可能同时涉及浏览器现象和代码实现。可以先在 Chrome 中保存复现步骤、控制台或网络证据，再把明确的工程问题交给 Code。两个入口之间传递的是证据和任务边界，不是整段无筛选的会话历史。

## 4. 按任务选择入口

| 任务 | 首选入口 | 原因 |
| --- | --- | --- |
| 持续研究同一主题并反复引用资料 | Projects | 主要问题是长期上下文组织 |
| 从多个网页采集公开字段并预填草稿 | Claude for Chrome | 信息和控件仍在浏览器页面 |
| 汇总授权目录中的会议稿和表格 | Claude Cowork | 工作对象是普通文件和知识成果 |
| 修复仓库缺陷并运行既有测试 | Claude Code | 结果需要代码差异和测试证据 |
| 根据网页故障证据修改前端代码 | Chrome 采证，Code 修改 | 观察与工程修改需要不同权限 |
| 将项目资料整理成周期简报 | Projects 提供背景，Cowork 处理文件 | 长期背景与文件执行职责分离 |

组合入口时，每个阶段都要有明确输入和输出。例如 Chrome 阶段只交付页面证据，Code 阶段只接收复现步骤和相关代码范围；不要因为最终会修改代码，就让浏览器阶段获得仓库写权限。

## 5. 从一个低风险任务开始验证

第一次选型可以使用同一套验收顺序：

```text
第 1 步：写出资料所在位置和最终交付物。
第 2 步：选择能直接接触该位置的最小权限入口。
第 3 步：只开放完成样例所需的页面、目录或仓库。
第 4 步：运行一次低风险样例并保存输入、输出和错误。
第 5 步：人工核对结果，再决定是否扩大范围或组合入口。
```

如果样例需要不断手工搬运信息，说明入口或阶段边界可能选错。如果样例已经能完成任务，也没有理由为了功能更多而扩大权限。

## 6. 选择前检查清单

```text
[ ] 已在 Projects、Chrome、Cowork、Code 中选定主要入口
[ ] 资料位置与交付物已经写清
[ ] 页面、目录、仓库和命令范围遵循最小权限
[ ] 读取、修改与外部提交没有混成一个授权
[ ] 发送、删除、付款、发布和权限变更保留人工确认
[ ] 文件成果有来源核对，代码成果有差异和测试证据
[ ] 组合入口之间只传递完成下一阶段所需的证据
[ ] 产品入口和可用性已按当前官方文档复核
```

## 7. 结论与限制

四个入口可以用一句话区分：Projects 保存同一主题的长期背景，Chrome 接触当前网页，Cowork 处理授权文件和通用知识工作，Code 在代码库中修改并验证工程结果。

选择时先问资料在哪里，再问任务必须执行什么动作，最后用交付物和验收证据决定入口。需要组合时，让每个入口只负责一个阶段，并在阶段之间传递最少必要信息。

具体账号权限、产品入口和功能范围可能变化，本文不判断套餐、发布时间或功能数量。涉及敏感资料、外部提交和生产修改时，入口选择不能替代组织授权、人工确认和独立验收。
