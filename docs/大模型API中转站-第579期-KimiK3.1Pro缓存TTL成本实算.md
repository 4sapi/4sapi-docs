# Kimi K3.1 Pro 上下文缓存的成本账：5m 与 1h TTL 怎么选

Kimi 开放平台把上下文缓存拆成了独立计费项：写入（Cache Write）分 `5m` 和 `1h` 两档，命中（Cached Input）单独定价。这个改动让账单更清楚，也让一个过去被忽略的问题浮上来——同样是"用了缓存"，选错 TTL 档位可能比不用缓存还费钱。

本文只回答一个问题：在 K3.1 Pro 上，什么时候该用默认的 `5m`，什么时候该显式传 `1h`，以及怎么确认缓存真的命中了。所有单价与字段名引自 Kimi 官方文档，检索日期 2026-10-26，相关页面最后更新 2026-10-23。

## 缓存的工作方式：只认前缀，按块存储

Kimi API 对重复的请求前缀自动启用上下文缓存，不需要手动创建，也不需要额外的开关。命中条件是"本次请求的前缀与上一次请求完全相同"，前缀中任何一处变化，该位置之后的内容都无法复用。

几条容易被忽略的机制：

| 机制 | 说明 | 实践含义 |
| --- | --- | --- |
| 前缀匹配 | 只认从头开始连续一致的部分 | 稳定内容前移，变动的放后面 |
| 块存储 | 缓存按块写入，不足一整块的部分按未命中计费 | 长前缀不会"刚好全部命中" |
| 自动续期 | 命中后按原 TTL 免费续期，续期不单独收费 | 间隔稳定的请求不需要换档 |
| TTL 锁定 | 条目首次写入时锁定 TTL，不可改写 | 想换档要等旧条目完全过期 |
| 两档不互通 | `5m` 与 `1h` 是两套缓存 | 混用会造成重复写入 |
| 组织隔离 | 缓存按 org 隔离，同组织内共享 | 多项目共享前缀能互补 |

来源：[上下文缓存最佳实践](https://platform.kimi.com/docs/guide/context-caching)，最后更新 2026-10-23。

## 先把单价摆清楚

K3 系列（上下文均为 1,048,576 tokens）的缓存相关单价如下，单位为每 1 MTok：

| 模型 | 输入（未命中） | 缓存命中 | 写入 5m | 写入 1h |
| --- | --- | --- | --- | --- |
| `kimi-k3.1-pro` | ¥13.00 | ¥1.30 | ¥13.00 | ¥26.00 |
| `kimi-k3.1-pro-highspeed` | ¥26.00 | ¥1.30 | ¥26.00 | ¥52.00 |
| `kimi-k3` | ¥20.00 | ¥2.00 | ¥20.00 | ¥40.00 |

来源：[模型推理价格说明](https://platform.kimi.com/docs/pricing/chat)，最后更新 2026-10-23。

三点读法。

**命中价约为未命中价的 1/10。** K3.1 Pro 是 13 降到 1.3，K3 是 20 降到 2。这个比例决定了缓存的经济性上限：命中率越高，输入成本越接近那个 1/10。

**5m 写入价等于输入价。** K3.1 Pro 的写入 5m 是 ¥13，与未命中输入同价。也就是说，用默认档时"第一次写缓存"没有额外惩罚——它就是你本来就要付的那次输入费用。官方对此的表述是：缓存写入的拆分是计费透明化，写入成本原先就包含在输入价格中，拆分后现有请求的整体费用不变。

**1h 写入价是输入价的 2 倍。** K3.1 Pro 是 26 对 13。多出来的这部分，是为了"跨过 5 分钟间隔还能复用"而预先支付的保险。这笔保险值不值，取决于后续命中几次。

这组比例有一个外部交叉验证：Artificial Analysis 的 K3.1 Pro 模型页在价格栏直接标了 **Cache Discount 90%**，与官方"命中价约为未命中价 1/10"的描述一致（[模型页](https://artificialanalysis.ai/models/kimi-k3-1-pro)，检索 2026-10-26）。两个独立口径对得上，你计算时就可以放心用 1/10 这个比例。

但要记住缓存只作用于输入。同一个页面上，K3.1 Pro 在 Intelligence Index 中的总输出量是 150M tokens（同组中位数 87M），输出偏多这件事缓存帮不上忙。

## 两档 TTL 的命中门槛

判断逻辑可以用一句话概括：1h 比 5m 多付的写入费，要由后续每次命中省下的差价补回来。

按 K3.1 Pro 的官方单价推算：

- 多付的写入费：¥26 - ¥13 = **¥13 / MTok**
- 每次命中省下的差价：¥13 - ¥1.30 = **¥11.70 / MTok**
- 回本所需命中次数：13 ÷ 11.7 ≈ 1.11，取整后为 **2 次**

也就是说，同一个前缀如果在 1 小时内还会再命中 2 次以上，选 `1h` 比 `5m` 更省；命中 2 次时净省约 ¥10.4 / MTok；只命中 1 次，净亏约 ¥1.3 / MTok。

官方在 K3 上给出的算例是同一个结构（多付 ¥20、每次省 ¥18、命中 2 次净省 ¥16），数值不同是因为 K3 的单价不同。用你自己的模型单价套上面的三步即可，不必记结论。

据此可以给出分档规则：

| 请求间隔 | 建议 | 理由 |
| --- | --- | --- |
| 稳定小于 5 分钟 | 默认 `5m` | 命中会自动续期，无需换档 |
| 可能超过 5 分钟、1 小时内会复用 | 显式传 `1h` | 避免过期后重复写入 |
| 通常超过 1 小时才复用 | 不必专门配置 | 写入费收不回来 |

第三种情况很多人忽略：不是"配了缓存就一定省"。如果同一个前缀一天才用一次，缓存写入就是纯亏损，不如让它按普通输入计费。

## 怎么设置

Chat Completions API 与 Responses API 都用 `prompt_cache_options`，省略时默认按 `5m` 写入：

```bash
curl https://api.moonshot.cn/v1/chat/completions \
  --header "Content-Type: application/json" \
  --header "Authorization: Bearer $MOONSHOT_API_KEY" \
  --data '{
    "model": "kimi-k3.1-pro",
    "messages": [
      {"role": "system", "content": "你是一个产品文档问答助手。\n\n产品文档：……"},
      {"role": "user", "content": "这个产品支持哪些认证方式？"}
    ],
    "prompt_cache_options": {"mode": "implicit", "ttl": "1h"}
  }'
```

`mode` 当前仅支持 `implicit`。Anthropic Messages API 走另一套字段，用顶层 `cache_control` 设置，消息体内的同名标记会被忽略：

```json
{
  "model": "kimi-k3.1-pro",
  "cache_control": {"type": "ephemeral", "ttl": "1h"},
  "max_tokens": 256,
  "messages": [{"role": "user", "content": "你好"}]
}
```

如果通过 Codex、Claude Code 这类工具接入，通常由工具自己发请求，你控制不了 `prompt_cache_options`。这种情况下能调的是"请求节奏"和"前缀稳定性"，而不是 TTL 档位。

## 怎么确认真的命中了

不要靠"账单看起来变便宜了"判断。三个 API 用三套字段：

| API | 总输入 | 缓存读取 | 缓存写入 |
| --- | --- | --- | --- |
| Chat Completions | `usage.prompt_tokens` | `usage.prompt_tokens_details.cached_tokens` | `usage.prompt_tokens_details.cache_write_tokens` |
| Responses | `usage.input_tokens` | `usage.input_tokens_details.cached_tokens` | `usage.input_tokens_details.cache_write_tokens` |
| Messages | `usage.input_tokens + cache_read_input_tokens + cache_creation_input_tokens` | `usage.cache_read_input_tokens` | `usage.cache_creation_input_tokens` |

两个易错点：

一是流式请求。Chat Completions 的流式调用需要设置 `stream_options.include_usage=true`，完整的缓存读写明细才会出现在最后一个 chunk 的 `usage` 里。不设这个参数，前面的 chunk 里看不到用量，很容易误判为"没有缓存"。

二是加总关系。对 Chat Completions 和 Responses，缓存读取、缓存写入和未缓存部分是互斥的，三者之和等于总输入 token 数。对账时如果对不上，说明统计口径被自己算错了，而不是平台算错。

还有一个只看单次请求看不到的信息：本次写入用的是哪一档 TTL。可以读响应头 `Msh-Usage-Cache-Write-Tokens-5m` 和 `Msh-Usage-Cache-Write-Tokens-1h`，全部命中、没有新增写入时对应值为 0。

来源：[上下文缓存最佳实践](https://platform.kimi.com/docs/guide/context-caching)。

## 一个 100k 前缀的实算

假设一个文档问答服务：固定前缀 100k tokens（产品文档 + system prompt），每天 200 次请求，请求间隔约 3 分钟。

按 K3.1 Pro 的 `5m` 档：

| 计费项 | 计算 | 金额 |
| --- | --- | --- |
| 首次写入 | 100k × 13 ÷ 1e6 | 1.30 元 |
| 后续 199 次命中 | 199 × 100k × 1.30 ÷ 1e6 | 25.87 元 |
| 合计 | — | 约 27.2 元 |

同样 200 次请求，如果前缀完全不复用（每次按未命中计）：

| 计费项 | 计算 | 金额 |
| --- | --- | --- |
| 200 次未命中 | 200 × 100k × 13 ÷ 1e6 | 260 元 |

差额约 9.6 倍。这个倍率不是"缓存帮你省了 90%"，而是"这段前缀本来就是重复内容，不复用相当于重复付费"。两者含义不同，前者容易变成宣传语。

间隔 3 分钟用 `5m` 就够，因为每次命中都会把有效期重新算成 5 分钟。改传 `1h` 在这里没有收益：多付 ¥13 / MTok 的写入费，省不出额外的东西。

## 命中率归零的五种写法

下面五种改动都会让前缀失效，而它们在代码评审里都不显眼。

**1. 前缀里塞时间戳或随机 ID。** 常见于"每次请求注入当前时间"。前缀一变，后面全部重算，等于每次都是首次写入。

**2. 每轮重新排序工具定义或参考资料。** 内容没变但顺序变了，前缀就算不同。固定顺序是低成本的高收益动作。

**3. 把变化的用户信息拼进 system prompt。** 用户名、租户 ID 这类字段应该放在后面的 user 消息里，而不是前缀中。

**4. 在历史中间删改消息。** 任何中间位置的插入或修改，都会让变更点之后的缓存失效。要裁剪就从最老的轮次整段删起。

**5. 频繁切换 `reasoning_effort` 档位。** 官方明确提示切档会破坏前缀缓存，建议在会话开始前确定档位。

配合官方给的正向做法：稳定内容（system prompt、工具定义、参考资料、代码库）放前部，变化内容（问题、工具结果、任务状态）放后部；定时任务的间隔控制在 TTL 内；不要在前缀里放动态字段。

## 对账时该看的三个数字

如果账单和预期对不上，按这三个数字查，比逐条翻请求明细快。

| 数字 | 从哪看 | 说明什么 |
| --- | --- | --- |
| 命中率 | 控制台 Caching 概览页 | 前缀是否真的被复用 |
| 写入摊销倍数（命中 ÷ 写入） | 同上 | 数值越大缓存越划算 |
| 输入三段加总 | `usage` 字段 | 是否等于总输入，统计口径是否正确 |

控制台还提供月度账单导出，新增了"账单明细-缓存写入"页，按天区分 5m 与 1h 两档写入费用；请求明细里新增"写缓存 Tokens(5min)"和"写缓存 Tokens(1h)"两列。如果账单里的缓存写入金额和你的请求日志对不上，先查这两列的时间边界（跨天、跨时区）。

## 通过统一网关时的额外验证

如果请求经过聚合网关，缓存相关字段是最容易在转发过程中丢失的部分。要单独验三件事：`usage` 是否保留三段明细、`prompt_cache_options` 是否被透传、响应头 `Msh-Usage-Cache-Write-Tokens-*` 是否还在。

以可替换实例来说，若通过 4SAPI 这类统一入口调用，参数支持范围以该平台控制台当期显示为准。缺失明细不代表"没有命中"，只代表你失去了观测手段——这种情况下的成本优化只能靠猜。

## 限制与结论

缓存能省的钱有上限：命中部分最低降到未命中价的 1/10，省不下输出费用。如果任务以生成长文为主，缓存对总成本的影响有限，优先优化的是输出长度和 `reasoning_effort` 档位。

另外两条硬约束：不是所有模型都支持缓存写入，官方明确 `kimi-k3.1-pro` 与 `kimi-k3` 支持，K2.7 与 K2.6 系列不支持；缓存在当前接口下不能手动清除，只能等 TTL 过期，这意味着错误的写入策略要付出时间代价才能纠正。

如果要给一个可执行的结论：默认用 `5m`，只在"请求间隔会超过 5 分钟、且 1 小时内还能复用 2 次以上"时显式传 `1h`；前缀稳定性比档位选择更重要，把时间戳和随机字段从前缀里清出去，收益通常大于换档。

下一步建议：挑一条线上真实请求，把 `usage` 三段和两个响应头打出来，连续发三次同样的前缀。如果第二次、第三次的命中 token 数没有显著上升，问题在请求构造，不在价格表。
