# 【大模型API中转站】第199期 设计工作流成本治理 | MCP日志与预算

本文是【大模型API中转站】系列的第199篇。本系列致力于用最低的成本、最清晰的方法，帮你打通多模型API的任督二脉。建议先收藏，随用随查。

Open Design 接 Codex 后，最容易被低估的问题是：

```text
设计工作流会花很多 token。
```

不是因为工具浪费。

而是设计任务天然多轮。

一次看似简单的需求：

```text
帮我做一个企业官网首页。
```

背后可能拆成：

```text
理解业务。
提炼卖点。
选择设计系统。
生成页面结构。
写 HTML/CSS。
自我审查。
根据反馈修改。
导出交付。
再接入工程。
```

如果每一步都直接调用高级模型，成本会很快失控。

所以企业级大模型接入不能只问：

```text
能不能生成？
```

还要问：

```text
谁生成的？
用什么模型生成的？
花了多少钱？
失败几次？
重试几次？
结果有没有被采用？
```

这篇就写设计类 Agent 工作流怎么做成本治理。

## 1. 设计 Agent 为什么容易贵

普通 API 调用通常是：

```text
一次输入。
一次输出。
```

设计 Agent 工作流通常是：

```text
多轮理解。
多文件生成。
多次工具调用。
多次预览修正。
多次导出。
```

成本来源包括：

```text
长需求文档。
品牌资料。
设计系统。
参考案例。
历史对话。
HTML / CSS / JSX 文件。
截图分析。
多轮修改。
高级模型审查。
```

尤其是 Open Design 这类工具，会把设计做成项目。

这是好事。

但如果不治理，项目上下文会越来越长。

最后每次修改都带上：

```text
完整文件。
完整设计系统。
完整聊天记录。
完整需求背景。
```

成本自然上升。

## 2. 先给设计任务分层

不要所有阶段都用同一个模型。

建议分四层：

| 阶段 | 适合模型 | 目标 |
| --- | --- | --- |
| 需求整理 | 低成本模型 | 把 brief 压成结构化任务 |
| 初稿生成 | 中等模型 | 生成可预览 artifact |
| 关键审查 | 高级模型 | 判断信息架构、视觉一致性、风险 |
| 工程落地 | Codex | 拆组件、接 API、改代码 |

高级模型应该用在：

```text
方向判断。
复杂审查。
重要交付。
高价值客户。
上线前检查。
```

不应该用在：

```text
整理资料。
重复改文案。
批量改颜色。
简单生成占位页。
无价值试错。
```

这也是 4SAPI 模型路由的价值。

它可以按：

```text
project
task_type
model
key_group
budget
```

把不同任务路由到不同模型。

## 3. MCP 日志要和模型日志打通

Open Design MCP 会产生这些关键动作：

```text
create_project
start_run
get_run
get_artifact
write_file
```

4SAPI 会记录模型调用。

要做成本治理，就要把两边串起来。

建议每条模型调用都能关联：

```text
project_id
project_name
run_id
conversation_id
agent
model
task_type
request_id
owner
```

如果只记录模型名和金额，不够。

你只能知道：

```text
今天 Fable 5 花了多少钱。
```

但你不知道：

```text
是哪个设计项目花的。
是哪次 start_run 花的。
是初稿生成还是最终审查。
有没有产出 artifact。
有没有被下载或接入工程。
```

企业成本治理必须追到项目和任务。

## 4. 建议记录的字段

设计工作流建议记录两张表。

第一张是运行表：

```text
run_id
project_id
project_name
owner
agent
skill
plugin
design_system
prompt_hash
started_at
finished_at
status
artifact_count
preview_url
```

第二张是调用表：

```text
request_id
run_id
project_id
key_group
model
task_type
input_tokens
output_tokens
cost
latency_ms
status_code
error_type
retry_count
fallback_model
```

这样你能回答：

```text
哪个项目最贵？
哪个 skill 最贵？
哪个设计系统导致上下文最长？
哪个 owner 触发最多高级模型？
哪类任务失败率最高？
哪些 artifact 生成了但没人用？
```

这才是经营视角。

## 5. 给不同项目设置预算

不要只设置全局预算。

设计任务应该按项目分预算。

比如：

```text
官网改版：每日 20 元。
销售物料：每日 10 元。
内部 dashboard：每日 5 元。
客户定制方案：单项目 50 元。
实验项目：每日 2 元。
```

预算动作分三档：

```text
70%：提醒 owner。
90%：降级模型。
100%：停止自动生成，转人工确认。
```

如果接入 4SAPI，可以在中转层做：

```text
Key 分组。
模型路由。
预算控制。
限流。
日志审计。
```

不要等月底账单出来再复盘。

设计工作流要当天看。

## 6. 重试是成本黑洞

设计生成失败后，最危险的动作是：

```text
直接再来一次。
```

因为失败可能不是偶发。

可能是：

```text
Prompt 太长。
设计系统上下文太大。
模型不适合当前任务。
工具调用失败。
artifact 保存失败。
输出格式不符合要求。
```

如果不看原因直接重试，就会：

```text
重复花钱。
重复失败。
污染队列。
让用户以为系统卡住。
```

建议：

```text
最多自动重试 1 次。
重试前压缩上下文。
重试时保留 original_request_id。
高成本模型重试前需要确认。
连续失败转人工排查。
```

日志字段要有：

```text
retry_count
original_run_id
original_request_id
retry_reason
cost_after_retry
```

否则你看不到重试浪费。

## 7. 设计质量也要进日报

成本治理不是只看省钱。

还要看产出。

设计任务可以记录：

```text
artifact 是否生成。
preview 是否打开。
是否被下载。
是否进入工程仓库。
是否被人工修改。
是否最终发布。
```

这样才能判断：

```text
贵但有用。
便宜但返工多。
失败但值得继续优化。
成功但没人采用。
```

比如：

```text
一个客户提案页花了 8 元，但直接用于销售演示。
一个内部实验页花了 30 元，但没有人打开。
```

两者的治理动作完全不同。

不要把所有成本都看成坏事。

要看成本是否换来了交付。

## 8. 每日设计工作流成本日报

日报可以这样写：

```text
# 设计工作流成本日报

日期：
总成本：
总运行数：
成功率：
平均单次成本：
Top 项目：
Top 模型：
Top owner：
失败最多任务：
重试最多任务：
未被使用 artifact：
建议动作：
```

异常卡片示例：

```text
project: 官网改版
owner: marketing-team
run_count: 12
cost: 36.8
main_model: Fable 5
retry_count: 9
main_reason: 每次修改都携带完整品牌资料和全量 HTML
action: 先用低成本模型压缩 brief，Fable 5 只做最终审查
deadline: 今日
```

这比一句“成本升高”有用。

## 9. 给 AI 的成本分析 Prompt

```text
你是企业设计工作流成本治理助手。

请根据 Open Design 运行表和 4SAPI 模型调用表，生成日报。

要求：
1. 先给总览：总成本、运行数、成功率、平均单次成本。
2. 找出成本 Top 项目、Top 模型、Top owner、Top skill。
3. 找出异常：重试过多、失败率高、长上下文、未被使用 artifact、高级模型滥用。
4. 给止血动作、优化动作、投资动作。
5. 不要只建议“少用模型”，要指出具体 task_type 和 owner。
6. 不展示完整 API Key，不泄露用户隐私。
```

这个 Prompt 可以每天自动跑。

低成本模型先生成日报。

高级模型只审查最贵的几条异常。

## 10. 三类治理动作

日报最后一定要落动作。

我建议分三类。

第一类，止血动作：

```text
暂停异常 Key。
限制高级模型。
降低并发。
取消自动重试。
把长任务转人工确认。
```

第二类，优化动作：

```text
压缩设计系统上下文。
沉淀常用模板。
把初稿生成换成中等模型。
把文案批量修改交给低成本模型。
把重复任务做成 plugin。
```

第三类，投资动作：

```text
保留高价值客户方案的高级模型审查。
保留上线前的设计一致性审查。
保留能减少工程返工的 Codex 落地检查。
```

成本治理不是一刀切。

它的目标是：

```text
把钱花在能减少返工、提高交付质量、缩短周期的地方。
```

## 11. 企业权限设计

建议把设计工作流权限分层。

普通成员：

```text
可以读取项目。
可以 get_artifact。
可以发起低成本模型生成。
不能删除项目。
不能无限 start_run。
```

项目负责人：

```text
可以发起高级模型审查。
可以提高单项目预算。
可以批准重试。
可以导出交付物。
```

管理员：

```text
可以管理 Key 分组。
可以配置模型路由。
可以查看全局日志。
可以停用异常项目。
```

MCP 工具很强。

尤其是：

```text
write_file
delete_file
delete_project
start_run
```

企业使用时不要默认全部开放给所有人。

## 12. 上线前预算清单

```text
是否按项目设置预算。
是否按 owner 记录成本。
是否按 task_type 统计调用。
是否限制高级模型频率。
是否限制单次上下文长度。
是否限制自动重试次数。
是否记录 run_id 和 request_id。
是否能追踪 artifact 是否被使用。
是否有日报。
是否有预算告警。
是否有人工确认节点。
```

如果这些都没有，Open Design 和 Codex 仍然可以试用。

但不建议直接变成企业生产流程。

## 13. 总结

设计类 Agent 工作流的成本治理，核心不是少用。

而是：

```text
知道每次生成属于哪个项目。
知道每次调用用了哪个模型。
知道失败和重试花了多少钱。
知道生成结果有没有被采用。
知道哪些任务值得继续投资。
```

Open Design 负责把设计变成项目和 artifact。

Codex 负责把 artifact 接到真实工程。

4SAPI 负责把模型调用、Key 权限、日志审计和预算控制统一起来。

一句话：

```text
设计工作流可以大胆试，但一定要按项目、模型、任务和负责人把账算清楚。
```
