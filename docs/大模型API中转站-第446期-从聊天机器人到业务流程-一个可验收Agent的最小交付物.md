# 从聊天机器人到业务流程：一个可验收 Agent 的最小交付物

演示里的 Agent 能对话、能检索、能调用工具，项目仍不算交付。进入业务流程后，接手的人得知道它解决什么任务、依据哪些资料、能做哪些动作、出错交给谁、改动后怎么验证、紧急时怎么停。单独一个 Prompt、链接或录屏回答不了这些问题。

本文给出一份最小交付包。不要求团队一开始就建完整平台，也不把文件数量当成熟度；每份材料只服务于一个决定：是否启用、谁负责、能否复核、出错怎样处理、后续怎样变更。它承接第 439 至 445 期，把观测、复盘、安全、身份、资料边界和灰度发布落到可以交接的项目材料上。

## 一、先定义“交付”的边界

Agent 交付要证明下面这条链路在已声明范围内成立，不只是“模型已经接通”：

```text
真实业务任务
  -> 受控输入与资料
  -> 受限 Agent 行为和身份
  -> 可观察结果与人工接管
  -> 可重复验收与变更管理
```

只要其中一环说不清，项目状态就应写成“原型可演示”或“试点运行中”，不能写“已完成生产交付”。这会直接影响后续用户能不能安全使用它。

## 二、最小交付包包含八项材料

| 材料 | 要回答的问题 | 最小内容 |
| --- | --- | --- |
| 任务说明 | Agent 解决什么，不解决什么 | 用户、触发点、输入、输出、非目标、停止条件 |
| 流程与责任 | 谁在何时接手与决定 | 当前流程、Agent 介入点、RACI 或 Owner 表 |
| 资料边界 | 能依据什么，不能读取什么 | 来源、时效、范围、敏感等级、资料 Owner |
| 身份与工具矩阵 | 以谁的身份执行哪些动作 | 执行身份、资源、权限、工具、副作用、撤销 |
| 验收任务集 | 如何证明当前范围可用 | 正常、边界、资料不足、越权、失败和重复样例 |
| 运行手册 | 日常怎么观察、排错与接管 | 指标口径、告警、人工操作、回退 |
| 变更记录 | 改了什么，为什么，影响什么 | 版本、范围、风险、回归和批准 |
| 交接与培训 | 新团队怎样开始使用与维护 | 入口、权限申请、演练、联系人、未决项 |

这些材料可以放在 Markdown、工单、代码库文档或组织已有系统里，不必另建一个“Agent 管理平台”。要求只有两个：彼此能链接，并且能回到权威来源。

## 三、任务说明要写出非目标和停止条件

任务说明不应只是“使用 AI 提升效率”。用一张任务卡固定边界：

```markdown
# 任务：内部支持回复草稿

使用者：指定支持团队
触发点：收到符合分类规则的内部工单
输入：工单正文与已批准产品资料
输出：带来源的回复草稿和待确认项
允许动作：读取、生成、写入草稿区
禁止动作：外部发送、修改工单状态、读取客户受限资料
人工接管：资料不足、来源冲突、权限拒绝、格式检查失败
停止条件：未授权访问、无法回溯来源、重复写入或关键事实错误
验收：固定任务集、人工抽检和运行记录
```

非目标让团队知道哪些需求不应在试点中悄悄加入；停止条件让团队在异常发生时不用临时争论是否继续。任务说明每次扩大范围或增加副作用后都应更新，并触发相应回归。

## 四、责任不等于“由 AI 项目组负责”

Agent 项目至少要明确四类 Owner：

| Owner | 主要责任 | 不能替代谁 |
| --- | --- | --- |
| 业务 Owner | 任务价值、用户采用、人工接管与范围决定 | 不替代资源或技术审批 |
| 资料 Owner | 内容时效、适用范围、访问边界 | 不替代业务流程决定 |
| 技术 Owner | Agent、工具、身份、日志、回退与版本 | 不替代业务验收 |
| 风险或审批 Owner | 高风险动作、例外访问与升级处理 | 不替代日常运行维护 |

一个人可以兼任多个角色，但责任名称不能含糊。出错时，技术 Owner 修机制，资料 Owner 确认事实是否过期，业务 Owner 决定结果还能不能进入流程。没有这层拆分，所有问题最后都会落到最会操作 Agent 的人身上。

## 五、验收包要保留“失败时怎么办”

第 438 期讨论了任务集和回归。交付时至少附上：

```text
当前通过的任务范围和版本。
尚未覆盖的任务、资料和副作用。
已知失败模式、人工接管方式和停止条件。
最近一次验收时间、样例、执行环境和结果。
每次变更后需要重跑哪些任务。
```

验收结论必须带条件。比如“草稿任务通过”不能被理解为“允许自动发送”；“在测试资料上通过”不能替代真实资料范围内的灰度结果。把未覆盖部分留在交付包中，不是示弱，而是防止下一位接手人把试点能力误当成全量授权。

## 六、运行手册应短到在事故中能用

运行手册不用写成宏观方案，重点是把动作写到能照着做：

```text
日常查看：任务终态、人工接管、错误类别、资源异常。
异常排查：如何通过 task_id 和 run_id 找回版本、工具与来源。
人工接管：怎样完成或取消正在进行的任务。
停止与回退：关闭哪些工具、身份或范围，如何验证已生效。
凭证与权限：谁能申请、轮换、撤销和检查访问。
升级路径：业务、资料、技术和安全问题分别联系谁。
```

手册中的命令、链接和联系人应定期演练。一个从未被验证过的回退路径，不能在上线文档里被当作可靠控制。

## 七、让变更有单独的入口

模型、Prompt、Skill、知识资料、MCP 工具、身份策略和业务流程的变化都可能改变 Agent 行为。每次变更至少记录：

| 字段 | 说明 |
| --- | --- |
| 变化内容 | 改了什么版本、规则或范围 |
| 变化原因 | 解决什么问题或响应什么业务变更 |
| 影响评估 | 涉及哪些任务、资料、身份和副作用 |
| 验证 | 重跑哪些回归任务，结果是什么 |
| 批准与发布时间 | 谁有权批准，何时生效 |
| 回退 | 出现异常时回到什么状态 |

不要把“只改了一句 Prompt”当作免于评估的理由。只要它可能改变工具选择、拒绝边界、资料使用或下游输出，就应按受影响范围验证。

## 八、用一次交接演练检验交付物

最好的验收不是原开发者对着自己的材料操作，而是让一个未参与实现的人完成一次受控交接：

```text
1. 根据任务说明复述范围、非目标和停止条件。
2. 找到自己的权限申请方式和可访问资料范围。
3. 在测试环境执行一个正常任务和一个资料不足任务。
4. 通过日志找到任务的 Agent、资料、工具和身份记录。
5. 模拟工具失败或权限拒绝，按运行手册转人工或回退。
6. 查看变更记录，说明下一次修改需要运行什么回归。
```

演练时找不到材料、解释不清权限，或者不敢执行回退，都说明交付包还没完成。先补文档和流程再演练，成本总比在真实事故里第一次找答案低。

## 九、按成熟度如实命名当前状态

以下状态可以帮助团队避免过早承诺：

| 状态 | 含义 |
| --- | --- |
| 演示原型 | 可展示主要能力，未在真实流程验证 |
| 受控试点 | 范围、资料和用户有限，人工接管明确 |
| 受限运行 | 白名单任务可运行，有观测、回退与责任人 |
| 生产能力 | 在批准范围内持续运行，变更和事故流程已形成闭环 |

这些词不是认证等级。它们的作用是让业务和技术团队对当前证据保持一致，防止把一个“能聊天的原型”当作已经具备所有业务授权的系统。

## 十、建议的交付目录

```text
agent-delivery/
  task-card.md
  scope-and-owners.md
  data-boundary.md
  identity-and-tools.md
  evals/
    task-set.md
    latest-result.md
  operations/
    dashboard-metrics.md
    incident-and-rollback.md
  changes/
    changelog.md
  handover/
    onboarding.md
    open-items.md
```

目录只是一种组织方式。关键材料也可以分布在代码仓库、工单系统和知识库中，但交接页必须能链接到它们，并说明哪一个才是当前权威版本。

## 十一、交付前检查清单

```text
[ ] 任务说明包含用户、输入、输出、非目标、人工接管和停止条件。
[ ] 业务、资料、技术与风险 Owner 已明确，并能处理各自的决定。
[ ] 资料范围、时效、敏感性、用途和例外流程可追溯。
[ ] 执行身份、工具、副作用、审批和撤销方式已记录。
[ ] 验收任务覆盖正常、边界、资料不足、越权、失败和重复操作。
[ ] 验收结果包含版本、环境、范围和未覆盖项。
[ ] 运行手册能用于查看、接管、排错、停止和回退。
[ ] Prompt、模型、工具、资料和权限变更都有验证与回退记录。
[ ] 非实现人员已完成一次测试交接或演练。
[ ] 当前成熟度被如实标为原型、试点、受限运行或生产能力。
```

## 结论与资料

可验收的 Agent 交付物，是一组让不同角色能做决定的证据：它做什么、用谁的权限做、依据什么资料、怎么观察、什么时候交给人、出错怎么停、改动后怎么重验。记录和路径都齐了，Agent 才算从演示变成团队能够维护的业务流程。

- [NIST AI Risk Management Framework](https://www.nist.gov/itl/ai-risk-management-framework)：参考以治理和风险管理贯穿 AI 生命周期的框架。
- [Google SRE Book：Postmortem Culture](https://sre.google/sre-book/postmortem-culture/)：参考通过事实、行动项和学习闭环维持可靠运行的工程实践。
- [OWASP：Top 10 for Large Language Model Applications](https://owasp.org/www-project-top-10-for-large-language-model-applications/)：参考 AI 应用在提示注入、敏感信息与过度代理方面的风险类别。
