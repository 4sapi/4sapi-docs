# Particle-1 的单价是基座的数倍：token 要省多少才算真划算

OpenRouter 在 2026 年 10 月 28 日上架了 Particle-1。上架页的描述是：基于 DeepSeek V4.1 Flash 做后训练的智能体编码模型，完成任务时使用明显更少的推理和工具调用 token，准确率接近基座。

这句描述里有一个没有数字的形容词："明显更少"。而它的单价写得很清楚，比基座高出数倍。单价更高、用量更少的模型，到底会不会更省钱，取决于少多少。本文回答一个问题：Particle-1 要把总 token 用量削减到什么程度，才能与基座打平，以及怎么用自己的任务验证。

文章里的盈亏平衡数字是我用脚本算的，不是实测。Particle-1 实际省多少 token，我没有数据。信息截止日期为 2026-10-30，价格会变，请重新打开页面核对。

## 二、"省 token"的说法能核验到哪一步

上架页的原话是用"substantially fewer reasoning and tool-call tokens"完成任务，同时让准确率"close to its base model"。

可以确认的：这是 OpenRouter 上的模型描述。

不能确认的：

- "substantially"具体是多少，没有数字。
- "close"具体差多少，没有数字。
- 在什么任务集上测的，没有说明。
- 谁测的，没有说明。

所以本文不引用任何"省了百分之几"。下面做的是反过来的事：算出需要省多少才够本，然后你拿它去对照自己测到的数字。

## 三、盈亏平衡怎么算

### 单次任务成本

一次任务的成本等于：

```text
成本 = 输入量 × (1 − 缓存命中率) × 输入价
     + 输入量 × 缓存命中率 × 缓存价
     + 输出量 × 输出价
```

输入量和输出量以百万 token 计。在智能体循环里，输入量是每一轮重复发送的上下文累加起来的总和，所以输入量通常远大于输出量，缓存命中率也很关键。

### 盈亏平衡

设基座完成同一任务的成本为 B，Particle-1 在**用量完全相同**时的成本为 P。若 Particle-1 把输入量和输出量**同比例**缩小到原来的 k 倍，则成本变为 k × P。令 k × P = B，得到：

```text
k = B ÷ P
需要削减的比例 = 1 − k
```

这里有两个前提，我必须说清楚：

1. 输入、输出同比例缩小。实际上，少几次工具调用会同时减少输出和之后每轮重复发送的输入，这个假设大体合理，但不一定精确。
2. 两个模型的缓存命中率相同。实际可能不同。

### 计算结果

我用 Python 脚本按上表价格算了四种情形。第一组是每个任务输入 2.0M、输出 0.1M；第二组是输入 0.5M、输出 0.05M。

| 缓存命中率 | 输入 / 输出（百万 token） | 基座成本 | Particle-1 同用量成本 | 同用量的价格倍数 | 要削减的总用量 |
| --- | --- | --- | --- | --- | --- |
| 0% | 2.0 / 0.1 | $0.1400 | $0.6000 | 4.29 倍 | 约 76.7% |
| 0% | 0.5 / 0.05 | $0.0475 | $0.1750 | 3.68 倍 | 约 72.9% |
| 90% | 2.0 / 0.1 | $0.0698 | $0.2040 | 2.92 倍 | 约 65.8% |
| 90% | 0.5 / 0.05 | $0.0300 | $0.0760 | 2.54 倍 | 约 60.6% |

读法：在这四种假设下，Particle-1 要把总用量削减约 61% 到 77%，才能与基座打平。输入占比越大、缓存命中率越低，需要削减得越多。

换一个说法：如果它实际只省了一半，那么在这几种情形里，它的单任务成本仍然是基座的约 1.3 到 2.1 倍。这是用上表的倍数乘以 0.5 得到的。

## 四、比较时容易漏掉的三件事

### 1. 成功率

省 token 只有在任务同样完成时才有意义。如果 Particle-1 省了用量，但成功率略低，就需要多跑几次或人工补救。更合理的指标是**每个成功任务的成本**：

```text
每个成功任务的成本 = 总花费 ÷ 成功任务数
```

举一个假设性的算例（纯算术，不是测量）：若两个模型每次尝试的成本分别是 0.07 美元和 0.09 美元，成功率分别是 80% 和 90%，那么每个成功任务的成本是 0.0875 和 0.1 美元。后者成功率更高，但每次尝试贵 0.02 美元，折算到每个成功任务仍然更贵。成功率的差距能不能抵消价格差，要看你自己的数字。

### 2. 推理 token 是否计费

Particle-1 页面列出了 reasoning 相关参数。推理过程产生的 token 在输出价下是否计费，上架页没有写，要查提供方的计费说明。如果计费，那么"推理 token 更少"确实会直接省钱；如果不计费，省 token 对账单的意义就不同。我没有核实，所以上面的计算把输出量统一当作按输出价计费。

### 3. 价格和提供方会变

上架页只有一家提供方，价格由它决定。单一来源的价格变动、限流或下线，对你的成本和可用性影响都更大。上面的比值只在 2026-10-30 的价格下成立。

## 五、用自己的任务验证

### 准备

1. 选 30 个真实任务，难度分布接近你的日常，每个任务有明确的完成判定（测试通过、命令输出符合预期等）。
2. 用同一个智能体框架、同一套提示词、同一组工具跑两个模型。
3. 每个任务每个模型至少跑 3 次，因为智能体运行有随机性。

### 记录

| 字段 | 来源 |
| --- | --- |
| 输入 token（含缓存命中部分） | 响应里的 usage 字段 |
| 输出 token | 同上 |
| 缓存读取 token | 同上 |
| 是否成功 | 你的判定脚本 |
| 轮数、工具调用次数 | 智能体日志 |
| 耗时 | 日志时间戳 |

### 计算

下面是一个可以直接使用的小函数。它把各次运行的 usage 乘以当前价格。价格单位是美元每百万 token。

```python
def run_cost(inp, cached, out, price):
    # inp: 总输入 token（含缓存命中）；cached: 其中命中缓存的 token
    return ((inp - cached) * price["inp"] + cached * price["cache"] + out * price["out"]) / 1_000_000

PARTICLE = {"inp": 0.25, "out": 1.00, "cache": 0.03}
BASE     = {"inp": 0.045, "out": 0.50, "cache": 0.006}
```

注意 inp 是否已经包含缓存命中部分取决于提供方的 usage 字段定义。上面的函数假设 inp 包含 cached。接入前先对照一次提供方的响应字段，不然会重复计算。

然后对每个模型汇总：

1. 总花费，除以成功任务数，得到每个成功任务的成本。
2. 输入、输出 token 的中位数，不只看平均值，因为少数长任务会拉高平均值。
3. 失败任务里 token 花了多少。失败也要付费。

### 判定

用第三节的盈亏平衡值做对照：

- 如果实测总用量的削减幅度低于你那组假设下的盈亏平衡值，那么 Particle-1 单任务更贵。
- 如果高于，再看成功率有没有下降。
- 两者都满足，才有理由换。

## 六、什么情况下它可能适合

下面是条件化的判断，不是对 Particle-1 的评价：

| 场景 | 倾向 |
| --- | --- |
| 总用量被大幅压缩（超过上面的盈亏平衡值）且成功率不降 | 值得继续测 |
| 对延迟敏感，轮数减少能明显缩短总耗时 | 即使成本持平，也可能有价值 |
| 任务量很大、单任务成本差异被放大 | 先小规模测，再放量 |
| 预算极度敏感、任务简单 | 基座的价格优势更明显 |
| 需要稳定的多提供方回退 | 单一提供方是风险 |

## 七、限制与结论

Particle-1 的单价明显高于它的基座，所以"省 token"能否抵消，是一个可以用数字回答的问题。在我设定的四种情形下，需要削减约 61% 到 77% 的总用量才能打平；这个范围依赖输入输出比和缓存命中率，也依赖"同比例缩小"的假设。

本文的限制：Particle-1 的实际省 token 幅度没有公开数字，我也没有测；只有 OpenRouter 一个信息来源，没有找到开发方的官方页面；盈亏平衡的前提是简化的；推理 token 的计费方式未核实；价格仅为 2026-10-30 的快照。

下一步建议：按第五节用 30 个任务各跑 3 次，算出每个成功任务的成本，再对照第三节的盈亏平衡表。数据出来之前，不需要为了"省 token"这个说法切换模型。
