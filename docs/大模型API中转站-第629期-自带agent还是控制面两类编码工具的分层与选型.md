# 自带 agent 还是控制面：两类编码工具该怎么分层选

"编码 agent 工具"这个说法把两种东西混在一起了。一种是自带 agent 的 harness：它实现主循环、工具集、权限规则，你直接对它下指令。另一种是控制面：它不实现 agent，而是去驱动你机器上已经装好的那些 CLI，把界面、会话和远程访问做在外面。

分不清这一层，选型就会从错误的维度开始。比如拿"谁的模型能力强"去比较一个不自带模型的工具，或者拿"支持几个客户端"去评价一个本地 CLI。

本文用两家我读过第一方文档的工具做对照：OpenCode（自带 agent）与 T3 Code（控制面），按七个维度说明两层各自的边界。文中不做排名，只写文档能支持的事实，以及哪些格子在公开文档里查不到。

信息检索日期为 2026-11-02。两家我都没有安装或运行过。

## 一、先看两家的定位

| 项目 | OpenCode | T3 Code |
| --- | --- | --- |
| 仓库 | [anomalyco/opencode](https://github.com/anomalyco/opencode) | [pingdotgg/t3code](https://github.com/pingdotgg/t3code) |
| 协议 | MIT | MIT |
| 自述 | The open source coding agent | agent harness 控制面 |
| agent 从哪来 | 自带：build（默认可写工作区内，但读敏感环境文件会问）、plan（可写自己的计划文件）、general 与 explore 子代理 | 不自带：驱动本机已装或已登录的 Claude Code、Codex、Cursor、Grok Build、OpenCode、fx、Kiro、Pi、Muse Code 等（Antigravity 不需要 CLI，在设置里登录） |
| Star（检索当天） | 223,865 | 38,169 |
| 最新发布 | v2.2.5（2026-10-30） | 桌面与命令行客户端，按发布页分发 |

第一行之外的差别都从这里派生：一个自己执行，一个转达。

## 二、七个维度

### 维度 1：agent 与模型的所有权

**该问什么：** 谁决定用哪个模型、谁维护主循环、谁负责工具调用的循环。

| OpenCode | T3 Code |
| --- | --- |
| 自己维护 agent 与工具集；模型来自 models.dev 目录或自定义提供方配置 | 模型与主循环在被驱动的那家 CLI 里；T3 Code 负责会话、界面，以及服务器侧的执行所有权（提供方进程、终端、Git、项目文件、检查点） |

由此推出一件事：OpenCode 的"换模型"是改自己的配置；T3 Code 的"换模型"取决于被驱动的那家允许什么。

### 维度 2：配置的来源与优先级

**该问什么：** 配置写在哪几个文件里，谁覆盖谁，能不能集中管控。

| OpenCode | T3 Code |
| --- | --- |
| `opencode.jsonc`，五级优先级：全局 → 仓库 → 子包 → `/etc` 系统级 → 托管设置；系统级高于项目级 | 偏好留在各客户端，环境默认值与项目覆盖留在所属服务器；一台机器上的可用权限模式可由管理员用托管策略封顶 |

两家都留了"组织级能压过个人"的位置，但强度不同：OpenCode 侧真正压得住用户与项目的只有托管设置（Linux 的 `/etc/opencode`、macOS 的托管配置）；项目自带的组织默认值加载最早、优先级最低，可被用户配置覆盖。T3 Code 侧的托管策略才是组织直接封顶。

### 维度 3：权限模型

**该问什么：** 能不能按命令、按路径、按工具分别授权，默认是放还是问。

| OpenCode | T3 Code |
| --- | --- |
| 规则三项：动作 + 资源 + 效果（allow/deny/ask）；没有规则匹配时兜底为 ask，但默认基础策略是从 `*`→allow 起手；多资源操作任一拒绝即整体拒绝；另有 policies 做硬拒绝 | 四档模式：Supervised、Auto-accept edits、Auto、Full access，按线程生效，初始默认 Full access；但可用档位随提供方收窄（Muse Code 与 Kiro 只有两档，fx 与 Grok 缺 Auto-accept edits）；四档之外还有按路由区分的 scope 授权 |

这是两家差别最大的一维：一个按资源写规则，一个按线程选档位。前者更细，后者更好懂。

### 维度 4：扩展机制

**该问什么：** 想加自定义能力时，扩的是哪一层。

| OpenCode | T3 Code |
| --- | --- |
| 插件：`plugins` 数组可写 npm 包、带版本包、scoped 包、本地目录；也会自动加载 `.opencode/plugins/` 下的 `.ts`/`.js`；技能放在 `.opencode/skills/<id>/SKILL.md` | 没有自有的插件扩展点（文档里没有 T3 自己的插件 API）；它复用被驱动 CLI 已有的插件与技能，并把这些能力收进自己的菜单；另有 MCP 服务器透传，以及让 T3 之外的 agent 通过 MCP 驱动它管理的线程 |

第四格的措辞要小心：这是"我没在文档里找到"，不是"它没有"。两者的证据强度不一样。

### 维度 5：多端与远程

**该问什么：** 能不能在手机上接着干，远程时执行发生在哪里。

| OpenCode | T3 Code |
| --- | --- |
| 有桌面端（README 标注 BETA）；README 没有提到手机接回家里机器的功能，但 v2 文档里有 client/server 划分与可指定服务端的启动参数 | 手机、浏览器、桌面三端；路由可达六类：局域网、Tailscale、其他 VPN、公网 URL、SSH、T3 Connect |

这一维的差别是决定性的：如果你的核心诉求是"离开电脑也能推进任务"，那这是控制面这一类工具的设计目标，而自带 agent 的 CLI 通常不解决它。

### 维度 6：可审计与回放

**该问什么：** 出了事能不能还原"谁在什么时候下发了什么"。

| OpenCode | T3 Code |
| --- | --- |
| 文档里有快照、压缩、指令等条目，具体语义我没有逐个读 | 编排状态以事件决定，**投影在被应用之后才是真实来源**；事件日志只留约一天，更早的由维护程序删除，投影无法由日志重建；命令意图与副作用分处事务内外（一个事务落库、外部动作在事务外执行）；检查点用隐藏 Git ref，不在用户分支上加提交 |

这一维我在 OpenCode 侧的证据不足，所以不给结论。写对比时最该避免的就是用一方的详细文档去比另一方的空白。

### 维度 7：许可

两家都是 MIT。这一维没有差别，列出来是为了说明：许可通常不是这两层的区分点。

## 三、哪些格子不该填

做这种对照时，有三类格子容易被顺手填错：

1. **用一家有、另一家文档没写的功能去比。** 比如上面的扩展机制。正确表述是"在其文档中未找到"。
2. **跨层比较能力。** 例如拿控制面的"多端"去对比自带 agent 的"多端"，看起来都是多端，但一个指的是远程控制别人的机器，一个指的是同一台机器上的不同界面。
3. **拿未经核验的数量比强弱。** 星标数、发布频率只能说明关注度，不能说明适配度。

## 四、三类常见误选

| 误选 | 症状 | 更合适的做法 |
| --- | --- | --- |
| 用控制面替代 harness | 装好之后发现什么都要先有别的 CLI，自己反而没有 agent | 先确认目标机器上已经装好并登录了至少一家 CLI |
| 用 harness 解决远程需求 | 想在手机上推进任务，结果只能靠远程桌面 | 远程是控制面的设计目标，不是 harness 的 |
| 只看权限档位不看粒度 | 选了四档模式的工具，但真正需要的是"这条命令允许、那条拒绝" | 需要按命令/路径细控时，规则式模型更合适 |

第三行是我认为最实用的一条判断：档位制适合"人盯着"的日常使用，规则制适合"要把边界写进配置文件交给别人执行"的场景。

## 五、条件化建议

| 你的情况 | 更贴近哪一层 |
| --- | --- |
| 想立刻有一个能改代码的 agent，且要能按命令细控 | 自带 agent 的 harness |
| 团队已经统一用某家 CLI，只缺界面与协作 | 控制面 |
| 需要在手机上批准和调度 | 控制面 |
| 需要把权限写成配置随代码走 | 规则式权限的一侧 |
| 需要离线、纯本地 | 取决于被驱动或自带的模型能不能本地跑，这一点两家都还要再查 |

最后一行的措辞是刻意的：我都没有实测过离线场景，只能提示这是下一个要查的点。

## 六、选型前先做一份验证清单

上面的七个维度都可以用一次小实验验一遍，不必读完文档。建议每项只做一件事：

| 维度 | 一次可完成的实验 | 看什么 |
| --- | --- | --- |
| agent 所有权 | 把默认模型换成一个不存在名字 | 报错里露出来的是哪一家的命名 |
| 配置优先级 | 全局与项目各设一个不同值 | 哪个生效；若都不生效，查是否有系统级或托管配置 |
| 权限粒度 | 让 agent 执行一条你确定要禁的命令 | 被拒还是被问；拒绝时是规则还是策略拦的 |
| 扩展机制 | 放一个最小插件或技能进去 | 有没有被加载；失败时报错是否指出位置 |
| 多端与远程 | 从另一台设备接上同一个会话 | 执行发生在哪台机器；断网后谁能继续 |
| 可审计 | 做一次改动再回滚 | 能否说清改动与回滚分别是谁触发的 |

这张表里最值得先做的是第三行与第五行：它们直接决定你能不能在团队里推广。

## 七、如果两层都要

还有一种常见组合：先用 harness 干活，再用控制面去盯。这不是折衷，而是分工——控制面把会话和远程做在外面，harness 在里面执行。T3 Code 的驱动列表里就包含 OpenCode，说明这种叠加在设计上是预期用法。

代价是多一个组件要维护，以及权限会在两层各有一套：控制面那边按路由与 scope 授权，harness 那边按规则与策略。排查"为什么这个操作被拒"时，要判断是哪一层拒的。

## 八、限制与结论

把工具分成"自带 agent"与"控制面"两层，比逐个比较功能更能解释差异：前者决定执行，后者决定接入与调度。选型时先确定你需要哪一层，再在同一层内比较。

本文的限制：只对照了两家，且都以文档为依据，没有实测；OpenCode 侧的可审计与快照能力我没有细读，因此不给对比结论；T3 Code 没有自有插件 API 这一条，依据是我读过的文档；它复用被驱动 CLI 的插件与技能，这一层我未实测；两家都没有跑过，所有行为描述都可能与实现有偏差。

下一步建议：拿你团队最常做的一件事，分别在两层里走一遍：先用 harness 完成一次真实改动，再用控制面从手机上看一眼同一次执行。两个都走通之后，你会更清楚缺的是执行能力还是接入能力。
