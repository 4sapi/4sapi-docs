# 半年做出一份 FDE 作品集：从小应用到真实用户

准备 FDE 求职时，很多作品集停在同一个位置：页面能打开，模型也会回复，但看不出谁会用、为什么要用、出错后怎么办。面试官看到的是一个功能演示，而不是候选人能把模糊问题推进到生产使用的证据。

半年可以用来完成一轮相对完整的项目训练：前两个月补工程底座，中间两个月加入模型与评估，最后两个月交给真实用户试用。它是一套练习框架，不是职位结果承诺。实际进度取决于原有能力、可投入时间、项目复杂度和能否接触真实用户。

## 一、先选一个能在半年内走完的问题

作品集选题不宜从“做一个通用 Agent 平台”开始。范围太宽，很容易把时间花在框架、页面和功能列表上，最后没有一个流程被真正使用。

更合适的题目通常有五个特征：

```text
有一个明确用户
用户现在已经在完成这项工作
输入和输出可以描述
错误能被人工发现和纠正
两个月内能做出第一版
```

例如，帮助客服根据有效知识起草回复、帮助运营整理异常数据并生成说明、帮助销售把会议记录转换成待办，都比“做一个企业级全能助手”更容易验证。

下面以“运营异常说明助手”为贯穿案例。系统读取已经脱敏的日报指标，标出达到既定规则的异常项，再由模型生成解释草稿。运营人员确认、修改或拒绝后，才能进入日报。案例只用于展示训练方法，不代表真实企业项目。

## 二、第 1—2 个月：做出别人能用的小应用

第一阶段不急着接模型，先证明自己能完成一条普通应用链路。

### 前置能力

选择 Python 或 TypeScript 中的一种，掌握基本语法、依赖管理和错误处理；能使用 SQL 操作一种关系型数据库；理解 HTTP、JSON、Git 和环境变量。

不需要同时学习多套前后端框架。选一套自己能持续维护的技术组合，把注意力放在输入、处理、保存、权限和部署上。

### 本阶段要做什么

运营异常说明助手的第一版可以包含：

- 登录和简单的用户角色；
- 上传或导入一份固定字段的日报数据；
- 用确定性规则识别异常指标；
- 在数据库保存任务、异常项和人工备注；
- 一个能查看历史记录的页面；
- 对字段缺失、重复上传和格式错误给出明确提示；
- 部署到一个测试环境，并把密钥放在环境变量中。

这一阶段故意不接大模型，是为了先分清哪些问题本来就能用普通代码解决。异常阈值、日期校验和字段完整性属于确定性规则，不应交给模型猜。

### 交付物

```text
可访问的测试应用
数据库表结构说明
三个正常输入样本
三个错误输入样本
部署步骤
已知限制清单
```

### 验收标准

找一位没有参与开发的人，给他测试账号和一页简短说明。对方能够独立导入数据、看到异常、添加备注并查看历史记录；输入错误文件时，系统不会丢失原记录，也不会只显示模糊的“运行失败”。

如果只有开发者自己的电脑能运行，就还没有完成第一阶段。

## 三、第 3—4 个月：加入模型、评估和人工复核

第二阶段再让模型承担适合它的任务：根据异常指标、相关备注和有限的业务背景，生成一段解释草稿。

### 模型任务要足够窄

不要让模型重新计算指标，也不要让它决定异常是否成立。给它结构化输入，并要求返回固定字段：

```json
{
  "summary": "异常现象的简短说明",
  "possible_causes": ["待人工核实的可能原因"],
  "missing_information": ["当前缺少的信息"],
  "risk_note": "不能直接下结论时的提示"
}
```

模型输出进入数据库前要做结构校验。字段缺失、内容无法解析或接口超时，都应进入明确的失败状态，允许用户重新生成或手工填写。

### 建立固定评估集

从自己构造或经过授权、脱敏的材料中准备一组样本，覆盖：

- 信息完整且原因明确；
- 只有异常现象，没有原因资料；
- 多个指标同时变化；
- 输入包含相互冲突的备注；
- 不应由系统推断的敏感原因；
- 模型服务超时或返回非法结构。

每条样本写预期行为。例如，资料不足时列出缺失信息，而不是编造原因；备注冲突时提示人工核实，而不是选择其中一个说成事实。

### 加入人工复核和可观察性

用户必须能查看输入依据，接受、修改或拒绝草稿。日志关联任务 ID、配置版本、模型调用、错误类型和人工动作。模型或提示词更新后，重新运行固定样本并保存差异。

### 交付物

```text
模型输入输出约定
固定评估样本与预期行为
结构校验和错误处理记录
人工接受、修改、拒绝流程
脱敏调用日志
一次版本变更前后的评估对比
```

### 验收标准

固定样本可以重复执行；模型返回非法结构或接口超时时，系统进入可解释的失败状态；用户能够在不丢失原始数据的情况下改用手工说明。评估结果不要求每次文字完全相同，但关键边界必须能够检查。

## 四、第 5—6 个月：让真实用户连续使用

第三阶段的重点不是继续增加功能，而是观察工具进入真实工作以后会在哪些地方失效。

找 3—5 位目标用户，在获得对方和数据所有者许可后，让他们使用两周左右。人数和周期只是小型练习的参考，不足以代表普遍结论；如果任务发生频率很低，应延长观察。

### 先记录原流程

在试用前记录用户原来如何完成日报：数据从哪里来，需要打开哪些工具，哪里经常返工，最终由谁确认。没有原流程，就无法判断新工具到底改变了什么。

### 试用期间记录什么

```text
用户在什么任务中打开了工具
完成了多少次有效处理
草稿被接受、修改或拒绝的原因
用户在哪一步返回旧流程
出现了哪些数据、权限和界面问题
一次失败如何恢复
每次改动对应哪条反馈
```

不要只收集“好不好用”的主观评价。请用户用具体任务演示，并观察他在哪里停顿、复制数据或绕开系统。真实行为通常比满意度问题更容易定位工程问题。

### 交付物

```text
经过授权的试用记录
问题与修改日志
一次失败复盘
版本前后对照
仍未解决的限制
后续是否继续使用的理由
```

### 验收标准

作品集能够回答：谁在什么场景使用，使用期间暴露了什么问题，你依据什么证据修改，修改后如何复查，以及哪些风险仍然保留。即使试用结果不理想，只要记录真实、分析清楚，也比只展示成功截图更有价值。

## 五、不同背景的人应该补哪一半

转向 FDE 不等于把过去经验清零。更有效的方法是保留已有优势，再补交付链路中缺失的一段。

| 原有背景 | 可以复用的能力 | 优先补齐的部分 |
| --- | --- | --- |
| 软件工程师 | 生产代码、测试、部署、故障处理 | 用户访谈、流程拆解、采用观察 |
| 数据分析师 | SQL、指标、业务沟通、数据质量 | 服务化、权限、API、部署和恢复 |
| 产品或咨询人员 | 需求澄清、行业流程、跨团队协调 | 编程、数据库、接口和可运行交付 |
| 售前或实施人员 | 客户沟通、系统集成、交付现场经验 | 主仓库代码、自动测试、长期维护 |

完全没有技术和行业经验时，可以先从数据分析、技术支持、实施助理或初级开发中建立一项可验证能力，再逐步扩展。FDE 往往需要多段经验汇合，不适合作为只靠课程名称完成的转型。

## 六、把项目整理成可核验案例

最终作品集不要只放技术栈和界面截图。使用下面的结构，可以让阅读者沿着问题、方案、证据和限制检查你的工作：

```text
业务背景：谁在什么场景遇到问题
原流程与痛点：现在如何完成，阻力在哪里
用户和权限：谁能看什么、做什么
系统架构：数据、规则、模型和界面如何连接
数据来源：来源、更新频率、授权与脱敏方式
模型任务与失败边界：模型负责什么、不负责什么
评估方法：固定样本、预期行为和回归方式
上线与回滚：如何灰度，失败后怎样回到原流程
使用记录：谁用了多久，发生了哪些真实动作
失败、修改与剩余限制：哪里没做好，如何调整
```

涉及真实用户和业务资料时，应先取得授权，删除身份、客户、密钥和内部系统信息。不能公开的证据可以说明验证方法和字段结构，不应为了作品集泄露数据。

## 结论

一份接近 FDE 工作方式的作品集，不靠功能数量取胜，而靠完整责任链：问题来自真实流程，系统可以被别人使用，模型行为能够评估，错误可以恢复，用户反馈能够推动修改。

半年路线适合已有一部分工程或行业基础的人建立这条责任链。时间不足时，可以缩小用户和功能范围，但不要删掉验证、失败记录和限制说明。它们才是区分功能演示与交付案例的关键材料。
