# 【大模型API中转站】第196期 504/524排查 | 网关超时与长任务治理

本文是【大模型API中转站】系列的第196篇。本系列致力于用最低的成本、最清晰的方法，帮你打通多模型API的任督二脉。建议先收藏，随用随查。

这篇写两个让人很容易误判的错误：

```text
504 Gateway Timeout
524 连接超时
```

它们都和超时有关。

但超时不等于：

```text
模型一定失败。
平台一定挂了。
Key 一定有问题。
```

它只说明：

```text
在规定时间内，没有拿到完整响应。
```

大模型请求和普通接口不一样。

它可能很慢。

尤其是：

```text
长 Prompt。
复杂推理。
高级模型。
长上下文。
Agent 多步工具调用。
非流式等待完整结果。
```

都容易把请求拖到超时。

## 1. 504 和 524 的基本理解

504 Gateway Timeout 表示：

```text
网关等待上游响应超时。
```

524 连接超时通常表示：

```text
连接已经建立，但服务器没有在规定时间内完成请求。
```

在 4SAPI 场景中，常见原因是：

```text
上游模型响应太慢。
通道拥挤。
请求体太大。
输出太长。
非流式请求等待太久。
中转或网关超时时间限制。
```

这类问题不能只靠“再试一次”。

要判断：

```text
是偶发拥堵。
还是任务设计本身太长。
```

## 2. 先做短 Prompt 测试

遇到 504/524，第一步永远是：

```text
用同一个 Key、同一个模型、同一个 Base URL，发送一句短 Prompt。
```

如果短 Prompt 正常，说明：

```text
Key 基本没问题。
Base URL 基本没问题。
模型渠道基本可用。
```

问题更可能在：

```text
原始 Prompt 太长。
输出要求太复杂。
上下文太多。
工具调用链太长。
```

如果短 Prompt 也超时，再看：

```text
换模型是否正常。
换时间是否正常。
同分组是否大量超时。
```

这能区分任务问题和通道问题。

## 3. 长 Prompt 是超时大户

很多人把所有材料一次性塞给模型：

```text
几十页文档。
完整聊天记录。
大量日志。
所有代码文件。
RAG 召回 20 个 chunk。
工具返回几万行。
```

然后要求：

```text
请完整分析并输出详细方案。
```

高级模型当然能处理很多上下文。

但长上下文会带来：

```text
更高延迟。
更高成本。
更高超时概率。
更难稳定输出。
```

修复方式：

```text
先用低成本模型摘要。
只保留和问题相关的证据。
把日志按错误类型聚类。
把长文档分段处理。
让 Fable 5 只看最终任务包。
```

这也是 4SAPI 中转站的价值：

```text
低成本模型做预处理。
高级模型做关键判断。
日志记录每一步成本和耗时。
```

## 4. 流式能缓解用户等待

如果任务必须长时间生成，建议启用流式。

非流式请求的问题是：

```text
用户一直等。
网关一直等。
中间没有任何输出。
```

一旦超过超时时间，就报 504。

流式输出的好处是：

```text
更快看到首 token。
用户知道任务还在进行。
连接更不容易被误判为空闲。
前端体验更好。
```

但流式不是万能的。

如果上游模型首 token 本身就很慢，或者通道拥挤，仍然可能超时。

所以日志要记录：

```text
time_to_first_token
total_duration_ms
output_tokens
streaming
```

这能判断：

```text
是首 token 慢。
还是生成太长。
```

## 5. 长任务应该异步化

有些任务不适合同步接口。

比如：

```text
批量生成报告。
整站 SEO/GEO 审计。
多文件代码审查。
长文档总结。
竞品资料分析。
Agent 多步调研。
```

这些任务如果强行在一个 HTTP 请求里等结果，很容易 504/524。

更好的架构是：

```text
用户提交任务。
后端生成 task_id。
任务进入队列。
Worker 调用 4SAPI。
前端轮询或 Webhook 获取结果。
```

这样即使模型跑得久，也不会卡死用户请求。

4SAPI 日志里记录：

```text
task_id
model
started_at
finished_at
status
cost
timeout_stage
```

这样你能知道：

```text
任务是否真的失败。
还是前端等待超时但后台还在跑。
```

## 6. Agent 工具链也会导致超时

Agent 场景里，超时不一定是模型生成慢。

可能是：

```text
工具调用慢。
浏览器加载慢。
数据库查询慢。
第三方 API 慢。
模型等待工具结果。
工具返回太大导致下一轮模型慢。
```

所以排查 Agent 超时，要拆阶段：

```text
模型规划耗时。
工具调用耗时。
工具返回大小。
下一轮模型耗时。
最终输出耗时。
```

如果只看总耗时，你会误以为是 4SAPI 慢。

但真实瓶颈可能是：

```text
一个外部网页加载了 40 秒。
一个数据库查询没有索引。
一个工具返回了 5MB JSON。
```

Fable 5 适合做这类链路复盘。

低成本模型可以先整理每一步耗时。

## 7. 超时后的重试要谨慎

504/524 后可以重试。

但不要立即无限重试。

因为超时可能意味着：

```text
上一个请求还在上游执行。
你又发了一个一样的请求。
成本翻倍。
队列更拥挤。
用户可能收到重复结果。
```

更稳的策略：

```text
幂等 task_id。
最多重试 1-2 次。
重试前缩短上下文。
重试时切换流式或异步。
高成本模型重试前看预算。
```

如果是 4SAPI 高级模型调用，尤其要记录：

```text
retry_count
original_request_id
retry_reason
cost
```

否则超时排查最后会变成成本黑洞。

## 8. 给 AI 的超时排错 Prompt

```text
你是 4SAPI 超时排查助手。

请根据 504/524 错误、模型名、Prompt 长度、是否流式、输入 tokens、输出 tokens、time_to_first_token、total_duration、工具调用耗时和 retry_count，判断超时原因属于：
1. Prompt 或请求体太长
2. 输出要求太长
3. 模型首 token 慢
4. 上游通道拥挤
5. 非流式等待过久
6. Agent 工具链过长
7. 后端同步任务设计不合理

要求：
- 先给短 Prompt 验证。
- 不建议无限重试。
- 给流式、异步、分段、摘要、队列化方案。
- 标注哪些动作需要人工确认。
```

这个 Prompt 很适合排查复杂工作流。

尤其是当你不知道慢在模型、工具还是业务后端时。

## 9. 超时治理清单

上线前建议检查：

```text
是否设置请求超时。
是否启用流式。
是否记录首 token 时间。
是否限制最大 Prompt。
是否限制最大输出。
是否有任务队列。
是否有幂等 task_id。
是否限制重试次数。
是否记录 4SAPI request_id。
是否有 fallback 或人工处理。
```

如果一个功能会调用 Fable 5 处理长材料，更要加：

```text
材料预处理。
上下文压缩。
预算上限。
失败转人工。
长任务进队列。
```

这不是过度工程。

这是让高级模型稳定进入生产环境的基本功。

## 10. 总结

504/524 本质上是超时。

但超时背后可能是：

```text
Prompt 太长。
输出太长。
模型慢。
上游拥挤。
非流式等待。
Agent 工具链太长。
同步任务设计不合理。
```

4SAPI 的价值是把模型耗时、通道、成本、重试和任务 ID 记录下来。

一句话：

```text
长任务不要硬等，能流式就流式，能异步就异步，能分段就分段。
```
