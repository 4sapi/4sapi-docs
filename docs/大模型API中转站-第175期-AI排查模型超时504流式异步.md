# 【大模型API中转站】第175期 AI排查模型超时504 | 流式和异步

本文是【大模型API中转站】系列的第175篇。本系列致力于用最低的成本、最清晰的方法，帮你打通多模型API的任督二脉。建议先收藏，随用随查。

大模型 API 接入后，另一个常见问题是：

```text
504 Gateway Timeout
request timeout
upstream timed out
```

尤其是用 Fable 5 这种高级模型跑复杂任务时。

用户会问：

```text
模型是不是挂了？
```

不一定。

超时可能来自：

```text
输入太长。
输出太长。
模型推理本来就慢。
中间网关超时。
客户端超时太短。
没有使用流式。
同步接口做了长任务。
后端还等着数据库或第三方 API。
```

这类问题不能只靠增加 timeout。

要先判断超时发生在哪一层。

## 1. 超时先定位层级

| 层级 | 可能原因 |
| --- | --- |
| 客户端 | fetch/axios 超时、浏览器断开 |
| 业务后端 | 同步等待模型、没有流式 |
| 4SAPI 网关 | 请求处理超时、上游慢 |
| 模型供应商 | 模型推理慢、排队 |
| 下游写入 | 结果写库慢、回调慢 |

如果不分层，AI 只能泛泛建议。

## 2. 给 AI 的超时排错包

```text
【现象】
- 错误原文：
- 状态码：
- 发生在客户端 / 后端 / 4SAPI / Nginx：
- 平均耗时：
- 超时时间点：

【请求】
- model：
- input_tokens：
- max_tokens：
- 是否 stream：
- temperature：
- 任务类型：

【链路】
- 浏览器 timeout：
- 后端 timeout：
- Nginx timeout：
- 4SAPI 日志 duration：
- 上游模型耗时：

【最近变更】
- 是否换了模型：
- 是否增加上下文：
- 是否改成高 effort：
- 是否新增工具调用：

【边界】
- 不建议无限加 timeout
- 先判断层级
- 给流式/异步/降级方案
```

## 3. 常见根因一：输入太长

长上下文会显著增加耗时。

如果你每次都把：

```text
完整聊天历史。
完整代码库。
完整日志。
完整文档。
```

塞给模型，超时很正常。

修复方向：

```text
上下文包。
先摘要。
检索相关片段。
证据编号。
只传必要材料。
```

这正好对应第162期讲的辅助模型上下文包。

低成本模型先整理。

Fable 5 只看关键证据。

## 4. 常见根因二：输出太长

有时输入不长，但输出要求太大。

比如：

```text
生成完整报告。
一次写 20 篇文章。
输出完整代码库。
逐行解释日志。
```

解决方式：

```text
限制 max_tokens。
分段输出。
先输出目录。
按章节生成。
长任务改成异步任务。
```

不要只加 timeout。

因为用户体验也会很差。

## 5. 常见根因三：没有 stream

用户界面里，非流式调用会等到模型全部生成完才返回。

如果任务本身要 40 秒，用户会以为卡死。

流式输出能改善体验：

```text
先返回 token。
前端持续显示。
后端连接保持活跃。
```

但 stream 不是万能。

如果中间 Nginx、CDN、框架不支持或缓冲了流式，也可能仍然超时。

AI 排查要看：

```text
客户端是否 stream。
后端是否转发 stream。
Nginx 是否 buffering。
前端是否正确读取 stream。
```

## 6. 常见根因四：同步接口做长任务

比如用户点按钮后，后端同步做：

```text
读取文件。
调用 Fable 5。
写数据库。
生成 PDF。
上传对象存储。
返回结果。
```

这很容易超时。

更稳架构：

```text
提交任务 -> 返回 task_id
后台队列处理
前端轮询或 WebSocket 获取状态
完成后取结果
```

Fable 5 可以帮你设计异步改造方案。

但不要让它一上来重构全部系统。

先让它给最小方案。

## 7. AI Prompt

```text
你是大模型 API 超时排查助手。

请根据请求参数、token 数、stream 设置、各层 timeout、4SAPI 调用日志和业务链路，判断超时发生在哪一层。

重点检查：
1. 输入是否过长
2. 输出是否过长
3. 是否未使用流式
4. Nginx/CDN/后端 timeout 是否过短
5. 是否同步接口承担长任务
6. 是否应改为队列或异步
7. 是否可以降模型或拆任务

要求：
- 不要只建议增加 timeout。
- 给短期止血和长期方案。
- 每个判断引用证据字段。
```

## 8. 4SAPI 日志字段

建议记录：

```text
model
input_tokens
output_tokens
duration_ms
stream
timeout_layer
task_type
effort
retry_count
```

有了这些，你能判断：

```text
哪个模型最慢。
哪类任务最容易超时。
是否高 effort 导致耗时明显增加。
stream 是否改善成功率。
```

## 9. 流式链路检查清单

很多团队以为自己用了 stream。

但实际链路里某一层把流式缓冲了。

检查：

```text
前端是否用 ReadableStream 逐块读取。
后端是否边收边转发。
Nginx 是否关闭 proxy buffering。
CDN 是否支持长连接。
框架是否把响应攒完再返回。
浏览器是否能看到首 token 时间。
```

可以让 AI 这样审查：

```text
请检查这条模型流式输出链路是否真的端到端流式。
我会提供前端 fetch 代码、后端转发代码、Nginx 配置和 4SAPI 调用参数。
请指出哪一层可能缓冲响应。
```

流式成功后，日志里建议记录：

```text
time_to_first_token
total_duration
stream_completed
client_aborted
```

这比只记录总耗时更有用。

## 10. 同步改异步的最小方案

不是所有超时都要大改架构。

可以先做最小异步：

```text
POST /tasks 创建任务，返回 task_id。
后台 worker 调用模型。
GET /tasks/{id} 查询状态。
完成后前端展示结果。
失败时返回 error_type 和重试建议。
```

这套方案适合：

```text
长文生成。
批量分析。
RAG 重建索引。
Fable 5 深度审查。
多工具 Agent 任务。
```

4SAPI 日志里把 `task_id` 和模型调用绑定起来。

这样用户问“为什么还没好”，你能查：

```text
任务是否排队。
模型是否已调用。
是否 429。
是否 504。
是否写库失败。
```

### 实战补充：长报告生成为什么要异步

假设你让用户上传一份 80 页 PDF，然后生成一份分析报告。

同步接口会经历：

```text
上传文件。
解析 PDF。
切分文本。
调用模型。
生成报告。
写数据库。
返回前端。
```

这里任何一步慢，用户都会等到超时。

更合理的是：

```text
上传成功后立即返回 task_id。
后台开始处理。
每个阶段更新状态。
前端显示进度。
失败时给 error_type。
```

让 Fable 5 审查这类链路时，要它输出：

```text
哪些步骤应该同步。
哪些步骤应该异步。
哪些状态需要入库。
哪些失败可以重试。
哪些失败必须人工处理。
```

这比单纯把 timeout 从 30 秒改到 300 秒更靠谱。

## 11. 总结

模型超时不要只加 timeout。

先看：

```text
哪一层超时。
输入多长。
输出多长。
是否 stream。
是否同步长任务。
是否需要队列。
```

通过 4SAPI，可以把 duration、tokens、model、task_type 记录下来。

Fable 5 适合做架构判断。

辅助模型适合先压缩上下文。

一句话：

```text
超时不是等得不够久，常常是任务形态设计错了。
```
