# CC Switch 如何配置 Gemini CLI 与 OpenClaw
Gemini CLI 与 OpenClaw 的配置对象、工作区和模型字段各有职责。本文分别说明在 CC Switch 中选择应用、保存配置、重启和验证的步骤，并把多模态、长上下文等能力留给当前版本文档核对。文中只讨论可在本地复现的步骤，不把单次结果扩展成产品承诺；每个结论都标注前提、证据和无法覆盖的边界。读者可以先完成最小验证，再根据自己的版本、权限和数据补充实验，避免把配置示例误当成普遍结论。

前两篇分别讲了 Claude 和 GPT/Codex。Gemini CLI 与 OpenClaw 的接入又是另一种情况：Gemini CLI 通常被拿来处理长上下文、资料整理和多模态任务；OpenClaw 更像一个有工作区、规则文件和长期任务的 Agent 系统。

它们都能通过 CC Switch 管理供应商，但验证重点不同：

~~~text
Gemini CLI：模型、上下文、多模态和输出稳定性
OpenClaw：模型入口、工作区、规则文件和工具权限
~~~


## 一、Gemini CLI 适合什么任务

Gemini CLI 不一定在每个编码任务上都最优，但常见优势是：

- 长文档和大段代码阅读
- 多文件上下文整理
- 资料摘要和结构化提取
- 图片、截图或其他多模态资料理解
- 搜索增强或研究型任务
- 将大量上下文压缩成行动清单


## 二、在 CC Switch 中配置 Gemini CLI

### 第一步：选择 Gemini CLI 应用

打开 CC Switch，在应用切换区域选择 Gemini CLI。确保你不是在 Claude Code 或 OpenClaw 页面添加供应商。



自定义供应商时，通常需要：

| 字段 | 检查点 |
| --- | --- |
| API 格式 | 选择 Gemini 原生或服务商明确支持的兼容格式 |
| 多模态开关 | 只有模型和入口都支持时才启用 |
| 本地路由 | 只有需要转换、日志或模型映射时开启 |

不要因为某个服务商支持 OpenAI-compatible，就默认 Gemini CLI 的所有功能都能通过同一个路径完成。文本、图片、工具调用和流式输出需要分别验证。

### 第三步：保存、启用、重启

保存之后：

1. 确认供应商显示为已启用。
2. 关闭正在运行的 Gemini CLI 进程。
3. 重新打开终端或 IDE 集成。
4. 发送最小文本请求。
5. 再测试长文本和多模态能力。

Gemini CLI 可能在启动时读取环境变量或配置文件。只点 CC Switch 的保存，不重启当前进程，旧配置仍可能留在内存里。

## 三、Gemini CLI 的三层验证

### 第 1 层：文本连通性

~~~text
只回复 OK，并告诉我当前模型 ID。
不要读取本地文件，也不要调用外部工具。
~~~

验证 API Key、Base URL、模型 ID 和基本输出。

### 第 2 层：长上下文

在测试目录准备一份不含敏感数据的文档，要求 Gemini CLI：

~~~text
只读取 docs/test.md，输出：
1. 文档主题
2. 3 条关键事实
3. 2 个仍然不确定的问题
不要修改文件，也不要读取其他目录。
~~~

检查模型是否真的读到了内容，输出是否截断，Token 和耗时是否可接受。

## 四、OpenClaw 与普通 CLI 的区别

OpenClaw 不只是一个模型客户端，它通常会涉及：

- Agent 工作区
- `AGENTS.md`、用户偏好和记忆文件
- 工具调用和任务编排
- 多 Agent 或长期任务
- 模型供应商与模型路由
- 工作区里的脚本、资料和输出文件


| 内容 | 由谁负责 |
| --- | --- |
| Agent 行为规则 | OpenClaw 工作区和规则文件 |
| 工具权限 | OpenClaw/CC Switch 的应用配置与审批 |
| 输出文件 | OpenClaw 工作区 |

不要把 API Key 写进 `AGENTS.md`、`SOUL.md`、README 或工作区备忘录。规则文件应该描述行为边界，不应该成为密钥仓库。

## 五、在 CC Switch 中配置 OpenClaw

### 第一步：选择 OpenClaw 应用

打开 CC Switch，切换到 OpenClaw 页面。确认它识别到了 OpenClaw 的配置或工作区位置。如果路径不对，先修正工作区，不要急着添加模型。



核心信息包括：

- 供应商名称
- Base URL
- API Key
- 上游协议
- 默认模型 ID
- 备用模型或故障转移模型
- 是否启用 CC Switch 本地路由

不同版本的 OpenClaw 配置层级可能不同，供应商可能写在应用配置、工作区配置或环境变量中。不要同时在三处写不同的模型，否则切换结果会很难解释。

### 第三步：区分默认模型和 Agent 角色

如果 OpenClaw 有多个 Agent 或不同任务角色，不要只改一个全局默认模型就认为所有 Agent 都切换了。逐一检查：

| 层级 | 要确认什么 |
| --- | --- |
| 全局默认 | 新建任务默认使用什么模型 |
| Agent 配置 | 某个 Agent 是否覆盖全局设置 |
| 工作区 | 是否有本地文件指定模型或供应商 |
| 路由层 | CC Switch 是否重写了模型 ID |

### 第四步：最小 Agent 验收

先给 OpenClaw 一个只读任务：

~~~text
只回复 OK，并告诉我当前使用的模型 ID。
不要读取工作区文件，不要调用工具，不要执行命令。
~~~

确认模型连通后，再测试只读工作区任务：

~~~text
只读取当前工作区的 AGENTS.md。
用 5 条要点总结其中的工作边界。
不要修改、创建、移动或删除任何文件。
~~~

最后再用一个小型、可回滚的任务验证工具调用。不要一开始就把真实客户资料和全部工作区交给新模型。

## 六、Gemini CLI 与 OpenClaw 的路由选择

| 场景 | Gemini CLI | OpenClaw |
| --- | --- | --- |
| 需要统一模型映射 | 可用本地路由 | 可用本地路由 |
| 需要跨应用日志 | 可用本地路由 | 更建议本地路由 |
| 需要工具调用转换 | 先做单工具测试 | 先做只读工具测试 |
| 需要故障转移 | 配置前先验证模型兼容 | 配置前先验证 Agent 行为 |

本地路由不是越早开越好。它增加了一个中间层，但也能提供协议转换、模型映射、日志和故障转移。默认监听地址应保持 `127.0.0.1`，不应该为了让其他设备“也能访问”而直接开放到 `0.0.0.0` 或公网。

## 七、常见问题

### Gemini CLI 能文本对话，读取长文档就失败


### Gemini CLI 能读文本，图片失败


### OpenClaw 回复正常，但 Agent 不按规则工作

这通常不是 API Key 问题。检查工作区路径、规则文件是否被读取、Agent 是否有自己的覆盖配置，以及 CC Switch 是否只改了模型供应商而没有改规则。

### OpenClaw 调用工具失败

先分开测试：纯文本、只读文件、单个无副作用工具。检查工具 schema、权限、参数格式、模型能力和本地路由日志。不要一遇到工具失败就更换十个模型。

### 切换供应商后仍使用旧模型

检查 OpenClaw 的进程是否重启、工作区是否覆盖全局配置、环境变量是否残留、CC Switch 当前启用的是不是 OpenClaw 供应商。

## 九、企业场景的分层治理

Gemini CLI 适合资料和上下文类工作，OpenClaw 更容易形成长期 Agent 工作区。企业接入时，建议分别设置：

- 只读资料项目与可写项目
- 测试模型 Key 与生产模型 Key
- 普通用户与管理员的供应商权限
- 允许使用的模型清单
- 允许调用的工具清单
- 单次、每日和每月预算
- 失败重试次数和熔断条件

通过企业级 API 网关或 CC Switch 的统一入口记录应用、项目、成员、模型和用量，才能回答“这次成本到底来自 Gemini CLI 的长文档，还是 OpenClaw 的 Agent 循环”。

## 总结


~~~text
Gemini CLI：先验文本，再验长上下文和多模态
OpenClaw：先验模型，再验工作区、规则和工具边界
~~~
