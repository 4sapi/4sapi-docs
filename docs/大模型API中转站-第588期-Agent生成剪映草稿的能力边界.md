# Agent 直接生成剪映草稿：pyJianYingDraft 的能力边界与验收清单

> 本文以一类开源短视频生产流水线的公开源码，以及上游库 [pyJianYingDraft](https://pypi.org/project/pyJianYingDraft/) 的文档为参照，只讨论可核验的技术事实。检索 2026-10-27。

自动化剪辑里最容易被夸大的一个环节是"生成草稿"。听上去是"AI 帮你剪完了"，实际是"AI 帮你把轨道、片段、关键帧写进了剪映的工程文件"。这两件事的差距，决定了你要验收什么。

这篇只回答一个问题：**用 Agent 生成剪映草稿，技术上能到哪一步，哪一步必须人来**。

## 先核实三件事

| 事实 | 核验方式 | 结果 |
| --- | --- | --- |
| 项目存在且开源 | GitHub API | 存在，Python，MIT，约 165 stars，创建于 2026-10-26 |
| 依赖库真实可用 | PyPI | `pyJianYingDraft` v0.3.1 存在，自述为"剪映草稿生成及导出工具" |
| 是否为官方接口 | 上游文档 | 非剪映官方 SDK，是社区对草稿文件格式的实现 |

第三条最关键：**这不是官方 API**。项目自己的文档也写明"上游功能说明标注基础功能支持剪映 10.8，但当前生成文件与结构检查不等于已经播放"。

## 草稿到底被写成了什么

剪映专业版的工程不是一个视频文件，而是一个目录，核心是两份 JSON：`draft_content.json`（工程内容）和 `draft_info.json`（入口索引）。一个典型的草稿生成流程可以拆成五步：

1. **校验计划**：读 `plan.json`，核对每镜的起止时间与素材是否齐全，复用已核验过的时间，不重新均分。
2. **建暂存工程**：在草稿根目录下新建本次专用目录，避免写到一半污染已有工程。
3. **复制素材**：把图片与音频复制进工程的 `materials`，并且**以内容哈希命名**。这一步解决的是"素材被移动或改名后，草稿打开变红"的常见问题。
4. **编排轨道**：用库里的 `DraftFolder`、`TrackSpec`、`VideoSegment`、`AudioSegment` 和可选的 `TextSegment` 组装。
5. **写关键帧**：把运镜曲线按输出帧率采样成**线性缩放/位移动画**，最后保存 JSON，并生成一份内容一致的入口副本。

第 5 步是这个流程里最值得注意的设计：上游库不支持贝塞尔缓动参数，所以"缓入缓出"不是靠曲线类型实现的，而是靠**密集采样 + 线性插值**逼近。这解释了一个常见疑问——为什么生成的草稿里关键帧数量比手动加的密集得多。

## 运镜参数的真实默认值

常见的说法是"出镜微推近 1.28x、进镜拉回 1.50x"，方向上没错，但从代码看更准确的描述是：

| 参数 | 默认值 | 实际含义 |
| --- | --- | --- |
| `punch_in` | 1.50 | 镜头进入时先放大到 1.5 倍，再用 1.8 秒缓出回到正常尺度 |
| `punch_in_dur` | 1.80 s | 上述回落时长 |
| `punch_out` | 1.28 | 镜头离开时推到 1.28 倍再切 |
| `punch_out_dur` | 1.00 s | 推近时长 |
| `cut_punch` | 开启 | 但只对图片镜头、且时长 ≥ 5 秒的才默认生效 |
| `cut_punch_anim` | 关闭 | 剪映自带的入出场动画默认不用 |

生效还有几个阈值容易忽略：`punch_in` 需大于 1.001 且时长 ≥ 0.10 秒、单镜 ≥ 0.55 秒；`punch_out` 需非末镜、时长 ≥ 0.08 秒、单镜 ≥ 0.70 秒。此外进入/退出时长会被压到镜头时长的 40% 与 28% 以内，两者之和超过 55% 时按比例缩。

于是"短镜头没有运镜"不是 bug，是设计：一个 3 秒的镜头硬塞 1.8 秒推镜，观感会比静止更差。

## 为什么不用剪映自带的转场

代码注释里给的理由很直接：剪映内置的"动感缩小""放大"这类入出场动画，**会在切点闪一帧黑**。对成片来说，一闪黑比没有运镜更伤完片率，所以默认全部关掉，改用自己写的线性关键帧。

这是一个典型的"看起来该用现成功能，实际必须绕开"的工程判断。它也提示了一件事：这类工具的价值不在于用了多新的模型，而在于把踩过的坑固化成默认值。

## 目录与依赖：最容易卡住的地方

草稿根目录不是猜出来的，项目给了明确的优先级：

```
--drafts-root 参数
  → 环境变量 JY_PROJECTS_ROOT
    → 用户 runtime 配置
      → 剪映 globalSetting 中的草稿位置
        → 唯一可确定且已存在的标准目录
```

依赖也不止 Python：需要 `libmediainfo`（读媒体信息）与 `ffmpeg/ffprobe`（校验音视频）。缺少前者时，常见表现是"素材解析失败"，而不是报缺库。

调用方式（路径按自己机器调整）：

```sh
python "<项目目录>/modules/render-history-video/scripts/export_jianying.py" \
  "<版本目录>/plan.json" \
  --drafts-root "<剪映设置里的草稿目录>"
```

默认拒绝同名草稿；显式加 `--overwrite` 会先把旧目录备份再写入，失败的暂存工程会清理、不覆盖旧成果。这个行为值得照抄到自己的脚本里——剪辑产物没有版本控制，误覆盖的代价是重做。

## 验收清单

生成完不能只看"脚本没报错"。项目文档列出的检查项按可自动化程度分成两类：

| 检查项 | 能否脚本化 | 通过标准 |
| --- | --- | --- |
| 两份 JSON 内容一致 | 能 | `draft_content.json` 与 `draft_info.json` 对齐 |
| 素材路径存在 | 能 | 全部指向最终 `materials` 目录 |
| 轨道数量与连续性 | 能 | 无空洞、无重叠 |
| 首镜从 0 开始 | 能 | 第一段起点为 0 |
| 音频覆盖到末尾 | 能 | 音轨结束 ≥ 视频结束 |
| 关键帧存在 | 能 | 有缩放/位移关键帧 |
| 字幕状态 | 能 | 如声明有字幕，需实际存在 |
| **在剪映里能播放** | **不能** | 需人工打开、预览、导出 |

最后一行是这个流程的边界：项目明确**不生成 `final.mp4`**，也**不操作剪映 UI 自动导出**。想让 Agent 连"点导出"都替你完成，属于另一类工具（GUI 自动化），风险与维护成本都高一个量级。

## 常见失败与定位

| 现象 | 可能原因 | 定位方法 |
| --- | --- | --- |
| 草稿列表里没出现新工程 | 剪映未刷新 | 重启剪映，或进出旧工程再返回 |
| 素材显示丢失 | 素材被移动/改名 | 检查是否按哈希命名并复制进 materials |
| 关键帧在剪映里看不到 | 运镜条件未满足（镜头太短） | 看 resolved_plan.json 里的 `has_punch_in/out` |
| 音画不同步 | 用了重新均分的时间而非核验时间 | 比对 plan 与对齐产物 |
| 打开报版本错误 | 上游库与剪映版本不匹配 | 核对库版本与剪映版本（上游标注 10.8） |

## 一个镜头条目至少要写什么

生成草稿的入口是 `plan.json`。从 `motion.py` 与对齐文档里能看到的字段反推，单个镜头条目至少需要：

```json
{
  "id": "S001",
  "image": "S001.png",
  "start": 0,
  "end": 8.0,
  "duration_s": 8.0,
  "zoom": [1.00, 1.12],
  "cut_punch": true,
  "punch_in": 1.50,
  "punch_out": 1.28
}
```

三个容易写错的地方：

- `end - start` 与 `duration_s` 必须一致，否则运镜时长会算错；
- `zoom` 是首尾两个缩放值（即慢推拉的起止幅度），不是速率；
- `cut_punch` 只是“允许”开关，是否真的生成关键帧还取决于时长阈值。

写完先跑一次导出、看 `resolved_plan.json` 里每一镜的 `has_punch_in` / `has_punch_out` 是否如预期，比在剪映里试错快得多。

## 两条渲染分支：本地成片 vs 草稿

同一个项目里其实有两条路，容易混：

| 分支 | 入口脚本 | 产出 | 适用 |
| --- | --- | --- | --- |
| 本地渲染 | `render.py` | 直接输出视频 | 批量、无人值守 |
| 草稿导出 | `export_jianying.py` | 可编辑工程 | 需要人工微调、加字幕与特效 |

值得注意的是两条分支共用同一份运镜实现（`motion.py`），所以同一个 `plan.json` 在两边应该得到一致的镜头运动。如果一个在本地看着流畅、导进剪映却变了，优先查帧率与时间量化，而不是重写参数。

## 这套做法适合谁

适合：有稳定模板（固定画风、固定节奏）、单条素材量大、且愿意为"验收"留人力的团队。它把重复劳动压掉了，剩下的是判断与验收。

不适合：需要复杂转场、需要逐帧精修、需要字幕时间轴精确到字的项目。这些环节剪映的交互界面比 JSON 好用得多，硬要自动化反而更慢。

## 限制与结论

确定的事实：草稿生成这一步是真实可行的，机制是写 JSON + 复制素材 + 采样关键帧；运镜参数与阈值在源码里可查；不生成成片、不碰剪映 UI。

不确定的部分：上游库与剪映版本的兼容性只能靠实测（上游只标注到 10.8）；不同显卡/系统上的预览表现可能不同；"生成结构正确"与"观感可用"之间始终隔着一次人工预览。

如果要给一个可执行结论：把这条链路当成"草稿生成器"而不是"自动剪辑器"，验收清单里保留那一条不能脚本化的项——在剪映里播一遍。省下的时间来自不用手动加关键帧，而不是不用看片。
