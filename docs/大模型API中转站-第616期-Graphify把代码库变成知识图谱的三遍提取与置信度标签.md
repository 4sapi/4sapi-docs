# Graphify 把代码库变成知识图谱：三遍提取流程与置信度标签怎么读

让编程智能体理解一个大仓库，常见做法是让它反复 grep 和读文件，上下文很快被占满。Graphify 的思路是先把仓库提取成一张图，之后用查询代替读文件。图里每条边带一个置信度标签，告诉你这条关系是直接读出来的，还是推断出来的。

本文回答三个问题：图是怎么提取出来的；三种置信度标签各表示什么；哪些步骤会把内容发给模型。文章依据仓库里的架构、原理和安全文档，我没有安装或运行过它，所以没有自己的输出可展示。信息截止日期为 2026-10-30，引用前请重新打开原文件。

两点要注意。第一，PyPI 包名是两个 y 的 graphifyy，README 声明其他 graphify 开头的包与项目无关，安装前先核对包名。第二，不到七个月发了 265 个版本，行为可能频繁变化。

## 二、它是什么

按架构文档的说法，它是一个由 Python 库支撑的编程助手技能：技能负责编排，库也可以单独使用。在助手里输入 /graphify 加路径，会得到三个文件：

| 文件 | 内容 |
| --- | --- |
| graph.html | 在浏览器里点击、筛选、搜索的交互图 |
| GRAPH_REPORT.md | 要点：关键概念、意外的连接、建议的问题 |
| graph.json | 完整的图，之后可以反复查询而不必重读文件 |

README 强调它不是向量索引，没有嵌入和向量库。

## 三、流水线

架构文档给出的主流程是 detect、extract、build、cluster、analyze、report、export。各阶段在独立模块里，用普通的 Python 字典和 NetworkX 图传递数据。

| 阶段 | 输入到输出 |
| --- | --- |
| detect | 目录到扫描摘要：按类别分组的文件、总文件数、总词数 |
| extract | 文件路径列表到 nodes 与 edges |
| build | 提取结果到 NetworkX 图 |
| cluster | 图到社区划分 |
| analyze | 图到枢纽节点、意外连接、建议的问题、导入环等 |
| report | 图加分析到 GRAPH_REPORT.md |
| export | 图到 graph.json、graph.html、Obsidian 库、SVG、GraphML、Cypher 等 |

一个对二次开发者有用的提醒：调用 extract() 时务必显式传 root。节点 id 和 source_file 都相对于它推导，不传时它会取所传路径列表的公共父目录。只传单个文件，就会以该文件所在目录为根，节点 id 可能带上提取那台机器上的路径片段。

## 四、三遍提取

原理文档把处理分为三遍，这是理解成本和隐私的关键。

| 遍 | 处理对象 | 方式 | 是否调用模型 |
| --- | --- | --- | --- |
| 第一遍 | 代码 | tree-sitter 解析出类、函数、导入、调用图、行内注释；SQL 的表、视图、外键、JOIN 做确定性提取 | 否，完全本地 |
| 第二遍 | 视频和音频 | 本地 faster-whisper 转写；转写提示用代码图里连接最多的概念做种子 | 否，本地 |
| 第三遍 | Markdown、PDF、图片、转写文本 | 多个模型子智能体并行读文件批次，各输出一段 JSON，再合并 | 是，消耗 token |

只含代码的语料会整个跳过第三遍。也就是说，一个纯代码仓库的建图，按文档是不调用模型的；README 因此说代码解析免费、完全本地、内容不出本机。

### 语言数量的两种说法

原理文档写第一遍支持 25 种语言，README 写约 40 种，架构文档里还有"新增语言提取器"的步骤。两处数字对不上，原因我没有查清，可能是文档更新不同步。如果你的主力语言不在常见之列，以官方的支持输入页面为准，并在自己的仓库上实测。

### 歧义扩展名会悄悄出错

README 提到一个容易被忽略的问题：有些扩展名在不同项目里含义不同，例如 .inc 可能是 PHP、Pascal、SQL 或汇编，.h 可能是 C 或 C++，.m 可能是 Objective-C 或 MATLAB。判断错了文件不会报错，而是按错误的语言解析，只产出少量偶然的节点，图看起来有内容，真正的符号却缺失。

解决办法是在扫描根目录放 .graphifyrc，用 language.inc=php 这样的行声明扩展名含义。如果你的仓库有这类文件，建图后先抽查对应文件的符号是否出现在图里。

## 五、三种置信度标签

每条边带一个 confidence 字段。

| 标签 | 含义 | 分数 |
| --- | --- | --- |
| EXTRACTED | 源码里直接写明的关系，例如导入语句、直接调用 | 恒为 1.0 |
| INFERRED | 合理推断，例如调用图的二次解析、上下文共现 | 带 confidence_score，见下 |
| AMBIGUOUS | 不确定，在报告里标出供人工复核 | 无 |

INFERRED 的分数用离散档位：

| 分数 | 含义 |
| --- | --- |
| 0.95 | 近乎确定：明确的跨文件引用，只有一个合理目标 |
| 0.85 | 证据充分：命名和上下文吻合 |
| 0.75 | 合理：与上下文相关，但不明确 |
| 0.65 | 较弱：只有命名相似 |
| 0.55 | 推测 |

这些档位是评分准则，我没有看到各档的校准结果，所以 0.95 不应读成"95% 概率正确"，只是最确定的一档。

### 推断边的精度证据很少

基准文档给了一次对推断边的人工审计：对 FastAPI 做只用语法树的抽取，检查源和目标都在 fastapi/ 目录下的跨文件推断边，共 12 条，全部正确。文档自己说明这是"带日期的人工抽查，不是持续测量的指标"。

12 条全对的统计含义有限。我按精确二项分布算：0 个错误、12 个样本时，错误率的 95% 单侧上界约 22%；常用的"三法则"给出约 25%。也就是说，这个抽查不能排除真实错误率在两成左右。这是我的计算，用于说明样本量，不是项目的结论。

文档还指出，测试目录里同名的辅助函数会让推断的调用边更嘈杂，这个标签在生产代码的跨文件解析上最有意义。

## 六、社区划分

社区用 Leiden 算法：按边的密度分组，连接密的节点归入同一社区。原理文档强调不需要嵌入，模型提取出的语义相似边已经在图里，直接影响社区形状。

有一个静默的行为需要知道：没有安装 leiden 额外依赖时，聚类会静默回退到 networkx 的 Louvain。之后再切换，会重排所有社区，README 建议这时全量重新标注。如果你把社区划分当作文档的一部分长期维护，请固定使用的后端。

## 七、缓存与增量

每个被提取的文件按内容哈希生成指纹，重跑时跳过未改动的文件，缓存在 graphify-out/cache/。常用命令：

| 命令 | 作用 |
| --- | --- |
| /graphify . --update | 只重新提取改动的文件 |
| /graphify . --cluster-only | 不重新提取，只重新聚类 |
| graphify hook install | 在提交和切换分支时自动重建 |

README 提醒：钩子在提交和切分支时触发，git pull 之后要手动运行 graphify update . ，否则图会比代码旧。

## 八、哪些内容会离开本机

安全文档的网络边界描述是：代码提取在本地且确定；语义提取可能把内容发给你配置的模型后端；ingest 命令会按你给的地址主动抓取；HTTP 形式的 MCP 是可选的网络监听。

据此归纳：

| 场景 | 是否外发 |
| --- | --- |
| 纯代码仓库 | 按文档不外发 |
| 含文档、PDF、图片 | 第三遍会把内容交给配置的模型后端 |
| 音视频 | 转写在本地，但转写文本若进入第三遍则会外发 |
| 使用 ingest 抓取网页或论文 | 向你指定的地址发请求 |

后端可以是云端接口，也可以是本地的 Ollama。有保密要求时，先确认第三遍用的是哪个后端。

### 提示注入

第三遍会把源文件内容放进模型上下文，而源文件可能被攻击者控制。安全文档的做法是：把每个文件包在带哈希的 untrusted_source 分隔块里，系统提示要求模型把它当惰性数据，并清洗已知的聊天模板和越狱标记。文档自己的评价是，这是基本防御，不能使注入变得不可能，只是把难度从"一次就成"提高到"需要规避"。

对不可信仓库建图时，要预期图里可能混入被诱导产生的节点或边。

## 九、自己验证：统计置信度分布

图建好后，先看分布，再决定信到什么程度。下面的脚本读 graph.json，统计各标签的数量，并列出分数低于 0.75 的推断边。

```python
import json, sys, collections
data = json.load(open(sys.argv[1], encoding="utf-8"))
edges = data.get("links") or data.get("edges") or []
by_conf = collections.Counter(e.get("confidence", "MISSING") for e in edges)
print("edges:", len(edges), dict(by_conf))
inferred = [e for e in edges if e.get("confidence") == "INFERRED"]
low = [e for e in inferred if e.get("confidence_score", 1.0) < 0.75]
print("INFERRED with score < 0.75:", len(low))
for e in low[:5]:
    print("  ", e.get("source"), "-", e.get("relation"), "->", e.get("target"), e.get("confidence_score"))
print("AMBIGUOUS:", sum(1 for e in edges if e.get("confidence") == "AMBIGUOUS"))
```

运行方式：python check.py graphify-out/graph.json。我在手造的小文件上测过：4 条边，1 条 EXTRACTED、2 条 INFERRED、1 条 AMBIGUOUS，正确列出了分数 0.65 的那一条；对空图输出全 0。字段名按文档写成 source、target、relation、confidence、confidence_score，边的列表键兼容 links 和 edges 两种写法。它没有在真实的 graphify 输出上跑过，真实文件的字段可能有差异。

### 读方向时的陷阱

架构文档提醒：graph.json 写成 directed 为 false，但每条边都有方向，方向由边的顺序决定。用普通的 node_link_graph 加载会丢失方向，因为无向图会按节点列表位置重排端点。应当通过 paths.load_node_link_graph() 加载，或先对原始字典调用 restore_arc_direction()，然后用 _src 和 _tgt 读方向。上面的统计脚本不涉及方向，但做"谁调用谁"的分析时必须注意。

## 十、什么时候这样做不合适

| 情形 | 原因 |
| --- | --- |
| 仓库很小 | 原理文档自己说，6 个文件已能放进上下文窗口，此时图的价值是结构清晰，不是压缩 |
| 主力语言支持不确定 | 语言数量文档不一致 |
| 大量使用歧义扩展名 | 需要配置 .graphifyrc，否则符号缺失 |
| 内容不能发给任何模型 | 含文档或图片时第三遍会外发 |

## 十一、限制与结论

Graphify 的设计要点很清楚：代码走确定的本地解析，文档走模型，每条边带来源标签，缓存和增量降低重跑成本。标签让你能区分"读出来的"和"推出来的"，这比一张没有来源的图更容易审计。

本文的限制：没有安装或运行；没有读源码；没有核对在线文档；推断边的精度证据只有一次 12 条的人工抽查；语言数量两处文档不一致；统计脚本只在假数据上测过。

下一步建议：在一个你熟悉的小仓库上建一次图，先用第九节的脚本看置信度分布，再随机抽 20 条 INFERRED 边对照源码判断对错，算出自己的推断边精度，再决定是否让智能体依赖它。
