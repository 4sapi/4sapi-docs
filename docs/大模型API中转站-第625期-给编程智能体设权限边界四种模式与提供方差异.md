# 给编程智能体设权限边界：四种模式的实际行为与提供方差异

让编程智能体自己跑起来之后，风险的核心不是模型有多聪明，而是它动手之前要不要问你。同一套工具，设成"每步都确认"会慢到没人用，设成"什么都不问"则等于把仓库交给一个会走神的同事。

T3 Code 把这件事做成了四种模式，按线程生效。但有两个地方容易被忽略：开箱默认是最宽松的那一档；不同提供方的实际行为并不一样，同一档在 A 家是自动评审、在 B 家是回退成询问。

本文逐条说明这四种模式、它们的作用域与默认值，以及文档里列出的提供方差异。信息来自仓库的[权限模式文档](https://github.com/pingdotgg/t3code/blob/HEAD/docs/user/permission-modes.md)，检索日期为 2026-11-02。我没有安装或运行过它。

## 一、四种模式各批准什么

| 模式 | 行为 |
| --- | --- |
| Supervised | 命令和文件改动都请求批准 |
| Auto-accept edits | 自动批准文件编辑，其他动作仍可能需要批准 |
| Auto | 使用提供方自己的自动评审批准例行操作，其余仍会询问 |
| Full access | 命令与编辑都不弹批准 |

这四档不是"严格程度递增"那么简单，区别在于**谁来判定什么叫例行**。这里先插一条容易漏的原文句子：文档说各家执行权限的方式不同，**有些只读动作在 Supervised 下可以直接进行**——所以它也不是纯粹按动作类型判定的。

- Supervised 与 Auto-accept edits 是规则式的：按动作类型（命令 / 编辑）决定。
- Auto 把判断交给提供方的评审机制，因此它的实际效果取决于那一家的实现。
- Full access 干脆不问。

理解了这一点，就能明白为什么下面会有一堆"某家不支持某档"的例外：档位依赖提供方的能力。

## 二、作用域：按线程，不是全局

文档对作用域的规定比较细，值得逐条看，因为配错了会以为自己在安全模式，实际跑在另一档。

| 问题 | 规则 |
| --- | --- |
| 模式在哪选 | 在消息编辑器里选，对当前线程生效 |
| 新线程用什么 | 用设置里的新线程默认值，**而不是你正在看的那个线程的模式** |
| 默认值在哪改 | Settings → Threads → New threads → Permissions |
| 谁能覆盖 | 项目可以覆盖环境默认值 |
| 初始默认是什么 | **Full access** |
| 已存在的线程 | 保持原有权限 |
| 草稿里选过的模式 | 保留 |

第二行与第五行组合起来有一个后果：一个团队如果只在某个线程里调过模式，以为全项目都收紧了，其实新开的线程仍然按设置里的默认值走，而初始默认值是最宽的那档。

想收紧的话，要动的是设置里的默认值，或者让项目配置覆盖它。

### 管理员上限

文档还提供了一个上收机制：管理员可以用托管策略限制一台机器上可用的模式，超出上限的模式会显示由谁管理。

这对多机团队有用：个人机器上可以放开，共享机器上设上限。注意它限制的是"可选范围"，不是强制某个线程必须用哪一档。

## 三、提供方差异：这是最容易被忽略的一层

同一档模式在不同提供方上的落地方式不同。文档列出的差异如下。

| 提供方 | Auto 的含义 | 特殊限制 |
| --- | --- | --- |
| Codex、Claude、Cursor、Grok、fx | 使用该提供方的自动评审 | 见下 |
| OpenCode、Antigravity | 没有等价机制，回退为询问 | — |
| Grok | 自动评审拦截的命令会转给用户批准 | 不提供 Auto-accept edits；命令批准没有"本次会话全部允许" |
| fx | 仍会发出的提示转到用户 | 不提供 Auto-accept edits 与 Full access |
| Muse Code | — | 只提供 Supervised 与 Full access |
| Kiro | — | 只提供 Supervised 与 Full access；在 Supervised 下还会请你复核该轮的文件改动 |
| ACP Registry 类 | 在自己模式里跑自己的工具 | T3 Code 按权限模式回答其批准请求 |

几处需要展开：

**OpenCode 与 Antigravity 的 Auto 会变成询问。** 如果你在这两家上选 Auto，期待"例行操作自动过"，实际是每个动作都问你。这不是 bug，而是没有等价机制时的保守回退。

**Grok 的命令批准没有会话级选项。** 文档给的理由很有意思：Grok 会为该命令记住整个项目。也就是说，一个"本次会话全部允许"在 Grok 上不是会话级的，而是项目级的，所以干脆不提供。文件改动批准倒是提供"本次会话全部允许编辑"。

**fx 与 Muse Code 的档位更少。** 当某个线程原本设在不受支持的档位时，会退到 Supervised 运行。这意味着你在界面上看到的模式名和实际执行的不一定一致。

## 四、四处反直觉的细节

### 1. Full access 不等于什么都不问

文档明确：Claude 即便在 Full access 下仍可能询问，条件是它自己的设置禁用了绕过权限，或者要求对某个动作批准；Antigravity 也可能继续发原生批准请求。

所以"我开了全权限"只是关掉了这一层的门，提供方自己还有门。

### 2. 危险删除有一道独立的安全检查

在绕过模式下，Claude 的危险删除安全检查会带原始警告拒绝该命令。如果警告提供了安全改写，它会用改写；否则它不做这次删除，并告诉你跳过了什么。

这条值得记住：全权限模式下你仍可能看到"某条命令被拒"，那不是工具挡的，是提供方挡的。

### 3. 用文字回复就能拒绝一个挂起的批准

当 Claude 的一个批准请求挂起时，你可以输入文字回复来拒绝它，并直接给提问的 agent 反馈——包括提问者是子智能体的情况。其他挂起的请求保持未答复。

比起点"拒绝"按钮，这个设计更实用：你可以在拒绝的同时说明该怎么改。

### 4. 子智能体的批准请求出现在父对话

带子智能体名字显示在父对话里，你不用切换线程就能回应。

这一点影响权限设计：即使子智能体在后台跑，它的越界动作也会露在你能看到的地方。

## 五、模式管不到什么

两件事要分清：

1. **权限模式不阻止 agent 就任务提问。** 它管的是执行动作，不是沟通。
2. **模式与项目的信任是两回事。** 权限模式决定 agent 能否不问就动手；而项目里带的配置、脚本、MCP 服务器要不要加载，是另一套授权。

第二点是我的提醒，不是这份文档的内容：权限模式文档只讲动作批准，没有涉及仓库自带资源（配置、脚本、MCP 服务器）的加载授权。我把它放在这里，是因为两者在实践里会互相影响——比如你批准的那条命令如果调用了仓库里的脚本，脚本本身的效果也在同一次批准里。

## 六、按场景怎么选

以下是基于文档行为的条件化建议，不是项目推荐。

| 场景 | 建议 | 理由 |
| --- | --- | --- |
| 第一次在新仓库上跑 | Supervised | 先看清它想做什么，再决定放不放 |
| 只读探查、写报告 | Supervised 足够 | 多数动作是读取，批准成本低 |
| 大量机械改写、有干净分支保护 | Auto-accept edits | 文件改动自动过，命令仍受控 |
| 有完整测试与回滚机制 | Auto（在支持的提供方上） | 用提供方评审筛例行操作 |
| 无人值守跑批 | 慎用 Full access，并配管理员上限 | 出问题时没人拦 |

最后一行要补充：如果你确实要无人值守，至少确保工作区在隔离分支或独立 worktree 上，让最坏情况止步于可以丢弃的一棵树。

## 七、三种常见的误配

下面三种都是“看起来设了、实际没生效”的情形，按上面两张表推得。

| 误配 | 为何不生效 | 怎么改 |
| --- | --- | --- |
| 在某个线程里改成 Supervised，以为全项目收紧了 | 模式按线程生效，新线程用设置里的默认值 | 改 New threads 的默认值，或让项目覆盖 |
| 在 OpenCode 上选 Auto，以为例行操作会自动过 | 该家没有等价机制，回退为询问 | 接受逐次询问，或改成 Supervised 并集中处理 |
| 以为 Full access 就能一路不被打断 | 提供方自己还会拦：Claude 的设置与危险删除检查、Antigravity 的原生请求 | 把“提供方仍会问”当成预期行为，不要当成故障 |

第二行与第三行合起来提示一件事：权限模式是本工具这一层的内定义，它不取消下面一层的限制。排查“为什么还会弹窗”时，先分清弹窗是哪一层发的。

## 八、怎么验证你的设置真的生效

配置这件事最容易出的错是"以为设了"。按下面几步核对：

1. **看新线程，不看老线程。** 新建一个线程，确认 composer 处显示的模式是你预期的那个。老线程会保留原权限，不能用来验证默认值。
2. **确认项目覆盖。** 如果你在项目里设了默认，确认它确实覆盖了环境默认值。
3. **测一档最危险的。** 在测试仓库里故意让 agent 执行一个会写文件且需要批准的动作，观察是否真的弹批准。这一步能同时验证模式与提供方是否支持该档。
4. **核对不可支持的组合。** 如果你用的提供方在上面那张差异表里，确认线程没有退到 Supervised 而你以为是别的档。
5. **检查管理员上限。** 在共享机器上确认上限有没有把你的模式压下来，界面上会显示由谁管理。

第 3 步是唯一能确认"实际行为"的方法。文档能告诉你设计意图，但提供方版本变了，行为可能跟着变。

## 九、限制与结论

四种模式的价值在于把"要不要问"变成一个显式的、可按线程设置的开关，并且承认不同提供方的能力不同，退到更保守的一档而不是假装支持。默认值是最宽的那档，这一点需要主动改。

本文的限制：没有安装或运行，所有行为描述来自文档；没有核对各提供方的版本差异；托管策略、ACP 类 agent 的细节我只引用了结论，没有读被引用的文档；不涉及跨项目或跨机器的集中管控方案。

下一步建议：先把自己常用的那几个仓库的默认值改成 Supervised，用一周，记录你实际批准了多少次、哪些其实是例行操作。有了这个比例，再决定往哪一档放，比凭感觉设更靠谱。
