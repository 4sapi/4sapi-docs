# 用斜杠命令固化重复的开发协作流程

分类：开发工具

标签：AI 编程、开发效率、提示词工程

摘要：开发者经常反复要求 AI 执行相同的仓库检查、提交说明或测试准备工作。下面给出一套将稳定流程设计为斜杠命令的思路，包括边界定义、命令模板、验证标准和维护方式，适合使用支持自定义命令的 AI 开发工具的团队。

每次进入项目都要让 AI 重复回答“当前分支是什么”“最近改了哪些提交”“测试从哪里开始跑”，看似只是多输入几句话，实际会让协作上下文越来越混乱。更麻烦的是，同一件事被不同人描述成不同提示词后，输出格式也会漂移，难以形成可靠习惯。

斜杠命令的价值不是把一段提示词缩短，而是把一个边界清晰、结果可检查的重复流程固化下来。以下以仓库状态检查为例，说明如何设计这样的命令；具体配置位置和注册方式需要以所用工具当前版本的官方文档为准。

## 先判断流程是否适合固化

适合做成命令的流程通常有三个特征：触发频率高、输入变化少、输出可以明确验收。仓库状态检查、变更摘要、提交前检查、故障信息收集都符合这些特征。

不适合直接固化的流程，则往往需要大量业务判断，例如“评估这次重构是否值得做”。这类任务可以用命令收集事实，但不应把最终判断写死在模板里。

在开始前，把命令的契约写清楚：

- 输入：命令运行目录，以及可选的范围参数。
- 操作：只读取版本控制信息，不修改工作区和远端仓库。
- 输出：当前分支、工作区状态、最近三条提交；非仓库目录要给出明确提示。
- 失败条件：版本控制工具不可用、目录无权限或命令执行失败。

这一步能防止一个看似方便的快捷命令，在不知情时执行写入、提交或推送操作。

## 用自然语言定义命令模板

多数 AI 开发工具都允许将命令映射为一段固定指令。下面的模板只描述目标和验证标准，不依赖某个产品的私有命令格式：

```text
命令用途：检查当前目录的 Git 仓库状态。

请仅执行只读 Git 查询。若当前目录不在 Git 工作树中，直接说明原因并停止。
若是 Git 仓库，按以下格式输出：
1. 当前分支名称；
2. 工作区是否有未提交修改；
3. 最近 3 条提交的短哈希、日期和主题。

不要执行 add、commit、push、reset、checkout 或其他会修改仓库状态的命令。
如果任一查询失败，保留错误信息并说明下一步排查方向。
```

这段模板的关键是“只读”“固定输出”和“停止条件”。相比“帮我看一下仓库情况”，它减少了模型自行补全任务范围的空间。

如果工具支持参数，可以再设计一个可选参数，例如 `--since` 用于限定提交时间范围。但参数越多，越接近一个需要维护的接口。优先保留最常用的默认路径，把少见需求交给普通对话处理。

## 给每个命令补一条验证路径

命令创建后，至少在三种场景中验证：干净仓库、有未提交修改的仓库，以及非 Git 目录。以 Git 为例，可以人工对照以下只读命令的输出：

```bash
git branch --show-current
git status --short
git log -3 --pretty=format:"%h %ad %s" --date=short
```

预期结果不一定要逐字一致，但分支、修改状态和提交记录应能相互对应。若 AI 输出了推测内容，例如把未跟踪文件误判为已提交，应该回到模板中补充判断规则，而不是只靠下一次临时纠正。

也应检查安全边界。对于仓库类命令，运行记录中不应出现 `git commit`、`git push`、`git reset` 或覆盖式检出等写操作。若工具具有权限预设，应将此类信息查询命令放在最低必要权限下运行。

## 把命令当成小型接口维护

命令一旦被团队复用，就需要像接口一样保持稳定。建议为每个命令保留用途、输入、权限、预期输出和最近验证日期。变更输出字段时，先确认是否有脚本、文档或其他命令依赖旧格式。

当一个命令开始包含多个互不相关的动作时，应拆分。例如“检查仓库、运行测试、生成发布说明”最好是三个命令：前两项的失败处理和权限要求明显不同，混在一起会让定位问题变得困难。

## 从需求到命令：一个完整的设计过程

下面用“提交前检查”说明如何把一个模糊需求逐步变成命令。第一步不是写提示词，而是列出人工操作清单：确认所在目录、读取当前分支、查看未提交文件、查看最近提交、确认是否存在未推送提交。第二步删掉不属于本次目标的动作，例如自动整理代码、修改提交信息或推送远端。第三步为每个输出字段指定来源和异常情况。

如果命令的使用者是整个团队，还应确定输出语言和格式。纯文本适合直接阅读，表格适合比较多个仓库，机器可读的 JSON 则适合被脚本继续消费。不要在同一命令中同时输出大量解释性段落和不稳定的机器格式；需要两种用途时，可以提供一个简洁的人读命令和一个明确声明格式的脚本命令。

命令描述可以拆成四块：角色约束、操作范围、输出契约、停止条件。角色约束说明 AI 是“只读检查器”还是“可以提出修改建议的助手”；操作范围说明允许访问的目录和命令；输出契约说明字段顺序、缺失值和时间格式；停止条件则规定遇到非仓库、权限错误或工具不可用时不能继续猜测。

## 一个可复用的命令规范

团队可以为所有自定义命令采用类似下面的记录格式。它不是某个具体工具的配置文件，而是方便评审和迁移的设计文档。

```yaml
name: repo
purpose: 输出当前仓库的只读状态摘要
inputs:
  - name: path
    required: false
    default: 当前工作目录
permissions:
  filesystem: read-only
  network: disabled
  repository_write: false
outputs:
  - current_branch
  - worktree_status
  - recent_commits
failure_cases:
  - not_a_repository
  - git_not_installed
  - permission_denied
validation: 与 git status、git log 的人工结果对照
```

在实际注册时，把这份记录转换成工具要求的命令文件或插件配置。这样做的好处是，换用其他 AI 开发工具时，只需重写外层适配，而不用重新讨论命令的行为边界。

## 参数、上下文和默认值怎么取舍

命令是否需要参数，取决于输入变化是否真的值得抽象。仓库检查中的“最近几条提交”可以设为固定的三条，因为这是最常见的快速浏览需求；如果团队经常需要审查两个版本之间的差异，则可以增加明确的 `base` 和 `head` 参数，并在缺失时拒绝猜测默认分支。

参数应有类型、默认值和非法值处理。例如，提交数量只能是正整数，路径必须在允许的工作区范围内，时间范围不能和提交范围同时产生歧义。对于来自用户的路径和分支名，命令实现应避免直接拼接到 shell 字符串中，优先使用参数数组或工具提供的安全调用接口。

命令还可能依赖会话上下文，例如上一次对话中确定的目标分支。依赖上下文可以减少重复输入，但也会增加不可见状态。建议在输出中明确显示实际使用的路径、分支和范围，让读者知道命令到底检查了什么。

## 失败案例与排查顺序

“命令没有返回结果”并不等于仓库没有问题。排查时可以按从环境到模板的顺序进行：

1. 先在同一目录手动执行只读 Git 命令，确认 Git 可用且目录权限正常。
2. 检查 AI 工具是否把命令注册到当前配置档，而不是另一个工作区或终端配置档。
3. 查看调用日志，确认命令是否真的被触发，参数是否被错误转义。
4. 对照输出契约检查字段是否缺失；若只缺少日期格式，属于模板问题，不要重新安装整个插件。
5. 如果模型在失败时继续编造提交记录，应在停止条件中加入“无可靠输出即停止”，并把错误原文保留给使用者。

常见的另一个问题是命令名称冲突。内置命令、自定义命令和插件命令可能使用同一个短名称。命名时应使用项目内唯一、含义明确的名称，并在安装或升级后重新列出命令清单确认实际生效项。

## 与脚本、CI 和团队规范的关系

斜杠命令适合交互式检查，不应取代持续集成中的确定性校验。比如格式检查、单元测试和依赖漏洞扫描仍应由 CI 使用固定版本的工具执行；斜杠命令可以帮助开发者收集状态、解释失败日志或生成检查清单。把两者职责混在一起，会导致本地对话能通过而流水线仍然失败。

如果命令输出要贴进代码评审，应避免包含访问令牌、内部路径和整段环境变量。可以在模板中要求对用户名、主机名和密钥进行脱敏，并限制最近提交的展示范围。对于涉及多个仓库的命令，还要说明扫描顺序和遇到单个仓库失败时是否继续。

## 版本升级前的回归检查

命令依赖的内置工具名称、插件加载方式和权限模型可能随版本变化。升级 AI 开发工具后，至少执行一次回归检查：命令是否仍出现在列表中、非仓库目录是否能正常停止、只读约束是否有效、输出字段是否保持兼容。如果底层命令或日志格式发生变化，应更新设计记录和示例，而不是让使用者自行猜测差异。

对于团队共享的命令，建议把测试场景放在仓库中，包括空仓库、浅克隆、存在未跟踪文件、分支名称包含空格以及没有远端的本地仓库。每次修改模板后运行这些场景，可以较早发现模型把异常情况当作正常结果的问题。

## 迁移到团队环境前的检查

个人命令迁移到团队环境时，先确认目录结构、默认分支和工具版本是否一致。相对路径在不同项目中可能指向不同文件，固定命令应输出实际工作目录并在发现不一致时停止。

还要明确谁可以修改命令定义。命令文件进入版本控制后，变更应经过代码评审，并在至少一个干净仓库中执行回归场景。这样可以避免某个人本机的别名、环境变量或插件状态被误当成团队标准。

## 命令交付前的最小检查表

- 在正确仓库和正确分支中运行。
- 非仓库目录能给出停止提示。
- 只读约束在日志中可观察。
- 输出字段与人工命令结果一致。
- 目标重名、权限错误和工具缺失都有处理说明。

## 结论

斜杠命令适合承载高频、低歧义、可验证的开发协作流程。先定义输入输出和权限边界，再用真实场景验证，最后将它作为小型接口持续维护，才能让快捷操作真正减少沟通成本。涉及执行脚本、修改文件或访问外部服务的命令，应另行明确授权与失败处理。
