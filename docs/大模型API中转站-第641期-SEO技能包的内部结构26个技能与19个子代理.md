# SEO 技能包的内部结构：26 个技能、19 个子代理与一套守卫规则

看到"某技能包含 26 个子技能、19 个专家代理"这类描述，第一反应通常是"这不就是一堆提示词吗"。差别在结构：谁负责路由、谁负责执行、哪些情况必须停下来。

claude-seo 是个适合拆开看的样本：它把 SEO 工作拆成多个技能文件与代理定义，还写了不少"硬规则"与错误处理表。本文按文件统计讲清它的结构、运行约定与守卫机制，不涉及任何效果评价。SEO 政策与合规边界另有一篇。

信息来自仓库 [README](https://github.com/AgriciDaniel/claude-seo/blob/HEAD/README.md)、[`plugin.json`](https://github.com/AgriciDaniel/claude-seo/blob/HEAD/.claude-plugin/plugin.json)、[路由技能的 SKILL.md](https://github.com/AgriciDaniel/claude-seo/blob/HEAD/skills/seo/SKILL.md) 与目录树，检索日期为 2026-11-04。我没有安装或运行过它。

## 一、先对齐数字

同一个东西在三处被写成了不同数字，先摆出来：

| 出处 | 说法 |
| --- | --- |
| README | 26 个子技能、19 个专家代理，最多 17 个代理并行 |
| `.claude-plugin/plugin.json` | "26 sub-skills（22 核心 + 1 编排 + 1 框架 + 2 扩展镜像）与 19 sub-agents" |
| `skills/seo/SKILL.md` 正文 | "Orchestrates 25 sub-skills（22 core + 1 framework integration + 2 extension mirrors）and 19 sub-agents" |

按文件数是这样的（我的统计）：

| 项目 | 数量 |
| --- | --- |
| `skills/` 下的 `SKILL.md` | 26 |
| `extensions/` 下的扩展技能 | 9（ahrefs、banana、bing-webmaster、dataforseo、firecrawl、matomo、profound、seranking、unlighthouse） |
| 合计 `SKILL.md` | 35 |
| `agents/` 下的代理定义 | 19 |
| `commands/` 目录 | 不存在 |

26 与 25 的差 1 不用猜：`skills/seo/SKILL.md` 里明说编排器自己（`seo`）就是 `skills/` 下的第 26 个，但它不编排自己，所以没列进下面的清单。插件清单算进去了、技能正文的括号没算，差别就在这一项。这类差异不影响使用，但说明**引用数字时要写清口径**。

另外注意最后一行：这个仓库没有 `commands/` 目录，而 README 说它有 30 个核心与扩展命令（另注若干扩展命令见 docs/COMMANDS.md）。命令是通过技能 frontmatter 的 `user-invocable` 与 `argument-hint` 暴露的，不是独立文件。这和上一个我拆过的插件仓库（命令放在 `commands/` 下）是不同的实现方式。

## 二、三层分工

| 层 | 数量 | 作用 |
| --- | --- | --- |
| 路由技能 | 1（`seo`） | 判断该走哪条具体工作流 |
| 核心技能 | 22 | 各自负责一块，如技术审计、内容质量、结构化数据、站点地图、性能、GEO 等 |
| 子代理 | 19（另有 3 个随扩展自带） | 并行执行的角色定义；此处只计 `agents/` 目录，三个扩展各另带一个 |
| 扩展 | 9 | 接外部数据源（关键词、外链、爬虫、站长平台等） |

路由技能的 description 写得很直白：它列出了触发词（SEO、audit、schema、Core Web Vitals、sitemap、E-E-A-T、AI Overviews、GEO…），并声明"只在 SEO 领域明确但具体工作流不明确时使用这个 hub，否则用具体的 seo-* 技能"。

这句话是这类技能包里最值得抄的一行：**路由技能不该抢具体技能的活。** 否则所有请求都被路由层接走，具体技能永远不触发。

## 三、技能文件里到底写了什么

以路由技能为例，它的结构是：

| 部分 | 内容 |
| --- | --- |
| frontmatter | name、description（含触发词清单）、`user-invocable: true`、`argument-hint`、license、metadata（version、category） |
| 运行约定 | 内置脚本一律通过插件自带的启动器执行，禁止用裸 Python |
| 命令表 | 一条命令一行，说明做什么 |
| 编排逻辑 | 何时派子代理、并行还是退回串行、如何检测业务类型 |
| 质量门 | 若干硬规则与阈值 |
| 错误处理 | 一张"情形 → 动作"表 |

第三行与第五、六行，是"提示词合集"与"技能包"的分界。

### 运行约定那条为什么重要

原文规定：跑内置脚本只能用如下形式，并明确禁止裸解释器：

```text
"${CLAUDE_PLUGIN_ROOT}/scripts/claude-seo" run <script.py>
```

它还解释了为什么仓库里没有顶层 `bin/` 目录：托管市场不接受。这类细节在自建时容易踩——你在本地跑得好好的，装到市场里就找不到入口。

## 四、仓库里不只有 Markdown

前面拆过的另一个插件仓库强调"组件全是文件、无代码"。这个仓库不是：

| 目录 | 内容 | 我的统计 |
| --- | --- | --- |
| `hooks/` | `hooks.json`、`run-python-hook.js`、`validate-schema.py` | 3 个文件 |
| `scripts/` | 各类内置脚本 | 61 个文件 |
| `tests/` | 测试 | 78 个文件（另有一个 `fixtures/` 目录；把目录条目算进去会得到 79） |
| `schema/`、`data/` | 结构化数据与数据文件 | 存在 |

README 声称有 1077 个测试通过，我没有复现，只能说仓库里确实有成规模的测试目录。

这个差别对选型有意义：**纯文件化便于审阅与移植，带脚本则能做确定性检查**（例如真正去抓页面、算 Lighthouse 分数、校验 JSON-LD）。两者不是优劣，而是"能验证什么"不同。

### 一个具体的派发例子

`/seo audit <url>` 这一类请求，在技能正文里的路径是这样的：

1. 先按首页信号判断业务类型（SaaS、本地服务、电商、出版、代理机构、其他）。
2. 抓取站内链接，上限 500 页，遵守 robots.txt。
3. 把后续工作派给子代理（技术、内容、Schema、站点地图、性能、视觉等）；子代理不可用时退回串行执行。
4. 汇总成按优先级排序的动作清单。

这个顺序里有两处设计值得注意。第二处的 500 页上限说明它默认"全站审计"是抽样式而非穷尽式；第三处的"不可用则串行"说明并行是优化而非前提——很多技能包在这一点上写死并行，导致在单代理环境里直接失败。

## 五、守卫规则：这套结构里最实用的部分

技能正文里有一批明确的"停手条件"，我按主题整理：

| 类别 | 规则（原文要点） |
| --- | --- |
| 规模化页面 | 位置页 30 个以上给警告，并要求 60% 以上独有内容；50 个以上硬停，需要用户说明理由 |
| 程序化发布 | 每批 50 到 100 页，观察 2 到 4 周再扩；500 页以上不是一律禁止，而是硬停并要求显式批准与薄内容审计 |
| 独立价值测试 | 若没有同类页存在，这一页是否还值得发布 |
| 结构化数据 | 不建议 HowTo schema；FAQ 富结果自 2026-05-07 起不再展示（HowTo 文档于 2023-09-14 移除、FAQ 停用写在 Google 更新日志 2026-05-08 条目，这两条我已核实） |
| 索引膨胀 | 低价值页 noindex；sitemap 中排除 noindex 页 |
| 事实来源 | Google 更新类问题必须查仓库自带的一手来源台账，不许凭记忆回答 |

注意这几条的共同形态：**阈值 + 触发的动作 + 需要谁来决定**。这比"注意不要过度优化"这种建议可执行得多。

## 六、错误处理表也值得抄

审计技能里有一张"情形 → 动作"表，我挑三条：

| 情形 | 规定动作 |
| --- | --- |
| URL 不可达 | 报告错误、建议核对 URL，**不猜站点内容** |
| robots.txt 拦截 | 报出被拦路径，只分析可访问页面，并在报告里注明这一限制 |
| 返回 429 | 退避、降低并发，报告部分结果并说明哪些部分没跑完 |

这三条覆盖了自动化审计最常见的三种失败。第二行尤其重要：**把"没看到"和"没有"分开**，是这类工具可信度的底线。

## 七、对自建技能包的启示

| 做法 | 为什么值得抄 |
| --- | --- |
| 单独一个路由技能，并写明"别抢具体技能的活" | 避免触发错层 |
| 每条工作流一个技能文件，正文写步骤与阈值 | 可审阅、可版本对比 |
| 质量门写成"阈值 + 动作 + 谁来定" | 能被执行，不只是提醒 |
| 错误处理列成表 | 失败时行为一致 |
| 内置脚本走统一启动器 | 换安装方式时不必改所有技能 |
| 明确区分"带脚本"与"纯文件"两类能力 | 决定你能验证什么 |

第四条在多 agent 并行的结构里格外重要：没有统一的失败约定，不同子代理会各自发挥。

## 八、限制与结论

这个技能包的形状可以概括为：一个负责分派的路由技能，22 个各自负责一块的核心技能，19 个可并行的子代理，9 个接外部数据的扩展；仓库里还带脚本、钩子与测试，因此它能做确定性检查。它最实用的部分不是命令数量，而是写进正文的质量门与错误处理表。

本文的限制：没有安装或运行，未复现任何测试或耗时数据；26 与 25 的差异由技能正文自述；FAQ 富结果与 HowTo 弃用两条已在 Google 文档更新日志里核实；扩展的可用性与授权未核验；不评价其审计结论的准确性。

下一步建议：如果你在做技能包，先写"错误处理表"和"质量门"，再写命令清单。前者决定它能不能被人放心交给 agent 自动跑，后者只是入口。
