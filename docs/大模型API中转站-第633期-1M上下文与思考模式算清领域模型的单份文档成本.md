# 1M 上下文与思考模式：算清领域模型的单份文档成本

长文档任务的成本，直觉经常出错。直觉会说"上下文大所以便宜"，或者"输入很便宜所以随便塞"。实际情况取决于三个数之间的关系：输入价、输出价、缓存价，以及你的调用里到底有多少轮会重发同一份材料。

至于法务这类场景为什么值得单独算：一份尽调材料几百页很常见，同一个文档在一个工具循环里会被反复发送。这时候差一个数量级，是能算出来的。

本文用 GLM-5.3-FlashX-Legal 的官方标价做算例。价格来自 [OpenRouter 的模型页](https://openrouter.ai/z-ai/glm-5.3-flashx-legal)（检索日期 2026-11-03），算术是我用脚本算的，页数与 token 的换算是估算假设，后面会标出来。不构成法律意见。

## 一、三个价格与它们的关系

| 项目 | 单价（每百万 token） |
| --- | --- |
| 输入 | $0.37 |
| 输出 | $1.25 |
| 缓存读取 | $0.075 |

先算两个派生比值，它们决定了成本结构：

| 比值 | 数值 | 含义 |
| --- | --- | --- |
| 输出价 ÷ 输入价 | 3.38 倍 | 一个输出 token 的钱够买约 3.4 个输入 token |
| 缓存价 ÷ 输入价 | 0.203 | 命中缓存时约为原价的 2 折（精确 2.03 折，折扣 79.7%） |

这两句话可以直接拿来指导设计：

1. **成本的大头通常不在读文档，而在写东西。** 除非你把同一份材料重发了很多轮。
2. **缓存是否命中，决定长文档任务能不能做。** 相差 5 倍。

## 二、按文档规模估输入成本

这里要先声明一个假设：**1 页约 700 token**。这是英文文档的粗略换算，中文、表格多、扫描件转文本的页会不一样。所有下面的数字都基于这个假设，你可以用自己的实际 token 数替换。

| 文档规模 | 估算 token | 输入成本 |
| --- | --- | --- |
| 50 页 | 3.5 万 | $0.0130 |
| 200 页 | 14 万 | $0.0518 |
| 1000 页 | 70 万 | $0.2590 |
| 恰好 100 万 token | 100 万 | $0.37 |
| 填满 1,048,576 token | 104.9 万 | $0.388 |

读完这张表，第一个结论是：**单纯"读一遍"很便宜。** 一份 200 页的材料一次输入约 5 分美元。

这也解释了为什么 1M 上下文这件事被反复提：按这个价格，塞满一次不到 4 毛美元。但"塞得进去"和"该塞进去"是两件事，第三、四节会展开。

## 三、真正的成本来自重复发送

工具循环是最常见的成本放大器。假设一个法务任务需要调 5 轮工具（检索条文、读另一份文件、生成表格、改稿、复核），而每一轮都要把那份 14 万 token 的材料重发一遍：

| 情形 | 计算 | 成本 |
| --- | --- | --- |
| 5 轮全部未命中缓存 | 70 万 token × $0.37 | $0.2590 |
| 1 轮未命中 + 4 轮命中 | 14 万 × $0.37 + 56 万 × $0.075 | $0.0938 |
| 上一行再加 2 万输出 token | 再加 2 万 × $1.25 | $0.1188 |

从 0.26 美元降到 0.094 美元，差别只在于那 4 轮有没有命中缓存。这个数还有一个前提：**缓存存储当前不额外收费**（定价页把该列标为限时免费），属临时政策；一旦开始收费，命中缓存的账要重算。

### 提高命中率的三个条件

缓存不是自动生效的，它要求前缀稳定：

1. **把不变的部分放在最前面。** 长文档、系统指令、工具定义放前面，本轮问题放最后。
2. **前缀逐字节稳定。** 哪怕前面多了一个空格或改了一个标点，后面全部失效。
3. **按用量字段验证。** 不要凭感觉判断有没有命中，看响应里的缓存字段。

第 2 条在工程上最容易被破坏：模板拼装时带入了时间戳、会话 ID 或随机排序的列表，缓存就永远不命中。

## 四、思考模式把成本推到输出侧

[OpenRouter 对该模型的描述](https://openrouter.ai/z-ai/glm-5.3-flashx-legal)里提到强制思考模式。这一条对成本的影响比价格表本身更大，原因很简单：**思考产生的 token 走输出价。**

按 3.38 倍的比值，输出侧每 1000 token 的钱等于输入侧约 3400 token。举两个量级：

| 场景 | 输出 token | 成本 |
| --- | --- | --- |
| 一次回答，其中一半是思考 | 2 万（1 万思考） | $0.0250（思考部分约 $0.0125） |
| 长文书初稿 | 20 万 | $0.25 |

第二行值得留意，但对比对象容易搞错：**一份 20 万 token 的初稿，输出成本约等于读 1000 页材料一次的输入成本**（$0.25 对 $0.259，几乎持平）；要凑出"十倍"，对应的是 100 页那一档。真正该记住的是量级关系：读得越多越便宜，写得越长越贵。

这里还有两个我没在表里标注的前提：单次输出上限是 131,072 token，所以 20 万 token 的初稿必然跨至少两次调用，而跨调用时输入会被重发，$0.25 只是输出侧的下界；同理，1,048,576 的上下文里还要容纳输出，工程上不存在"把 1M 全部当输入"的调用。

强制思考还有一层影响：它意味着你无法通过"关闭思考"来省钱。如果某些任务不需要推演，这个模型在这部分没有折扣空间。

## 五、1M 上下文的两个陷阱

**陷阱一：装得下不等于用得好。** 上下文越长，中段内容被忽略的概率越高。这不是这个模型特有的问题，但对法务场景影响直接：如果关键条款在文档中段，你可能会得到一个"看起来完整"却漏掉它的结论。

**陷阱二：延迟与并发。** 该模型的卖点之一是基座 FlashX 的 200 tokens/s（官方对基座的描述），但那是生成速度，不是处理长输入的速度。输入越长，首 token 时间越长。这一项我没有实测，只能提示要自己量。

实践建议：与其把 1000 页塞进去，不如先检索定位到相关的 20 到 50 页再送入。这样既省输入成本，也降低"中段被忽略"的风险。

## 六、一个可复用的估算公式

```text
单任务成本 =
    未命中输入 token ÷ 1e6 × 输入价
  + 命中缓存 token  ÷ 1e6 × 缓存价
  + 输出 token      ÷ 1e6 × 输出价
```

用代码写出来，方便在跑之前先估：

```python
IN, OUT, CACHE = 0.37, 1.25, 0.075   # 每百万 token，2026-11-03 的标价

def cost(tok_in=0, tok_out=0, tok_cache=0):
    return tok_in/1e6*IN + tok_out/1e6*OUT + tok_cache/1e6*CACHE

# 例：14 万 token 文档，5 轮工具循环，1 轮未命中 4 轮命中，输出 2 万
print(cost(tok_in=140_000, tok_cache=560_000, tok_out=20_000))   # 0.1188
```

这个函数我在本机跑过，输出与第三节表格一致。

### 估算的三个步骤

1. **数输入。** 用 tokenizer 或接口的用量字段，把每轮的输入 token 记下来，别用页数估。
2. **数轮次。** 工具循环有几次会把同一前缀重发，直接影响缓存能省多少。
3. **数输出。** 包括思考 token。如果拿不到思考的单独计数，就用总输出量乘输出价，宁可高估。

## 七、四个容易漏计的成本项

| 项目 | 为什么容易漏 |
| --- | --- |
| 重试与重跑 | 失败一次就多一轮输入，长文档时这项不小 |
| 工具调用往返 | 每次工具结果都要再次进入上下文，等价于重发 |
| 结构化输出失败 | 格式不合规要重来，输出侧的钱白花 |
| 人工复核时间 | 不是 token 成本，但通常比 token 成本高一个量级 |

最后一行值得单独说：一份 200 页材料的推理成本只有几美分，而人复核一次要几十分钟。所以"省 token"往往不是这类应用的成本优化重点——**减少返工次数**才是。

## 八、怎么验证估算与实际一致

| 步骤 | 做什么 |
| --- | --- |
| 1 | 拿一份真实文档，跑完整任务，记录每次调用的用量字段 |
| 2 | 用上面的公式把每轮相加，与账单或控制台的用量对比 |
| 3 | 差异超过 20% 时，先查缓存命中率，再查是否有重试 |
| 4 | 把这次的输入、轮次、输出记成基线，之后改动配置都对照它 |

第 3 步的次序很重要：缓存命中率是最常见的偏差来源，而且这类问题通常不报错，只在账单上体现。

## 九、限制与结论

三个数字决定长文档任务的成本：输入便宜、输出贵 3.38 倍、缓存约 2 折。在这个结构下，读文档的钱很少，写东西的钱和重复发送的钱才是重点；强制思考模式进一步把成本从输入侧推到输出侧。

本文的限制：价格是 2026-11-03 的快照；"1 页约 700 token"是我的估算假设，不是官方数据；没有实测调用，没有核对思考 token 的计费细节；缓存字段的行为以接口为准，文档未逐个核验；不构成法律意见。

下一步建议：拿你手上最长的一份文档，先只做一次"读入 + 提三条风险"的最小调用，记录用量字段，再用第六节的公式算一遍。这一次的真实数字比任何估算表都有用。
