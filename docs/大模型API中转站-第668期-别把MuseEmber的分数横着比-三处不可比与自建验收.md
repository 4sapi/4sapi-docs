# 别把 Muse Ember 的分数横着比：三处不可比与自建验收

官方发布 Muse Ember 时给了一张对照表：十行评测、三列模型，格子里标着"最佳结果"。排得整齐，容易让人以为这是同一把尺子量出的三个数。

实际上至少有三处不可比：跑分的 harness 不同，评分口径不同，复合指标的权重也不公开。再加上同一页面里同一个配置会出现两个数（36 与 35.8），差异已经小到不该用来做决策。

本文只讲怎么读这些数字：哪些能横着比，哪些只能竖着看，哪些干脆不能用；最后给一套用自己任务集做的验收流程。不评价模型好坏。

## 一、先把数字的来源分成四层

同一批基准，现在至少有四个出处，口径各不相同。

| 来源 | 内容 | 性质 |
| --- | --- | --- |
| 官方发布博客 | 10 行评测的对比表，格子里标"最佳结果" | 厂商自测，转引第三方结果 |
| 官方评估方法 PDF | 每个 benchmark 的任务数、判分器、删题规则、跑法 | 厂商自测的方法说明 |
| Artificial Analysis 模型页 | 智能指数 36、每任务成本 $0.14、每任务 3.2 分钟 | 第三方独立跑分 |
| OpenRouter 模型页收录的 Vals AI 结果 | 10 项：7 个单项 benchmark、3 个指数 | 第三方跑分，经聚合平台展示 |

检索日期均为 2026-11-12。三个出处里，前两个是同一家，后两个各自独立。入口如下（检索于 2026-11-12）：

- 官方发布博客：https://research.meta.ai/blog/muse-ember
- 评估方法 PDF：https://research.meta.ai/static/muse-ember-evaluation-report
- Artificial Analysis 模型页：https://artificialanalysis.ai/models/muse-ember
- OpenRouter 模型页（含 Vals AI 结果）：https://openrouter.ai/meta/muse-ember

先看一个能说明问题的例子：Terminal-Bench 4.0 这一项，官方博客写 40.9，Vals AI 在 OpenRouter 页面上写 39.4。同一个 benchmark、同一个模型，差 1.5 个百分点。差异来自跑的 harness 与重试策略，不是模型变了。

所以第一条读法是：跨来源的分数不要直接相减。要么在同一来源内比较，要么只拿它做方向判断。

## 二、第一处不可比：三家不同 harness

官方对比表里 Terminal-Bench 4.0 那一行的脚注写得很清楚：每个模型用的是它"最佳公开 harness"。Muse Ember 是 mini-swe-agent，Claude Haiku 5.5 用的是 Anthropic 系统卡里 Claude Code 的结果，GPT-6 Luna 用的是 Terminal-Bench 榜上 Codex 的结果。

考核的是"模型在某个 agent 里完成任务"的能力，其中 agent 的提示、工具集、重试逻辑都会影响分数。三个模型跑在三套不同的 agent 里，横向比出来的差额里，有一部分属于 harness 而不属于模型。

Artificial Analysis 的 Coding Agent Index 也一样：Muse Ember 跑在 Muse Code 里，Claude Haiku 5.5 跑在 Claude Code 里，GPT-6 Luna 跑在 Codex 里（官方评估方法 PDF，检索于 2026-11-12）。这是行业里通行的做法，但读表的人要明白它不是控制变量实验。

能横比的只有同 harness 内的数字，比如同一套 mini-swe-agent 下的各家成绩。跨 harness 的差额只说明"这套组合在这套题上得了多少分"。

## 三、第二处不可比：评分口径

同一行分数可能是"部分得分"，也可能是"全对才算过"，差别可以很大。

**OSWorld 2.1 是两个口径并排给的。** 官方表里 Ember 是 69.5（partial）/ 33.8（binary），Haiku 5.5 是 68.9 / 27.8，GPT-6 Luna 是 50.5 / 17.0。partial 是每任务的平均得分，binary 是拿满分的任务占比。看 partial 会觉得两家打平，看 binary 就差 6 个百分点。而且这一项官方用的是自己的框架，不是官方 runner，模型判分部分由 Claude Sonnet 4.6 打分。

**GDP.pdf 用的是 all-pass。** 每个评分项都要过才算对，三家的分数是 22.8 / 22.8 / 20.8，挤在一起。这种口径对"格式漂亮的半成品答案"不给分，所以分数低不代表模型差，代表它不宽容。

**Agents' Last Exam 有删题。** 官方用 ALE v1.0 的 Linux 子集，105 个任务去掉 5 个（数据超出存储上限，或脚本没返回分数），三个模型去的是同一批。部分 LLM 判分用 GPT-5.5。

这三处放在一起看，能得出一个实用判断：**binary 或 all-pass 的分数，最接近"一次做对"的能力**。做子代理选型时该看这类数字，而不是 partial。

把常见的几种口径并排放在一起，读表时先认清格子里是哪一个：

| 口径 | 含义 | 分数怎么解读 |
| --- | --- | --- |
| partial / mean score | 每任务平均得分，做了一半也给分 | 高不代表一次能做对 |
| binary / strict pass | 拿满分的任务占比 | 最接近一次做对 |
| all-pass | 每个评分项都过才算对 | 对半成品不给分 |
| pass@1 | 第一次尝试就完全通过 | 与子代理场景最贴近 |

## 四、第三处不可比：复合指标的权重

官方表里的 Personal Superintelligence Index（PSI）是内部复合指标，由 8 项评测合成：Agents' Last Exam、AutomationBench-AA、JobBench、OfficeQA Pro V2、GDP.pdf、GDP.xlsx、VBT、FocusBench。评估方法 PDF 列了这 8 项，没有给权重。

Artificial Analysis 的智能指数是 v5.0.1 版本，该模型页写"包含 9 项评测"：AA-Briefcase v1.1、AutomationBench-AA、Terminal-Bench 4.0、FrontierCode-AA 2.0、AA-Omniscience v1.1、GDP.pdf、HLE-Diamond、CritPt v2 和 Terminal-Bench-Science 0.1。页面同样只给总分，没有逐项权重。

复合指标的问题不在于它不严谨，而在于**权重决定了结论**。一个偏编码的加权方案和一个偏知识工作的加权方案，会把同样的单项成绩算成不同的名次。所以复合分只能回答"综合起来大概什么水平"，回答不了"我的任务上能不能用"。

顺带一个观察：同一个官方页面，表格里 Ember（max）的智能指数写 36，成本-智能散点图里对应点是 35.8；Haiku 5.5 表格写 36，散点图里最高点是 36.2。同一页两处并存，差 0.2 到 0.4。这个量级的差距是排版的舍入与快照时间差，不该拿来做选择依据。

## 五、"三分之一成本"这句话的成立条件

官方博客的原话是：它以约三分之一的成本追平 Haiku 的最高分，并且超过 Luna 的所有档位。

拿同一页散点图上的点来核对：

| 模型与档位 | 智能指数 | 每任务成本 |
| --- | --- | --- |
| Muse Ember 最高点 | 35.8 | $0.136 |
| Claude Haiku 5.5 最高点 | 36.2 | $0.411 |
| Claude Haiku 5.5 中间档 | 34.3 | $0.248 |
| GPT-6 Luna 最高档 | 27.8 | $0.152 |

对着 Haiku 的最高点，0.136 / 0.411 约等于三分之一，这句话成立；但分数是 35.8 对 36.2，低 0.4 分，"追平"是宽松说法。对着 Haiku 的中间档，0.136 / 0.248 是 55%，不是三分之一。

所以这句话成立的条件要写全：**与 Haiku 在最高推理档的成绩相比，成本约为三分之一，分数差 0.4**。省掉后半句，读者会以为在任何档位都是三分之一。

## 六、两处口径冲突，以及怎么处理

**模态。** 官方文档与 OpenRouter 都写 Ember 输入支持文本、图像、视频、音频、PDF。Artificial Analysis 的模型页写"支持文本与图像输入"。三方不一致。合理解释是第三方只测了它能稳定测的两类，但这只是推断。处理办法是以官方文档为准做能力判断，第三方页面只当参考。

**Provider 数量。** Artificial Analysis 写"可通过 1 个 provider 调用"，OpenRouter 列出 2 家：Google Vertex 与 Meta 自己，并给出两家的延迟、吞吐与三天可用率（Meta 端点 100%，Vertex 86.94%，检索于 2026-11-12）。两边都对，只是统计时间与范围不同。选型时以聚合平台的实际路由列表为准，因为它会随上架变化。

另外，OpenRouter 页面写明这个模型"不支持 EU in-region 路由"。这条不是分数，但对有数据驻留要求的团队是硬约束，比任何 benchmark 都重要。

## 七、自建验收：三十到五十条真实任务

公开分数适合粗筛，不适合验收。下面这套流程只用人手边已有的东西。

1. **建任务集。** 从日志里抽 30 到 50 条真实子任务，把失败过的样本也放进去。全挑成功案例，任何模型都能过。
2. **锁四个变量。** 同一 harness、同一 `reasoning_effort`、同一 `max_output_tokens`、同一采样参数。少锁一个，比较就不成立。
3. **跑两到三个模型。** 至少放一个现役执行层模型做基线。一次全套跑下来是 100 到 150 次请求，成本可以忽略。
4. **两级判定。** 严格通过（产出直接可用）与一次内返工（人改一次能用）。只看第一级会把"改两下就能用"算成失败。
5. **记四个数。** 严格通过率、返工率、每任务成本、P95 延迟。成本按实际 token 乘官方价目算，不要拿第三方的每任务成本套用。
6. **看差异显著性。** 50 条任务上 2 个百分点的差距没有意义。把判定标准提前写成"差 5 个百分点以上才换"，能省掉很多争论。

跑完这轮，得到的是"在我这 50 条任务上，换过去多几个返工、少多少钱"，而不是"哪个模型更强"。

## 八、什么时候可以只看公开分数

两种情况可以。

一是粗筛：判断某个模型值不值得进入上面那轮验收。这时看同一来源内的排序和量级，而不是分值本身。比如"每任务成本差一个数量级"比"指数高 1 分"稳得多。

二是排雷：看哪些单项明显落后。FrontierCode 2.0 那一项，Haiku 5.5 是 34.9、Ember 是 27.2、Luna 是 25.2，这是官方表里 Ember 唯一落后的一项。这种单点落后比总分更有信息量，因为它能对应到任务类型。

除此之外，公开分数都只该当参考，不该当验收线。厂商自测、第三方复核、聚合平台收录，三层的目标不同，谁都不会按你的业务分布加权。

## 九、五种常见的读表错误

把上面的内容压成一张清单，这五种错误在实际评审里出现得最多：

1. **把不同 harness 的行相减。** Terminal-Bench 4.0 那一行的三个成绩来自三套 agent，差额里混着 harness 的贡献。
2. **把 partial 当 strict。** OSWorld 2.1 上 69.5 与 33.8 是同一个模型的两个口径，引用时写错口径会把结论放大一倍。
3. **拿复合指数的 1 分差做决策。** 权重不公开，1 分的差额落在舍入与快照误差里。
4. **把一次发布的快照当稳定状态。** 同一页两处给出 36 与 35.8，这类数字会随版本变动，引用时要带检索日期。
5. **忽略删题与判分器。** Agents' Last Exam 去掉了 5 个任务，部分判分由另一个模型做，这两件事都会轻微改变分数。

## 十、限制与结论

本文只讨论数字怎么读。所有分数都是 2026-11-12 在官方与第三方页面读到的，第三方数据仍在积累。本文没有新的实测，百分比是我按页面上的数据点做的除法。

结论三条。

一是横比之前先看 harness。跨 harness 的差额里混着 agent 的能力，不能整体记在模型头上。

二是优先看 binary 与 all-pass 口径的分数。partial 分高的模型，可能在"一次做对"上明显落后，而子代理场景要的正是后者。

三是把公开分数当粗筛，把自建验收当决策。30 到 50 条真实任务、锁死四个变量、两级判定、算清每任务成本，一次能跑完，结论比榜单贴近业务。
