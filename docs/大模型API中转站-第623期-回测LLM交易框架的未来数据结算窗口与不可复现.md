# 回测一个 LLM 交易框架：未来数据、结算窗口与不可复现

用一个大模型驱动的研究框架做回测，最容易得到的结果不是"差"，而是"看起来很好"。因为未来数据进入回测的方式非常多，而且大多数是静默的：程序不报错，报告照出，数字还更漂亮。

TradingAgents 的 [CHANGELOG](https://github.com/TauricResearch/TradingAgents/blob/HEAD/CHANGELOG.md) 在这个问题上特别有参考价值。它从 0.3 到 0.7 的每个版本都在修与"未来数据"有关的问题，一条条摆出了这类系统会从哪里漏。本文把这些修补归纳成可检查的清单，再讲清入场口径与结算窗口的门道。

先说清定位：本文讨论方法和风险，不涉及任何标的，也不给出任何买卖判断，不构成投资建议。项目 README 也写明了同样的限定。信息来自[仓库文档](https://github.com/TauricResearch/TradingAgents)与[源码](https://github.com/TauricResearch/TradingAgents/blob/HEAD/tradingagents/backtest.py)，检索日期为 2026-11-01，我没有运行过任何一次回测。

## 一、先看框架自己的提醒

在讲漏洞之前，这三段原文的意思值得先记住。

| 出处 | 意思 |
| --- | --- |
| README 可复现性一节 | 同一标的同一天跑两次结果可能不同，这是研究工具的预期行为，不是缺陷 |
| 回测模块文档 | 一次运行只产出一个决策，无法据此判断决策质量；该模块评估决策质量，不是组合模拟器，也不应扩展成一个 |
| README 结尾 | 回测结果不保证与任何已公布数字一致，应把框架当作研究多智能体分析的脚手架 |

第三条尤其重要。它等于说：即便照着官方参数跑，也不能指望复现论文里的数字。

## 二、未来数据从哪些缝隙进来

下面每一条都对应 CHANGELOG 里的一次实际修复（我按问题归类，不逐字引用）。

| 缝隙 | 问题是什么 | 后果 |
| --- | --- | --- |
| 宏观数据版本 | 历史宏观请求曾按"今天的数据版本"返回，后来的修订被一并带进回测 | 回测用上了当时还不存在的修正值 |
| 社交情绪时点 | 社交平台与论坛内容曾不带日期抓取 | 历史运行看到的是"现在"的讨论 |
| 财报时间戳口径 | 部分数据源按覆盖期间而非申报日标注财报 | 回看历史时会把尚未公布的报表当成已公布 |
| 内部人交易 | 按发生时间而非申报时间标注 | 历史运行看到后来才披露的交易 |
| 日期格式 | 模型给出的未补零日期（如 2024-7-5）曾被当成更晚的日期 | 读到了运行日之后才提交的监管文件 |
| 过滤器的实现细节 | 某数据源的前视过滤因为载荷是字符串而整段被跳过 | 过滤等于没开 |
| 记忆回灌 | 历史决策的结算结果曾被回灌给更早的决策 | 用未来的结果修正过去的判断 |

这些缝里最值得警惕的是第一条和最后一条，因为它们不在数据抓取层。

第一条是版本问题：宏观数据会被修订，取"当前最新"就是把后见之明接进历史。修法是按 as-of 日期固定数据版本。

最后一条是记忆问题：这类系统会把过去的决策与反思回灌给下一次判断。如果结算发生在持仓期走完之前，回灌的就是用未来结果写成的教训。项目为此加了时点防护，并把"持仓窗口未走完就结算"这件事单独修掉。

### 一个具体的例子

README 用一家美国公司的历史数据说明了"按申报原样"意味着什么：某年总资产申报为 396 亿美元，两年后被重述为 362 亿美元；那么介于两者之间的日期运行，读到的应当是 396 亿，而不是重述后的 362 亿。

这个例子说明，point-in-time 不是"取历史数据"这么简单，而是"取当时能看到的那一版"。

## 三、入场与结算口径

第二个容易出错的地方是"用什么价格入场、什么时候结算"。

### 入场：决策日之后第一个收盘

项目把决策的入场点定在决策日之后的第一个收盘，理由写在文档里：一次运行会读到该日收盘之后发布的新闻。如果用决策日当天的收盘价入场，就等于用收盘价买到了一个还需要看当晚新闻才能得出的判断。

这是回测里最常见的隐性未来数据之一。它的隐蔽之处在于：数据本身没有错，错的是时间对齐。

### 结算：几个被修掉的边界

| 边界 | 修法 |
| --- | --- |
| 当日仍在交易的 K 线 | 不再用它结算，避免用一个尚未定型的收盘价 |
| 超过一周的休市（如长假） | 恢复交易后再结算，而不是一直挂着 |
| 持仓期未走完就重跑 | 等到窗口真正走完再结算，避免提前用部分收益结算 |
| 同一决策重复结算 | 共享日志的多个运行各自只结算一次，中断后已完成的结果保留 |

### 最隐蔽的一处：续跑混用两种口径

v0.7.0 的升级说明里有一条需要注意：结算口径从"决策日收盘"改成"决策日之后第一个收盘"之后，**旧记忆日志里已结算的结果保留旧口径**。所以用同一个 run_id 续跑的回测会同时包含两种口径的结果。

官方建议是：要比较就像对像地比，开一轮新的。

这条对任何"可恢复的长任务"都成立：当你改了评分或结算规则，历史结果不会自动重算，混在一起看会得出错误结论。

## 四、评级的方向语义

回测按评级分组统计，而统计方式取决于每个评级声称了什么方向：

| 评级 | 声称的方向 |
| --- | --- |
| Buy | 向上 |
| Overweight | 向上 |
| Hold | 不声称方向 |
| Underweight | 向下 |
| Sell | 向下 |

因此 Hold 没有命中率可言，源码里对它的方向值就是 0，统计时明确输出"未声称方向"。

按这个分布，五档里两档声称向上、两档向下、一档不表态，即 40%、40%、20%（我的算术）。含义是：如果模型大量输出 Hold，表面上看"命中率"会缺失很大一块，而实际可评估的样本会变少。看回测汇总时，先看每档的样本数，再看命中率。

## 五、单元格独立，不是组合模拟器

回测在一组标的与日期上跑，每个组合是一格。源码文档明确了两条边界：

1. 各单元格相互独立。
2. 传入的组合是每一格共用的同一本账，而不是逐格结转的持仓。

含义：这一轮跑完的"收益"不是你账户的曲线，而是一批互不相干的决策各自的结果。想得到组合层面的结论，需要自己按时间顺序模拟资金与仓位，而这个框架刻意不提供。

我认为这个边界划得对。把评估工具和撮合模拟混在一起，最容易产出的就是一段看起来平滑、其实假设了无限流动性和完美成交的净值曲线。

## 六、为什么不可复现

源码文档用一句话承认了这件事：每格只有一次模型采样，且文本类信息源没有归档，所以这些数字是指示性的，不可重复。

README 把波动来源拆成三类：

| 来源 | 说明 |
| --- | --- |
| 模型采样 | 即使固定温度，各家也不保证逐字节一致；推理模型的内部推理本身是采样的，波动最大 |
| 实时数据 | 新闻、论坛、社交内容随时间变化，今天跑历史日期看到的输入也和上周不同 |
| 数据快照 | 价格与技术指标已被固定到已验证快照，公司身分也已确定性解析，这两块不再是波动源 |

第二条值得强调：把分析日期固定在历史某天，只能固定价格窗口，社交与新闻源仍然反映"现在"。这意味着**用这类框架回看过去，输入本身就不可重建**。

实践含义：在这种前提下，"回测出多少收益"这个数字本身没有可迁移性。能给的信息是相对比较——比如同一批单元格上两种配置的差异方向，而且差异要大于波动才有意义。

## 七、一个量级感受

回测的代价容易被低估。按官方示例的网格方式，从 2026-06-01 到 2026-08-01 每 7 天一格，是 9 个日期（2026-06-01 到 2026-07-27）。乘上标的数：

| 标的数 | 单元格数 |
| --- | --- |
| 2 | 18 |
| 10 | 90 |

每一格都要跑完整的多智能体流程：四类分析师、多空辩论、交易员、三名风险辩手、组合经理。按默认配置，仅四个分析师各 20 轮工具调用上限就有最多 80 轮调用（我的算术，不含辩论与经理）。90 格意味着这套流程跑 90 次。

所以在做网格之前，先用一两格验证配置与成本，再决定网格大小。项目也提供了 `--run-id` 续跑，中断后可以接着跑。

## 八、自查清单

拿到任何一份这类框架的回测结果，按下面的顺序问：

| 检查项 | 具体问法 |
| --- | --- |
| 数据版本 | 宏观与财务数据是按 as-of 固定，还是取当前最新 |
| 社交与新闻 | 历史运行能否重建当时的文本输入；不能的话结论如何限定 |
| 时间戳口径 | 财报按申报日还是覆盖期间；内部人交易按发生还是申报 |
| 日期处理 | 未补零日期、时区、长休市是否都处理了 |
| 入场价 | 用的是决策日收盘，还是其后的第一个收盘 |
| 结算窗口 | 持仓期是否走完；有没有提前结算 |
| 口径变更 | 是否混用了修改前后的结算规则 |
| 样本量 | 每档评级各有多少格；Hold 占多少 |
| 独立性与组合 | 单元格是否独立；有没有偷偷做成净值曲线 |
| 可重复性 | 同一格重跑结果的差异有多大 |

最后一项最容易被跳过。建议对同一格重复跑几次，看评级是否稳定；如果同一标的同一天能从 Buy 跳到 Sell，那么网格里任何一格的结果都不该单独解读。

## 九、限制与结论

这类框架的回测能回答的问题很有限：它评估的是决策质量的一小部分，且每次只有一次采样、文本输入不可重建。未来数据的缝隙又多又静默，项目自己是靠一代代修补才逐条堵上的。

本文的限制：没有运行过任何回测；CHANGELOG 里的 issue 编号未逐个核对；单元格数与评级分布是我按源码和示例做的算术；没有评估过任何标的，也不构成投资建议；论文声称的收益与回撤改进我没有复现。

下一步建议：如果你想用这类框架做研究，先固定一个极小的网格（例如 2 个标的、3 个日期），把第八节逐项过一遍，并对同一格重复跑三次看评级是否稳定。这三步能筛掉大部分"看起来很好"的结论。
