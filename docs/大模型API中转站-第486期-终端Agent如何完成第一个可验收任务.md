# 终端 Agent 如何完成第一个可验收任务

分类：人工智能

标签：AI Agent、终端工具、效率工具

摘要：第一次使用终端 Agent，最容易卡在“不知道从哪句话开始”，或被一句“已经完成”误导。本文用一份虚构会议记录演示从建立练习目录、准备输入、提交任务到独立验收的完整流程，重点说明路径、权限、输出和证据链。

终端 Agent 和普通聊天工具的区别，不在于输入框换成了黑色背景，而在于它能读取当前电脑里的文件、运行命令并把结果写回磁盘。能力变强以后，任务的后果也更真实：它可能读错文件、写错目录，或者在没有明确范围时执行额外动作。

因此第一次练习不应该追求复杂。准备一个独立目录，放入一份虚构材料，让 Agent 生成一个新文件，再回到命令行检查原件和结果。这个过程看似简单，却包含了以后整理资料、修改代码和生成报告都需要的基本习惯：先确认工作位置，明确输入和输出，限制操作范围，最后独立验收。

这里不绑定某个终端 Agent 的具体版本。不同工具的安装命令、登录方式和快捷键会变化，实际使用时应以当前版本的官方文档为准。文中的命令示例采用类 Unix 终端写法，Windows 用户需按 PowerShell、WSL 或 Windows Terminal 的环境调整路径。

## 一、先判断任务是否适合终端 Agent

适合入门的任务通常具备四个条件：材料已经存在、动作可以描述、输出有固定位置、结果能够逐项检查。把一份会议记录整理成行动清单就符合这些条件。原始材料是什么、要提取哪些字段、输出写到哪里、怎样判断有没有漏项，都可以提前写清楚。

相反，“帮我把项目做好”“整理一下电脑”“优化所有文件”都不适合第一次练习。这些说法没有限定材料和范围，Agent 可能需要自己猜测目标，甚至触碰不该修改的目录。任务越模糊，工具能力越强，偏离目标后造成的影响可能越大。

第一次练习的材料应该是虚构的、短小的、容易人工核对的文件。不要直接拿客户合同、私人照片、生产代码或包含密钥的配置文件测试。低风险材料能让你观察工具行为，而不用同时承担数据泄露和误修改风险。

## 二、建立独立练习目录

先在终端创建一个工作目录，并把输入与输出分开。下面是 macOS、Linux 或 WSL 中的一种写法：

```bash
mkdir -p ~/Downloads/agent-practice/input
mkdir -p ~/Downloads/agent-practice/output
cd ~/Downloads/agent-practice
pwd
ls
```

`mkdir -p` 会创建不存在的目录；`cd` 进入练习目录；`pwd` 显示当前绝对路径；`ls` 列出当前位置内容。执行后，应该看到 `input` 和 `output` 两个目录，并确认当前路径确实是刚创建的位置。

如果 `pwd` 显示的不是预期目录，先不要启动 Agent。终端 Agent 的相对路径都以启动位置为基础，工作目录错了，后续的 `@input/...` 和 `output/...` 也会指向错误位置。Windows PowerShell 可以用 `New-Item -ItemType Directory` 创建目录，用 `Get-Location` 和 `Get-ChildItem` 检查位置。

把输入和输出分开有两个好处。第一，任务开始前 `output` 通常是空的，完成后新增文件一眼可见；第二，Agent 即便误写结果，也不容易覆盖原始材料。这个目录不是系统级沙箱，只是一个更容易观察和恢复的工作起点。

## 三、准备一份可核对的输入

在 `input` 中创建 `meeting.md`，内容可以是：

```markdown
# 项目启动会记录

会议日期：2026-08-26

- 官网说明页由小林整理，截止日期为 2026-08-28。需要核对安装命令是否仍然有效。
- 教程截图由小周制作，截止日期为 2026-08-30。需要隐藏账号、私人路径和凭据。
- 发布前检查由小陈负责，截止日期为 2026-09-01。需要确认命令和截图逐项对应。

补充说明：本次只制作练习文件，不修改其他目录，不发送或上传任何内容。
```

这份材料故意包含三个负责人、三个日期和三条风险提醒。任务完成后，你可以不依赖模型的自我评价，直接对照原文检查这些字段是否全部保留。输入材料短而明确，也便于观察 Agent 是如何读取、理解和写入文件的。

如果你需要确认输入文件在任务前后没有变化，可以先计算校验值：

```bash
shasum -a 256 input/meeting.md
```

Windows PowerShell 可使用 `Get-FileHash input\meeting.md -Algorithm SHA256`。校验值只说明文件内容是否完全一致，不能告诉你具体哪里变化；发现变化时仍需查看差异。

## 四、启动 Agent 并确认三个状态

启动终端 Agent 前，先确认版本和工作目录。不同工具的命令不同，原则是先运行版本查询，再从练习目录启动。进入界面后至少看三个位置：当前目录、当前模型或账号、会话是否保存。

当前目录决定相对路径和默认工作范围；模型或账号决定请求发送到哪里；会话设置决定后续是否会保存文件路径、提示词和工具输出。认证、订阅和 API Key 属于外部服务配置，必须由使用者本人完成，不要把真实凭据粘贴进文章、截图或聊天记录。

第一次启动时不要同时安装很多扩展、切换多个模型或调整大量参数。环境变化越多，遇到问题时越难知道原因。先用默认能力完成单文件任务，确认基本链路可用，再逐项增加设置。

如果启动界面显示加载了项目规则、扩展或技能，先记下名称。加载提示只说明资源进入了会话，不代表它建立了操作系统级隔离，也不代表每条规则都会自动正确执行。工具调用和最终文件仍然需要检查。

## 五、把提示词写成可验收的任务单

在输入区引用材料，并明确动作、限制、输出位置和验收条件。一个足够具体的任务可以这样写：

```text
读取 input/meeting.md，整理成 output/action-list.md。

必须保留每个事项、负责人、截止日期和风险提醒；
不得修改或覆盖 input 中的原文件；
不得访问当前练习目录以外的内容；
不得发送、上传、删除或安装任何东西。

完成后列出新增和修改的文件，并说明我应该如何逐项验收。
```

“读取什么”解决材料身份问题；“整理成什么”说明动作和输出；“不得做什么”限制范围；“如何验收”把完成条件变成可检查事实。只写“帮我整理一下”时，Agent 不知道哪个文件是原始材料，也不知道应该生成什么格式。

限制要写成具体动作，而不是抽象的“不要出错”。例如不修改 `input`、不访问目录外内容、不上传和不删除，都比“保持安全”更容易观察。提示词本身不是系统权限，若当前账号能够读写其他目录，Agent 仍可能在工具层面访问它们，所以应结合工作目录、账号权限和必要的外部隔离。

## 六、观察工具事件，而不是只看总结

提交任务后，终端界面一般会显示读取、写入和命令执行等事件。你需要关注它是否读取了指定输入，是否只写入目标输出，是否尝试访问额外路径。

如果只要求整理一份 Markdown，却看到 Agent 搜索整个主目录、读取无关配置或执行网络命令，应先按 Escape 或工具提供的中断操作停止，再检查任务范围。工具事件比最后一句“已经完成”更能说明电脑上实际发生了什么。

正常情况下，事件链至少应能解释三件事：输入文件被读取，输出文件被创建，过程中没有超出授权范围的额外动作。某些工具可能把多个底层操作折叠显示，遇到不清楚的情况，应打开详细日志或改用更小的任务重试。

## 七、独立检查输出文件

Agent 说完成后，退出或暂时离开会话，回到命令行检查实际文件：

```bash
ls -l input output
test -f output/action-list.md
sed -n '1,120p' output/action-list.md
shasum -a 256 input/meeting.md
```

检查输入校验值是否与任务前一致；确认输出文件确实存在且非空；打开输出内容，核对小林、小周、小陈、三个日期和三条风险提醒。不要把“文件存在”当成内容正确，空文件、格式错误和字段缺失都可能通过这一项。

验收可以分成两层。第一层由 Agent 根据提示词做自查，例如列出它提取的事项；第二层由人直接回到原始材料核对。两层使用的依据不同，能够减少模型把自己的错误总结当成证据。

## 八、失败时怎样定位问题

如果没有生成输出，先检查当前目录和输入路径，再看工具事件是否出现权限或命令错误；不要立即重写整段提示词。如果输出缺少日期或负责人，说明验收条件不够突出，补充字段要求后重试。如果输出位置错误，说明相对路径或工作目录没有确认清楚。

如果输入文件被修改，先停止后续动作，保留当前状态并与备份或版本记录对比。不要让 Agent 在不清楚原因时继续“修复”，否则可能覆盖更多内容。练习目录可以直接删除后重建，真实项目则应使用版本控制、备份或回收站等可恢复机制。

模型输出流畅但事实错误时，优先回查原始文件和工具输出。换模型可能改变文字风格，却不一定解决输入范围、口径或验收不清的问题。先修正材料指向和结果标准，再考虑模型选择。

## 九、把一次练习变成可重复流程

任务通过后，可以把输入目录、输出目录、提示词和验收命令保存成一份练习说明。下一次换一份虚构会议记录，先复制练习目录再运行，检查流程是否仍能识别负责人、日期和风险字段。

如果输出格式稳定，再把长期约束放进项目规则文件，把每次变化的材料和目标留在当前提示词中。不要一开始就安装扩展或写复杂脚本；先确认内置读取、写入和命令能力已经满足需求。

## 十、哪些任务暂时不要交给 Agent

涉及真实密钥、生产删除、付款、法律承诺、公开发布和不可恢复迁移的任务，不适合作为第一次练习。即便以后处理，也应使用隔离环境、专用账号和明确的人工确认点。

Agent 可以帮你列出操作步骤、生成草稿和检查日志，但最终授权仍由人完成。把“建议执行”和“已经执行”分开写，能减少把计划误当成事实的风险。

## 十一、给练习增加一个反例

可以在输入文件中加入一条没有负责人或截止日期的事项，观察 Agent 是否把缺失信息标为待确认，而不是自行补写。这个反例能验证提示词是否真的要求保留不确定性。

## 十二、把验收命令保存下来

将查看输出、比较校验值和检查关键字段的命令保存为 `verify.sh` 或 PowerShell 脚本。脚本只读，不要在里面加入清理和覆盖操作。下次换输入材料时，先运行同一套检查，再判断流程是否仍然可靠。

## 结论

这套验收习惯也适用于后续更复杂的任务。

第一次使用终端 Agent，不需要先掌握所有命令和扩展。只要从独立练习目录开始，明确输入、动作、限制和输出，再通过工具事件与命令行双重验收，就能完成一条完整且可复核的任务链。真正值得迁移到日常工作的，不是某个特定提示词，而是“先确认位置，后执行；先生成结果，后独立核对”的方法。
