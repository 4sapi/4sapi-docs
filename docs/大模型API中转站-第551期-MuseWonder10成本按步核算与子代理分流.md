# Muse Wonder 1.0 成本怎么算：按步核算与子代理分流

以 **2026 年 10 月 14 日**核验的信息为准，公开定价口径显示 Muse Wonder 1.0 约为每百万输入 4.00 美元、每百万输出 20.00 美元，缓存读取约为每百万 0.20 美元。**这类价格属于可变事实，接入前应以 Meta 官方 API 文档为准**；官方发布说明本身重点描述的是能力，而不是定价。[Muse Wonder 发布说明](https://research.meta.ai/blog/muse-wonder)

这个价格在前沿档位里属于正常水平，但它面向的是**长任务**，而长任务最贵的从来不是单价，而是**步数**。一个 20 步的任务，即使每步都不长，累积成本也会远超一次问答。本文只回答一个问题：**怎么给长任务代理做成本预算，并用子代理分流把花费用在刀刃上。**

## 一、成本公式要按步展开

普通模型按请求核算就够，代理式模型必须按步核算：

```text
任务成本 = Σ(每步输入成本 + 每步输出成本)
         + 缓存写入成本
         - 缓存复用节省
         + 重试成本
         + 子代理成本
```

关键在“每一步都要重新带上上下文”，所以随着步数增加，单步输入会越来越大——除非做了压缩或状态外置。这是长任务成本呈**超线性**增长的根本原因。

## 二、一步要花多少钱

按公开单价做算术推算（假设算例，非实测）：

| 单步输入 | 单步输出 | 无缓存成本 | 缓存命中 80% |
| --- | --- | --- | --- |
| 5,000 | 500 | 0.020 + 0.010 = 0.030 美元 | 约 0.014 美元 |
| 20,000 | 800 | 0.080 + 0.016 = 0.096 美元 | 约 0.048 美元 |
| 80,000 | 1,000 | 0.320 + 0.020 = 0.340 美元 | 约 0.166 美元 |

第三行说明上下文膨胀的代价：单步输入到 8 万 token 时，一步就要三毛多。如果任务有 15 步且没有压缩，总成本会明显超过用便宜模型多跑几轮。

这些数字是按官方单价的**算术推算**，不是实测，实际以账号用量为准。

## 三、缓存对长任务尤其重要

缓存读取价格是普通输入的 5%（0.20 对 4.00）。长任务里，系统说明、工具定义和规则几乎每步都要带，这部分如果命中缓存，成本差距很大。

让缓存生效的要点：

1. 稳定内容（系统说明、工具 schema、规则）放前缀。
2. 前缀在任何一步都不能变。
3. 动态内容（观察结果、工具返回）放末尾。
4. 用用量字段确认命中，而不是推断。

需要提醒：缓存写入按普通输入计费且更高，只有在**同一前缀被多步复用**时才划算。长任务天然满足这一点，所以缓存设计是长任务成本优化的第一优先级。

## 四、子代理分流是核心手段

Muse Wonder 1.0 支持把工作委派给子代理。从成本角度看，这是把“贵的模型”用在关键决策上、把“便宜模型”用在执行细节上的机会。

一种常见的分流：

```text
主代理（Muse Wonder）  → 规划、关键判断、最终验收
子代理（小模型）        → 检索、抽取、格式化、简单工具调用
```

这样，贵的模型只处理“需要判断”的步骤，执行类步骤交给便宜模型。判断标准是：**这一步是否需要权衡取舍**。需要权衡的留给主代理，机械执行的交给子代理。

需要提醒：子代理不是免费的。委派本身要写清任务描述（计入主代理成本），子代理的调用也要计费。只有当“委派开销 + 子代理成本”低于“主代理自己做”的成本时，分流才划算。

## 五、控制上下文膨胀

长任务成本超线性增长，主要来自上下文累积。三种控制手段：

- **摘要压缩**：把完成的步骤压成一段简短记录替换原始历史。
- **状态外置**：把中间产物写入文件或数据库，需要时读取，而不是一直带在对话里。
- **滑动窗口**：只保留最近若干步的细节，更早的只留结论。

判断时机可以用两个信号：单步输入是否持续增长、响应是否变慢。一旦出现，就应该插入压缩。

## 六、单位交付成本

长任务真正的指标是“完成一个合格任务花多少钱”：

```text
单位交付成本 =
  主代理成本
+ 子代理成本
+ 重试成本
+ 人工接管成本
```

如果任务经常需要人工接管，说明它可能不适合全自动；如果经常重试，说明工具契约或验收标准有问题。这两个信号比单看账单更有诊断价值。

## 七、和更便宜模型的分工条件

前沿模型贵，小模型便宜。分工条件是：

- **任务复杂、步数多、判断密集** → 主代理用前沿模型。
- **任务简单、量大、可兜底** → 交给小模型。
- **同一任务内部** → 规划用前沿模型，执行用小模型。

不要因为前沿模型强就把所有步骤都交给它，也不要因为小模型便宜就把规划也下沉——规划错了，后面所有步骤都要重来，反而更贵。

## 验证与限制

验证成本模型时：

1. 记录每一步的输入、输出与耗时。
2. 统计步数分布，找出长尾任务。
3. 统计缓存命中率。
4. 对比分流前后单位交付成本。

需要明确的限制：

- 本文价格来自 2026 年 10 月 13 日公开信息，属于可变事实。
- 成本数字是**假设算例**，不是实测。
- 子代理分流效果高度依赖任务结构，需实测确认。
- 长任务成功率会随步数下降，成本与成功率要一起看。

## 八、缓存结构的实操模板

把每一步的请求组织成固定结构，可以让缓存稳定命中：

```text
[稳定] 系统说明：代理的角色与总目标
[稳定] 工具定义：所有可用工具的 schema
[稳定] 业务规则：不可违反的约束
[稳定] 验收标准：完成的判定条件
[动态] 当前状态摘要
[动态] 最近若干步的观察结果
[动态] 本次需要模型决定的问题
```

前四段在任务的所有步骤里保持不变，是缓存的价值所在。后三段的顺序也要固定，避免因拼装顺序抖动而破坏前缀。每次请求前，把前三段的内容做一次哈希校验，一旦发现变化就要意识到这批请求可能无法命中缓存。

## 九、批量长任务时的取舍

当长任务从单个变成批量，成本会以“任务数 × 平均步数”放大。三个取舍：

1. **并发 vs 限流**：并发过高会触发限流与重试，重试又是成本。宁可用队列平滑，也不要猛冲。
2. **完整 vs 尽早停**：给任务设置“够用即停”的判定，避免为追求完美多跑若干步。
3. **全自动 vs 关键点人工**：在高成本步骤前插入人工确认，可以避免整批任务在同一处反复烧钱。

判断批量方案是否划算，看的是**单位交付成本**而不是单任务成本。一个单任务便宜但经常需要人工接管的方案，批量后往往更贵。

## 十、把成本信号接进运营

成本不是算一次就完的，要持续观测。建议周度关注：

- 平均步数与步数 P95。
- 缓存命中率。
- 子代理占比。
- 人工接管比例。
- 单位交付成本。

当缓存命中率下降或平均步数上升时，通常意味着任务结构或提示词发生了变化，需要及时回到工程侧排查。
## 把子代理协议写清楚

成本分流的另一半是**协议**。主代理把工作委派出去，返回格式不统一，主代理就要反复试错，这本身也是成本。子代理的任务描述至少包含：

```text
task_id
goal           # 一句话目标
constraints    # 不可违反的约束
inputs         # 允许读取的资源
output_schema  # 期望的返回结构
timeout        # 超时上限
retry_policy   # 失败是否可重试
```

返回同样要结构化，成功与失败都要能被主代理判断：

```json
{"ok": true,  "result": "...", "confidence": 0.82}
{"ok": false, "error_code": "TIMEOUT", "retryable": true}
```

协议写清楚之后，“委派是否划算”才有稳定的度量基础。

## 什么情况下别做子代理分流

分流不是越多越好。下列情况通常不必拆：

1. **任务很短**：拆出去写任务描述的开销大于收益。
2. **需要全局一致性**：子代理各自为战容易产生前后矛盾。
3. **子任务高度依赖前序细节**：把上下文完整传过去，成本接近不拆。
4. **子代理失败概率高**：失败重试的成本会吃掉分流省下的钱。

判断标准：**拆分省下的输入成本，是否大于委派开销加上子代理失败的重试成本。**

## 成本与质量的联合看板

长任务代理只看成本会走偏。建议把成本和成功率放在同一张看板上：

| 指标 | 说明 | 恶化信号 |
| --- | --- | --- |
| 平均步数 | 完成任务需要的步数 | 步数上升 |
| 成功率 | 一次跑完的比例 | 下降 |
| 升级比例 | 转人工的比例 | 上升 |
| 缓存命中率 | 前缀复用情况 | 下降 |
| 单位交付成本 | 每个合格任务的花费 | 上升 |

四个指标里任何一个持续恶化，都说明任务结构或提示词需要调整，而不是简单换模型。
## 限制与结论

Muse Wonder 1.0 的成本由单价、步数和上下文增长共同决定。要做预算，必须按步核算而不是按请求核算；要控成本，优先做三件事：把稳定前缀整理好吃满缓存、把执行类步骤下沉到子代理、用摘要或状态外置控制上下文膨胀。
