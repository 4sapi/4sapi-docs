# Agent 时代如何留在循环里：从探索到验收

Agent 把视频素材整理了，转录做了，片段挑了，代码也生成了。最后成片能够播放，任务看起来完成了，颜色却不对。面对这个结果，很多人会继续补一句更长的 Prompt：“请把画面调得更专业、更有电影感。”问题是，使用者自己可能都说不清哪里不对，更说不清什么样的颜色才算对。

用户提供的演讲整理把这个场景讲得很具体：讲者用 Agent 处理视频、转录、脚本和界面，第一版结果暴露出色彩分级知识的缺口。接下来他没有只让 Agent 重试，而是先让 Agent 解释陌生概念、生成可视化，再把它连接到自己熟悉的 shader。人的理解变清楚以后，提示、方案和验收才有了共同基础。

这篇文章不讨论如何自动生成视频，而是讨论一个更普遍的问题：当 Agent 能连续执行复杂任务时，人应该怎样留在循环里，提供有效的判断，而不是只在最后被动验收一个看似完整的产物？

## 1. 人留在循环，不等于每一步都手工审批

有人听到 human-in-the-loop，第一反应是每个工具调用都弹窗确认。这样当然能增加控制，但也会把 Agent 变成一个需要人逐步遥控的自动补全工具。

更有价值的做法是把人的介入放在最能改变结果的节点：

```text
目标阶段：确认问题和受众。
探索阶段：补齐陌生概念和未知约束。
方案阶段：确认路线、范围和风险。
执行阶段：让 Agent 连续推进并记录状态。
验收阶段：用样例、测试和人工判断确认质量。
```

人不必看住每一次读取文件，但应该能在 Agent 走远之前发现目标理解错了。人不必手写每一行代码，但应该能定义哪些输出不能接受。

## 2. 第一种方式：探索

当任务涉及陌生领域时，先让 Agent 成为解释器和研究助手，不要直接让它交付最终产物。

比如你第一次接触色彩分级，不要只写：

```text
把视频颜色调好。
```

可以拆成：

```text
我对色彩分级不熟。
请先解释曝光、白平衡、对比度、饱和度和色调映射之间的关系。
用一个简单的像素值例子说明每一步会改变什么。
列出判断一段画面颜色是否合理时要观察的现象。
最后告诉我，哪些选择属于审美偏好，哪些属于技术错误。
不要修改项目，先输出学习笔记。
```

这一步的产物不是最终视频，而是一个人的心智模型。它至少应该让人能回答：

```text
我在看什么？
哪里可能出错？
什么是可测的？
什么需要审美判断？
下一轮应该给 Agent 哪种反馈？
```

演讲中的视频案例是一个具体展示，不足以证明 Agent 能独立完成专业后期制作。它更适合用来说明：在陌生领域，人的第一项工作可能不是下指令，而是建立判断语言。

## 3. 第二种方式：规格访谈

很多失败并非实现差，而是需求一开始就没有被问清楚。规格访谈的作用，是让 Agent 先通过问题补齐目标、受众、范围和限制。

可以让 Agent 先只问问题：

```text
你现在是需求访谈员。
请先不要写代码或生成最终文档，只问完成这个任务所必须知道的问题。
问题按目标、受众、输入、限制、验收和发布方式分组。
每轮最多问 5 个问题。
遇到不影响第一版的细节，先标记为可延期决定。
```

一个合格的规格访谈通常要覆盖：

| 维度 | 要问什么 | 可能的产物 |
| --- | --- | --- |
| 目标 | 最终要改变什么 | 一句话目标 |
| 受众 | 谁会使用或审阅 | 读者画像 |
| 输入 | 哪些资料可信 | 输入清单 |
| 范围 | 什么明确不做 | 排除项 |
| 限制 | 技术、时间、权限和格式 | 约束表 |
| 验收 | 什么证据证明完成 | 验收清单 |
| 发布 | 谁批准，产物放哪里 | 交付流程 |

规格访谈不是让 Agent 无限提问。每个问题都应能改变任务方案或验收条件；没有这种影响的问题，可以暂时放到“待确认”列表。

## 4. 第三种方式：技术计划

规格确定后，继续让 Agent 直接执行仍然可能太早。技术计划把目标翻译成步骤、依赖、风险和验证点。

一个小型技术计划可以包含：

```markdown
## 目标
生成一个可在浏览器播放的短视频预览。

## 已确认
- 原始素材在 source/。
- 需要保留现有旁白。
- 预览需要包含标题和时间轴标记。

## 未确认
- 色彩风格偏自然还是高对比。
- 移动端是否需要单独裁切。

## 计划
1. 检查素材格式和时长。
2. 生成转录并人工抽查。
3. 根据选定片段生成第一版剪辑。
4. 生成叠加 UI 并在浏览器中验证。
5. 依据样例检查颜色、字幕和节奏。

## 风险
- 颜色标准尚未定义。
- 字幕时间轴可能需要人工微调。

## 停止条件
如果素材无法解码或颜色验收标准无法确定，暂停并请求决定。
```

技术计划的作用不是把路线锁死。它应该是一个可更新的假设：执行中发现更好的路径，可以修改计划，但要说明为什么修改、影响了什么、如何重新验收。

## 5. 第四种方式：实现笔记

Agent 长时间工作时，聊天上下文不能承担全部状态。实现笔记让人和下一轮 Agent 都能理解当前进度。

实现笔记不需要写成流水账，只记录会影响下一步的内容：

```markdown
## 已完成
- 转录已生成，抽查了开头、中段和结尾。
- 片段选择写入 edit-plan.json。
- 第一版预览可以播放。

## 当前问题
- 画面暗部偏灰，具体原因未确认。
- 字幕在第二个片段提前出现。

## 已尝试
- 增加整体饱和度：肤色变得不自然，已回退。
- 只调整亮度：暗部仍然缺少层次。

## 需要补的知识
- 色彩空间和 tone mapping 的区别。

## 下一步
- 先生成色彩解释和像素可视化，不直接继续调参。

## 人工决定
- 选择自然还原还是风格化高对比。
```

这类笔记保存的是状态、证据和未决问题，不是“永久记忆”。它应该有来源、有时间和有效范围，过期后可以删除或更新。

Anthropic 的 [Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents) 讨论了长时任务需要怎样的 Harness 和阶段化协作。具体工具实现会不同，但“让任务能够从检查点继续，而不是只依赖一次长对话”的原则适用于许多 Agent 工作流。

## 6. 第五种方式：解释器

解释器的作用，是把 Agent 做出的中间结果转成使用者能判断的形式。

一个代码 Agent 修改了 shader，普通使用者可能看不懂几十行参数变化。解释器可以生成：

```text
修改了哪些输入？
每个参数如何影响画面？
哪一处改变了暗部？
哪一处改变了色调？
这个修改可能带来什么副作用？
如何用一个最小样例观察变化？
```

一个文档 Agent 生成了周报，解释器可以把每个结论链接回原始会议纪要和数据字段。一个代码 Agent 修复了 Bug，解释器可以说明复现路径、修改文件、测试结果和未覆盖边界。

解释器不是把内部思考过程完整暴露出来，而是提供对任务有用的外部证据：输入、动作、变化、验证和限制。人需要的是能判断结果的解释，不是更多无法核对的长篇推理。

## 7. 五种方式如何串成一条流程

把它们按一个真实任务串起来，可以是：

```text
探索：先学会描述问题。
  ↓
规格访谈：明确目标、受众、输入和验收。
  ↓
技术计划：把目标拆成可执行阶段。
  ↓
实现笔记：保存中间状态、失败尝试和未决问题。
  ↓
解释器：把中间产物和验证证据交给人判断。
  ↓
下一轮：根据人的反馈更新计划或停止任务。
```

不是每个任务都需要完整走五步。

如果是修复一个有清晰测试的 Bug，可以跳过长时间探索；如果是第一次接触视频后期，探索和解释器就很有价值；如果是高风险生产变更，规格、计划、实现记录和人工验收都不应省略。

## 8. 按阶段安排人的介入

可以用下面这张表判断人应该在哪里出现：

| 阶段 | Agent 适合做什么 | 人需要确认什么 |
| --- | --- | --- |
| 目标 | 询问问题、整理需求 | 目标、受众和排除项 |
| 方案 | 比较路线、列风险 | 技术取舍和不可接受风险 |
| 执行 | 读资料、改文件、运行工具 | 只在越权或高风险动作前介入 |
| 反馈 | 汇总测试、截图、差异 | 结果是否朝正确方向变化 |
| 验收 | 生成报告和证据包 | 是否符合质量标准并可以交付 |

这种安排同时考虑了效率和控制。人不需要审批每一次低风险读取，但要在计划错误、权限扩大、数据敏感或验收标准不清时及时接管。

## 9. 工具也会随模型变化而过时

用户提供的演讲整理中，讲者回顾了一个提问工具的变化：早期模型只能稳定地调用一次，后来可以连续追问，再后来简单选择框可能不足以承载更丰富的访谈和报告交互。这个例子说明，工具不是一次设计永久不变的组件。

工具变化时，要重新问：

```text
这个工具解决的是当前模型的真实限制吗？
它让人更容易理解和选择，还是只增加了一层界面？
它能否保存中途状态？
它是否允许任务方向改变？
模型能力提升后，它会不会变成固定路线的约束？
```

这里的工具演进是视频材料中的工程观察，不代表所有 Agent 产品都会经历相同路线。Anthropic 的 [Equipping agents for the real world with Agent Skills](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills) 也提醒我们，能力组织和工具发现需要考虑模型怎样在任务中逐步取得信息；具体做法应通过当前任务的日志和验收来复查。

## 10. 一份可复制的人机协作模板

开始一个复杂任务时，可以让人和 Agent 共同维护下面的文件：

```markdown
# Collaboration Brief

## Goal
这次任务要改变什么？

## Audience
谁使用、谁审阅、谁最终批准？

## Unknowns
哪些概念、资料和约束还不清楚？

## Acceptance examples
给出至少一个可接受结果和一个不可接受结果。

## Plan
当前阶段、下一步、依赖和风险。

## Evidence
文件路径、测试、截图、数据来源或运行日志。

## Feedback
人对当前结果的具体判断，以及判断依据。

## Decision
继续、修改计划、请求补充信息或停止。
```

关键在于 `Feedback` 必须具体。下面两种反馈的价值不同：

```text
不对，再改改。
```

```text
第二段暗部细节丢失，但第一段曝光可以接受。先不要提高整体饱和度，请解释当前色彩空间、找出只影响暗部的参数，并生成一个 A/B 预览。
```

第二种反馈包含位置、现象、排除项、下一步和验证形式，Agent 才能把人的判断转成行动。

## 11. 评估不应只看最终产物

Agent 可以生成一个看起来完整的结果，但完整不等于正确。评估时至少应保留：

```text
目标是否被正确理解。
中途是否发现了关键未知。
工具是否提供了必要证据。
失败是否被记录并避免重复。
人是否在正确节点介入。
最终结果是否满足验收条件。
```

Anthropic 的 [Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) 讨论了 Agent 评估需要结合任务、环境和可观察结果。对个人项目来说，不必立刻建复杂评估平台，但至少要保存任务输入、执行轨迹、产物、验证输出和人工反馈，才能知道下一次改进了什么。

## 12. 结论与限制

Agent 降低的是执行成本，不是判断成本。人在循环中的新职责，不是替 Agent 逐步点击按钮，而是在目标、未知、方案、反馈和验收这些节点提供高价值判断。

探索帮助人理解陌生概念，规格访谈帮助双方对齐目标，技术计划把目标变成路线，实现笔记保存状态，解释器把中间结果变成可判断的证据。五种方式可以按任务风险和熟悉程度取舍，不是固定流程。

本文中的视频生产、色彩分级和工具演进都来自用户提供的演讲整理，不能单独证明某个 Agent 的专业能力或任何产品的普遍路线。真正落地时，要用自己的任务记录验证：哪一个反馈点最能减少返工，哪一种解释能帮助人做出决定，以及什么情况必须停止自动执行。
