# AI Agent 的灰度发布：先放哪些任务，什么时候必须人工确认

Agent 通过测试后，团队常常只剩两个选项：“直接全自动”或“继续做演示”。其实还可以走第三条路：先限定用户、资料和动作，保留人工接管，再根据运行结果逐步扩大范围。

灰度发布把风险先放在小范围里，让团队看得到，也停得下来。它尤其适合具有检索、工具调用或业务写入能力的 Agent。本文不提供通用的上线人数或通过率阈值，因为任务影响、样本量和组织承受能力不同；重点是建立一套能决定扩大、保持、回退或暂停的过程。

## 一、先按任务风险排序，不按“模型有多聪明”排序

同一个 Agent 能做很多事，也不该第一天就拿到全部动作权限。可以先从四个维度判断任务风险：

| 维度 | 低风险信号 | 高风险信号 |
| --- | --- | --- |
| 数据 | 已发布、无个人信息的资料 | 客户、员工、合同或受限数据 |
| 动作 | 只读、生成本地草稿 | 外部发送、写入、删除、扣费 |
| 可逆性 | 可撤销、无下游影响 | 不可逆或影响多个对象 |
| 可验证性 | 有固定字段和人工抽检 | 结果难以在短期判断、依赖专业决定 |

第一批灰度优先选“可逆、可验证、数据范围小”的任务。比如，用已批准资料生成内部回复草稿，就比直接替公司给客户发通知更合适。灰度也不能替代风险审查；法律或安全边界没搞清楚时，先停在人工工具或模拟环境。

## 二、把自动化程度拆成四种发布模式

| 模式 | Agent 可以做什么 | 人负责什么 | 适用阶段 |
| --- | --- | --- |
| 观察模式 | 只记录建议，不写入业务系统 | 对比建议与真实处理 | 刚完成原型或规则不稳定 |
| 草稿模式 | 生成可审阅结果，不能提交 | 修改、批准或丢弃草稿 | 第一批真实用户 |
| 确认模式 | 准备具体动作，等待人确认 | 核对对象、范围和副作用 | 可逆写入或有限外部动作 |
| 受限自动模式 | 在白名单范围自动执行 | 审查异常、抽检与扩权决定 | 已有稳定证据的低风险任务 |

“受限自动”也不是无人值守。任务类型、身份、资料范围、工具参数、数量和停止条件都要先锁住。新增任务、资料范围或副作用时，应重新回到草稿或确认模式，不能直接借用旧授权。

## 三、为每次发布写出灰度矩阵

发布范围不能只写“先给一小部分用户”。要明确谁、什么输入、哪些动作和什么退出规则：

| 项目 | 示例写法 |
| --- | --- |
| 任务 | 把指定类别工单整理为内部回复草稿 |
| 用户 | 已培训的支持团队成员 |
| 资料范围 | 已发布的产品文档，不含客户资料 |
| 执行身份 | 只读检索 + 草稿写入服务账号 |
| 允许工具 | 内部检索、草稿创建 |
| 禁止动作 | 外部发送、改工单状态、删除内容 |
| 人工节点 | 每份草稿发布前人工确认 |
| 观测 | 结构错误、人工重大修改、转人工、超时、调用异常 |
| 停止条件 | 未授权访问、错误写入、无法追溯或连续异常 |
| 回退 | 关闭草稿写入，退回人工模板 |

每个字段都要由能承担责任的人确认。业务 Owner 决定任务是否有价值，资源 Owner 决定资料范围，技术 Owner 决定工具、身份、观测和回退。没有 Owner 的灰度，最后会变成发生问题时无人有权暂停。

## 四、人工确认要确认什么

人工确认不能只剩一个“继续”按钮。确认人至少要看到：

```text
任务目标与发起人。
Agent 使用了哪些来源或输入。
将要执行的动作、对象、数量和范围。
是否会产生发送、写入、删除或费用等副作用。
为什么符合当前规则，哪些内容仍不确定。
撤销方式或无法撤销的提示。
```

人工确认也不能成为无差别的点击劳动。如果团队发现确认人每次都在补同一类事实、修同一种格式或拒绝同一种工具调用，应把这一模式进入第 440 期的复盘队列，修复任务卡、资料边界、工具契约或 Agent 策略。

## 五、扩大范围前看趋势与失败类型

扩大灰度不能靠“大家感觉不错”，也不能只看一条总成功率。回看第 439 期的观测记录，至少检查：

| 观察项 | 需要回答的问题 |
| --- | --- |
| 任务结果 | 是否在限定任务中稳定完成，哪些终态增加 |
| 人工接管 | 人是在做预期确认，还是持续救援与大幅重写 |
| 失败分类 | 问题来自资料、工具、权限、实现还是任务定义 |
| 安全边界 | 是否有越权、异常范围、注入或不可追溯行为 |
| 资源表现 | 重试、长尾延迟或资源用量是否异常 |
| 用户采用 | 用户是否真的把结果纳入原工作流，还是绕开系统 |

要看多个任务周期，不能只挑表现最好的一天。样本少时，结论也要保守：最多只能说“在已观察范围内未发现某类问题”，不能据此宣布系统对所有任务都可靠。

## 六、什么时候必须回退或暂停

预先定义停止条件，才能避免事故发生后在业务压力下继续放大范围。以下任一情况通常应立即触发调查，必要时回退：

```text
发生未授权数据访问、外部写入或无法解释的权限扩大。
无法关联任务、版本、身份、工具和实际结果。
同一任务出现重复副作用，且下游无法可靠撤销。
关键资料错误、过期或无来源结论进入了业务决策。
人工接管无法处理，或用户无法得知 Agent 做了什么。
发布、工具、模型或权限变更后出现阻断性退化。
```

回退不等于删掉整个系统。可以先关掉高风险工具，退回草稿模式，缩小资料范围，或者只保留观察模式。前提是回退动作能执行、能验证，且不会丢掉复盘证据。

## 七、把灰度设计成一组小实验

一个阶段只验证一个主要变化。以下是一个示例节奏：

```text
阶段 A：观察模式。对比 Agent 建议与人工原流程，不改变任何结果。
阶段 B：草稿模式。限定用户和资料，人工每次审核。
阶段 C：确认模式。允许创建可逆草稿或待审批动作，确认内容绑定具体对象。
阶段 D：受限自动。仅对白名单任务和参数自动执行，继续抽检与监控。
```

不要同时扩大用户、资料、工具、模型和写入权限，否则出现变化时无法判断原因。每一阶段结束时保存版本、范围、指标、异常样例、用户反馈和下阶段决定。即使决定“不扩大”，这也是有效结果，能够防止不成熟的自动化被业务压力推向生产。

## 八、处理用户绕过和影子流程

灰度期间，用户可能嫌 Agent 慢、确认多，转而把结果复制到别的工具，或者继续用旧表格。这不一定是培训问题，也可能说明工作流没有解决原来的瓶颈。

应区分：用户是因为输出错误、等待太久、看不懂依据、权限卡住，还是 Agent 增加了新步骤。通过访谈与运行数据确认后，再决定优化界面、补资料、缩小任务或维持人工流程。不要为了提高“使用率”而取消必要的确认与边界。

## 九、灰度发布操作卡

```markdown
# 灰度发布：版本与范围

## 目标
- 要验证的工作变化：
- 不验证什么：

## 范围
- 用户与任务：
- 数据和执行身份：
- 工具与允许动作：
- 明确禁止：

## 控制
- 人工确认：
- 观测与日志：
- 抽检方式：
- 停止条件：
- 回退步骤：

## 决定
- 业务 Owner：
- 技术 Owner：
- 资源 Owner：
- 阶段结束复核：
```

操作卡应在发布前审阅，发布后随版本变化更新。发布不是点一次开关；版本变化后，范围和风险控制还要重新确认。

## 十、检查清单

```text
[ ] 第一批任务按数据、动作、可逆性和可验证性评估过风险。
[ ] 已选择观察、草稿、确认或受限自动中的明确模式。
[ ] 灰度矩阵写清用户、资料、身份、工具、禁止事项与回退。
[ ] 人工确认展示具体对象、范围、依据与副作用。
[ ] 指标区分自动完成、人工确认、救援、失败和阻止。
[ ] 扩大范围前审查趋势、失败分类、权限和资源异常。
[ ] 停止条件不是事后补写，并且有人有权执行回退。
[ ] 每阶段只验证有限变化，版本与范围可追溯。
[ ] 用户绕过路径会被调查，不用取消控制点来掩盖。
[ ] 高风险或不确定任务保持人工节点，不借用低风险任务的授权。
```

## 结论与资料

灰度发布把“是否全自动”拆成一连串问题：哪些任务、哪些资料、哪些身份和哪些动作下，Agent 能提供可验证价值；出了问题谁发现、谁停止、怎么恢复。边界内积累到足够证据后，再扩大范围，才是工程决定。

- [NIST AI Risk Management Framework](https://www.nist.gov/itl/ai-risk-management-framework)：参考以治理、映射、测量与管理贯穿 AI 系统生命周期的思路。
- [Google SRE Book：Canarying Releases](https://sre.google/sre-book/canarying-releases/)：参考通过有限范围验证发布变化、保留回退能力的工程原则。
- [OWASP：Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)：参考最小权限与授权验证实践。
