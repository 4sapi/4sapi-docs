# 企业知识库怎么验收：两套测试集和一套可追溯结果

知识库演示时答对几个问题，不代表项目可以验收。演示题通常由交付团队准备，资料和答案提前熟悉，问题范围也相对可控；真实验收要看的是，客户没有提前透露题目时，系统能否持续处理约定场景，并把错误、拒答和权限边界表现出来。

这篇文章聚焦两套测试集的设计，以及如何把自然语言回答转成双方都能复核的验收结果。

## 一、先定义“通过”而不是先写题目

测试集不是问题大合集。

每道题都要绑定：

```text
业务需求。
输入资料。
预期答案或评分规则。
允许引用的来源。
不可接受的错误。
```

如果没有这些字段，测试人员最后只能说“看起来不错”。

## 二、为什么要准备两套测试集

建议拆成：

| 测试集 | 由谁设计 | 什么时候使用 |
| --- | --- | --- |
| 交付测试集 | 交付团队与客户共同确认 | 开发、回归、预验收 |
| 独立验收集 | 客户准备并保留 | 最终验收 |

交付测试集用于发现问题和定位回归。

独立验收集用于检验交付方没有只针对已知题目优化。

两套题目不能完全相同，否则验收会失去独立性。

## 三、第一套测试集从需求点开始

不要从“收集大家觉得有趣的问题”开始。

先把项目需求拆成可测试的能力：

```text
回答产品参数。
解释安装步骤。
识别不适用条件。
引用资料来源。
拒答无依据问题。
隔离不同部门内容。
```

每个需求点至少准备一个正向用例和一个反向用例。

例如“回答安装步骤”对应的反向用例可以是缺少型号、型号冲突或资料已经过期。

## 四、正向用例怎么写

正向问题需要存在明确依据。

示例字段如下：

| 字段 | 示例 |
| --- | --- |
| case_id | POS-001 |
| 场景 | 产品认证查询 |
| 问题 | 产品 A 通过了哪些认证？ |
| 标准答案 | 以批准版本资料为准 |
| 来源 | DOC-014 第 3 页 |
| 判定 | 要点齐全且无额外认证 |

正向题不宜写成“请介绍产品 A 的所有信息”。

范围过大，评分就会变成主观印象。

## 五、反向用例更能暴露边界

反向题可以覆盖：

```text
资料中不存在的参数。
两个版本互相冲突的参数。
用户无权访问的内容。
缺少关键条件的操作问题。
要求模型猜测未来结果的问题。
```

合格回答不一定是“拒绝”。

它可以说明缺少什么、引用什么、需要谁确认，但不能编造一个确定答案。

## 六、把问题按答案类型分组

自然语言输出也可以分类验收：

| 类型 | 例子 | 判定方式 |
| --- | --- | --- |
| 事实题 | 参数、认证、日期 | 与标准答案比对 |
| 条件题 | 在什么情况下可安装 | 检查条件是否完整 |
| 引用题 | 来源在哪份资料 | 检查文档和页码 |
| 拒答题 | 资料没有该信息 | 检查是否明确说明未知 |
| 权限题 | 不能访问的部门资料 | 检查是否泄露 |

事实题适合自动或半自动判断。

条件题和开放题需要业务人员参与。

## 七、标准答案比例不是行业常数

在一次实际交付中，可以让大部分题目拥有确定答案，剩余题目由人评估。

例如把约 85% 的题目设计成有标准答案的事实题，其他题目用于判断解释、边界和拒答质量。

这个比例只是项目方法，不是所有知识库都必须遵守的标准。

它传达的原则是：尽量把验收建立在可判断的问题上，不要全部依赖“读起来顺不顺”。

## 八、评分表要区分错误类型

建议不要只填一个“通过/不通过”。

至少记录：

```text
事实错误。
遗漏关键条件。
引用错误。
无依据扩写。
权限越界。
拒答不充分。
格式问题。
```

错误类型不同，修复路径也不同。

事实错误可能来自资料、解析或检索。

权限越界则应优先暂停相关功能并检查数据过滤。

## 九、交付方测试集的确认流程

推荐流程如下：

```text
交付方根据需求起草题目。
业务人员检查题目是否符合真实工作。
双方确认标准答案和评分规则。
交付方建立基线结果。
开发和修复后重复运行。
把每次结果写入版本记录。
```

客户确认测试范围很重要。

如果客户从未确认题目，验收时可能出现“系统没测到真正关心的问题”。

## 十、独立验收集要保留但不提前公开

客户可以从真实工作中抽取一批问题，交给指定验收人员保管。

交付团队提前知道的内容可以包括：

```text
题目数量范围。
覆盖哪些业务域。
评分规则和通过阈值。
是否允许人工复核。
```

不必提前公开每一道题的具体问法和答案。

这样既能让交付团队准备环境，也能保留验收的独立性。

## 十一、验收不应只看平均分

平均通过率可能掩盖高风险错误。

例如 90 道普通题回答正确，但 1 道权限题泄露研发资料，项目仍然不能简单判为通过。

建议设置硬性门槛：

```text
权限越界次数必须为 0。
无依据编造关键参数次数必须为 0。
核心产品问题通过率达到约定阈值。
所有失败题目都有原因和处理结论。
```

阈值要在项目开始前写清，不要到验收当天临时决定。

## 十二、失败结果要保留原始证据

每次运行至少保存：

| 证据 | 用途 |
| --- | --- |
| 原始问题 | 证明输入没有被改写 |
| 完整回答 | 复核模型实际输出 |
| 检索片段 | 判断资料是否召回 |
| 引用来源 | 检查出处和版本 |
| 用户身份 | 复核权限上下文 |
| 时间和版本 | 对应系统配置 |

不要只把最终得分抄进表格。

缺少原始回答，后续无法判断问题来自资料、检索还是生成。

## 十三、如何定位一条错误答案

可以沿着以下链路回放：

```text
用户问题 → 身份和权限 → 检索结果 → 解析文本 → 原始资料 → 生成回答
```

每一步都要问：

```text
输入是否正确？
这一步是否丢失信息？
是否引用了过期版本？
是否出现了越权内容？
```

如果扫描文本和原始图片一致，但答案仍然错误，继续向资料源追查。

企业真实案例中，最终错误可能来自一份历史上就印错的纸质文档。

## 十四、开放答案怎样人工评分

开放问题可以采用四档规则：

| 分数 | 含义 |
| --- | --- |
| 0 | 无法回答、严重错误或越权 |
| 1 | 有部分相关内容，但缺少关键条件 |
| 2 | 基本可用，需要少量人工补充 |
| 3 | 完整、准确、边界清楚并有来源 |

评分人要看到同一份规则和示例。

如果多人评分，建议抽取部分题目做交叉复核，记录分歧原因。

## 十五、验收过程中的需求变化

项目中途经常会出现新问题：

```text
增加一个部门。
接入一个没有接口的系统。
纳入一批未整理的纸质资料。
把内部知识库改成对外客服。
```

这些变化会改变测试范围和风险。

不能继续使用原来的通过率解释新范围。

应记录变更内容、影响的题目、增加的工作量和新的验收安排。

## 十六、验收报告应该写什么

一份简洁的验收报告可以包含：

```text
测试版本和日期。
测试集版本与题目数量。
各类题目的通过情况。
硬性失败项。
人工评分结果。
未解决问题。
权限和数据范围。
客户确认意见。
```

报告要区分“未测试”和“测试失败”。

没有运行过的题目不能默认为通过。

## 十七、常见失败方式

### 失败一：只测演示题

模型可能只是记住了固定资料和问法，无法说明泛化到真实问题的能力。

### 失败二：只看平均准确率

平均分掩盖不了权限越界和关键参数编造。

### 失败三：客户只在最后一天给反馈

如果测试范围没有提前确认，双方对“完成”可能有不同理解。

### 失败四：没有保存检索结果

后续只能争论答案好不好看，无法定位技术链路。

## 十八、结论

知识库验收的核心，是把“感觉可用”转成可复核的测试协议。

交付方测试集负责开发和回归，客户独立验收集负责检验真实场景；两者都要有题目、来源、评分和失败记录。

标准答案题越多，结果越容易讨论；开放题也可以保留，但必须由明确规则和人工复核支撑。

最终报告不只写通过率，还要写版本、权限、未测试项和硬性失败项。

当每条结论都能回到原始问题、检索片段和资料版本，企业知识库才真正具备交付和持续改进的基础。
