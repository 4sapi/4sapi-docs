# AI Coding 生成的代码怎么看：新手从报错到定位问题

AI 生成的代码第一次运行就成功，当然最好。

但更常见的情况是：页面能打开，按钮没有反应；请求发出去了，列表却没有更新；终端显示成功，浏览器仍然报错。

这时，真正重要的不是继续让 AI“再写一遍”，而是学会判断问题属于哪一类，并把可验证的信息交给它。

## 一、先区分三类问题

### 1. 语法错误

代码格式不正确，程序无法被正确读取。

常见例子是少了括号、引号没有闭合、关键字写错。

### 2. 运行错误

代码可以被读取，但执行到某一步失败。

例如请求接口时返回错误，变量为空，文件路径不存在。

### 3. 产品错误

程序运行了，但结果不符合真实需求。

例如用户 A 通过修改地址看到了用户 B 的记录，页面显示成功但数据没有保存。

AI 通常比较容易处理前两类问题。

第三类需要你判断“这个结果是否真的符合需求”。

## 二、先复现，再提问

不要只告诉 AI“这里有 Bug”。

先写清楚：

- 做了什么；
- 页面出现了什么；
- 原本期待什么；
- 问题能否稳定复现。

如果问题不能稳定复现，也要记录出现的大致条件，例如浏览器尺寸、输入内容、操作顺序和网络状态。

## 三、保存完整错误信息

错误信息不要只截取最后一行。

终端和浏览器控制台通常会给出：

- 错误类型；
- 错误消息；
- 文件路径；
- 行号和列号；
- 调用堆栈；
- 请求地址和状态码。

这些信息能帮助定位问题。

如果只说“页面白屏”，AI 只能猜测。

## 四、浏览器控制台看什么

打开开发者工具后，先看 Console 和 Network。

Console 用来观察 JavaScript 错误、警告和日志。

Network 用来检查请求是否发出、返回什么状态码、响应内容是否符合预期。

例如按钮点击没有结果，可能是：

- 点击事件没有绑定；
- 事件函数抛出异常；
- 请求没有发出；
- 请求返回错误；
- 请求成功但页面状态没有更新。

这五种情况的修复方向不同。

## 五、先问 AI 原因，不要直接改代码

调试时可以这样提问：

~~~text
请先分析这个错误，不要修改代码。
请列出：
1. 最可能的原因；
2. 需要检查的文件；
3. 需要补充的证据；
4. 如何验证你的判断；
5. 如果判断成立，最小修改范围是什么。
~~~

先得到假设，再决定是否执行修改。

这样可以避免 AI 为了“马上修好”而大范围重构。

## 六、理解变量和函数的作用

你不需要一开始掌握所有语法，但至少要能回答：

- 这个变量保存什么；
- 这个函数接收什么参数；
- 函数返回什么结果；
- 条件判断什么时候成立；
- 哪一步改变了页面状态；
- 表单数据从哪里来、到哪里去。

可以让 AI 用简单语言解释一段代码：

~~~text
请逐段解释这段代码。
不要重写，也不要评价风格。
说明每个变量、函数、条件和外部请求的作用。
最后画出数据从输入到输出的路径。
~~~

## 七、从输入到输出画路径

以表单为例，完整路径可能是：

~~~text
用户输入
-> 前端校验
-> 组装请求
-> 发送 API
-> 服务端校验
-> 写入数据库
-> 返回结果
-> 更新页面状态
~~~

任何一段断开，用户都会觉得“按钮没用”。

如果你能指出数据在哪一步丢失，调试效率会明显提高。

## 八、不要把所有报错都归因于模型

常见问题可能来自：

- 依赖版本不兼容；
- 环境变量没有加载；
- 端口被占用；
- API 地址写错；
- 数据库没有启动；
- 浏览器缓存旧文件；
- 权限规则阻止请求。

模型只是实现链路中的一个环节。

## 九、修复要遵循最小范围

如果问题发生在一个表单校验函数，不要顺手重构整个表单系统。

可以明确要求：

~~~text
只修复这个复现问题。
不要修改数据库结构、路由和无关组件。
保留现有接口格式。
完成后列出修改文件和验证步骤。
~~~

修改范围越小，回归验证越容易。

## 十、修复后必须重新复现

修复成功不是“错误消失”这么简单。

至少检查：

1. 原来的复现步骤不再失败；
2. 正常输入仍然有效；
3. 空输入和异常输入有明确提示；
4. 其他页面没有被破坏；
5. 刷新或重新启动后行为一致。

如果修复的是请求错误，还要检查服务端日志和响应数据。

## 十一、产品错误要用场景验收

产品错误通常不会在控制台报红。

例如“用户 A 看到了用户 B 的数据”，程序可能完全正常运行。

这类问题需要准备不同用户、不同数据和不同权限的测试场景。

验收问题可以写成：

~~~text
用户 A 创建一条记录。
用户 B 登录后查看列表。
预期：用户 B 看不到用户 A 的记录。
实际：检查页面、接口响应和数据库查询结果。
~~~

## 十二、用测试保护已修复的问题

如果某个 Bug 已经稳定复现，可以让 AI 先生成测试，再运行测试。

测试至少应该覆盖：

- 原来失败的情况；
- 正常情况；
- 边界输入；
- 错误处理。

测试通过后，再进行其他修改。

## 十三、Git 是后悔药

每个可用阶段都保留提交。

修改前查看状态，修改后查看 diff，验证通过后再提交。

这样你可以知道：

- 哪次修改引入问题；
- 哪个版本仍然可用；
- 哪些改动可以单独撤回。

不要把所有修改堆在一个巨大提交里。

## 十四、调试记录模板

~~~text
问题标题：
首次发现时间：
运行环境：
复现步骤：
预期结果：
实际结果：
完整错误：
涉及文件：
可能原因：
已尝试方案：
验证结果：
是否需要回滚：
~~~

这份记录也可以作为下一次向 AI 提问的上下文。

## 十五、结论

AI Coding 新手不需要先学完所有编程知识，但必须学会从现象提取证据。

区分语法错误、运行错误和产品错误，查看控制台与网络请求，描述稳定复现步骤，限制修复范围，再用同样的步骤验证结果，这套方法比不断要求 AI“重写一遍”可靠得多。

AI 可以帮助你读代码和找原因，但最终要由你确认产品行为是否符合真实需求。
