# 用 WorkBuddy 整理办公资料：从原始文件到可交付报告

让 Agent 写一份报告并不难，难的是让这份报告可以交付。它需要读对资料，理解字段，区分事实和推断，适合目标读者，并且能让人追溯每个关键结论来自哪里。

本文只围绕一个办公问题展开：如何把会议纪要、项目进展记录和一份数据表整理成项目周报。WorkBuddy 的具体入口、文件能力和界面名称会随版本、账号和组织配置变化，因此文中使用“工作区”“文件处理入口”“计划或草稿确认”等通用称呼。重点是可迁移的资料处理和验收方法，不把未独立核验的界面能力写成固定承诺。

## 1. 先定义输入和交付物

假设任务如下：

```text
输入：3 份会议纪要、1 份项目进展表、1 份上周周报。
读者：项目负责人和需要协调资源的部门同事。
产出：一份本周项目周报初稿。
内容：本周完成、关键数据、风险问题、下周计划、需要决策的事项。
验收人：项目负责人，最终发布前由资料提供者核对事实。
```

这个定义比“帮我整理一下这些文件”更适合 Agent。它说明了资料范围、读者、产物和验收人，也提前限定了报告不应该包含什么。

如果输入资料中有客户隐私、合同、财务或内部人事信息，先确认组织规则和工具账号的处理边界。不能因为文件可以上传，就默认可以上传。

## 2. 准备一个不会污染原始资料的工作区

建议把每次办公任务放进独立目录：

```text
project-weekly-report/
  source/       原始会议纪要、进展表和旧报告
  working/      字段提取、事实核对和中间草稿
  output/       待审阅的报告
  review/       人工修改和待确认事项
```

不一定要使用完全相同的目录名，但要保留三个边界：

```text
source/ 不作为写入目标。
working/ 保存提取结果和问题清单。
output/ 只放可以交给人审阅的产物。
```

文件准备也要做一次清点：

```text
会议纪要：记录会议日期、参与人和讨论范围。
进展表：确认列名、单位、时间区间和空值含义。
上周周报：只作为格式和背景参考，不自动视为本周事实。
```

如果同一项目存在多个版本，文件名中加入日期或版本标记。不要让 Agent 自己猜哪个文件更新。

## 3. 先做资料清单，再做报告

第一次提交任务时，建议先要求 Agent 只读清点资料：

```text
请读取当前工作区 source/ 下的资料，但不要生成最终报告，也不要修改原始文件。

请输出：
1. 文件清单、文件类型和日期；
2. 每份资料可以支持哪些字段；
3. 表格的列名、数据类型、单位和缺失值情况；
4. 不同文件之间可能冲突的项目、人员、日期或数字；
5. 仍然无法确认的信息。

如果字段含义不明确，请先停止并列出问题。
```

这一步的目的，是防止 Agent 直接把一份格式漂亮但事实错误的周报写出来。

### 资料清点的验收点

```text
[ ] 是否读取了 source/ 中的全部预期文件？
[ ] 是否识别了同名文件和旧版本？
[ ] 是否理解了表格字段和单位？
[ ] 是否发现日期或数字冲突？
[ ] 是否把未知信息标出来？
[ ] 是否没有修改 source/？
```

只有资料清单没有明显问题，才进入下一步。

## 4. 使用结构化提示词

办公任务的提示词至少包含目标、输入、输出、规则和验收。可以直接使用下面的模板：

```text
目标：
把当前工作区 source/ 中的资料整理成一份项目周报初稿。

读者：
项目负责人和需要协调资源的部门同事。

输入范围：
只读取 source/ 下与本项目本周进展相关的会议纪要、进展表和上周周报。

输出：
请生成 Markdown 报告，包含：
1. 本周摘要；
2. 已完成事项；
3. 关键数据和口径；
4. 当前风险与阻塞；
5. 下周计划；
6. 需要负责人决策或协调的事项；
7. 待确认信息。

事实规则：
- 每个具体数字标注来源文件和字段或段落。
- 会议纪要中的计划不能直接写成已完成事项。
- 资料没有支持的内容写“待确认”，不要自行补全。
- 不同资料冲突时列出冲突，不要替我选择。

文件规则：
- 不修改、覆盖、删除 source/ 下的原始文件。
- 把中间提取结果放到 working/。
- 把报告初稿放到 output/project-weekly-report.md。

交付：
任务结束时说明读取了哪些文件、生成了哪些文件、哪些内容需要人工确认。
```

如果当前版本提供提示词优化或计划预览，可以先使用它检查目标、输入、输出和限制是否被保留；如果没有这些入口，就手动检查提示词的五个部分。

## 5. 先确认计划，再生成初稿

对真实办公材料，建议把流程分成两个阶段：计划和执行。

### 计划阶段应该看到什么

```text
准备读取哪些文件。
准备如何解释字段。
准备如何处理冲突和缺失。
准备输出哪些文件。
哪些地方需要人确认。
```

如果计划把上周周报当成本周事实，或者准备直接覆盖原始表格，应在执行前修正。计划不需要很长，但必须让你看出它是否理解了资料边界。

### 执行阶段的交付

执行完成后，不要只拿最终报告。至少要让 Agent 同时提供：

```text
报告初稿。
来源映射或引用说明。
待确认清单。
读取文件清单。
生成文件清单。
没有执行的动作。
```

这些信息可以写在 `working/` 或 `review/` 中，方便人工复核。

## 6. 报告初稿怎么验收

一份项目周报至少需要四轮检查。

### 6.1 事实检查

逐项检查：

```text
人员、项目和日期是否正确？
本周完成和计划事项是否混淆？
数字是否来自正确字段和时间区间？
同一指标在不同段落中口径是否一致？
推断是否明确标为推断？
```

不要因为文本读起来顺，就跳过事实核对。模型最容易把“计划完成”写成“已经完成”，也容易把上一周报告里的背景句复制成当前状态。

### 6.2 来源检查

报告中的关键事实建议使用这种格式：

```text
本周完成接口联调 3 项（来源：2026-08-03 项目进展表，字段“已完成事项”）。
```

如果平台或交付格式不适合把来源直接写进正文，也可以在文末加来源表：

| 报告结论 | 来源文件 | 位置 | 是否需确认 |
| --- | --- | --- | --- |
| 接口联调完成 | 2026-08-03-progress.xlsx | 已完成事项列 | 否 |
| 客户验收时间待定 | 2026-08-02-meeting.md | 第二项行动 | 是 |

来源标注的目标不是让报告变得复杂，而是让审阅人能快速验证关键内容。

### 6.3 结构和受众检查

面向项目负责人的周报，通常应该先讲结论，再讲证据和问题。可以检查：

```text
开头是否说明项目当前状态？
完成事项和风险是否分开？
阻塞问题是否说明影响和需要的决定？
下周计划是否能直接转成行动？
是否删掉了与本周决策无关的背景？
```

如果是给技术团队看的报告，可以保留接口、测试和依赖细节；如果是给非技术负责人看的报告，应把技术状态翻译成影响、风险和决策，而不是堆砌日志。

### 6.4 文件检查

最后检查：

```text
文件是否在 output/？
原始 source/ 是否保持不变？
标题、日期和项目名称是否正确？
表格是否能正常打开？
Markdown、Word 或 PDF 转换后是否出现截断？
是否包含不应交付的内部备注？
```

## 7. 四个常见失败分支

### 7.1 字段含义不清

现象：Agent 把“预计完成日期”当成“实际完成日期”，或者把金额字段当成数量。

处理：暂停报告生成，让它先输出字段解释、单位、时间口径和示例值。由熟悉业务的人确认后，再继续计算和写作。

### 7.2 数据来源缺失

现象：报告里出现了一个没有文件、段落或字段支持的数字。

处理：把数字改成“待确认”，回到原始资料核对；如果原始资料没有这个数字，就删除，不要求模型凭感觉补全。

### 7.3 结构不适合读者

现象：报告内容基本正确，但领导找不到风险和需要决策的事项，或者技术人员看不到复现信息。

处理：先明确读者和阅读场景，再让 Agent 只调整结构和表达，不重新计算数据。这样可以减少格式修改引入事实变化。

### 7.4 敏感资料不应上传

现象：输入中包含客户手机号、合同金额、身份证号、内部账号或未公开经营数据。

处理：停止上传，按组织规则使用脱敏副本或批准的内部环境。脱敏后要检查替换是否破坏了字段关系；如果报告需要真实身份才能完成，就交给有权限的人处理，不要绕过规则。

## 8. 把人工复核写成明确动作

“请人工检查”太宽泛。可以按下面的方式分配复核：

```text
资料负责人：确认事实、数字、日期和来源。
项目负责人：确认状态、风险、优先级和下周计划。
技术负责人：确认技术描述、依赖和测试结论。
发布人：确认格式、受众、敏感信息和最终版本。
```

如果只有一个人负责全部复核，也要分轮进行：先事实，后结构，再格式。一次性从头到尾通读，很容易被流畅表达带过错误。

## 9. 一个可重复的办公交付流程

把上面的步骤压缩成固定流程：

```text
1. 建立独立工作区，原始资料只读。
2. 清点文件、日期、字段和冲突。
3. 写清目标、读者、输入范围、输出和规则。
4. 先看计划，确认不会覆盖原始资料。
5. 生成报告初稿和来源映射。
6. 先核事实，再核结构，最后核格式。
7. 把待确认项交给对应负责人。
8. 修改后保存最终版本和复核记录。
```

对于重复的周报任务，可以把这套流程沉淀成模板，但每周的字段口径、资料日期和敏感信息都要重新确认，不能因为上周模板可用就跳过本周核对。

## 10. 交付前清单

```text
[ ] 本次读取的文件和版本已列出。
[ ] 原始文件没有被覆盖、删除或改名。
[ ] 每个关键数字都有来源和口径。
[ ] 计划事项没有被写成已完成事项。
[ ] 冲突、缺失和推断都已标记。
[ ] 报告结构符合目标读者的阅读顺序。
[ ] 风险、阻塞和需要决策的事项清楚可见。
[ ] 敏感信息已按组织规则处理。
[ ] 输出文件能打开，格式没有截断。
[ ] 人工复核记录已保存。
```

这张清单的作用是验收交付物，不是证明 Agent 永远正确。它能降低漏检，但不能代替资料负责人对业务事实负责。

## 11. 结论与限制

WorkBuddy 这类办公 Agent 是否有价值，不在于它能不能一次生成一篇漂亮报告，而在于它能不能稳定完成“资料清点、计划确认、产物生成、来源核对和人工复核”这条链路。

对第一次使用的人，最重要的不是打开所有功能，而是把一个低风险、资料边界清楚的周报任务跑通。原始资料只读、输出单独保存、数字可追溯、未知信息不补全，这四条先守住，再考虑模板、自动化和更复杂的连接能力。

本文没有把 WorkBuddy 的具体登录方式、入口名称、技能市场或远程能力写成固定事实，因为这些内容可能随版本、账号和组织配置变化。实际使用前应按照当前官方产品说明和组织安全规则核对；如果当前环境不支持某个入口，可以保留同样的资料清点、来源标注和人工验收方法，换用可控的文档处理工具完成。
