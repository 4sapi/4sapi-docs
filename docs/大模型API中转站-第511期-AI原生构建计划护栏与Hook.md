# AI 原生构建怎么控风险：plan.md、CLAUDE.md、Skill 与 Hook

让 Coding Agent 自主修改代码，真正难的不是让它调用更多工具，而是控制它什么时候可以动、能动哪些文件，以及如何证明修改没有绕过检查。规则全写在提示词里，长任务中可能被遗漏；每个动作都要人批准，又会把提速消耗在审批队列里。

更实用的做法，是把构建阶段的控制拆成几层：先用 `plan.md` 约束实现范围，再用 `CLAUDE.md` 和 Skill 提供建议，用 Hook、测试和分支保护执行必须成立的规则。

这篇文章聚焦构建阶段的分层护栏：计划、项目规则、Skill、Hook、测试和分支保护分别承担什么责任。

## 一、先区分建议性控制和确定性控制

可以把控制分成两类：

| 类型 | 典型手段 | 作用 |
| --- | --- | --- |
| 建议性控制 | Prompt、CLAUDE.md、Skill | 提高正确行为出现的概率 |
| 确定性控制 | Hook、沙箱、测试、分支保护 | 阻止不允许的行为或结果 |

建议性控制适合解释背景和工作习惯。

确定性控制适合保护密钥、冻结目录、生产分支和必须通过的测试。

不能把“请不要修改测试”当作测试保护。

真正重要的规则，要在工具或仓库层面再次检查。

## 二、plan.md 是构建前的一道门

构建任务不应从“直接开始改代码”开始。

先让 Agent 读取已接受的规格，探索仓库，然后生成 `plan.md`。

计划至少写清：

```text
准备修改哪些文件。
每个文件要改变什么。
实现顺序是什么。
会新增或修改哪些测试。
哪些路径明确不碰。
完成后运行什么验证。
```

一个没有参加前面讨论的工程师，应能只读这份计划并完成同一工作。

如果计划仍然只有“优化模块、补充测试”这样的句子，就还不够具体。

## 三、先接受计划，再允许写入

建议把流程写成：

```text
读取 spec.md → 探索仓库 → 生成 plan.md → 工程师接受 → 允许修改文件
```

这一步的价值在于：方向错误时，修改的是文档，不是几十个文件的 Diff。

计划被接受之前，Agent 可以搜索、读取和提出方案，但不应该进入大范围写入。

## 四、实现偏离计划时怎么办

实际构建中经常会发现计划遗漏依赖或低估复杂度。

这不代表计划失效，而是要把变化显式记录：

```text
发现了什么新事实。
为什么原计划不再适用。
哪些文件范围发生变化。
测试和风险是否增加。
是否需要重新接受计划。
```

可以在同一个变更中更新 `plan.md`，也可以重新提交一个计划版本。

关键是不要让最终 Diff 与原计划之间没有解释。

## 五、CLAUDE.md 只放真正会反复用到的规则

项目规则文件适合保存新人第一天需要知道的内容：

```text
如何启动和测试。
目录和模块职责。
代码风格和命名约定。
常见错误与排查方法。
哪些路径不能随意修改。
提交前必须运行的命令。
```

规则文件应保持短小。

如果每次会话都会读取它，把所有历史背景都塞进去，会消耗上下文，也会让真正重要的规则变得不显眼。

## 六、错误出现两次就写进规则

一个实用习惯是：同类错误第二次出现时，不只修当前代码，也更新项目规则。

例如 Agent 两次都把测试命令写错，就在规则文件中补上：

```text
运行测试必须使用 `pnpm test --filter parser`，不要调用根目录的全量脚本。
```

规则文件不是错误流水账。

只保留能够减少下一次返工的长期经验。

## 七、Skill 适合放组织方法，不适合放硬限制

Skill 可以封装复杂的工作方法，例如：

```text
如何做一次安全评审。
如何生成迁移计划。
如何检查文档是否有遗漏。
如何整理变更日志。
```

它属于建议性控制。

如果规则必须始终成立，Skill 后面还需要 Hook、CI 或权限系统再次检查。

例如 Skill 可以提醒“不要把密钥写进 Diff”，但凭据扫描和提交钩子应负责真正阻止它。

## 八、Hook 应该保护什么

构建期 Hook 适合处理快速、确定和局部的检查：

```text
阻止编辑受保护路径。
阻止敏感文件进入 Diff。
对变更文件自动运行 formatter。
对变更文件运行快速 lint。
检查工具参数是否越界。
```

Hook 要尽量快，并且只处理当前变更。

重型测试、完整安全扫描和集成测试可以放到提交或 PR 阶段。

## 九、不要把审批 Hook 放在每个小动作上

如果构建期每次写文件都要人工批准，多个并行会话会同时等待人。

这样人的注意力又回到 Agent 的关键路径上。

更合理的分层是：

```text
构建期：自动允许安全的内循环，阻止确定的越界。
提交期：运行完整检查并生成结果。
PR 阶段：审阅计划、Diff、测试和风险。
生产门：对发布、权限和不可逆动作保留人工批准。
```

## 十、受保护路径要在工具层拦截

以下目录通常需要额外保护：

```text
生成文件目录。
迁移锁文件。
生产配置。
审计规则。
测试基线。
依赖冻结目录。
```

只在提示词里写“请不要改”不够。

可以让 Hook 在文件写入前检查路径，发现越界就拒绝，并告诉 Agent 应该如何申请或改用其他路径。

## 十一、修 Bug 时先锁定失败测试

修复任务最容易出现“把测试改绿”的假完成。

更稳的流程是：

```text
复现 Bug → 写一个预期失败的测试 → 提交测试基线 → 禁止修改该测试 → 修改实现 → 运行测试
```

如果修复前测试确实失败，修复后在不修改测试的前提下通过，它才构成较强证据。

可以用路径 Hook 阻止修复任务编辑新增的回归测试。

## 十二、并行会话与子代理不是一回事

并行会话通常是多个完整 Agent，各自有独立工作树。

子代理是在一个主会话内部运行，拥有自己的上下文和工具限制。

它们适合的任务不同：

| 方式 | 适合 |
| --- | --- |
| 并行会话 | 多个独立方案、多个模块、不同 worktree |
| 子代理 | 重复验证、代码探索、只读审查 |
| 单会话 | 强依赖顺序、统一设计和敏感决策 |

并行数量不应由机器能启动多少决定，而应由人能认真审阅多少决定。

## 十三、并行前先切清共享资源

并行任务启动前，写清：

```text
每个会话负责哪些文件。
哪些目录只读。
结果通过什么文件交接。
谁负责最终合并。
冲突由谁解决。
```

两个 Agent 同时改同一个核心接口，通常不会因为并行而更快。

适合并行的是低耦合探索和独立验证，不是所有任务都复制一份。

## 十四、终检要使用新上下文

写代码的 Agent 很容易相信自己在实现过程中形成的假设。

因此，完成后可以启动一个新的只读验证上下文，检查：

```text
规格是否满足。
计划是否被绕过。
测试是否真的覆盖目标。
Diff 是否包含无关修改。
是否有明显安全风险。
```

验证代理只读、不修复。

如果它发现问题，再回到执行阶段修复，避免“验证和修改同时发生”。

## 十五、用一个命令包装反馈回路

Agent 不应自行猜测“项目是否通过”。

可以提供一个统一命令：

```bash
./scripts/verify-change.sh
```

这个命令负责：

```text
检查格式。
运行变更相关测试。
检查类型和 lint。
检查敏感文件。
返回明确的非零退出码。
```

命令输出还应告诉 Agent 下一步应该查看什么，而不是只打印一行失败。

## 十六、把规则和配置纳入版本控制

以下文件都可能改变 Agent 行为：

```text
CLAUDE.md。
Skill 定义。
Hook 脚本。
权限配置。
REVIEW.md。
测试和 eval 配置。
```

它们不能只存在某台工程师电脑里。

修改这些文件也要走 review，并在必要时运行回归任务。

否则团队会出现“代码没变，但 Agent 行为变了”的难以解释情况。

## 十七、构建阶段的最小护栏清单

小团队至少可以落地：

```text
有一份被接受的 plan.md。
项目规则文件不超过一页核心内容。
敏感路径和测试基线有确定性保护。
有一个可重复运行的验证命令。
Diff 中不出现密钥和无关文件。
完成后由新上下文做一次只读终检。
```

## 十八、结论

AI 编码的治理重点，不是让模型永远不犯错，而是让错误在影响扩大前被发现和阻断。

`plan.md` 控制构建前的方向，`CLAUDE.md` 和 Skill 提供可复用的建议，Hook、测试和分支保护负责执行必须成立的规则。

并行会话可以提高吞吐，但只有在文件边界、交接方式和人工审阅能力都清楚时才有价值。

当构建过程留下计划、Diff、测试和终检证据，Agent 才能从“会改代码”逐步变成“可被工程流程接住的执行者”。
