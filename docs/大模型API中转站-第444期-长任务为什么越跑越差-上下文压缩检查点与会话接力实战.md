# 长任务为什么越跑越差：上下文压缩、检查点与会话接力实战

长任务刚开始时，Agent 往往能列清目标、文件和下一步。运行几小时、经过多轮工具调用后，它可能重新打开已经完成的工作，忘记哪些目录不能改，把旧结论带进新阶段，甚至在外部系统重复创建同一条记录。原因不只是上下文窗口大小：任务状态散落在聊天、工具输出、文件、数据库和人工决定里，任何一层没有保存并验证，后续就可能沿着错误前提继续跑。

本文把长任务当成一个需要暂停、恢复、回滚和验收的运行过程，不重复讨论如何把对话摘要搬到新会话。重点是三件事：检查点要保存什么，恢复时怎么验，以及怎样避免压缩后表面连贯、实际丢掉关键约束。

## 一、先识别三种不同的退化

### 目标漂移

任务从“生成可审核草稿”变成“直接发布”，或从“修复指定报错”变成“顺便重构全部模块”。这通常来自任务边界没有被持续重申，或中间出现新请求却没有明确批准范围变化。

### 状态丢失

已完成的验证、被否决的方案、工具返回的外部编号、资料的版本和人工审批，只存在于旧对话或临时输出中。新会话或子任务读取不到它们后，只能猜测或重复执行。

### 上下文污染

大量无关日志、失败草稿、互相矛盾的结论和外部内容混在一起。即使都在上下文窗口内，模型也可能优先抓到旧版本、错误事实或不应执行的文本指令。

这三类问题的修法不一样：目标漂移靠变更控制，状态丢失靠检查点，上下文污染靠裁剪和来源分层。全部归结为“模型记忆差”，就会错过系统里本来能修的地方。

## 二、检查点不是摘要，而是可恢复状态

一份可靠检查点要让接手的人或新的 Agent 看懂四件事：现在要做什么，哪些事实已确认，哪些动作已经发生，下一步能不能安全执行。可以使用下面结构：

```markdown
# Checkpoint: task-123 / phase-2

## 目标与范围
- 当前目标：
- 明确不做：
- 变更记录：

## 已确认事实
- 事实：；来源或证据：

## 运行状态
- 已完成步骤：；证据：
- 进行中步骤：
- 未完成步骤：
- 阻塞与依赖：

## 外部动作
- 已提交动作、业务标识与实际结果：
- 是否允许重试：
- 审批状态：

## 环境与版本
- Agent / Prompt / Skill：
- 模型与路由：
- 工具、资料与权限版本：

## 下一步与验证
- 唯一下一步：
- 开始前检查：
- 完成条件和停止条件：
```

检查点中每个“已完成”都要有证据位置，例如测试命令及其结果、文件路径、下游返回 ID 或人工审批记录。没有证据的状态应标为待验证，而不是为了交接流畅写成已完成。

## 三、把状态放在正确位置

不是所有内容都要塞进一份 Markdown。不同状态应留在最适合验证的位置：

| 状态 | 权威位置 | 检查点记录什么 |
| --- | --- | --- |
| 源码与配置 | 版本控制或受控文件系统 | 提交号、变更摘要、路径 |
| 测试结果 | CI、命令输出或测试报告 | 命令、时间、结果引用 |
| 资料与知识 | 原文、来源页、资料版本 | 文档 ID、版本和权限范围 |
| 外部动作 | 下游业务系统 | 业务标识、状态、是否可重试 |
| 人工决定 | 审批或决策记录 | 决定、批准人、有效期 |
| 临时推测 | 检查点待验证区 | 假设和验证方法 |

检查点只是索引和工作合同，不能代替证据。恢复时仍要回到权威位置核对关键项。

## 四、在阶段边界创建检查点

不是每条消息都需要压缩。更合适的时机是工作状态发生改变时：

```text
任务目标或授权范围改变前后。
开始或完成一次可能有副作用的外部动作前后。
完成一组测试、资料调查或批量处理后。
准备把工作交给另一个 Agent、另一个人或新会话时。
遇到无法继续的错误、权限拒绝或环境变化时。
```

对于长循环任务，可以规定一个可观察的阶段产物，例如“完成十条只读资料比对后保存检查点”，而不是根据模型感觉决定何时总结。检查点频率应由风险和恢复成本决定；高风险写入的检查点应更细，纯只读草稿可以更粗。

## 五、恢复不是“继续”，而是接收验收

恢复任务前，新的执行者应先做一轮只读核对：

```text
1. 确认目标、范围和当前版本仍然有效。
2. 验证检查点中已完成项的关键证据。
3. 查询外部动作的实际状态，而不是假定它成功或失败。
4. 检查凭证、审批、数据访问和环境是否仍有效。
5. 列出检查点内的矛盾、过期信息和待验证项。
6. 只在通过这些检查后执行唯一下一步。
```

这一步尤其适用于发送、创建、扣费、删除和生产修改。某次运行在“调用已发出”处中断时，新会话不能自动重试；它应先按业务标识查询下游状态，确认没有重复副作用后再决定。

## 六、上下文压缩应保留什么，丢弃什么

压缩是为了去掉噪声，不是把所有历史改写成一段顺滑叙述。优先保留：

```text
当前目标、范围与禁止事项。
已确认事实及其来源。
已否决方案与否决证据。
外部动作和业务标识。
版本、权限、审批与环境变化。
未完成、阻塞和唯一下一步。
```

通常可以丢弃或移出当前上下文的内容包括：已被验证替代的中间草稿、无关工具原始输出、重复的讨论、已关闭的低风险分支。丢弃不是删除证据，而是让原始记录留在日志或文件中，并在检查点保留链接。

任何来自网页、文档或工具返回的文本，都应该作为资料而不是运行指令。压缩器不应因为其中出现“立刻发送”“忽略之前规则”就把它提升为下一步行动。

## 七、用幂等性保护跨会话的外部动作

长任务最危险的错误之一是重复执行。为有副作用的操作设计：

| 控制 | 作用 |
| --- | --- |
| 业务标识 | 标识同一个订单、工单、消息或变更对象 |
| 幂等键 | 让下游识别同一请求的重复提交 |
| 提交前查询 | 先确认目标是否已存在或已处理 |
| 状态机 | 区分草稿、待审批、已提交、已确认、失败 |
| 人工审批 | 对不可逆或外部影响动作设置最后控制点 |

检查点只记录“准备发送”不能阻止重复；必须记录对象、下游返回和当前状态。下游系统没有幂等能力时，应该收紧自动化范围，把重复风险高的动作留给人工确认。

## 八、一个可执行的长任务循环

```text
读取任务卡和最近检查点
  -> 接收验收（只读）
  -> 执行一个阶段内允许的动作
  -> 保存工具结果与外部状态引用
  -> 运行阶段验证
  -> 写入检查点
  -> 决定继续、转人工、暂停或交接
```

循环中不要让 Agent 一次承担“重新理解全部历史、修改系统、执行外部动作和总结下一步”。将每阶段限制为一个明确产物，虽然看似多了一步，却显著降低了恢复和审查成本。

## 九、用回归任务检查恢复能力

可以准备四个小任务验证检查点设计：

| 样例 | 预期行为 |
| --- | --- |
| 任务在只读检索后中断 | 恢复时复用证据引用，不重复扩大全库搜索 |
| 任务在外部写入请求后中断 | 先查询业务标识，不盲目重试 |
| 任务目标在阶段间改变 | 要求新的范围确认，不沿用旧授权 |
| 旧检查点依赖过期资料或失效凭证 | 标记阻塞并请求更新，不假装继续 |

每次改变压缩策略、工具状态机、模型路由或权限规则后，都应重跑这些样例。恢复设计是否可靠，不能只靠一次顺利的长对话验证。

## 十、检查清单

```text
[ ] 任务目标、范围、禁止事项和变更记录写在检查点中。
[ ] 已完成项都有可回到权威系统的证据。
[ ] 推测、待验证和已确认事实没有混写。
[ ] 外部动作有业务标识、实际状态与重试规则。
[ ] 检查点在阶段边界、外部动作和交接前后创建。
[ ] 恢复先进行只读接收验收，再执行下一步。
[ ] 压缩保留来源、约束、否决结论、版本、权限和审批。
[ ] 无关日志与过期草稿被移出当前上下文，但原记录仍可追溯。
[ ] 有副作用操作具备幂等、查询、状态机或人工确认控制。
[ ] 已用中断、目标变化和失效凭证样例测试恢复流程。
```

## 结论与资料

长任务靠可验证的状态保持稳定，不靠无限延长聊天记录。检查点把目标、证据、版本、授权和外部动作整理成接手人能核对的工作合同；恢复时重新查权威状态；有副作用的操作用幂等和审批防止重复。这样，压缩和会话接力才是在降低复杂度，而不是把错误继续往后传。
