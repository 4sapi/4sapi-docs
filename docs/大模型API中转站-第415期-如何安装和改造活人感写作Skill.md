# 如何安装和改造活人感写作 Skill

很多人第一次接触写作 Skill 时，会把它理解成一张更长的提示词清单：里面规定哪些词不能用，哪些句式要少写，结尾应该怎样收束。

这种理解只对了一部分。一个真正有用的写作 Skill，不应该只是把所有文章改成同一种口吻，也不应该把作者训练成某个固定风格的复制品。它更像一套协作流程：在模型开始写之前，先采访作者、收集真实材料、厘清判断和证据；在模型写完之后，再检查哪些地方变成了公共正确意见，哪些细节可能是模型补出来的，哪些表达过度解释了原本可以留下余味的内容。

本文以开源的 `human-writing` 项目为例，讲清楚如何安装和使用一类“活人感写作 Skill”，以及如何把它改造成适合自己的工具。项目地址为 [https://github.com/KKKKhazix/human-writing](https://github.com/KKKKhazix/human-writing)。具体安装入口会随 Agent 产品和版本变化，本文重点放在可迁移的方法，不把某个客户端的按钮位置写成永久规则。

## 一、安装之前，先理解 Skill 能解决什么

写作 Skill 能做的事情，通常包括：

- 把一次性“请写文章”变成采访、整理、写作、审查几个阶段；
- 提醒模型优先索取真实案例、原话、时间和具体动作；
- 让模型区分作者经历、外部事实、推断和待核验内容；
- 降低固定句式、过度总结和情绪解释的出现频率；
- 在初稿完成后，从事实、逻辑、节奏和作者存在感几个角度进行审查。

它不能完成的事情同样重要：

- 不能替你凭空创造真实经历；
- 不能保证所有外部事实自动正确；
- 不能把任何模型都变成同一个水平；
- 不能通过删除几个词，让没有观点的内容变得有价值；
- 不能替你决定哪些话值得公开、哪些经历适合署名。

如果把 Skill 当成“AI 味过滤器”，你会反复修改词语；如果把它当成“写作协作协议”，你会更关心材料、判断和验收。

## 二、安装前先做一次安全检查

任何来自网络的 Skill，都不应该因为名字听起来有用，就直接放入拥有大量权限的 Agent 环境。

安装前至少检查以下内容：

### 1. 看清它包含哪些文件

优先查看仓库的说明文件、Skill 主文件、示例和脚本。重点关注它是否要求读取整个磁盘、访问凭据、执行外部命令或自动上传文件。

一个纯写作 Skill 通常只需要读取你主动提供的文本，不应该要求访问 API Key、浏览器 Cookie、SSH 私钥或企业内部目录。

### 2. 区分指导文本和可执行代码

Skill 可能只有 Markdown，也可能包含脚本、模板和配置。Markdown 也不是天然安全的，因为它可能诱导 Agent 执行超出任务范围的动作；带脚本的仓库则需要额外检查依赖、网络请求和文件写入路径。

如果你只想测试写作流程，建议先把它放在一个没有敏感文件的测试目录中，使用一份脱敏材料运行。确认它的行为之后，再考虑在真实项目里启用。

### 3. 留意版本和来源

公开仓库会持续变化。安装时记录仓库地址、提交版本或下载时间，之后出现行为变化才有机会定位原因。对于团队使用，最好把经过审查的 Skill 文件纳入自己的版本管理，而不是每次都直接拉取最新内容。

可以用下面这段提示让 Agent 先做安装审查：

```text
请先审查这个写作 Skill，不要立即安装，也不要执行其中的脚本：
https://github.com/KKKKhazix/human-writing

请输出：
1. 仓库包含哪些文件和目录；
2. 哪些内容只是写作规则，哪些内容可能触发命令、网络或文件操作；
3. 它需要哪些权限；
4. 是否存在读取凭据、上传数据或修改工作区的行为；
5. 安装到当前 Agent 后，调用方式和影响范围是什么；
6. 你建议保留、删除或隔离哪些部分。

没有完成审查前，不要执行安装和脚本。
```

这一步有点慢，却能避免把“写文章”任务和不必要的系统权限混在一起。

## 三、两种常见安装方式

### 方式一：通过支持 Skill 安装的 Agent 调用

如果你的 Agent 支持从 GitHub 地址安装技能，可以直接发送类似下面的请求：

```text
请安装并启用这个写作 Skill：
https://github.com/KKKKhazix/human-writing

安装前先检查文件内容和权限需求。
只启用写作相关规则，不执行与写作无关的脚本或外部操作。
安装完成后告诉我：
- Skill 的名称；
- 它会在什么任务中触发；
- 它的主要工作阶段；
- 如何显式调用；
- 如何暂时停用。
```

安装完成不等于它已经生效。需要让 Agent 明确告诉你实际加载了哪个文件、当前使用的版本和触发方式。若它只能回答“已经安装好了”，却说不清这些信息，就应该继续检查，而不是直接拿重要文章测试。

### 方式二：手动下载后审查和接入

如果客户端不支持直接安装，可以先将仓库下载到隔离目录，再阅读 Skill 主文件。对于只包含 Markdown 的项目，手动接入通常是把经过审查的规则复制到 Agent 的技能目录、项目规则文件或专用提示词中。

手动接入时要确认三件事：

1. 规则的作用范围是单次任务、当前项目，还是全局所有对话；
2. 是否会覆盖你已有的写作规则、品牌语气和事实核验流程；
3. 关闭或回滚的方法是什么。

不要把多个相似的写作 Skill 同时全局启用。规则之间如果互相冲突，模型可能在句式、篇幅、格式和审查顺序上摇摆，最后很难判断是哪一条造成了结果变化。

## 四、安装后的第一次测试，不要直接写长文

正确的验收方式不是立即让模型写一篇五千字文章，而是准备一份短材料，观察它是否真的改变了协作流程。

测试材料最好包含四类信息：

- 一个明确但不完整的主题；
- 两三条自己的真实经历；
- 一个仍然不确定的判断；
- 一条需要核验的外部事实。

然后发送：

```text
请使用刚安装的写作 Skill 处理下面的材料。

要求：
1. 先不要写文章；
2. 一次只问我一个问题；
3. 把我提供的内容分为事实、判断、外部资料和待核验项；
4. 不得补写没有发生过的经历、对话、日期和数字；
5. 等我确认材料后，再给出文章结构。

主题：________。
我的材料：
________。
```

如果模型跳过采访直接写完整文章，说明 Skill 没有正确触发，或者当前 Agent 的系统规则优先级高于它。此时先查加载状态，不要继续堆叠更多“请像真人一样写”的要求。

## 五、把调用方式从“写文章”改成“协作模式”

活人感写作最重要的变化，是把一个长任务拆成几个可以验收的阶段。

### 阶段一：材料访谈

这一阶段的目标不是产出文字，而是找回作者的具体经验。可以要求模型一次只问一个问题，并且优先问：什么时候发生、在哪里发生、谁做了什么、结果是什么、作者的看法何时改变。

如果模型问出的问题过于抽象，例如“这件事给你带来了什么启示”，可以改为“当时你具体做了哪个动作，后来发现它和之前的想法有什么不同”。

### 阶段二：事实与判断分离

让模型分别列出：发生过的事情、作者对事情的理解、来自外部的材料、暂时没有证据的推测。这个分离很重要，因为很多文章的 AI 味，来自模型把推测包装成了事实，把公共观点伪装成了作者经验。

### 阶段三：结构设计

只让模型设计文章路径，不让它提前填充漂亮段落。结构至少应该回答：读者的问题是什么、作者的主张是什么、哪条事实支持它、可能的反例是什么、限制在哪里。

### 阶段四：成稿

成稿时给模型一条明确边界：可以改变表达，不可以改变事实；可以调整顺序，不可以替作者增加经历；可以指出缺口，不可以用想象填空。

### 阶段五：反向审查

最后让模型站到审稿人的位置，专门查四类问题：公共正确意见、无来源细节、过度解释和作者立场消失。审查结果先列出来，作者确认后再修改。

## 六、不同模型怎么配合，不能只看“文风好不好”

在实际使用中，用户可能会把同一个 Skill 放到多个模型上。此时不要只比较哪一篇更像“人写的”，而应该记录相同材料下的过程差异。

可以观察以下指标：

| 指标 | 观察问题 |
| --- | --- |
| 采访质量 | 是否问到场景、动作和变化，而不是只问感受 |
| 事实纪律 | 是否擅自补充细节、数字、引语和来源 |
| 结构能力 | 是否能围绕一个问题组织材料 |
| 反方能力 | 是否能指出作者论证的范围和漏洞 |
| 语言控制 | 是否过度使用总结句、比喻和抽象名词 |
| 修改服从度 | 作者要求保留迟疑时，是否又把它改成确定结论 |
| 长文稳定性 | 到后半篇是否忘记前面确认过的事实 |

不同模型可能各有侧重。有的模型采访更细，有的模型整理更快，有的模型写出的句子更有节奏，也有的模型在长文中更容易把不确定内容说满。不要把单篇体验写成普遍排名，最好用同一份材料做小型 A/B 测试，并保留中间过程。

测试记录可以很简单：

```text
日期：________
模型与版本：________
Skill 版本或提交：________
输入材料长度：________
是否先采访：是 / 否
自行补写的事实数量：________
作者需要重写的核心段落：________
保留的真实细节数量：________
作者对最终判断的认可度：1-5
```

这样的记录比“感觉这一版更有活人感”更容易指导后续改造。

## 七、如何把通用 Skill 改成属于自己的版本

通用 Skill 的价值，是提供一个起点。长期使用后，你应该把自己的经验沉淀进去，但不要把它改造成一套只能复制旧文章的固定文风。

### 1. 加入“作者事实库”，不是加入一堆形容词

可以整理一个个人材料文件，记录长期稳定的信息：职业背景、常见读者、实际做过的项目、反复出现的判断、明确不愿意表达的内容，以及一些真实的语言习惯。

比起写“我的文风要真诚、克制、有温度”，更有效的是记录：

- 我通常怎样描述一个失败；
- 我有哪些判断经过实践后改变过；
- 哪些词我确实使用，哪些词是模型强行加给我的；
- 我习惯用什么类型的案例；
- 我希望读者在结尾停留在哪里，而不是被一句口号推走。

### 2. 用“保留和禁止”两张表

禁止表可以列出反复出现的模板化表达，但不要把它当成绝对禁词。某个词在合适语境下完全可以使用，问题通常是高频、堆叠和缺乏具体内容。

保留表更重要，可以记录你希望模型不要删除的东西：不确定性、原话、具体动作、失败过程、反例、局部判断和不够漂亮但准确的句子。

### 3. 把真实文章作为案例，而不是当作硬模板

挑选几篇你真正认可的文章，让模型分析它们为什么成立：事实密度如何、观点怎样出现、段落怎样转向、哪些地方没有解释、哪些句子承担了关键作用。

不要简单要求“模仿这篇文章的风格”。那会把表面词汇和句式复制过来，反而削弱自己的表达。更好的请求是“提取这篇文章可迁移的方法，不复制原句，也不要把我的文章写成同一作者”。

### 4. 给 Skill 加上停机条件

如果作者没有提供事实，Skill 应该停下来提问；如果外部事实没有来源，应该标记待核验；如果文章已经完成，不能为了凑字数继续加抽象总结。

一个好的 Skill 不只是知道什么时候生成，还知道什么时候不应该生成。

## 八、常见故障和排查顺序

### 故障一：安装了 Skill，但模型还是直接写

先确认 Skill 是否被当前客户端加载，再确认调用名称和作用范围，最后检查是否有更高优先级的系统或项目规则覆盖。不要先修改正文提示。

### 故障二：模型问了很多问题，但文章仍然空泛

问题可能太偏向情绪和观点，缺少场景、动作和结果。把“你有什么感受”换成“你当时做了什么”“哪个细节让你改变了想法”。同时检查作者是否真的提供了可以写入文章的材料。

### 故障三：模型开始编造很有画面感的细节

在提示里明确禁止补造，并要求它为每个具体细节标注来源。已经出现的细节不要直接润色，要返回材料账本核对；无法核对就删除或改成明确的不确定表达。

### 故障四：文章变得过度朴素，失去表达力度

活人感不是反对所有修辞。检查是否把比喻、节奏和概念解释全部删掉了。应当删除的是无来处的漂亮句子，而不是删除所有漂亮句子。只要辞章服务于真实判断，就可以保留。

### 故障五：文章越来越像自己过去的文章

这通常意味着 Skill 里的案例和禁忌过度固化。减少直接模仿，增加不同题材、不同节奏和不同立场的样本；同时把 Skill 的任务从“复刻声音”改成“追问材料、验证事实、保持作者判断”。

## 九、最后的验收标准

一篇文章是否真的因为 Skill 变好，可以用下面的标准验收：

1. 文章是否围绕一个可以回答的问题展开；
2. 作者能否指出至少三处只有自己才提供得出来的材料；
3. 外部事实是否有对应来源，推断是否被标明为推断；
4. 模型是否在材料不足时提问，而不是自行补写；
5. 文章是否保留了真实的限制、迟疑和反例；
6. 是否减少了模板化总结，但没有故意制造错误和粗糙；
7. 删除某句漂亮结尾后，前文是否仍然成立；
8. 作者是否愿意在署名后对核心判断负责；
9. 换一个读者阅读时，是否能看出作者为什么要在此时写这篇文章；
10. 同样的流程换一份材料，是否仍然有效，而不是只能复刻某篇样文。

这十条比“像不像某位作者”更适合检验一个通用写作 Skill。

## 结语：Skill 的目标不是替你发声

一个好的写作 Skill，最终应该让作者更清楚自己想说什么，而不是让所有人都变成同一种声音。它可以帮助你把混乱的经历整理成材料，把模糊的感受追问成判断，把查证过的事实组织成文章，再把已经属于你的内容写得更清楚。

但它不应该替你生活、替你回忆、替你承担判断，也不应该用一套固定腔调覆盖掉你的差异。

安装 Skill 是开始，真正的价值来自持续记录：哪些问题问得好，哪些地方发生了编造，哪些修改让文章更像你，哪些“去 AI 味”反而删掉了本来很重要的内容。

当这些反馈逐渐沉淀下来，你得到的就不只是一个写作插件，而是一套越来越了解你的协作方法。模型负责提高表达效率，人负责保留经验、判断和方向。写作的主体，始终应该是后者。
