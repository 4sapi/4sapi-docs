# 企业 AI 知识库权限怎么设计：从部门隔离到旧系统接入

知识库回答错误，可能是资料本身有问题；知识库泄露信息，则通常是权限设计出了问题。很多项目先做一个所有人都能搜索的演示版本，到了真实交付阶段才发现，研发图纸、销售报价、售后记录和人事制度根本不能放在同一个可见范围里。

这篇文章聚焦接入前的权限设计，并进一步说明怎样判断旧系统是否具备安全、稳定的连接条件。

## 一、权限设计先回答三个问题

不要从“给哪个用户开权限”开始。

先问：

```text
谁可以看到这份知识？
谁可以用它提问？
谁可以修改、审核和下架它？
```

这三个动作经常被混在一起。

一个销售可能可以查询已发布的产品参数，但不能修改原始资料。

一个研发人员可以维护技术条目，却不应该自动看到所有人事制度。

一个管理员可以维护账号，但不一定应该阅读业务内容。

## 二、建立“主体—资源—动作”矩阵

最小权限模型可以用三列表示：

| 主体 | 资源 | 动作 |
| --- | --- | --- |
| 销售组 | 已发布产品手册 | 查询 |
| 售后组 | 故障处理知识 | 查询、提交修订 |
| 研发组 | 设计资料 | 查询、审核 |
| 知识管理员 | 全部已授权知识 | 上架、下架、版本管理 |
| 审计人员 | 访问日志 | 只读 |

先把动作拆开，再讨论系统角色。

“能访问”不等于“能修改”，更不等于“能发布”。

## 三、权限边界应该跟业务组织对齐

企业常见的权限维度包括：

```text
部门。
岗位。
项目。
地区。
客户。
产品线。
资料密级。
```

不要一开始就设计几十种角色。

先找出真正影响回答范围的维度，再按业务场景组合。

例如售后知识可能按产品线隔离，销售资料还要按地区或客户组隔离。

如果权限维度无法用业务语言解释，后续维护会变得困难。

## 四、检索权限必须在检索前生效

一个常见错误是：先把所有文档召回，再在回答阶段让模型“不要泄露”。

这不是可靠的权限隔离。

正确方向是：

```text
用户身份确认 → 计算可见资源 → 在可见范围内检索 → 生成回答 → 记录审计日志
```

模型提示词可以提醒边界，但不能替代数据层过滤。

如果用户无权访问某个文档，最好让它从召回集合中消失，而不是让模型看见后再要求模型保密。

## 五、回答中还要保留来源边界

权限过滤不只影响正文，也影响引用。

需要检查：

```text
引用的文件是否对当前用户可见。
引用片段是否跨越了不可见段落。
回答摘要是否泄露隐藏文档的存在。
错误提示是否暴露目录结构或文件名。
```

例如不能因为用户没有权限读取研发文档，就回答“研发资料里写的是……”。

即使不展示原文，这句话也可能泄露敏感信息。

## 六、把维护权限和内容审核分开

知识库不是上传网盘。

资料进入回答范围前，通常需要审核状态：

| 状态 | 含义 |
| --- | --- |
| 草稿 | 只有维护人员可见 |
| 待审核 | 业务负责人需要确认 |
| 已发布 | 进入指定检索范围 |
| 已过期 | 不再参与默认回答 |
| 已下架 | 保留记录但不可检索 |

维护者可以编辑草稿，但不应默认拥有发布权。

发布动作需要留下人、时间、版本和变更原因。

## 七、旧系统接入前先查有没有接口

客户经常会提出“把 ERP、OA、CRM 全部接进来”。

这句话还不是技术方案。

要先确认：

```text
系统是否提供正式 API。
接口是否支持只读访问。
是否有稳定的身份认证方式。
数据字段和更新时间是否可解释。
接口是否允许按部门或项目过滤。
```

如果系统没有接口，不能默认通过脚本模拟登录、抓页面或直接改数据库解决。

这些做法可能破坏原系统稳定性，也会把项目带入不可控范围。

## 八、为什么老系统没有接口时要谨慎

没有接口意味着缺少稳定契约。

今天能抓到的页面，明天可能因为改版而失效；今天能读到的数据库字段，明天可能因为升级而变化。

知识库项目通常不是遗留系统改造项目。

如果接入一个旧系统需要先反向工程、补权限、改数据库和承担升级兼容，应该把它单独评估。

“客户想接入”不等于“原项目已经包含接入”。

## 九、只读接入也要做数据分层

只读并不意味着没有风险。

一个只读接口仍可能返回：

```text
客户联系方式。
报价和折扣。
内部故障记录。
未发布产品信息。
员工个人数据。
```

接入前应明确字段白名单，而不是把整个表直接同步到知识库。

同步任务还要记录来源、更新时间和删除策略。

如果源系统删除了记录，知识库中的副本是否也要下架，必须提前定义。

## 十、私有化和云端不是先进与落后的选择

部署方式首先取决于数据要求：

| 条件 | 可能的方向 |
| --- | --- |
| 数据不能离开企业环境 | 私有化或隔离网络 |
| 可以使用外部模型 | 云端或托管服务 |
| 需要连接多个内网系统 | 重点评估网络和凭证边界 |
| 没有专门运维团队 | 选择团队能持续维护的方案 |

私有化部署也不代表答案天然正确。

它主要改变数据路径、模型运行环境和参数控制方式。

资料质量、检索策略、权限和验收仍然需要单独处理。

## 十一、先测模型能力，再评估硬件

客户要求私有化时，常见顺序是先问“需要买多大的服务器”。

更合理的顺序是：

```text
固定业务问题 → 测试候选模型 → 明确最低能力 → 估算并发与上下文 → 评估硬件
```

如果模型无法回答关键问题，机器配置再高也不能解决知识缺口。

硬件评估至少需要输入：

```text
模型大小和量化方式。
并发用户数。
单次输入长度。
期望响应时间。
是否需要多模态解析。
是否允许排队或异步处理。
```

## 十二、身份、密钥和日志要分层

知识库接入多个系统时，不能让所有组件共用一个超级账号。

建议按用途拆分：

| 凭证 | 用途 | 权限 |
| --- | --- | --- |
| ingest-reader | 同步源系统 | 指定表只读 |
| search-service | 在线检索 | 只访问索引服务 |
| admin-console | 配置维护 | 需要人工审批 |
| audit-reader | 审计查询 | 只读日志 |

密钥要支持轮换、撤销和过期。

日志中不要写入原始密钥，也不要为了排查问题把完整敏感文档复制到普通日志。

## 十三、权限测试至少覆盖四种情况

不要只用管理员账号测试。

至少准备：

```text
同部门有权限用户。
跨部门无权限用户。
刚离职或已禁用用户。
同时属于多个项目的用户。
```

每种身份都测试查询、引用、上传、审核和下架。

还要测试权限变化后的生效时间：用户被移出部门后，旧会话是否仍能看到原内容？

## 十四、旧系统接入的验收条件

一项接入不应只用“页面能搜到”验收。

建议写清：

```text
同步范围和字段白名单。
同步频率和失败重试。
源数据删除后的处理。
权限变化的传播时间。
接口异常时的降级方式。
审计日志保留字段。
```

如果源系统没有稳定接口，应把“暂不接入”作为合格结论，而不是把模拟抓取当成默认方案。

## 十五、需求边界要写进 SOW

工作范围说明中至少写明：

```text
接入哪些系统。
每个系统由谁提供接口和测试账号。
交付方只读还是允许写入。
数据清洗由谁负责。
权限规则由谁确认。
旧系统无接口时如何处理。
新增系统怎样走变更流程。
```

这份说明不是为了增加文档，而是为了避免“接入所有系统”被理解成无限范围。

## 十六、常见失败方式

### 失败一：把提示词当权限系统

提示词可以约束行为，但不能替代数据过滤和身份校验。

### 失败二：全量同步再想办法隐藏

进入索引的数据越多，误检索和泄露面越大。

### 失败三：用管理员账号跑所有任务

这样测不出普通用户真正能看到什么。

### 失败四：无接口系统强行抓取

短期可能演示成功，长期缺少稳定契约和责任边界。

## 十七、结论

企业知识库的权限设计，核心不是多做几个角色，而是把身份、资源、动作和审核状态拆开。

检索应在可见范围内进行，模型不能成为最后一道保密闸门。

旧系统接入前必须确认接口、字段、认证和删除策略；没有稳定接口时，明确暂不接入往往比强行改造更容易验收。

私有化部署也要先验证模型能否满足固定业务问题，再讨论硬件和并发。

当这些边界写进工作范围、权限矩阵和测试用例，知识库才有机会从演示系统变成可持续维护的业务系统。
