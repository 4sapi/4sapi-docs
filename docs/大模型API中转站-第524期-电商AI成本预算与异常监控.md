# 电商 AI 成本怎么算：Token、重试和人工返工要放在一张账里

很多人第一次接入 AI，只看模型单价。

但电商系统的真实成本通常还包括输入上下文、输出内容、缓存命中、工具调用、失败重试、人工审核和返工时间。

模型单价只是账单的一部分。

如果一个便宜模型经常出错，最后需要人工重做，单次调用便宜也不代表任务成本低。

## 一、先定义任务级成本

可以先用这条公式：

```text
任务成本 = 输入成本 + 输出成本 + 缓存成本 + 工具成本 + 重试成本 + 人工修正成本
```

如果任务最终没有通过验收，还要把失败损失记录下来。

对电商来说，更有意义的不是“每天用了多少 Token”，而是：

- 一个合格客户的调研成本；
- 一条有效询盘的 AI 成本；
- 一份合格报价的生成成本；
- 一笔订单的客服和售后成本。

## 二、按项目拆账

至少把这些项目分开：

| 项目 | 典型任务 |
| --- | --- |
| lead-research | 找客户、去重、资料补全 |
| seo-content | 关键词、页面、FAQ 和更新 |
| customer-support | 意图识别、回复草稿、售后分类 |
| quote-assistant | 产品匹配、报价草稿、利润检查 |
| order-ops | 订单、物流、退款和复购分析 |

如果所有项目共用一张账单，只能知道总额，无法判断哪条业务线正在消耗预算。

每次调用都应该带上 `project_id`、`task_id` 和 `run_id`。

## 三、输入和输出分开记录

建议保存：

```text
input_tokens
cached_tokens
output_tokens
tool_calls
duration_ms
retry_count
status
```

输入上下文越长，输入 Token 可能越高。

输出越长，输出成本通常也越高。

客服意图识别可能只需要短输出，客户研究则需要更长的结构化结果，两者不能按平均值估算。

## 四、缓存命中不能靠感觉判断

有些平台支持输入缓存，但缓存是否生效取决于前缀、时间窗、请求参数和提供方规则。

测试时要记录：

- 第一次请求的输入用量；
- 第二次请求的输入用量；
- 缓存命中字段；
- 提示词前缀是否一致；
- 工具定义是否变化；
- 模型和版本是否变化。

第二次请求更快，不等于已经证明缓存命中。

只有账单字段或接口日志明确记录，才能把它算进缓存收益。

## 五、重试成本经常被漏掉

失败重试可能来自：

- 网络超时；
- 接口限流；
- 工具参数错误；
- 结构化输出解析失败；
- 上游返回空结果；
- 人工拒绝后重新生成。

这些问题的责任边界不同。

建议给每次重试增加 `retry_reason`，并限制最大次数。

如果一个任务因为状态没有更新而无限重试，成本会在短时间内失控。

## 六、把人工时间折算进来

AI 生成报价草稿后，如果人工平均需要 8 分钟修改，那么这 8 分钟也是任务成本。

可以记录：

```text
human_review_minutes
human_rework_minutes
approval_status
```

如果模型输出更长，但人工修改更多，就不能只看 Token 价格判断它更便宜。

## 七、成本要和业务结果关联

一个 SEO 任务生成了 100 个页面，不代表带来了 100 个有效询盘。

一个客户调研任务输出了很长报告，也不代表它识别出了合格客户。

建议增加结果字段：

```text
qualified_lead
valid_reply
quote_created
order_won
refund_triggered
```

然后计算：

```text
每个合格线索成本 = 项目总成本 / 合格线索数
每个有效报价成本 = 项目总成本 / 有效报价数
每个成交订单成本 = 项目总成本 / 成交订单数
```

分母为 0 时不要写成 0，要标记为“暂无结果”。

## 八、延迟和错误也要入账

客户发来询盘后，客服系统如果需要等待很久，回复体验会下降。

SEO 批处理如果频繁失败，内容队列会不断积压。

因此至少要看：

- 平均延迟；
- p95 延迟；
- 错误率；
- 超时率；
- 队列积压量；
- 重试次数。

成本正常但延迟上升，同样可能影响成交。

调用量不大但错误率突然升高，也需要立即排查。

## 九、给每个项目设置预算

预算建议分成三层：

```text
日预算：防止循环错误在当天扩大
周预算：观察趋势和季节性波动
月预算：用于经营计划和资源分配
```

超过预算时，可以先提醒，再暂停非关键任务。

高价值报价和客服回复不应因为某个 SEO 项目超预算而全部停止。

项目级预算比全局总预算更容易定位问题。

## 十、异常规则怎么写

可以设置这些初始规则：

| 异常 | 触发条件 | 动作 |
| --- | --- | --- |
| 调用暴增 | 1 小时调用量超过近 7 日均值 | 暂停批处理并提醒 |
| 成本异常 | 单任务成本超过历史 p95 | 转人工复核 |
| 错误上升 | 15 分钟错误率超过阈值 | 检查接口和版本 |
| 延迟上升 | p95 延迟连续超阈值 | 切换备用路径或降速 |
| 重试循环 | 同一任务重试达到上限 | 标记失败并停止 |
| 结果下降 | 有效字段完整率持续降低 | 回滚提示词版本 |

阈值需要用自己的历史数据校准。

不要直接照抄别人的数字。

## 十一、查账时按顺序排查

成本突然上升时，依次检查：

1. 请求量是否增加；
2. 输入上下文是否变长；
3. 缓存是否失效；
4. 重试次数是否增加；
5. 路由是否切换到更高成本模型；
6. 人工返工是否变多；
7. 是否有重复任务或死循环。

先定位异常项目和时间段，再决定是修复缓存、限制重试还是调整模型。

不要看到总账上涨就直接关闭所有 AI 项目。

## 十二、提示词版本也要计入成本

提示词修改可能改变输出长度、字段完整率和人工修改量。

建议给每个版本绑定：

```text
prompt_version
model
input_tokens
output_tokens
duration_ms
error_rate
business_result
```

如果新版本让报告更长，但有效字段没有增加，说明成本可能只是被放大了。

提示词应该像代码一样可回滚。

## 十三、低风险任务和高价值任务分路由

普通翻译、分类和字段提取，可以使用成本更低的模型或更轻的推理设置。

复杂客户判断、报价分析和高价值回复，需要更强的模型和更严格的人工审核。

路由的依据应该是任务失败成本，而不是模型热度。

任何自动切换都要留下日志，否则出了问题无法追溯到底是哪条路由产生了结果。

## 十四、保留统一日志字段

```text
run_id
project_id
task_id
model
model_version
prompt_version
input_tokens
cached_tokens
output_tokens
tool_calls
retry_count
duration_ms
status
human_review_minutes
business_result
estimated_cost
```

日志要做脱敏，避免把客户隐私、API Key 和完整订单内容直接写入公共报表。

## 十五、结论

电商 AI 成本不能只看每百万 Token 单价。

真正应该核算的是一次有效业务动作花了多少 Token、多少时间、多少重试和多少人工修正。

按项目拆账、按任务记账、给预算设置异常阈值，再把成本和询盘、报价、订单关联起来，才能知道 AI 到底是在创造价值，还是只是在增加账单。
