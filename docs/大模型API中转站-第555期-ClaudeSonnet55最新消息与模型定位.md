# Claude Sonnet 5.5 是什么：中间档的规格、定位与分工

以 **2026 年 10 月 14 日**核验的官方文档为准，Claude Sonnet 5.5 的官方定位是「**速度与智能的最佳组合**」，支持自适应思考与视觉，上下文窗口 1,000,000 tokens，最大输出 128,000 tokens，默认 effort 为 high。[Anthropic 模型概览](https://platform.claude.com/docs/en/about-claude/models/overview)

在一个四档结构里，Sonnet 处在中间：比 Haiku 强，比 Opus 和 Fable 便宜。中间档最容易被误用——要么被当成“便宜版 Opus”什么都让它做，要么被当成“贵版 Haiku”只做简单任务。本文只回答一个问题：**Claude Sonnet 5.5 应该在什么位置，承担哪类任务。**

## 一、官方规格

| 项目 | 内容 |
| --- | --- |
| 定位 | 速度与智能的最佳组合 |
| 思考模式 | 自适应 |
| 默认 effort | high |
| 上下文窗口 | 1,000,000 tokens |
| 最大输出 | 128,000 tokens |
| 可靠知识截止 | 2026 年 6 月 |
| 训练数据截止 | 2026 年 6 月 |
| 退役时间 | 不早于 2027 年 9 月 28 日 |
| 输入 | 文本、图像 |
| 输出 | 文本 |

两个细节值得注意：**默认 effort 是 high**（比 Haiku 的 medium 更高），说明官方默认把更多推理预算给到这一档；**退役时间不早于 2027 年 9 月**，便于做版本规划。

## 二、平台标识

| 平台 | 标识 |
| --- | --- |
| Claude API | `claude-sonnet-5-5` |
| Amazon Bedrock | `anthropic.claude-sonnet-5-5` |
| Google Cloud | `claude-sonnet-5-5` |
| Microsoft Foundry | `claude-sonnet-5-5` |

跨云部署时注意 Bedrock 需要 `anthropic.` 前缀。

## 三、放进四档阵容里比较

官方的四档结构与价格：

| 模型 | 输入 | 输出 | 思考模式 | 默认 effort | 定位 |
| --- | --- | --- | --- | --- | --- |
| Claude Fable 5.1 | $10 | $50 | 自适应（常开） | high | 高难度推理与长时程代理 |
| Claude Opus 5.5 | $4 | $20 | 自适应（常开） | medium | 长时程代理编码与知识工作 |
| Claude Sonnet 5.5 | $2 | $10 | 自适应 | high | 速度与智能的平衡 |
| Claude Haiku 5.5 | 0.10 起 | 0.50 起 | 自适应 | medium | 高并发、延迟敏感 |

三个观察：

1. **Sonnet 的输入价是 Haiku 的二十倍，是 Opus 的一半**。
2. **它的默认 effort 反而是四档里较高的**，说明官方认为这一档的典型任务需要较多推理。
3. **官方选型建议**：不确定时从 Opus 5.5 开始；需要更强推理或长时程代理、且在 Opus 上提高 effort 后仍不达标时，用 Fable 5.1。

## 四、中间档覆盖的任务区间

Sonnet 5.5 承接的是那些“用轻量档做不好、用前沿档又太贵”的任务：

- **编码与代码审查**：跨文件修改、解释代码、写测试。
- **分析与梳理**：读多份材料后给出结构化结论。
- **中等复杂度推理**：需要几步推断，但不需要极长链条。
- **写作**：技术文档、说明、报告。
- **代理工作流的主力步骤**：既需要判断，又要求成本可控。
- **工具调用编排**：多步工具调用，规模适中。

共同点是：**任务需要真正的理解与判断，但不至于难到必须动用前沿档。**

## 五、什么时候不该用它

- **高频简单任务**：分类、抽取这类应下沉到 Haiku，单位成本差一个数量级。
- **极复杂的长任务**：需要长链条推理或复杂编排时应交给 Opus / Fable。
- **短问答**：一句话的问题，中间档也是浪费。
- **严格确定性计算**：优先用代码。

判断标准：**任务的难度是否落在“中间”。**

## 六、和 Haiku、Opus 的分工条件

用两个问题来判断：

**问题一：出错的代价有多大？**

- 代价低、可兜底、量大 → Haiku。
- 代价中等、需要判断 → Sonnet。
- 代价高、链条长 → Opus / Fable。

**问题二：任务需要“想清楚”吗？**

- 依据基本都在输入里 → Haiku。
- 需要一定的推理链 → Sonnet。
- 需要长链条推理与反复修正 → Opus / Fable。

真实项目里更常见的做法是**混用**：Sonnet 做主力，Haiku 分担量大简单部分，Opus 处理少数困难样本。

## 七、默认 effort 是 high 意味着什么

官方把 Sonnet 5.5 的默认 effort 设为 high，这一点在成本核算上很重要：

- 同一段输入，在这一档上默认会做更多推理。
- 如果任务其实很简单，可以评估下调 effort 是否够用。
- 反之，如果任务偏难，可以考虑上浮到 Opus 而不是在这一档硬撑。

**effort 是一个容易被忽略的成本旋钮。** 很多人只比较模型单价，却忘了同一模型在不同 effort 下的成本与延迟差别也很大。

## 八、验证与限制

要判断该把哪些任务放在 Sonnet 上，建议：

1. 从现有任务里按难度分成三组。
2. 每组分别用 Haiku、Sonnet、Opus 各跑一遍。
3. 比较正确率、延迟和成本。
4. 找出“Sonnet 已经够好”的任务，把它们从 Opus 迁下来。
5. 找出“Haiku 已经够好”的任务，把它们从 Sonnet 迁下去。

需要明确的限制：

- 价格、粗略规格与退役时间以 2026 年 10 月 14 日官方文档为准，属于可变事实。
- 四档划分是**按定价与官方定位做的工程推断**，不是官方性能结论。
- 跨平台价格可能不同，需分别核对。
- 实际质量需用自己的样本验证。

## 九、常见误解

- **“中间档样样都不行”**：它覆盖的正是最常用的任务区间。
- **“统一用一个模型最省事”**：错配档位的成本浪费通常大于管理成本。
- **“换便宜档一定省钱”**：判断密集的任务换档后，重试与人工成本会吃掉节省。
- **“effort 不影响成本”**：它直接影响推理量与账单。

## 十、按任务分级的实操模板

把“分级”落成配置，比靠记忆判断更可靠：

```yaml
tasks:
  classify_ticket:     {tier: light, reason: "答案空间有限，量大可兜底"}
  extract_invoice:     {tier: light, reason: "字段固定，失败可转人工"}
  review_pull_request: {tier: mid,   reason: "需要跨文件理解与判断"}
  write_design_doc:    {tier: mid,   reason: "需要结构化的组织与表达"}
  plan_migration:      {tier: heavy, reason: "长链条推理，误判代价高"}
```

三个好处：可审计（每个任务为什么用这一档写在文件里）、可调整（改档位不改代码）、可度量（按档位统计成本与质量）。

## 十一、跨厂商对照的思路

不要只在同一家族内比较。以当前主流厂商的中间档为例，价格与定位大致落在同一区间：

| 厂商 | 中间档 | 输入 | 输出 |
| --- | --- | --- | --- |
| Anthropic | Claude Sonnet 5.5 | $2 | $10 |
| OpenAI | GPT-6 Sol / GPT-6.1 Sol | $2 | $10 |
| Google | Gemini 4 Argon 之下的中间档 | 以官方定价页为准 | 以官方定价页为准 |

价格接近时，选择依据通常是：

- **工具与生态**：你的现有系统对哪家的接口更熟。
- **长上下文表现**：在你自己材料上的稳定性。
- **缓存与批处理**：折扣渠道是否满足需求。
- **合规与部署**：数据驻留、可用区域。

**不要只看单价。** 同一价位下，能否吃到缓存、是否支持批处理，对最终账单的影响远大于零点几美元的单价差。

## 十二、三种“看起来适合 Sonnet 其实不适合”的任务

1. **批量短判定**：看起来是“中等价值”，但答案空间有限、量大，实际该下沉到 Haiku。
2. **长篇一次性生成**：看起来需要“智能”，但更考验结构与一致性，用旗舰档反而更容易一次写对。
3. **需要逐条核对的高合规任务**：看起来是“中等难度”，但误判代价高，应上浮到更高档并配人工。

识别的关键是问一句：**这类任务真正的瓶颈是“判断力”还是“成本”还是“规模”？** 只有判断力在中间区间的任务才属于 Sonnet。

## 十三、上线前的检查清单

1. 任务难度确实落在中间档。
2. 有可用于对照的样本与指标。
3. 稳定前缀已整理，能吃到缓存价。
4. effort 档位经过验证，不是照抄默认。
5. 有回滚方案。
6. 日志包含模型标识、effort 与用量字段。
7. 跨平台价格与配额已核对。

## 十四、把“档位”当配置而不是当代码

最后一条工程建议：**不要让模型名散落在业务代码里**。把档位定义在配置中：

```yaml
light:  claude-haiku-5-5
mid:    claude-sonnet-5-5
heavy:  claude-opus-5-5
frontier: claude-fable-5-1
```

业务代码只引用 `mid` 这样的档位名。这样换模型、调档位、做 A/B 都只改配置，不用改业务逻辑，也不会出现“某个函数里硬编码了旧模型”的情况。
## 限制与结论

Claude Sonnet 5.5 是四档阵容里的中间档，官方定位为速度与智能的平衡，默认 effort 为 high，价格是 Haiku 的二十倍、Opus 的一半。它适合承接“轻量档做不好、前沿档太贵”的任务，比如编码、分析、中等推理和写作。

落地建议是先把现有任务分档，再用样本做对照，把错配的任务迁到正确档位，并把 effort 当作成本旋钮一起评估。价格、标识与退役时间请在上线前回到官方页面重新核对。
