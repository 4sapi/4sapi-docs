# WorkBuddy 文件技能实战：Excel、Word、PDF、PPT 怎么交付

让 Agent “处理文件”听上去像一个动作，实际至少包含四件事：读对文件、理解字段或结构、生成正确的交付物、确认没有损坏原始资料。前两件做不好，后面的排版再漂亮也没有价值。

用户提供的 WorkBuddy Skills 素材把 `xlsx`、`docx`、`pdf` 和 `pptx` 列为高频能力。它们确实覆盖了办公中最常见的文件类型，但不要把技能当作一键交付的承诺。不同文件的风险点不同：表格容易错在口径，Word 容易错在模板和条款，PDF 容易错在扫描与分页，PPT 容易错在逻辑和受众。

这篇按文件类型给出一套可复用的处理方法。文中的目录、提示词和验收方式同样可迁移到其他 Agent 工具；具体技能名称、界面入口和可用功能应以当前 WorkBuddy 版本为准。

## 一、开始前，先把原始文件与交付物分开

不论要处理哪种文件，先准备一个独立工作区：

```text
file-task/
  source/       原始文件，只读保存
  working/      提取结果、预览和中间稿
  output/       等待人工审核的交付物
  review/       审阅意见、问题清单和最终版本说明
```

这不是形式主义。只要 `source/` 和 `output/` 混在一起，一次批量改名、格式化或错误保存就可能覆盖原件。对于多个版本的文件，在文件名中标记日期或版本，并要求 Agent 在处理前先列出它识别到的文件清单。

一个通用的开场任务可以这样写：

```text
请只读取 source/ 中的文件，先不要修改、移动或生成最终交付物。

请输出：
1. 文件清单、格式、修改日期和疑似版本关系；
2. 每份文件可提取的关键信息；
3. 字段、单位、页数、模板或格式异常；
4. 需要我确认的文件与问题。
```

先得到这张清单，再决定由哪项技能处理。它能防止 Agent 选错版本，也能让你提前发现扫描版 PDF、加密文件、隐藏 Sheet、失效链接等问题。

## 二、Excel：先确认数据口径，再让它汇总和画图

`xlsx` 技能的价值，不只是“能做表格”，而是能把数据清洗、公式、Sheet、图表和异常记录放进同一条流程。最常见的失败不是公式报错，而是口径没说清：销售额是否含税、日期以订单日还是付款日为准、客户名称是否允许模糊合并、空值是未知还是零。

### 2.1 先做表结构盘点

```text
请读取 source/ 中的 Excel，但不要修改原文件。

对每个 Sheet 输出：
- Sheet 名称、行列数和表头；
- 日期、金额、数量等字段的格式与单位；
- 缺失值、重复值和异常值；
- 可能需要确认的统计口径。
```

这一步完成后再下汇总任务。不要直接说“按地区做销售分析”，因为“销售”这个词在不同表里可能指订单额、已付款金额、含税收入或预测值。

### 2.2 让处理过程可复核

下面的提示词适合多表合并任务：

```text
请处理 source/ 中的销售表。

目标：按地区和月份汇总已付款销售额，并生成柱状图。
口径：以付款日期统计；金额按表内币种，不跨币种相加；空金额标为待确认，不视为 0。
步骤：
1. 先输出字段映射和合并预览；
2. 生成 working/cleaned-data.xlsx 和 working/anomalies.xlsx；
3. 经我确认后再生成 output/sales-summary.xlsx；
4. 在报告中说明统计范围、排除项和异常数。
```

验收时至少检查四件事：总行数是否对应、合并前后金额是否合理、异常项是否单独列出、图表标题和单位是否准确。图表不是结论本身，它只是帮助人发现趋势的视图。

## 三、Word：先定内容结构和模板，再生成可编辑文档

Word 文档常被误解为“把文字导出成 `.docx`”。真正容易出问题的是标题层级、页眉页脚、条款编号、目录、字体、页边距以及模板里的占位符。尤其是合同、通知、方案和正式报告，文本本身正确不代表格式可交付。

处理 Word 时，先提供一份明确的结构和模板规则：

```text
目标：根据 source/ 中的项目材料生成方案初稿。
读者：业务负责人。
输出：可编辑的 Word 文档，保存到 output/。
结构：封面、摘要、背景、方案、实施计划、风险、附录。
格式：使用提供的模板；保留已有页眉页脚和样式；不改动模板中未授权的品牌元素。
事实规则：数字、日期和项目状态必须来自 source/；缺失内容标为待确认。
```

如果是合同、制度、通知等有法律或合规含义的文件，Agent 可以帮助整理、套版和发现缺项，但不应替代专业审核。特别是“标准劳动合同模板”这类任务，格式完整不代表条款适用于当地法律、行业或双方约定。

### 3.1 Word 文件的交付检查

```text
[ ] 标题层级与目录是否能正常更新。
[ ] 页眉、页脚、页码和版式是否继承了正确模板。
[ ] 占位符、批注和内部备注是否已处理。
[ ] 表格是否跨页错位，长段是否出现截断。
[ ] 事实、条款和日期是否由相应负责人核对。
[ ] 最终文件是否仍可在目标办公软件中编辑。
```

需要强调的是，先生成 Markdown 大纲再生成 Word 往往更可靠。先确认结构、内容和待确认项，再把通过的文字放进模板，能减少每次改文案都重新破坏版式的概率。

## 四、PDF：把“读得到”与“读对了”分开

PDF 的难点不在文件后缀，而在来源。原生文本 PDF 通常可以按章节与页码提取；扫描件需要 OCR；双栏排版、表格、图片、页眉脚注又会影响阅读顺序；加密或受限文件则需要先确认是否有合法访问权限。

因此，读 PDF 的第一轮任务不应该是“总结这份报告”，而是验证解析质量：

```text
请读取 source/ 中的 PDF，并先输出解析检查报告：
1. 文件页数、是否为扫描件、是否存在无法读取页面；
2. 目录和章节结构；
3. 图表、表格与脚注的提取情况；
4. 可疑乱码、缺页、阅读顺序异常或需要人工查看的位置。

不要先给结论，也不要根据无法读取的页面补写内容。
```

只有解析检查过关，才进入摘要、对比和引用。长报告的摘要最好按读者和问题组织，而不是简单压缩全文。例如行业报告可以提取市场规模、竞争格局、增长因素、限制条件和原始页码；合同可以提取主体、期限、费用、责任、终止条件和待专业人士核对的条款。

### 4.1 PDF 的来源标注

对于会进入报告、方案或决策材料的关键结论，建议保留页码和短引用：

| 结论 | 来源 | 位置 | 状态 |
| --- | --- | --- | --- |
| 某项市场数据 | 报告文件名 | 第 X 页图表 | 待人工核对单位 |
| 合同交付期限 | 合同文件名 | 第 X 条 | 待业务确认 |

这样做不是为了让所有材料都写满脚注，而是为了让关键判断能回到原件。PDF 摘要最危险的情况，是文字读起来顺、数字看着合理，但页码、时间区间或图表单位已经错位。

## 五、PPT：先验收故事线，最后才是版式

用户提供的素材强调 `pptx` 可以生成可编辑演示文稿。这确实能减少从空白页开始的工作，但绝大多数糟糕的 PPT 问题并不出在动画或配色，而在“每一页要让谁理解什么”没有定下来。

先让 Agent 输出逐页大纲：

```text
根据 source/ 中的产品材料，设计一份 10 页以内的汇报大纲。

受众：业务负责人。
每页必须给出：
- 标题（一个完整观点，不是话题）；
- 支持该观点的证据或图表；
- 演讲者备注；
- 本页需要确认的事实。

先不要生成最终 PPT。
```

标题写成“市场机会”时，读者看不到结论；写成“目标行业的需求主要集中在三类重复流程”时，读者知道这页要表达什么。大纲确认后，再让技能生成可编辑的 `.pptx`，并将数据表、图表和引用来源一起交付。

### 5.1 演示文稿的四轮验收

```text
逻辑：页面顺序能否支撑一次完整的沟通。
事实：数字、图表、时间和来源是否准确。
视觉：字体、留白、对齐、对比度和图表标签是否可读。
演示：在实际屏幕上播放后，是否有截断、溢出或不必要的动画。
```

如果需要套用公司模板，先验证封面、母版、字号和图表样式是否保留。不要只看编辑器里的缩略图；导出 PDF 或实际放映一次，才知道文字是否被裁切。

## 六、把四类文件串成一次真实交付

假设你要完成一次月度经营汇报，输入包括 PDF 行业报告、Excel 销售数据、Word 项目材料，输出是正式报告与 PPT。可以按这个顺序运行：

```text
1. 清点所有输入文件、版本、字段和权限。
2. 解析 PDF，得到可引用的事实与页码。
3. 清洗 Excel，确认统计口径并生成数据与异常表。
4. 根据已核对的事实写 Markdown 大纲或 Word 草稿。
5. 审阅内容、数字、风险与待确认项。
6. 以确认后的大纲生成 PPT，并检查模板和播放效果。
7. 将最终交付物、来源映射和审阅记录一起保存。
```

顺序不能颠倒。先做 PPT 再找数据，很容易得到一套好看但无法支撑的叙事；先让 Agent 写最终报告再检查 PDF 解析，也会把错误带进每一个后续文件。

## 七、文件任务的边界清单

```text
[ ] 原始文件、处理中间件和最终输出位于不同目录。
[ ] 每份输入文件的版本、来源和读取范围已确认。
[ ] 表格统计口径、单位和异常规则已经写清。
[ ] Word 模板、保留样式和不可改动内容已经说明。
[ ] PDF 已先经过解析质量检查，再用于提取事实。
[ ] PPT 已先验收逐页观点，再生成最终页面。
[ ] 关键数字和判断能回到文件、页码或字段。
[ ] 原始文件没有被覆盖、删除或改名。
[ ] 输出文件在目标软件中可打开、可编辑、无截断。
[ ] 涉及合同、财务、客户或敏感资料时，已按组织规则处理。
```

## 八、四类文件各自最常见的失败方式

文件处理的错误往往不在最后一步才出现。下面这张表可以作为排查起点：

| 文件类型 | 常见现象 | 先检查什么 | 合理处理 |
| --- | --- | --- | --- |
| Excel | 汇总数看似正确但总额对不上 | 统计口径、重复行、筛选条件、单位 | 保留原始行，输出对账表和异常行 |
| Word | 内容完整但打开后格式错乱 | 模板版本、样式、分页与字体 | 先验证模板，再生成可编辑初稿 |
| PDF | 摘要顺畅但漏掉关键条款或图表 | 扫描质量、页码、双栏阅读顺序 | 做解析检查，关键结论回到原页核对 |
| PPT | 版式很好但汇报讲不下去 | 每页核心观点、数据来源、受众 | 先评审大纲和叙事，再处理视觉 |

有一个共同规律：不要让 Agent 在信息不完整时默默补齐。金额缺失、模板无效、PDF 无法识别、图表没有来源，都应该变成可见的问题清单。所谓“智能”不应该表现为把未知藏起来，而应该表现为知道何时停止并请求确认。

## 九、文件任务也需要一份变更清单

代码任务有 `git diff`，文件任务同样需要一个能让人快速核对的变更说明。每次生成 Word、PPT 或清洗后的 Excel，可以要求 Agent 在 `review/` 中输出一份记录：

```text
输入文件：文件名、版本、读取范围。
输出文件：路径、格式与生成时间。
处理动作：合并了哪些 Sheet、替换了哪些字段、套用了哪份模板。
未处理项：无法读取的页面、缺失字段、冲突数据。
人工确认项：需要资料 Owner、财务、法务或项目负责人核对的内容。
```

这份清单会把“生成了一个附件”变成一项可审阅的工作。尤其在多人协作时，审阅人不必从头猜 Agent 做过什么，可以直接检查差异和待确认项。

对于不能可靠比较二进制文件的场景，还可以保存一份结构化中间产物，例如 Excel 的字段映射、Word 的 Markdown 初稿、PPT 的逐页大纲、PDF 的引用页码表。中间产物不是额外负担，它们是最终文件出问题时最容易定位的证据。

## 十、先用小样本验证，再扩大到全量文件

批量文件任务最忌讳“先跑完整目录，出错再说”。更安全的试用节奏是：

```text
第一轮：用 2 到 3 个脱敏样例验证读取、输出格式和保存路径。
第二轮：故意加入一个重复记录、缺失字段或异常版式，检查是否能标记。
第三轮：用一小批真实但可恢复的文件运行，人工逐项对照。
第四轮：确认后再扩大到完整数据集，并保留本轮输入清单。
```

如果是历史资料迁移或大量发票、合同、PPT 的批处理，应该额外保留抽样复核比例和失败队列。无法识别的文件不要悄悄跳过，也不要强行转换后混入结果；放入失败队列、记录原因，再决定由人处理还是调整规则重跑。

## 十一、不同角色怎么验收同一份文件

同一个交付物，关注点并不一样。把复核责任拆开，能减少“所有人都以为别人看过”的情况：

| 角色 | 主要检查内容 |
| --- | --- |
| 资料提供者 | 输入是否齐全，数据、日期和业务事实是否准确 |
| 业务负责人 | 结论、风险、优先级和行动项是否可用于决策 |
| 专业负责人 | 财务、法务、技术或合规描述是否符合专业要求 |
| 发布或交付人 | 格式、模板、受众、敏感内容和交付路径是否正确 |

Agent 可以把这些检查项列出来，不能替代有责任的人签字确认。涉及合同、税务、医疗、投资或人事信息时，尤其要保留专业复核和组织规定的审批过程。

## 十二、结论

文件技能真正节省的不是几次复制粘贴，而是把资料清点、结构化处理、格式生成和人工验收串成稳定流程。`xlsx`、`docx`、`pdf`、`pptx` 各有擅长的边界，混在一起做时更需要先确定口径、版本和交付顺序。

让 Agent 先读取、再预览、后生成；让人先核事实、再核结构、最后核格式。守住这条顺序，文件处理才会从“生成一个看似完整的附件”变成真正可交付的工作。
