# 【大模型API中转站】第146期 Agent入门 | Workflow、ReAct和4SAPI

本文是【大模型API中转站】系列的第146篇。本系列致力于用最低的成本、最清晰的方法，帮你打通多模型API的任督二脉。建议先收藏，随用随查。

这一篇开始，我们把 Agent 这件事拆成几篇来讲。

先说结论：

```text
Agent 不是“模型更聪明”。
Agent 是“模型外面多了一套任务系统”。
```

很多人第一次接触 Agent，会把它理解成：

```text
给大模型一个目标。
让它自己想。
让它自己调工具。
让它自己交付结果。
```

听起来很爽。

但生产里真正的问题不是“它会不会想”，而是：

```text
它每一步调了什么模型？
用了哪个 Key？
花了多少钱？
调了哪个工具？
失败以后重试了几次？
最后为什么停下来？
日志能不能回放？
出了问题谁负责？
```

这些问题回答不上来，Agent 就不是生产力系统，而是一个会自动烧 Token 的黑盒。

所以这篇不讲玄学，也不讲“通用智能体马上替代一切”。

我们只讲一件事：

```text
一个能落地的 Agent，到底比普通聊天多了哪几层工程。
```

## 1. Agent 和聊天机器人的区别

普通聊天模型的链路很短：

```text
用户提问
  -> 模型回答
  -> 用户判断
```

Agent 的链路会变长：

```text
任务目标
  -> 生成计划
  -> 调用工具
  -> 读取结果
  -> 更新状态
  -> 决定下一步
  -> 验证结果
  -> 判断是否停止
```

这就带来一个本质变化：

```text
聊天模型主要产出文本。
Agent 主要执行任务。
```

文本回答错了，你可以追问一句。

任务执行错了，可能已经改了代码、发了请求、写了数据库、消耗了预算，甚至触发了外部流程。

所以企业落地 Agent 时，第一步不是选最强模型，而是把调用边界画清楚。

你至少要知道：

| 问题 | 为什么重要 |
| --- | --- |
| 谁触发了任务 | 方便追责和复盘 |
| 任务属于哪个项目 | 方便成本归因 |
| 每一步用了哪个模型 | 方便做模型路由和横评 |
| 工具权限有多大 | 防止越权操作 |
| 失败后怎么处理 | 防止无限重试 |
| 何时停止 | 防止长任务烧钱 |

这也是为什么 4SAPI 这类大模型 API 中转站，在 Agent 场景里比普通聊天场景更重要。

聊天工具只要能回答就行。

Agent 工具还要能被管理。

## 2. Workflow 和 Agent 不是一回事

很多团队第一步就走偏，是因为把 Workflow 和 Agent 混在一起。

Workflow 是固定流程。

Agent 是动态决策。

可以这样理解：

| 类型 | 特点 | 适合场景 |
| --- | --- | --- |
| Workflow | 步骤提前写死，模型只负责每一步里的子任务 | 客服分类、内容审核、表格清洗、固定报表 |
| Agent | 模型根据中间结果决定下一步 | 代码修复、复杂调研、长文资料整理、多工具排错 |

举个例子。

如果你要做一个客服工单分类系统，流程通常很固定：

```text
读取工单
  -> 判断类型
  -> 判断紧急程度
  -> 分配给对应队列
  -> 生成回复建议
```

这更适合 Workflow。

没必要让模型自由决定下一步。

但如果你让 AI 帮你排查一个线上 bug，它可能需要：

```text
先读日志。
再查最近发布。
再看配置。
再搜索报错。
再写一个复现脚本。
再判断是不是依赖版本问题。
```

这时下一步取决于上一步结果，就更像 Agent。

我的建议很简单：

```text
能用 Workflow 解决的，先不要上 Agent。
```

不是 Agent 不高级。

而是生产系统里，自由度越高，排查成本越高。

企业做大模型接入，优先级应该是：

```text
稳定
  -> 可观测
  -> 可控成本
  -> 再谈自主性
```

## 3. ReAct：Agent 最常见的执行循环

很多 Agent 底层都会跑一个类似 ReAct 的循环。

不要被名字吓到，它的意思很简单：

```text
Reason：判断当前要做什么
Act：调用工具或执行动作
Observe：读取工具返回结果
Repeat：继续下一轮
```

换成工程流程就是：

```text
模型看到任务
  -> 选择一个动作
  -> 系统执行动作
  -> 动作返回结果
  -> 模型根据结果继续判断
```

比如一个代码修复 Agent：

```text
任务：修复登录页报错

第1轮：
模型决定读取错误日志
工具返回 stack trace

第2轮：
模型决定搜索相关文件
工具返回 LoginForm.tsx 和 auth.ts

第3轮：
模型决定修改代码
工具返回 diff

第4轮：
模型决定运行测试
工具返回失败信息

第5轮：
模型继续修复
工具返回测试通过

第6轮：
模型总结结果并停止
```

这套结构的价值，是模型不需要一口气猜完整方案。

它可以边看结果边调整。

但危险也在这里：

```text
每多一轮，就多一次出错机会。
每多一次工具调用，就多一次权限和成本风险。
```

所以 ReAct 不是“让模型自由跑”。

真正生产可用的 ReAct，一定要加上：

- 最大轮数。
- 每轮预算。
- 可用工具清单。
- 禁止操作清单。
- 失败重试次数。
- 人工确认节点。
- 完整调用日志。

少了这些限制，Agent 很容易从“自动执行”变成“自动跑偏”。

## 4. Tool Use：让模型从会说变成会做

大模型本身只会生成文本。

它不会真的查数据库。

不会真的跑代码。

不会真的打开浏览器。

不会真的发邮件。

Tool Use 的作用，就是给模型接上外部工具。

常见工具可以分成几类：

| 工具类型 | 典型用途 | 风险点 |
| --- | --- | --- |
| 搜索工具 | 查实时资料、查文档、查错误信息 | 资料质量不稳定 |
| 文件系统 | 读写代码、整理文档、搜索项目 | 误改文件 |
| 代码执行 | 跑测试、算数据、验证结果 | 沙箱隔离 |
| 数据库 | 查询业务数据、写入任务状态 | 权限和脱敏 |
| 浏览器 | 点页面、填表单、抓取信息 | 页面变化和提示注入 |
| 外部 API | 调 CRM、工单、日历、IM | 越权和误触发 |

工具越多，Agent 看起来越强。

但工具越多，工程风险也越高。

一个健康的设计不是把所有工具都塞给模型，而是按任务分配最小工具集：

```text
写代码 Agent：文件系统 + Git + 测试命令。
客服 Agent：知识库检索 + 工单系统 + 回复草稿。
运营 Agent：表格读取 + 内容生成 + 审核队列。
财务 Agent：只读报表 + 摘要生成，不给写权限。
```

能只读，就不要写。

能先生成草稿，就不要直接发送。

能人工确认，就不要自动提交。

这是 Agent 落地的基本安全感。

## 5. 4SAPI 中转站在 Agent 链路里的位置

很多人把 4SAPI 理解成“换个地址调用模型”。

在普通聊天里，这个理解勉强够用。

但在 Agent 里，4SAPI 更像模型调用的控制层。

一条完整链路可以这样看：

```text
Agent 应用 / 工作流平台 / 本地工具
        ↓
4SAPI 中转站：Key、模型路由、日志、额度、成本
        ↓
Claude / GPT / Gemini / DeepSeek / Qwen / Kimi 等模型
        ↓
工具层：搜索、文件、数据库、MCP、浏览器
```

注意这里的分工。

工具层负责“做事”。

模型负责“判断下一步”。

4SAPI 负责“管模型调用”。

它主要解决这些问题：

| Agent 问题 | 4SAPI 侧的治理方式 |
| --- | --- |
| 多个工具到处填 Key | 统一入口，Key 分组管理 |
| 不知道哪个任务花钱 | 调用日志和项目维度归因 |
| 强模型被滥用 | 模型路由和额度限制 |
| 失败重试烧钱 | 预算、限流和告警 |
| 团队共用一个 Key | 按项目、环境、成员拆分 |
| 生产和测试混在一起 | dev、staging、prod 分离 |

Agent 越自动化，越需要这层网关。

否则你看到的只是“AI 在干活”，看不到它背后的调用账单。

## 6. 最小接入方式：先统一 Base URL 和 Key

如果你的 Agent 框架支持 OpenAI Compatible 接口，通常先从三项配置开始：

```text
Base URL: https://4sapi.com/v1
API Key: 4SAPI 控制台创建的令牌
Model: 4SAPI 模型广场里的模型名称
```

环境变量可以这样组织：

```text
OPENAI_BASE_URL=https://4sapi.com/v1
OPENAI_API_KEY=你的4SAPI令牌
AGENT_MODEL=你要使用的模型名称
```

如果是团队使用，我建议至少拆三类 Key：

| Key | 用途 | 额度建议 |
| --- | --- | --- |
| `agent-dev` | 本地测试、提示词调试 | 小额度，方便试错 |
| `agent-staging` | 预发环境、定时任务演练 | 中额度，接近生产 |
| `agent-prod` | 生产任务 | 单独预算和告警 |

不要把一个生产 Key 同时塞进：

```text
本地脚本
桌面客户端
n8n 工作流
线上服务
团队共享文档
```

这会让日志归因变得很难。

一旦成本异常，你不知道到底是哪个入口在烧钱。

## 7. 企业落地时，先做“窄 Agent”

Agent 最容易失败的地方，是一上来就想做通用。

比如：

```text
帮我处理公司所有运营问题。
帮我自动维护整个代码库。
帮我做一个万能客服。
帮我每天自动优化业务。
```

这些目标太大。

更靠谱的做法，是先做窄场景：

```text
只处理 GitHub Issue 的重复问题归类。
只给 PR 做第一轮风险摘要。
只把客服对话整理成知识库候选条目。
只把日报里的异常指标生成排查建议。
只在测试失败后读取日志并给出修复方向。
```

窄 Agent 有三个好处：

```text
工具少。
权限小。
验收标准清楚。
```

只有窄场景跑稳了，再往外扩。

这也是为什么我更建议企业先从 Workflow 开始，再逐步增加 Agent 能力。

## 8. 上线前检查清单

一个 Agent 真要接到生产，至少过这张清单。

| 检查项 | 合格标准 |
| --- | --- |
| 任务边界 | 能一句话说清它负责什么、不负责什么 |
| 模型入口 | 所有模型调用统一走 4SAPI 或同类网关 |
| Key 管理 | 按项目、环境、用途拆分 |
| 工具权限 | 默认最小权限，危险操作需要确认 |
| 最大轮数 | 每个任务有明确循环上限 |
| 成本上限 | 每个任务或每天有预算阀门 |
| 日志审计 | 能回放每一步模型调用和工具调用 |
| 失败策略 | 知道失败后重试、降级还是转人工 |
| 停止条件 | 知道什么时候算完成，什么时候放弃 |

这里面最容易被忽视的是停止条件。

很多 Agent 不是不会开始，而是不知道什么时候该停。

它会继续搜索、继续改、继续总结、继续重试。

在聊天窗口里，这只是烦。

在 API 账单里，这就是成本。

## 9. 总结

这一篇可以记住三句话。

第一句：

```text
Agent = 模型 + 工具 + 状态 + 决策 + 验证 + 停止。
```

第二句：

```text
能用 Workflow 解决的，先不要急着上 Agent。
```

第三句：

```text
Agent 一旦自动调用模型，就应该把模型入口统一收进 4SAPI 这类中转站。
```

因为真正难的不是让模型回答一句话。

而是让它在多步任务里：

```text
少跑偏。
可追踪。
可控费。
可审计。
可停止。
```

下一篇继续往下拆：MCP、Context Engineering 和 Harness。

也就是 Agent 外面那层真正决定可用性的工程壳。
