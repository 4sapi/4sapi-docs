# 知识工作插件的三层清单：17 个目录、22 个清单与 123 条市场条目

看一个插件仓库，最容易只看它的 README 表格。但表格通常是精选版，真实体量要看文件。

这个仓库是个典型例子：README 说开源了 11 个插件，仓库里有 17 个顶层插件目录（含 22 个插件清单，因为其中一个目录下挂着 5 个第三方插件），而它的市场清单里有 123 条条目。三个数字分别对应"官方推荐"、"官方提供"、"可安装"，混着用就会对覆盖范围产生误判。

本文的统计口径写在这里：以存在 `.claude-plugin/plugin.json` 的目录计为插件，`partner-built` 是容器目录，里面的 5 个插件单独计数。

本文按文件统计把这三层理清，再拆解插件的四类组件与一个关键的占位符机制。信息来自仓库 [README](https://github.com/anthropics/knowledge-work-plugins/blob/HEAD/README.md)、[市场清单](https://github.com/anthropics/knowledge-work-plugins/blob/HEAD/.claude-plugin/marketplace.json)与目录树，检索日期为 2026-11-04。我没有安装或运行过任何插件。

## 一、先把三个数字分开

| 层 | 数量 | 是什么 |
| --- | --- | --- |
| README 表格 | 11 | 官方在首页推荐的插件 |
| 仓库顶层插件目录 | 17 | 以存在 `.claude-plugin/plugin.json` 的顶层目录计 |
| 仓库插件清单 | 22 | 含 `partner-built/` 下的 5 个（apollo、brand-voice、common-room、slack、zoom） |
| 市场清单 | 123 | `.claude-plugin/marketplace.json` 里 plugins 数组的条目，含第三方 |

比这 11 个多出来的顶层目录有 6 个：design、engineering、human-resources、operations、pdf-viewer、small-business；再加上 `partner-built/` 里的 5 个第三方插件，合计 22 个插件清单。

一个可交叉验证的细节：市场清单里指向本仓库的相对路径源正好 22 条，与 22 个清单一一对应。

三个数字的用途不同：

- **11** 是入口，说明官方认为大多数人会从这些开始。
- **17 / 22** 是仓库自带的范围（顶层目录 / 含容器目录里的插件），你想要的角色可能不在 11 个里面，但可能在 22 个里面。
- **123** 是这台"应用商店"的规模，包含第三方（例如通讯、销售、安全扫描、检索等方向的厂商插件）。

第 3 层要特别小心：条目的存在不等于可用。第三方插件的质量、权限与维护状态各不相同，选之前要单独看它的清单与 `.mcp.json`。

## 二、四类组件是什么关系

README 说每个插件打包四类内容。用其中一个插件的目录结构可以对照：

```text
finance/
├── .claude-plugin/plugin.json   # 清单：名称、版本、描述
├── .mcp.json                    # 工具连接：MCP 服务器与地址
├── CONNECTORS.md                # 占位符与类别映射说明
├── README.md
└── skills/                      # 领域知识与工作流
    ├── reconciliation/
    │   └── SKILL.md
    ├── close-management/
    └── ...
```

四类组件的分工：

| 组件 | 触发方式 | 内容形态 |
| --- | --- | --- |
| 技能（skills） | 自动，相关时触发 | SKILL.md 加可选的 references/ 参考文件 |
| 命令（commands） | 显式，输入斜杠命令 | Markdown 文件 |
| 连接器（connectors） | 由 `.mcp.json` 声明 | JSON 配置，指向 MCP 服务器 |
| 子代理（sub-agents） | 由插件声明 | README 提及，我没有逐个核对实现 |

原文强调所有组件都是文件——markdown 与 JSON，没有代码、没有基础设施、没有构建步骤。这句是项目自述，我用目录树核了一下，只部分成立：绝大多数文件确实是 Markdown 与 JSON，但确有插件自带 Python 脚本（生物研究目录下就有质量分析、绘图等脚本，技能正文还直接指示执行），另有少量 HTML 示例。所以"没有代码"应当理解为"不需要构建步骤"，而不是"仓库里没有可执行代码"。连接器指向的外部服务当然也是有代码、要联网的，这一点在下一篇展开。

## 三、技能数量分布很不均

按目录树统计，`SKILL.md` 共 252 个，但分布极不均匀：

| 插件 | 技能数 |
| --- | --- |
| partner-built | 71 |
| small-business | 44 |
| sales | 36 |
| data / engineering | 各 10 |
| human-resources / legal / operations | 各 9 |
| finance / marketing / product-management | 各 8 |
| design | 7 |
| bio-research | 6 |
| customer-support / enterprise-search | 各 5 |
| productivity | 4 |
| cowork-plugin-management | 2 |
| pdf-viewer | 1 |

两点值得注意：

1. **前三名占了约六成。** 71+44+36 = 151，占 252 的 59.9%。也就是说，"技能数量多"这件事主要集中在第三方聚合目录与小企业包，而不是那 11 个推荐插件。
2. **推荐插件的技能密度其实不高。** productivity 只有 4 个技能，finance 8 个，legal 9 个。这说明一个插件的价值不在于技能条数，而在于技能写得够不够具体。

按算术：252 ÷ 22 约 11.5，252 ÷ 17 约 14.8。若扣除 `partner-built`（71 个技能，且是 5 个插件的合计），余下的是 181 个技能；注意 `small-business` 的 plugin.json 里 author 写的是 Anthropic，属第一方，不能扣除。第一方平均约 181 ÷ 17 ≈ 10.6 个每插件。**推荐 ≠ 内容最多**，这是看这类仓库时容易搞反的一点。

另外两个统计：命令文件（`commands/` 下的 `.md`）共 15 个，`.mcp.json` 共 21 个。

命令的分布比总数更值得看：这 15 个命令只落在 3 个插件里（partner-built 10、pdf-viewer 4、product-management 1），finance、sales、legal、data 等一个都没有。而 README 举例的 `/finance:reconciliation`、`/sales:call-prep` 在仓库里找不到对应的命令文件——它们其实是技能（skills 目录下的 `reconciliation`、`call-prep`），通过 frontmatter 的 `user-invocable` 暴露，走的是技能通道而不是命令通道。

这也修正了一个容易得出的错误结论：命令少不等于"大多数能力自动触发"。更准确的说法是，这个仓库用技能承载能力，命令只是少数插件额外提供的快捷方式。

## 四、技能里到底写了什么

拿财务插件的对账技能当样本，`SKILL.md` 的结构是：

| 部分 | 内容 |
| --- | --- |
| frontmatter | name、description、argument-hint（形如 `<account> [period]`） |
| 声明 | 开头写明"协助对账流程，不提供财务建议，签核前须由具备资质的财务专业人士复核" |
| 分类 | 对账类型：总账对明细账、银行对账、公司间对账 |
| 步骤 | 每种类型给出编号流程，例如银行对账要依次取银行对账单余额、取总账现金余额、找未兑现支票、找在途存款 |
| 差异原因 | 列出常见成因：手工凭证未反映到明细账、明细账未过账、批处理时间差等 |
| 表样 | 给出标准对账表格式，两侧调到调整后余额、差额为零 |

这个样本说明"技能"不是提示词模板，而是**把岗位的方法论写成可执行的检查流程**，并附带行业标准的呈现格式。那个免责声明也值得注意：它是写进技能正文的，不是附在仓库说明里。

对读者的含义：评估一个插件对你有没有用，看技能正文比看 README 描述准确得多。正文会暴露它的假设——比如假设你有总账与明细账两套系统。

## 五、一个关键的解耦设计：占位符

这是我认为这套插件里最值得抄的机制。

`CONNECTORS.md` 说明：插件文件里用 `~~category` 作为占位符，代表用户在该类别下连接的任何工具。例如 `~~data warehouse` 可能指 Snowflake、BigQuery 或任何有 MCP 服务器的数据仓库。

所以插件本身是**工具无关**的：它按类别描述流程（数据仓库、聊天、项目跟踪器），而 `.mcp.json` 预配的是具体产品。

`finance` 的映射表长这样：

| 类别 | 占位符 | 内置服务器 | 其他可选 |
| --- | --- | --- | --- |
| 数据仓库 | `~~data warehouse` | Snowflake、Databricks、BigQuery | Redshift、PostgreSQL |
| 邮件 | `~~email` | Microsoft 365 | — |
| 办公套件 | `~~office suite` | Microsoft 365 | — |
| 聊天 | `~~chat` | Slack | Microsoft Teams |
| ERP / 会计 | `~~erp` | 暂无受支持的服务器 | NetSuite、SAP、QuickBooks、Xero |
| 分析 / BI | `~~analytics` | 暂无受支持的服务器 | Tableau、Looker、Power BI |

这个设计的好处很直接：技能文本写一次，换工具只改配置。缺点是它把"接线是否真的通"留给了配置，而配置里藏着一堆空值——下一节说。

## 六、`.mcp.json` 里的真实状态

`finance/.mcp.json` 声明了 6 个服务器，但其中 4 个的地址是空字符串：

| 服务器 | 状态 |
| --- | --- |
| bigquery | 有真实地址 |
| slack | 有真实地址，并带 oauth 配置（含 callbackPort 3118） |
| snowflake / databricks / google calendar / gmail | `url` 为空字符串 |

财务插件的 [`CONNECTORS.md`](https://github.com/anthropics/knowledge-work-plugins/blob/HEAD/finance/CONNECTORS.md) 用星号标注了这种情况："占位符——MCP 地址尚未配置"。也就是说，**"内置服务器"这个词在这一层的意思是"给你留了位置"，不是"开箱即用"。**

这类细节决定你第一次上手要花多久：如果按 README 的"开箱即用"预期安装，你会发现财务插件连不上数据仓库，得先去填地址。

## 七、怎么用这三个数字做判断

| 你的问题 | 看哪一层 |
| --- | --- |
| 有没有覆盖我这个岗位 | 17 个顶层目录（22 个清单）里找，别只看 11 个 |
| 里面写得细不细 | 打开对应插件的 `skills/*/SKILL.md` 读正文 |
| 能不能接我的系统 | 看该插件的 `CONNECTORS.md` 类别表与 `.mcp.json` 的地址状态 |
| 有没有第三方替代 | 市场清单里的 123 条，但要单独审权限与维护状态 |

四行里第三行最容易被跳过，却最影响落地。

## 八、限制与结论

这个仓库的组织方式可以概括成三层：11 个是推荐入口，22 个是仓库自带（分布在 17 个顶层目录里），123 条是市场可见；四类组件里技能是主体（252 个），命令很少（15 个）；插件与具体产品通过 `~~category` 占位符解耦，而配置层留了不少待填的空地址。

本文的限制：没有安装或运行，所有结论基于 README、清单文件与目录树；17、22、252、123 这些数字是我按文件统计的，官方未公布同名口径；没有逐个核对子代理的实现；第三方插件只统计条目数，未评价其质量。

下一步建议：先在你关心的那个岗位目录下，随机打开两份 `SKILL.md` 读一读。如果正文里的流程与你的实际做法差得远，那这个插件更接近"改起来比重写省事"，而不是"装完就能用"。
