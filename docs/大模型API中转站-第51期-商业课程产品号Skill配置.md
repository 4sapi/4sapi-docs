# 【大模型API中转站】第51期 商业课程产品号Skill | 转化协作配置

本文是【大模型API中转站】系列的第51篇。本系列致力于用最低的成本、最清晰的方法，帮你打通多模型API的任督二脉。建议先收藏，随用随查。

前两篇分别讲了长文创作者和图文短视频创作者。

这一篇看更接近商业结果的几类人：

```text
知识付费 / 课程 / PPT 创作者
商业广告 / 带货 / 私域转化创作者
AI 工具 / 产品号 / 科技号创作者
个人 IP / 矩阵号 / 内容团队
```

它们和普通内容号最大的区别是：内容不是终点，交付、转化、协作和复盘才是终点。

课程创作者不能只写一篇文章，还要交付课件、作业、答疑和资料包。

商业广告不能只写一句卖点，还要拆竞品、处理异议、跟进线索和生成方案书。

产品号不能只发“更新了”，还要讲清楚版本变化、使用场景、测试结果和迁移建议。

矩阵团队不能只靠个人灵感，还要统一人设、共享 Skill、整理素材和复盘数据。

这类工作流更适合用 Codex + Skill + 大模型API中转站来管理。

## 1. 课程和知识付费：把内容变成交付物

知识付费最核心的不是“会讲”，而是能不能持续交付清楚的材料。

推荐 Skill 组合：

| 环节 | 推荐 Skill | 作用 |
| --- | --- | --- |
| 课程研究 | `content-research-writer`、`notion-research-documentation` | 整理资料、搭课程大纲 |
| 课件和资料包 | `paperjsx`、`canvas-design` | 生成 PPTX、DOCX、PDF、信息图 |
| 学员管理 | `spreadsheet-formula-helper` | 课程表、学员表、作业表、数据统计 |
| 答疑和售后 | `support-ticket-triage` | 整理问题、分类、优先级和回复 |
| 直播课复盘 | `meeting-notes-and-actions`、`meeting-insights-analyzer` | 课后笔记、行动项、学员反馈分析 |
| 品牌统一 | `brand-guidelines` | 统一课程品牌、课件风格、表达口径 |

一个可落地流程是：

```text
资料库
  -> 课程大纲
  -> 讲稿
  -> PPT / PDF
  -> 作业表
  -> 直播答疑纪要
  -> 学员问题库
  -> 下一期课程优化
```

课程内容不要只放在聊天记录里。

建议目录：

```text
course-workflow/
  research/
  syllabus/
  lessons/
    lesson-01/
      outline.md
      script.md
      slides/
      homework.md
  students/
    roster.xlsx
    homework-status.xlsx
  qna/
    raw/
    triage.md
    faq.md
  delivery/
    pptx/
    pdf/
    templates/
  review/
    feedback.md
    next-iteration.md
```

这样 `paperjsx` 负责交付物，`spreadsheet-formula-helper` 负责表格，`support-ticket-triage` 负责答疑，整个课程才像产品，而不是散装资料。

## 2. 课程创作者的实用指令

从一堆资料变成课程，可以这样开始：

```markdown
请根据 research/ 目录里的资料，为一门 4 节课的训练营设计课程结构。

请输出：
1. 课程目标。
2. 目标学员画像。
3. 4 节课标题和学习目标。
4. 每节课的讲解大纲。
5. 每节课的作业。
6. 需要制作的课件和资料包。
7. 哪些内容必须人工确认。

要求：
不要承诺无法验证的效果。
不要把资料里的案例改造成虚假成功案例。
```

直播课结束后，可以继续处理转写稿：

```markdown
下面是直播课转写稿和聊天区问题。

请输出：
1. 课后笔记。
2. 学员高频问题。
3. 已解决问题和未解决问题。
4. 建议补充到 FAQ 的条目。
5. 下一节课需要调整的内容。
6. 可以直接发给学员的复习清单。
```

这里特别适合走 4SAPI 做模型分层：

| 任务 | 模型策略 |
| --- | --- |
| 转写稿摘要 | 低成本或中等模型 |
| 课程结构设计 | 强文本模型 |
| PPT / DOCX 生成 | 代码和文档生成能力强的模型 |
| 学员反馈分类 | 低成本模型 |
| 课程迭代判断 | 强模型 + 人工判断 |

## 3. 商业广告：先拆竞品，再写转化

商业内容最怕自嗨。

你以为卖点很清楚，用户看到的可能只是一堆功能词。

推荐 Skill 组合：

| 环节 | 推荐 Skill | 作用 |
| --- | --- | --- |
| 竞品拆解 | `competitive-ads-extractor` | 拆竞品广告、卖点、钩子、素材结构 |
| 线索研究 | `lead-research-assistant` | 研究潜在客户、公司信息、线索资料 |
| 文案生成 | `content-research-writer` | 把卖点变成用户能听懂的话 |
| 商务沟通 | `email-draft-polish` | 报价、邀约、合作、催单 |
| 售后反馈 | `support-ticket-triage` | 整理客户问题和常见异议 |
| 命名和域名 | `domain-name-brainstormer` | 新产品、新栏目、新服务命名 |
| 方案书 | `paperjsx` | 报价单、方案书、PPT、PDF |
| 投放数据 | `spreadsheet-formula-helper` | 整理线索、报价、ROI、投放数据 |

商业广告的工作流可以这样拆：

```text
竞品广告
  -> 钩子拆解
  -> 卖点表
  -> 用户异议
  -> 广告文案
  -> 私域话术
  -> 邮件跟进
  -> 方案书
  -> ROI 复盘
```

注意，这里的重点不是“抄竞品”，而是理解表达结构。

可以这样让 Codex 分析：

```markdown
请分析这些竞品广告素材。

请输出：
1. 每条广告的目标用户。
2. 主卖点。
3. 开头钩子。
4. 证据类型：数据、案例、背书、对比、演示。
5. 用户异议。
6. 可能夸大的地方。
7. 我们可以学习的结构。
8. 不应该照搬的表达。
```

再写自己的文案：

```markdown
请基于我们的产品资料和上面的竞品结构，生成 5 版广告文案。

要求：
1. 不使用竞品原句。
2. 不编造客户案例和数据。
3. 每版对应一个不同用户痛点。
4. 标出需要补充证据的地方。
5. 给出适合投放的平台。
```

商业内容的底线很简单：可以优化表达，不能编造证据。

## 4. 私域转化：不要只写话术，要整理异议

私域成交经常卡在异议处理。

用户会问：

```text
为什么这么贵？
和竞品有什么区别？
适不适合我？
有没有案例？
售后怎么保证？
多久能看到效果？
```

这些问题不要每次临场回答。

可以用 `support-ticket-triage` 和 `email-draft-polish` 做一个异议库：

```markdown
请把这些客户聊天记录整理成异议库。

请输出：
1. 高频问题分类。
2. 每类问题背后的真实担心。
3. 已有材料里能回答的证据。
4. 还缺什么证据。
5. 建议回复话术。
6. 不应该承诺的内容。
```

再把它变成私域 SOP：

```text
首次咨询
  -> 需求确认
  -> 适配判断
  -> 资料发送
  -> 异议处理
  -> 报价方案
  -> 成交跟进
  -> 售后反馈
```

这类内容很适合走团队统一模型入口。

原因是商业线索、客户问题、报价和售后反馈都比较敏感，不应该散落在个人 Key 和个人聊天窗口里。

## 5. AI 产品号：把更新写成用户能懂的价值

AI 工具、产品号、科技号的内容，最容易写成“功能播报”。

比如：

```text
新增 X 功能。
优化 Y 体验。
修复 Z 问题。
```

用户真正关心的是：

```text
这对我有什么用？
我需不需要升级？
原来的流程会不会受影响？
有没有替代方案？
成本会不会变化？
```

推荐 Skill 组合：

| 环节 | 推荐 Skill | 作用 |
| --- | --- | --- |
| 更新日志 | `changelog-generator` | 把版本变化写成清晰说明 |
| 测评教程 | `content-research-writer` | 写测评、教程、选型文章 |
| 网页测试 | `webapp-testing` | 测试网页应用流程，输出结果 |
| Agent 工具链 | `mcp-builder` | 构建和评估 MCP Server |
| 项目拆解 | `create-plan` | 先拆计划，再做开发实录 |
| 需求到实现 | `notion-spec-to-implementation` | 把需求文档变成开发计划 |
| 开发成长 | `developer-growth-analysis` | 分析学习盲区和编码习惯 |
| CI 问题 | `gh-fix-ci`、`gh-address-comments` | 处理 GitHub Actions 和 PR 评论 |
| 技术资料包 | `paperjsx` | 把技术内容做成 PPT、PDF、报告 |

产品号可以固定一个更新模板：

```markdown
请把这份 changelog 改成面向用户的产品更新文章。

请输出：
1. 一句话总结这次更新。
2. 这次更新影响哪些用户。
3. 新功能的使用场景。
4. 迁移或配置注意事项。
5. 已知限制。
6. 适合写成教程的后续选题。
7. 适合写成短视频的 3 个角度。

要求：
不要夸大功能。
不要把内部修复写成重大突破。
涉及价格、权限、模型能力时标记需要人工复核。
```

如果是工具测评，可以加上 `webapp-testing`：

```markdown
请测试这个 Web App 的核心流程，并输出测评素材。

请关注：
1. 注册和登录是否顺畅。
2. 首次使用路径。
3. 核心功能是否能完成。
4. 错误提示是否清楚。
5. 哪些地方适合截图。
6. 哪些问题需要在文章里提醒读者。
```

产品号的内容要克制。读者信任来自准确，而不是每次都说“重磅更新”。

## 6. 个人 IP 和矩阵团队：把个人能力变成组织能力

个人 IP 和矩阵团队最需要的不是某一个写作 Skill，而是统一规范。

推荐 Skill 组合：

| 环节 | 推荐 Skill | 作用 |
| --- | --- | --- |
| 人设和风格 | `brand-guidelines` | 统一语气、视觉、内容风格 |
| 团队共享 | `skill-share` | 团队共享 Skill 和可复用指令 |
| 内部沟通 | `internal-comms` | 写内部通知、项目更新、团队沟通 |
| 会议纪要 | `meeting-notes-and-actions` | 把会议转成纪要、决策、行动项 |
| 复盘分析 | `meeting-insights-analyzer` | 分析会议和增长复盘中的问题 |
| 素材管理 | `file-organizer` | 整理素材、成稿、封面、视频、数据 |
| 知识沉淀 | `notion-knowledge-capture`、`notion-research-documentation` | 灵感、案例、评论和选题入库 |
| 批量初稿 | `content-research-writer` | 基于资料批量生成内容初稿 |
| 自定义流程 | `skill-creator` | 创建自己的专属 Skill |

矩阵号最怕的是每个账号各写各的，最后读者记不住你是谁。

建议先写一份团队级规范：

```markdown
# 内容团队规范

## 账号矩阵
- 主账号负责深度观点
- 小红书账号负责图文拆解
- 视频号负责口播和案例
- 社群负责答疑和转化

## 统一规则
- 核心观点必须一致
- 案例和数据来源必须一致
- 标题可以按平台调整
- 结论不能互相冲突

## 工作流
- 每周一选题会
- 每周二调研和资料归档
- 每周三长文初稿
- 每周四拆图文和视频
- 每周五发布和复盘

## 审核边界
- 数据、价格、政策、客户案例必须人工确认
- 商业承诺必须由负责人审核
- 未授权素材不得发布
```

再用 `skill-share` 把可复用指令、模板和 Skill 共享给团队成员。

这一步会把个人经验变成组织能力。

## 7. 用 4SAPI 管住成本和权限

商业、课程和团队场景比个人写作更需要模型治理。

建议至少分四类 Key：

```text
content-draft
visual-generation
business-sales
team-review
```

也可以按项目拆：

```text
course-2026-summer
ads-client-a
product-channel
matrix-team
```

这样一旦成本异常，能定位是谁、哪个项目、哪类任务在消耗。

模型路由也可以分层：

| 任务 | 模型策略 |
| --- | --- |
| 表格整理、问题分类、命名归档 | 低成本模型 |
| 商业文案、课程大纲、产品更新文章 | 中等到强文本模型 |
| 竞品拆解、用户异议、方案判断 | 强推理模型 |
| PPT、PDF、网页、表格生成 | 代码和文档生成能力强的模型 |
| 封面、海报、视觉素材 | 图像或多模态模型 |
| 最终审核 | 强模型 + 人工负责人 |

不要把销售线索、客户资料、报价方案和学员信息随便丢进不清楚权限的工具。

越接近商业结果，越要把 Key、日志、权限和数据边界说清楚。

## 8. 合规和责任边界

这几类工作流的风险比普通写作更高。

| 场景 | 风险 | 建议 |
| --- | --- | --- |
| 课程 | 夸大学习效果、虚假案例 | 不承诺无法验证的结果 |
| 广告 | 编造数据、误导转化 | 所有证据可追溯 |
| 私域 | 过度承诺、诱导成交 | 话术必须符合真实交付能力 |
| 产品号 | 误报功能、价格、权限 | 发布前核对官方文档和后台 |
| 团队矩阵 | 多账号结论冲突 | 用统一规范和审核清单 |
| 客户资料 | 隐私泄露 | 脱敏、分权、保留最小必要信息 |

AI 可以提高生产效率，但不应该替代商业判断。

尤其是广告、课程和销售内容，宁可少写一点，也不要把不确定的东西写成确定承诺。

## 9. 最小落地方案

如果你做课程，先跑这个：

```text
content-research-writer 做课程大纲
paperjsx 做课件和资料包
spreadsheet-formula-helper 管学员表和作业
support-ticket-triage 整理答疑
meeting-insights-analyzer 做课后复盘
```

如果你做商业广告，先跑这个：

```text
competitive-ads-extractor 拆竞品
content-research-writer 写卖点和文案
lead-research-assistant 做线索研究
email-draft-polish 写跟进邮件
paperjsx 做方案书
spreadsheet-formula-helper 看 ROI
```

如果你做产品号，先跑这个：

```text
changelog-generator 写更新说明
webapp-testing 做实际测试
content-research-writer 写教程测评
create-plan 拆开发实录
paperjsx 做资料包
```

如果你做团队矩阵，先跑这个：

```text
brand-guidelines 统一风格
skill-share 共享工作流
file-organizer 管素材
meeting-notes-and-actions 管会议行动项
notion-knowledge-capture 沉淀选题和案例
skill-creator 固化自己的爆款流程
```

## 10. 总结

商业、课程、产品号和团队矩阵的共同点是：

```text
内容只是入口，交付和复盘才是结果。
```

所以 Skill 配置也不能只围绕写稿。

它应该覆盖：

```text
资料
  -> 内容
  -> 视觉
  -> 交付物
  -> 商务沟通
  -> 用户反馈
  -> 数据复盘
  -> 团队协作
```

4SAPI 这类大模型API中转站适合放在中间统一模型、Key、日志和成本，让不同环节用不同模型，也让团队知道钱花在哪里、风险在哪里。

一句话总结：

```text
个人创作者靠 Skill 提效，商业团队靠 Skill 把提效变成可管理的生产系统。
```

到这里，7 类创作者的 Codex Skill 配置就拆完了。

如果你不知道从哪开始，先别追求全自动内容工厂。先选一个真实场景，跑通一条链路，再把它写进自己的专属 Skill。
