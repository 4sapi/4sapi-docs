# 如何识别 OpenAI 兼容中转站改写了请求参数

把一个 OpenAI-compatible 接口接进应用后，最迷惑人的情况不是请求直接报错，而是请求看起来成功了，返回内容也像是对的，后来才发现某些字段并没有按自己发送的方式生效。

例如，客户端明确指定了 `text.verbosity: "low"`，响应中却显示为 `medium`；限制了 `parallel_tool_calls: false`，模型仍然返回并行调用；请求里没有 `instructions` 和工具，响应对象却包含了额外指令或工具定义。还有一种更棘手的情况：模型 ID、Token 用量和回答风格都“看起来合理”，但这些信号并不能证明上游一定是声明的那一个模型。

这类问题不能靠肉眼看一段回答来判断。下面给出一套可复现的审计方法，适用于接入 OpenAI-compatible Chat Completions 或 Responses API 的客户端、Agent 和中转服务。目标只有一个：把“能不能用”“参数有没有被改写”“模型身份能否证明”拆开，留下足够的原始证据，让接口升级、换模型或更换服务商时可以重新核验。

这里讨论的是接口行为审计，不对任何服务的速度、价格或模型质量作结论。示例中会使用 4SAPI 作为一个待测 endpoint 名称；脚本和判断规则可直接替换为其他 OpenAI-compatible 接口。

## 先把三个问题分开

很多测试报告把所有结果压缩成“兼容”或“不兼容”，信息量很低。至少应分别回答下面三个问题。

| 结论 | 真正要验证的内容 | 不能证明什么 |
| --- | --- | --- |
| `CAPABILITY` | 某项功能能否完成协议闭环，例如工具调用和回调 | 参数是否原样传递、真实上游模型身份 |
| `TRANSPARENCY` | 显式字段是否被改写，是否出现未发送的指令或工具 | 模型本身的质量或来源 |
| `IDENTITY` | 是否有足够证据确认上游模型和版本 | 仅凭响应字段不能形成严格证明 |

举个具体例子：第一轮返回了合法的 `function_call`，第二轮接收 `function_call_output` 后还原了随机生成的 receipt，这可以证明工具回调链路在该次测试条件下是可用的，`CAPABILITY` 可以通过。但是，如果请求中的 `reasoning.context: "current_turn"` 在响应中变成了 `"all_turns"`，参数透明度就应当失败。两种结论并不冲突。

反过来，参数看起来全部一致，也不等于模型身份已经被证明。中转层、兼容层和客户端都可能生成或规范化 `model`、`usage`、`reasoning_tokens` 等字段。它们是排查线索，不是可验证的模型来源凭证。

## 适用场景和前置条件

这套方法适合以下场景：

1. 你的应用通过 `/v1/responses` 或 `/v1/chat/completions` 接入了非直连 API。
2. 需要使用 Function Calling、推理参数、Structured Output、并行工具调用等非基础能力。
3. 想判断问题出在 SDK、网关、中转层还是上游，而不是只得到一个 HTTP 200。
4. 希望保存一次可审计的验收记录，而不是依赖聊天窗口截图。

开始前准备 Python 3.10 及以上版本和一个 HTTP 客户端即可。示例使用 `httpx`：

```text
httpx
```

测试环境变量不要写入代码仓库：

```text
OPENAI_BASE_URL=https://your-relay.example.com/v1
OPENAI_API_KEY=replace-with-your-key
PROBE_MODEL=gpt-5.6-sol
PROBE_TIMEOUT_SECONDS=180
```

其中 `OPENAI_BASE_URL` 建议以 `/v1` 结尾，最终请求路径为 `{OPENAI_BASE_URL}/responses`。程序启动时要检查地址没有被拼成 `/v1/v1/responses`，也不要把完整 API Key 写进日志、报告或截图。

最重要的一项前置条件是：第一轮排查使用原始 HTTP 请求，不要从 Agent 桌面端、IDE 插件或封装 SDK 发起正式结论测试。客户端有可能自动附加系统提示词、工具集、历史消息、重试逻辑和默认参数。经过这些层以后，即便发现额外字段，也无法判断是哪个层注入的。

## 建立可复查的证据包

参数透传不是看一次响应就能得出结论。每个 case 至少保存四类材料：脱敏后的请求体、原始响应体、HTTP 状态与响应头、客户端测得的时间和错误。建议目录按运行时间隔离：

```text
reports/
  20260822-153000/
    environment.json
    01-baseline.request.json
    01-baseline.response.json
    01-baseline.meta.json
    02-reasoning.request.json
    02-reasoning.response.json
    summary.md
```

`environment.json` 不应保存密钥，但应记录 Python 版本、脚本 Git 提交、测试时间、请求地址的主机名、模型 ID、超时设置和是否启用流式。否则三周后出现差异时，无法判断是接口变了、脚本变了，还是测的根本不是同一环境。

保存请求前先递归脱敏。下面的函数仅展示最小做法；真实项目还应对自定义认证字段和可能出现在输入里的个人信息增加规则。

```python
from copy import deepcopy

SENSITIVE_KEYS = {"authorization", "api_key", "api-key", "x-api-key"}

def redact(value):
    if isinstance(value, dict):
        cleaned = {}
        for key, item in value.items():
            if key.lower() in SENSITIVE_KEYS:
                cleaned[key] = "***REDACTED***"
            else:
                cleaned[key] = redact(item)
        return cleaned
    if isinstance(value, list):
        return [redact(item) for item in value]
    return value

def save_json(path, payload):
    path.write_text(
        json.dumps(redact(deepcopy(payload)), ensure_ascii=False, indent=2),
        encoding="utf-8",
    )
```

请求体与响应体都应保存原始 JSON 结构，不要只抽取最终文本。`tools`、`instructions`、`parallel_tool_calls`、`reasoning`、`text` 等字段往往不在最终回答里，过早简化会丢掉正是需要审计的证据。

## 先做一个没有变量的基线请求

在带工具和推理参数之前，先发送一个最小的固定输出请求。它的用途不是测试模型能力，而是确认地址、认证、模型 ID 和 Responses API 对象结构。

```json
{
  "model": "gpt-5.6-sol",
  "input": "只输出 RELAY_BASELINE_OK，不要添加标点或解释。"
}
```

本地断言至少包括：HTTP 状态码为 `200`、`object` 为 `response`、`status` 为 `completed`、`error` 为 `null`，输出项中存在 `message`，最终文本严格等于 `RELAY_BASELINE_OK`。

如果这一步失败，不要立即往请求中叠加工具、JSON Schema、流式和推理开关。先检查路径是不是 API 实际支持的路径、模型名是否有效、超时是否足够，以及目标服务是否只兼容 Chat Completions 而没有完整实现 Responses API。一个路径能返回某段文本，并不表示它实现了同样的对象和状态机。

基线通过后，可以记录响应中能够回显的字段，但不要立刻假定“回显值就是真实处理过程”。除非接口文档明确承诺某字段代表最终生效配置，否则它只能算观察值。后面的对照才负责把观察值变成清晰的 `PASS`、`WARN` 或 `FAIL`。

## 给每个字段设计单独的探针

把很多可变字段塞进同一个请求，虽然省请求次数，但一旦出现差异，就难以定位冲突来源。更稳妥的做法是每个 case 只改变一到两个字段，基线字段保持固定。

建议把待审计字段分成六组。

### 1. 模型与请求生命周期

这组包括 `model`、`store`、`previous_response_id` 和请求 ID。`model` 不同于“模型身份”，它只是客户端发出的路由请求。审计时要记录：请求模型名、响应模型名、实际 HTTP 路径、是否收到重定向、响应 ID 是否存在。

若请求发送明确模型 ID，响应却显示为另一个不相关的模型 ID，应记为参数改写失败。若团队对别名解析有事先约定，例如请求 `gpt-5.6` 后统一解析为某个固定部署名，则在报告中写成“允许的别名解析”，并把映射规则写进测试前提，不能事后把任何变化都解释成别名。

`store: false` 需要单独验证。它关注的是客户端能否完整回传上一轮 `output`，而不是服务端是否记住会话。`previous_response_id` 是另一条服务端状态链路：前者通过、后者失败时，结论应是“手动上下文续传通过，服务端续传不支持或待核验”，不能合并成一个模糊的成功或失败。

### 2. 工具集与工具选择

工具相关字段包含 `tools`、`tool_choice` 和 `parallel_tool_calls`。测试时先发送一个很小、严格的 Function Tool，再把工具名、`call_id`、参数 JSON 和回调结果分别断言。

对于参数透明度，除了“发送的工具是否存在”，还要检查“未发送的工具是否出现”。未提供任何 `tools`，响应却带了某个工具定义或工具调用，是高风险信号：它可能来自 SDK 默认配置、网关注入、运行环境规则，也可能是上游的兼容实现。无论来源是哪一个层，原始 HTTP 探针下都应标为 `FAIL`，再进入定位步骤。

同理，如果显式发送 `parallel_tool_calls: false`，响应结果仍表现为并行调用，不能只因为任务最后完成了就忽略。先保存具体的调用结构，再确认响应字段是否回显、上游是否文档声明忽略该选项，最后把它判为明确改写或字段无法观察。

### 3. 指令与输入边界

`instructions` 是最容易被客户端或 Agent 框架自动填充的字段之一。为了检查注入，创建一个明确不包含 `instructions` 的请求体，并在保存前确认该字段确实不存在，而不是空字符串或 `null`。

如果响应对象、调试日志或服务端回显中出现了非空 `instructions`，应保留完整内容的脱敏副本，并判定为 `FAIL`。这里的重点不是判断这段指令“好不好”，而是它没有出现在测试请求中。没有原始请求快照的情况下，无法区分“代码忘了删”与“链路中被插入”，所以先保存再推断。

为避免提示词自身造成干扰，指令注入探针的用户输入应非常短，例如要求返回一个随机 nonce。不要要求模型解释自己的系统提示词，因为这种问题既不能可靠取得真实内部指令，也会把模型行为与协议字段混在一起。

### 4. 推理与输出控制

推理模型常见字段有 `reasoning.effort`、`reasoning.context`、`reasoning.mode`、`text.verbosity` 与 `max_output_tokens`。这些字段不能用最终答案的长短来反推是否生效，必须做请求、响应和可验证任务三层对照。

例如，同一题目可以分别以 `reasoning.effort: "none"` 和 `"max"` 运行多次，记录正确率、延迟、输入 Token、输出 Token 与响应中出现的推理字段。若请求中的 `reasoning.context: "current_turn"` 变成 `"all_turns"`，或者 `text.verbosity: "low"` 变成 `"medium"`，这是直接可写进透传报告的字段差异。若 `max_output_tokens: 2048` 在响应中变成 `null`，也应保留原始结构，而不是把 `null` 自动当成服务端默认值后删除证据。

不过，字段变化不必然说明所有请求都会被改写。它只说明该 case、该时间、该版本下存在不一致。报告应使用“观察到”“在本次请求中”“需要服务端确认”这样的边界描述，避免把一次实测扩大成永久结论。

### 5. 结构化输出与自定义工具

如果接口声称支持 Custom Tool 或 Grammar，建议增加一个不依赖自然语言判断的固定测试。比如定义 `math_exp`，要求它只输出：

```text
17 * 25 + 3
```

断言 `type` 是 `custom_tool_call`、工具名正确、`call_id` 非空，并且 `input` 与固定表达式完全一致。自然语言中“我会调用 math_exp”不算成功；它只能说明模型说了什么，不能说明协议层返回了什么。

这类 case 的价值在于发现兼容层是否把 Custom Tool 降级成普通文本，或者把 Grammar 丢弃。它与 Function Calling 的 JSON 参数测试相互补充，但不应被混为同一个断言。

### 6. 流式响应与网络行为

对于生产上依赖 SSE 的客户端，还应把 `stream: true` 单列为测试维度。检查首个事件、文本增量、工具参数增量、完成事件和错误事件的顺序；保存原始事件序列，不只保存拼接后的最终文本。

网络重试要谨慎。`429`、`5xx`、TLS 断开、读超时、空响应和非法 JSON 都是接口健康状况的一部分。为了观察稳定性，可以对网络类故障最多自动重试一次，但报告里必须同时保留首次失败和重试结果。只保留成功的第二次，会人为放大兼容性结论。

## 用随机 nonce 区分“模型猜对”与“上下文真的到了”

普通固定提示很容易产生假阳性。比如工具结果里写死 `{"status":"ok"}`，模型第二轮回答“状态正常”，不能证明它读到了工具输出，也可能只是根据用户请求猜出了常见答案。

解决办法是在每次运行时生成不可预测的值，并把它放进工具回调。Python 可以这样生成：

```python
import secrets

receipt = secrets.token_hex(12)
```

第一轮拿到 `function_call` 后，模拟工具结果：

```json
{
  "accepted": true,
  "server_status": "healthy",
  "reason": "probe_ok",
  "receipt": "每次运行时生成的随机值"
}
```

第二轮回传时，必须同时保存原始用户输入、第一轮完整 `output`，以及与第一轮 `call_id` 一致的 `function_call_output`。对于 reasoning 模型，还应保留第一轮的 reasoning item；只回传 `function_call` 有可能导致缺失模型继续推理所需的上下文。

通过条件不是“模型大致说对了”，而是最终文本准确包含该次运行的 receipt。若 receipt 不一致，先检查回调请求是否真的发送、`call_id` 是否匹配、JSON 是否被二次编码、第一轮 output 是否被截断，再讨论服务端是否丢弃了上下文。这个排查顺序比直接把错误归因为“模型记忆不好”可靠得多。

## 制定统一的判定规则

审计规则要在运行前写好，不能在看到结果后临时解释。以下规则可作为一份保守基线：

| 观察到的结果 | 建议状态 | 处理方式 |
| --- | --- | --- |
| 显式发送字段与可观察到的响应字段一致 | `PASS` | 保留请求与响应快照 |
| 接口没有提供足以核对的回显字段 | `WARN` | 说明无法验证，不把它当作已透传 |
| 显式字段被改成另一有效值 | `FAIL` | 记录两侧值和 case 名称 |
| 未发送 `instructions` 却出现非空指令 | `FAIL` | 定位客户端、代理和上游注入点 |
| 未发送工具却出现额外工具或工具调用 | `FAIL` | 保存完整工具结构，排除 SDK 默认行为 |
| 响应模型名发生未经约定的变化 | `FAIL` | 检查路由、别名和回退规则 |
| 网络失败或响应无法解析 | `FAIL` | 记录原始错误，不用成功重试覆盖 |

下面是一个方便汇总的结果结构：

```json
{
  "case": "reasoning_context_current_turn",
  "status": "FAIL",
  "request": {
    "reasoning": {
      "effort": "max",
      "context": "current_turn"
    }
  },
  "observed": {
    "reasoning": {
      "effort": "max",
      "context": "all_turns"
    }
  },
  "evidence": [
    "02-reasoning.request.json",
    "02-reasoning.response.json"
  ],
  "note": "响应中观察到 context 与显式请求值不一致。"
}
```

最终摘要应避免只写一个总状态。建议至少输出：

```text
CAPABILITY: PASS | WARN | FAIL
TRANSPARENCY: PASS | WARN | FAIL
IDENTITY: VERIFIED | PARTIALLY_VERIFIED | UNVERIFIED
```

若没有来自上游或基础设施层的可审计证据，`IDENTITY` 应保持 `UNVERIFIED`。这一写法不是否定接口可用性，而是让结论与证据强度对应。

## 为什么响应字段不足以证明模型身份

常见的误判方式有三种。

第一种是看 `model` 字段。这个字段说明响应声称使用了哪个模型名，但可能经过别名映射、路由层改写或兼容层填充。它对排查很有用，却不是模型权属或推理来源的证明。

第二种是看 `usage` 和 `reasoning_tokens`。Token 统计能帮助估算调用量、发现异常大的上下文或比较同一接口的重复运行；但字段名称和数字都是 API 返回的一部分，不能独立证明上游请求路径。即使数值符合预期，也只能作为弱证据。

第三种是比较回答风格、基准题表现或某个特殊能力。模型行为受提示词、采样、工具、缓存、检索和后处理影响很大。某次回答像某个模型，无法排除中间层改写、替代模型或混合路由。

想把身份证据做得更强，需要增加不依赖响应自述的材料，例如与上游的可核验服务合同、具备访问控制的请求审计日志、供应商提供的部署和版本证明，或由双方约定的端到端追踪机制。它们仍然需要结合组织信任与权限边界判断；在没有这些材料时，最诚实的报告就是“能力和透明度已按用例测试，模型身份未被独立验证”。

## 发现差异后，按层排查而不是直接归因

当你看到额外指令、工具或字段改写时，先建立最短链路，再逐层加回组件。推荐顺序如下：

1. 用 `httpx` 或 `curl` 直接对 endpoint 发送最小 JSON。
2. 使用同一份 body 经过当前 SDK，比较 SDK 发出的实际 HTTP 请求。
3. 再经过 Agent 框架或 IDE 插件，查看它是否合并了系统提示词、历史与 Skills。
4. 最后检查公司网关、鉴权代理、模型路由和上游兼容层的日志或配置。

如果直接 HTTP 已出现注入或改写，问题范围大概率在客户端之外；如果直连正常、SDK 才出现差异，优先审查 SDK 版本、默认配置与拦截器。不要只从响应里的文本判断归属，也不要在没有证据时把责任写给某个服务。

对于容易触发安全审查的指令字段，报告里可以保存哈希、长度和必要片段，而不把可能包含项目机密的完整系统提示词复制进工单。例如记录 `SHA-256`、来源 case、字段路径和“请求中不存在，响应中非空”即可支持排查。

## 常见失误

**只看 HTTP 200。** HTTP 成功只说明服务接受了请求。结构化输出、回调、参数和流式顺序仍可能不符合协议。

**只保存最终文本。** 文本不包含被注入的工具定义和很多配置字段，排错时几乎没有价值。应保存脱敏 JSON 和原始事件。

**把响应缺字段当作透传成功。** 没有可比对的数据时应是 `WARN`，而不是 `PASS`。

**把重试后的成功当作稳定。** 首次 `TLS`、`429` 或超时同样需要进入报告。可重试不代表故障没有发生。

**让测试客户端承担太多功能。** 有状态 SDK、Agent 和浏览器端都会引入变量。先建立原始 HTTP 基线，再验证上层集成。

**把身份问题写成“真假模型”争论。** 工程上更有用的做法是列出证据等级和可验证边界：协议是否可用、参数是否透明、身份是否有独立佐证。

## 用对照请求缩小参数改写的来源

发现字段不一致后，下一步不应立即将责任归给某个中转层。先建立一组只改变一个因素的对照请求，通常可以快速缩小问题范围。每组都通过同一个原始 HTTP 客户端、同一个 endpoint 和同一模型运行，避免 SDK 或 Agent 框架在中间继续注入变量。

例如可以安排下面四类对照：

| 对照组 | 唯一变化 | 用途 |
| --- | --- | --- |
| 无工具基线 | 不发送 `tools` 与 `instructions` | 检查是否存在默认指令或工具注入 |
| 工具组 | 只增加一个严格 Function Tool | 检查工具是否被保留、改名或扩展 |
| 推理组 | 只改变 `reasoning.effort` 或 `reasoning.context` | 检查字段映射和默认值替换 |
| 输出控制组 | 只改变 `text.verbosity` 或 `max_output_tokens` | 检查截断、默认输出策略与回显差异 |

每组最好使用相同的短输入和随机 nonce。随机值可以排除“模型根据固定提示猜中了答案”的假阳性；短输入则降低历史上下文、检索和复杂工具选择对结论的干扰。运行顺序应交错，出现网络失败时保留原始错误与重试规则，避免某一组刚好全部落在服务拥塞时段。

若直接 HTTP 的无工具基线就出现额外 `instructions`，问题范围在 SDK 之外；若直连正常、只有应用 SDK 的请求出现，则检查 SDK 版本、请求构造器和拦截器；若只有 Agent 层出现，优先检查会话历史、全局系统提示词与插件初始化。这样的层层缩小比从最终文本推测原因更可靠。

## 区分“规范化”与“无法解释的改写”

并非所有字段差异都具有同样风险。有些接口会把等价别名解析为规范模型 ID，或省略一个本来未承诺回显的默认字段；另一些则会把显式值替换成不同的有效值，甚至插入请求中不存在的指令和工具。报告应把这两类情况分开。

可以在项目中预先维护一份允许清单，例如明确允许 `gpt-5.6` 被路由为团队约定的固定部署 ID，或允许服务省略不支持的可选观测字段。允许清单必须写明版本、依据和适用条件，不能在看到差异后临时补上。超出清单的变化仍保持 `FAIL` 或 `WARN`，等待服务端文档或日志给出解释。

对于接口没有回显的字段，正确状态是“无法观察”，不是“已原样透传”。可以用行为测试补充弱证据，例如设置一个很小的输出上限并检查是否截断，或要求禁止并行调用并检查 call 的数量；但行为也会受模型决策影响，不能替代字段级证据。报告中应写明哪部分来自回显，哪部分来自行为，哪部分仍不可验证。

## 让审计结果具备完整性与可追溯性

参数审计往往发生在接口争议或事故之后，原始文件一旦被手工修改，时间线就失去价值。对重要运行，可为每个脱敏后的 request、response、SSE event 和汇总生成 SHA-256，写入一个 manifest：

```text
run_id
测试时间与时区
脚本版本或 Git commit
endpoint 主机与路径
模型请求值
每个证据文件名与 SHA-256
断言结果与状态
人工复核人和复核时间
```

哈希不能证明模型身份，也不能阻止上游返回被改写的字段；它的作用是证明团队后来查看和讨论的是同一份本地证据。与脱敏规则、访问权限和保留期限一起使用，才能让审计文件既可追查，又不会变成另一份泄露密钥或用户数据的风险来源。

当需要向服务方提交问题时，优先发送最小可复现 case：请求体、预期行为、实际字段差异、HTTP 状态、时间、响应 ID 和已经排除的客户端层。不要附上完整业务聊天记录或所有内部系统提示词。对方能据此在服务端日志中定位请求，你也能保留足够的证据判断修复是否真正生效。

## 身份核验的结论应随证据升级

`IDENTITY: UNVERIFIED` 不代表接口一定不是所声明的模型，它只表示当前证据不足以独立确认上游。若后来获得了经过权限控制的上游请求日志、部署版本证明、可验证的端到端追踪或正式的供应链证明，可以将结论升级为“在某个日期、某个路由和某个证据范围内得到部分验证”。

即使拥有这些材料，也应避免写成跨时间、跨区域或所有请求的绝对判断。模型路由可能随着版本、容量、回退策略和区域配置改变。最有用的报告格式是写清“验证了什么、使用了什么证据、未验证什么、何时需要重新验证”。这种证据分级比一句“确定是真的”更适合工程验收和后续排错。

## 结论

审计 OpenAI-compatible 接口时，基础回答正确只是起点。更可靠的验收方式是保存原始请求和响应，用随机 receipt 验证多轮上下文，再对模型、工具、指令、推理和输出控制字段逐项比较。

这样得到的结果会更克制，也更能指导决策：功能通过可以继续集成；字段差异需要决定是否能接受默认值或改为客户端控制；缺少独立证据时，模型身份保持未验证。每次升级 SDK、切换路由或更换 endpoint 后，重跑同一套 case，就能把“感觉不对”变成可定位的协议差异。

相关协议可参考 OpenAI 官方的 [Function Calling 指南](https://developers.openai.com/api/docs/guides/function-calling) 与 [Responses API 参考](https://platform.openai.com/docs/api-reference/responses/create)。
