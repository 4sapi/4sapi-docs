# 拆解 Superpowers 的方法论：七步流程与哪些环节是硬约束

多数"给 agent 加流程"的尝试，最后变成一份提示词：写得再细，也靠模型自觉。Superpowers 的做法不同：它既有写成提示的部分，也有靠钩子在会话启动时注入引导、靠明确规则删掉不合规产物的部分。

本文拆两件事：这套方法论实际规定了什么，以及哪些环节是机制上的硬约束、哪些仍然只是对模型的强提示。分清这一点，才知道把它引入团队时该期待什么。

信息来自仓库 README 与五个技能文件，检索日期为 2026-11-02。我没有安装或运行过它。

README 的自我定位是：一套给编码 agent 的完整开发方法论，建立在可组合的技能之上，并配一些初始指令确保 agent 真的会用它们。

最后半句是关键：**技能不自动生效，需要机制保证它们被触发。**

## 二、七步流程

README 把它写成七步，我按原文顺序列出，并补上每一步的实际约束：

| 步 | 技能 | 做什么 | 关键约束 |
| --- | --- | --- | --- |
| 1 | brainstorming | 先不写代码，问出你真正要什么，然后把理解复述给你纠正 | 小改动在对话里定，项目级要产出可据以规划的设计文档 |
| 2 | using-git-worktrees | 设计批准后建立隔离工作区，跑项目初始化，验证测试基线干净 | 在动手前确认基线 |
| 3 | writing-plans | 拆成小任务，每个任务写明文件路径、接口与测试、验证步骤 | README 说"完整代码"，但技能正文反而警告"计划比它描述的代码还长，就等于替人把代码写了"，完整代码只留在签名与测试定不下来的算法处 |
| 4 | subagent-driven-development 或 executing-plans | 按计划执行：每个任务派一个全新子代理并在其后评审，或在一个上下文里顺序做完、最后整体评审一次 | 两种执行方式的成本差异明确 |
| 5 | test-driven-development | 强制 RED-GREEN-REFACTOR | 先写测试、看它失败、再写最小实现 |
| 6 | requesting-code-review | 任务之间评审，按严重度报告问题 | 严重问题阻塞进度 |
| 7 | finishing-a-development-branch | 验证测试，给出合并/PR/保留/丢弃的选项，清理工作区 | 结束时要给出一组选项（原文没有写"必须选一个"） |

第 1 步的顺序值得注意：文档明确说，在进入计划模式之前如果还没做过 brainstorming，要先做 brainstorming。也就是说"先想清楚"被放在前置位置，而不是建议。

## 三、十五个技能怎么分工

README 按用途分了四组：

| 组 | 技能 |
| --- | --- |
| 测试 | test-driven-development |
| 调试 | systematic-debugging、verification-before-completion、diagnosing-superpowers |
| 协作 | brainstorming、writing-plans、executing-plans、dispatching-parallel-agents、requesting-code-review、receiving-code-review、using-git-worktrees、finishing-a-development-branch、subagent-driven-development |
| 元 | writing-skills、using-superpowers |

有三件事从这张表里能读出来。

第一，**调试占了三个位置**，其中 diagnosing-superpowers 是"排查 Superpowers 自己"：当你觉得某个技能该触发没触发、或者 agent 跑偏了，让它读会话记录，逐行给证据。

第二，**接收评审也是一个技能**（receiving-code-review）。多数流程只管"怎么请求评审"，不管"收到意见后怎么回应"，这一项补的是后半段。

第三，**写技能本身也有方法论**（writing-skills），说明它的作者把技能当作需要测试的代码，而不是文档。

## 四、哪些是硬约束

这是本文的重点。分三层看。

### 层一：机制强制

| 机制 | 作用 |
| --- | --- |
| 会话启动钩子 | 在会话开始时注入 using-superpowers 引导技能；仓库的钩子配置把触发点列为 `startup|clear|compact`，也就是启动、清空、压缩后都会重注入。文档列出 Claude Code、Codex、Cursor、Gemini、Pi、Muse 等走这条路；Antigravity 是例外，靠技能描述促使模型加载 |
| TDD 的删除规则 | 技能原文规定：先写了代码再补测试，那段代码要删掉，不许留作"参考"、不许"边写测试边改编"、不许再看它，从测试重新实现 |
| 完成前验证 | 技能要求"先跑验证命令、确认输出，再声称完成"；"测试通过"这一声明需要的是测试命令的 0 失败输出，而不是上一次的印象 |
| 计划的固定头 | 计划文档必须以固定头部开始，其中含一行"REQUIRED SUB-SKILL"，给出两个可选的执行子技能（推荐子代理驱动，或内联执行） |

第二行到第四行本质上是规则：它们不能物理阻止模型偷懒，但把"合规"写成了可检查的判据。审计时你可以拿这条去对：这段代码有没有先写测试？

### 层二：强提示

| 内容 | 为什么只是提示 |
| --- | --- |
| "1% 可能适用就必须调用" | 这是用措辞施压，模型仍可能判断"这条不适用" |
| 反合理化清单 | 技能列了一张"你在自我合理化的想法"对照表，例如"这只是个小问题""我先看看代码"；它提高的是遵守概率，不是确定性 |
| 流程技能优先 | 规定先走流程技能再用实现技能，靠的是模型按顺序读 |

### 层三：环境限制

钩子机制不是所有 harness 都能等价实现。README 自己写了一个例子：Hermes Agent 没有压缩后钩子，因此一个很长的会话在首轮之后发生压缩，就会丢掉引导；建议遇到技能不再触发时开新会话。

这说明"硬约束"有边界：**平台没有对应钩子时，机制退化成提示。**

## 五、计划粒度的具体规定

writing-plans 里几条规定很实在，可以直接借：

1. **读者设定。** 计划写给一个没见过这个代码库、也没看过设计文档的工程师，假设他能写地道代码，但不知道你决定了什么——哪个文件、哪个名字与签名、用规格里的哪些值、哪个测试证明哪个任务。
2. **任务右置。** 任务是"自带测试周期、并且值得一个新评审把关"的最小单位；把配置、脚手架、文档折进需要它们的那个任务；只在"评审者可能接受 A 而拒绝 B"的地方切分。
3. **步骤粒度。** 每一步是一个动作、有一个可检查的结果：写失败测试 → 跑它确认失败 → 写最小实现 → 跑测试确认通过 → 提交。
4. **全局约束。** 计划头部要有一段 Global Constraints，把规格里的项目级要求（版本下限、依赖限制、命名规则）逐字抄进来，每个任务隐式继承。

第 2 条是我认为最有用的一条判据：**切分点应该选在"评审者可能一个接受一个拒绝"的地方**，而不是按文件或按层切。这条规则能直接把"按技术分层拆任务"这种坏习惯挡掉。

## 六、两种执行方式的成本对照

subagent-driven-development 与 executing-plans 的差别，文档说得很直白：

| 方式 | 做法 | 成本 |
| --- | --- | --- |
| 子代理驱动 | 每个任务派一个全新实现子代理，任务后评审（规格符合性 + 代码质量），最后再来一次整分支评审 | 每个任务、每次评审各占一个全新上下文 |
| 内联执行 | 一个上下文里做完所有任务，最后只做一次整分支评审 | 一个上下文加一个最终评审者 |

同一份技能里还写了一条经验：一次派发曾经达到 4.2 万字符，其中 99% 是粘贴的历史。它给出的结论是：全新子代理只需要它的任务、它涉及的接口和全局约束，别的都不要。

这条对自建系统的启发很直接：**子代理的成本主要不在模型调用，而在你往提示里塞了什么。**

## 七、完成前验证的要求

verification-before-completion 的核心句是"证据先于声明"。它给了一张对照表，把常见声明和各自需要的证据分开，例如：

| 声明 | 需要 | 不算数 |
| --- | --- | --- |
| 测试通过 | 测试命令输出 0 失败 | 上一次跑的结果、"应该能过" |
| 已修复 | 针对原始症状的测试通过 | 只是把代码改了 |

技能里还有一句很硬的话，大意是：跳过任何一步就不是验证，而是在说谎。

对团队来说，这张表的价值在于它把"完成"从主观判断变成了可核对的东西。

## 八、一处需要知道的默认行为

README 的最后一节说明了遥测：brainstorming 的可视化伴侣里，一个 logo 默认从项目维护方网站加载，请求里带当前版本号，不含项目、提示或 agent 的信息。可以用环境变量 `SUPERPOWERS_DISABLE_TELEMETRY` 关闭，也遵从 Claude Code 的 `DISABLE_TELEMETRY` 与 `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC`。

对个人使用影响不大；对有出网白名单的环境，这是一条要在部署前处理的默认项。

## 九、这套方法论的可借鉴处与代价

**可借鉴：**

- 把"先想清楚"做成流程的第一步，并规定进入计划模式前必须先做。
- 任务切分以"评审者能否分别接受"为判据。
- 计划头部固定，全局约束逐字抄自规格，避免执行者自己发挥。
- TDD 对"先写代码"给出一条不给解释余地的处置：删掉重来。
- 完成声明必须带命令输出。

**代价：**

- 子代理驱动模式下，每个任务和每次评审都占一个上下文，调用次数随任务数线性增长。
- 流程技能先行的规则会让简单任务也走一遍完整流程；对一次改一行的场景，这是纯开销。
- 机制依赖平台钩子，跨 harness 时会出现能力差异（例如没有压缩后钩子的平台会丢引导）。

## 十、限制与结论

Superpowers 的方法论可以概括为：用技能把流程写死，用钩子保证技能被读到，用可核对的判据（测试输出、删除规则、计划固定头）把"合规"变成能检查的东西。它明确区分了不能商量的部分和可以判断的部分，这个区分本身比具体规则更值得借。

本文的限制：没有安装或运行过任何技能；只读了 README 与五个技能文件，其余十个技能的内容没有读；没有核验钩子在各平台的实际注入时机；星标数与文件数是检索当天快照。

下一步建议：先读 writing-plans 与 verification-before-completion 这两份，它们对流程的约束最具体、也最容易脱离这套框架单独使用。等你确认团队能接受"完成必须带证据"这一条，再谈整套引入。
