# Cloudflare 安全审计技能拆解：六阶段流程为何要把发现与验证隔离

让编程智能体"审计一下这个仓库的安全"，最常见的结果是一份很长的清单：有真问题，也有大量"建议加固"和猜测。读的人要自己判断哪些值得修。cloudflare/security-audit-skill 想解决的正是这个问题：它不追求列得多，而是规定发现漏洞的智能体和确认漏洞的智能体必须是两个。

本文回答一个问题：这个技能的流程是怎么设计的，每个设计想防住什么，哪些说法只是项目自述。文章只依据仓库里的文档和脚本，不包含我对任何代码库跑过一次审计的结果。内容限于防御视角的流程分析，不涉及具体攻击方法。

信息截止日期为 2026-10-30。仓库在更新，引用前请重新打开原文件。

## 一、它是什么，不是什么

仓库信息来自 GitHub API 和 README（检索于 2026-10-30）：

| 项目 | 内容 |
| --- | --- |
| 仓库 | [cloudflare/security-audit-skill](https://github.com/cloudflare/security-audit-skill) |
| 协议 | MIT |
| 创建 | 2026-06-18 |
| 最近推送 | 2026-09-14 |
| 主要语言 | JavaScript（校验脚本） |
| Star 数 | 52,904（检索当天） |
| 形态 | 一组 Markdown 指令加两个 Node 校验脚本，不是可执行的扫描器 |

README 的自我定位是：把编程智能体变成安全审计员，由多个相互隔离的智能体依次做侦察、覆盖式搜索、候选验证、结构化输出、记录复核和报告。

README 还说，这个技能是 Cloudflare 漏洞发现系统的起点，该系统的描述见一篇名为 Build your own vulnerability harness 的博客。我没有打开那篇博客，所以这层渊源只是 README 的说法。

要点：**它本身不扫描代码**。真正读代码、做判断的是你的编程智能体。技能提供的是流程、提示词和格式约束。

## 二、两种运行模式

SKILL.md 开头规定了两种模式，这一点容易被忽略：

| 模式 | 触发 | 行为 |
| --- | --- | --- |
| 指导模式（默认） | 安全问题、局部评审、方法咨询 | 只用相关部分，不创建输出目录，不写审计文件 |
| 完整审计模式 | 明确要求审计或渗透测试整个代码库，或要求报告文件 | 走完六个阶段并写出全部文件 |

SKILL.md 还写道：如果请求可能指两种模式之一，先问一个聚焦的问题，再创建文件。

这个设计避免了一个常见副作用：你只是问了个安全问题，智能体却启动了整套多智能体流程。

## 三、六个阶段

按 README 和 SKILL.md：

| 阶段 | 做什么 | 产出 |
| --- | --- | --- |
| 1 侦察 | 梳理架构、信任边界、输入面、已有证据 | architecture.md、coverage-ledger.json |
| 2 覆盖式搜索 | 从覆盖账本的单元分配给相互隔离的搜索智能体；用覆盖评审找空缺 | 候选清单 |
| 3 候选验证 | 每个唯一候选交给全新的验证智能体，任务是反驳它 | 验证结论 |
| 4 结构化输出 | 写出 confirmed、needs_validation、rejected 三类记录并按 schema 校验 | findings.json |
| 5 记录复核 | 全新的智能体逐条核对最终记录里的源码主张 | verified 或 replace |
| 6 报告 | 从已验证记录生成 REPORT.md 等三份文档 | 报告 |

两个值得注意的规则：

1. 阶段 3 的验证者"没有搜索过这个候选"。验证提示词的第一句就是"你没有写这个候选，尝试从仓库源码和有界的本地证据来反驳它"。
2. 阶段 5 不只复核 confirmed。文档明确写了"不要只验证 confirmed 记录"，因为一个误导性的 needs_validation 交接会浪费所有者的时间，还可能固化一个错误前提。

## 四、三种结论，各自有硬性格式

这是整个设计里最有实用价值的部分。

| 结论 | 含义 | 必须有 | 不得有 |
| --- | --- | --- | --- |
| confirmed | 完整的源码路径加有界的实际观察结果 | 根因、预期行为、条件、执行方式、修复建议、严重度、置信度 | 阻塞项、验证计划、拒绝原因 |
| needs_validation | 源码里有具体的边界假设，但决定性的事实在源码之外 | 声称的根因、调用路径、证据、阻塞项、至少一个本地或部署侧验证计划 | 严重度、执行结果、修复建议 |
| rejected | 候选已被证伪 | 声称的根因、调用路径、证据、拒绝原因 | 严重度、执行结果、验证计划 |

规则里有几句很直接：

- 只有 confirmed 记录才有严重度。needs_validation"不是低置信度的 confirmed 漏洞"。
- 整体严重度不能超过已证明的影响。
- needs_validation 不能当"存放投机想法的地方"。验证者要判断阻塞项是否真的在源码和本地观察之外。
- rejected 记录保留下来，目的是让之后的运行不会在没有新证据的情况下重复同一个无依据的主张。

把这三类分开，对读报告的人是实际的帮助：你不必在一长串"可能的问题"里自己分辨哪些已经被复现，哪些只是线索。

## 五、"边界加结果"的准入门槛

SKILL.md 的核心原则之一是：每个候选都必须写出五件事。

1. 较低信任级别的主体是谁。
2. 它接受了什么输入或动作。
3. 本应存在的控制措施是什么。
4. 越过了哪条边界。
5. 受影响的主体或资源，以及具体的已观察到或所有者可观察到的结果。

文档同时列出了不应升级为安全发现的情形：缺少最佳实践、对部署行为的猜测、一般性的解析器崩溃、只影响自己的影响。

反模式清单里还有这些：把清单偏离当成漏洞；没有可达边界违例的纵深防御建议；在有界本地证据足够时仍去测线上环境；猜测代理、浏览器或身份提供方行为；报告比实际观察更强的效果；让严重度和 JSON 记录不一致。

这套门槛的作用是压低误报。代价是漏报：任何说不清"谁越过了什么边界"的真实问题，都会被降级。

## 六、写入隔离与沙箱要求

这一块解释了为什么 README 把沙箱列为要求，而不是建议。

### 谁能写什么

- 父智能体是共享文件的唯一写入者：run-metadata.json、architecture.md、coverage-ledger.json、findings.json 和三份报告。
- 每个搜索或验证智能体有独立目录 agents/<id>/，里面分 scratch/ 和 artifacts/。
- 智能体和被审计代码启动的进程只能写 scratch/。
- artifacts/ 由父智能体控制，只能通过可信的"提升"代码写入。

### 运行被审计代码的条件

SKILL.md 要求同时满足：

- 无外部网络（需要本地通信时只用隔离的回环命名空间）。
- 环境变量来自明确的白名单，主目录和缓存指向 scratch。
- 目标和工具链只读。
- 有明确的 CPU、内存、进程数、文件大小、磁盘和时间限制。

如果这些控制做不到，规则是**不执行目标代码**，把缺失的沙箱能力记为 needs_validation 的阻塞项。

另外禁止的事包括：探测线上端点、测试共享进程的可用性、花费付费 API 额度、安装依赖、让构建去联网。

这条规则的实际含义是：在没有沙箱的机器上运行这个技能，它的合规行为是少做事，而不是照做。

## 七、覆盖账本与多次运行

阶段 1 要建立覆盖账本，后续每个智能体的结果都要回写。账本由校验脚本检查，脚本里列出的必填字段包括 coverage_id、surface、boundary、subsystem、attack_class、status、reviewed_paths、result_fingerprints、unresolved 等。

账本的用途是回答"这次到底看了哪些、没看哪些"。SKILL.md 规定了多次运行如何叠加：

- 之前的 confirmed 记录只有在相关源码和条件都未变化时才能带入本次，且仍要经过本次的验证。
- 源码变化过的记录要重新验证。
- 之前的 rejected 只抑制"未变化的同一个失败主张"，不抑制对应单元的覆盖。
- 之前的 quick 或限定范围运行，只贡献它记录过的证据和空缺，不能推出"其余部分没问题"。

文档还给出三档配置：quick、standard、deep，并说明"配置改变的是广度和冗余，而不是证据标准"。预算以智能体调用总次数计，并规定预算不够时的处理顺序，宁可标记为 incomplete，也不静默变薄。

## 八、哪些是自述，无法从仓库验证

README 的设计原则部分有这样一句：在项目自己的测试运行中，单次运行找到的漏洞大约是多次运行合计的一半。这是项目自述。仓库里没有给出测试对象、漏洞数量和统计方法，所以不能当作定量依据。能确认的只是：项目的设计假设是"一次运行不会穷尽目标"，因此要求多次叠加并保留账本。

同样属于自述的还有：这个技能是该公司漏洞发现系统的起点（见上文），以及各项设计"提高了准确率"。仓库没有提供对比实验。

## 九、什么情况下它可能不适合你

| 情形 | 原因 |
| --- | --- |
| 没有能并行调度子智能体的编程智能体 | README 要求模型支持工具调用和并行子智能体 |
| 无法搭建满足条件的沙箱 | 规则要求无网络、白名单环境、只读目标和资源限制，否则不执行代码 |
| 只想快速过一遍 | 完整流程会启动多个智能体，成本高；quick 配置能缓解但会标明是局部覆盖 |
| 需要审计的问题依赖线上部署事实 | 规则禁止探测线上环境，这类问题只会得到 needs_validation |
| 需要有人签字的合规结论 | 输出是智能体的分析，文档并未声称可以替代人工评审 |

## 十、限制与结论

这个技能的核心思想是流程约束：发现与验证分开，结论分三类且格式不同，没有边界和结果的候选不能算发现，没有沙箱就不执行。这些都能在仓库的文档里直接读到。

本文的限制：没有在任何代码库上运行过它；没有测量误报率或漏报率；没有读完全部十几个攻击类别文档，只读了总纲、验证与报告文档以及校验脚本的入口部分；无法核验项目自述的统计。

下一步建议：先在一个你熟悉、且已知存在若干历史漏洞的小仓库里运行一次 quick 配置，比较它的 confirmed 与你已知问题的重合度，再决定是否扩大使用。
