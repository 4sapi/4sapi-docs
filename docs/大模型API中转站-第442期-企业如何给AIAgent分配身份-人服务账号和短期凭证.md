# 企业如何给 AI Agent 分配身份：人、服务账号和短期凭证

“让 Agent 能访问业务系统”首先是身份问题，不只是接口配置。每一次读取客户记录、生成草稿、提交工单或发送通知，都要能回答：谁发起，Agent 用谁的权限执行，权限为什么够用又没有放大，事后怎样撤销。

所有 Agent 共用一个管理员 Key，部署确实快，但审计、收权和事故处置会马上变难。下面不绑定某家身份平台，只比较三种常见模式：用户委托、服务账号和短期凭证，以及它们怎样和审批、日志、最小权限配合。

## 一、先分开四个“谁”

一条 Agent 调用里常常混着多个主体。把它们分开，是后续授权和审计的前提。

| 主体 | 它回答的问题 | 示例 |
| --- | --- | --- |
| 发起用户 | 谁提出业务请求 | 一位客服主管请求生成摘要 |
| Agent 身份 | 哪个自动化系统在编排任务 | `support-summary-agent` |
| 执行身份 | 实际向下游系统出示什么凭证 | 受限服务账号或用户委托令牌 |
| 资源 Owner | 谁负责被访问的数据或系统 | 客户系统、知识库或工单系统负责人 |

日志里不能只留一句“AI 调用了 API”。至少要关联发起用户、Agent 版本、执行身份、目标资源、授权范围、审批事件和结果。出了异常，团队才知道联系谁、撤销什么、影响了哪些任务。

## 二、三种常见授权模式

### 1. 用户委托：按发起人的范围工作

用户委托意味着 Agent 代表当前用户访问其本来有权访问的资源。适合需要遵循个人资料范围的查询、个人草稿或只读助手。

优点是权限与用户自然一致，审计也容易说明“谁请求了什么”。局限是后台长任务、多人协作、用户离线后继续执行，以及跨系统权限映射都会更复杂。用户身份不应自动允许 Agent 执行所有同等权限的高风险写入，仍可在 Agent 层进一步缩小动作集合。

### 2. 服务账号：为一个固定业务职责而存在

服务账号适合固定、可定义的后台职责，例如只读查询某个知识库，或向指定内部队列创建草稿。它不属于具体员工，权限应只覆盖这个职责。

服务账号不能只是“系统管理员账号的别名”。不要用一个万能账号服务所有 Agent。把不同任务拆成不同身份后，即使某个凭证出问题，影响范围也更小，日志也更容易归因。

### 3. 短期凭证：按任务临时授予有限能力

短期凭证可以来自身份平台代理、临时授权或受控令牌交换。重点不在于令牌“更短”，而在于范围、受众、有效期和撤销条件都能绑定到一次任务。

这类模式适合偶发的敏感操作、跨系统自动化或需要人工审批后才可执行的动作。它需要更成熟的身份基础设施和失败处理：令牌过期时 Agent 必须可解释地转人工或重新请求授权，不能无限重试，更不能退回到长期管理员 Key。

## 三、选择模式时看任务，不看工具名称

| 任务 | 推荐起点 | 原因 | 额外控制 |
| --- | --- | --- |
| 查询用户本人可见的资料 | 用户委托 + 只读范围 | 保留个人数据边界 | 记录资源范围与来源 |
| 汇总已发布的内部文档 | 专用只读服务账号 | 业务职责固定 | 限定文档集合与返回量 |
| 创建内部草稿 | 受限服务账号 | 可管理、可审计 | 目标队列白名单与幂等键 |
| 发送外部消息或变更订单 | 短期凭证或人工执行 | 风险与影响高 | 展示确认内容、双重检查、撤销流程 |

同一个工具可能服务不同任务，因此不要根据“它叫邮件工具”或“它叫数据库工具”决定权限。要看实际对象、范围、动作、可逆性和业务后果。

## 四、建立一张身份与权限矩阵

在接入前，把 Agent 的真实操作写进表格。它比一份笼统的“AI 有只读权限”更能发现问题。

| Agent | 执行身份 | 资源 | 动作 | 范围 | 默认模式 | 人工确认 | 失效或撤销方式 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 摘要 Agent | `svc-summary-read` | 产品知识库 | 读取 | 已发布文档 | 自动 | 否 | 禁用账号或策略 |
| 工单 Agent | `svc-ticket-draft` | 工单系统 | 创建草稿 | 指定项目 | 自动 | 否 | 删除草稿或禁用账号 |
| 通知 Agent | 临时任务令牌 | 消息系统 | 发送 | 单一收件人和模板 | 等待审批 | 是 | 令牌过期或撤销 |

矩阵要由业务 Owner 和资源 Owner 一起确认。业务方说明任务为什么需要这个动作，资源方确认哪些数据和操作可以开放。任何一方说不清时，都不要让 Agent 开发者自行猜。

## 五、最小权限不只是少几个 Scope

最小权限至少有五个维度：

```text
资源：只能访问哪一类数据、哪一个工作区或项目。
动作：读取、创建草稿、更新、发送、删除分别授权。
时间：凭证有效多久，长期任务如何续期。
条件：是否仅限指定网络、任务类型、模板或审批后调用。
数量：一次可读取、写入或发送多少对象。
```

“可写工单”这个权限太宽。可以改成：“只能在项目 A 创建草稿，不能变更状态、不能删除、每次任务最多一条，并要求幂等键。”权限细化后，Agent 即使在异常上下文中选错工具，影响范围也小得多。

## 六、不要把长期密钥塞进 Prompt、仓库和前端

长期密钥应放在组织认可的密钥管理或运行时注入机制中，由执行环境按身份和任务读取。下面这些做法都要避免：

```text
把真实 Key 写入 Prompt、Skill、示例文档或聊天记录。
提交到代码仓库、测试夹具或截图。
让浏览器前端直接持有能访问生产资源的密钥。
多个 Agent、环境或个人共用同一个高权限令牌。
为了排错把完整 Authorization 头写进普通日志。
```

日志通常只需要记录凭证标识、身份名称、授权范围摘要、到期时间和调用结果。真的需要查看敏感配置时，应走受控访问流程，而不是在事故群里转发。

## 七、审批要绑定具体动作，而不是绑定一句泛泛授权

当 Agent 需要 L2 或 L3 级动作时，审批记录需要绑定任务与动作内容：

```text
任务和运行编号：批准的是哪一次执行。
执行身份：实际会使用哪个账号或临时令牌。
动作摘要：发送、写入、删除或权限变更的对象与范围。
依据：用户目标、输入来源和规则检查结果。
有效期：这次批准能在多久内使用。
结果：批准、拒绝、过期或已执行。
```

审批通过后，系统仍需在执行前校验任务、目标和范围没有变化。不能因为用户在上午批准过“发送一封通知”，下午就允许 Agent 把修改后的内容发给更多人。

## 八、把紧急撤销做成操作卡

身份设计真正派上用场，往往是在出错时。每个 Agent 至少准备一张短操作卡：

```text
触发条件：发现越权、异常调用量、凭证疑似泄露或错误外部写入。
第一动作：停止相关 Agent 或关闭工具策略。
撤销对象：服务账号、令牌交换策略、审批入口或网络访问规则。
影响判断：查询最近的身份、资源、任务和 run_id。
恢复条件：完成根因分析、回归任务与最小范围验证。
Owner：当班技术负责人、资源 Owner 与业务负责人。
```

撤销演练应在隔离或低风险环境完成，确认关闭一个身份后不会意外影响无关系统。没有经过演练的“紧急开关”，在真正的事故里往往找不到或不敢按。

## 九、从试点开始的实施顺序

```text
1. 选择一个只读或可逆的单一任务，不从外部写入开始。
2. 列出发起用户、Agent、执行身份和资源 Owner。
3. 填写身份与权限矩阵，限定资源、动作、时间、条件和数量。
4. 用测试身份和脱敏数据验证正常、越权、过期、拒绝与撤销路径。
5. 将身份、审批和工具事件关联到 task_id 与 run_id。
6. 灰度到有限工作区，观察异常调用、人工接管和权限拒绝。
7. 复盘后再决定是否扩大范围或增加新的动作。
```

身份体系不需要一开始就覆盖所有系统，但第一批接入必须留下可复制的矩阵、日志和撤销流程。否则之后每增加一个 Agent，都会重新制造一份不可审计的例外。

## 十、检查清单

```text
[ ] 已区分发起用户、Agent 身份、执行身份与资源 Owner。
[ ] 每种业务动作在身份与权限矩阵中都有资源、范围与 Owner。
[ ] 默认使用专用、最小权限身份，不共用个人或管理员 Key。
[ ] 用户委托、服务账号和短期凭证按任务风险选择。
[ ] 权限同时限制资源、动作、时间、条件和数量。
[ ] 高风险动作的审批绑定具体任务、对象、范围和有效期。
[ ] 凭证不出现在 Prompt、仓库、前端、截图或普通日志中。
[ ] Agent、身份、资源、审批和结果可通过 task_id、run_id 关联。
[ ] 已验证令牌过期、权限拒绝、重复调用与异常撤销。
[ ] 紧急停用与恢复步骤有明确 Owner 并经过演练。
```

## 结论与资料

AI Agent 的身份是业务授权的可执行表达，不是藏在环境变量里的技术细节。把发起人、编排者、执行身份和资源 Owner 分开，再用最小权限、具体审批和可演练的撤销流程把它们连起来，Agent 才能进入真实系统运行。

- [NIST：Digital Identity Guidelines](https://pages.nist.gov/800-63-4/)：参考身份、认证与生命周期管理的通用原则。
- [OAuth 2.0 Security Best Current Practice](https://datatracker.ietf.org/doc/html/draft-ietf-oauth-security-topics)：参考令牌范围、生命周期与安全使用建议；实施应以组织的身份平台规范为准。
- [OWASP：Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)：参考最小权限、拒绝优先与授权测试的基础实践。
