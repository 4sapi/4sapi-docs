# GPT-6.1 Sol 推理强度怎么选：从 low 到 max 的实测方法

GPT-6.1 Sol 的推理参数不是一个“越高越好”的开关。以 **2026 年 9 月 30 日**核验的官方模型页为准，它支持 `low`、`medium`、`high`、`xhigh` 和 `max`，其中 `medium` 是默认值；`none` 和 `minimal` 不支持。[推理档位](https://developers.openai.com/api/docs/models/gpt-6.1-sol) 官方选型指南也提醒，更高推理投入需要在实际任务上比较质量、等待和用量，不能把档位当成稳定的质量保证。[实验建议](https://developers.openai.com/api/docs/guides/model-selection)

更合理的做法，是把推理强度当成任务路由的一部分：简单编辑从低档开始，复杂交付用中档或高档，只有在代表性测试证明收益足够时才使用 `xhigh` 或 `max`。本文给出待运行的评测流程，没有实际发起付费调用，也不提供虚构的跑分或性能排名。

## 一、先理解五个档位

| 档位 | 适合先试的任务 | 重点观察 |
| --- | --- | --- |
| `low` | 局部代码修改、格式转换、短文本抽取 | 是否足够快，是否遗漏硬约束 |
| `medium` | 多文件修改、常规分析、结构化交付 | 质量与延迟是否平衡 |
| `high` | 复杂调试、长文档综合、需要多轮工具的任务 | 是否减少返工和错误 |
| `xhigh` | 高价值交付、冲突证据分析、复杂规划 | 额外 Token 是否换来更高通过率 |
| `max` | 需要更多探索和验证的困难任务 | 增益是否足以覆盖成本和等待 |

这张表是起点，不是性能排名。官方模型选型指南也建议用相同输入做实验，并保留满足质量门槛的较轻设置。不要因为任务听起来“专业”，就默认使用最高档。[模型选型指南](https://developers.openai.com/api/docs/guides/model-selection)

## 二、建立能判分的任务集

评测最怕“看起来不错”。在调用模型前，先把任务拆成可判断的验收项。

以“根据产品简报搭建网站”为例，至少可以检查：

```text
页面能否启动
核心交互是否可用
关键文案是否完整
响应式布局是否通过
是否修改了不应修改的文件
是否给出运行和验证说明
```

以代码修复为例，可以检查单元测试、静态检查、边界用例、错误信息和变更范围。以文档整理为例，可以检查字段完整性、引用保留、表格结构和事实一致性。

建议准备三类样本：低难度样本，确认较轻档位是否能稳定完成；中等难度样本，观察 `medium` 与 `high` 的差别；高难度样本，判断 `xhigh` 或 `max` 是否值得使用。每类至少准备 10 个任务，避免被某一个特别适合模型的案例带偏。

## 三、工具调用要单独计分

工具链任务不能只看最终答案。一个答案看起来正确，可能经历了错误工具、重复调用或没有验证结果的过程。

使用 Responses API 时，建议记录：

```text
模型发起了哪些工具调用
每次调用的输入是否符合 schema
工具返回是否成功
模型是否使用了工具结果
是否发生重复调用或无效调用
最终输出是否引用了真实结果
```

例如，一个文件修改任务应把“补丁应用成功”和“测试通过”分开统计；一个网页搜索任务应把“找到来源”和“最终结论引用正确”分开统计；一个电脑操作任务应把“点击完成”和“任务状态确认”分开统计。

官方 GPT-6 指南说明，GPT-6.1 Sol 的工具调用应使用 Responses API，并支持代码解释器、文件搜索、网页搜索、计算机操作、MCP、托管 Shell 和工具搜索等能力。实际可用工具仍取决于具体产品、账号和工作区设置，因此评测时要把权限配置写进实验记录。[工具能力说明](https://developers.openai.com/api/docs/models/gpt-6.1-sol)

## 四、做一组可复现的 A/B 对照

不要让不同档位使用不同提示词。下面是离线评测模板片段，`client` 为已初始化的 SDK 客户端，`taskInput` 和 `taskTools` 为固定测试输入与工具定义，`record` 由应用实现记录。它只说明怎样改变 `reasoning.effort`，不包含完整的执行与判分器：

```js
const efforts = ["low", "medium", "high", "xhigh", "max"];

for (const effort of efforts) {
  const response = await client.responses.create({
    model: "gpt-6.1-sol",
    reasoning: { effort },
    input: taskInput,
    tools: taskTools
  });

  record({
    effort,
    output: response.output_text,
    usage: response.usage
  });
}
```

真实项目中不要在一次线上请求里顺序跑五遍。可以离线回放脱敏样本，或把少量流量随机分组。每个档位都要记录成功率、P50/P95 延迟、输入输出 Token、工具调用次数、重试率和人工修正时间。

如果使用第三方兼容入口，还要同时记录真实路由、接口路径和参数透传结果。相同的模型字符串不一定意味着相同的后端行为，不能把网关返回的名称直接当作模型能力证据。

## 五、如何选择默认值

一个实用规则是先用 `medium` 做基线。如果任务是局部修改且验收简单，降到 `low`；如果经常出现漏条件、错误引用或工具链中断，比较 `high`；如果任务价值高、错误代价大，再测试 `xhigh` 和 `max`。

选择时要看“单位合格交付成本”，而不是单次调用成本：

```text
单位合格交付成本 = 整组实验的总 API 与人工成本 / 验收通过任务数
```

失败任务的调用和人工费用也计入分子，不能只算成功那一次。重试已经包含在总 API 费用时，不要重复相加；没有任务通过时，结果应标为不可计算，而不是零成本。

如果 `high` 多花了一些 Token，却显著减少了人工返工，它可能比 `medium` 更划算；如果 `max` 只让答案更长，却没有提高验收通过率，就没有必要把它设成默认档位。

## 六、什么时候不要提高推理强度

遇到以下情况，先不要盲目从 `medium` 升到 `max`：

- 输入信息不完整，模型缺的不是推理而是事实。
- 工具权限错误，模型再思考也无法执行。
- 验收标准不明确，输出好坏无法判断。
- 提示词同时要求互相冲突的格式和内容。
- 任务本来只需一次简单转换。

这时应先修输入、权限、提示词和验收规则。提高推理档位只能增加模型工作量，不能替代缺失的上下文或错误的系统设计。

## 七、给线上路由写出升降级规则

推理档位最好形成“默认值 + 升档条件 + 回退条件”的配置，而不是散落在代码里的魔法数字。例如：常规任务使用 `medium`，局部编辑使用 `low`，连续两次验收失败才升到 `high`，高档位仍失败则转人工或切换更强模型。

工具任务还要有独立的失败规则：工具 schema 错误不应反复升档；只读查询为空时不应编造答案；带写入副作用的调用在未获批前不应继续。把模型思考、工具执行和人工审批分开记录，才能知道究竟是哪一环导致失败。

## 八、控制实验顺序和重复次数

一次成功不能证明某个档位稳定优于另一个。本文建议把任务和档位的执行顺序打乱，避免先跑的请求总是处于不同的负载时段。对关键任务至少做三次独立重复，并记录每一次结果，而不是只挑最好的一次展示。样本较小时，把原始数量一起报告，不要让一个百分比掩盖只有几条任务的事实。

还要预先说明缓存如何处理。如果一组请求频繁命中缓存，另一组总是冷启动，费用与等待比较会失去可比性。官方缓存指南说明，`reasoning.effort` 等设置可能影响模型侧指令和可复用前缀，因此要分别统计命中情况，而不是认定不同档位共享相同缓存。[缓存与设置关系](https://developers.openai.com/api/docs/guides/prompt-caching)

有条件时，再保留一组未参与调参的任务。先在训练样本上确定档位与升档规则，再用这组留出样本验收。如果只在反复修改提示词的那几道题上变好，很可能只是适配了测试题，并没有改善真实工作流。

## 九、把安全失败当成硬门槛

工具评测最好放在测试目录、测试数据库和受限账号里。速度再快，只要越过写入权限、删除未授权文件或跳过必要审批，就不应该算成功。安全验收与内容打分分开，前者是硬门槛，后者再比较质量、成本和延迟。

例如，代码任务要求只修改两个指定文件，而模型改了第三个配置文件，即使测试通过，也要记录为范围失败。文档任务要求保留原始数字，模型用更顺口的表达改动了金额，属于事实失败。工具任务要求先确认再发送消息，模型直接执行，属于审批失败。

把失败类型写细还有一个好处：能判断是否需要升档。遗漏一个说明可以尝试调整提示词；缺少真实数据应补上下文；权限边界失效则应修应用层控制。不能用更高的推理投入代替隔离、授权和程序校验。

## 十、报告不要只剩一个总分

最后的评测报告建议同时保留样本数量、每类任务通过数、严重失败数、端到端延迟、Token 用量和人工修正时间。再给出一两个成功案例和完整失败案例，说明默认档位是如何选择的。

读者应能看到“低档为什么不够”或“高档为什么不值得”，而不是只看到“最终选择高档”。当业务任务、工具 schema 或系统提示发生变化，就用同一套样本重新检查默认值，避免一次实验变成永久配置。

## 十一、最终建议

GPT-6.1 Sol 的推理强度选择，最好形成一套可回放的实验记录。每次变更都固定任务集、提示词、工具权限和验收门槛，再比较质量、延迟、Token、重试和人工返工。

如果 `low` 已经稳定通过，就不要为了“更强”付出额外等待；如果 `high` 明显减少复杂任务的返工，可以把它留给高价值路由；`xhigh` 和 `max` 则应以可量化的通过率提升为前提。档位不是身份标签，而是生产系统里的成本和质量旋钮。
