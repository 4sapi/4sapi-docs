# Claude Fable 5.1 首轮测评：先看长任务和工具调用是否可靠

最近有人把一个新模型名称写成“Claude Fable 5.1”，并希望直接拿来做代码、资料整理和自动化任务。

真正麻烦的地方不是会不会聊天，而是这个型号能不能在一项长任务里保持目标、正确使用工具，并在没有完成时明确说出来。

本文只解决一个问题：如何对 Claude Fable 5.1 做一轮不夸大的首轮测评。

先说明范围。

截至本文写作日（2026-09-02），当前仓库没有保存该型号的官方发布页、版本公告、价格表或完整原始跑分。

因此，文中的“Fable 5.1”是本次测评使用的模型标签，不把它当成已经被官方资料确认的产品事实。

如果你的控制台显示的是其他模型 ID，请把实际 ID、提供方和路由记录补进测试表，再复用本文方法。

## 一、这轮测评要回答什么

首轮测评不追求一次给模型排位，而是回答四个更具体的问题：

```text
它能否准确执行明确指令？
它能否在长上下文中保持任务状态？
它能否调用工具并根据结果修正方案？
它的输出是否方便人工验收和回滚？
```

这四个问题分别对应聊天、长文档、Agent 和工程交付场景。

如果只测试一句问答，最多能说明语言表达体验，无法说明它是否适合长任务。

## 二、先把事实、观察和判断分开

模型测评最容易出现的问题，是把体验句子写成产品事实。

本文采用三种标记：

| 标记 | 含义 | 写法示例 |
| --- | --- | --- |
| 已核验 | 有官方文档或原始日志支持 | “请求返回 200，模型 ID 为……” |
| 本次观察 | 只代表本轮环境和样本 | “在本轮任务中，它完成了……” |
| 待确认 | 缺少资料或需要复测 | “尚不能据此判断长期稳定性” |

“支持多少上下文”“是否原生多模态”“价格是多少”都属于可变事实。

没有一手来源或控制台记录时，不应凭模型名称推断这些能力。

同样，“比上一代更快”“编码能力提升”“更适合企业”也需要同条件对照，不能用印象代替证据。

## 三、测试环境记录表

开始测试前，先建立一份环境记录。

建议把下面的表格保存为 `fable51-test-run.md`，每跑一次就复制一份。

| 字段 | 本次记录 |
| --- | --- |
| 测试日期 | 2026-09-02（Asia/Shanghai） |
| 模型显示名称 | Claude Fable 5.1（待确认标签） |
| 实际 model ID | 以控制台或 API 响应为准 |
| 提供方/路由 | 以请求日志为准 |
| 客户端版本 | 填写 CLI、SDK 或网关版本 |
| 仓库提交 | 填写 Git commit；没有仓库则写输入快照哈希 |
| 操作系统 | 填写系统与版本 |
| 权限 | 只读、工作区写入、联网、外部发送分别记录 |
| 重试规则 | 预先约定最多重试次数 |
| 测试样本 | 任务编号、输入文件和验收标准 |

如果通过 4SAPI 这类兼容网关调用，建议额外记录 `request_id`、`model`、`route`、`status` 和 `usage`。

这里的网关只作为可替换的记录实例，不代表它在价格、速度或稳定性上优于其他入口。

## 四、测试任务不要只准备一道题

我建议至少准备五类任务，每类任务都有独立验收条件。

| 任务 | 输入 | 验收条件 |
| --- | --- | --- |
| 指令跟随 | 一段有格式约束的需求 | 字段齐全、顺序正确、没有额外内容 |
| 长文档抽取 | 多份带冲突日期的资料 | 标出来源、时间和冲突点 |
| 受控编码 | 一个最小复现仓库 | 测试通过且 Diff 在约定目录 |
| 工具调用 | 文件搜索、脚本和测试命令 | 工具参数正确，结果被实际引用 |
| 失败恢复 | 人为制造的超时或错误 | 能区分重试、降级和人工确认 |

不要把五类任务拼成一条超长提示词。

每个任务单独运行，才能知道失败发生在哪一层。

## 五、任务一：指令跟随怎么测

第一项测试可以很小，但要故意加入容易混淆的约束。

示例输入：

```text
请把下面三条需求整理成 JSON。
要求：
1. 只能输出 JSON，不要 Markdown 代码围栏。
2. 每项必须包含 id、risk、next_step 三个字段。
3. risk 只能是 low、medium、high。
4. 原文没有提到的信息写 null，不要自行补充。
```

验收时不要只看 JSON 能否解析，还要检查：

```text
字段是否完整。
枚举值是否越界。
缺失信息是否真的保留为 null。
是否偷偷添加了原文没有的事实。
```

这一项主要测“遵守边界”，不是测文采。

如果模型回答很漂亮，却多写了一个未经输入支持的日期，仍应判为失败。

## 六、任务二：长上下文不能只看窗口大小

长上下文测评的重点，不是把文本堆到最大，而是看模型能否持续引用正确状态。

可以准备十到二十份短文档，分别写入：

```text
项目目标。
模块负责人。
版本限制。
已知缺陷。
互相冲突的日期。
需要人工确认的动作。
```

在文档末尾提出跨文件问题，例如：

```text
找出所有关于上线日期的冲突。
只采用最后更新时间较新的来源。
列出仍需人工确认的事项。
不要修改任何原文。
```

验收要看三点：

1. 是否引用了正确文件；
2. 是否把冲突和确定事实分开；
3. 是否保留了“待确认”状态。

如果模型只给出一个看似确定的日期，却没有说明来源，不能算长上下文能力通过。

## 七、任务三：编码测评要把 Diff 纳入结果

编码任务建议使用一个很小的仓库，避免环境问题盖过模型差异。

例如，仓库包含一个解析配置文件的函数，现有测试明确暴露一个边界错误。

提示词可以这样写：

```text
先阅读 README 和测试，再定位失败原因。
只允许修改 src/parser 和 tests/parser 目录。
不要升级依赖，不要修改 CI，不要联网下载新包。
完成后运行指定测试，并说明仍未验证的部分。
```

编码测评至少记录：

| 指标 | 记录内容 |
| --- | --- |
| 正确性 | 新增与原有测试是否通过 |
| 范围 | 修改文件是否越界 |
| 过程 | 工具调用轮数、失败命令和重试次数 |
| 交付 | Diff 是否可读，是否附带验证命令 |
| 人工成本 | 需要人工修正的分钟数 |

模型说“已修复”不等于任务完成。

只有测试结果、Diff 和验收标准同时满足，才可以记为 `PASS`。

## 八、任务四：工具调用看结果，不看姿势

工具调用测评应设计一个必须读取真实结果的任务。

例如，让模型扫描目录，找出没有许可证字段的配置文件，再生成清单。

正确流程应接近：

```text
列出目录 → 读取候选文件 → 解析字段 → 生成清单 → 再次抽查
```

如果模型没有执行读取，只凭文件名猜测结果，应该记为 `FAIL`。

如果工具返回错误，模型需要说明：

```text
错误发生在哪一步。
是否可以安全重试。
重试前是否需要改变参数。
是否必须暂停请求人工处理。
```

这比单纯统计调用次数更有意义。

工具调用越多，不代表完成质量越高；无效调用还可能增加成本和失败面。

## 九、任务五：失败恢复决定能不能进长任务

可以人为制造三种故障：

```text
一次网络超时。
一个命令返回非零退出码。
一个工具返回字段缺失。
```

预先写好规则：网络超时允许重试一次；命令失败必须先读取错误；字段缺失不得自行编造。

观察模型是否能保持任务状态，而不是从头开始乱跑。

失败恢复的结果建议分为四类：

| 状态 | 含义 |
| --- | --- |
| `PASS` | 按规则恢复并完成验收 |
| `PARTIAL` | 主流程完成，但仍有明确缺口 |
| `FAIL` | 越界、编造结果或关键验收失败 |
| `INFRA_ERROR` | 外部服务故障，无法判断模型能力 |

把 `INFRA_ERROR` 和模型失败分开，才能避免误判。

## 十、首轮观察应该怎么写

如果只跑了一次，建议使用下面这种表述：

```text
本轮为单次 smoke test，样本量不足以支持模型间排名。
在指令跟随任务中，输出格式符合要求；
在工具调用任务中，仍需人工检查工具结果是否被完整引用；
长任务稳定性和异常恢复能力待更多样本验证。
```

不要把它改写成没有条件的排名、稳定性或成本结论。

例如，单次输出通过格式检查，不能推出它在所有任务中都更快、更稳或更省。

这类结论既没有测试条件，也没有可追溯证据。

## 十一、推荐的评分卡

为了减少“感觉很好”的影响，可以给每项任务打四档分数。

| 分数 | 含义 |
| --- | --- |
| 0 | 未执行、越界或结果不可用 |
| 1 | 完成部分步骤，需要大量人工接管 |
| 2 | 基本完成，但有可修复缺口 |
| 3 | 按验收标准完成，并留下证据 |

评分时先看是否通过硬性条件，再看表达质量。

例如，代码测试失败时，即使解释写得很清楚，也不能把正确性记为 3 分。

建议把评分拆成：指令、事实、工具、交付四列，而不是只保留一个总分。

## 十二、重复运行和对照组

单次体验只能说明一次观察。

如果要比较 Fable 5.1 与已有模型，至少固定：

```text
同一仓库提交。
同一提示词。
同一权限。
同一工具版本。
同一验收标准。
```

每个任务建议运行三次，预算允许时运行五次。

执行顺序应交错，避免某个模型总在网络繁忙时运行。

汇总时先报告通过率，再报告通过样本的中位耗时和 Token。

不要把失败运行剔除后，只展示最短的一次。

## 十三、API 接入时先核对模型身份

新模型最常见的接入误判，是请求成功但实际调用了别的模型。

在兼容接口中，至少检查：

```text
请求体里的 model。
响应中的 model 或等价字段。
网关日志中的路由目标。
失败时返回的错误码和消息。
```

如果响应没有返回模型身份，就把“模型身份未回显”记为风险项，而不是默认相信前端下拉框。

通过 4SAPI 作为示例入口时，可以给每次请求增加 `project`、`environment` 和 `request_id`，便于把测试结果和日志对上。

示例配置只保留结构，不填真实密钥：

```bash
export MODEL_BASE_URL="https://example.invalid/v1"
export MODEL_API_KEY="replace-me"
export MODEL_NAME="claude-fable-5.1"
```

上面的地址和模型名只是占位示例，实际值必须以当前提供方文档和控制台显示为准。

## 十四、常见接入失败与排查顺序

### 1. 返回 404 或 model not found

先检查模型 ID 是否拼写正确，再确认当前 Key 是否有该模型权限。

不要因为网页显示“Fable 5.1”就直接猜测 API 名称。

### 2. 返回 400 参数错误

把请求缩减到最小字段，只保留 `model`、`messages` 和必要的生成参数。

逐个恢复可选参数，并记录是哪一个字段触发错误。

### 3. 流式输出中断

先关闭流式，确认非流式请求能否完成。

如果非流式成功，再检查客户端对事件类型、空增量和结束标记的处理。

### 4. 工具调用字段丢失

保存原始响应，不要只看 SDK 二次封装后的对象。

检查工具名、参数 JSON 和工具结果是否按同一 `tool_call_id` 关联。

## 十五、安全和成本边界

测评 Key 不应直接复用生产 Key。

建议单独建立测试项目，限制额度和可调用模型，并关闭不必要的外部写权限。

长上下文和多轮工具调用会放大输入、输出与重试成本。

成本记录至少包括：

```text
输入 Token。
输出 Token。
缓存 Token（如果提供方返回）。
重试次数。
人工修正时间。
```

Token 少不一定更便宜，模型单价也不等于一次任务成本。

真正需要比较的是“通过一次验收所花的总资源”。

## 十六、哪些场景暂时不适合直接上线

在以下条件不满足前，不建议把新型号直接接入无人值守循环：

```text
模型身份无法核验。
成功标准无法写清。
失败后没有停止规则。
工具权限没有分层。
没有原始日志和回放记录。
没有人工接管入口。
```

可以先用只读任务、沙箱仓库和小额度 Key 做灰度。

等通过率、越界率和人工修正时间有连续样本后，再决定是否扩大范围。

## 十七、最终结论

对 Claude Fable 5.1 的首轮测评，重点不是给出一个夸张排名，而是确认它在明确条件下能否完成可验收工作。

目前仓库没有该型号的官方资料和完整原始跑分，因此本文不对上下文上限、价格、发布日期或跨模型性能下结论。

可复用的结论只有两条：

第一，测评必须同时看指令、事实、工具和交付，不能只看聊天观感。

第二，任何“更快”“更稳”“更便宜”的说法，都要回到同一模型 ID、同一任务、同一权限和重复样本中验证。

如果后续拿到官方文档或三次以上原始运行记录，只需补齐环境表、结果表和引用位置，就能把本文升级为正式对照测评。
