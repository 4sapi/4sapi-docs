# Agent 出错后如何复盘：从执行轨迹到可修复根因

Agent 出错后，团队常见的处理方式有两种：把整段对话再贴给模型，或者一句话归因于“模型不够聪明”。前一种做法常常漏掉版本、权限和工具状态；后一种做法则跳过了任务定义、输入质量、环境和实现这些更容易修的部分。

复盘要把四件事说清楚：发生了什么，影响了哪些任务，为什么在当前条件下发生，以及怎样证明修复没有带来新的退化。本文接续第 439 期的运行观测，适用于有工具调用、检索、审批或外部写入的 Agent。

## 一、先止损，再解释

复盘前先止损。对于可能影响外部系统的 Agent，先处理行动边界：

```text
1. 停止或缩小相同路径的自动动作。
2. 保留失败任务、版本、权限和关键事件的引用。
3. 确认是否发生外部写入、重复通知或敏感数据访问。
4. 需要时撤销短期凭证、关闭工具或切回草稿模式。
5. 向受影响的业务 Owner 说明已知事实与暂未确认的部分。
```

不要在证据尚未保全前修改线上 Prompt、重跑生产任务或清理日志。修复可以很快，但覆盖现场会让后续无法判断修复是否真的有效。

## 二、为每次失败建立最小证据包

故障单不用一开始就写成长报告，但至少要让另一位同事能够复现，或者明确指出你的判断哪里不成立。目录可以这样组织：

```text
incidents/INC-2026-0813-001/
  summary.md
  task-card.md
  input-reference.json
  run-events.jsonl
  tool-calls.jsonl
  result-before-review.json
  review-notes.md
  environment.json
  redactions.md
  reproduction.md
```

`input-reference.json` 记录输入的受控引用、哈希、长度、数据版本和访问位置，不应为了方便把敏感原文复制到每份事故目录。`environment.json` 则记录 Agent 代码、Prompt 或 Skill、模型路由、工具版本、知识快照、权限档位和重试规则。

一页摘要应先写事实而不是原因：

| 字段 | 示例写法 |
| --- | --- |
| 现象 | 工单摘要遗漏了已尝试措施，人工改为不可交付 |
| 首次发现 | 某日某时，来自人工评审队列 |
| 影响 | 两项内部草稿未发送，无外部写入 |
| 当前状态 | 草稿模式保留，相关任务已转人工 |
| 证据 | 指向 run_id、输入版本、评审记录 |
| 尚不确定 | 是否只影响包含附件引用的任务 |

“模型幻觉”只是猜测，不应直接写进现象栏，应留在待验证假设中。

## 三、沿执行轨迹重建事实

Agent 的最终回答只是最后一个节点。复盘需要按时间线核对每一步发生了什么：

```text
接收任务 -> 准备上下文 -> 读取资料 -> 调用工具 -> 处理工具返回
-> 请求审批 -> 生成结果 -> 写入或交接 -> 人工发现问题
```

对于每个节点，回答三个问题：输入是什么、系统做了什么、输出或错误是什么。下面是一个简化检查表：

| 节点 | 要查的证据 | 常见误判 |
| --- | --- | --- |
| 输入 | 任务卡、字段完整性、数据版本 | 把用户未提供的信息当成模型遗漏 |
| 上下文 | 检索结果、截断和排序信息 | 只看知识库里是否“存在”资料 |
| 工具 | 参数、返回、超时和重试 | 忽略工具只返回了部分数据 |
| 权限 | 授权范围、拒绝和审批事件 | 把正常拒绝当成系统故障 |
| 推理与生成 | 结构化输出、引用、未知项 | 只凭语气判断是否正确 |
| 下游动作 | 幂等键、写入结果、通知记录 | 忽略重复执行造成的影响 |

轨迹日志要保留失败尝试。只留下重试后的正确结果，会看不见同一任务实际消耗了多少资源，也容易漏掉偶发但高风险的行为。

## 四、先分类，再选择修复层

一个可行动的分类框架如下：

| 类别 | 可观察现象 | 优先修复层 |
| --- | --- | --- |
| 任务定义 | Agent 完成了相邻目标，验收双方理解不同 | 任务卡、输出契约、示例 |
| 输入或上下文 | 必要资料缺失、过期、截断或无法检索 | 数据、索引、来源与上下文预算 |
| 工具契约 | 参数不匹配、返回为空、幂等性缺失 | 接口、校验、超时与重试策略 |
| 权限与审批 | 越权尝试、无权却继续执行、审批绕过 | 最小权限、策略与人工节点 |
| Agent 实现 | 状态恢复错误、循环调用、错误未暴露 | 代码、状态机、退出条件 |
| 模型或路由 | 固定条件下行为稳定退化 | 模型选择、Prompt、回退策略 |
| 环境与依赖 | 网络、服务、版本或配置漂移 | 发布、依赖、环境健康检查 |
| 验收缺口 | 无法判定什么结果应算合格 | 测试集、评分规则和评审说明 |

分类不是为了给事故贴标签，而是为了决定修哪一层。工具返回被截断的搜索结果时，继续改 Prompt 也不会凭空补出缺失事实；业务要求本身不清楚时，增加检索只会带来更多噪声。

## 五、用假设表避免“看完结果才解释”

把每个可能原因写成可证伪的假设，再决定要查看的证据。

| 假设 | 支持它的证据 | 能推翻它的证据 | 验证动作 |
| --- | --- | --- | --- |
| 附件资料未进入上下文 | 轨迹没有附件引用 | 同 run 中有完整附件内容 | 固定任务重跑并记录上下文清单 |
| 检索工具超时后返回空列表 | 有超时事件且最终没有来源 | 工具返回正常且结果被忽略 | 单独调用工具并检查错误处理 |
| 输出格式变更导致下游遗漏字段 | 版本切换后解析失败 | 字段实际存在且解析正常 | 对照契约运行结构检查 |

一条证据可能同时支持多个假设，别急着宣布根因。至少要找到一个能稳定复现的条件；如果暂时做不到，就记录“当前无法复现，只能缓解与观测”。

## 六、修复前先写回归任务

复盘最后要留下一个下次变更还能再跑的任务，而不只是会议纪要。回归任务应包含：

```markdown
目标：复现某类附件引用任务的摘要遗漏
输入：固定脱敏样例与资料版本
允许动作：读取指定资料、生成草稿
禁止动作：外部写入与额外联网
预期：输出包含“已尝试措施”；资料不足时列为未知；引用可回到输入
失败条件：字段缺失、无来源结论、调用未授权工具、重复副作用
```

修复后别只重跑那条“曾经失败的样例”。至少再跑一条正常任务、一条相邻边界任务和一条权限或工具错误任务。否则很可能修好一条路径，又在另一条路径上制造新问题。

## 七、区分修复验证与发布决定

修复验证只回答“这项改动是否解决已知问题”。发布决定还要考虑影响范围、未知风险、回滚能力和人工接管。

```text
修复验证通过：固定回归任务与相邻任务符合预期。
灰度可用：有限任务范围内有观测、接管和回滚路径。
不宜扩大：根因不清楚、关键证据缺失，或仍会触及高风险动作。
需要回滚：当前版本引入阻断性错误，且旧版本或草稿模式可恢复。
```

不要把“无法复现”写成“已经修复”。它最多意味着当前证据不足；后续应增加观测字段、保留隔离策略，或通过受控样例继续验证。

## 八、一次复盘的最小模板

```markdown
# INC-编号：简短标题

## 事实与影响
- 发现方式：
- 受影响任务与时间范围：
- 是否有外部副作用：
- 当前缓解措施：

## 运行条件
- Agent / Prompt / Skill 版本：
- 模型与路由：
- 工具、知识与权限版本：
- 输入引用与脱敏说明：

## 执行轨迹
- 关键事件：
- 错误与重试：
- 人工评审结果：

## 假设与验证
| 假设 | 证据 | 验证结果 |

## 根因与修复
- 已确认根因：
- 不确定项：
- 改动：
- 回滚方式：

## 回归与后续
- 新增任务：
- 验证范围：
- 负责人和复核日期：
```

其中“已确认根因”和“不确定项”必须并列。复盘文档最危险的状态，是把便利的推测包装成完整解释。

## 九、复盘完成前检查清单

```text
[ ] 已先停止、限制或转人工处理可能有副作用的路径。
[ ] 保存了 run_id、事件、版本、权限和输入引用。
[ ] 敏感内容遵守脱敏与访问政策。
[ ] 现象、影响与原因没有混写。
[ ] 已沿任务、上下文、工具、权限和下游动作查看轨迹。
[ ] 根因假设有能支持或推翻它的证据。
[ ] 修复对应明确层级，没有默认只改 Prompt。
[ ] 新增了固定回归任务，并覆盖相邻边界。
[ ] 发布决定包含观测、人工接管与回滚方式。
[ ] 未确认的风险仍留在待办，而不是被“无法复现”关闭。
```

## 结论与资料

好的复盘能从异常结果回到当时的任务、环境和行动轨迹，再把修复沉淀成可重复的回归任务。这样，失败不会被简单归咎于模型，也不会随着下一次版本更新被遗忘。

- [Google SRE Book：Postmortem Culture](https://sre.google/sre-book/postmortem-culture/)：参考无责复盘、事实记录与后续行动的工程原则。
- [OpenAI：Evals guide](https://developers.openai.com/api/docs/guides/evals)：参考把失败样例沉淀为可重复评估数据的思路。
- [OWASP：Top 10 for Large Language Model Applications](https://owasp.org/www-project-top-10-for-large-language-model-applications/)：参考把提示注入、过度代理与不安全输出纳入调查的风险类别。
