# Vibe Coding 常用 UI 组件怎么做：从 Modal 到 Command Palette

让 Agent 生成一个 Modal、Toast 或 Carousel 并不难。难的是把它放进真实工作流以后，用户能不能在键盘下完成操作，错误发生时能不能知道怎么修复，手机端打开以后会不会遮住提交按钮，关闭以后焦点会不会跑到页面角落。

UI 组件不是一张静态截图，而是一组状态和转换。一个 Modal 至少有打开、关闭、提交、加载和错误；一个表单至少有空值、输入中、校验失败和提交成功；一个轮播至少要处理上一张、下一张、暂停和触摸滑动。提示词只描述颜色和圆角，Agent 就会优先完成“看起来像”，而不是“用起来对”。

本文把 10 个常用组件拆成可执行的设计要求，并给出一张状态矩阵、一份完整提示词和一套浏览器验收流程。组件数量不是越多越好，选择它们的前提是它们确实服务于页面任务。

## 1. 先把组件写成状态机

每个交互组件都可以先用四个问题描述：

```text
谁触发：点击、键盘、悬停、滚动、拖动还是页面加载？
发生什么：显示、切换、提交、加载、定位还是确认？
怎么结束：完成、关闭、取消、超时、失败还是用户离开？
用户怎么知道：焦点、文本、图标、颜色、进度、错误说明还是 URL？
```

例如“点击按钮打开设置弹窗”还不够具体，应继续补充：

```text
初始：弹窗隐藏，焦点在打开按钮。
打开：弹窗显示，标题可读，焦点进入第一个表单控件。
提交：按钮进入 loading，避免重复提交。
错误：字段附近显示具体原因，焦点移动到第一个错误字段或错误摘要。
关闭：Esc、关闭按钮和取消按钮都能关闭，焦点回到打开按钮。
```

这段状态描述比“做一个简洁的设置弹窗”更容易被 Agent 正确实现，也更容易在截图和键盘测试中发现缺口。

## 2. Modal：处理需要用户决定的短流程

Modal 对话框适合确认、编辑、选择和短表单。它会暂时打断背景内容，因此只应该承载一个清晰任务，不要把一整页后台塞进弹窗。

### 必须明确的行为

```text
触发：打开按钮有可读名称，并明确弹窗用途。
进入：焦点移动到标题、关闭按钮或第一个可操作控件。
操作：背景不可误触，提交按钮有默认、loading、成功和错误状态。
关闭：关闭按钮、取消按钮和 Esc 的行为分别定义。
恢复：关闭后焦点回到触发元素，背景滚动位置不丢失。
```

### 可复制提示词

```text
创建一个用于编辑项目资料的 Modal。
使用语义 dialog 结构，包含标题、说明、表单、取消和保存按钮。
打开后管理焦点，关闭后恢复到原来的打开按钮；背景内容不能被键盘访问或误点击。
保存期间按钮显示 loading 并阻止重复提交；失败时显示错误摘要和字段级错误。
桌面端最大宽度 560px，手机端改为接近全屏的可滚动面板，底部操作按钮始终可见。
按 Esc 关闭，但如果表单存在未保存修改，先显示二次确认。
```

原生 `dialog` 的细节可以参考 MDN 的 [`<dialog>`](https://developer.mozilla.org/en-US/docs/Web/HTML/Element/dialog) 文档。不要只给弹窗加一个半透明背景；焦点、滚动锁定和关闭后的恢复才决定它是否能用于真实任务。

## 3. Drawer：把次级任务放到侧面或底部

Drawer 从左、右或底部滑入，常用于筛选、导航、设置和移动端操作。它比 Modal 更适合承载一组相关内容，但不应该用动画掩盖层级混乱。

### 方向如何选择

```text
左侧：常见于全局导航和文档目录。
右侧：常见于详情、属性、检查和辅助信息。
底部：常见于手机筛选、分享和操作菜单。
```

### 可复制提示词

```text
创建一个项目筛选 Drawer。
桌面端从右侧打开，宽度 360px；手机端从底部打开，最大高度为视口的 85%。
标题区包含关闭按钮，内容区独立滚动，底部固定“清除”和“应用”操作。
打开后焦点进入关闭按钮，Esc 和关闭按钮都能关闭，关闭后焦点回到筛选触发器。
应用筛选时显示 loading，失败时保留用户已选条件并给出重试入口。
背景遮罩和页面滚动锁定不要影响 Drawer 内部的滚动。
```

Drawer 和 Modal 的主要区别是内容量与空间关系，不是“一个从侧面进来、一个从中间进来”。如果抽屉里有复杂编辑流程，要重新判断是否应该独立成页面，避免在狭窄区域里塞入难以阅读的表格。

## 4. Accordion：收起低优先级内容

Accordion 手风琴适合 FAQ、设置分组和补充说明。它让用户逐项展开，而不是一次把所有内容都铺开。

### 可复制提示词

```text
创建一个 FAQ Accordion，共 6 个问题。
每个问题使用真实 button，关联自己的内容面板，正确设置 aria-expanded 和 aria-controls。
默认只展开第一项；打开一项时是否关闭其他项要保持一致。
面板展开后内容仍然可以被键盘访问，关闭后不保留不可见控件的焦点。
移动端保持完整的标题和点击区域，错误或加载中的内容不能静默消失。
```

Accordion 的标题应该是用户能够独立理解的问题，而不是“更多信息”“点击查看”这种没有上下文的文字。若所有内容都需要同时比较，Accordion 会增加记忆成本，应该使用普通分组或表格。

## 5. Tooltip：补充短信息，不承载关键内容

Tooltip 适合解释图标、缩写和不常见的操作。它不适合放长段说明、必填规则或唯一的操作入口，因为触摸设备没有稳定的悬停状态。

### 验收重点

```text
图标按钮本身有可访问名称，Tooltip 只是补充说明。
鼠标悬停、键盘获得焦点和触摸长按的行为有明确取舍。
Tooltip 不被视口边缘裁切，也不遮挡当前正在操作的控件。
用户移动到 Tooltip 内容时不会瞬间消失。
减少动态效果时不播放夸张的飞入动画。
```

### 可复制提示词

```text
为设置页的图标按钮添加 Tooltip。
Tooltip 文本限制在一到两行，使用 aria-describedby 关联，不把关键操作只放在 Tooltip 里。
键盘 focus 时显示，失去焦点时关闭；Esc 可以关闭；在靠近视口边缘时自动调整方向。
移动端提供可见的辅助文本或帮助区域，不依赖 hover。
```

如果用户需要阅读很长的解释，应使用帮助文本、Popover 或侧栏，而不是把 Tooltip 做成小型文档。

## 6. Toast：反馈结果，但不能替代错误处理

Toast 适合通知“已复制”“保存成功”“已加入队列”等短暂结果。它不适合承载必须阅读的错误、重要决策或需要用户输入的内容。

### 一个合格的 Toast 需要什么

```text
触发：明确由哪个操作产生，避免无来源地自动弹出。
内容：一句话说明发生了什么，必要时提供撤销或查看详情。
状态：success、info、warning、error 有不同语义，不只换颜色。
通知：使用合适的 aria-live，让屏幕阅读器能获得结果。
关闭：自动消失时给足阅读时间，也提供手动关闭。
堆叠：多条通知有顺序、有上限，不覆盖页面主要操作。
```

### 可复制提示词

```text
创建右下角 Toast 区域，支持 success、info、warning、error 四种状态。
每条通知有简短标题、说明和关闭按钮；成功消息可自动消失，错误消息保持到用户关闭。
使用 aria-live="polite" 处理普通通知，错误通知需要根据严重程度选择更强的提示方式。
移动端 Toast 适配安全区域，不遮挡底部导航、提交按钮和键盘输入区域。
减少动态效果时取消位移动画，但保留状态变化和可读文本。
```

错误信息如果会影响表单提交，必须同时出现在表单内，而不能只在右下角短暂闪过。Toast 是反馈通道，不是唯一的错误存储位置。

## 7. Carousel：控制一组需要顺序浏览的内容

Carousel 轮播适合精选内容、图片组和有限数量的推荐项。它不适合把所有重要内容藏在自动播放的横向轨道里。

### 可复制提示词

```text
创建一个项目精选 Carousel，共 4 个面板。
提供上一项、下一项、当前页指示器和暂停自动播放的控制。
默认不自动播放；如果启用自动播放，悬停、focus、触摸和页面不可见时暂停。
所有面板都能通过键盘访问，当前面板和隐藏面板的可访问性状态清晰。
移动端支持触摸滑动，但保留可见的按钮和页码，不能只依赖手势。
```

自动播放的轮播常见三个问题：用户还没读完就切换，键盘焦点跟不上视觉内容，以及移动端左右滑动和页面滚动发生冲突。若每一项都很重要，网格或纵向列表通常更容易阅读和比较。

## 8. Lightbox：放大媒体，也要提供返回路径

Lightbox 适合查看大图、视频或作品细节。缩略图负责浏览，Lightbox 负责沉浸查看；它不能让用户丢失当前媒体的位置。

### 可复制提示词

```text
为作品集图片创建 Lightbox。
点击缩略图后打开全屏媒体查看器，显示媒体标题、当前序号、上一张、下一张和关闭按钮。
打开后焦点进入关闭按钮；Esc 关闭并回到原来的缩略图；左右方向键切换媒体。
图片保留清晰的 alt 或旁边的文字说明，加载失败时显示占位和重试。
手机端不让媒体超出视口，控制按钮适配 safe-area，双击和缩放手势不能阻止关闭。
```

如果 Lightbox 里有视频，要额外处理暂停、音量、加载和错误；如果媒体需要被单独分享，考虑用 URL hash 或独立详情页表达当前项目，而不是只保存在组件内部。

## 9. Form：把输入、校验和结果连成一条路

表单是最容易暴露组件质量的地方。输入框、选择器、复选框、按钮和错误提示必须组成一个可以完成任务的系统。

### 表单状态矩阵

| 状态 | 用户看到什么 | Agent 必须实现什么 |
| --- | --- | --- |
| empty | 标签、占位说明、必填提示 | label 与控件关联，不依赖 placeholder |
| focus | 当前输入项明确 | 键盘焦点可见，不能被颜色背景吞掉 |
| filled | 已输入值和格式说明 | 保留值，格式错误不要静默清空 |
| loading | 提交正在处理 | 禁止重复提交，保留用户输入 |
| error | 字段或摘要说明原因 | 错误与字段关联，给出修复方法 |
| success | 结果和下一步 | 告知是否完成，提供继续或返回入口 |
| disabled | 不可用原因清楚 | 不仅降低透明度，必要时解释前置条件 |

### 可复制提示词

```text
创建一个联系表单：姓名、邮箱、项目类型、需求说明和提交按钮。
每个控件都有可见 label，字段级错误紧邻控件，并使用 aria-describedby 关联说明。
提交前校验格式，提交中显示 loading 并保留内容；失败时显示错误摘要和重试按钮。
成功后显示明确结果，不要只把按钮文字改成“完成”。
移动端单列排列，错误文本换行不破坏布局，键盘打开时提交按钮仍能滚动到视口内。
```

表单的错误文案要回答“哪里错了”和“怎么改”，例如“邮箱格式不正确，请输入 name@example.com”比“Invalid input”更有帮助。具体业务规则仍然要由项目提供，Agent 不能凭空编造提交成功或数据已保存。

## 10. Command Palette：给熟悉用户一条快速路径

Command Palette 命令面板适合工具型产品、后台和编辑器。用户输入关键词后，从一组命令、页面或最近记录中选择操作。它是快捷入口，不应成为唯一导航。

### 可复制提示词

```text
创建一个 Command Palette，支持快捷键打开、关键词搜索和分组结果。
打开后焦点进入搜索输入框，结果按“页面、项目、操作”分组，显示快捷键提示。
上下方向键移动，Enter 执行，Esc 关闭并恢复触发前的焦点；没有结果时给出可读说明。
危险操作需要二次确认，执行期间显示 loading，失败时保留原搜索并提供重试。
手机端提供明显的搜索按钮和全屏输入界面，不依赖桌面快捷键。
```

命令面板的关键不是做出一个黑色浮层，而是命令名称、别名、分组和权限状态可被理解。危险操作、不可用命令和需要登录的命令都应该解释原因，不能让用户按 Enter 后才发现没有反应。

## 11. Floating Action Button：只突出一个高频动作

Floating Action Button，简称 FAB，适合移动端突出一个主要创建动作，例如新建项目、新建笔记或发起任务。它不适合同时承载多个同等重要的操作，也不适合遮住输入框和表格。

### 可复制提示词

```text
在项目列表的移动端右下角添加一个 FAB，用于“新建项目”。
按钮有可见文本或可访问名称，固定位置适配 safe-area，不遮挡列表最后一项和底部导航。
滚动时可以隐藏或缩小，但恢复方式清晰；点击后打开新建流程并显示 loading、error 和 success 状态。
桌面端将 FAB 改为列表顶部的普通主要按钮，避免两套入口同时抢夺注意力。
```

如果页面已经有底部导航、Cookie 提示、聊天按钮和播放器，继续添加 FAB 通常只会制造遮挡。先检查现有固定层，再决定这个动作是否真的值得浮在内容之上。

## 12. 一张组件状态矩阵

下面的矩阵可以作为 Agent 的实现边界，也可以作为人工验收表：

| 组件 | 触发 | 必备状态 | 关闭或结束 | 键盘与可访问性 |
| --- | --- | --- | --- | --- |
| Modal | 点击、快捷操作 | open、loading、error、dirty | 取消、保存、Esc | dialog、焦点进入与回收 |
| Drawer | 筛选、目录、设置 | open、loading、empty、error | 关闭、应用 | Esc、独立滚动、焦点回收 |
| Accordion | 点击标题 | expanded、collapsed、loading、error | 再次点击 | button、aria-expanded、aria-controls |
| Tooltip | hover、focus | visible、hidden | blur、Esc、离开 | aria-describedby，不承载关键操作 |
| Toast | 操作结果 | success、info、warning、error | 超时、手动关闭 | aria-live、可读关闭按钮 |
| Carousel | 按钮、手势 | active、paused、loading | 到达末项、停止 | 方向键、暂停控制、状态说明 |
| Lightbox | 点击媒体 | open、loading、error | 关闭、上一项、下一项 | Esc、方向键、焦点回收 |
| Form | 输入、提交 | empty、focus、error、success | 提交完成、取消 | label、错误关联、可见焦点 |
| Command Palette | 快捷键、按钮 | open、searching、empty、error | Esc、执行 | 方向键、Enter、焦点回收 |
| FAB | 点击 | default、loading、disabled、error | 完成、关闭流程 | 可访问名称、不遮挡内容 |

## 13. 一份可直接复制的组件实现提示词

```text
目标：为一个 AI 工具作品集实现一组可复用 UI 组件，组件服务于真实页面任务，不做装饰性堆叠。
页面包含：项目列表、项目详情、联系表单、图片画廊和设置面板。

组件范围：
1. Modal：编辑项目资料，支持未保存修改确认。
2. Drawer：移动端目录和项目筛选。
3. Accordion：FAQ 和补充说明。
4. Tooltip：解释不常见图标，关键内容不能只放在 Tooltip。
5. Toast：显示保存、复制和失败反馈。
6. Carousel：只展示有限数量的精选项目，默认不自动播放。
7. Lightbox：查看作品大图，支持键盘切换和关闭。
8. Form：联系表单，支持字段校验、loading、error、success。
9. Command Palette：搜索页面、项目和非危险操作。
10. FAB：移动端唯一的“新建项目”入口。

统一约束：
- 先输出组件清单、状态矩阵、事件流和焦点移动规则，再开始写代码。
- 使用语义 HTML、原生 button、label 和真实链接；不要用 div 冒充所有交互。
- 为 dialog、accordion、tabs 或菜单等模式正确设置 ARIA 状态，不为了通过静态检查而乱加属性。
- 所有异步操作都有 loading、success、error 和 retry 的可见处理；失败不能静默。
- Modal、Drawer、Lightbox 和 Command Palette 打开后管理焦点，关闭后回到触发元素。
- 390px 手机宽度和 1280px 桌面宽度都要测试，组件不能横向溢出、遮挡输入和固定导航。
- 尊重 prefers-reduced-motion；自动播放默认关闭，动画不能成为完成任务的前置条件。
- 先运行项目已有测试，再启动服务，用鼠标、触摸和纯键盘分别执行核心流程。
- 输出每个组件的截图、测试结果和未解决限制，不要声称未验证的功能已经完成。
```

如果通过 4SAPI 这类可替换模型入口协助生成组件草稿，先确认当前配置和实际可用能力，再让 Agent 逐项对照状态矩阵修改；模型生成的 ARIA 属性和业务结果都不能替代浏览器中的真实验证。

## 14. 浏览器验收：不要只点一次“打开”

### Modal、Drawer、Lightbox

```text
打开后焦点是否进入组件？
Tab 是否会进入背景中不可见的控件？
Esc、关闭按钮和取消按钮是否行为一致？
关闭后焦点是否回到原触发元素？
手机端内容是否独立滚动，最后一个按钮是否可见？
```

### Form、Toast、Accordion

```text
空提交时错误是否紧邻字段并说明修复方法？
提交期间是否阻止重复提交且保留输入？
成功和失败是否都有可读文本，而不是只换颜色？
屏幕阅读器是否能接收到 Toast 或错误摘要？
折叠后是否仍能通过键盘访问隐藏内容？
```

### Carousel、Command Palette、FAB

```text
不使用鼠标能否完成切换、搜索和执行？
自动播放是否可以暂停，页面离开后是否停止？
没有搜索结果和命令失败时是否有下一步？
FAB 是否遮挡 Bottom Navigation、表单或最后一条列表？
减少动态效果时核心任务是否仍然完整？
```

建议把这些检查写成浏览器测试或手工测试记录，而不是只凭一张截图判断。截图可以发现重叠、截断和层级问题，不能证明焦点回收、Esc 和错误恢复。

## 15. 常见失败：组件完成了外观，没完成任务

### Modal 能打开，不能关闭

关闭图标没有可访问名称，点击遮罩也没有规则，Esc 不工作，导致用户只能刷新页面。修复时先明确关闭策略，再统一按钮、键盘和遮罩行为。

### Toast 把错误藏起来

网络失败只在角落显示两秒，表单内容没有错误标记，用户不知道是邮箱错了还是服务不可用。重要错误必须留在用户当前任务附近。

### Carousel 自动播放抢走控制权

用户还没读完标题，内容就切走；键盘焦点留在已隐藏的面板；手机左右滑动带动整页横向移动。默认静态展示，确实需要自动播放时提供暂停和焦点感知。

### Tooltip 承担了标签职责

所有按钮都只剩图标，用户必须逐个悬停才能知道含义，触摸设备上更难使用。关键动作保留可见文字，Tooltip 只补充少量说明。

### FAB 和固定层互相遮挡

底部导航、聊天入口、Cookie 提示和 FAB 都采用固定定位，最后变成四个互相覆盖的按钮。固定层必须统一规划空间，必要时删除一个入口，而不是继续调整 z-index。

### ARIA 属性和真实行为不一致

按钮写着 `aria-expanded="true"`，面板却没有出现；或者隐藏内容仍能被 Tab 访问。可访问性属性是行为的声明，不能把它当作装饰标签。

## 16. 结论：组件质量藏在转场之间

Modal 和 Drawer 解决临时任务，Accordion 解决内容收纳，Tooltip 解决短说明，Toast 解决结果反馈，Carousel 和 Lightbox 解决媒体浏览，Form 解决输入与校验，Command Palette 解决熟悉用户的快速路径，FAB 只负责突出一个高频动作。

真正需要写进 Vibe Coding 提示词的，不是“圆角 12px、阴影柔和、动效流畅”，而是每个组件谁触发、状态如何变化、错误怎样恢复、焦点去哪里、手机端如何降级。只要这些条件明确，视觉风格才有机会在真实交互中保持稳定。
