# 子代理该不该换 Muse Ember：按任务分层与三条停用线

一次跨文件重构，主循环只发十来次请求，子代理发出的请求是几百上千次。延迟、限速、账单三层压力都压在这一层。所以每次有小模型发布，第一个问题总是同一个：子代理能不能换过去。

Meta 在 2026-11-09 发布 Muse Ember，官方定位就是这一层：大模型规划，它执行重复的有界任务。模型 ID `muse-ember-1.0`，上下文 1,048,576 tokens，最大输出 524,288 tokens，输入支持文本、图像、视频、音频和 PDF（官方博客与文档，检索于 2026-11-12）。

本文只回答分层问题：哪些子任务换过去划算，哪些换过去会返工，换之前要改哪些字段，怎么用几十条历史任务验证。基准分数怎么读、每任务成本怎么算，各有单独一篇。

## 一、先确认它在家族里的位置

同一条产品线里有三个模型能接 OpenAI 协议，参数接收同一个请求体，换模型等于换 `model` 字段。差异集中在定价、默认推理档和是否有折扣变体。

| 项目 | Muse Wonder | Muse Spark | Muse Ember |
| --- | --- | --- | --- |
| 定位 | 复杂软件工程、长周期 Agent | 规模化的 Agent 与编码 | 高频重复工作的执行层 |
| 模型 ID | `muse-wonder-1.0` | `muse-spark-1.3`（推荐） | `muse-ember-1.0` |
| 默认推理档 | `max` | `high` | `max` |
| 上下文 | 1,048,576 | 同左 | 同左 |
| 最大输出 | 官方未列出 | 官方未列出 | 524,288 |
| 每百万 token 输入 / 输出 | $4.00 / $20.00 | $1.25 / $4.25 | $0.10 / $0.50 |
| 折扣变体 | 无 | `muse-spark-1.3-contributor` | 无 |

数据来自官方 Choose a model、Pricing and rate limits 与 Muse Ember 三页（检索于 2026-11-12）。524,288 这个上限目前只在 Ember 的模型页与发布博客里给出，Wonder 与 Spark 的页面没有列出，拿它当 `max_output_tokens` 填给另两个模型属于外推。

三处先记住：

- **换模型是低风险试错。** 三个模型接收同一个请求体，改 `model` 就跑得起来，"先在子代理上试"不需要工程改造。
- **它只有标准模式。** 官方写明 Ember 没有 Contributor 变体。对数据合规有硬要求的团队少了一个会被误开的开关；反过来，已经在用折扣价的团队，这一层省不出那部分。
- **默认推理档是 `max`。** 不显式传 `reasoning_effort` 就按最高档跑，分派时漏这个参数，省钱的假设不成立。代价放在成本那篇算。

## 二、官方划定的四类重复工作

官方文档对适用场景的措辞都是"重复多次的有界工作"：

1. **子代理任务**：主 Agent 分派出去的聚焦编码任务、终端命令、信息查找。
2. **工具调用**：嵌在大工作流里的工具调用，单次成本和延迟会累积。
3. **路由**：给请求分类，再转给对应的处理器或模型。
4. **大批集合处理**：同一任务跑在几千个图像、文件或记录上，比如给照片打标题并分类、抽字段、给工单分类，多个请求并行。

共同点是：单次任务有明确终点，判断难度低，但次数多。官方 cookbook 给过一次参考运行：10,000 张照片，Ember 处理 1,269 次请求，每次 8 张 512 像素的图，平均每张约 265 输入、46 输出 token（检索于 2026-11-12）。这就是"有界"：一次请求固定看 8 张图，回答固定格式的问题。

反过来说，"重构这个模块的依赖关系"不是有界任务：上下文要自己找，改法要自己定，改错了没人拦。

## 三、按任务分层的一张表

官方 Choose a model 页有一张按工作负载选模型的表。下面节选与子代理分层有关的部分，最右列是我按"是否需要判断"做的归类，不是官方说法。

| 工作负载 | 官方建议模型 | 归类 |
| --- | --- | --- |
| 真实仓库里的跨文件改动 | Muse Wonder | 主循环 |
| 数小时的 Agent 运行、子代理编排 | Muse Wonder | 主循环 |
| 编码 Agent 或框架的主循环 | Muse Wonder | 主循环 |
| 需要低一档成本的主循环 | Muse Spark | 主循环 |
| 主 Agent 分派的子任务，含编码子任务 | Muse Ember | 执行层 |
| 工具调用、紧凑的工具循环、对延迟敏感的一轮 | Muse Ember | 执行层 |
| 分类、路由、其他高频请求 | Muse Ember | 执行层 |
| 同一任务跑在几千个图像、文件或记录上 | Muse Ember | 执行层 |

这张表可以直接当分派规则用。落到代码上通常是一个判断函数：任务来自主循环的计划、输入输出形状固定，走执行层；需要读多份上下文才能决定改什么，留在主循环。

一个常见错位是让执行层模型"顺便排个优先级"。按固定标签分类归 Ember，但给待办排行属于权衡判断，回主循环更稳。

## 四、三条停用线

官方文档写了什么时候不该用 Ember：硬单发编码问题、知识密集的问题、视觉编码，改用 Muse Spark 或 Muse Wonder。这三条值得单列，因为它们最容易被框架绕过去。

**第一条：硬单发编码。** 一次请求就要产出可合并改动。第三方机构 Artificial Analysis 的 FrontierCode 2.0 私有题集上，Claude Haiku 5.5 是 34.9%，Muse Ember 是 27.2%，GPT-6 Luna 是 25.2%（官方博客引用的 AA 数据，检索于 2026-11-12）。这是官方对比表里 Ember 唯一落后的一项，落后 7.7 个百分点。把这类任务分给子代理，省下的钱会变成返工。

**第二条：知识密集、又不做检索。** 官方把"不检索、凭记忆回答的知识问题"指派给 Spark 或 Wonder。子代理如果被设计成不看文档直接答的形态，这条就适用。

**第三条：视觉编码。** 指看着设计稿或截图写实现。Ember 能读图，细粒度视觉题上甚至领先，但"看图写实现"考的是推理链，属于主循环的活。

另两条硬约束：

- **音频别混进来。** 官方文档说明 Muse Spark 1.3 的音频响应质量可能下降，建议改用 Spark 1.2 或语音转写模型。多模态子代理里，音频要单独分流，不能默认跟着 Ember 走。
- **折扣与数据授权绑定。** 只有 Spark 提供 Contributor 变体。如果团队策略是"原型用允许训练的折扣价、上线切标准价"，子代理这层从头只有标准价，预算别按折扣价做。

## 五、差距有多大：指数接近，单项有坑

官方博客给了一张与 Muse Spark 1.3 的对照：Artificial Analysis 智能指数 36 对 37，每任务成本 $0.14 对 $2.39。指数差 1 分，成本差 17 倍。

这组数字解释两件事。

第一，把重复任务放到执行层，动机不是"小模型够聪明"，而是"这层判断本来不值那么多钱"。指数只差 1 分，说明常规任务上两者成功率接近；成本差 17 倍，说明放在哪层决定账单量级。

第二，总体接近，单项仍能差出 7 个百分点以上。分层该按任务类型做，不是按指数做。

还有一条反面提醒：Artificial Analysis 在同一模型页给出"每任务 $0.14、每任务 3.2 分钟、首个答案 token 5.03 秒、输出 446 tok/s"（检索于 2026-11-12）。那是它在自己指数任务上量到的，任务集与业务不同，方向可参考，绝对值不能照搬。

## 六、接进去要改的字段

官方说 Model API 兼容 OpenAI 协议，也提供 Anthropic 格式的 Messages 端点。三处容易改错。

**第一，base URL 与 key 的环境变量名。** OpenAI SDK 读 `OPENAI_API_KEY`，Anthropic SDK 读 `ANTHROPIC_API_KEY`，都不认厂商给的变量名，要显式传。Anthropic SDK 的 `base_url` 设成 `https://api.meta.ai`（SDK 自己补 `/v1/messages`），key 走 `auth_token`。LiteLLM 走 OpenAI provider，模型 ID 要加 `openai/` 前缀。

**第二，推理档参数的位置。** Chat Completions 用顶层 `reasoning_effort`，Responses API 嵌成 `reasoning.effort`。两者都接受 `minimal` 到 `max`，传 `none` 返回 HTTP 400。

**第三，框架里的别名映射。** 官方给了 Claude Code / Claude Agent SDK 的映射：`opus` 指向 `muse-wonder-1.0`，`sonnet` 指向 `muse-spark-1.3`，`haiku` 别名与子代理模型指向 `muse-ember-1.0`。Codex 那边是把 `muse-wonder-1.0` 设为默认模型。

最小可跑的一次调用如下，跑通再谈分层：

```shell
curl -X POST "https://api.meta.ai/v1/responses" \
  -H "Authorization: Bearer $MODEL_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
  "model": "muse-ember-1.0",
  "reasoning": {"effort": "minimal"},
  "input": "把这条工单分类为 billing、bug 或 feature，并给一句理由：十月发票被扣了两次。"
}'
```

这里显式写了 `effort`。省略时按 `max` 跑，延迟和输出 token 都上一个台阶，验证阶段会误判"子代理太慢"。

## 七、验证：拿 50 条历史任务回放

公开分数不能替代自己的任务集。下面这套流程不需要新写测试，用日志里已有的子任务就能做。

1. **抽样。** 从最近两周的子代理请求里抽 50 条，覆盖实际用到的任务类型，别只挑简单的。
2. **固定变量。** 同一批输入、同一 `reasoning_effort`、同一 `max_output_tokens`、同一 harness，三个模型各跑一遍，共 150 次请求。
3. **两级判定。** 先看严格通过率（产出直接可用、不需人改），再看返工率（需要改一次以上的比例）。只看第一级会高估小模型。
4. **同时记三件事。** 每次请求的 `cached_tokens`、`reasoning_tokens`、端到端耗时。前两个决定账单，第三个决定能否开 16 路并行。
5. **算每任务成本。** 用实际 token 乘官方单价，不要拿第三方页面的每任务成本套自己的业务。
6. **设决策线。** 常见做法：执行层严格通过率不低于主模型的 95%、单任务成本低于主模型的 20% 就切；低于 90% 先拆细任务再试。

再加一级混合跑：主循环用 Wonder、子代理用 Ember，和全部用 Wonder 对比总成本与总时长。分层图的是总账更低，不是单次调用更低。

## 八、如果调用走兼容层

不少团队不直连厂商端点，而是把多个模型放在一层 OpenAI 兼容网关后面，用统一的 key 和计费对账。以 4SAPI 这类中转网关为例，它对外暴露 `/chat/completions` 风格的路由，模型名由网关侧映射。

这种架构下有两件事要自己确认，否则分层判断会失真：别名到真实模型的映射写在网关配置里，`haiku` 这类别名未必指向 Ember；网关也可能带默认参数，请求里没写的 `reasoning_effort` 由谁补，只能从回包倒推。最省事的核对是发一个已知答案的短请求，读回包的模型字段和 `reasoning_tokens`，确认落到哪个模型、跑在哪个档。

## 九、限制与结论

先划边界：上面的分层依据是官方定位、官方文档和一次公开评测，没有我自己跑的压测。Ember 才发布三天，独立复现只有 Artificial Analysis 与 Vals AI 两处。官方对比表的 harness 不统一，怎么读另有一篇。

结论三条。

一是把它当执行层，不当主循环。判断类工作留在主循环，重复的有界任务交给它，这是官方定位，也是成本结构决定的。

二是三条停用线要写进分派规则，不是写在文档里。硬单发编码、无检索的知识问题、看图写实现，一旦被框架吞进去，返工成本会盖过省下的钱。

三是先回放再上线。50 条历史任务、固定 effort、两级判定、同时记账单和耗时，一天能跑完，比看榜单可靠。
