# 自托管一套语义层之前：端口、凭据与出站数据的边界

把一套开源系统跑起来通常半小时；接到公司数据上通常三周，卡住的常常不是功能。

是这几件事：哪个端口不该对宿主机开、密码落在哪张表、哪些请求会把数据送出去、"我们做了 PII 处理"覆盖了什么。

下面按 NVIDIA auto-ontology 仓库里的文件逐项看。事实来自 `docker-compose.yml`、`.env.example`、`docs/` 下三份文档、`helm/` 的模板清单与两份源码（检索日期 2026-11-09）。没部署过，也没接真实数据库。

## 一、先把服务摊开

`docker-compose.yml` 里 7 个服务：5 个常驻，2 个一次性任务。发布到宿主机的映射有 5 条：

| 服务 | 容器内 | 宿主机 | 说明 |
| --- | --- | --- | --- |
| 前端 | 3000 | 3000 | 带鉴权的入口 |
| 后端 | 3001 | 3001 | 文本转 SQL、目录与本体 API |
| 摄取服务 | 3002 | 3002 | 摄取、语义编译 |
| Postgres | 5432 | `${POSTGRES_PORT}` | 目录、本体、向量 |
| pgAdmin | 80 | 5050 | 数据库管理界面 |

**MCP 不在 compose 里。** README 后半段的组件表把它列在 3003，但 compose 没有这个容器。仓库里的 chart 也不含它：`templates/` 只有前端、后端、摄取、Postgres、pgAdmin 与两个迁移 Job，`values.yaml` 关于 MCP 只有一行 `mcpPublicUrl`，注释称其为 "the separately deployed MCP server"。DEPLOYMENT.md 把该镜像列为同批发布物，并说 chart 会把自己用的镜像 pin 到该版本——按仓库现状，进程要自己部署；NGC 上发布的 chart 是否一致我没核。

所以"一键起全套"不成立：compose 给的是应用加数据库。

## 二、该对外的有两个面

README 说"客户端走 3000 端口"，那句管的是 compose 里的 API 客户端，**管不到 MCP**。

MCP 是第二个面向客户端的入口。`docs/mcp.md` 的配置例子用公网 HTTPS 地址，并写明它"可以跑在任何能连到这个部署的地方"。**3000 对内是应用，3003 是对 agent 客户端的门。**

两件事：

- `AUTO_ONTOLOGY_MCP_PUBLIC_URL` 必须和客户端 URL **逐字一致**——令牌绑定在该地址上。排错清单里有这条报错，最常见原因是 `127.0.0.1` 与 `localhost` 混用。
- MCP 不持有数据库凭据与模型配置，也没有自己的密钥；它是 3000 的 HTTP 客户端，鉴权继承自前端。它必须可达，但不必可信。

## 三、四个不该发布的端口

README 提醒把 3001 和 3002 留在私有网络，理由写在同一段：

- 后端 FastAPI **信任前端转发的 `x-auto-ontology-user-id` 头**。谁能直连 3001，谁就能编一个用户 ID 冒充任何人。
- 摄取服务的 ingest、delete、reset、compile 端点**自身没有鉴权**。

compose 默认把 3001、3002、5432、5050 全映射出来。本地方便，上服务器就是四个洞。pgAdmin 尤其容易漏：它不属于应用，却是一个用 `change-me` 就能登进去、还能登记任意源库凭据的界面。

## 四、鉴权的四条路，和开户的真实入口

每个 `/api/...` 请求按四段解析：会话 cookie → API token（`x-api-key` 或 Bearer）→ MCP 的 OAuth bearer → 受信调用方转发的 SSO ID token。

自助注册是关的。但"关掉注册"不等于"账号只有一个入口"：

| 入口 | 端点 | 谁能用 |
| --- | --- | --- |
| 首个管理员 | 环境变量 bootstrap | 部署者 |
| 邀请开户 | `POST /api/invitations` | 有 `user: create` 权限的人 |
| 接受邀请 | `/api/invitations/[token]/accept` | **公开路由**（代码里是 `withPublic`），注释写明"令牌即凭据、一次性" |
| 邀请重置 | `/api/invitations/reset` | 给已有账号改密码 |

文档没写这块（`docs/authentication.md` 只说注册关闭），但代码在 `frontend/app/api/invitations/`。第三行是关键：**接受端点是公开的，谁拿到链接谁就有账号。** 风险从"有人能自己注册"变成"链接会不会被转发到群里"。

然后是占位值：管理员密码、`POSTGRES_PASSWORD=change-me`、pgAdmin 账号，以及写死在仓库里的 `AUTH_SECRET=myverylongsecret123`。快速开始写了：compose 会把 Postgres、pgAdmin 和 Web 应用发布到宿主机，启动前换密码——只提这三个，没提 3001 和 3002。

## 五、连接密码存在哪张表

`docs/connections.md` 写得清楚：

- **不配 Vault**：整个连接对象，**包括密码**，序列化成 JSON，**未加密**地存在 Postgres 的目录行上。
- **配 Vault**：凭据写进 Vault，按库名索引，目录行里不存。

Vault 需要四个变量齐全才生效。**缺变量不报错，但会打一条 warning 然后按明文存**（原文 "ignored with a warning"）。这条 warning 是唯一能发现"以为配了、其实还在明文"的信号。

对自托管意味着两件事：备份的可信范围，以及谁能读 `catalog` 表。**备份带着源库密码，敏感性就升了一级。**

还有一处容易踩：连接有两个来源（UI 连接与 `CONNECTION_STRINGS`），优先级在两条路径上相反——问答时 UI 优先，摄取时环境变量优先。文档建议**一个部署只用一种**。

## 六、什么会出站，什么不是出口

两个真出口，加一个常被当成出口的东西。

**模型端点。** 默认走 NVIDIA 托管 API（`integrate.api.nvidia.com`，rerank 走 `ai.api.nvidia.com`）。四个角色——`REASONING`、`NON_REASONING`、`EMBED`、`RERANK`——都能改成自托管 NIM 或任意 OpenAI 兼容端点。这决定问题文本、schema、样例值会不会离开内网。

**KumoRFM（可选）。** 配了 key 后预测类问题路由到托管服务，它要**上传所连的表**。两个闸门：`KUMO_MAX_TABLES` 默认 20，`KUMO_MAX_ROWS_PER_TABLE` **默认不限**——即默认行数全量上传，只有表数量有上限。README 写明启用前看清会送什么。

**PII 检测不是出口，是标签。** 它唯一的出站是把列名、表名、描述送进上面那个端点。三层误解要拆开：

1. **默认关闭。** `infra/feature_flags.py` 把它做成 opt-in，没在设置里打开过的实例一次都不分类；缺配置行或读库失败也按关处理。
2. **只看元数据。** `pii_detection/service.py` 写明检测只看到元数据，采样值被刻意排除在 `ColumnInput` 之外——分类器拿到的只有列名、表名、描述。
3. **是打标，不是脱敏。** 标签从列传到由它构建的列属性与 SQL 属性，下游消费方是目录标签与检索面板。我按 `mask|redact|anonym|obfusc|scrub` 全仓检索，**没找到对列值做掩码的代码**；脱敏只有三处，都在外围：连接串写日志前脱密码、Kumo 字面量写遥测前脱、连接对象公开 payload 脱凭据。这是缺席性证据，不证明不存在。

一处实现细节：判不准时"保守记为 PII"只发生在 LLM 那一支；没配分类器或调用失败时返回 `REVIEW`，既不打标也不算处理完。

## 七、几处文档与实现不一致

| 现象 | 依据 | 处理 |
| --- | --- | --- |
| 默认嵌入与重排模型名两套：README 的 NIM 小节一套，「Models」表与 `.env.example` 另一套 | 三处里两处一致 | 以 `.env.example` 为准：与 Models 表互证，NIM 小节是孤例 |
| `.env.example` 注释提到用 Neo4j 做 join 路径检查 | 目录树无 neo4j 文件、无该依赖、compose 无该服务 | 只按注释引用，不推断"图存在图数据库"；注释也说无边界会回落到实时探测 |
| README 两张组件表：前一张无 MCP，后一张有 3003；compose 与 Helm 都无 MCP | 三处对照 | 写清 MCP 需单独部署 |

**部署前把 `.env.example` 和 compose 当配置事实，把 README 当导读。**

## 八、两个容易出事的运维细节

**目录比连接活得久。** 摄取每 `INGEST_INTERVAL_HOURS` 一次（默认 24），启动先跑。MCP 文档提醒：`databases` 非空不代表 `can_execute_sql` 为真——目录是某次摄取建的，源库换密码后目录还完整摆着，表现是"能搜术语、每个问题都失败"。

**权限改了不用重发令牌。** 令牌不透明，每次调用都去 UserInfo 校验，权限从账号取而非令牌；注册与授权记录存数据库，多副本共享，重启不踢人。含义是 MCP 可当无状态服务水平扩容；但每次调用都多一次对前端鉴权端点的请求——前端挂了 MCP 跟着报错。

## 九、上线前验收清单

| # | 检查 | 不合格的信号 |
| --- | --- | --- |
| 1 | 管理员密码、`POSTGRES_PASSWORD`、pgAdmin 口令、`AUTH_SECRET` 全换 | 还是样例值或仓库字面值 |
| 2 | 宿主机只发布 3000（MCP 另算） | 3001/3002/5432/5050 也在 `0.0.0.0` |
| 3 | 3001、3002 只在内网可达 | 办公网能直接 curl 通 |
| 4 | 要跨机用 MCP 时，3003 对客户端可达 | 塞进内网只能本机用 |
| 5 | `AUTO_ONTOLOGY_MCP_PUBLIC_URL` 与客户端 URL 逐字一致 | 登录报 resource does not match |
| 6 | 连接来源只用一种 | 两种都在用，不清楚哪条生效 |
| 7 | Vault 四变量齐全，或接受明文 | 日志里 partial Vault warning 没人看 |
| 8 | 连接按 schema 白名单与表正则收敛，deny 优先 | 全库扫进来 |
| 9 | 模型端点自托管还是托管，密钥归属清楚 | 不知道 schema 去了哪 |
| 10 | KumoRFM 未启用，或行数上限有值 | 开着但不设上限 |
| 11 | 共识：PII 检测默认关闭、只打标不脱敏 | 有人以为已经脱敏 |
| 12 | 需要时打开探测开关并记成本 | 以为默认防错都开着 |

第 4、5 项最易漏：只盯 3000，会把 MCP 一起关掉。第 12 项也容易跳过——探测默认关、空结果修复默认开，默认不等于"都防住了"。

## 十、许可证与维护方式

Apache-2.0。`THIRD_PARTY_NOTICES.md` 列组件与上游许可，容器镜像另有 `CONTAINER_THIRD_PARTY_NOTICES.md`，合规评审要逐条看。

一条要先知道：**项目声明不接受外部 PR。** 集成请求和缺陷以 issue 提，维护团队自己改代码。对使用方意味着 bug 只能等，或自己维护 fork——Apache-2.0 下允许，但要承担合并成本。安全漏洞走 `SECURITY.md` 的官方路径，明确要求别通过 GitHub 公开提。

## 十一、结论与边界

自托管的难点不在跑起来，在**定下三件事**：暴露面（3000 加一个单独部署的 MCP）、凭据落点（Vault 或明文，选一个并知情）、出站路径（模型端点与 KumoRFM）。

我的判断：数据不能出内网时，先改模型端点——四个角色全部指向自托管；暂时做不到，就别把生产库接进来，用脱敏副本编译语义层。

限制：没部署，结论全来自仓库文件；三处不一致只并列陈述，未推断原因；开关效果、KumoRFM 上传、PII 标签下游用法未实测；"没有掩码代码"是缺席性证据。

下一步如果只做一件事：把 compose 的端口映射改成只留 3000，再从另一台机器 curl 3001。能通，说明边界还没建立。
