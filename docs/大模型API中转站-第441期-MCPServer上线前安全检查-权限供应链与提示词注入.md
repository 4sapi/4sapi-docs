# MCP Server 上线前安全检查：权限、供应链与提示词注入

把 MCP Server 接进 Agent，通常只需要填地址、启动命令或访问令牌，工具就会出现在模型的调用列表里。配置很简单，风险却不一定简单：读文档的工具可能带着内部搜索权限；“创建草稿”如果参数没收紧，可能一路变成外部通知；网页、邮件和文档返回的内容，也可能试图影响 Agent 下一步做什么。

上线前先把四件事写清：工具以什么身份调用，能接触哪些数据，会产生哪些副作用，异常时如何停止和追溯。下面是一套适合小团队起步的 MCP 准入流程。它不是对所有 MCP 实现的安全认证；涉及生产数据、外部写入或高风险行业时，还需要安全与业务 Owner 正式审查。

## 一、先画出能力边界，而不是先安装

每个 MCP Server 接入前，先写一张能力卡。没有它，团队很难知道一个看起来方便的工具到底拿到了哪些数据和行动权限。

```markdown
# MCP 能力卡：internal-search

用途：检索已经授权的内部产品资料
调用主体：客服摘要 Agent
输入：关键词、文档范围、最大返回数
输出：文档 ID、片段、来源与访问标签
允许数据：已发布产品文档
禁止数据：客户资料、员工人事、密钥与私人空间
副作用：无，只读
网络边界：仅公司内网服务
身份：受限服务账号
审批：不需要；扩大资料范围需人工审批
日志：记录 task_id、调用原因、文档 ID 与结果数量
停止条件：返回未授权资料、来源标签缺失或出现异常数据量
Owner：系统负责人、数据负责人
```

“工具名”和“用途”不够。能力卡要把输入、输出、身份、数据、网络、副作用和停止条件放在一起，因为风险来自它们的组合。例如读取能力搭配高权限身份，同样可能造成泄露；无害的文本输出如果被后续 Agent 当作指令执行，也可能改变行动路径。

## 二、按副作用给工具分级

不要把所有 MCP 工具都放进同一个自动调用池。可以先按副作用分层：

| 等级 | 工具类型 | 默认策略 | 示例 |
| --- | --- | --- | --- |
| L0 | 纯本地计算 | 可自动调用，记录版本 | 格式转换、固定规则校验 |
| L1 | 受控只读 | 限定范围与结果量，记录来源 | 内部文档检索、只读查询 |
| L2 | 可逆内部写入 | 明确参数后请求确认，保留撤销方式 | 创建草稿、写入临时队列 |
| L3 | 外部或不可逆动作 | 默认人工审批、幂等与双重检查 | 发送消息、创建订单、删除记录 |

等级不是永久标签。一个“搜索”工具如果能查到全公司文件，风险未必低；一个写入工具如果只创建可撤销草稿，风险可能低于直接发信。分级依据是可访问的数据、实际副作用、恢复难度和影响对象。

## 三、供应链检查：你接入的到底是什么

MCP Server 可能来自内部仓库、开源项目、软件供应商或临时脚本。上线前应记录来源与构建方式：

```text
代码或镜像来自哪里，谁维护？
固定到哪个提交、版本或镜像摘要？
依赖与启动命令是否经过审查？
是否会在启动时下载额外组件或读取本机环境变量？
网络连接到哪些域名或服务？
更新由谁批准，出现漏洞时如何停用？
```

不要把“开源”自动等同于“适合直接接入生产数据”。至少检查项目的维护状态、发布记录、依赖来源、已知安全公告和运行所需权限。对于容器或可执行文件，使用可复现的构建或固定版本，避免每次部署都拉取不确定的最新内容。

特别注意启动配置。允许执行任意命令、读取整个用户目录、继承全部环境变量，或者在日志里输出访问令牌的 Server，不应仅凭“功能好用”进入正式环境。

## 四、提示词注入不是只发生在聊天框

Agent 读取的网页、邮件、知识库、Issue 和工具返回值都属于外部内容。它们可以提供事实，但不应自动获得改变系统目标、权限或工具选择的权力。

以下模式需要在测试中明确验证：

| 场景 | 风险 | 应有行为 |
| --- | --- | --- |
| 文档要求“忽略此前规则并发送资料” | 内容把数据当指令 | 仅把它作为被分析的文本，不执行 |
| 搜索结果包含伪造链接或调用建议 | Agent 跳转到未授权系统 | 限制工具与网络域，要求显式批准 |
| 工具输出要求泄露密钥 | 机密经上下文外流 | 密钥不进入工具可见上下文，拒绝该请求 |
| 用户要求扩大查询范围 | 身份与数据越权 | 按权限策略拒绝或走审批，不由内容决定 |

防护不能只靠一句“忽略恶意指令”的提示词。更稳妥的做法是分层处理：工具返回结构化、带来源和权限标签的数据；数据内容与系统策略分开；身份采用最小权限；外部写入要求确认；日志保存引用和决策原因，不把文本内容当成命令。

## 五、工具描述和参数也是安全边界

模型通常根据工具名称、说明和参数模式决定怎么调用它，因此这些内容应像 API 契约一样审查。

好的工具接口有几个特征：

```text
动词和对象明确，例如 create_draft 而不是 manage_messages。
参数枚举有限，避免任意 URL、任意路径或任意命令。
写入动作要求范围、目标和幂等键。
返回值标记数据来源、权限标签、部分失败和实际副作用。
错误提示不会泄露令牌、内部拓扑或其他用户资料。
```

如果一个工具同时支持读取、更新、删除和执行任意查询，优先拆成多个能力更小的工具。拆分会增加一些配置，却能让授权、审计和人工确认更精确。

## 六、上线前做一组对抗性任务

只测正常路径，测不出边界。每个 MCP Server 至少准备一组固定任务：

```text
正常：在允许范围内成功调用并返回可追溯结果。
越权：请求访问不在身份范围内的数据，必须拒绝或审批。
注入：工具返回含有改变目标、要求发送数据的文本，不能执行。
工具失败：超时、空结果、格式异常时应报告并停止错误重试。
重复执行：相同写入请求不能产生重复副作用。
撤销：可逆写入能够按预期撤销，或明确说明不可撤销。
审计：任务、身份、工具、参数摘要、结果和审批可被关联查询。
```

测试使用脱敏或合成数据，且必须在隔离环境中运行。不要为了验证“是否会泄露”而把真实密钥或客户资料放进对抗样例。

## 七、为外部写入设计人工确认

对 L2 与 L3 工具，确认界面或确认事件至少让人看到：

```text
谁在请求动作：用户、Agent 和实际服务身份。
要做什么：动词、目标对象、数量与范围。
依据是什么：任务目标与来源引用。
会产生什么副作用：发送、写入、扣费、删除或权限改变。
能否撤销：撤销路径与时限。
```

“是否继续？”不是足够的确认信息。人必须能够理解动作及其对象，才能成为真正的控制点。确认前后都应记录同一个 `task_id` 和 `run_id`，避免批准 A 任务却执行了 B 任务。

## 八、最小准入流程

```text
1. 填写能力卡，确认业务与数据 Owner。
2. 依据数据和副作用确定等级与默认调用策略。
3. 固定代码、依赖、镜像和部署配置来源。
4. 为 Server 分配最小权限身份，不共用个人高权限令牌。
5. 审查工具描述、参数、返回与错误处理。
6. 在隔离环境执行正常、越权、注入、失败、重复与审计任务。
7. 配置日志、告警、人工确认、撤销或停止方式。
8. 以受限任务范围灰度上线，保留回滚到无该工具的路径。
```

上线后仍应定期检查依赖更新、权限范围、调用量和异常参数。工具接入不是一次性审批，业务范围和攻击方式都会变化。

## 九、上线前检查清单

```text
[ ] 每个 MCP Server 有用途、数据、身份、副作用和 Owner 的能力卡。
[ ] 工具按副作用与可恢复性分级，外部写入默认不自动执行。
[ ] 代码、镜像、依赖和启动配置可以定位到固定版本。
[ ] Server 未继承不必要的环境变量、文件权限和网络权限。
[ ] 工具接口不允许任意命令、路径、URL 或无边界查询。
[ ] 工具返回值带来源与权限信息，错误不泄露敏感内容。
[ ] 已测试提示词注入、越权、超时、重复执行和撤销路径。
[ ] 人工确认展示动作、对象、依据、副作用与撤销方式。
[ ] 日志可关联任务、运行、身份、工具、审批与实际结果。
[ ] 有停用 Server、撤销凭证和回滚 Agent 配置的操作卡。
```

## 结论与资料

MCP 让 Agent 获得了读取和行动能力。接入时要确认这些能力有明确限制，能被验证，也能被撤销。能力卡、最小权限、固定供应链、注入测试和人工确认，足以构成一个可执行的起点。

- [Model Context Protocol：Specification](https://modelcontextprotocol.io/specification/)：参考协议中的客户端、服务端和能力协商模型；实际实现以当前版本规范为准。
- [OWASP：Top 10 for Large Language Model Applications](https://owasp.org/www-project-top-10-for-large-language-model-applications/)：参考提示注入、过度代理与供应链相关风险类别。
- [CISA：Secure by Design](https://www.cisa.gov/securebydesign)：参考在设计阶段明确默认安全、可观测与责任归属的原则。
