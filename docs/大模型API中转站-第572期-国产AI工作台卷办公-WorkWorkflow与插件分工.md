# 国产 AI 工作台开始卷办公：Work、Workflow 和插件怎么分工

很多人第一次用 AI 工作台处理办公任务，会把它当成一个更大的聊天框：把文件拖进去，说一句“帮我整理”，然后等结果。
单份材料这样用没问题，但任务一旦变成几十份票据、几百篇文章，或者需要操作专业软件，聊天框就会暴露三个问题：分工不清、过程不可见、结果不好验收。

ZCode 把办公能力拆成了三层：Work 模式、动态工作流和插件。
公开演示记录把办公入口称为 Work 模式，官方更新日志的表述是“办公和编程两种模式切换”；本文沿用 Work 模式这个叫法，具体入口以当前界面为准。
它们不是互相替代的关系，而是分别解决“一次任务”“一大批任务”和“专业工具缺口”。
这篇文章只回答一个问题：拿到一个办公任务，应该先交给哪一层。

## 先看一个真实的困惑

假设你手里有三件事：

1. 把 12 张发票和截图整理成一份 Excel 报销单。
2. 检查 380 篇教程里的 6000 多个链接是否失效、价格是否过时。
3. 根据一段网站录屏，复刻一个可以运行的前端页面。

这三件事都能叫“让 AI 帮我做一下”，但执行方式完全不同。
第一件事需要读文件、识别票据、生成表格，并在关键金额上接受人工复核。
第二件事需要把几千个链接分组、并发检查、交叉比对，还要能说清每个结论来自哪一步。
第三件事需要理解视频、抓取素材、搭项目，再用截图和动效反复比对。

如果全部塞进一个对话，模型可能也能开始干，但你很难知道它现在做到哪、哪些结论有证据、失败了该从哪一步重来。
所以先分层，比先选模型更重要。

## 官方更新日志能确认什么

ZCode 的更新日志记录了两个关键节点。
3.14.0 新增动态工作流，用一段脚本编排多个子智能体协作完成复杂任务，同时新增办公和编程两种模式切换。
3.16.2 新增插件市场，可以浏览、安装和管理插件。
来源：[ZCode 更新日志](https://zcode.z.ai/cn/changelog)，访问日期：2026-10-20。

官方仓库 README 还说明，仓库包含客户端、后端服务、共享 UI，以及 Agent CLI 与运行时源码，并在 2026-10-19 更新到 3.16.2。
来源：[ZCode README](https://github.com/zai-org/ZCode/blob/3c5b227649371507ddc4eb46ac5133afe6db1cab/README.md?plain=1)，访问日期：2026-10-20。

这两个事实放在一起看，能得出一个判断：ZCode 已经不只是“写代码的桌面工具”，而是在把任务入口、执行流程和扩展能力做成一个工作台。
但工作台的能力越多，越需要知道每层适合什么。

## 第一层：Work 模式，解决“一次任务，一份交付”

Work 模式适合的是这样的任务：

- 输入是少量文件，通常十几份以内。
- 任务目标可以用一段话讲清。
- 中间需要人看一眼，发现不对可以马上补充要求。
- 交付物是表格、文档、演示稿或一份整理结果。

比如报销单、会议纪要、周报初稿、竞品资料汇总。
这类任务的关键不是“并发”，而是“理解材料”和“把结果做对”。

Work 模式的优势在于反馈快。
文件拖进去，模型先读一遍，发现明显问题会提出来；接着加载对应技能做表格或文档；最后给出一个可以直接打开检查的产物。
人可以在中途打断、补充字段、要求重做某一列。

但它也有明显边界。
单次任务里的异常检测，依赖模型有没有看见、有没有理解对。
它不会自动变成一套可审计的财务流程，也不应该替代报销审批人。

一次公开演示任务里，12 份虚构票据埋了 5 个问题，Work 模式找出了 4 个，漏掉了大小写金额不一致的那一张。
这个结果说明它能承担“初筛和整理”，不能说明它每次都能达到同样的命中率。
来源：一组公开演示记录，本文未复跑；记录日期：2026-10-20。

## 第二层：Workflow，解决“任务很多，但流程固定”

当任务从 12 份文件变成 380 篇文章、6000 多个链接，问题就不再是“模型读不读得懂”，而是“怎样让几百次检查按同一套标准跑完”。

ZCode 的动态工作流，官方规格写得很清楚：主 Agent 不是边做边和子 Agent 商量，而是先写一段 TypeScript 脚本。
脚本里可以用 `agent()` 创建子 Agent，用 `.ask<T>()` 给任务并拿到带类型的结果，用 `files.*`、`git.*` 读工作区，用 `phase()` 划分阶段，用 `artifact.*` 发布交付物。
来源：[Dynamic Workflow 规格](https://github.com/zai-org/ZCode/blob/3c5b227649371507ddc4eb46ac5133afe6db1cab/docs/dynamic-workflow.md?plain=1)，访问日期：2026-10-20。

这带来四个实际差别：

| 差别 | 普通多 Agent 对话 | 脚本化工作流 |
| --- | --- | --- |
| 分工 | 边做边决定 | 先写清阶段和依赖 |
| 结果 | 多为自然语言汇总 | 可按类型和 Schema 校验 |
| 并行 | 依赖上下文里的临时安排 | 由脚本明确 fan-out 和 join |
| 复跑 | 重新描述一遍需求 | 保存脚本，下次换输入再跑 |

它更适合“宽而结构化”的任务：每个文件都要检查、每个链接都要访问、每个结论都要归档。
不适合“只有一句话、但没有明确验收标准”的任务，因为脚本会把模糊需求放大成大量无效调用。

## 第三层：插件，解决“工具链缺口”

有些任务不是模型不会想，而是缺少专业工具。
比如读取 PDF、生成 Word、做演示稿、处理电子表格，或者驱动浏览器、连接 GitHub、飞书、钉钉、企业微信。

ZCode 的插件文档说明，一个插件可以把技能、命令、子智能体、MCP 服务器和 Hook 打包在一起。
插件市场分为公开和个人两个来源，安装后附带的组件会注册到当前工作台。
来源：[ZCode Plugin 文档](https://zcode.z.ai/cn/docs/plugin)，访问日期：2026-10-20。

插件层的价值不是“功能更多”，而是把某个专业动作变成可重复的流程。
比如 Video2code 这类插件，把“看录屏、抽帧、抓素材、写页面、做视觉对比”串成一条链路。
如果没有插件，模型也能尝试，但每一步都要临时拼工具，稳定性和可复用性都会差很多。

插件也有一个常见误区：把它当应用商店，看到什么装什么。
装得越多，技能元数据占用的上下文越多，模型反而更难判断什么时候该用哪个技能。
官方技能文档明确提醒，建议只启用常用技能。
来源：[ZCode Skill 文档](https://zcode.z.ai/cn/docs/skill)，访问日期：2026-10-20。

## 一张选择矩阵

拿到任务后，可以按下面四项判断：

| 判断项 | 偏向 Work | 偏向 Workflow | 偏向插件 |
| --- | --- | --- | --- |
| 输入规模 | 十几份以内 | 几十到几百份 | 取决于插件能力 |
| 流程 | 可以边看边改 | 固定、可拆分、可并行 | 需要专业工具或外部服务 |
| 交付 | 一份表格或文档 | 一份带来源的清单或报告 | 一个可运行产物或专业文件 |
| 验收 | 人工逐项核对 | 抽样复核加脚本证据 | 截图、录屏、文件打开验证 |

更具体一点：

- 报销单、会议纪要、周报初稿：先用 Work 模式。
- 全站链接检查、批量文档核对、跨文章矛盾扫描：考虑 Workflow。
- 录屏复刻、PDF 转文档、设计稿生成、第三方系统操作：先看插件市场有没有现成能力。
- 需要改代码、跑测试、提交 Git：用编程模式或 Coding Agent，不要硬塞进办公模式。

这张表不是产品说明书，而是一个决策顺序。
先判断任务规模，再判断流程是否固定，最后判断有没有工具缺口。
三层都解决不了，才回到“换模型”或“拆任务”。

## 三层能力怎样接起来

一个完整的办公任务，经常需要三层配合。

以“整理一批项目资料并生成汇报”为例：

1. 用 Work 模式读会议纪要、需求文档和表格，先做一份资料清单。
2. 如果资料有几百份，把“逐份提取字段”写成 Workflow，让子 Agent 分组处理。
3. 如果最终要生成 PPT 或 Word，用文档类插件完成格式转换和排版。
4. 人检查关键数字、来源和对外表述，再决定是否发布。

这里最重要的不是工具数量，而是每一步都有可检查的中间产物。
资料清单、字段表、问题列表、最终报告，应该能一层层对上。
如果中间产物丢了，只剩一段“我已经整理好了”的回复，后面很难追责。

## 一次公开演示给出的边界

这组公开演示记录里，三个任务分别对应三层能力：

| 任务 | 使用层 | 单次结果 | 主要限制 |
| --- | --- | --- | --- |
| 12 份票据整理报销单 | Work 模式 | 生成 3 个工作表，5 个预设问题找到 4 个 | 大小写金额不一致漏检，关键金额仍需人工复核 |
| 380 篇教程、6287 个链接检查 | Workflow | 调度 105 个子代理，输出 219 个问题 | 消耗 4000 多万 Token，耗时较长 |
| 30 秒录屏复刻网站 | Video2code 插件 | 首页和部分页面接近原版，未点击页面做成占位页 | 布局有差异，免费套餐可能限流，版权需自行判断 |

这些数字只代表那一次任务，不是产品基准测试。
它们能说明能力上限大概在哪里，也能说明失败会以什么形式出现。
选型时真正要问的是：我的任务能不能接受这种失败方式？

如果报销单漏掉一个金额，后果可能是退回重做。
如果链接检查漏掉几个死链，后果可能只是下一轮再补。
如果复刻页面布局有差异，后果可能是原型能用、但不能直接上线。
不同后果，对应不同的人工复核强度。

## 验收比“能不能做”更重要

三层能力都需要验收，只是验收对象不同。

Work 模式看产物：

- 工作表结构是否完整。
- 公式是否重算过。
- 每笔金额能否追溯到原始文件。
- 异常项是否单独标出，而不是被静默忽略。

Workflow 看过程：

- 阶段划分是否覆盖全部输入。
- 每个子 Agent 的结果是否有结构化字段。
- 失败和重试是否被记录。
- 最终清单能否回到具体文件和具体证据。

插件看差异：

- 产物能不能打开、能不能运行。
- 关键页面和交互是否对得上。
- 哪些地方是占位、哪些地方是模型补全。
- 有没有侵犯版权、商标或隐私。

验收不需要一开始就设计得很复杂。
哪怕只记录“输入清单、输出清单、异常清单”三张表，也比只看最终回复可靠。

## 什么时候不该用这三层

有些任务不适合交给 AI 工作台，或者不适合直接交给某一层。

- 需要做财税、法律、医疗等专业判断的任务，AI 只能整理材料，不能替代责任人。
- 涉及真实付款、发消息、提交表单等不可逆动作，必须先确认权限和回滚方式。
- 包含大量个人隐私、客户数据或商业机密的资料，先脱敏，再决定能不能上传。
- 没有明确验收标准的“帮我优化一下”，先拆成可检查的小目标。
- 一次性的小任务，不值得写工作流脚本，直接手动做可能更快。

工具越多，越要保留“这件事不该自动化”的判断。
自动化不是目的，稳定交付才是。

## 结论

ZCode 的办公能力可以按三层理解：

- Work 模式负责单任务、少量材料、需要边看边改的交付。
- Workflow 负责大批量、流程固定、需要并行和审计的检查。
- 插件负责补足专业工具链和外部系统连接。

选择顺序应该是：先看输入规模和流程，再看工具缺口，最后才看模型。
如果任务后果很重，就把人工复核放在交付前，而不是放在出问题之后。

下一步验证建议：拿自己手里一个真实但脱敏的小任务，分别用 Work 模式和一份手工流程跑一遍，记录产物、异常和人工耗时。
有了这组对照，再决定要不要把它升级成工作流或插件。
