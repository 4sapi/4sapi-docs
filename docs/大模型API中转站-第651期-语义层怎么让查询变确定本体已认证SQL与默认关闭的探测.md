# 语义层怎么让查询变确定：本体、已认证 SQL 与默认关闭的探测

自然语言查数据库，最坏的失败不是报错。

报错能立刻发现，改个问法重来。麻烦的是另一种：SQL 语法没问题，跑得通，返回一个数，只是数错了——过滤值拼错、join 走错、口径不是业务部门那个。它安静地进到报表里，三天后被人指出来。

NVIDIA 开源的 auto-ontology 就是冲着这个失败模式去的。仓库 `.env.example` 里有一句注释把动机写得很直白：这些检查是拿常驻查询成本，换"避免静默返回错值"（避免 SQL 返回非空但错误的行）。

下面拆它的机制：确定性来自哪几处、哪几处默认没开、哪些环节仍靠模型。信息来自仓库 README、`.env.example` 与三份源码（检索日期 2026-11-09），我没有部署过。

## 一、它想补的是定义，不是翻译

README 开头的说法是：agent 能检索文档、能查数据库，但卡住 agentic analytics 的是可靠性——一个更快的营收数字，如果是错的，就一文不值。

于是它要建一层上下文，回答六个问题：数据在哪、什么意思、该不该用、怎么用、从哪来、什么和它相似。

六问里只有"在哪"是纯元数据问题，其余五个都涉及语义。所以它不是"不做 text-to-SQL"——功能第一条就是把问题翻译成 SQL——而是**在翻译之前先定住词**。

顺序差别很大：先定词，模型只在几个已认证的定义之间选；先翻译，每一步都在自己发明口径。

## 二、本体里有三类定义

生成出来的本体，内容不是一张表清单，而是三样东西：

| 类型 | 是什么 | 作用 |
| --- | --- | --- |
| 术语（Terms） | 业务概念，如"客户""发票行"，带描述与同义词，映射到实际列 | 让问题里的词能落到物理列上 |
| SQL 属性（SQL attributes） | 复核过的 SQL 表达式，如毛利率、滚动合计 | 让同一个指标每次都用同一种算法 |
| 关系（Relationships） | 表怎么 join，含桥接表，从键和数据里推断 | 让跨表问题找到正确的连接路径 |

第二类是这套设计里最关键的一格，后面还会回来说。

生成阶段分四步：读源（抽 schema、profile 列、把采样值带进目录）→ 命名实体（逐表抽术语并映射到列）→ 解析关系（推断 join 与桥接表，并从查询历史里建议 SQL 属性）→ 写入本体（定义进 Postgres，向量进 pgvector）。

README 给了一个规模参考：对微软的示例销售库 Wide World Importers 编译一次，产出 31 个术语。认证（Certify）是人和草稿之间的那一步：术语、描述、SQL 属性确认无误后标成已认证。

## 三、回答一个问题的五步

1. 分类意图，抽出问题里提到的实体；
2. 用 embedding 检索候选的术语、列、SQL 属性；
3. 用这些候选写 SQL；
4. 对着数据库校验过滤值与查询，失败就修复；
5. 执行，返回答案、SQL 和走过的步骤。

第 4 步是它和"直接让模型写 SQL"最大的区别：不是写完就执行，而是先验。验什么、什么时候验，决定了它的可靠性上限。

## 四、确定性来自五处，默认只开两处

把源码和文档对起来看，能约束"模型乱来"的机制有五处，但默认状态并不一致：

| 机制 | 默认 | 作用 |
| --- | --- | --- |
| 复用已认证的 SQL 属性 | 常开 | 指标一旦被认证成一段 SQL，后续同类问题复用它，而不是每次重写公式 |
| 空结果修复 | 常开 | 查出来是空，先触发一轮值修复重试，而不是直接把"0 条"交给用户 |
| 字面量对库校验（`DB_PROBE_PROACTIVE`） | **关** | 对带分类过滤的查询跑几次 DISTINCT 探测，抓拼错的枚举值 |
| join 路径检查（`DB_PROBE_JOIN_PATH_CHECK`） | **关** | 确认两表之间的连接路径在语义外键图里存在，没有边才回退到值重叠探测 |
| GROUP BY 空操作检测（`DETECT_VACUOUS_GROUP_BY`） | **关** | 拒绝把每行唯一的列拿去做聚合——那种聚合跑得通、结果是原样，却像做了汇总 |

这张表改变了常见的印象。**开箱状态下的确定性主要来自"复用已认证定义"和"空结果修复"，而不是对库探测。** 过滤值校验则没这么清楚：预执行的字面量探测默认关，常开的是空结果修复；README 第 4 步把校验写成无条件。我按"探测是加固层"理解，没实测。

如果你的源库里枚举值脏、JSONB 字段多、表之间靠隐式关系连接，那就该把对应开关打开——代价是每次查询多几次探测。

先量三件事：分类过滤在查询里多常见、JSONB 字段有多少、跨表问题里有多少是指定值。

这些都能从慢查询日志里数出来；数完再决定，比照文档默认值猜靠谱。

## 五、为什么那几道默认关着

源码里的注释给了理由，两类的理由还不一样。

字面量探测关着，是因为它跑在**每条**带分类过滤的查询上，是常驻成本，所以做成 opt-in。GROUP BY 空操作检测关着，是因为它依赖主外键元数据与数据画像，元数据不全时可能误杀正确查询，反而多烧一轮重建。

还有一个坑要单独说。`.env.example` 里那行写作 `# DETECT_VACUOUS_GROUP_BY=true`——**前面有个井号**，注释掉才等于不启用。肉眼扫过去很容易读成"默认开启"。

再有一个组合风险。`.env.example` 提到：关掉 `DB_PROBE_JOIN_PATH_CHECK` 时，意图校验那一侧会退化成自己判断 join 合法性。注释里给了一句明确的"不建议"——如果这时再把那一项单独设成"合法性已在别处验证"，就没有任何环节在查 join 了。

## 六、哪些环节仍然是模型判断

即使所有开关都打开，链条上仍有三处是模型在拿主意：

- **意图分类与实体抽取。** 问题里的"营收"落到哪个术语，靠模型加检索。
- **候选筛选。** embedding 召回一堆术语和列，选哪几个进 SQL，是模型判断。
- **写 SQL 与修复 SQL。** 校验失败后怎么改，也是模型。

所以准确的说法不是"确定性地生成 SQL"，而是**把模型的不确定性限制在几个可检查的节点之间**。定义是确定的，校验是确定的，生成仍是不确定的。

模型角色有四个：`REASONING`（建本体、写答案 SQL、给可答性打分）、`NON_REASONING`（意图、实体抽取、候选选择、SQL 校验修复）、`EMBED`、`RERANK`。配置上用的是所谓 triplet：每个角色三个字段——`<PREFIX>_ENDPOINT`、`<PREFIX>_API_KEY`、`<PREFIX>_MODEL`，没设的字段逐项回退到 `DEFAULT_MODELS_*`。

这里有个容易被讲成"成本优化"的地方，实际上不是：**`REASONING` 与 `NON_REASONING` 的默认值是同一个模型**（`nvidia/nemotron-3.5-lightning-30b-a3b`）。角色切分留了口子——把 `NON_REASONING_MODEL` 换成更便宜的小模型就能把钱省在意图与抽取上——但这是配置项，不是开箱收益。

## 七、怎么判断它到底行不行

README 没有给任何准确率数字。Benchmarks 那一节只有一句：跑 BIRD 这类基准，去看同一组织的另一个评测仓库。也就是说**这个仓库本身不提供分数**，谁引用分数都得去那边取，并看清口径。

不给分数的项目，验收只能自己搭。我整理了三层：

| 层 | 验什么 | 怎么看 |
| --- | --- | --- |
| 就绪 | 语义层编译了没有、数据库连上没有 | `check_readiness` 明确区分这两件独立的事；官方提醒 `databases` 非空不等于能执行 SQL |
| 覆盖 | 这个问题本体覆盖得了吗 | `check_answerable` 给覆盖度，官方示例里问广告花费返回 0.5，并说明没有对应术语 |
| 结果 | 答案对不对 | 每次回答都带 SQL 与步骤，可以对回源库；MCP 侧结果上限 100 行，用 `row_count` 与 `truncated` 标明截断 |

第二层最容易被跳过。"本体没这个概念"和"模型这次写错"是两种失败，前者调 prompt 没用，得补术语。

还有个细节能看出对"agent 会乱来"的预判：MCP 只暴露 9 个工具，OpenAPI 规范里却有 87 个操作，文档说全部暴露会明显降低工具选择质量。工具里刻意没有浏览表结构、读原始列这类能力，逼 agent 走语义层。

延迟也要有预期：`ask_question` 是完整链路，多次模型调用，官方说法通常几十秒。验收时顺手记两个字段：是否触发修复循环、总耗时。同一道题"一次写对"和"改三轮才对"正确率一样，但后者说明候选里混了干扰项，后面会突然变差。

## 八、五种常见的误配

**摄取与查询用不同的 embedding 模型。** 官方两处都强调这一点：摄取和查询必须用同一个。不一致时的预期表现是召回一堆不相关的候选（这条是推断，未验证）。

**把 `EMBED_MODEL` 删掉或清空。** 样例文件已经替你显式写了一行 `EMBED_MODEL=nvidia/nemotron-3.5-embed-1b`，注释也说明了原因：留空的字段会回退到默认的对话模型。风险来自"我只抄了 `DEFAULT_MODELS_*` 三行"这种简化。

**把"编译完成"当成"可以用"。** 编译只是生成草稿，术语、描述、SQL 属性还要人认证。跳过认证，等于把模型自拟的定义当成公司口径。

**把 `check_answerable` 的覆盖度当准确率。** 它回答的是"本体里有没有能支撑这个问题的定义"，不是"生成的 SQL 对不对"。

**把结果当实时。** 摄取按 `INGEST_INTERVAL_HOURS` 周期跑，默认 24 小时，启动先跑一次。源库新加一列，当天语义层里没有它，表现是"覆盖不了"而不是"权限不够"（同样是推断）。

五条的共同点：都不报错，只降质量。监控发现不了，只能靠对照实验。

## 九、结论与边界

这套设计的核心不是"让模型更会写 SQL"，而是**把可复用的业务定义变成一等公民**：术语定住词，SQL 属性定住算法，关系定住连接路径，模型只负责在这几样之间选和拼。

我的判断：对已经有语义模型或指标定义、但下游 agent 老是问错的企业，这个结构对得上问题；对只有一个干净小库、问题又固定的场景，写几条 SQL 模板更省事。

限制：没有部署，没跑过一次问答；机制描述来自 README 与源码，不是实测；五处机制的默认值取自 `.env.example` 与 `db_probe/config.py`，实际行为未验证；第八节两处失败现象是我的推断；仓库不提供基准分数，本文也没引用任何分数；`.env.example` 注释提到用 Neo4j 做 join 路径检查，但目录树没有 neo4j 模块、组件表说本体存 Postgres，这处不一致我只并列陈述，不推断原因。

下一步如果只做一件事：拿你自己库里三个口径最容易吵架的指标，看它们能不能写成一条 SQL 属性。写不出来，问题就不在查询层，在定义层。
