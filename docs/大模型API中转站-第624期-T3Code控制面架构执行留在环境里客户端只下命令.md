# T3 Code 的控制面架构：执行留在环境里，客户端只下命令

当一个工具同时提供网页、桌面和手机客户端，又说能控制你机器上的编程智能体时，第一个该问的问题是：代码到底在哪里跑。如果答案是"客户端把任务发到云端再回来"，那它和你本机的仓库、环境变量、凭据就是两回事；如果答案是"仍然在你机器上跑"，那客户端只是遥控器，问题就变成遥控器能做什么、不能做什么。

T3 Code 的架构文档把这条边界写成了硬规则。本文拆解它的四个设计：执行归属、事件与副作用的分离、命令回执的含义、以及检查点怎么做到不加提交。这些设计和具体产品无关，做多端控制或远程开发的人都能借用。

架构描述来自仓库的 [`docs/internals/overview.md`](https://github.com/pingdotgg/t3code/blob/HEAD/docs/internals/overview.md)；仓库元数据（协议、创建时间、星标、文件数）来自 GitHub API 与 README。检索日期为 2026-11-02。我没有安装或运行过它，也没有读它引用的源码文件。

## 一、先看这个项目是什么

| 项目 | 内容 |
| --- | --- |
| 仓库 | [pingdotgg/t3code](https://github.com/pingdotgg/t3code) |
| 协议 | MIT |
| 创建 | 2026-02-08 |
| 最近推送 | 2026-11-02 |
| Star 数 | 38,169（检索当天） |
| 自述定位 | agent harness 控制面：控制本机已有的各家 agent，支持 iOS、Android、Web 与 Electron 桌面端 |

它的做法不是另起一个 agent，而是复用你机器上已经装好并登录的 CLI（Claude Code、Codex、Cursor、Grok Build、OpenCode、Antigravity 等）。README 说得很直接：这些工具在你电脑上配好之后，T3 Code 就能控制它们。

这句话的技术含义是：模型调用、订阅、凭据、工作区都在你原来的环境里，T3 Code 提供的是上层编排与多端界面。

## 二、第一条硬规则：执行留在环境里

架构文档的第一段就是边界声明，可以拆成三句：

1. 执行留在拥有工作区的那个环境里。
2. 网页、桌面、移动客户端通过经过认证的 RPC 控制它。
3. 远程客户端**绝不能**用自己的文件系统、提供方凭据或机器状态，替代那个环境的。

第三句是这条设计的核心。它排除了一整类问题：手机上没有你的仓库，没有你的 API key，也没有你的环境变量；如果它要显示文件，那必须是从环境取来的内容，而不是本地缓存被当成真相。

文档还补了一句容易被忽略的：桌面应用内置了服务器，但它的渲染进程遵守同一边界。也就是说，"桌面版"不是特权客户端，它和网页版一样走同一条 RPC。

### 所有权清单

| 归属 | 内容 |
| --- | --- |
| 服务器 | 提供方进程、终端、Git、项目文件 |
| 客户端 | 平台服务与界面；共享的连接与领域状态放在共享包里 |

把"连接逻辑"和"界面"分开是有理由的：文档说这能避免重连与多环境行为在网页与移动端各自漂移。做过双端应用的人大概都遇到过这种分叉：同一套重连逻辑写了两遍，半年后就只有一端正确。

## 三、第二条规则：认证与会话不等于方法授权

文档里有一句话值得抄下来：套接字通过认证，不等于它上面的每个方法都被授权。

这句话区分了两层安全检查。第一层是连接级：这个设备有没有通过配对拿到会话。第二层是方法级：这个会话能不能做这件事。

两层的区别在实践里很关键。如果只有第一层，那么任何能连上的客户端都能做所有事；有了第二层，同一个连接可以只能读、不能改。

同一个思路还出现在订阅设计里：客户端只收到它需要的状态，所以"看一个线程"的客户端不必为所有线程的历史付费。这是性能考虑，但也顺便限制了横向暴露面。

权限的具体粒度会讲在远程访问那篇里，这里的重点是架构上留了这个位置。

## 四、第三条：事件是决定物，投影才是真实来源

这是我认为最值得借鉴的部分，但它的口径容易被讲反。文档的原文是：编排状态以事件的形式被决定，而**投影在被应用之后才是真实来源**。事件日志并不长期保存——它只为在线读者保留约一天的历史（用于重连回放与命令 id 重试），更早的事件由投影维护程序删除，因此**投影无法从日志重建**。

### 命令与副作用分开

文档描述的链条是：

| 角色 | 做什么 | 不做什么 |
| --- | --- | --- |
| 编排器 | 串行化命令、决定产生哪些事件 | 不做提供方或文件系统工作（原文明确） |
| EventSink | 在**一次**数据库事务里提交事件、持久化投影、命令回执、待发副作用 | 不执行副作用（原文只说外部 I/O 要在事务之外，这格是我从分工反推的） |
| effect worker | 在意图被记录之后执行副作用，再把结果回灌 | 不决定意图（同上，推断） |

好处是重试可以做成幂等：命令被重放时，因为意图和回执已经在同一个事务里落库，系统知道这条命令处理过；而慢的、可能失败的外部动作放在事务之外，不会把数据库事务拖长。

### 命令回执不等于完成

文档明确写了这一点：一条命令被确认，只代表意图已提交，不代表提供方工作、检查点或其他后续步骤已经完成。

这条区分解释了很多"为什么界面上显示成功但东西还没好"的问题。它也给出正确的做法：界面应订阅事件来显示进展，而不是把回执当成完成信号。

### 副作用不能简单重放

还有一条更细的规则：与丢失的提供方进程绑定的副作用不能直接重放，恢复时会先把它们作废，再接纳新任务。

这条比看起来重要。外部副作用（例如已经发给模型的请求）通常不是幂等的；如果盲重放，可能重复调用、重复计费。先作废再重来，是更保守但也更安全的顺序。

## 五、第四条：检查点不加提交

智能体改代码时，想做"回滚到上一步"的功能，直觉做法是每次改动都提交一次。这会污染用户的分支历史。

文档给出的做法是用隐藏的 Git ref 捕获工作区状态，不在用户分支上加提交。同时规定了一条约束：回滚必须让工作区与提供方会话协调；如果某个提供方无法回滚它自己的会话，那么必须在改动文件系统之前就拒绝这个操作。

为什么这个顺序重要？因为两侧状态会不一致：

- 只回滚文件、不回滚对话：模型以为已经做的修改还在，下一轮它会基于不存在的前提继续推理。
- 只回滚对话、不回滚文件：文件里留着改动，但对话忘了，用户看到的是"没解释的变更"。

先拒绝、而不是先改文件，保证的是不制造这种不一致状态。这是一个典型的"宁可失败也不半成功"的设计。

## 六、一个容易漏的细节：外部动作的回环

文档提到线程结算由服务器负责，其中有个case：在 T3 之外发生的合并不会给 T3 发通知，例如 agent 自己在终端里执行了 `gh pr merge`。

解法是在"运行了合并或关闭命令的那次执行结束时"，由同步组件重新读取该线程的链接状态。

这类问题在编排系统里很常见：你以为是自己的界面在改状态，其实外部工具也能改。只要有一个外部入口存在，就不能假设事件一定从自己这边发出来。

## 七、这套设计对自建系统的启发

| 做法 | 可以怎么用 |
| --- | --- |
| 执行归属写进文档第一段 | 让"谁拥有文件与凭据"成为不可协商的前提 |
| 连接认证与方法授权分开 | 远程接入时默认只读，写权限单独授予 |
| 意图与副作用分事务 | 重试幂等、长任务不阻塞事务 |
| 回执不等于完成 | 界面状态来自事件流而非接口返回 |
| 检查点用隐藏 ref | 支持回滚又不污染用户分支 |
| 外部动作后主动重读 | 别假设状态只由自己改变 |

第五行有一个前提：用隐藏 ref 需要你的工具能操作 Git 底层引用。对非 Git 管理的工作区，要另找机制。

## 八、这套架构的代价

以下是基于设计的推断，不是项目自述。

| 设计 | 代价 |
| --- | --- |
| 事件日志加投影 | 多一层需要维护的持久化；schema 变更要考虑旧环境启动与重放兼容 |
| 意图与副作用分离 | 组件更多，排查一个动作要跟两个地方 |
| 客户端只拿订阅状态 | 客户端要正确处理增量与重连 |
| 回执语义分离 | 需要前端正确区分"已提交"和"已完成" |
| 多端一致 | 共享逻辑的包一旦改错，两端一起错 |

文档自己也提到兼容负担：持久化的事件必须能在重放时解码，改 schema 会影响旧环境启动，而不只是新客户端发来的流量。

## 九、限制与结论

这套架构的可取之处不在功能列表，而在把几件事写成了规则：执行永远留在拥有工作区的那一端，客户端连自己的机器状态都不能当真相；命令的意图与副作用分处事务内外（一个事务落库，外部动作在事务之外执行）；回执只表示意图已提交；回滚前先确认两侧状态能一起撤销。

本文的限制：没有运行过任何客户端或服务器；只读了架构文档，没有读它引用的源码；权限与远程访问的具体粒度另有两篇讨论；文档提到的兼容性细节我只引用了结论，没有核对实现。

下一步建议：如果你在做类似的编排系统，先确定"副作用不可重放"这一条怎么落地——它决定你的失败恢复是保守还是激进。其余设计都可以后补，这一条改起来最贵。
