# Grok Bot 多 Bot 怎么协作：从任务交接到电商团队审批

创建多个 Bot 并不自动等于拥有一支数字员工团队。如果每个 Bot 都没有明确结果，或者多人同时改同一份文件，协作只会增加混乱。真正需要设计的是任务顺序、交接内容、最终负责人，以及哪些动作必须停在人工审批。

这篇文章聚焦多 Bot 的交接协议、共享文件和审批边界，并用电商运营场景串起一条完整协作链。

## 一、什么时候应该创建第二个 Bot

第二个 Bot 不应该因为“看起来很酷”而创建。

出现以下信号时，才值得拆分岗位：

```text
一个岗位长期同时处理两类不同结果。
两类工作使用不同数据源和判断标准。
交接关系已经反复出现。
每个阶段都能独立验收。
```

例如情报研究员负责找资料，内容筛选员负责判断哪些选题值得继续。

这两个职责的输入、判断和交付不同，拆分后才有实际意义。

## 二、先定义交接协议

Bot 之间不能只传一句“你继续处理”。

每次交接至少包含：

```text
任务目标。
当前阶段。
输入文件或消息。
已完成事项。
未完成事项。
需要接收方回答的问题。
交接后的验收标准。
```

示例：

```text
情报研究员已完成过去 7 天 Grok Bot 资料收集。
请内容筛选员按目标读者、证据完整度和可操作性排序，
标记需要补充来源的条目，并把结果保存到 /workspace/grokbot-demo/output/topics.md。
不要发布内容，不要联系作者。
```

## 三、共享目录要有清晰的文件约定

多个 Bot 使用共享云电脑时，建议为每个项目单独建目录：

```text
/workspace/grokbot-demo/
├── input/
│   └── research-2026-09-03.md
├── working/
│   └── topic-review.md
├── output/
│   └── approved-draft.md
└── evidence/
    └── handoff-001.md
```

文件名要能说明内容、日期和阶段。

不要让两个 Bot 同时覆盖 `final.md`。

可以约定：只有最后负责人能写入 `output/`，其他 Bot 只能写入自己的工作区。

## 四、一对一交接适合线性流程

一对一消息适合固定顺序：

```text
研究员 → 筛选员 → 编辑员 → 人工确认
```

每次只唤醒下一名负责人，过程简单，也容易定位错误来自哪一环。

如果接收方需要补充信息，应在回复中列出缺口，而不是悄悄猜测。

## 五、群聊适合公开交接

当所有参与者都需要看到上下文时，可以使用群聊。

群聊第一条消息要写清：

```text
共同目标。
当前负责人。
交接顺序。
共享文件目录。
最终停止位置。
```

示例：

```text
共同目标：完成本周 AI 选题清单。
情报研究员先整理原始资料，内容筛选员负责排序并提出补充要求，
情报研究员完成返修，最终结果停在人工确认，不自动发布。
```

群聊不是让所有 Bot 同时发言。

每个阶段只设置一名负责人，避免多人同时改写同一文件。

## 六、什么时候使用 @everyone

@everyone 会同时唤醒整组 Bot，应该谨慎使用。

适合的情况是：

```text
所有成员都要独立检查同一份变更。
发生重大范围变化，需要重新评估。
最终汇总前，需要各岗位提交状态。
```

普通交接只 @ 下一名负责人即可。

唤醒整组 Bot 会增加重复读取和重复输出，也可能导致文件冲突。

## 七、先做最小交接实验

第一次不要从复杂团队开始。

可以只验证三步：

1. Bot A 生成一份结构化文件；
2. Bot B 读取文件并提出两个补充问题；
3. Bot A 根据问题修订，最后停在人工确认。

验收时检查：

```text
Bot B 是否读取了正确文件。
补充问题是否来自输入缺口。
Bot A 是否保留了原始事实。
最终结果是否没有自动外发。
```

## 八、电商团队先创建一个值班员

电商场景不建议一开始就创建十个岗位。

第一阶段可以创建“店铺经营值班员”，只读商品、库存、订单和内容表现数据，生成一份经营晨报。

岗位说明可以这样写：

```text
每天读取指定的商品表、库存表、订单表和内容表现表。
输出昨日经营概况、缺货与积压、订单异常、内容表现和当天待处理事项。
只读数据并生成报告。
不改价、不改库存、不发布内容、不退款、不取消订单、不发送客户消息。
数据缺失或日期不一致时明确报错，不使用旧数据冒充当天数据。
```

先用脱敏 CSV 跑通一份晨报，再考虑连接真实系统。

## 九、稳定以后再拆三个专业岗位

当值班员的结果稳定后，可以拆出：

| Bot | 负责结果 | 禁止动作 |
| --- | --- | --- |
| 内容增长专员 | 选题、内容表现和优化建议 | 不直接发布 |
| 商品库存分析员 | 缺货、积压和库存趋势 | 不改库存、不改价 |
| 订单售后助理 | 履约、退款和咨询异常队列 | 不退款、不发消息 |

原来的值班员可以升级成运营主管，负责读取三份结果，生成老板需要决定的事项。

## 十、一次真实的跨岗位交接

假设库存分析员发现某个 SKU 预计只够三天销售。

它应交给内容增长专员：

```text
SKU。
当前库存。
近期开单量。
预计库存天数。
计算依据。
需要调整的内容计划。
```

内容增长专员检查接下来是否仍在重点推广这个 SKU。

如果是，就提出暂停相关选题、转移流量或等待补货的建议，但不直接修改线上内容。

订单售后助理可以同时检查延迟发货咨询是否增加，并生成客户回复草稿。

运营主管最后只汇总三个需要老板决定的问题：是否补货、是否调整内容计划、是否修改预计发货话术。

## 十一、共享文件要避免“最后写入者获胜”

多个 Bot 同时改同一个文件时，容易出现覆盖。

建议采用追加和版本化：

```text
库存分析员写 inventory-risk-001.md。
内容专员写 content-impact-001.md。
售后助理写 support-impact-001.md。
运营主管读取三份文件后生成 daily-brief-001.md。
```

每个文件只由一个岗位负责写入。

如果确实需要修改同一份草稿，必须明确当前负责人和版本号。

## 十二、最终负责人不能由模型自动推断

团队协作中，最容易被忽略的是最终责任人。

应在任务开始时写明：

```text
谁可以决定建议是否采用。
谁可以批准发布或发送。
谁负责处理失败和争议。
```

运营主管可以汇总建议，但不能替老板批准补货、改价或退款。

Bot 之间可以协作，责任授权仍然属于人。

## 十三、高风险动作必须设审批点

以下动作建议默认停在人这里：

```text
发布 X 内容或商品内容。
发送客户私信和邮件。
付款、退款和取消订单。
删除文件。
修改账号权限。
更改生产系统。
```

Bot 可以准备草稿、列出影响、生成回滚步骤，但不能因为“任务目标是完成”就自行执行不可逆动作。

## 十四、审批规则要写具体范围

“所有危险操作需要审批”太模糊。

应写成可匹配的规则：

```text
发布任何 X 内容前必须审批。
删除 /workspace/client-a/ 下的文件前必须审批。
改变订单退款状态前必须审批。
向外部客户发送消息前必须审批。
修改生产数据库或部署配置前必须审批。
```

范围越清楚，用户越容易判断这次操作是否真的需要接管。

## 十五、同一账号下的权限边界

多个 Bot 共享同一账号、云电脑、文件和登录状态时，岗位分工不等于权限隔离。

因此不要把“内容 Bot 不应该看订单”理解成系统已经自动阻止它。

真正需要隔离时，应使用独立账号、独立连接器权限或独立运行环境。

## 十六、团队运行日志要记录什么

每次交接至少记录：

| 字段 | 说明 |
| --- | --- |
| task_id | 哪个任务 |
| sender | 谁发起交接 |
| receiver | 谁接收 |
| input_file | 读取了什么 |
| output_file | 生成了什么 |
| status | 完成、部分完成或失败 |
| approval | 是否等待人工 |
| timestamp | 发生时间 |

日志的作用不是增加形式，而是让团队可以回放：哪一环没有读到数据，哪一环越过了边界，哪一环产生了重复文件。

## 十七、常见失败方式

### 失败一：所有 Bot 都叫“总监”

岗位范围过大，没人能判断交付是否完成。

### 失败二：没有交接文件

下一个 Bot 只能从聊天历史猜当前状态。

### 失败三：所有人同时编辑最终文件

后写入的内容可能覆盖前一个岗位的证据。

### 失败四：把建议当成执行授权

库存分析员提出补货建议，不等于它可以生成采购单或付款。

### 失败五：用共享账号假装权限隔离

岗位名称不能代替真实系统权限。

## 十八、结论

多 Bot 协作的核心不是数量，而是分工、交接、文件和审批。

先让一个岗位稳定交付，再拆出真正不同的专业职责；每次交接都传递目标、输入、状态和验收标准；每个阶段只保留一个文件负责人。

电商团队可以从只读经营晨报开始，逐步增加内容、库存和售后分析岗位，但发布、退款、付款、删除和生产变更仍应停在人工审批。

这样搭出来的数字员工团队，才更接近一条能回放、能纠错、能交付的业务流程。
