# 【大模型API中转站】第147期 MCP与Harness | 企业API网关搭架构

本文是【大模型API中转站】系列的第147篇。本系列致力于用最低的成本、最清晰的方法，帮你打通多模型API的任督二脉。建议先收藏，随用随查。

上一篇我们讲了 Agent 的基本结构：

```text
模型
  + 工具
  + 状态
  + 决策
  + 验证
  + 停止
```

这一篇往工程层再走一步。

真正的企业 Agent，不是把一个模型接进来就结束。

它至少有三层：

```text
模型入口：谁来调用 Claude、GPT、Gemini、DeepSeek。
工具入口：谁来调用 GitHub、Notion、数据库、搜索、浏览器。
运行外壳：谁来管理上下文、状态、日志、重试、权限。
```

对应到现在最常听到的几个词，就是：

```text
4SAPI 中转站：模型 API 网关。
MCP：工具接入协议。
Harness：Agent 运行外壳。
Context Engineering：上下文管理方法。
```

这些词很容易混。

这篇就把边界拆清楚。

## 1. MCP 解决的是“工具怎么接”

先说 MCP。

MCP 可以理解成 Agent 工具层的标准接口。

在没有 MCP 之前，一个工具想被不同 Agent 使用，往往要给不同平台写不同适配：

```text
给 Claude 写一套。
给 ChatGPT 写一套。
给 Cursor 写一套。
给本地 Agent 框架再写一套。
```

工具少的时候还能忍。

工具一多，就是组合爆炸。

MCP 的思路是：

```text
工具提供方实现一个 MCP server。
Agent 客户端按统一协议发现工具、读取描述、传参数、拿结果。
```

比如你想让 Agent 操作 GitHub、查数据库、读 Notion、访问内部知识库，都可以把它们包装成 MCP server。

这样 Agent 看到的不是一堆散乱 SDK，而是一组结构化工具。

简单说：

```text
MCP 不是模型。
MCP 不是中转站。
MCP 是工具接入层。
```

这一点很重要。

很多人听到 MCP 火，就以为有了 MCP 就解决了 Agent 落地。

不是。

MCP 只解决“工具怎么挂上来”。

它不负责你的模型成本。

不负责模型路由。

不负责 API Key 分组。

不负责预算控制。

不负责团队审计。

这些还是要交给 4SAPI 这类模型 API 网关，以及 Agent harness 里的治理逻辑。

## 2. 工具层越标准，权限越要收紧

MCP 的好处，是让工具更容易接。

但工具越容易接，权限越容易失控。

一个企业内部 Agent 可能会接这些工具：

| 工具 | 常见用途 | 权限风险 |
| --- | --- | --- |
| GitHub | 读 issue、写 PR、跑 review | 误提交、误关 issue |
| 数据库 | 查客户、查订单、查日志 | 数据泄露、误写入 |
| Notion/飞书文档 | 查知识库、写总结 | 写错文档、覆盖内容 |
| Slack/企业微信 | 发通知、读群消息 | 误发消息、泄露内容 |
| 浏览器 | 操作后台、填表单 | 被页面内容诱导 |
| 文件系统 | 读写本地项目 | 误删或误改 |

所以 MCP 接入时，最小权限原则一定要前置。

不要给一个通用 Agent 直接挂全公司工具。

更推荐按角色拆：

```text
research-agent：只读搜索、知识库、文档。
coding-agent：只读写指定代码目录、跑测试。
ops-agent：只读日志、生成排查建议，不直接重启服务。
support-agent：只读工单、生成回复草稿，不自动发送。
finance-agent：只读报表，不写付款和审批。
```

工具描述也要写清楚。

不要只告诉模型：

```text
tool: update_ticket
```

而要写清：

```text
这个工具只能更新工单备注。
不能关闭工单。
不能修改客户信息。
不能发送外部邮件。
```

模型不是安全边界。

工具权限才是。

## 3. Context Engineering：别把上下文塞成垃圾桶

Agent 的第二个大坑，是上下文。

很多人以为上下文窗口越大越好。

实际不是。

上下文窗口大，只代表能塞更多东西。

不代表塞进去的东西都有用。

Context Engineering 的核心不是“多塞”，而是：

```text
把下一步真正需要的信息，以尽量高信号的方式交给模型。
```

一个 Agent 每跑一步，都会产生新信息：

```text
用户目标。
系统规则。
历史消息。
工具定义。
工具返回结果。
文件内容。
搜索结果。
错误日志。
中间计划。
之前失败的尝试。
```

如果每一步都全量塞回去，很快就会变成上下文垃圾桶。

模型看得越多，未必越稳。

有时反而更容易被无关信息带偏。

更合理的做法是分层：

| 信息类型 | 处理方式 |
| --- | --- |
| 系统规则 | 固定保留，短而清楚 |
| 当前任务目标 | 每轮保留 |
| 最近工具结果 | 保留原文或关键片段 |
| 旧历史 | 摘要压缩 |
| 大文件 | 按需检索，不全量塞 |
| 项目长期规则 | 写入规则文件或知识库 |
| 无关日志 | 丢弃 |

这一层做得好，Agent 会像一个知道自己在干什么的人。

做得不好，Agent 会像一个桌上堆满纸、每张都扫一眼的人。

看起来很努力，实际抓不住重点。

## 4. Harness：模型外面那层壳

现在很多工程讨论里会提到 harness。

这个词可以理解成：

```text
把模型架起来、接上工具、喂上下文、收结果、做验证、管日志的整套外壳。
```

如果模型是发动机，harness 就是底盘、仪表盘、刹车、油表和维修接口。

一个 Agent harness 通常负责这些事：

| 模块 | 作用 |
| --- | --- |
| 模型适配 | 调用不同模型，处理返回格式 |
| 工具注册 | 告诉模型有哪些工具可用 |
| 上下文管理 | 决定每轮给模型看什么 |
| 状态存储 | 记录任务进度、中间产物、检查点 |
| 执行控制 | 控制最大轮数、超时、重试 |
| 验证器 | 跑测试、检查格式、模型互审 |
| 日志追踪 | 记录每次模型调用和工具调用 |
| 权限系统 | 限制工具、目录、外部 API |
| 成本治理 | 记录 token、模型、费用、归属 |

所以不要把 Agent 能力全归功于模型。

同一个模型，套在不同 harness 里，表现可能差很多。

这也是为什么有些产品看起来“模型一样”，但一个能交活，一个总跑偏。

差距往往就在外面那层工程。

## 5. 4SAPI 在 Harness 里负责什么

4SAPI 不替代 harness。

它是 harness 里“模型调用入口”的重要一层。

一套企业级 Agent 架构可以这样拆：

```text
业务系统 / 工作流平台 / 桌面 Agent
        ↓
Agent Harness：任务、状态、工具、验证、停止
        ↓
4SAPI：模型入口、Key、路由、日志、预算、审计
        ↓
上游模型：Claude / GPT / Gemini / DeepSeek / Qwen / Kimi
        ↓
MCP 工具层：GitHub / DB / Docs / Search / Browser
```

4SAPI 主要管这些：

```text
统一 Base URL。
统一 API Key。
模型名称和分组。
不同项目的调用日志。
不同模型的成本统计。
预算、额度、限流。
失败原因和状态码。
测试环境和生产环境隔离。
```

MCP 主要管这些：

```text
工具发现。
工具描述。
工具参数。
工具执行。
工具返回。
```

Harness 主要管这些：

```text
任务流。
上下文。
状态。
重试。
验证。
停止。
权限策略。
```

这三层不要互相替代。

混在一起，后期很难维护。

## 6. 推荐的企业架构

如果你要给团队搭一个 Agent 平台，我建议先按这张图理解：

```text
用户 / 工单 / PR / 定时任务
        ↓
任务入口层
        ↓
Agent Controller
  - 任务拆解
  - 最大轮数
  - 状态检查
  - 停止判断
        ↓
Context Manager
  - 当前目标
  - 最近结果
  - 项目规则
  - 检索摘要
        ↓
Model Gateway: 4SAPI
  - 模型路由
  - Key 分组
  - 调用日志
  - 成本统计
        ↓
Tool Gateway: MCP Servers
  - GitHub
  - 数据库
  - 文档
  - 搜索
  - 浏览器
        ↓
Verifier
  - 测试
  - 格式校验
  - 安全检查
  - 人工确认
```

这套结构的好处是职责清楚。

模型换了，不影响工具。

工具换了，不影响模型网关。

任务逻辑改了，不需要到处改 Key。

成本异常，可以从 4SAPI 日志里追。

工具异常，可以从 MCP server 日志里追。

任务跑偏，可以从 harness 的状态和轨迹里追。

这才是能长期维护的 Agent 工程。

## 7. 接入教程：先把模型入口收口

落地时不要一口气全做。

第一步先把模型入口统一。

如果你的 Agent 框架支持 OpenAI Compatible 接口，可以先配置：

```text
Base URL: https://4sapi.com/v1
API Key: 4SAPI 令牌
Model: 模型广场中的模型名称
```

建议按任务角色拆模型：

| 角色 | 模型要求 | 4SAPI 治理重点 |
| --- | --- | --- |
| Planner | 推理强，低频 | 额度小，日志完整 |
| Worker | 稳定、速度快 | 控制单轮成本 |
| Reviewer | 质量高，能发现风险 | 只在关键节点调用 |
| Summarizer | 便宜、格式稳定 | 可批量低成本 |

对应的环境变量可以这样命名：

```text
AGENT_BASE_URL=https://4sapi.com/v1
AGENT_PLANNER_KEY=planner角色的4SAPI令牌
AGENT_WORKER_KEY=worker角色的4SAPI令牌
AGENT_REVIEWER_KEY=reviewer角色的4SAPI令牌
AGENT_SUMMARY_KEY=summarizer角色的4SAPI令牌
```

不一定一开始就拆这么细。

但至少不要让所有角色共用一个生产 Key。

否则你后面看日志时，只能看到一团调用。

## 8. 再把工具入口标准化

第二步再接 MCP。

建议顺序是：

```text
先接只读工具。
再接低风险写工具。
最后才接高风险操作。
```

例如：

| 阶段 | 工具 | 是否允许写 |
| --- | --- | --- |
| 第1阶段 | 搜索、知识库、日志查询 | 不允许 |
| 第2阶段 | GitHub issue 备注、文档草稿 | 只写草稿 |
| 第3阶段 | PR 创建、工单状态更新 | 需要人工确认 |
| 第4阶段 | 生产后台操作 | 原则上不自动执行 |

工具配置时，要给每个工具写清楚用途。

尤其是内部工具。

不要让模型猜：

```text
这个接口到底是只读，还是会改数据？
这个参数会不会触发外部通知？
这个操作能不能撤销？
```

工具描述越清楚，模型越不容易误用。

权限越小，误用后果越可控。

## 9. 常见误区

### 误区一：有了 MCP 就不用 API 网关

错。

MCP 管工具，不管模型成本。

模型调用还是要有统一入口、Key、日志、额度和预算。

这正是 4SAPI 中转站的位置。

### 误区二：上下文越大越稳

不一定。

上下文越大，噪声也可能越多。

真正有价值的是高信号上下文，而不是全量上下文。

### 误区三：所有工具都给同一个 Agent

危险。

更好的做法是按角色拆 Agent，按角色给工具。

### 误区四：只看模型效果，不看运行轨迹

Agent 不是一次回答。

它是多步执行。

只看最后结果，不看中间轨迹，出了问题很难复盘。

## 10. 总结

这一篇可以记住一个分工：

```text
MCP 管工具。
4SAPI 管模型入口。
Harness 管任务执行。
Context Engineering 管模型看到什么。
```

企业级大模型接入，不应该把所有复杂度塞进业务代码里。

更好的方式是分层：

```text
模型统一走 4SAPI。
工具统一走 MCP。
任务统一放进 harness。
上下文按需检索和压缩。
日志按项目、环境、角色归因。
```

这样 Agent 才不是一堆会动的 prompt。

而是一套可以上线、可以排查、可以控费、可以审计的工程系统。
