# AI 产品评估要过能力、成本和价值三道边界

找到一个真实需求以后，下一步不是立刻开发，而是判断它能不能成为一个可交付的产品。很多评估只看第一关：模型现在能不能做。

但即使模型能完成，调用成本可能不成立；即使成本能控制，用户也可能不愿意为结果买单。一个 AI 产品至少要连闯三关：能力、成本和价值。

本文只解决一个问题：如何用这三条边界评估 AI 产品想法。文章不提供固定模型、价格或性能结论，因为这些内容会随版本和服务变化；重点是给出可重跑的判断框架、记录方式和失败条件。

## 一、三条边界分别回答什么

```text
能力边界：系统现在能不能稳定完成任务。
成本边界：每次交付的资源消耗能不能接受。
价值边界：用户是否真正需要这个结果，并愿意持续使用。
```

能力线和成本线会随着模型、工具和工程优化移动。价值线更多锚定在人性和业务结果上，不会因为模型升级就自动消失。

因此，不能因为某个新模型发布，就直接推断一个产品已经成立。模型只是改变了可行范围，仍需重新验证成本和用户价值。

## 二、第一关：能力边界

能力评估不应只问“能不能生成”，而要问“能否在真实条件下稳定完成”。建议拆成五个问题：

```text
输入长度和格式是否在支持范围内。
核心判断是否能达到业务要求。
专业术语、格式和上下文是否稳定。
失败时能否被识别、重试或回退。
输出能否被人或程序快速验收。
```

一个演示成功，不代表长任务、脏数据和异常输入也能成功。测试集至少包含正常样例、边界样例和不完整样例，并记录每次失败的具体原因。

## 三、能力够不到时怎么办

需求和能力之间不只有“做”与“不做”两种选择，可以分三类处理：

```text
马上能做的：直接交付最小版本。
半年内可能做到的：先搭接口、数据结构和验证样例。
长期无法稳定做到的：用工程补，或者明确放弃。
```

“先搭架子”不是把所有未来功能都写出来，而是保留最小可替换接口。例如先把输入、输出和人工确认点固定下来，等模型能力成熟后再替换中间步骤。

工程补足也有成本。若每次模型输出都要人工重排、逐句核对或反复重试，系统可能只是把工作从一个界面搬到另一个界面。

## 四、第二关：成本边界

AI 产品成本不能只看单价。一个简单的估算式是：

```text
单次成本 = 调用次数 × 每次输入输出量 × 单位价格
```

如果是 Agent 任务，还要把工具调用、重试、检索、音频处理、存储和人工复核时间纳入估算。单价下降时，调用次数和输入量可能因为流程变复杂而上升，最终账单未必下降。

成本记录应至少包含：

```text
每次任务的请求次数。
输入和输出量。
使用的模型或服务类型。
失败与重试次数。
人工审核时间。
```

没有这些数据，就无法判断优化是否真的有效。

## 五、一个典型的成本优化思路

假设系统要处理一段长视频，最初方案让模型直接输出复杂 JSON，每次只处理少量字幕。结构字段越多，单次请求越小，调用次数不断增加。

可以重新设计：

```text
让模型输出更适合处理的纯文本或 HTML。
由程序负责解析、对比和回写时间轴。
把整体术语分析与逐段翻译分开。
只在需要高质量判断的步骤使用更强模型。
```

这种取舍不是“格式越简单越好”，而是把确定性工作交给程序，把语言判断交给模型。优化后要重新验证解析错误、术语一致性和人工复核时间，不能只看请求次数。

## 六、成本边界的四个取舍

| 取舍 | 可能收益 | 需要观察的代价 |
| --- | --- | --- |
| 减少调用次数 | 降低请求开销和等待 | 单次失败影响范围变大 |
| 缩短上下文 | 减少输入量 | 可能丢失必要背景 |
| 模型分层 | 让简单任务使用低成本模型 | 路由和验收逻辑更复杂 |
| 程序解析输出 | 减少模型结构化负担 | 解析器需要测试和维护 |

每个优化都要在同一批样例上前后对照。否则“成本下降”可能只是把费用转移到了工程维护或人工审核。

## 七、第三关：价值边界

价值问题回答的是：用户得到的结果，是否值得他改变现有习惯或付出费用。

不同产品的价值来源不同：

```text
有些产品交付确定性结果。
有些产品减少完成任务所需时间。
有些产品帮助用户探索和创作。
有些产品提供专业判断的辅助材料。
```

不要把“模型生成了内容”直接等同于“用户获得了价值”。如果结果需要用户花更长时间清理、复核和修正，产品可能没有减少负担。

## 八、用户买的是结果还是过程

在字幕翻译、格式转换这类任务里，用户往往更在乎结果是否可用；在写作、绘图和视频创作里，用户还会在乎内容是否体现自己的判断和风格。

因此，评估时要问：

```text
用户要的是最终文件，还是创作过程中的控制感。
用户能否快速发现并修正错误。
结果是否保留了人的意图和责任。
当结果不理想时，用户是否仍愿意继续使用。
```

如果产品只是批量制造用户不想要的内容，技术上可行也不等于值得投入。价值判断必须回到真实使用和反馈，而不是只看演示效果。

## 九、三条边界如何一起评估

可以建立一张条件矩阵：

| 组合 | 结论倾向 | 下一步 |
| --- | --- | --- |
| 能力足、成本可控、价值明确 | 进入最小交付 | 固定验收与监控 |
| 能力足、成本过高、价值明确 | 优先优化流程 | 记录成本因子变化 |
| 能力不足、价值明确 | 先做人工辅助或搭架子 | 等待能力变化再复测 |
| 能力足、价值不明确 | 暂停扩展 | 观察真实使用频率 |
| 三项都不成立 | 停止项目 | 保存失败原因 |

这不是打分排名，而是帮助团队说明“为什么现在做”或“为什么暂时不做”。

## 十、验证时不要忽略人工时间

模型调用便宜，不代表产品交付便宜。如果每份结果都需要人完整重做，成本边界就没有通过。

建议记录：

```text
模型处理耗时。
人工检查耗时。
人工修改的比例。
错误导致的返工时间。
用户从输入到拿到结果的总等待时间。
```

把这些数据和调用费用放在同一张表里，才能看到产品真正的交付成本。

## 十一、常见误区

### 误区一：只看模型单价

调用次数、上下文长度和失败重试同样会影响成本。

### 误区二：只看最成功的 Demo

边界输入和人工复核才会暴露真实交付成本。

### 误区三：把“有人点赞”当成价值成立

关注度不等于持续使用。要观察用户是否愿意把它放进真实流程。

### 误区四：为了成本删掉验收

验收不是可有可无的装饰。高风险结果没有验证，省下的调用费可能换来更大的返工和责任成本。

## 十二、结论与限制

AI 产品评估至少要经过三道边界：能力、成本和价值。能力决定系统能不能做，成本决定交付是否可持续，价值决定用户是否愿意持续使用。

能力和成本会随模型与工程变化，应该定期重测；价值则要回到真实用户、真实任务和真实反馈。任何一条边界没有证据，都不应被包装成确定结论。

最小可行的评估记录，不是一个漂亮的 Demo，而是一组样例、一次成本核算、一份人工复核记录和明确的停止条件。
