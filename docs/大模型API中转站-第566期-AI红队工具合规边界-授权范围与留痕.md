# AI 红队工具的合规边界：授权、范围与留痕

“红队工具”这个词有很强的迷惑性：它听起来像专业术语，仿佛只要目的正当，使用方式就自动合法。现实恰好相反——一套能扫描、爆破、横向移动、拿 Shell 的能力，无论被打包成多么正规的名字，**合法与违法之间的差别几乎完全落在那张授权书和它的执行边界上**。

最近出现的一些 AI 客户端插件，把这类攻击能力直接塞进了本地 Agent 的“技能”里，让不具备安全背景的人也能一键调用。能力越容易获得，边界就越需要写清楚。本文不教任何攻击方法，也不评价任何具体工具，只回答一个问题：**当你要使用带攻击能力的工具做红队或安全评测时，怎样做才在授权、范围、数据和留痕上站得住。**

先说明：本文不是法律意见，涉及具体司法辖区和具体行为时，应以当地执业律师的判断和相关法律法规的现行文本为准。

## 一、为什么这类工具天然敏感

一个普通工具和一套攻击工具的区别，不在于名字，而在于能力落在哪一类动作上。可以把常见能力按“对目标的影响”粗分：

| 能力类别 | 典型动作 | 未授权时的性质 |
| --- | --- | --- |
| 信息收集 | 探测、指纹、目录枚举 | 可能构成对他人系统的未授权访问尝试 |
| 凭据攻击 | 口令猜测、票据利用 | 通常直接指向入侵 |
| 横向移动 | 内网渗透、跳板 | 扩大未授权访问范围 |
| 命令执行 | 反向 Shell、WebShell | 取得对系统的控制 |
| 持续化与隧道 | 代理、隧道、驻留 | 长期控制与数据外发通道 |

这里的关键判断是：**这些能力在授权范围内是评测手段，在授权范围外就是对他人信息系统的攻击。** 两者使用的工具、命令、甚至操作步骤可以完全一样，唯一区别是授权与边界。

因此，判断一个工具是否“危险”，不如判断一次使用是否“被授权”。工具本身不是合规对象，使用行为才是。

## 二、合法与否取决于四个要素

把常见的安全评测合规要求收敛一下，核心是四件事。四件都不满足时，基本可以断定越线：

```text
1. 资产归属：目标的 Owner 是否明确，且与你或你的委托方有法律关系。
2. 书面授权：是否有授权方签署的、可核验的授权文件。
3. 范围与时间：目标、方法、时间窗、禁止项是否写清楚。
4. 可追溯：全过程是否留痕，能否证明没有超出授权范围。
```

其中第 4 条经常被忽略。红队的一个现实是：即使你确实获得了授权，如果拿不出授权文件、日志和报告，一旦出现争议，你很难证明自己“做过什么、没做过什么”。

## 三、授权范围要写到什么颗粒度

“我们授权你做安全测试”这类一句话授权，实践中几乎不可用。可执行的授权至少应包含：

| 要素 | 需要写明的内容 |
| --- | --- |
| 目标 | 域名、IP 段、应用、账号范围（白名单式列举） |
| 方法 | 允许和禁止的技术类别，例如是否允许口令攻击、社工 |
| 时间窗 | 起止日期与每日可操作时段 |
| 影响容忍 | 是否允许导致服务降级、重启、数据变更 |
| 数据规则 | 可接触的数据类型、脱敏与销毁要求 |
| 联系人 | 双方值班联系人、升级路径、紧急停止方式 |
| 例外 | 明确排除的资产，例如生产核心库、第三方系统 |

特别注意“排除项”和“第三方资产”：很多授权只覆盖了委托方自有系统，但目标域名可能解析到云厂商、CDN 或第三方 SaaS。**授权方无权授权不属于它的资产。** 碰到边界资产应按“默认不测”处理。

## 四、环境与数据：能离线就离线

减少合规风险最有效的手段，是把测试从真实目标挪到受控环境：

```text
优先：自建或厂商提供的离线靶场、合成目标。
其次：与生产隔离的预发布环境，且已获得该环境 Owner 的书面授权。
避免：直接在生产环境上做破坏性、不可逆或高频探测。
禁止：对未获授权的任何公网或第三方系统发起测试。
```

数据规则同样重要。测试过程中可能触达真实数据，处理原则是“最小化”：

- 只收集证明漏洞所必需的最少信息，不整库拉取；
- 不在个人设备、聊天工具或未授权存储中长期留存；
- 报告中使用脱敏样本，不上传可还原的原始数据；
- 项目结束后按约定销毁临时数据，并保留销毁记录。

把“数据最小化”写进项目计划，而不是事后补救，能避免大部分合规争议。

## 五、留痕与交付：让过程可被复核

留痕的目的不是自证清白，而是让任何第三方在事后都能复核“做了什么、影响范围多大、有没有越界”。一套可用的留痕至少包括：

| 材料 | 用途 |
| --- | --- |
| 授权文件 | 证明合法性来源与范围 |
| 执行日志 | 还原时间线、目标、方法与结果 |
| 证据 | 漏洞的可复现片段（脱敏） |
| 影响评估 | 说明测试是否造成副作用 |
| 报告 | 结论、风险分级、修复建议 |
| 披露记录 | 漏洞通报与修复跟踪 |

对发现的高危漏洞，应采用负责任披露：先在约定渠道通知受影响方，给出修复窗口，再决定是否公开技术细节。公开时应评估是否会帮助未授权者。

## 六、法规框架：先知道自己在哪张网里

在中国大陆语境下，与安全测试最直接相关的法规包括：

- 《中华人民共和国网络安全法》
- 《中华人民共和国数据安全法》
- 《中华人民共和国个人信息保护法》
- 《中华人民共和国刑法》，尤其是其中关于非法侵入计算机信息系统、破坏计算机信息系统等条款（第二百八十五条、第二百八十六条）

来源：国家法律法规数据库 [flk.npc.gov.cn](https://flk.npc.gov.cn/)（访问日期：2026-10-20）

这里要强调两点：

- **授权不能对抗法律。** 即使拿到委托方授权，测试仍须遵守数据与个人信息保护的要求，不能借“安全测试”之名收集、留存和扩散个人信息。
- **工具方的免责声明不转移责任。** 一些攻击性工具的 README 会写明“仅限自有或已授权环境使用”“后果自负”。这类声明约束的是使用者，不会把责任推回工具作者，也不能替代你与资产 Owner 之间的授权。

再强调一次：以上只是一般性说明，不构成法律意见；具体行为的定性需要结合所在司法辖区、行为性质与后果，由专业人士判断。

## 七、红线清单

下面这些情况，无论目的多正当，都应视为红线：

```text
[ ] 对未获授权的公网或第三方系统发起任何扫描或测试。
[ ] 用“授权方名下”的资产推导去测试其云厂商、CDN、SaaS 等第三方。
[ ] 超出授权时间窗或目标白名单继续操作。
[ ] 使用会导致生产不可逆影响的方法，除非逐项获得额外批准。
[ ] 收集、留存或外发超出验证漏洞所需的真实数据。
[ ] 无法提供授权文件、执行日志或影响评估。
[ ] 发现漏洞后私下利用、出售或不按约定披露。
[ ] 把他人系统取得的凭据、Shell 或数据用于授权范围之外。
```

## 八、企业内部的审批与监督

对组织而言，红队能力的使用最好走一条可审计的流程，而不是靠个人自觉：

| 环节 | 要求 |
| --- | --- |
| 立项 | 明确目标系统、范围、方法与数据规则 |
| 审批 | 由资产 Owner 与安全负责人共同签署授权 |
| 执行 | 使用专用身份与网络出口，全程留痕 |
| 监督 | 设置紧急停止方式与联系人，异常即停 |
| 复盘 | 影响评估、修复跟踪与流程改进 |

其中“专用身份与网络出口”值得单独规划：用可识别、可撤销、可关联日志的身份执行测试，比事后靠聊天记录还原过程可靠得多。

## 九、结论与限制

红队工具的价值在于暴露真实风险，它的合法性完全依附于授权与边界。可以有条件地总结三条：

- **工具中性，行为定性。** 同一套能力在授权范围内是评测，超出范围就是攻击。
- **授权要具体到可执行。** 目标白名单、方法、时间窗、数据规则、联系人和终止条件缺一不可。
- **留痕是底线能力。** 没有日志、证据和报告，就无法证明边界被遵守。
