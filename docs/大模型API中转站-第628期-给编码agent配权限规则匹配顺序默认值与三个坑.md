# 给编码 agent 配权限规则：匹配顺序、默认值与三个坑

编码 agent 的权限配置有两种失败方式：一种是太松，它在你没看见的时候跑了危险命令；另一种是以为收紧了，其实规则一行都没生效。第二种更常见，因为写错的规则往往不报错、只是不生效。（具体到旧字段名，文档没有说明是静默忽略还是直接报错，见第八节。）

OpenCode 的权限体系用一条条"动作 + 资源 + 效果"的规则表达，看起来简单，但有四处细节决定它到底按不按你想的走：没匹配时用什么默认值、多条规则谁赢、一次操作涉及多个资源怎么合并、以及默认策略里已经写进去了什么。

本文按这四点展开，最后给三个坑和验证方法。信息来自 opencode.ai 的 [v2 权限文档](https://opencode.ai/v2/docs/permissions/)，检索日期为 2026-11-02。我没有安装或运行过它。

## 一、规则长什么样

一条规则三个字段：

| 字段 | 含义 |
| --- | --- |
| action | 工具的动作，例如 read、edit、shell、subagent |
| resource | 被使用的值：路径、命令、URL、查询、技能 ID、代理 ID |
| effect | allow、deny 或 ask |

文档给的典型配置是"命令一律询问，放行常规 Git 查看，禁止推送"：

```jsonc
{
  "permissions": [
    { "action": "shell", "resource": "*", "effect": "ask" },
    { "action": "shell", "resource": "git status *", "effect": "allow" },
    { "action": "shell", "resource": "git diff *", "effect": "allow" },
    { "action": "shell", "resource": "git push *", "effect": "deny" }
  ]
}
```

三种效果的语义：

| 效果 | 结果 |
| --- | --- |
| allow | 直接执行，不提示 |
| deny | 阻止该操作 |
| ask | 等客户端决定 |

## 二、没有规则匹配时会问

这是第一处关键细节：文档明确写了，**没有任何规则匹配时，OpenCode 用 ask**。

但这句话很容易被读过头，需要和默认策略一起看：每个 agent（包括自定义 agent）其实都从一条基础策略起手，第一条就是 `*`/`*` → allow（细节见第五节）。也就是说 ask 只是"一条规则都没命中时的兜底值"，而在默认配置下，几乎总有一条允许规则先命中；文档还说后加的全局与 agent 规则会覆盖这些默认值。

这也解释了"只写 deny 不写 allow"为什么能工作——原因不是"其余落到 ask"，而是 deny 规则一旦命中就生效，与有没有写 allow 无关。反过来，删掉自定义规则并不等于回到 ask，而是回到那条 `*` → allow 的基础策略。

### 匹配规则本身

| 模式 | 含义 |
| --- | --- |
| `*` | 零个或多个字符，包含斜杠 |
| `?` | 恰好一个字符 |
| 其他 | 字面字符 |

还有几条容易忽略的：

1. 模式匹配的是**整条**规范化路径，不是子串。
2. 反斜杠会被归一化成斜杠；Windows 上大小写不敏感。
3. 以 `" *"` 结尾的 shell 模式也匹配不带参数的命令，例如 `git status *` 同时匹配 `git status` 和 `git status --short`。

第 3 条很实用：不必为同一个命令写两条规则。

## 三、多条规则谁赢：最后匹配者

第二处关键细节：规则按顺序求值，**最后匹配的那条生效**。

文档给的例子正是把具体例外放在宽泛规则之后：先 `shell * → ask`，再 `git status * → allow`，再 `git push * → deny`。如果顺序反了，先 allow 后 ask，结果就是全都 ask。

### 三层追加顺序

配置来源的追加顺序是：

1. 低优先级配置先加载；
2. 全局规则随后追加；
3. agent 规则最后追加。

因为最后匹配者胜，所以**agent 规则实际上盖过全局规则**。这一点在给不同 agent 设不同边界时很重要。

## 四、一次操作涉及多个资源时

第三处关键细节：一个操作可能检查多个资源，例如一个补丁改了多个文件。文档给的合并规则是：

1. 任一 `deny` → 拒绝；
2. 否则任一 `ask` → 询问；
3. 否则允许。

这个顺序是保守的：只要有一个资源被拒，整个操作就不做。对多文件补丁来说，这避免了"部分改动被写进去"的中间状态。

## 五、默认策略里已经写了什么

如果你什么都没配，系统也不是空的。文档列出了每个 agent（包括自定义 agent）都从这段基础策略开始：

| 规则 | 效果 |
| --- | --- |
| `*` / `*` | allow |
| `read` / `*.env` | ask |
| `read` / `*.env.*` | ask |
| `read` / `*.env.example` | allow |

也就是说：默认放行一切，只有读 .env 会问，而 .env.example 例外放行。这个默认值的取向是"能用优先"，不是"安全优先"。

### 内置 agent 各自追加的策略

| agent | 追加策略 |
| --- | --- |
| build | 允许提问 |
| plan | 允许提问；拒绝编辑，除了 `~/.opencode/plan` 下的文件 |
| general | 拒绝提问与启动子代理 |
| explore | 除 shell、read、glob、grep、webfetch、websearch、external_directory 外全拒；读 .env 询问 |
| title / summary | 全部拒绝 |
| compaction | 保持基础策略 |

`plan` 那一行是这套设计里最具体的例子：它的只读性质不是靠提示词，而是靠一条"拒绝编辑"的规则实现的，并把计划文件留在白名单里。

## 六、三个坑

### 坑 1：外部目录默认不提示

文档专门写了一段：位于活动位置与项目工作树之外的路径，会在检查 read 与 edit 规则之前先检查 `external_directory`；而**默认策略允许 `external_directory`**，所以不加规则时，外部路径不会被询问。

换句话说：默认配置下，agent 读或改你项目之外的路径不会弹窗。想让它先问，要显式加：

```jsonc
{
  "permissions": [
    { "action": "external_directory", "resource": "*", "effect": "ask" }
  ]
}
```

这条对"项目目录之外放着凭据或私人材料"的人来说，是本篇最该先做的一件事。

文档还给了一个配套细节：`external_directory`、`read`、`edit` 这三类资源在加载配置时会把 `~/`、`$HOME/` 展开，而 shell 资源保持原始命令文本、不做 home 展开。所以同一个 `~/x` 在两类规则里含义不同。

### 坑 2：shell 的边界比看起来大

文档对 shell 说了两句重话：

1. shell 以**宿主用户的文件系统、进程与网络权限**运行。
2. 从命令文本推断目录是"尽力而为"，所以应当用窄的 shell 白名单，而不是试图写一个能识别所有危险命令的模式。

第 2 条的意思是：别指望用通配符枚举坏命令。反过来做更可靠——默认 ask，只把你确认安全的少数命令前缀设成 allow。

还有一层保护值得知道：shell 权限检查用一个内置扫描器，覆盖 Bash、Zsh、POSIX sh 与 PowerShell；遇到语法畸形或它无法安全分析的动态求值，它会返回扫描错误，而**不是**执行未经验证的子命令。

这是"宁可失败也不猜"的设计，但它也意味着某些合法但复杂的命令会被拒。遇到这种情况，正确的处理是改写命令或明确授权那一段前缀，而不是关掉检查。

### 坑 3：always 会变成项目级规则，子代理不吃父权限

审批时客户端可以回复三种：

| 选择 | 结果 |
| --- | --- |
| once | 只批准这次 |
| always | 批准，并把工具建议的模式保存为项目级 allow |
| reject | 拒绝，并拒绝该会话内其他待处理请求 |

第二行是坑所在：`always` 不只是"这次算了"，它会把规则写下来，成为持久的、项目范围的 allow。文档说这类规则永不覆盖已配置的 deny，这点是好的；但它确实会扩大后续的放行面。

而且**保存什么模式由工具自己决定**：有的工具建议 `*`，shell 建议命令前缀，技能与子代理建议它们的 ID。所以一次随手点的 always，可能比你预期宽。文档自己也提醒：定期检查并删掉不再需要的宽泛批准。

第三行也有个细节：`reject` 会连带拒绝该会话内其他待处理的请求。批量操作时要留意，你以为拒了一个，可能拒了一批。

关于子代理，文档写得很直接：**自定义子代理用它自己的权限，而不是父权限的子集**。所以给主 agent 收紧了，不代表它调起来的子代理也收紧。要给子代理边界，得在 `agents.<id>.permissions` 下单独写。

## 七、policies：企业侧的硬拒绝

除了规则，还有一层 `policies`：它在规则与已保存审批之后执行，把 allow 或 ask 转成 deny，且从不授予访问。文档说全局与 Console 管理的 policies 覆盖项目配置，用途正是"组织禁止某条命令，即使仓库允许"。

配置的优先级那篇讲过：托管设置最高，但仅仅设配置挡不住用户加插件，要靠 policies。两处呼应，指向同一个思路——规则管"能不能做"，策略管"组织允不允许"。

## 八、怎么验证规则真的生效

| 检查 | 做法 | 预期 |
| --- | --- | --- |
| 顺序对不对 | 把宽泛规则放前、例外放后 | 例外生效；反过来则全部落到宽泛规则 |
| 默认值 | 删掉所有自定义规则 | 回到基础策略：除读 `.env` 会问外，其余放行（不是变问） |
| 多资源合并 | 让 agent 改一个允许目录和一个拒绝目录的文件 | 整个操作被拒 |
| 外部目录 | 让 agent 读项目外的文件 | 加规则后应询问；不加规则默认不问 |
| 子代理 | 主 agent 收紧后，让它调一个自定义子代理 | 子代理按自己的规则走，可能更宽 |
| 字段名 | 检查是否用了 V2 名字 | 文档只写了"应改用"新名字；旧字段是静默忽略还是报错，文档未表态，只能自己试 |

最后一行值得单列：文档说明 V2 用 `permissions`、`shell`、`subagent`，而 V1 是 `permission`、`bash`、`task`。文档没有说旧字段会被静默忽略还是会报错——它只写了"应改用新名字"；提供方那一页另有明确说法：某些退役的提供方 ID 在 V2 里会被直接拒绝。所以旧写法两种结果都可能出现，而"配了但没生效"也确实常常出在字段名上。

## 九、限制与结论

这套规则的价值在于三点：没匹配时兜底为询问、多资源取最严、agent 规则能覆盖全局。但要注意兜底值只在"一条规则都没命中"时才出现——默认基础策略是从 `*`→allow 起手，所以真正的默认行为是放行，要安全就得自己把宽口径改成 ask。要收紧的话，优先级是：先给 `external_directory` 加 ask，再把 shell 从全 ask 改成少量前缀 allow，最后才考虑动默认基础策略。

本文的限制：没有运行过，所有行为来自 v2 文档；没有核对文档与 v2.2.5 实现是否一致；扫描器具体能分析到什么程度，文档没给边界清单；policies 在 Console 侧的下发方式未核验。

下一步建议：先只做一件事——给 `external_directory` 加一条 `ask`，然后用一次"读项目外文件"的操作确认真的会问。这一步能同时验证字段名、优先级和生效性。
