# 用 PTC 模式编排多步骤工具调用

批量处理文件、检查多个配置或生成统一报告时，Agent 往往会重复“调用工具、读取结果、再调用工具”的循环。任务一多，模型与工具之间的往返会变长，执行轨迹也难以一眼看清。

PTC 模式提供了另一种组织方式：让模型写一段 TypeScript 程序，用 SDK 将多个工具调用编排在一起，再执行整段程序。它适合步骤稳定、输入范围明确的自动化工作；如果任务仍在探索阶段，逐步调用工具往往更好控制。

这里聚焦一个具体问题：什么样的任务值得用 PTC，以及如何在不扩大副作用的前提下验证它是否适合当前流程。配置说明依据 DeepSeek Harness `dsh@0.1.1-rc.2` 官方仓库，核对日期为 2026 年 8 月 22 日。

## PTC 和逐步调用的差别

传统工具调用更像交互式排查：模型先读一个文件，根据结果再搜索、编辑或运行命令。每一步都可以调整方向，适合信息不完整的问题。

PTC 更接近写一个小型自动化脚本：模型先定义输入、循环、分支和输出，再把多次操作放进一个 `run_code` 执行单元中。

官方 PTC 预设的配置说明了两个关键事实：它保留标准模式的能力，并在工具呈现层将模式设为 `code`。因此，PTC 的重点不是减少可用工具，而是改变模型调用工具的形式。[官方配置](https://github.com/deepseek-ai/DeepSeek-Harness/blob/b150a551b8d465e31e418e1b2eaf5e79bbb7d28e/apps/cli/config/agent-presets/code/agent.cordis.yml)

可以用下面的抽象流程理解区别：

```text
逐步调用：读取一个文件 -> 判断 -> 读取下一个文件 -> 判断 -> 汇总
PTC：    定义文件集合 -> 循环读取 -> 按规则提取 -> 一次输出汇总
```

这不意味着后者一定更快。程序本身也可能写错，或者因为结果异常而需要重新执行。它的收益来自减少结构明确任务中的无效往返，而不是绕过判断和验证。

## 哪些任务适合 PTC

先检查任务是否同时满足以下条件：

| 判断条件 | 说明 |
| --- | --- |
| 步骤可预先描述 | 在执行前就能写出读取、筛选、转换和输出的顺序 |
| 输入范围明确 | 能限定目录、文件列表、记录数或查询条件 |
| 规则可程序化 | 同一判断能在多份输入上重复执行 |
| 输出可验证 | 可以用数量、文件清单、测试或 Diff 验证结果 |
| 副作用可控制 | 先在只读或小样本环境执行，必要时再写入 |

典型例子包括：扫描一个目录中的配置并列出缺失字段、对一组日志按固定关键词分类、读取多个源文件生成依赖清单。它们的共同点是循环和规则稳定，而不是“任务看起来很长”。

以下情况则先保留标准模式：需求还在不断变化；每一步都依赖语义探索；操作涉及生产资源、付费接口或大范围写入；团队无法审阅 TypeScript 和执行轨迹；没有明确的验收方式。

## 用小样本验证 PTC

不要从整个仓库或全部文件开始。先选 3 到 10 个可公开、可恢复的样本，明确输入和输出边界。例如，检查目录中 YAML 文件是否包含三个必填字段，可以这样描述任务：

```text
只读取 docs/examples 目录下的 YAML 文件。
检查每个文件是否包含 name、description、version 三个字段。
输出 JSON 汇总：文件路径、缺失字段和已检查总数。
不要修改任何文件；遇到无法解析的文件，把错误写入结果，不要跳过。
```

这段任务描述限制了目录、规则、输出和副作用。模型生成 PTC 程序后，先看四件事：

1. 输入是否仍限于 `docs/examples`，没有扩大到工作区其他目录；
2. 调用是否只读，没有出现编辑或外部写入；
3. 输出中是否包含样本总数与失败项；
4. 抽查一到两个文件，确认汇总结果与实际内容一致。

如果需要后续写入，再把写入拆成第二个任务。先生成候选变更、审阅 Diff、运行验证命令，确认无误后才允许应用修改。不要因为 PTC 可以在一次程序中串联操作，就把读取、批量修改和外部发布放在同一次执行里。

## 一个可审查的任务结构

对任何 PTC 任务，建议在提示词中明确以下结构：

```text
输入：只处理哪些路径、记录或接口返回。
规则：每项执行哪些确定性检查或转换。
输出：以什么格式返回，包含哪些计数和失败信息。
副作用：默认只读；若写入，允许修改哪些文件。
停止条件：解析失败、范围不符或发现敏感内容时如何处理。
验证：执行后使用哪个命令、样本或 Diff 复核。
```

这套结构的价值是让 PTC 程序和普通自动化脚本一样可审查。模型输出的代码不是“内部思考”，而是实际会驱动工具调用的执行逻辑。

## 将一次批处理拆成四个阶段

PTC 最容易出问题的地方，不是模型不会写循环，而是把“发现范围”“读取数据”“修改资源”和“验证结果”压进了同一段不可分辨的执行过程。即使任务最终成功，也难以确认每一项修改为什么发生。一个更稳妥的做法是按阶段拆开。

| 阶段 | 目标 | 默认副作用 | 推荐输出 |
| --- | --- | --- | --- |
| 发现 | 列出候选输入并确认范围 | 无 | 文件列表、记录数、排除项 |
| 读取与转换 | 解析输入，应用确定性规则 | 无 | 结构化中间结果、解析错误 |
| 变更 | 生成或应用经过审阅的修改 | 受限写入 | Diff、目标路径、成功与失败清单 |
| 验证 | 检查写入后结果是否满足条件 | 无或可恢复 | 测试结果、再次扫描、残留项 |

第一轮 PTC 任务最好只做前两步。它可以读取文件、解析结构、检查规则并输出候选结果，但不能修改任何内容。人工或另一个只读检查确认范围无误后，第二轮任务才允许将候选结果转为变更。这样即使模型误解了一个字段，也只会产生可审阅的清单，而不是批量写错文件。

例如，批量补充缺失字段时，不要一开始就说“把所有 YAML 都修好”。更好的第一轮任务是：

```text
只读扫描 config/templates 目录中的 YAML 文件。
列出缺少 owner 字段的文件，并输出每个文件当前的 name、version 和缺失字段。
不修改文件；无法解析时记录文件名和错误。
最后给出已扫描、候选修改、解析失败三个数量。
```

在拿到候选清单后，检查目录、文件数和两三个具体样本。第二轮再限定“只修改上一轮列出的文件，并在每个变更后重新解析 YAML”。这种两段式写法增加了可审查性，不依赖于模型是否恰好在第一次就完全理解任务。

## 让输出天然具备核对条件

PTC 的输出不要只有一句“处理完成”。对于批处理，至少应能回答四个问题：处理了多少项、成功多少项、失败多少项、每个失败为什么失败。下面是适合要求 Agent 返回的结果形状：

```json
{
  "scope": "config/templates",
  "scanned": 12,
  "matched": 4,
  "changed": 0,
  "errors": [
    {
      "path": "config/templates/broken.yml",
      "reason": "YAML parse error"
    }
  ],
  "items": [
    {
      "path": "config/templates/example.yml",
      "missing": ["owner"]
    }
  ]
}
```

这里的数字只表示字段含义，不是实际运行结果。真正执行时，`scanned` 应能与发现阶段的文件列表对应，`matched` 应能通过抽查复核，`changed` 在只读试运行时必须为 `0`。如果这些计数对不上，应先停在数据收集阶段排查，而不是继续写入。

需要调用外部接口时，输出中还应包含请求数量、成功状态、可重试错误和不可重试错误。不要把 API Key、完整请求头或敏感响应原文放进汇总；记录脱敏的资源标识、状态码和错误类型通常足以支持排查。

## 控制可重复执行和外部副作用

批处理常常因为网络错误、进程中断或部分失败需要重跑。若同一程序重跑一次就会再重命名文件、重复创建资源或再次发送消息，问题会从“失败”变成“重复副作用”。因此在设计任务时，要明确写出重跑规则。

对文件任务，可以要求先检查目标内容是否已经存在；对生成文件的任务，可以写到独立输出目录并用清单记录已生成项目；对外部请求，可以使用测试资源、dry-run 参数或事先约定的幂等键。Agent 未必能凭空知道你的业务幂等规则，必须在提示词中给出可检查条件。

不具备可恢复条件的操作，例如删除大批量文件、修改生产配置、发送面向用户的消息、触发付费任务，不应作为 PTC 的首次全量执行。即使流程很明确，也应先用模拟数据或受控子集验证，再单独由具备权限的人确认执行范围。

## Code Mode 改变的是调用形态，不是权限边界

PTC 的官方配置在标准预设之上增加 `tool-presentation`，将模式设为 `code`：模型面对的是由工具生成的 SDK，并通过 `run_code` 执行 TypeScript 程序。配置同时强调，沙箱、审批栈、持久化与模型路由仍属于宿主层；PTC 并没有因为把多步操作写成代码，就取得额外的主机权限。[PTC 官方配置](https://github.com/deepseek-ai/DeepSeek-Harness/blob/b150a551b8d465e31e418e1b2eaf5e79bbb7d28e/apps/cli/config/agent-presets/code/agent.cordis.yml)

这点在审查时很重要。把 PTC 看成“模型替你写了一个自动化脚本”是恰当的；把它看成“自动化脚本因此可以绕过原来的目录、网络或审批限制”则是错误的。程序中的每一次工具操作仍受当前部署的工具能力和策略约束。任务说明里写清可读目录、可写目录、允许的外部端点和停止条件，依然是必要的。

同样，不要用代码体积判断任务是否适合 PTC。一段很短的程序可能包含循环删除、批量更新或多次外部请求；一段较长的只读解析程序反而风险很低。审阅时优先检查“它会对哪些对象做什么”“失败时是否继续”“是否能安全重跑”，而不是只看 TypeScript 有多少行。

## 给 PTC 提示词增加执行前后的两个关卡

为了让代码生成过程更可控，可以在提示词中要求两个显式关卡。第一个关卡是执行前的范围确认：先列出输入集合、预计调用的工具类型和最大处理数量，等待它们与任务约束一致后才执行。第二个关卡是执行后的核验：汇总成功、失败、跳过和未处理项，并用独立的只读操作抽查结果。

一个适合低风险任务的提示词骨架如下：

```text
阶段 A：只发现，不写入。
先输出将处理的文件列表、总数、排除规则和可能的解析异常。
若目录超出指定范围、数量超过 20 或发现敏感文件，停止并报告。

阶段 B：仅在阶段 A 的范围经确认后执行。
每次变更前检查目标是否已满足条件；只修改候选列表中的路径。
完成后输出每个路径的结果和总计，并重新读取所有已修改文件进行验证。
出现单项失败时继续处理其余安全项目，但在汇总中保留失败；不要自动扩大范围。
```

这不是要求模型一定要向人类等待确认。是否需要人工确认取决于任务权限；即使在自动执行场景，阶段 A 也应成为程序内部可检查的 guardrail。它会将“要处理什么”变成一份可保存的中间产物，发生问题时可以快速判断错误来自范围发现还是变更规则。

## 处理失败和部分成功

批处理很少只有“完全成功”或“完全失败”。例如 20 个配置文件中 18 个能解析、2 个语法错误；或 10 个外部请求中 1 个限流、其余成功。如果程序遇到第一项异常就终止，可能损失已收集的诊断信息；如果它吞掉异常继续执行，又会给出不可靠的完成结论。

更合适的规则是把失败类别写进任务：输入不可解析、权限不足、网络可重试、网络不可重试、结果校验不通过。对于只读任务，可以继续收集每项错误并在最后汇总；对于写入任务，必须确保失败不会把单个对象留在半更新状态。无法保证原子性的操作，应先生成变更计划，或为每项记录可恢复的前状态。

报告中至少分开四种计数：`scanned`、`eligible`、`changed`、`failed`。只有 `failed` 为零且 `changed` 与确认范围相符，才适合写“全部完成”。当 `failed` 非零时，PTC 的价值仍然存在，因为结构化失败清单比一段笼统的自然语言总结更容易交给下一次人工或自动化处理。

## 把程序与运行证据一起保存

PTC 带来的额外可审查性来自代码与输出能形成对应关系。对重要任务，应保存生成的 TypeScript、执行时的输入范围、工具调用日志、结构化汇总与验证结果，并从中移除凭据和业务敏感内容。仅保存最终聊天回答，日后无法重放“为什么扫描了这些文件”“哪个分支决定了写入”。

第一次运行某类任务后，还应复盘程序里有哪些规则其实是项目约定而不是通用规则。比如路径排除、字段默认值、幂等键格式、失败重试次数等。将它们移入项目规则、配置文件或可审查的脚本参数，能让下一次 PTC 调用不必依赖模型记住上次的隐含经验。

## 何时应该停止使用 PTC

PTC 不是“步骤多”的默认答案。出现下列信号时，停下来切回标准模式或拆分任务：

1. 中间结果改变了原先的任务定义，后续规则不再是预先确定的。
2. 大量输入无法解析，无法判断是数据异常还是程序假设错误。
3. 需要根据代码语义、产品取舍或用户意图逐项作不同决定。
4. 输出缺乏可验证的总数、路径或错误列表，只剩自然语言总结。
5. 执行涉及不可逆资源，而团队无法审阅生成的程序或变更范围。

此时继续把更多判断塞进 TypeScript，通常只会让一段程序越来越长、越来越难审。标准模式的逐步工具调用虽然往返更多，却允许在每一步检查新证据、调整方向和中止任务。选择方式应由任务的不确定性决定，而不是由“是否希望少几轮调用”决定。

## 常见失败与排查

| 现象 | 常见原因 | 处理方式 |
| --- | --- | --- |
| 程序处理了不该处理的文件 | 输入路径或 glob 过宽 | 固定目录和样本清单，先输出待处理列表再执行 |
| 结果缺项 | 解析失败被忽略，或循环提前退出 | 要求统计成功、失败与跳过数量，并保留错误原因 |
| 单次执行失败后难定位 | 程序把太多步骤揉在一起 | 拆成“收集”和“写入”两段，保留中间结构化结果 |
| 结果正确但耗时没有改善 | 步骤本身并不适合并排或批量 | 回到标准模式，比较质量和可维护性而非只看调用轮数 |
| 生成了不可审阅的大段代码 | 任务边界过大 | 缩小样本和规则，不以一次完成全量操作为目标 |

PTC 的运行结果应当像脚本日志一样阅读：先看处理范围，再看成功与失败统计，最后抽查输出。只有在小样本稳定后，才逐步放大输入范围。

## 如何比较 PTC 与标准模式

如果要判断 PTC 是否值得保留，至少固定以下变量：同一模型和版本、同一仓库提交、同一任务描述、同一输入样本、相同的权限范围和相同的重试规则。

记录的结果不应只有总耗时，还应包括：任务是否通过验收、错误数量、修改 Diff、人工修正时间、工具调用轮数，以及输入输出 Token。对有随机性的模型任务，应运行多次并报告样本数和异常情况。

单次更快，只能说明该次条件下的观察；如果结果质量、修改范围或人工修正成本变差，就不能把它视为改进。

## 结论

PTC 适合把“已经想清楚的重复步骤”变成一次可执行的工具编排。它并不取代逐步探索，也不会自动降低风险。

从小样本、只读任务开始，明确输入、规则、输出、停止条件和验证方式，才能判断 PTC 是否真的适合你的自动化流程。对于需要持续发现问题、不断调整策略的任务，标准模式仍是更容易审查的选择。
