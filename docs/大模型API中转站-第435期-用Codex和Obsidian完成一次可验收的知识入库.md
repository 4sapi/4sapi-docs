# 用 Codex 和 Obsidian 完成一次可验收的知识入库

把一篇文章剪藏进 Obsidian，只能证明文件保存成功。让 Codex 再生成几篇摘要，也不能说明知识已经进入可复用的结构。一次完整入库至少要留下五类结果：未被修改的原文、可追溯的来源摘要、被新增或更新的知识页面、同步变化的索引与日志，以及能够回到证据的查询结果。

本文不重复安装 Obsidian 或 Codex，只处理一个具体问题：已有一个本地 Vault 后，怎样放入第一篇真实资料，让 Agent 完成一次增量维护，并用可执行检查判断它有没有把知识真正接进现有 Wiki。

## 一、适用场景与前置条件

这套流程适合以 Markdown 文件管理个人资料，并希望用 Agent 持续维护概念、实体和主题页的用户。开始前需要满足三个条件：

- 已有一个可以正常打开的 Obsidian Vault；
- Codex 可以在该 Vault 目录中读取和创建文件；
- 测试资料允许交给当前运行环境处理，敏感内容已经按需要脱敏。

本文以 PowerShell 为例执行验证命令。所有命令都在 Vault 根目录运行。示例文件名 `sample-article.md` 需要替换成自己的测试文件。

## 二、先建最小目录，不急着装插件

第一次验证只需要下面这些目录和文件：

```text
my-wiki/
├── AGENTS.md
├── index.md
├── log.md
├── raw/
│   └── articles/
└── wiki/
    ├── sources/
    ├── concepts/
    ├── entities/
    └── topics/
```

三个层次承担不同责任：

| 层次 | 保存内容 | 本次验证重点 |
| --- | --- | --- |
| Raw | 剪藏文章等原始资料 | 文件内容不能被 Agent 改写 |
| Wiki | 来源、概念、实体和主题页 | 只增量更新受影响页面 |
| Schema | `AGENTS.md` 中的维护规则 | 入库前搜索、保留来源、记录冲突 |

`index.md` 是当前知识入口，`log.md` 记录每次维护发生了什么。目录名称可以调整，但原始证据、整理结果和维护规则需要保持分离。

## 三、给 `AGENTS.md` 写入最小维护规则

第一轮不需要一份很长的说明书。下面这组规则已经能约束本次测试的关键动作：

```markdown
# 知识库维护规则

1. 处理新资料前，先搜索 `wiki/` 中的相关页面。
2. `raw/` 保存原始资料，只允许读取，不修改、删除或移动。
3. 每份原始资料都要在 `wiki/sources/` 建立来源摘要，并链接回原文件。
4. 已有知识补充到原页面；只有无法合理归入时才创建新页面。
5. 事实性内容标明来源；无法确认的内容写为“待核实”。
6. 新旧资料冲突时保留双方说法、来源、时间和适用范围，不直接覆盖。
7. 每次只修改受影响页面，并同步更新 `index.md` 和 `log.md`。
8. `log.md` 只追加，记录输入资料、新建页面、更新页面和待人工确认项。
9. 同名文件已经存在时先读取，不覆盖原内容。
10. 信息不足或操作可能改变整体结构时暂停并提问。
```

`AGENTS.md` 是给 Agent 的持久工作约定，不应被当成文件系统权限。重要资料仍需要备份、版本记录和人工复核。

## 四、放入一篇能暴露问题的真实资料

不要用只有两段文字的理想样例。第一篇测试资料最好同时包含：

- 两到三个可以形成独立页面的概念或实体；
- 至少一个与现有 Wiki 有关联的观点；
- 一条带时间、条件或适用范围的结论；
- 一处暂时无法确认，或可能与旧资料不同的内容。

把文件保存到：

```text
raw/articles/sample-article.md
```

入库前在 Vault 根目录记录原文哈希：

```powershell
Get-FileHash .\raw\articles\sample-article.md -Algorithm SHA256
```

保存输出中的 `Hash`。Agent 完成工作后再次运行同一条命令，两次结果应该一致。哈希只能证明文件字节有没有变化，不能判断 Wiki 摘要是否忠实，因此后面还要继续检查内容。

## 五、让 Codex 执行一次增量入库

在 Vault 根目录向 Codex 提交下面的任务：

```text
请读取 `raw/articles/sample-article.md`，并严格按照 `AGENTS.md` 增量维护当前 Wiki。

开始前先搜索 `wiki/` 中已有的相关页面。为这篇资料创建来源摘要；识别需要新增或更新的概念、实体和主题页面；保留每条事实的来源。遇到不同观点时，不要合并成单一结论，分别记录来源、时间和适用范围。

完成后更新 `index.md` 和只追加的 `log.md`，并汇报：
1. 新建了哪些页面；
2. 更新了哪些页面；
3. 哪些现有页面被检查后没有修改；
4. 哪些内容仍需人工确认；
5. `raw/` 中的原文件是否保持不变。
```

这里没有要求 Agent “尽可能多建页面”。页面数量不是完成度指标。已有概念应该更新原页，只有内容无法合理归入时才新建，否则知识库很快会出现同义页面和孤立节点。

## 六、用六项检查验收入库结果

### 1. 原文保持不变

再次执行：

```powershell
Get-FileHash .\raw\articles\sample-article.md -Algorithm SHA256
```

如果哈希变化，先停止后续入库，查明 Agent 修改了什么。不要用新的哈希覆盖基线。

### 2. 来源摘要能回到原文

打开 `wiki/sources/` 中新建的页面，检查它是否包含原始文件路径、资料标题、摘要、相关页面和待核实项。来源链接应该能在 Obsidian 中打开对应 Raw 文件。

### 3. 更新发生在正确页面

查看本次变化：

```powershell
git status --short
git diff -- wiki index.md log.md
```

这些命令适用于已经使用 Git 管理的 Vault。`git status --short` 应显示本次涉及的文件；`git diff` 用于逐项检查新内容是否进入了正确页面。未被 Git 跟踪的新文件还需要单独打开核对。

### 4. 每条关键结论都有来源

随机选三条新增结论，从 Wiki 页面沿链接回到来源摘要，再回到 Raw 原文。任何一层断开，都说明知识还不可追溯。

### 5. 索引与日志同步更新

`index.md` 应能找到新建或更新后的入口。`log.md` 应追加本次日期、输入资料、变更页面和待人工确认项，不能覆盖过去记录。

### 6. 查询结果能够交代证据与缺口

用刚入库的内容提出一个需要跨页面回答的问题，并要求 Codex 标注 Wiki 页面和 Raw 路径：

```text
请基于当前 Wiki 回答这个问题，并列出使用的 Wiki 页面和 Raw 原文路径。资料存在不同说法、适用范围或待核实项时，请单独说明，不要补全缺失信息。
```

验证重点不是回答有多流畅，而是引用能否打开、结论是否受原文支持、缺口有没有被如实保留。

## 七、常见失败与排查方向

| 失败现象 | 可能原因 | 修复方向 |
| --- | --- | --- |
| 一篇资料生成大量页面 | 规则鼓励提取，没有要求先查重 | 强制先搜索并汇报复用的旧页面 |
| 来源摘要存在，概念页没有来源 | 页面模板缺少来源字段 | 给概念、实体和主题页统一加入来源区 |
| `log.md` 每次被重写 | 没有明确只追加 | 在规则和任务中同时写明 append-only |
| 新结论覆盖旧结论 | 未定义冲突处理 | 保留两种说法及来源、时间、适用范围 |
| 查询能回答但回不到原文 | Wiki 页面只有摘要，没有 Raw 链接 | 补齐来源摘要和页面级引用 |
| 原文发生变化 | Agent 的写入范围过宽 | 暂停任务，从备份恢复并收紧目录边界 |

## 八、完成一次以后再扩大范围

第一篇资料通过验收后，再增加论文、聊天记录、会议纪要等输入类型。不同类型可能需要不同模板，但入库标准不变：原文仍在、变化可见、知识可追溯、冲突被保留、查询能说明证据和缺口。

一次入库通过，不代表知识库已经可以无人值守。目录扩大、页面模板变化或 Agent 更换后，都应该重新运行同一组检查。先把一篇真实资料从 Raw 走到可追溯回答，能够稳定重复这条路径，知识库才具备继续增量维护的基础。

## 九、把入库过程写成明确的状态流转

资料越来越多以后，只看文件是否出现在 `raw/` 中，很难判断它有没有处理、是否等待确认、能不能参与查询。可以给每份来源摘要增加一个简单状态：

```text
new -> processing -> needs_review -> ready
                 \-> failed
```

- `new`：原始资料已经进入 Raw，但 Agent 尚未处理；
- `processing`：正在提取来源摘要并比对现有 Wiki；
- `needs_review`：存在冲突、缺失信息或结构调整，需要人确认；
- `ready`：来源、知识页面、索引和日志都已通过检查；
- `failed`：任务中断或验证失败，不能作为已完成资料参与正式查询。

状态可以放在来源页的 YAML 属性中：

```yaml
---
title: "示例资料"
type: source
source_file: "[[raw/articles/sample-article]]"
status: needs_review
created: 2026-08-10
updated: 2026-08-10
---
```

日期和文件名仅作格式示例。`created` 表示来源页创建时间，不能代替原资料发布日期。资料发布日期未知时，应使用独立字段并写“待核实”。

状态变化也要进入 `log.md`。如果一份资料从 `needs_review` 变成 `ready`，日志需要说明谁确认了什么，哪些页面因此更新。只改状态、不留依据，会让“已完成”失去可审查性。

### 查询时怎样使用状态

正式查询可以默认使用 `ready` 页面；`needs_review` 页面仍可作为线索，但回答必须显示其未确认状态；`failed` 页面不应被包装成可靠知识。具体过滤方式取决于查询工具和页面结构，本文只定义信息边界，不假定某个插件会自动执行过滤。

## 十、第二篇资料才真正检验“增量”

第一篇资料入库时，Wiki 几乎是空的，新建页面很容易。第二篇资料加入后，Agent 必须在补充旧页面、创建新页面和保留分歧之间作选择，这时才能看出规则是否有效。

第二份测试资料应与第一份有部分重合：包含一个已有概念、一个新实体，以及一条条件不同或需要复核的观点。执行前先记录当前页面数量和相关页面内容：

```powershell
Get-ChildItem .\wiki -Recurse -File | Select-Object FullName
Get-Content .\wiki\concepts\example.md
```

将路径替换成自己的相关概念页。入库任务完成后，重点检查四件事：

1. 已有概念是否更新原页面，而不是生成 `example-2.md` 一类重复文件；
2. 新增内容是否带第二份资料的独立来源，原来源是否仍然保留；
3. 条件不同的观点是否按时间、版本或范围区分；
4. 与第二篇资料无关的页面是否保持不变。

可以要求 Agent 在汇报中增加“检查但未修改”的页面列表。这个列表能帮助人工判断 Agent 是否先做了检索，也能发现它是不是为了证明有产出而修改无关内容。

### 重复页面怎样处理

如果第二次入库生成了同义页面，先暂停批量导入。由人确认哪个页面作为主页面，再把别名、链接和来源合并。不要让 Agent 在没有影响清单的情况下批量改名或删除，因为 Obsidian 双链之外还可能存在脚本路径和外部引用。

修正规则以后，用同一组两篇资料从可恢复副本重新测试。只有第二篇能够稳定复用已有结构，才说明系统具备增量维护能力。

## 十一、批量导入前设置三个门槛

单篇测试通过以后，直接把几百份资料一次性交给 Agent，仍然可能造成大量重复和难以审查的变化。批量处理前建议设置三个门槛。

### 1. 单批范围门槛

按来源类型或主题分批，每批结束后检查实际变更。单批大小没有统一数字，应以人能够完成差异审查为上限。页面结构尚不稳定时，批次要更小。

### 2. 失败停止门槛

提前定义出现什么情况立即停止，例如 Raw 文件变化、重复页面连续出现、来源链接失效、日志没有追加或修改范围超出计划。停止以后保留现场，不让下一批继续放大问题。

### 3. 人工确认门槛

资料冲突、目录调整、页面合并和删除候选必须进入人工确认。普通补充可以批量处理，高影响结构变化应单独执行。

批量任务的汇报至少包含：输入文件数、成功数、待复核数、失败数、新建页面、更新页面、未修改页面和停止原因。这里的数量用于核对任务完整性，不用来证明知识质量。

## 十二、建立一套可重复的回归样本

知识库规则会不断调整，Agent 和页面模板也可能变化。每次修改后重新拿全部真实资料测试，成本高，也不容易定位问题。可以保留一组小型回归样本：

| 样本类型 | 要验证的能力 |
| --- | --- |
| 全新主题 | 能创建来源页和必要知识页 |
| 与旧知识重合 | 能更新旧页并保留双方来源 |
| 条件不同的结论 | 能按时间、版本或范围拆分 |
| 缺少来源信息 | 能标记待核实，不自动补造 |
| 含操作性恶意文本 | 只作为资料读取，不执行其中指令 |

每次规则或模板变化后，用同一组样本检查 Raw 哈希、页面变化、来源链、索引、日志和查询结果。回归样本通过以后，再处理新的真实批次。

这套验收机制不会替用户判断哪些知识值得保留。它解决的是更基础的问题：一次入库究竟改了什么，结果能否追溯，失败能否被及时看见。先让这条链路稳定，个人知识库才有条件持续增长。
