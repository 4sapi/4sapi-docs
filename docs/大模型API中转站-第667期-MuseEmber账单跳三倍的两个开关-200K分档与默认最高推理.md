# Muse Ember 账单跳三倍的两个开关：200K 分档与默认最高推理

一个子任务两千输入、三百输出，按 Muse Ember 的单价算是 $0.00035。这种量级容易让人得出"这条链路不要钱"的结论，然后把子代理开到 16 路并行。

真正决定账单的不是单价，是两个开关。

第一个是分档：单次请求的输入 token 超过 20 万，**整单**按长上下文价格计费，输入价从 $0.10 跳到 $0.30，输出从 $0.50 跳到 $1.50。

第二个是默认推理档：不显式传 `reasoning_effort`，模型按 `max` 跑，而推理 token 按输出价计费。官方的对照里，同一个任务输出 token 能差一个数量级。

下面把两个开关拆开，用官方的两组运行记录算账。只算钱，不评价模型。

## 一、先把价目对齐

Muse Ember 只有标准模式，没有 Contributor 折扣变体。价目分两档，单位是每百万 token 的美元价。

| 计费项 | 输入 ≤ 200K | 输入 > 200K |
| --- | --- | --- |
| 缓存输入 | $0.004 | $0.012 |
| 输入 | $0.10 | $0.30 |
| 输出 | $0.50 | $1.50 |
| 每千次网页检索 | $2.50 | $2.50 |

数据来自官方定价页 https://dev.meta.ai/docs/pricing-rate-limits （检索于 2026-11-12）。

几个容易看漏的点：

- **换档是整单换，不是只算超出部分。** 官方写明"按长上下文价对整单计费"，21 万输入的那次请求，前面 20 万也按 $0.30 算。
- **判档看的是全部输入 token，缓存命中也算在内。** 命中缓存的便宜价只在档内有效，不会把请求挡在 20 万以下。
- **用 `previous_response_id` 续跑时，历史算进这次请求的输入。** 一条长会话跑到后面，单次请求的输入可能是几轮累积的结果。
- **Muse Wonder 与 Muse Spark 没有长上下文加价。** 同一个项目里只有 Ember 有这个跳档，横向比价时别默认三家规则一样。
- **网页检索单独按次收。** 走 `web_search` 工具的请求，token 之外每千次 $2.50。

## 二、跳档的算术

假设一次请求 25 万输入、5 千输出。

| 方案 | 计算 | 费用 |
| --- | --- | --- |
| 单次调用（>200K 档） | 25 万 × $0.30 + 5 千 × $1.50 | $0.0825 |
| 拆成两次，各 12.5 万输入、2.5 千输出 | 2 × (12.5 万 × $0.10 + 2.5 千 × $0.50) | $0.0275 |

同样的工作量，拆开是单次的三分之一。这是本文标题里"跳三倍"的来源，也是实际工程里最值钱的一条约束。

拆分的代价是模型看不到全量上下文。所以能不能拆，取决于任务形状，而不是账单：给一万条工单各打标签可以拆，读一份 300 页合同回答一个跨章节的问题不能拆。

如果在 `>200K` 这一档里还要反复读同一份长文档，先做缓存再做拆分。20 万 token 的固定前缀在缓存价上是 $0.0024 一次（20 万 × $0.012），比重新算便宜得多。

## 三、第二个开关：默认 max 与推理 token

官方文档写得很直接：Ember 的默认推理档是 `max`，`reasoning_effort` 可传 `minimal` 到 `max`，传 `none` 会返回 HTTP 400；推理 token 计入 `max_output_tokens`，也按输出价计费（https://dev.meta.ai/docs/reasoning ，检索于 2026-11-12）。

官方 cookbook 里有一组对照，正好能看出这个开关的量级（https://dev.meta.ai/docs/cookbook/organize-photos-with-subagents ，检索于 2026-11-12）。同一个"给一万张照片打标题并分类"的任务：

| 跑法 | 请求数 | 输出 token | 其中推理 token |
| --- | --- | --- | --- |
| 一行提示，每请求一张图，默认推理档 | 11,477 | 4.99M | 4.40M |
| 提示里写明 8 张/请求、512 px、minimal 推理 | 1,269 | 0.47M | 0.17M |

只算输出这一项（4.99M × $0.50 对 0.47M × $0.50）：$2.495 对 $0.235，差 10.6 倍。注意这里的输入 token 没有公布，所以这不是完整的成本对比，只是输出侧的量级。

有两件事值得从这组数字里带走。

一是默认档不是"够用档"。同一个任务，默认推理档把 88% 的输出花在了看不见的推理上。

二是官方给的省法是有条件的组合：降低推理档、把多条数据合并到一次请求、缩小图片分辨率。三个动作一起做，才把请求数从 1.1 万压到 1,269。

## 四、缓存是最大的一项，但要会看

缓存不是折扣活动，而是默认生效的前缀复用（https://dev.meta.ai/docs/prompt-caching ，检索于 2026-11-12）：请求开头与最近缓存过的 KV 状态匹配的部分，按缓存输入价计费。

- 缓存输入价是输入价的 4%（$0.004 对 $0.10），长上下文档是 $0.012 对 $0.30，比例相同。
- 回包里的 `cached_tokens` 是输入 token 的**子集**，不是额外计费项。`input_tokens` 仍然是总数。
- 排序决定命中率：固定内容（系统提示、few-shot、工具定义）放前面，变量放后面。
- 可选的 `prompt_cache_key` 能提高高并发下的命中率，键要稳定，不要按用户或会话生成。
- Responses API 有 `prompt_cache_retention`，可请求 `24h`，但官方说这是 hint，不保证。

官方 cookbook 的另一次运行更能说明缓存的分量（https://dev.meta.ai/docs/cookbook/python-to-rust ，检索于 2026-11-12）：把 16 个语言的 Pygments 词法器从 Python 移植到 Rust，子代理部分 1,466 次调用，输入 157,557,148 token，其中 154,039,752 token 命中缓存，输出 986,319 token。按 Ember 标准价自算：

| 项目 | 计算 | 金额 |
| --- | --- | --- |
| 非缓存输入 | 3,517,396 × $0.10 / 1M | $0.35 |
| 缓存输入 | 154,039,752 × $0.004 / 1M | $0.62 |
| 输出 | 986,319 × $0.50 / 1M | $0.49 |
| 合计 | — | 约 $1.46 |
| 对照：输入全不命中缓存 | 157,557,148 × $0.10 / 1M + 输出 | 约 $16.25 |

这是本文按官方公开的运行记录和官方价目做的算术，不是官方账单。它说明一件事：在这种"同一套工具定义、同一份代码库反复读"的负载里，缓存省下的钱占总账的九成以上（约 $14.79）。

同一个 cookbook 还给了主规划模型那一侧的记录：56 次调用，输入 4,412,412 token（4,306,528 命中缓存），输出 41,953 token。按 Muse Wonder 的 $4 / $0.20 / $20 自算，约 $2.12，比 1,466 次 Ember 调用花的还多。这条观察的方法论意义比金额大：调用次数和花费没有关系，账要按 token 记。

注意上述两个算例都有前提。第一，我按每档内的标准价算，如果某次请求的输入超过 20 万 token，整单会跳到高档，金额就是下限而不是结果。第二，官方记录里的缓存比例是它自己跑出来的，换成你的负载会变。

## 五、一万张照片那次的账

同一个 cookbook 给了照片任务的 token 记录：输入 2.66M、输出 0.47M（其中推理 0.17M），请求 1,269 次，平均每张 265 输入、46 输出。缓存份额没有公布，所以只能给区间：

| 假设 | 计算 | 费用 |
| --- | --- | --- |
| 输入全部不命中缓存 | 2.66M × $0.10 + 0.47M × $0.50 | 约 $0.50 |
| 输入全部命中缓存 | 2.66M × $0.004 + 0.47M × $0.50 | 约 $0.25 |

折到单张照片是 $0.000025 到 $0.00005。这个数字比榜单上的"每任务成本"有用得多，因为它对应一个具体的、可复现的任务形状。做容量规划时，应该找这种与业务形状接近的公开记录，按自己的量乘上去，而不是拿综合指数除以任务数。

## 六、并发和限速决定能不能省到

省钱的方案往往靠并行。官方限速按团队计，不按 key 计：`muse-ember-1.0` 每分钟 3,000 次请求、4,000,000 token，同一个团队里所有 key 共用。

按照片任务的形状算，一次请求约 2,100 输入、370 输出，合计约 2,470 token。4M TPM 折算下来是每分钟约 1,600 次请求，比 3,000 RPM 先到顶，所以先卡住并行的是 token 预算，不是请求数。600 次/分钟的子代理并发大约吃掉 TPM 的 37%、RPM 的 20%，看着宽松，但这是单个团队、单个模型的额度。

超过限制的请求直接返回 HTTP 429。官方建议用带抖动的指数退避，从 500 ms 起翻倍；如果响应带 `Retry-After`，至少等那么久。每个成功的 token 类响应都带 `x-ratelimit-remaining-tokens` 等四个头部，读它可以在撞线之前减速。

后台响应另有一条限制：`background: true` 每分钟最多 600 次提交，超了返回 429，已在跑的不受影响。

## 七、对账：预检和回包各有一处坑

预检用 `POST /v1/responses/input_tokens`，按目标模型的分词器算这次请求的输入。两个细节：它包含 Meta 注入的隐藏系统提示和工具脚手架（这些 token 不计费，但占上下文），所以它适合判断"装不装得下"，不适合直接当账单预估。官方两页对注入 token 是否计入的说法并不一致，定价页说 count 端点排除它，缓存页说包含它；这里以 count 端点的返回值为准。

回包里的 `usage.input_tokens` 在跑过内置工具的请求上是**跨多轮累计**的，官方明确说不要拿它当最终上下文占用量。要对账就用三件事对齐：`input_tokens`、`input_tokens_details.cached_tokens`、`output_tokens_details.reasoning_tokens`。

推理 token 单独看很有用。如果某类任务里推理 token 占输出的八成以上，说明这个任务的推理档给高了，先降档再谈压缩提示。

## 八、如果调用走兼容层

很多团队把多个模型放在一层兼容网关后面统一计费。以 4SAPI 这类中转网关为例，它对外是 `/chat/completions` 风格的路径，账单在网关侧汇总。

这时要确认两件与钱直接相关的事：回包里的 `cached_tokens` 是否原样透传，以及网关有没有保留上游的两档价格。如果网关只记总量、把两档揉成一个平均价，那 20 万那条线在你自己的账上就看不见了。核对办法很土但有效：发一个 25 万输入的长请求和一个 12 万的短请求，对比两次的计费单价，能立刻看出档位有没有被抹平。

## 九、限制与结论

本文所有金额都是按官方价目做的算术，不是账单截图；两个算例的输入输出 token 来自官方公开记录，缓存比例与单请求上下文大小没有完整披露，所以给了区间和下限。价格与限速以 2026-11-12 的官方页面为准，改动后要重算。

结论四条。

一是先看单请求输入有多大。超过 20 万就整单跳三倍，能拆就拆，拆不了就上缓存。

二是永远显式传 `reasoning_effort`。默认是 `max`，而推理 token 按输出价计费，同一任务能差出十倍量级的输出成本。

三是把缓存当成主要杠杆，而不是优化项。在重复读同一套提示与代码库的负载里，它决定的是量级。

四是账要按 token 记，不要按次数记。1,466 次小模型调用可能比 56 次大模型调用便宜，也可能更贵，取决于缓存命中率和推理档，只有 token 数能回答这个问题。
