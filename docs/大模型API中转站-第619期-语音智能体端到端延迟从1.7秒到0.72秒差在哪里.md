# 语音智能体的端到端延迟：从 1.7 秒到 0.72 秒差在哪里

做实时语音交互，功能跑通之后，决定体验的往往是一个数：用户说完话到听见回应要等多久。超过一秒，对话就开始像对讲机；超过两秒，用户会怀疑是不是没听到。

NVIDIA 在 2026 年 10 月 30 日的官方博客里公布了一次构建的两个延迟数字：生成式回答 1.70 秒，预置缓存回答 0.72 秒。本文用这两个数做拆解：这 1.7 秒由哪些部分组成，0.98 秒的差距来自哪里，以及你自己怎么测出属于你的数字。

需要先说清来源的性质。这是 NVIDIA 官方组织发布的博客，但数字来自一个具体装置在具体硬件上的单次构建，不是产品基准，也没有说明样本量。本文引用时都会标注这一点。我没有部署过这套东西，也没有测过任何延迟。信息截止日期为 2026-11-01。

## 一、两个数字，以及它们各自的含义

来源：[Building a Haunted House with NVIDIA Nemotron Open Models](https://huggingface.co/blog/nvidia/nemotron-halloween)（发布于 2026-10-30，检索于 2026-11-01）。原文写的两个指标是：

| 指标 | 数值 |
| --- | --- |
| 语音结束到音频开始的中位数，Bolt Q4 加 TTS | 1.70 秒 |
| 同一指标，预置缓存回答 | 0.72 秒 |

原文括号里补了一句：语音结束检测当前等待 300 毫秒静音。另有一处提到 100 毫秒用于补偿 Audio2Face-3D 的缓冲。

计时起点是"语音结束"，这一点很关键，后面会回到它。

## 二、把 1.70 秒拆开

按原文给出的两个固定开销，先做减法。这是我算的，不是原文的拆解：

```text
1.70 秒 = 1700 毫秒
1700 - 300（静音判定）- 100（动画缓冲）= 1300 毫秒
```

也就是说，留给"识别收尾、模型生成、语音合成首段出声"的预算大约是 1.3 秒。

同样算缓存那档：

```text
720 - 300 - 100 = 320 毫秒
```

320 毫秒要装下的是识别收尾、路由和播放已缓存的音频，理论上够用。这也解释了为什么缓存路线对延迟帮助这么大：它把最贵的两个环节整个跳过了。

要注意这是减法，不是剖面。真实的耗时是重叠的，比如合成第一小段就能开始播放，不必等整句合成完。所以 1300 毫秒不能当成三段相加。

## 三、0.98 秒的差距来自哪里

1700 减 720 等于 980 毫秒。这一档差别在做什么，原文写得很清楚：缓存路径用预置的文本和已保存的录音，跳过对话生成与语音合成。

由此可以做一个推断：在这个装置里，生成回复加合成语音合计约 0.98 秒。这是推断，不是原文结论。成立的条件是两条路径除了这两步之外开销相同，实际未必，例如缓存路径可能还省掉了情绪标签选择和部分音频后处理。

另外，1700 除以 720 约 2.36 倍。如果只看总数，容易得出"缓存让响应快 2.4 倍"的结论；但按上面的拆解，真正的差别集中在那 0.98 秒的两步上，其余开销没变。这个区别在做优化决策时很重要：你要压的是生成与合成，而不是整体。

## 四、这个构建用了四个手段

原文列出的做法，可以归成四类。

| 手段 | 具体做法 | 针对哪一段 |
| --- | --- | --- |
| 边生成边出声 | 整句还没生成完，就把可说话的那部分文本放出去，让播放先开始 | 生成与合成的等待 |
| 预置文本库 | 常见问候和玩笑用现成文本，不用模型现场写 | 生成 |
| 缓存录音 | 熟悉场景直接播已保存的音频，跳过合成 | 合成 |
| 拆卡分工 | 语言与语音链路一块 GPU，Unreal 场景与动画另一块 | 互相抢算力导致的抖动 |

第四条的原文理由是"保持动画帧率稳定，瓶颈是算力不是内存"。这一点常被忽略：语音交互里，动画或前端渲染与模型推理抢同一块卡，会造成延迟抖动，表现为"有时候快有时候卡"。把它拆开，牺牲的是硬件成本，换来的是延迟分布更集中。

还有一条与延迟相关的设置：原文说对话时关掉推理（reasoning）。推理过程对角色扮演这类任务收益有限，但会显著拉长首 token 时间。

## 五、和蓝本自称的"亚秒级"怎么对上

Nemotron Voice Agent 蓝本的 README 写的是"亚秒级端到端延迟"，支持多路并发。这和 1.70 秒看起来冲突，但两者不是同一件事，我列出现有信息，不做裁决：

| 维度 | 蓝本 README | 这次的单次构建 |
| --- | --- | --- |
| 计时起点 | 只说"端到端"，没有定义 | 语音结束到音频开始，含 300 毫秒静音判定 |
| 语音合成 | 默认 Magpie TTS Multilingual | 换成零样本音色版本 |
| 硬件 | 云、服务器、单卡三种配置 | 两块工作站级 GPU 分工 |
| 动画 | 不在链路里 | Audio2Face-3D 加 Unreal，另有 100 毫秒补偿 |
| 样本量 | 未说明 | 未说明，仅给中位数 |

最可能的解释是三者叠加：多了动画一段、换了音色方案、计时起点包含静音判定。但我没有测过，也没有找到蓝本测量条件的说明，所以只能说这三个数字不能直接比较。

给自己的提醒：看到"亚秒级"这类描述，先问计时起点和被测链路包含哪些环节。差 300 毫秒的起点定义，就足以让同一套系统在两张表上差三分之一。

## 六、自己测：先把时间戳定义清楚

想优化，先要有一个稳定的测量。下面是可执行的步骤。

### 1. 定义计时起点

两种常见定义，选一个并写进报告：

- **说话结束（end of speech）**：用户最后一个字结束。
- **发音结束判定（end of utterance）**：系统判定用户说完了，通常是静音持续一段时间之后。

两者相差的就是静音判定窗口，这次构建里是 300 毫秒。混用这两种定义做对比，结论会整体偏移。

### 2. 定义计时终点

- **首段音频到达播放端**：更接近用户感知。
- **首个音频数据块生成**：更容易在服务端采集。

推荐采集两者，差值反映的是传输与缓冲。

### 3. 每次交互记录一行

```text
turn_id, t_speech_end, t_eou, t_first_text, t_first_audio, t_audio_played, cached, ok
```

字段不必和我一样，但要能算三种时间：语音结束到首音、判定结束到首音、首音到实际播放。

### 4. 报分位数，不报平均值

延迟分布通常有长尾。平均值会被少数慢请求拉高，p90 才反映"最差的那几次有多差"。样本至少几十次，最好上百次，并且覆盖不同的说话长度、不同回答长度、缓存命中与否。

### 5. 分别统计缓存命中与未命中

这次构建的两个数字就是按这条分开的。混在一起算平均，只会得到一个没人能用的数。

### 6. 固定环境再对比

同一台机器、同一模型精度、同一并发数。换一项就重新测，不要跨环境比较。

## 七、一个算分位数的小脚本

下面这个脚本读一列毫秒值，输出样本数、中位数、p90、最小值和最大值。它只做统计，不采集时间戳。

```python
import sys, math, statistics

def pct(xs, p):
    """近秩法：第 p 百分位（p 取 0-100），1 个样本也适用"""
    xs = sorted(xs)
    if not xs:
        raise ValueError("no samples")
    k = math.ceil(p / 100 * len(xs))
    return xs[max(1, min(len(xs), k)) - 1]

vals = [float(x) for x in open(sys.argv[1], encoding="utf-8").read().split()]
print(f"n={len(vals)} median={statistics.median(vals):.0f} p90={pct(vals,90):.0f} min={min(vals):.0f} max={max(vals):.0f}")
```

用法：`python pct.py latencies.txt`，文件里是一列用空格或换行分隔的毫秒数。

我在本机用四组手造数据测过：

| 输入 | 输出 |
| --- | --- |
| 10 个样本（980 到 2100） | n=10，median=1550，p90=1900 |
| 单样本 1700 | n=1，median=1700，p90=1700 |
| 3 个样本（500、700、900） | n=3，median=700，p90=900 |
| 空文件 | 抛 StatisticsError，退出码非 0 |

第一版我写错了公式，10 个样本时 p90 返回了最大值 2100，而不是第 9 个 1900。近秩法应该是取第 ceil(p/100×n) 个，而不是四舍五入后再减一。写这类小工具时，先用手造数据验证一遍，比事后怀疑统计结果省事。

注意这个实现用近秩法，p50 取的是第 5 个样本（1500），与 statistics.median 的 1550 略有差别。两种都合理，但报告里要说明用的是哪种。

## 八、四个容易搞错的测量细节

1. **把静音判定当成延迟的一部分，却对外宣称不含它。** 用户感受到的等待包含这一段。要么减掉，要么说明。
2. **只测服务端，不测播放端。** 音频块生成了但被播放缓冲吃掉，用户还是觉得慢。
3. **忽略并发。** 单路测出的数字在多路并发下未必成立。蓝本 README 强调支持多路并发，但没给并发下的延迟数字。
4. **不做缓存命中的区分。** 缓存命中率会随时间变化，把两种混在一起算平均，结果既不可复现也不可比较。

## 九、限制与结论

这次构建给出的两个数字，价值在于它按"缓存命中与否"分开报，并交代了两个固定开销（300 毫秒静音判定、100 毫秒动画缓冲）。这让别人能拿来做减法，算出自己的预算边界。

能支持的做法：先定义计时起终点，分缓存与未缓存统计，报分位数，再看那 0.98 秒能不能压。

本文的限制：数字来自单个装置的单次构建，没有样本量和分布；1.3 秒与 0.32 秒是我做的减法，不是剖面；0.98 秒等于生成加合成的推断有前提；蓝本的"亚秒级"没有测量条件说明；分位数脚本只在手造数据上测过。

下一步建议：拿你现在的语音链路，按第六节记一周的真实交互，先得到一个 p50 和 p90。有了这两个数，再决定是压在生成、合成，还是压在那 300 毫秒的判定窗口上。
