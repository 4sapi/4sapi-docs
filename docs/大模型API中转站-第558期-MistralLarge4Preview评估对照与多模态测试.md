# Mistral Large 4 Preview 怎么评估：API 对照与多模态测试

Mistral Large 4 目前处于公开预览阶段：权重与许可尚未发布，只能通过 API 调用。这类模型最容易出现的问题不是“测得不准”，而是**测完之后发现结论不可用**——样本是随手挑的、对照条件不一致、打分带着先入为主。

本文只解决一个问题：**如何用一套可复现的方法评估 Mistral Large 4，得到能支撑决策的结论。** 以 **2026 年 10 月 14 日**核验的官方模型目录为基础，规格与可用性以官方页面为准。[Mistral 模型概览](https://docs.mistral.ai/getting-started/models/models_overview/)

## 前置条件

- **访问方式**：通过 API 调用，权重未开放，无法本地部署。
- **凭证**：有效的 API key 与足够配额。
- **对照对象**：当前生产使用的模型，用于同条件比较。
- **样本**：一组覆盖真实分布的任务样本，评估期内固定不变。
- **标注**：需要人工评分或明确的通过标准。

## 第一步：固定样本

样本决定结论的有效性。要求：

1. **覆盖真实分布**：不要全是简单样例。
2. **包含困难样例**：边界情况要占一定比例。
3. **固定不变**：评估期内不更换样本，否则无法对比。
4. **带参考标准**：每条样本给出可判定的正确答案或评分标准。
5. **规模适中**：几十条足以看出趋势，不必追求上千条。

## 第二步：同条件对照

对照必须控制变量：

```text
同一提示词
同一温度等采样参数
同一输入内容
同一评分标准
同一天内跑完（避免模型侧变动）
```

如果新旧模型用不同的提示词，结论就没有可比性。常见错误是“给新模型写了更精细的提示词”，这会把提示词差异混进模型差异。

## 第三步：盲评

打分时隐藏模型来源：

- 输出顺序随机化。
- 评分人不显示模型标识。
- 每条独立评分，不打乱批次。

盲评能显著减少主观偏差。如果不能盲评，至少要让评分人不知道哪份来自新模型。

## 第四步：多模态专项测试

Mistral Large 4 是原生多模态模型，视觉任务要单独测：

- **图像理解**：分类、识别、关系判断。
- **文档图像**：表格、票据、表单的字段抽取。
- **图像与文本联合**：根据图像回答文本问题。
- **困难样本**：模糊、遮挡、低分辨率的图像。

注意：图像会转成 token，**分辨率直接影响成本**。测试时要记录图像尺寸与耗时，否则无法解释成本差异。

## 第五步：记录指标

每次评估至少记录：

```text
sample_id
model
prompt_hash
input_tokens
output_tokens
latency_ms
quality_score
pass_fail
eval_date
```

`prompt_hash` 用来确认新旧模型用的是同一提示词；`eval_date` 用来标注结论的有效期。

## 第六步：结果解读

看到结果后，避免三个陷阱：

1. **只看平均分**：平均分掩盖分布，要看困难样本上的差距。
2. **忽略延迟**：质量相同但延迟翻倍，未必适合交互场景。
3. **忽略成本**：单位任务成本要算上重试与人工。

正确的解读方式是：**按任务类型分组比较**，而不是给一个总分。

## 第七步：许可与部署核对

预览阶段的关键待办：

- 权重是否发布。
- 许可条款是否明确。
- 是否允许商用与私有化。
- 是否有部署形态限制。

在这些明确之前，评估只能得出“能力如何”的结论，得不出“能不能用”的结论。把这两件事分开写进文档。

## 常见错误与排查

| 现象 | 可能原因 | 排查方向 |
| --- | --- | --- |
| 结论反复 | 样本太小或分布偏 | 扩大并固定样本 |
| 新旧无差异 | 提示词不同条件 | 统一提示词与参数 |
| 分数虚高 | 评估者知道来源 | 改为盲评 |
| 成本算错 | 忽略图像 token | 记录图像尺寸与用量 |
| 结论过期 | 预览模型已更新 | 标注评估日期并定期复测 |

## 验证清单

- 样本覆盖真实分布且固定。
- 对照使用同一提示词与参数。
- 评分采用盲评。
- 多模态任务单独测试并记录图像尺寸。
- 记录质量、延迟、成本三项。
- 明确标注评估日期。
- 许可与部署结论单独列出，并注明“待确认”。
- 有定期复测计划。

## 建立可复用的评估脚手架

把上面的流程固化成一个脚手架，能让后续评估省很多力气：

```text
eval/
  samples.jsonl     # 固定样本：输入、参考答案或评分标准
  prompts/          # 各任务的提示词，带哈希
  run_eval.py       # 对指定模型批量跑样本，落盘原始输出
  blind.py          # 随机化并隐藏模型来源，生成盲评文件
  score.py          # 汇总质量、延迟、成本
```

三个要求：

1. **原始输出必须落盘**，便于事后复看与模型更新后对比。
2. **提示词带哈希**，确认对照时用的是同一版本。
3. **结果带评估日期**，明确结论有效期。

有了脚手架，“换个模型再测一遍”就从几天变成几十分钟。

## 评估报告应该写什么

一份可直接支撑决策的评估报告，应包含：

- **范围**：评估了哪些任务、哪些样本、什么时间。
- **方法**：提示词、参数、评分方式、是否盲评。
- **结果**：分组展示质量、延迟、成本，而不是只给总分。
- **限制**：样本偏差、评估者偏差、预览模型的不确定性。
- **结论**：哪些任务可迁移、哪些需继续观察、哪些明确不适合。
- **待办**：许可、权重、正式定价等需要等待的事项。

其中“限制”一节最容易被省略，但它恰恰决定了结论能用到什么程度。写清限制，等于提前告诉读者结论的边界。
## 评估要覆盖的维度不止质量

新模型评估容易只测“效果好不好”。一份完整的评估至少要覆盖四类维度：

| 维度 | 具体指标 | 为什么重要 |
| --- | --- | --- |
| 质量 | 通过率、人工评分 | 决定能不能用 |
| 效率 | P50 / P95 延迟、吞吐 | 决定能不能撑住量 |
| 成本 | 单位任务成本、重试率 | 决定值不值得换 |
| 工程 | 接口兼容、限流、稳定性 | 决定迁移代价 |

只看质量就迁移，常见后果是“效果更好但延迟翻倍”或“跑量后账单失控”。

## 多模态任务的样本设计

评估多模态能力时，样本设计比模型选择更关键。建议按四类构造：

1. **清晰样本**：正常质量、正常光线，用于测基本能力。
2. **边界样本**：模糊、遮挡、旋转、低分辨率。
3. **专业样本**：与业务直接相关的文档类型（票据、表单、合同）。
4. **干扰样本**：含无关文字或水印，用于测鲁棒性。

每类都要有人工标注的正确答案。只测第一类，会得出偏乐观的结论。

## 常见评估反模式

- **样本太少**：几十条里挑出来的结论不可靠。
- **样本不固定**：评估中途换样本，前后无法比较。
- **提示词不同**：给新模型写了更精细的提示词，结论无法归因。
- **非盲评**：评分人知道来源，主观偏差被放大。
- **只看平均**：平均分掩盖了困难样本上的差距。
- **不记日期**：新模型迭代后，旧结论失效却仍在用。

## 评估结果怎么写进决策

评估不是为了排名，而是为了回答三个问题：

1. **能不能用**：质量是否达到业务门槛。
2. **值不值得用**：单位任务成本是否优于现状。
3. **什么时候能用**：许可、权重、区域可用性是否就绪。

把结论写成“条件 + 结论”的形式，例如“在法律文档抽取任务上，质量与现状持平，成本更低，但许可待确认”——这样的结论才能直接进入决策。
## 限制与结论

评估 Mistral Large 4 Preview 的关键不是跑多少条，而是**控制变量并把结论和有效期一起记录下来**。预览模型随时可能更新，任何不标注日期的结论都不适合作为长期依据。

本文的评估方法是通用的，不依赖具体模型；规格与可用性属于可变事实，以 2026 年 10 月 13 日信息为准。在权重与许可明确之前，建议只用于能力评估，不接生产链路。
