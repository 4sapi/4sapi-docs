# 【大模型API中转站】第149期 Computer Use | 可靠性和成本治理

本文是【大模型API中转站】系列的第149篇。本系列致力于用最低的成本、最清晰的方法，帮你打通多模型API的任督二脉。建议先收藏，随用随查。

前面三篇讲了 Agent 的结构、MCP、Harness、Subagent 和记忆。

这一篇收尾，讲最容易让人兴奋、也最容易翻车的一层：

```text
Computer Use。
Browser Agent。
桌面 Agent。
可靠性。
成本模型。
```

先说结论：

```text
能控制浏览器和桌面的 Agent，很像“会自己用电脑的人”。
但生产落地时，它更像“需要全程限权、录屏、预算和验收的新员工”。
```

让模型点网页、填表单、看截图，听起来比写 API 适配更通用。

但通用意味着不确定。

不确定意味着风险。

所以企业不要一上来就让 Browser Agent 操作后台、提交订单、更新客户资料。

更稳的路线是：

```text
先只读。
再草稿。
再人工确认。
最后才是有限自动执行。
```

同时，所有模型调用都应该走 4SAPI 这类大模型 API 中转站，做模型路由、Key 分组、调用日志、预算阀门和失败追踪。

否则 Browser Agent 不是助手，是黑盒。

## 1. Computer Use 到底解决什么

传统工具调用要给每个系统写接口。

比如你想让 Agent 操作一个 CRM，就要接 CRM API。

想操作工单系统，就要接工单 API。

想操作某个老后台，如果它没有 API，就很麻烦。

Computer Use 的思路反过来：

```text
不为每个软件写 API。
让模型像人一样看屏幕、点按钮、输入文字。
```

这一下打开了想象空间。

理论上，只要人能通过界面完成的事，Agent 也有机会完成：

```text
打开网页。
登录后台。
搜索订单。
填写表单。
下载报表。
复制结果。
整理摘要。
```

但注意两个字：

```text
理论上。
```

实际工程里，桌面和浏览器自动化有几个天然难点：

| 难点 | 说明 |
| --- | --- |
| 页面变化 | 按钮位置、文案、弹窗随时会变 |
| 视觉误判 | 截图里相似元素容易点错 |
| 状态复杂 | 登录态、权限、缓存、网络都会影响结果 |
| 操作不可逆 | 有些按钮点了就提交 |
| 调试困难 | 错一步后，后面全偏 |
| 安全风险 | 网页内容可能诱导 Agent 做错事 |

所以 Computer Use 很适合演示。

但要上生产，必须加很多护栏。

## 2. Browser Agent 最适合先做只读任务

浏览器 Agent 不要一开始就做“自动操作”。

先做只读任务最稳。

比如：

```text
打开指定页面。
读取页面信息。
截图。
提取字段。
生成摘要。
标记异常。
把结果写入草稿。
```

这些任务失败了，影响相对小。

不要一开始就让它：

```text
提交表单。
付款。
删除记录。
修改权限。
发送外部邮件。
批量更新客户状态。
```

如果业务必须写入，建议加人工确认：

```text
Agent 填好表单。
暂停。
展示即将提交的内容。
人确认。
系统再提交。
```

这一步看起来降低自动化程度。

但它能把风险从“自动事故”降到“人工确认的半自动流程”。

对企业来说，这通常更值。

## 3. Browser Agent 的提示注入风险更大

普通聊天里的提示注入，是用户或文档试图让模型忽略原规则。

Browser Agent 里，风险更大。

因为网页本身也会进入模型上下文。

攻击路径可能是：

```text
你让 Agent 打开一个网页。
网页里藏着一段指令。
模型把网页内容当成任务上下文。
它被诱导去做不该做的事。
```

这不是理论问题。

只要 Agent 会读外部网页、截图、HTML、邮件、IM 消息，就要假设外部内容不可信。

防护思路不是一句“不要被注入”。

而是工程隔离：

| 防护 | 做法 |
| --- | --- |
| 权限隔离 | 浏览器 Agent 默认只读 |
| 域名白名单 | 只允许访问指定系统 |
| 人工确认 | 写操作前暂停确认 |
| 敏感信息隔离 | 不把密码、密钥暴露给模型 |
| 操作审计 | 记录截图、动作、模型调用 |
| 输出校验 | 检查它准备提交的内容 |
| 沙箱环境 | 先在测试账号和测试数据里跑 |

这里尤其要注意：

```text
不要让模型直接看到生产密钥。
不要让模型直接操作不可逆按钮。
不要让外部网页内容拥有“指挥权”。
```

模型可以读取网页。

但网页不能命令模型。

这个边界要靠系统设计，不是靠模型自觉。

## 4. Agent 可靠性：十步任务不是十次 95%

Agent 可靠性有一道很朴素的数学题。

假设每一步成功率 95%。

听起来不错。

但一个任务如果要连续走 10 步，整体成功率就会明显下降。

因为它不是加法，是乘法。

每多一步，都多一个失败点。

这就是为什么很多 Agent 演示很漂亮，生产很难用：

```text
演示只要成功一次。
生产需要稳定成功很多次。
```

一个 Browser Agent 的任务可能包含：

```text
打开页面。
等待加载。
识别按钮。
点击。
处理弹窗。
输入字段。
校验结果。
翻页。
下载文件。
提取内容。
写入系统。
```

这里任何一步错了，后面都可能跑偏。

所以提升 Agent 可靠性，不是只换更强模型。

还要加 harness：

```text
步骤检查。
失败重试。
截图回放。
状态确认。
关键节点人工确认。
工具返回结构化结果。
最大轮数。
预算上限。
```

模型变强可以提高单步成功率。

工程护栏才能防止错误被级联放大。

## 5. 可靠性指标怎么设计

企业评估 Agent，不要只看“回答质量”。

要看任务级指标。

建议至少记录：

| 指标 | 说明 |
| --- | --- |
| 任务完成率 | 最终是否达到验收标准 |
| 单步失败率 | 哪一步最容易失败 |
| 平均重试次数 | 是否存在重复失败 |
| 人工接管率 | 多少任务需要人处理 |
| 平均成本 | 每个任务花多少钱 |
| 平均耗时 | 端到端耗时 |
| 回滚次数 | 写操作是否经常出错 |
| 高风险操作次数 | 涉及提交、删除、付款等 |
| 日志可回放率 | 出错后能不能复盘 |

这比“模型看起来聪明”更有用。

一个 Agent 真正上线前，要能回答：

```text
它在哪些任务上能稳定完成？
在哪些任务上经常失败？
失败后会不会继续乱跑？
每次失败平均花多少钱？
人工接管能不能及时发生？
```

回答不上来，就还不适合生产自动化。

## 6. 4SAPI 如何做 Agent 成本治理

Agent 的成本问题，比普通聊天复杂。

普通聊天通常是一问一答。

Agent 是多轮：

```text
计划调用。
工具选择调用。
结果分析调用。
失败重试调用。
最终总结调用。
审查调用。
```

Browser Agent 还可能多出视觉理解、截图分析、长上下文读取。

所以企业要把成本拆开看。

建议在 4SAPI 里按任务和角色做归因：

| 维度 | 示例 |
| --- | --- |
| 项目 | `crm`、`docs`、`ops` |
| 环境 | `dev`、`staging`、`prod` |
| Agent 类型 | `browser`、`coding`、`review` |
| 角色 | `planner`、`worker`、`reviewer` |
| 任务 ID | `ticket-1024`、`pr-88` |
| 模型 | 具体模型名称 |
| 结果 | `success`、`failed`、`manual_handoff` |

这样你才能算清楚：

```text
一次成功任务平均多少钱？
一次失败任务平均浪费多少钱？
哪个角色最适合降模型？
哪个阶段必须保留强模型？
哪个项目正在异常消耗？
```

没有这些数据，谈“Agent 省钱”都是感觉。

有了这些数据，才能做模型路由。

## 7. 模型路由：强模型用在关键点

Agent 不应该每一步都用最强模型。

更合理的是分阶段路由：

| 阶段 | 推荐模型策略 |
| --- | --- |
| 任务理解 | 中高能力模型，保证目标不偏 |
| 页面读取 | 支持视觉或长上下文的模型 |
| 简单提取 | 低成本模型 |
| 复杂判断 | 强推理模型 |
| 写操作前审查 | 强模型或双模型复核 |
| 最终总结 | 低成本模型 |

例如一个浏览器报表任务：

```text
Planner：强模型，判断要抓哪些字段。
Browser Worker：视觉能力稳定的模型，读页面和截图。
Extractor：低成本模型，整理表格。
Reviewer：强模型，检查异常和风险。
Summary：便宜模型，生成日报。
```

这套结构用 4SAPI 做路由会更清楚。

不同角色用不同 Key、不同模型、不同预算。

出了问题也能定位。

如果所有阶段都走同一个强模型，确实省配置。

但长期一定贵。

## 8. 生产上线的四道闸门

Browser Agent 和 Computer Use 上线，我建议至少有四道闸门。

### 第一，环境闸门

先在测试环境跑。

用测试账号、测试数据、测试后台。

确认它不会误点、误填、误提交。

### 第二，权限闸门

默认只读。

写操作要单独授权。

高风险操作必须人工确认。

### 第三，预算闸门

每个任务设置最大调用次数和最大预算。

例如：

```text
单任务最多 20 次模型调用。
单任务最多 5 次浏览器动作失败重试。
单任务成本超过阈值自动转人工。
```

### 第四，验收闸门

每个任务必须有明确验收标准。

比如：

```text
字段提取必须有来源截图。
表单提交前必须展示 diff。
代码修改必须通过测试。
报表生成必须保留原始链接。
```

没有验收标准，就不要自动化。

## 9. 适合先做的 Browser Agent 场景

适合先做：

```text
网页信息提取。
后台报表下载。
竞品页面监控。
表单草稿生成。
工单资料汇总。
截图巡检。
低风险重复操作。
```

谨慎做：

```text
客户资料修改。
订单状态更新。
权限变更。
自动付款。
批量删除。
生产后台配置。
对外消息发送。
```

不是这些场景永远不能做。

而是它们必须有更强的权限、审计和人工确认。

## 10. Agent 的成本模型正在变化

传统大模型 API 是按 token 收费。

Agent 时代，用户真正关心的不是 token，而是：

```text
任务有没有完成。
节省了多少人力。
减少了多少返工。
带来了多少业务结果。
```

所以企业内部评估 Agent，也应该从“单次调用成本”升级到“任务成本”。

可以算三层：

| 层级 | 计算方式 |
| --- | --- |
| 调用成本 | 每次模型调用多少钱 |
| 任务成本 | 一个完整任务总共多少钱 |
| 结果成本 | 一个成功结果平均多少钱 |

举例：

```text
一个任务花 1 元但成功率 30%，真实成功成本约 3.33 元。
一个任务花 2 元但成功率 90%，真实成功成本约 2.22 元。
```

所以便宜模型不一定真的便宜。

贵模型也不一定真的贵。

要看任务成功率、返工率和人工接管率。

这就是为什么 4SAPI 的日志、模型路由和成本统计要和任务结果打通。

只看 token 单价，会误判。

## 11. 最终上线清单

如果你准备把 Computer Use 或 Browser Agent 接进企业流程，上线前按这张表过一遍。

| 检查项 | 标准 |
| --- | --- |
| 模型入口 | 统一走 4SAPI 或同类网关 |
| Key 拆分 | dev、staging、prod 分开 |
| 角色路由 | planner、worker、reviewer 分开统计 |
| 浏览器权限 | 默认只读，写操作单独授权 |
| 域名限制 | 只能访问白名单系统 |
| 敏感信息 | 密码、密钥不进模型上下文 |
| 截图记录 | 关键动作前后保留截图 |
| 最大轮数 | 单任务有调用上限 |
| 预算上限 | 成本超限自动停止 |
| 人工确认 | 高风险动作前必须确认 |
| 失败回放 | 能复盘模型调用和工具动作 |
| 验收标准 | 每类任务有明确成功条件 |

这张清单过不了，就别急着放生产。

先做内测，先做只读，先做草稿。

## 12. 总结

这一组 Agent 文章讲到这里，可以收成一条主线：

```text
Agent 不是模型本身。
Agent 是模型、工具、上下文、记忆、权限、日志、验证和成本控制合在一起的工程系统。
```

Computer Use 和 Browser Agent 让模型看起来更像“会用电脑的人”。

但企业落地不能只看演示。

要看：

```text
是否可控。
是否可审计。
是否可回放。
是否可预算。
是否可停止。
是否真的降低成功任务成本。
```

4SAPI 这类大模型 API 中转站，在这里的价值不是“换个接口地址”。

而是把 Agent 背后的模型调用变成可管理的企业级 API：

```text
统一入口。
统一 Key。
统一路由。
统一日志。
统一预算。
统一审计。
```

Agent 能不能干活，看模型。

Agent 能不能放心用，看工程。

而工程里最先要补上的，往往就是模型入口、权限、日志和成本治理。
