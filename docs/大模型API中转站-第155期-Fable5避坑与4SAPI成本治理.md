# 【大模型API中转站】第155期 Fable 5避坑 | 4SAPI成本治理

本文是【大模型API中转站】系列的第155篇。本系列致力于用最低的成本、最清晰的方法，帮你打通多模型API的任督二脉。建议先收藏，随用随查。

前面四篇讲了 Fable 5 的 Prompt、上下文和 Loop。

这一篇收尾，讲避坑。

先说结论：

```text
Fable 5 很强，但不能无脑放飞。
```

它越适合长程任务，越容易暴露几类工程问题：

```text
提前停止。
上下文预算焦虑。
安全拒绝。
旧 Skill 触发推理提取风险。
Loop 成本失控。
并行子代理用量不可见。
```

这些问题不代表模型不能用。

它们代表你需要一层企业级治理。

也就是这个系列一直讲的：

```text
模型能力归模型能力。
生产落地要靠网关、日志、预算、权限和 fallback。
```

## 1. 坑一：它说了下一步，却没有真的执行

长会话深处，Fable 5 偶尔会出现一种情况：

```text
它写：“我接下来会运行测试。”
然后回合结束了。
```

或者：

```text
它明明已经有足够信息继续推进，却停下来问你要不要继续。
```

人工使用时，你回一句：

```text
继续，端到端做完。
```

通常就行。

但如果是自主管线，这种提前停止会让任务卡住。

可以加一条系统提醒：

```text
如果你陈述了下一步意图，必须立即执行对应的工具调用，
不要以纯文本意图结束回合。

已有足够信息时不要请求许可，直接推进。
只有破坏性或不可逆操作、范围变更、或需要用户独占信息时才暂停。
```

这条适合写进：

```text
Claude Code 项目规则。
Fable 5 Skill。
长程 Agent 系统提示。
/goal 或 /loop 启动模板。
```

## 2. 坑二：上下文预算焦虑

Fable 5 在极长会话中，有时会看到剩余上下文预算，然后开始“节省”。

表现可能是：

```text
主动建议开新会话。
提前总结移交。
压缩还没完成的工作。
减少必要检查。
```

有些场景这是好事。

但如果任务还没完成，它过早移交就会降低质量。

首选方案：

```text
不要把上下文预算数字暴露给模型。
```

如果架构上必须展示，可以加一句：

```text
不必为上下文预算担心。按当前任务的完整需求工作，
不要因为节省上下文而压缩、总结或提前移交你的工作。
如果确实无法继续，先说明阻塞原因和已经验证的事实。
```

注意最后一句。

不是让它永远硬撑。

而是防止它因为“省上下文”放弃必要工作。

## 3. 坑三：安全拒绝和误伤

Fable 5 对某些安全领域更敏感。

常见会触发拒绝或中断的方向包括：

```text
进攻性网络安全。
恶意软件。
漏洞利用。
某些生物和生命科学实验细节。
试图提取隐藏推理过程。
```

这当然有必要。

但企业里也会遇到误伤。

例如：

```text
合规安全审计。
防御性漏洞排查。
内部红线检查。
代码安全 review。
```

如果你的任务是合规防御目的，要在提示词里讲清楚：

```text
这是防御性安全审计。
不要提供攻击步骤、利用代码或绕过方案。
只输出风险描述、影响范围、修复建议和验证方式。
```

但即便这样，也可能触发拒绝。

所以生产环境要设计 fallback。

## 4. 坑四：旧 Skill 里的“展示推理”会出问题

很多旧提示词会写：

```text
展示你的思考过程。
逐步解释你的推理。
输出 chain of thought。
```

迁移到 Fable 5 时，这类内容要清理。

它可能触发 reasoning_extraction 相关拒绝或回退。

更稳的写法是：

```text
不要展示隐藏推理过程。
请输出结论、关键证据、判断标准和可复现的验证步骤。
```

用户需要的是：

```text
为什么可信。
证据在哪里。
怎么验证。
下一步做什么。
```

不是模型内部思考全文。

建议你全局扫描旧 Skill、系统提示、AGENTS、CLAUDE.md、工作流模板，搜索：

```text
思考过程
逐步推理
chain of thought
show your reasoning
step-by-step reasoning
```

发现后改成：

```text
给出证据和判断依据。
不要输出隐藏推理。
```

## 5. 坑五：强模型被用在所有小任务上

Fable 5 很强。

但不是每个任务都值得用。

下面这些任务，通常没必要上 Fable 5：

```text
标题改写。
短摘要。
简单分类。
固定格式 JSON 提取。
低风险批量改写。
重复轮询状态。
```

适合 Fable 5 的任务是：

```text
复杂架构判断。
长程 Agent。
跨文件代码审计。
高价值 PR review。
Prompt/Skill 迁移。
生产故障复盘。
企业级 API 网关方案设计。
```

不要把 Fable 5 当“默认车道”。

它更适合作为“升级车道”：

```text
普通任务先走性价比路线。
遇到复杂判断、长程执行、关键审查，再升级到 Fable 5。
```

## 6. 用 4SAPI 做 fallback 路由

生产环境建议把 Fable 5 放在 4SAPI 的路由策略里，而不是散落在各个客户端配置中。

一个简单策略：

| 场景 | 主模型 | fallback |
| --- | --- | --- |
| 高价值规划 | Fable 5 | Opus 或其他强推理模型 |
| 普通实现 | Sonnet / Codex / 性价比模型 | Fable 5 兜底 |
| 简单摘要 | 低成本模型 | 中等模型 |
| 安全拒绝 | Fable 5 | 防御场景专用模型或人工 |
| 长程任务失败 | Fable 5 | 人工接管或拆小任务 |

fallback 不是为了绕过安全限制。

而是为了处理：

```text
模型暂不可用。
分类器误伤。
上下文不适配。
成本超限。
任务需要拆分。
```

如果某个请求被安全拒绝，不要自动换模型继续生成高风险内容。

要先判断：

```text
这是合规防御任务，还是确实越界？
```

越界就停。

合规但误伤，再走受控 fallback。

## 7. 成本治理：建一张“任务利润表”

Agent 任务不能只看单次 token 单价。

更应该像看一张小型利润表：

```text
模型成本是多少？
人工返工省了多少？
失败重试浪费了多少？
最终有没有形成可复用资产？
```

这比单纯比较“哪个模型便宜”更接近真实业务。

假设：

```text
模型 A 每次任务 1 元，成功率 40%。
模型 B 每次任务 2 元，成功率 90%。
```

真实成功成本：

```text
A：约 2.5 元一次成功。
B：约 2.22 元一次成功。
```

便宜模型不一定便宜。

贵模型不一定贵。

关键看：

```text
一次命中率。
返工率。
重试次数。
人工接管率。
最终交付质量。
```

所以 4SAPI 日志里建议记录：

| 字段 | 说明 |
| --- | --- |
| `task_type` | 任务类型 |
| `model` | 使用模型 |
| `effort` | effort 档位 |
| `prompt_version` | Prompt 或 Skill 版本 |
| `input_tokens` | 输入消耗 |
| `output_tokens` | 输出消耗 |
| `retries` | 重试次数 |
| `fallback` | 是否回退 |
| `manual_handoff` | 是否人工接管 |
| `final_status` | 是否完成 |

再额外加两个业务字段：

| 字段 | 说明 |
| --- | --- |
| `reuse_asset` | 是否沉淀成 Prompt、Skill、脚本、文档 |
| `human_saved_minutes` | 预估节省的人工时间 |

有了这些，你才能判断：

```text
哪些任务值得用 Fable 5。
哪些任务该降模型。
哪些 Prompt 版本更省。
哪些 loop 在空转。
哪些任务虽然模型贵，但能沉淀长期资产。
```

## 8. 并行子代理要拆成五张报表

Dynamic Workflows 或多代理并行很强。

但它会快速放大调用。

比如：

```text
1 个 planner。
8 个 worker。
2 个 reviewer。
1 个 judge。
每个跑 3 轮。
```

这已经不是一次任务调用。

这是几十次调用。

所以日志要拆到 agent_role。

更实用的做法，是给并行任务拆五张报表：

```text
计划报表：planner 花了多少钱，计划有没有减少返工。
执行报表：worker 各自处理了什么，谁失败最多。
验证报表：reviewer 找出了哪些真实问题。
仲裁报表：judge 选择了哪个方案，为什么。
沉淀报表：summary 是否产出可复用 SOP、Skill 或脚本。
```

你要能看到：

```text
哪个 worker 最贵。
哪个 reviewer 最有价值。
并行是否真的减少时间。
并行是否增加返工。
```

如果不能看清，就先不要大规模并行。

先小批量试点。

## 9. 告警阈值怎么设

只有日志还不够。

企业要把 Fable 5 的使用变成可运营能力，最好设几类告警。

| 告警 | 触发条件示例 | 处理方式 |
| --- | --- | --- |
| 成本告警 | 单任务成本超过预算 150% | 停止 loop，转人工确认 |
| 重试告警 | 同一 task_id 重试超过 5 次 | 拆小任务或换模型 |
| fallback 告警 | 某模型 fallback 率超过 20% | 检查 Prompt 或模型状态 |
| 拒绝告警 | refusal 连续出现 | 判断是否越界或误伤 |
| 并行告警 | 子代理数量超过上限 | 暂停新 worker |
| 空转告警 | 多轮无文件、日志、测试变化 | 停止任务并生成复盘 |

这些告警可以先不自动化。

哪怕每天从 4SAPI 日志里导一张表人工看，也比完全靠感觉强。

真正成熟以后，再把告警接到企业微信、飞书、Slack 或工单系统。

## 10. 回退策略样例

可以把 fallback 写成一张策略表。

例如：

| 触发条件 | 动作 |
| --- | --- |
| Fable 5 拒绝且任务涉及安全 | 检查是否为防御性任务；越界则停止 |
| Fable 5 超预算 | 降到中等模型继续摘要，复杂判断转人工 |
| Fable 5 提前停止 | 注入继续执行提示，最多重试 1 次 |
| 低成本模型失败 2 次 | 升级到 Fable 5 high |
| reviewer 发现高风险 | 停止自动合并，转人工 |

写成伪配置大概是：

```text
route:
  default_worker: cost_effective_model
  planner: fable5_high
  reviewer: fable5_high

fallback:
  low_model_failed_twice: upgrade_to_fable5
  fable5_refusal_security: require_policy_check
  fable5_budget_exceeded: summarize_and_handoff
  high_risk_action: require_human_approval
```

这不是为了复杂。

而是为了让团队知道：

```text
什么情况继续。
什么情况降级。
什么情况升级。
什么情况必须停。
```

没有 fallback 策略的 Agent，很容易在异常时乱撞。

## 11. 一套企业上线检查清单

Fable 5 进入企业生产前，建议过这张表：

| 检查项 | 标准 |
| --- | --- |
| Prompt 迁移 | 旧 Skill 已清理过度约束和推理提取指令 |
| 模型入口 | 统一走 4SAPI 或企业 API 网关 |
| Key 管理 | 按项目、环境、角色拆分 |
| 路由策略 | 明确哪些任务用 Fable 5，哪些不用 |
| fallback | 拒绝、失败、超预算时有受控处理 |
| 成本字段 | 记录 model、effort、task_type、final_status |
| Loop 上限 | 每个 /goal 或 /loop 有最大轮数和预算 |
| 并行限制 | 子代理数量有上限 |
| 安全边界 | 生产、删除、发送、部署前必须人工确认 |
| 审计 | 模型调用和工具调用能回放 |

这张表过不了，就先别全量放开。

Fable 5 越强，越应该先灰度。

## 12. 推荐的 7 天试用打法

如果你现在只有短期窗口，可以这样安排：

| 天数 | 任务 |
| --- | --- |
| 第1天 | 审计旧 Prompt、Skill、系统提示 |
| 第2天 | 迁移最高频的 3 个工作流 |
| 第3天 | 跑一个长程代码或文档任务 |
| 第4天 | 建 notes 记忆系统 |
| 第5天 | 用 /goal 跑可验证目标 |
| 第6天 | 小批量试并行子代理 |
| 第7天 | 复盘 4SAPI 日志、成本、成功率、返工率 |

重点不是疯狂消耗。

而是找到：

```text
哪些任务 Fable 5 真能降返工。
哪些旧提示词应该删。
哪些工作流值得长期用 API。
哪些任务继续用便宜模型就够。
```

## 13. 总结

Fable 5 的最佳实践，不是把所有任务都交给它。

而是：

```text
高价值任务用强模型。
低价值任务用便宜模型。
长任务有检查点。
Loop 有停止条件。
并行有上限。
拒绝有受控 fallback。
成本有日志。
```

个人使用可以靠体感。

企业使用必须靠治理。

4SAPI 这类大模型 API 中转站，在这里的作用，不是把一句请求转发出去那么简单。

更适合把它理解成 Fable 5 的“路由账本”：

```text
这次为什么用 Fable 5？
有没有更便宜的模型能做？
失败后回退到哪里？
这次调用有没有形成可复用资产？
下次同类任务还要不要走同一路由？
```

这组 Fable 5 方法论到这里收束。

一句话：

```text
学会用 Fable 5，不是学会命令它。
是学会当好委托人。
```

把意图讲清楚。

把边界画明白。

把做完的标准定义好。

然后用 4SAPI 把成本、权限和日志管住。
