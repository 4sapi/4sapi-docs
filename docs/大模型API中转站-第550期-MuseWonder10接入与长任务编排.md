# Muse Wonder 1.0 怎么接入：工具调用、长任务编排与验收

把 Muse Wonder 1.0 接进项目时，第一个请求通常很顺利，真正的麻烦出现在**第二步之后**：工具调用返回了什么、模型有没有正确理解、出错后该重试还是换路径、任务到底算不算完成。

本文只解决一个问题：**如何把 Muse Wonder 1.0 接成一个能稳定跑完长任务的代理，并定义可验收的完成标准。** 以 **2026 年 10 月 14 日**核验的官方博客与文档为基础。官方把 Muse Wonder 的持续执行能力称为 Active Focus，并列举了「尝试替代路径、绕过阻塞、适应新信息、必要时请求澄清、执行重要操作前先确认」等行为，这也正是编排循环需要落地的几件事。[Muse Wonder 发布说明](https://research.meta.ai/blog/muse-wonder)

## 前置条件

- **接口**：使用支持工具调用的对话或代理接口，具体路径以官方文档为准。
- **模型标识**：请求里填写 Muse Wonder 1.0 对应标识。
- **上下文**：1,048,576 tokens，但长任务会逐步消耗窗口。
- **能力**：流式输出、视觉、工具调用、推理、结构化 JSON 均按官方说明可用。
- **执行环境**：长任务通常需要文件、命令或浏览器等外部能力，需另外搭建并做权限隔离。

## 环境与配置

```bash
export API_KEY="..."
export BASE_URL="..."
export MUSE_MODEL="muse-wonder-1.0"
```

把模型标识抽到环境变量里，便于在测试与生产之间切换。长任务通常还需要额外的环境配置：工作目录、超时上限、并发上限和日志路径。

## 第一步：先把工具契约定清楚

代理能否跑完，主要取决于**工具定义是否清晰**，而不是模型本身。每个工具至少要有：

1. **名称**：语义明确，不要用 `do_stuff` 这类含糊命名。
2. **参数 schema**：类型、必填项、取值范围写全。
3. **返回结构**：成功与失败都要有结构化返回。
4. **副作用说明**：是否会写文件、发请求、产生费用。
5. **幂等性**：同一参数重复调用是否安全。

工具描述写得含糊，模型就会反复试错；返回结构不统一，模型就无法判断上一步是否真的成功。

## 第二步：搭一个显式的循环

不要指望模型一次就输出完整方案。长任务应该跑在一个显式循环里：

```text
1. 观察当前状态
2. 模型决定下一步动作
3. 执行动作，拿到结构化结果
4. 记录日志
5. 判断是否满足完成条件
6. 未完成则回到第 1 步，直到达成目标或触发上限
```

循环必须有三个上限，否则任务可能无限跑下去：

- **步数上限**：超过就停，交人工。
- **成本上限**：累计花费超过阈值就停。
- **时间上限**：超时即停。

这三个上限是长任务代理的基本安全阀。

## 第三步：处理错误与恢复

官方描述提到模型会尝试从错误中恢复。要让它有效，需要给循环提供清晰的失败信号：

```text
工具返回 {
  "ok": false,
  "error_code": "FILE_NOT_FOUND",
  "message": "...",
  "retryable": true
}
```

要点：

- **区分可重试与不可重试**：文件不存在可以重试别处，权限不足重试也没用。
- **限制重试次数**：同一动作连续失败达到上限就换路径或停下。
- **记录失败序列**：连续失败的序列往往比单次失败更有诊断价值。

## 第四步：上下文管理

长任务的上下文会不断累积，即便窗口很大也会退化。三种常用手段：

1. **摘要压缩**：把已完成的步骤压缩成简短记录。
2. **状态外置**：把关键状态写进文件或数据库，而不是留在对话里。
3. **只保留相关历史**：每一轮只带与当前决策相关的最近若干步。

判断何时压缩，可以观察“最近几轮是否还在参考资料”和“响应是否开始变慢”。

## 第五步：定义验收标准

“模型说完成了”不等于任务完成。验收标准必须可检验，例如：

- 文件是否存在、内容是否符合规格。
- 测试是否全部通过。
- 页面是否可以打开且关键元素存在。
- 数据条数与来源是否一致。

把验收写成**可执行的检查**，而不是让模型自评。模型自评只能作为辅助信号。

## 常见问题与排查

| 现象 | 可能原因 | 排查方向 |
| --- | --- | --- |
| 反复调用同一工具 | 工具返回信息不足或幂等性问题 | 完善返回结构、加幂等保护 |
| 中途停滞 | 缺少明确的下一步信号 | 在提示里提供状态摘要 |
| 越跑越慢 | 上下文膨胀 | 引入摘要与外置状态 |
| 成本失控 | 缺少步数与成本上限 | 加安全阀 |
| 误报完成 | 验收标准不明确 | 改为可执行检查 |
| 高风险误操作 | 权限过宽 | 收窄权限、加审批 |

## 验证清单

- 工具契约（名称、schema、返回、幂等）已定义。
- 循环有步数、成本、时间三个上限。
- 失败信号区分可重试与不可重试。
- 有上下文压缩或状态外置机制。
- 验收标准是可执行检查，而非模型自评。
- 每步都有日志与耗时记录。
- 高风险操作有额外审批与回滚。
- 有单任务成本上限。

## 权限与沙箱：长任务的隐含前提

长任务代理通常需要真实的外部能力，这会带来一组和模型本身无关的风险。常见做法是把执行环境隔离：

- **文件系统隔离**：只挂载任务真正需要的目录，其余不可见。
- **网络访问白名单**：只允许访问必要的域名。
- **凭证隔离**：使用最小权限的临时凭证，且可随时吊销。
- **资源上限**：限制 CPU、内存、磁盘和执行时长。
- **可回滚**：关键操作前留快照，出错可还原。

对于有副作用的操作（发送消息、提交订单、删除数据），建议默认走**人工审批**，而不是让代理直接执行。代理在这一步更适合“准备好动作并等待确认”，而不是“直接做”。

## 从单次任务到批量任务

当单个任务跑通后，下一步往往是把同样的流程批量执行。这时要注意三点：

1. **隔离性**：每个任务使用独立的执行上下文，避免互相污染。
2. **并发控制**：批量并发会放大限流与成本，需要队列和并发上限。
3. **失败隔离**：单个任务失败不应拖垮整批，失败任务可单独重试。

批量场景里，最容易被忽视的是**幂等**：一个任务在超时后被重跑，如果有副作用，可能造成重复提交。批量上线前，务必确认每个任务可以安全重跑。

## 观测：长任务的最小日志集

长任务没有观测就等于黑盒。最小日志集建议包含：

```text
task_id
step_index
action
tool_name
tool_ok
error_code
input_tokens
output_tokens
cost_cumulative
latency_ms
```

有了这些字段，才能回答三个关键问题：任务卡在哪一步、成本花在哪一步、失败是否有规律。
## 对照官方能力清单检查你的循环

官方对 Active Focus 的描述可以直接当作检查清单：你的循环是否支持这五件事？

| 官方描述的行为 | 循环里的对应实现 |
| --- | --- |
| 尝试替代路径 | 失败后允许换方案，而不是只重试同一动作 |
| 绕过阻塞 | 识别“这条路走不通”，切换到其他路径 |
| 适应新信息 | 新观察到来时更新计划 |
| 请求澄清 | 信息不足时暂停并提问 |
| 执行前确认 | 重要操作前先取得确认 |

逐项对照后，通常会发现缺的是后两项：大多数自建循环只做了“重试”，没做“澄清”和“确认”。而这两项恰恰是长任务能否安全落地的关键。

## 用官方基准的思路设计验收

官方在发布说明里提到了几个评测方向，它们也可以借来设计自己的验收：

- **长周期软件项目**（官方提到 SWE-Marathon）：验收要看“多轮修改后项目是否仍可运行”，而不是单次改动是否正确。
- **领悟指令并产出专业成果**（官方提到法律代理基准）：验收要看“是否遵循了详细约束”，而不只看产出是否存在。
- **专注能力**（官方提到 FocusBench）：验收要看“遇到阻塞后能否继续推进”。

把这些思路翻译成可执行检查，比让模型自评“我完成了”可靠得多。

## 记忆与上下文的分工

官方的 Active Memory 描述了两件事：跨会话保留，以及按需检索。落进循环时，要明确谁负责什么：

```text
模型负责：判断「当前任务需要哪条历史信息」
系统负责：存储、检索、把结果注入上下文
```

如果把这件全交给模型（比如把全部历史塞进上下文），成本会随会话增长失控；如果全交给系统（只用关键词检索），又容易漏掉语义相关的信息。合理分工是：系统做粗筛与存储，模型做相关性判断。

## 观测：长任务的最小日志集

长任务没有观测就等于黑盒。最小日志集建议包含：

```text
task_id
step_index
action
tool_name
tool_ok
error_code
clarify_flag      # 本步是否请求澄清
confirm_flag      # 本步是否需要确认
input_tokens
output_tokens
cost_cumulative
latency_ms
```

有了这些字段，才能回答三个关键问题：任务卡在哪一步、成本花在哪一步、失败是否有规律。`clarify_flag` 与 `confirm_flag` 还能帮你评估“澄清频率是否过高”。
## 限制与结论

Muse Wonder 1.0 的接入难点不在调用本身，而在**把长任务装进一个有边界、可观测、可验收的循环里**。工具契约、循环上限、错误恢复和验收标准，是决定代理能否进生产的关键。

本文的请求与工具结构属于**示意**，真实字段以官方文档为准；规格与价格属于可变事实，以 2026 年 10 月 13 日信息为准。建议先用一个 5 到 15 步的真实任务跑通全流程，确认成功率和失败卡点后再考虑放量。
