# 开箱即用的代价：订阅、凭证与日志上报的边界

装好一个本地 Agent，第一件该问的不是"功能够不够"，而是"什么会离开这台机器"。

这类边界由两种东西共同划定：**条款**（厂商允不允许）和**代码**（客户端怎么做）。前者决定能不能，后者决定有没有做到。

下面按 cindy 仓库里的文件逐项核对。事实来自 README、`docs/dev-rules/` 下的凭证与日志上报规则、`config/endpoint.json`；我没有安装客户端，行为描述来自文档，不是实测。

## 一、先看默认会连哪些地址

客户端默认连官方云服务。端点有两份清单：`config/endpoint.json`（国内区）与 `config/endpoint.global.json`（全球区），对应开发入口的 `--region=cn` 与 `--region=global`。

我各数了一遍：**两份清单各自 22 条 URL、21 个主机、4 条 WebSocket**。国内区 17 条在 cindy.com.cn、5 条在 cindy.app；全球区 22 条全在 cindy.app。

按用途分类：

| 类别 | 例子 | 说明 |
| --- | --- | --- |
| 鉴权与会话 | auth、chat、oauth-broker、auth-desktop-callback | 登录、会话、第三方授权中转与回跳 |
| 设备互联 | device-link | 手机控制电脑的中转；**可改指向自建 relay** |
| 模型与语音 | model-access、voice | 托管模型与语音输入 |
| 素材与分享 | oss、share | 附件存储、会话分享 |
| 扩展 | skillhub（新旧两个字段）、plugin | 技能与插件分发 |
| 集成 | github、webhook、四条 hook（telegram / x / feishu / slack） | 代码托管代理与消息渠道 |
| 运维 | heartbeat、cdn、mobile-update | 心跳、更新 |
| 站点 | website | 官网链接，非请求目标 |

这张表不说明好坏，说明的是**默认出网面**。要收窄，就得知道每一条各自负责什么——这也是端点清单值得开源的原因：它让"它连了谁"变成可查的事实。

但它不等于全部出网面：日志上报目标被**有意排除在清单之外**，改成构建期注入、运行期只读。理由在日志规则第 4 节：第三方域名不在区域域名集合内，加进清单会让离线缓存被判不可信、影响离线启动；而免签写入地址一旦可被远程改写，等于允许把日志改投他人 logstore。

## 二、订阅凭证为什么不在客户端里

这一节最值得读，因为它解释了"有些功能看起来能做得更顺，产品却没做"。

项目文档的写法是：Anthropic 只允许用户用自己的订阅登录**未修改的 Claude Code**；第三方应用不得提供 Claude.ai 登录，也不得收集、存储或中转订阅凭证。

于是做法是只做内置 CLI 的外壳：

- 登录只拉起 `claude auth login --claudeai`；
- 登录态只读 `claude auth status --json`；
- 凭证留在 CLI 自己的凭证库（macOS 钥匙串或 `~/.claude`），客户端不读取、不复制、不刷新。

2026-11-07 起，用户显式添加的供应商内订阅账号走官方多账号方式：只在该账号的 CLI 子进程里设 `CLAUDE_CONFIG_DIR`，目录名带 owner 摘要与随机 id、不含邮箱，不接受外部路径。

还有一条判定：**只有 Claude.ai 订阅账号的 OAuth 登录算"Claude 订阅"**。Console 账号、API Key、apiKeyHelper、中转 token 或第三方云登录，一律按 `not_a_subscription` 处理，客户端也不替用户改 CLI 的登录。

需要说明：以上是**项目文档对 Anthropic 条款的说法**，我没有去条款页核对原文。但无论条款细节如何，"凭证不进第三方客户端"这个实现选择，本身就是可验证的边界。

## 三、Codex 与 Linux：两种不同的谨慎

Codex 的共享登录用**文件软链接，不是硬链接**。Windows 上没有创建软链接权限时，走 Cindy 自己的独立 OAuth 流程，凭证由 Codex 写在该实例的 `codex-home/auth.json`；后台对账不复制 token，也不按时间戳双向同步。

文档还写了三条拒绝条件：旧别名清理失败、仍有共享链接、无法确认文件类型时，**宁可拒绝启动这次独立登录流程**，也不把系统凭证交给一个"声称独立"的登录。

Linux 那边是另一类问题——**加密后端可能悄悄降级**。文档说：在 Electron ready 之前，对 Hyprland、labwc 与没有桌面身份的会话默认选 `gnome-libsecret`；因为 Chromium 不认识这些会话时会落到 `basic_text`，而打包版把它当成"加密不可用"。显式 `--password-store` 优先于此默认值；不新增明文降级，libsecret 缺失时继续拒绝明文。

准确说法是：**能拒绝写入的时候拒绝明文**，而不是降级后给个提示。回退本身仍在发生，只是被拒绝落盘；开发版还留了一个 `XDT_DEV_SAFE_STORAGE_BASIC=1` 的调试旁路。

## 四、三套独立的遥测通道

README 把这件事拆得很清楚，三套机制互不隶属：

| 通道 | 何时发生 | 内容 | 开关 |
| --- | --- | --- | --- |
| 使用统计（TapDB） | 官方构建默认开启 | 设备标识、系统与应用版本、启动与活动事件；登录后关联账号 ID | 设置里可关 |
| 心跳 | 仅在已验证的云登录期间 | 账号 ID、平台、版本 | 本地模式不发 |
| 日志上传 | 手动触发；崩溃补传需另开"崩溃时自动上传" | 见下一节 | 需隐私同意，自动上传默认关 |

必须写清的细节：

- 使用统计**与账号 ID 关联**，README 自己写明"不是完全匿名"；不采集聊天内容、文件内容、工作目录数据。
- 桌面关闭后立即停止后续上报；**本地模式（Skip Sign-In）不向 TapDB 上报**。
- 移动端关闭后立即解绑账号并停止显式触发的上报，但已初始化的原生 SDK 无法反初始化——要完全退出重启。
- 心跳与日志上传**不受统计开关影响**，是两个不同机制。
- 桌面原生崩溃转储留在本地、不自动上传；诊断日志需手动上传。
- **自己编译不等于干净**：桌面开发构建默认不初始化 TapDB（`XDT_TAPDB_DEV=1` 只抬掉构建门禁，仍要同意），移动端需注入 `clientId`/`clientToken`；但自建发布流水线要求这两个值非空。

"关掉了统计"不等于"什么都不发了"，这是本节最该带走的一句。

## 五、日志上报：四层收窄与一个字节 0

前提：日志由客户端直接送到日志服务，**中间没有服务端再过一遍**，所以客户端这套过滤就是唯一防线。

| 层 | 决定什么 | 具体做法 |
| --- | --- | --- |
| 源白名单 | 读哪些文件 | 只构造 `main-<date>.log` 与 logs 根的 `agent-<date>.ndjson`；`sessions/**` 与 `*cc-debug.raw.log` 永不构造路径 |
| 记录白名单 | 放行哪些记录 | deny-by-default，只放行与用户内容无关的基础设施来源 |
| 正则红线 | 抹除敏感片段 | 宁可多抹，不可漏 |
| 字段白名单 | 带出哪些字段 | 只有 `ts`、`level`、`src`、`scope`、`msg` 五个字段离开本机 |

第一层里 `agent-*.ndjson` 要单独说：它**默认只在崩溃补传时附带**，手动上传不打开；唯一例外是 `/issue` 且调用方显式开启，且读侧只取 `source === 'proxy'` 的记录（双闸）。同文件里还有可能带提示词的 `maker` 源日志。

两个细节见取舍。

**判据必须落在字节 0。** 日志里有一行格式哨兵 `#cindy-log-format:2`，读侧判据是"文件第 0 字节就是哨兵"，不是"文件里出现过"。原因写得很清楚：哨兵行可被正文逐字伪造，判据一放宽就能伪造放行记录头混进去。代价是升级当天那份文件整份不上报。

**proxy 记录必须逐字段重建，不能搬原样 `msg`。** 请求体在调试开关下可能带完整 prompt，上游错误体在 warn 级也会写日志，光按等级过滤挡不住。

两条都是同一类判断：**在白名单体系里，"看起来没问题"的捷径往往是漏洞入口。**

## 六、移动端有一个已知例外

README 自己披露了一处问题：企业 SSO 会跳过政策接受步骤；若没有同意记录、而该登录在重启后被恢复，当前迁移逻辑可能把一次全新安装标记为"已同意"，从而在用户未显式接受政策时开始上报。

文档给的缓解办法是：关闭"使用统计"，可以阻止这条迁移把它打开。

我单独列它不是因为它重大，而是因为它说明一件事：**同意流程的边界，往往不是被主路径守住的，而是被"迁移""恢复""例外登录"这些边角路径削掉的。**

## 七、本地模式挡住什么、挡不住什么

Skip Sign-In 常被理解成"隐私模式"，准确说它只是**少了一类出网**：

| 挡住 | 挡不住 |
| --- | --- |
| 不向 TapDB 上报使用统计 | 模型请求本身仍发出（你配的提供方） |
| 不发心跳（文档写明本地模式不发） | 服务端能力不可用（README 只给到这个粒度） |
| 不产生与账号关联的事件 | 技能与插件仍可能从扩展端点取内容 |

README 对"服务端能力不可用"没有再细分；跨设备、云伴生体、同步是否全在其中，我按字面理解，未逐项验证。

## 八、验收清单

| # | 检查 | 不合格的信号 |
| --- | --- | --- |
| 1 | 知道默认连哪两份各 22 条端点，各负责什么；知道哪条可替换 | 只知道"它连官方" |
| 2 | 订阅凭证在官方 CLI 凭证库里，客户端无副本 | 客户端目录里找到订阅 token |
| 3 | Codex 凭证是软链接或独立 OAuth，非硬链接共享 | 多实例指向同一 inode |
| 4 | Linux 上密码后端不是 `basic_text` | 提示加密不可用却继续用 |
| 5 | 三套通道分别确认：统计、心跳、日志上传 | 只关了一个就以为全关 |
| 6 | 统计与账号 ID 的关联是否可接受 | 以为"匿名" |
| 7 | 崩溃自动上传是否需要，默认是关的 | 以为崩溃日志会自动传 |
| 8 | 排障时确认走的是四层收窄后的通道 | 直接让对方发原始日志 |
| 9 | 移动端"使用统计"状态（尤其 SSO 登录后） | 全新安装却显示已同意 |

## 九、结论与边界

这类产品的边界不是"开源"或"隐私优先"能概括的，它由三层组成：**条款约束什么能做、代码决定做到什么、写进文档的例外说明哪里还没做到。**

最值得学的是日志那四层——尤其"判据必须落在字节 0"和"proxy 记录逐字段重建"。这不是产品卖点，是有人在自己的实现里找过洞之后留下的结论。

限制：没有安装客户端，行为描述来自 README 与工程规则；第二节关于条款是项目说法，未回查原文；端点数字是两份 JSON 的静态统计，运行时是否全部使用未验证；自建 relay 我未部署过；移动端例外为项目自述，未复现。

下一步只做一件事：装好先关掉使用统计，再看设置里还剩哪些上报开关。剩下的那些就是这张边界图的真实形状。
