# 【大模型API中转站】第174期 AI排查429限流 | 并发预算和退避

本文是【大模型API中转站】系列的第174篇。本系列致力于用最低的成本、最清晰的方法，帮你打通多模型API的任督二脉。建议先收藏，随用随查。

大模型 API 接入后，第二个常见错误是：

```text
429 Too Many Requests
```

很多人看到 429，就以为：

```text
请求太多，重试就行。
```

不一定。

429 可能来自：

```text
每分钟请求数超限。
每分钟 token 数超限。
并发超限。
Key 预算用完。
项目额度用完。
同一任务重试风暴。
模型供应商临时限流。
多个业务共用一个 Key 抢额度。
```

所以 429 最适合 AI 做日志聚合。

尤其适合用 4SAPI 的调用日志来查。

## 1. 先区分四种 429

| 类型 | 说明 |
| --- | --- |
| RPM | requests per minute 请求数过多 |
| TPM | tokens per minute token 过多 |
| concurrency | 同时进行的请求太多 |
| budget | 预算或额度不足 |

如果只看状态码，四种都是 429。

但修法完全不同。

RPM 超限要降频。

TPM 超限要减少上下文或输出。

并发超限要排队。

预算不足要分 Key、设额度、做成本治理。

## 2. 给 AI 的 429 排错包

```text
【现象】
- 429 错误原文：
- 发生时间段：
- 影响业务：
- 是否某个模型：
- 是否某个 Key：

【调用日志】
- 每分钟请求数：
- 每分钟 token 数：
- 并发数：
- 重试次数：
- 失败率：
- fallback 记录：

【任务】
- task_type：
- 是否批量任务：
- 是否长上下文：
- 是否流式：
- 是否有自动重试：

【4SAPI】
- Key 分组：
- 预算：
- 额度：
- 模型路由：
- 最近是否新增业务：

【边界】
- 不建议无限重试
- 不建议所有任务都升级到强模型
- 先给限流原因判断
```

这份包能让 Fable 5 判断是哪类限流。

## 3. 辅助模型先做日志聚合

不要让 Fable 5 直接读全部日志。

先让低成本模型做：

```text
请按分钟聚合这些 4SAPI 调用日志。
输出：
- minute
- request_count
- input_tokens
- output_tokens
- error_429_count
- retry_count
- top_model
- top_key_group
不要分析根因。
```

得到聚合表后，再给 Fable 5。

高级模型负责判断：

```text
是请求峰值。
是 token 峰值。
是重试放大。
还是预算策略。
```

## 4. 常见根因一：重试风暴

最危险的是：

```text
429 后立即重试。
重试又 429。
并发越堆越多。
整个系统雪崩。
```

修复方向：

```text
指数退避。
加 jitter。
最大重试次数。
按错误类型区分是否可重试。
超过阈值进队列或降级。
```

不要所有错误都重试。

尤其：

```text
401/403 不该重试。
400 参数错误不该重试。
429 可以有限退避。
500/503/504 可以有限退避。
```

## 5. 常见根因二：批量任务挤占实时任务

比如你晚上跑内容批量摘要。

结果占满同一个 Key。

白天客服系统也用这个 Key。

于是客服 429。

解决不是简单加钱。

而是分 Key：

```text
realtime-key：客服、产品实时请求。
batch-key：批量摘要、离线任务。
agent-key：长程 Agent。
fable-key：Fable 5 高价值任务。
```

4SAPI 里按 Key 分组和预算控制。

这样一个批量任务不会打爆所有业务。

## 6. 常见根因三：长上下文占满 TPM

一次请求可能只有 1 个。

但它带了几十万 token。

于是 TPM 爆了。

AI 排查时要看：

```text
input_tokens。
output_tokens。
上下文长度。
是否重复传历史。
是否没有做摘要。
```

修复方向：

```text
上下文包。
RAG 检索。
摘要缓存。
限制 max_tokens。
长任务拆段。
```

Fable 5 很适合判断哪些上下文必须保留。

辅助模型适合先摘要。

## 7. 常见根因四：所有任务共用强模型

如果所有任务都走 Fable 5 或强模型：

```text
标题改写。
日志摘要。
客服分类。
代码审查。
长程 Agent。
```

很容易限流和超预算。

建议路由：

```text
短摘要 -> 低成本模型
分类 -> 低成本模型
普通问答 -> 中等模型
复杂判断 -> Fable 5
最终审查 -> Fable 5 或 reviewer
```

429 很多时候是架构问题。

不是某一次请求问题。

## 8. AI Prompt

```text
你是大模型 API 429 限流排查助手。

请根据 4SAPI 调用日志聚合、Key 分组、模型、token、并发和重试记录，判断 429 属于：
1. 请求数超限
2. token 超限
3. 并发超限
4. 预算或额度不足
5. 重试风暴
6. 批量任务挤占实时任务

要求：
- 不建议无限重试。
- 给出退避、队列、降级、Key 分组和模型路由建议。
- 区分短期止血和长期治理。
- 每个结论引用日志字段。
```

## 9. 4SAPI 治理字段

建议记录：

```text
task_type
key_group
model
input_tokens
output_tokens
duration_ms
retry_count
status_code
fallback_model
budget_bucket
```

有了这些，429 可以复盘。

没有这些，只能猜。

## 10. 一个真实排查例子

假设你看到客服系统突然 429。

第一眼看日志：

```text
10:00-10:05，客服请求 429 增加。
同一时间 batch-summary 任务开始跑。
batch-summary 使用同一个 prod-key。
retry_count 从 0.2 上升到 4.8。
```

这个时候不要先怪客服系统。

更像是：

```text
离线批量任务挤占了实时业务 Key。
429 后重试又放大了请求量。
```

短期处理：

```text
暂停 batch-summary。
客服系统保留 prod realtime key。
批量任务换 batch-key。
把 429 重试改成指数退避。
```

长期治理：

```text
实时业务和批量任务分 Key。
每个 Key 设置预算和并发上限。
4SAPI 日志按 task_type 聚合。
每天看 429 和 retry_count。
```

这就是 AI 排查 429 的价值。

它不是告诉你“请求太多”。

而是帮你看出：

```text
哪个任务把谁挤掉了。
```

## 11. 退避策略模板

可以让 Fable 5 审查你的重试策略：

```text
请审查下面的大模型 API 重试策略。
重点判断：
1. 401/403/400 是否被错误重试
2. 429 是否有指数退避和 jitter
3. 500/503/504 是否有最大重试次数
4. 是否会在高并发下形成重试风暴
5. 是否有队列或降级方案
```

一个基本原则：

```text
配置错误不要重试。
限流错误慢点重试。
临时故障有限重试。
超过阈值转人工或降级。
```

如果系统里有 Agent Loop，还要加一条：

```text
同一个 task_id 连续 429 超过阈值，停止当前 loop，并生成排障报告。
```

否则 Loop 会用最贵的方式证明自己已经被限流。

## 12. 总结

429 不是一句“请求太多”。

它可能是：

```text
并发问题。
token 问题。
预算问题。
重试问题。
路由问题。
```

AI 排查 429，最重要的是聚合日志。

4SAPI 的价值就是：

```text
让你看到哪个 Key、哪个模型、哪个任务类型、哪个时间段打爆了额度。
```

一句话：

```text
429 不要猛重试，要先看是哪种限流。
```
