# 看到 CPU 跑大模型的宣称：三个速度口径与一份复现清单

同一台机器、同一个模型，你可以诚实地报出 44 tok/s、9 tok/s，或者 14 tok/s。

第一个是预填充速度，第二个是纯解码速度，第三个是加投机解码之后的解码速度。三个数都是真的，混着用就成了营销。

llama-modchip 的 README 把这几个数字并排列出，算是比较规矩的写法。但读者得自己会拆，否则"284B 在 64GB CPU 上跑起来"这句话，可能被理解成"聊天跟本地小模型一样快"。

下面给一套读法与验法。事实来自仓库 README、ARCHITECTURE.md、FAQ.md 与评测脚本（检索日期 2026-11-10）；我没有运行过它，也没有下载模型，所有性能与质量数字都是项目自述。

## 一、三个口径，各回答不同问题

| 口径 | 常见标签 | 回答什么 | 容易误读成 |
| --- | --- | --- | --- |
| 预填充 | pp512 | 一次塞进 512 个 token 要多久 | "生成速度" |
| 纯解码 | N=1 | 一个 token 一个 token 生成有多快 | "整体体验" |
| 加投机解码 | +drafter | 加了草稿模型之后的解码 | "模型本身变快了" |

以 284B 那个模型在 Ryzen 9 9955HX（16 核，无 GPU）上的数据为例：预填充 43.16 到 44.36，纯解码 9.06 到 9.95，加投机 11.5 到 14.7。

三个数放在一起才有意义：预填充快，说明长文档灌进去不算灾难；解码慢，说明逐字输出就是慢；投机能提到 14，说明瓶颈在"每次只算一个 token"这个模式上。

**判断一个宣称，第一句要问：这是 pp 还是 tg？** 只写一个数字的，基本是挑了个好看的。

另外，服务端数字要和机器绑在一起看。项目报的 20.7 到 23.6 tok/s 是 Apple M5 Max（64GB 统一内存）跑 `llama-server` 的结果，不是那台 9955HX 的。

## 二、质量账：哪些是自比，哪些才是对原版

先看一个容易误读的数字。README 表里 Top-6 那行写余弦 1.00000、KL 0.0000，看着像"量化零损失"。

表头说清了参照物：这些概率与 KL 是"相对未打补丁的 Top-6 执行"测的——也就是**同一个 56.56 GiB 检查点、同一个 Top-6 配置下，打补丁前后自比**，属于"补丁前后逐位一致"的等价性自检。它证明的不是量化无害，而是这套内核没改变输出。

真正对比原始 76.87 GiB 版本的数字是另一个：README 的量化表里写 top-logit 余弦 0.9964。

两个数不冲突，但含义完全不同。**看质量指标，第一个问题永远是"跟谁比"。**

四类指标，各有盲区：

| 指标 | 衡量什么 | 盲区 |
| --- | --- | --- |
| logit 余弦 | 两个分布像不像 | 整体高度相似时，个别 token 排序变化看不出 |
| KL 散度 | 分布差异的距离（nats） | 同样 KL，代码补全与长文写作的容忍度不同 |
| top-1 命中 | 最高概率那个 token 对不对 | 样本量常常不披露 |
| 任务级通过率 | 具体任务能不能过 | 题目与通过线由项目自己定 |

第四类最接近"能不能用"，但最需要看细节。项目那个 100 分制脚本，我读了源码：工具调用 30 分、可执行代码 30 分、长上下文 needle 与算术 20 分，**最后 20 分是速度**——公式是 `20 × decode_tps ÷ 15`，解码到 15 tok/s 才拿满。

所以 98.5 这个分数里，**有 20 分在测速度**。若按质量侧一分不扣反推，速度侧是 18.5，对应解码约 13.9 tok/s——但这只是反推：13.9 高于本文引用的纯解码 9.06 到 9.95，只有开投机解码（11.5 到 14.7）才落在这个区间，而评测默认是否带草稿模型，文档没说。反过来也不唯一：若解码到 15 tok/s 以上、速度拿满 20，质量侧就得是 78.5。稳妥的读法只有一句：**这 100 分里有 20 分测的是速度，当纯质量分会读反；按默认无损配置自己跑，分数可能低于 98.5。**

还有一条：脚本里的 needle 测试是 8.5K token 的干草堆。README 与 FAQ 提到的 256K needle 属于架构论证，脚本里没有对应测试项。

## 三、兼容账：自定义张量类型 = 工具链锁定

这条最容易忽略，但会直接卡住迁移。

项目引入了一个自定义量化类型 `GGML_TYPE_Q2_0`，type ID 是 40，用来把 MLA 的投影压到 3.75 bpw。README 写得很直白：未打补丁的 llama.cpp、Ollama、LM Studio 会报 `unknown tensor type 40` 并拒绝加载。

要说准确一点：284B 那个 1.71 bpw 不是这个类型带来的，主要来自标准 `IQ1_S`（1.5625 bpw）铺在 256 个路由专家上；`Q2_0` 是另一块拼图。

但这不改变结论：

- **能跑这个模型的运行时，只有它自己那套二进制。**
- **反向也成立**：你没法把这些权重拿回标准 llama.cpp 做 A/B，除非另外下一次标准量化的同款。
- **升级路径受项目节奏约束**：上游改了算子或元数据，补丁得跟着改。

这不是缺陷，是代价：要非常规压缩率，就得付非常规兼容性。**选它之前先问：我的部署环境能不能只跑它家的二进制。**

## 四、四条失败实验，两类边界

一个技术项目最值得读的部分，往往是它承认没做成什么。ARCHITECTURE 第 5 节列了四项，但它们不是同一类问题。

**两条是质量边界：**

- 把 Top-K 压到 2 以下，出现质量崩塌，项目称之为"脑叶切除"效应；Top-4 是它找到的甜点。
- 后训练三值量化（1.58 bit，权重只有 -1、0、+1）会毁掉路由与 SSM 层。

**两条是工程边界：**

- 在 CPU 上做 AQLM。加性量化靠 GPU 的纹理与共享内存查表，CPU 没有对应通路，实测比连续读的 Q4_0 慢三到四倍。
- 静态宏码本。训练分布内还行，遇到分布外提示吞吐掉到 0.71 到 0.94 倍，比不投机的基线还慢。

分开看才有用：**"2 bit 以下还能保质量"的宣称要对着前两条；"2 bit 更快"的宣称要对着后两条。**

## 五、五步复现清单

如果你有一台候选机器，按这个顺序验，半天能出结论。

**第一步，只查硬件。** 项目自带 `scripts/check_cpu_readiness.py`，检查指令集、可用内存、大页配置，并跑一个约 0.6 秒的多核 DRAM 流式微基准（脚本里的 `measure_dram_bandwidth_gbs`，运行时会打印这行），既然整套账都是带宽账，这一步最该看的就是它测出的带宽值——是该平台实测，换平台重测。不想跑脚本，`./modchip status` 只查大页与共享内存

**第二步，跑 30 秒测速。** `./modchip bench` 输出一份可提交的记分卡，两阶段测速。

**第三步，记录三个容易漏的参数。** 测速时的上下文长度、常驻内存（VmRSS）、swap 使用量。没有"swap 为零"这个前提，速度数字不可比。

**第四步，跑评测。** `./modchip eval` 跑那个 100 分制。读的时候记得拆成质量 80 与速度 20 两块，否则看不出哪块掉了。

**第五步，做反向对照。** 拿同家族的标准量化 GGUF（如 Q4_0 版）在标准 llama.cpp 上跑同样 bench，两个数一比，才知道"这套补丁带来多少"，而不是"这个模型有多快"。

第五步最容易被跳过。没有它，你无法区分模型能力与工程优化。

## 六、听到一个宣称时，先反问四句

1. **什么硬件？** 16 核 Zen 5 桌面与 8 核低压本，标称带宽相近，实测能差一倍。
2. **多长上下文？** 按 ARCHITECTURE 的算式，同一个 30B 模型从 512 到 128K 上下文，理论上限会从 41.6 掉到 13.8 tok/s。
3. **哪个口径？** pp、tg、还是加了投机的服务端数字。
4. **质量怎么测的？** 对照的是原始模型、还是同一个检查点打了补丁前后。

四句问完，多数"惊人数字"会缩水到合理区间。这不是说项目在骗人，而是**省略口径的表述天然会放大**。

## 七、五类场景下，结论不成立

**没有 AVX-512 的老机器。** 核心优化（寄存器分块、VNNI 内积、非临时加载）压着 AVX-512 写。只有 AVX2 能跑，但"提升 77%"这类数字不适用。

**内存不够。** 284B 那套要 62.5 GiB 可用内存；项目给的原版是 76.87 GiB，两者差 14 GiB 多，装不下不是慢一点，是抖动到不可用。

**Windows。** 有 Windows 路径，但显存与内存调度走 WDDM，要留几百 MB 预留，拆分策略要单独算。照 Linux 的结论套过去会翻车。

**多用户并发。** 排行榜上的数字都是 N=1。项目的 FAQ 确实主张过服务器平台可以跑多路并发（靠共享页缓存与每 NUMA 钉核），但那段没有实测表支撑，与单请求数字不是一回事。

**虚拟机或共享宿主。** 云主机的"8 vCPU"背后是共享内存控制器，带宽随邻居变化。项目在 Graviton3 上报的 44.97 tok/s 没说是否受同宿影响，别当独占基线。

## 八、一次实际的对齐演算

把方法用一遍，对象是同一个 30B 混合专家模型的两个量化版本：

| 配置 | 文件大小 | 纯解码 |
| --- | --- | --- |
| Q4_0 基线 | 17.59 GiB | 19.54 tok/s |
| Fractal-64 | 14.35 GiB | 25.02 tok/s |

只看最后一行，结论是"降量化带来 +28% 速度"。但按带宽÷每 token 字节换算（激活 3.0B）：

- Q4_0：3.0e9 × 4.50 ÷ 8 ≈ 1.69 GB/token，乘 19.54 得约 33 GB/s。
- Fractal-64：3.0e9 × 3.75 ÷ 8 ≈ 1.41 GB/token，乘 25.02 得约 35 GB/s。

**字节降了约 17%，速度涨了 28%，相乘得到有效带宽只多约 7%。** 也就是说这 28% 里，大头是"少读了字节"，小头才是内核与局部性收益。

两个附带发现也值得记下来。

第一，这两个 bpw 标签是**路由专家张量**的，不是整个文件的：17.59 GiB 除以 30.2B 参数约等于 5.0 bpw，说明还有 Q8_0、F32 的张量在抬高平均值。所以用它们算的是同口径比值，结论不受影响。

第二，33 到 35 GB/s 只有项目自述可持续带宽（72 到 76 GB/s）的 45% 左右。**这说明"纯解码 = 纯带宽"这个说法在 30B 上并不完全成立**，还有解包、页表、注意力在占时间——这也正好回到第五步为什么要做反向对照。

## 九、结论与边界

读这类项目，把"能跑"和"好用"分开：能跑是容量账，好用是带宽账加质量账。三个口径对齐了，数字才有意义。

我的判断：这类方案适合单用户、离线、数据敏感、能接受十几秒出一段话的场景；不适合并发、低延迟、强工具调用的生产服务。

限制：没有运行任何代码，数字全部来自项目自述；100 分制由项目定义（含 20 分速度分），不是第三方基准；Apple Silicon 与 Graviton 的数字来自项目收集的第三方实测，我只引用未复核；第八节的 33 到 35 GB/s、"45%"与"7%"是我的换算。

下一步只做一件事：先跑第一步的硬件检查，重点看它输出的带宽数，再用你的上下文长度重算一遍上限。两个数出来，你就知道该继续还是该放弃。
