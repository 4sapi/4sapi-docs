# 拆开 Codex 的 Agent 循环：一次任务为什么会调用多轮模型

你让 Codex 修一个测试，它先读文件，再执行命令，发现失败后继续修改，最后才回复。
界面里只发生了一次提问，后台却可能经历多次模型请求。
如果把这段过程理解成“一个提示词换一个答案”，就很难解释它为什么继续、什么时候停止，以及中断后哪些工作已经发生。

这篇文章从公开源码追踪一条普通编码任务的执行路径。
读完后，你应该能把一个卡住的任务定位到输入准备、模型请求、工具执行或收尾阶段，而不是只说“Agent 又转圈了”。

分析基线是 OpenAI Codex 仓库提交 `46d252f8bf8b09f4ef765bc72e40f02c229da3e6`，资料核对日期为 2026-10-20。
本机命令行版本为 `codex-cli 0.141.0`。
源码提交与本机二进制分别记录，本文没有把二者当作同一次构建，也没有编译该提交。

## 先区分三个容易混在一起的对象

理解循环之前，可以先建立一张阅读用的概念表。
表中的“模型请求”是分析单位，不是要求所有公开协议都有同名对象。

| 对象 | 用来回答的问题 | 观察方式 |
| --- | --- | --- |
| Thread | 这份会话和历史属于谁 | 线程 ID、会话记录 |
| Turn | 当前处理哪一轮用户输入 | 回合开始、完成与中断事件 |
| 模型请求 | 这一步发给模型什么，返回什么 | 请求输入、输出项、工具结果 |

一次 Turn 内可以有工具调用和后续模型请求。
把工具执行看成独立步骤后，“一轮任务为什么耗时很长”才有可测量的拆法。
这不是说三个对象一定一一嵌套成固定树，运行中输入、后台工作和恢复路径会增加复杂性。

这一判断的直接依据是 `RegularTask::run` 对 `run_turn` 的调用，以及 `run_turn` 内部的采样循环。
两处源码都应阅读：前者负责普通任务的生命周期，后者负责一次推进过程中的模型交互。
来源：[普通任务入口 regular.rs](https://github.com/openai/codex/blob/46d252f8bf8b09f4ef765bc72e40f02c229da3e6/codex-rs/core/src/tasks/regular.rs)、[回合实现 turn.rs](https://github.com/openai/codex/blob/46d252f8bf8b09f4ef765bc72e40f02c229da3e6/codex-rs/core/src/session/turn.rs)，核对日期 2026-10-20。

## 普通任务怎样进入循环

`RegularTask::run` 并不是拿到输入就立刻发送一个 HTTP 请求。
该基线先发出回合开始事件，处理启动阶段的准备，再进入 `run_turn`。
准备过程里还涉及扩展生命周期和预热结果，取消信号也会影响后续路径。
来源：[regular.rs 的 run 实现](https://github.com/openai/codex/blob/46d252f8bf8b09f4ef765bc72e40f02c229da3e6/codex-rs/core/src/tasks/regular.rs#L40)。

这带来一个排错上的区别：看见“回合开始”，只能说明任务生命周期已经开始。
它不能单独证明模型已收到请求。
如果此时卡住，应该继续检查准备阶段，而不是直接归因于模型推理很慢。

以下伪代码是本文对主干的归纳，并非可编译的源码摘录：

```text
接收输入
发出回合开始事件
完成本回合所需的准备
进入推进过程
    准备本次模型输入和工具表面
    请求模型并处理流式输出
    执行被接受的工具调用
    收集工具结果与新到输入
    判断是否需要继续
    必要时处理上下文窗口
    满足停止条件后进入收尾
普通任务检查是否还有待处理输入
```

“必要时”很重要。
不是每一轮都会调用工具，也不是每次调用工具都会触发压缩。
具体顺序和分支应以固定提交的实现为准。

## 模型返回的并不总是一段最终答案

在这个循环里，模型输出需要经过结构化处理。
工具调用项会进入工具路由，工具结果随后成为继续推进所需的信息。
普通助手消息则可能用于展示、记录或最终答复。
来源：[turn.rs 中的采样处理](https://github.com/openai/codex/blob/46d252f8bf8b09f4ef765bc72e40f02c229da3e6/codex-rs/core/src/session/turn.rs#L2628)、[ToolRouter::build_tool_call](https://github.com/openai/codex/blob/46d252f8bf8b09f4ef765bc72e40f02c229da3e6/codex-rs/core/src/tools/router.rs#L257)。

因此，屏幕上出现一句“我先检查测试”并不是可靠的结束标记。
它可能只是任务中的一段说明。
同样，工具已经执行完，也不意味着用户任务已经通过验收。
模型还可能需要读取结果、修正方案，或者解释失败原因。

为避免误读，观察记录至少分成三栏：

| 记录 | 能证明什么 | 不能证明什么 |
| --- | --- | --- |
| 助手文字 | 模型生成了这段内容 | 相应操作一定发生 |
| 工具结果 | 某个调用返回了结果 | 业务目标已经完成 |
| 回合终态 | 本轮推进已收尾 | 修改正确、测试覆盖充分 |

这是验证方法上的划分，不是对某种界面显示方式的要求。

## 停止条件比“没有工具调用”更复杂

`run_turn` 会收集模型是否需要后续工作，以及是否存在待处理输入。
该基线中，`needs_follow_up` 合并了 `model_needs_follow_up` 与 `has_pending_input`。
停止附近还会进入 stop hooks 的处理。
来源：[采样后的继续判断](https://github.com/openai/codex/blob/46d252f8bf8b09f4ef765bc72e40f02c229da3e6/codex-rs/core/src/session/turn.rs#L581)。

这说明一个常见的简化模型不够准确：
“最后一次输出没有工具调用，所以这一轮必然立即结束。”
如果还有新输入、收尾钩子或其他需要处理的状态，实际路径可能继续。
反过来，发生终止错误后，也不能靠重复推进同一输入来假装任务仍在正常运行。
普通任务入口对终止错误有单独判断。

研究这段代码时，值得逐个追踪以下问题：

1. 继续标志由谁设置，何时重置？
2. 新输入什么时候被视为当前回合的待处理工作？
3. 工具失败是转成可反馈信息，还是成为终止错误？
4. 取消信号传到了模型请求、工具等待还是两者？
5. 收尾逻辑有没有能力要求再推进一步？

这些问题比记录“用了几轮”更接近故障原因。
轮数只是结果，状态变化才解释原因。

## 用一个小任务验证你的理解

准备一个不含真实业务数据的小仓库。
放一个文本文件，再要求 Codex 读取其中一个固定标记并返回它。
先让模型回答纯文本，再要求它必须读取文件，两种任务分别记录。

建议保存下面这些字段：

```json
{
  "case": "read-marker",
  "cli_version": "实际测得的版本",
  "source_commit": "若做源码比对则填写提交",
  "thread_id": "从事件中提取",
  "turn_id": "从当前协议中提取",
  "tool_observed": null,
  "terminal_status": null,
  "marker_matches": null
}
```

这里的 `null` 表示尚未执行和判定。
不能在没有事件证据时预填成功，也不能假设每个输出格式都有相同的字段名。
若使用 `codex exec --json`，应按它自己的事件结构提取数据。
OpenAI 官方说明该模式输出 JSONL 事件，适合脚本消费；它的事件结构不应直接当成 app-server 消息。
来源：[Non-interactive mode](https://developers.openai.com/codex/noninteractive)，核对日期 2026-10-20；页面未据以确认独立修订日期。

## 循环异常时，先找最后一个已完成阶段

| 现象 | 下一步检查 |
| --- | --- |
| 开始事件后没有可见输出 | 准备阶段、连接与后续错误 |
| 反复调用同一个工具 | 参数是否变化、返回值是否有效 |
| 工具已返回但一直继续 | 待处理输入、继续标志与收尾条件 |
| 停止后还有后台进程 | 工具生命周期与进程退出状态 |
| 回合完成但结果不对 | 验收条件、测试与实际文件差异 |

这些是排查方向，不是从界面现象直接得出的根因。
例如连续调用同一个命令，既可能是合理重试，也可能是输入没有提供新信息。
要区分它们，必须同时查看参数、输出和下一步决策。

公开源码能解释 Codex 怎样组织一次任务，却不能证明某个桌面版本、某个账号环境一定走了同一条路径。
对于自己的故障，最有用的证据仍是版本、事件和实际副作用。

读懂 Agent 循环后，你可以把“它为什么还没停”改写成一个具体问题：哪一项状态仍要求继续，或者哪个阶段尚未完成。
这时，逆向分析才开始变成可以复核的工程判断。
