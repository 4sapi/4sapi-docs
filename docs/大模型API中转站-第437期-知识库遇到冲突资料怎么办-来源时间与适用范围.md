# 知识库遇到冲突资料怎么办：来源、时间与适用范围

同一个主题收进第二篇、第三篇资料后，个人知识库迟早会出现冲突：一份文档说功能已经开放，另一份仍写内测；旧笔记适用于某个版本，新文章却把结论写成普遍规则；两位作者使用同一个词，定义并不相同。如果 Agent 为了生成“完整答案”把这些内容合成一句话，知识库看起来更整齐，证据却被抹平了。

本文给出一套可执行的冲突处理方法。目标不是让 Agent 自动裁决谁对，而是保留每种说法的来源、时间、适用范围和确认状态，让后续查询能够说明当前依据，也能回到原文复核。

## 一、先判断是不是真的冲突

两句话不同，不一定互相否定。处理前先检查五个维度：

| 维度 | 需要核对的问题 | 常见情况 |
| --- | --- | --- |
| 时间 | 两条资料的发布日期和生效时间是否不同？ | 产品更新前后的说明 |
| 版本 | 是否针对不同软件、模型或文档版本？ | 旧版本不支持，新版本支持 |
| 定义 | 关键词是否采用同一个定义？ | “本地”分别指本机与内网 |
| 范围 | 用户、地区、套餐、权限或场景是否不同？ | 管理员可用，普通用户不可用 |
| 证据 | 是原始记录、官方说明、转述还是作者判断？ | 一手文档与个人体验并存 |

只有主体、条件和时间一致，结论又互相排斥时，才能暂时标记为直接冲突。条件不同的内容更适合写成分支，而不是强行选择一个答案。

## 二、来源页先保留每份资料自己的说法

每份 Raw 资料都应该有独立来源摘要。来源页只记录这份资料说了什么，不提前替整个知识库给出统一结论。

```markdown
---
title: "资料标题"
type: source
source_file: "[[raw/articles/sample-article]]"
published: "待核实"
ingested: "2026-08-10"
---

## 摘要

## 关键结论
- 结论：
- 原文位置：
- 原文条件：

## 涉及页面

## 信息缺口

## 与现有知识的差异
```

日期和文件名是格式示例，实际页面必须填写真实值。资料没有发布日期时写“待核实”，不能用入库日期代替发布日期。

来源页分开以后，即使主题页以后更新，原资料的立场和上下文仍然保留。

## 三、主题页用“结论 + 条件”记录差异

主题页不要只有一段最终摘要。遇到不同说法时，可以增加一个“观点与适用范围”区域：

```markdown
## 当前可用结论

- 结论：
- 适用条件：
- 依据：
- 确认状态：已确认 / 待核实 / 已过期
- 最后复核：

## 观点与适用范围

### 说法 A
- 内容：
- 来源：
- 时间：
- 版本：
- 适用范围：
- 证据类型：

### 说法 B
- 内容：
- 来源：
- 时间：
- 版本：
- 适用范围：
- 证据类型：

## 尚未解决的问题

## 复核负责人
```

“当前可用结论”可以为空。证据不足时保留分歧，比生成一个没有条件的折中句更可靠。

## 四、让 Agent 按七步处理冲突

可以把下面的流程写进知识库维护规则：

1. 处理新资料前搜索相关来源页、概念页和主题页。
2. 提取新资料的结论，同时保留时间、版本和适用范围。
3. 与现有结论逐项比较，不只比较关键词相似度。
4. 条件不同的内容拆成适用范围分支。
5. 条件相同但结论相反时，同时保留两种说法并标记冲突。
6. 只有出现足够证据和有权确认时，才更新“当前可用结论”。
7. 在 `log.md` 记录冲突来源、受影响页面和待人工确认项。

对应的任务提示可以这样写：

```text
请读取新增资料，并在更新 Wiki 前检查相关页面中的现有结论。

比较时分别核对主体、时间、版本、定义、适用范围和证据类型。条件不同的内容分别保留；条件相同但结论相反时，建立冲突记录，不要合并成折中结论，也不要直接覆盖旧内容。

只有资料能够支持且确认状态明确时，才更新“当前可用结论”。否则保留原状态，将问题、来源和需要谁确认写入待核实区域，并追加到 `log.md`。
```

## 五、把事实、推断和作者判断分开

很多表面冲突来自证据强度不同。一份资料记录了实际发布日期，另一篇文章只是预测“很快会发布”；一个测试记录说明某环境下运行成功，另一位作者据此判断“所有环境都支持”。这些内容不能放在同一层比较。

页面中可以给每条内容标明类型：

- **事实**：原始资料可以直接支持的状态、动作、日期或结果；
- **推断**：根据资料和条件得出的可能解释；
- **作者判断**：作者给出的取舍、建议或观点；
- **待核实**：当前缺少来源、条件或确认人的内容。

Agent 可以协助分类，但不能凭语气替资料提升证据等级。原文写“可能”，Wiki 不能改成“已经”；个人体验也不能自动变成所有用户都适用的产品结论。

## 六、查询时不要隐藏分歧

知识库存在冲突时，回答模板也要变化。查询结果至少交代四件事：

```text
当前能确认什么？
结论适用于什么时间、版本和范围？
还有哪些不同说法？
每种说法分别来自哪里？
```

例如，资料 A 对应旧版本，资料 B 对应新版本，回答应该明确按版本区分。如果两份资料时间和范围相同，却仍互相矛盾，就说明当前无法给出单一结论，并列出需要核实的原始来源。

“信息不足”也是有效结果。Agent 的任务是帮助用户定位证据与分歧，不是每次都生成确定答案。

## 七、用一组冲突样本做验收

在测试 Vault 中准备下面四组材料：

| 样本 | 预期处理 |
| --- | --- |
| 同一功能的旧版与新版说明 | 按版本拆分，不把旧结论删除 |
| 同一个词的两种定义 | 分别记录定义来源和使用场景 |
| 相同条件下的相反结论 | 标记直接冲突，进入人工复核 |
| 一条有来源、一条无来源 | 保留两条，但标明不同证据状态 |

每组材料入库后检查：Raw 是否保持不变，来源页是否各自独立，主题页是否保留条件，日志是否记录冲突，查询结果能否回到两份原文。

如果 Agent 生成了没有来源的折中结论、自动删除旧说法，或者用较新的入库时间替代资料时间，本次测试不通过。

## 八、什么时候可以关闭冲突

冲突不会因为页面写得更长而自动消失。关闭前需要说明：新增了什么证据，谁作出确认，旧说法为什么不再适用，以及它属于错误、过期还是适用范围不同。

即使已经得到当前结论，也不必删除旧记录。可以把旧说法标记为“已过期”或“仅适用于某版本”，并保留来源。这样后续遇到历史项目或旧文件时，知识库仍能解释当时为什么会出现不同答案。

自生长并不等于新资料不断覆盖旧资料。更可靠的增长方式，是让知识库逐渐看清每条结论从哪里来、在什么条件下成立、什么时候发生变化。来源、时间和适用范围被完整保留后，Agent 才能在查询时给出有边界的回答，人也能在关键分歧上作出真正的判断。

## 九、给每个冲突建立独立台账

冲突只写在主题页里，后续很容易被其他编辑淹没。可以建立 `wiki/conflicts/` 目录，为需要人工处理的冲突分配稳定 ID。

```markdown
---
title: "C-012 示例功能是否开放"
type: conflict
status: open
created: 2026-08-10
updated: 2026-08-10
owner: "待指定"
---

## 冲突问题

## 共同条件
- 主体：
- 时间范围：
- 版本：
- 用户或权限：

## 说法 A
- 结论：
- 来源：
- 原文位置：
- 证据类型：

## 说法 B
- 结论：
- 来源：
- 原文位置：
- 证据类型：

## 当前影响
- 影响哪些页面：
- 影响哪些查询或决定：

## 需要的证据

## 处理记录
```

日期和编号只是示例。冲突状态可以使用 `open`、`waiting_evidence`、`resolved` 和 `superseded`：

- `open`：已经确认存在分歧，尚未指定下一步证据；
- `waiting_evidence`：已明确需要什么资料或由谁确认；
- `resolved`：当前条件下已有可用结论，并保留处理依据；
- `superseded`：冲突所针对的版本或场景已经不再使用，但历史记录仍保留。

台账页面要双向链接到相关来源页和主题页。主题页只显示当前结论与冲突摘要，详细证据留在冲突页，避免每个主题页面都变成难以阅读的调查记录。

## 十、用一个版本冲突走完整个流程

假设知识库中已经有一份旧文档，写着某功能只对管理员开放。新加入的资料则写“团队成员都可以使用”。两句话看起来相反，但 Agent 不能马上用新资料覆盖旧结论。

### 第一步：分别保存来源

旧文档和新资料各自拥有来源页，记录标题、原始路径、发布日期、产品版本和原文位置。发布日期或版本缺失时明确写“待核实”。

### 第二步：检查比较条件

Agent 需要确认两份资料说的是不是同一个功能、同一种工作区、同一版本和同一用户角色。如果新资料针对测试版，旧资料针对稳定版，它们属于范围不同；如果版本确实发生更新，则属于时间变化。

### 第三步：建立冲突记录

条件仍不清楚时，创建冲突页，并把主题页的当前状态标成待核实。此时查询应该返回两种说法和缺失条件，不给出单一权限结论。

### 第四步：补充一手证据

查找能够说明当前版本与权限范围的原始资料，或者由对应系统 Owner 在实际环境中验证。个人转述可以提供线索，不能自动替代当前配置和正式说明。

### 第五步：更新当前结论

如果确认新版本已经向团队成员开放，主题页可以更新为：在指定版本和工作区条件下，团队成员可用；旧版本仍只允许管理员。旧来源不删除，而是标记它适用的历史范围。

### 第六步：记录决定

冲突页写明新增证据、确认人、处理日期和受影响页面，状态改为 `resolved`。`log.md` 追加本次修改，索引中的待核实入口同步更新。

整个过程的重点不是判定“新资料一定更对”。新资料也可能省略条件，旧资料也可能仍适用于某些环境。只有时间、版本和范围被确认后，“更新”才有明确含义。

## 十一、冲突页面也会过期

冲突解决以后，产品、制度和个人理解还会继续变化。知识库需要知道哪些结论应该重新检查。

可以在主题页和冲突页记录：最后复核时间、复核触发条件、当前 Owner。触发条件比固定日期更重要，例如：

- 软件版本发生变化；
- 官方规则或内部制度更新；
- 数据 Owner 或业务负责人更换；
- 查询中再次出现无法解释的例外；
- 新资料与当前结论使用了不同定义；
- 原始来源链接失效。

定期维护时，Agent 可以列出长期未复核、来源失效或 Owner 为空的冲突页，但是否重新调查由人决定。没有变化迹象的历史冲突不必为了“保持活跃”反复改写。

### 关闭不等于删除

已解决的冲突仍然解释了知识为什么发生变化。删除以后，用户只会看到当前结论，不知道旧笔记为何不同。可以把已关闭记录移到历史视图或通过状态过滤，但原始证据和处理记录应继续保留。

## 十二、批量处理冲突时避免伪精确评分

资料很多时，团队可能想让 Agent 给每个来源打一个统一可信度分数。分数看起来方便排序，却容易把来源类型、时间、适用范围和具体证据压成一个无法解释的数字。

更实用的做法是保留离散字段：

```text
来源类型：官方说明 / 系统记录 / 会议确认 / 个人文章 / 待核实
时间状态：当前 / 历史 / 未知
范围完整性：完整 / 部分缺失 / 未知
证据位置：可定位 / 只有转述 / 缺失
确认状态：已确认 / 待复核 / 已过期
```

这些标签同样需要由团队定义，不能把“官方”自动等同于适用于当前环境。它们的价值是帮助用户理解差异和筛选复核队列，而不是替人计算唯一答案。

当冲突数量增加时，可以按“影响当前工作”“缺少 Owner”“来源已失效”“等待外部证据”等条件排序。优先处理会影响实际决定的分歧，低影响的历史争议可以保留状态，不必强行收口。
