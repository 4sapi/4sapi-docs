# FDE 怎样把 AI Demo 变成可运行的业务流程

用几份帮助文档做知识库，再接一个模型 API，一天内就能演示“客服回复助手”：员工输入问题，系统检索资料并生成一段回答。真正准备上线时，麻烦才会集中出现。过期政策能不能被检索，模型把退款金额写错怎么办，谁可以查看客户订单，回复发出后如何追查，接口超时会不会卡住整个工单。

这些问题不是给提示词再加几句话就能解决。FDE 需要把演示拆成一条有数据边界、权限控制、质量评估、人工复核和异常恢复的业务流程。本文用一个假设的客服场景，给出从 Demo 到小流量生产的检查方法。

## 一、先定义业务结果，不要先换模型

假设一家软件公司希望减少客服整理回复的时间。第一版工具只负责起草，员工确认后才发送给客户。这个范围比“做一个智能客服”更容易控制，也更容易验证。

项目开始前，应把成功条件写成可观察事件：

```text
输入：一张已有分类和客户上下文的工单
处理：检索有效知识，生成带依据的回复草稿
输出：客服可以接受、修改或拒绝草稿
边界：系统不自动退款，不直接改变订单，不绕过人工发送
记录：保存知识版本、生成结果、人工动作和失败原因
```

业务指标也要和工具的职责一致。首轮灰度可以记录草稿被查看、接受、修改和拒绝的次数，以及人工从打开工单到完成回复所用的时间。不要在没有基线和样本的情况下承诺“效率提升多少”。

## 二、把生产准备拆成九个关口

### 1. 业务指标

先写清楚项目想改变哪个环节。如果目标是缩短首次响应时间，就要确认等待发生在资料查找、内容撰写还是内部审批。指标选错以后，系统即使被频繁调用，也可能没有解决瓶颈。

### 2. 数据来源与时效

知识库不应只是一个文档文件夹。每份资料需要有来源、负责人、生效时间、失效时间和适用产品。检索结果如果来自已废止政策，模型生成得再流畅也不能使用。

订单、合同和历史工单属于不同数据域。接入前要确认字段含义、更新频率和缺失值处理方式。无法取得实时数据时，应在界面上显示数据时间，而不是让用户误以为看到的是当前状态。

### 3. 身份与最小权限

模型调用不能代替业务权限。客服只能看到自己有权处理的客户资料，检索服务也应继承或重新校验这个边界。

至少要区分普通客服、主管和系统管理员。高风险信息可以在进入模型前脱敏；日志中不应保存完整密钥、会话凭据或不必要的客户数据。

### 4. 模型与 API 配置

把模型名称、API 地址、超时、重试次数和输出格式放进配置层，不要散落在多个业务文件中。开发、测试和生产使用不同令牌，并为令牌标记用途和额度边界。这样切换模型或排查请求时，不需要重新改动整个客服系统。

如果团队使用 OpenAI-compatible 网关统一测试入口，4SAPI 可以作为一个可替换的候选示例。其公开接入文档提供了令牌、模型名称和 URL 配置入口，但团队仍需按当前文档逐项核对模型名、路径、权限和调用日志，不能把兼容接口理解成所有参数都完全相同。[公开接入文档](https://4sapi.apifox.cn/8181987m0)用于核对这些配置入口。

选择哪一种接口不改变验收方式：发送一条固定测试请求，确认认证成功、模型名可识别、响应结构能被解析，并在脱敏日志中找到对应请求。

### 5. 固定评估集

上线前准备一组来自真实问题类型、经过脱敏的测试样本。至少覆盖：普通咨询、资料冲突、信息不足、越权请求、需要转人工和知识库没有答案。

每条样本写明预期行为，而不是只写标准答案。例如，信息不足时应该追问，越权请求应该拒绝，找不到有效依据时应该转人工。模型或提示词发生变化后，用同一组样本重跑，才能看见回归。

### 6. 人工复核

第一版既然只起草，就必须让客服清楚看到草稿、依据和风险提示，并能接受、修改或拒绝。按钮名称应对应真实动作，不能把“采纳建议”和“已经发送”混成同一个状态。

人工复核不是免责开关。系统仍要记录修改比例、拒绝原因和常见错误，用来判断是知识有问题、检索有问题，还是模型输出不适合当前任务。

### 7. 日志与成本归因

一次工单处理可能包含检索、重排、生成和重试。日志至少需要关联请求 ID、工单 ID、模型配置版本、知识版本、耗时、Token 用量、错误类别和人工动作。

不同环境和项目应使用可区分的令牌或调用标识。这样才能回答某次成本来自正常生成、超时重试还是测试脚本，也能在凭据泄露时只撤销受影响范围。

### 8. 重试、回滚与故障责任

只对适合重试的临时错误进行有限重试，并避免重复发送业务动作。接口连续失败时，客服界面应允许回到原有的手工流程，而不是一直显示加载状态。

回滚不只是切回旧模型，还包括关闭自动建议、恢复上一版提示词、撤销有问题的知识版本，以及通知当班负责人。每个动作都应有明确执行人。

### 9. 采用情况

系统上线后，要观察员工是否真的打开建议、在哪一步退出、为什么修改，以及是否重新回到旧工具。采用率低不一定是培训不足，也可能是页面遮挡了原始工单、依据不可信或等待时间过长。

FDE 的工作是找到具体阻力，再判断应该改流程、数据、界面还是模型，而不是把低使用率简单归因于用户不愿改变。

## 三、上线检查表要能指向回退动作

下面的表格适合小流量灰度前逐项确认。具体阈值应由团队根据业务风险和历史基线设定。

| 检查项 | 通过条件 | 失败信号 | 回退动作 |
| --- | --- | --- | --- |
| 知识时效 | 样本引用当前有效资料 | 引用已废止政策 | 下线对应知识版本 |
| 数据权限 | 测试账号只能读取授权工单 | 可查看其他团队客户数据 | 关闭入口并检查权限链路 |
| 评估回归 | 固定样本达到团队设定门槛 | 越权或无依据回答增加 | 恢复上一版配置 |
| 人工复核 | 草稿不能绕过确认直接发送 | 状态混乱或误发送 | 关闭发送集成，只保留草稿 |
| API 调用 | 固定请求可追踪且错误可识别 | 超时无提示、重复重试 | 切回手工流程并限制重试 |
| 日志 | 请求与工单、版本和人工动作可关联 | 无法定位一次错误 | 暂停扩量，补齐追踪字段 |
| 回滚 | 值班人员能在演练中完成恢复 | 依赖临时改代码 | 保持当前流量，不继续扩展 |

## 四、用七天灰度记录代替“感觉不错”

首轮灰度不必覆盖全部客服。选择一个风险可控的问题类别和少量用户，每天保留同样的记录字段：

```text
日期：
参与用户数：
进入工具的工单数：
草稿接受 / 修改 / 拒绝数：
转人工或回到旧流程的次数：
主要失败类别：
涉及的知识版本和模型配置：
当日改动：
是否触发回退：
待确认问题：
```

七天只是记录模板的示例周期，不是通用的上线结论。工单量很低、业务周期较长或风险较高时，需要延长观察，并由业务、安全和工程负责人共同决定是否扩量。

## 五、FDE 怎样判断项目可以继续扩量

扩量前不只看成功请求比例，还要同时回答四个问题：

1. 系统是否在正确的用户和权限范围内运行？
2. 固定评估集是否能稳定复现关键风险？
3. 失败时能否回到原流程，并找到责任人？
4. 用户是否真正采用，修改和拒绝是否有可解释原因？

任何一项答案不清楚，都比“模型回答看起来不错”更值得优先处理。生产系统的可靠性来自可观察、可限制和可恢复，而不是来自一次成功演示。

## 结论

把 AI Demo 变成业务流程，需要补齐业务指标、数据时效、身份权限、接口配置、评估集、人工复核、日志归因、异常回退和采用观察。它们共同决定系统能否在真实环境中承担责任。

这套方法适合从辅助起草、内部查询等低风险任务开始。涉及自动退款、订单变更或其他高风险动作时，还需要更严格的授权、审批、审计和恢复设计，不能直接沿用演示阶段的边界。
