# 怎么复核智能体安全审计报告：confirmed 结论的逐条检查方法

智能体交来一份安全审计报告，里面有几条标着 confirmed 的漏洞。能不能直接开工单修？不能。报告写得有条有理，不等于每一条都对。需要一套固定的复核动作，花的时间要比重新审计少得多。

本文以 cloudflare/security-audit-skill 产出的 findings.json 为例，回答一个问题：拿到这类报告后，每条记录应该怎么检查，校验脚本帮你证明了什么，又没有证明什么。方法对其他格式类似的报告也适用。文章只讨论防御性的复核，不涉及利用方法。

信息截止日期为 2026-10-30。文中关于技能的描述来自仓库文档，我没有用它审计过任何代码库，所以没有真实报告可供演示，示例都是结构说明。

## 一、先分清三类记录

findings.json 里每条记录的结论只能是三种之一。依据是仓库的
[VALIDATION-AND-REPORTING.md](https://github.com/cloudflare/security-audit-skill/blob/main/skills/security-audit/VALIDATION-AND-REPORTING.md)（检索于 2026-10-30）：

| 结论 | 它声称什么 | 你的默认态度 |
| --- | --- | --- |
| confirmed | 完整的调用路径加一个有界的、实际观察到的结果 | 当作"待复核的主张"，不是定论 |
| needs_validation | 源码里有边界问题的线索，决定性事实在源码之外 | 当作线索，交给能观察部署环境的人 |
| rejected | 候选被证伪 | 通常不用看，除非你怀疑被误杀 |

规则要求 confirmed 带有根因、预期行为、触发条件、执行方式、观察结果、修复建议、严重度和置信度。needs_validation 不得带严重度。rejected 不得带严重度和修复建议。

如果报告里一条 needs_validation 同时写了严重度，或者 confirmed 缺少观察结果，说明记录本身就不合规，这是第一个信号。

## 二、校验脚本能证明什么

技能带了两个零依赖的 Node 脚本：

| 脚本 | 校验对象 | 用法 |
| --- | --- | --- |
| validate-findings.cjs | findings.json | `node validate-findings.cjs <findings.json>` |
| validate-coverage-ledger.cjs | coverage-ledger.json | `node validate-coverage-ledger.cjs <coverage-ledger.json>` |

文档对它们的定位写得很清楚：**校验成功只证明格式和账本一致性**。

具体来说，脚本能发现这些问题：

- 字段缺失、多余字段（schema 使用 additionalProperties: false）。
- 不同结论使用了不该用的字段，例如 confirmed 里出现 blockers。
- 调用路径的结构：多步路径要以 entrypoint 开头、以 sink 结尾，中间只能是 propagation。
- 整体严重度是否超过已记录的影响。
- 输入过大：超过 5 MiB、顶层记录超过 1000 条、嵌套超过 64 层都会被拒绝；错误信息最多输出 100 条。

脚本不能发现：

- 引用的文件行号是否真的存在这行代码。
- 调用路径是否真的可达。
- "观察结果"是否真的被观察过。
- 严重度判断是否合理（只查"不超过影响"这个内部一致性）。
- 修复建议是否有效或会不会引入新问题。

所以脚本通过，是复核的起点，不是终点。

## 三、逐条复核 confirmed 的七个动作

这些动作对应文档里阶段 5 要求验证者做的事，只是换成由人来做。

### 1. 核对每个引用位置

对记录里的每个仓库相对路径和行号，打开代码确认：

- 文件存在，行号在范围内。
- 那一行确实在做描述所说的事。
- 报告引用的版本与你现在审计的提交一致。run-metadata.json 里应有 source_ref，对不上就先停下。

这一步成本低，能挡住引用不存在的位置。

### 2. 核对入口是不是真入口

文档要求调用路径的第一项是"真实的低信任入口"。问自己：

- 这个入口能被谁触达？是公网用户、已认证用户，还是只有内部服务能调用？
- 如果只有高权限主体才能到达，它是不是跨边界？

文档里的反模式明确写了"把预期中的同一主体权限或只影响自己的效果当作跨边界结果"。

### 3. 找路径上的现有控制

报告会写出缺失的检查，但你要独立找一遍路径上的校验、鉴权、规范化和框架层保护。文档要求验证者重建源码里可见的校验、鉴权、规范化和包含类控制。如果你能在路径上找到报告没提的有效控制，这条记录应该降级或拒绝。

### 4. 核对条件

confirmed 记录要写触发条件。逐条看：这些条件在你的实际部署中成立吗？例如某个配置项默认值、某个特性开关、某个代理是否存在。报告基于源码，可能不知道你的部署。

### 5. 在你自己的沙箱里复现最小结果

记录里有目标原生接口形式的执行方式和观察结果。复现时遵守同样的边界：

- 只在隔离环境里运行，无外部网络。
- 使用虚构的主体和资源，不用真实数据。
- 做到观察到最小结果就停。

不要因为"想确认影响有多大"而扩大测试。也不要对线上环境复现。

### 6. 核对严重度

文档给了严重度锚点：

| 级别 | 文档里的锚点 |
| --- | --- |
| critical | 未认证者获得代码执行、完整数据存储访问或任意账号接管 |
| high | 完全击败明确的安全控制，且有实际后果，例如认证绕过、跨租户读写 |
| medium | 真实的边界违例，但影响范围有限或前提少见 |
| low | 泄露非机密内部信息，或需要持续投入才有微小收益 |
| informational | 已确认但影响极小，主要作为更大发现的前提 |

文档里区分 high 与 medium 的判断是：已证明的结果是完全击败了一项明确控制，还是只是削弱了它。你说不出具体损害，严重度就应该比感觉的低。

### 7. 评估修复建议

文档要求修复建议指向"在最后一个可信决策点强制执行不变量的最小源码改动"，并附回归测试。检查：

- 修复是不是真的在强制不变量，而不是把信任挪到另一个地方。
- 有没有回归用例，能在修复前失败、修复后通过。
- 会不会破坏现有行为。

## 四、复核 needs_validation

这类记录的价值在于它提出了一个具体问题，但答案不在代码里。检查：

1. **阻塞项是否真的无法在本地回答。** 如果你用一个小测试夹具就能解决，那它本不该停在这里。
2. **验证计划是否可执行。** 文档要求计划分为本地和部署两类：本地用有界夹具；部署侧是请所有者观察某个配置、身份、路由、策略或运行时事实，**不向线上发送审计流量**。
3. **是否点明了边界和可能的具体结果。** 泛泛的"这里可能有问题"不合格。
4. **不要因为它没有严重度就忽略它。** 它缺的是证据，不是重要性。

处理方式：把部署侧的验证计划转给能看配置的人，答复回来后再决定升级为 confirmed 还是拒绝。

## 五、rejected 记录什么时候值得看

默认不需要看。但这些情形值得抽查：

- 报告里 rejected 的数量远多于 confirmed。
- rejected 的原因是"假设的前提不可能成立"，而你知道前提在你的环境里成立。
- 被拒绝的候选涉及你特别在意的资产。

文档说明，rejected 保留是为了让后续运行不重复无依据的主张，并且"只抑制未变化的同一失败主张"。如果代码或部署变了，同一个候选应该重新进入。

## 六、覆盖账本：报告没说的部分

报告只告诉你找到了什么。账本告诉你看了什么。

按文档，账本里每个单元有状态（covered、candidate、blocked、deferred、out_of_scope 等）、复核过的路径和本地检查记录。复核时重点看：

| 看什么 | 为什么 |
| --- | --- |
| 运行配置（quick、standard、deep）和范围 | quick 或限定范围的运行必须自述为局部覆盖 |
| deferred 和 blocked 的单元 | 这些是没看或没看完的部分 |
| out_of_scope | 文档要求范围外的内容标 out_of_scope，不能标 covered |
| run_status | 是 complete 还是 incomplete，以及 incomplete_reason |
| 预算 | 预算耗尽时会在账本里留下未验证的候选，它们不会出现在 findings.json |

关键的一句：**没有发现，不等于没有问题**。文档自己也规定，即使是干净的运行，也只能报告覆盖了哪些、没覆盖哪些，不能暗示已穷尽目标。

## 七、一份可以直接用的复核清单

```text
□ source_ref 与当前审计的提交一致
□ run_status 为 complete；若为 incomplete，已读 incomplete_reason
□ 两个校验脚本都通过（只代表格式合格）
□ 每条 confirmed：引用行号逐一打开核对过
□ 每条 confirmed：入口确实是低信任主体可达
□ 每条 confirmed：路径上没有报告遗漏的有效控制
□ 每条 confirmed：触发条件在我们的部署中成立
□ 每条 confirmed：在隔离环境用虚构数据复现了最小结果
□ 每条 confirmed：能用一句话说出具体损害；说不出则降级
□ 每条 confirmed：修复建议在最后可信决策点强制不变量，有回归用例
□ 每条 needs_validation：部署侧验证计划已转给所有者，未向线上发流量
□ 已读覆盖账本里的 deferred、blocked、out_of_scope
□ 报告没有被当作"其余部分安全"的证明
```

## 八、两个常见误区

**误区一：多个智能体都同意，就是真的。** 文档的设计是验证者没有搜索过这个候选，目的就是引入独立性。但独立性来自流程，不来自数量。如果验证者读了搜索者的结论再点头，独立性就弱了。文档允许验证者读搜索者的材料，同时要求它重读每个被引用的当前源码位置，并独立运行能安全复现的决定性检查。

**误区二：项目说多跑几次更全，所以跑得越多越安全。** README 说，在项目自己的测试里，单次运行找到的漏洞大约是多次运行合计的一半。这是项目自述，仓库里没有给出数据来源。能确定的只有设计假设：单次运行不会穷尽目标。多次运行叠加覆盖，但每次的新记录仍需要复核。

## 九、限制与结论

复核智能体审计报告，核心是把"记录看起来合规"转换成"每个主张都被一个独立的人或脚本重新确认过"。校验脚本解决格式，其余要靠人：行号、入口、控制、条件、复现、严重度、修复。

本文的限制：没有拿到一份真实的 findings.json，所以清单没有在真实报告上试过；对脚本能发现的问题，我列的是文档和脚本入口部分显示的内容，没有逐条读完 800 行的校验逻辑；严重度锚点引自文档，是该项目自己的标准，你的组织可能有不同的分级。

下一步建议：用一个你熟悉的仓库跑一次 quick 配置，拿到报告后按第七节清单逐条过一遍，记录每条花了多长时间、有几条在哪一步被推翻。这组数字比任何自述都更能告诉你，这类报告在你的环境里可以信到什么程度。
