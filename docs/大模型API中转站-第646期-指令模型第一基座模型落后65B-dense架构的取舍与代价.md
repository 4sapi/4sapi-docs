# 指令模型第一、基座模型落后：65B dense 架构的取舍与代价

一份模型卡里出现两个相反的结论，读的人很容易只记住对自己有利的那个。Ripple-65B Preview 的模型卡就是这种：**指令模型在 TerminalBench 2.1 上以 80.52 排第一，而同一家的基座模型在传统评测上落后于更大的 MoE 模型**——MMLU 83.7 对 89.1，HumanEval 70.9 对 83.8。

这不是数据打架，而是两个不同的问题：一个是"训练配方把模型调成了什么样"，另一个是"架构与算力换来了什么"。

本文只讲第二层：这套 65B dense 架构为什么这么设计、每处改动想解决什么、以及它的代价在哪。分数排序与口径问题在另一篇里讲。所有数字来自[官方发布页](https://www.ricursive.com/ripple)与[模型卡](https://huggingface.co/ricursiveAI/Ripple-65B-Preview)（检索日期 2026-11-06），我没有下载权重。

## 一、先摆出两张表的反差

同一个模型卡里，两张对照表的结论方向不同：

| 项目 | 指令模型表 | 基座模型表 |
| --- | --- | --- |
| 对照对象 | 美国开放权重前沿模型（500B 到 975B） | 几家开放权重基座（225B 到 671B） |
| 它在 agentic coding 上的位置 | TerminalBench 2.1 第一（80.52） | 未在基座表里评 |
| 它在 MMLU 上的位置 | 89.6，低于 Muse 92.6、Beam 92.4、Nemotron 92.0、Inkling 91.3 | 83.7，低于 Nemotron 89.1 与 DeepSeek V4 Flash 88.7 |
| 它在 HumanEval 上的位置 | 未列 | 70.9，低于 Nemotron 83.8，也低于只有 225B 的 Laguna M.1（83.4） |
| 它有优势的地方 | Terminal-Bench 第一、SWE-bench Pro v2.0 Hard 第一；τ³-bench banking 31.27 仅次于 Beam 的 36.1 | WinoGrande 83.4 为表内最高 |

一句话概括：**指令模型在"动手做事"这类任务上强，基座模型在"知道得多"这类任务上弱。**

## 二、模型卡自己的解释

模型卡没有回避这个反差，给的解释是训练数据上的取舍：

- 预训练阶段"保持数据干净、合成数据最少"，重点是高质量自然数据，而不是针对评测做优化。
- 大量合成数据被放到中期训练阶段，这样"可以在不阻塞预训练的情况下快速迭代合成数据配方"。
- 对 Nemotron 3 Ultra 的解读是：它在传统预训练评测上很强，可能因为大量使用任务种子化的合成数据，但"这部分表现没有迁移到现代 agentic 任务"。

这是厂商的解读，我无法独立验证。但它给出一个可检验的预测：**如果一个模型的基座分很高而 agentic 分不高，去看它预训练里是否掺了大量面向评测的合成数据。** 反过来，基座分不高而 agentic 分高的模型，其世界知识可能不如同尺寸对手。

对选型的含义很直接：**你要的是"知道得多"还是"做得多"？** 这两件事在这份卡里就不是同一个模型版本的强项。

## 三、为什么选 dense，不选 MoE

这是整套设计里最反潮流的一条：其他几家在同一张表里的模型都是 MoE，它选了 dense。发布页给的理由是降低基础设施复杂度：

| 原文理由 | 含义 |
| --- | --- |
| 精简预训练与后训练的基础设施复杂度 | 不用为专家路由、负载均衡、专家并行写专门逻辑 |
| 简单分片即可 | 不需要复杂的并行策略就能把训练跑起来 |
| 无自定义 kernel | 不必写硬件专用算子 |
| 无量化（BF16） | 训练全程保持高精度，省掉量化与精度对齐的调试 |
| MFU 维持 40% | 硬件利用率不靠特殊优化也能到这个水平 |

这五条合起来是一句工程判断：**用"每 token 计算更贵"换"实现更简单"。**

这份取舍的合理性取决于你的处境。对大厂，MoE 的推理成本优势值得投入工程复杂度；对一个小团队（模型卡说团队从 1 人扩到 5 人），dense 能让"从零训一个能用的模型"这件事变得可行。这也是它敢把 3200 万美元总研发成本写出来的底气之一。

代价也很明确：dense 65B 每个 token 都要动用全部 65B 参数。而表里那些 MoE 的激活参数只占总参数的 4% 到 10%（Inkling 41/975、Muse 42/816、Beam 23/501、Nemotron 55/550）。**所以"参数少"是对总参数而言；按每 token 计算量比，它并不便宜。**

## 四、thin-and-deep：具体改了什么

架构描述比一般发布稿具体，可以直接对照：

| 项 | 内容 |
| --- | --- |
| 形态 | thin-and-deep：d_model 5120（窄），80 层（深） |
| 结构谱系 | 从 Olmo 3 的 llama 类结构改为 Gemma 3N 类，理由是"提升大规模训练的稳定性" |
| 注意力头 | 过配（数量多于常规），为提升推理表现 |
| 混合比例 | 提高 SWA（滑窗注意力）与全局注意力层的比例，并缩小 SWA 窗口，用来抵消多头的成本 |
| 四处新增 | FFN activation clipping、gated attention、global NoPE、value residuals |

四处新增各自想解决什么，原文只给了名称与一句目的，没有消融实验。按公开信息能说的只有这些：

- **FFN activation clipping**：限制前馈层的激活幅度，通常用于训练稳定性。
- **gated attention**：给注意力输出加门控。原文只列了这个组件名，并把 v1.3 那一版称为 sigmoid gated attention；它与"过配注意力头"是不是配套设计，原文没有说，这是我的猜测。
- **global NoPE**：全局注意力层不做位置编码，只按内容匹配；配合 SWA 层承担局部位置信息。
- **value residuals**：值向量的残差连接，属于深层网络里缓解梯度与信息传递的手段。

这四条与"过配头 + 提高 SWA 比例"放在一起，看起来是同一套思路：**把局部交给滑窗、把全局交给少数不带位置编码的层**。至于门控是否用来"关掉多余的容量"，原文没写，只有组件名与"提升推理表现"这一句目的。 这与我在别的文章里拆过的小模型混合架构是同一类设计，只是这里的规模从 1.7B 放大到 65B。

## 五、16 倍与 55 倍：这是相对量，不是无条件效率

发布页与模型卡都提到计算效率（CE）的提升：

- 最终模型阶梯在**代码上**的 CE 相对 **Olmo 3 的 ladder** 提升 16 倍——原文这条带两个限定：**在 4B 模型规模上测的**，且写作"up to 16x"；
- 55 倍只见于模型卡（"up to 55x for the full hero run"），指最终全规模正式跑，发布页没有这个数。

这两句必须带上三个限定读：

1. **相对对象是 Olmo 3 的 ladder**，不是无条件的效率，也不是与其他模型的端到端对比。
2. **衡量口径是 dolma_stack 的交叉熵**，也就是"在代码数据上拟合得好不好"，不等于下游任务分数。
3. **16 倍与 55 倍的差别来自规模**——模型卡解释了：Olmo 3 基线的斜率更平，所以规模越大，优势越明显。

阶梯本身的过程也有信息量：v1.0 用 StepFun 的批大小与学习率缩放到 v1.6 加 value residuals，中间有一版（v1.4 的 2-stream mHC）"小规模有效、4B 规模无效"因此被否决。**这种"被否决的一版"比成功清单更能说明他们在做什么**：他们是在小规模上筛改动，再到大规模上复核。

## 六、训练阶段表说了什么

| 阶段 | Token | 步数 | 序列长度 | 批大小 |
| --- | --- | --- | --- | --- |
| 预训练 | 12T | 877,500 | 8K | 1408 → 3072 |
| 中期训练 | 200B | 8,000 | 64K | 384 |
| 长上下文 | 6.5B | 389 | 2M | 8 |
| SFT | 183B | 7,274 | 128K | 192 |
| 长上下文 SFT | 13.5B | 802 | 2M | 8 |
| RL | — | 700 | 128K | 2048 |

从这张表能读出三个判断：

1. **长上下文的成本很低**：6.5B token、389 步就到了 2M 序列。所以"支持 1M 上下文"这类能力，在今天的配方里主要是后期扩展的工程活，而不是重训。
2. **RL 的步数（700）与 SFT（7,274）差一个量级**，但 RL 的批大小是 2048。700 步乘批大小 2048，约等于 143 万，正好对上发布页说的"1.4M rollouts"——所以那个数是步数乘批大小算出来的。
3. **预训练序列只有 8K**，其余长度都在后期扩展。这意味着它的长上下文能力来自扩展阶段，而不是原生长序列训练。

第三条对读者有用：**想评估某个模型的长上下文能力，看它预训练序列长度，比看宣称的最大上下文更有信息量。**

## 七、部署形态：四种产物与一个推断

| 形态 | 用途（原文口径） |
| --- | --- |
| BF16 指令模型 | 本仓库；模型卡称所有模型都在 BF16 全精度下评测 |
| NVFP4 指令模型 | 面向本地开发，配 colab |
| BF16 基座 | 仅预训练检查点，无中期训练与合成 QA |
| DFlash2 | 卡页头部列出的第四个仓库（4B 级投机解码草稿模型，Apache-2.0），本文未展开 |

发布页与模型卡都说它可在 NVIDIA DGX Spark 这类硬件上运行；而 2×B200、batch=8、未量化、无自定义 kernel 时达 250 tok/s 这一条**只在模型卡**里。

这里要加一个推断，并标明是推断：**65B 的 BF16 权重大约 130GB**（65B × 2 字节），桌面级设备跑得动的是 NVFP4 版本，不是 BF16 版。模型卡没有给显存数字，这个换算是按参数量推的。

## 八、这套取舍的边界

| 取舍 | 好处 | 代价 |
| --- | --- | --- |
| dense 而非 MoE | 实现简单、无自定义 kernel、无量化 | 每 token 全参数激活，吞吐与推理成本高于同分 MoE |
| 预训练保持干净 | 基座可复用，不绑死评测 | 基座分数不亮眼，世界知识弱于大模型 |
| 合成数据放中期 | 迭代快、不阻塞预训练 | 后训练占比高，指令版与基座版能力差异大 |
| thin-and-deep | 参数量小、单卡/桌面可跑 | 深层窄模型的并行效率与通信开销要自己调 |
| 阶梯式验证 | 小规模先筛、大规模复核 | 只对"他们最优化过的代码能力"有 16 倍证据 |

最后一行是最需要警惕的：16 倍 CE 是在**代码**上测的。换成数学或长文档，这条结论没有依据。

## 九、限制与结论

这份架构说明的价值在于具体：d_model 5120、80 层、四个新增组件、训练阶段表、MFU 40%、无自定义 kernel——这些都能在公开页面核对，也都能被复现或反驳。

而它的边界同样具体：dense 的每 token 计算量不低，基座的世界知识不是强项，长上下文靠后期扩展，16 倍效率只在代码口径上有证据。

本文的限制：没有下载权重、没有推理；所有架构描述与效率数字都来自发布页与模型卡，属厂商自述；四处新增组件的作用是我按通行做法解释的，原文没有给消融；BF16 显存是推算；MFU 40% 与 250 tok/s 未复现。

下一步建议：如果你要评估这套配方能否迁移到自己的领域，先看两件事——你的领域是否也在"代码/工具调用"这类结构化输出上，以及你的部署侧是否承受得住 dense 65B 的每 token 开销。两点都成立，再谈复现。
