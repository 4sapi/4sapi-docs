# 教程、观点文和复盘为什么不能共用一套文风

同一个作者写出来的文章，语气可以保持相近，组织方式却不应该完全相同。教程需要让读者在有限条件下复现结果；观点文需要让判断站在证据上；案例复盘要还原当时的选择、失败和变化。如果三类文章都套用“提出问题、列出三点、总结价值”的模板，教程会缺步骤，观点会像口号，复盘则会把事后结论伪装成当时早已知道的答案。

第 372 期已经讨论过个人风格档案，但风格档案只解决作者层的问题。本文继续往下拆，把共享作者规则与文体规则分开，给教程、观点文和案例复盘各做一份输入合同、段落推进和验收标准。这样模型先判断“这是什么文章”，再决定“它应该怎么写”。

## 一、共享作者层与文体层

写作专家系统可以分成两层。共享作者层保存事实边界、常用语气、价值判断、隐私规则和不愿出现的表达；文体层保存文章类型自己的任务、材料和结构。两层不能混为一份万能提示词。

| 层级 | 管什么 | 不应该管什么 |
| --- | --- | --- |
| 作者层 | 谁可以用第一人称、事实边界、基本语气 | 教程必须有几步、观点文如何反驳 |
| 文体层 | 读者要完成什么、证据如何组织、结尾交付什么 | 作者真实经历和永久禁词 |
| 文章任务层 | 本次主题、受众、材料、范围和成功标准 | 所有文章长期有效的风格规则 |

模型收到任务后，先做文体路由：读者要照着操作，是教程；读者要理解一个判断，是观点文；读者要从过程和决策中学习，是复盘。无法判断时，提出一个澄清问题或输出两种结构草案，不要默默选择最熟悉的模板。

## 二、教程的规则：让读者能复现

教程不是把知识讲得完整，而是让读者在明确前置条件下完成一个动作。它的规则重点是输入、步骤、结果和风险。

```markdown
## tutorial-rule

- reader_problem: 读者在什么环境下卡住
- prerequisites: 版本、权限、输入和依赖
- steps: 每一步的动作、命令或配置
- success_signal: 读者看见什么才算成功
- failure_path: 出现什么错误，如何定位和回退
- evidence: 哪些行为来自官方文档或实际验证
- ending_contract: 总结适用范围、限制和下一次实验
```

教程的段落通常先给动作，再解释原因。每个步骤都要有可观察的成功信号，不能只写“完成配置后即可使用”。如果一个步骤会修改外部系统、删除文件或产生费用，必须写清授权和回滚条件。

教程不应该为了“像真人”而故意省略关键前置条件，也不应该把一次成功的演示写成任何环境都能复现。适当的限定词不是 AI 味，而是技术诚实。验证教程时，让没有参与写作的人只看正文执行一次，记录他在哪一步需要猜测；猜测点就是规则或说明的缺口。

## 三、观点文的规则：让判断站得住

观点文的交付物不是一串步骤，而是一个可争论、可核对的判断。它可以有鲜明立场，但必须把事实、推理和价值选择分开。

```markdown
## opinion-rule

- reader_problem: 读者对什么判断感到犹豫
- thesis: 用一句话写出可反驳的核心判断
- evidence: 支持判断的事实、样本和来源
- counter_case: 哪些情况会让判断失效
- reasoning: 事实如何连接到结论
- uncertainty: 哪些部分只能条件化表达
- ending_contract: 给出适用范围，不把判断改成号召
```

观点文的推进可以是“冲突现象、核心判断、证据、反例、条件化结论”。它不需要把所有材料都列完，但每个关键判断都要回答“依据是什么”和“如果条件变化会怎样”。反例不是为了装客观，而是帮助读者知道观点的边界。

常见失败是先有漂亮结论，再让模型寻找支持它的材料；或者把个人偏好写成行业事实。审稿时可以把文章中的句子标记为事实、推理、价值判断和未知。如果一段只有形容词和结论，没有事实或逻辑连接，它更像宣传文案，不像观点文章。

## 四、复盘文的规则：还原当时的决策

案例复盘最容易发生“事后聪明”。作者知道最终结果，模型又倾向于把过程整理成一条顺滑的成功路径，导致读者看不到当时有哪些选择、哪些信息缺失，以及为什么某个决定在当时仍然合理。

```markdown
## retrospective-rule

- case_scope: 项目、时间范围和脱敏边界
- initial_state: 当时知道的目标、资源和限制
- decision_points: 每个关键选择与可选方案
- evidence_at_time: 决策当时真正可见的材料
- failure_and_change: 发生了什么，哪条假设被推翻
- present_learning: 现在得到的经验，不倒灌到过去
- ending_contract: 给出可迁移原则和不可复制条件
```

复盘的段落适合按时间和决策点推进，而不是按“背景、方法、价值”整齐排列。每次写出“我们应该一开始就知道”时，都要回到当时材料检查：如果当时确实不知道，就改成“现在回看可以发现”。这不是削弱文章，而是保护复盘的可信度。

复盘也要说明哪些细节被脱敏、哪些结果无法公开、哪些经验只适用于特定团队。一个没有失败、没有分歧、没有代价的复盘，往往是事后重写的案例，而不是可学习的过程。

## 五、同一主题怎样路由到不同文体

假设主题是“给内容团队接入一个模型 API”。

写成教程，读者需要看到环境变量、请求示例、响应解析、日志和失败回滚；写成观点文，作者可以讨论统一入口是否值得，但必须比较维护责任、数据边界和成本归因；写成复盘，重点应该是团队当时为什么选择某条路线、遇到什么兼容问题、哪条假设后来被推翻。

| 读者目标 | 文体 | 主要材料 | 成功信号 |
| --- | --- | --- | --- |
| 想照着完成一次接入 | 教程 | 配置、命令、响应和错误 | 读者能在范围内复现 |
| 想判断是否值得采用 | 观点文 | 对照事实、反例和条件 | 读者能理解判断边界 |
| 想从真实过程吸取经验 | 复盘 | 时间线、决策、失败和改变 | 读者看懂为什么这样走 |

文体路由还要考虑材料是否足够。只有一份产品说明，没有亲历过程，就不应写成复盘；只有个人感受，没有可核对事实，就不应包装成行业判断；只有命令没有验证结果，就不应承诺完整教程。模型发现材料与文体不匹配时，应该报告缺口，而不是用通用段落补齐。

## 六、把文体路由做成任务入口

文体判断最好在生成正文前完成。任务入口可以要求作者填写一张简短表格：

```markdown
- reader_goal: 读者看完要完成什么
- input_material: 当前有哪些资料和证据
- first_person_scope: 哪些经历允许使用第一人称
- chosen_type: tutorial / opinion / retrospective
- forbidden_mix: 本文不承担哪些交付物
- success_signal: 用什么可见结果判断写成了
```

`reader_goal` 比“写一篇关于某主题的文章”更能帮助路由。如果答案是“让读者完成一次配置”，加载教程规则；如果答案是“判断一条路线是否值得采用”，加载观点规则；如果答案是“理解一次选择为什么失败”，加载复盘规则。`forbidden_mix` 用来阻止模型把不属于本文的内容塞进来，例如观点文不顺便写完整安装教程，复盘文不把缺失的当时资料补成操作步骤。

路由结果需要可见。可以在草稿头部写出选择的文体、选择理由、已加载规则和未满足材料。审稿完成后删除这些元信息，但保留在构建记录里。若模型把教程写成观点文，作者只需修改路由和对应规则，不必在整篇正文里反复要求“更像教程”。

## 七、混合文章要显式分区

真实文章有时确实需要混合文体。例如先给出可复现的 API 配置，再讨论这条路线的维护代价。问题不在于混合，而在于让同一段落同时承担互相冲突的职责。

可以显式划分两个区块：

```text
区块 A：操作教程
目标：完成最小验证
规则：前置条件、命令、成功信号、错误和回滚

区块 B：条件化观点
目标：帮助读者判断是否继续投入
规则：事实、成本责任、反例、未知和适用边界
```

区块 A 的结论是“这个实验是否跑通”，区块 B 的结论是“在什么条件下值得采用”。两者可以引用同一事实，但使用不同的句式和验收标准。发布前分别审查每个区块，再检查过渡句是否明确告诉读者从操作进入判断。不要把观点段落藏在步骤之间，也不要在结尾重新把两个交付物压成一句营销式总结。

## 八、混用规则的检测与修复

可以给初稿做一个“文体一致性审查”。第一步标记每段承担的职责：教程段落是否有动作和结果，观点段落是否有判断和依据，复盘段落是否有时间和决策。第二步检查段落之间是否跳错轨道，例如教程突然出现没有证据的价值判断，观点文突然堆出十条命令，复盘文把事后结论放进最初决策。

修复时只改文体层，不要为了补一个教程步骤而改写作者基本语气，也不要为了让观点更鲜明而越过作者事实边界。若任务本来需要混合文体，可以显式分区：前半篇是可复现教程，后半篇是条件化观点；每个区块使用自己的规则和验收标准。

## 九、适用边界与结论

教程、观点文和复盘可以共享作者的事实边界与基本语气，但不能共享全部结构。教程对动作、前置条件和成功信号负责；观点文对判断、证据、反例和不确定性负责；复盘对时间线、当时信息、决策和失败负责。

文体规则的价值不在于把文章分成三个固定模板，而在于让模型知道读者这次要带走什么。先做文体路由，再加载对应规则；材料不够时暴露缺口；完成后按文体的成功标准审稿。这样个人风格才能在不同文章里保持辨识度，而不是所有内容都套上同一件外衣。
