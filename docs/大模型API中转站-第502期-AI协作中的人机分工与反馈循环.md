# AI 协作中哪些事交给模型哪些事留给人

当 AI 能写代码、做 PPT、整理资料和操作工具时，很多人会问：哪些工作应该交给 AI？如果执行都被自动化了，人还需要练什么？

一个更实用的答案不是把任务简单分成“AI 做”与“人做”，而是把流程拆成三个位置：执行、判断和反馈。模型适合执行大量可描述、可验证的动作；人仍然需要定义问题、确认方向、判断质量，并把结果反馈回下一轮。

本文只解决一个问题：如何在 AI 协作中划分人和模型的责任。内容覆盖 Human in the Loop、项目上下文、旧项目维护、结果验收和个人反馈循环，适合产品、开发、运营和知识工作者。

## 一、先把任务拆成三层

任何 AI 工作流都可以先拆成：

```text
定义层：要解决什么问题，什么结果算完成。
执行层：具体查资料、写代码、生成文件和调用工具。
验收层：结果是否正确、安全、可用，是否值得继续。
```

模型可以参与三层，但责任重点不同。执行层最容易自动化；定义层和验收层需要更强的业务理解、经验和判断。

如果人只给一句“帮我做好”，模型会自行补充目标和标准，最后双方都可能误以为对方已经确认。先把完成条件写清楚，才能让 AI 执行得更稳定。

## 二、执行层为什么适合交给 AI

以下工作通常具有重复、可描述和可检查的特点：

```text
整理文件和表格。
生成初稿和备选方案。
按规则改写或转换格式。
运行测试并汇总日志。
从资料中提取字段。
根据明确步骤调用工具。
```

交给 AI 不等于放弃控制。要给出输入范围、禁止事项、输出格式和验证方式。模型执行得越多，越需要清楚的权限和停止条件。

## 三、定义层是人的第一项核心工作

定义问题时，至少要说明：

```text
目标用户是谁。
当前痛点是什么。
输入和输出分别是什么。
有哪些时间、预算和安全约束。
什么结果不可接受。
```

复杂任务还要补充替代方案、失败边界和需要人工确认的节点。定义层做得越清楚，模型越不需要猜测；猜测越少，返工越少。

这不是要求每个人都写长篇规格文档。一个短而具体的任务协议，往往比一段充满形容词的愿景更有用。

## 四、验收层是人的第二项核心工作

人不一定要逐行检查 AI 的每个中间动作，但必须能够判断最终结果是否满足目标。验收至少覆盖：

```text
功能是否完整。
事实、数字和引用是否正确。
性能是否满足实际使用。
安全边界是否被突破。
结果是否方便后续维护。
```

不同任务的验收标准不同。代码需要测试、Diff 和安全检查；文章需要事实、结构和语气复核；数据整理需要回到原始文件抽查；对外发送的内容还要确认责任和授权。

## 五、验证题给 Agent，判断题留给人

可以把任务分成两类问题：

```text
验证题：能通过规则、脚本或测试回答的问题。
判断题：需要业务目标、风险偏好和责任授权回答的问题。
```

例如“这个文件是否存在”“每条英文是否对应一条中文”“JSON 是否符合 Schema”，适合让 Agent 或程序验证。

“是否值得上线”“是否接受这个风险”“是否同意对外承诺”，则应留给人。把判断题伪装成验证题，会让模型替你承担不该承担的责任。

## 六、高风险动作保留确认点

以下动作通常不适合无确认执行：

```text
修改生产环境。
发送外部邮件或正式订单。
发布文章、代码或产品版本。
改变预算、合同和付款条件。
删除数据或覆盖原文件。
代表团队做出承诺。
```

可以让 AI 准备草稿、列出影响范围和生成回滚步骤，但最后确认应由有授权的人完成。确认点越清楚，团队越容易知道什么时候必须停下来。

## 七、旧项目为什么需要上下文文件

长生命周期项目最怕“每次都从头解释”。可以维护一个简短的项目上下文文件，记录：

```text
目录结构和模块职责。
启动、测试和部署命令。
兼容性限制。
不能随意修改的接口。
已知问题和回滚方式。
```

文件名可以按团队习惯选择，例如 `AGENTS.md` 或其他项目规则文件。重点不是名字，而是让 Agent 每次开始任务前读取同一份地图。

上下文文件也会过期。每次变更后同步更新，过时文档比没有文档更容易误导任务。把“文档是否同步”列入验收，而不是等项目出错以后再补。

## 八、老项目的最小安全工作流

维护测试不足的旧项目时，可以按以下顺序：

```text
先读取项目规则和当前状态。
只选择一个可回退的小任务。
让 Agent 先解释准备修改的范围。
保存修改前的基线和测试结果。
执行最小单元或集成测试。
检查 Diff、日志和副作用。
确认通过后再合并或部署。
```

不要因为模型能一次改很多文件，就把大任务一次性放进去。小步提交更容易定位错误，也方便在方向错时回退。

## 九、把反馈循环做成资产

每次协作都应该留下可复用的反馈：

```text
任务目标。
使用的输入和规则。
模型做了什么。
哪里失败或需要人工修改。
最终采用了什么方案。
下一次应该保留或改变什么。
```

这些记录可以变成项目规则、提示词、测试样例、Skill 或培训材料。没有记录的反馈只能改善一次对话，有记录的反馈才能改善下一次任务。

## 十、个人也可以建立反馈循环

个人学习和工作可以采用同样的结构：

```text
定义一个想完成的小目标。
让 AI 帮你做出第一版。
自己验收并指出具体问题。
把修正后的方法写下来。
下次用同类任务验证是否进步。
```

例如学习英语时，不只是让模型给答案，而是自己先说一遍，再让模型指出最重要的问题，重说后把高频错误记录下来。写作、编程和做图也可以用同样的循环。

## 十一、像训练模型一样训练自己

可以用一个类比理解个人进化：

```text
大量输入，建立基础知识。
通过实践，把知识连接到真实任务。
接受反馈，发现错误和盲点。
修改方法，形成新的习惯。
再次实践，验证变化是否有效。
```

模型会通过训练、微调和对齐变化，人也会通过输入、实践和反馈变化。关键是不要把旧经验当成永久规则。新工具出现后，重新检查原来的工作方式，可能会发现过去为了弥补能力不足而保留的步骤已经可以删除。

## 十二、品味和判断如何提升

很多结果没有简单的对错标准，例如文章、视觉设计、产品体验和视频。AI 可以提供备选方案，但无法自动替你决定哪一个真正适合目标。

提升判断力需要：

```text
持续接触高质量样本。
自己做出可比较的版本。
把好与坏的差异说具体。
记录用户或同事的真实反馈。
回看当时的判断是否成立。
```

“我觉得不好”还不够。要继续问：哪里影响了理解？哪里破坏了节奏？哪一个细节让人不愿继续使用？能说清楚，才可能把品味转成可复用的规则。

## 十三、如何判断代码结果是否可靠

非专业使用者不必理解每一行实现，但也不能完全不验收。可以先检查三件事：

```text
功能是否覆盖需求。
性能是否在真实环境可接受。
安全是否通过常识级和专业级检查。
```

功能可以用任务清单和测试验证；性能可以观察响应时间、CPU、内存和错误率；安全涉及弱密码、注入、越权和敏感数据暴露时，应请有经验的人复核。

实现细节是否优雅，可以在风险较低时再优化。对高风险系统，安全和可回滚优先级高于代码表面整洁。

## 十四、如何处理“AI 会不会替代我”的焦虑

把自己理解成“只负责执行的人”，确实容易被自动化冲击。可以把角色向更高一层移动：

```text
从写每一行代码，移动到拆分任务和定义验收。
从手工整理每份资料，移动到设计资料流和复核点。
从等待别人给需求，移动到发现问题并验证价值。
```

这不是逃避基础能力。没有足够的专业知识，人仍然无法定义好问题、识别坏结果或判断风险。执行减少以后，定义和验收反而需要刻意练习。

## 十五、常见误区

### 误区一：让 AI 替代责任人

模型可以建议和执行，但不能替你批准预算、合同、上线和对外承诺。

### 误区二：只看生成速度

生成快不等于交付快。审阅、修改、测试和回滚也要计入总时间。

### 误区三：把每个反馈都写成长文

先记录具体失败和修复方式，保持短小可执行，后续再沉淀成规则。

### 误区四：项目规则长期不更新

过期上下文会让 Agent 按错误地图行动。每次变更后同步维护。

## 十六、结论与限制

AI 协作的核心不是把所有事情交给模型，而是把执行、判断和反馈放到合适的位置。模型负责大量可描述、可验证的执行；人负责定义问题、确认方向、评估风险和验收结果。

当反馈被记录成项目规则、测试样例和工作方法，个人和团队就能形成持续循环。模型会升级，工具会变化，真正需要长期积累的是发现问题的能力、判断结果的品味和对责任边界的清楚认识。
