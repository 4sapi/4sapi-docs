# 让模型操作控制台：五级权限、确认模式与三道互不替代的闸门

让 agent 干活到一定阶段，会遇到一个具体问题：它要不要能操作你自己的管理界面？能点按钮、能填表、能触发部署，听起来省事；但它也意味着一个会看错、会自信编造的进程，拿到了你的操作权限。

ruflo 的控制台给了一个可参考的答案：给模型四个工具，配一个五级权限开关和一个确认模式开关，并且把"哪些动作需要人确认"做成按类别判定而不是按级别一刀切。

本文拆这套设计，重点在四个容易做错的地方。信息来自该项目的[架构决策记录 ADR-444](https://github.com/ruvnet/ruflo/blob/HEAD/v3/docs/adr/ADR-444-claude-controls-the-console.md)，检索日期为 2026-11-03。我没有安装或运行过它。

## 一、先看它长什么样

模型能调用的工具只有四个：

| 工具 | 作用 |
| --- | --- |
| console_state | 读当前页面、屏幕上可读的文字、可用条目清单、待确认项、上次结果、控制设置 |
| console_open | 跳到某个页面并打开面板，但不接管输入 |
| console_set | 填页面上的字段（目标、配置档、严谨度、研究问题与深度、成本预算等） |
| console_run | 执行某个面板条目，用的 id 与 `/ruflo run` 接受的一致 |

一个实现细节值得先记：工具返回**必须是字符串**，返回对象会被 schema 检查拒绝。这条约束看着琐碎，实际决定了后面所有的清洗逻辑——因为一旦返回值是自由文本，就必须考虑文本里可能夹带什么。

## 二、五级权限各放开什么

| 级别 | 模型可以做 |
| --- | --- |
| off | 什么都不做，工具根本不注册 |
| read | 读状态、开页面、执行只读条目 |
| write | 另外可以填字段、执行本地写入类条目 |
| manage | 另外可以执行触网类条目（更新、推送、拉取） |
| full | 另外可以花钱、删除、停止（部署、取消、重置） |

这个分法的关键在于**按后果分级，而不是按功能分级**。同样是"执行一个条目"，写本地文件和推送到远端是两回事，触发收费与删除数据又是两回事。

另一条值得抄的做法：级别不足或已暂停时，整条请求被拒绝并说明该去改哪个设置，**不会部分执行**。半成功在自动化里最难排查。

## 三、确认模式：auto 与 ask

| 模式 | 行为 |
| --- | --- |
| ask | 除只读外，每个动作都停在控制台的确认行，等人答复 |
| auto | 人选定级别后，Claude 在该级别内自动执行 |

这里有一段很值得注意的修订史，文档里写得很直白：

1. 最初默认是 off，且确认模式默认 ask。结果是使用者打开控制后，Claude 在每一次写入上"等一个根本没人被问到的 Yes"——文档的原话是这个确认提示压根没有弹出来，而不是使用者不愿点。
2. 于是把默认确认改成 auto。文档给的理由是：级别本身才是真正的限制，而级别默认是关的、只有人能提高——所以确认模式不必再重复设一道。
3. 后来又改成默认 read + ask（2026-10-05）：级别默认定为 read（只读、不动作），"等不到确认"的问题在默认级别下不会发生；同时把待确认项做成控制台里的横幅提示。注意中间存在过 `off + auto` 的窗口，级别默认此前从未是 read，所以这里不是"改回"而是"新定"。

这段修订说明一件事：**默认值不是安全策略的全部，级别与确认模式要一起设计。** 一个"安全但没人用"的默认值，实际效果等于没有控制。

## 四、第一个坑：auto 不等于全自动

这是这篇最该记住的一条。文档记录了一项后续修订：`auto` 不再适用于所有类别——

**类别为 network、spend、delete 的动作，即使在 auto 下也一律等人确认。** 模型的调用会被告知"正在等人确认"，并且不得重试。源码里这份名单还多一项：`ALWAYS_ASK = ['network', 'install', 'spend', 'delete']`。

同时保留了一条：auto 仍会让本地的 write 类动作无人值守执行。

换句话说，auto 的含义被收窄成"日常写入可以自动，出圈的动作必须有人"。

还有一处 ADR 没写、源码里却存在的区别：动作类别实际有六种（read、write、network、install、spend、delete），**`install` 是独立一类，需要 `full` 级别**，而不是像 ADR 那样把安装写在 manage 下面。如果你按 ADR 的表述以为 manage 就能装东西，实际会被拒。

### 那类别怎么定

按条目自身的信息推断：控制台的只读标记优先，其次看标签、命令与备注里的词。

| 词 | 判为 |
| --- | --- |
| 删除、停止、重置、清理、迁移 | delete |
| 计费轮次、"花钱" | spend |
| 安装、推送、拉取、更新、发布 | network |
| 其他非只读 | write |

备注里明确写"不花钱""不是收费""不跑 agent"之类的，不计入对应类别。

## 五、第二个坑：分类靠词推断，就会分错

同一个 ADR 里记录了它的实测过程与结果，这是我认为最值得读的一段。

他们做了一次覆盖 270 个面板条目的审计，发现三个条目被误判成普通写入：`stop the swarm`、`memory cleanup`、`memory migrate`。按上面的词表，"stop"和"cleanup""migrate"本该判成 delete。审计后已改判。

更值得注意的是审计的边界，文档自己写明：归类结果是 105 个 read、101 个 write、27 个 network、2 个 spend、4 个以上 delete，合计 239 项，**其余未逐项归类，而且没有测试锁定这个划分**。

这告诉你两件事：

1. 靠标签词推断权限类别，本质是启发式，必然有漏网的。
2. 没有测试钉住的分类，会随条目增加而漂移。

给自己的做法：如果你也按词推断，至少要有一个测试，穷举所有条目并断言每个条目的类别；新增条目时测试会失败，迫使你显式分类。

## 六、第三个坑：把权限收在环境变量里

文档还记录了一次收紧：环境变量 `RUFLO_CONSOLE_CONTROL` 现在**只能下调级别或强制 ask，不能上调**。

原因写得很清楚：项目设置里的 `env` 不能给模型比人保存的更多控制权。

这一条对所有"用配置控制权限"的系统都成立：只要存在一个能提权的入口，权限上限就是那个入口，而不是那个设置项。

## 七、第四个坑：回复里带出秘密

2026-10-08 的一次修订记录了一条可能把秘密带进模型的路径，值得逐条看。要说明的是：文档描述的是能力缺口（这些文本没过筛查就到了模型），没有声称发生过实际泄漏事件。

- 失败运行的 `stderr` 细节、"已在等待"的拒绝信息、引用模型输入内容的拒绝信息、未知条目 id、抛出的异常——**这些路径此前只做了转义，没有过秘密筛查**，于是 token 或邀请链接里的代码可能经由错误信息进入模型上下文。
- 被控制字符切开的邀请链接代码没有被遮住。
- 像 `v2.1.0-beta.3` 这样的版本号被误当成秘密遮住。

修法是统一到一个函数，四步：去转义序列；制表与换行变空格、其他控制与不可见字符直接删掉（防止把凭据切开绕过遮罩）；截断到上限；当原文、拼接后或截断后的形态像秘密时，整行隐去而不是部分遮罩。

这个坑的普适性很强：**你在"只读"路径上同样会漏。** 错误信息、拒绝信息、参数回显，都是外发通道。

## 八、三道闸门互不替代

把这套设计里的限制并列起来看，会发现它们是三层独立机制，任何一层都不能替代另一层：

| 层 | 机制 | 管什么 |
| --- | --- | --- |
| 1 | 控制台的五级权限与确认模式 | 模型能对控制台做什么（文档称这是 Claude Code 许可之外的"第二道"独立限制） |
| 2 | 每个动作自身的类别判定 | 这个动作是只读、写入、触网、花钱还是删除 |
| 3 | Claude Code 自身的权限体系 | 工具本身有没有被允许；未列入的工具会提示人 |

文档明说 Claude Code 自身的权限仍然生效，控制台级别只是"第二道"独立限制——所以严格说它排在平台许可之后，不是第一道。这个叠加是对的：**平台层不知道你的业务语义，你的业务层不知道平台的许可列表。**

另外还有几条恒定的上限：每次最多 40 个控制台动作（源码里是 `MAX_CALLS_PER_TURN = 40`）、单次会话里各类动作还有预算（write 20、network 5、install 2、spend 3、delete 3，用尽后即使在 auto 下也要等人）、无法把值传进 shell、有一个整体暂停按钮（Take back control）与对应的恢复、以及一份记录每次动作结果的日志。

这里有一处**文档与实现不一致**，值得单独记：ADR 写文本值上限 500 字符，但源码里取的是 `LONG_TEXT_MAX`，其值等于 `INPUT_VALUE_MAX = 10_000`。也就是说 500 这个数在代码里已经不成立。引用任何一条上限时，最好回源码确认一次，而不是只信 ADR。

## 九、怎么自己验这套东西

文档里给了一个可照搬的验收方法：用环境变量开启真实会话的端到端脚本，跑四种情形——控制关闭、只读、写入加自动确认、写入加人工确认。四种各跑一次，看行为是否与级别一致。

他们的实测发现了三个单元测试没抓到的问题，其中两个很典型：

- 分类器把"不花钱"读成了花钱，导致创建任务在 write 级别被误拒。
- 一个动作的后续计费轮次是调用返回后异步排队的，于是模型驱动时会多触发一次不应有的计费。

这两个都不是逻辑错误，而是**语义与时序问题**，只有真跑才会暴露。

如果你自己做，建议的最小验收集是：

1. 每个级别各测一次"该被拒的动作确实被拒"。
2. 在 auto 下测一次 network/spend/delete 是否仍然等人。
3. 在暂停状态下测一次是否整条拒绝。
4. 故意让一个动作失败，检查错误信息里有没有带出敏感值。

第 4 条最容易被跳过，而它正是上面第七节的来源。

## 十、限制与结论

这套设计的可借鉴处是四件事：按后果分五级而不是按功能分级；把确认模式与级别当成两个独立维度一起设计；network/install/spend/delete 在任何确认模式下都要人（实现口径；ADR 原文只列了 network/spend/delete 三类）；权限入口只能降不能升。它的三个已知薄弱点是：类别靠词推断所以会错、分类结果没有测试锁定、错误与拒绝路径曾有未经筛查就到达模型的通道（文档未称发生过实际泄漏）。

本文的限制：没有安装或运行，所有行为描述来自 ADR、README 与部分源码文件；ADR 有两处已与实现不一致（install 的级别归属、文本上限），我以源码为准并在正文标注；测试与审计数字是项目自述，我没有复现；ADR 里提到的其他修订（ADR-450、ADR-407）我没有逐个打开；四个工具的实际返回格式我未实测。

下一步建议：如果你正在给自己的系统设计"agent 操作界面"的权限，先把动作清单按后果分一遍类，然后检查有没有一条能提权的配置入口。这两步不需要写代码，但决定了后面所有实现的上限。
