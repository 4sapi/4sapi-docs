# 开箱即用的本地 Agent 怎么拼出来：客户端开源，能力与界面解耦

"装好就能用"这句话，在一个本地 Agent 上要兑现的东西比想象中多：不用租服务器、不用配网关、换台设备能接着干、手机上还能操作那台电脑。

cindy 把它写成了产品定位。中文 README 的原话是"开源、开箱即用的 AI Agent"，英文版多一句"ready out of the box and yours to shape"。仓库 9,653 星、1,203 个 fork、未关闭条目 2,929 个（GitHub 的 open_issues_count，含 PR；抓取于 2026-11-10）。

本文拆它怎么做到，以及让渡了什么。

事实来自仓库 README 与 `docs/dev-rules/` 下的规则文档；我没有安装客户端，也不是实测。

## 一、先说清哪部分开了源

| 部分 | 是否在本仓库 | 说明 |
| --- | --- | --- |
| 桌面客户端（Electron） | 是 | `apps/desktop` |
| 移动客户端（Expo / React Native） | 是 | `apps/mobile` |
| 共享能力包 | 是 | `packages/*`：鉴权、设备互联、agent 编排、模型提供方等 |
| 工具二进制 | 按需下载 | claude-code、codex、ripgrep 由 `pnpm install` 按平台取；Android platform-tools 按固定版本下载并校验 sha256 |
| 后端服务 | **否** | README 明写：后端在另一个仓库，不属于这个 monorepo |

表的口径来自 README；`apps/` 下另有 `host`、`web`、`cindy-headless` 三个目录，用途未说明。`repo-map.md` 的工具版本表比 README 多一个 `pi`。

所以"开源"的含义是：**你拿到的是客户端与里面的编排逻辑，服务端不在其中。**

## 二、两种模式，能力不同

README 写了两条路，差别不在登录界面，而在能力集合。

| 模式 | 账号 | 能用什么 |
| --- | --- | --- |
| 托管服务 | 需要 Cindy 云账号 | 完整服务：跨设备、云伴生体、同步 |
| Skip Sign-In | 不需要 | 本地 agent；账号状态显示"未登录"，**服务端能力不可用** |

第二行是这篇最该记住的一句。它意味着：

- 可以只把它当本地 agent 用，不注册。
- 但跨设备接管会话、云端记忆同步这类功能，免登录状态下不成立。
- 本地模式不发心跳（数据边界那篇展开）。

**"开箱即用"其实是"两条默认路径"**：连着云是最省事的路径，断开云是最少依赖的路径，二者不是同一个产品的两种皮肤。

## 三、三条最相关的规则

仓库的《架构原则与不变量》共四条，这里取三条，**第三条（含主界面布局树）不展开**。

**能力独立于承载它的界面。** 共享 package 自己提供能力，经初始化、配置或回调拿到宿主能力，**不许 import Desktop 的 Renderer 或 Main**。

同一节里还有一句分工：agent 编排集中在 `maker-core`，Main 承担宿主能力，Renderer 表达状态和用户意图；确定的流程与约束由代码保证，模型只判断真正需要推理的部分。

那句"不允许 import"的后果是：同一套能力可给桌面、手机、远程入口复用，不拖带某个界面的生命周期。真正的分水岭在这里：流程写进代码，行为才可预测；交给模型自由发挥，同一台机器两次结果都可能不同。

**Main 只准顶层静态 import，禁止运行时动态 `import()`。** 文档给的理由是依赖在打包时可见，加载时机和错误路径不留给运行期猜。

我的理解是：这条约束的是"开箱即用"最容易翻车的地方——动态加载的模块在别人机器上找不到，用户看到的就是空白。文档只写到"不留给运行期猜测"，没写失败表现。

**让不同入口共享事实。** 同一任务的状态、权限和执行结果，由共同的业务入口解释；控制端呈现执行端的事实——这一条下一节整节都在用它。

## 四、多设备：事实只有一个来源

多设备难的不是连上，是**谁说真话**。

规则里写了三件事：

- 界面上的"已收到"不等于执行端的"已完成"。
- 手机经 device-link 控制电脑；SSH 工作区的文件与进程在远端，路径与操作按**实际执行位置**解析。
- 重试范围与故障范围相称：单个请求或单台控制端故障，不该拆掉其他设备在用的共享连接。

第三条最容易被忽略。多设备系统里最常见的坏味道是"一处失败、全局重连"——手机信号抖一下，桌面正在跑的会话跟着断。

README 对这个能力的描述是"你的电脑就是服务器，不用租服务器或自建"。默认线路是设备互联（`packages/device-link`、`device-link-protocol`）加官方中转；"官方中转"这点出自 `docs/self-hosted-relay-plan.md`，README 没写。

## 五、中转这一层可以自建，但有范围

凭证与存储规则文档里有一张表，三行分别写桌面端、移动端和**用户自己的服务器**。选择「部署到我的服务器」后，经 SSH 写入：

| 位置 | 内容 |
| --- | --- |
| `/opt/cindy-relay` | Node 运行环境与 `relay.mjs` |
| `/var/lib/cindy-relay` | 属 `cindy-relay` 用户、0700：设备凭证哈希、证书档案、Let's Encrypt 账户密钥、0600 的 TLS 材料 |
| `/etc/systemd/system/cindy-relay.service` | 服务单元 |

两条关键约束写在原文里：**主人凭证明文与主人私钥从不离开主人电脑**；卸载前核对中转 ID 与主人公钥，匹配才删除。

客户端侧，桌面把部署记录存在 `owners/<owner-key>/device-link-relay/config.json`（地址、中转 ID、主人公钥，不含秘密），凭证与签名私钥在 `secrets/<中转ID>.enc`，经 safeStorage 加密，**Linux 只有 `basic_text` 时拒绝保存**。整棵目录按账号隔离。

但替代范围要写准。`self-hosted-relay-plan.md` 写明：自建只替换**设备之间的中转**，登录与模型仍走官方；切过去后**手机系统推送不可用**（凭据绑在官方应用上），**供应商分享与共享任务仍经官方中转**（跨账号，成员关系与转发校验在官方）。自建中转绑在主人账号上，跨账号设备直接拒绝。

所以准确说法是：**同账号设备之间的中转可以自建；云侧（账号、会话同步、伴生体）不行。**

后半句是从"后端不在本仓库 + 自建只替换设备间流量"推出来的，文档没有直接写"云侧禁止自托管"。理论上你可以另写一套服务端，但那不在上游兼容范围内。

## 六、三种引擎的适配层在哪

内置三种 agent 引擎：Claude Code、Codex、Pi。适配层在 `packages/maker-core/src/agents/` 下——目录树里 `claude-code`、`codex`、`pi` 三个目录都在，另有一个 `shared`。

这里有个容易写错的地方，我第一版就错了：`maker-cc-manager` 与 `maker-pi-manager` **不是**本地引擎管理器，而是跑在远程 SSH 机器上的 `cc-remote` / `pi-remote` 守护进程，服务远程工作区，不是本地三选一。

README 对切换的描述很直白：切换 harness 是"交接或重建引擎上下文"，**不保证两者内部状态一致**。

这等于承认：换引擎不是热插拔。会话层面的连续性（消息、文件、工具结果）由 Cindy 保证，引擎内部状态（上下文窗口里装了什么）不保证。

含义：同一会话可换引擎，不用重建会话；但别指望它"记得"上一个引擎推理到哪一步；重要结论最好落进会话，而不是留在引擎上下文里。

## 七、让一个 agent 带队

README 还写了一种用法：让一个 agent 做领队，分别安排规划、并行实现和独立评审，共享目标与验收标准。仓库里对应的是 `packages/orca-workflow` 与 `docs/dev-rules/` 下的多智能体编排文档。

这部分只做事实陈述：**多智能体的收益取决于任务能否被切成可独立验收的块**，这个前提跟工具无关。README 没给量化结果。

## 八、"开箱"让渡了什么

| 让渡 | 具体是什么 |
| --- | --- |
| 云侧控制权 | 后端不在这仓库；账号、会话同步、伴生体无法自托管（推断，见第五节） |
| 部分出网不可换 | 中转可换成自己的服务器，但登录、模型、供应商分享仍走官方 |
| 引擎状态连续性 | 换 harness 是重建上下文，不是迁移内部状态 |
| 维护节奏 | 2,929 个未关闭条目（issue+PR），迭代快、跟进要成本 |

第一行是根本性的：**"开源"在这里解决的是"可审计、可改客户端、可自建设备中转"，不解决"云侧整套自托管"**。

## 九、分叉之前先算三笔账

**工具二进制不在仓库里。** claude-code、codex、ripgrep（另列 `pi`）由 `pnpm install` 按平台下载；Android platform-tools 在 Windows 打包前按固定版本下载并校验 sha256。分叉后，这些依赖的版本锁定责任转到你手上。

**服务端行为改不了。** 后端不在这个仓库，涉及服务侧逻辑的改动无法自行落地。你能改的是客户端怎么调用它。

**端点清单分两类。** 设备中转地址可以在设置里切换（官方 / 我的服务器 / 这台电脑当中转 / 已加入的中转，切换前有确认），不用分叉；`config/endpoint.json` 里其余地址要改，就属于维护一个分叉。

## 十、要不要用：六个判断

1. **你要的是客户端、中转，还是整套云服务？** 客户端可改、中转可自建；云侧整套自托管，这里没有。
2. **跨设备是核心需求吗？** 是就绕不开账号；不是，Skip Sign-In 也能跑。
3. **你会不会换引擎？** 会，就把关键结论落进会话与文件，别留在引擎上下文里。
4. **团队要不要审代码？** 客户端可审；服务端审不到，这一点要在合规预期里写清。
5. **能不能接受默认连官方云？** 端点清单可查，中转类可切换，其余属分叉。
6. **谁跟进上游？** 迭代快的项目，客户端分叉的合并成本要提前算。

## 十一、结论与边界

"开箱即用"在这个项目里的技术含义是三件事：能力与界面解耦（所以多端能复用）、编排进代码（所以行为可预测）、多入口共享同一份事实（所以换设备不出双份真相）。

代价同样清楚：云侧闭源、部分出网不可换、引擎切换是重建。而"设备中转可自建"这一点，是它能拿出来说的少数几个可验证的自主性。

限制：没有安装客户端，行为描述来自 README 与工程规则，不是实测；多智能体效果未验证；issue 与 PR 数是抓取快照；三个 `apps/` 目录用途未知，未推断；"云侧不行"是推断，已在第五节标注。

下一步如果只做一件事：先用 Skip Sign-In 跑一个真实任务，记录哪些功能因为"未登录"而不可用。那张缺失清单，就是这个产品开箱程度的真实刻度。
