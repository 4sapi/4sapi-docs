# 【大模型API中转站】第144期 Fable 5上手避坑 | 别把强模型当默认模型

本文是【大模型API中转站】系列的第144篇。本系列致力于用最低的成本、最清晰的方法，帮你打通多模型API的任督二脉。建议先收藏，随用随查。

你第一次打开 Fable 5，最容易犯的错，不是不会用。

而是把它当成一个更强版 Opus。

或者更直接一点：

```text
把它当成默认聊天模型。
```

这样很快就会难受。

小任务上，它贵得没必要。

硬任务上，你又不知道怎么判断它到底有没有做完。

Fable 5 很主动。

它会自己读上下文。

会自己想办法验证。

会把一个看起来两行 CSS 就能修掉的问题，拆成一条很长的调查链路。

这很强。

也很贵。

截至本文写作时（2026年7月3日），Anthropic 官方 Fable 5 API 价格是：

```text
输入：10 美元 / 100万 token
输出：50 美元 / 100万 token
```

token 可以简单理解成模型读写内容时消耗的计量单位。

如果只是问一句话、回一句话，成本还能估。

但 Fable 5 真正擅长的是长程 Agent。

它一旦开始：

```text
读文件。
看日志。
写计划。
改代码。
跑测试。
读失败输出。
再改一轮。
生成总结。
```

账单就不是按“回答一次”算。

而是按“一段工程流程”算。

所以这篇不写模型排行榜。

只解决一个问题：

```text
普通开发者第一次用 Fable 5，到底应该怎么开始？
```

先说结论：

```text
Fable 5 不应该做默认模型。
它应该做硬任务升级层。
```

普通任务继续用便宜模型。

中等任务用 Sonnet、Opus、GPT、Gemini 这类主力模型。

只有当任务足够硬、足够长、足够脏，才升级到 Fable 5。

如果你已经通过 4SAPI 这类大模型API中转站做统一入口，Fable 5 最适合放在强模型池里，而不是放在默认路由上。

## 1. Fable 5 的价值不是回答更漂亮

普通模型更像一个回答问题的人。

你问它。

它答。

你追问。

它再答。

Fable 5 更像一个能接工单的高级助手。

它值钱的地方，不是把一句话润色得更像专家。

而是把一件复杂任务推进到：

```text
你可以验收。
```

这点很重要。

比如一个 bug，表面看是前端样式问题。

普通模型可能会先猜：

```text
是不是 overflow 设置错了？
```

Fable 5 更应该做的是：

```text
复现问题。
看相关文件。
跑本地服务。
打开页面。
截图验证。
改一小步。
再跑测试。
如果不对，承认猜错，再往回查。
```

这就是长程 Agent 的价值。

它不是说得更好听。

它是更愿意把事情追到底。

但也正因为这样，它不适合所有任务。

你拿它做普通问答、短摘要、低价值批量文案，就像请一个高级架构师帮你批量改标点。

能做。

但不划算。

## 2. 一句话判断：这个任务是不是硬、长、脏

我建议用三个字判断 Fable 5 值不值得上：

```text
硬。
长。
脏。
```

### 硬

硬，是有明确验收标准。

不是“回答得看起来不错”。

而是：

```text
测试要通过。
类型错误要消失。
页面 bug 要复现后修掉。
公共 API 不能被破坏。
PR review 要给出文件级证据。
```

没有验收标准的任务，不适合测 Fable。

因为你不知道它到底做完没有。

### 长

长，是上下文多、步骤多、约束多。

比如：

```text
几十个文件的重构。
跨模块依赖升级。
长 issue thread 归因。
多轮调试。
文档、日志、截图混在一起。
```

这种任务不是回答一次就结束。

它需要持续行动。

Fable 的优势就在这里。

### 脏

脏，是任务现场不干净。

真实工程问题很少像 benchmark 题一样漂亮。

常见情况是：

```text
文档过期。
测试偶发失败。
依赖版本乱。
截图只露出一半。
报错堆栈很长。
需求里夹着产品约束。
```

Fable 5 的差距，往往要在这种现场里看。

如果任务干净、短、明确、低价值，先别急着上 Fable。

用便宜模型就好。

## 3. 哪些任务值得交给 Fable 5

可以从五类任务开始测。

### 第一类：多文件重构

不要只让它改一个函数。

让它读调用链、设计迁移顺序、分批修改、跑测试、写变更摘要。

验收标准写清楚：

```text
不能改公共 API。
不能引入新依赖。
测试必须通过。
必须说明迁移影响面。
```

这种任务能看出 Fable 是否真的会做工程。

### 第二类：带陷阱的 bug 修复

给一个看起来像前端问题，实际原因可能在依赖、状态、配置或浏览器兼容里的 bug。

看它会不会过早下结论。

更好的表现是：

```text
先复现。
再测量。
再看日志。
必要时承认证据不够。
最后给出可验证修复。
```

### 第三类：长上下文 PR review

给它一个跨模块 PR。

让它找：

```text
破坏性变更。
迁移遗漏。
测试缺口。
性能风险。
安全边界。
```

要求它输出：

```text
文件路径。
具体原因。
影响范围。
修复建议。
优先级。
```

只说“这段代码可能有问题”，不够。

### 第四类：多模态工程任务

给它截图、报错页、设计稿、PDF 表格或控制台图。

不要只让它看图说话。

要让它从图里推操作路径：

```text
这个 UI 哪里错了？
应该去哪个组件查？
可能是哪类 CSS 或数据状态问题？
怎么验证？
```

Fable 5 的视觉和长程推理价值，适合放在这种任务里测。

### 第五类：自我验证任务

不要问：

```text
帮我写一段代码。
```

换成：

```text
先给计划。
改完后运行测试。
失败就继续修。
最后告诉我验证了什么、没验证什么。
```

Fable 值不值钱，主要看它能不能追到可验收。

## 4. 哪些任务不要上 Fable 5

这些任务不建议默认用 Fable：

```text
普通问答。
短代码片段。
简单 JSON 提取。
低价值批量摘要。
标题改写。
普通客服分类。
一次性脑暴。
简单正则。
没有验收标准的泛泛建议。
```

不是 Fable 做不了。

是没必要。

如果一个任务人工十分钟就能解决，先用便宜模型。

如果便宜模型失败，再考虑升级。

不要一上来就把最贵模型推到默认路由。

强模型真正的用法是：

```text
处理少数硬任务。
降低返工。
提高关键任务成功率。
```

不是让每个请求都显得贵。

## 5. 入口怎么选：官方产品、API、Claude Code、4SAPI

第一次用 Fable 5，不建议直接上复杂企业架构。

先从真实任务开始。

常见入口有四类。

### 入口一：Claude 官方产品

比如：

```text
Claude.ai
Claude Desktop
Claude Mobile
Claude Code
Claude Cowork
```

这个入口适合快速试水。

拿一个开源项目、一个截图 bug、一个小型重构任务先跑起来。

看它的工作方式是不是符合预期。

缺点是：

```text
不太适合团队统一记账。
不太适合严肃横评。
不太适合沉淀模型路由规则。
```

### 入口二：Claude API

官方 API 模型名是：

```text
claude-fable-5
```

API 适合接进：

```text
自己的 Agent。
CI 评测脚本。
内部工具。
企业后台。
自动化工单系统。
```

好处是可控。

麻烦也在这里：

```text
账单。
限额。
fallback。
日志。
失败重试。
数据边界。
```

都要你自己处理。

### 入口三：Claude Code / Cursor 类 Coding Agent

Fable 5 在 coding agent 里最容易展示价值。

因为它可以：

```text
读仓库。
改文件。
跑命令。
看测试输出。
调整方案。
继续验证。
```

但风险也最大。

它越主动，你越要给它：

```text
sandbox。
测试账号。
低权限目录。
无生产密钥环境。
预算闸门。
```

强模型一旦能操作电脑，就不能只靠“请不要乱动”。

权限要在环境层控制。

### 入口四：4SAPI 统一入口

如果你已经在用 4SAPI 做大模型API中转站，可以把 Fable 5 放进统一模型池。

4SAPI 在这里的价值不是让你把所有请求都打到 Fable。

而是：

```text
统一 Key。
统一 Base URL。
统一日志。
统一成本统计。
统一预算控制。
后续方便做模型路由。
```

个人试水时，可以先用官方产品或 API。

团队使用时，更建议通过 4SAPI 统一入口，避免每个人各自拿一个 Key 乱试。

## 6. 别写聊天 prompt：把需求写成工单

很多人测新模型，还在用旧提示词：

```text
你是资深工程师，请帮我解决这个问题。
```

这太空。

Fable 5 应该吃更像工单的输入。

一个好任务包至少包含六件事：

```text
目标。
上下文。
硬约束。
可操作权限。
验收标准。
汇报格式。
```

### 目标

别写：

```text
优化这个项目。
```

写：

```text
把旧的 user settings 读取逻辑迁移到新的 config service，保留现有 API 行为。
```

目标越具体，模型越不容易乱探索。

### 上下文

要交代：

```text
哪些目录重要。
哪些文件可以忽略。
当前失败现象是什么。
有没有相关 issue。
有没有错误日志。
有没有截图。
之前试过什么。
```

上下文不是越多越好。

是越相关越好。

### 硬约束

提前写清：

```text
不能引入新依赖。
不能改数据库 schema。
不能破坏 public API。
不能修改生成文件。
不能改安全策略。
```

强模型越主动，约束越要清楚。

### 可操作权限

明确它能做什么：

```text
可以读文件。
可以改文件。
可以跑测试。
可以启动本地服务。
可以截图。
是否允许访问网络。
```

不要一上来给外部网络、生产密钥和主账号权限。

### 验收标准

这是最重要的部分。

比如：

```text
pnpm test 通过。
pytest tests/test_config.py 通过。
页面截图里不再出现横向滚动条。
生成 migration 文档包含回滚方案。
```

没有验收标准，模型容易交出“看起来完成”的答案。

### 汇报格式

让它最后固定输出：

```text
Root cause
Files changed
Verification
Remaining risks
```

这样你才能快速验收。

## 7. 一份可直接复制的 Fable 5 工单模板

下面这段可以直接复制给 Claude Code、API Agent 或 4SAPI 后面的业务系统。

```text
你要处理一个真实工程任务，不要只给建议。

目标：
【写清要完成的工程目标】

上下文：
【仓库、相关目录、错误日志、截图、issue、已有尝试】

硬约束：
1. 不要改公共 API，除非先说明原因。
2. 不要引入新依赖，除非先解释收益和风险。
3. 不要修改生成文件。
4. 不要接触生产密钥、真实用户数据或外部付费服务。
5. 每次修改后运行相关测试。
6. 如果证据不足，先说明你还需要检查什么。

允许操作：
【读文件 / 改文件 / 跑测试 / 启动本地服务 / 截图 / 是否允许访问网络】

验收标准：
1. 【测试命令】通过。
2. 【用户可见问题】消失。
3. 输出变更摘要、验证记录、未覆盖风险。

最后输出：
- Root cause
- Files changed
- Verification
- Remaining risks
```

Fable 5 擅长长程执行。

输入越像真实工单，它越有机会把这部分能力跑出来。

## 8. 第一次试 Fable 5，别测泛泛问题

不要问：

```text
你和 Opus 谁更强？
你适合做什么？
帮我写一个排序算法。
```

这种问题看不出 Fable 的价值。

第一次测试，我建议准备 5 个真实但低敏的任务：

```text
一个小仓库 bug。
一段失败测试日志。
一张 UI 异常截图。
一个跨 5-10 个文件的小重构。
一个 PR review。
```

每个任务都要写清：

```text
目标。
约束。
允许操作。
验收标准。
```

然后看它能不能把任务推进到验收。

不要只看第一轮回答。

要看完整过程。

## 9. 新手试用清单

```text
[ ] 我没有把 Fable 5 设为默认模型
[ ] 我准备的是硬、长、脏任务
[ ] 任务里有明确验收标准
[ ] 我给了必要上下文，而不是把整个仓库无脑塞进去
[ ] 我写清了不能碰的文件、依赖、API 和数据
[ ] 我使用测试仓库或低敏项目
[ ] 我没有提供生产密钥、真实客户数据和主账号权限
[ ] 我要求它最后输出验证记录和未覆盖风险
[ ] 如果用 4SAPI，已单独创建 Fable 测试 Key 或强模型分组
[ ] 我会记录本次任务是否真的减少返工
```

## 10. 总结

Fable 5 不是普通聊天模型。

也不应该是默认模型。

它真正的位置是：

```text
硬任务升级层。
长程 Agent 兜底层。
关键工程验收层。
```

第一次用 Fable 5，不要问：

```text
你强在哪？
```

直接给它一个真实但低敏的任务。

看它能不能：

```text
读上下文。
拆步骤。
动手验证。
失败恢复。
最后交出可验收结果。
```

如果它明显减少返工，就值得继续测。

如果 Opus、Sonnet、GPT 或 Gemini 已经能稳定完成，就别硬上 Fable。

个人试水可以先用官方产品或 API。

团队使用建议通过 4SAPI 这类大模型API中转站，把 Fable 5 放进统一 Key、统一日志和统一成本体系里。

下一篇继续讲企业怎么做：

```text
成本怎么算？
fallback 怎么记录？
30 天数据保留怎么处理？
sandbox 怎么设？
4SAPI 里怎么做 Fable 5 路由？
```
