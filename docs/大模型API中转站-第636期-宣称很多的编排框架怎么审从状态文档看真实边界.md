# 宣称很多的编排框架怎么审：从它自己的状态文档看真实边界

评估一个号称"多智能体编排、自适应记忆、联邦通信、企业级护栏"的框架，最容易犯的错是拿 README 的功能清单当结论。README 是营销面，它会把"有"写得比"能用"更响亮。

更可靠的材料是仓库里那些不为宣传写的东西：状态文档、治理目录、架构决策记录、变更日志。这些文件是给维护者自己看的，通常会露出真实的完成度。

本文拿 ruflo 当样本走一遍这套审读方法。选它是因为它的文档比较齐全——恰好够用来演示。全文不评价这个项目好不好，只演示怎么读。

信息来自仓库第一方文件（[README](https://github.com/ruvnet/ruflo/blob/HEAD/README.md)、[docs/STATUS.md](https://github.com/ruvnet/ruflo/blob/HEAD/docs/STATUS.md)、[.harness/README.md](https://github.com/ruvnet/ruflo/blob/HEAD/.harness/README.md)、[SECURITY.md](https://github.com/ruvnet/ruflo/blob/HEAD/SECURITY.md)、[ADR-444](https://github.com/ruvnet/ruflo/blob/HEAD/v3/docs/adr/ADR-444-claude-controls-the-console.md)），检索日期为 2026-11-03。我没有安装或运行过它。

## 一、第一步：把同一指标的数字并列

同一个指标在不同文档里出现不同数字，是最容易查、信息量最大的一步。

| 指标 | README 的说法 | docs/STATUS.md 的说法 | 同一份 STATUS 后文 |
| --- | --- | --- | --- |
| MCP 工具数 | 314 | 323 | 300 |
| 顶层 CLI 命令数 | 26 | 45 | 49 |

三处并列，不是取平均值的问题，而是**这三组数各自对应不同的统计口径或不同时间点**。任何一组单独引用都会误导读者。

同样的矛盾在这份仓库里还有两处，同样值得并列：同一份 STATUS 的概述段写"32 个可安装插件"，清点表写 33；README 正文写"26 个 CLI 命令"，而同一篇 README 里另一处又写"60+ 命令"。也就是说，真正需要并列的不止这六格。

正确做法是：把差异写出来，说明你无法判断哪个是当前值，并在使用前自己数一遍。这个项目提供了清点脚本（`scripts/inventory-capabilities.mjs`），也就是说这件事是可以自己核实而不是只能相信的。

## 二、第二步：看统计日期与包版本是否对得上

STATUS.md 写得很规矩：能力清点注明"2026-05-25 经审计"，测试基线写明快照版本是 ruflo@3.10.2 与配套 CLI 3.10.1，并给了具体提交号。

这里就出现了第一个时间差：**能力计数是 5 月的，包版本是 3.10.2**，中间隔了五个多月。这不是造假，而是"标注了日期却容易被当作最新值"的典型情况。

所以审读时要养成一个习惯：看到任何数字，先找它旁边的日期，再找文档里声明的版本，两者不匹配就把结论降级为"某个时点的值"。

### 顺带发现的一处硬冲突

SECURITY.md 的支持版本表写的是：3.5.x 支持，3.0–3.4 与 2.x 不支持。而 STATUS 的快照是 3.10.2。

两处并列，我不判断哪个对。但这条冲突有实际后果：**如果你跑的是 3.10.x，按 SECURITY.md 你不在"支持版本"列表里**。安全政策的适用范围是选型时的硬条件，值得直接问维护者。

## 三、第三步：分清默认开启与按需开启

功能清单最容易造成的误解是"写了就等于默认有"。STATUS 里有几处写得比较诚实，值得当作范例：

| 功能 | 状态 |
| --- | --- |
| 静态加密（AES-256-GCM） | **按需开启**：设 `CLAUDE_FLOW_ENCRYPT_AT_REST=1` 才启用，默认关闭 |
| 联邦预算熔断 | 仅 Phase 1 已发布；Phase 2 到 4 标注 deferred |
| 密钥链与口令解析 | 标注 deferred |
| 按工具逐个的见证签名 | 标注 pending |

按需开启本身不是问题——默认关闭能保住原有测试基线，这是一个合理的工程取舍。问题在于宣传面通常不会强调"默认关"。

审读的动作很简单：把功能清单里每一条标注成三种状态之一——默认开启、需要配置、尚未完成。第三种最常见也最容易被漏掉，因为它常常写在"接下来做什么"而不是"已有什么"。

## 四、第四步：看治理文件里没做的部分

这个仓库有一个 `.harness/` 目录，放的是给外部治理工具读的策略与清单文件。里面三项值得注意：

| 文件 | 状态 |
| --- | --- |
| mcp-policy.json | 已有：默认拒绝、审计日志开启、危险模式清单、每轮调用预算 |
| manifest.json | 已有：安全相关文件的 sha256 指纹 |
| witness.json | **文档写明"尚未创建"** |

前两项让它的自我评估结果看起来不错（治理对齐满、威胁模型最严重级别为 info、扫描 0 项待处理的发现），但第三项缺位，所以它自己的注释里带着一条 "witness missing"。

这个细节的价值在于：**它把"体检结果良好"和"还有一项没做"写在了同一页。** 读这类文档时，往后多看两段，往往就能看到正面的部分后面跟着的保留条件。

顺带一个可借鉴的做法：他们的冒烟步骤会锁定策略里的三条不变量（默认拒绝、审计日志、危险动作需批准），外加两项"必须为正数"的数值要求（工具超时、每轮调用上限），一旦被改动 CI 就失败。把治理规则做成测试，比写在文档里有效。

## 五、第五步：看它有没有记录自己的失败

这一条是判断文档可信度的分水岭。宣传面只写成功；给维护者看的文档会写踩过的坑。

这个仓库的 ADR 在这一点上写得比较具体，例如：

- 一次覆盖 270 个面板条目的审计发现三类动作被误判成普通写入（停止、清理、迁移本应算删除类），已改判；同时写明合计只覆盖 239 项、其余未逐项归类、**没有测试锁定这个划分**。
- 一次端到端测试（四次真实会话：控制关、只读、写入加自动确认、写入加人工确认）发现了三个单元测试没抓到的问题，包括把"不花钱"的分类读成花钱，以及一个动作的后续计费轮次是异步排队的、本该在模型驱动时跳过，实际却触发了。
- 一次修订承认多条返回路径此前只做转义、没做敏感内容筛查，导致凭据可能进入模型上下文；修法是统一清洗函数，并加了针对性测试。

这三条都属于"对外的宣称没有覆盖、但真实存在"的问题。一个项目愿意把这些写进文档，说明它的状态文档有一定可信度；反过来说，**如果一个项目的文档里只有成功记录，你在审读时就要把结论整体降级。**

## 六、第六步：验证机制能替代信任到什么程度

这个项目提供了 `ruflo verify`：它拉取清单、对被引用的每个文件重算 SHA-256、从 git 提交重新导出公钥、验证签名，任何漂移以非零退出并指出文件。这是一条比"相信我"强得多的机制。

但要看清它的范围。STATUS 里同时写着：按能力逐个的见证签名仍在进行（任务 25、26 未完成）。也就是说，**当前被签名覆盖的是"文档里列出的修复"，不是全部 300 多项能力。**

审读时的正确表述是："它有一个可运行的完整性校验，覆盖范围目前是修复清单，不是全量能力。" 这句话比"它支持密码学验证"准确得多。

## 七、第七步：数一遍接入路径

接入方式有几个，决定了维护面的宽度，也决定了你排障时要在几层之间找原因。这个项目 README 给了三条：

| 路径 | 怎么用 | 依赖 |
| --- | --- | --- |
| Claude Code 插件 | 加插件市场后装 core、console、mods，再 `/reload-plugins` 与 `/ruflo` | 需要指定版本的 Claude Code |
| MCP 服务器 | 初始化后把客户端指向 `npx ... mcp start` | 客户端要支持本地 stdio MCP |
| 独立终端界面 | `npx ruflo tui`，可选 `--plain` 只打印一帧 | 可以完全不装 Claude Code |

三条并列意味着三套配置、三套可用性边界。README 自己也写了"hook 支持取决于客户端"这类限定。评估时值得问一句：**如果你只用其中一条，另外两条的复杂度是否会成为维护负担？**

数接入路径还有一个副作用：它能暴露"文档里说的能力"和"你能走到的能力"之间的差。比如某些能力只在插件路径下有，走 MCP 就只有工具没有控制台。

### 一个可以当场做的核对

清点数字这件事不必只靠信任。如果仓库里带了清点脚本，跑一次就能得到当前值，比在三组数字之间猜更有用：

```bash
git clone --depth 1 https://github.com/ruvnet/ruflo /tmp/ruflo
cd /tmp/ruflo
node scripts/inventory-capabilities.mjs   # 文档称此脚本自动生成能力清点
```

预期结果是打印各类能力的当前计数；实际输出格式我没有验证过。如果脚本跑不起来，那么"能力计数"这一项就应当在你自己的记录里标成未核实——这一点比数字本身更重要。

第 1 步里那三组数字的差异，很可能就是"用不同脚本、在不同时间点、按不同口径数出来的"。把清点方法也当作待核验的一环，是这套审读的最后一块。

## 八、这套方法总结成七问

| 问 | 在本例里问出了什么 |
| --- | --- |
| 同一指标有几处数字 | 314/26、323/45、300/49 三组并列 |
| 数字旁有没有日期 | 能力计数是 2026-05-25，包是 3.10.2 |
| 哪些功能是按需开启 | 静态加密默认关闭 |
| 治理文件里缺了什么 | witness.json 尚未创建 |
| 有没有失败记录 | 有：分类错误、实测发现、泄漏修补 |
| 验证机制覆盖多大范围 | 覆盖修复清单，不是全量能力 |
| 有几条接入路径、各自依赖什么 | 三条：插件、MCP、独立终端，各有版本与客户端要求 |

七问都不需要装环境，全部来自仓库里的 Markdown。成本大概是半小时。

## 九、这套方法的边界

它有三个局限，得说清楚：

1. **只读文档不能证明实现。** 文档说默认关闭加密，实际行为要跑一次才知道；这里所有结论都以"文档称"为前提。
2. **写得诚实的文档反而更容易被误读。** 因为它会写"deferred""pending""not yet created"，快速浏览时容易把这些当成缺陷清单，而它们其实只是完成度标注。
3. **不能用来判断项目质量。** 一个功能没做完的框架，可能恰好是你需要的；一个功能齐全的框架，可能文档一团糟。这套方法只回答"宣称与现状的差距在哪里"。

第 3 点尤其重要。审读的目的是让你知道自己在用什么，不是替你下结论。

## 十、限制与结论

评估一个宣称很多的框架，把 README 放在最后读。先看状态文档里的数字与日期、治理目录里的缺项、决策记录里的失败、以及验证机制的范围，四条合起来能给你一个"当前真实完成度"的轮廓。

本文的限制：没有安装或运行，所有结论都基于仓库文档；三处能力计数的差异原因未查清，我没有运行清点脚本；SECURITY.md 与 STATUS 的版本冲突并列保留，不判断哪个正确；没有核对源码实现与文档是否一致；不评价项目本身。

下一步建议：拿这套七问去审你正在考虑的那个框架。如果半小时内你答不出第三问与第四问，说明它的状态文档不足以支撑决策，这本身就是答案。
