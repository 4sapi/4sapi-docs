# 多轮工具调用重放前如何校验调用与结果

多轮工具调用中，代理有时需要把上一轮上下文带入下一次请求。最容易被忽略的边界是：客户端可能已经提交了完整历史，代理却又追加了一份缓存的回放内容。只要同一个调用被重复写入，或调用和结果没有按 `call_id` 配对，上游就可能拒绝整个会话；更糟的是，损坏历史还会在后续请求中持续复现。

下面给出一个用于网关或中间层的重放判定方法：先核对工具调用与工具结果的配对关系，再决定是否需要追加历史。

## 问题与边界

工具调用不是普通聊天文本。调用项表示“模型要求应用执行某项操作”，结果项表示“应用已经把该调用的结果交回”。OpenAI 的[函数调用指南](https://developers.openai.com/api/docs/guides/function-calling)要求应用执行模型请求的函数调用，并将函数调用输出提交回模型；这意味着调用与结果的关联必须在会话历史中保持完整。

一个已合并的修复展示了重放层面的故障：客户端未使用上一次响应 ID、而是自己携带完整工具历史时，桥接层仍追加旧回放，导致工具调用重复。[Issue #5850](https://github.com/Wei-Shaw/sub2api/issues/5850) 给出了复现分析；[PR #5864](https://github.com/Wei-Shaw/sub2api/pull/5864) 在 2026-08-22 合并，新增了完整历史和仅有结果两类回归测试。

本文的规则只适用于中间层确实负责重建历史的场景。原样透传请求时，不应在没有明确职责的情况下改写客户端消息。

下文的本地验证代码需要 Python 3.10 或更高版本，不依赖第三方包。

重放逻辑中至少有三个状态所有者：客户端当前输入、代理缓存的历史和上游用来续接的响应标识。问题通常不在任何一个状态单独错误，而在代理没有明确规定谁是当前轮的权威来源。

```text
客户端完整历史 ───────> 当前输入
                         │
上游 previous_response_id -> 续接锚点 ─> 重放判定 ─> 最终上游输入
                         │
代理缓存回放 ───────────> 候选补充状态
```

当客户端已经给出完整历史且没有续接锚点，代理缓存只能是“待验证候选”，不能无条件追加。否则相同的调用和结果会被拼接两次，错误在下一次上游校验时才暴露。

## 两个方向的配对规则

工具调用历史需要分别检查两个方向，但两个方向适用的时机不同：

| 方向 | 规则 | 为什么 |
| --- | --- | --- |
| `function_call_output -> function_call` | 任一结果都必须引用当前历史中已有的调用 | 没有调用上下文的结果无法解释 |
| 已完成历史 `function_call -> function_call_output` | 准备重放前，历史调用必须有对应结果 | 未闭环调用带到下一轮会污染上下文 |
| 当前流中的 `function_call -> function_call_output` | 可以暂时不完整 | 应用可能还在执行工具，不能过早删除真实调用 |

因此不能用一条简单的“所有调用都必须有结果”规则处理全部流量。它会误伤当前轮正在执行的工具；但也不能只检查结果是否有调用，否则旧调用可能在历史里永久滞留。需要先区分“当前轮实时项”和“准备作为历史回放的项”。

## 用 call_id 做最小配对检查

以下函数只回答一个问题：当前输入是否已经拥有每个工具结果所需要的调用上下文。若客户端带了前一响应 ID，代理可以按自身协议执行回放；若没有前一响应 ID，且当前历史已闭环，就不应再追加旧状态。

```python
def needs_replay(previous_response_id: str | None, items: list[dict]) -> bool:
    if previous_response_id:
        return True

    call_ids = {
        item["call_id"]
        for item in items
        if item.get("type") == "function_call" and item.get("call_id")
    }
    output_call_ids = {
        item["call_id"]
        for item in items
        if item.get("type") == "function_call_output" and item.get("call_id")
    }
    return not output_call_ids.issubset(call_ids)


complete_history = [
    {"type": "function_call", "call_id": "call_42"},
    {"type": "function_call_output", "call_id": "call_42", "output": "ok"},
]
output_without_call = [
    {"type": "function_call_output", "call_id": "call_42", "output": "ok"},
]

assert needs_replay(None, complete_history) is False
assert needs_replay(None, output_without_call) is True
assert needs_replay("resp_previous", complete_history) is True
print("replay pairing checks passed")
```

将代码保存为 `verify_replay_pairing.py` 后，在空的本地测试目录运行 `python verify_replay_pairing.py`。预期输出是 `replay pairing checks passed`。这不是完整的协议实现：真实系统还应处理不同工具类型、撤销事件和重复 ID。但它把最关键的决策从“发现任意工具结果就回放”改成“确认当前输入是否缺少结果所需的调用”。

下面的辅助函数可用于在“准备回放的历史”上寻找三类异常：重复调用 ID、没有调用的结果，以及没有结果的历史调用。这里将最后一类单独返回，而不是立即删除，因为调用方还需要结合取消状态、持久化检查点和协议语义决定怎样恢复。

```python
def inspect_replay_history(items: list[dict]) -> dict[str, set[str]]:
    seen_calls: set[str] = set()
    duplicate_calls: set[str] = set()
    output_ids: set[str] = set()

    for item in items:
        call_id = item.get("call_id")
        if not call_id:
            continue
        if item.get("type") == "function_call":
            if call_id in seen_calls:
                duplicate_calls.add(call_id)
            seen_calls.add(call_id)
        elif item.get("type") == "function_call_output":
            output_ids.add(call_id)

    return {
        "duplicate_calls": duplicate_calls,
        "orphan_outputs": output_ids - seen_calls,
        "unfinished_calls": seen_calls - output_ids,
    }


report = inspect_replay_history([
    {"type": "function_call", "call_id": "call_ok"},
    {"type": "function_call_output", "call_id": "call_ok"},
    {"type": "function_call", "call_id": "call_twice"},
    {"type": "function_call", "call_id": "call_twice"},
    {"type": "function_call_output", "call_id": "call_missing"},
    {"type": "function_call", "call_id": "call_unfinished"},
])

assert report == {
    "duplicate_calls": {"call_twice"},
    "orphan_outputs": {"call_missing"},
    "unfinished_calls": {"call_twice", "call_unfinished"},
}
print("replay history inspection passed")
```

将代码追加到 `verify_replay_pairing.py` 后运行，预期最后一行是 `replay history inspection passed`。真正实现中，重复调用可能需要拒绝请求、选择权威副本或根据协议进行去重；这里先把异常显式暴露出来，避免它们在字符串拼接中消失。

## 重放流程应分五步

1. 标记来源。为每个项记录它来自客户端当前输入、代理缓存还是上游续接状态；没有来源标记的历史不应直接重放。
2. 解析当前输入中的调用 ID 和结果引用的调用 ID，并先检查是否有重复 ID 或孤儿结果。
3. 若客户端提供前一响应 ID，按该协议的续接规则处理。不要再把同一轮完整历史无条件拼接到续接请求中。
4. 若没有前一响应 ID，且当前输入中的结果都有对应调用，把当前历史视为完整输入，禁止追加缓存回放。
5. 只有结果缺少调用上下文时，才从已验证的状态中补充必要调用，并在补充后再次执行配对检查。

第四步不能靠伪造成功结果完成。中间层通常不知道工具是否执行过、是否产生过外部副作用，也不知道真实结果是什么。面对无法确认的历史，应停止续接、向客户端报告不完整上下文，或从已验证的检查点重新开始。

如果历史里只有一个未完成调用，也不能默认“补一个失败结果”就能恢复。对读取型工具，这种结果可能只是误导模型；对写入型工具，它还可能掩盖一个已经部分执行的副作用。恢复策略必须由调用方的业务协议定义，而不是由通用网关猜测。

## 用状态表代替隐式拼接

字符串级别的“前缀相同就不追加”在工具调用场景不够稳妥：相同调用可能顺序不同、包含不同元数据，或只在某些字段上重复。更可靠的做法是将准备回放的数据解析为状态表，至少按以下键组织：

| 键 | 用途 | 必须记录的最小信息 |
| --- | --- | --- |
| 调用 ID | 连接调用与结果 | `call_id`、工具类型、来源轮次 |
| 响应锚点 | 判断是否走续接 | 是否存在、所属会话 |
| 项来源 | 区分客户端与缓存 | `client`、`replay`、`continuation` |
| 生命周期 | 区分实时和历史 | `in_flight`、`completed`、`cancelled` |
| 配对状态 | 决定是否能重放 | 已配对、缺调用、缺结果、重复 |

只有“缓存来源 + 已完成 + 已配对”的项才适合作为自动回放候选。客户端已提交的完整项应优先保留原样；处于 `in_flight` 的当前调用则应继续等待正常工具结果或取消信号，而不是被历史清理逻辑删除。

## 取消、重试与幂等性

工具调用出现在流中，不代表工具一定被应用执行。网络断开可能发生在模型发出调用之后、客户端接收之前，也可能发生在应用执行工具之后、结果回传之前。代理只看见其中一段时，不能据此判断业务操作是否已经完成。

因此应把三个概念分开：

- **传输重试**：同一请求没有得到可确认响应时的重新发送。
- **工具重试**：应用再次执行工具，可能产生副作用。
- **会话重放**：把历史带入下一轮模型请求。

这三者不能共享一个“失败后再试一次”的开关。对有副作用的工具，调用方至少应使用可追踪的操作 ID 或幂等键；网关在不掌握工具语义时，只能报告会话上下文不完整，不能假设工具可安全重跑。

## 建立可观察的回归测试

至少覆盖以下场景：

| 场景 | 预期 |
| --- | --- |
| 客户端提交完整调用和结果，且没有前一响应 ID | 不追加缓存回放 |
| 客户端只提交结果 | 识别为缺少调用上下文 |
| 客户端提供前一响应 ID | 走显式续接分支，不与完整历史重复拼接 |
| 已取消或断线的调用没有结果 | 不把该调用当作可安全回放的完整历史 |
| 同一个 `call_id` 出现多次 | 拒绝、去重或记录协议错误；具体策略须由协议定义 |

还应增加两类跨轮测试：

| 场景 | 预期 |
| --- | --- |
| 第一轮已完整 call/output，第二轮客户端再次提交完整历史 | 最终上游输入只保留一份调用和一份结果 |
| 第一轮被取消，第二轮带入未完成调用 | 不伪造输出；中间层拒绝续接或从明确检查点重建 |

测试的核心断言应放在“最终上游输入”而不是中间缓存。缓存可以暂时存在冗余；真正会造成协议错误的是冗余或残缺状态被发送到下一轮。

日志也应只记录低敏感度信息，例如调用数量、结果数量、是否有前一响应 ID，以及缺失 ID 的不可逆摘要。不要把用户输入、工具参数或工具返回值完整写入日志。

建议为每一次重放决策记录一个固定的、可搜索的结构化事件：

```json
{
  "replay_decision": "skip_current_history_complete",
  "has_previous_response_id": false,
  "client_call_count": 2,
  "client_output_count": 2,
  "cached_call_count": 2,
  "orphan_output_count": 0,
  "unfinished_history_call_count": 0
}
```

该记录不包含调用参数、工具输出或用户消息，却足以判断代理为什么没有重放、为什么请求被拒绝，或为什么需要人工检查状态。

## 排查顺序

当上游报告“缺少工具结果”“找不到调用”或同一会话反复失败时，可以按下面顺序排查：

1. 为一次失败请求提取脱敏调用 ID 列表，确认是否有重复和孤儿结果。
2. 检查客户端是否提供了前一响应 ID，或已经发送完整历史；这两个分支不能同时无条件追加缓存。
3. 比较最终上游输入与客户端输入，找出只由缓存引入的调用或结果。
4. 查看该轮是否取消、超时或断线；这决定未完成调用是实时状态还是损坏历史。
5. 对有副作用的工具停止自动重试，交由业务层按操作 ID 判断是否已经执行。

这样得到的是可验证的状态差异，而不是“上游偶发 400”一类无法行动的结论。

## 限制与结论

“结果引用的调用都存在”只能说明基础关联完整，不能证明工具结果在业务上正确。对有副作用的工具，还需要调用方提供幂等键、取消语义和持久化状态。

但在重放前建立双向配对检查，能先消除一类确定的协议错误：把已完整的客户端历史再次拼接，或把没有结果的旧调用带到下一轮。对多轮工具调用来说，完整性比盲目续接更重要。先明确状态所有权、再按调用 ID 证明历史完整，才能让重放成为可测试的恢复步骤，而不是隐式拼接的副作用。
