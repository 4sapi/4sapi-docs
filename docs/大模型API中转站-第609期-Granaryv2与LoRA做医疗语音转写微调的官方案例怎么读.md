# 用 Granary v2 与 LoRA 做医疗语音转写微调：官方案例的数字怎么读

专业领域的语音转写，常见的痛点是通用模型把药名、缩写和数字写错。NVIDIA 在 2026 年 10 月 28 日的博客里给了一个医疗案例：先改提示词，再用合成语音加少量真实录音微调，留出集上的词错误率从 22.44% 降到 12.17%。

这类案例的价值不在最终那个数字，而在它的评测设计：什么数据用来调参，什么数据留着只测一次，哪些对比是公平的。本文回答一个问题：这个案例的数字怎么读，哪些结论可信，哪些不能直接比较，以及你为自己的领域做同样的事时该怎么设计。

文章不含我的复现。所有数字来自 NVIDIA 博客自述，我只复算了其中的相对降幅。信息截止日期为 2026-10-30。

## 一、资料来源

| 来源 | 内容 | 日期 |
| --- | --- | --- |
| [Nemotron 3.5 Transcribe and Granary v2 博客](https://huggingface.co/blog/nvidia/nemotron-transcribe-granary) | 数据集说明、医疗案例、结果 | 2026-10-28，检索于 2026-10-30 |

博客还链接了案例的复现命令和微调教程，我没有打开，所以训练脚本的细节不在本文范围内。

## 二、先理解数据：Granary v2

案例用到的数据集 Granary v2 属于 NVIDIA 的语音数据集合。博客给出的规模：

| 项目 | 数值 |
| --- | --- |
| 公开清单覆盖时长 | 463,062 小时 |
| 语言 | 48 种（v1 为 25 种） |
| 来源语料 | 16 个 |

博客特意说明：这些数字描述的是数据集发布本身，**不是**转写模型完整训练数据的构成或采样权重。读的时候不要把 463,062 小时当成模型的训练量。

### 三种训练目标

同一句话，数据集给三种写法：

| 目标 | 示例 |
| --- | --- |
| 文本规范化、逐字 | I paid, uh, twenty-five euros. |
| 逆文本规范化，保留口头语 | I paid, uh, €25. |
| 逆文本规范化，去口头语 | I paid €25. |

对应数据清单里的字段名 tn_raw、itn_raw、itn_clean。这点对你的评测很重要：**你的业务想要哪种写法，要在提示词里说清，评测的参考答案也要用同一种。** 否则模型输出对了写法，却被当成错误。

### 四阶段流水线

博客把数据构建流程分为四步：

1. 音频准备：分段、跟踪说话人、标注声学事件和语言。Granary v2 的来源已经分好段，这一步在本次发布中跳过。
2. 转写：每种语言分配主模型和备用模型，主模型未通过幻觉检查时回退；用人工参考转写保留可信拼写。
3. 任务标签生成：派生转写变体，检查字符速率、幻觉模式和与参考的一致性；只有通过的记录才获得上下文词和翻译。
4. 高保真筛选：去掉含噪声、削波或多人说话的片段。以 VoxPopuli 为例，从 354k 小时压到 111k 小时（22 种欧洲语言）。

对读者的启发是：这个数据集的价值不只是数据，而是**带质量标记的、可复用的构建流程**。博客称流水线可以在自己的录音或有授权的公开语料上运行，原始音频要按各语料的原始许可另行下载。

## 三、案例的实验设计

被测基准是印度医生和医学生的医疗英语录音，共 3,619 条，没有预先划分的训练集。博客把它按说话人拆开：

| 划分 | 数量 | 用途 |
| --- | --- | --- |
| 调参集 | 855 条 | 选提示词、选检查点 |
| 留出集 | 2,764 条 | 每个最终系统只解码一次 |

按说话人划分很关键。同一个人的录音如果同时出现在调参和测试里，模型可能记住的是这个人的口音，而不是领域术语。

### 训练数据怎么来的

因为没有现成训练集，案例自己造数据：

| 来源 | 时长 |
| --- | --- |
| 合成语音（由生成的医疗文本和公开药品目录制作） | 约 153 小时 |
| 带口音英语（Common Voice） | 29 小时 |
| 医疗录音（MultiMed） | 63 小时 |

一个细节值得学：**合成时把"写出来的形式"和"念出来的形式"分开。** 博客举例，标签是 HbA1c，送给语音合成的文本是 H B A one C。这样模型学到的是"听到这串音，写成 HbA1c"。

另外，训练文本过滤了与基准参考完全相同的句子，以及共有 8 词序列的句子，用来降低数据泄漏。

### 训练配方

- 训练语音编码器和投影层。
- 对语言模型用 LoRA 适配。
- 两次运行使用不同的数据配比。
- 适配器合并后，对选定检查点做均匀平均，得到一个最终模型。
- 检查点按解码后的调参集结果选，不只看训练损失。
- 整个过程（从文本生成到评测）约 14 个 GPU 小时，使用一块 NVIDIA GB300。

最终系统使用一条固定的格式约定提示词，一次模型推理，没有检索或后处理。

## 四、结果表，以及哪些不能直接比

博客里出现了两组不同数据范围的数字，必须分开读。

### 全集（3,619 条）

| 系统 | WER |
| --- | --- |
| 开箱默认 | 30.8% |
| 改进提示词（写明语言和字母表） | 23.8% |
| 微调后 | 11.8% |

博客称微调相对开箱减少约 62% 的转写错误。我复算：(30.8 − 11.8) ÷ 30.8 ≈ 61.7%，一致。

**但博客自己指出了这组数字的问题**：全集包含用来选提示词和检查点的 855 条调参数据。所以这组数字偏乐观，不是干净的泛化证据。

### 留出集（2,764 条，每个系统解码一次）

| 指标 | 最佳提示词基线 | 微调后 |
| --- | --- | --- |
| WER | 22.44% | 12.17% |
| 关键词 WER | 9.2% | 6.5% |
| 语义 WER | 10.0% | 7.6% |

相对降幅：(22.44 − 12.17) ÷ 22.44 ≈ 45.8%，与博客一致。博客称这是"提升能泛化到新说话人的最清楚证据"，我同意这个判断：它用了没参与选择的数据和没见过的说话人。

### 不能直接比较的地方

| 对比 | 问题 |
| --- | --- |
| 30.8%（全集默认）与 22.44%（留出集基线） | 数据范围不同，基线定义也不同（前者是开箱默认，后者是最佳提示词），不能拿来算"提示词带来了多少" |
| 11.8%（全集微调）与 12.17%（留出集微调） | 数据范围不同，11.8% 包含调参数据 |
| 提示词的收益 | 应当只看同一数据范围内的对比：全集内是 30.8% 到 23.8% |

这是读任何微调案例都要注意的事：先看每个数字用的是哪一批数据。

### 与其他系统的对比

在同一批留出说话人和同一个评分流程下，博客给出：

| 系统 | WER |
| --- | --- |
| 微调后的模型 | 12.17% |
| 一个开源医疗专用模型 | 13.79% |
| 一个常用的通用 ASR 模型 | 14.92% |

这三个差距约 1.6 到 2.8 个百分点。博客没有给出置信区间或显著性检验。2,764 条片段，差距是否稳定，无法从公开资料判断。

### 通用能力的代价

LibriSpeech test-clean 的 WER 从 1.54% 升到 1.69%，上升 0.15 个百分点。这是微调的通用英语退化，幅度很小。博客同时承认，医疗专用模型在品牌药名和诊断名称的精确匹配上仍领先，并指出下一步是收集医生念品牌名的真实录音。

## 五、把方法迁移到你自己的领域

不需要医疗场景，下面的流程对法律、金融、工业语音都成立。

### 第一步：先只改提示词

案例里仅仅在提示词中写明语言和字母表，全集 WER 就从 30.8% 降到 23.8%，没有训练任何东西。先做这一步，成本最低。

### 第二步：划分数据

1. 按说话人（或按录音来源）拆分，不要按片段随机拆。
2. 一部分用来选提示词和检查点，另一部分留着，每个最终系统只测一次。
3. 博客的建议是至少保留 100 条真实、已标注的片段用于选检查点。

### 第三步：设计写出形式与念出形式

列出你领域里"写法固定但念法多样"的术语：缩写、药名、型号、金额、日期。为每个术语准备：

- 目标写法（参考答案里的样子）。
- 一个或多个念法（给语音合成的文本）。

### 第四步：混合合成与真实数据

案例里合成语音约占一半以上，但配了带口音的真实英语和真实医疗录音。只用合成语音，模型可能学到合成声音的特点而不是真实环境。

### 第五步：训练近似的配方

- 编码器和投影层全量训练，语言模型用 LoRA。
- 多次运行用不同数据配比，最后对检查点做平均。
- 用解码后的调参集结果选检查点。

我没有运行过这个配方，所以不确定它在你的数据规模下的表现。

### 第六步：评测三类指标

| 指标 | 为什么 |
| --- | --- |
| 整体 WER | 总体质量 |
| 实体错误率 | 业务真正关心的术语 |
| 通用语音保留 | 防止过度专门化 |

案例的关键词 WER 和语义 WER 就是为了避免只看整体数字。

## 六、WER 为什么不够：一个小例子

下面是我用自己写的函数在本机算的两个例子（按空格分词，不做规范化）：

| 参考 | 假设 | WER |
| --- | --- | --- |
| the patient takes metformin twice daily | the patient takes met forming twice daily | 0.333 |
| hba1c is seven point two | h b a one c is seven point two | 1.0 |

第一行：药名被拆成两个词，6 个词里 2 处编辑，WER 是 0.333，但这个错误对业务的后果远比"漏掉一个冠词"严重。

第二行：把念出来的形式当作输出，和写出形式的参考比较，WER 高达 1.0，但模型其实"听对了"，只是没按约定的写法输出。

这两个例子说明两点：一是整体 WER 掩盖实体错误，二是**写出形式的约定必须在参考和输出两边一致**，否则评测在测写法而不是测识别。这也解释了案例为什么要单独设计"写出形式与念出形式"的训练数据。

## 七、局限与结论

案例的优点是评测设计相对干净：按说话人划分，留出集每个系统只测一次，报告了关键词和语义指标，还披露了通用能力的小幅退化，并承认专用模型在品牌药名上仍领先。

本文的限制：所有数字是 NVIDIA 自述，我只复算了两个相对降幅；没有打开博客链接的复现命令和教程；没有运行任何训练；案例只覆盖印度口音的医疗英语，不能推到其他语言或口音；合成语音的占比和声音多样性对结果的贡献，博客没有做消融。

下一步建议：先在你自己的领域用 100 条真实标注录音做一次只改提示词的对比，再决定是否值得投入微调。如果提示词改完差距已经够小，微调的收益可能不大。
