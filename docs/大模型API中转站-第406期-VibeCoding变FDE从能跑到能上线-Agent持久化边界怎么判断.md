# 从能跑到能上线：Agent 持久化边界怎么判断

很多 Agent 项目做到第二阶段，都会遇到一个比“模型能不能回答”更工程化的问题：到底什么要写数据库，什么可以放内存，什么以后重新生成就行？

最常见的回答是“重要的就保存”。问题是，“重要”没有统一定义，也没有办法验收。对一个页面来说，进度文字可能很重要；对一次退款流程来说，人工确认、动作参数和外部回执才是不能丢的证据。

真正需要判断的是四件事：数据丢失后能不能安全重建，重建后结果会不会改变，它是否影响外部动作和责任追踪，以及它是不是只能依附当前进程。本文用一套持久化边界检查方法，串起一个售后工单 Agent 的数据流，并说明从“有 Run 记录”走到“可恢复工作流”还需要补什么。

## 1. 一句话判断标准

要保存的不是所有中间数据，而是丢失后会改变结果、断掉证据链或造成重复副作用的状态。

可以先记住下面这句话：

```text
服务重启以后，系统还能回答什么？
```

如果系统无法回答“哪件事已经发生、谁确认过、任务做到哪一步、哪些动作不能再做、失败后从哪里继续”，数据库里即使有很多表，也还没有形成可靠的执行记录。

## 2. 五类数据边界

把数据分成五类，比直接争论“这条信息重不重要”更容易验收。

### 2.1 业务事实

业务事实是系统以后仍然需要相信、查询和约束的内容，例如：

```text
工单状态、订单标识、客户与负责人
人工确认结果和确认人
退款是否已经发起
外部系统返回的结果和状态
权限、版本和有效期
```

这类数据不能依赖模型记忆，也不能只放在当前对话上下文里。它们通常进入业务表、事件表或其他可靠存储。

### 2.2 执行证据

执行证据回答“系统当时做了什么”。它包括：

```text
一次 AI Run 的发起人、配置版本和状态
输入或关键输入的快照
模型输出快照和结构校验结果
工具调用事件、错误原因和取消信息
人工查看、修改、接受和拒绝记录
审计日志中的操作者、动作和结果
```

执行证据的重点不是保存所有 Token，而是保留足以解释结果、定位失败和复盘责任的字段。模型重新生成一段相似文本，不能替代当时那一次输出的证据。

### 2.3 恢复点

恢复点保存任务继续执行所需的最小状态，例如：

```text
当前步骤和已完成步骤
等待的条件
已确认的中间结果
下一步需要读取的输入
重试次数和恢复版本
```

Checkpoint 不是聊天记录备份，也不是把进程内对象全部序列化。它的目标是让另一个进程知道任务应从哪里继续，并且不重复已经完成的高风险动作。

### 2.4 派生数据

派生数据可以从已经保存的事实安全算回，例如：

```text
页面上显示的“正在分析中”
根据工单字段生成的筛选标签
从 Run 状态和事件算出的进度摘要
缓存的列表排序和只读统计视图
```

派生数据丢失以后，最多让页面重新计算、重新加载或短暂显示空状态。前提是来源事实仍然存在，而且重算不会改变已经发生过的业务结果。

### 2.5 运行时句柄

运行时句柄只在当前进程、连接或请求活着时有意义，例如：

```text
AbortController
Socket 连接
数据库连接池中的连接对象
当前 HTTP Response
进程内 Map
```

这些对象不能直接写入数据库。你可以保存“任务已被取消”这个业务状态，但不能保存一个 AbortController，期待服务重启以后还能控制旧请求。MDN 的 [AbortController](https://developer.mozilla.org/en-US/docs/Web/API/AbortController) 文档描述的是当前异步操作的取消接口，它不负责跨进程的任务恢复。

## 3. 四个可验收的问题

面对任何一条数据，不要先问“它看起来重要吗”，按下面顺序检查。

### 问题一：丢了以后能不能安全重建？

如果来源事实还在，重建只会恢复展示，不会改变业务结果，它可以作为派生数据或缓存处理。

```text
UI 进度：可以根据 Run 状态和事件重算。
筛选标签：可以根据工单字段重算。
列表摘要：可以从业务表和事件表重新聚合。
```

如果重建需要再次调用模型、再次查询一个会变化的外部接口，或者需要猜测当时的人工判断，就不能简单归为可重建。

### 问题二：重建以后结果会不会改变？

模型输出、检索结果、外部 API 返回和带时间条件的业务判断都可能变化。即使输入文字一样，模型配置、知识版本、提示词和外部数据变化，也可能得到不同结果。

因此，曾经影响业务决策的输出至少要保存结果快照、配置版本和来源标识。之后可以重新生成一个新版本，但新版本不能冒充原来的事实。

### 问题三：它会不会产生外部动作？

退款、发券、发消息、创建订单、修改工单和发送邮件都可能产生副作用。此时必须同时考虑：

```text
幂等键：同一次业务动作如何识别为同一件事？
参数快照：当时到底向外部系统提交了什么？
外部回执：外部系统接受、拒绝还是超时？
审计记录：谁在什么时间以什么依据发起或确认？
```

只保存“准备退款”这句话不够。服务重启后，系统必须知道请求是否已经送出、外部系统有没有成功，以及重试是否安全。

### 问题四：它是不是运行时句柄？

如果它依附当前进程或网络连接，就不要伪装成持久状态。AbortController、Socket、Response 和进程内 Map 可以帮助当前调用完成，但不能承担服务重启后的事实恢复。

它们真正需要持久化的是对应的业务结果：运行中、已取消、失败、已完成、等待人工，或者等待外部回执。

## 4. 一张持久化边界表

| 类型 | 例子 | 丢失后的判断 | 推荐处理 |
| --- | --- | --- | --- |
| 必须入库 | 业务状态、人工确认、模型输出快照、外部回执、幂等键 | 会改变结果或无法追责 | 业务表、事件表、审计表 |
| 可以重建 | UI 进度、筛选标签、缓存视图 | 来源事实还在且重算安全 | 查询时计算或异步重建 |
| 只能留内存 | AbortController、Socket、Response | 依附当前进程，跨进程没有意义 | 进程内管理，业务结果另行持久化 |
| 需要补齐 | Step、checkpoint、等待条件、worker lease | 多步骤任务无法从中途安全继续 | 工作流状态表和恢复协议 |
| 取决于风险 | 检索结果、草稿摘要、临时文件 | 是否影响决策、是否可复现 | 保存版本或明确标为派生数据 |

这张表不能机械套用。比如检索结果通常可以重新查，但如果它曾经被人工确认或用于生成对外回复，就应该保存当时的文档版本、引用和结果快照。

## 5. 用售后 Agent 串一次完整流程

假设用户提交了一条售后请求：

```text
这个耳机用了两天就坏了，我想退款。
```

Agent 可能要读取订单、检查售后规则、生成退款建议、等待人工确认，再决定是否调用退款接口。沿着这条流程，可以把数据边界看得更清楚。

### 必须保存的内容

```text
工单当前状态和订单关联
订单规则判断所使用的版本
本次 AI Run 的发起人、状态、模型和 Prompt 版本
模型给出的建议快照及失败原因
人工确认的操作者、动作、时间和草稿快照
退款动作的幂等键、参数和外部回执
审计日志中的谁、何时、做了什么和结果
```

这些数据丢失以后，系统可能重复退款、把旧规则当成新规则，或者无法证明是谁确认了什么。

### 可以重新生成的内容

```text
页面上的“正在分析中”
根据事件重新计算的进度条
按照工单字段计算的筛选标签
从已有事实聚合出的只读摘要
```

重新生成这些内容不会创建新的外部动作，也不会改变已经记录的业务事实。

### 只能留在内存里的内容

```text
当前 HTTP 请求的 AbortController
当前浏览器的流式连接
当前 HTTP Response
activeAiRuns：runId -> AbortController
进程内的请求尝试记录
```

它们可以服务当前请求的即时交互，但服务重启以后自然消失。正确的做法不是强行把 Map 序列化，而是让数据库里的 Run 状态和事件表成为跨进程可查询的事实来源。

### 多步骤场景还需要补什么

如果流程从“读取订单”走到“检查规则”“生成建议”“等待人工”“执行退款”，只保存一个 Run 状态通常不够。还需要明确：

```text
每个 Step 的状态、输入和输出引用
checkpoint 保存的下一步位置和等待条件
worker lease，避免两个 worker 同时接管任务
外部动作记录与回执
失败后的重试和人工接管协议
恢复时如何判断动作已经发生
```

这才是“可恢复工作流”的边界。Run 记录能说明一次执行存在，不等于系统已经能够从任意中断点继续。

## 6. 一个售后 Agent 项目的现状对照

下面按照一个企业售后工单 AI 工作台的现有结构来核对。这里的字段是项目盘点示例，实际项目仍应以代码、数据库迁移和运行日志为证据。

### 已经入库：Ticket

工单档案保存业务事实：

```text
业务状态
优先级
分类
版本
客户
订单
负责人
```

这些字段决定谁处理、按什么规则处理以及当前工单处于什么阶段，不能靠上下文回忆。

### 已经入库：AiRun 与 AiRunEvent

`AiRun` 可以保存：

```text
谁发起了这次执行
使用的模型和 Prompt 版本
当前状态、结果和失败原因
Token 用量
取消信息
```

如果调用链通过 4SAPI 这样的兼容入口接入多个模型，持久化层仍应保存实际模型标识、配置版本、Prompt 版本和调用结果摘要，不要只保存“经过了哪个网关”。入口名称不等于模型能力，具体模型和参数要以当前项目配置核验；模型重跑也不能替代旧输出快照。

`AiRunEvent` 保存执行过程中发生的事件。两者结合以后，系统能够追踪一次 AI 处理从开始到结束的大致过程，也能区分运行中、失败、取消和完成。

### 已经入库：人工确认与审计

`HumanConfirmation` 可以保存：

```text
人工动作
幂等键
payload hash
草稿快照
审核结果
```

`AuditLog` 保存操作者、动作、结果和摘要。它们共同回答：谁确认过，确认了什么，之后系统做了什么。

### 仍然只在内存里：运行时对象

当前进程里的对象可能包括：

```text
activeAiRuns：runId -> AbortController
aiRunAttempts：进程内请求尝试记录
```

这部分是合理的运行时设计，但必须清楚它的边界：重启以后 Map 消失，系统不能再依靠它判断业务事实。数据库里的 Run 状态应该能独立解释任务处于什么状态。

### 当前还缺少：完整恢复能力

如果项目还没有下面这些内容，就不应把它描述成完整的多步骤工作流系统：

```text
步骤级 Step 记录
checkpoint 和可恢复等待条件
退款、发券、消息等外部动作的回执
跨进程 worker 接管同一任务的 lease
恢复时避免重复副作用的协议
```

准确的工程结论应该是：项目已经保存 Run 状态、事件、人工确认和审计，但还没有完整的跨进程工作流恢复能力。

## 7. 模型重跑和任务恢复不是一回事

这两个概念很容易被混在一起。

### 模型重跑

模型重跑是重新创建一次计算。它可能使用新的模型配置、新的 Prompt、新的知识版本或新的外部数据，结果可以和上次不同。

```text
旧 Run：已经完成，结果和配置被保存。
新 Run：重新生成候选结果，拥有新的 runId 和版本。
人工：比较新旧结果，再决定是否采用。
```

重跑适合修复格式错误、尝试新提示词和生成候选答案，但不能覆盖旧结果，更不能在没有确认的情况下重复执行外部动作。

### 任务恢复

任务恢复是从原任务的已知状态继续执行。它需要知道哪些步骤已完成、哪些事件已经发生、下一步等待什么，并避免重新执行已经成功的副作用。

```text
原 Run：等待人工确认，已完成订单读取和规则检查。
恢复：从等待条件继续，不重新退款，不重新覆盖人工判断。
新进程：读取 checkpoint、事件和外部回执后接管任务。
```

没有 Step、checkpoint、lease 和动作回执时，系统只能重新开始或人工判断，不能把“重跑”包装成“恢复”。

## 8. 外部动作要单独建模

只把外部动作写成一个 Run 的结果，往往不够。可以为每个可能产生副作用的动作设计独立记录：

```text
action_id：系统内部动作 ID
run_id：所属 AI Run
idempotency_key：本次业务动作的幂等键
action_type：退款、发券、发消息等
payload_hash：提交参数的摘要
payload_snapshot：必要时保存脱敏后的参数快照
status：pending、sent、succeeded、failed、unknown
external_id：外部系统返回的 ID
receipt：外部回执或错误
created_at / updated_at：时间
```

其中 `unknown` 很重要。请求超时不等于外部动作一定没有发生。遇到这种状态，系统应该先查询外部结果或进入人工核对，而不是直接重试。

外部系统的幂等协议各不相同，具体字段和查询方式要以目标接口的官方文档为准。持久化边界的通用原则是：把动作意图、提交参数和外部结果拆开记录。

## 9. 持久化审计的执行顺序

对一个已有 Agent 项目做审计时，可以按下面顺序调查：

```text
1. 找到所有数据库模型、迁移和关键字段。
2. 找到进程内 Map、缓存、队列、全局变量和临时文件。
3. 沿一次任务从开始到结束画出身份、状态、事件、人工决策和外部动作。
4. 将每项归为业务事实、执行证据、恢复点、派生数据或运行时句柄。
5. 对每项回答四个判断问题，并记录代码路径或日志证据。
6. 找出会产生副作用的动作，补查幂等键、参数快照、回执和审计。
7. 模拟进程重启、worker 重启、请求超时和重复消息。
8. 输出必须持久化、可以重建、只能留内存和尚未确认四张清单。
```

调查结论要带证据：表名、字段、迁移文件、函数、变量、事件类型或日志样例。只写“这里应该持久化”是设计意见，不是完成审计。

## 10. 进程重启验收场景

不要只检查数据库里有没有数据，直接设计中断场景：

| 中断位置 | 重启后应该知道什么 | 不合格表现 |
| --- | --- | --- |
| AI 调用进行中 | Run 仍是运行中、失败或可安全取消 | 页面永远加载，系统不知道结果 |
| 模型已返回、尚未人工确认 | 输出快照、配置版本和等待状态 | 重启后只能重新生成一份新建议 |
| 人工已确认、外部动作未确认 | 动作意图、幂等键和待核对状态 | 重新点击可能重复退款 |
| 外部接口超时 | 结果未知，能查询或人工接管 | 把超时当失败直接重试 |
| Step 已完成、下一步未开始 | 已完成步骤和 checkpoint | 从第一步重跑全部流程 |
| 两个 worker 同时恢复 | lease 或锁定关系 | 两个进程同时执行副作用 |

每个场景都应该有预期状态、日志证据和恢复动作。只有完成这类演练，才能知道持久化设计是否真的解决了重启问题。

## 11. 一份可复制的 Codex Prompt

```text
请为我的 Agent 项目做一次“持久化边界审计”。

先不要修改代码。

请按下面顺序调查：

1. 找到所有数据库模型、迁移和关键字段。
2. 找到所有进程内 Map、缓存、队列、AbortController、全局变量和临时文件。
3. 梳理一次 Agent 任务从开始到结束产生的身份、状态、事件、人工决策和外部动作。
4. 把每项数据归为：业务事实、执行证据、恢复点、派生数据、运行时句柄。
5. 对每项判断并给出证据：
   - 丢失后能否安全重建？
   - 重建结果是否可能改变？
   - 是否可能重复外部副作用？
   - 是否影响审计、追责或人工恢复？
6. 每条结论给出文件路径、数据表、函数、事件类型或变量证据。
7. 单独找出退款、发券、发消息、创建工单等外部动作，检查幂等键、参数快照、外部回执和未知状态处理。
8. 最后输出四张清单：必须持久化、可以重建、只能留在内存、尚未确认。
9. 检查项目是否只有 Run 状态而没有 Step、checkpoint、worker lease 和恢复协议。
10. 如果缺少完整恢复能力，请明确写出，不要把现有运行记录描述成可恢复工作流。

输出格式：
- 先给出任务生命周期图。
- 再给出持久化边界表。
- 每一项附证据和风险。
- 最后给出最小补齐方案、重启演练场景和不应修改的运行时句柄。
```

这个 Prompt 的重点是要求 Agent 先调查再下结论，并且每条判断都回到代码和数据证据。它不能替代人工审计，也不能自动证明外部接口的幂等行为。

## 12. 常见错误

### 把“重要”当成唯一标准

重要是人的感受，安全重建、结果一致性、副作用和审计影响才是可以讨论和验收的标准。

### 把所有中间结果都写进数据库

这会让数据库变成聊天记录和调试垃圾场。先区分业务事实、执行证据和派生视图，只保存能改变未来判断或解释过去行为的内容。

### 只保存最终结果

最终结果无法说明使用了哪个规则、哪个 Prompt、谁确认过和中途是否失败。没有事件和版本，出错以后只能猜。

### 把 AbortController 当成任务状态

AbortController 只能取消当前异步操作。业务代码必须另行写入取消事件和 Run 状态，恢复逻辑也不能依赖旧对象还活着。

### 把模型重跑当成断点恢复

重新调用模型可以得到新答案，但不会自动知道旧步骤已经产生了什么外部动作。重跑必须产生新版本，恢复必须读取旧状态并避免重复副作用。

### 把一次 Run 记录当成完整工作流

Run 只能表示一次执行的总体状态。跨进程、长时间、多步骤和人工等待场景还需要 Step、checkpoint、lease、动作回执和接管协议。

## 13. 结论与限制

判断 Agent 项目是否需要入库，可以从四个问题开始：丢失后能不能安全重建，重建结果会不会改变，是否会产生外部动作，以及它是不是只能活在当前进程里。

业务事实、人工确认、模型输出快照、幂等键、外部回执和审计事件通常需要持久化；UI 进度、筛选标签和缓存视图可以在来源事实存在时重建；AbortController、Socket、Response 和进程内 Map 只服务当前运行时。多步骤任务则要进一步补齐 Step、checkpoint、等待条件、worker lease 和恢复协议。

这套判断不能替代具体业务的风险评估。涉及退款、订单变更、发券或消息发送时，必须根据目标系统的接口语义和实际演练验证幂等与回执处理。数据库表的数量也不能代表系统具备恢复能力，真正的标准是进程重启后，系统还能否解释过去、避免重复，并安全决定下一步。
