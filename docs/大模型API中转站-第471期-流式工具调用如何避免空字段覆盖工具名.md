# 流式工具调用如何避免空字段覆盖工具名

流式工具调用不是把一个完整 JSON 对象切成几段那么简单。一个事件常常只携带本次新增的参数片段，因此“字段未出现”和“字段出现但值为空”具有不同含义。转换器若把本应缺失的工具名序列化为 `"name":""`，下游在合并增量时可能把先前正确的工具名覆盖为空，最终无法分派工具调用。

这里聚焦流式响应的增量序列化与客户端重建，不依赖某个模型或网关的私有协议。

## 问题出现在哪里

OpenAI 的[流式响应文档](https://developers.openai.com/api/docs/guides/streaming-responses)说明 Responses API 使用 Server-Sent Events 持续交付事件。对于把一种流式协议改写成另一种协议的适配器，必须把“本次没有新增工具名”编码成**不输出 `name` 字段**，而不是输出空字符串。

这一差异曾在一个已合并修复中造成实际故障：[Issue #5631](https://github.com/Wei-Shaw/sub2api/issues/5631) 记录了参数增量反复出现空工具名的问题；[PR #5632](https://github.com/Wei-Shaw/sub2api/pull/5632) 通过为可选字段启用省略空值的序列化，并增加回归测试修复了它。该 PR 于 2026-08-21 合并。

下文的本地验证代码需要 Python 3.10 或更高版本，不依赖第三方包。

这个问题与模型是否会调用工具无关。即便上游生成了正确的工具调用，错误也可能发生在“把事件写成 JSON”和“客户端按事件重建状态”之间。因此排查要从事件序列开始，而不是只检查最终响应对象。

```text
上游流式事件
    -> 兼容层转换
    -> JSON 序列化
    -> SSE 分块发送
    -> 客户端按调用索引累积
    -> 工具分派
```

## 缺失、null 与空字符串不是一回事

流式协议中，字段的三种表述至少有下列不同语义：

| JSON 形态 | 常见含义 | 对工具名的安全处理 |
| --- | --- | --- |
| 没有 `name` 键 | 本次没有提供名称更新 | 保留先前名称 |
| `"name": null` | 明确的空值，是否允许由协议决定 | 默认拒绝或按协议处理，不能悄悄视为未更新 |
| `"name": ""` | 明确写入空字符串 | 对标识符而言应视为无效输入 |
| `"name": "exec"` | 提供工具名 | 设置或校验与此前值一致 |

很多语言的默认零值会掩盖这一区别。例如结构体字段默认是空字符串，序列化器又把所有字段都输出，便会把“转换器没有给名称”错误地变成“转换器要求客户端把名称清空”。[PR #5632](https://github.com/Wei-Shaw/sub2api/pull/5632) 的关键修复正是让参数增量中的空名称不被序列化。

## 先定义增量合并约定

一个可靠的约定很简单：

- 第一个工具调用事件给出工具名和空参数。
- 后续参数事件只给出 `arguments` 片段，不携带 `name`。
- 客户端仅在字段实际出现时更新对应状态；工具名为空的事件应被视为生产端错误，而不是正常增量。

下面的示例把该约定写成可执行检查。它同时演示了正确事件和错误事件的区别。

```python
def make_arguments_delta(index: int, fragment: str, name: str | None = None) -> dict:
    function = {"arguments": fragment}
    if name is not None:
        if not name:
            raise ValueError("tool name must be omitted, not sent as an empty string")
        function["name"] = name
    return {"index": index, "function": function}


def merge_tool_delta(state: dict, delta: dict) -> dict:
    function = delta["function"]
    if "name" in function:
        if not function["name"]:
            raise ValueError("received an empty tool name")
        state["name"] = function["name"]
    state["arguments"] = state.get("arguments", "") + function.get("arguments", "")
    return state


state = merge_tool_delta({}, make_arguments_delta(0, "", name="exec"))
state = merge_tool_delta(state, make_arguments_delta(0, '{"command":"pwd"}'))

assert state == {"name": "exec", "arguments": '{"command":"pwd"}'}
assert "name" not in make_arguments_delta(0, "{")["function"]

try:
    make_arguments_delta(0, "{", name="")
except ValueError:
    print("empty tool name rejected")
```

将代码保存为 `verify_stream_delta.py` 后，在空的本地测试目录运行 `python verify_stream_delta.py`。预期输出是 `empty tool name rejected`。示例刻意让生产端拒绝生成空名称；这比让下游默默猜测“空字符串是否等价于缺失”更容易发现转换错误。

## 按调用索引维护状态

一次响应可能同时生成多个工具调用，事件也可能交错到达。消费者不应只维护一个全局 `name` 和 `arguments`，而应按流事件中的工具调用索引分别累积。下面的示例演示两个调用交错出现时，后续参数增量仍不会影响彼此的名称：

```python
def apply_indexed_delta(calls: dict[int, dict], delta: dict) -> None:
    index = delta["index"]
    target = calls.setdefault(index, {"name": None, "arguments": ""})
    function = delta["function"]

    if "name" in function:
        name = function["name"]
        if not name:
            raise ValueError("empty tool name")
        if target["name"] not in (None, name):
            raise ValueError("tool name changed during one call")
        target["name"] = name

    target["arguments"] += function.get("arguments", "")


calls: dict[int, dict] = {}
apply_indexed_delta(calls, {"index": 0, "function": {"name": "read_file", "arguments": ""}})
apply_indexed_delta(calls, {"index": 1, "function": {"name": "run_query", "arguments": ""}})
apply_indexed_delta(calls, {"index": 1, "function": {"arguments": '{"sql":"select 1"}'}})
apply_indexed_delta(calls, {"index": 0, "function": {"arguments": '{"path":"a.txt"}'}})

assert calls[0] == {"name": "read_file", "arguments": '{"path":"a.txt"}'}
assert calls[1] == {"name": "run_query", "arguments": '{"sql":"select 1"}'}
print("interleaved delta checks passed")
```

将代码追加到 `verify_stream_delta.py` 后再次运行，预期最后一行是 `interleaved delta checks passed`。实际客户端的调用索引、ID 和事件名称可以不同，但“每个调用独立累积、名称只由明确的非空值设置”的规则不变。

## 在适配器中如何落地

如果适配器使用静态语言，工具名应建模为可选字段，而不是默认空字符串的必填字段。序列化时应遵循两条规则：

1. 首个携带工具定义的事件中，名称必须非空。
2. 仅含参数片段的事件不应序列化名称字段。

然后加入两个方向的回归测试：

```text
输入：第一个事件含 name=exec，第二个事件只含参数片段
断言：第二个 JSON 事件没有 name 键；客户端最终工具名仍为 exec

输入：第二个事件显式含 name=""
断言：生产端测试失败，或消费者在接收处记录协议错误
```

不要只测试最终模型响应。工具调用一般在模型输出后才由应用分派，空名称可能先表现为“未知工具”，随后又因被写进对话历史而导致下一轮失败。逐事件断言能把故障定位在序列化边界。

如果适配器使用 Go、Rust、Java 或 TypeScript，不必照搬 Python 代码，但应保留同样的状态表达能力：可区分“字段不存在”“字段存在且为合法名称”“字段存在但非法”。例如，序列化层可将名称表示为可选指针、可空联合类型或仅在有值时才写入对象。仅把字段类型改为字符串而不控制序列化行为，仍会重新引入空字符串。

## 将测试拆成三个层级

### 1. 序列化测试

直接对转换器输出的 JSON 断言，不要只对内存对象断言。测试要检查后续参数事件中确实**没有** `name` 键，而不是检查它的值为空。

```text
首个事件：{index: 0, function: {name: "exec", arguments: ""}}
后续事件：{index: 0, function: {arguments: "{"}}
错误事件：{index: 0, function: {name: "", arguments: "{"}}
```

第一个和第二个事件应通过；第三个应在生产端测试中被禁止，或在消费端显示为协议错误。

### 2. 重建测试

用与真实客户端相同的合并策略依次消费事件。断言最终名称仍是 `exec`，参数能够拼成可解析的 JSON。这个测试能发现“转换器输出看起来合理，但客户端合并规则不同”的情况。

### 3. 端到端工具分派测试

注册一个无副作用的测试工具，例如只返回固定 JSON 的 `echo`。流结束后，检查分派器收到的名称准确、参数可解析，并且没有额外的空名称调用。不要用删除文件、发送通知或修改数据的工具作为流式回归测试。

## 日志和指标应关注什么

生产日志不应该保存完整工具参数，因为参数中可能含路径、查询语句或用户内容。对排障真正有用的通常是以下字段：

| 字段 | 用途 |
| --- | --- |
| 请求关联 ID | 将同一响应的事件串起来 |
| 工具调用索引或临时 ID | 区分并行调用 |
| 首次出现名称的事件序号 | 检查名称是否被延迟或重复发送 |
| 空名称事件计数 | 作为转换错误的告警信号 |
| 每个调用的参数片段数 | 发现异常分块或无限流 |
| 流结束状态 | 区分正常完成、取消和网络中断 |

这些数据应仅记录计数、布尔值和短 ID。若必须关联名称，优先记录受控测试工具名，或对生产名称做白名单/摘要处理。

## 常见误区

### 把空字符串当作“没有变化”

这是最常见的错误。JSON 中键不存在、键为 `null`、键为 `""` 是不同状态。是否接受 `null` 取决于具体协议；但若工具名是标识符，空字符串不应被当作保留旧值的信号。

### 只记录最终拼接后的参数

参数正确并不能证明工具调用正确。日志至少应在测试环境记录事件序号、工具调用索引、是否出现 `name` 键以及名称是否为空；不要记录完整用户输入或工具参数。

### 用非流式测试替代流式测试

非流式响应会一次性得到完整对象，无法覆盖“后续增量是否错误带出默认值”的问题。必须分别验证 `stream=true` 与非流式路径。

### 允许后续事件改名

一个调用一旦被声明为 `read_file`，后续片段又变为 `run_query`，通常不是正常增量，而是索引复用、状态串线或转换错误。示例中的“名称只能从未设置变为一个非空值，之后保持不变”正是为了尽早发现这种情况。若具体协议允许重命名，应把规则写进显式的状态迁移测试，而不是放任覆盖。

### 把所有异常都当作可重试的网络错误

空字段属于请求或响应结构问题，重新建立相同流通常会得到相同事件。应先保留脱敏事件摘要、定位生成端或转换端，再决定是否重试。对已开始执行的工具调用，盲目重试还可能导致副作用重复。

## 发布前检查清单

- 首个工具调用事件是否含非空名称？
- 参数增量事件是否省略 `name`，而不是输出空字符串？
- 多个调用交错时，状态是否按索引或调用 ID 隔离？
- 序列化后的真实 JSON 是否经过断言？
- 流结束时，工具名和参数是否能被无副作用测试工具消费？
- 日志是否避免记录完整用户内容和工具参数？

## 限制与结论

不同 SDK 对流式事件的类型名称和对象结构可能不同，本文不要求所有客户端使用同一种字段名。需要保持不变的是语义：缺失字段不应被默认值伪装成显式更新。

当工具调用跨协议转换时，把可选字段建模为真正的可选字段，并把空值视为可测试的异常输入，可以避免一个很小的序列化细节在流式重建后变成整轮工具调用失败。把测试落在“真实 JSON 事件序列”和“客户端重建后的工具分派”两个边界，能比只检查最终文本更早发现问题。
