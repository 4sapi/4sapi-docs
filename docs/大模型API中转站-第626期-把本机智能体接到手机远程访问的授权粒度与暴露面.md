# 把本机智能体接到手机：远程访问的授权粒度与暴露面

在地铁上用手机看一眼 agent 跑到哪一步、顺手批一条命令，这个场景很实际。但它和普通的远程桌面不是一回事：你要连的是那台能改代码、能执行命令、手里握着模型凭据的机器。

所以真正该先问的不是"能不能连上"，而是"连上之后，那个客户端能做什么"。T3 Code 的远程访问文档把这件事写得很细，其中一条容易被忽略：不显式指定范围时，配对令牌拿到的是全部权限。

本文按"连接路径 → 授权粒度 → 暴露面 → 收紧步骤"整理。信息来自仓库的[远程访问文档](https://github.com/pingdotgg/t3code/blob/HEAD/docs/user/remote-access.md)，检索日期为 2026-11-02。我没有配对过任何设备，也没跑过任何命令。

## 一、先说一个前提

文档开头就写明：那台机器必须在工作时保持运行并且可达。这看起来是废话，实际是最常见的失败原因——远程连不上，多数时候不是配置错，而是宿主机休眠、关了桌面应用，或者根本没起服务。

文档还有一条相关说明：关闭桌面应用的最后一个窗口会停掉它的本地服务器；只保存登录不会启动服务器。换句话说，"我登录过了"和"它现在在服务"是两件事。

## 二、几条常见的连接路径

| 方式 | 怎么用 | 特点 |
| --- | --- | --- |
| T3 Connect | 桌面端在 Sharing & access 里登录并启用；命令行 `t3 up` 选它 | 不需要路由转发，靠账号把设备和环境关联起来 |
| 局域网或私有网络 | `t3 up --lan`，或 `t3 serve --lan` | 直接连宿主地址，需要能路由到它 |
| Tailscale HTTPS | 桌面端启用 Tailscale HTTPS，或 `t3 serve --tailscale-serve` | 走 tailnet 内的 HTTPS 地址 |
| SSH | 桌面端添加 SSH 环境 | 自动起服务并开端口转发 |

上面这四行是我按操作方式归的类。文档自己的枚举是六类：局域网、Tailscale、其他 VPN、公网 URL、SSH、T3 Connect——也就是说"其他 VPN"与"公网 URL"是本文表格里没单列的两类。这些路由可以同时存在，连接时会选第一条能回应的。

文档提到一个实际问题：Tailscale 的 `100.64.0.0/10` 地址段与 Cloudflare WARP 等其他 VPN 共享，所以这个段里的地址在没法确认时会被当作 VPN 处理。这类地址段冲突是排查"看着有地址却连不上"时的常见原因。

## 三、最该先知道的一条：默认授权是全部

这是本文的核心。

文档原文的意思是：不给 `--scope` 时，配对令牌和签发的 bearer 会话会获得**全部权限，包括管理访问与 T3 Connect 管理**。

也就是说，你在手机上完成配对之后，默认拿到的那个客户端，权限足以反过来改这台机器的访问设置。

### 还有一个连带风险

文档接着补了一句更关键的：因为主机上的终端、或者一个全权限的 agent，也能触达那些能力，所以一个不该管理访问的客户端，还需要同时不给 `terminal:operate` 与 `orchestration:operate`。

这句话的含义是权限不是完全独立的：只要客户端能开终端、或能让 agent 用全权限跑，它就绕过了上层限制。想真正限制一个客户端，得同时从这两条路都堵上。

### 范围长什么样

文档给出的范围示例：

| 范围 | 允许什么 |
| --- | --- |
| orchestration:read | 文档只给了名字，未给语义定义（我的理解是读取编排状态，未核验） |
| relay:read | 同上，语义未核验 |
| filesystem:read | 浏览主机文件、打开工作区文件、查看本地改动 |
| filesystem:write | 编辑文件、把计划保存到工作区 |
| source-control:write | 客户端直接做 Git 与 PR 操作：推送、切分支、克隆、删除 worktree |

这里有一个容易误读的点：文档明确 `source-control:write` **不约束任务内部行为**。也就是说，即使客户端没有这个范围，它启动的一个任务仍然可以在环境允许的范围内随意使用 Git。

所以"权限范围"管的是客户端自己能做什么，不是 agent 在任务里能做什么。后者是权限模式管的（见另一篇讨论批准策略的文章）。

### 怎么用

```
npx t3 pair --scope orchestration:read --scope relay:read
```

这是文档给出的形式：想要哪些范围就写几次 `--scope`，写了就替换掉默认权限。同一个选项在创建配对与签发会话的命令上也能用。

## 四、权限按路由区分

第二处容易出错的地方：权限不是按设备算的，而是按路由算的。

文档说得很明确：路由详情里显示的权限只对标记为"In use"的那条路由生效，其他路由不被检查；直连配对与 T3 Connect 有各自的会话，可能授予不同权限。

实际含义是：

- 你通过 T3 Connect 配对时给的是只读范围，不代表走局域网直连的那条路也只读。
- 那条权限只描述当前这条路由，别把它当成整台设备的权限。
- 想确认当前连接能做什么，要看那条正在使用的路由的权限，而不是笼统地看设备。

排查"为什么这个设备能做那件事"时，先确定它现在走的是哪条路由。

## 五、四处容易忽略的暴露面

### 1. 局域网模式下一个配对码挡着整个网络

文档原意是：开启局域网访问后，服务器会接受来自本地网络与 tailnet 的连接，此时只有一个配对码挡着这些网络上的其他设备。

这句话值得读两遍。它不是说配对码很弱，而是说防护的边界就是那一个码：同一网络里的其他人拿到链接或码，就能连上。所以配对链接的分享方式就是安全级别。

### 2. 配对码要当密码

文档专门写了一句：把配对 URL 与授权码当作密码，不要放进截图、日志或缺陷报告。

这条在实践里非常容易违反：远程排障时顺手截图，链接就在地址栏里。

文档还提到配对链接的分享限制：在设置里创建的链接，只有在创建它的客户端打开着 Sharing & access 页面时才能复制；离开或刷新页面就要重新生成。这个限制的方向是对的，但它不是加密保护。

### 3. HTTP 端点与"托管链接救不了不可达"

如果要用托管网页版，文档要求宿主有 HTTPS 端点。同时说明：托管配对链接不会把不可达的后端变可达，也不会把 HTTP 变成 HTTPS。

这两句合起来的意思是：想让网页端连上，安全传输要你自己解决。用明文 HTTP 在局域网里跑得通，但那意味着你审批命令、查看代码的流量也是明文。

### 4. 浏览器跑在 Chrome 沙箱里，但 root 下没有沙箱

远程访问会用到宿主上的无头浏览器。文档说它默认在 Chrome 的沙箱中运行，而 Chrome 无法以 root 启动沙箱，所以如果服务器以 root 运行，就要改成非 root 用户才能保留沙箱；也可以设置 `T3CODE_SERVER_BROWSER_SANDBOX=0` 关掉沙箱。

最后那个开关是应急用的，不是默认推荐。它做的事是降低隔离，不是提高便利。

## 六、一处和凭据生命周期有关的细节

文档提到：有活动连接的会话在访问凭据过期后仍会列在列表里。

这条对"吊销"这件事有影响：一个还在连着的会话，不会因为凭据过期就自动消失。所以清理时要做的是主动吊销会话，而不是等它过期。文档没有说凭据过期后能否重连，这一点我没有核验。

## 七、把权限收紧的可执行步骤

按上面的规则，一个偏保守的做法是：

1. **先决定给什么，再生成链接。** 先想清楚这个设备要做什么，用 `--scope` 只给需要的那几项。只读查看就用读取范围。
2. **确认没有拿到终端与编排写权限。** 如果要限制客户端的管理能力，除 scope 外还要确认它没有 `terminal:operate` 与 `orchestration:operate`。
3. **每个设备单独一条一次性链接。** 文档说明配对会授权该设备未来的连接，所以不要一条链接发多台设备。
4. **用局域网时先想清楚谁能到那个网络。** 只有一个码在挡，网络里还有谁，就等于潜在能有谁。
5. **需要网页端就先解决 HTTPS。** 不要指望托管链接替你加密。
6. **服务器不以 root 运行。** 否则浏览器沙箱失效，而你多半不会收到提示。
7. **定期在被控机的 Sharing & access 里吊销不用的会话。** 别等凭据过期。
8. **改权限要重新配对。** 文档明确：单纯重连不会改变权限，要给某台设备换权限，得用一条新的配对链接重新配对。
9. **截图前检查地址栏与配对信息。**

## 八、怎么验证权限真的被限制

配好之后，别只看配置界面，做一次反向验证：

1. 用受限范围配对一台设备。
2. 在这个设备上尝试一个应当被禁止的操作，例如修改设置或开一个终端。
3. 预期结果是被拒绝，而不是界面隐藏。文档提醒过：旧客户端可能显示服务端会拒绝的控件，所以"界面没有按钮"不能当证据。
4. 换一条路由再试一次。如果局域网路由的权限比 T3 Connect 宽，刚才的结论就不成立。
5. 记录结果，下次改动后再跑一遍。

第 3 步的预期有个前提：文档说新配对不带 `--scope` 时包含全部能力，所以如果你的反向验证没被拒绝，第一件事是确认这条会话当时到底带了哪些范围。

## 九、什么时候不该这么做

| 情形 | 原因 |
| --- | --- |
| 机器上放着生产凭据且没有隔离 | 远程客户端的权限上限就是你机器的权限 |
| 只能用明文 HTTP 且网络不可信 | 审批与代码内容都走明文 |
| 无法把服务从 root 改成普通用户 | 浏览器沙箱失效 |
| 团队共享一台机器 | 一台机器上的会话与授权会被多人共用，吊销粒度不够细 |
| 只想"顺手看一眼" | 这个场景的成本（配对、权限、暴露面）常大于收益 |

第二行与第四行是最常见的两个坑。前者是技术债，后者是组织问题。

## 十、限制与结论

远程访问这类功能的价值很直接，但它把"能改代码的进程"接到了网络上，所以授权粒度比便利性重要。三件事值得记住：默认配对拿到的是全部权限；权限按路由区分，不是按设备；局域网模式下只有一个配对码挡着同网络的其他设备。

本文的限制：没有配对过任何设备，也没有跑过任何命令，所有行为描述来自文档；没有核对 T3 Connect 服务端的实现与托管方式；没有验证各范围在实际版本里是否都已生效；`--scope` 的具体可用清单以命令的 `--help` 为准。

下一步建议：先在一台不含生产凭据的机器上走一遍第七节与第八节，把"被拒绝"这个结果真正看到一次。看到之后，再决定要不要把同样的配置用到主力机器上。
