# 企业 AI 如何评估与治理：从试点到 90 天落地

企业 AI 项目最容易出现两个极端：一边只看模型回答得像不像，另一边一开始就设计一个覆盖全公司的复杂治理平台。前者无法证明业务价值，后者往往在真实用户开始使用之前就消耗了大量时间。

更实用的做法，是从一个风险可控的试点开始，同时记录效率、质量、采用和业务影响；把数据权限、人工确认、版本、日志、回滚和责任人写进流程，而不是等系统出错以后再补。

本文提供一套适合早期企业 AI 项目的评估与治理框架。它不承诺某个固定周期一定上线，而是把 90 天作为一个可调整的工作节奏：前期建立基线，中期小范围运行，后期依据证据决定扩量、修改或停止。

## 1. 先把“有效”拆成四类指标

AI 项目不能只看生成质量。至少要同时记录四类指标。

### 效率指标

```text
单次任务耗时
每周节省的人工时间
单位时间内处理的任务数量
等待和返工所占的时间
交付周期
```

效率指标需要有试点前基线。比如原来整理一份周报需要多久，接入 AI 后减少的是资料整理、初稿撰写还是审核等待？没有前后对照，就不能把“用了 AI”写成效率提升。

### 质量指标

```text
事实错误率
人工修改比例
重要信息遗漏率
引用或来源缺失率
越权回答和不应回答的比例
客户投诉或内部退回情况
```

质量指标必须和任务目标对应。客服草稿要关注政策依据和升级条件，会议纪要要关注行动项和负责人，用户反馈分类要关注重复合并和重要问题遗漏。不能用一个“看起来不错”的总分覆盖所有风险。

### 使用指标

```text
实际打开工具的用户数
完成一次完整任务的次数
接受、修改、拒绝和回到旧流程的比例
连续使用情况
用户主动反馈的问题类型
```

有调用量不代表有价值。员工可能因为培训要求打开工具，却在下一步全部复制回旧系统。真正要观察的是用户是否把它纳入原有工作路径。

### 业务指标

```text
客户响应是否更及时
销售线索是否更容易跟进
内容审核周期是否变化
产品反馈是否更快进入评审
错误和风险是否减少
```

业务指标通常受很多因素影响，不能把一项变化全部归因于 AI。要记录观察周期、参与范围、同时发生的流程变化和未解决的干扰因素。

## 2. 试点前先建立基线

一个最小基线记录不需要复杂数据平台，但必须足够支持前后比较：

```text
任务类型和样本范围
参与岗位和用户数量
原流程步骤
单次耗时和每周频率
人工修改、退回和遗漏情况
当前工具、数据来源和已知限制
由谁确认结果
```

如果不能取得精确数值，可以先使用抽样记录、操作日志、人工计时和结构化访谈，并标记测量误差。不要为了生成漂亮报表而编造基线。

试点完成后，使用尽量一致的样本和记录字段再次测量。指标变化只能说明当前条件下的观察结果，不能自动外推到所有部门和所有任务。

## 3. 把治理写成可以执行的规则

治理不是一份只在会议上阅读的原则文档，而是需要进入页面、接口、权限和日志的行为约束。

### 数据边界

先划分数据等级：公开资料、内部资料、客户数据、合同和财务数据、身份凭据以及法律或监管敏感信息。每一类数据要明确：是否允许进入模型、是否需要脱敏、谁可以查看、日志保存什么、保留多久。

### 人工确认

```text
资料整理和草稿生成：可以自动执行，但要保留来源。
对外回复和公开发布：必须由负责人确认。
金额、合同、客户承诺和订单变化：必须审批。
删除、权限变化和外部写入：需要明确授权和审计。
重大经营或人事决策：AI 只能提供分析材料。
```

人工确认要有真实状态，而不是在按钮上写“已完成”。系统应保存谁确认、确认哪个版本、确认前看到了什么，以及确认后发生了什么动作。

### 权限与最小访问

模型调用不能自动获得业务系统的全部权限。检索服务和工作流都应重新检查用户身份、部门、资源范围和当前动作。越权请求应被拒绝并记录原因，而不是让模型自己决定是否可以访问。

### 版本与变更

一次输出可能同时受到模型、Prompt、技能、知识和业务规则影响。至少记录：

```text
模型标识与配置版本
提示词或技能版本
知识资料版本
输入数据时间和来源
工具调用结果
人工修改与最终状态
```

如果系统通过 4SAPI 这类兼容入口调用模型，网关配置、实际模型标识和响应元数据也应进入可追踪的运行记录；具体模型清单和参数以当前环境核验，不把入口名称写成性能或稳定性承诺。

## 4. 让错误可以被发现和恢复

生产治理的核心不是保证模型永远正确，而是让错误尽快被发现，且能回到原来的安全流程。

每个试点至少要设计这些失败路径：

```text
模型超时：显示明确状态，允许有限重试或转人工。
输出格式错误：不写入下游系统，保留原始响应和错误原因。
资料没有答案：明确标记未知，不用通用知识补全企业规则。
权限不足：拒绝访问并保留审计事件。
外部系统失败：不重复执行有副作用的动作，进入待核对状态。
知识版本过期：停止使用或提醒负责人复核。
用户拒绝建议：保留拒绝原因，不强迫再次采用。
```

回退不只是“切换到旧模型”。还可能包括关闭自动建议、恢复上一版 Prompt、撤销一份知识版本、禁用外部写入、恢复手工流程和通知值班负责人。

## 5. 建立跨部门但足够小的推进团队

企业 AI 落地不应由技术团队独自承担。一个小型试点至少需要明确这些责任：

| 角色 | 需要负责的决定 |
| --- | --- |
| 业务负责人 | 场景是否真实、结果是否可用、是否继续扩量 |
| AI 产品负责人 | 流程、范围、优先级和验收条件 |
| 技术负责人 | 接入、部署、权限、日志、故障和回滚 |
| 知识负责人 | 资料版本、有效期、冲突和维护 |
| 风险或合规负责人 | 数据边界、审批、审计和保留策略 |
| 一线代表 | 真实使用、修改原因和旧流程对照 |

一个人可以承担多个角色，但不能让“谁负责”成为上线后才讨论的问题。尤其要明确谁有权暂停自动流程，谁可以批准扩大用户范围。

## 6. 一套 90 天试点路线

下面是一套可调整的工作节奏，数字是阶段安排，不是普遍上线承诺。

### 第 1—2 周：场景与基线

完成用户访谈、原流程记录、数据权限盘点和风险分类。选一个主要场景，定义输入、输出、人工节点和不做的范围。记录试点前耗时、质量和使用情况。

### 第 3—4 周：资料与验收集

整理与场景直接相关的知识，标注来源、版本、负责人和权限。准备正常、边界、信息不足、越权和服务失败样例，给出预期行为。

### 第 5—6 周：最小可用版本

实现最短业务路径：进入任务、取得输入、调用模型或工具、展示结果、人工确认、写回状态。接入日志、版本、权限和失败处理，不做与目标无关的平台功能。

### 第 7—8 周：小范围灰度

选择风险可控的用户和数据范围。记录任务完成、接受、修改、拒绝、转人工、回到旧流程和失败恢复情况。每日或每轮次整理主要问题。

### 第 9—10 周：修复高频问题

根据证据修改资料、Prompt、技能、页面和工作流。每次变更记录影响范围，并用固定样例进行回归。不要同时修改所有层，否则无法知道问题来自哪里。

### 第 11—12 周：做出扩量决定

比较基线与试点结果，检查权限、审计、回滚和采用情况。结论可以是扩大范围、保持当前规模、缩小范围、重新设计或停止项目。停止也是一种有效的工程决定。

## 7. 灰度记录表

```text
日期：
场景和版本：
参与用户与数据范围：
任务总数：
成功完成数：
人工修改数：
人工拒绝数：
转回旧流程数：
主要错误类别：
涉及的模型、Prompt、技能和知识版本：
是否触发回退：
用户反馈及证据：
下一轮只修改什么：
```

这张表的作用是把“大家感觉还行”变成可以复盘的记录。数据量少时可以使用表格维护，任务复杂后再接入日志和报表系统。

## 8. 扩量前的验收清单

```text
[ ] 真实用户知道什么时候应该使用 AI，什么时候回到旧流程。
[ ] 试点范围、数据权限和负责人已经写清楚。
[ ] 关键资料有版本、有效期、来源和维护人。
[ ] 固定样例覆盖正常、边界、越权、无答案和服务失败。
[ ] 模型输出、工具调用、人工动作和最终状态可以关联。
[ ] 结果不是直接写入高风险系统，或已有明确审批与回滚。
[ ] 超时、格式错误、权限失败和外部未知状态都有处理路径。
[ ] 关键指标有基线，观察结论没有超出样本范围。
[ ] 一线用户的接受、修改、拒绝原因已经被记录。
[ ] 有人可以暂停自动流程，并知道怎样恢复手工处理。
```

## 9. 可复制的 AI 试点评估 Prompt

```text
请对这个企业 AI 试点做一次上线前评估，不要只评价模型回答是否流畅。

请按下面顺序输出：
1. 复述业务目标、使用者、输入、输出和主要用户路径；
2. 列出试点前基线以及每个指标的来源；
3. 分别设计效率、质量、使用和业务四类指标；
4. 找出会产生金额、合同、客户承诺、权限变化或外部写入的步骤；
5. 检查数据权限、知识版本、模型配置、Prompt、技能和日志是否可追踪；
6. 列出正常、边界、越权、资料无答案、超时和格式错误样例；
7. 为每类失败给出发现信号、人工接管方式和回退动作；
8. 判断当前项目适合扩大、保持、缩小、重做还是停止，并给出证据；
9. 明确列出尚未验证的假设，不要把推断写成事实。

如果无法从现有代码、日志或访谈记录中得到证据，请标记为“未确认”，不要用模型常识补齐。
```

## 10. 常见治理误区

### 只看模型回答，不看业务链路

模型回答流畅，只能说明生成内容可读。它不能证明数据权限、引用依据、人工确认、外部动作和回滚都正确。

### 没有基线就宣布提升

试点后某项指标变化，可能来自用户培训、流程调整、参与人员变化或样本差异。没有基线和对照条件，应该写成当前观察，而不是普遍结论。

### 治理部门最后才介入

数据边界、审批和审计如果等到上线前才补，往往需要重写页面和接口。风险负责人应该在选场景时参与，而不是只负责最后签字。

### 没有暂停按钮

自动流程一旦进入生产，必须有人能关闭它、解释为什么关闭，以及如何回到旧流程。不能把所有问题都交给当班员工临时判断。

### 把使用率当成唯一成功指标

员工使用频繁可能是因为输出不可靠、需要反复重试。要同时查看接受、修改、拒绝、完成时间和回到旧流程的原因。

## 11. 结论与限制

企业 AI 评估要同时看效率、质量、使用和业务结果，治理要同时覆盖数据、权限、版本、人工确认、日志、失败处理和回滚。90 天路线的价值不在于承诺某个固定结果，而在于让团队按阶段留下基线、样例、运行记录和明确的扩量决定。

真正可以上线的试点，不一定是功能最多的项目，而是能够说明谁在使用、输入从哪里来、结果怎样判断、错误如何恢复、责任由谁承担，以及为什么值得继续投入的项目。

这套方法适合低到中风险的企业 AI 探索。涉及财务支付、医疗、人事、法律、重大客户承诺或自动外部动作时，应增加专业审查、严格授权和更强的审计与演练，不能直接套用普通内容生成项目的验收标准。
