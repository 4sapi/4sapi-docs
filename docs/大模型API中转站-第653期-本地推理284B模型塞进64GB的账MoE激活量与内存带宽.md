# 本地推理：284B 模型塞进 64GB 的账，MoE 激活量与内存带宽

一个 284B 参数的模型，被压到 56.56 GiB，装进一台 64GB 内存、没有独立显卡的机器，每秒吐 9 到 10 个 token。

这组数字来自 llama-modchip 的 README 与 ARCHITECTURE.md（Apache-2.0，v2.4.0，检索日期 2026-11-10）。**我没有下载模型，也没有跑过它的 bench，下面所有速度与质量数字都是项目自述。**

那这篇写什么？写它为什么可能成立，以及你自己算一遍的方法。

这类宣称最容易两头误解：一边觉得"CPU 跑 284B 是标题党"，另一边觉得"加根内存条就能替代显卡"。两种判断都跳过了中间那几本账。

## 一、四本账，别混着算

| 账 | 问题 | 决定什么 |
| --- | --- | --- |
| 容量 | 权重压到多少字节，装不装得进内存 | 能不能启动 |
| 带宽 | 每生成一个 token 要读多少字节 | 解码速度上限 |
| KV | 上下文变长后每 token 多读多少字节 | 长对话的上限 |
| 算力 | 预填充时要算多少次乘加 | 首字延迟（TTFT） |

项目文档里有两段话，点出这类估算最常见的两个错。

第一段：单 token 生成时，矩阵乘矩阵退化成矩阵乘向量，每个权重只用一次，算术强度约 1 FLOP/字节，于是 CPU 的计算单元大半时间在等内存控制器。**这说的是解码，不是预填充。**

第二段出自 FAQ：把单 token 的带宽公式套到 512 token 的批量预填充上，或者假设 284.33B 参数全部按同一个位宽压缩，都是"常见的纸面错误"。

我第一版踩了第二个，下面把两个坑都标出来。

## 二、容量账：1.71 bpw 是被内存逼出来的

先算最硬的一本。DeepSeek-V4-Flash 是 284.33B 总参数、13.17B 激活的混合专家模型，43 个 MLA 层，256 个路由专家加 1 个共享专家。

按位宽乘参数量，再除以 8：

- BF16（16 bit）：284.33e9 × 16 ÷ 8 ≈ 569 GB，约 529 GiB。
- 4 bit：约 142 GB，约 132 GiB。
- 1.71 bpw：284.33e9 × 1.71 ÷ 8 ≈ 60.8 GB，约 56.6 GiB。

项目给的文件大小是 56.56 GiB，也就是 60,730,782,208 字节。反算一下有效位宽：

```
60,730,782,208 × 8 ÷ 284.33e9 ≈ 1.7086 bpw
```

所以 1.71 是四舍五入值，对得上。这个"低"本身是分层压缩的结果，不是所有层都用 1.71。

真正的问题不是"能不能压到 1.71"，而是**为什么原来那个 76.87 GiB 的量化版不行**。

64 GiB 内存（常说的"64G"）的机器，Linux 下可用内存约 62.5 GiB。76.87 GiB 装进去只能靠交换或页缓存抖动——项目说要么抖动，要么被 OOM 杀掉。压到 56.56 GiB 后加上 256K 的 KV，项目报总常驻 58.9 GiB（README 另一处写峰值 57.61 GiB，口径不同），卡在可用内存内，swap 为零。

**我从这两个数字倒推一个判断：1.71 bpw 这个位置是被 62.5 GiB 这条硬线挤出来的。** 换一台 256GB 的机器，你大概不会选这个档。

## 三、带宽账：上限是算出来的

这本账决定你会看到 4 tok/s、9 tok/s 还是 40 tok/s。

硬件参数：双通道 DDR5-5600，理论峰值 89.6 GB/s。可持续带宽两种口径：ARCHITECTURE 写 72 到 76，FAQ 写 71.7。取 75 估算，上限会偏乐观几个百分点，不影响结论。

dense 30B 模型在 Q4_0 下约 17 GB，每个 token 都要全读一遍：

```
75 GB/s ÷ 17 GB/token ≈ 4.4 tok/s
```

MoE 30B-A3B 每 token 只激活约 3.0 到 3.3B 参数，约 1.8 GB：

```
75 GB/s ÷ 1.8 GB/token ≈ 41.6 tok/s
```

**同一个带宽，因为稀疏激活，上限差了将近十倍。** 混合专家在 CPU 上真正的价值不是算得快，是读得少。

现在套到 284B 那个模型上。先做一个粗算（这一步是我的推算）：

```
13.17e9 × 1.71 ÷ 8 ≈ 2.81 GB/token
75 GB/s ÷ 2.81 GB ≈ 26.7 tok/s
```

但 2.81 这个字节数是**下界**。1.71 是全模型平均位宽，而激活的参数里 MLA 投影按 3.75 bpw、共享专家按 4.5 bpw 上下，位宽高于均值；用它乘激活参数，等于假设两者同分布。

项目自己给了另一个数：`wo_b × wo_a` 这条纯线性链占"总 DRAM 流量的 31%"，合 991.6 MB/token。反推全模型每 token 流量约 3.2 GB。

```
75 GB/s ÷ 3.2 GB ≈ 23.4 tok/s
```

实测 9.06 到 9.95（默认无损 Top-6 档），效率大约四成。

**两个估算之间的 2.81 和 3.2，差值就是分层位宽的影响。** 这也说明为什么"用统一 bpw 乘参数量"只能当量级判断，不能当结论。

## 四、KV 账：上下文一长，上限自己会掉

上面两本账都假设上下文很短。真实使用里，KV 缓存会慢慢把带宽吃掉。

文档给了 Qwen3-30B-A3B 的例子：48 层、4 个 KV 头、128 维，Q4_0 量化下每 token 的 KV 是 27.65 KB。

- 16K 上下文：KV 共 453 MB，已经超过 CPU 的 64 MB L3，等于每生成一个 token 都要多读 453 MB。
- 128K 上下文：KV 共 3.62 GB，单 token 要读 1.8 GB 权重加 3.62 GB KV，合计约 5.42 GB。

```
75 GB/s ÷ 5.42 GB ≈ 13.8 tok/s
```

同一个模型、同一台机器，上下文从 512 涨到 128K，理论上限从 41.6 掉到 13.8。**"多少 tok/s"不写上下文长度，就没有可比性。**

这也是这类项目挑 Mamba-2 混合架构的原因：30B 的 Nemotron 在 256K 下 KV 只占 432 MB，比标准 GQA 的混合专家小一个数量级。

## 五、算力账：预填充是另一回事

解码在等内存，预填充在等计算——这是两本完全不同的账。

FAQ 里给了干净推导：预填充跑 512 token 一批的 GEMM，即使整个 17.59 GiB 的所有专家都碰一遍，权重也只流一次，摊到每 token：

```
17.59 GiB ÷ 512 token ≈ 35.2 MB/token
306.8 tok/s × 35.2 MB ≈ 10.8 GB/s
```

再看算术强度：从单 token 的约 1 FLOP/字节，抬到 512 批的 160 FLOP/字节以上。**这时候瓶颈已经不是内存，是 AVX-512 的计算单元。**

所以预填充能到 241 到 306.8 tok/s，而解码只有二十几。两个数字不矛盾，它们由不同资源决定。看一个宣称时，先分清它说的是哪一头。

## 六、量化：压哪些层，留哪些层

1.71 bpw 不是统一位宽，而是一张分工表：

| 部分 | 位宽处理 |
| --- | --- |
| embeddings、dense L0、43 个共享专家、MLA 的 kv_a / q_a / wkv_b | Q4_K / Q5_K / F32 |
| MLA 投影（README 简写 wq_b 与 attn_output；完整清单还含 compressor/indexer，合计约 11.8B 参数） | Fractal-64（3.75 bpw） |
| 256 个路由专家主体 | IQ1_S（1.5625 bpw）为主 |
| 敏感的边界层 | IQ2_XXS（2.06 bpw）、IQ1_M（1.75 bpw） |

规律很清楚：**共享的、每个 token 都要走的、影响数值稳定性的部分保精度；稀疏激活的、每次只碰一小部分的专家压到极限。**

很多量化实践失败的原因，就是把所有层一视同仁地压。

## 七、稀疏还能再省：Top-K 的代价

MoE 每 token 只走部分专家，这个"部分"可调。项目给了四档：

| 配置 | 余弦 | KL（nats） | top-1 | 纯解码 |
| --- | --- | --- | --- | --- |
| Top-6 无损（默认） | 1.00000 | 0.0000 | 100% | 9.06–9.95 |
| Top-5，L2 求积 | 0.99714 | 0.0042 | 95.8% | 9.68–9.87 |
| Top-5 + 门控优先 SwiGLU | 0.99385 | 0.0531 | 100% | 10.15 |
| Top-4 + 门控优先 SwiGLU | 0.99126 | 0.0281–0.0694 | 100% | 10.12–10.74 |

读这张表要注意四件事。

第一，**第一行不是"量化没损失"的证明**。README 写明这些数相对"未打补丁的 Top-6 执行"测，即同一检查点关掉剪枝自比。对比原始 76.87 GiB 版本的另一数是 top-logit 余弦 0.9964。

第二，四行不是单一变量：第二与第四行还差 SwiGLU。

第三，**余弦更低但 top-1 更高的现象从第三行就开始了**——同样 100% top-1，余弦却比第二行低，更像 SwiGLU 带来的，不宜归因到 Top-K。

第四，架构文档 Top-4 的余弦是 0.99587，与 README 的 0.99126 不一致；top-1 样本量未披露，4.2 个百分点不宜过度解读。

项目结论很硬：Top-4 是物理甜点，没有微调不要压到 2 以下。背后是它记录的失败实验。

## 八、单 token 的时间花在哪

这张表来自 30B-A3B 模型 N=1（不投机）的性能计数器剖析——**不是 284B 的数据，284B 的同级拆解文档里没有**：

| 阶段 | 优化前 | 优化后 |
| --- | --- | --- |
| 总耗时 | 58.8 ms（17.0 tok/s） | 39.5 ms（25.3 tok/s） |
| 裸 DDR5 内存读 | 26.0 ms（44%） | 25.2 ms（64%） |
| TLB 与四级页表遍历 | 14.0 ms（24%） | 0.8 ms（2%） |
| 位解包与 AVX shuffle | 11.0 ms（19%） | 6.5 ms（16%，VNNI 8x8 计算） |
| SSM 扫描、注意力、线程迁移 | 7.8 ms（13%） | 7.0 ms（18%） |

注意顺序：优化前第二大开销不是计算，是**页表遍历**（14 ms），用 9,300 个 2MB 大页后降到 0.8 ms。第三大开销是位解包——量化省下的内存要用 CPU 指令还回去。

优化后的结构才是常态：**64% 时间在等内存**，计算占 16%。项目那些手段——非临时加载、寄存器分块、投机解码——本质是同一件事：让每一字节读得更值。

## 九、给你自己的机器估个数

不用下载模型，四步判断值不值得试。

**第一步，算容量。**

```
字节数 ≈ 参数量 × 位宽 ÷ 8
```

留出 KV 与运行时开销。经验上模型文件别超过可用内存的 80%，否则页缓存与 swap 会把速度打到个位数。

**第二步，算每 token 字节数。** 用激活参数量，不用总参数量；如果坚持用平均位宽，记得那是个下界。

```
每 token 字节 ≈ 激活参数 × 位宽 ÷ 8
```

**第三步，估上限。**

```
上限 ≈ 可持续带宽 ÷ 每 token 字节
```

双通道 DDR5 按 60 到 75 GB/s 保守估，四通道翻倍，八通道再翻；项目在 8 通道平台报的单流解码约快三到四倍。实测通常是上限的四到六成，这是经验区间。

**第四步，加上下文修正。** 每 token 的 KV 大小乘以上下文长度，加到每 token 字节里再除一次。长上下文场景下，KV 会变成主要开销。

上限低于 3 tok/s，交互式就没戏，只能批处理。

## 十、结论与边界

这套东西成立的前提是三件事：模型是稀疏激活的混合专家、权重能压到装进物理内存、你接受"解码由带宽决定"。

我的判断：对已经有大内存机器、又需要数据不出内网的人，这条路值得算一遍；对需要稳定低延迟、或者依赖长上下文的场景，先按第四节的算法把 KV 账算清楚，再决定。

限制：速度与质量数字都是项目自述，未复现；第三节 2.81 是字节下界，除出的 26.7 是速度上限，3.2 与 23.4 由项目流量占比反推，"四成效率"由此算出；58.9 与 57.61 GiB 两种口径并列；带宽 71.7 与 75 并存，取 75 偏乐观；第八节拆解只对 30B 成立。

下一步只做一件事：先跑 `check_cpu_readiness.py`（不下载模型），再用激活参数量套第三节公式。两个数出来，就不用再问"我这台能不能跑"。
