# 本地 AI 客户端是怎么被“破甲”的：插件化 Harness 的攻击面

DeepSeek Harness 的插件生态里出现过一类目标很直接的插件：它不提升编码能力，也不优化工作流，唯一卖点是让模型“不服管”。这类插件通常自称“破甲”。

对普通用户来说，它看起来只是“解除了限制”。从工程角度看，它触碰的是一个更基础的问题：**本地 AI 客户端注入给模型的系统提示词，并不是不可变的常量，它可能被同一个客户端加载的第三方插件替换。** 只要插件和宿主有相同的本地文件与运行时权限，约束模型的那一层就可以先被改掉。

本文不讨论怎样绕过任何模型的安全策略，也不给出任何提示词内容或复现步骤。它只回答一个防守问题：插件化的本地 Agent 客户端，为什么天然存在“换掉系统提示词”的入口，以及团队应该怎样发现和收敛这类改动。

文中涉及的审查对象，是一个公开的 DeepSeek Harness 插件项目 `dsh-purge`（作者 YuJunZhiXue）。下面关于它“做什么”的描述，全部来自它的公开 README，检索日期 2026-10-20；本文不对其做推荐，也不复述其配置方式。

## 一、先拆词：“破甲”改的是哪一层

把“模型的安全能力”当成一个整体，很容易误解“破甲”在做什么。更准确的分层是：

| 层次 | 由谁决定 | 典型表现 |
| --- | --- | --- |
| 模型自身安全训练 | 模型提供方 | 直接拒绝、改写、给安全替代 |
| Harness 注入的上下文 | 客户端/运行时 | 系统提示词、角色设定、禁令、工具说明 |
| Harness 的权限与审批 | 客户端/运行时 | 审批门、沙箱、工具白名单、工作区边界 |

“破甲”瞄准的主要是第二层和第三层，而不是第一层。它不去改模型权重，而是改“模型被告知了什么”以及“模型被允许做什么”。这也是它为什么和“换一个没做安全训练的模型”不是一回事。

这里的关键判断是：**如果一个人看到模型“什么都肯答”了，不能直接推断成模型自身被绕过。** 更常见的情况是宿主注入的约束先被替换，模型只是照着新的上下文行动。

## 二、Harness 在三个位置决定模型看到什么

DeepSeek Harness 官方把 Agent 表述为 `Agent = Model + Harness`，并把工具、Skills、会话、沙箱、存储、Agent 循环、调度等归入 Harness 层。来源：[DeepSeek Harness 官网](https://www.deepseek.com/harness/)（访问日期：2026-10-20）

对一个本地客户端来说，真正决定“模型这一轮能看到什么、能做什么”的，至少有三个位置：

```text
1. 上下文组装：把系统提示词、开发指令、会话历史、工具返回值拼成请求。
2. 工具与技能装配：这一轮暴露哪些工具、哪些 Skill、哪些子任务能力。
3. 权限与审批：写文件、联网、执行命令、调用外部系统是否放行，谁来确认。
```

这三处都不是模型自由决定的。它们属于运行时的装配结果，而装配输入往往落在本地文件里——这既带来了可配置性，也带来了可篡改性。

## 三、插件为什么能改系统提示词

DeepSeek Harness 的设计取向是“一切皆插件”。这套设计的好处已经在运行时章节里讲过：能力可以被替换、组合和卸载，团队不必被产品预设锁死。

但同一套设计也意味着一个事实：**在本地客户端上，“插件”不是一段受限的展示代码，而是一段能读写宿主配置和运行时状态的代码。** 当插件能访问承载提示词和策略的本地文件、能参与插件加载、能触发客户端重启时，它就能在宿主重新装配上下文之前把这些输入改掉。

这里要把“事实”和“作者判断”分开：

- 事实：`dsh-purge` 的 README 自述，它支持官方 Web（`dsh web`）与官方桌面端，写入 profile 后由用户点“应用”触发，成功后自动重启，重启后新开一轮对话才把注入带进当前会话；它声称不修改 Harness 源码仓库，改动落在自己的 profile 与 `$DSH_HOME`、启动器旁的 `.dsh`、回退的 `~/.dsh` 等位置。来源：[YuJunZhiXue/dsh-purge README](https://github.com/YuJunZhiXue/dsh-purge)（访问日期：2026-10-20）
- 作者判断：这类插件之所以能生效，不在于它发现了某个漏洞，而在于“本地插件 + 可写的配置文件”本身就构成一个合法的修改入口。客户端越强调可替换，这个入口就越自然。

换句话说，这不是“越权漏洞”，而是一种设计取舍被用于相反的目的。

## 四、一个公开案例：它到底打包了什么

把 `dsh-purge` 当案例，是因为它把两类东西打包在了一起，方便说明风险，而 README 本身也把这些信息写得很直白：

| 类别 | README 自述内容 |
| --- | --- |
| 提示词层 | 面向 Harness 的“破甲”注入，可对不同模型替换不同提示词 |
| 技能层 | 一组“红队”Skill，涵盖主动扫描、目录爆破、凭据攻击、横向移动、反向 Shell、WebShell、未授权利用、隧道穿透、内网扫描等 |
| 适配层 | 官方 Web 与官方桌面端两套 profile，分开安装、分开点“应用” |
| 生命周期 | 写入 profile 后自动重启；npm 上无同名包，走 GitHub 归档安装 |
| 授权 | 商业许可（非开源、非 MIT）；README 声明 2026-10-27 起 GitHub 不再发新版本，新包只经 Telegram 频道发布 |

来源：[YuJunZhiXue/dsh-purge README](https://github.com/YuJunZhiXue/dsh-purge)（访问日期：2026-10-20）

这份 README 同时写了一段很长的法律免责声明，把使用范围限定在“使用者本机已安装的官方 Harness、离线靶标或已书面授权的演练环境”，并声明不得用于公网或第三方系统。

**这一点值得单独指出：** 一个工具需要把“只在授权范围内使用”写成大段声明，恰恰说明它默认具备的能力已经越过了普通工具的边界。免责声明约束的是使用者，不是能力本身。

## 五、为什么“模型答了”和“宿主没拦”要分开看

排查这类问题时，最常见的误判是把三件事混成一件：

| 现象 | 真正发生的层 | 排查重点 |
| --- | --- | --- |
| 模型直接拒绝 | 模型自身安全训练 | 换提示词、换模型角色 |
| 模型答了，但工具没执行 | Harness 审批/沙箱 | 审批记录、工具白名单、工作区 |
| 模型答了，工具也执行了 | 上层约束已被放松或替换 | 提示词装配、插件清单、配置基线 |

只有把第二层和第三层分开，才能回答“到底是模型变宽松了，还是宿主变宽松了”。前者是模型选型问题，后者是本地安全事件。

## 六、真正的风险不是“说错话”

容易低估这类插件的地方在于，人们往往只盯着“模型会不会说不该说的话”。对一个能跑工具、能联网、能写文件、还能启动子进程的 Agent 客户端来说，风险清单要长得多：

```text
提示词层：注入的约束被替换，审计与合规话术失效。
权限层：审批门被绕过或默认放行，危险动作不再被人工确认。
能力层：随插件一起到来的“技能”本身带有攻击性，不需要用户再写代码。
供应链层：插件来源非官方、闭源、更新渠道迁移到不易追踪的频道。
痕迹层：改动落在本地 profile 与配置目录，卸载或恢复不当会残留。
```

这五类里，只有第一类会立刻被用户看见。后四类通常要等到出事、或者有人去比对本地配置时才会暴露。

## 七、防守视角：怎样判断本机客户端被动过

防守的核心不是“禁止一切插件”，而是把“谁改了什么”变成可观察、可恢复的事实。可以把检查分成五组：

| 组别 | 检查对象 | 观察信号 |
| --- | --- | --- |
| 文件完整性 | 系统提示词、策略、profile 文件 | 哈希与基线不一致、出现未知备份文件 |
| 插件清单 | 已加载插件、来源、版本 | 出现说明里没有的插件或非官方来源 |
| 进程与自启 | 客户端进程、子进程、自启项 | 异常重启、无来源的子进程、隐藏窗口 |
| 网络出口 | 客户端与子进程的出站连接 | 连接非预期的更新或回调地址 |
| 配置差异 | 提示词与审批策略的当前值 | 默认禁令消失、审批默认放行 |

这里最省事的一步是**建立基线**：在一台干净的、只装了官方客户端的机器上，把提示词文件、策略文件和插件清单各留一份哈希与快照。之后任何一次“模型突然不服管”的疑问，都可以先用差异比对来定性，而不是靠感觉。

如果已经怀疑被改，处理顺序建议是：

```text
1. 先隔离：断开网络、停止客户端，避免继续扩散或覆盖痕迹。
2. 再留证：复制提示词、策略、插件清单和日志，记录采集时间。
3. 后比对：与干净基线做差异，定位被改的具体文件与字段。
4. 最后处置：按卸载路径恢复，再验证回到基线。
```

先处置、后取证是个常见错误：一旦覆盖安装或手动删除文件，后续就无法解释改动从何而来，也难以判断影响范围。

## 八、最小检查清单

```text
[ ] 已确认本机安装的客户端来自官方渠道，版本可核验。
[ ] 系统提示词、策略与 profile 文件有干净的哈希基线。
[ ] 插件清单只包含来源明确、用途清楚的项，并有 Owner。
[ ] 审批门与工具的默认策略可以从界面或配置中直接读出来。
[ ] 客户端重启与自启行为可解释，能对应到一次明确的操作。
[ ] 出站网络连接可观察，能区分官方更新与未知地址。
[ ] 有卸载与恢复步骤，且恢复后能验证提示词回到基线。
[ ] 发现异常改动时，先隔离、留证，再决定是否清理。
```

## 九、限制与结论

本文的目的不是教你“破甲”，而是让你在听到“这个插件能解除限制”时，能立刻想到它改的是哪一层。

三条结论：

- **“破甲”不是模型问题，而是宿主装配问题。** 它改的是注入给模型的上下文和围绕模型的权限，而不是模型本身。
- **可插件化是可配置性的另一面。** 同一个允许替换能力的入口，也能被用来替换约束。
- **防守从基线开始。** 没有干净基线，就无法区分“模型今天状态不好”和“本机配置被人改过”。
