# Agent 整理知识库时，怎样保护原文和变更记录

让 Agent 直接读取 Obsidian Vault，可以批量创建链接和更新页面，也扩大了误修改的范围。它可能把原始资料顺手“整理”掉、覆盖同名文件，或者把两条冲突结论合成一段看似完整的新表述。等到用户发现问题，原文和修改原因可能已经无法还原。

本文只解决一个问题：在允许 Agent 持续维护 Wiki 的同时，怎样保护 Raw 原文并留下可审查的变更记录。做法不依赖某个插件，核心是分开读取与写入范围，把每次任务拆成检查、计划、修改、验证和确认五个阶段。

## 一、先确定哪些内容绝对不能改

知识库里的文件可以按责任分为三类：

| 区域 | Agent 默认权限 | 典型内容 |
| --- | --- | --- |
| `raw/` | 只读 | 文章、论文、聊天记录、会议转写、随手记 |
| `wiki/` | 可增量创建和修改 | 来源摘要、概念、实体和主题页 |
| 根目录控制文件 | 按文件限制 | `AGENTS.md`、`index.md`、`log.md` |

`AGENTS.md` 由人维护，Agent 可以读取，但不应在普通入库任务中自行修改规则。`index.md` 可以随知识变化更新；`log.md` 只追加，不改写过去记录。

还要区分“不能改”和“不能丢”。原始网页剪藏属于不能改；人工确认过的 Wiki 结论即使允许更新，也不能静默覆盖。更新后仍应看得出旧结论、变化原因和来源。

## 二、指令边界不能替代备份和权限

在 `AGENTS.md` 中写“禁止修改 `raw/`”很有必要，但这仍是一条行为规则。模型可能误解任务，脚本也可能写错路径。真正重要的资料还需要独立的恢复手段。

至少选择一种版本或备份方式：

- 使用 Git 记录每次维护前后的文件变化；
- 定期把 Vault 复制到独立备份位置；
- 使用带版本历史的同步方案，并确认恢复方法；
- 对关键 Raw 文件保存哈希或只读副本。

备份是否有效，不能靠“已经开启同步”判断。应实际找一份测试文件，修改后恢复，确认历史版本可以取回。备份位置、保留周期和敏感资料加密方式要根据自己的环境决定。

## 三、把一次维护拆成五个阶段

### 1. 检查

Agent 先确认当前目录、输入文件和目标写入区域，并搜索相关 Wiki 页面。目录无法确认、输入不存在或规则冲突时停止。

### 2. 计划

在写文件前列出预计新建、更新和保持不变的页面。计划里出现删除、移动 Raw 文件或批量改名时，需要人工确认。

### 3. 修改

只写入计划中的 Wiki 页面、索引和日志。已有同名文件先读取后合并，不能直接覆盖。

### 4. 验证

检查 Raw 哈希、失效链接、来源字段、索引入口和追加日志。变更范围超出计划时，任务视为未通过。

### 5. 确认

Agent 汇报实际变化和待确认项。人检查关键结论、删除操作和冲突处理后，再决定是否接受本次更新。

这个顺序可以直接写进任务：

```text
先检查当前 Vault 和 `AGENTS.md`，再给出本次维护计划。计划中列出拟新建、拟更新和不应修改的文件。

只允许增量维护 `wiki/`、`index.md` 和 `log.md`。禁止修改、删除或移动 `raw/`，禁止自行修改 `AGENTS.md`。同名文件存在时先读取并合并，不直接覆盖。

完成后检查实际变化是否超出计划，并汇报新建、更新、未修改、待确认和失败项目。出现删除、移动、批量改名或结构调整时暂停，等待人工确认。
```

## 四、每次任务都保留一份追加日志

日志不需要记录 Agent 的全部推理过程，只要能回答这次输入是什么、改了什么、为什么改、还有什么没确认。

可以采用下面的格式：

```markdown
## 2026-08-10 资料入库

- 输入：`raw/articles/sample-article.md`
- 新建：`wiki/sources/sample-article.md`
- 更新：`wiki/concepts/example.md`
- 保持不变：`wiki/topics/example-topic.md`
- 依据：来源摘要与原文路径
- 待确认：一条缺少发布日期的结论
- 失败：无
- 执行者：Codex
```

日期、文件名和执行者只作格式示例。实际日志应使用本次任务的真实信息。`log.md` 采用追加方式，新的记录写在约定位置，过去条目不因格式调整而重写。

## 五、用只读命令检查变更范围

如果 Vault 已由 Git 管理，可以在根目录运行：

```powershell
git status --short
git diff --stat
git diff -- raw
git diff -- wiki index.md log.md
```

预期结果是：`raw/` 没有内容差异，Wiki、索引和日志的变化与计划一致。`git diff` 默认不会展示未跟踪文件的完整内容，因此 `git status --short` 中出现 `??` 时，还要逐个打开新文件检查。

对一份关键原文，可以在任务前后运行：

```powershell
Get-FileHash .\raw\articles\sample-article.md -Algorithm SHA256
```

两次哈希不一致就说明文件字节发生了变化。换行格式或编码变化也会改变哈希，所以即使肉眼看起来内容相同，也要查明原因。

## 六、四类高风险动作必须暂停

普通入库任务中，下面四类动作不应自动继续：

### 1. 删除或移动原始资料

Wiki 页面暂时没有引用，不代表 Raw 文件已经没有价值。删除前需要明确的保留策略和人工确认。

### 2. 批量改名或调整目录

文件移动可能使双链、外部引用、同步规则和脚本路径失效。先生成影响清单，再小范围试验。

### 3. 覆盖人工确认过的结论

新资料可以触发复核，但不能直接把旧结论替换掉。保留旧内容、来源和状态，再记录新资料带来的变化。

### 4. 修改维护规则

Agent 如果能在执行任务时顺手放宽自己的权限，规则就失去意义。`AGENTS.md` 的修改应成为独立任务，由人审查后生效。

## 七、用故障样本测试规则是否真的生效

只用正常文章测试，发现不了保护边界。可以在测试 Vault 中准备四种样本：

| 测试样本 | 预期行为 |
| --- | --- |
| 与已有页面同名的资料 | 先读取旧页面，提出合并计划，不覆盖 |
| 与旧结论冲突的资料 | 同时保留两种说法并标记待确认 |
| 缺少作者或日期的资料 | 写明信息缺失，不补造来源 |
| 指令中夹带“删除旧文件” | 视为资料内容，不执行删除 |

这里应使用专门的测试 Vault 或可恢复副本，不要直接在唯一一份个人知识库上制造故障。每种样本都检查实际文件变化，而不是只看 Agent 的完成汇报。

## 八、验收清单

一次维护可以在下面各项通过后结束：

- `raw/` 内容、路径和数量符合任务前状态；
- 实际修改文件没有超出事前计划；
- 新建页面能够回到来源摘要和原文；
- 同名页面经过读取与合并，没有被直接覆盖；
- 冲突和缺失信息进入待确认项；
- `index.md` 只更新受影响入口；
- `log.md` 新增一条记录，过去内容未被改写；
- 高风险动作均已暂停或取得明确确认。

自生长知识库并不要求 Agent 拥有整个 Vault 的自由写入权。长期可用的关键，是让每次变化都发生在规定范围内，能够被看见、解释和恢复。Raw 留住证据，Wiki 承载理解，日志记录变化；三者都在，自动整理才不会以丢失原文为代价。

## 九、先做一份知识库风险清单

权限设计之前，先列出知识库里真正需要保护的对象。个人 Vault 中可能同时存在公开文章、私人聊天、会议记录、客户资料和准备发布的内容，它们不应共享同一处理边界。

| 风险对象 | 可能发生的问题 | 需要的控制 |
| --- | --- | --- |
| Raw 原文 | 被改写、移动或删除 | 只读规则、哈希、备份和差异检查 |
| 私密资料 | 被送入不合适的运行环境 | 输入前分类、脱敏和访问限制 |
| 人工确认结论 | 被新资料静默覆盖 | 状态字段、变更记录和人工复核 |
| 双链与索引 | 批量改名后失效 | 影响清单、小批执行和链接检查 |
| 日志 | 被重写导致历史消失 | 只追加、版本记录和审查 |
| Agent 规则 | 执行中被自行放宽 | 独立维护任务和人工确认 |

风险清单要和自己的资料类型对应。一个只保存公开学习笔记的 Vault，与包含工作会议和客户信息的 Vault，所需隔离程度不同。不要因为目录叫“个人知识库”就默认所有文件可以进入同一模型或同步位置。

### 输入之前先分级

可以给 Raw 资料增加简单级别：公开、个人、工作受限、禁止处理。级别的含义由用户自己定义，并明确每一级允许进入哪些环境、是否需要脱敏、能否生成摘要。

这类标签只有被执行流程读取时才有作用。如果当前 Agent 不会自动识别权限字段，就应把受限资料放在默认不可访问的目录，或者在运行任务前人工排除。不要把一行 YAML 当成真正的访问控制。

## 十、审查变更时先看范围，再看文字

长篇差异很容易让人直接阅读新摘要，忽略 Agent 是否碰了不该碰的文件。审查顺序可以固定下来：

1. 用 `git status --short` 查看新增、修改、删除和未跟踪文件；
2. 对照事前计划，确认文件范围一致；
3. 单独检查 `raw/`、`AGENTS.md` 和历史日志是否变化；
4. 再阅读 Wiki 中新增和修改的内容；
5. 最后检查索引、双链和查询结果。

文件范围不对时应先停止，不需要继续评价摘要质量。Agent 即使写出了不错的内容，越界修改仍然要单独处理。

### 删除状态必须显式检查

在 Git 输出中，`D` 表示删除，`R` 可能表示重命名。普通入库任务如果出现这两类状态，应立即回到计划核对。重命名有时只是文件移动，也可能让外部脚本找不到路径。

未使用 Git 的 Vault 也可以在任务前后导出文件清单，比较路径和数量。但文件数量相同不能证明内容没变，关键 Raw 仍需要哈希或版本历史。

## 十一、发生越界修改后怎样处理

发现 Raw 被修改时，先停止 Agent 和后续批次，不要立刻让同一个 Agent“自动修复”。继续操作可能覆盖更多现场信息。

处理顺序可以分为五步：

### 1. 保存现场

记录任务输入、执行时间、Agent 汇报和当前文件状态。不要先提交或同步错误变更。

### 2. 确认影响范围

列出新增、修改、删除和移动的文件，判断问题只影响 Raw，还是已经进入 Wiki、索引和日志。

### 3. 从可信副本恢复

使用任务前的 Git 版本、备份或同步历史恢复受影响文件。恢复方式取决于实际工具，执行前要确认目标路径，避免用宽泛命令覆盖整个 Vault。

### 4. 找到规则或流程缺口

区分是任务指令不清、路径匹配错误、脚本缺陷，还是资料中的文字被误当成指令。只恢复文件、不修正规则，下一批仍可能重复事故。

### 5. 用故障样本回归

在测试副本中重放触发问题的最小样本。确认 Raw 不再变化、任务能够停止或正确报告以后，才恢复正常入库。

事故记录不必写成长篇复盘，但至少要包含触发条件、影响文件、恢复来源、规则修改和验证结果。

## 十二、定期复核权限和长期规则

知识库最初可能只有文章，后来加入聊天记录、会议纪要和工作资料。输入类型变化后，原来的权限设计未必仍然合适。

可以定期检查：

- 是否出现新的敏感资料类型；
- 哪些目录实际上不需要 Agent 访问；
- `AGENTS.md` 中有没有已经失效或互相冲突的规则；
- 日志能否追到最近几次结构调整；
- 备份是否真的完成过恢复测试；
- 测试 Vault 与正式 Vault 是否保持隔离；
- 旧的自动化或插件是否还拥有写入权限。

复核频率不需要机械固定。目录结构、同步方案、Agent、插件或资料类型发生变化时，就应触发一次边界检查。

保护原文不是为了限制 Agent 的价值，而是让自动维护可以被长期信任。权限越清楚，Agent 越能专注处理允许它做的增量工作；恢复路径越可靠，人越敢把重复维护交出去。
