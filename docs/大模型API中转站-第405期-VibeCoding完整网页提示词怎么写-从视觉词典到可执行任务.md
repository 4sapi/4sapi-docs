# Vibe Coding 完整网页提示词怎么写：从视觉词典到可执行任务

很多 Vibe Coding 失败，不是 Agent 不会写 CSS，而是任务从一开始就没有被说清楚。用户只给一句“做一个高级的 AI 产品官网”，Agent 只好自己猜品牌、受众、页面结构、素材比例、按钮行为和移动端规则。最后虽然得到了一整页代码，却很难解释为什么这样排、下一步做什么，以及哪里算完成。

视觉词典的价值，不是让提示词堆满术语，而是把模糊审美翻译成可执行条件：用 Bento Grid 表达主次，用 Split-screen 组织首屏，用 Sidebar 承载分类，用 Modal 处理短流程，用状态和截图验收交互。真正高效的提示词，应该像一份小型网页任务书，而不是几句形容词。

本文提供一套从目标到交付的写法。示例会组合布局、页面结构、导航和常用组件，但重点放在“怎么交给 Agent 做”和“怎么判断它是否真的做对”。

## 1. 完整任务书的八个字段

一份能执行的网页提示词，至少包含八个字段。它们不一定要写成八个标题，但信息不能缺失。

```text
1. 角色：Agent 以什么身份工作，负责设计、前端、内容还是测试？
2. 目标：页面为谁解决什么问题，主要成功动作是什么？
3. 受众：访问者知道什么、不知道什么、使用什么设备？
4. 页面：需要哪些 URL、页面和核心区块？
5. 信息架构：用户先看什么，再看什么，如何返回和深入？
6. 视觉系统：布局、容器、字体层级、颜色、图片和间距如何约束？
7. 交互：导航、组件、表单、加载、错误、键盘和移动端如何工作？
8. 技术与验收：使用什么技术，如何运行，必须通过哪些截图和行为检查？
```

这八个字段的顺序也有意义：先说为什么做，再说做什么，最后才说怎么实现和怎么验收。如果一开始就规定“用三列网格和玻璃拟态”，却没有目标和页面路径，Agent 很容易把视觉方案当成产品方案。

## 2. 角色：让 Agent 知道自己负责什么

“你是一名资深设计师”仍然太宽泛。设计、实现、测试和内容整理是不同工作，最好直接写出阶段职责和输出物。

### 不够具体的写法

```text
你是一名顶级网页设计师，请做一个很有质感的网站。
```

### 更可执行的写法

```text
你同时承担信息架构师、产品设计师和前端工程师的职责。
先输出页面树、用户路径、区块清单和状态表；确认结构后再实现界面。
实现后启动开发服务，用桌面端和移动端截图复盘，并根据问题清单迭代。
不要在没有素材和业务事实的地方编造数据、客户名称或结果。
```

角色字段不是为了增加称谓，而是为了限定 Agent 的工作顺序。它应该让 Agent 知道先规划、再实现、再验证，也知道哪些内容必须等待用户提供。

## 3. 目标与受众：先决定页面服务谁

同一个 AI 产品，对开发者、运营人员和企业采购者的页面结构可能完全不同。提示词至少要交代三件事：访问者是谁，访问时最想完成什么，以及页面希望他完成什么下一步。

### 可复制写法

```text
目标：让潜在合作方在 2 分钟内理解这支团队能解决什么问题，并查看一个真实项目案例。
受众：产品负责人和技术负责人，桌面端阅读较多，也可能通过手机分享链接。
主要行动：先查看代表项目，再阅读解决过程，最后通过联系表单发起沟通。
次要行动：浏览 Notes 和 About，但不要让次要链接与主要行动竞争。
```

有了目标，页面中的每个区块才有判断标准。Hero 不是因为“首页应该有 Hero”才存在，而是为了在首屏交代身份、价值和下一步；FAQ 不是因为词典里有这个组件才存在，而是为了消除行动前的关键疑问。

## 4. 页面与信息架构：先画路线，再排区块

页面字段要写 URL、用途和主要入口。一个个人 AI 工具作品集可以这样定义：

```text
/                 首页，建立身份并展示代表项目
/work             项目列表，支持分类和分页
/work/project-a   项目详情，解释问题、过程、结果和复盘
/notes            文章列表，支持按主题浏览
/about            个人背景、能力和时间线
/contact          联系表单和常见问题
```

然后给每个页面写区块顺序，而不是只列组件名称：

```text
首页：Sticky Navbar -> Hero -> Featured Work -> Capabilities -> Notes -> Contact -> Footer
项目列表：Breadcrumb -> Page Header -> Filter Drawer/Sidebar -> Project Grid -> Pagination
项目详情：Breadcrumb -> Project Hero -> Overview -> Problem -> Process -> Outcome -> Reflection -> Related Work
联系页：Page Header -> FAQ Accordion -> Form -> Contact Details -> Footer
```

这里的箭头表达用户阅读路线，不是要求所有区块都做成同一种视觉样式。首页可以用 Bento Grid 突出代表项目，项目详情可以使用窄阅读列加宽幅媒体，项目列表可以用 Card 或 Masonry，布局要服从内容关系。

### 页面结构的三个检查问题

```text
用户是否能只看页面标题就知道当前页面任务？
每个区块是否给下一个区块提供了必要的上下文？
主要行动是否在首屏出现，并在内容读完后有合理出口？
```

如果答案是否定的，先改信息架构，不要继续给页面添加动画和装饰。

## 5. 视觉系统：把审美变成尺寸和关系

“简洁”“有设计感”“高级”不能直接被浏览器执行。视觉系统至少要写出布局关系、容器约束、层级和素材规则。

### 一个可执行的视觉段落

```text
整体方向：克制、清晰、偏编辑式的 AI 工具作品集，不使用无关的办公桌或抽象科技素材。
容器：正文最大宽度 1180px，长文阅读列控制在 680px 左右，左右留白随屏幕变化。
布局：首页用不对称 Bento Grid 突出代表项目；项目详情使用窄文案列和宽媒体区；设置和筛选使用 Sidebar 或 Drawer。
网格：桌面端 12 列，平板端 6 列，手机端单列；列间距和区块间距使用稳定的 CSS 变量。
层级：页面标题、区块标题、正文、辅助说明和按钮文字有明确字号与行高，长标题允许自然换行。
素材：优先使用真实项目截图和可检查的图片；为媒体提供尺寸、比例和 alt 文本，避免加载前布局跳动。
```

视觉规范还应该说明哪些东西不要做：不要平均九宫格，不要用绝对定位硬拼整页，不要让文字压在无法阅读的图片上，不要用大量渐变和阴影掩盖信息层级。限制越具体，Agent 越容易把“风格”转成代码行为。

## 6. 交互系统：把默认状态以外的情况写进去

网页提示词如果只描述页面静态状态，完成度通常会停在第一张截图。把关键组件按事件写出来：

```text
Navbar：桌面显示全局链接，手机收进 Hamburger；打开后焦点进入菜单，Esc 关闭并恢复焦点。
Tabs：切换同一上下文内容，当前 tab 使用 aria-selected；需要分享时用 URL 参数恢复。
Sidebar：桌面固定或 sticky，手机改为 Drawer；深层 URL 打开时自动展开当前父级。
Modal：打开、提交、loading、error、未保存确认和关闭后的焦点回收都要实现。
Accordion：标题是真实 button，使用 aria-expanded 和 aria-controls；错误内容不能静默消失。
Form：字段级错误紧邻输入框，提交中阻止重复操作，失败后保留用户输入。
Lightbox：支持关闭、上一张、下一张、Esc 和方向键，加载失败提供重试。
```

不需要给每个组件写一套复杂动画，但必须写清楚触发、反馈、结束和恢复。交互状态是网页任务的一部分，不是 Agent 完成默认样式后再临时补的细节。

## 7. 技术与验收：把“完成”定义出来

技术约束要足够支持实现和检查，但不要把不必要的工具名变成目标。可以这样写：

```text
使用项目已有的前端框架和组件方式，不引入没有必要的新依赖。
页面使用语义 HTML、CSS Grid/Flexbox 和响应式断点，保持现有构建命令可运行。
所有按钮和链接有明确的语义、可见焦点和可访问名称。
图片保留稳定比例和尺寸占位，加载失败时有可读的替代内容。
启动开发服务后，验证 1280px 桌面、768px 平板和 390px 手机宽度。
```

验收条件要写成可观察的事实：

```text
首屏能说明身份、价值和主要行动。
桌面端没有横向滚动，手机端没有被固定层遮挡的按钮。
纯键盘可以打开菜单、切换 Tab、完成表单、关闭弹窗并回收焦点。
直接打开 /work/project-a 能显示正确的面包屑、侧栏状态和详情内容。
表单加载、错误、成功状态都可见，错误说明能指导用户修复。
截图中无文字重叠、内容溢出、图片空白和按钮跳动。
```

验收要避免“整体感觉不错”这类无法复现的结论。每一条都应该能由截图、浏览器操作、控制台日志或测试结果证明。

## 8. 一份完整可复制的网页提示词

下面这份提示词可以直接作为一个独立任务书使用。使用时只需要替换品牌、内容和真实素材。

```text
你是一名同时负责信息架构、产品设计、前端实现和浏览器验收的 Agent。
请为“Northstar Studio”创建一个个人 AI 工具作品集网站。

一、目标与受众
目标：让潜在合作方在短时间内理解团队能力，查看一个完整项目案例，并发起联系。
受众：产品负责人、技术负责人和希望了解 AI 工作流的创作者；桌面端阅读较多，也会通过手机分享。
主要用户路径：理解身份 -> 查看代表项目 -> 阅读问题与过程 -> 查看结果 -> 发起联系。
主要行动：View Project；次要行动：Contact。

二、页面与信息架构
页面：Home、Work、Project Detail、Notes、About、Contact。
Home 顺序：Sticky Navbar、Hero、Featured Work、Capabilities、Writing、Contact、Footer。
Work 顺序：Breadcrumb、页面标题、分类筛选、项目网格、Pagination。
Project Detail 顺序：Breadcrumb、项目 Hero、Overview、Problem、Role、Process、Key Decisions、Outcome、Reflection、Related Work。
Contact 顺序：页面标题、FAQ Accordion、联系 Form、联系方式、Footer。
详情页提供 Anchor Link 目录；手机端目录改为可关闭 Drawer。

三、视觉系统
方向：克制、清晰、编辑式的技术作品集；不用无关的办公桌、宇宙或抽象蓝色光球素材。
容器最大宽度 1180px；正文阅读列约 680px；图片区允许全宽穿插。
首页使用不对称 Bento Grid，让一个代表项目占据最大视觉面积；项目列表使用稳定 Card Grid；图片组使用保留原始比例的 Masonry 或普通网格。
桌面端 12 列，平板端 6 列，手机端单列；使用 CSS Grid 处理页面二维关系，使用 Flexbox 处理导航和按钮组。
标题、正文、辅助文本和按钮有清晰层级；不使用负 letter-spacing，不让长标题被截断。
真实项目截图优先于装饰图；媒体提前预留比例，所有图片有准确 alt 文本。

四、导航与交互
桌面 Navbar 显示 Home、Work、Notes、About、Contact，当前页面用 aria-current="page"。
手机端使用 Hamburger Menu；button 有 aria-label、aria-expanded 和 aria-controls；打开后焦点进入菜单，Esc 关闭并恢复焦点。
Project Detail 使用 Breadcrumb 和 Anchor Link；滚动时当前区块状态可识别，固定 Navbar 不遮挡标题。
Work 使用筛选状态和 Pagination，筛选条件写入 URL query，页码使用 page 参数，刷新后可复现。
项目图片使用 Lightbox，支持关闭、加载、错误、上一张、下一张、Esc 和方向键。
联系表单支持 empty、focus、filled、loading、error、success、disabled 状态；错误与字段关联，失败后保留输入。
必要的确认流程使用 Modal；保存期间阻止重复提交，未保存修改关闭前二次确认。
FAQ 使用 Accordion，真实 button 正确设置 aria-expanded 和 aria-controls。
页面较长时显示 Back to Top，但不遮挡表单、底部导航或最后一条内容。

五、实现约束
先输出页面树、用户路径、区块清单、组件状态矩阵和文件修改计划，不要直接开始写代码。
使用项目已有框架、命令和依赖；如果需要添加依赖，先说明理由。
使用语义 HTML、真实 href、可见焦点和可访问名称；不要用 div 冒充 button 或 link。
支持 1280px、768px 和 390px 宽度，不出现页面级横向滚动。
使用 prefers-reduced-motion 控制非必要动画；自动播放默认关闭，动画不能阻止操作。
移动端适配 safe-area，固定导航、Drawer、Lightbox 和 Back to Top 不能互相遮挡。
不编造客户、数据、价格、评价、发布日期或项目结果；缺少内容时使用明确的待补素材占位。

六、执行顺序
1. 读取项目结构和现有样式，确认入口、构建命令和素材位置。
2. 输出页面树和状态矩阵，检查信息架构是否覆盖主要用户路径。
3. 先实现页面骨架和响应式布局，再填充视觉系统，最后实现交互状态。
4. 启动开发服务，分别用桌面和手机视口检查首页、列表、详情和联系页。
5. 使用鼠标、触摸和纯键盘完成主要路径；检查控制台错误、焦点、URL 和表单结果。
6. 输出问题清单，按“截图问题、行为问题、内容问题、可访问性问题”分类。
7. 修复问题后重新截图；每次只修改一组相关问题，并说明修改前后的差异。
8. 最终报告包含运行命令、页面路径、已验证事项、未验证事项和需要真实素材补充的地方。
```

这份提示词的核心不是字数，而是把目标、结构、状态和证据绑定起来。若页面规模很小，可以删去不适用的页面和组件，但不要删掉验收条件。

## 9. 如何让 Agent 分阶段工作

把整页任务一次交给 Agent，容易出现“代码很多、问题也很多”。更稳妥的方式是分成四轮，每一轮都有明确产物。

### 第一轮：信息架构

要求 Agent 只输出页面树、用户路径、区块顺序和内容缺口，不写视觉细节。此时重点检查页面是否真的覆盖用户目标，主要行动是否只有一个，详情页是否需要独立 URL。

### 第二轮：布局骨架

让 Agent 实现容器、网格、区块高度、媒体比例和断点，先用真实尺寸的占位素材。检查手机端重排、长标题、长按钮和空数据状态，不要过早调颜色。

### 第三轮：视觉与组件

再加入字体、颜色、图片、卡片、导航和交互组件。每个组件都要带上默认、loading、error、success、disabled 或 close 等适用状态。

### 第四轮：截图与行为复盘

让 Agent 启动服务并截取至少两种视口。截图用于发现重叠、留白失衡、图片裁切和层级问题；键盘和触摸用于验证焦点、关闭、滚动、表单和 URL。问题要具体到元素和动作，例如“390px 下 Drawer 底部应用按钮被浏览器安全区域遮挡”，不要只写“移动端不够好看”。

## 10. 一份可复用的失败反馈模板

当第一版不符合预期时，不要重新发送一段更长的形容词。使用结构化反馈：

```text
问题 1：390px 宽度的首页首屏中，Hero 标题与主要按钮重叠。
位置：Home / Hero / 右侧视觉模块。
复现：视口设为 390 x 844，刷新页面，等待字体和图片加载完成。
期望：标题、说明和按钮按纵向顺序排列，按钮完整可见，首屏仍能看到下一区块的开头。
约束：保留桌面端 Bento Grid；手机端改为单列，视觉模块放在主要行动之后。
验证：截图检查无重叠，Tab 顺序为导航 -> 标题后的主要按钮 -> 视觉模块中的链接。

问题 2：项目详情页点击目录后，标题被 Sticky Navbar 遮挡。
位置：Project Detail / Anchor Link。
复现：点击 Process 目录链接。
期望：目标标题滚动到导航下方，URL hash 更新，当前目录状态同步。
约束：保留平滑滚动，但在 prefers-reduced-motion 下关闭动画。
验证：鼠标、键盘 Enter 和直接打开带 hash 的 URL 都得到同一位置。

问题 3：联系表单提交失败后，错误只出现在 Toast 中。
位置：Contact / Form。
复现：提交无效邮箱或模拟网络错误。
期望：字段附近出现具体错误，输入值保留，提交按钮恢复可用，并提供重试。
约束：Toast 可以保留作为补充，但不能作为唯一错误信息。
验证：键盘焦点能到第一个错误字段，屏幕阅读器能读到错误说明。
```

反馈越接近复现步骤和期望行为，Agent 越容易修复真正的问题。只说“请更高级一点”，等于让它重新猜一次。

## 11. 截图验收表

| 检查面 | 桌面端 | 移动端 | 证据 |
| --- | --- | --- | --- |
| 首屏 | 身份、价值、主要行动层级清楚 | 标题和按钮不溢出，下一区块有提示 | 首页截图 |
| 布局 | 网格关系稳定，内容有主次 | 桌面关系合理重排为单列或两列 | 首页、列表截图 |
| 导航 | 当前页、面包屑和目录状态正确 | 菜单可打开关闭，安全区不遮挡 | 交互录像或操作记录 |
| 内容 | 详情页有问题、过程和结果 | 长文可以连续阅读，不被固定层挡住 | 详情页截图 |
| 组件 | Modal、Form、Lightbox 状态完整 | 抽屉和表单可滚动，按钮可见 | 状态截图 |
| 键盘 | Tab 顺序符合用户路径 | 虚拟键盘打开后仍能提交和修复错误 | 手工测试记录 |
| URL | 详情、分页、筛选可复现 | 分享链接打开后状态一致 | URL 样例 |
| 性能与稳定性 | 图片加载不让布局跳动 | 无横向滚动和明显内容闪烁 | 控制台和截图 |

表格中的“证据”很重要。它要求 Agent 交付的不只是源代码，还包括能够复查的页面状态和操作结果。

## 12. 何时应该删减提示词

完整任务书不等于把所有术语都写进去。下面几种情况应该删减：

```text
只有一个静态页面：不需要 Pagination、Command Palette 和复杂 Sidebar。
内容很短：不需要 Sticky Storytelling、Back to Top 和多层 Accordion。
没有真实媒体：不要假装已经有 Lightbox，先定义素材交付和占位比例。
没有后端提交：Form 可以先做前端校验和明确的未接入状态，不能伪造成功。
用户需要比较全部内容：不要用 Carousel 隐藏信息，改用网格或表格。
```

组件和页面结构都要服务于任务。少一个不必要的组件，往往比多一层装饰更能提高可读性和可维护性。

## 13. 模型协作时的边界

不同模型在规划、写代码、整理文案和视觉复盘上的表现可能不同。无论通过何种入口调用，都应该把任务拆成可检查的阶段，并保留浏览器截图、控制台日志和测试结果。4SAPI 可以作为模型入口示例，但具体模型、参数、上下文长度和可用工具必须以当前配置与实际验证为准，不能把入口名称写成能力承诺。

更重要的是，模型输出不能替代三类判断：业务事实是否真实，用户路径是否合理，页面在真实设备上是否可用。模型可以帮你生成候选结构和修复方案，最终验收仍然要回到页面、键盘、URL 和实际素材。

## 14. 常见失败：提示词很长，任务仍然模糊

### 术语很多，目标为空

提示词写了 Bento、Masonry、Glassmorphism 和 Motion，却没有说明访问者是谁。Agent 只能把词汇拼在一起，页面看起来复杂，但用户不知道先点哪里。

### 页面清单很全，用户路径断裂

Home、Work、Notes、About、Contact 都有了，但项目详情没有返回入口，联系表单没有回答常见疑问，导航也没有当前状态。完整页面数量不等于完整体验。

### 验收只看桌面首屏

桌面端一张截图无法证明菜单、表单、弹窗、分页和焦点工作。至少要验证一个完整用户路径，再覆盖移动端和键盘路径。

### 反馈只有审美判断

“太普通”“不够高级”“多一点科技感”不能直接转成修复动作。反馈应该指出元素、视口、复现步骤、期望和约束。

### Agent 自己编造内容

当真实项目截图、客户名称和效果数据缺失时，生成的案例内容很容易被误认为事实。应明确写出“待补素材”，并让页面在缺少内容时仍保持合理结构。

## 15. 结论：一份好提示词是一条可验收的工作流

Vibe Coding 的关键不是把一句话写得更华丽，而是把网页任务拆成 Agent 能执行、用户能复查的条件：谁在使用，为什么访问，需要经过哪些页面，区块如何排列，导航如何定位，组件如何反馈，移动端如何重排，完成后用什么证据验收。

布局负责安排空间，页面结构负责安排叙事，导航负责安排方向，UI 组件负责安排动作。把四层内容组织在同一份任务书里，Agent 才不会只完成一张静态海报，而更有机会交付一条可以浏览、操作和复盘的网页体验。

真正值得保留的提示词，应该能回答三个问题：下一步做什么，出了问题怎么修，什么证据可以证明已经做对。做到这三点，视觉词典才不只是灵感清单，而会变成一套可重复使用的生产流程。
