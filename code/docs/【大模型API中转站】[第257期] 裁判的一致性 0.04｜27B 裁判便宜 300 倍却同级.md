# 【大模型API中转站】[第257期] 裁判的一致性 0.04｜27B 裁判便宜 300 倍却同级

自动评测流水线通常会以"一个裁判模型"收尾，而多数团队**从未测过这个裁判与人工判断的一致性**。

这不是疏忽，而是因为它看起来没必要——裁判只是个判定器，模型够强就行。直到有一次真去测了，结果是一致性指标 **kappa = 0.04**。这个数字的含义接近于随机；而它同时在系统里持续产生判定，并成为所有下游评估与训练信号的基础。我在 4sapi（https://4sapi.com）上搭评测链路时，把这个审计配方固定成了上线前的必做项。

## 一、先把"一致性"测出来

审计的第一步极其简单：拿一批人工标注过的样本，跑一遍裁判，算一致性。

在一份生产环境的 text-to-SQL 流水线审计中，部署中的裁判与双人金标的一致性表现是：

| 测试集 | 一致性（Cohen's kappa） |
| --- | --- |
| 分歧富集集 | **0.04** |
| 均匀随机抽检 | **0.42** |

两个数字的差异本身也说明问题：**在随机抽检上 0.42 看起来"还行"，而在分歧富集集上只有 0.04**。原因在于随机抽检里绝大多数样本是容易的，裁判只要同意主流判断就能拿到不低的一致性；而一旦把注意力集中在真正有分歧的样本上，裁判的判别力就暴露了。

这给审计方式提了个要求：**必须使用分歧富集集**。只用随机样本评估裁判，会得到系统性偏高的结果，而分歧样本恰恰是裁判真正需要起作用的地方。

## 二、偏差的方向比大小更危险

kappa = 0.04 说明判别力不足，但真正造成损害的是偏差的**方向**：该审计发现裁判**过度标记了 77.1% 的人工判定为正确的案例**。

也就是说，裁判的倾向是把做对的结果判成做错。这个方向会造成连锁后果：

- 正确的模型输出被记为失败，评测分数被系统性压低；
- 如果这套判定用于筛选训练数据，正确样本会被错误剔除；
- 团队会去"修"一些本来不存在的问题，因为失败案例看起来真实存在。

对比另一种偏差方向——把做错的结果判成做对。那会导致分数虚高、问题被掩盖，同样有害，但至少不会让团队在错误方向上投入工时。两种方向都需要警惕，而在只看一致性指标时，方向是看不出来的，必须额外统计**假阳与假阴的分布**。

这一处也解释了为什么"裁判准不准"这个问法本身不够精确。更可操作的说法是：**裁判的假阳率与假阴率分别是多少**。两者对业务的影响完全不同——假阳浪费复核工时，假阴放过真实问题。选裁判时应当按业务更怕哪一种来定权重，而不是只看一个总体准确率。

审计中把这个机制命名为**评分等级幻觉**（grade-hallucination）：裁判并非随机出错，而是倾向于生成一个看起来有依据、实际与证据不符的判定。

## 三、成本结论比技术结论更重要

这份审计最有价值的发现是关于成本的。

替换裁判之后的结果是：**自托管的 27B 模型**（kappa = 0.72）落在了与**最强闭源裁判**（kappa = 0.71）相同的区间。原话是：在 n = 96 的样本量上两者对比功效不足，**但对部署决策而言这几乎不重要，因为自托管方案的每次调用成本约为前者的 1/300**。

这条直接改写了裁判选型的默认假设。通常的直觉是"裁判要准，所以用最强的"，但数据表明：**在裁判这个任务上，27B 级模型与最强模型处于同一水平，而成本差三个数量级**。原因不难理解——裁判是判定任务，输入已经被上游处理好，不需要复杂推理或长链条规划，因此能力需求低于主任务模型。

由此得到的操作结论是：裁判选型应当**独立于主任务模型选型**。用旗舰模型做业务推理、用可自托管的中等模型做裁判，是一个在质量与成本上都更合理的组合。

## 四、集成并不免费

一个自然的补救思路是"多裁判投票"。审计结果给出了反直觉的结论：**把弱裁判与强裁判配对反而降低了一致性**。

原因可以这样理解：集成的收益来自**成员各自都可信**时的误差抵消；如果成员中有明显不可信的，它的错误会污染整体判断，而简单多数投票无法识别谁是错的。

有效的形态是**同强度成员加严格路由**：三个强裁判在**全体一致**路由下达到 kappa = **0.79**，自动覆盖率 **89.7%**。注意这里的两个条件——成员强度相当，且采用全体一致（而非多数）作为自动判定条件，其余交给人工。

这与前面提到的替换方案对照很有意思：换一个自托管中等模型拿到 0.72、成本 1/300；换成三个强裁判全体一致拿到 0.79、成本至少三倍。**从 0.72 到 0.79 的这 0.07，要不要付三倍成本，取决于业务对判定误差的敏感度**——但至少现在的选择是清楚的，而过去只有一个默认答案。

## 五、域外测试会顺手发现问题

审计配方还有一个副产品：把同一套流程应用到域外数据上，会发现**金标本身的问题**。

在该审计的域外测试中，同一套配方把另一个数据集里**专家撰写的金标 SQL 标记出 25.5%** 属于候选问题。这不意味着那些金标真的错了——作者明确说明这是"在自有标注协议下的候选问题"——但它说明：**专家标注同样存在与判定协议不一致的部分**，而这部分会持续影响任何基于该金标的评测。

实践含义是，审计的对象不只包括裁判，也包括金标。当一个评测结果反复出现"模型与金标不一致"时，值得分出一部分精力去核对金标，而不是默认问题在模型侧。

## 六、裁判"无依据作答"怎么识别

另一类问题比一致性更根本：**裁判在自己没有依据的情况下，仍然给出自信的判决**。

一个多智能体验证框架的实测结果很极端：它在 **78%–95%** 的比较上判定"两个方案一样好"，准确率仅 **4.4%**，而同一个模型被直接询问时达到 **43.7%**。更简单的问题或更大的裁判模型都不改变这个结果。

原因在于验证方法对证据的两个隐含要求：

```text
条件一：证据必须独立于被审答案
条件二：证据必须在两个候选之间有所不同
```

检索文档场景下这两个条件自动成立；但在**代码评判**场景下，两个候选共享大量相同结构，条件二不再成立——证据无法区分它们，于是框架退化成"两者皆可"的默认输出。而这种输出**在外观上与有依据的判决完全相同**。

好消息是识别方法不需要标注：从流水线自身日志中可以提取两个**无需标签的测量**，用其中一个做门控后，流水线**拒答**它无法判断的比较，准确率从 **20.7% 提升到 36.9%**，同时仍然回答了一半的比较。

## 七、拒答门控：宁可不判

这条给出一个可直接套用的设计：**给裁判加一层"我无法判断"的出口**。

现在的裁判实现几乎都只输出判定结果，没有"弃权"这个选项。加上之后有两个立即收益：

- 准确率提升：拒掉无依据的比较后，剩余判定的准确率显著上升；
- 人工量可控：门控阈值可以调节自动覆盖率，把不确定的部分交给人，而不是让人去复核全部结果。

门控阈值的选择是一个典型的精度-覆盖权衡。审计中拒掉约一半比较换来 16 个百分点的准确率提升，这个交换在多数场景下是划算的——因为被拒的那一半交给人工，本来也是需要人工把关的部分。

## 八、审计配方

把上面的环节整理成一套可复用的配方：

1. 取一批人工标注样本，**其中必须包含分歧富集集**；
2. 计算裁判与金标的一致性（kappa 或等价指标），**两个测试集分别算**；
3. 统计假阳与假阴分布，**确认偏差方向**，而不只看总体一致性；
4. 用自托管中等模型替换，重新计算一致性；
5. 若需提升，试用三个同强度裁判加全体一致路由，并记录自动覆盖率；
6. 加拒答门控，调节阈值并记录准确率与覆盖率的对应关系；
7. 把同一配方应用于域外数据，检查金标自身的候选问题。

第七步常被忽略，但它成本极低——配方已经写好，只是换一份输入。

整份配方还有一个顺序上的建议：**先做第 1–3 步，再决定后面怎么做**。前两步会说明当前裁判是否真的不可信，第三步则说明偏差朝哪个方向。如果一致性本来就在 0.7 以上、偏差也不集中在某一侧，那后面几步（替换、集成、门控）都不必做，省下一整套改造工作。

## 九、接入示例

下面这段脚本实现裁判的一致性审计与拒答门控，两个测试集分开统计，并输出偏差方向。

```python
import os, json, itertools
from collections import Counter
from openai import OpenAI

client = OpenAI(
    api_key=os.getenv("FOURSAPI_API_KEY"),
    base_url="https://4sapi.com/v1",
)

JUDGE = os.getenv("JUDGE_MODEL", "qwen3.6-27b")
STRONG = os.getenv("STRONG_MODEL", "claude-opus-4-7")
CONF_FLOOR = float(os.getenv("CONF_FLOOR", "0.6"))   # 门控阈值


def judge(model, item):
    """返回 (verdict, confidence)。verdict ∈ {1 通过, 0 不通过, -1 弃权}。"""
    r = client.chat.completions.create(
        model=model, temperature=0,
        messages=[
            {"role": "system",
             "content": "判断候选答案是否与参考答案一致。"
                        "输出 JSON：{\"verdict\": 0或1, \"confidence\": 0到1}。"
                        "依据不足时必须给出 confidence 低于 0.6。"},
            {"role": "user", "content": json.dumps(item, ensure_ascii=False)},
        ],
    )
    try:
        obj = json.loads((r.choices[0].message.content or "").strip())
        return int(obj["verdict"]), float(obj["confidence"])
    except Exception:
        return -1, 0.0


def kappa(pairs):
    """Cohen's kappa：pairs = [(judge, gold), ...]，取值 0/1。"""
    n = len(pairs)
    if not n:
        return 0.0
    a = [(x, y) for x, y in pairs if x in (0, 1)]
    if not a:
        return 0.0
    po = sum(1 for x, y in a if x == y) / len(a)
    cj, cg = Counter(x for x, _ in a), Counter(y for _, y in a)
    m = len(a)
    pe = sum(cj[k] * cg[k] for k in (0, 1)) / (m * m)
    return (po - pe) / (1 - pe) if pe != 1 else 0.0


def audit(items, model=JUDGE):
    """items: [{"bucket":..., "gold":0/1, ...}]"""
    per = {}
    for it in items:
        v, c = judge(model, it)
        if v == -1 or c < CONF_FLOOR:
            per.setdefault(it["bucket"], []).append(("abstain", it["gold"]))
        else:
            per.setdefault(it["bucket"], []).append((v, it["gold"]))

    for bucket, rows in per.items():
        answered = [(a, b) for a, b in rows if a != "abstain"]
        abstained = len(rows) - len(answered)
        fp = sum(1 for a, b in answered if a == 1 and b == 0)   # 判通过但金标是否
        fn = sum(1 for a, b in answered if a == 0 and b == 1)   # 判不通过但金标是通过
        print(f"[{bucket}] n={len(rows)} 弃权={abstained} "
              f"自动覆盖={len(answered) / len(rows):.1%} kappa={kappa(answered):.3f}")
        print(f"          假阳(误判通过)={fp}  假阴(误判不通过)={fn}")


def ensemble(items):
    """三个同强度裁判全体一致才自动判定，否则弃权。"""
    models = [STRONG, os.getenv("STRONG2", "gpt-6-astra"), os.getenv("STRONG3", "claude-fable-5-1")]
    out = []
    for it in items:
        votes = [judge(m, it)[0] for m in models]
        out.append((votes[0] if len(set(votes)) == 1 and votes[0] != -1 else "abstain", it["gold"]))
    answered = [(a, b) for a, b in out if a != "abstain"]
    print(f"[全体一致] 自动覆盖={len(answered) / len(out):.1%} kappa={kappa(answered):.3f}")


if __name__ == "__main__":
    with open(os.getenv("AUDIT_SET", "./judge_audit.json"), encoding="utf-8") as f:
        items = json.load(f)
    print("=== 单裁判审计 ===")
    audit(items)
    print("=== 三裁判全体一致 ===")
    ensemble(items)
```

输出里最该关注的是那两行假阳与假阴。它们直接说明偏差方向——只有知道了方向，才知道该往哪边调整判定协议。第三行输出的自动覆盖率决定了人工复核的工作量，这是这套方案能否长期运行的关键。

## 十、成本与风险提示

- **审计样本必须包含分歧富集集**，否则一致性会被系统性高估。
- **偏差方向要单独统计**，只看总体一致性会掩盖最有害的那类错误。
- **裁判选型独立于主任务模型**，中等模型在判定任务上常与最强模型同级，成本差可达三个数量级。
- **集成的前提是成员各自可信**，弱强混搭可能比单裁判更差。
- **金标也要审计**，域外测试常能发现标注协议不一致的部分。
- **门控阈值需要根据业务调整**，精度与覆盖率的权衡取决于人工复核的成本。

## 结论

自动评测链路里最容易被忽略的一环是裁判本身：它从未被测量，却持续产出所有下游判断的依据。这次审计给出的三组数字——一致性 0.04、替代方案成本 1/300、拒答门控把准确率从 20.7% 提到 36.9%——分别指向三件可立即着手的事：用分歧富集集测一致性、把裁判换成可自托管的中等模型、给裁判加一层"无法判断"的出口。再补一条集成的纪律：只有成员各自可信时，投票才有意义；以及一条顺手能做的事——用同一套配方检查金标自身。我在 4sapi.com 上把这套审计做成上线前的固定步骤之后，评测结论被推翻的情况明显减少，因为它第一次有了可验证的基准。
