# 【大模型API中转站】[第170期] MoE 稀疏翻译模型自托管｜50 语种按激活算钱

Cohere Labs 放出的 North Small Translate 1.0 是一个开放权重（open-weights）研究发布模型：218B 总参数、25B 激活参数的稀疏 MoE 架构，专门面向 50 种语言的高质量机器翻译。写这期的时候，我正在 4sapi（https://4sapi.com）维护多模型中转，翻译类流量的账单结构刚好能拿来当参照系——下面把自托管的显存账、云 API 的对比账和混合路由的接入方案一次算清。

## 一、开篇痛点：多语种翻译业务的三难选择题

多语种翻译是我手里最稳定也最头疼的一条业务线：电商商品页、合同摘要、客服工单、产品文档，几十个语向，批量大、时效要求中等、质量要求高。过去半年这条线一直在三个坑里打转。

第一个坑是成本。翻译走通用大模型 API，输入输出都很长，按量计费的账单跟着字符量线性走；业务旺季某个语向一扩量，当月账单直接翻倍。更麻烦的是不同语向往往要换不同模型，路由表越养越长，哪个语向用哪个档位的模型，全靠踩坑试出来。

第二个坑是隐私。合同文本和客服工单里全是真实姓名、金额、内部报价，这类内容走云 API，出域评估每次都要重做一遍，法务的耐心是有限度的。

第三个坑是质量。通用模型在小语种上的输出波动明显，术语前后不一致，一篇文档里同一个功能名能翻出三个版本，译后编辑的工时把 API 省下的钱又吃了回去。

于是题目变成：云端 API 便宜但不敢放敏感数据，本地部署干净但 218B 的总参数看起来高不可攀，全自建又怕运维拖垮团队。这三难不是三选一的题，下面用一条混合路由把三难同时解开。

## 二、原理速览：总参数管容量，激活参数管算力

先花两分钟把 MoE 的账理清楚。MoE（Mixture of Experts，专家混合）的核心思路是把一个大模型拆成很多个专家子网络，再加一个路由器（Router）：每个 token 到达时，路由器只在全部专家里挑出少数几个参与计算，其余专家这一步完全休息。模型的总容量由全部专家加起来决定，而单步计算量只由被激活的那一小部分决定。

放到 North Small Translate 1.0 上就是两组数字的分工：218B 总参数负责容量，足够装下 50 种语言的翻译知识；25B 激活参数负责算力，每个 token 实际走过的计算路径，大约相当于一个 25B 级稠密模型的负担。

```text
MoE 稀疏激活的一次前向（示意）：

输入 token
   │
   ▼
路由器 Router ──► 给所有专家打分，挑出少数专家
   │
   ▼
被选中的专家参与计算（激活参数合计约 25B）
其余专家本步休眠（但仍常驻显存）
   │
   ▼
专家输出加权合并
   │
   ▼
输出 token
```

对部署方来说，这套架构给出两条铁律：显存按总参数算，所有专家无论当班与否都要常驻显存，218B 就是 218B；吞吐按激活参数算，每个 token 的计算量由 25B 档的激活路径决定，批量打满之后，单位算力的产出远高于同量级稠密模型。忘掉任何一条，部署方案都会算错。

## 三、"开放权重研究发布"意味着什么

North Small Translate 1.0 的发布形态是开放权重研究发布，这组定位对落地方意味着三件事。

第一，权重拿得到。模型权重可以下载到自己的机器上，自托管、量化、针对垂直语料的微调都有了入口——这是和闭源 API 最本质的区别，敏感文本不出域的方案从这里才真正成立。

第二，边界也写明了。研究发布不是商业产品：许可证条款要逐条读，商用范围、再分发、对外提供翻译托管服务是否在授权范围内，都以许可证原文为准；没有 SLA，没有专属支持，问题靠社区和自己的工程能力扛。

第三，支持节奏自担。研究发布的模型更新没有承诺表，量化版本、推理框架的适配要自己跟进验证。我的做法是把研究发布当高潜力试验田：先在非关键链路把质量、吞吐、运维三件事跑通，数据达标再谈进生产，而不是一上来就押注核心业务。

## 四、部署账：显存按总参数算，估算口径先摆出来

部署账从显存开始。推理和训练不一样：所有专家必须常驻显存，这部分由总参数决定；KV cache、激活值、框架开销再往上加。下表按 218B 总参数做字节数推算，全部是估算口径，实际占用以所用推理框架的实测为准。

| 精度 | 每参数字节 | 权重显存（估算口径） | 部署量级判断（估算口径） |
| --- | --- | --- | --- |
| FP16 / BF16 | 2 B | 约 436 GB | 8 卡 80GB 级服务器起步，还需预留 KV cache 余量 |
| INT8 | 1 B | 约 218 GB | 4 卡 80GB 级起步，或 8 卡 48GB 级 |
| INT4 | 0.5 B | 约 109 GB | 2 卡 80GB 级起步，翻译质量必须重新抽检 |

三行数字之外还有三笔隐性的账。一是 KV cache：批量翻译的请求长度不短，并发一上来，KV 的占用会明显抬升，容量规划要按峰值并发算，不能只看权重。二是专家并行：总参数装不进单机时，专家要切到多卡甚至多机，通信拓扑和专家间的负载均衡直接决定吞吐能不能兑现，路由倾斜（某些专家被频繁命中）是常见的隐性瓶颈。三是量化质量：MoE 对量化的容忍度和稠密模型不完全一样，路由器对数值误差敏感，INT4 版本上线前必须拿金标准句对重新验收，不能默认精度减半、质量不减。

## 五、为什么翻译任务特别适合专用 MoE

翻译为什么值得专用 MoE，而不是继续用通用大模型？我把原因归纳成三条，外加一条容易被忽略的运维红利。

第一，任务窄。翻译的输入输出结构高度固定：源语言进、目标语言出，不需要多轮工具调用，不需要长链推理。任务窄意味着服务可以用低温度、短上下文、高吞吐的方式跑，MoE 的大容量全部用在刀刃上——语种覆盖和领域术语，而不是浪费在通用闲聊能力上。

第二，批量大。翻译业务的典型形态是离线批量：整站商品页过一遍、整个文档库翻一个语向。批量任务可以把 GPU 打满，而 MoE 的吞吐优势恰恰要在高负载下才兑现——激活参数小、单 token 算力省，攒成大批次之后，与稠密模型的吞吐差距会被进一步放大。

第三，计费敏感。翻译是按字符或按 token 结算的生意，毛利直接由单 token 算力成本决定。同样一笔算力预算，激活参数小的模型能跑出的字符量更多，这在比价和核算毛利时是硬指标。

运维红利在于：50 种语言在一个模型里，意味着路由层不用按语向维护一堆小模型。调度系统只需要决定走云端还是走本地，不需要再决定这个语向用哪个模型，路由表、评测集和监控面板都小一圈。

## 六、接入教程：混合路由的批量翻译流水线

接入方案用混合路由：常规语种且非敏感的文本走云 API 中转，吃弹性和免运维；敏感文本、涉密合同、内部工单强制走本地自托管服务，数据不出域。两侧都走 OpenAI 兼容接口，业务代码只维护一套客户端。云侧把中转站的地址写进 base_url 即可，本地侧用任意主流推理框架起一个 OpenAI 兼容服务，模型名指向自托管的翻译模型。

```python
import os
from openai import OpenAI

# 演示：混合路由的批量翻译流水线
# 路由规则：常规语种 + 非敏感 -> 云 API 中转；敏感文本 -> 本地自托管服务
cloud_client = OpenAI(
    base_url="https://4sapi.com/v1",          # 云 API 中转入口 4sapi，OpenAI 兼容协议
    api_key=os.environ["CLOUD_API_KEY"],
)

local_client = OpenAI(
    base_url="http://127.0.0.1:8000/v1",      # 本地推理框架暴露的 OpenAI 兼容服务
    api_key=os.environ.get("LOCAL_API_KEY", "local"),
)

MODEL_CLOUD = "gpt-5-mini"                    # 演示型号：常规语种走高性价比档
MODEL_LOCAL = "north-small-translate-1.0"     # 本地 MoE 翻译模型在推理框架里的服务名

GLOSSARY = {
    "结算周期": {"en": "billing cycle", "ja": "請求サイクル"},
    "会员权益": {"en": "membership benefits", "ja": "会員特典"},
}

SENSITIVE_KEYWORDS = ("合同", "薪资", "身份证", "内部报价", "工单号")

def is_sensitive(text: str) -> bool:
    # 命中敏感词即强制本地路由，判定宁严勿松
    return any(k in text for k in SENSITIVE_KEYWORDS)

def build_prompt(text: str, target_lang: str) -> str:
    terms = "；".join(f"{k} -> {v.get(target_lang, v['en'])}" for k, v in GLOSSARY.items())
    return f"目标语言：{target_lang}\n术语表：{terms}\n待翻译：{text}"

def translate_batch(items: list, default_lang: str = "en") -> list:
    results = []
    for item in items:
        text = item["text"]
        lang = item.get("target_lang", default_lang)
        if is_sensitive(text):
            client, model, route = local_client, MODEL_LOCAL, "local"
        else:
            client, model, route = cloud_client, MODEL_CLOUD, "cloud"
        try:
            resp = client.chat.completions.create(
                model=model,
                messages=[{"role": "user", "content": build_prompt(text, lang)}],
                temperature=0,   # 翻译任务关掉随机性，术语与译法才稳定
            )
            out = resp.choices[0].message.content.strip()
        except Exception as exc:
            # 失败降级：云侧异常回落本地，本地异常记录待重试，不让批量任务中断
            out = f"[TRANSLATE_FAILED:{route}:{exc}]"
        results.append({"id": item["id"], "route": route, "translation": out})
    return results

if __name__ == "__main__":
    jobs = [
        {"id": "t-001", "text": "新会员注册即赠首月会员权益。", "target_lang": "ja"},
        {"id": "t-002", "text": "补充协议：薪资结算周期调整为月度。", "target_lang": "en"},
    ]
    for row in translate_batch(jobs):
        print(row["id"], row["route"], row["translation"][:40])
```

几个工程要点值得单独说。路由判断放在业务侧而不是网关侧，敏感词命中即本地，判定清单要随业务词汇持续维护；术语表以明文拼进提示词，比微调见效快，还能按客户维度切换版本；temperature 固定为 0，翻译要的是确定性与术语一致；批量任务务必写降级路径，云侧限流或抖动时回落本地，保证整批任务跑完，失败行落库待重试；本地服务的并发上限要单独压测，它是敏感链路的唯一保障，不能按云侧的弹性假设来配。

## 七、成本对比：自托管 vs 云 API（估算口径）

成本对比只给算账结构，不报绝对价格：所有单价、租赁价都是演示值与估算口径，落地前按当时的实际报价重算。

假设口径如下：云 API 按每百万字符 30 元的演示单价计（输入输出摊算在内）；自托管按一台 8 卡 80GB 级服务器，市场租赁价折算每月约 1.5 万元（估算口径，含电费与带宽），批量离线吞吐按每月 3 亿字符的保守上限估算（估算口径）；运维人力按 0.2 个人力折算约 3000 元每月。

| 月翻译字符量 | 云 API 月成本（演示单价估算） | 自托管月成本（估算口径） | 结论 |
| --- | --- | --- | --- |
| 2000 万字符 | 约 600 元 | 约 1.8 万元 | 云 API 完胜，自托管纯亏 |
| 1 亿字符 | 约 3000 元 | 约 1.8 万元 | 云 API 仍明显占优 |
| 3 亿字符 | 约 9000 元 | 约 1.8 万元 | 打平的量级开始出现 |
| 10 亿字符 | 约 3 万元 | 约 2.4 万元（需扩容分片） | 自托管摊薄，云侧线性上涨 |

这张表真正想说的是两条曲线的形状。云 API 是线性成本：字符量翻倍、账单翻倍，但零固定投入、零闲置风险；自托管是台阶成本：固定支出封顶，量越大摊得越薄，代价是闲时也在烧钱，外加一张随时可能响的运维告警。翻译业务的真实答案通常不是二选一：长尾语向和基础量走云 API，把固定成本留给敏感文本和高频大语向，这正是混合路由的经济学依据。

还有一个不能折算成钱的变量：敏感文本走本地，规避的是数据出域的合规风险。这类风险一旦发生，损失远超两个方案之间的差价，把它排除在对比之外，账才算完整。

## 八、质量验收：术语表、回译抽检与语种覆盖抽测

翻译质量的验收要做成可重复的流水线，而不是靠肉眼扫两段。三道工序缺一不可。

术语表注入。业务术语整理成语对表，像上面代码里那样拼进提示词；核心功能名、产品名、法律术语必须进表。术语表按客户和业务线分版本管理，出现译法争议时先改表再重跑，比动模型快得多，也留得下修订记录。

回译抽检。每批译文按比例抽样，把译文回译回源语言，与原文比对相似度，低于阈值的样本进人工复核队列。回译不能证明译文正确，但能高效暴露漏译、语义反转和整句丢失这类硬伤，是批量场景里性价比最高的自动质检。

语种覆盖抽测。50 种语言各维护一组金标准句对，覆盖电商、合同、工单三类语料；每次模型版本变更、量化档位调整之后全量重跑，任何语种通过率跌破门槛，该语种自动切回云 API 或人工通道。验收是闸门不是仪式：未达标语种不允许自动发布。

## 九、成本与风险提示：许可证、数据出境与人工复核

最后把风险面摊开，逐条对应到动作。

许可证边界。研究发布的许可证是整套方案的法律地基，商用范围、再分发、对外提供翻译服务是否在授权范围内，逐条确认后再上生产；条款有歧义的地方先问清楚再动手，不要拿社区都在用来当理由。

数据出境合规。敏感文本本地闭环只是底线；走云 API 的部分要确认服务商的数据处理条款，留存期限、删除机制、是否用于训练，逐项落到合同里。跨区业务还要确认目的地司法辖区的数据入境要求，链路上每一个环节都要有明确的责任主体。

最终人工复核。机器译文直接对外的风险由业务承担：错译一个金额、一个日期，代价可能是真实的商务纠纷。对外发布的链路上保留人工终审环节，自动化负责把人从重复劳动里解放出来，不负责替人签字。

合规红线也给自己划一条：这里讨论的只有合法接入、架构设计、负载均衡与计费优化，任何绕过官方限制的方案都不在讨论范围之内。

## 十、落地检查清单

上线前逐项核对，清单没有全绿之前不放开自动发布：

- [ ] 许可证条款经法务确认，商用范围明确覆盖现有业务
- [ ] 敏感词路由规则已上线，命中即强制本地通道
- [ ] 本地服务通过 OpenAI 兼容接口验收，失败降级路径演练通过
- [ ] 50 语种金标准句对就绪，当前版本全量通过率达标
- [ ] 术语表按业务线分版本管理，争议译法有修订记录
- [ ] 显存与并发压测完成，容量规划按峰值并发留有余量
- [ ] 成本模型按实际报价重算，混合路由的分档阈值重新校准
- [ ] 对外发布链路保留人工终审，复核记录可追溯

## 十一、总结

这期围绕 North Small Translate 1.0 把 MoE 稀疏翻译模型的自托管经济学走了一遍：总参数管容量、激活参数管算力的两条铁律，决定了显存按 218B 算、吞吐按 25B 算；开放权重研究发布给了敏感数据不出域的入口，也标出了许可证与支持上的边界；混合路由把云 API 的线性成本和自托管的台阶成本拼进同一条业务线，敏感文本与高频大语向留给本地，长尾语向交给云端；再配上术语表注入、回译抽检、语种覆盖抽测的三道验收工序，以及一份上线前的逐项清单。整套方案的账目结构来自我在 4sapi（https://4sapi.com）维护多模型中转时对翻译流量的治理实践，可以直接搬到同类业务上对照使用。
