# 【大模型API中转站】[第07期] 模型能力评测指南｜创造力基准实测

常规基准能测出模型知道多少，却测不出它在陌生环境里会不会探索。

作为 4sapi 团队的接入实战记录，我从 70 个隐藏规则游戏的方法论出发，把发现能力的评测缩小成三个可以复用的接入选型用例。

## 一、开篇：分数之外，模型还差什么

常规基准能测出模型的"知识量"，却测不出模型的"直觉"。

- 数学、代码、常识问答，分数一路飙升；
- 但遇到"规则隐藏、目标未知、只能靠交互探索"的任务，前沿模型集体碰壁；
- 结论：**模型在"已知规则的世界"里很强，在"要自己发现规则的世界"里还很弱**。

这一期以一个新基准（DiG-bench）为引，讲三件事：这个基准为什么测的是"创造力"、它的方法论能不能抄、以及接入模型时怎么用这套思路做选型。

## 二、原理速览：什么是"发现"能力

传统基准给模型喂的是"规则明确、目标清楚"的任务，模型只需要在规则内优化。

```text
传统基准：规则已知 -> 目标已知 -> 找最优解
发现类任务：规则隐藏 -> 目标隐藏 -> 先探索 -> 再求解
```

DiG-bench 做的是后者：**每个游戏都是一个自包含的封闭小世界，有自己的法则，但规则和目标都隐藏，玩家必须通过交互一点点揭开**。

```text
游戏开始
   ↓
玩家尝试动作
   ↓
观察环境如何变化
   ↓
推断隐藏机制
   ↓
利用机制通关
```

这更像人类面对陌生环境时的学习方式：先试、再总结、再优化。测的不是"知道多少"，而是"能不能发现"。

## 三、关键事实：70 个游戏与它的"硬度"

DiG-bench 的 70 个游戏有四个值得抄的设计：

| 设计 | 说明 | 为什么重要 |
| --- | --- | --- |
| 纯文本交互 | 游戏天然适配语言模型 | 不需要视觉/动作接口 |
| 专家手工构建 | 人类专家逐个设计 | 保证规则有逻辑、可解 |
| 任务私有 | 大多数游戏不公开 | 防止模型提前训练过 |
| 人类可通但难 | 每个游戏至少一人通关 | 难度有上界，不是死题 |

关键结论：**这些游戏对当前前沿模型来说"令人安心地难"**——现有模型无法通关。而每个游戏都有人类通关记录，说明难的根源在"发现能力"，不在"游戏无解"。

## 四、方法论拆解：这套基准为什么能测创造力

### 4.1 隐藏规则 = 逼出探索

规则一隐藏，模型就不能靠"背题"得分，必须产生新动作假设、验证、修正。这直接测量模型在**新环境里的适应性**，而不是训练数据覆盖度。

### 4.2 私有任务 = 堵住数据泄漏

大多数游戏不公开，模型在训练时大概率没见过。这保证了"通关"只能来自推理能力，而不是记忆能力。**自建评测集时，这一条最值得抄**。

### 4.3 可玩性 = 保证公平

每个游戏有人类通关记录，说明有解、有路径、难度合理。模型失败归因于能力，而不是任务设计缺陷。

## 五、自建评测：如何测"直觉与创造力"

买不起 70 个专家游戏，但方法论可以缩到最小版本。

### 5.1 三种任务类型

```text
A 类：规则反转任务（已知规则，故意反转一条）
B 类：隐藏规律任务（给例子，不解释规则）
C 类：交互发现任务（动作-反馈回路，自己找目标）
```

### 5.2 最小交互评测脚本

```python
import json
import requests

class DiscoveryEval:
    def __init__(self, api_base: str, model: str):
        self.base = api_base
        self.model = model

    def act(self, history: list[dict]) -> str:
        """让模型在游戏里走一步"""
        r = requests.post(f"{self.base}/chat/completions", json={
            "model": self.model,
            "messages": [
                {"role": "system", "content": "当前处在一个规则未知的游戏里。只能输出动作名，不要解释。"},
                *history,
            ],
            "max_tokens": 32,
        })
        return r.json()["choices"][0]["message"]["content"].strip()

    def run_game(self, game: dict, max_steps: int = 30) -> dict:
        history, done = [], False
        for step in range(max_steps):
            action = self.act(history)
            result = game["step"](action)          # 游戏环境反馈
            history.append({"role": "user", "content": f"动作: {action} -> {result}"})
            if result.get("won"):
                done = True
                break
        return {"won": done, "steps": len(history)}
```

模型只能看到"动作-反馈"历史，看不到规则——这就是最小化的发现能力测试。

### 5.3 评测维度

| 维度 | 看什么 |
| --- | --- |
| 通关率 | 完成的游戏数 / 总数 |
| 步数效率 | 平均多少步通关（越少越好） |
| 探索多样性 | 是否尝试了不同动作，还是死磕一种 |
| 错误修正 | 反馈冲突后，模型是否调整策略 |

## 六、接入选型：把"发现能力"放进评测矩阵

真实接入场景不需要模型会玩隐藏游戏，但需要模型**在 API 边界变化时快速适应**：

- 换接入端点、换网关参数，模型表现是否稳定；
- 新工具、新格式出现时，模型能否少报错上手；
- 提示词风格变化后，输出质量是否骤降。

我的做法：把"交互发现"缩成三个接入级用例，作为模型候选的固定评测项：

```text
用例一：给定新 JSON 结构，让模型第一次就正确解析
用例二：给一条模糊指令，让模型通过追问澄清（而不是瞎猜）
用例三：工具返回异常，让模型换一种方式重试
```

三个用例都不需要专家游戏，但能测出"模型在陌生输入前会不会探索"。实测里，这部分表现与模型在常规基准上的排名并不一致——**有些高分模型在这里很僵，有些中等模型反而更会问**。这直接影响接入体验。

### 6.1 统一接入，排除变量

选型对比时，最难控制的是"接入差异"：不同厂商的端点、超时、格式转换都可能改变模型输出。我的做法是让所有候选模型走同一个接入网关（https://4sapi.com），用同一套 OpenAI 兼容格式、同样的超时与重试策略，保证对比只差在"模型本身"，不差在"接入方式"。评分时把请求参数、采样温度、上下文长度全部固定，评测才有可比性。

## 七、成本与风险提示

- **评测有成本**：交互式评测每次都是多轮 API 调用，30 步 × 若干候选模型，费用要提前预算；
- **随机性**：模型输出有采样随机性，同一游戏要多跑几轮取统计，别拿单次结果下结论；
- **任务泄漏**：自建评测集也要"私有化"，反复复用的任务集迟早被模型记住；
- **别过度解读**：70 个游戏测的是"发现能力"这一个维度，不否定模型在编码、数学等维度的优势。

## 八、实施清单

1. 定义要测的能力维度（发现/适应/澄清）；
2. 每个维度建 5–10 个私有任务；
3. 固定接入方式与模型参数（统一走同一网关，减少干扰）；
4. 每个任务跑 3 轮，记录通关率、步数、探索多样性；
5. 与常规基准分数对照，找"分数与体验背离"的候选；
6. 把结果写进模型选型表，作为接入决策的一部分。

## 九、避坑提示

- **别拿公开基准当万能尺**：公开任务集有数据泄漏风险，分数虚高；
- **别单轮定胜负**：交互任务随机性大，统计多轮再比；
- **别忽略提示词影响**：系统提示说"只能输出动作"，和没说，结果差异巨大；
- **别把"不会玩隐藏游戏"当"模型不行"**：那是能力维度不同，选型看任务匹配。

## 总结

DiG-bench 的价值不在 70 个游戏本身，而在它把"发现能力"变成了可测的东西：隐藏规则、私有任务、交互探索、人类通关对照。接入场景里，把这套方法论缩成"新结构解析、模糊指令澄清、异常重试"三个用例，就能在日常选型中持续测量模型的适应力。分数高不高是一回事，**在陌生环境里会不会探索，是另一回事**。

我是 4sapi 团队的接入实战记录者。如果用自建用例测出过不同结论，欢迎在评论区聊聊，一起把选型评测表补得更全面。
