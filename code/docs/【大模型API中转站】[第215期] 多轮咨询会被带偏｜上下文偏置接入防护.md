# 【大模型API中转站】[第215期] 多轮咨询会被带偏｜上下文偏置接入防护

客服、助理、顾问类 agent 的输入几乎全是转述：用户怎么说，比发生了什么更能左右模型的结论。一项覆盖 12 个 LLM 的仿真评测证实，模型对带偏见的叙事框架存在系统性敏感，而更长的对话并不必然带来更稳的判断。

## 一、开篇痛点：一句带立场的转述，足以带偏整个会话

先看两个我在线上案例里反复见到的模式。

客服工单场景：用户开口就是"物流太差了，三天没动，我要投诉"。模型接住情绪，顺着"物流有责"的框架往下推，赔偿方案、安抚话术、升级路径全部朝这个方向生成。事后查系统记录才发现，包裹卡在收货地址填错这一步，责任根本不在物流。

售前咨询场景：用户说"据我所知，别家方案都是本地部署的"。模型把这句转述当成行业事实，后面的对比分析从第一段就跑偏，越推越远。

两个案例的共同点：事实底座是完整的，系统里明明有记录可查，但模型优先采信了用户的叙事。问题不在某次发挥失常，而在接入架构默认把"用户的转述"当成"世界的事实"喂给了模型。转述型输入越多的业务——客服、售前、顾问、审核申诉——风险敞口越大。

动手治理之前，先把通道跑通是有意义的：在 4sapi（https://4sapi.com）创建一个中转 Key，用同一套对话代码在十几个主流模型之间随时切换，后面要做的双框架回归、跨模型对比才有统一的执行底座。

## 二、原理速览：Fuse 怎么把"被带偏"变成可测量的题

这类现象难讨论，是因为缺一个可对照的标准答案：同一句话换个人说，模型给两个结论，谁对谁错没有裁判。Fuse 的价值就在这里——它是一个开源的多智能体仿真框架，附带 2.1 万样本的数据集，聚焦"经由用户中介的社会推理"。

构造分三层：

- 一个带隐藏动机的目标 agent，与其他 agent 交互，其中有一个代表用户的 agent；
- 受测助手看不到目标动机，只能通过向用户代表咨询来推断；
- 动机是预设的，所以每道题天然自带可验证的正确答案。

这个设计把"模型是不是被带偏了"从主观印象变成了可打分的题。保真度用 2.4 万条人工标注校验过，被测对象是 12 个 LLM。四个发现依次是：

1. 经过用户中介转述后，社会推理的固有难度被放大；
2. LLM 对用户带偏见性的叙事框架表现出系统性敏感；
3. 模型比人类需要更多细节才能得出正确判断；
4. 更长的对话不必然提升表现——尽管澄清机会更多。

对做接入的人来说，这四条比跑分榜单有用得多：它们不是厂商营销指标，而是直接对应接入架构里的四类风险。

## 三、四个发现的接入侧映射

先给一张总表，后面分节逐条展开。

| 评测发现 | 接入侧风险 | 线上典型症状 | 第一道防线 |
| --- | --- | --- | --- |
| 转述放大社会推理难度 | 中间人信息损耗被模型放大 | 基于二手描述做出错误归因 | 关键判断回原始凭证取数 |
| 对带偏见叙事框架系统性敏感 | 上下文被单方叙事污染 | 情绪化工单得到一边倒结论 | 事实与叙事分层标注 |
| 比人类需要更多细节 | 缺细节时结论质量骤降 | 不问就猜，猜错还很自信 | 澄清式追问策略 |
| 长对话不必然提升表现 | 偏置随轮次累积 | 聊得越久立场越固化 | 置信度门控与摘要重置 |

## 四、风险一：上下文被单方叙事框架污染

叙事框架的常见形态有四种，值得逐个认识：

- **情绪前缀**："太差了""离谱"这类词放在句首，模型先入为主地给事件定了性；
- **归因预设**："肯定是仓库的问题"，把待验证的结论伪装成了已知前提；
- **对比框架**："别家都能当天到，就这里不行"，用未经核实的对照物抬高指控强度；
- **权威背书**："客服之前也是这么说的"，借系统身份给单方说法加权重。

发现二说的"系统性敏感"，含义是这不是偶发抖动，而是换一种说法就换一个结论方向的稳定倾向。模型顺着框架走，是因为框架看起来像"用户的真实意图"，顺着走最省力；而转述又天然经过了一层有立场的压缩，发现一说的"难度被放大"正是这层压缩造成的。

工程上的对应动作有两个：一是在上下文里把叙事层和事实层显式分开，让模型看见"这是转述"而不是把两者混在一个 user 消息里；二是在系统提示里固化中立立场——叙事可以被复述，但不能被当成已验证事实参与推理。具体实现见第七、八节。

## 五、风险二：信息越多，结论不一定越稳

发现四最容易反直觉：对话更长、澄清机会更多，表现却不必然提升。落到接入侧，多轮会话不是安全垫，而是偏置累积器，机制至少有三条：

1. **他方污染累积**：每轮用户转述里的立场词都在往上下文里沉淀，第十轮的上下文已经不是中立底座；
2. **自我污染回流**：模型第一轮的推断写在回复里，第三轮被用户引用回来，就从"待验证假设"变成了"之前确认过的信息"；
3. **沉没成本效应**：聊了十几轮之后，模型倾向于维持此前结论的自洽，而不是推翻重来。

对应的处理办法：

- **摘要重置**：超过阈值轮次后，把历史压缩成"已核实事实清单 + 未决问题清单"，重建上下文；
- **证据固定**：关键结论挂证据链而不是靠"聊着聊着记住了"，结论可以被追溯，也可以被推翻；
- **快照对比**：每过 N 轮，用同一份事实底座重新问一遍核心判断，答案漂移就触发复审。

## 六、风险三：澄清不会自动发生

发现三和发现四合起来看更扎心：模型比人类需要更多细节才能得出正确判断，而澄清机会摆在面前，模型未必主动用。人类顾问会靠常识补全缺口，模型缺细节时的默认行为是硬猜，而且猜得一脸自信——输出流畅、语气笃定，恰恰是最危险的状态。

结论很明确：澄清必须被主动设计成机制，而不是指望模型自己想起来问。什么条件下必须问、问什么、最多问几轮、问不到怎么办，这四个问题的答案都要写进系统提示和代码里，第十一节给具体策略。

## 七、上下文治理：把事实和叙事拆开标注

第一层防护是把上下文从"一锅端的消息流"改成"分层标注的结构"。三层划分：

- **事实层**：订单号、时间戳、系统记录、凭证截图里的结构化字段，可核验；
- **叙事层**：用户的转述、抱怨、评价，带立场，只代表陈述者；
- **推断层**：模型自己此前的假设，不允许回流成事实。

```python
from dataclasses import dataclass, field
from enum import Enum
from typing import List


class ClaimType(str, Enum):
    FACT = "fact"            # 可核验事实：订单号、时间戳、系统记录
    NARRATIVE = "narrative"  # 用户叙事：带立场、情绪或评价的转述
    INFERENCE = "inference"  # 模型自己的推断，不允许回流成事实


@dataclass
class Turn:
    role: str
    content: str
    claim_type: ClaimType = ClaimType.NARRATIVE
    source: str = "user"                     # user / crm / ticket_system / agent
    evidence_ids: List[str] = field(default_factory=list)


def build_context(turns: List[Turn]) -> str:
    """把消息流渲染成分层上下文，喂给模型前先完成标注。"""
    blocks = ["[事实层] 以下条目可核验，可作为推理依据"]
    blocks += [f"- ({t.source}) {t.content}"
               for t in turns if t.claim_type == ClaimType.FACT]
    blocks.append("[叙事层] 以下为陈述者单方转述，仅代表其立场")
    blocks += [f"- {t.content}"
               for t in turns if t.claim_type == ClaimType.NARRATIVE]
    blocks.append("[推断层] 以下为待验证假设，不作为结论依据")
    blocks += [f"- {t.content}"
               for t in turns if t.claim_type == ClaimType.INFERENCE]
    return "\n".join(blocks)
```

标注本身不需要全靠人工：有结构化字段可查的走规则，自由文本交前置小模型分类，标注错误的代价远远小于污染整个会话的代价。

## 八、系统提示固化中立立场，结论挂上证据链

第二层防护在系统提示和输出格式上。系统提示要点：

```text
角色：中立咨询助理。
规则：
1. [叙事层] 内容是陈述者的单方转述，可以复述，不能作为已验证事实参与推理；
2. 结论必须引用 [事实层] 条目作为证据；只有叙事层支撑时，confidence 必须为 low；
3. 关键槽位（订单号、时间、金额、对方说法）缺失时，先输出澄清问题，不输出结论；
4. 每个结论附带一条反方向检查：如果结论错了，最可能是哪条信息不可靠。
```

结论统一走结构化证据链输出，配合门控函数：

```python
EVIDENCE_CHAIN_SCHEMA = {
    "name": "verified_conclusion",
    "schema": {
        "type": "object",
        "properties": {
            "conclusion": {"type": "string"},
            "confidence": {"type": "string",
                           "enum": ["high", "medium", "low"]},
            "evidence": {
                "type": "array",
                "items": {
                    "type": "object",
                    "properties": {
                        "claim": {"type": "string"},
                        "source": {"type": "string"},
                        "type": {"type": "string",
                                 "enum": ["fact", "narrative", "inference"]},
                    },
                    "required": ["claim", "source", "type"],
                },
            },
            "missing_info": {"type": "array", "items": {"type": "string"}},
            "counter_check": {"type": "string"},
        },
        "required": ["conclusion", "confidence", "evidence",
                     "missing_info", "counter_check"],
    },
}


def gate(result: dict) -> str:
    """置信度门控：证据不达标就拦下结论，转入澄清式追问。"""
    facts = [e for e in result["evidence"] if e["type"] == "fact"]
    if result["confidence"] == "low" or not facts or result["missing_info"]:
        return "ASK_CLARIFY"
    return "PROCEED"
```

门控的意义在于把"模型的自信"和"业务的可信"解耦：confidence 是模型自评，gate 是接入方的确定性规则，后者不信任前者。

## 九、接入教程：在 4sapi 中转站上落地这套方案

整套防护对接入层没有特殊要求，OpenAI 兼容接口即可。步骤如下：

**1. 环境准备**：Python 3.9+，安装 SDK。

```bash
pip install openai
```

**2. 获取 Key**：在 4sapi 官网 https://4sapi.com 注册并创建 API Key，中转站聚合了主流模型，一份 Key 可以在多个模型之间切换。

**3. 配置与调用**：base_url 指向中转地址，系统提示、分层上下文、证据链输出一次配齐。

```python
import json
import os

from openai import OpenAI

client = OpenAI(
    api_key=os.environ["SAPI_API_KEY"],   # 在 4sapi 控制台创建
    base_url="https://4sapi.com/v1",      # OpenAI 兼容地址
)

SYSTEM_PROMPT = (
    "角色：中立咨询助理。\n"
    "1. [叙事层] 内容是陈述者的单方转述，不能作为已验证事实参与推理；\n"
    "2. 结论必须引用 [事实层] 条目作证据，只有叙事层支撑时 confidence 取 low；\n"
    "3. 关键槽位缺失时输出澄清问题，不输出结论；\n"
    "4. 每个结论附带反方向检查。严格按 JSON 输出。"
)


def ask(context: str, question: str, model: str = "gpt-4o") -> dict:
    resp = client.chat.completions.create(
        model=model,                      # 同一套代码可切换任意已接入模型
        messages=[
            {"role": "system", "content": SYSTEM_PROMPT},
            {"role": "user", "content": f"{context}\n\n当前问题：{question}"},
        ],
        response_format={"type": "json_object"},
        temperature=0,
    )
    return json.loads(resp.choices[0].message.content)
```

部分模型对 `response_format` 的支持程度不同，不支持时退化为在系统提示里强制 JSON 并做解析兜底。

**4. 验证**：跑一组双框架样例（同一事实、中立与带偏置两种转述），检查结论是否随框架翻转；再切换另一个模型重跑同一组样例。请求流向如下：

```text
业务应用（分层上下文 + 证据链门控）
        |
        v
  4sapi 中转站（https://4sapi.com，OpenAI 兼容）
        |
        +--> 主判断模型：强模型，输出结构化结论
        +--> 前置标注模型：便宜模型，做叙事/事实分类，快且省
```

## 十、对抗性评测：把带偏置框架的测试集变成回归资产

防护不能只靠上线前的直觉检查，要有自己的对抗性测试集。构造方法模仿双框架对照：每道题由事实底座加两种叙事框架组成，标准答案从事实底座推出，与框架无关。

```text
同一个事实底座 + 两种叙事框架
        |
        v
  +-------------+       +-------------+
  | 框架 A       |       | 框架 B       |
  | 中立转述     |       | 带偏置转述    |
  | "三天没更新" |       | "太差了要投诉"|
  +-------------+       +-------------+
        |                     |
        +----------+----------+
                   |
                   v
      受测 agent 多轮咨询（允许澄清）
                   |
                   v
         结构化结论（含证据链）
                   |
                   v
          与标准答案对照打分
                   |
        +----------+----------+
        |                     |
    结论一致              结论随框架翻转
        |                     |
      通过            记为偏置命中 -> 进回归清单
```

每条用例固定五个字段：`fact_base`（事实底座）、`framing_neutral`（中立框架）、`framing_biased`（带偏置框架）、`expected`（标准答案）、`key_slots`（关键槽位）。核心指标是偏置命中率：结论随框架翻转的比例。

框架变体至少覆盖第四节列出的四种形态，再加两类边界用例：事实底座本身残缺的（测澄清触发），以及叙事与系统记录直接冲突的（测取数优先级）。这套测试集要资产化：换模型、改系统提示、调门控阈值，都重跑一遍，偏置行为是模型属性，不是常数。

## 十一、澄清式追问怎么设计才不会反向带偏

澄清本身也有坑：问题里塞了假设，就等于用提问把模型又带偏一次。四条设计原则：

- **触发条件显式化**：证据链里 fact 类证据为空，或 `key_slots` 有缺失，必须触发澄清，不给模型"自行斟酌"的空间；
- **问缺口不问立场**：问"第一次发现异常是什么时间"，不问"是不是特别生气"——前者补事实，后者只是在采样情绪；
- **限轮次**：最多两轮澄清，之后给出带前提条件的临时结论并标注 confidence，避免无限追问拖垮体验；
- **问题自身保持中性**：澄清问题的模板要过一遍对抗检查，确保不带预设归因。

## 十二、上线前评测清单

至少逐项过完再放流量：

1. 同一事实底座配中立与带偏置两种框架，确认结论不随框架翻转；
2. 在首轮注入带情绪前缀的转述，到第 10 轮后复测核心判断，确认没有漂移；
3. 抽掉关键槽位，确认模型输出澄清问题而不是硬猜；
4. 检查证据链里 fact 类证据占比，仅叙事层支撑的结论必须被 gate 拦下；
5. 模拟接口超时重试，确认证据链与置信度输出稳定；
6. 切换到备选模型重跑同一测试集，对比偏置命中率与澄清触发率；
7. 低置信会话确认被正确路由到人工或兜底话术；
8. 审查日志：叙事层没有被记成事实层，真实客户对话已脱敏；
9. 调整门控阈值后全量回归，而不是只跑新增用例。

## 十三、成本与风险提示

- **token 成本上升但可控**：分层标注会让上下文变长，证据链输出会让回复变长；可以把前置标注交给便宜模型，主判断留给强模型，通过 4sapi（https://4sapi.com）的多模型路由在一个应用里混搭计费；
- **对抗测试集只覆盖已知偏置模式**：情绪前缀、归因预设、对比框架、权威背书之外的变体需要持续扩充，固定测试集长期使用会被"练熟"；
- **换模型必须重测**：偏置行为与具体模型强相关，升级或更换模型后，历史评测结论不可继承；
- **评测数据合规**：来自真实对话的用例先脱敏再入库，叙事层内容尤其容易夹带个人信息；
- **门控阈值按业务校准**：过紧会造成澄清轰炸，过松等于没防，错误成本高的业务收紧，轻交互业务放宽；
- **合规边界**：以上手段全部服务于正常业务的质量与安全治理，只讨论合法接入与架构设计，不涉及任何绕过模型安全策略的用法。

## 结论

转述即输入，框架即偏置。一项覆盖 12 个 LLM 的仿真评测用可验证的构造证实：经过用户中介的转述会放大推理难度，模型对带偏见的叙事框架系统性敏感，缺细节时倾向于硬猜，更长的对话也不必然更稳。落到接入侧就是四件事：事实与叙事分层标注、系统提示固化中立立场、澄清式追问主动设计、关键结论置信度门控；再配一套双框架对抗评测资产，让这套防护可以持续回归。接入层面，在 4sapi（https://4sapi.com）拿一份 Key，同一套代码就能把方案跑在不同模型上——偏置行为是模型属性，换模型就要重新测。
