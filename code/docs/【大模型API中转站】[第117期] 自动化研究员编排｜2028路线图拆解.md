# 【大模型API中转站】[第117期] 自动化研究员编排｜2028路线图拆解

这一期，4sapi 拆解的主题是自动化 AI 研究员路线图：OpenAI 计划在 2028 年 3 月前交付能在人类监督下完成熟练研究员数天任务的 Agent，而这类多阶段研究 Agent 的接入架构、模型路由与成本治理，正是 API 中转场景最值得展开的话题。

## 开篇痛点：研究型 Agent 是成本黑洞

把「自动化研究员」落到 API 调用上，第一眼看到的往往不是智能，而是账单。

一个研究任务天然是多阶段的：接需求、拆子任务、检索文献、精读文档、生成假设、设计实验、跑代码、复核结论。任何一步都不是一次对话能完成的，每一步都要消耗 token，而且失败就要回环重来。把全部阶段都扔给旗舰模型直连，一个任务烧掉上百万 token 是常态；多个 Agent 并行时，数字还要再翻几倍。

成本之外还有两个隐性代价。其一是延迟：旗舰模型单次响应慢，串行流水线里的等待被逐级放大。其二是稳定性：某个阶段一次抽风，整条链已经烧掉的 token 全部白费，只能重跑。研究型 Agent 的工程难点，从来不是「能不能调用模型」，而是「怎么把每一分 token 花在刀刃上」——这正好是接入架构、分级路由与预算治理要解决的问题。更麻烦的是，这些成本往往藏在细节里：上下文窗口被长文档撑满后，单次请求的计价翻倍；重试策略写得粗糙，一次限流抖动就能让同一批 token 反复计价；阶段产物不落盘，每次回环都要从头再读一遍文档。这些细节单看都不大，叠在一起就是账单上的天文数字。

## 路线图速览：从自动化实习生到自动化研究员

先把这期的核心事实摆齐。

其一，OpenAI 计划在 2028 年 3 月前开发出「自动化 AI 研究员」，目标是在人类监督下完成熟练研究员需要数天才能完成的明确任务，同时全程保持人类监督，以确保对齐与安全。

其二，研究组织内部已经在更频繁地使用编码 agent：研究人员使用编码 agent 的频率持续上升，代码生成与实验执行的占比明显增加，人类研究员的精力因此转向更复杂、更需要判断力的任务。

其三，组织曾在一次安全事件后暂停过强化学习训练，但并未停摆，而是继续调整安全措施与透明度，以推进安全 AGI 的开发。

把这三条放在一起，能看到一条清晰的加速路线：从「自动化实习生」到「自动化研究员」的时间表，勾勒出研究组织自动化的轨迹。更进一步，监督半径一旦扩大，成本治理能力就变成真正的瓶颈——谁能压住 token 消耗，谁就能把自动化研究的规模推得更大。这条逻辑不只属于 OpenAI，任何搭建研究型 Agent 的团队都适用，这也是这一期要重点展开的部分。需要特别注意的是，时间表只是表面信息，真正影响接入决策的，是这条路线背后的两个信号：自动化研究的颗粒度在从「实习生任务」向「研究员任务」上移，监督与成本正成为规模化的双重约束。对做 API 接入的团队而言，提前把多阶段编排与预算治理的架子搭好，任务量上来时才接得住。

## 原理速览：多阶段研究流水线

自动化研究员的底层，是一条可编排的多阶段流水线。每个阶段负责一类工作，阶段之间传递结构化产物，失败则触发回环：

```
任务接收 → 检索 → 阅读 → 推理 → 校验
   │         │       │       │       │
 目标拆解   文档召回  精读摘要  假设与实验  结论复核
              │         │       │         │
              └─────────┴───────┴─────────┘
                     失败回环（重检索 / 重读 / 重推理）
```

流水线的价值在于：每个阶段对模型能力的要求不同，这就有了分级路由的空间。检索与摘要用轻量模型足够，假设生成与实验设计才需要旗舰模型。把模型选择从「全链同一档」改成「按阶段分档」，成本曲线会立刻掉下来。

## 为什么多阶段天然烧 token

理解成本结构，才能设计治理方案。多阶段流水线的 token 消耗有三个放大器。

第一是重复：同一批文档会在阅读、推理、校验阶段反复出现，每次都要重新编码，上下文越长，重复成本越高。

第二是回环：研究任务几乎不可能一次成功。检索不准要重检索，精读不够要重读，假设被校验推翻要重推理。每多一轮回环，就多一轮全链成本。

第三是并行：多 Agent 同时开工时，阶段间还有信息交换与汇总，这部分 token 常常被忽略，却在账单上真实存在。

三个放大器叠加，单任务成本很容易失控。所以降本不能靠「少调用」，而是靠「分级调用」与「控制边界」，这正是下面两节方案的核心。

## 方案：模型分级路由

分级路由的核心，是给每个阶段匹配最合适的能力档位：

| 流水线阶段 | 模型档位 | 典型工作 | 成本特征 | 出错代价 |
| --- | --- | --- | --- | --- |
| 任务接收 / 拆解 | 轻量 | 目标解析、子任务拆分 | 低 | 中（可回环修正） |
| 检索 / 召回 | 轻量 | 关键词、向量召回、候选排序 | 低 | 低（可补召回） |
| 阅读 / 精读 | 中档 | 长文档精读、要点抽取 | 中 | 中（影响下游质量） |
| 推理 / 实验设计 | 旗舰 | 假设生成、实验代码、深层推理 | 高 | 高（核心价值所在） |
| 校验 / 复核 | 中档 | 事实核对、代码审查 | 中 | 高（安全关键） |

两个注意点。其一，轻量模型不是「降级」，而是把资源留给真正需要深推理的阶段，总质量不降反升；其二，路由必须可观测——每个阶段的模型、token、耗时都落日志，后续调优才有参照，而不是凭感觉拍脑袋。

## 方案：预算三层治理

路由解决「怎么省」，预算解决「怎么控制不超」。推荐任务级、阶段级、账户级三层预算结构：

```
任务级预算（单任务 Token 上限，任务启动前预分配）
   └→ 阶段级预算（检索 / 阅读 / 推理 / 校验各自配额）
        └→ 账户级预算（日 / 月总盘，硬顶熔断）
```

任务级预算在任务启动前预分配，防止单个研究任务无限膨胀；阶段级预算给每个阶段独立配额，阶段超限时触发降级或提前回环；账户级预算是最后一道闸，日或月总量触顶立即熔断，保护账户不被意外账单击穿。三层互相咬合：任何一层触顶，整条流水线都必须停下或降级，而不是悄悄继续烧钱。

## 接入教程：多阶段编排与预算控制

接入侧是标准的 OpenAI 兼容接口：注册后创建 key，把 base_url 指向官方接入点，即可用 openai 库直接编排多阶段流水线。以下是一套带分级路由与三层预算的参考实现：

```python
import os
from openai import OpenAI

client = OpenAI(
    api_key=os.environ["DSH_API_KEY"],   # 在控制台创建，走环境变量
    base_url="https://4sapi.com/v1",     # 统一接入点
)

# 模型路由表：检索用轻量、推理用旗舰
ROUTER = {
    "retrieve": "light-model",     # 轻量档：召回与摘要
    "read":     "mid-model",       # 中档：精读抽取
    "reason":   "flagship-model",  # 旗舰档：假设与实验设计
    "verify":   "mid-model",       # 中档：复核与事实核对
}

# 预算三层：任务级 / 阶段级 / 账户级
BUDGET = {
    "task":   1_200_000,                         # 单任务 Token 上限
    "stage":  {"retrieve": 200_000, "read": 300_000,
               "reason": 500_000, "verify": 200_000},
    "account_daily": 20_000_000,                 # 账户级每日硬顶
}

def chat(stage: str, messages: list) -> str:
    """带阶段级预算校验的对话调用，超限即熔断。"""
    if BUDGET["stage"][stage] <= 0:
        raise RuntimeError(f"stage budget exhausted: {stage}")
    resp = client.chat.completions.create(
        model=ROUTER[stage],
        messages=messages,
        max_tokens=min(4096, BUDGET["stage"][stage]),
    )
    used = resp.usage.total_tokens
    BUDGET["stage"][stage] -= used
    BUDGET["task"] -= used
    BUDGET["account_daily"] -= used
    if BUDGET["task"] <= 0 or BUDGET["account_daily"] <= 0:
        raise RuntimeError("budget cap reached: orchestration stopped")
    return resp.choices[0].message.content

def run_research(question: str) -> dict:
    """多阶段研究流水线：接收 → 检索 → 阅读 → 推理 → 校验。"""
    plan = chat("retrieve", [
        {"role": "system", "content": "拆解研究任务并生成检索计划。"},
        {"role": "user", "content": question},
    ])
    docs = retrieve_docs(plan)    # 接入真实检索服务，返回候选文档
    digest = chat("read", [
        {"role": "system", "content": "精读候选文档并抽取要点。"},
        {"role": "user", "content": docs},
    ])
    hypothesis = chat("reason", [
        {"role": "system", "content": "基于要点生成假设与实验设计。"},
        {"role": "user", "content": digest},
    ])
    verdict = chat("verify", [
        {"role": "system", "content": "复核假设与事实，标注不确定项。"},
        {"role": "user", "content": hypothesis},
    ])
    return {"plan": plan, "digest": digest,
            "hypothesis": hypothesis, "verdict": verdict}
```

这套实现的关键设计有三点。其一，chat 函数把预算校验收拢在调用入口，任何阶段超限都会以异常的形式立刻中断，而不是静默降质；其二，路由与预算分离，换模型档位不动业务代码，调预算不动路由逻辑；其三，整条流水线返回结构化字典，四个阶段的产物可以单独审计，也能在失败时定位到具体阶段重跑。

配置侧有三件事要做。其一，路由表与预算参数放进配置文件而不是写死在代码里，方便按任务类型切换档位与额度；其二，账户级限额在控制台同步设置，代码熔断与平台硬顶形成双保险；其三，为每个任务生成唯一 ID，账单按任务 ID 对账，成本归因才说得清。

## 负载均衡与并发设计

多 Agent 编排跑起来之后，单线程串行就不够用了。并发设计要处理三件事。

请求调度：多个研究任务同时跑时，用队列把请求打散，避免瞬间打爆限流；重试加指数退避，把偶发抖动消化在调度层而不是业务层。

多 key 负载均衡：在合法接入范围内，把流量分摊到多个 key 与多个模型档位上，既降低单点限流风险，也让不同档位的配额各归其位。

熔断与降级：某个模型档位持续报错时，熔断该档位并把流量切到备用档位；预算触顶时，流水线整体降级为「只读汇总」，而不是继续生成。

## 横向对比：三种编排方式

| 编排方式 | 接入成本 | 单任务成本 | 质量稳定性 | 适用场景 |
| --- | --- | --- | --- | --- |
| 全旗舰直连 | 低 | 高 | 稳定 | 小批量、重推理 |
| 单模型多阶段 | 低 | 中 | 一般 | 快速验证流水线 |
| 分级路由多 Agent | 中 | 低 | 高 | 规模化研究编排 |

分级路由多 Agent 的接入成本最高，但任务量上来之后，省下的 token 会快速覆盖这部分成本。判断标准很直接：单任务成本乘以任务量，超过路由与预算体系的搭建成本，就值得上；反之，小规模场景直接用中档模型串一遍更务实。换句话讲，这套方案的核心收益不是省下某一次调用的钱，而是把「单任务的期望成本」压下来：路由负责省单价，预算负责兜底线，两者配合，自动化研究的单位成本才真正可预期。

## 成本与风险提示

几点实操提示，都是踩过坑才总结出来的。

token 复用：同一批文档会在多个阶段反复出现，开启 prompt caching 或显式复用上下文，能省下可观的重发成本。

回环控制：失败回环必须有次数上限与降级路径，否则一次坏输入会让流水线无限重试，烧穿阶段级预算。

对账与计费：每阶段记录 usage，按任务 ID 汇总，日账单与平台账单交叉核对，偏差早发现早处理。

安全与对齐：人类监督不能省。自动化研究员的核心承诺是「在人类监督下工作」，校验阶段必须保留人工复核入口，尤其是实验结论与事实性断言。

合规红线：全程只使用合法授权的 API 接入与计费方式。架构设计、分级路由、负载均衡、预算优化都属于正常的工程范畴，不做任何绕开授权或违规代理的操作。
