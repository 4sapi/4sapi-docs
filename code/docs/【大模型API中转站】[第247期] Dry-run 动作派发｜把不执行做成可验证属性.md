# 【大模型API中转站】[第247期] Dry-run 动作派发｜把不执行做成可验证属性

给 agent 接工具时最容易走得过头的一步，是把"读"和"写"打包成同一个接口。一旦打包，模型判断该不该做，就成了唯一的闸门。

真正稳的做法是反过来：把动作能力先做成**不会产生效果**的形态，让 agent 在 dry-run 上表达意图，由确定性代码决定是否真正派发。我在 4sapi（https://4sapi.com）上做工具层设计时，这套结构是固定下来的。

## 一、先把接口分成三类

治理的起点是接口分类，而不是加提示词。三类接口的能力与风险完全不同：

| 接口类型 | 能力 | 副作用 | 治理方式 |
| --- | --- | --- | --- |
| 只读资源 | 读取指标、状态、告警、元数据 | 无 | 默认可开，保留读取审计 |
| dry-run 工具 | 提交动作意向，返回将要发生什么 | 无 | 策略校验后返回提议 |
| 真实动作 | 实际改变外部系统状态 | 有 | 需授权，默认关闭 |

多数系统的问题是只做了第一类和第三类，中间那层缺失。缺了 dry-run 层，agent 想"试试看"时唯一的出口就是真实动作，于是每一次探索都带着副作用。

这层之所以常被跳过，原因在开发顺序上。接工具时先做的是"读"接口，因为容易验证；再做"写"接口，因为业务需要。dry-run 层既不是业务功能，也不是必须的读取能力，很容易被判定为可后置。等到发现 agent 频繁误操作时再加，往往已经有一批调用方依赖了真实动作的返回结构，改起来成本更高。所以更划算的做法是在第一次接动作类工具时就把这层留出来——哪怕先只返回一个空提议，接口形态固定下来，后续补字段是低成本的事。

这三类的边界也需要明确写在工具描述里，让模型自己知道哪一类只是提议。否则模型会按真实动作的语义去理解 dry-run 的返回值，把"提议已被接受"读成"动作已完成"，进而在后续推理里当作既成事实使用。

## 二、什么叫做成可验证属性

"这个工具不会真的执行"—这句话如果只是文档里的承诺，就没有治理价值。做成属性意味着：**任何面向 agent 的请求，都不派发外部操作**，而且这个约束可以被独立测试。

具体到实现上有三个要求：

第一，dry-run 的返回值里不含执行结果，只含**将要执行的内容**。它不能因为"顺便执行了"而返回真实数据。

第二，派发真实动作的代码路径与 dry-run 路径**不共享入口**。共享入口意味着一个参数错误就可能打通两条路径。

第三，约束要能在测试里被直接断言，而不是靠阅读代码确认。

## 三、治理链：从请求到派发

完整的动作派发链路如下，每一步都是确定性判断：

```text
agent 发起工具请求
    |
    v
[1] 归类：只读 / dry-run / 真实动作
    |
    +-- 只读 ------> 直接执行，记录读取审计
    |
    +-- dry-run --> [2] 策略校验
    |                   |
    |                   +-- 参数合法？目标存在？状态未过期？
    |                   +-- 通过 -> 返回提议（含影响范围与所需授权）
    |                   +-- 拒绝 -> 返回可见的拒绝原因
    |
    +-- 真实动作 -> [3] 授权校验
                        |
                        +-- 授权通过 -> 派发 -> 记录动作审计
                        +-- 未授权 -> 转为 dry-run 提议返回
```

关键点是最后一条分支：**未授权的真实动作请求不报错，而是降级成 dry-run 提议返回**。这样 agent 能得到"我需要什么授权才能做这件事"的信息，而不是陷入重试循环。

这条设计还有一个容易忽视的好处：它让工具层的行为在有无授权时保持**同一形状**。如果未授权时直接返回错误，模型面对的是两种不同的响应结构，它会花决策预算去处理这个差异，甚至尝试用别的工具绕过去达成目的。统一成提议形状之后，未授权与已授权在模型看来的区别只是"提议里多了一个已批准标记"，行为路径不变，越权尝试的动机也就下降了。

## 四、dry-run 返回体该包含什么

dry-run 的价值取决于它返回的信息量。返回一个"OK"等于什么都没做。我要求返回体至少包含：

- **目标**：将被影响的具体对象标识，不是模糊描述；
- **参数**：经过校验与归一化之后的实际参数；
- **预期副作用**：这次动作会改变哪些状态、影响哪些下游；
- **所需授权**：需要哪一类授权、由谁批准；
- **可逆性**：是否可回滚、回滚方式；
- **拒绝项**：若被部分拒绝，明确列出哪一项因何被拒。

有了这些字段，agent 才能在下一步做出有意义的选择：换参数、申请授权，或者放弃。

## 五、无效与过期状态必须可见拒绝

一个容易忽略的点是：dry-run 最容易掩盖的问题不是"能不能做"，而是"**基于的状态是否还成立**"。

比如 agent 读到一个设备状态，据此提出动作，但中间状态已经变化。若 dry-run 仍然返回通过，后面真实派发时就会出错。

正确做法是让状态校验结果**可见**：状态已过期或被推翻时，dry-run 必须明确返回"依据失效"，并给出重新读取的提示。这比静默失败有用得多——前者让 agent 自我纠正，后者只会让它重复提交。

## 六、三条路径分别验证

"不执行"这个属性要在三条路径上分别验证，缺一条都不算成立：

1. **资源路径**：读取类请求不能因为参数构造而触达写操作；
2. **提议路径**：dry-run 请求在任何参数组合下都不能产生外部操作；
3. **授权路径**：授权通过后的派发路径必须与 dry-run 路径分离，且未授权时不能有副作用。

这三条要写成独立的测试用例，作为上线门禁。只测其中一条，另外两条就是未知状态。

测试写法上有个技巧：不要只测"正常参数"，要专门测**构造出来的边界参数**——超长标识符、空值、层级错位、以及看起来像目标但实际不存在的对象。这类输入正是能打通路径的那一类。每条用例都应该断言两件事：返回值符合预期，以及**没有产生外部调用**。后者可以用一个计数桩来验证，把工具层的出口统一挂上计数器，测试结束时断言计数为零。这样"不执行"就从阅读代码时的信心变成了测试报告里的一行结论。

## 七、语义元数据为什么值得单独做

工具描述的信息量直接影响 agent 的调用正确率。一个具体现象是：把指标标识符等**语义信息显式写进资源元数据**后，结构化输出中对必需标识符的符合度明显提升，而通用化的描述会带来更多字段错配。

这条的实践含义是：工具 schema 不是越简洁越好。对字段含义、取值范围、单位、必需性这些信息的显式声明，换来的是更少的下游纠错。

## 八、叙述合理不等于产物可用

另一个必须提前设计的验收点：agent 输出的**结构化结果**与它给出的**叙述性说明**是两回事。

一个动作提议可以表述得非常合理——目标清楚、理由充分、读起来像专业判断——同时它的结构化字段是错的：标识符写错、单位缺失、字段层级错位。如果验收只看叙述，就会把错误放过去。

我的做法是把两者分开验收：叙述用于人工复核，结构化字段用 schema 与取值域做机器校验，任一不通过即视为未通过。机器可读的合规性优先级高于表述的合理性。

## 九、授权票据怎么设计

如果 dry-run 层与真实动作层靠"请求里有没有授权标记"来区分，那这层治理基本等于没做——闸门交给了调用方。票据设计要满足几条硬性要求：

**一是绑定具体动作**。票据必须编码动作类型与目标标识，不能是一张通用通行证。否则一次授权会被复用到其他目标上。

**二是绑定具体参数**。同一动作、不同参数的影响范围可能完全不同，只锁动作不锁参数，等于只挡住了名字，没挡住内容。

**三是一次性且有时效**。派发成功后即失效，超过有效窗口自动作废。这样即使票据被记录或复用，也拿不到第二次效果。

**四是不可由调用方构造**。票据应由服务端生成并签名，校验在服务端完成；客户端只负责原样回传。

**五是可追溯**。票据要能关联到发起它的那次提议、批准它的那次授权，以及最终的派发记录。审计时需要沿这三者还原完整链路，缺一环就无法回答"这次动作是谁批准的"。

这五条落地之后，dry-run 层的价值才完整：它不只是给模型看的预览，也是授权链路的起点。

## 十、接入示例

下面这段代码把工具分成只读与 dry-run 两类，在网关侧完成策略校验与审计记录。入口从环境变量读取。

```python
import os, uuid, logging
from datetime import datetime, timezone
import requests

BASE_URL = os.getenv("MODEL_BASE_URL", "https://4sapi.com/v1")
API_KEY = os.getenv("FOURSAPI_API_KEY", "")

READ_ONLY = {"get_metrics", "get_alarms", "get_context"}          # 只读：直接执行
DRY_RUN = {"set_parameter", "restart_task", "apply_profile"}     # 动作：只返回提议

logging.basicConfig(level=logging.INFO)
LOG = logging.getLogger("gateway")

REGISTRY = {  # 已登记的目标与必需字段，用于策略校验
    "set_parameter": {"required": {"target_id", "param", "value"}, "reversible": True},
    "restart_task": {"required": {"task_id"}, "reversible": True},
    "apply_profile": {"required": {"profile_id"}, "reversible": False},
}


def validate(tool, args):
    """返回 (ok, reason)。无效或过期状态一律可见拒绝。"""
    spec = REGISTRY.get(tool)
    if spec is None:
        return False, "未登记的动作"
    missing = spec["required"] - set(args)
    if missing:
        return False, "缺少必需字段: " + ",".join(sorted(missing))
    if args.get("state_stale"):
        return False, "依据的状态已过期，请重新读取后再提交"
    return True, ""


def propose(tool, args, stale=False):
    """dry-run：不派发任何外部操作，只返回提议。"""
    ok, reason = validate(tool, {**args, "state_stale": stale})
    ticket = "dry-" + uuid.uuid4().hex[:12]
    LOG.info("dryrun tool=%s ticket=%s ok=%s reason=%s", tool, ticket, ok, reason)
    if not ok:
        return {"accepted": False, "reason": reason, "ticket": ticket}
    spec = REGISTRY[tool]
    return {
        "accepted": True,
        "ticket": ticket,                      # 提议票据，非执行凭据
        "target": args.get("target_id") or args.get("task_id") or args.get("profile_id"),
        "args": args,
        "would_change": spec["required"],
        "reversible": spec["reversible"],
        "needs_authorization": not spec["reversible"],
        "dispatched": False,                   # 可断言的属性：永不派发
        "at": datetime.now(timezone.utc).isoformat(),
    }


def dispatch(tool, ticket, authorized=False):
    """真实动作入口，与 propose 完全分离；未授权一律降级为提议。"""
    if not authorized:
        return {"dispatched": False, "reason": "未授权，已转为提议", "ticket": ticket}
    if not ticket.startswith("dry-"):
        raise ValueError("票据来源不明，拒绝派发")
    LOG.info("dispatch tool=%s ticket=%s", tool, ticket)
    resp = requests.post(f"{BASE_URL}/tools/{tool}", json={"ticket": ticket},
                         headers={"Authorization": f"Bearer {API_KEY}"}, timeout=20)
    return {"dispatched": True, "status": resp.status_code}
```

两个可直接用于测试的断言：`propose()` 的返回值里 `dispatched` 恒为 `False`；`dispatch()` 在 `authorized=False` 时不做任何网络调用。这两条覆盖了提议路径与授权路径。

## 十一、上线前的验收清单

1. 所有工具是否已归类为只读、dry-run 或真实动作，且无未归类项；
2. dry-run 返回值是否包含目标、参数、预期副作用、所需授权与可逆性；
3. 是否存在任何参数组合能让 dry-run 触达外部写入；
4. 状态过期时是否返回可见拒绝，而不是静默通过；
5. 未授权的真实动作请求是否降级为提议，而不是报错或重试；
6. 派发路径与 dry-run 路径是否分离，票据是否无法被伪造复用；
7. 结构化字段是否有独立的 schema 校验，与叙述验收分开；
8. 三条路径是否都有独立测试用例并进入门禁。

## 十二、成本与风险提示

- **dry-run 不能预测全部影响**。它校验的是参数与状态，不是运行时的真实效果。涉及不可逆操作时，仍需人工确认。
- **授权绕过是最需要防的一环**。票据必须与具体动作绑定、一次性、有有效期；只靠"原始请求里带没带授权标记"来判定，等于把闸门交给了调用方。
- **状态过期是高频误判源**。读取与派发之间的时间窗越长，状态失效概率越高。建议为需要状态的动作加最大有效窗口。
- **自建这层有维护成本**。每接一个新工具就要补登记项与测试用例，所以更合理的做法是把它做成接入规范，而不是事后补。
- **不要用提示词替代这一层**。提示词能让模型更谨慎，但无法提供可验证的约束。

## 结论

"不执行"必须是一个属性，而不是一句承诺。做法是把工具能力拆成只读、dry-run 与真实动作三类，让动作请求先以提议形态返回，再由确定性代码决定是否派发；同时把这个约束在资源、提议、授权三条路径上分别验证，并进入上线门禁。另外三件容易被忽略的事同样重要：状态过期要可见拒绝，结构化字段要独立于叙述验收，授权票据要绑定动作、参数与时效。这几件事做完，agent 才真正是"能读、能提建议、但不能自己动手"。我在 4sapi.com 上把网关侧定下来之后，工具层新增能力从"要审一遍模型提示词"变成了"补一条登记项加一个测试用例"，维护方式也从经验判断变成了清单作业。
