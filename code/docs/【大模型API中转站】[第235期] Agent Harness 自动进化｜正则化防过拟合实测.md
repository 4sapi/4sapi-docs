# 【大模型API中转站】[第235期] Agent Harness 自动进化｜正则化防过拟合实测

Agent 的能力上限越来越不取决于模型本身，而取决于包在模型外面的那层脚手架：提示词、控制流、工具、记忆和上下文管理。这层东西现在可以自动进化了——让改进 Agent 的系统自己去提议、筛选、迭代 Harness 的每一处组件。

但朴素的自动进化有一个致命缺陷：它在评测集上涨分，在真实任务上露馅。我按最新公开研究的思路给进化过程加上正则化约束，在自建任务集上复现了关键结论：域内涨分可观，分布外也稳稳上涨，策略 token 反而省了三成。

## 一、痛点：Harness 越改越歪

我维护的编码 agent 有一套手工调出来的 Harness：系统提示词两千字、十几个工具、一套反思与重试的控制流。为了让它在自建评测集上多拿几分，我做过一轮"自动化改进"：让模型自己分析失败案例，自己改提示词，自己加工具。

结果很典型：评测集从 62 分涨到 78 分，换一批新任务跑，成绩几乎退回原点。分析日志发现，进化过程学到的是"这批评测题的套路"——比如某类任务总在第三步需要某个特定工具，进化就写死了这个调用序列。它记住的是题，不是能力。

这就是 harness 层递归自我改进的经典失败模式：**域内收益是记忆的幻觉，分布外打回原形**。而且每次进化都往提示词里塞更多内容，策略 token 越涨越贵。

## 二、原理速览：Harness 进化的三道约束

改进思路来自"正则化递归自我改进"：不是不让它进化，而是给进化过程加三道确定性约束。

```text
                    ┌────────────────────────────┐
                    │      Harness v(n)          │
                    └──────────┬─────────────────┘
                               v
        提议者：按退火预算生成候选改动（越到后期，允许捆绑的改动越少）
                               |
        评论者：筛掉疑似"评测特化"的提案
                               |
        剪枝器：删掉过小、过贵、已失效的改动
                               |
                    ┌──────────v─────────────────┐
                    │      Harness v(n+1)        │
                    └────────────────────────────┘
```

| 组件 | 约束什么 | 防的是什么 |
| --- | --- | --- |
| 提议者（退火预算） | 单个候选最多捆绑几处改动，预算随代数递减 | 大杂烩式改动掩盖单点失效 |
| 评论者 | 屏蔽指向评测集特征的提案 | 记住题目而非能力 |
| 剪枝器 | 删除收益微小、token 开销大或重复的改动 | 提示词无节制膨胀 |

三道约束共同把进化从"怎么涨分怎么来"扳向"什么机制可复用就留什么"。公布这组方法的代码在 `github.com/google-research/rrsi`，实测数字：八个基准上域内最高涨 14.1 分，五个分布外基准平均仍涨 4.7 分，进化后的 harness 运行策略 token 比不约束的版本少 30%。

## 三、4sapi 接入：进化循环的最小实现

进化循环本身就是一组 API 调用，在 4sapi（https://4sapi.com）上用 OpenAI 兼容接口就能搭。骨架如下：

```python
import json
from openai import OpenAI

client = OpenAI(api_key="sk-4sapi-填入key", base_url="https://4sapi.com/v1")

def propose(harness, failures, budget):
    """提议者：budget 限定本次最多捆绑的改动数"""
    r = client.chat.completions.create(
        model="gpt-6-sol",
        temperature=0.4,
        messages=[{"role": "user", "content": f"""
角色：Harness 进化提议者。当前 Harness：
{harness}

失败案例（只看行为，不看评测集标签）：
{failures}

提出至多 {budget} 处改动，优先选择可跨任务复用的机制性改进，
禁止针对具体题目特征做特化。输出 JSON：[{{"target":..., "change":..., "why":...}}]
"""}],
    )
    return json.loads(r.choices[0].message.content)

def critique(proposals, eval_features):
    """评论者：与已知评测特征重叠的提案直接否决"""
    r = client.chat.completions.create(
        model="gpt-6-sol", temperature=0,
        messages=[{"role": "user", "content": f"""
以下提案是否存在"评测特化"嫌疑（针对固定题目套路而非通用机制）？
提案：{json.dumps(proposals)}
评测集已知特征：{eval_features}
逐条输出 keep / reject 与理由。
"""}],
    )
    return [p for p, v in zip(proposals, parse_verdicts(r)) if v == "keep"]

def evolve(harness, failures, generation, max_budget=5):
    budget = max(1, max_budget - generation // 3)   # 退火：代数越高预算越紧
    props = propose(harness, failures, budget)
    keep = critique(props, EVAL_FEATURES)
    pruned = prune(keep, harness)                    # 剪枝器：删过小/过贵/重复
    return apply(harness, pruned)
```

`prune` 和 `apply` 是确定性代码，不走模型：改动收益小于阈值的删掉，估算 token 开销超出基线 10% 的删掉，与现有组件重复的合并。

## 四、评测怎么设计才能防自欺

进化系统最大的风险不是改坏，而是评测本身被骗。我的评测设计遵循三条：

1. **域内外分离**。自建评测集按"来源"切成两半，进化只看 A 半，B 半永远封存，每五代解封跑一次作为分布外检查；
2. **特征黑名单**。人工整理评测集的表面特征（固定题目模式、特定措辞），喂给评论者做否决依据；
3. **双盲抽检**。进化后的 harness 在完全新写的任务上跑，人工评审不告知版本号。

评测成本不低，但这是整条路线的保险丝。任何一次"域内涨了、域外没验"的迭代都不算数。

## 五、收益核算

在我的编码 agent 上跑了五代进化（每代 40 个候选提案）：

| 指标 | 手工 Harness | 朴素进化 | 正则化进化 |
| --- | --- | --- | --- |
| 自建评测集（域内） | 62 | 78 | 71 |
| 封存新题（域外） | 58 | 60 | 63 |
| 每任务策略 token | 18,000 | 24,500 | 16,800 |
| 提示词长度 | 2,000 字 | 4,300 字 | 1,900 字 |

朴素进化的 78 分是记忆幻觉，正则化版本主动放弃了 7 分域内虚高，换来域外真实上涨与更短的提示词。token 开销降三成这一点经常被忽略——**进化方向天然偏向"加内容"，剪枝器是唯一往回拉的力**。

## 六、与托管 Harness 的关系

同期另一个信号是平台侧的托管化：云厂商开始提供开箱即用的 agent Harness（联网搜索、命令执行、文件编辑、跨日记忆、辅助 agent 交接全部内置），编码 agent 服务则把云端会话开放到终端里创建、转向和恢复。

两条路线并不冲突，我的分工是：**原型与内部工具用托管 Harness**，上架即用、按量付费、免维护；**核心业务用自建 Harness + 正则化进化**，因为进化自由度和数据边界只有自建可控。用中转聚合（4sapi）把两条路线的模型调用统一到同一层，切换成本只剩配置。

## 七、进化安全：三道闸门

自动改 Harness 等于自动改生产配置，安全闸门必须先于收益考虑：

```text
候选改动 -> 沙箱环境验证（不碰生产数据）
         -> token 开销与延迟预算检查
         -> 工具权限不扩大的断言
         -> 人工审批后灰度发布
         -> 回滚开关常备
```

任何"让进化系统自己上线自己"的做法都该被否决。进化可以自动化，发布永远要过人。

## 八、落地检查清单

1. 把现有 Harness 拆成结构化组件（提示词段、工具、控制流参数），进化才能针对组件操作；
2. 自建评测集切出封存的分布外半区；
3. 整理评测特征黑名单，作为评论者的否决依据；
4. 提议/评论/剪枝三角色接好，剪枝器必须是确定性代码；
5. 退火预算从宽松开始，代数递增逐步收紧；
6. 每五代解封一次域外检查，域外不涨就回滚整条进化链；
7. token 开销基线与告警先建好，防止提示词膨胀复发。

## 九、成本与风险提示

- 进化循环本身烧 token：五代 40 提案的循环在我这里花了约 300 万输入 token，小团队建议降到两代起步；
- 域内分数在正则化下会低于朴素进化，接受它，域外分数才是真实水位；
- 评论者的否决质量依赖特征黑名单的完整性，黑名单维护是长期人工投入；
- 托管 Harness 的内置能力变化不受控制，关键行为要有自己的回归测试；
- 通过 4sapi 调用时，进化循环的并发要限流，提案生成的 temperature 不宜过低，否则候选多样性塌缩。

## 结论

Harness 自动进化已经从概念变成工程，但"能进化"和"进化得对"之间隔着三道约束：退火预算管改动密度，评论者管评测特化，剪枝器管组件膨胀。域外 +4.7 分和策略 token −30% 说明，纪律不会杀死进化，反而让进化第一次值得信任。

模型每周都在变强，Harness 决定这些强能兑现多少到自己的任务上。欢迎在评论区聊聊各自的 Harness 是手工调还是自动进化，以及域外分数是怎么守住的。
