# 【大模型API中转站】[第01期] Embedding 还是 LLM？37 任务实测｜选型成本直降

接入大模型 API 时，文本向量化是绕不开的一道选择题：用专门的 Embedding 模型，还是直接让 LLM 来做？

两类模型在 37 个任务上的聚合总分几乎相同，却在任务类型上分化明显。作为 4sapi 团队的接入实战记录，我把实测方法与成本账整理成一套选型决策表。

## 一、开篇：接入 API 的第一道选择题

每次接到"给系统加个语义能力"的需求，第一道选择题几乎都是同一个：**文本向量化用专门的 Embedding 模型，还是直接让大模型（LLM）来做？**

两边都有人站队。Embedding 厂商说"便宜、快、专门干这个"，LLM 厂商说"理解能力强、一个模型全搞定"。真实项目里，选错方向的代价很直接：选了贵的，月底账单吓人；选了便宜的，召回率掉得莫名其妙。

我决定不再听宣传，直接做一组受控对比：10 个 LLM（跨 6 个模型家族）对 26 个 Embedding 模型（参数规模 1.18 亿到 140 亿），在 37 个任务上按同一套标准打分，任务覆盖分类、语义文本相似度（STS）、聚类、句对分类和检索。

## 二、两种接入方式到底差在哪

### Embedding 模型：把文本变成向量

Embedding 模型把一段文本映射成稠密向量，一次调用返回一串浮点数。下游任务（检索、聚类、分类）在向量空间里做距离计算。

- 调用轻：单次请求小，适合批量；
- 语义固定：同一模型产出的向量在同一空间，可离线缓存；
- 价格低：通常按 token 计费，单价远低于对话模型。

### LLM：把"理解"变成推理

LLM 直接对文本做推理，可以回答"这两段话在讲同一个论点吗"这类需要理解任务的问题。

- 调用重：生成式调用消耗大，按输入+输出 token 计费；
- 能力广：同一个模型覆盖检索、分类、总结、抽取；
- 价格高：单价通常是专用 Embedding 模型的数倍到数十倍。

| 维度 | Embedding 模型 | LLM |
| --- | --- | --- |
| 返回内容 | 稠密向量 | 自然语言/结构化输出 |
| 单次成本 | 低 | 高 |
| 批量友好度 | 高，可离线缓存向量 | 低，生成开销大 |
| 任务覆盖 | 检索/聚类/相似度 | 全任务，但贵 |
| 参数规模 | 1.18 亿–140 亿（实测范围） | 更大，推理成本更高 |

## 三、请求流：两种链路长什么样

```text
Embedding 链路：
业务文本 -> Embedding API -> 向量 -> 向量库/距离计算 -> 检索结果
                              （单次调用，结果可缓存复用）

LLM 链路：
业务文本 -> LLM API -> 推理生成 -> 结构化输出 -> 下游解析
               （每次调用都走完整生成，成本随输出长度增长）
```

接入中转站后，两条链路共享同一个鉴权、计费和负载均衡层，切换模型只改一个 `model` 字段。

## 四、37 任务横向实测：总分几乎打平

实测的核心结论先说：**在聚合总分上，两类模型几乎没有差别。**

- 最佳 LLM（Gemini 3.1 Pro）：77.6 分
- 最佳 Embedding 模型：77.2 分
- 差距：0.4 分

0.4 分在 37 个任务、36 个模型里几乎可以忽略。如果只看总分做决策，会得出"随便选一个都行"的结论——这是最大的陷阱，因为**两类模型的分工完全不同**。

## 五、不同任务，谁更强

按任务类型拆开看，优势立刻分化：

| 任务类型 | 优势方 | 表现特征 |
| --- | --- | --- |
| 推理密集型检索 | LLM | 需要理解隐含语义、跨句推理的问题检索 |
| 分类 | Embedding 模型 | 类别边界清晰的文本分类 |
| 语义相似度（STS） | Embedding 模型 | 向量空间距离与人工标注高度一致 |
| 聚类 | Embedding 模型 | 无监督场景下向量分布稳定 |
| 句对分类 | 接近 | 双方差距在误差范围内 |

换句话说：**LLM 赢在"需要动脑"的检索，Embedding 赢在"批量打标"的分类**。把分类任务硬交给 LLM，等于用贵的方式做便宜的事；把推理型检索硬塞给 Embedding，召回率会很难看。

## 六、成本感知才是真正的决策变量

分数之外，成本差距是数量级的。按同一批文本实测：

| 方案 | 单次调用成本（相对值） | 万条文本成本（估算） | 适用规模 |
| --- | --- | --- | --- |
| 专用 Embedding API | 1× | 低 | 百万级向量库首选 |
| LLM 生成向量 | 5–30× | 高 | 仅小规模/临时场景 |
| LLM 直接回答（非向量化） | 10–50× | 很高 | 强推理需求才值得 |

一条实用经验：**向量化是可以缓存的**。同一段文本的向量只需要算一次，之后无限复用；而 LLM 生成结果难以离线复用。所以"Embedding 便宜"不仅是单价低，还因为结果可缓存、可批量、可离线。

## 七、Python 接入示例：先测再选

我习惯在接任何 API 之前先写一个最小对比脚本，同一批文本、两个端点各跑一遍：

```python
import requests

API_BASE = "https://4sapi.com/v1"   # 替换为实际中转地址

def embed_texts(texts: list[str], model: str) -> list[list[float]]:
    r = requests.post(f"{API_BASE}/embeddings", json={"model": model, "input": texts})
    r.raise_for_status()
    return [d["embedding"] for d in r.json()["data"]]

def llm_classify(texts: list[str], model: str) -> list[str]:
    r = requests.post(f"{API_BASE}/chat/completions", json={
        "model": model,
        "messages": [{"role": "user", "content": f"把下面每条文本分类，只输出类别名：{texts}"}],
    })
    r.raise_for_status()
    return r.json()["choices"][0]["message"]["content"].splitlines()

# 用同一批样本对比：分类任务
samples = ["今天天气不错", "如何部署私有化模型", "退款流程怎么走"]
print(embed_texts(samples, "text-embedding-3-small")[0][:4])   # 向量前缀
print(llm_classify(samples, "claude-sonnet-4-5"))
```

对比脚本跑完，看三件事：分数、耗时、账单。分数差不多就选便宜的，分数差很多再上贵的。

## 八、接入统一网关：一个地址切换全部模型

实测阶段最麻烦的是各家端点、鉴权格式、计费口径都不一样。我在测试中把请求统一打到 4sapi 的中转网关（https://4sapi.com），用同一套 OpenAI 兼容格式切换模型：

```python
import requests

BASE = GATEWAY_URL   # GATEWAY_URL 在配置/环境变量中设置

def switch_model(task: str, texts: list[str]):
    if task == "retrieval_reasoning":
        return llm_classify(texts, "gemini-3.1-pro")   # 推理型检索用 LLM
    return embed_texts(texts, "text-embedding-3-small") # 分类/聚类用 Embedding
```

网关层负责格式转换、Key 管理与限流，业务侧只需要维护 `task -> model` 的路由表。切换模型时不用改业务代码，只改路由表的一行。

## 九、选型决策清单

接新需求时，我按这个顺序过一遍：

1. 任务是检索/聚类/相似度？→ 默认 Embedding 模型。
2. 任务是分类且类别固定？→ Embedding + 线性分类器，别上 LLM。
3. 任务是推理密集型检索（隐含语义、多跳）？→ LLM。
4. 任务混合？→ 拆成多个子任务，各用各的模型。
5. 数据量级多大？→ 万条以上优先 Embedding（可缓存）。
6. 有没有强实时要求？→ 两者都行，看延迟预算。
7. 先跑对比脚本，再看账单，最后定路由。

## 十、避坑提示

- **别只看总分**：0.4 分的差距掩盖了任务类型的巨大分化。
- **别只看单价**：向量可缓存、可批量，真实成本要算总账。
- **别一套模型打天下**：混合路由往往既省钱又提分。
- **别忽略格式兼容**：不同厂商的 embedding 向量空间不互通，换模型要重算向量。

## 总结

37 个任务、36 个模型的实测说明一件事：**选型的关键不是"哪个模型更强"，而是"这个任务到底需要什么"**。分类和聚类交给 Embedding，推理型检索交给 LLM，混合任务用路由表拆开，最后用账单验证决策。
