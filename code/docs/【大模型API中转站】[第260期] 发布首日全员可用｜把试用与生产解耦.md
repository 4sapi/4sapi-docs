# 【大模型API中转站】[第260期] 发布首日全员可用｜把试用与生产解耦

模型迭代的速度已经快于企业的采购与评估周期。等一轮审批走完，试用的往往已经是上一代模型——团队永远落后一个版本，而"是否该用新模型"的讨论总是在过时的信息上展开。

一家公司在内部解决这个问题的做法是：**让全部员工在模型发布首日就能试用新模型**，规模是 **12000 人**。关键不在于他们动作快，而在于把**试用**与**生产**做了解耦——试用全量开放，生产另有一套判断流程。我在 4sapi（https://4sapi.com）上帮团队设计接入治理时，这套结构是我见过最实用的一种。

## 一、先看清矛盾的实质

常规流程是串行的：新模型发布 → 评估 → 审批 → 小范围试点 → 逐步放开。每一环都合理，但串起来的时间远超模型的迭代周期。

矛盾的实质在于**两类决策被混在了一起**：

- **"能不能用"**——这是安全性、合规性、数据边界的问题，必须谨慎，但它的答案通常与模型版本关系不大（用哪个模型都要满足同样的边界要求）；
- **"该不该用"**——这是效果与成本的问题，需要真实使用数据才能回答，而真实数据只能来自实际使用。

常规流程把这两个决策串在一起，于是"该不该用"也必须等"能不能用"审完。而"该不该用"恰恰需要尽早开始收集数据。

## 二、把两个决策拆开

解法就是把两者拆成两条独立的轨道：

```text
新模型发布
    |
    v
[准入判断] 数据边界、合规要求、供应商条款是否满足
    |         （与模型版本无关的通用条件，判断一次，长期有效）
    |
    +-- 通过 -> 立即开放试用（带实验标签 + 按人预算）
    |              |
    |              v
    |          [证据收集] 内部基准 / 用户反馈 / 成本追踪
    |              |
    |              v
    |          [推广判断] 是否进入生产（按任务类型分别决定）
    |
    +-- 不通过 -> 不开放
```

拆开之后，两条轨道的节奏就对了：准入判断是**一次性**的，条件稳定；推广判断是**持续**的，跟着数据走。而且推广判断可以**按任务类型分别做**——同一模型可能适合编码补全，不适合面向客户的文案，两者不必一起放开。

## 三、实验标签：把试用隔离出来

试用能全量开放的前提是它**不影响生产**。实现方式是用实验标签做隔离：

- 试用流量带独立标签，与生产流量在**配额、日志、计费**三处分开；
- 试用请求的结果**不进入生产链路**，不参与任何对外的输出；
- 试用有独立的**时效**，到期自动失效，避免"临时试用"变成长期依赖。

第三点最容易被忽略。如果没有时效，试用会把一批隐性依赖沉淀下来——等到要下线时才发现有人的日常工作流已经建在上面。设置时效并在到期前主动确认，比事后清理便宜得多。

## 四、按人预算：控制爆炸半径

全量开放试用最大的风险是成本失控。12000 人同时试用，如果没有任何限制，一次异常调用模式就能产生可观的开销。

对策是**按人预算**，并且分成四类分别管理。分四类的原因是不同性质的消耗需要不同的控制方式：

| 预算类型 | 管什么 | 超限行为 |
| --- | --- | --- |
| 日常额度 | 常规试用调用 | 降级到默认模型 |
| 实验额度 | 主动申请的对比测试 | 需申请，单独计 |
| 峰值额度 | 短时高频调用 | 限速，不直接拒绝 |
| 团队额度 | 部门汇总上限 | 触发提醒与复核 |

四类里最值得说明的是**峰值额度**。直接拒绝高频调用会让正当的批量测试失败，体验很差；改为限速则保留了可用性，同时抑制了异常流量。这个设计把"防滥用"与"不打断正常工作"两个目标同时满足了。

四类预算之间还有一个配合关系：日常额度管住常态化消耗，峰值额度管住瞬时冲击，实验额度给超出常规的需求留一条申请通道，团队额度则负责兜底。缺少实验额度时，需要做大范围对比测试的团队会想办法绕过日常限额，反而更难管理；缺少团队额度时，个人层面的额度都正常而部门整体异常的情况不会被发现。**四类是一个最小的完备集合**，少于四类就会出现可见性盲区。

团队额度则是为了处理另一种情况：个人都在额度内，但某个部门整体消耗异常。这类问题在个人视角下不可见，必须有汇总层面的观察。

## 五、判断推广的三类证据

试用数据收集完之后，决定是否进入生产需要三类证据，缺一类都会导致判断偏斜。

**内部基准**回答"能力是否达标"。关键是要用**自有任务集**而不是公开基准——公开基准偏向难题，会高估差距；自有任务集反映真实分布，才对应实际收益。

**用户反馈**回答"是否好用"。这类证据主观且分散，但能捕捉到基准测不出的问题：延迟体感、输出风格、以及在多轮交互中的稳定性。收集方式上，不要只做满意度打分，让使用者描述**具体在哪个环节不顺**更有用。

**成本追踪**回答"是否划算"。这一项必须有客观数据，不能靠估算——因为模型换代时 token 用量画像会变，旧的价格对比往往失效。

三类证据的关系是：基准与成本给出门槛判断，用户反馈给出体验判断。**只有前两类时不建议推广**，因为体验问题往往在规模化之后才集中暴露。

## 六、成本追踪为什么要落在可观测性上

成本追踪如果只做"月度总账"，对推广决策几乎没有帮助——它太滞后，也无法归因。

更有效的做法是把成本追踪接入既有的可观测性体系，让每一笔消耗都能挂到**具体的调用方、任务类型与模型版本**上。这样三类问题才能被回答：

- 某任务类型换到新模型后，每任务成本是升还是降；
- 哪些调用方是主要消耗方，它们是否属于推广目标；
- 某个模型版本的整体成本中，有多少来自试点流量、多少来自生产。

这些问题的答案决定了推广是"按任务类型逐步放开"还是"整体切换"。我在实践中几乎没见过整体切换是正确选择的情况——不同任务类型的最优档位本来就不同。

## 七、网关承担什么

上述机制要落地，需要一个统一的入口承担四件事：**配置分发**（新模型什么时候对谁可见）、**治理**（谁有权限调用什么）、**计量**（每次调用记在谁头上）、以及**可观测性**（成本与质量数据的汇总口径）。

统一入口的价值在于**避免各自为政**。如果每个团队自己接模型，预算无法统一、成本无法归因、下线时也找不到全部调用方。相反，当所有调用都经过同一入口，模型上线与下线就都变成了配置变更——「让全员在发布首日可用」这类动作才可能实现。

## 八、接入示例：实验标签与按人预算

下面这段脚本实现一个最小的网关侧策略：按实验标签放行、按调用方累计预算、超限时降级或限速。

```python
import os, time
from collections import defaultdict
from fastapi import FastAPI, HTTPException
from pydantic import BaseModel
from openai import OpenAI

app = FastAPI()

client = OpenAI(   # 统一入口：所有调用经此转发，便于配置分发、计量与可观测性
    api_key=os.getenv("FOURSAPI_API_KEY"),
    base_url="https://4sapi.com/v1",
)

DEFAULT_MODEL = os.getenv("MODEL_DEFAULT", "claude-sonnet-5-5")
PILOT_MODEL = os.getenv("MODEL_PILOT", "claude-opus-5-5")

BUDGETS = {   # 四类预算：日常 / 实验 / 峰值 / 团队（单位：美元）
    "daily": float(os.getenv("BUDGET_DAILY", "5")),
    "experiment": float(os.getenv("BUDGET_EXPERIMENT", "50")),
    "peak": float(os.getenv("BUDGET_PEAK_RPM", "60")),      # 这一项是每分钟请求数
    "team": float(os.getenv("BUDGET_TEAM", "2000")),
}

PILOT_UNTIL = os.getenv("PILOT_UNTIL", "2026-10-31")

_spend = defaultdict(float)       # (user, bucket) -> 金额
_team_spend = defaultdict(float)  # team -> 金额
_rpm = defaultdict(list)          # user -> [时间戳]


def pilot_active(today=None):
    today = today or time.strftime("%Y-%m-%d")
    return today <= PILOT_UNTIL


def check_peak(user):
    now = time.time()
    _rpm[user] = [t for t in _rpm[user] if now - t < 60]
    if len(_rpm[user]) >= BUDGETS["peak"]:
        return False
    _rpm[user].append(now)
    return True


def resolve_model(user, team, want_pilot):
    """决定本次请求实际使用的模型：无权限或超限则降级到默认模型。"""
    if not want_pilot:
        return DEFAULT_MODEL, "standard"
    if not pilot_active():
        return DEFAULT_MODEL, "pilot-expired"
    if _spend[(user, "daily")] >= BUDGETS["daily"]:
        return DEFAULT_MODEL, "daily-limit"
    if _team_spend[team] >= BUDGETS["team"]:
        return DEFAULT_MODEL, "team-limit"
    if not check_peak(user):
        raise HTTPException(status_code=429, detail="peak rate limited")
    return PILOT_MODEL, "pilot"


class Call(BaseModel):
    user: str
    team: str
    pilot: bool = False
    cost: float = 0.0


@app.post("/route")
def route(c: Call):
    model, reason = resolve_model(c.user, c.team, c.pilot)
    if reason == "pilot":
        _spend[(c.user, "daily")] += c.cost
        _team_spend[c.team] += c.cost
    return {"model": model, "reason": reason,
            "daily_used": round(_spend[(c.user, "daily")], 4),
            "team_used": round(_team_spend[c.team], 4)}


@app.get("/report")
def report():
    return {
        "pilot_active": pilot_active(),
        "top_users": sorted(((u, round(s, 3)) for (u, b), s in _spend.items() if b == "daily"),
                            key=lambda kv: -kv[1])[:10],
        "teams": {t: round(s, 3) for t, s in _team_spend.items()},
    }
```

三个机制分别对应前文的设计：`pilot_active` 实现试用的**时效**，`resolve_model` 实现**超限降级而非直接拒绝**（除了峰值走限速），`/report` 提供**个人与团队两个视角**的消耗视图——后者是为了发现"个人都在额度内、部门整体异常"的情况。

## 九、下线同样重要

试用到期或推广决策为"不采用"时，需要能干净地下线。这里有三个容易出问题的点：

**第一，找到全部调用方。** 这正是统一入口的价值——调用方清单是入口的日志，不需要各自上报。

**第二，处理隐性依赖。** 有些调用方可能把试用模型名硬编码在配置里。下线前应当做一次全量扫描，并把模型名统一改为通过入口解析。

**第三，给出替代方案而不是直接关闭。** 下线时自动降级到默认模型，并在响应里保留降级标记，比直接报错对使用者友好得多，也能让依赖问题自然暴露。

把上下线合起来看，这套流程真正解决的是**节奏问题**。模型半年迭代一次的时候，串行审批完全可以跟上；迭代周期缩到几周之后，串行流程必然落后。而解耦之后，准入判断的频率与模型迭代无关，推广判断则可以跟着数据持续进行，两者各自都不会成为瓶颈。这也是"首日全员可用"能实现的根本原因——它不是把审批做得更快，而是让审批不再是关键路径，从而让模型的采纳速度与迭代速度对齐，而不是永远差一个版本。这一点在模型迭代周期缩短到几周量级之后，已经成为组织效率的直接影响项：采纳慢一步，团队在这个周期内的所有判断都建立在过时信息上。

## 十、成本与风险提示

- **准入判断要一次做全**，否则每次新模型发布都要重新审一遍通用条件，节奏又会被拖慢。
- **按人预算的额度需要迭代**。初值给得太紧会阻碍正当试用，太松则失去控制意义；上线后按实际分布调整。
- **成本追踪的粒度决定推广决策的质量**。只能看总账时，推广判断会退化为"整体切换或不动"。
- **试用流量与生产流量必须在计费与日志上完全分离**，否则推广评估的数字会被生产流量污染。
- **下线的替代路径要预先设计**，临时关闭会引发大量失败请求，反而让下线的阻力变大。

## 结论

模型发布首日全员可使用，靠的不是流程审批得更快，而是把"能不能用"与"该不该用"两个决策拆开：前者一次判完长期有效，后者用实验标签、按人预算与三类证据持续判断。这套结构的三处关键设计值得直接复用——**实验标签做隔离并带时效**、**按人预算分四类管理**（尤其峰值走限速而非拒绝）、**成本追踪接入可观测性以支持按任务类型分别推广**。最后一点往往被低估：有了统一入口，上线与下线都变成配置变更，这才是"跟得上迭代节奏"的前提。

还有一处组织层面的前提值得说明：这套流程能跑起来，依赖**接入方的自觉**——如果团队绕过统一入口自行对接模型，预算与归因都会失效，下线时也找不到全部调用方。所以网关的价值不只是技术上的统一，它同时是**组织约定的载体**：把"所有模型调用经过同一入口"变成一条硬性要求，后面所有的治理动作才有数据基础。我在 4sapi.com 上帮团队落地时，第一步从来不是配置网关，而是先把这条约定讲清楚。
