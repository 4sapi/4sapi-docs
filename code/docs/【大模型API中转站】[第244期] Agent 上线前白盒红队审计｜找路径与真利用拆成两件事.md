# 【大模型API中转站】[第244期] Agent 上线前白盒红队审计｜找路径与真利用拆成两件事

一个能读写文件、调用 API、执行代码的 Agent，上线前必须回答一个问题：外部内容能不能借它的手，做到部署方不允许它做的事。我在 4sapi（https://4sapi.com）上把这套白盒审计流程完整跑了一遍，结论是：找攻击路径和真正实施利用是两项不同的工作，必须拆开做。

## 一、安全失效的两个来源

AI agent 把语言模型与可修改的文件、可调用的 API、可执行代码的工具、外部数据和工具返回值连在一起，由此产生的失效分成两类。

第一类是对抗性内容改变了 agent 的工具使用。网页、Issue、检索结果、工具返回值里的一段文本，就能让 agent 去读不该读的文件、调不该调的工具、把数据发到不该发的地址。根因在于外部内容与系统指令之间没有确定的边界。

第二类是周边软件本身存在漏洞。路径穿越、命令注入这类问题与模型无关，harness、工具实现、插件、MCP 服务里任何一处拼接或校验不当，都会让一次本该受限的调用越过边界。

两类失效对应两种审计动作：第一类必须在运行时里验证，第二类可以在仓库里追踪。混在一起做，审计往往只覆盖一半。

## 二、这类审计的三个前提

白盒部署前审计的第一步，是把合法两个字写实。审计方可以访问目标仓库和一个受控运行时，但判定标准是：攻击必须通过任务定义的攻击者接口发起，并由外部验证器确认。

三个前提缺一不可。授权：只针对自有系统或已获书面授权的系统，范围、时间窗口与数据处理方式都要事先写清。受控运行时：所有验证动作都发生在隔离环境里，不接生产数据、不连生产网络、不动第三方系统。外部验证器：成败由独立于投放过程的判定器确认，而不是由执行攻击的一方自己宣布。

这三点是这类审计区别于普通红队的地方；没有它们，审计就成了没有边界的试探。

## 三、审计总流程：五个阶段

整条链路固定成五个阶段，前一段的产出是后一段的输入。

```text
[0] 授权与范围界定
    书面确认：目标仓库、受控运行时、攻击者接口、外部验证器、禁触项
              |
              v
[1] 仓库级路径追踪（发现角色）
    从攻击者可控输入出发，沿数据流走到敏感操作
    产出：有代码支撑的候选攻击路径清单
              |
              v
[2] 受控运行时验证（利用角色）
    在隔离环境里把候选路径变成具体行为
    按运行时反馈修正前提与路径
              |
              v
[3] 外部验证器确认
    由独立判定器按事先写死的标准确认结果
              |
              v
[4] 修复与回归
    按可达性与影响面排序修复；把路径固化成回归用例
```

阶段 1 和阶段 2 是两份不同的工作：前者在静态代码上做，后者在运行时里做。交给同一个环节，结论容易停在看起来能通。

## 四、阶段一：从攻击者可控输入追踪到敏感操作

路径追踪只做一件事：找出所有外部能写的位置，再找出所有后果严重的位置，然后证明两者之间存在一条有代码支撑的通道。发现角色的职责是追踪攻击者可控输入到敏感操作，记录候选路径；每条路径都要有证据，而不是直觉。

常见的攻击者可控输入源：

- 用户消息与多轮对话历史；
- 工具返回值，例如网页抓取与检索结果；
- 仓库里可被外部写入的文件，例如 Issue、PR 描述与测试数据；
- 外部 API 与 MCP 服务的响应；
- 部署链上游可控的配置与环境变量；
- 复制进代码库的文档片段与提示词模板。

常见的敏感操作：

- 工作区之外的文件读写与删除；
- Shell、子进程与任意代码执行；
- 出网请求，尤其是携带上下文的请求；
- 凭证读取与使用；
- 数据库与内部服务调用；
- Git 推送、部署动作与权限修改；
- 动态创建并执行新工具。

追踪有两条纪律。一是每条候选路径都要落到具体文件、具体函数、具体配置上，没有代码证据的推断不进清单。二是给路径标注前提，例如某个开关的默认值、某个挂载点是否可写；前提越多，运行时验证越容易证伪。

## 五、阶段二：路径发现与实施利用为什么必须分开

AgentXploit 把审计拆成两个角色：Analyzer Agent 负责仓库级路径发现，Exploiter Agent 负责把路径变成具体攻击，并依据运行时反馈修正。两阶段的输入、产出与失败方式都不一样。

| 维度 | 发现路径 | 实施利用 |
| --- | --- | --- |
| 输入 | 仓库代码、配置、工具定义 | 候选路径清单、受控运行时 |
| 方法 | 静态追踪、数据流分析 | 运行时执行、按反馈修正 |
| 产出 | 有代码支撑的候选路径清单 | 可复现的验证结果 |
| 主要失败方式 | 路径不可达 | 前提不成立，回退修正 |
| 衡量口径 | 覆盖率与证据完整度 | 成功率与可复现性 |
| 主要归属 | 代码与架构 | 运行时与配置 |

拆开的价值在数字上也能看到。AgentXploit-Bench 收录了 12 个开源 AI agent 系统与框架中的 72 个可复现漏洞；三次运行中，AgentXploit 的端到端成功率为 59.3%，Codex 为 38.4%，在 token 预算对齐的比较中 Codex 达到 46.3%。在已经提供注入点的 AgentDojo 上，Exploiter Agent 的利用成功率为 79.2%，AgentVigil 为 52.7%。

这说明分工的位置：注入点给好时，利用阶段的成功率可以很高；端到端数字更低，说明仓库级发现更容易卡住，两部分要单独测量。

## 六、受控运行时里怎么安全验证

验证阶段最容易被做成危险动作演示。要让验证既真实又安全，三件事必须做到。

隔离：每次验证用一次性容器或虚拟机，不挂载生产数据，网络只保留必要白名单，结束后整机销毁重建。

凭证不落地：运行时按需注入最小权限的临时凭证，不写进文件、不进模型上下文、日志脱敏，用后作废。

可回滚：环境有快照，验证前先确认回滚路径；把验证成功定义为在受控环境里观察到预期的副作用，而不是在真实系统里造成影响。

还要保留完整证据：谁在什么时间、通过哪个攻击者接口、投放了什么输入、触发了哪条调用链、被哪层策略拦截。这份记录要同时交给外部验证器和修复环节。

## 七、审计范围与授权清单

范围界定是唯一不能事后补的环节。下列各项必须在开工前书面写清，写不清就不开工。

| 必须界定的项 | 要写清的内容 | 没写清的后果 |
| --- | --- | --- |
| 目标仓库与提交范围 | 具体仓库与 commit 区间 | 范围漂移，结论无法复现 |
| 受控运行时边界 | 网络白名单、挂载点、资源上限 | 验证可能触达真实数据 |
| 攻击者接口 | 从哪里发起、允许哪些通道 | 结果无法归因与复现 |
| 外部验证器 | 判定标准、证据格式、谁来判 | 成败由执行方自证 |
| 时间窗口与人员 | 起止时间、参与人、联系方式 | 越界操作无人可查 |
| 数据处理与销毁 | 证据如何保存与销毁 | 审计数据成为新泄露面 |
| 发现上报与修复 | 谁先知道、多久修完、如何回归 | 高危项被拖到上线之后 |
| 禁止触碰项 | 生产数据、第三方系统、真实用户 | 一次越界就毁掉授权 |

清单之外还有一条底线：只审自有系统。对不属于自己的系统做同类动作，不在讨论范围内。

## 八、外部验证器：不能自己判自己

验证阶段的执行方天然倾向于宣布成功，所以成败要由外部验证器确认。判定标准同样要事先写死，至少三条：目标副作用是否真实发生、动作是否通过约定的攻击者接口发起、过程是否留下可复现的记录。

外部验证器的第二个作用是过滤环境噪声。受控环境里的一次异常返回，可能来自配置漂移、凭证过期或网络抖动，而不是真实漏洞；没有独立判定，这些都会被记成利用成功，把修复资源引到错误的位置。

## 九、把候选路径固化成回归测试用例

审计产出的候选路径不能只停在报告里，要变成可回归的测试用例集：每条路径一个用例，写明输入源、敏感操作、复现前提与期望的策略判定。这样修复后能自动验证该拦的确实拦住了，下一次改配置、加插件时也能重跑。

下面这段脚本把候选路径清单交给模型整理成可回归的用例集。Key 从环境变量读取，请求走 OpenAI 兼容入口。

```python
import json
import os
from openai import OpenAI

client = OpenAI(
    api_key=os.environ["FOURSAPI_API_KEY"],
    base_url="https://4sapi.com/v1",
)

SYSTEM = """把一条白盒审计发现的候选路径整理成回归用例，只输出 JSON：
{
  "case_id": "小写短横线标识",
  "source": "攻击者可控输入源",
  "sink": "敏感操作",
  "preconditions": ["复现所需的最小前提"],
  "expected": "期望被策略拒绝或降级的具体判定",
  "priority": "block | high | medium | low"
}
没有代码证据的路径不要生成用例。"""


def to_case(path, model="gpt-6-sol"):
    resp = client.chat.completions.create(
        model=model,
        messages=[
            {"role": "system", "content": SYSTEM},
            {"role": "user", "content": json.dumps(path, ensure_ascii=False)},
        ],
        response_format={"type": "json_object"},
    )
    return json.loads(resp.choices[0].message.content)


def build_suite(candidates_file, out_file):
    with open(candidates_file, encoding="utf-8") as f:
        paths = json.load(f)["paths"]
    cases = []
    for path in paths:
        if not path.get("code_evidence"):
            continue  # 无代码支撑的候选路径不进回归集
        cases.append(to_case(path))
    with open(out_file, "w", encoding="utf-8") as f:
        json.dump({"cases": cases}, f, ensure_ascii=False, indent=2)
    return len(cases)


if __name__ == "__main__":
    n = build_suite("audit/candidates.json", "audit/regression_suite.json")
    print(f"{n} 条候选路径已固化为回归用例")
```

用例集要和策略层对上：每条用例的 expected 必须是可自动判定的结论，例如工作区外写入被拒绝、出网请求被拦截、凭证读取返回空。判不了的期望要改写成可判的形式，否则回归会退化成人工目测。

## 十、修复优先级：按可达性与影响面排序

修复顺序不该按漏洞数量排，而该看两个维度：路径在真实部署里是否可达，命中后的影响面有多大。可达性看攻击者接口是否暴露、前提是否默认成立；影响面看敏感操作的等级，从数据外带到权限修改逐级上升。

```text
这条候选路径在真实部署里可达吗？
    |
    +-- 可达，且能触达高影响敏感操作
    |       -> 阻断上线，先修策略与实现，再重跑回归
    |
    +-- 可达，但影响面有限
    |       -> 本次修复，排进上线前清单
    |
    +-- 不可达，但前提可能随配置变化
    |       -> 加监控与告警，写成回归用例长期看护
    |
    +-- 不可达，且前提在实际部署中不存在
            -> 记录原因，降级为观察项
```

修复手段也分层：能在策略层拦住的优先改策略；必须改代码的连同工具实现一起修；需要架构拆分的，例如把高风险操作拆成专用工具，按项目节奏推进；短期内无法根治的，先用监控与审批补偿。

## 十一、这套方法的量级

把流程放回参照系，几个数字可以直接对照。AgentXploit-Bench 的 72 个可复现漏洞分布在 12 个开源 AI agent 系统与框架里，说明同类问题是普遍存在的工程债。端到端成功率 59.3% 对 38.4%，token 预算对齐后 Codex 为 46.3%，说明两阶段分工在相同资源下更有效；在已提供注入点的 AgentDojo 上，Exploiter Agent 的利用成功率达到 79.2%，AgentVigil 为 52.7%，说明验证环节做得好不好，直接决定审计结论的成色。

按工程经验估算，一轮完整审计里，仓库级追踪产出的候选路径约有半数会在运行时验证阶段被排除（估算，随系统复杂度浮动）。被排除的路径会成为回归用例里的观察项，前提变化时能被重新激活。

## 十二、上线前审计 checklist

上线前按这个清单逐条确认：

1. 授权文件是否覆盖仓库、受控运行时与时间窗口；
2. 攻击者接口是否已定义，且与实际暴露面一致；
3. 候选路径是否每条都有代码证据与前提说明；
4. 运行时验证是否在一次性环境完成，凭证是否按需注入、用后作废；
5. 外部验证器是否独立于执行方，判定标准是否事先写死；
6. 每条路径是否都有可达性与影响面评级；
7. 高影响且可达的项是否已修复并重跑通过；
8. 修复过的路径是否已进入回归用例集并接入持续集成；
9. 无法立即修复的项是否有监控或审批补偿；
10. 审计证据、结论与未决项是否归档并明确复查时间。

## 十三、常见误区与合规边界

三个误区最容易踩。一是把审计做成绕过一切的演示，这会越过授权边界；正确做法是始终通过任务定义的攻击者接口发起验证。二是只在模型层加提示词防护而不动策略层。三是审计一次就收工，攻击面随配置、插件与工具更新持续变化，回归用例要长期保留。

合规边界只有一句话：只对自有系统做白盒审计，全部动作发生在受控运行时里；任何可直接复用去攻击他人系统的细节都不应出现在审计报告里，保留证据位置与判定标准就够了。

## 结论

上线前的白盒红队审计，本质上是把两件事拆开：先在仓库里找攻击路径，再到受控运行时里验证利用，最后由外部验证器确认，修复之后固化成回归用例。发现路径和实施利用的输入、方法、产出与失败方式都不同，分开做，数字和速度都更好。

执行时守住三个前提（授权、受控运行时、外部验证器），按流程图跑五个阶段，用可达性与影响面排修复优先级，用回归用例把一次性审计变成长期防线。在 4sapi.com 这类统一入口上把审计脚本与回归用例接进现有流水线，是把这套流程变成日常动作的最短路径。
