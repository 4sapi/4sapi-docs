# 【大模型API中转站】[第193期] 83 万行 Rust 用 Agent 重写｜单人数月替代团队两年

一个跑在 Node.js 与 V8 上、用 TypeScript 写成、终端界面靠 Ink + React 撑起来的智能体运行时，被整体重写成 832,378 行生产级 Rust；工期约 14.5 周，横跨 128 个 pull request，绝大多数代码由 AI 智能体编写，主力只有一名开发者。这一篇不谈模型跑分，只拆这套工程方法：增量 PR 怎么分流、回归门禁怎么设、单开发者加智能体的额度怎么算、共享运行时怎么把一次修复摊到所有产品上。配套的调度与核算代码我挂在 4sapi（https://4sapi.com）的网关侧跑。

## 一、开篇痛点：一次性切换为什么必然失控

八十万行级别的语言迁移，失败很少败在语法层面。真正的坑在切换策略：把所有改动堆在一条长期分支上，等全部完成再一次性合并回主干。分支存活多久，主干就漂移多久，重写分支就得被迫做同样久的语义对齐；功能冻结窗口一开，同期所有能力扩展只能排队等待；到了切换那一刻，全部风险同时到期，而中间没有任何可以停下来复核的检查点。真出了问题，回滚的代价接近再做一次迁移。

第二个坑是验收口径。语言迁移最大的错觉是"编译通过就等于迁移完成"。编译只证明类型对得上，不证明行为等价：并发模型从事件循环换成原生线程之后，回调顺序、取消语义、错误传播路径都会变；一个在 TypeScript 里靠单线程假装原子的小段逻辑，落到真并发的 Rust 里可能立刻暴露竞态。因此迁移的验收单位不该是"整个运行时",而应该是"某个可以被单独验证的行为切片"。

第三个坑是成本看不到中途水位。一次性切换的预算模型只有两档：项目结束前一路烧钱，结束后突然省钱。中间没有任何反馈回路告诉团队"现在这个做法贵得离谱"。增量交付天然带反馈——每个 PR 都要过门禁、都要算一次额度消耗，贵的做法会在一两周内自己暴露出来。

## 二、事实底稿：先把数字与边界钉死

先把事实边界钉死。GitHub Copilot CLI、Copilot app、Copilot SDK 三者背后是同一个 Copilot agent runtime，一个可以嵌入应用与服务的智能体运行框架，而不是三套各自为政的实现。重写之前，这套运行时由 TypeScript 编写，跑在 Node.js 与 V8 之上，最初服务于 GitHub Copilot cloud agent（CCA），终端交互层用 Ink + React 搭建。重写之后，它变成完全用 Rust 实现的生产级运行时，代码量 80 万行以上，精确数字是 832,378 行。

| 维度 | 迁移前 | 迁移后 |
| --- | --- | --- |
| 实现语言 | TypeScript | Rust |
| 运行基础 | Node.js + V8 | 原生编译运行时 |
| 终端界面 | Ink + React | Rust 侧重写 |
| 代码规模 | — | 832,378 行生产级代码 |
| 执行主体 | 完整开发团队 | 一名开发者 + AI 智能体 |
| 交付节奏 | 立项一到两年 | 约 14.5 周，128 个 PR 增量合入 |

工期结构同样关键：整个过程约 14.5 周，横跨 128 个 pull request，逐个合入 main，并随版本增量发布，没有等到最后一次性切换。其中大部分代码由 AI 智能体编写。人力对比更直白：同类项目此前需要一整个开发团队做一到两年，这一轮主要由一名开发者用几个月完成；团队其他成员在同一时间并没有停下来，而是继续扩展运行时的能力与覆盖范围。

质量侧的口径也要写清楚：少数不可避免的回归问题在过程中被快速发现并修复，运行时性能提升数个数量级。这里的措辞是"数个数量级"，不是一个精确倍率，做容量规划时必须按自家负载重测，不能直接按这个描述拍板。

## 三、增量 PR 分流：128 次小赌注替代一次大赌注

128 个 PR 是整套方法里最值得抄走的一条。它的核心不是"提交次数多"，而是每一次提交都是可以独立回滚、独立观察、独立计价的原子单元。运行时的能力在迁移过程中一直可用，旧实现与新实现可以在同一版本里共存，切片的替换顺序由我控制，而不是由分支合并日决定。

分流要按依赖拓扑排，不按文件目录排。纯数据结构、错误类型、序列化这些叶子节点先走，它们被大量上层模块依赖，先固化能显著降低后面每个切片的冲突概率；状态机与调度核心放中间，因为它们的行为契约必须等叶子层稳定后才能定死；最后才是四处调用别人的装配层与 CLI 入口。终端 UI 这类高耦合面单独成批，不与核心逻辑混在一个 PR 里。

每个 PR 还要守住三条硬边界：其一，单个 PR 的改动规模上限固定，超了就拆，避免评审和回滚成本失控；其二，任何 PR 都不允许同时改行为语义与语言栈，两件事混在一起出问题时无法判断是翻译错了还是设计错了；其三，每个 PR 必须自带上线开关或兼容层，保证合入之后主干随时可发布。

## 四、架构动因：产品不该各自实现一套 harness

这套运行时同时支撑 VS Code、Visual Studio、CCA、Copilot Code Review（CCR）、Copilot Cowork、Copilot Studio，以及 Excel、Outlook、PowerPoint、Word 等产品。这些产品此前大多各自实现了自己的智能体循环，之后陆续替换为 Copilot SDK——也就是进入该运行时的入口。

动因很朴素：这些产品都不应该各自实现一整套生产级 agent harness。智能体循环看起来只是一段"调用模型、解析工具调用、执行工具、回填结果"的 while 循环，但要做到生产级，必须同时解决推理重试、工具沙箱、权限审批、会话持久化、断线恢复、并发调度、可观测性与成本归集。每多一个产品自己实现一遍，就多一份重复的缺陷面。

共享之后得到的是复利：智能、安全、可靠性与性能不再各修各的，一处修复能修复所有产品。这句听起来像口号，在成本表上却非常具体——同一个权限漏洞的修复成本从"产品数 × 单点修复"变成"1"，同一个性能优化的覆盖面从"一个入口"变成"全部入口"。这也是把 832,378 行 Rust 一次性重写值得做的根本理由：底座的收益会被上层所有产品放大。

## 五、回归样本与门禁：让智能体的提交可信

让 AI 智能体写大部分代码，瓶颈从来不是生成速度，而是判断"这段生成结果能不能信"。我的做法是把可信度外置成机器可判定的门禁，而不是靠人工读 diff。

回归样本要提前攒，不能等重写完再补。有效样本的构成是三段：真实会话回放（把线上或团队日常使用的会话轨迹存下来，作为行为快照）、边界用例（空输入、超长上下文、并发取消、中断恢复、工具报错、权限被拒）、以及黄金输出对照（同一输入在旧实现与新实现上跑，比较结构化结果而不是比较字符串）。三段里最有价值的是第一段，因为它覆盖的是真实分布，不是想象出来的分布。

门禁分四层，按代价从低到高排列，每层都必须能自动判定通过或失败：

1. 编译与静态检查：目标是零警告增量，避免新代码把历史噪音放大；
2. 单元与契约测试：重点覆盖翻译过程中最容易走样的错误传播与取消语义；
3. 回放对照：同一批会话样本跑新旧两套实现，输出结构化差异报告；
4. 性能基线：单请求延迟、吞吐、内存峰值三项，任一项回退超过阈值即拦截。

四层门禁的顺序不能颠倒。回放对照很贵，必须放在静态检查和单测之后，否则大量本该在十秒内被打回的提交会挤占最贵的算力预算。

## 六、单开发者加智能体的额度与成本核算

这一轮的成本结构，和人海战术完全不同。团队两年的人力预算里，绝大部分是沟通、排期和等待；一人加智能体的结构里，绝大部分是模型 token 与算力，人力占比反而很小。核算方法也要跟着换：不再按人月估算，而是按"每个 PR 的 token 消耗 × PR 数量"估算，再加一层重试放大系数。

必须承认一个现实：编码智能体的 token 消耗不是线性的，而是随任务难度超线性上升。改一个纯函数可能只花几千 token；调一个跨越三层并发语义的回归可能烧掉几十万 token，因为智能体会反复读文件、跑测试、猜错、再读一遍。因此预算模型要按 PR 类型分层定价，而不是给全项目一个平均单价。

| PR 类型 | 占比估算 | 单 PR token 量级 | 主要放大因素 |
| --- | --- | --- | --- |
| 叶子模块翻译 | 高 | 低 | 依赖少，一次成型 |
| 状态机与调度核心 | 中 | 高 | 反复回放对照与并发调试 |
| 装配层与 CLI 入口 | 中 | 中 | 跨模块接口对齐 |
| 回归修复类 | 低 | 很高 | 定位成本远高于修改成本 |

重试放大系数是这张表里最容易被忽略的一项。同一个任务让智能体重试三次，成本大约是三倍，但成功率未必是三倍。因此额度控制必须设三重闸门：单 PR 上限、单日上限、单阶段上限。撞到任何一重就停下来人工判断，而不是让循环自动续跑。

## 七、自建 harness 与直接调用 API 的成本对比

把智能体当编码劳动力用，有三种成本结构，长期账完全不同。

第一种是直接调用 API，自己写一层薄薄的循环。边际成本最低，因为每一分钱都花在推理上，没有任何中间层加价。代价是 harness 要自己写：工具定义、沙箱、重试、上下文压缩、失败回滚、并发调度、成本归集，一样都不能少。做小规模任务时这是最划算的选择；做到几十个并行任务时，维护这套循环本身就会变成一条独立的人力线。

第二种是自建一套生产级 harness。控制力最强，可以针对自家代码库做深度优化，例如自定义索引、自定义编译缓存、自定义工具集。代价是这套 harness 的研发与维护成本会持续存在，而且它会变成一个新的、需要长期供养的系统。

第三种是复用已经成型的智能体运行框架，把产物接到自家流程里。优势是安全、可靠性、性能这些最难写的部分不用重写；劣势是接入方式受框架约束。值得注意的是，共享运行时的价值正好落在这里：一处修复能修复所有接入方，相当于把 harness 的维护成本按接入方数量摊薄。

三种结构的分界线可以概括成一句话：任务量小时买 API，任务量大且流程独特时自建，任务量大且需求通用时复用框架。真正贵的选择是"任务量很大、却坚持自己维护全套 harness 又不愿意投入维护人力"——那条路上，每一次回归都要靠通宵解决。

## 八、共享运行时的复用收益

共享带来的收益可以从三个层面量化。

修复层面：同一个缺陷在 N 个产品里各修一次，总成本是 N 倍；收敛到一套运行时之后是 1 倍，节省量与产品数量成正比。接入的产品越多，这条曲线越陡。

能力层面：新增一项能力（比如更严格的工具权限策略、更完整的会话恢复、更细的成本归集），只要底座做一次，所有接入方同时获得。这项收益很难直接折成钱，但它决定了产品线的迭代速度上限。

性能层面：优化落在共享运行时上，等于对所有产品同时生效。运行时性能提升数个数量级这条结论，价值不在于某一个 CLI 变快了，而在于 VS Code、Visual Studio、Excel、Outlook、PowerPoint、Word 这些入口同时变快了。

共享也有代价，必须提前设计，否则会把收益吃回去：接口版本要有兼容窗口，避免接入方被迫跟随升级；能力开关要能按接入方灰度，避免一个产品的特殊需求污染全局默认值；成本归集要能按接入方拆账，否则谁在用、谁在烧钱说不清楚；权限模型要在底座统一，不能让某个接入方绕过审批路径。

## 九、调度链与治理链

把整套方法画成一条链，口径会清楚很多：

```text
事实底稿与迁移范围冻结
        |
   依赖拓扑排序（叶子 -> 核心 -> 装配 -> UI）
        |
   切片成 PR 批次（单批改动规模设上限）
        |
        +--> 编码智能体按批次生成改动
        |         |
        |    自检：编译 + 静态检查 + 单测
        |         |
        |    回放对照：新旧实现结构化差异
        |         |
        |    性能基线：延迟 / 吞吐 / 内存
        |         |
        +--> 任一门禁失败 -> 打回同一批次重做（计入重试额度）
        |
   门禁全绿 -> 合入 main -> 随版本增量发布
        |
   额度与成本归集（单批 / 单日 / 单阶段三重闸门）
        |
   回归样本回流：本批暴露的缺陷补进样本库
        |
   共享运行时同步惠及全部接入产品
```

这条链上最关键的两处设计是回环：失败批次打回时携带完整上下文重做，而不是从头再来；每个批次暴露出的新缺陷都补进回归样本库，让样本库随批次变厚。128 个 PR 跑完，样本库本身也成了资产。

## 十、教程：按 PR 分批调度 Agent

调度器的职责只有三件事：把改动计划拆成有上限的批次、把批次交给智能体、把门禁与额度管住。密钥只从环境变量读取，仓库里不落任何明文凭证。

```python
import os
import json
import time
from dataclasses import dataclass, field

from openai import OpenAI

# 兼容 OpenAI 协议的接入层：密钥与地址都从环境变量读取，代码与仓库中不保留明文
client = OpenAI(
    api_key=os.environ["OPENAI_API_KEY"],
    base_url=os.getenv("OPENAI_BASE_URL", "https://4sapi.com/v1"),
)
MODEL = os.environ["AGENT_MODEL"]  # 用自己在控制台选定的模型 ID

# 单价只作为估算输入，按自家账单口径填，不写死任何厂商报价
PRICE_IN = float(os.getenv("PRICE_IN_PER_MTOK", "0"))
PRICE_OUT = float(os.getenv("PRICE_OUT_PER_MTOK", "0"))

MAX_LOC_PER_PR = int(os.getenv("MAX_LOC_PER_PR", "4000"))
MAX_TOKENS_PER_PR = int(os.getenv("MAX_TOKENS_PER_PR", "600000"))
MAX_TOKENS_PER_DAY = int(os.getenv("MAX_TOKENS_PER_DAY", "4000000"))


@dataclass
class Batch:
    pr_id: int
    title: str
    files: list[str]
    loc: int
    kind: str  # leaf / core / assembly / ui
    attempts: int = 0
    spent_tokens: int = 0
    ctx: list[dict] = field(default_factory=list)


def plan_batches(plan: list[dict], max_loc: int = MAX_LOC_PER_PR) -> list[Batch]:
    """按依赖拓扑给定的顺序装箱：叶子先走，超限即切新批次。"""
    order = {"leaf": 0, "core": 1, "assembly": 2, "ui": 3}
    batches, cur, cur_loc = [], [], 0
    for item in sorted(plan, key=lambda x: order.get(x["kind"], 9)):
        if cur and cur_loc + item["loc"] > max_loc:
            batches.append(cur)
            cur, cur_loc = [], 0
        cur.append(item)
        cur_loc += item["loc"]
    if cur:
        batches.append(cur)
    return [
        Batch(
            pr_id=i + 1,
            title=f"{b[0]['kind']}:{b[0]['name']}..{b[-1]['name']}",
            files=[f for it in b for f in it["files"]],
            loc=sum(it["loc"] for it in b),
            kind=b[0]["kind"],
        )
        for i, b in enumerate(batches)
    ]


def run_gate(batch: Batch) -> dict:
    """四层门禁：编译 -> 单测 -> 回放对照 -> 性能基线。任一层失败即整批打回。"""
    stages = ["compile", "unit", "replay", "perf"]
    report = {"pr_id": batch.pr_id, "stages": {}, "pass": True}
    for s in stages:
        ok = call_gate(batch, s)  # 接自家 CI，返回布尔
        report["stages"][s] = ok
        if not ok:
            report["pass"] = False
            break  # 便宜的门禁先跑，失败即短路，不浪费贵的算力
    return report


def call_gate(batch: Batch, stage: str) -> bool:
    raise NotImplementedError("接自家 CI：编译、单测、回放对照、性能基线")


def budget_ok(day_spent: int, batch: Batch) -> bool:
    return (
        batch.spent_tokens < MAX_TOKENS_PER_PR
        and day_spent + batch.spent_tokens < MAX_TOKENS_PER_DAY
    )


def estimate_cost(in_tok: int, out_tok: int) -> float:
    return in_tok / 1e6 * PRICE_IN + out_tok / 1e6 * PRICE_OUT


def run_batches(batches: list[Batch], max_attempts: int = 3) -> list[dict]:
    results, day_spent = [], 0
    for b in batches:
        while b.attempts < max_attempts:
            b.attempts += 1
            in_tok, out_tok = dispatch_agent(b)          # 调模型生成改动
            b.spent_tokens += in_tok + out_tok
            if not budget_ok(day_spent, b):
                b.ctx.append({"role": "user", "content": "额度闸门触发，停止扩写，只做最小修复"})
            report = run_gate(b)
            if report["pass"]:
                day_spent += b.spent_tokens
                results.append({"pr": b.pr_id, "ok": True, "attempts": b.attempts,
                                "cost": estimate_cost(in_tok, out_tok)})
                break
        else:
            results.append({"pr": b.pr_id, "ok": False, "attempts": b.attempts,
                            "note": "转人工判断，不自动续跑"})
    return results


def dispatch_agent(batch: Batch) -> tuple[int, int]:
    """把批次交给智能体，返回 (输入 token, 输出 token)。"""
    resp = client.chat.completions.create(
        model=MODEL,
        messages=[
            {"role": "system", "content": "只改指定文件，不改行为语义，输出可评审的补丁。"},
            {"role": "user", "content": json.dumps({"files": batch.files}, ensure_ascii=False)},
        ],
    )
    usage = resp.usage
    return usage.prompt_tokens, usage.completion_tokens
```

这套调度器有三个刻意设计。其一，门禁顺序硬编码成从便宜到贵，并在第一次失败处短路，避免用最贵的回放对照去做本该静态检查拦下的题目。其二，额度闸门不抛异常，而是给智能体追加一条"只做最小修复"的指令，把超预算的批次降级成收尾模式，而不是直接丢弃。其三，重试到上限就转人工，不让循环无限续跑——自动续跑是额度失控最主要的入口。

## 十一、成本估算模板

把 token 账单换算成可决策的数字，需要一张能把"每批"汇总到"每阶段"的表。下面这套口径可以直接套：

| 科目 | 计算方式 | 用途 |
| --- | --- | --- |
| 单批推理成本 | 输入 token × 单价 + 输出 token × 单价 | 判断批次设计是否合理 |
| 重试成本 | 单批成本 × 实际尝试次数 - 首次成本 | 定位难切的模块与不稳的提示词 |
| 阶段总成本 | 各批成本求和 | 与团队人力方案做对比 |
| 人力替代量 | 团队月数对应的人力预算 | 折算净收益 |
| 门禁算力成本 | 回放对照与性能基线的机器时长 | 容易被忽略的隐藏科目 |
| 回归修复成本 | 修复批次成本之和 | 衡量迁移质量 |

两类错误在这一步最常见。第一类是把门禁算力算成零：回放对照要重跑新旧两套实现，性能基线要独占机器，这些机器成本在长周期项目里不是小数。第二类是把重试成本按平均值摊销：重试是超线性的，少数几个难切模块能吃掉相当比例的预算，只有单独列出来才会被发现。

## 十二、上线前的可复用清单

迁移类项目开工前，按这张清单逐条确认：

1. 事实底稿写清楚：语言、运行时、代码规模、工期、合入方式，一人一份，口径统一；
2. 依赖拓扑排序完成，叶子模块排在核心模块之前；
3. 单 PR 改动规模上限确定，超过即拆；
4. 每个 PR 自带上线开关或兼容层，合入后主干随时可发布；
5. 四层门禁全部可自动判定，且顺序固定为编译、单测、回放、性能；
6. 回归样本库先攒后做，覆盖真实会话回放、边界用例、黄金输出对照；
7. 额度三重闸门就位：单批、单日、单阶段；
8. 重试上限与人工接管条件写进流程，禁止无限自动续跑；
9. 成本表覆盖推理、门禁算力、回归修复三类科目；
10. 密钥只走环境变量注入，禁止进入代码、日志与提示词；
11. 共享运行时的接口兼容窗口、灰度开关与按接入方拆账方案确定；
12. 每批暴露的新缺陷回流样本库，让样本随进度变厚。

## 十三、成本与风险提示

- 832,378 行与约 14.5 周是特定项目的口径，直接套到自家代码库上会严重失真，先用自己的小规模切片实测再外推；
- "数个数量级"的性能提升不是可观测量，容量规划必须按自家负载重压，不能按描述拍板；
- AI 智能体编写大部分代码，意味着评审重点必须从"写得对不对"转向"门禁能不能判定它对不对"，门禁弱的团队会先崩在回归上；
- 重试是超线性成本项，不设上限的自动续跑是最主要的额度失控入口；
- 增量分流的收益依赖主干始终可发布，一旦出现"先合进去等会儿再修"的批次，回滚能力立刻归零；
- 共享运行时的收益与接入方数量成正比，接入方少的时候，底座维护成本可能高于收益，需要先算账；
- 权限、审批与审计要在底座统一，接入方不得绕过；敏感凭证不进模型上下文，也不进代码仓库；
- 只走合法合规的接入与计费渠道，不做任何绕过官方限制的配置。

## 十四、总结

这一期把"用 API 型编码智能体做超大规模重构"拆成了一套可复用的工程方法：832,378 行 TypeScript 到 Rust 的完整迁移，横跨 128 个 pull request 增量合入 main 并随版本发布，约 14.5 周由一名开发者配合 AI 智能体完成，替代了此前需要一个完整团队做一到两年的方案，少数不可避免的回归在过程中被快速发现并修复，运行时性能提升数个数量级。方法的核心是三件事——按依赖拓扑把迁移切成可独立回滚的批次、把可信度外置成四层可自动判定的门禁、把额度管成单批单日单阶段三重闸门。收益侧则来自共享运行时：同一个运行时支撑 VS Code、Visual Studio、CCA、Copilot Code Review（CCR）、Copilot Cowork、Copilot Studio 以及 Excel、Outlook、PowerPoint、Word，产品不再各自实现一套生产级 agent harness，一处修复即可修复全部。调度与核算代码我挂在 4sapi（https://4sapi.com）的网关侧配合使用，批次设计、门禁顺序与成本科目都可以照抄，只有数字必须按自家代码库重测。这套分批迁移的取舍在自家项目里怎么落地，欢迎在评论区聊聊。
