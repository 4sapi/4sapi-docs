# 【大模型API中转站】[第165期] SWE-2 编码模型横向对比｜四分之一价格逼近旗舰

这一期把镜头对准编码模型的价格断层：SWE-2 把接近旗舰的编码成绩装进了四分之一价格的档位。整篇围绕一个工程问题展开——编码 Agent 的 token 账单，如何靠任务分层路由压下来。

## 一、开篇痛点：月账单拆到哪里都疼

我常年在几个仓库上跑编码 Agent：丢一个 Issue 进去，让 Agent 自己定位、改代码、跑测试、交 diff。用久了会发现一个尴尬的结构：绝大多数调用其实落在低难度任务上——定位明确的 bug 修复、补几条边界测试、单模块内的小重构；真正需要深度推理的疑难任务反而是少数。但账单是按旗舰单价全额结算的，难度与单价的错配，直接变成了钱。

Agent 化还在放大这个错配。上下文反复进出、工具调用来回往返、失败后的自动重试，每一环都在给 token 计数器加数。同样一个改 bug 的任务，对话式问一次模型，和交给 Agent 跑完整流程，消耗完全不在一个量级。单价不降，消耗量上涨，月账单的曲线就可想而知。

我的解法不是换更便宜的模型硬扛，而是分层路由：低难度任务走性价比档，高难度任务保留旗舰档。要做这件事，物理前提是把所有模型收进同一个 OpenAI 兼容入口——我平时通过 4sapi（https://4sapi.com）把多家模型挂进同一个 base_url，之后切换模型只是改一个字符串的事。这一期的新变量是 SWE-2，它把性价比档的天花板抬高了，路由策略值得重新算一遍。

## 二、SWE-2 成绩单：50.0% 分数与 64% 成本降幅

先把关键数字摆齐。Cognition 发布了编码模型 SWE-2，在 FrontierCode 1.1 Main1 基准上得分 50.0%，同时成本便宜 64%。这两个数字单看都不算惊人，放在一起才显出分量：在同一条基准线上，SWE-2 的得分与成本双双越过 SWE-1.7 和 Grok 4.6——分数更高，价格更低，两头的账都赢了。

再往上比：SWE-2 以小得多的价格，匹配了 GPT-5.6 Sol 与 Fable 5/5.1 的成绩；面对 OpenAI 当前旗舰 GPT-6 Astra，则以四分之一的成本把差距缩小到几分以内。补充一点背景：GPT-6 Astra 主打推理、编码与电脑操作，正在向 Pro/Plus/Enterprise/Business 各档推开，是这一轮对比里最贵也最强的参照物。

我的读法是：编码模型市场出现了清晰的性价比断层——同一个质量档位里，第一次有了价格低一截的选项。对跑编码 Agent 的团队来说，这不是换个聊天模型的问题，而是路由策略可以重新定价的问题：路由点往下移一格，账单结构就换一档。

## 三、原理速览：性价比断层与路由点

把六个模型按"质量—成本"两个轴摆开，断层结构一目了然（下图为定性示意，非精确刻度）：

```text
质量
  ^
  |  GPT-6 Astra ............ 旗舰档：分数最高，成本最高
  |
  |  GPT-5.6 Sol == Fable 5/5.1 .. 质量与 SWE-2 相当，价格高出一截
  |  SWE-2 .................. 性价比断层点：低一档价格，贴近上一档质量
  |
  |  SWE-1.7 == Grok 4.6 .... 得分与成本双输给 SWE-2
  |
  +-----------------------------------------------> 成本
     低                                              高

路由点卡在断层处：任务难度低于阈值 -> 走 SWE-2 档
                  任务难度高于阈值 -> 走 GPT-6 Astra 档
```

这张图里真正重要的不是某个模型的具体位置，而是 SWE-2 上方那一格空档：它上面一档的质量，要花高得多的价格才买得到；它下面一档的选项，则分数和价格双输。路由的本质，就是把决策点卡在这个断层上——断层以下交性价比档，断层以上交旗舰档。

还有一个推论：断层位置不是静态的。每次有新模型发布，断层就可能整体下移一格，路由点也要跟着移。所以路由层不应该把模型名和阈值写死在业务代码里，而要保持可配置——这也是后面接入方案的设计原则。

顺带把路由和负载均衡的分工说清楚。负载均衡解决的是同一档位内的容量问题：同一档挂多个模型或多个渠道，按延迟与可用性分流；分层路由解决的是档位之间的定价问题：按任务难度决定进哪一档。两者叠加才是完整的接入架构——路由定档，均衡保活，任何一层失效都不应该拖垮另一层。

## 四、横向对比表：六个模型的位置

下表把成绩与成本放在一起看。SWE-2 的分数与成本关系有具体数字，其余位置只做定性描述，口径在最后一列标明：

| 模型 | FrontierCode 1.1 Main1 得分 | 成本位次 | 与 SWE-2 的关系 | 口径 |
| --- | --- | --- | --- | --- |
| SWE-2 | 50.0% | 低 | 基准 | 具体数字 |
| SWE-1.7 | 低于 SWE-2 | 高于 SWE-2 | 得分与成本双输 | 定性 |
| Grok 4.6 | 低于 SWE-2 | 高于 SWE-2 | 得分与成本双输 | 定性 |
| GPT-5.6 Sol | 与 SWE-2 同一质量档 | 明显更高 | 质量相当、价格更贵 | 定性 |
| Fable 5/5.1 | 与 SWE-2 同一质量档 | 明显更高 | 质量相当、价格更贵 | 定性 |
| GPT-6 Astra | 高于 SWE-2，差距几分以内 | 最高档 | SWE-2 以约四分之一成本逼近 | 定性（相对口径） |

需要说明：表中除 50.0% 之外均为定性位次，"四分之一成本""几分以内"都是相对口径，不是具体报价，价格随时可能调整。读表的方式是先找两个锚点：同一质量档里最便宜的，现在指向 SWE-2；质量上限，仍然是 GPT-6 Astra。分层路由要回答的问题只是——手头每个任务，该落在哪一列的哪一格。

## 五、任务分层：哪些活下沉，哪些活留守旗舰

分层清单从任务特征出发，比从模型价格出发更稳：

**下沉到性价比档（SWE-2 档）：**

- 带失败测试复现的 bug 修复：定位路径短，验证标准明确；
- 补单元测试和边界用例：产出好不好，测试通过率直接衡量；
- 单模块内的小重构：影响面可以被 diff 和测试框住；
- 依赖小版本升级、格式调整、注释与文档补充；
- CI 告警的初步分诊：先判断是不是真问题，再决定派给谁。

**留守旗舰档（GPT-6 Astra 档）：**

- 跨模块的大型迁移：改动半径大，错误成本按模块数放大；
- 架构设计与技术选型：错误决策的代价远超单次调用差价；
- 没有复现路径的疑难 bug：需要长链推理，不是模式匹配能解决的；
- 接口契约与数据结构的大改动：牵一发动全身；
- 安全敏感路径与生产事故热修：不容许试错。

**灰色地带：** 中型重构、跨两个模块的改动这类不好归类的任务，先用性价比档跑一轮，产物过完整回归再合入；失败率超标就把阈值收紧。分层的目的是省预算，不是省验证。

## 六、接入教程：一个入口跑两条产线

接入结构很简单：所有模型收进同一个 OpenAI 兼容入口，路由层只做两件事——给任务定级，沿降级链调用。以 4sapi（https://4sapi.com）为例，申请好兼容入口后，base_url 指向网关地址，密钥走环境变量，路由逻辑全部留在应用侧：

```python
import os
from openai import OpenAI

# 网关地址与密钥从环境变量读取，避免硬编码进代码库
client = OpenAI(
    api_key=os.environ["GATEWAY_API_KEY"],
    base_url=os.environ["GATEWAY_BASE_URL"],
)

# 分层路由表：键是任务层级，值是网关侧的模型名，以网关实际提供的为准
MODEL_BY_TIER = {
    "budget": "swe-2",          # 日常修复、补测试、小重构
    "flagship": "gpt-6-astra",  # 大型迁移、架构设计、疑难问题
}

# 降级链：主选失败时按此顺序切换，避免单点不可用拖垮整批任务
FALLBACK_TIERS = ["budget", "flagship"]


def ask_model(model: str, task: str, timeout: float = 120.0) -> str:
    resp = client.chat.completions.create(
        model=model,
        messages=[
            {"role": "system", "content": "coding agent"},
            {"role": "user", "content": task},
        ],
        temperature=0.2,
        timeout=timeout,
    )
    return resp.choices[0].message.content or ""


def run_task(task: str, tier: str) -> str:
    # 主选层级优先，失败后沿降级链切换，全部失败才向上抛错
    order = [tier] + [t for t in FALLBACK_TIERS if t != tier]
    last_error: Exception | None = None
    for t in order:
        try:
            return ask_model(MODEL_BY_TIER[t], task)
        except Exception as err:
            # 超时、限流、模型不可用走同一条降级路径，并记录日志
            last_error = err
    raise RuntimeError(f"all fallback models failed: {last_error}")
```

两个工程细节值得强调。一是降级链的方向要有讲究：旗舰档任务降级到性价比档时，产物必须过完整回归才算成功，否则降级省下的钱会加倍还回去；二是路由表放在配置里，模型名和阈值都支持热更新，断层移动时不用发版。

接入完成后，先做一次冒烟验证：同一批历史任务分别以两个档位各跑一遍，核对返回格式、工具调用行为和上下文长度限制是否一致。兼容入口抹平的是协议差异，不是模型行为差异，system 提示词和参数默认值仍要按模型分别校准——这一步偷懒，后面的回归数据就全不可信。

## 七、路由判定：把复杂度变成分数

定级不能靠感觉，至少要有一个启发式打分器。特征从任务元数据里取：改动文件数、diff 规模、是否带失败测试、是否跨模块、是否动接口契约：

```python
from dataclasses import dataclass


@dataclass
class TaskFeatures:
    files_touched: int       # 涉及文件数
    diff_lines: int          # diff 总行数
    has_failing_test: bool   # 是否带失败测试复现
    cross_module: bool       # 是否跨模块改动
    touches_contract: bool   # 是否动接口契约或数据结构


def complexity_score(t: TaskFeatures) -> int:
    # 各项权重只是起点，最终以自有回归集校准的结果为准
    score = 0
    score += min(t.files_touched, 8) * 2        # 文件数贡献，封顶防止单点拉爆
    score += min(t.diff_lines // 50, 6) * 3     # diff 规模贡献，封顶 18
    score += 6 if t.cross_module else 0         # 跨模块直接抬档
    score += 8 if t.touches_contract else 0     # 动契约视为高风险
    score += -4 if t.has_failing_test else 0    # 有失败测试，定位路径短，降档
    return max(score, 0)


def pick_tier(score: int) -> str:
    # 阈值从保守值起步，回归验证稳定后再逐步放宽
    return "budget" if score <= 16 else "flagship"
```

打分器的价值不在精确，而在可审计：每个任务为什么走了哪一档，特征和分数都在日志里，阈值调错了能立刻归因。上线初期把阈值压低，让更多任务先走旗舰；等回归数据证明性价比档的解决率达标，再一格一格放开。分数模型后续还可以加入历史维度——同目录近期任务的返工率，就是很好的修正项。

## 八、成本测算：全旗舰 vs 分层路由

测算用指数法，不涉及任何具体价格：把旗舰档单个任务的成本记为 100，SWE-2 按"四分之一成本"的相对口径记为 25，路由比例是工程假设。全部为估算口径，非基准数据：

| 策略 | 路由构成 | 成本指数（全旗舰=100，估算口径） | 定性说明 |
| --- | --- | --- | --- |
| 全量旗舰 | 100% 旗舰档 | 100 | 质量上限，账单上限 |
| 保守分层 | 50% 性价比档 + 50% 旗舰档 | 约 62.5 | 先跑通链路，风险最小 |
| 进取分层 | 70% 性价比档 + 30% 旗舰档 | 约 47.5 | 接近腰斩，依赖阈值质量 |
| 全量下沉 | 100% 性价比档 | 约 25 | 最便宜，复杂任务质量风险最高 |

两个结论值得记下。其一，分层路由的收益在"保守分层"这一档就已经很明显，不需要激进压榨路由比例；其二，省下来的预算建议拿出一部分，给旗舰档买"复杂任务配额"——高价值任务该上旗舰就上，整体交付质量反而比全量旗舰时代更稳，因为旗舰的调用预算集中到了真正需要它的地方。

## 九、成本与风险提示：基准分不等于生产表现

基准分数是选型依据，不是质量承诺。FrontierCode 1.1 Main1 上的 50.0% 是基准口径下的成绩，自有仓库的语言分布、测试基建、代码风格都和基准任务集不同；"差距几分以内"落到生产里，可能被一次错误的迁移放大成几天的回滚。所以性价比档上线前，至少完成三件事：

- 用自有回归集做 A/B：同一批历史任务分别交给性价比档和旗舰档，记录解决率、返工率和单任务成本，拿到的是自己的数字，不是别人的基准；
- 给性价比档的产物加验证门：编译通过、测试通过、lint 干净才计入成功，不达标自动沿降级链重试；
- 监控降级率与返工率：指标抬升就收紧阈值，宁可多花旗舰的钱，也不让坏 diff 流进主干。

还有一条常被忽略：模型价格与档位随时可能调整，这一篇里的所有位次关系都有保质期。路由层保持可配置，定期复核成绩与账单，才是长期省钱的姿势。

## 十、落地检查清单

1. 建自有回归集：从历史任务里抽一批带验收标准的样本，作为所有模型调整的路标。
2. 跑 A/B 基线：现役旗舰与候选性价比档各跑一遍回归集，拿到解决率与成本的实测数。
3. 阈值保守起步：先让少数低风险任务下沉，逐步放宽，每放宽一次都复核回归结果。
4. 配置降级链：每个层级都有备用模型和超时设置，失败自动切换并记录。
5. 落路由日志：任务特征、分数、选中模型、结果与成本全量落盘，可归因、可复盘。
6. 加验证门：所有 Agent 产物强制过测试与 lint，性价比档产物额外加人工抽查。
7. 设预算护栏：任务级与月度 token 预算双告警，超限熔断而不是放任重试。
8. 盯降级率：降级率异常抬升，通常意味着阈值错配或上游模型变动，先回滚再排查。
9. 定期复核路由表：新模型发布、价格调整、断层移动，都对应一次路由表更新。

## 十一、总结

这一期的主线：Cognition 的 SWE-2 在 FrontierCode 1.1 Main1 上拿到 50.0%，同时成本便宜 64%，得分与成本双超 SWE-1.7 和 Grok 4.6；它以小得多的价格匹配 GPT-5.6 Sol 与 Fable 5/5.1，并以四分之一成本把与 GPT-6 Astra 的差距缩小到几分以内。对编码 Agent 的运营者，这意味着性价比档有了新锚点：把低难度任务下沉到 SWE-2 档，把旗舰预算留给大型迁移与架构设计，配合打分路由、降级链和回归验证，账单结构就能从"全旗舰"切换到"按难度分层"。接入层面，4sapi（https://4sapi.com）这类 OpenAI 兼容入口，把多模型路由简化成一个配置问题。分层路由省下的不只是钱，还有把旗舰算力用在刀刃上的从容。欢迎在评论区聊聊。
