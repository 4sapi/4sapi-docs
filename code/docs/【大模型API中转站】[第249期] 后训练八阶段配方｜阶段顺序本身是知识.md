# 【大模型API中转站】[第249期] 后训练八阶段配方｜阶段顺序本身是知识

后训练的资料里，最不缺的是"某阶段用了什么方法"，最缺的是"阶段之间怎么排、为什么这么排"。方法可以替换，顺序错了却会让整条链返工。

一份在 GLM-4.5-Air-Base（106B-A12B）上开放、可复现的配方（Rufus-Air）把顺序讲清楚了一回：它把后训练组织成一条**八阶段串行流水线**，并公开了数据、奖励设计、基础设施、阶段顺序与分阶段结果。我在 4sapi（https://4sapi.com）上评估自建与接管的取舍时，这类完整披露比单点技巧有用得多。

## 一、八阶段顺序

顺序是：**SFT → Reasoning RL → Coding RL → Instruction-Following RL → General Agent → Coding Agent → Search Agent → RLHF**。

把它画成依赖关系更清楚：

```text
底座模型（106B 总参 / 12B 激活）
    |
    v
[1] SFT ──────────── 建立基本指令格式
    |
    v
[2] Reasoning RL ─── 建立可迁移的推理行为
    |
    v
[3] Coding RL ────── 在推理之上叠加领域技能
    |
    v
[4] Instruction-Following RL ── 收敛格式与约束遵循
    |
    v
[5] General Agent ── 通用工具使用与多步执行
    |
    v
[6] Coding Agent ─── 领域化 agent 行为
    |
    v
[7] Search Agent ─── 检索与信息整合
    |
    v
[8] RLHF ─────────── 偏好对齐收尾
```

两个特征值得先注意：**推理类 RL 排在领域类之前**，且**通用 agent 排在领域 agent 之前**。这两处顺序不是风格选择，而是依赖关系。

还有一处不那么显眼但同样有含义：**指令遵循排在能力类阶段之后、agent 类阶段之前**。它处在一个过渡位置——先让模型在推理与编码上放开，再用指令遵循把输出格式与约束收敛起来，然后才进入需要严格按工具规范行事的多步任务。如果把指令遵循放到最前面，模型会在能力尚未展开时就被格式约束收紧，后续的 RL 阶段再想把能力放开，又要与既有约束对抗。

最后是 **RLHF 收尾**。它调整的是输出的整体风格与偏好倾向。放在末尾意味着前面的能力与格式都已定型，对齐只需调整表达；放在中间则会被后续阶段重新冲淡。这条顺序把"能力建设"与"表达对齐"分成了清晰的前后两段，是整条流水线最容易理解也最容易违反的一处。

## 二、为什么推理阶段要排在领域阶段之前

强化学习的收益不是均匀分布的。当底座还没有形成可复用的推理路径时，直接做领域 RL，优化压力会集中在**领域特有的表层模式**上：模型学到"这类题该输出什么形状"，而不是"这类问题该怎么想"。

一旦先做过推理 RL，领域 RL 就有了可复用的中间行为可以调用，优化落点变成"在已有推理习惯之上补齐领域知识"。这决定了同一份领域数据能带来多少**可迁移**的增益。

一个可检验的判据是：领域 RL 之后，在**未参与训练的推理类评测**上是否也有提升。如果完全没有，通常说明推理阶段没有先立起来，领域收益被锁在了表层。

## 三、为什么通用 agent 要排在领域 agent 之前

同样的逻辑出现在 agent 类阶段。通用 agent 阶段建立的是与工具交互的**通用循环**：读结果、判断信息是否足够、决定下一步、处理失败。领域 agent 阶段建立的才是特定领域的工具集与流程知识。

如果先做领域 agent，模型可能把"某领域的工具调用顺序"整段记住，而不是学会通用的循环。后者在面对新工具时能迁移，前者不行。搜索结果里给出的顺序正是"通用在前、领域在后"，与推理那处的排法一致——**先建可迁移的通用行为，再叠加领域特化**。

## 四、各阶段的目标与验收

把八个阶段摊开对比如下。奖励设计与验收指标是按流水线逻辑做的工程化归纳，用于工程判断。

| 阶段 | 训练目标 | 数据形态 | 主要失败信号 |
| --- | --- | --- | --- |
| SFT | 建立指令格式与基本应答 | 高质量示范对 | 格式守住但推理无提升 |
| Reasoning RL | 形成可迁移推理路径 | 带验证信号的推理题 | 只在训练题型上提升 |
| Coding RL | 叠加编码技能 | 代码任务与测试反馈 | 过拟合测试样例 |
| Instruction-Following RL | 收敛格式与约束遵循 | 带约束的指令集 | 约束过强导致拒答或退化 |
| General Agent | 通用工具交互循环 | 多步任务轨迹 | 单步正确但不会恢复 |
| Coding Agent | 领域化 agent 行为 | 仓库级任务 | 依赖特定仓库惯例 |
| Search Agent | 检索与信息整合 | 检索增强任务 | 无检索也照答 |
| RLHF | 偏好对齐 | 人类或模型偏好对比 | 讨好式输出、信息量下降 |

这张表最有用的一列是最后一列。每个阶段的失败信号都指向一类**典型偏差**，而它们的共同特征是"在训练口径上看起来变好了"。所以分阶段验收必须有独立于训练信号的指标，否则偏差不会被发现。

举一个具体的读法：SFT 阶段的失败信号是"格式守住但推理无提升"。如果验收只看输出格式的合规率，这个阶段会被判为成功，但它没有为后面的推理 RL 提供任何基础。同理，Instruction-Following 阶段的"约束过强导致拒答或退化"，在约束遵循率这个指标上表现为满分，只有看拒答率才能发现。**每个阶段的验收指标必须包含一个能反映该阶段典型偏差的反向指标**，这是这张表给出的最实用的一条规则。

## 五、阶段的排序原则

从这条流水线可以抽出三条可复用的排序原则：

**第一，先可迁移，后特化。** 推理先于领域，通用 agent 先于领域 agent。任何"通用行为"的建立都应排在其领域化之前。

**第二，先能力，后约束。** 指令遵循与偏好对齐排在能力类阶段之后。反过来做，约束会压制尚未成形的能力，表现为模型变得保守、拒答增多。

**第三，对齐收尾放在最后。** 偏好对齐会调整输出的整体风格，如果放在中间，后续的能力阶段会把这种风格重新冲淡，等于白做一轮。

## 六、奖励设计的自查项

RL 类阶段的风险集中在奖励上。接一个阶段之前，我会先过一遍这几项：

- 奖励是否只看**结果**而不看**过程形态**？只看结果通常更稳，但可能奖励出投机行为。
- 是否存在**可被利用的捷径**？比如答案能被猜中、格式能被硬凑。
- 奖励信号与验收指标是否**同源**？同源会让验收失去独立性。
- 是否会**诱导特定输出形态**？比如长度偏好、列表偏好。

其中"捷径"最需要提前想。一个常见的例子是：如果奖励来自某个可被枚举的判定，模型可能学会枚举而不是推理。

另一类风险来自奖励的**尺度变化**。同一条奖励在训练早期与晚期的作用强度不同：早期信号稀疏时一个强奖励能推动行为成形，晚期行为已收敛时同一个奖励会过度放大差异。所以奖励权重最好随阶段调整，而不是八个阶段共用一套。这与上一期讨论的阈值型惩罚漂移是同一类问题——凡是写死在配置里的常数，都可能随着训练推进而失去原本的作用。

## 七、分阶段验收与回滚点

串行流水线最大的成本是返工。若在第 6 阶段发现问题，可能要退回到第 3 阶段重跑，后面三段全部重做。降低这个成本的办法是**把每个阶段的基线固定下来**：

- 每阶段结束保存 checkpoint，并记录该阶段的行为指标快照；
- 用**同一批固定评测样本**跑每个阶段，使指标可比；
- 每个阶段都定义"可接受区间"，偏离即暂停，不进入下一阶段；
- 记录每阶段的训练配置，便于精确回退到某个阶段而不是重头再来。

## 八、分阶段回归对比脚本

下面这段脚本用同一批样本对多个阶段的 checkpoint 做回归对比，把指标变化按阶段排出来，用于定位是在哪一阶段出现退化的。

```python
import os, json
from statistics import mean
import requests

BASE_URL = os.getenv("MODEL_BASE_URL", "https://4sapi.com/v1")
API_KEY = os.getenv("FOURSAPI_API_KEY", "")

STAGES = [  # 阶段名 -> 该阶段 checkpoint 对应的模型标识
    ("sft", os.getenv("MODEL_SFT", "stage-sft")),
    ("reasoning_rl", os.getenv("MODEL_REASONING", "stage-reasoning")),
    ("coding_rl", os.getenv("MODEL_CODING", "stage-coding")),
    ("if_rl", os.getenv("MODEL_IF", "stage-if")),
    ("general_agent", os.getenv("MODEL_AGENT", "stage-agent")),
    ("rlhf", os.getenv("MODEL_RLHF", "stage-rlhf")),
]

BUCKETS = ["主流程", "需并行", "参数缺失", "目标不存在"]  # 评测样本按行为类别分层


def ask(model, prompt):
    resp = requests.post(
        f"{BASE_URL}/chat/completions",
        headers={"Authorization": f"Bearer {API_KEY}"},
        json={"model": model, "temperature": 0,
              "messages": [{"role": "user", "content": prompt}]},
        timeout=60,
    )
    resp.raise_for_status()
    return resp.json()["choices"][0]["message"]["content"]


def score(model, samples):
    """samples: [{"bucket": 类别, "prompt": ..., "check": 判定函数}]"""
    per_bucket = {b: [] for b in BUCKETS}
    for s in samples:
        out = ask(model, s["prompt"])
        ok = 1.0 if s["check"](out) else 0.0
        per_bucket.setdefault(s["bucket"], []).append(ok)
    return {b: round(mean(v), 4) for b, v in per_bucket.items() if v}


if __name__ == "__main__":
    with open(os.getenv("EVAL_SET", "./eval_samples.json"), encoding="utf-8") as f:
        samples = json.load(f)

    prev = None
    for name, model in STAGES:
        cur = score(model, samples)
        line = " ".join(f"{b}={cur.get(b, '-')}" for b in BUCKETS)
        delta = ""
        if prev:
            delta = " | 变化: " + " ".join(
                f"{b}={round(cur.get(b, 0) - prev.get(b, 0), 4):+}" for b in BUCKETS)
        print(f"{name:>14}: {line}{delta}")
        prev = cur
```

重点是最后那行差值：**退化会以某个分层指标突然下降的形式出现**，而不是被总体平均掩盖。这也是把评测样本按行为类别分层的原因——主流程指标在多数退化场景下都是稳定的，问题藏在分支里。

## 九、小规模复现的资源估算

自建这条流水线的门槛主要在两处：**后训练本身的开销**与**评测的成本**。

按 106B-A12B 这类稀疏结构估算（以下是估算，用于量级判断）：权重占用取决于精度，BF16 下约 212GB，INT8 约 106GB，INT4 约 53GB；RL 阶段还要为优化器状态与激活预留额外显存，通常是权重占用的数倍。

**评测成本更容易被低估**：八个阶段、每阶段一批固定样本、按行为分层，调用次数是样本数乘以层数乘以阶段数。若样本集有数百条、分四层、走八个阶段，总调用量会到万级。这部分费用应当按"每个阶段都要重跑一遍"来预算，而不是只算一次。

还有一项不进显存也不进调用量的成本：**阶段间的等待与人工判断**。八个阶段串行，任何一阶段的结果都需要人来判断是否进入下一阶段。如果每阶段都要等一天出结论，整条流水线的日历时间会被拉长到与算力无关的尺度。缓解方式是让每阶段的判据尽量自动化——把"可接受区间"写成脚本判定，人只处理越界情况。这与验收标准必须量化的理由是同一个：不能量化的标准只能靠人看，而人看就意味着等待。

## 十、成本与风险提示

- **串行流水线的返工成本随阶段数放大**。越靠后的阶段出问题，回退代价越高。所以前置阶段的行为验收要更严，不要为了赶进度把问题带到后面。
- **后训练顺序要与底座能力匹配**。同一份配方的效果依赖底座已具备的基础能力；底座差异大时，顺序可能也需要调整。
- **奖励同源会让验收失效**。用训练信号当验收指标，等于自己给自己判卷。
- **对齐阶段的收益容易被后续阶段冲淡**。若确需在中间插入能力阶段，对齐应当在其后补做。
- **自建与接管的取舍要算全**。自建省下的是按量调用费用，付出的是显存、评测与人力；接入侧则相反。先用固定样本集把两条路的实际效果比一遍，再决定投入方向。

## 结论

这份配方的价值不在八个阶段各自用了什么方法，而在顺序：**先可迁移后特化、先能力后约束、对齐收尾放最后**。这三条原则解释了推理 RL 为什么排在领域 RL 之前、通用 agent 为什么排在领域 agent 之前。配上每条阶段的失败信号、分阶段验收与回滚点、以及按行为分层的评测样本集，整条流水线才有可能在出问题时被定位，而不是整段重来。我在 4sapi.com 上评估自建与接管的取舍时也是这个顺序：先用同一批分层样本测出两条路的差距，再决定把预算投在哪一边。
