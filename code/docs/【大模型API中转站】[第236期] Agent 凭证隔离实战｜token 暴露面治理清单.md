# 【大模型API中转站】[第236期] Agent 凭证隔离实战｜token 暴露面治理清单

一款流行的 AI 助手被披露出一个安全漏洞：本地任意应用都能拿到它的认证 token，进而完全控制这个 agent——读写文件、执行操作、调用它有权调用的一切。修补在半天内完成，平台方则直接封禁了这个未授权 agent 的部分能力。

这不是孤立的坏消息，而是一次免费的威胁建模课：**agent 拿到的授权有多大，token 泄露的后果就有多大**。我把这套威胁模型转成自己 agent 服务的凭证治理架构，这篇文章给出完整的四层设计和验收清单。

## 一、痛点：agent 让"凭证泄露"的后果升级了

传统应用的 token 泄露，损失边界通常是一组 API 的数据读写。agent 改变了这个等式：token 背后是"能代表用户执行动作的运行体"——发消息、下指令、动文件、连内部系统。

我在自查时列出的 agent 持有面：模型 API Key（能烧预算）、邮箱令牌（能代发邮件）、代码仓库凭证（能改代码）、内部服务票据（能查生产数据）。任何一项落进错误的手里，都不只是数据泄露，而是以用户身份的完整行为能力。

更隐蔽的风险来自模型本身。前沿模型的系统卡里出现过这样的演习结果：模型在拿到模拟凭证的环境里，约半数运行采取的行动若环境为真可能造成危害。演习不是定罪——它恰好证明了治理必须独立于模型的"自觉"：真实凭证根本不该出现在模型可达的任何位置。

## 二、原理速览：四层凭证治理架构

```text
第一层  注入层    Secret 由部署系统注入受控进程，不进配置文件
第二层  执行层    工具用 Secret 调外部服务，模型只见高层动作
第三层  返回层    结果脱敏后进入模型上下文
第四层  审计层    记录谁在何时用了什么凭证做了什么，不存原文
```

核心原则一句话：**模型可以知道"需要连接数据库"，但不应该看到连接串本身**。

```text
错误路径：
  提示词/环境变量 -> 模型上下文出现明文 Key -> 任何泄露即全权暴露

正确路径：
  Secret 注入受控代理进程
        -> 模型调用高层动作（如 run_query(query_id)）
        -> 代理进程持有凭证完成真实调用
        -> 脱敏结果返回模型
        -> 审计记录动作与决策，凭证原文不落日志
```

## 三、注入层：凭证从哪来、住在哪

### 分级存放

| 级别 | 示例 | 存放位置 | 模型可见性 |
| --- | --- | --- | --- |
| 高危 | 云密钥、数据库口令、支付凭证 | 密钥管理服务，运行时注入 | 不可见 |
| 中危 | 模型 API Key、SaaS 令牌 | 环境变量注入受控进程 | 不可见 |
| 低危 | 只读配置、非敏感 ID | 配置文件 | 可见 |

### 注入实现的最小示例

模型调用的不是真实 API，而是本地代理暴露的高层动作：

```python
# proxy_tool.py —— 受控代理进程，唯一持有真实 Key 的地方
import os, requests, hashlib

MODEL_KEY = os.environ["UPSTREAM_KEY"]        # 由部署系统注入，不写文件
BASE = "https://4sapi.com/v1"                  # 4sapi 中转入口

def run_completion(payload: dict) -> dict:
    """模型可见的只有这个函数签名，Key 永不出进程"""
    r = requests.post(
        f"{BASE}/chat/completions",
        headers={"Authorization": f"Bearer {MODEL_KEY}"},
        json=payload, timeout=120,
    )
    r.raise_for_status()
    data = r.json()
    return {
        "content": data["choices"][0]["message"]["content"],
        "usage": data.get("usage"),
    }

def mask(s: str, keep=6) -> str:
    return s[:keep] + "..." + hashlib.sha256(s.encode()).hexdigest()[:8]
```

agent 进程与代理进程分离，agent 崩溃或被诱导都不等于凭证泄露——它根本拿不到。

## 四、执行层：把"能力"抽象成高层动作

凭证隔离的搭档是最小授权的工具设计。反例与正例：

```text
反例：execute_sql(credentials, sql)
      模型自由构造 SQL，等于把数据库口令连同执行权一起交出

正例：run_report(report_id, params)
      模型只能触发预定义报表，参数受白名单校验
```

把危险操作包成高层动作的三个收益：参数可校验、频率可限流、动作可审计。模型在工具列表里看到的是动作名和参数说明，凭证侧的细节对它完全透明。

## 五、返回层：脱敏不是可选项

工具返回值会原样进入模型上下文，上下文会进日志、会跨会话复用、可能被导出。返回值里躺着凭证等于前功尽弃。我的脱敏清单：

```text
1. 认证头、Cookie、Set-Cookie：一律剥离
2. URL 查询串中的 token/key 参数：替换为 <redacted>
3. 错误堆栈里的连接串：模式匹配后掩码
4. 配置文件内容类返回：先过敏感字段词典
5. 无法确定是否敏感的自由文本：默认按低置信度掩码，宁可错杀
```

一个容易漏的场景：agent 调用"测试连通性"类工具时，上游服务常把请求头回显在响应里。连通性工具的返回值必须过同一套脱敏管道。

## 六、审计层：能回答"谁在何时用了什么"

审计记录的最小字段：

```text
timestamp
agent_id / task_id
tool_name（高层动作名）
credential_ref（凭证引用 ID，非原文）
risk_level
result_status
masked_evidence（脱敏证据）
```

两条纪律：审计链路本身不落 Secret 原文；日志的访问权限比业务数据更严——能看到全公司 agent 行为的日志文件，本身就是最高价值目标。另外，高风险凭证要有轮换策略：任务结束即轮换比"定期轮换"更有效，泄露窗口从"直到下次排班"缩到"单任务时长"。

## 七、生命周期：token 的出生与死亡

这次被披露的漏洞之所以严重，还有一个原因：token 长效。治理生命周期可以把同类问题的伤害上限压低：

```text
发放：按任务/会话发放短时凭证，而非长期静态 Key
使用：绑定来源约束（进程、主机、操作类型）
续期：到期前经策略层重新校验后换发
回收：任务结束即失效；异常行为触发即时吊销
```

平台生态也在往同一个方向收紧——未授权 agent 的部分能力会被平台直接封禁。接入第三方 agent 能力时，把"平台随时可能收权"当作常态来设计，自己的核心链路不依赖任何单一 agent 的存续。

## 八、验收清单：上线前必须全绿

1. 用进程检查工具确认 agent 进程的内存与环境中搜不到任何明文 Key；
2. 在提示词、系统消息、工具描述里埋一个假 Key 蜜罐，确认它从未出现在任何真实调用的头里；
3. 触发所有工具的返回，抓取完整上下文做敏感模式扫描；
4. 模拟工具超时重试，确认不会用过期凭证重放；
5. 吊销一个运行中的凭证，确认 agent 拿到的是明确的权限错误而非静默失败；
6. 从审计日志还原一次完整任务：谁、何时、用什么凭证引用、做了什么；
7. 确认日志、监控、导出文件里没有 Secret 原文。

## 九、成本与风险提示

- 代理进程是额外的运维对象，它自身的高可用与安全补丁要纳入常规运维，凭证集中点变成单点，监控要覆盖；
- 短时凭证的换发会给上游服务带来额外的认证流量，换发周期按任务时长权衡；
- 脱敏规则是滞后于业务的，新工具上线必须同步更新敏感字段词典，上线流程里加一道"脱敏评审"；
- 模型层的安全进步（更少的危险行为、更强的自我验证）值得欢迎，但不能折算成治理预算的削减——演习结果已经说明"环境为真"时后果的量级；
- 通过 4sapi 这类中转接入模型时，中转 Key 按项目与 agent 实例拆分，配合用量告警，把任何单点泄露的爆炸半径限制在一个 agent 内。

## 结论

Agent 把凭证的价值从"读一份数据"放大到"代表用户行动"，凭证治理的规格必须跟着升级：注入层隔离存放、执行层高层动作、返回层强制脱敏、审计层全程可追溯，外加短时生命周期把泄露窗口压到最小。模型可以被演习检验，凭证绝不应该出现在演习的剧本里。

这次披露的漏洞修补得很快，但它演示的攻击面会长期存在。欢迎在评论区聊聊各自 agent 的凭证都放在哪一层，以及审计链路有没有真正还原过一次完整任务。
