# 【大模型API中转站】[第219期] Harness 组件 176 组实测｜纯 bash 接口降本

Agent 的 Harness 一直被当黑盒整体评测，这次有人把它拆成了零件：固定执行循环，只动三个组件，跑满 176 组匹配设置，结论里有好几条反直觉。

实验设计值得先说清楚：4 个模型，在 SWE-Bench Verified 和 Terminal-Bench 2.1 两个基准上，围绕规划、动作空间、上下文管理三个组件做了 5 种上下文管理策略、4 种上下文窗口预算和组件消融，合计 176 组匹配设置。我把这批结论对着自己的 Agent 网关逐条核对过，这篇讲哪些直接能抄、哪些要按自家任务改。模型接入统一走 4sapi（https://4sapi.com），Harness 配置与模型选择分开管理。

## 一、开篇痛点

自建 Agent 的团队几乎都纠结过同样几个问题：

- 上下文塞不下怎么办？摘要、省略、压缩，选哪个？
- 要不要给模型配规划组件？配了好像没什么用，不配又心里发虚；
- 工具列表做多大？十几个专用工具还是一个万能 bash？
- 换了模型，上一套 Harness 配置还适用吗？

这些问题的公共答案是"看情况"，但没人说得清看哪些情况。这批 176 组设置的价值就是把"情况"量化成了可查的对照表。

## 二、原理速览：三组件怎么拆

实验把 Harness 拆成三个可独立替换的组件：

```text
执行循环（固定不动）
    |
    +-- 组件一: 规划     是否生成显式计划、何时更新
    |
    +-- 组件二: 动作空间 预定义工具集 vs 纯 bash 接口
    |
    +-- 组件三: 上下文管理 5 种策略 x 4 种窗口预算
```

轨迹层面的归因也很有意思：上下文管理改变的是轨迹能跑多长而不改变行为模式；规划改变的是轨迹在哪里停下来；动作空间改变的是写代码的粒度。

## 三、发现一：上下文管理是预算紧缩时的救命件

5 种上下文管理策略里，收益最大的是**规则式省略先于 LLM 摘要**的分层策略；而"把被省略的内容做成可恢复机制"这步，模型几乎从不使用，纯粹增加系统复杂度，且不带来准确率收益。

| 窗口预算 | 无上下文管理 | 有分层管理 |
| --- | --- | --- |
| 宽裕 | 差异不大 | 差异不大 |
| 紧张 | 溢出失败率陡增 | 主要收益：防溢出 |

上下文管理的主要价值不是"让模型更聪明"，而是**防止上下文溢出导致的硬失败**。预算宽裕时它是奢侈品，预算紧张时它是必需品。

## 四、发现二：规划组件的身份随模型强度切换

同一个规划组件，对不同强度的模型扮演不同角色：

```text
弱模型: 规划 = 准确率脚手架（显著提分）
强模型: 规划 = 成本节省器   (准确率几乎不变，路径更短)
```

这解释了我之前的困惑："为什么加了规划没感觉变好"——因为主力模型够强，规划只在省 Token 上起作用。反过来，小模型做批量子任务时，规划组件就是准确率的垫脚石。

## 五、发现三：bash 能力决定动作空间的选择

动作空间的结论最反直觉也最实用：

| 模型 bash 熟练度 | 推荐动作空间 | 理由 |
| --- | --- | --- |
| 弱 | 预定义工具集 | 预定义工具显著提升表现 |
| 强 | 纯 bash 接口 | 成本大幅下降，命令行为主的任务尤其明显 |

强模型 + 纯 bash 的组合在我的网关里实测：Token 消耗明显下降，因为不再为每次调用携带庞大的工具描述与结构化参数。代价是审计粒度变粗——bash 命令的语义比专用工具模糊，权限与审计层要补强。

## 六、接入教程：按模型分档配置 Harness

我把结论落成了网关里的分档路由：模型接入走 4sapi（https://4sapi.com），Harness 配置按模型档位和任务类型自动选择：

```python
from openai import OpenAI

client = OpenAI(
    api_key="4sapi-key",
    base_url="https://4sapi.com/v1",
)

HARNESS_PROFILES = {
    # 弱模型 + 批量子任务: 规划 + 预定义工具 + 分层上下文管理
    "worker": {
        "model": "small-model",
        "planning": True,
        "tools": ["read_file", "run_tests", "apply_patch"],
        "ctx_strategy": "rule_elision_then_summary",
    },
    # 强模型 + 命令行任务: 无规划 + 纯 bash + 紧预算上下文管理
    "senior": {
        "model": "claude-sonnet-4-5",
        "planning": False,
        "tools": ["bash"],
        "ctx_strategy": "rule_elision_then_summary",
    },
}

def run_task(profile: str, task: str) -> str:
    cfg = HARNESS_PROFILES[profile]
    system = ("先输出简要计划再执行。" if cfg["planning"]
              else "直接执行，命令要可审计。")
    resp = client.chat.completions.create(
        model=cfg["model"],
        messages=[
            {"role": "system", "content": system},
            {"role": "user", "content": task},
        ],
        tools=build_tools(cfg["tools"]),
        max_tokens=8192,
    )
    return resp.choices[0].message.content or ""
```

注意 `ctx_strategy` 的实现顺序：先用规则（截断旧工具输出、折叠重复块）省掉大头，剩余部分再交给 LLM 摘要；不要做"可恢复省略"，实测没人用。

## 七、成本核算：三组件各省多少

以我网关近一个月的量做粗算（强模型主力任务）：

| 优化项 | 手段 | 相对节省 |
| --- | --- | --- |
| 动作空间 | 预定义工具集 → 纯 bash | 输入 Token 明显下降 |
| 规划 | 关闭显式规划 | 每任务少一段计划文本 |
| 上下文管理 | 规则式省略前置 | 防溢出重跑，重跑率下降 |

三项叠加的节省方向不同：动作空间和规划省的是单次调用的 Token，上下文管理省的是"失败重跑"的整单成本。后者单价更高，也更容易被忽视。

## 八、风险提示

- **bash-only 的审计代价**：语义模糊的命令让权限判断和事后审计变难，生产环境要配命令白名单；
- **结论的适用边界**：176 组设置覆盖的是编码类任务，通用办公类任务先小流量验证；
- **规划不要一刀切关掉**：混用模型时，弱模型档位仍要保留规划；
- **策略叠加验证**：三组件的收益不是线性叠加的，改完要跑整体回归；
- **协议兼容**：纯 bash 接口在部分中转通道上的工具调用协议有差异，接入前先过冒烟。

## 九、检查清单：Harness 配置上线前

1. 按模型档位分配置规划开关与动作空间；
2. 上下文管理实现"规则省略 → LLM 摘要"分层，不做可恢复机制；
3. 记录每任务的 Token 消耗与轨迹长度，验证归因；
4. bash-only 档位补命令白名单与审计增强；
5. 每次换模型重跑组件消融，别沿用旧配置；
6. 看板分档展示：准确率、Token 成本、溢出重跑率。

## 总结

把 Harness 当整体不如把它当三个零件：上下文管理是预算紧缩时的防溢出必需品（分层策略最优，可恢复机制是死代码）；规划组件对弱模型是准确率、对强模型是成本；动作空间则取决于模型的 bash 熟练度——强的用纯 bash 接口反而大幅降本。我的配置原则是"模型分档、组件分档、按 176 组结论初始化、按自家任务消融校准"，接入层统一走 4sapi（https://4sapi.com）保持协议干净。欢迎在评论区聊聊大家的 Harness 配置和省 Token 妙招。
