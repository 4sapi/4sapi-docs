# 【大模型API中转站】[第199期] MCP 只读插件外包规划｜省下周额度还不碰生产

规划是长上下文、多轮推理的重活，写代码是确定性执行，两者的成本结构完全不同，却常常抢同一份周额度。我最近把这套流程固化了下来：让 Codex 把自建服务器封装成一个 MCP Server，作为插件交给 ChatGPT 网页版的 GPT-6 Pro 调用，由它读取真实生产数据与 GitHub PR 记录来做分析与规划；Codex 只在最后执行落地。这一期把请求流、三条硬约束的落地方式和一个只读 MCP Server 的 Python 骨架写清楚，配额核算走 4sapi（https://4sapi.com）这类正规计费口径。

## 一、开篇痛点：贵额度被规划吃掉

每个用 Codex 干活的团队大概都遇到过同一件事：一周的 Pro 会员额度，往往不是消耗在敲代码上，而是消耗在"先想清楚该怎么做"上。

进入一个陌生仓库，先让它读目录、读配置、读历史提交、读 PR 讨论，再让它产出改造方案、拆分步骤、列出风险点。这一连串动作里，真正改动文件的只占很小一段，其余全是长上下文读取与多轮推理。读得越多，上下文越长，单轮越贵；思考得越久，轮数越多，额度掉得越快。等到方案想明白，可用的额度已经不多，执行阶段反而开始束手束脚。

更麻烦的是，规划和执行对模型能力的要求并不一样：

- 规划需要长时间的记忆、跨文件关联、对历史决策的追溯，以及反复自我修正；
- 执行需要的是确定性、可验证、可回滚，对模型"聪明程度"的边际需求其实低得多。

把这件重活放在最贵的额度预算里跑，等于用跑车的油去发电。

## 二、为什么要拆：规划与执行是两种负载

先把两类负载拆开看，理由就非常直白。

| 维度 | 规划类负载 | 执行类负载 |
| --- | --- | --- |
| 典型动作 | 读生产指标、读 PR 记录、拆步骤、列风险 | 改文件、跑测试、提 PR、修回归 |
| 上下文规模 | 极长，且需要反复回读 | 中等，局部为主 |
| 轮数 | 多轮，来回澄清 | 少轮，目标明确 |
| 失败代价 | 方案跑偏，返工重来 | 编译失败，立刻发现 |
| 对额度预算的敏感度 | 高，吃掉大头 | 中，可控 |

拆开之后，两组收益同时出现。

第一组是成本侧：规划不消耗编码额度预算，长期挂在最贵的那份周额度上的固定开销被移走，单位产出的综合成本明显下降。第二组是质量侧：规划用的模型可以挂着最长的上下文、最宽松的推理预算去想事情，不用因为"心疼额度"而砍掉必要的读取步骤。

关键在于，什么算"贵"取决于我的账单结构，而不是某个通用结论。哪一部分占比最高、把它移到哪里最划算，得按我自己的口径实测再定，不要照搬别人的划分。

## 三、MCP 作为桥：让外部模型读到真实数据

规划要成立，前提是外部模型能读到真实数据。让它凭描述猜生产状态，产出的方案只能算文案，不能算规划。

MCP Server 正好是这个位置上的最小接口面：Codex 把自建服务器的能力封装成一组工具，以插件形式暴露出去，ChatGPT 网页版的 GPT-6 Pro 侧按需调用，读到的就是生产环境的真实指标与仓库里的真实 PR 记录，而不是我转述的二手描述。

这里有一个容易走偏的地方：接口面越大，看起来越"方便"，风险也越大。一个能读生产、又能写生产的 MCP Server，等于把生产写通道挂到了外部模型的调用栈上。所以接口面必须按"只读"来收，而不是按"顺手"来收。

```text
ChatGPT 网页版（GPT-6 Pro）
        |
        |  MCP 工具调用（只读工具名 + 参数）
        v
自建 MCP Server（插件）
        |
        |  1. OAuth 令牌校验：签名 / 受众 / 作用域 / 有效期
        |  2. 租户绑定：令牌里的租户与请求对象必须一致
        |  3. 工具白名单：不在清单内的工具直接拒绝
        |  4. 字段级脱敏：按对象裁剪字段、屏蔽敏感值
        v
内部只读数据源（生产指标、GitHub PR 记录）
        |
        v
脱敏结果 + 审计编号回传模型
        |
        v
模型产出规划：步骤、依赖、风险、验收点
        |
        v
Codex 在编码额度内执行（唯一能改文件与提交 PR 的一侧）
```

这张图里最重要的一条边，是最后那一段箭头：外部模型只负责想，改文件与提交 PR 始终留在 Codex 侧。规划与执行之间隔着一条只读边界，这条边界就是整个方案的护栏。

## 四、三条硬约束：只读、最小权限、OAuth 鉴权

整套工作流立在三条硬约束上，缺任何一条都不该上线。

- 只读：MCP Server 不提供任何写工具，所有工具都是查询语义，写操作在协议层根本不存在；
- 最小权限：只暴露规划真正需要的对象与字段，能读汇总就不读明细，能读字段就不读整行；
- OAuth 鉴权：每一次调用都带可校验的令牌，令牌绑定租户，具有明确的生命周期，并且全程留下审计记录。

三条约束不是并列的三个开关，而是一条链：OAuth 决定"是谁在调用"，最小权限决定"能读到什么"，只读决定"最多能造成什么后果"。前两层收窄，最后一层兜底。

## 五、硬约束之一：只读如何真正落地

只读最常见的错误做法是靠提示词约束——在给模型的说明里写一句"请不要修改数据"。这不是约束，这是建议。

真正落地的只读需要三层同时成立。

### 工具清单只有查询语义

注册给外部模型的工具名里，不出现 create、update、delete、close、merge 这类动词。规划需要的通常是"读某段时间的指标""读某个 PR 的讨论与变更文件""读某条流水线的历史结果"，把这些整理成固定的查询工具，写操作就没有入口可走。

### 数据源侧用只读账号

MCP Server 连接内部数据源时使用的凭证，本身就只有读取权限。这一层即使被绕过，写通道也打不开。凡是需要更高权限才能读的对象，宁可先不提供，也不要临时提权。

### 传输与协议只暴露查询

如果底层是 HTTP 接口，只放行 GET 语义的方法；如果是 SQL 类数据源，只允许参数化查询，禁止拼接语句，也禁止调用任何带副作用的过程。

三层叠起来，只读就从"约定"变成了"能力边界"。此时哪怕模型被外部内容诱导，能做的也只是多读几次。

## 六、硬约束之二：最小权限与字段级脱敏

只读解决的是"能不能写"，最小权限解决的是"能读到多少"。两者不是一回事：一个能读全部生产明细的只读接口，泄露风险并不低。

最小权限按三档收敛。

| 收敛层次 | 做法 | 例子 |
| --- | --- | --- |
| 对象层 | 只注册规划必需的对象 | 只要指标与 PR 记录，不要用户表与订单表 |
| 行层 | 按租户、按时间段、按项目过滤 | 令牌租户与请求对象不一致即拒绝 |
| 字段层 | 白名单字段 + 类型转换 | 只回传状态、耗时、结论，不回传原始负载 |

字段级脱敏是这里最容易被省略、也最值得做细的一步。做法很朴素：为每个对象维护一份字段白名单，脱敏函数只按白名单取值，白名单之外的字段一律不进返回值。这样即使上游对象新增了敏感字段，返回结果也不会自动变大。

几个具体口径：

- 邮箱、手机号、内部人员姓名一律不进返回值，需要区分责任人时改用不可逆的短标识；
- 密钥、令牌、连接串、Cookie 这类值不设白名单，永远不返回；
- 原始日志、堆栈、请求体默认不返回，需要时只回传聚合后的计数与时序；
- PR 记录只回传标题、状态、变更文件路径与讨论摘要，不回传原始 diff 全文。

脱敏写在返回路径上，而不是写在调用方。调用方可能是任何一个模型，指望它自觉不做记录是不现实的。

## 七、硬约束之三：OAuth 鉴权、租户绑定与令牌生命周期

鉴权这一层用 OAuth 是合适的选择：令牌可校验、可过期、可撤销、可审计，比一对长期共享的静态密钥好管得多。

落地时关注四件事。

### 令牌必须被真校验

每次工具调用都校验签名、受众、作用域与有效期，任何一项不通过直接返回拒绝。解析令牌只用于读取声明，不做任何"信任客户端自报身份"的分支。

### 租户绑定写进校验

令牌里的租户标识与请求要访问的对象必须一致。这一步防的是横向越权：同一套 MCP Server 服务多个租户时，一个租户的令牌不能读到另一个租户的数据。

### 生命周期明确

访问令牌短有效期，刷新令牌单独管控并绑定到具体设备；令牌撤销后立即失效，不依赖缓存过期。规划类调用通常是一段密集读取，短有效期不会带来明显打扰。

### 审计与令牌同源

审计记录里记下令牌标识与租户，但不记令牌原文。出了问题要能回答"哪个租户、通过哪个令牌、在什么时候读了什么"，而不是把令牌抄进日志。

## 八、审计日志：读操作也要留痕

读操作不改变状态，但不代表不需要审计。规划类调用的价值恰恰在于它读了什么，这份记录同时是安全证据和成本凭证。

每条审计记录至少包含：

```text
task_id
tenant_id
token_id（不含令牌原文）
timestamp
tool_name
sanitized_arguments
object_scope（对象 + 行过滤条件 + 字段白名单版本）
result_status
row_count
latency_ms
```

三个设计口径：

1. 记录的是"读了哪个范围"，而不是"读到了什么内容"，避免审计库变成第二份数据副本；
2. `sanitized_arguments` 保存前先过一遍脱敏，参数里可能混入标识类信息；
3. 审计写入与工具返回解耦，审计失败不应该静默放过，至少要落在本地并告警。

有了这份日志，额度核算和安全追溯可以共用一套数据：某个租户这周读了哪些对象、读了多少次、返回了多少行，一目了然。

## 九、Python 骨架：白名单、脱敏、鉴权、审计

下面这个骨架把四条逻辑收在一个只读入口里，结构上刻意保持可以直接替换数据源。模型调用侧仍走 OpenAI 兼容接口，base_url 指到 4sapi 的兼容端点，密钥只从环境变量读取。

```python
import os
import time
import uuid
from dataclasses import dataclass, field

import requests  # OAuth 令牌内省

# 密钥只从环境变量读取，任何情况下不写进代码与仓库
API_BASE_URL = os.environ.get("API_BASE_URL", "https://4sapi.com/v1")
API_KEY = os.environ.get("API_KEY")
OAUTH_INTROSPECT_URL = os.environ.get("OAUTH_INTROSPECT_URL")
AUDIT_SINK = os.environ.get("AUDIT_SINK")

if not API_KEY:
    raise RuntimeError("缺少 API_KEY，请通过环境变量注入，不要硬编码")


# 一、工具白名单：清单之外一律拒绝，不存在任何写工具
READONLY_TOOL_ALLOWLIST = {
    "read_prod_metrics": {
        "scopes": ["metrics:read"],
        "fields": {"metric", "window", "value", "status", "updated_at"},
        "row_filter": lambda tenant, args: {"tenant": tenant, "window": args.get("window", "7d")},
    },
    "read_github_pr_records": {
        "scopes": ["repo:read"],
        "fields": {"number", "title", "state", "files", "review_summary", "updated_at"},
        "row_filter": lambda tenant, args: {"tenant": tenant, "repo": args.get("repo", "")},
    },
    "read_ci_history": {
        "scopes": ["ci:read"],
        "fields": {"pipeline", "commit", "result", "duration_sec", "updated_at"},
        "row_filter": lambda tenant, args: {"tenant": tenant, "pipeline": args.get("pipeline", "")},
    },
}


def mask_record(record: dict, allowed_fields: set) -> dict:
    """字段级脱敏：白名单之外一律不返回，上游新增字段不会自动泄露。"""
    masked = {k: record.get(k) for k in allowed_fields}
    if "files" in masked and isinstance(masked["files"], list):
        masked["files"] = [str(p) for p in masked["files"]][:50]  # 只回传路径，不回传 diff
    return masked


def verify_token(auth_header: str, required_scopes: list):
    """校验 OAuth 令牌：签名 / 受众 / 作用域 / 有效期，并取出租户绑定。"""
    if not auth_header or not auth_header.lower().startswith("bearer "):
        return None
    token = auth_header.split(" ", 1)[1].strip()
    resp = requests.post(
        OAUTH_INTROSPECT_URL,
        data={"token": token},
        timeout=5,
    )
    if resp.status_code != 200:
        return None
    info = resp.json()
    if not info.get("active"):
        return None
    if info.get("aud") != "readonly-mcp":
        return None
    if not set(required_scopes).issubset(set(info.get("scope", "").split())):
        return None
    return {"tenant_id": info.get("tenant_id"), "token_id": info.get("jti")}


def audit(event: dict) -> None:
    """审计写入与业务返回解耦，失败要能被发现，而不是静默吞掉。"""
    event["event_id"] = str(uuid.uuid4())
    try:
        requests.post(AUDIT_SINK, json=event, timeout=3)
    except Exception:
        print("[audit-fallback]", event)


@dataclass
class ReadOnlyMcpServer:
    fetch: object  # 内部只读数据源客户端，凭证本身只有读权限
    _seen: dict = field(default_factory=dict)

    def call_tool(self, name: str, args: dict, auth_header: str) -> dict:
        started = time.time()
        task_id = str(uuid.uuid4())
        spec = READONLY_TOOL_ALLOWLIST.get(name)
        if spec is None:
            audit({"task_id": task_id, "tool_name": name, "result_status": "tool_not_allowed"})
            return {"error": "tool_not_allowed", "task_id": task_id}

        token = verify_token(auth_header, spec["scopes"])
        if token is None:
            audit({"task_id": task_id, "tool_name": name, "result_status": "unauthorized"})
            return {"error": "unauthorized", "task_id": task_id}

        tenant = token["tenant_id"]
        if args.get("tenant") not in (None, tenant):
            audit({"task_id": task_id, "tenant_id": tenant, "tool_name": name,
                   "result_status": "tenant_mismatch"})
            return {"error": "tenant_mismatch", "task_id": task_id}

        rows = self.fetch(name, spec["row_filter"](tenant, args))
        masked = [mask_record(r, spec["fields"]) for r in rows]

        audit({
            "task_id": task_id,
            "tenant_id": tenant,
            "token_id": token["token_id"],
            "tool_name": name,
            "sanitized_arguments": {k: v for k, v in args.items() if k != "tenant"},
            "object_scope": sorted(spec["fields"]),
            "result_status": "ok",
            "row_count": len(masked),
            "latency_ms": int((time.time() - started) * 1000),
        })
        return {"data": masked, "task_id": task_id, "readonly": True}
```

四个细节值得单独拎出来。

1. 白名单是唯一入口：`READONLY_TOOL_ALLOWLIST` 之外的名字在第一步就被拒掉，新增工具必须改代码、走评审，不能靠配置热加。
2. 脱敏发生在返回路径上：`mask_record` 只按白名单取值，原始对象再胖也不会撑大返回值。
3. 租户校验在读取之前：令牌租户与参数租户不一致时直接返回，连数据源都不碰。
4. 审计失败走兜底打印：宁可日志难看，也不静默丢事件。

## 十、接入准备：环境与 Key 管理

把骨架跑起来之前，先把准备动作做干净。

1. **凭证注入**：`API_KEY`、`OAUTH_INTROSPECT_URL`、`AUDIT_SINK` 全部通过环境变量或密钥管理服务注入，仓库里不出现任何真实值，`.env` 一律进忽略清单。
2. **只读数据源账号**：为 MCP Server 单独建一个只有读权限的账号，不复用业务账号，不复用管理账号。
3. **网络位置**：MCP Server 部署在能访问内部数据源、但不具备生产写通道的位置，出网白名单只放必需的几个地址。
4. **工具清单评审**：把工具名、参数、返回字段、脱敏规则列成表，逐条确认"规划真的需要它吗"，能砍的先砍。
5. **熔断与限额**：给单租户设好请求频率上限与返回行数上限，规划阶段读得密，没有上限容易把数据源压出问题。
6. **上线前的一次空跑**：用测试租户的令牌跑一遍全部工具，确认返回值里没有白名单之外的字段。

第 4 步最容易被跳过，也最值得认真做。工具清单每多一个，攻击面和审计成本就多一份，而规划真正需要的往往只有三五个查询。

## 十一、额度与成本核算方法

省额度这件事，凭感觉说不清楚，得有一套口径固定、每周回归的核算方法。我按四步走。

先用固定样本定义范围。拿三到五个真实的规划任务，覆盖不同类型的读取：跨仓库的改动评估、单个 PR 的影响面分析、指标异常的原因排查、新需求的方案拆分。同一批任务在"全部交给 Codex"和"规划外包、执行留在 Codex"两种模式下各跑一遍。

再把消耗分档记录。至少要能区分：规划轮的输入与输出规模、规划轮数、执行轮的规模与轮数、返工次数。

接着把成本折算到单位产出。按任务算，不按次算：一个规划任务从提出到合并，总共消耗了多少额度预算，其中规划占多少、执行占多少。这样"外包规划是否划算"才有可比的数字。

最后做周期回归。每周固定跑一次同一批样本，观察比例变化，同时盯住质量指标——规划退货率、执行返工率、方案被推翻的次数。

| 核算项 | 口径定义 | 采集方式 | 判定标准 |
| --- | --- | --- | --- |
| 规划轮额度占比 | 规划轮消耗 / 单任务总消耗 | 按任务 ID 归集调用记录 | 占比高，外包收益空间大 |
| 单位产出成本 | 单任务总消耗 / 已合并任务数 | 任务台账 + 计费明细 | 连续两周下降才算有效 |
| 规划退货率 | 需要重新规划的规划数 / 总规划数 | 任务标签人工标注 | 上升说明外包侧上下文不足 |
| 执行返工率 | 返工执行轮数 / 总执行轮数 | 提交记录 + 回滚记录 | 上升说明规划质量下降 |
| 读取命中率 | 规划一次通过所需读取次数占比 | 审计日志 row_count 统计 | 过低说明工具粒度不对 |

判断标准要提前写死，不能等看到数字再定。具体比例阈值按我自己的口径实测再定：账单结构、任务类型、团队规模不一样，别人跑出来的数字搬过来只会误判。

## 十二、上线验收清单

这套东西上线前，我会把下面每一条都跑一遍，任何一条不通过就不放行。

1. 工具清单核对：外部模型可见的工具全部为查询语义，没有任何写动词，也没有隐藏的管理接口。
2. 越权测试：用一个租户的令牌请求另一个租户的对象，确认返回拒绝，且拒绝发生在读数据之前。
3. 令牌测试：缺失、过期、受众不符、作用域不足四种情况各测一次，确认全部被拦。
4. 脱敏测试：构造一条包含敏感字段的原始记录，确认返回值里只有白名单字段。
5. 只读验证：检查数据源账号权限，确认其本身不具备写入能力。
6. 审计验证：抽查若干次调用，确认能从审计记录还原租户、令牌标识、工具、参数与返回行数，且记录里没有令牌原文与敏感值。
7. 限额验证：触发频率上限与行数上限，确认熔断生效且模型收到明确错误。
8. 失败路径验证：断开数据源、断开鉴权服务，确认返回明确错误而不是放行。
9. 额度回归：按上一节的口径跑一轮固定样本，确认单位产出成本确实变化，且质量指标没有恶化。
10. 通道确认：确认整条链路只走正规接口与正规计费渠道，不存在任何绕过官方限制的配置。

第 9 条最容易被当成"跑一次就够了"。成本口径会随着任务结构变化而漂移，不回归就等于没有口径。

## 十三、风险提示与边界

这套方案的收益来自"把规划搬出编码额度预算"，但边界必须讲清楚。

- **数据面风险**：只读不等于无风险。规划类读取往往是聚合视角，多个字段拼起来可能还原出敏感信息，字段白名单要按组合效果复核，而不是只逐字段看。
- **间接注入**：PR 标题、讨论内容、指标维度的文本里可能夹带诱导性内容。它们只能当数据看，工具权限必须在模型之外兜住，不能靠一句系统提示词。
- **工具粒度风险**：工具太少，模型读不到关键信息，规划质量下降、退货率上升；工具太多，审计与权限成本失控。粒度要跟着退货率调，而不是跟着感觉调。
- **成本口径风险**：把规划移走不等于总成本下降，如果外部侧读取轮数失控，总体可能更贵。核算必须按单位产出算，不按单次调用算。
- **权限漂移**：临时提权、临时新增工具、临时放宽字段，是这套体系最常见的失效方式。任何一次放宽都要留记录、设期限，到期自动回收。
- **合规边界**：不碰生产写通道，不做绕过官方限制的配置，额度与计费走正规渠道。规划外包节省的是**预算结构**，不是**应付的费用**。

还有一条实践层面的提醒：不要因为省额度而砍掉必要的数据读取。规划质量一旦掉下来，返工消耗的执行额度会迅速把省下来的部分吃掉。

## 十四、总结

这一期把"规划外包、执行留在本地"这套工作流拆开写完了。核心判断只有一句：规划是长上下文、多轮推理的重活，执行是确定性落地，把前者交给不消耗编码额度预算的模型承担，最贵的那份额度才能集中花在真正改代码上。MCP Server 是这座桥的最小接口面——Codex 把自建服务器封装成插件，ChatGPT 网页版的 GPT-6 Pro 通过它读取真实的生产指标与 GitHub PR 记录来做分析与规划。

三条硬约束是整个方案的骨架：只读靠工具白名单、只读数据源账号、只放行查询语义三层落地；最小权限按对象、行、字段三档收敛，脱敏写在返回路径上；OAuth 鉴权把租户绑定、作用域、令牌生命周期和审计串成一条链。配上骨架代码、一套按单位产出核算的额度方法，以及十条上线验收清单，这套东西才算能长期跑。配额核算与计费走 4sapi（https://4sapi.com）这种正规口径，不碰生产写通道，不做绕过官方限制的配置，额度这件事才有可持续的答案。规划与执行怎么切分、字段白名单该收多紧，欢迎在评论区聊聊。
