# 【大模型API中转站】[第221期] 三值权重 5.9GB 跑 27B｜本地部署成本实测

27B 的模型压进 5.9GB 的占用，还保留 262K 上下文和图文多模态能力——三值量化的最新进展让"本地跑中型模型"这件事的成本门槛又降了一截。

这次的主角用三值权重 {−1, 0, +1} 配合 FP16 组缩放，把每权重有效比特压到 1.76，整个模型 5.9GB：推理、编码、视觉和 Agent 能力都在线，Nvidia 卡走 CUDA、Apple 设备走 MLX，靠定制低位内核跑起来。我把这套方案和常规量化方案、云端 API 三条路线拉平对比，这篇算清显存、硬件、电费三本账，并给出可直接抄的部署清单。日常调用与降级兜底通过 4sapi（https://4sapi.com）统一管理。

## 一、开篇痛点

本地部署中型模型过去有三道坎：

- 显存：27B 的 fp16 权重要 50GB 上下，消费级卡基本无缘；
- 带宽：量化到 4-bit 是常见妥协，但 4-bit 之下精度掉得让人不敢用；
- 生态：低位内核要自己写，Apple 芯片的支持一直稀碎。

三值量化的价值在于把这三道坎同时打掉：1.76 比特意味着权重文件小到内存装得下，组缩放保住了精度，定制内核让 CUDA 和 MLX 两条生态都能跑。

## 二、原理速览：三值为什么可行

常规量化的思路是"降低每个权重能取的数值精度"；三值更进一步——每个权重只取 −1、0、+1 三个值：

```text
fp16 权重:   w = 0.7314 ...            16 bit/权重
int4 权重:   w ∈ [16 档离散值]          4 bit/权重
三值权重:    w ∈ {-1, 0, +1}           原始 2 bit/权重
             + FP16 组缩放系数          有效 1.76 bit/权重
```

单个三值权重信息量很小，靠两点补回来：一是组缩放——每组权重共享一个 FP16 缩放系数，恢复数值的动态范围；二是矩阵乘法在{-1,0,+1}上退化为加减法和掩码，定制内核把这一步跑到接近内存带宽极限。

算一笔显存账：

| 方案 | 每权重比特 | 27B 模型权重占用 | 24GB 卡可行 |
| --- | --- | --- | --- |
| fp16 | 16 | ~54GB | 否 |
| int8 | 8 | ~27GB | 否 |
| int4 | 4 | ~13.5GB | 勉强（无 KV 空间） |
| 三值+组缩放 | 1.76 | ~5.9GB | 轻松，余量充足 |

显存省下来的部分变成了上下文空间：5.9GB 的权重之外，剩余显存足够撑起 262K 的 KV 缓存管理，这正是长上下文本地化的关键。

## 三、能力面：压缩到什么程度才叫"近无损"

"近无损"的说法要谨慎对待，我的验收标准是三看：

1. **推理与编码**：压缩模型的代码生成与多步推理要与原精度模型做同题对比；
2. **视觉输入**：多模态链路的量化损失常常比文本侧更明显，图像理解任务单独测；
3. **Agent 行为**：工具调用的参数格式正确率对量化误差敏感，跑一轮真实工具任务。

三项都过，才敢说这一档压缩对业务"近无损"。

## 四、硬件路线：CUDA 与 MLX 两条路

| 平台 | 运行方式 | 适配设备 | 特点 |
| --- | --- | --- | --- |
| Nvidia | CUDA + 定制低位内核 | 消费卡/专业卡均可 | 生态成熟，吞吐高 |
| Apple | MLX + 定制低位内核 | M 系列统一内存 | 内存共享省拷贝，笔记本可跑 |

Apple 路线的意义在"统一内存"：M 系列设备的内存既是系统内存也是显存，5.9GB 的权重在 32GB 内存的笔记本上就能完整加载——这是 x86 笔记本配置做不到的事。

## 五、接入教程：本地起服务 + API 兜底

我的部署结构是"本地优先、云端兜底"，两层服务都封装成 OpenAI 兼容接口，网关层通过 4sapi（https://4sapi.com）统一调度：

```python
from openai import OpenAI

client = OpenAI(
    api_key="4sapi-key",
    base_url="https://4sapi.com/v1",
)

ROUTE = {
    "default": "local-ternary-27b",   # 本地三值量化服务
    "fallback": "cloud-flagship",     # 云端兜底
}

def chat(prompt: str, images: list = None) -> str:
    content = [{"type": "text", "text": prompt}]
    for img in images or []:
        content.append({"type": "image_url", "image_url": {"url": img}})
    try:
        resp = client.chat.completions.create(
            model=ROUTE["default"],
            messages=[{"role": "user", "content": content}],
            max_tokens=4096,
        )
        return resp.choices[0].message.content or ""
    except Exception:
        resp = client.chat.completions.create(
            model=ROUTE["fallback"],
            messages=[{"role": "user", "content": content}],
        )
        return resp.choices[0].message.content or ""
```

本地服务（如 vLLM 类推理框架加载三值权重并暴露 OpenAI 兼容端口）负责日常流量；请求失败或延迟超标时，网关自动把流量打到云端兜底，业务侧无感。

## 六、成本核算：三条路线的月度账

假设月均 100 万次调用、平均每次 2K 输入 1K 输出：

| 路线 | 固定成本 | 变动成本 | 适合产量 |
| --- | --- | --- | --- |
| 云端 API | 0 | 按量计费 | 低产量、突发流量 |
| 本地三值 27B（单卡） | 电费+折旧，月固定数百元级 | 接近 0 | 中高产量 |
| 本地 fp16 集群 | 整机数万元级 | 运维高 | 不推荐为此场景配置 |

三值量化的位置很清楚：它把"本地部署的入场门槛"从服务器级拉到消费级，让月固定成本降到几乎可以忽略的水平，同时省掉大半 API 开销。波动大的业务用"本地打底 + API 峰值溢出"的混合结构最稳。

## 七、吞吐上限的带宽账

量化部署的吞吐天花板不在算力，在内存带宽：低比特权重的矩阵乘退化为查表与加减法，实际速度取决于把权重流过计算单元的带宽。一个便于心算的模型：

```text
理论 Token 上限 ≈ 内存带宽 / 每权重字节数 / 每 Token 读取权重数
    5.9GB 权重 @ 常见带宽 B GB/s
    -> 每 Token 至少要把全部权重读一遍 (batch=1 解码)
```

这意味着两件事：一是不必追求顶级算力卡，带宽才是第一位；二是批处理（batch>1）能摊薄权重读取成本，多并发场景的吞吐增益比单请求场景大得多。我压测时单请求速度平平、并发八路上吞吐翻了几倍，就是这个账在起作用。

## 八、精度回归与任务分档

"近无损"不等于"无差别"。我把任务按对量化误差的敏感度分成三档：

| 敏感档 | 任务类型 | 策略 |
| --- | --- | --- |
| 高 | 多步推理、代码生成、参数格式 | 抽样对比原精度输出，异常回退 |
| 中 | 摘要、翻译、常规问答 | 批量回归样张把关 |
| 低 | 分类、打标、粗筛 | 直接切量化模型 |

分档的价值在于把有限的验证资源花在高敏感任务上。每档维护一套固定回归样张，模型或内核版本一变就全量重跑——低位内核迭代快，这层回归是版本升级的刹车片。

## 九、风险提示

- **量化对长尾能力的影响**：常规任务看不出差别，冷门语言、极端长文推理要单独回归；
- **低位内核的成熟度**：定制内核迭代快，锁定验证过的版本，升级先跑基准；
- **KV 缓存预算**：262K 上下文是能力上限，实际可用长度取决于剩余显存，长文任务先压测；
- **视觉链路**：图像输入的预处理要与训练口径一致，否则保真度打折；
- **数据合规**：本地部署的数据不出域是优点，但接入云端兜底时，敏感任务要走脱敏或白名单。

## 十、检查清单：三值量化部署验收

1. 权重文件校验与版本锁定；
2. 文本/代码任务与原精度模型同题对比；
3. 视觉理解任务单独回归；
4. 工具调用任务验证参数格式正确率；
5. 长上下文压测，确认实际可用窗口；
6. 本地服务的失败率与延迟看板，兜底切换演练；
7. 电费与折旧入账，验证月度成本模型。

## 总结

三值权重加 FP16 组缩放把 27B 模型压到 5.9GB、1.76 有效比特，262K 上下文和图文多模态没有掉队，CUDA 与 MLX 双生态让消费级硬件第一次真正摸到了中型模型的本地部署。我的结论：中高产量业务值得为这套方案搭一条"本地打底、云端兜底"的混合链路，本地服务封装成标准接口后由 4sapi（https://4sapi.com）统一调度，成本模型从此从按量计费变成固定电费。欢迎在评论区聊聊本地部署的显存账和量化方案的实测数据。
