# 【大模型API中转站】[第237期] Opus 5.5 登顶编码榜｜单价降两成总成本反涨

Claude Opus 5.5 的输入与输出单价各降两成，缓存读取单价降了六成，Coding Agent Index 从 Opus 5 的 60 分抬到 66 分，但单任务成本从 $10.79 涨到 $13.04，涨幅 21%。

我在 4sapi（https://4sapi.com）上把这轮价格表与用量数据重新过了一遍，得到的结论很朴素：单价只是成本公式里的一个系数，另一个乘数是用量，而这次用量涨得比单价跌得快。

## 一、先把数字摆清楚

这轮发布值得记下来的数字分三组：能力、单价、用量。

能力这一组，Claude Opus 5.5 在 Claude Code max effort 配置下拿到 Coding Agent Index 66 分，是当前测得最高分；上一代 Opus 5 为 60 分，Claude Fable 5.1 为 62 分。三项编码评测同步抬升，其中 Terminal-Bench 4.0 从 54.5% 升到 63.1%，涨了 8.6 个百分点，是三项里增幅最大的；DeepSWE v1.1 从 62.5% 升到 68.4%；SWE-Atlas-QnA 从 62.1% 升到 66.4%。

| 评测项 | Opus 5 | Opus 5.5 | 变化 |
| --- | --- | --- | --- |
| Coding Agent Index（Claude Code max effort） | 60 | 66 | +6 |
| Terminal-Bench 4.0 | 54.5% | 63.1% | +8.6 个百分点 |
| DeepSWE v1.1 | 62.5% | 68.4% | +5.9 个百分点 |
| SWE-Atlas-QnA | 62.1% | 66.4% | +4.3 个百分点 |

单价这一组，输入从每百万 token $5 降到 $4，输出从 $25 降到 $20，都是两成的降幅；缓存读取从 $0.50 降到 $0.20，降幅六成。

用量这一组才是重点：单任务 token 用量约 15.6M，Opus 5 为 11.4M，涨了三成七；其中输出 token 约为 Opus 5 的 2.4 倍。

三组数字放在一起，就是这篇文章要拆的那道题。

## 二、三项编码评测为什么同步抬升

Terminal-Bench 4.0 的增幅最大，+8.6 个百分点。这一项衡量的是在终端环境里完成多步操作的能力，包含长链路执行、错误恢复与工具编排；DeepSWE v1.1 与 SWE-Atlas-QnA 分别抬升 5.9 与 4.3 个百分点，覆盖仓库级代码修改与代码问答。

一个规律值得留意：越依赖长链路执行的项目，涨幅越大。长链路意味着更多中间步骤、更多工具返回、更多自检回合，而这些恰好都是 token 消耗的主要来源。能力提升与用量增长在编码 agent 上是同一件事的两面——模型愿意多想一步、多验证一次、多写一段说明，分数就上去了，token 也跟着上去了。

这也解释了为什么 Opus 5.5 的输出 token 会达到 Opus 5 的 2.4 倍。输出侧的增长不是浪费，它是得分的一部分，但同时是最贵的那一部分。

## 三、单价 × 用量 = 任务成本

把成本写成一个公式，这轮的倒挂就不难理解了：

```text
单任务成本 = 未命中输入的 token 数 × 输入单价
           + 命中缓存的 token 数   × 缓存读取单价
           + 输出 token 数         × 输出单价
```

三项相加，才是这个任务真实的开销。单价只出现在系数位置，token 数出现在变量位置。

问题在于，系数由服务方定，变量由模型在任务里自己走出来。轮数、缓存利用率、模型档位，这三件事共同决定用量，而它们都会随会话长度与复杂度变化。同一段系统提示词，任务简单时几轮就收敛，任务复杂时几十轮还在自检，单任务成本可以差好几倍。

所以"单价降了两成"这句话在采购语境里成立，在任务语境里不成立。采购看的是价目表，任务看的是用量记录。

## 四、为什么单价降两成，总成本反涨 21%

把两代数字并排放：

| 项目 | Opus 5 | Opus 5.5 | 变化 |
| --- | --- | --- | --- |
| 输入单价（每百万 token） | $5 | $4 | -20% |
| 输出单价（每百万 token） | $25 | $20 | -20% |
| 缓存读取单价（每百万 token） | $0.50 | $0.20 | -60% |
| 单任务 token 用量 | 11.4M | 15.6M | +36.8% |
| 其中输出 token | 基准 | 约 2.4 倍 | +140% |
| 单任务成本 | $10.79 | $13.04 | +20.9% |
| 折算混合单价（成本 ÷ 用量，估算） | 约 $0.95/M | 约 $0.84/M | 约 -12% |

最后一行是按给定数字做的折算，不是官方口径：$10.79 ÷ 11.4M 约等于每百万 token $0.95，$13.04 ÷ 15.6M 约等于每百万 token $0.84。也就是说，单位 token 的综合成本确实降了，降幅大约一成出头；但用量涨了三成七，两个乘数一乘，总成本还是往上走。

这就是"单价降两成、总成本反涨 21%"的全部机制：降价是真的，涨量也是真的，量涨得比价跌得快。

再往下追一层，输出 token 是这次的关键变量。输出单价 $20 是输入单价 $4 的五倍，是缓存读取单价 $0.20 的一百倍。输出 token 涨到 2.4 倍，对总成本的边际影响远大于同比例的输入增长。Opus 5.5 用更便宜的输入输出 token 与大量缓存读取压住了一部分开销，但压不过输出侧的增长。

## 五、成本归因：一条链看清钱的去向

单任务成本不是一个孤立的数，而是一条链上的乘积：

```text
任务成本归因链

会话长度 / 轮数 ───────► 输入 token 总量 ──┐
                                           ├─► 输入侧成本 ──┐
缓存命中率 ────────────► 有效输入单价 ─────┘                │
                                                           ├─► 单任务成本
输出 token 占比 ───────► 高单价部分权重 ───────────────────┤
                                                           │
模型档位 / fallback 策略 ► 单价系数 ───────────────────────┘
```

链上的每一段都可以单独观测，也可以单独干预。轮数由任务定义与提示词决定；缓存命中率由前缀结构决定；输出占比由模型行为与输出规范决定；单价系数由选型决定。四个旋钮里，前三个是工程侧能拧的，最后一个是采购侧的事。

实际排查时按链的顺序往回走：成本超预算，先看是轮数失控还是输出膨胀；轮数正常而输入成本高，再看缓存命中率；两者都正常，才轮到讨论要不要换档位。跳过前两段直接换模型，通常只是把成本换了个地方发生。

## 六、缓存利用率：这轮降幅最大的一项

缓存读取从 $0.50 降到 $0.20，降幅 60%，是价目表上降幅最大的一格。它的意义不在于绝对价格，而在于相对折扣被拉大了：

- Opus 5：缓存读取 $0.50 对输入 $5，命中的部分是未命中部分的十分之一；
- Opus 5.5：缓存读取 $0.20 对输入 $4，命中的部分变成未命中部分的二十分之一。

折扣从 10 倍拉到 20 倍，意味着缓存命中率对单任务成本的影响比上一代更陡。命中率高，成本曲线几乎是平的；命中率低，成本立刻向未命中价靠拢。

观测口径很简单：命中率等于缓存读取 token 除以输入 token 总数。这个比值应该在会话里单调上升，因为共享前缀在前几轮之后基本不再变化。如果它长期停在低位，问题通常不在服务端，而在前缀本身——时间戳、随机 ID、每轮重新排序的工具清单，都会让前缀失配，让整段输入按未命中价重新计价。

## 七、输出 token 占比：最贵的那个变量

输出 token 只占总用量的一小块，却常常贡献最大的一块成本，原因就在单价差。按 Opus 5.5 的价目表算，一个输出 token 的价格等于 5 个未命中输入 token，或者 100 个缓存读取 token。

所以第二个观测点是输出占比，即输出 token 除以输入与输出 token 之和。这个比值在编码 agent 上天然偏高，因为模型要输出完整的代码块、补丁和验证结论。Opus 5.5 的输出 token 约为 Opus 5 的 2.4 倍，这个倍数直接解释了成本倒挂的大部分。

可控的干预手段有三个：把输出规范收紧，只要求补丁与结论，不要求整份文件复述；把长输出拆成多轮短输出，让每一轮的上下文继续复用；对非关键路径的任务降档，用更便宜的档位承担高输出量的环节。

## 八、按任务核算成本的四个步骤

按 token 核算成本在 agent 场景里几乎没有指导意义，因为一次"调用"对应的用量跨度太大。按任务核算才是可用的口径：

1. **定义任务单元**。一个 PR、一个 issue、一次代码审查，各自算一个任务。任务单元定义不清，所有平均值都会失真。
2. **采集三个量**。输入 token（区分命中与未命中）、输出 token、轮数。这三个量在一次会话的 usage 里都能拿到。
3. **套当前单价算单任务成本**。单价做成配置表，按模型分档维护，不要写死在调用点。
4. **按任务类型分组看分布**。平均值会掩盖长尾，P50 与 P95 一起看，才知道预算该按哪个口径留。

前三步是采集，第四步是决策。多数团队卡在第二步——只记了总花费，没记单任务用量，于是价格一变就只能重估预算，无法判断到底贵在哪一段。

## 九、Pareto 前沿与分层选型

同一批发布把智能指数与单任务成本的 Pareto 前沿整体推了一下，新增的点位大致是这样：

| 配置 | 智能指数 | 单任务成本 | 定位 |
| --- | --- | --- | --- |
| GPT-6 Luna(max) | 37 | $0.068 | 高频低难度环节 |
| MiMo-V2.6-Pro | 46 | $0.13 | 中等难度主力 |
| GPT-6 Sol(max) | 48 | $1.06 | 通用编码任务 |
| Claude Opus 5.5(max with fallback) | 58 | $5.98 | 关键路径，当前最高分 |

这张表里最值得注意的不是最高分，而是跨度：从 $0.068 到 $5.98，成本相差约 88 倍，而指数只差 21 分。绝大多数任务的难度并不落在最高分那一档，把它们放在最高分档位跑，等于用几十倍的单价换十几分的余量。

分层选型的判断依据可以按这个顺序走：

```text
任务进来
   |
失败代价高？（生产发布 / 数据迁移 / 关键链路）
   |                    |
  是                   否
   |                    |
Opus 5.5 档位      任务可拆分？（初筛 + 执行）
                        |             |
                        是            否
                        |             |
              Luna 初筛 → Sol 执行    Sol 档位
```

判断的核心只有一条：失败返工的成本是否超过降档省下的钱。返工一次要重跑整条链，还要加上人工确认的时间，通常比差价贵得多。所以降档试验应该从非关键路径开始，用质量抽检守门，而不是拿核心链路做实验。

## 十、接入示例：把成本观测接到调用链上

接入时把"算成本"这件事直接放进调用循环，每轮记录用量，任务结束时汇总。这样单价一变，改一张配置表就能重新估值，不需要翻历史日志。

```python
import os
import json
from openai import OpenAI

client = OpenAI(
    api_key=os.environ["FOURSAPI_API_KEY"],
    base_url="https://4sapi.com/v1",
)

PRICE = {  # 单价表按每百万 token 计价，做成配置，不写死在调用点
    "claude-opus-5.5": {"input": 4.00, "cache_read": 0.20, "output": 20.00},
    "claude-opus-5": {"input": 5.00, "cache_read": 0.50, "output": 25.00},
}


def round_stats(model: str, usage) -> dict:
    p = PRICE[model]
    cached = getattr(usage.prompt_tokens_details, "cached_tokens", 0) or 0
    prompt = usage.prompt_tokens
    fresh = prompt - cached
    out = usage.completion_tokens
    cost = (fresh * p["input"] + cached * p["cache_read"] + out * p["output"]) / 1_000_000
    return {
        "cached_tokens": cached,
        "prompt_tokens": prompt,
        "cache_hit_rate": round(cached / prompt, 4) if prompt else 0.0,
        "output_tokens": out,
        "cost_usd": round(cost, 4),
    }


def run_task(model: str, system_prompt: str, steps: list) -> None:
    messages = [{"role": "system", "content": system_prompt}]
    total_cost = 0.0
    total_tokens = 0
    for i, step in enumerate(steps):
        messages.append({"role": "user", "content": step})
        resp = client.chat.completions.create(model=model, messages=messages)
        messages.append(resp.choices[0].message)
        stat = round_stats(model, resp.usage)
        total_cost += stat["cost_usd"]
        total_tokens += stat["prompt_tokens"] + stat["output_tokens"]
        print(f"round {i}: {json.dumps(stat, ensure_ascii=False)}")
    print(f"task_total_usd={total_cost:.4f} tokens={total_tokens}")


if __name__ == "__main__":
    run_task(
        model="claude-opus-5.5",
        system_prompt=open("system_prompt.txt", encoding="utf-8").read(),
        steps=["先复现失败用例", "给出最小修复补丁", "跑一遍回归并汇报结论"],
    )
```

Key 从环境变量读取，不进代码仓库。模型名与单价都从配置表走，接入侧只维护一份价格表；模型标识以控制台当前放行的名称为准，切档时只动配置。

三段输出要盯住：`cache_hit_rate` 应该在第二轮之后稳定在高位；`output_tokens` 是成本的主要来源；`task_total_usd` 才是要进看板的那个数。

## 十一、成本估算表怎么读

把用量与缓存命中率两个变量做成一张敏感性表，比盯单价表有用得多。下面这张表是估算，前提写清楚：某编码任务总 token 约 15.6M，其中输出约 0.36M（按输出占比约 2% 的假设），其余为输入；单价按 Opus 5.5 的 $4 / $0.20 / $20 计算。

| 输入缓存命中率 | 输入侧成本（估算） | 输出侧成本（估算） | 单任务合计（估算） |
| --- | --- | --- | --- |
| 0% | $60.96 | $7.20 | $68.16 |
| 50% | $32.00 | $7.20 | $39.20 |
| 90% | $8.84 | $7.20 | $16.04 |
| 95% | $5.94 | $7.20 | $13.14 |

读法有三条。

第一，命中率从 0 走到 95%，输入侧成本掉了约一个数量级，输出侧成本一动不动。缓存只作用于输入，对输出没有任何帮助，所以高输出占比的任务光靠缓存救不回来。

第二，命中率越高，边际收益越小：从 0 到 50% 省下约 $29，从 90% 到 95% 只省约 $3。缓存改造的收益主要来自前几个百分点，后面的投入要算清回报再动手。

第三，在这套假设下，$13.04 的实际单任务成本对应的是接近 95% 的输入缓存命中率。这轮定价的实际表现高度依赖缓存——命中率高，$13.04 才成立；命中率掉到 50%，同一个任务的成本估算会抬到接近 $39。

## 十二、接入检查清单

1. 模型名以控制台当前放行的标识为准，档位切换只改配置表；
2. Key 从环境变量读取，按最小权限发放，并配置用量告警；
3. 每轮记录输入 token、缓存读取 token、输出 token 与轮数；
4. 系统提示词、工具定义、项目规范前置且稳定，去掉前缀里的时间戳与随机 ID；
5. 确认缓存命中率在第二轮之后上升；长期为零时优先检查前缀是否每轮都在变；
6. 把单任务成本而不是总花费作为看板指标，同时看 P50 与 P95；
7. 用历史真实任务做 A/B，对比质量、轮数与输出 token 量，再决定是否升档；
8. 单价表与预算阈值做成配置，价格调整时只改一处；
9. 所有接入遵守各平台服务条款，不做任何规避官方限制的配置。

## 十三、成本与风险提示

- 单价与折扣以官方当前公告为准，长期项目把价格做成配置而不是硬编码；
- 单任务成本随会话长度与复杂度变化，同一个模型在简单任务与复杂任务上的成本可能相差数倍，预算要按任务类型分开留；
- 输出 token 约为上一代 2.4 倍，长任务需要设置单任务预算上限与最大轮数，避免无界自检；
- 缓存读取单价虽然只有 $0.20，但只在命中时生效，命中率是唯一的开关；
- 高能力档位适合失败代价高的环节，非关键路径优先降档，用抽检守住质量；
- 智能指数是聚合口径，具体到某类任务有升有降，迁移前用自有任务验收。

## 结论

Opus 5.5 这轮发布给出了一个很干净的样本：输入输出单价各降两成、缓存读取降六成，三项编码评测全线抬升，单任务成本却从 $10.79 涨到 $13.04。原因不在定价，在用量——单任务 token 从 11.4M 涨到 15.6M，输出 token 涨到 2.4 倍，而输出是价目表上最贵的一格。

把"单价 × 用量 = 任务成本"当成核算主线之后，动作就明确了：单价做成配置，用量进看板，缓存命中率与输出占比当成两个一等观测点，选型按失败代价分层而不是按分数排序。我在 4sapi（https://4sapi.com）上复核这几个数字时，最直接的感受是：能被观测的成本才是可控的成本。
