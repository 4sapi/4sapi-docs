# 【大模型API中转站】[第05期] 模型遗忘与数据合规｜上下文敏感删除实战

删除一个用户的数据，不只是删数据库。向量库、日志、缓存、供应商侧，每一层都可能残留风险。

作为 4sapi 团队的接入实战记录，这一篇从 API 场景的数据生命周期出发，整理成可验证的删除流水线与巡检方法。

## 一、开篇：数据删除请求来了怎么办

做 AI 产品最容易被忽略、也最致命的一环，是**数据合规**。

- 用户要求删除自己的数据，删除接口却只管删了数据库，忘了向量库和日志；
- 模型微调过包含敏感信息的语料，用户要求"忘记"，系统却根本没有遗忘能力；
- 平台把 AI 伴侣、对话记录当普通数据存，监管收紧后连夜下线。

这一期只讲一个工程问题：**API 场景下，怎么把"数据"真正删除干净**。不讨论司法，不讨论政策博弈，只讲可落地的技术路径。

## 二、原理速览：为什么"删数据"不是删数据库

在接入大模型 API 的应用里，一份用户数据往往同时存在于多个层面：

```text
用户的输入文本
   ↓
① 应用数据库（结构化记录）
② 向量库（Embedding 持久化）
③ 模型训练语料（历史微调）
④ 第三方 API 缓存（供应商侧）
⑤ 日志与审计（请求留痕）
```

"遗忘一个用户"不是删一条记录，而是**这五层都要处理**。很多人只做了第①层，剩下几层全是遗留风险。

### 什么是上下文敏感的遗忘

传统遗忘评测用"互不相交的遗忘集/保留集 + 独立事实"，这让模型"太容易过关"。真实场景里，同一句话在**上下文不同**时，是否该被删是不同的。

```text
错误做法：删所有含"张三"的句子
  → 误删了"张三提交了『公司』项目里程碑"这类无关内容

正确做法：按"上下文"判定，只删除"张三=敏感身份"这一语义的关联
```

这是我测量一个遗忘痛点时的最大感悟：**遗忘不是删词，是维护语义边界**。

## 三、深入：上下文敏感遗忘

### 3.1 三类遗忘约束

| 约束类型 | 含义 | 例子 |
| --- | --- | --- |
| 独立事实遗忘 | 删除单个孤立事实 | 删掉"经理是张三" |
| 关联事实遗忘 | 删除关联身份 | 删除"张三"与"项目X"的关联 |
| 上下文敏感遗忘 | 只在特定上下文隐藏语义 | 解密→删除"张三=名字"，保留校准性事实 |

### 3.2 当前基线的问题

现有的冻结方法依赖"互不相交的遗忘集/保留集"，这有一个严重缺陷：**遗忘集和保留集里的知识是独立的，但真实任务里它们会交叉**。一个"张三"可以被同时驱逐"身份"和保留"百科"——这两件事必须在上下文中区分。

### 3.3 我的做法

与其训练一个"遗忘模型"，我更推荐**在工程侧分而治之**：

```text
① 过滤层：输入侧拦截，不敏感数据不给模型
② 隔离层：按用户/项目隔离存储，删除按范围进行隔离
③ 覆盖层：删除后插入新的"中立"上下文，覆盖原记忆
④ 排查层：定期扫描向量库与日志，清除残留
```

## 四、工程路线：分而治之的删除

与其在模型参数层面做"遗忘"（又贵又不可控），我在 API 接入流程里把"数据删除"拆成四步：

### 4.1 第一步：向量库也是"数据库"

凡是写入向量库的内容，都要给每条向量打标记：

```python
import requests

VECTOR_Q = "https://4sapi.com/v1/vectors"   # 示例向量服务端点

def store_with_meta(text: str, user_id: str, model: str):
    vec = requests.post(f"{VECTOR_Q}", json={"input": text, "model": model}).json()
    vec["metadata"]["owner"] = user_id          # 归属标记
    vec["metadata"]["tenant"] = "user-provided" # 治理属性
    # 写库时同时取下一条：删除索引也以 user_id 为分区
    return vec
```

关键：**每条向量都带归属与失效时间**，删除时按条件批量扫。

### 4.2 第二步：输入过滤

"未然"比"善后"省事。在请求落库之前加过滤层：

```python
SENSITIVE_PATTERNS = [
    r"身份证[号]?\s*[:：]?\s*\d{17}[\dXx]",
    r"手机号\s*[:：]?\s*1[3-9]\d{9}",
]

def should_guard(text: str) -> bool:
    import re
    return any(re.search(p, text) for p in SENSITIVE_PATTERNS)
```

命中直接不入库、不进日志、不参与友好度。

### 4.3 第三步：删除脚本全流程

```python
import requests

def delete_user_data(user_id: str):
    """五个数据层的删除：结构化、向量、对话、日志用覆盖"""
    results = {}
    # ① 结构化数据库
    results["db"] = db_delete(user_id)
    # ② 向量库
    results["vector"] = vector_delete_by_owner(user_id)
    # ③ 对话缓存
    results["cache"] = cache_invalidate(user_id)
    # ④ 日志脱敏标记
    results["logs"] = anonymize_logs(user_id)
    # ⑤ 供应商：提交删除请求，并确认幂等回调
    results["supplier"] = request_supplier_deletion(user_id)
    return results
```

每一个子操作都能返回成功/失败，汇总成删除报表。

## 五、防删 + 保留的边界处理

### 5.1 删除要可审计，又要保证安全性

删除操作不是"直接清空"，要有：

- 删除先记录 `delete_job_id`，再执行，便于溯源；
- 删除失败要触发重试与告警；
- 删除完成后，配合反向扫描验证（抽查向量库是否还有残留）。

### 5.2 向量库删除的坑

向量库的删除并不简单：

- 向量是按向量维度存的，不是按 `user_id` 存的 → 必须建 `owner_id` 反向索引对；
- 批量删除要分页 + 分批，避免打爆库；
- 删除后向量库**必须执行 `compact`/重建段**，否则旧数据虽不可查但仍占用。

## 六、模型层的"上下文敏感遗忘"

如果真的必须在模型层做（例如因历史微调数据被要求删除），工程上配合：

1. 只在**语义边界明确**的语境里做遗忘，避免误删公转；
2. 用"遗忘集 / 保留集"交叉验证，测精度与召回；
3. 遗忘后跑 in-context 评测，确认敏感语义不再浮现；
4. 必要时直接重训练或换基座，比在参数上加补丁更可控。

## 七、API 接入的合规清单

我把它整理成一份可勾选的 checklist：

1. 每个回答是否都有 [`user_id`] 归属，且删除可回溯；
2. 向量库按 owner 建反向索引，删除可批量；
3. 敏感输入在过滤层被拦截，不进日志；
4. 日志脱敏，用户反馈、供应商数据删除有回调；
5. 删除有 `delete_job_id`、可验证、可审计；
6. 定期采样本扫描，抽查残留向量；
7. 微调/历史模型若含敏感，重新评估或替换。

## 八、避坑提示

- **别只删数据库**：向量库、日志、缓存、供应商全要同步；
- **必把"逻辑删除"当真正删除**：标记 `deleted` 的字段再被读回来就是泄漏；
- **别忘白盒 SQL / 全文检索**：关键词搜索也可能捞回已删内容；
- **别忽略服务端日志**：请求日志、调试快照里都可能残留敏感原文。

## 九、删除的验证与巡检

删除完成后，需要证明它真的删干净了，而不是"看起来没了"。

### 9.1 删除成功后的验证

```python
def verify_deletion(user_id: str) -> dict:
    checks = {
        "db": count_rows_where_owner(user_id) == 0,
        "vector": count_vecs_by_owner(user_id) == 0,
        "cache": cache_get(user_id) is None,
        "logs": not any(has_sensitive(user_id) for _ in iter_recent_logs()),
    }
    return checks
```

四个子检查全部 `True`，删除才判为完成；任一 `False` 则进入重试与告警。

### 9.2 巡检（周期性）

- 每周抽查一批已删除用户的向量与日志，确认没有残留；
- 用样本数据做"删除后复现"测试，确认模型不再关联敏感信息；
- 对供应商侧，保留一份"删除发起/回调"绑定表，可追溯。

### 9.3 把遗忘做成产品能力

```text
用户发起删除请求
   ↓
生成 job_id → 分发给各子系统
   ↓
结构化库 / 向量库 / 缓存 / 日志 并行处理
   ↓
collect 结果，生成删除报告
   ↓
不通过 → 重试 / 人工介入
   通过 → 归档 + 审计
```

删除不是一次性动作，而是带状态、可验证、可回退的流水线。接入 API 的应用把这一段做扎实，比"模型会不会遗忘"更可控、更容易上线。

## 总结

API 场景的数据合规，核心是**把"多站点的数据"一次性交给"可靠删除"**。向量库带 owner、日志脱敏、删除有审计、供应商删除需回调确认。这些在模型层面很难，但在工程数据面完全可以落地。让我用一套"过滤层 + 隔离层 + 适配层 + 排查层"的体系，把数据合规做成可验证的工程，而不是纸上谈兵。
