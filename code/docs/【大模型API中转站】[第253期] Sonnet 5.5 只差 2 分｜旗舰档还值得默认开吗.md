# 【大模型API中转站】[第253期] Sonnet 5.5 只差 2 分｜旗舰档还值得默认开吗

过去一年做模型选型的默认动作是"关键链路用旗舰"，理由很简单：旗舰更强，差价可以接受。

这个理由正在失效。中端档位与旗舰档位的差距已经缩到个位数分数，而两档的单价差通常是数倍。我在 4sapi（https://4sapi.com）上做接入选型时，判断口径已经从"哪个更强"换成了"这 2 分值不值这个差价"。

## 一、先看这组数字

一边是模型发布侧的数据：中端档位在 Artificial Analysis Intelligence Index 得 **56 分**，仅比旗舰档位低 **2 分**；而在同档位的最高 effort 配置下，比上一代高 **18 分**。跨代提升远大于跨档差距，这是第一个值得注意的结构。

另一边是 Agent Arena 的成本与效果数据：

| 档位 | Agent Arena 表现 | 单任务成本 |
| --- | --- | --- |
| 旗舰档（High） | 排名第 2，净改进 +12.15% | 比上一代旗舰低 56% |
| 中端档（Max） | 排名第 23，净提升 +1.6% | $0.05 |

把两行放在一起，能看出一个连续的选择空间：从 **$0.05 的 +1.6%** 到 **排名第 2 的 +12.15%**，中间还有许多未列出的档位。这意味着"默认开旗舰"不再是唯一合理的默认值，而是这条曲线上的一个点，且是成本最高的那个点。

## 二、2 分差在什么场景下会显露

"只差 2 分"是聚合结论，落到具体任务上不是均匀分布。我的经验是把任务分成三类来看：

**第一类，单轮、规则明确、可校验。** 抽取、分类、格式转换、摘要初筛。这类任务上 2 分差基本不可感知，因为输出对错由规则判定，两个档位给出的结果都能通过校验。中端档位在这类任务是纯收益。

**第二类，多步推理、工具编排。** 差异会显现，但形式不是"答错"，而是**一次决策错误的连带成本**。多步任务里每一步都依赖前一步，中间一步偏了后面全都跟着偏。这类任务的成本不只看单价，还要看返工率。

**第三类，需要长链条一致性或高精度计算。** 差异最明显。这类任务更适合旗舰档位，或者用中端档位加确定性校验兜底。

分类之后，判断就变成一道算术题：中端档位在第二类任务上的返工增量成本，是否小于它在单价上省下的钱。第一类和第三类相对好判断，第二类需要实测。

还有一类任务值得单独列出来：**输出直接面向外部用户的场景**。这类任务的成本不只算 token 与返工，还要算错误的外溢代价——一次措辞失当、一次数据错引，修复成本远高于省下的模型费用。我把这类任务一律归入高档，不参与降档实验。判断依据很简单：如果错误的代价需要人工介入、且影响范围超出系统内部，就不适合用"能通过校验"作为放行标准。

## 三、迁移成本不能忽略

换档位有一个容易被低估的成本：**提示词需要重新校准**。同一段提示词在两个档位上的表现并不一致——effort 校准、输出格式约束、拒绝行为的边界都可能不同。

所以真实的选择不是"旗舰 vs 中端"两笔差价，而是：

```text
留在旗舰            = 现有提示词 + 旗舰单价
换到中端            = 重校提示词的人力 + 中端单价 + 返工风险
```

当 2 分差对应的能力折损很小、而两档单价差是数倍时，第二行通常仍然划算；但如果提示词体系庞大且高度依赖旧模型的行为特征，重校成本可能吃掉第一年的差价。这也是为什么发布方会同时提供**提示词迁移指南**——它把重校从试错变成按清单执行，直接降低了第二行的成本。

## 四、分层路由：把成本花在真正难的地方

比较稳的做法不是二选一，而是按任务分层。请求进入后先做一次轻量判断，再决定走哪个档位。

```text
请求进入
    |
    v
[1] 复杂度预判（规则 + 小模型）
    |
    +-- 低 ---> 中端档位（高频、可校验）
    |              |
    |              +-- 校验不通过 -> 升级到旗舰重试
    |
    +-- 高 ---> 旗舰档位（多步、长链条）
    |
    v
[2] 成本归因：按档位分别记录 token 与任务数
    |
    v
[3] 定期复盘：哪些任务本可降档、哪些被误降
```

关键在于**校验不通过就升级**这条回路。它把风险从"降档可能做错"变成"降档做错会被兜住"，让分层从赌博变成可控的工程动作。

## 五、复杂度预判怎么做

预判不需要精确，只需要有判别力。我用的信号按可靠性排序：

1. **任务类型标签**：如果调用方本来就带任务类型，直接用，这是最准的信号；
2. **预期步数**：需要工具调用或多轮交互的任务，直接走高档；
3. **输入长度与结构**：长文档、多文件、需要跨段引用的一律走高档；
4. **历史统计**：同一类任务过去在中端档位上的校验失败率，超过阈值就整类升级。

最后一条最值得做。前三条是静态规则，需要人工维护；第四条是从实际数据里长出来的，能自动适应任务分布的变化。我把它做成按任务类型维护的失败率表，超过阈值就自动把该类任务标记为"必须高档"。

## 六、能力差与价格差的换算

把两个差换算到同一个单位，选型就有依据了。我用的是"每点智能指数的成本"这个粗口径：

```text
每点成本 = 单任务成本 / 智能指数
```

按此口径，$0.05 对应 56 分时每点约 $0.0009，而排名第 2 的档位在成本高出一个数量级以上的情况下，换来的净改进是 +12.15% 对 +1.6%。这个口径很粗，但足以回答一个重要问题：**提升一档能力的边际价格是多少**，以及这个边际价格在具体任务上换来多少实际收益。

真正的判断还是要回到任务：如果业务对错误的容忍度低、返工成本高，边际价格再贵也值；如果是内部工具、错了重跑一次就行，那中端档位是明确更优的选择。

换算口径的另一个用途是**给调价做预案**。供应商的价格与档位迭代很快，如果选型逻辑写死在代码里，每次调价都要重新评估全部链路。把"每点智能指数的成本"做成一个可计算的量，并在配置里保留各档位的单价，就能在调价后几分钟内算出：哪些任务的最优档位变了、哪些没变。只有真正变化的那部分才需要人工复验，其余保持不动。这是把价格波动的影响面从"全量重估"收缩到"差异项"的做法。

## 七、接入示例：分批路由与成本归因

下面这段代码实现按任务类型分批路由，并分别统计各档位的成本与升级率，用于事后复盘。

```python
import os
from collections import defaultdict
from openai import OpenAI

client = OpenAI(
    api_key=os.getenv("FOURSAPI_API_KEY"),
    base_url="https://4sapi.com/v1",
)

ECON = os.getenv("MODEL_ECON", "claude-sonnet-5-5")
FLAG = os.getenv("MODEL_FLAG", "claude-opus-5-5")

PRICE = {   # 各任务类型的单价（每百万 token），按计费类型分开记
    ECON: {"in": 3.0, "out": 15.0},
    FLAG: {"in": 5.0, "out": 25.0},
}

LOW_RISK = {"extract", "classify", "format", "summarize"}   # 可校验、容错高
FALLBACK_RATE = float(os.getenv("FALLBACK_RATE", "0.15"))    # 该类任务升级率阈值

_stats = defaultdict(lambda: {"calls": 0, "escalated": 0, "cost": 0.0})


def pick_model(task_type, hist):
    """低风险任务走中端；若历史升级率超阈值则整类升级到旗舰。"""
    if task_type not in LOW_RISK:
        return FLAG
    if hist.get(task_type, {}).get("escalated", 0) / max(hist.get(task_type, {}).get("calls", 1), 1) > FALLBACK_RATE:
        return FLAG
    return ECON


def call(model, system, user, max_tokens=1024):
    r = client.chat.completions.create(
        model=model, max_tokens=max_tokens, temperature=0,
        messages=[{"role": "system", "content": system},
                  {"role": "user", "content": user}],
    )
    u = r.usage
    p = PRICE[model]
    return r.choices[0].message.content, (u.prompt_tokens * p["in"]
                                          + u.completion_tokens * p["out"]) / 1_000_000


def run(task_type, system, user, validate=None):
    """validate 返回 True 表示通过；不通过则升级到旗舰重试。"""
    model = pick_model(task_type, _stats)
    text, cost = call(model, system, user)
    _stats[task_type]["calls"] += 1
    _stats[task_type]["cost"] += cost

    if validate and not validate(text) and model == ECON:
        _stats[task_type]["escalated"] += 1
        text, cost2 = call(FLAG, system, user)
        _stats[task_type]["cost"] += cost2
        return text, "escalated"

    return text, "ok"


def report():
    for t, s in sorted(_stats.items(), key=lambda kv: -kv[1]["cost"]):
        rate = s["escalated"] / s["calls"] if s["calls"] else 0.0
        print(f"{t:>10}: 调用={s['calls']:>4} 升级率={rate:6.1%} "
              f"成本=${s['cost']:.4f} 单次=${s['cost'] / s['calls']:.5f}")


if __name__ == "__main__":
    print(f"中端={ECON} 旗舰={FLAG}")
    # 实际使用时按业务循环调用 run()，结束后调用 report()
```

`report()` 输出的升级率是最有价值的指标：它直接说明哪些任务类型的降档尝试失败了。稳定在低位的类型可以保持中端，接近阈值的需要重新评估是否值得继续降档。

## 八、降档判断的三条纪律

**第一，用真实任务集测，不用公开基准。** 基准偏向难题，会高估能力差；真实流量的任务构成才是决策依据。

**第二，分级降档，不要一次到底。** 先降一档观察一段时间，稳定之后再考虑继续降。一次降到最低档，出问题时无法区分是档位不足还是提示词不匹配。

**第三，保留升级通路。** 降档的前提是校验不通过时能升级重试。没有这条通路，降档就是一次性赌注。

三条纪律之外还有一条运维上的要求：**降档决策要能回滚**。把档位选择做成配置项而不是硬编码，线上出现质量投诉时可以在分钟级切回上一档位，再从容分析原因。这比事后争论"到底是不是降档导致的"高效得多——先恢复到已知良好状态，再定位问题，是所有线上变更的通用顺序，降档也不例外。

## 九、分层之后还需要观测什么

分层路由上线后，有几项指标需要持续看，否则降档的效果会随时间漂移：

- **各档位的升级率**，按任务类型分开统计，这是判断降档是否成立的主指标；
- **每任务成本**而不是每百万 token 价格，前者包含 token 量变化，后者会掩盖它；
- **延迟分布**，不同档位的响应时间不同，降档可能改变整体的超时与重试参数；
- **质量抽检的通过率**，用于发现校验器覆盖不到的静默错误。

四项里前两项决定收益，后两项决定风险。只看前两项，容易在质量缓慢下滑时毫无察觉；只看后两项，则会把分层做成保守到没有收益的摆设。两者一起看，分层才是一个可持续的策略。

## 十、Agent 任务的特殊考虑

Agent 任务与前两类不同：它的成本不只看单价，还看**每任务 token 量**。同一任务在低档模型上可能需要更多轮次和更多重试，token 量的上升会部分抵消单价优势。

所以评估 Agent 场景的降档收益时，口径必须是**每任务成本**而不是每百万 token 价格。今日 Agent Arena 给出的 $0.05/task 就是这样的口径，它已经包含了该模型完成一次真实任务所需的全部 token 消耗——这才是可以和旗舰档位直接比较的数字。

一个可用的经验判据：如果降档后每任务成本的降幅明显小于单价降幅，说明 token 量的上升吃掉了大部分收益，此时降档的实际价值有限。

Agent 场景还有一处与单轮任务不同的地方：**它的成本对失败最敏感**。单轮任务失败一次只损失一次调用；Agent 任务失败可能意味着整条链路重跑，前面所有轮次的消耗全部沉没。所以在 Agent 链路上做降档实验时，样本量要比单轮任务大得多——单轮任务几十条就能看出趋势，Agent 任务往往需要上百条才能把重跑成本的影响稳定测出来。

## 十一、成本与风险提示

- **2 分差是聚合值**，具体任务上有升有降，迁移前必须用自有任务验收。
- **提示词重校成本要计入**，尤其是提示词体系庞大、依赖旧模型行为特征的场景。
- **多步任务的错误放大效应**比单轮明显，关键链路不要只为了单价降档。
- **降档后要重测延迟分布**，不同档位的响应时间不同，可能影响超时与重试参数。
- **价格与档位迭代很快**，把模型名与单价做成配置而不是硬编码，避免每次调价都要改代码；
- **校验器本身也可能是瓶颈**。如果降档依赖校验来兜底，校验器的覆盖率就决定了可降档的范围；校验覆盖不到的错误会静默通过，这类错误在设计校验规则时就要先列出来。

## 结论

当两档能力只差 2 分，选型的默认值就该从"用旗舰"改成"按任务分层"。做法并不复杂：先按可校验性把任务分成三类，低风险类走中端并挂上校验不通过的升级通路，高风险类保持旗舰，然后用每任务成本而不是每百万 token 价格来复盘。这套流程的价值在于它把"要不要降档"从一次赌博变成可测量的工程动作——升级率会说明哪些任务降对了，哪些该退回去。我在 4sapi.com 上按这个口径跑了一段时间之后，成本结构里最明显的变化不是单价，而是"哪些任务其实一直不需要旗舰"这个问题终于有了数据答案。
