# 【大模型API中转站】[第243期] 纯 Rust 训练 LLM 踩坑｜静默梯度缺陷与分词陷阱

一位开发者独自用纯 Rust 端到端预训练了一个语言模型：没有团队、没有 PyTorch、训练路径中不含 Python，租用 GPU 花费 164 美元。我把这套记录放进 4sapi（https://4sapi.com）的评测链路里对照了一遍，最想留下的判断是：训练栈里最危险的不是崩溃，而是静默失败——8 个框架缺陷全部通过了常规 loss 曲线检查。

## 一、164 美元跑完一次预训练：成就，不是推荐

量级先摆清楚：一个人、一张卡、一笔不到两百美元的租用开销，跑完了从语料处理到产物抽检的完整预训练流程。开发者给这件事的定性很克制——这是一项成就，不是一份推荐路径。

更值得带走的不是模型本身。训练栈是纯 Rust：张量与算子走 Candle，部分训练路径走 Burn，训练循环里没有一行 Python。更有价值的动作发生在训练之后：把两个框架当作训练后端使用，逐个记录缺陷并分类，Candle 记录 5 个，Burn 记录 3 个。

关键词是「训练后端」。两个框架的公开叙事长期围绕推理与端侧部署展开，放到反向传播、优化器状态、混合精度、kernel 融合这些训练特有的路径上，问题密度完全不同。推理只需要一次前向；训练还要反向、梯度归约、参数更新、检查点恢复，任何一环静默失效，进程都不会报错。

| 项目 | 数值 | 说明 |
| --- | --- | --- |
| 参数规模 | 约 0.4B | 孟加拉语优先的语言模型 |
| 训练数据 | 约 20 亿 token | 单次预训练预算 |
| 训练时长 | 54.6 小时 | 单张租用 H100 |
| 算力开销 | 164 美元 | 租用 GPU 的实付金额 |
| 训练栈 | 纯 Rust | 训练路径中不含 Python |
| 语言优先级 | 孟加拉语优先 | 英语能力被刻意压低 |

表格里的数字是记录给出的实测值；下文涉及换算的结论会标注为估算。

## 二、静默失败为什么比崩溃更贵

崩溃是训练里最友好的错误。段错误、断言失败、显存溢出都会立刻停下进程，留下栈和日志，修复路径清晰。真正吃掉预算的是另一类：进程活着，曲线在动，日志干净，但训练在某个环节已经不再做正确的事。

两个典型样本。融合 kernel 静默不产生梯度，某些参数从头到尾没收到梯度，冻结在初始化附近，训练却不报错、不告警、不变慢。反向传播吞吐只有理论 GPU 吞吐的 3%，结果正确，只是慢了三十多倍（估算，按吞吐比直接换算）。前者浪费正确性，后者浪费时间，共同点是都不主动暴露自己。

算一笔账：164 美元摊到 54.6 小时上约合 3 美元每小时（估算）。若反向传播的真实吞吐只有理论值的 3%，同样步数的训练，仅反向这一段的墙钟时间就要膨胀到三十多倍（估算）。单看一张卡跑一天并不刺眼，但实验重复十次、超参试三组，隐性开销就超过了显性开销。

更麻烦的是决策污染。曲线正常下降时，人会本能地把结果归因于模型容量或超参，于是继续加预算，而问题藏在框架的 kernel 里。算力可以再买，被错误结论带偏的实验周期买不回来。

## 三、训练栈校验链：从数据到产物验收

把记录抽象一层，能得到一条与语言、与框架都无关的校验链。每一环都必须有能力拒绝放行，否则它不是校验，只是仪式。

```text
原始语料
   |
分词器训练 + 生育率抽检        <- 字符/token，按语言与脚本分别统计
   |
单步前向 / 反向 冒烟           <- 最小 batch，断言形状、dtype、数值范围
   |
梯度流仲裁器                   <- 每个可训练参数：存在、有限、非零
   |
loss 曲线 + 分语言 loss 分解    <- 全局曲线正常不代表每一路都正常
   |
产物验收                       <- 固定提示词生成抽检 + 随机初始化对照
```

前两个环节在数据侧，中间两个在数值侧，最后两个在产物侧。这条链的价值在于顺序：把便宜的检查放在前面。生育率抽检只要几秒，梯度流仲裁器只要一次前向加一次反向，都能在启动长跑之前完成；而 loss 曲线要跑几百步才看出趋势，产物验收要等整轮跑完。

实际踩坑的顺序往往相反：先启动长跑，再从曲线里反推问题。曲线能给出的信息量远小于它给人的权威感——8 个缺陷全部通过了曲线检查，说明曲线是必要条件，不是充分条件。

## 四、梯度流仲裁器：把不可见变成可断言

最值得直接抄走的动作，是把「梯度应该流动」变成一次可执行断言：跑一次前向与反向，逐个检查每个可训练参数是否收到有限且非零的梯度。记录里把它称为梯度流仲裁器，并说明它可以推广到任何框架——它检查的是训练语义，不是某个框架的 API 细节。

为什么不看全局梯度范数？因为范数会被少数活跃参数掩盖。输出层与嵌入层正常、中间某些层完全收不到梯度时，全局范数依然是一个漂亮的非零数，曲线依然会缓慢下降，这正是融合 kernel 静默失效能躲过检查的原因。记录里明确提到，这套纪律捕获了六个此类静默失败。

```python
import torch

def gradient_flow_arbiter(model, batch, loss_fn, atol=1e-12):
    """跑一次前向/反向，断言每个可训练参数都收到有限非零梯度。"""
    model.train()
    model.zero_grad(set_to_none=True)
    loss = loss_fn(model(**batch))
    loss.backward()

    total, dead, nonfinite = 0, [], []
    for name, p in model.named_parameters():
        if not p.requires_grad:
            continue
        total += 1
        g = p.grad
        if g is None or g.abs().sum().item() <= atol:
            dead.append(name)
        elif not torch.isfinite(g).all().item():
            nonfinite.append(name)

    report = {
        "loss": float(loss.detach()),
        "trainable": total,
        "grad_received": total - len(dead),
        "dead": dead,
        "nonfinite": nonfinite,
    }
    assert not dead, f"未收到梯度的参数: {dead[:8]}"
    assert not nonfinite, f"梯度出现 inf/nan: {nonfinite[:8]}"
    return report
```

三个要点：用 `set_to_none=True` 清空梯度，避免上一轮的残留值伪装成本轮梯度；用 `abs().sum()` 而不是范数，范数在极端尺度下可能因浮点下溢变成零；断言失败时输出参数名列表，参数名就是排查线索。

接进 CI 的成本是几秒。框架升级后必须重跑，因为缺陷随版本流动；混合精度训练时把断言放到 loss scaling 之后执行，否则 inf 与 nan 会被缩放掩盖。仲裁器只检查梯度有没有到，不检查梯度值对不对，后者靠数值对照与 loss 分解兜底。

## 五、分词器生育率：被静默反转的语料配比

第二个通用检查是分词器生育率，也就是每个 token 平均覆盖多少个字符。记录里有一组值得记下的数字：朴素的字节级分词把孟加拉语压缩到约 1.4 字符/token，英语是 3.9；修复分词方案后，孟加拉语达到约 4.1。

生育率本身不是问题，配比反转才是问题。语料的语言配比通常按文档数或字符数来定，训练预算却按 token 计。孟加拉语的生育率只有英语的三分之一多一点，同样字符数的语料就会消耗掉远多于预期的 token。粗略估算：字符数一比一的设定下，孟加拉语实际拿到的 token 量约为英语的 3.9 除以 1.4，接近 2.8 倍（估算）。设想中的「孟加拉语优先、英语补充」会静默变成「孟加拉语几乎独占」，全程不报错。修复后两者接近，4.1 对 3.9，字符配比才能映射成 token 配比。

```python
def fertility(tokenizer, texts):
    """每个 token 平均覆盖的字符数。按语言/脚本分组统计才有意义。"""
    chars = sum(len(t) for t in texts)
    tokens = sum(len(tokenizer.encode(t)) for t in texts)
    return chars / tokens if tokens else 0.0

def audit_mix(tokenizer, corpus_by_lang, target_share, tol=0.05):
    """比对目标 token 占比与实测 token 占比，偏差过大就拒绝开跑。"""
    stats, tokens = {}, {}
    for lang, docs in corpus_by_lang.items():
        stats[lang] = fertility(tokenizer, docs)
        tokens[lang] = sum(len(tokenizer.encode(d)) for d in docs)
    total = sum(tokens.values())
    for lang in target_share:
        actual = tokens[lang] / total
        gap = abs(actual - target_share[lang])
        print(f"{lang}: fertility={stats[lang]:.2f} "
              f"target={target_share[lang]:.2f} actual={actual:.2f}")
        assert gap < tol, f"{lang} token 占比偏离目标 {gap:.2f}"
    return stats
```

这段检查要在长跑之前执行，每个语言几百个文档就足以暴露量级差异。字节级分词在非拉丁文字上普遍吃亏：一个孟加拉语字符在 UTF-8 里通常占三个字节，逐字节建模会把一个字符拆成多个 token；拉丁文字一个字符一个字节，同样的词汇表容量下效率高得多。这不是分词器的缺陷，而是设计取舍，但取舍对配比的影响是静默的。

## 六、4sapi 接入：把数据与评测环节交给 API

自建训练与调用 API 不是对立的两条路。训练跑在 GPU 上，但流水线里有大量环节不需要 GPU：语料清洗、去重、分类、构造评测集、给生成结果打分。这些环节交给 API，成本低、迭代快，而且不会污染训练栈——它们不进反向传播路径，也就不可能引入梯度类缺陷。

接入写法如下，Key 从环境变量读取，不写进代码也不落盘。

```python
import os
from openai import OpenAI

client = OpenAI(
    api_key=os.getenv("FOURSAPI_API_KEY"),
    base_url="https://4sapi.com/v1",
)

def grade_sample(prompt, reference, candidate, model="gpt-6-luna"):
    """给固定提示词的生成结果打分，作为产物验收的抽样环节。"""
    resp = client.chat.completions.create(
        model=model,
        temperature=0.0,
        messages=[
            {"role": "system", "content":
             "给候选答案与参考答案的一致性打分，只输出 0 到 1 之间的小数。"},
            {"role": "user", "content":
             f"提示词：{prompt}\n参考答案：{reference}\n候选答案：{candidate}"},
        ],
    )
    return float(resp.choices[0].message.content.strip())

def normalize_rows(rows, model="gpt-6-sol"):
    """把语料里的重复表述归并成统一写法，减少训练集里的同义冗余。"""
    out = []
    for row in rows:
        resp = client.chat.completions.create(
            model=model,
            temperature=0.0,
            messages=[
                {"role": "system", "content": "只做规范化改写，不增删信息。"},
                {"role": "user", "content": row},
            ],
        )
        out.append(resp.choices[0].message.content.strip())
    return out
```

分工线很清楚：清洗、分类、格式规范化这类高频低难度环节走便宜档位；评测集构造、生成抽检打分这类需要判断力的环节走中档；loss 分解、梯度统计、吞吐对标必须在本机完成，因为它们的输入是 GPU 上的张量，不是文本。

两条纪律一起执行：Key 权限最小化并配置用量告警；只上传抽样数据，不上传整套专有语料。中转站的价值在于 OpenAI 兼容格式，同一批评测任务可以快速换模型跑对照，不必为每个模型改一遍 SDK。

## 七、Candle 与 Burn 的缺陷类型对照

记录给出 8 个缺陷：Candle 5 个，Burn 3 个。被点名描述的三个尤其值得记住，它们恰好覆盖三种失败形态。

| 框架 | 缺陷总数 | 已记录的具体缺陷 | 症状 | 常规 loss 曲线能否发现 |
| --- | --- | --- | --- | --- |
| Candle | 5 | 融合 kernel 静默不产生梯度 | 参数不更新，训练照常推进 | 否 |
| Burn | 3 | 反向传播吞吐约为理论 GPU 吞吐的 3% | 结果正确，只是慢三十多倍 | 否 |
| Burn | 3 | 多十亿参数规模下 kernel 融合路径段错误 | 训练中途崩溃，小规模无法复现 | 否 |

三类静默失败对应三种检查手段。把类型归纳出来，比记住某个具体缺陷更有复用价值：

| 缺陷类型 | 症状 | 检测手段 | 检查成本 |
| --- | --- | --- | --- |
| 梯度缺失 | 参数冻结，loss 仍下降 | 梯度流仲裁器，逐参数断言 | 一次前向反向 |
| 吞吐塌陷 | 只慢不错，预算被吞 | 单步计时与理论吞吐对标 | 几十步计时 |
| 规模相关崩溃 | 小规模正常，大规模段错误 | 规模阶梯压测 | 每一档若干步 |
| 数值不稳定 | 混合精度下 inf/nan 传播 | 断言放在 loss scaling 之后 | 与仲裁器合并 |
| 分词错配 | 语言配比与设计不符 | 生育率抽检与 token 占比比对 | 秒级 |

三类缺陷性质不同：梯度缺失是正确性缺陷，吞吐塌陷是性能缺陷，规模相关崩溃是稳定性缺陷。但工程上的处理方式是同一个——把「本来应该是这样」写成断言，在长跑之前执行。第三类最难，它只在多十亿参数规模下出现，小规模复现不出来，能做的只有规模阶梯压测。

## 八、0.4B 孟加拉语优先模型的结果怎么读

评估数字是：每 token 负对数似然 0.93，随机初始化对照为 12.60。两个数字的差距说明模型确实学到了孟加拉语的统计结构。对照基线的意义正在这里：单个负对数似然没有绝对含义，必须与同分词器、同数据、同初始化分布下的对照一起读。

口径问题也容易被忽略：负对数似然是分词器相关的。生育率从 1.4 改到 4.1 之后，同样一段文本的 token 数变了，每 token 的指标随之改变，跨分词器比较没有意义（估算前提），只能在同一套分词器内部纵向比较。

英语常识多选题上只有随机水平，这一条要放在预算语境里读。按常见的每参数约 20 token 的经验比例估算，0.4B 参数对应的计算最优 token 量在 80 亿量级，而这次只跑了约 20 亿，约为该口径的四分之一（估算）。预算被刻意压低，能力自然偏科：孟加拉语优先，英语让位。这是取舍的结果，不是缺陷。

## 九、算力预算：单张 H100 的 54.6 小时

换算成单位指标：164 美元除以 54.6 小时约合 3 美元每小时（估算）；20 亿 token 除以 54.6 小时，平均约 1 万 token 每秒（估算）。

第二个数字值得多看一眼。0.4B 参数、单张 H100、约 1 万 token 每秒，是相当保守的水平。记录里 Burn 的反向吞吐只有理论值的 3%，这个比例可以直接解释一部分差距（估算）。静默性能缺陷的代价就在这里：它不让训练失败，只让同样的预算买到更少的步数，而人往往先怀疑模型和超参，最后才怀疑框架。

预算结构里，租用开销只是显性部分：

| 开销项 | 性质 | 这次记录的数值 |
| --- | --- | --- |
| GPU 租用 | 显性、可变 | 164 美元 |
| 墙钟时间 | 显性、可变 | 54.6 小时 |
| 框架缺陷排查 | 隐性、固定 | 8 个缺陷，未量化 |
| 分词方案返工 | 隐性、固定 | 生育率 1.4 到 4.1 |
| 错误结论导致的重复实验 | 隐性、放大 | 取决于发现得早晚 |

前两行是实测值，后三行是结构性的：它们一定存在，具体金额取决于发现得早还是晚。这也是校验纪律的经济意义——把隐性开销前移成几秒的断言。

## 十、上线前检查清单

把记录整理成一份自建训练或微调的上线前清单，按执行顺序排列：

1. 数据侧：语料去重、清洗、留出评测集，并确认评测集内容没有进入训练集；
2. 分词器生育率按语言与脚本分别统计，token 占比与设计配比的偏差控制在 5% 以内；
3. 单步前向与反向冒烟：形状、dtype、数值范围全部断言通过；
4. 梯度流仲裁器：逐参数断言梯度存在、有限、非零，失败时输出参数名；
5. 随机初始化对照：同一套分词器与数据跑一次对照，确认负对数似然有量级差距；
6. 单步计时与吞吐对标：前向、反向、优化器更新分别计时，与理论吞吐的差距必须有解释；
7. 规模阶梯压测：从最小规模到目标规模，每一档至少跑若干步，覆盖 kernel 融合路径；
8. loss 分语言、分域分解，不只看全局曲线；
9. 混合精度下把数值断言放在 loss scaling 之后执行；
10. 检查点保存与恢复一致性：恢复后 loss 与梯度统计不跳变；
11. 固定提示词的生成抽检，用人工或 API 打分，并记录基线分数；
12. 预算熔断：单位时间开销与总预算告警，异常慢的跑批自动暂停。

第 2、4、6、7 项是这次记录直接对应的检查，其余从训练工程的一般经验补上。清单的价值不在于长，而在于每一项都能失败——一条永远不会失败的检查，等于没有检查。

## 十一、何时该自建、何时该走 API

记录给出的结论很克制：此后开发者转回 PyTorch 做训练，只保留 Rust 做端侧服务。Rust 目前不是有竞争力的训练场所，但可能是好的服务场所。训练吃的是生态成熟度——算子覆盖、kernel 融合、混合精度、分布式、调试工具；服务吃的是部署形态——无 GC、依赖少、二进制小、跨平台。取舍可以按几个维度判断：

| 判断维度 | 倾向自建 / 自训 | 倾向走 API |
| --- | --- | --- |
| 数据敏感度 | 数据不能出内网 | 只送抽样样本即可 |
| 任务独特性 | 通用模型明显不达标 | 通用模型已经够用 |
| 调用规模 | 量大且稳定，固定成本可摊薄 | 量小或波动大 |
| 迭代速度 | 需要改权重、改分词器、改训练目标 | 提示词与路由就能解决 |
| 团队结构 | 有专职训练工程能力 | 没有专职训练人力 |
| 延迟与部署 | 端侧、离线、极低延迟 | 可接受网络往返 |
| 成本结构 | 一次性固定投入换低边际成本 | 纯可变成本，随用随付 |

一个不需要精确数字的判断方式是看成本结构：自建把成本从可变变成固定——GPU 租用、人力，以及记录里最扎眼的那部分框架调试工时；API 保持纯可变。只有当任务独特性足够高、数据敏感度足够强、调用量足够大到摊薄固定成本，自建才可能比 API 的边际开销更划算。任何一个条件不成立，先走 API 都是更理性的默认值。

## 十二、成本与风险提示

- 算力预算：164 美元是单次小规模预训练的租用开销，按 54.6 小时折算约 3 美元每小时（估算）。把参数与 token 量放大一到两个数量级，预算会以远高于线性的速度增长（估算），小规模实验的单价不能直接外推到规模化训练；
- 框架成熟度：Candle 与 Burn 在推理与可移植部署上有清晰价值，但作为训练后端仍有缺陷记录。把「能在框架里跑通前向」当成「能当训练后端」是危险的判断，反向路径、优化器状态、kernel 融合、多十亿参数规模都要单独验证；
- 静默错误的隐性成本：反向吞吐只有理论值 3% 意味着同样的步数要多花三十多倍时间（估算）；梯度静默缺失意味着跑完的算力全部作废，而且表面上一切正常；
- 数据与合规：只使用有明确使用权限的语料，训练集与评测集的隔离要在流程上保证，不能靠人记；
- 经由中转站调用 API 时，Key 从环境变量读取、不落盘、权限最小化，并配置用量告警；只上传抽样数据，不上传整套专有语料；
- 一次成功的训练是成就，不是可复现的工程能力。把单次记录当成推荐路径，会低估框架缺陷带来的隐性工时。

## 结论

这次记录的主线是静默失败。崩溃会自己喊停，静默失败不会：融合 kernel 不产生梯度、反向传播吞吐塌陷到理论值的 3%、多十亿参数规模下融合路径段错误、字节级分词把孟加拉语的生育率压到 1.4 并反转语料配比——8 个缺陷全部通过了常规 loss 曲线检查。对应的纪律只有两条最通用：用梯度流仲裁器把「梯度应该流动」写成逐参数断言，用分词器生育率把「语料配比应该正确」写成占比断言，两者都能推广到任何框架与任何语言。再往外一层是取舍：训练栈优先成熟生态，服务栈可以用新生态；自建把成本变成固定，API 保持可变。164 美元买到的不只是一次预训练，还有一份关于框架成熟度的实测清单，这份清单比模型本身更值钱。

把数据清洗、评测集构造与生成抽检这些不需要 GPU 的环节挂到 4sapi（https://4sapi.com）上，训练侧就能只专注数值与梯度这两件事。
