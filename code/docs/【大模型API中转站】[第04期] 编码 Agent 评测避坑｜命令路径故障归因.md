# 【大模型API中转站】[第04期] 编码 Agent 评测避坑｜命令路径故障归因

编码 Agent 的端到端分数很能骗人：命令生成、序列化、包裹、二次解析、执行，任何一层出错都表现为同一个失败。

作为 4sapi 团队的接入实战记录，我沿用 56 个任务、14 个事故族的评测思路，把故障归因拆成可执行的对照实验。

## 一、开篇：分数全绿，为什么还是不敢用

给编码 Agent 做评测，最让人困惑的一幕是：**端到端分数很好看，可一进真实仓库就各种翻车**。

- 测试集上任务完成率 90%，真实项目里改个文件都失败；
- 报错信息指向"命令执行失败"，但模型明明生成了正确的命令；
- 同一个任务换台机器、换种调用方式，结果就不同。

问题不在模型，而在评测本身：**端到端的"匹配分数"把中间环节全部糊成了一团**。命令生成了吗？命令传对了吗？执行环境对吗？结果验证了吗？四件事任何一个出错，最终分数都是同一个"失败"。

这一期把编码 Agent 的"命令路径"拆开看：故障到底发生在哪一层，以及怎么评测才能定位到真正的问题。

## 二、原理速览：生成契约与执行传输

编码 Agent 的完整链路比表面看起来长得多：

```text
模型生成命令
   ↓
序列化（把模型输出转成字符串）
   ↓
包裹（加上解释器、环境变量、工作目录）
   ↓
重新解析（Shell/接口二次解析命令）
   ↓
执行
   ↓
结果返回（再被模型读取）
```

我把前半段叫作"生成契约"（模型承诺输出什么），后半段叫作"执行传输"（命令如何被真实执行）。**匹配分数只能证明两端结果一致，证明不了中间传输没出错**。

常见的中间层故障：

- 命令里含特殊字符（引号、空格、通配符），序列化时被转义或丢失；
- 包裹层插入了解释器路径，改变了命令语义；
- 二次解析把一条命令拆成了两条，或把参数拼错；
- 换行符、编码问题导致命令被截断。

## 三、故障从哪来：一次真实排查

我遇到过的最典型的例子：模型输出

```bash
grep -r "error_code" src/
```

端到端评测里这条命令"执行成功"（匹配分数通过），但真实环境里文件根本没被搜索到。排查后发现：

1. 序列化层把双引号做了转义，变成 `\"error_code\"`；
2. 包裹层又套了一层 `bash -c`，二次解析后引号语义全变；
3. 最终执行的是残缺的命令，静默失败。

**每个环节都可能"看起来没变，实际上变了"**。评测如果不盯住中间层，永远发现不了这类问题。

## 四、量化边界：56 个任务、14 个事故族

为了把这个问题量化，我参考了一套面向命令路径的评测方法，核心设计值得直接抄：

- **56 个一次性任务**，来自 14 个事故衍生族（每个族对应一类真实事故）；
- 每个任务做**精确的最终状态校验**（不只看命令退出码，还要验证文件、环境、结果）；
- 在"生成契约"与"执行传输"的边界上故意设置一个未转义的解析器，制造可控的故障注入点；
- 在插值点做转义，能复现原始命令的路径结果——从而区分"命令生成错误"和"执行链路引入的错误"。

```text
故障注入设计：
任务 -> 生成契约（模型输出命令）
    -> 边界点（故意不转义的特殊字符）
    -> 执行传输（Shell 二次解析）
    -> 最终状态校验（文件/环境/结果）

对照实验：边界点转义后重跑
    -> 若结果恢复，故障在执行传输层
    -> 若结果仍错，故障在命令生成层
```

这套方法的精髓是**对照实验**：同一任务跑两次，一次在边界点转义、一次不转义，就能把故障层定位出来。

## 五、Python 示例：带中间层断言的评测脚本

我把这套思路落成一个可复用的评测脚本：

```python
import subprocess
import tempfile
import pathlib

class CommandPathEval:
    def __init__(self, escape_boundary: bool):
        self.escape_boundary = escape_boundary

    def run(self, raw_command: str, workdir: str) -> dict:
        # ① 序列化层：是否对边界字符做转义（对照组开关）
        cmd = raw_command
        if self.escape_boundary and '"' in cmd:
            cmd = cmd.replace('"', '\\"')

        # ② 包裹层：固定解释器与工作目录
        full = f"bash -c {cmd}"

        # ③ 执行 + 最终状态校验
        result = subprocess.run(
            full, shell=True, cwd=workdir, capture_output=True, text=True, timeout=30
        )
        return {
            "exit_code": result.returncode,
            "stdout": result.stdout,
            "stderr": result.stderr,
            "state_ok": self.check_final_state(workdir),
        }

    def check_final_state(self, workdir: str) -> bool:
        # 精确校验：目标文件是否真的生成且内容正确
        target = pathlib.Path(workdir) / "output.txt"
        return target.exists() and "done" in target.read_text(encoding="utf-8")


def locate_failure_layer(raw_command: str, workdir: str):
    with_escape = CommandPathEval(escape_boundary=True).run(raw_command, workdir)
    without_escape = CommandPathEval(escape_boundary=False).run(raw_command, workdir)

    if with_escape["state_ok"] and not without_escape["state_ok"]:
        return "执行传输层（边界转义导致）"
    if not with_escape["state_ok"] and not without_escape["state_ok"]:
        return "命令生成层（模型输出本身错误）"
    return "无故障（两层均正常）"
```

关键点：**只看 `exit_code` 不算数，必须做最终状态校验**。退出码为 0 的文件可能是空文件，状态校验才能发现。

## 六、评测集怎么建

参考 14 个事故族的思路，我按下面几类建评测集：

| 事故族 | 任务示例 | 关注点 |
| --- | --- | --- |
| 引号/转义 | 删除含空格的文件 | 序列化与二次解析 |
| 通配符 | 批量重命名 `*.tmp` | 包裹层语义 |
| 环境变量 | 使用未导出的变量 | 执行环境 |
| 编码 | 处理中文文件名 | 编码转换 |
| 幂等 | 重复执行同一命令 | 状态一致性 |
| 超时 | 卡住的进程 | 资源限制 |

每类任务都要配"转义/不转义"对照，才能区分故障层。

## 七、接入评测的注意点

评测编码 Agent 时，接入层同样会引入干扰：

- **同一个模型换接入端点，命令输出可能不同**（上下文长度、系统提示差异）；
- 中转网关的**超时与重试策略**会影响命令执行结果；
- 请求格式（OpenAI 兼容 vs 原生格式）可能改变模型的输出风格。

我的做法：评测时固定接入方式，跑基线模型在同一网关（https://4sapi.com）上的输出作为参照，再对比不同模型的表现——**先统一接入变量，再比较模型变量**。

## 八、评测清单

上线编码 Agent 前，至少跑：

1. 每个任务都做最终状态校验，不只查退出码；
2. 每个事故族至少 4 个任务（56 任务/14 族）；
3. 边界点转义对照实验，定位故障层；
4. 同一任务重复 3 次，记录失败率（模型有随机性）；
5. 固定接入端点与超时策略，消除接入干扰；
6. 失败样本单独归类：命令生成 vs 执行传输。

## 九、避坑提示

- **别信端到端匹配分数**：它证明不了中间层没出错；
- **别只测成功路径**：故障注入（特殊字符、超时、断网）才能暴露传输层问题；
- **别把失败全归咎模型**：先做对照实验，可能问题在序列化或包裹层；
- **别忽略静默失败**：命令返回 0 但什么都没做，是最难查的故障。

## 十、容错与重试设计

定位到故障层之后，容错策略也不同：

```text
命令生成层故障 -> 换模型 / 换提示词 / 提高采样次数
执行传输层故障 -> 修序列化与转义 / 换包裹方式 / 加校验重试
环境类故障     -> 固定环境镜像 / 预检依赖 / 沙箱重建
```

重试必须配合最终状态校验：**只有状态校验失败才重试，重试前重置环境**，避免在脏状态上反复执行。

## 总结

编码 Agent 评测的核心方法论：**把"生成契约"和"执行传输"分开看，用对照实验定位故障层，用最终状态校验代替退出码**。56 个任务、14 个事故族的量化边界说明，中间层的坑比想象中多，但每类坑都有对应的归因方法。
