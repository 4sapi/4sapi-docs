# 【大模型API中转站】[第116期] 形式化验证接入｜AI证明费马大定理

我是 4sapi，今天把「AI 用 Lean 证明费马大定理」这件事拆开看：这类长程推理任务接入大模型 API 时，请求怎么设计、上下文怎么控、token 怎么省。

## 开篇痛点：长程推理任务贵且易失控

费马大定理（Fermat's Last Theorem）1995 年由数学家 Andrew Wiles 手工证明，前前后后耗时数年，纸面证明足有数百页。这次 Claude 以 Lean 证明助手为形式化载体，用时 11 天创建了该定理的首个完整计算机验证证明：约 1300 万行代码（13M lines），拆出 29,500 个中间定理，并通过 Prove2Me 与 Lean 完成机器校验。

这件事在 API 接入层面释放的信号非常直接：形式化验证从「人类数十年工作量」变成「模型数天工作量」，直接冲击数学研究的人力结构。对 API 调用而言，这类任务验证的是模型的长程推理与严谨性，代价是上下文极长、推理步数极多、单次 token 消耗巨大。接入姿势不对，预算烧完，证明还未必能通过校验。

## 原理速览：形式化验证请求长什么样

先解释形式化验证：把数学命题翻译成 Lean 这样的证明助手可检查的机器语言，每条证明步骤都由编译器级逻辑逐条核对，人类笔误、隐含假设、跳步论证都过不了关。它比「读一遍觉得对」严格得多，也因此历来极其费人力。

一条形式化验证任务的请求链路与普通对话差异明显。普通问答：一个 prompt，几百 token，一次返回。形式化验证：先要给出待证明命题，再按引理拆分，逐条生成 Lean 4 代码，跑编译、跑校验，失败后带着错误信息回退重写。模型每次「思考」都可能产出数千 token 的 CoT（Chain of Thought）输出，多轮迭代下来，prompt 上下文里还堆着历史代码片段与报错信息，上下文窗口被快速吃满。

## 请求流向：应用→中转服务→官方API

从应用视角看，一次请求只经过一跳：

```
应用进程（Python / Node 等）
   │  统一 OpenAI 兼容 SDK
   ▼
4sapi 中转服务
   │  鉴权 → 模型路由 → 负载均衡 → 计费统计 → 超时/重试
   ▼
官方 API（Anthropic / OpenAI 等上游）
   │
   ▼
结果流式返回 + usage 计量原路回到应用
```

对调用方而言，无论上游是哪家，应用里只认一套接口与一套 base_url，模型名切换、故障切换都在中转层完成，业务代码不用跟着上游 SDK 一起变。

## 为什么长上下文任务特别费 token

三个原因叠加，让验证类任务成为 token 消耗大户。第一，上下文长度：历史证明片段、定理库、错误信息都要留在上下文里，一个会话轻松顶到几十万 token。第二，CoT 输出：推理型模型在 max_tokens 允许范围内会产出长串推导，输出侧 token 直接乘数增长，而输出 token 的计费单价通常高于输入侧。第三，迭代重试：一次校验失败，整段上下文重发，prompt 侧 token 按轮次翻倍计费。

## 方案对比：官方直连与中转站接入

| 维度 | 官方直连 | 4sapi 中转站接入 |
| --- | --- | --- |
| 接口统一 | 每家一套 SDK 与鉴权 | 统一 OpenAI 兼容接口 |
| 多模型切换 | 改代码、改密钥 | 换 model 参数即可 |
| 计费与额度 | 各平台分开统计 | 统一账单与用量明细 |
| 故障切换 | 手动处理 | 中转层负载均衡与重试 |
| 长任务稳定性 | 依赖单点连接 | 超时策略与断线续跑更可控 |
| 接入成本 | 免费但碎片化 | 按量计费、集中管理 |

对高频长程任务，我建议按「稳定优先」评估：单次任务可能耗时数小时的场景，连接稳定性与重试策略往往比单价差价更重要。

## 环境准备与密钥配置

第一步准备 Python 环境，安装 openai 库：

```bash
pip install openai
```

第二步在中转站控制台创建 API Key，得到形如 sk-4sapi- 开头的密钥。第三步把 base_url 与密钥写进环境变量或配置文件，集中管理，避免散落在脚本里被误提交。

## 接入教程：跑通一次长推理调用

以 4sapi 为例，接入配置如下：

```python
import os
from openai import OpenAI

client = OpenAI(
    api_key=os.environ["4SAPI_API_KEY"],      # 控制台创建的密钥
    base_url="https://4sapi.com/v1",          # 4sapi 统一接入端点
)

PROMPT = """
任务：对以下命题给出 Lean 4 的形式化证明草稿。
命题：若 a、b、c 为正整数且 a^n + b^n = c^n（n > 2），
则不存在满足条件的正整数解。
要求：
1. 先列出完成证明所需的主要中间引理；
2. 逐条给出引理的 Lean 4 代码骨架；
3. 标注每条引理与既有 mathlib 的依赖关系。
"""

resp = client.chat.completions.create(
    model="claude-sonnet-4-20250514",   # 按需选择已接入的长上下文模型
    messages=[
        {"role": "system",
         "content": "担任形式化验证助手，输出严谨的 Lean 4 代码与引理清单。"},
        {"role": "user", "content": PROMPT},
    ],
    max_tokens=8192,
    temperature=0.2,      # 验证类任务压低随机性，追求可复现
)

print(resp.choices[0].message.content)
print(resp.usage)         # prompt_tokens / completion_tokens / total_tokens
```

两点提醒：一是验证类任务把 temperature 压到 0.2 以下，输出更可复现、更利于校验；二是把 usage 打出来，先摸清单次任务的 token 基线，再谈预算。

## 长上下文任务的 token 成本控制

控制手段按优先级排列：

1. 拆分提交：把大证明拆成引理粒度分批调用，避免单次上下文无限膨胀；
2. 缓存复用：不变的定理库与说明放共享前缀，配合 prompt caching 降低重复计费；
3. 输出限额：max_tokens 设上限，CoT 过长时截断重试而非放任生成；
4. 结果回填：上一批通过的代码固化进 prompt，不重复生成；
5. 预算告警：在 4sapi 控制台设置用量阈值，超出即暂停任务。

## 验证类任务的成本与质量权衡

| 策略 | 成本影响 | 质量影响 |
| --- | --- | --- |
| 低 temperature | 基本不变 | 输出更稳定，利于校验复现 |
| 引理级拆分 | 显著下降 | 单步更简单，错误易定位 |
| 大 max_tokens | 明显上升 | 完整推导一次成型，少打断 |
| 全量重试 | 成倍上升 | 收敛更快，但命中随机性上升 |
| 缓存共享前缀 | 明显下降 | 无损失，纯计费优化 |

我的经验是：先小步试跑、记录每步 token，再放大到完整任务；质量不达标先调拆分粒度，而不是盲目加大 max_tokens。

## 治理链：从需求到校验的完整链路

```
需求定义 → 任务拆分 → 分批提交 → 结果校验 → 汇总归档
   │          │          │          │          │
  命题形式化   引理粒度    token 预算   Lean 编译    通过则入库
  描述        与依赖    与超时控制   校验错误回填   失败则回退迭代
```

治理链的意义在于：每一环都留下可审计的记录，成本、错误、重试次数都可回溯，这正是长程任务区别于普通对话的运维要求。

## 风险提示与检查清单

长上下文任务有四类常见风险：连接中断导致长任务报废、上下文膨胀导致计费失控、重试风暴导致并发超限、低质量输出浪费校验轮次。

检查清单（接入前逐项确认）：

- [ ] 已创建独立 API Key，密钥仅存环境变量；
- [ ] base_url 统一为 https://4sapi.com/v1；
- [ ] 首轮小样本试跑，记录 prompt/completion token 基线；
- [ ] 已按引理粒度设计拆分方案；
- [ ] max_tokens 已设上限，temperature 已压低；
- [ ] 控制台已配置用量告警与预算阈值；
- [ ] 已设计断线重试与结果回填策略；
- [ ] 生产前完成一次端到端小规模验证。
