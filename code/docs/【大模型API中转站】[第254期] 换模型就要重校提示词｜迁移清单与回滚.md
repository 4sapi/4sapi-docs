# 【大模型API中转站】[第254期] 换模型就要重校提示词｜迁移清单与回滚

升级模型版本时，最容易被低估的工作不是改配置，而是让提示词重新对齐。

同一段提示词在两个版本上的表现并不一致：输出格式的严格程度、拒绝的触发边界、推理深度的默认档位、甚至对同一句约束的理解侧重都可能变化。官方会随模型版本发布专门的提示词指南，覆盖 effort 校准、无人值守运行、安全拒绝、进度更新、多应用工作流等场景——**这份指南存在本身，就是"提示词不是可移植资产"的证明**。我在 4sapi（https://4sapi.com）上做版本迁移时，把它当成一次需要回归测试的变更来处理。

## 一、为什么提示词会随版本失效

提示词与模型之间是一种隐含的契约：模型在训练与对齐过程中形成了对某些表述方式的行为倾向，提示词则依赖这些倾向来生效。

版本迭代会改变这些倾向。三处最常见的漂移来源：

**一是对齐目标的调整。** 新版本在安全拒绝、语气、主动性上的训练目标可能变化，导致原先"写一句就管用"的约束需要更明确的表述。

**二是推理深度的默认值变化。** 新版本可能默认投入更多或更少的推理步骤，于是同一个提示词在不同版本上的延迟与成本都不同。

**三是表述理解的变化。** 同一句"只输出 JSON"，两个版本对"只"的执行严格程度可能不同。

这三处都不是 bug，而是正常迭代的副产品。但对依赖提示词精确行为的系统来说，它们的净效果就是**行为漂移**。

值得强调的是漂移的**方向不可预测**。同一个新版本，在格式遵循上可能更严格（原先靠约束兜住的问题消失了），同时在拒绝边界上可能更宽松（原先拒掉的请求现在会执行）。所以"升级后感觉更好了"这种主观印象完全不能替代验证——两种方向的变化可以同时存在，只在部分任务上互相抵消。

## 二、用"合同"的视角看提示词

我在迁移时用的是一个比较硬的视角：把提示词当成接口契约，把模型当成实现。

按这个视角，每一条提示词约束都对应一条可验证的断言。比如：

```text
提示词约束                      对应断言
--------------------------------  ----------------------------------
"只输出 JSON"                   输出可被 json.loads 解析
"不超过 200 字"                 输出汉字数 <= 200
"不解释过程"                    输出不含推理段落标记
"遇到敏感请求要拒绝"            敏感样本集上的拒绝率 >= 阈值
"进度更新不超过每 5 轮一次"     进度消息数量 <= 轮数 / 5
```

只有把约束变成断言，版本迁移才有验收标准。否则"提示词还能用"只能靠肉眼观察，而肉眼观察对概率性行为几乎无效。

这个视角还带来一个额外好处：**断言本身就是一份提示词文档**。新人接手时，看断言清单比读几千字的提示词更容易理解系统到底依赖哪些行为保证。当某条断言长期没有失效时，它也在提示这条约束可能是多余的——这与前面提到的"优先删除"是同一件事的两个触发点。

## 三、迁移前的行为基线

迁移的第一步不是改提示词，而是**把当前版本的行为记录下来**。

基线需要覆盖三类样本：**主流程样本**（日常任务，验证基本功能不退化）、**边界样本**（参数缺失、超长输入、格式异常，验证健壮性）、以及**对抗样本**（诱导越界、要求越权、注入式内容，验证约束边界）。

我在基线里会固定记录四类数据：输出内容、是否通过各条断言、token 用量、响应延迟。后两项虽然与提示词无直接关系，但版本迁移常常同时改变它们，需要一并观测。

```text
基线采集（旧版本）
    |
    v
[主流程样本] [边界样本] [对抗样本]
    |
    +-- 输出内容 + 断言结果 + token 用量 + 延迟
    |
    v
固化为回归集（版本化，与提示词版本一同归档）
```

样本量的分配上有个取舍。对抗样本的**单条信息量**最高（一条就能暴露拒绝边界的移动），但它的覆盖面窄；主流程样本覆盖面广但单条信息量低。我的配比大约是主流程占一半、边界与对抗各占四分之一，并保证每一类里都包含该类型下最极端的用例——极长输入、完全空输入、以及看起来像正常业务实则越界的请求。

## 四、effort 校准：先定成本再调表述

effort 参数（或等价的推理深度档位）是迁移时最先要定下来的东西，因为它直接决定成本量级。

同一段提示词在不同 effort 档位下的表现差异，往往大于提示词本身的调整空间。所以顺序应当是：**先按任务的成本容忍度选定 effort 档位，再在该档位上校准提示词**，而不是反过来。

一个常见的错误是沿用旧版本的 effort 设置。新版本在相同档位下的推理深度可能更大，成本随之上升；也可能更小，导致质量下降。两种情况都会让"只是升级了版本"变成一次未预期的成本或质量变化。

我的做法是为每个任务类型记录"effort 档位 / 质量指标 / 每任务成本"三元组，迁移后重测一次，确认三者关系仍可接受。

这里还有一个容易忽略的细节：**effort 与提示词存在交互**。当提示词的约束写得更明确时，模型在较低 effort 下也能稳定遵守；反过来，含糊的提示词往往需要更高 effort 才能收敛。这意味着清理提示词之后，有可能顺带把 effort 档位也降下来——两项收益叠加，是迁移中最值得主动去找的机会。

## 五、六类高风险提示词模式

不是所有提示词都同样脆弱。按我的经验，以下六类在版本迁移时最容易失效，需要优先重校：

| 模式 | 为什么脆弱 | 迁移时的检查方式 |
| --- | --- | --- |
| 纯否定式约束（"不要…"） | 新版本对否定的执行力度可能不同 | 换成正面描述后对比效果 |
| 格式硬约束（"必须输出…"） | 格式遵循的严格程度会变 | 用解析器验证而非肉眼 |
| 隐性长度控制（"简要"） | 对"简要"的默认理解会变 | 统计输出长度的分布 |
| 依赖旧版本怪癖的绕行写法 | 怪癖本身可能被修掉 | 直接删掉，看是否仍有必要 |
| 针对旧版本防护的加固句 | 防护对象已不存在，只剩干扰 | 逐条评估能否删除 |
| 拒绝边界的诱导式说明 | 拒绝策略变化会让诱导失效 | 用对抗样本重测拒绝率 |

其中第五类最值得主动清理：为旧版本的某个具体问题写的加固句，在新版本上通常已经没有作用，但它占据了系统提示词的篇幅，还会给模型带来额外的解释负担。**每次版本迁移都是一次清理提示词的机会**，而不是只做加法。

## 六、按场景迁移的检查清单

官方指南列出的场景本身就是一份检查清单。逐个对照：

**无人值守运行**：长时程任务在无人监督下会持续消耗资源，需要确认新版本在缺少人工反馈时的行为是否仍然收敛，以及进度更新的频率是否合适——过密会推高成本，过疏则无法判断任务是否卡住。

**安全拒绝**：拒绝的触发边界可能扩大或收窄。扩大意味着正常的业务请求被误拒，收窄意味着该拒的没拒。两个方向都要用对抗样本测。

**进度更新**：如果任务依赖模型主动报告进度，需要重新校准报告频率与内容粒度。

**多应用工作流**：跨应用的上下文传递在新版本上可能需要调整格式，尤其是在工具返回结构的处理上。

**视觉输入**：如果链路涉及图片，新版本对图像分辨率、长宽比、多图顺序的处理都可能不同。

**结构化输出**：这是最需要机器校验的一项，任何肉眼判断都不可靠。

## 七、对照回归脚本

下面这段脚本对两个版本跑同一批样本，逐条比对断言结果与成本，用于判断迁移是否引入退化。

```python
import os, json, time
from openai import OpenAI

client = OpenAI(
    api_key=os.getenv("FOURSAPI_API_KEY"),
    base_url="https://4sapi.com/v1",
)

OLD = os.getenv("MODEL_OLD", "claude-opus-5")
NEW = os.getenv("MODEL_NEW", "claude-opus-5-5")
EFFORT = os.getenv("EFFORT", "high")

CHECKS = {   # 断言：名称 -> 判定函数（返回 True 表示通过）
    "json_parsable": lambda out: _try_json(out),
    "under_200_han": lambda out: len([c for c in out if "\u4e00" <= c <= "\u9fff"]) <= 200,
    "no_reasoning_block": lambda out: "思考：" not in out and "推理：" not in out,
}


def _try_json(out):
    try:
        json.loads(out.strip().strip("`").removeprefix("json").strip())
        return True
    except Exception:
        return False


def run_one(model, system, user):
    t0 = time.perf_counter()
    r = client.chat.completions.create(
        model=model, temperature=0,
        messages=[{"role": "system", "content": system},
                  {"role": "user", "content": user}],
    )
    out = r.choices[0].message.content or ""
    return {
        "out": out,
        "checks": {k: bool(f(out)) for k, f in CHECKS.items()},
        "tokens": r.usage.total_tokens,
        "ms": int((time.perf_counter() - t0) * 1000),
    }


def compare(samples, system):
    rows = []
    for s in samples:
        a = run_one(OLD, system, s["prompt"])
        b = run_one(NEW, system, s["prompt"])
        diff = [k for k in CHECKS if a["checks"][k] != b["checks"][k]]
        rows.append({
            "bucket": s["bucket"],
            "prompt": s["prompt"][:40],
            "regressed": diff,
            "old_tokens": a["tokens"], "new_tokens": b["tokens"],
            "old_ms": a["ms"], "new_ms": b["ms"],
        })
    return rows


if __name__ == "__main__":
    with open(os.getenv("SAMPLES", "./migration_samples.json"), encoding="utf-8") as f:
        samples = json.load(f)
    system = open(os.getenv("SYSTEM_PROMPT", "./system_prompt.txt"), encoding="utf-8").read()

    rows = compare(samples, system)
    bad = [r for r in rows if r["regressed"]]
    print(f"样本 {len(rows)}，退化 {len(bad)}")
    for r in bad:
        print(f"  [{r['bucket']}] {r['prompt']} -> 退化项 {r['regressed']}")
    tok_old = sum(r["old_tokens"] for r in rows)
    tok_new = sum(r["new_tokens"] for r in rows)
    print(f"token 变化: {tok_old} -> {tok_new} ({(tok_new - tok_old) / tok_old:+.1%})")
```

两个输出最有用：退化清单直接说明哪些断言在新版本上不成立，token 变化率则说明**同一段提示词在两个版本上的开销差**。后者常被忽略，但它决定了迁移是否需要重新做预算。

## 八、迁移的顺序

把上面的环节串起来，迁移顺序是：

1. 用旧版本采集基线，固化为版本化的回归集；
2. 按成本容忍度选定新版本的 effort 档位；
3. 逐条评估现有提示词约束，**优先删除而非新增**；
4. 跑对照回归，看退化清单；
5. 针对退化项做最小改动，不要顺手重写整段提示词；
6. 记录新版本的 token 与延迟画像，更新预算；
7. 保留回滚开关，灰度观察后再全量。

第四步和第五步的顺序很关键：**先看完全部退化项，再决定改哪里**。逐项试改容易陷入局部最优，把一个断言改好了，另一个被连带破坏。一次改完再回归，能一次看清整体变化。

## 九、回滚设计

迁移必须可回滚。做法上没什么特殊：把模型名、effort 档位、系统提示词版本三样做成一组版本化的配置，切换时整体生效。

需要注意两点。**一是提示词与模型的绑定关系**：如果把提示词存成全局常量、模型名存在环境变量里，回滚模型时会用到不匹配的提示词。两者必须打包成同一个版本单元。**二是灰度粒度**：按请求比例灰度会让同一份提示词在两个模型上并行生效，如果提示词是为其中一个校准的，另一个的表现会失真。更稳的做法是按**任务类型或租户**灰度，让每个灰度单元内部保持自洽。

## 十、成本与风险提示

- **迁移的成本不只是算力**，重校提示词、重跑回归、灰度观察都是人力投入，排期时要算进去。
- **token 画像会变**。同一段提示词在新版本上的用量可能显著不同，预算需要同步更新，而不是沿用旧值。
- **不要在迁移的同时改业务逻辑**。两处变更叠在一起，出问题时无法区分原因。
- **回归集要版本化**。提示词、模型、样本集三者必须能对应到同一次发布，否则事后无法复现任何结论。
- **清理旧加固句时要有依据**。删掉一条约束前，先在回归集上验证删掉之后没有退化——凭直觉判断"这句应该没用了"并不足够。

## 结论

提示词不是跨版本的可移植资产，这一点由官方随发布提供迁移指南就能看出来。把它当成接口契约来处理，迁移就变成一次有验收标准的变更：先把现有约束变成可验证的断言，用旧版本采基线，按成本选 effort，优先删除而不是新增，跑对照回归，再灰度切换。这套流程的收益不只是"迁移不出错"，还包括每次迁移都顺手清掉一批为旧版本写的加固句——我在 4sapi.com 上按这个顺序做完一次迁移之后，系统提示词比迁移前还短了一截，而质量没有下降。
