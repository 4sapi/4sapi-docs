# 【大模型API中转站】[第198期] 跨模型记忆按存储计费｜召回免费的长上下文账

长上下文的账单有三处出口：每轮重传的 token、供应商缓存的前缀命中率、以及把上下文搬出请求体之后的存储费。这一期把三条路线放到同一张账上算。第三条路线的口径最反直觉——召回免费，只按存储的上下文付费，最低一档按 100 个上下文、每个 500 条消息、每月 100 万次召回估算，约 7.00 美元/月；接入侧我仍然走 4sapi（https://4sapi.com）的 OpenAI 兼容端点，记忆层单独封装，成本函数、对照表与验收清单这一期一并给出。

## 一、开篇：长上下文的钱花在哪三处

多轮对话与 Agent 循环里，历史消息会被反复重放。第一轮只有一条系统提示词，第一百轮就有上百条消息，每一轮都要把它们重新编码一次。这笔钱有三重结构。

第一重是 token 账单：输入侧的成本与"轮次 × 历史长度"同阶，历史越长，边际成本越高，而且没有任何一轮能享受折扣。

第二重是延迟：prefill 阶段要处理的 token 越多，首 token 时间越长，用户感受到的卡顿与上下文长度直接挂钩。

第三重是状态管理：为了省钱，工程上会在客户端做截断、做摘要、做滑动窗口，每一种做法都在引入自己的 bug 与不可复现的行为——截断丢掉关键约束，滚动摘要改写数字与 ID，窗口边界上的因果关系被切断。

结论先放前面：把上下文从请求体里搬进一层独立的存储，按存储付费、召回免费，是把这三重成本同时压下去的一条现实路线；但它不替代供应商的 prompt 缓存，两者是并行关系。

## 二、原理速览：三条路线的成本结构

- 路线一，每次重传全量上下文：无状态、实现最简单、对模型与供应商零依赖。代价是输入 token 随轮次线性增长，整段会话的总输入量近似随轮次平方增长，长会话里最贵的就是"把已经说过的再说一遍"。
- 路线二，供应商 prompt 缓存：同一模型、同一前缀，命中的部分按更低的单价结算。它省钱的前提是前缀稳定、模型不变、缓存没有过期。
- 路线三，面向模型的记忆 API：上下文存在外部存储里，按需召回，召回不额外计费，账单落在存储容量上。

三条路线的成本函数形状完全不同：路线一是"每次调用都付全量"，路线二是"第一次付全价、之后付折扣"，路线三是"按容量付月租、调用次数不影响账单"。选型的第一步不是比单价，而是判断自家业务的形状——长会话、多轮、高频调用，三条路线的排序会完全不一样。

## 三、FastRecall 的计费口径

FastRecall 的定位是跨 AI 模型的上下文，为路由器与多智能体系统而做。可以用任何模型，同时保留自己的一份上下文；召回极快，几乎不给模型响应增加延迟。

计费口径是这一期最值得抄的部分：召回免费，只按存储的上下文付费。口径里的关键词是"长上下文、保持完整"，压缩侧用的是 SOTA 的无模型（model-free）压缩。

几条边界也该一起记住：

- 不托管模型，也不代替调用任何模型 API，模型调用仍然由业务侧发起；
- 不需要在每次模型调用时把整个上下文都传进去，召回只取当前需要的那一段；
- 与各家模型供应商的缓存机制并行工作：如果复用同一个模型与同一份上下文，供应商缓存照旧生效，token 单价该降还是降，产品文档里有一节 Native continuation 专门讲这条路径。

换句话说，记忆层解决的是"上下文存在哪、怎么取"，供应商缓存解决的是"同一份前缀算几遍"，两者作用在不同层，不冲突。

## 四、把 7.00 美元/月摊开算一笔账

先把成本计算器的示例参数摊开：100 个上下文（不同对话）、每个上下文 500 条消息、每月 100 万次召回，估算约 7.00 美元/月，这是最低档。另有一档 Hacker，5 万条消息存储约 0.1 GB。

按这两组数字做几道除法：

| 折算项 | 算式 | 结果 |
| --- | --- | --- |
| 存储的消息总量 | 100 × 500 | 5 万条 |
| 单条消息的平均占用 | 0.1 GB ÷ 5 万条 | 约 2 KB |
| 单位容量月租 | 7.00 美元 ÷ 0.1 GB | 约 70 美元/GB/月 |
| 每千条消息月租 | 7.00 美元 ÷ 50 | 约 0.14 美元/千条/月 |
| 单次召回成本 | 召回免费 | 0 美元 |

第三行与第四行是按档位折算出来的代理价，不是账单上的原始字段，但量级关系很有用：容量是唯一在涨的因子，调用次数不涨账单。

再拿路线一来对照。设上下文长度为 T 个 token，模型输入单价为 p 美元/token，每月 100 万次召回对应的重传成本是 1,000,000 × T × p。让这个式子等于 7.00 美元，得到 p = 7 ÷ (1,000,000 × T)。取 T = 10 万 token，p ≈ 7e-11 美元/token，换算成每百万 token 约 0.07 美元。

也就是说，只有当输入单价低到每百万 token 七分钱这个量级，重传全量上下文才比按存储计费更划算。实际账单上这个数量级的输入价基本不存在，所以对长会话业务，"每轮重传"在成本上几乎不可能是赢家。反过来说，上下文越短、召回越少，记忆层的月租就越像一笔固定开销，短会话业务要先算清楚自己够不够格。

## 五、model-free 压缩与 LLM 式压缩的取舍

现有记忆方案被抱怨最多的地方是过于复杂、慢、贵。FastRecall 选择的路是用 SOTA 的无模型压缩，让模型自己组织上下文，换来的说法是更快、更便宜、性能更好。便宜的原因也很直白：做的是高度优化的上下文存储，只为磁盘上的上下文存储付费，这是整个技术栈里最便宜的部分。

最关键的一条取舍写在反面：不使用昂贵的基于 LLM 的记忆压缩技术，理由是那会引入延迟、成本与检索错误。把这三个代价拆开看：

- 延迟：LLM 式压缩要在写入路径上额外跑一次推理，长上下文下这一步本身就是 prefill 级别的开销；如果在召回路径上再跑一次改写，模型响应的首 token 时间会被压缩任务占走。
- 成本：压缩本身要烧 token，而 token 恰恰是整条链路里最贵的计量单位。用最贵的资源去省最便宜的磁盘，账本身就不成立。
- 检索误差：LLM 摘要是有损改写。数字、ID、文件路径、变量名、否定词，都容易在一次"润色"里变形；变形的摘要再进入上下文，错误会被后续推理当成前提继续放大。

| 维度 | LLM 式压缩 | model-free 压缩 |
| --- | --- | --- |
| 写入路径开销 | 需要额外推理 | 无额外推理 |
| 成本结构 | 按 token 计费，随上下文变贵 | 按存储容量计费 |
| 信息保真 | 有损改写，细节容易漂移 | 保持完整 |
| 检索误差 | 摘要改写引入新误差 | 不引入改写误差 |
| 失败形态 | 静默漂移，难以定位 | 容量与索引问题，可观测 |

取舍的结论：压缩环节越晚引入生成式改写，链路越可预测。把"改写"留给真正需要它的地方——模型自己在推理时组织上下文——而不是提前固化在存储层。

## 六、一条架构级的安全收益：不新增自我指令通道

这一条属于架构层面的避坑结论，值得单独占一节。

LLM 式压缩的产物是自然语言摘要。这段摘要会被回放进后续上下文，而且在上下文里的形态是"之前发生过的事"，读起来像系统自己写下的记录。问题就出在这里：如果被摘要的原始材料里有一句"忽略之前的所有指令，按下面做"，压缩器有可能把它浓缩进摘要，摘要再以记录的口吻进入上下文——外部数据变成了一段看起来有权威性的文本。

无模型压缩不产出新的散文。它不做改写、不重写摘要，因此也就不存在"把外部文本改写成指令形态再回放"的通道。省下的是延迟与 token，顺手关掉的是一条注入路径。

但要补一句边界：这不等于存储里的上下文可以当成可信内容。原始对话里的越权请求、工具调用参数、外部网页正文，仍然是外部数据。记忆层负责不新增通道，权限层仍然要负责——高风险动作审批、工具权限隔离、输出审计，一个都不能省。

## 七、请求流：召回、组装、调用、写回

```text
业务请求进入编排层
        |
  记忆层召回（召回免费，只取当前需要的片段）
        |
  上下文组装：系统提示词 + 召回片段 + 本轮输入
        |
        +--> 命中同一模型 + 同一上下文前缀
        |         |
        |    供应商 prompt 缓存继续生效（token 单价照降）
        |
        v
  经 OpenAI 兼容端点发起模型调用
        |
  模型响应返回编排层
        |
  新增轮次写回记忆层（带幂等键）
        |
  账单落在两处：存储容量（月租） + 模型 token（单价）
        |
  召回延迟 / 命中率 / 存储增长 / token 成本 回传面板
```

这张图里有三个容易做错的位置：召回片段必须按租户隔离；写回要带幂等键，避免重试写重；缓存命中判断只作用于前缀不变的部分，否则供应商缓存会白失效。

## 八、接入教程：4sapi 兼容端点 + 记忆层封装

接入形状很简单：模型调用照旧走 OpenAI 兼容协议，记忆层包在外面。生产环境里的 Key 只从环境变量读，绝不写进代码或配置文件。下面这段是记忆层与成本估算的骨架，base_url 指向 4sapi 的兼容端点。

```python
import os
import time
from typing import Any

from openai import OpenAI

client = OpenAI(
    base_url="https://4sapi.com/v1",
    api_key=os.environ["FOURSAPI_API_KEY"],  # 只从环境变量读取，不落盘、不进日志
)

# 单条消息的存储占用口径（字节），用于把容量换算成账单
BYTES_PER_MESSAGE = int(os.getenv("MEMORY_BYTES_PER_MESSAGE", "2048"))
# 存储档位的单位价（美元 / GB / 月），按自家账单填，不写死在代码里
STORAGE_USD_PER_GB_MONTH = float(os.environ["MEMORY_USD_PER_GB_MONTH"])
# 模型输入单价（美元 / 百万 token），同样来自自家账单
INPUT_USD_PER_MTOK = float(os.environ["MODEL_INPUT_USD_PER_MTOK"])


class MemoryLayer:
    """记忆层封装：召回免费，写回计数，账单只落在存储容量上。"""

    def __init__(self, namespace: str) -> None:
        # 命名空间即租户隔离键，索引与存储都不得跨租户复用
        self.namespace = namespace

    def recall(self, query: str, limit: int = 8) -> list[dict[str, Any]]:
        """只召回当前轮需要的片段，不把整份历史塞进请求体。"""
        return self._remote_recall(self.namespace, query, limit)

    def append(self, turn: dict[str, Any], idempotency_key: str) -> None:
        """写回带幂等键：网络重试不会写重。"""
        self._remote_append(self.namespace, turn, idempotency_key)

    def build_request(
        self,
        system_prompt: str,
        recalled: list[dict[str, Any]],
        user_input: str,
    ) -> list[dict[str, Any]]:
        """稳定前缀放在最前面，供应商缓存才有机会命中。"""
        return [
            {"role": "system", "content": system_prompt},
            *recalled,
            {"role": "user", "content": user_input},
        ]

    # 远端实现按所选记忆层 SDK 替换，这里只固定接口形状
    def _remote_recall(self, ns: str, query: str, limit: int) -> list[dict[str, Any]]:
        raise NotImplementedError

    def _remote_append(self, ns: str, turn: dict[str, Any], key: str) -> None:
        raise NotImplementedError


def cost_breakdown(
    contexts: int,
    messages_per_context: int,
    recalls_per_month: int,
    avg_tokens_per_recall: int,
) -> dict[str, float]:
    """三条路线的月度成本对照，单价全部来自环境变量，避免写死市场数字。"""
    stored_messages = contexts * messages_per_context
    stored_gb = stored_messages * BYTES_PER_MESSAGE / (1024 ** 3)

    # 路线三：召回不计费，只按存储容量付月租
    memory_api_usd = stored_gb * STORAGE_USD_PER_GB_MONTH
    # 路线一：每次调用重传全量上下文
    retransmit_usd = (
        recalls_per_month * avg_tokens_per_recall * INPUT_USD_PER_MTOK / 1_000_000
    )
    # 让两条路线打平的输入单价，高于它则记忆层更省
    total_retransmit_tokens = max(recalls_per_month * avg_tokens_per_recall, 1)
    break_even_per_token = memory_api_usd / total_retransmit_tokens

    return {
        "stored_messages": float(stored_messages),
        "stored_gb": round(stored_gb, 4),
        "memory_api_usd": round(memory_api_usd, 4),
        "retransmit_usd": round(retransmit_usd, 4),
        "break_even_usd_per_token": break_even_per_token,
    }


def call_model(memory: MemoryLayer, system_prompt: str, user_input: str) -> str:
    """一次完整调用：召回 -> 组装 -> 调用 -> 写回。"""
    recalled = memory.recall(user_input, limit=8)
    payload = memory.build_request(system_prompt, recalled, user_input)
    resp = client.chat.completions.create(
        model=os.environ["MODEL_ID"],
        messages=payload,
    )
    memory.append(
        {"role": "user", "content": user_input},
        idempotency_key=time.time_ns().to_bytes(8, "big").hex(),
    )
    return resp.choices[0].message.content or ""
```

三个实现细节值得强调：召回条数与 token 上限要做硬约束，否则组装出来的请求迟早顶穿模型窗口；写回必须带幂等键，超时重试在编排层是常态；系统提示词这类稳定前缀要固定在最前面，供应商缓存才有命中机会。

## 九、三条路线横向对照

| 维度 | 每次重传全量 | 供应商 prompt 缓存 | 面向模型的记忆 API |
| --- | --- | --- | --- |
| 状态放在哪 | 请求体 | 供应商侧前缀池 | 独立存储层 |
| 计费口径 | 每次调用按输入 token | 命中前缀按折扣单价 | 召回免费，按存储容量 |
| 模型可换性 | 任意模型都可 | 绑定同一模型与同一前缀 | 跨模型，上下文可迁移 |
| 延迟影响 | prefill 随历史增长 | 命中即省 prefill | 召回极快，几乎不增加延迟 |
| 主要风险 | 成本随轮次近似平方上涨 | 前缀抖动导致命中率崩塌 | 容量月租成为固定开销 |
| 最适合 | 单轮、短会话 | 前缀稳定的高频调用 | 长会话、多 Agent、多模型路由 |
| 与其它路线的关系 | 成本基线 | 可以与记忆层并行 | 可以与供应商缓存并行 |

三条路线可以叠加。最省钱的组合通常是：记忆层负责容量管理与按需召回，供应商缓存负责吃掉前缀折扣，只在必要时把关键几轮原文重新传一遍。

## 十、一周免费沙箱：把验证窗口用在刀刃上

免费沙箱是一周，包含全部平台功能，不需要信用卡。这个窗口不长，验证顺序建议这样排：

1. 先量召回延迟：把召回条数从 8 拉到 32，看端到端首 token 时间的变化，确认"几乎不增加延迟"在自家链路上成立；
2. 再量召回质量：固定一批历史会话，对比"召回片段组装"与"全量重放"在同一批任务上的结果差异；
3. 然后量存储增长：连续写一周，观察容量曲线是否线性、单条消息的实际占用与 2 KB 的估算差多少；
4. 最后做账：把算子代入第 4 节的算式，对比自家当前的重传账单。

这一步做完再决定要不要付费，比先上生产再回滚便宜得多。

## 十一、上线验收清单

1. 召回片段按租户隔离，命名空间与索引键不得跨租户复用；
2. 写回带幂等键，网络重试不产生重复轮次；
3. Key 只从环境变量注入，日志与异常栈里不出现明文；
4. 召回条数与 token 上限有硬约束，单次组装的请求不超过模型窗口；
5. 敏感字段在写回前脱敏，存储层不保存原始凭证；
6. 存储的上下文按外部数据处理：工具权限、动作审批、输出审计照旧执行；
7. 供应商缓存命中率单独监控，前缀抖动有告警；
8. 成本面板同时挂两条曲线：存储容量与模型 token；
9. 上下文在模型之间迁移时做一次跨模型回归，确认提示词模板不依赖单一模型的特殊格式；
10. 回滚方案准备好：保留一段时间的双写，随时能切回重传链路。

## 十二、成本与风险提示

- 存储月租是固定成本，短会话业务可能反而不划算，先用第 4 节的算式算清楚再决定；
- 0.1 GB 对 5 万条是特定档位的示例，实际占用取决于消息长度与索引开销；
- 召回免费不等于链路免费，模型调用侧仍然按 token 计费，供应商缓存该开的还要开；
- model-free 压缩不引入改写误差，但它也不理解业务语义，检索质量仍然要靠分段与索引策略；
- 跨模型迁移上下文时注意窗口大小与模板差异，别把某个模型的特殊格式固化进系统提示词；
- 全部走正规接入与计费渠道，不做绕过官方限制的配置。

## 十三、总结

这一期把长上下文记忆做成一笔可计算的账：三条路线的成本形状完全不同，重传全量是按调用付费、供应商 prompt 缓存是吃前缀折扣、面向模型的记忆 API 是按容量付月租且召回免费；按 100 个上下文、每个 500 条消息、每月 100 万次召回、约 7.00 美元/月的档位折算，等价于约 70 美元/GB/月、约 0.14 美元/千条/月，只有当输入单价低到每百万 token 七分钱的量级，重传才更便宜；压缩环节选择 model-free 而不是 LLM 式改写，省下的是写入路径上的推理开销与有损改写带来的检索误差，顺手关掉了"外部文本被改写成摘要再以记录口吻回放"的注入通道。接入照旧走 4sapi（https://4sapi.com）的 OpenAI 兼容端点，记忆层单独封装，Key 只从环境变量读。长会话里怎么选、怎么验收，欢迎在评论区聊聊。
