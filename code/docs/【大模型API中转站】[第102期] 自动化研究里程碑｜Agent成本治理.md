# 【大模型API中转站】[第102期] 自动化研究里程碑｜Agent 成本治理

一个研究组织现在每投入 1 个人工工作日，就有 3.1 个 agent 工作日同时在跑。这不是实验室演示，而是已经进入日常生产流程的状态。

这篇记录自动化研究从"演示"走向"日常"的接入架构，重点拆解一个容易被忽略的问题：agent 工作量放大的同时，API 成本也在同步放大。我通过 4sapi（https://4sapi.com）统一接入层做的多 Agent 编排与成本治理方案，可以作为参考。

## 一、开篇痛点

Agent 能做研究，但研究型 Agent 是成本黑洞。

一个研究任务被拆给 Agent 之后，流程通常是：检索资料 → 读文档 → 推理 → 写报告 → 交叉验证。每一步都可能调用多次模型，单任务 token 消耗轻松破百万。任务规模翻倍，成本不是翻倍，而是指数增长。

当 Agent 开始承担"自动化研究实习生"这类角色时，成本治理就从可选项变成了必选项。没有预算控制的自动化研究，跑一个月就会发现账单比人工还贵。

## 二、自动化研究 Agent 的典型架构

我搭的自动化研究流水线分五个阶段：

```text
任务接收（人工下指令）
    |
    v
检索 Agent（搜索、抓取、去重）
    |
    v
阅读 Agent（长文档摘要、关键信息抽取）
    |
    v
推理 Agent（综合多份材料、形成结论）
    |
    v
校验 Agent（查漏、纠错、输出报告）
```

每个阶段独立成 Agent，阶段之间用结构化中间结果传递，不互相污染上下文。这样的好处是：单个 Agent 的上下文窗口不需要很大，token 消耗可预测，也方便单独给某个阶段降级或升级模型。

## 三、3.1 倍的含义：运行时长不等于等效产出

自动化研究组织公布的数据里，一个关键概念需要区分：3.1 倍衡量的是运行时长，不是等效人力。

| 口径 | 含义 | 对成本的影响 |
| --- | --- | --- |
| agent 工作日 | agent 实际运行的总时长 | 直接决定 token 消耗 |
| 等效人力 | agent 产出相当于几个熟练研究员的成果 | 决定价值，但很难精确测量 |
| 人工监督比 | 每个研究员同时监督几个 agent | 决定人力成本 |

把 3.1 倍理解成"一个研究员顶 3.1 个研究员"是错的；更准确的理解是"一个研究员的监督半径内，有 3.1 倍的工作量在并行跑"。这对成本治理的意义是：token 消耗按运行时长线性增长，必须盯住运行时长，而不是盯住产出。

## 四、成本治理的第一道闸：模型分级

不是所有阶段都用旗舰模型。我的分级策略：

| 阶段 | 模型档位 | 原因 |
| --- | --- | --- |
| 检索 | 轻量模型 | 任务简单，只需要提取链接和摘要 |
| 阅读 | 长上下文模型 | 文档长，需要大窗口 |
| 推理 | 旗舰模型 | 结论质量直接决定报告质量 |
| 校验 | 中档模型 | 只做查漏纠错，不需要最强推理 |

模型分级之后，同样的任务量，token 成本可以压到原来的三分之一。分级路由在 4sapi 上通过配置实现：每个 Agent 声明自己的模型要求，接入层按声明路由。

## 五、成本治理的第二道闸：任务级预算

分级只能降低单价，预算控制才能防止失控。我给每个研究任务设置了三层预算：

```text
任务级：单任务 token 上限，超限自动暂停
    |
    v
阶段级：每个 Agent 的单次调用上限，防止单点爆炸
    |
    v
账户级：日消耗上限，超限触发告警
```

```python
from openai import OpenAI

client = OpenAI(api_key="4sapi-key", base_url="https://4sapi.com/v1")

TASK_BUDGET = 2_000_000  # 单任务 token 预算

def run_research_agent(task, budget_left):
    if budget_left <= 0:
        raise BudgetExceeded("任务预算耗尽，已暂停")
    resp = client.chat.completions.create(
        model="gpt-6-astra",
        messages=[{"role": "user", "content": task}],
        max_tokens=8000,
    )
    used = resp.usage.total_tokens
    return resp.choices[0].message.content, budget_left - used
```

预算不是硬编码在 Agent 逻辑里，而是由接入层统一统计。这样无论哪个 Agent 跑飞，都会被同一套预算体系兜住。

## 六、把中间结果结构化，减少重复调用

自动化研究最容易浪费成本的地方是重复阅读同一批文档。我要求检索 Agent 输出的不是原文，而是结构化条目：

```json
{
  "sources": [
    {
      "url": "https://example.com/report",
      "title": "报告标题",
      "key_points": ["要点1", "要点2"],
      "relevance": 0.9
    }
  ]
}
```

阅读 Agent 只处理 `key_points`，需要细节时才回原文。这样绝大多数 token 消耗发生在一次性的精读阶段，后续 Agent 复用结构化结果，整体调用次数大幅下降。

## 七、并行与串行的成本权衡

多 Agent 流水线可以并行，但并行不是免费的：

| 模式 | 优点 | 成本特征 |
| --- | --- | --- |
| 全串行 | 上下文复用好，逻辑清晰 | 总耗时 = 各阶段之和 |
| 全并行 | 总耗时 = 最慢阶段 | token 消耗与阶段数成正比 |
| 混合 | 相关阶段并行，无关阶段串行 | 平衡点，需实测 |

我的默认做法是混合：检索与阅读并行跑，推理等所有阅读结果齐了再开始，校验最后串行。这样既控制了总耗时，又不会出现"为了并行而并行"的 token 浪费。

## 八、成本与风险提示

- 运行时长口径要盯紧：3.1 倍是运行时长，不是等效人力，别被数字误导；
- 分级路由是降本主力：旗舰模型只留给推理阶段；
- 预算必须三层：任务级、阶段级、账户级缺一不可；
- 结构化中间结果是隐形降本项：减少重复阅读，token 消耗直线下降；
- 合规：自动化研究的检索与处理只面向合法内容，不抓取敏感数据。

## 九、自动化研究接入检查清单

1. 把研究任务拆成检索、阅读、推理、校验四类子任务；
2. 为每类子任务指定模型档位，在接入层配置分级路由；
3. 建立任务级、阶段级、账户级三层预算；
4. 中间结果全部结构化，禁止 Agent 之间传原文；
5. 记录每个阶段的 token 消耗与耗时，周报复盘；
6. 用 20 个典型任务压测预算体系，确认超限能自动暂停。

## 十、我的观察

自动化研究真正改变的不是"Agent 能做什么"，而是"一个人能同时管理多少个 Agent"。监督半径扩大之后，成本治理能力反而成了瓶颈。谁能把 token 消耗压下来，谁就能把自动化研究规模推得更大。

## 总结

自动化研究的价值来自规模，规模的前提是成本可控。模型分级、任务预算、结构化中间结果这三招，加上 4sapi（https://4sapi.com）统一接入层的集中计费，让自动化研究从"跑得起"变成"跑得稳"。欢迎在评论区聊聊自动化研究的成本控制心得。
