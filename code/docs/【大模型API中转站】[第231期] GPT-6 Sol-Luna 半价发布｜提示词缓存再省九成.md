# 【大模型API中转站】[第231期] GPT-6 Sol/Luna 半价发布｜提示词缓存再省九成

OpenAI 在同一天内把 GPT-6 系列补齐到三档：Astra 之上，新增 Sol 和 Luna 两款次旗舰。核心信息只有一条：能力大体保留，价格砍半。

对以 API 为生的接入方来说，这比任何跑分都有分量。我在 4sapi（https://4sapi.com）上把两款模型的接入和缓存策略跑了一遍，结论先放在这里：在长系统提示词、多轮复用的 agent 场景里，半价加缓存叠加之后，同样的任务开销可以压到原来的四分之一左右。

## 一、两款模型的定位与价格

先把数字摆清楚：

| 模型 | 输入价格（每百万 token） | 输出价格（每百万 token） | 相对 GPT-5.6 同档 |
| --- | --- | --- | --- |
| GPT-6 Sol | $2 | $10 | 约一半 |
| GPT-6 Luna | $0.10 | $0.50 | 约一半 |
| GPT-6 Astra | 旗舰档 | 旗舰档 | — |

两款模型基于 GPT-6 Astra 的技术成果，把大部分能力带进更快、更便宜的档位，靠缓存和推理效率的改进把价格压下来。第三方评测给出的智能指数与 GPT-5.6 持平，各分项有升有降——也就是说，这一轮不是能力跃迁，而是成本工程。

对接入方而言，"智能持平、单价减半"意味着同样预算能跑的任务量翻倍，或者同样任务量的开销直接减半。这是结构性的变化，不是促销。

## 二、痛点：agent 场景对单价的敏感度被放大

单轮问答对价格不敏感，agent 场景完全不同。

一个典型的 agent 会话长这样：系统提示词动辄几千 token（工具定义、角色设定、输出规范），加上项目上下文，前缀轻松过万；每轮交互都要重复发送这段前缀；一个任务跑几十轮；再叠加并行子任务，输入 token 的总量是问答场景的一到两个数量级。

我算过一笔账（用"开销"这个词更准确）：假设一个 agent 任务平均 60 轮交互，每轮携带 1.2 万 token 的共享前缀加 800 token 的新增内容。按旗舰价格，光是重复前缀的输入开销就占总成本的大头。价格减半解决一半，剩下的一半就轮到缓存出场。

Luna 的定位在这里就清晰了：$0.10/$0.50 的价格带已经贴近开源模型自托管的边际成本，适合做初筛、分类、格式转换这类高频低难度环节；Sol 接住编码、推理、计算机使用这些主力任务。

## 三、原理速览：缓存为什么能省这么多

请求流向不变：

```text
应用 -> 4sapi 中转（OpenAI 兼容格式） -> OpenAI API
                |
        前缀命中检查 -> 命中部分按缓存价计费
```

GPT-6 这一代的提示词缓存做了两件事：

1. **默认提高缓存命中率**。系统侧自动识别可复用的共享前缀，不再依赖手工对齐；
2. **30 分钟窗口内，复用的合格共享前缀最高给到 90% 的输入折扣**。命中的部分按一折计费，未命中的部分照常计价。

对 agent 来说这几乎是量身定做：系统提示词、工具定义、项目规范在整个任务生命周期内完全不变，恰好构成最理想的共享前缀。前缀越长、复用轮次越多，缓存的价值越大。

## 四、4sapi 接入：十分钟跑通

我在 4sapi（https://4sapi.com）上接入的完整过程如下。中转站的好处是 OpenAI 兼容格式直接可用，不需要为每个模型适配不同的 SDK。

### 环境准备

```bash
pip install openai
```

### 配置与首调

```python
from openai import OpenAI

client = OpenAI(
    api_key="sk-4sapi-填入key",
    base_url="https://4sapi.com/v1",
)

resp = client.chat.completions.create(
    model="gpt-6-sol",          # 另一档用 gpt-6-luna
    messages=[
        {"role": "system", "content": SYSTEM_PROMPT},   # 长系统提示词
        {"role": "user", "content": "把这份周报按结论先行重写"},
    ],
    temperature=0.2,
)
print(resp.usage.prompt_tokens_details)
print(resp.choices[0].message.content)
```

返回的 `usage` 里能看到缓存命中明细。第一轮全是未命中（冷启动），第二轮开始，只要前缀不变，命中的部分就按缓存价走。

### 验证缓存是否生效

```python
def probe_cache(client, system_prompt, n=3):
    for i in range(n):
        r = client.chat.completions.create(
            model="gpt-6-sol",
            messages=[
                {"role": "system", "content": system_prompt},
                {"role": "user", "content": f"第 {i} 轮：只回复 ok"},
            ],
        )
        d = r.usage.prompt_tokens_details
        print(f"round {i}: cached={d.cached_tokens}, total={r.usage.prompt_tokens}")
```

三轮下来 `cached_tokens` 应该逐步逼近前缀总长。如果始终为零，优先检查系统提示词是否每轮都在变（时间戳、随机 ID 是最常见的元凶）。

## 五、缓存友好的提示词结构

缓存按前缀匹配，所以 messages 数组的排列顺序直接决定省钱效率。我在项目里固化的结构是：

```text
messages[0]  系统提示词（稳定，数千 token，全程不变）
messages[1]  工具与输出规范（稳定）
messages[2]  项目上下文（任务级稳定）
messages[3+] 动态对话轮次（持续追加，永不重排）
```

三条纪律：

1. **稳定内容前置，动态内容后置**。任何会变的内容都不要插在前面；
2. **去掉前缀里的时间戳和随机数**。一个 `当前时间：2026-09-23 10:00` 会让后续全部前缀失配；
3. **多任务共享同一段系统提示词**时，把它做成常量而不是每次拼接。

一个反例值得记下来：把用户名、会话 ID 拼进系统提示词，每个会话都拿到一个不同的前缀，缓存形同虚设。会话级信息应该放在 messages 的后面位置，或者作为第一条 user 消息。

## 六、单任务成本核算

以"60 轮 agent 任务、12,000 token 共享前缀、每轮 800 token 动态输入、1,500 token 输出"为基准，静态估算三种配置的开销比例：

| 配置 | 相对开销（以 GPT-5.6 旗舰无缓存为 100） | 说明 |
| --- | --- | --- |
| GPT-5.6 旗舰，无缓存 | 100 | 基准 |
| GPT-6 Sol，无缓存 | 50 | 单价减半 |
| GPT-6 Sol + 缓存命中 90% | 约 12 | 半价 × 前缀一折 |
| 初筛走 Luna + Sol 收尾 | 可低于 10 | 分层路由再砍一层 |

数字是静态估算，实际命中率取决于前缀稳定性，但量级是对的：半价和缓存叠加，agent 场景的开销下限被重新定义了。这正是"按任务定价"叙事的物质基础——单 token 价格减半叠加任务内的复用，单任务成本的降幅远大于五成。

## 七、Luna 的边界在哪

便宜不等于万能。我在真实任务里划出的分工线：

| 任务类型 | 建议档位 | 原因 |
| --- | --- | --- |
| 分类、路由、格式转换、摘要初筛 | Luna | 高频、容错高、难度低 |
| 长文写作、复杂编码 | Sol | 质量差一档，返工成本反超差价 |
| 多步规划、工具编排 | Sol | 一轮决策错误的代价是整条链 |
| 简单抽取、校验 | Luna | 规则明确，模型只需执行 |

一个实用的做法是先全量用 Sol 跑出基线，再逐类任务试降 Luna，用质量抽检守门。降档省下来的开销很可观，但返工一次的开销往往比差价更贵，别用关键路径做实验。

## 八、迁移检查清单

从 GPT-5.6 迁到 GPT-6 Sol/Luna，按这个清单走：

1. 模型名替换为 `gpt-6-sol` / `gpt-6-luna`，确认中转站已放行新模型；
2. 用 10 条历史真实任务做 A/B，对比输出质量与 token 消耗；
3. 检查系统提示词是否缓存友好（稳定、前置、无随机内容）；
4. 在 `usage` 里确认 `cached_tokens` 非零且逐步上升；
5. 高频低难度环节试切 Luna，抽检质量；
6. 重新标定超时与重试参数（更快的模型可能改变延迟分布）；
7. 更新成本看板的单价表和预算告警阈值。

## 九、成本与风险提示

- 缓存折扣有 30 分钟窗口限制，跨窗口的长间隔任务（比如每小时跑一次的批处理）吃不到最高档折扣，预算按未命中价兜底；
- 智能指数持平是聚合结论，具体到某个垂直任务，GPT-6 相对 GPT-5.6 有升有降，迁移前必须用自己的任务验收；
- Luna 在长链条 agent 里的错误放大效应比单轮场景明显，关键链路不要只为了便宜降档；
- 通过 4sapi 这类中转接入时，注意 Key 的权限最小化与用量告警，账号级限额要预留价格切换期的波动空间；
- 模型档位迭代很快，价格与折扣以官方当前公告为准，长期项目把单价做成配置而不是硬编码。

## 结论

GPT-6 Sol 和 Luna 把"旗舰能力、一半价格"变成现实，提示词缓存再把 agent 场景的输入开销往下压了一个数量级。对接入方，真正的动作只有两个：把提示词结构改造成缓存友好，把任务分层让 Luna 接住高频低难度环节。两件事都不难，收益却直接写进成本表。
