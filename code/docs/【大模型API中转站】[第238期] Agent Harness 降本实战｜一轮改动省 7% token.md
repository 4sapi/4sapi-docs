# 【大模型API中转站】[第238期] Agent Harness 降本实战｜一轮改动省 7% token

一个生产级编程智能体及其多智能体实验，在提示词精简、工具卸载、缓存布局、稀疏行号、子智能体调优这一轮改动之后，整体 token 成本下降约 7%，质量没有出现可测量的损失。这套方法的顺序只有两步：先测量，再改动。我在 4sapi（https://4sapi.com）上把同一套流程完整跑了一遍，下面整理成一份可以照着执行的 harness 审计流程。

## 一、优化目标：按任务计量的加权 token 成本

优化目标要写得足够窄，否则动作一定会跑偏：在不出现可测量质量下降的前提下，降低每个已完成任务的按价格加权 token 成本。这个定义里有三个限定词。

第一个是"已完成任务"。中途放弃的任务不产生业务价值，却把成本留在了计费里，所以分母必须是完成的任务数，而不是请求数。

第二个是"按价格加权"。输出、未缓存输入和缓存输入这三类 token 的定价差别非常大，把三者直接相加，说明不了钱花在哪里。同样是十万 token，全部落在输出档和全部落在缓存输入档，开销可以差出一个数量级。

第三个是"可测量"。质量下降必须是可观测的，所以测量口径要在改动之前定死。

## 二、为什么按请求省钱反而可能更贵

按任务而非按请求计量，是这套方法论的第一个分水岭。

每一轮请求都会重新发送前缀：工具定义、指令、设置，以及到目前为止的对话。前缀内容几乎不变，但每一轮都要被重新计价一次。于是有一个反直觉的结论：能缩小每个请求、但会增加轮数的改动，整体上可能更贵。

举一个常见例子（估算）：把一个一次能读完的文件拆成三次小范围读取，单次输入确实小了，可轮数变成三轮，每轮都要重发一遍完整前缀。若前缀在一万五千 token 量级、每轮新增只有几百 token，按任务汇总的成本反而上升——被重复计价的从来不是新增内容，而是前缀。

## 三、token 成本归因：从请求组装到按任务汇总

归因要做的，是把总成本还原到 harness 的具体代码位置上。整条链路分四段。

```text
[1] 请求组装（每一轮）
    系统提示词 + 工具 schema + 设置
    对话历史（裁剪或摘要之后的部分）
    本轮新增的工具结果与用户输入
              |
              v
[2] 按计费类型拆分
    输出 token        -> 输出单价（最高）
    未缓存输入 token  -> 输入单价（基准）
    缓存输入 token    -> 缓存单价（最低）
              |
              v
[3] 按任务汇总
    task_cost = Σ_round( 输出×P_out
                       + 未缓存输入×P_in
                       + 缓存输入×P_cached )
    再除以已完成任务数，得到单任务加权成本
              |
              v
[4] 归因到 harness 的位置
    提示词层 / 工具层 / 历史层 / 缓存层 / 子智能体层
```

跳过第二段直接看 token 总量是最常见的误判：输入 token 多并不等于贵，输出 token 少也不等于省。

## 四、harness 测绘清单

审计的第一步是把 harness 梳理清楚，找出所有会影响"发什么、发多长、发几轮"的位置。

| 位置 | 要查什么 | 典型浪费 |
| --- | --- | --- |
| 请求组装点 | 消息在哪里拼装、顺序由谁决定 | 多处拼装、顺序不稳定 |
| 系统提示词 | 篇幅、是否含命令式清单与旧模型防范 | 为弱模型写的护栏长期留存 |
| 工具 schema | 工具数量、描述长度、是否全量加载 | 每轮重发从未被调用的工具 |
| 框架或 SDK 钩子 | 消息顺序、缓存控制、工具加载的钩子位置 | 默认行为覆盖了缓存断点 |
| 工具结果格式 | 结果如何序列化、是否带冗余字段 | 大文件全量回显、重复行号 |
| 历史管理 | 如何保存、裁剪、摘要 | 永不裁剪，或摘要失真 |
| 子智能体 | 如何生成、并行度、继承多少上下文 | 每个分支都带完整前缀 |
| 模型与提供商 | 实际调用了哪些模型与 API | 档位与任务难度不匹配 |
| 缓存行为 | 自动或显式断点、TTL、最小可缓存长度 | 断点与稳定前缀不对齐 |
| 定价表 | 输出、未缓存输入、缓存输入三档价格 | 只按输入输出两档核算 |

清单里有两处最容易漏。一是框架或 SDK：如果请求由某个框架或 SDK 负责构建，必须找到它在消息顺序、缓存控制和工具加载方面的钩子，否则改了提示词也落不到实际请求上。二是缓存行为与定价：断点是自动还是显式、TTL 多长、最小可缓存长度多少、三档价格分别是多少，这些要从中转入口或提供商文档里拿准确值。

## 五、测量基线：用 usage 观测缓存命中与输出占比

测绘完成后立刻测基线，不做基线就没有"改动前后"这个说法。观测数据全部来自响应的 usage 字段，不需要额外埋点。

```python
import os
from openai import OpenAI

client = OpenAI(
    api_key=os.environ["FOURSAPI_API_KEY"],
    base_url="https://4sapi.com/v1",
)

P_OUT = float(os.getenv("PRICE_OUTPUT", "10"))  # 三档单价（每百万 token，示例值，请替换为当前实际定价）
P_IN = float(os.getenv("PRICE_INPUT", "2"))
P_CACHED = float(os.getenv("PRICE_CACHED", "0.2"))


def run_task(messages, model="gpt-6-sol", max_rounds=40):
    total_in = total_out = total_cached = 0
    rounds = 0
    for _ in range(max_rounds):
        resp = client.chat.completions.create(model=model, messages=messages)
        usage = resp.usage

        details = getattr(usage, "prompt_tokens_details", None)
        cached = getattr(details, "cached_tokens", 0) if details else 0

        total_in += usage.prompt_tokens
        total_out += usage.completion_tokens
        total_cached += cached
        rounds += 1

        # 简化写法：真实 harness 在这里执行工具并把结果追加进 messages
        messages.append(resp.choices[0].message)
        if resp.choices[0].finish_reason == "stop":
            break

    uncached = total_in - total_cached
    cost = (total_out * P_OUT
            + uncached * P_IN
            + total_cached * P_CACHED) / 1_000_000

    return {
        "rounds": rounds,
        "input_tokens": total_in,
        "output_tokens": total_out,
        "cached_tokens": total_cached,
        "cached_ratio": round(total_cached / total_in, 3) if total_in else 0.0,
        "output_cost_share": round(total_out * P_OUT / (cost * 1_000_000), 3) if cost else 0.0,
        "weighted_cost": round(cost, 4),
    }
```

这段脚本给三个关键读数：缓存占比说明缓存布局有没有生效；输出成本占比说明钱是花在生成上还是花在重发前缀上，两者对应完全不同的改法；加权成本除以任务数，才是要比较的那个数。

基线跑法：固定同一批真实任务、同一个模型、同一套评分口径，先跑一遍拿到加权成本、轮数、缓存占比和输出占比；每次只动一个变量，跑完再对比。轮数一旦上升，就必须回头确认按任务汇总的成本是否仍然下降。

## 六、缓存布局与提示词结构的对照

缓存按前缀匹配，提示词的排列顺序直接决定省钱效率。稳定内容前置、动态内容后置、只追加不回改，这三条纪律落到具体位置上是这样：

| 结构位置 | 缓存视角 | 稳定性要求 | 常见反例 |
| --- | --- | --- | --- |
| 系统提示词 | 最长、最该命中的前缀 | 全程不变 | 拼进时间戳、会话 ID |
| 工具 schema | 紧随其后的稳定段 | 任务生命周期内不变 | 每轮按需动态增删工具 |
| 设置与环境描述 | 稳定段 | 变更走版本号 | 把随机采样参数写进正文 |
| 项目上下文 | 任务级稳定段 | 一个任务内不变 | 每轮重新检索并重排 |
| 对话历史 | 持续追加段 | 只追加、不重排、不回改 | 中途裁剪导致前缀失配 |
| 工具结果 | 动态段 | 放在尾部 | 大文件全量回显 |

静态上下文只留给大多数轮次都需要的内容，其他一切都应该在需要时可被发现。

工具卸载属于同一类改动：把几十个工具的 schema 全量挂在每轮请求上，等于为从未被调用的能力持续付费；按需加载、按任务类型裁剪工具集，既降成本也降干扰。

## 七、五条原则：改的是发送的内容

### 原则一：改变的是 harness 发送的内容，而不是要求模型更努力

不要把"注意节省 token、不要浪费"这类要求写进提示词。这样做的结果是模型变得不愿承担有雄心的任务，有时还会中途退出，说自己不该浪费 token。省 token 是 harness 的责任，不是模型的任务。

### 原则二：有能力的模型需要的是定义，而不是命令

以"不要"开头的禁令、"必须"式的强制要求、"重要"之类的强调清单，以及针对旧模型习惯写的防范措施，通常都可以用对每个工具功能的平实描述来替代。按这种方式精简系统提示词，实测可以削减约三分之二的篇幅，而且更短的提示词在多个模型家族中都照样奏效。判断标准很简单：只保留模型无法知道的内容（产品、环境、用户的具体流程）和对话记录里真正出现过的怪癖，其余一律删掉。

### 原则三：静态上下文只留给大多数轮次都需要的内容

前缀里每多一段只在少数轮次用到的内容，都是对整个任务生命周期的持续付费。

### 原则四：要预期删减会胜出

为较弱模型编写的护栏、已经变成瓶颈的协调步骤，以及针对模型如今已能自行完成的行为所写的提示词，全都在消耗 token。默认假设是它们可以被删掉，除非能证明删了会变差。

### 原则五：真实使用情况说了算

评测是快速的替代指标，但它们偏向难题，会错过真实请求的构成。优化方向要由真实流量决定，评测只用来做质量守门。

## 八、机会点排序与改动优先级

先梳理 harness 并测量基线，再对机会点排序，然后直接做那些可以安全做的改动，把其余的放到开关后面或者写成提案，最后汇报。排序依据是三个量的乘积：触及多少请求、单次触及能省多少、风险有多大。

实测结果是，一轮包含提示词精简、工具卸载、缓存布局、稀疏行号、子智能体调优的改动，让整体 token 成本下降约 7%，质量没有损失。需要说清楚的是，那些更大的百分比只适用于每项改动所触及的那部分请求。这些数字用来判断量级，不要当成目标。

| 改动 | 触及面 | 风险 | 建议优先级 |
| --- | --- | --- | --- |
| 提示词精简 | 每一轮前缀 | 低 | 直接做 |
| 工具按需卸载 | 每轮工具 schema | 低 | 直接做 |
| 缓存布局对齐 | 前缀命中率 | 低 | 直接做 |
| 稀疏行号 | 工具结果体积 | 低 | 直接做 |
| 子智能体调优 | 并行分支 | 中 | 放开关后灰度 |
| 历史裁剪与摘要 | 长任务全程 | 中高 | 放开关后灰度 |
| 模型档位下调 | 全局 | 高 | 先写提案 |

排在前四行的改动只改变发送内容的组织方式，可以安全地直接做；后三行会改变模型看到的信息量或能力边界，收益更大，但必须走开关或提案。

## 九、开关与回滚：把不确定的改动放到后面

```text
这个改动可以安全地直接做吗？
    |
    +-- 触及面小、可逆、无质量风险  -> 直接做，结果并入新基线
    |
    +-- 触及面大、可逆、质量待验证  -> 放到开关后面，灰度验证
    |
    +-- 触及面大、影响质量或不可逆  -> 写成提案，附验收标准
    |
    +-- 收益无法测量                -> 先补测量，再决定
```

开关的实践要点：

1. 每个改动一个独立开关，用环境变量或配置项控制，默认值保持旧行为；
2. 不要把所有改动打包成一个总开关，否则回滚时会连带撤掉已经验证过的收益；
3. 灰度从一类任务或一部分流量开始，开关粒度要和风险粒度对齐；
4. 开关开启前后都要记录加权成本、轮数、缓存占比和质量抽检；
5. 开关有生命周期，验证完成后要么全量要么删除，长期堆积本身就是技术债；
6. 提案类改动要写明预期收益、验收标准和回滚条件。

## 十、上线前检查清单

一轮改动要上线前，按这个清单逐条确认：

1. 基线是否用真实任务集测过，而不是只跑了评测；
2. 改动前后是否同一批任务、同一模型、同一评分口径；
3. 缓存占比是否上升，前缀里是否还有时间戳、随机 ID、动态工具列表这类失配源；
4. 轮数是否变化；若上升，按任务汇总的加权成本是否仍然下降；
5. 输出 token 占比是否异常，长输出往往是成本主因，与前缀问题是两套解法；
6. 每个改动是否有独立开关，默认行为是否仍为旧版本；
7. 质量抽检是否覆盖被改动触及的任务类型，并做过一次回滚演练；
8. 成本看板的单价表与预算告警是否同步更新，被推迟的改动及原因是否记录在案。

## 十一、成本与风险提示

- 约 7% 是整体数字，单项改动的大百分比只适用于它触及的那部分请求，不要拿单项百分比当整体预期；缓存折扣有窗口与最小可缓存长度限制，跨窗口任务按未命中价兜底，预算不能按最高折扣算；
- 删减提示词有下限，模型无法知道的产品、环境与流程信息必须保留，删过头只是把成本转移到返工上；
- 历史摘要与模型降档是收益最大也最容易伤质量的两类改动，必须走开关或提案，不要在关键路径上直接试；
- 三档单价会变，把价格做成配置项而不是硬编码；通过中转入口接入时注意 Key 的权限最小化与用量告警。

## 结论

token 成本治理不是一串省钱的技巧，而是一条固定顺序：先梳理 harness 并测量基线，再按触及面、收益和风险对机会点排序，直接做只改变发送内容组织方式的低风险改动，把会影响信息量或能力边界的改动放到开关后面或写成提案，最后汇报。核心度量只有一个——每个已完成任务的按价格加权 token 成本，而它必须按任务汇总，因为每一轮都要重发前缀。

这套流程落在一个生产级编程智能体及其多智能体实验上，一轮改动带来约 7% 的整体降幅，质量没有损失。数字不大，但方向可持续：删减会持续胜出，每一步都留有回滚余地。在 4sapi.com 这类中转入口上跑同一批任务做前后对比，是把这套方法论变成日常动作的最短路径。
