# 【大模型API中转站】[第169期] 8B 原生多模态自部署实测｜端侧视觉选型

一个 8B 的原生统一多模态模型，把视觉理解、推理和图像生成收进同一套表征，并且不依赖外部视觉 encoder，也不依赖 VAE。这件事对端侧部署的意义，比榜单排名大得多。

## 一、先说痛点：视觉账单和数据出域的两难

我手上的视觉业务长期被同一个问题夹住：工单截图、设备巡检照片、监控抓帧，每月的量稳定上涨。全部走云端视觉 API，账单按月爬坡，而且图片一旦出了内网，合规同事就会追问里面有没有人脸、有没有客户信息、有没有生产环境的界面。反过来，把视觉任务全部挪到端侧或私有化机器上，我又会担心两件事：一是小规模模型的能力到底够不够用，二是自己养一套多模态推理服务的运维成本到底有多高。

这个两难不是靠"选边站"能解决的。我最后落地的思路是把问题拆开：数据不允许出域的部分，交给本地部署的小模型；可以出域但要求高质量的部分，交给云端；两侧行为统一成一套 OpenAI 兼容调用。云侧入口我收敛在一个聚合网关上，也就是 4sapi（https://4sapi.com），本地服务和云端模型挂进同一路由层，业务代码只写一份。后面把这套做法完整展开。

## 二、"原生统一"到底统一了什么

传统视觉语言模型的主流结构是三段式：视觉 encoder 负责把图像压成特征，对齐层把特征投影到语言空间，LLM 在语言空间里做理解和推理；如果还要生成图像，就得再挂一条独立的生成管线，中间还需要 VAE 在像素和潜空间之间来回编解码。三段式的代价很实际：两套表征、两份权重、两条服务链路，显存开销成倍上涨，部署和排障都要维护两套东西。

SenseNova-U1.5 走的是另一条路：8B 规模的原生统一多模态模型，不依赖外部视觉 encoder，不依赖 VAE，用同一套表征完成视觉理解、推理与图像生成。对我这种要在边缘和私有环境部署模型的人来说，这个设计的好处可以直接换算成工程语言：一份权重文件，一条推理管线，一个服务端口，就能同时接住"看图说话"和"按描述生成"两类请求。端侧最稀缺的就是显存和运维带宽，省掉一整条独立管线，比任何单项跑分都实在。

## 三、原理速览：两条管线摆在一起看

```text
传统三段式管线（encoder + LLM + 独立生成器）

图像 ──> 视觉 encoder ──> 对齐层 ──> LLM ──> 文本输出（理解与推理）
                                  └──> 扩散生成管线 ──> VAE 编解码 ──> 图像输出（生成）

SenseNova-U1.5 的原生统一管线

图像 ──┐
       ├──> 统一 patch 表征 ──> 8B Transformer ──> 文本输出（理解与推理）
文本 ──┘                     └──────────────────> 图像输出（生成，无 VAE、无外挂 encoder）
```

统一的关键在"表征"这两个字。图像被切成 patch 之后，以统一的表征形式和文本 token 进同一个 Transformer，理解、推理、生成不再需要在不同表征空间之间搬运信息。从部署视角看，这条管线少了一次跨模型的特征转换，少了一份要常驻显存的编码器权重，KV cache 和批处理调度也只有一套逻辑。我在估算端侧资源的时候，最喜欢这种"少一个组件"的架构，因为每一个被拿掉的组件，都是一块不再需要排障的电路。

## 四、四个关键手段，各自解决什么问题

围绕高保真与指令遵循，SenseNova-U1.5 用了四个关键手段：patch 重建、数据策展、专家优化、on-policy 蒸馏。下面按我的理解逐个拆开，重点说每个手段对应哪个工程痛点。

**patch 重建。** 图像 token 化之后最怕信息丢失，细节一丢，OCR 和小目标识别这类任务就先遭殃。patch 重建相当于给表征加了一条硬约束：模型必须能从内部表征把图像重建回来，逼着表征留住足够的细节。我把它理解成一种"信息保底"机制，保的正是视觉侧的高保真。

**数据策展。** 多模态模型的上限很多时候不是参数量决定的，而是数据配比和数据质量决定的。理解和生成两类任务的数据要放在一起策展，指令遵循能力尤其依赖高质量的指令数据，而不是单纯堆量。这一条给我的启发是：自部署之后做领域适配，数据配比的工作比买卡更值得花时间。

**专家优化。** 一个模型同时承担理解和生成，天然存在互相拖累的风险。专家优化我理解为在训练和结构侧为不同能力做的专门安排，让两类任务不至于抢同一份容量。具体实现细节以官方技术资料为准，我不替它下结论，但方向是明确的：统一架构不等于所有任务平均用力。

**on-policy 蒸馏。** 小模型向大模型学习，最常见的失败方式是背答案：在离线数据上背得很熟，换一种问法就露馅。on-policy 蒸馏让 8B 模型在自己生成的输出分布上向更强的教师对齐，学到的是行为方式而不是固定答案。对部署方来说，这一条直接关系到指令遵循的稳定性——线上用户的问法是长尾分布，模型必须经得起换着花样问。

## 五、评测观念要先换：按部署约束选模型

我现在的评测观念是：先写下部署约束，再决定评测对象。在边缘部署场景里，比如野外红外相机、有限网络甚至完全无网络的环境，小型本地部署的 VLM 才是与部署实际相关的评测对象，而不是前沿规模模型。道理很朴素：红外相机蹲在山里，请求根本发不出去，一个再强的云上模型也参与不了这个业务，拿它当参照系只会得出错误结论。

落到操作层面，我的做法是三步。第一步，把部署约束写成硬性条款：网络可用性、算力上限、时延预算、功耗预算。第二步，评测集从部署现场来：真实光照、真实分辨率、真实拍摄角度，而不是网络图库里的干净样本。第三步，只在真的能部署进现场的候选集合内做比较，8B 和更小规模的本地模型互相比，前沿模型只作为能力上限的参考线。这样一来，"8B 原生多模态够不够用"就从一个抽象问题，变成一组可以量化回答的指标。

## 六、自部署硬件需求：8B 级多模态的显存估算

先给估算方法（估算口径）：模型权重的显存占用约等于参数量乘以每个参数的字节数，FP16/BF16 每参数 2 字节，INT8 每参数 1 字节，INT4 每参数约 0.5 字节；在权重之外，还要为 KV cache、激活值和运行时开销留余量，KV cache 的大小取决于上下文长度和图像 patch 数量，多模态请求的图像部分会显著放大这一项。

| 精度方案 | 权重显存估算 | 建议整机显存（估算口径） | 适合的场景 |
| --- | --- | --- | --- |
| FP16/BF16 | 约 16 GB | 24 GB 单卡 | 精度优先，室内有电有网，预算充足 |
| INT8 | 约 8 GB | 16 GB 单卡 | 性价比主力，多数私有化部署的默认选择 |
| INT4 | 约 4–5 GB | 8 GB | 边缘盒子、野外离线设备、功耗受限场景 |

两点提醒。第一，这是通用估算口径，不代表任何具体模型在某个推理框架下必然支持某种量化格式，实际可用性和精度损失以模型仓库的发布说明和自己的压测为准。第二，多模态请求的显存水位波动比纯文本大，图像 patch 数量一多，KV cache 就会顶上去，容量规划要按峰值算，不要按均值算。我的习惯是按峰值负载留出三成左右余量，宁可单卡贵一档，也不要线上 OOM。

## 七、接入教程：用 vLLM 类工具起一个 OpenAI 兼容服务

自部署的接入路径已经很成熟，核心思路是把本地模型包装成 OpenAI 兼容接口，让业务代码感觉不到后面是本地还是云端。以 vLLM 这类推理框架为例，流程分四步。第一步，拿到模型权重，确认许可证允许当前用途。第二步，用推理框架起服务，把服务名固定下来，例如 `vllm serve <模型路径> --served-model-name sensenova-u1.5 --port 8000`，具体参数以模型仓库的部署说明为准，这套流程我在本地完整走通过一遍。第三步，确认服务暴露了 OpenAI 兼容端点，通常是 `/v1/chat/completions`。第四步，业务侧统一路由：敏感图走本地，复杂任务走云端。云侧我没有为每家厂商单独写一套调用代码，而是统一走 4sapi（https://4sapi.com）的 OpenAI 兼容接口，换云上模型只改配置，不改代码。如果是无网络的边缘设备，起服务的方式完全一样，只是路由层永远选择本地分支。

下面是一段完整的 Python 示例，包含本地与云端两个客户端、最粗粒度的敏感判断和混合路由：

```python
# coding: utf-8
"""本地 8B 多模态服务与云端 API 的统一调用示例。"""
import base64
from pathlib import Path

from openai import OpenAI

# 本地 vLLM 服务暴露的 OpenAI 兼容端点，敏感图只允许走这一侧
local_client = OpenAI(base_url="http://127.0.0.1:8000/v1", api_key="EMPTY")

# 云端聚合网关暴露的 OpenAI 兼容端点，复杂任务走这一侧
cloud_client = OpenAI(base_url="https://gateway.example.com/v1", api_key="sk-demo")

LOCAL_MODEL = "sensenova-u1.5"    # 与 vllm serve 的 --served-model-name 保持一致
CLOUD_MODEL = "cloud-vlm-model"   # 网关侧配置的云端多模态模型名

SENSITIVE_HINTS = ("身份证", "人脸", "病历", "内网", "客户")

def is_sensitive(prompt: str) -> bool:
    """最粗粒度的敏感判断，生产环境应替换为策略引擎或标注服务。"""
    return any(word in prompt for word in SENSITIVE_HINTS)

def encode_image(image_path: str) -> str:
    """把本地图片编码成 data URL，供 OpenAI 兼容接口使用。"""
    raw = Path(image_path).read_bytes()
    return "data:image/jpeg;base64," + base64.b64encode(raw).decode("utf-8")

def build_messages(image_data_url: str, question: str) -> list:
    """按 OpenAI 多模态消息格式组装图文请求。"""
    return [{
        "role": "user",
        "content": [
            {"type": "image_url", "image_url": {"url": image_data_url}},
            {"type": "text", "text": question},
        ],
    }]

def ask(image_path: str, question: str) -> str:
    """混合路由入口：敏感图锁定本地，其余任务交给云端。"""
    messages = build_messages(encode_image(image_path), question)
    if is_sensitive(question):
        client, model = local_client, LOCAL_MODEL
    else:
        client, model = cloud_client, CLOUD_MODEL
    resp = client.chat.completions.create(
        model=model,
        messages=messages,
        max_tokens=1024,
    )
    return resp.choices[0].message.content

if __name__ == "__main__":
    answer = ask("./samples/scene.jpg", "描述图中的场景，并列出可见的异常项")
    print(answer)
```

这段代码刻意保持简陋，关键词匹配只是占位逻辑，生产环境应该换成策略引擎或人工抽检流程。但骨架是完整的：图片编码、双客户端、路由决策、统一返回。把 `is_sensitive` 换成真实策略，其余部分几乎可以直接投产。

## 八、混合路由：敏感图走本地，复杂任务走云端

路由层是我认为最值得投入设计的一个环节，它同时决定了数据主权、成本和可用性。我的路由维度有四个。数据敏感度：包含人脸、证件、客户数据、生产环境信息的图片，一律锁在本地 8B 模型上，这是硬规则，不给弹性。任务难度：多图对比、精细推理、需要大量世界知识的任务，本地小模型没有把握的，路由到云端，用质量换成本。时延要求：交互式场景优先本地，离线批量任务可以排队走云端的低价时段。可用性：云端不可达或超时，自动回落本地，哪怕输出质量降一档，业务也不能断。

负载均衡上，本地多卡部署时交给推理框架的并发调度，多实例之间在网关侧做加权和健康检查；云侧多条通道互为备份，按成功率动态切换。还有一条容易被忽略的纪律：每次请求落在哪一侧、为什么落在这一侧，都要有日志。这份日志既是成本对账的依据，也是合规审计时最有力的证据——数据去了哪里，路由说了算，日志说了清。

## 九、云 API 与自部署的成本对比

成本测算全部基于示例假设（估算口径）：单张图片平均折算 5000 token；云端多模态模型综合单价按 5 元/百万 token 计；自部署单卡整机按 2 万元、3 年直线折旧，折合约 556 元/月；电费按 1 元/度、整机 300 W 常开计算，约 216 元/月；自部署固定成本合计约 770 元/月。这些数字只为说明量级和结构，替换成实际报价后，结论的方向通常不变。

| 月图像量 | 云端 API 月成本（示例估算口径） | 自部署单卡月成本（示例估算口径） | 我的倾向 |
| --- | --- | --- | --- |
| 1 千张 | 约 25 元 | 约 770 元（固定） | 云端，省心 |
| 1 万张 | 约 250 元 | 约 770 元（固定） | 云端略优，数据敏感或需离线则自部署 |
| 10 万张 | 约 2,500 元 | 约 770 元起，留意并发上限 | 自部署 |
| 100 万张 | 约 25,000 元 | 视并发扩容，摊薄后仍显著更低 | 自部署为主 + 云端兜底 |

这张表里最重要的不是具体数字，而是两条曲线的形状：云 API 成本随量线性上涨，自部署成本近乎固定，只在并发顶到上限时阶梯式扩容。示例口径下，分水岭在每月 3 万张附近。另外两笔隐性成本要计入：自部署的运维人力，以及量化精度损失带来的业务风险。反过来，云端也有一笔隐性收益——弹性，业务量突然翻倍时不需要采购周期。所以最终决策从来不是纯算术题，而是在算术结果上叠加数据主权和运维能力之后的综合判断。

## 十、什么时候选原生统一架构：能力、延迟、数据主权

能力维度：业务同时需要理解和生成——比如"看图、改图、再解释为什么这么改"的闭环任务——原生统一架构用一套表征和一条管线覆盖两类请求，维护成本明显更低。如果只需要纯理解，而且追求极致精度，那么传统多段式架构里的成熟大模型仍然值得放进候选集一起比，架构先进不等于每个单项都赢。

延迟维度：少一套常驻的视觉 encoder，少一次跨表征的转换，对端侧的首响应时延和内存占用都更友好，生成类请求还省去了加载第二套模型的开销。具体数字取决于硬件和框架，我坚持一切以现场压测为准，但结构上的节省是确定的。

数据主权维度：这是最没有商量余地的一维。图片不允许出内网是硬约束时，本地部署的小模型是唯一可行解，这时候讨论的不再是"要不要自部署"，而是"在能自部署的模型里选哪个"。原生统一加上 8B 规模，恰好把理解和生成一起装进了这个约束圈里。

## 十一、风险提示：从研究发布到生产就绪的距离

第一，研究发布不等于生产就绪。新模型的工程配套——推理框架适配、量化方案、长稳压测、异常处理——都需要自己验证，官方能给的通常是能力上限，生产表现要靠自己的压测数据说话，部署参数以模型仓库的说明为准。

第二，模型许可证要逐条读。商用范围、再分发限制、是否允许量化后再发布，这些条款直接决定部署方案是否成立，法务确认之前不要把方案写进排期。

第三，生成内容的合规审核要前置。模型具备图像生成能力，意味着输入和输出两侧都要有审核机制：输入侧拦违规请求，输出侧拦违规内容，日志留存满足溯源要求。这一块没有捷径，属于上线前必须完成的工程项，而不是上线后的补救项。所有讨论都建立在合法接入与合规运营的前提上，架构设计和成本优化解决的是效率问题，替代不了合规义务。

## 十二、选型检查清单

最后把我实际在用的检查清单列出来，按顺序过一遍，能挡掉大部分选型事故：

1. 写下部署约束：网络可用性、算力上限、时延预算、功耗预算。
2. 圈定能进现场部署的候选模型集合，评测只在集合内进行。
3. 用部署现场的真实数据构建评测集，包含最难的那批样本。
4. 按峰值负载做显存规划，留三成余量，确认目标量化格式可用。
5. 确认模型许可证覆盖当前用途，法务确认留档。
6. 设计混合路由规则：数据敏感度、任务难度、时延、可用性四个维度。
7. 打通本地 OpenAI 兼容服务与云端聚合网关，业务代码只保留一套调用。
8. 路由决策全量记日志，成本对账与合规审计共用这一份记录。
9. 生成能力上线前接好输入输出双侧审核与留存。
10. 设定回滚与降级预案：云端不可达回落本地，本地异常降级到规则兜底。

## 十三、总结

这一期把 8B 原生统一多模态模型的选型问题从头到尾走了一遍：SenseNova-U1.5 用同一套表征完成理解、推理与生成，省掉外部视觉 encoder 和 VAE；patch 重建、数据策展、专家优化、on-policy 蒸馏四个手段分别守住保真与指令遵循；评测观念要从"追前沿规模"换成"按部署约束选对象"；自部署侧给出了显存估算口径、vLLM 类工具的 OpenAI 兼容接入和混合路由骨架；成本侧用示例假设画出了每月约 3 万张的分水岭。我自己的落地形态，是本地 8B 服务加 4sapi（https://4sapi.com）的云端通道共用一个路由层，数据主权和成本两头都拿得住。8B 级原生多模态真正把端侧视觉从"能不能部署"推进到"值不值得部署"，剩下的判断权在使用现场。如果已经在端侧跑过多模态模型，或者对云边混合路由有自己的拆法，欢迎在评论区聊聊。
