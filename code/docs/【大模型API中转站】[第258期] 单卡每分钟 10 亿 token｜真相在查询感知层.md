# 【大模型API中转站】[第258期] 单卡每分钟 10 亿 token｜真相在查询感知层

推理成本下降的速度，已经从"每几个月降一点"变成"同一代硬件上再压一个数量级"。

一个查询感知推理层给出的实测数据是：**单张 H100 上超过每分钟 10 亿 token**，比通用推理引擎快 **10 倍以上**，每十亿 token 成本**不到 $0.06**。同一时期，GPU 租赁价格在九个月内从 $4.40 翻倍到 $8.08 每 GPU 小时。两个数字方向相反却同时成立——理解这个差额从哪来，决定了自建推理的收益判断是否成立。我在 4sapi（https://4sapi.com）上做推理侧的成本评估时，把这三层拆开看。

## 一、先把量级换算清楚

每分钟 10 亿 token 是个很大的数字，但把它换到日常口径更直观：

```text
每分钟 10 亿 token
  = 每秒约 1,667 万 token
  = 假设单次回答 800 token，每秒可服务约 2 万次请求
  = 单卡日吞吐量级：约 1.4 万亿 token
```

每十亿 token 不到 $0.06，意味着单卡日成本量级在几十美元。把这个数字与商用 API 的单价对照，就能直接判断自建在什么规模上开始划算——而这正是本节要算清的事。

需要注意的是，这类吞吐数字通常是在**特定负载形态**下测得的（输入输出比例、批大小、序列长度都有影响）。引用时应当同时确认测试条件，而不是把它当作通用指标。

## 二、为什么"查询感知"能带来数量级差异

通用的推理引擎按请求到达的顺序处理，对每个请求都走同样的路径。但真实负载里请求差异极大：有的只需读缓存，有的要完整计算；有的输出几个 token，有的输出几千个。

"查询感知"指的是推理层在调度前**先判断这个请求需要什么**，再决定走哪条路径。可判断的维度包括：

- 前缀是否命中缓存，命中则跳过重复的 prefill；
- 输出长度预期，短输出可以走更激进的分批；
- 计算与内存的瓶颈归属，据此选择并行策略；
- 是否需要与其他请求合并批处理。

省下来的成本主要来自两处：**避免重复的 prefill 计算**，以及**让批处理组合更合理**。前者对应缓存命中率，后者对应设备利用率。这两项正是通用引擎按顺序处理时难以兼顾的部分。

## 三、推理成本的三个层次

理解成本结构比记住某个数字更重要。我把推理成本分成三层：

| 层次 | 决定因素 | 优化手段 | 典型幅度 |
| --- | --- | --- | --- |
| 硬件层 | GPU 型号、租价 | 采购、长约、替代厂商 | 1.5–2 倍波动 |
| 引擎层 | 调度、缓存、批处理 | 查询感知调度、KV 缓存复用 | 10 倍以上 |
| 模型层 | 参数量、量化、稀疏度 | 量化、蒸馏、小模型路由 | 5–10 倍 |

三层的优化幅度差异很大。硬件层是线性的价格博弈，能做的主要是采购与长约；**引擎层有数量级空间**，且不改变模型能力；模型层收益也大，但会直接影响质量。

这张表解释了一个常见误区：把成本优化等同于"换更便宜的硬件"。实际上硬件层的波动最小，而引擎层和模型层的空间要大得多。今日这组数据（比通用引擎快 10 倍以上）正落在引擎层——**它没有换硬件，也没有换模型**。

## 四、硬件涨、单位跌，差额去哪了

回到那个矛盾：GPU 租价翻倍，AI 使用价格却在下降。

差额被三处吸收：

**一是引擎层的效率提升。** 上面那组的 10 倍以上提速，直接摊薄了每 token 的硬件成本。

**二是利用率提升。** 同一张卡能服务的请求量上升，闲置时间减少，单位请求分摊的固定成本随之下降。

**三是融资补贴。** 在竞争扩张阶段，价格是争夺使用量的工具，部分成本由融资填补而非收入覆盖。

三者的可持续性不同：效率提升是**结构性**的，会长期保留；利用率提升受负载波动影响，高负载时收益大、低负载时缩水；补贴是**阶段性**的，会随竞争格局变化而调整。

判断长期价格走向时，只看前两项就能得到大致方向——而这也是为什么"硬件涨价必然推高 API 价格"这个推论不成立。

## 五、自建的收益边界在哪

自建推理是否划算，取决于三个量的比较：**自建的固定成本**、**API 的可变成本**、以及**负载的实际形态**。

一个简化的盈亏平衡口径：

```text
自建月成本 ≈ 设备或租金 + 运维人力 + 闲置损耗
API 月成本 ≈ 实际 token 量 × 单价

自建更优的条件：实际用量 × 单价 > 自建月成本
```

但这个口径有两个容易出错的地方。

**第一，"实际用量"应按时段峰值而非平均值计算。** 自建要覆盖峰值，峰值期间的闲置在平均口径里看不见，却实实在在计入成本。

**第二，API 单价不是固定的。** 缓存命中、批处理、以及分层路由（把简单请求发给小模型）都能把有效单价压到标称价以下。用标称单价与自建比较，会高估自建的收益。

我实际使用的判断顺序是：先做分层路由把有效单价压下来，再看剩余用量是否够撑起自建。这个顺序很重要——很多时候做完分层，自建的必要性就消失了。

## 六、吞吐优化不该只看吞吐

引擎层优化最容易犯的错误是只盯吞吐，忽略其他指标。需要同时观测的至少有四项：

- **吞吐**：单位时间的 token 量；
- **首 token 延迟**：交互场景下比吞吐更影响体感；
- **尾延迟**：P99 决定超时与重试参数；
- **显存占用与并发上限**：决定单卡能同时服务多少请求。

四项之间存在取舍。增大批处理能提高吞吐，但会推高首 token 延迟和尾延迟；缓存复用能降低计算量，但会占用显存、压低并发上限。所以"最快"不是单一目标，而是**按业务选择组合**：批处理类任务重吞吐，交互类任务重首 token 延迟。

一个实用做法是把负载按延迟敏感度分成两类，分别用不同的批处理策略，而不是用一套参数服务全部请求。

## 七、端侧这一层的新约束

推理分层通常讲三层：端侧、边缘、云。端侧的价值很清楚——数据不出设备、离线可用、单次查询零成本。但它的约束比"慢一点"要尖锐得多。

在旗舰移动设备上的实测发现：**持续的端侧生成会让 GPU 推理运行时变得不稳定，在连续几次查询后崩溃或静默卡死**。失效点位于当前工具链（kernel 编译与移动 GPU 上的长 prompt prefill），**即使设备是凉的也会复现**，且对长生成最严重。

"静默卡死"比"变慢"危险得多：变慢可观测、可重试；静默卡死会让请求挂起而没有明确错误，调用方只能等超时。对做端侧推理的团队，这意味着三件事必须做：**限制连续生成次数与单次长度**、**在客户端实现看门狗**、**对端侧失败有明确的降级路径**（而不是无限重试）。

分层路由在真实硬件上的另一条实测结论同样值得记住：在路由策略的奖励里，**必须给"本地执行"一项正的权重**，否则纯成本最优的策略会退化成"把每一次查询都卸载到云端"——本地推理的价值（数据不出端、离线可用）在纯成本目标下没有位置。这是多目标优化里很典型的一个陷阱：**用单一成本指标优化多目标系统，会系统性地牺牲掉未被计入的那些目标**。

## 八、接入示例：吞吐与成本实测

下面这段脚本对同一批请求测吞吐、首 token 延迟与单位成本，用于对比不同配置。

```python
import os, time, threading
from openai import OpenAI

client = OpenAI(
    api_key=os.getenv("FOURSAPI_API_KEY"),
    base_url="https://4sapi.com/v1",
)

MODEL = os.getenv("MODEL_NAME", "gpt-6-sol")
CONCURRENCY = int(os.getenv("CONCURRENCY", "8"))
PRICE_IN = float(os.getenv("PRICE_IN", "2"))
PRICE_OUT = float(os.getenv("PRICE_OUT", "10"))


def one_request(prompt, max_tokens=256):
    """返回 (首token耗时, 总耗时, 输出token数, 输入token数)。"""
    t0 = time.perf_counter()
    first = None
    out_tokens = 0
    in_tokens = 0

    stream = client.chat.completions.create(
        model=MODEL, max_tokens=max_tokens, temperature=0, stream=True,
        stream_options={"include_usage": True},
        messages=[{"role": "user", "content": prompt}],
    )
    for chunk in stream:
        if chunk.choices and chunk.choices[0].delta.content:
            if first is None:
                first = time.perf_counter() - t0
            out_tokens += 1
        if getattr(chunk, "usage", None):
            in_tokens = chunk.usage.prompt_tokens

    return first or 0.0, time.perf_counter() - t0, out_tokens, in_tokens


def bench(prompts):
    results = []
    lock = threading.Lock()

    def worker(p):
        r = one_request(p)
        with lock:
            results.append(r)

    threads = []
    t_start = time.perf_counter()
    for i, p in enumerate(prompts):
        t = threading.Thread(target=worker, args=(p,))
        t.start()
        threads.append(t)
        if len(threads) >= CONCURRENCY:
            for t in threads:
                t.join()
            threads = []
    for t in threads:
        t.join()
    wall = time.perf_counter() - t_start

    ttft = sorted(r[0] for r in results)
    total_out = sum(r[2] for r in results)
    total_in = sum(r[3] for r in results)
    cost = (total_in * PRICE_IN + total_out * PRICE_OUT) / 1_000_000

    print(f"请求数 {len(results)}  并发 {CONCURRENCY}  墙钟 {wall:.2f}s")
    print(f"吞吐 {total_out / wall:,.0f} token/s")
    print(f"首token 中位 {ttft[len(ttft) // 2] * 1000:.0f}ms "
          f"P99 {ttft[int(len(ttft) * 0.99) - 1] * 1000:.0f}ms")
    print(f"输入 {total_in} 输出 {total_out} token  成本 ${cost:.5f}")
    print(f"单位成本 ${cost / max(total_out, 1) * 1_000_000:.4f} / 百万输出 token")


if __name__ == "__main__":
    demo = ["用一句话解释什么是 KV 缓存。"] * int(os.getenv("N_REQ", "32"))
    bench(demo)
```

两个使用要点：**首 token 延迟必须单独测**，它决定交互体感，而吞吐指标完全反映不出来；**单位成本要按输出 token 折算**，这样不同输出长度的负载之间才可比。

还有一处容易漏测：**并发下的稳定性**。上面的脚本把并发固定为一个值，实际评估时应当扫一遍并发档位，观察吞吐的拐点——吞吐通常随并发上升，但到达某一点后会因为显存压力或调度开销而回落，而尾延迟往往在那之前就开始劣化。找到这个拐点比记住一个吞吐峰值有用得多，因为它是**容量规划的实际依据**：单卡能承载多少并发，应当由拐点前的区间决定，而不是由峰值吞吐倒推。

评估时还应当区分**输入密集**与**输出密集**两类负载。前者瓶颈在 prefill（长文档理解、长上下文推理），后者瓶颈在 decode（长文生成、代码补全）。两类负载的最优批处理策略不同，混在一台机器上会互相干扰——这也是分层部署的一个理由：把同类负载聚在一起，比追求单机通吃更容易把资源利用率做上去。

## 九、成本与风险提示

- **吞吐数字依赖负载形态**，引用任何提速倍数时都要核对测试条件（输入输出比、批大小、序列长度）。
- **端侧持续生成存在静默失效风险**，必须限制连续次数与长度，并在客户端加看门狗。
- **多目标优化要显式给非成本目标加权**，否则本地执行、离线可用这类价值会被纯成本目标挤掉。
- **自建要按峰值而非均值算成本**，峰值期间的闲置是真实开销。
- **API 的有效单价低于标称价**，缓存、批处理与分层路由都能压低它，比较前先把自己的有效单价算出来。
- **引擎层的收益是结构性的**，会长期保留；补贴带来的价差是阶段性的，不要把两者混为一谈；
- **容量规划要看拐点而不是峰值**。吞吐峰值对应的并发往往已经伴随尾延迟劣化，可持续的负载应当落在拐点之前的区间，否则高峰期会集中出现超时。

## 结论

单卡每分钟 10 亿 token 这个数字，真正有意义的部分是它出现在**引擎层**——没有换硬件，也没有换模型，靠查询感知的调度把成本再压了一个数量级。这解释了为什么 GPU 租价翻倍与 AI 价格下降可以并存：差额被效率、利用率与补贴吸收，而其中效率这一项是结构性的、会长期保留。对使用方，可操作的顺序是先把有效单价压下来（缓存、批处理、分层路由），再看剩余用量是否值得自建；对做端侧推理的团队，则要先解决热约束下的静默失效，并在多目标里显式给本地执行留出权重。三层成本里，引擎层是唯一"不动模型、不换硬件"就能拿到数量级收益的地方，因此值得优先投入工程精力；硬件层的议价空间与模型层的能力取舍，都应当排在它之后考虑。我在 4sapi.com 上按这个顺序评估时，最有用的结论往往不是"该不该自建"，而是"做完分层之后，自建的必要性还剩多少"。
