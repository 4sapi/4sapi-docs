# 【大模型API中转站】[第172期] Pro 订阅暂停启示｜旗舰供给紧张期的接入策略

旗舰模型的供给从来不是恒定的：订阅会停售，配额会收紧，延迟会抖动。当业务把全部流量押在同一个旗舰模型上，供给端的每一次收紧，都会直接变成线上事故。

## 一、一次订阅暂停带来的被动

我注意到，OpenAI 因为 GPT-6 Astra 的需求压力暂停了 $200/月 的 Pro 订阅，同时 GPT-6 Astra 正在向 Pro、Plus、Enterprise、Business 各档位推开。消息本身一句话就能说完，背后的含义却值得琢磨：旗舰模型的算力是有限资源，需求一膨胀，供给分配方式就会调整，订阅这种"看起来最稳"的形态，同样会被暂停或重新分配。

我在 4sapi 做接入层的日常维护，对这种压力并不陌生。新旗舰模型上线时最常见的剧本是：接入当天一切正常，三天后配额收紧，一周后延迟开始抖动，业务方在群里追问报表为什么没跑出来。问题的根源往往不是模型不好，而是接入架构把全部希望押在了一条供给通道上。

单点依赖的代价分两层。第一层是可用性：停售、限流、超时，任何一种都会让依赖它的任务直接失败，而且失败来得毫无预兆。第二层是节奏：为了保住仅剩的配额，高价值的规划审查任务和低价值的日常摘要混在同一个队列里，真正重要的请求反而抢不过琐事。订阅停售只是把这两层代价一次性摆上了台面。

## 二、供给紧张的三种形态

第一种形态是订阅停售。$200/月 的 Pro 订阅暂停，意味着原本靠订阅额度运转的日常任务瞬间失去输入。订阅的特点是先付钱、后用量，供给一旦停售，手里没有任何可调节的杠杆，只能等待重新开放，或者把存量任务迁到按量计费的通道上。停售考验的是供给结构的多样性。

第二种形态是配额降档。档位没变，密钥还能用，但单位时间内的可用量被下调，或者高峰期的优先级被压低。这种形态更隐蔽：合同还在，账单照付，限额错误却开始零星出现。很多团队第一次发现，是在周五晚上批处理任务集中触发限额的时候。配额降档考验的是水位监控的灵敏度。

第三种形态是延迟抖动。请求仍然成功，但 P95 延迟从两秒漂到十几秒，超时率上升，重试风暴随之而来，而重试本身又会加剧拥堵，形成恶性循环。延迟抖动是最容易被忽略的形态，因为它不报错，只是变慢，直到下游的超时机制把"变慢"翻译成"失败"。延迟抖动考验的是超时预算与退避策略的设计。

三种形态对应三种信号：停售看供给结构，配额看水位，延迟看质量分布。接入架构如果只按"能不能调通"来设计，三种形态里至少有两种会漏。

## 三、原理速览：一条请求的完整旅程

把防御体系串起来，一条请求的完整旅程是这样的：

```text
业务请求（带任务类型标记）
   |
   v
按任务分级查找模型链：旗舰 → 中档 → 轻量
   |
   v
检查配额水位与健康探测
   |
   v
主模型（旗舰）──成功──> 返回结果，记录审计
   |
   | 失败 / 超时 / 限额
   v
降档模型（中档）──成功──> 返回结果 + 降级标记
   |
   | 失败 / 超时 / 限额
   v
轻量模型 ──成功──> 返回结果 + 强降级标记
   |
   | 失败
   v
进入排队队列，按退避节奏等待恢复，或返回明确降级说明
   |
   v
全程审计日志与告警：每次选择、每次降档、每次排队都留痕
```

这张图里最值得强调的是两件事。其一，"检查配额水位"发生在选模型之前：水位低于阈值时直接跳过旗舰，省掉一次注定失败的重试，也把宝贵的窗口留给真正的旗舰任务。其二，排队队列是正式成员，不是兜底的遮羞布：排队事件要有 ID、有预计等待时长、有恢复通知，业务方拿到的应该是一个有状态的过程，而不是一个黑洞。

## 四、三层防御：路由层、预算层、体验层

第一层是路由层，核心动作是把多模型能力做成基础设施。旗舰模型做规划与审查，中档模型做常规执行，轻量模型做摘要与格式化，每类任务都有自己的模型链和自己的优先级顺序。路由层的入口最好收敛到一处，例如把密钥与模型清单统一托管在 https://4sapi.com 这类 OpenAI 兼容的聚合中转站上，上游更换模型时，业务代码不需要改动，只改配置。

第二层是预算层，核心动作是给任务分层额度。规划与审查类任务配最高预算，执行类任务配中等预算，摘要与格式化类任务配最低预算。预算不只是钱，还包括每类任务允许的重试次数、超时上限和可接受的降档幅度。没有分层额度，一次重试风暴就能把当月账单打穿；有了分层额度，成本波动才有上界。

第三层是体验层，核心动作是让降级可见、可控、可解释。降级不是失败，但必须是显式的：响应里带标记，指标里单独计数，必要时告知业务方当前处于降档状态。排队等待也是体验层的一部分——供给紧张期让请求有序排队，比无限制重试更体面，也更有效。

三层防御的共同点是：都不依赖某一家供应商的善意。路由层假设主模型会失效，预算层假设用量会失控，体验层假设降级会发生。假设越保守，系统越稳。

## 五、路由设计的五个要点

**要点一：按任务分级，而不是按用户分级。** 旗舰模型的价值在于深度推理与质量审查，执行与摘要类任务用它属于浪费，也在不必要地挤占稀缺供给。分级的第一步是给任务打标：规划、审查走旗舰优先；常规执行走中档优先；摘要、格式化、分类走轻量优先。打标本身要成为调用协议的一部分，而不是口头约定。

**要点二：失败预算要写成参数。** 一次业务请求允许消耗多少时间、允许重试几次、允许降档到哪一档，都要在路由器里集中配置，而不是散落在各处代码里。失败预算耗尽之后应该进入排队或显式失败，而不是无限重试——无限重试在供给紧张期只会放大拥堵。

**要点三：会话粘性要保留。** 同一个会话降档换模型后，后续轮次尽量沿用同一个模型，避免上下文在两个模型之间反复横跳，导致风格漂移与重复解释。粘性绑定会话 ID，并设置释放时间，避免长期占住已经恢复的旗舰额度。

**要点四：静默降级要打标记。** 降档模型返回的响应，必须在响应元信息里带上降级标记与实际服务的模型名。标记是后续三件事的原料：账单按模型归因、评测按降档口径回归、业务侧在必要时收到告知。没有标记的降级，等于把质量问题悄悄埋进生产。

**要点五：恢复探测要自动。** 被熔断跳过的模型，需要低成本探测机制判断恢复：用极小的探针请求周期性试探，成功后逐步放量，而不是等人工发现再去改配置。恢复探测和熔断是一对，缺了任何一个，路由器都会停在错误的状态上。

## 六、接入教程：一个最小故障转移路由器

下面这段 Python 示例，以 4sapi 提供的 OpenAI 兼容接口为例，实现一个最小但完整的故障转移路由器，覆盖模型优先级列表、超时与重试预算、按任务的模型映射、熔断标记与恢复探测。任何 OpenAI 兼容的上游都可以套用同样的结构。

```python
import time
import logging
import openai

logging.basicConfig(level=logging.INFO)
log = logging.getLogger("failover-router")

# OpenAI 兼容入口：base_url 指向中转站，密钥在控制台创建后放入环境变量
BASE_URL = "https://4sapi.com/v1"
client = openai.OpenAI(base_url=BASE_URL, api_key="sk-xxx")

# 模型优先级列表：从旗舰到轻量，成本由高到低，名称按实际上游替换
MODEL_CHAIN = ["flagship-model", "mid-tier-model", "lite-model"]

# 按任务的模型映射：规划与审查坚持旗舰优先，执行与摘要直接从低档起步
TASK_CHAIN_MAP = {
    "plan_review": ["flagship-model", "mid-tier-model"],
    "execute": ["mid-tier-model", "lite-model"],
    "summarize": ["lite-model", "mid-tier-model"],
}

TIME_BUDGET_SECONDS = 30        # 单次请求整条链路的时间预算
BREAKER_THRESHOLD = 3           # 连续失败多少次后熔断
BREAKER_COOLDOWN_SECONDS = 120  # 熔断冷却时长，期间跳过该模型

breaker = {name: {"fails": 0, "opened_at": 0.0} for name in MODEL_CHAIN}


class ModelUnavailableError(RuntimeError):
    """整条模型链不可用时抛出，由上层决定进入重试队列或显式降级。"""


def model_available(name: str) -> bool:
    state = breaker[name]
    if state["fails"] < BREAKER_THRESHOLD:
        return True
    # 冷却结束后放行一次探测请求，成功即恢复，失败则重新计时
    return time.time() - state["opened_at"] > BREAKER_COOLDOWN_SECONDS


def record_result(name: str, ok: bool) -> None:
    state = breaker[name]
    if ok:
        state["fails"] = 0
        return
    state["fails"] += 1
    if state["fails"] >= BREAKER_THRESHOLD:
        state["opened_at"] = time.time()
        log.warning("model %s enters cooldown after repeated failures", name)


def route(task_type: str, messages: list) -> dict:
    chain = TASK_CHAIN_MAP.get(task_type, MODEL_CHAIN)
    deadline = time.monotonic() + TIME_BUDGET_SECONDS
    last_error = None
    for name in chain:
        if not model_available(name):
            log.info("skip %s: breaker open", name)
            continue
        try:
            resp = client.chat.completions.create(
                model=name,
                messages=messages,
                timeout=max(3.0, deadline - time.monotonic()),
            )
            record_result(name, ok=True)
            # 静默降级不可取：命中非首选模型时必须打标记，供评测、账单与告知使用
            return {
                "content": resp.choices[0].message.content,
                "served_by": name,
                "primary": chain[0],
                "degraded": name != chain[0],
            }
        except Exception as exc:  # 超时、限额、5xx 均计为一次失败
            record_result(name, ok=False)
            last_error = exc
            log.warning("call %s failed: %s", name, exc)
    # 失败预算耗尽：进入带退避的重试队列等待恢复，不绕过限制，也不无限重试
    raise ModelUnavailableError(
        f"task={task_type} chain_exhausted last_error={last_error}"
    )
```

几处细节值得展开。base_url 指向 https://4sapi.com 的 /v1 路径后，chat.completions 的调用方式与直连 OpenAI 完全一致，换模型只改配置不改代码；中转站一侧同样可以配置多模型路由，把故障转移再往上提一层，业务侧路由与中转侧路由互为备份，单层失效仍有兜底。

`route()` 返回字典里的 `served_by` 与 `degraded` 两个字段，必须原样写进业务日志与指标。它们是三件事的原料：账单按模型归因，评测按降档口径回归，业务方在必要时收到"当前处于降档状态"的告知。

`ModelUnavailableError` 抛出后，调度层应把请求放进带 TTL 的重试队列，按指数退避等待，同时触发告警。等待恢复是正当操作，供给紧张期尤其如此——队列的长度本身就是一条值得监控的指标。

## 七、成本对比：三种策略的账本

下面用一套统一的估算口径比较三种接入策略：以旗舰模型完成一个标准任务的 token 成本为基准 1.0，中档模型按 0.25 计，轻量模型按 0.05 计；失败重试成本按失败概率乘以单次成本累计；质量差价按返工率与人工校验的折算成本估算。表中所有数字均为示例估算，实际以各家牌价与账单为准。

| 策略 | 单任务 token 成本（估算） | 失败重试成本（估算） | 质量差价（估算） | 综合评价 |
| --- | --- | --- | --- | --- |
| 全旗舰 | 1.00 | 低（约 0.05） | 最低 | 成本最透明，但供给紧张期最先被限流，可用性最差 |
| 分级路由 | 约 0.35 | 中（约 0.10） | 低（约 0.05，集中在降档任务） | 旗舰留给规划与审查，对供给波动的敏感度最低 |
| 全便宜模型 | 约 0.08 | 高（约 0.25，返工率上升） | 最高（返工与校验成本显著上升） | 账单好看，质量账单与人力账单难看 |

表格传达三条结论。其一，全旗舰策略的账面成本最高，风险也最集中：成本确定的前提是供给确定，而供给恰恰是最不可控的变量。其二，分级路由把成本花在刀刃上，多出来的失败重试成本，本质是给可用性买的保险。其三，全便宜模型的隐性成本藏在质量差价里，返工、人工校验和线上质量事故折算下来，未必真的便宜。账要一起算，不能只看 token 单价那一列。

## 八、成本与风险提示

成本端最大的风险，是降档省下的钱被返工花回去。降档模型的输出差异不总是坏事，但必须被度量：同一批任务分别用旗舰与降档模型跑一遍评测集，差异可接受才允许降档进入常规路径，差异不可接受就收紧该任务的降档边界。评测回归应在供给平稳期建好，供给紧张时才临时搭，来不及。

风险端有两条红线。第一条，降级必须告知而不是静默：业务方拿到的响应要么带降级标记，要么收到明确说明，静默降级会让质量问题在不知情中进入生产。第二条，不把精力花在绕过官方限制上：多账号轮换、滥用试用额度一类操作，既违反服务条款，也会让审计与账单彻底失控。排队等待与正当降级，才是供给紧张期的正确姿势。

还有一条容易被忽略的合同风险：配额弹性要写进采购条款。能谈出高峰期临时扩容的条款，就比只有固定配额的条款多一层缓冲；能维持多供应商并行供给，就比单一独家供给多一层保险。条款平时用不上，紧张期就是缓冲垫。

## 九、供给紧张自查清单

供给紧张来临之前，按这份清单逐项自查：

1. **订阅依赖度盘点**：列出所有依赖订阅额度运转的任务线，估算订阅停售后有多少任务失去供给；占比超过三成，就应把其中一部分迁到按量计费通道上。
2. **配额水位监控**：为每个模型、每个密钥配置额度与水位告警，阈值设在限额的七成左右，为处置留出时间；水位指标要区分按分钟的突发和按天的累计。
3. **备选模型清单**：每类任务至少准备一条降档链，写清楚备选模型的上下文长度、接口差异和已知短板，不要等到切换当天才发现上下文装不下。
4. **降级预案演练**：定期人为熔断主模型，观察路由器行为、降级标记与业务告知是否符合预期；没有演练过的预案，等于没有预案。
5. **合同与额度弹性**：确认合同里有高峰扩容或临时增购条款，确认账单体系能按任务类型归因成本；弹性条款平时用不上，紧张期就是缓冲垫。

五项全部通过，供给紧张才只是"一次波动"；缺任何一项，它都会升级成"一次事故"。

## 十、降级之后：评测回归与告知义务

降级不是路由器的终点，而是一系列后续动作的起点。

第一件事是评测回归。每次降档发生时，把命中降档的任务抽样进入评测集，与旗舰模型的基线输出对比，重点看结构化输出的格式稳定性、长上下文任务的遗漏率、多轮任务的指令遵从。回归结果决定降档模型能否继续留在这条任务链上，也决定降档边界要不要收紧。回归要持续做，因为模型版本更新本身也会移动基线。

第二件事是业务告知。对内部业务方，告知可以是仪表盘上的降级徽标加一封自动通知；对外产品，告知要遵循产品自己的承诺口径，至少保证"当前由备选模型提供服务"这件事不隐瞒。告知的颗粒度可以粗，事实必须真。

第三件事是事后复盘。紧张期结束后，把整个事件的时间线拉出来：信号什么时候出现、路由器什么时候切换、队列什么时候清空、哪些任务的降档超出了预期边界。复盘产出物是后续架构调整的输入，例如把某类任务的降档链从两档扩到三档，或者把某类任务重新收紧回旗舰。

## 十一、总结

这一期想沉淀的结论很简单：供给紧张不是异常状态，而是旗舰模型时代的常态。订阅会停售，配额会收紧，延迟会抖动，应对方式不是祈祷，而是架构——路由层用多模型拆掉单点依赖，预算层用分层额度管住失控重试，体验层用显式降级和有序排队保住业务节奏。我在 4sapi 的接入实践里反复验证过一个顺序：先给任务打标，再建模型链，再配水位告警，最后演练降级预案，缺任何一步，紧张期都会更疼。对分级路由、熔断参数或评测回归如果有不同做法，欢迎在评论区聊聊。
