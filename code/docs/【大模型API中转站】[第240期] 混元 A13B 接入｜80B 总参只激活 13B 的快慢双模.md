# 【大模型API中转站】[第240期] 混元 A13B 接入｜80B 总参只激活 13B 的快慢双模

腾讯把 Hunyuan-A13B 开源出来，给出的数字很有指向性：总参 80B，推理时只激活 13B。

我在 4sapi（https://4sapi.com）上把这款模型接进去跑了一轮，最直接的体会是：稀疏激活管的是单位算力成本，双模式思维链管的是单任务成本，两件事分属不同层级，混在一起谈就会得出相反的结论。

## 一、三个数字看懂 A13B

Hunyuan-A13B 是腾讯发布的开源大模型，底座是 Mixture-of-Experts（MoE）架构，在模型能力、计算效率与部署成本之间取平衡。看这款模型只需要抓住三个数字。

第一个数字是 80B，总参数量。它决定知识容量与能力上限：参数量越大，可容纳的模式越多，在数学、科学、编程这类需要长程推理的任务上越有余量。

第二个数字是 13B，推理时每个 token 实际参与计算的参数量。它决定单位算力成本：前向计算只走被路由选中的那部分专家，算力开销按 13B 的量级计，而不是按 80B 的量级计。

第三个数字是 2，也就是双模式思维链提供的两种推理深度。它决定单任务成本：同一个问题，快思考用几十个输出 token 收尾，慢思考可能要几百甚至上千个输出 token，而输出 token 恰恰是按较高单价计费的那部分。

三个数字各管一层。只盯着 80B，会高估部署门槛；只盯着 13B，会低估显存占用；只盯着吞吐，会忽略输出 token 膨胀带来的费用上升。

## 二、训练侧的两个抓手

预训练语料是经过严格过滤的 20T token，并强化了 STEM 数据策展。这一步的目标不是把语料堆大，而是把事实可靠性与推理能力提上来。在需要严格过滤的领域，语料质量比语料规模更能决定回答的稳定性。

训练流程包含高质量的监督微调与大规模强化学习。SFT 负责把基础能力对齐到指令跟随的格式上，RL 负责在可验证的任务上继续抬高上限。两段叠加之后，模型在数学、科学、编程、通用语言理解与 agent 任务上的表现具有竞争力，常常接近规模更大的模型；推理吞吐也维持在较高水平，适合延迟敏感的场景。

发布目的同样直接：支持开放研究与实践部署。这句话对工程侧的含义是，权重可获取、可自部署，同时也能通过托管服务调用，两条路径都成立，取舍点不在能不能用，而在哪条路径的单位成本更低。

## 三、稀疏激活的计算路径

把一次前向拆开看，MoE 的稀疏性集中出现在 FFN 层：

```text
输入 token 序列
      |
Embedding + 注意力层（所有 token 共享，全量参与计算）
      |
Router / Gate 打分（每个 token 得到一组专家权重）
      |
Top-k 专家选择（每个 token 只走少数几个专家）
      |
被选中的专家执行 FFN（其余专家常驻显存但不参与计算）
      |
专家输出按权重合并
      |
下一层 / 最终输出
```

关键点在两处。第一，注意力层与 Router 是共享结构，这部分开销与总参无关，而与序列长度和隐层宽度相关。第二，专家权重必须常驻显存，但只有被选中的专家参与计算。

所以"80B 总参、13B 激活"翻译成工程语言是：显存按 80B 的量级准备，算力按 13B 的量级消耗。这解释了稀疏模型在延迟敏感场景里的优势——单 token 的矩阵乘规模小，decode 阶段的显存带宽压力下降，吞吐自然抬高；也解释了它为什么不能省显存——专家是静态资源，按需换进换出会付出额外代价。

## 四、三层成本模型

把成本拆成三层，每一层的抓手完全不同。

第一层，能力上限由总参决定。这一层几乎没有优化空间，只能选型：80B 的总参换来接近更大规模模型的表现，需要这个能力就得接受对应的显存门槛。

第二层，单位算力成本由激活参数决定。同一台机器上，13B 激活意味着每个 token 的浮点运算量约为 80B 全量激活的六分之一左右（按激活参数比例估算，未计入注意力层开销）。这一层的抓手是量化与批处理：权重精度从 FP16 降到 FP8 或 INT4，显存占用与带宽需求同步下降，吞吐随之上升。

第三层，单任务成本由推理深度决定。这一层的抓手是任务分流与提示词纪律：一个多步问题如果被快思考草率收尾，返工重问的代价会超过慢思考一次做对的代价；反过来，一个格式转换任务如果走了慢思考，中间推理文本会把输出 token 抬高数倍，而收益为零。

三层之间是乘法关系，不是加法关系。选型错在第一层，后两层怎么调都补不回来；分流错在第三层，第一层投入的能力会被输出 token 慢慢吃掉。

## 五、快慢双模的适用任务对照

双模式思维链的做法是按任务复杂度调节推理深度：常规查询走快思考，复杂多步问题走慢思考。落到工程里，判断标准不是任务听起来难不难，而是任务是否需要中间步骤。

| 任务类型 | 建议模式 | 判断依据 | 成本特征 |
| --- | --- | --- | --- |
| 分类、意图识别、字段抽取 | 快思考 | 单步完成，答案极短 | 输出 token 少，单任务开销低 |
| 格式转换、改写、摘要 | 快思考 | 规则明确，正确性可校验 | 输出长度与输入规模相关 |
| 检索结果归纳、简单问答 | 快思考 | 答案在给定材料之内 | 延迟敏感，吞吐优先 |
| 多步数学与逻辑推导 | 慢思考 | 需要中间步骤与自检 | 输出 token 显著增多 |
| 代码生成与调试 | 慢思考 | 需要试错与边界检查 | 一次做对省下的返工更值 |
| 长链条 agent 规划与工具编排 | 慢思考 | 单步错误会放大到整条链 | 关键链路不降档 |
| 批量离线数据加工 | 按复杂度分流 | 先抽样标定再定规则 | 分流比例决定总开销 |

可执行的落地顺序是：先全量走慢思考跑出质量基线，再逐类任务试降快思考，用抽检守门。降档省下的是输出 token，赔进去的是返工，只有当返工带来的额外开销低于降档收益时，这次降档才算成立。

## 六、显存与吞吐的估算方法

自建部署之前先做两道估算。以下全部是工程口径的估算，用于判断可行性，不是实测数据。

显存估算的核心纪律是：权重按总参算，不按激活参数算。80B 参数在 FP16 下约 160GB，FP8 下约 80GB，INT4 下约 40GB，再叠加 KV cache 与激活峰值，实际需要预留比权重更高的余量。

| 权重精度 | 权重占用（估算） | 单机可行性（估算） | 说明 |
| --- | --- | --- | --- |
| FP16 | 约 160GB | 需要多卡 | 精度最好，门槛最高 |
| FP8 | 约 80GB | 大显存单卡或多卡 | 常见折中档 |
| INT4 | 约 40GB | 单机可放 | 需要验证精度损失 |

吞吐估算可以用一条粗公式：每 token 需要读取的激活参数量，乘以精度字节数，再除以有效显存带宽。13B 激活配 INT8 精度，意味着每 token 大约读取 13GB 量级的权重数据，带宽越高，单序列速度越快。批处理能摊薄权重读取成本，但会同步抬高 KV cache 压力，两者存在对冲。这条公式给出的是上界，实际还要打折扣，估算值只用来判断方案是否可行，不能用来承诺性能。

## 七、接入示例：按复杂度切换推理模式

接入部分用 OpenAI 兼容格式走一遍，Key 从环境变量读取，不写进代码文件。

```python
import os
from openai import OpenAI

client = OpenAI(
    api_key=os.getenv("FOURSAPI_API_KEY"),
    base_url=os.getenv("FOURSAPI_BASE_URL", "https://4sapi.com/v1"),
)

MODEL = "hunyuan-a13b"  # 模型名以服务侧模型列表为准

FAST_HINT = "直接给出结果，不展开中间过程，输出尽量简短。"
SLOW_HINT = "先写出推理步骤，再给出结论，步骤之间做一次自检。"

COMPLEX_MARKERS = ("证明", "推导", "重构", "多步", "权衡", "为什么")
LONG_TASK_CHARS = 300


def pick_mode(task: str) -> str:
    """粗分流：多步或长任务走慢思考，其余走快思考。"""
    if any(m in task for m in COMPLEX_MARKERS) or len(task) > LONG_TASK_CHARS:
        return "slow"
    return "fast"


def run_one(task: str, mode: str | None = None) -> dict:
    mode = mode or pick_mode(task)
    # 部分服务侧暴露了显式思考开关，参数名以文档为准；
    # 这里用系统提示词控制推理深度，兼容性最好。
    resp = client.chat.completions.create(
        model=MODEL,
        messages=[
            {"role": "system", "content": SLOW_HINT if mode == "slow" else FAST_HINT},
            {"role": "user", "content": task},
        ],
        temperature=0.6 if mode == "slow" else 0.2,
        max_tokens=2048 if mode == "slow" else 256,
    )
    usage = resp.usage
    return {
        "mode": mode,
        "prompt_tokens": usage.prompt_tokens,
        "completion_tokens": usage.completion_tokens,
        "text": resp.choices[0].message.content,
    }


def run_batch(tasks: list[str]) -> dict:
    """按模式分组累计 token 用量，用来观察推理深度对开销的影响。"""
    stats: dict[str, dict[str, int]] = {}
    for task in tasks:
        r = run_one(task)
        bucket = stats.setdefault(r["mode"], {"count": 0, "in": 0, "out": 0})
        bucket["count"] += 1
        bucket["in"] += r["prompt_tokens"]
        bucket["out"] += r["completion_tokens"]
    return stats


if __name__ == "__main__":
    tasks = [
        "把这段返回结果转成 JSON，字段固定为 id、status、msg。",
        "给出三种缓存策略的权衡，并推导在命中率变化时的成本曲线。",
    ]
    for mode, s in run_batch(tasks).items():
        avg_out = s["out"] / s["count"]
        print(f"{mode}: 任务数={s['count']} 输入={s['in']} 输出={s['out']} 平均输出={avg_out:.0f}")
```

这段示例做了三件事：从环境变量取 Key 与接入地址；用关键词与长度做一次粗分流，决定走快思考还是慢思考；把 usage 里的输入与输出 token 按模式分组累计。第三件事最关键，因为推理深度的影响只体现在输出 token 上，不看这一项就无法验证分流是否真的省下了开销。

跑通之后建议先看两个数：慢思考任务的平均输出 token 是不是显著高于快思考，以及快思考任务的返工率是否可接受。前者确认分流生效，后者确认质量没有塌。

## 八、本地部署与走 API 中转的取舍

两条路径没有绝对优劣，差别在于负载形态与数据边界。

| 维度 | 本地或自建部署 | 走 API 中转 |
| --- | --- | --- |
| 初始投入 | 需要 GPU 采购或长期租用，权重常驻显存 | 无硬件投入，按量付费 |
| 单位成本 | 固定成本摊薄，满载时边际成本低 | 随用随付，闲置时不产生费用 |
| 负载适配 | 适合高频稳定负载 | 适合验证期与波动负载 |
| 弹性 | 受自有卡数限制 | 并发可随业务伸缩 |
| 运维负担 | 量化、显存、并发、升级都要自己扛 | 由服务侧承担 |
| 数据边界 | 数据不出内网，便于内控 | 数据经过中转与上游，需要事先确认边界 |
| 模式控制 | 采样参数与提示词完全自控 | 参数覆盖范围以服务侧为准 |
| 适合的起点 | 高频稳定、数据敏感、需要深度定制 | 快速验证、成本试算、先看真实 token 分布 |

一个务实的组合是：先用中转把分流比例、输出 token 分布和返工率标定出来，拿到真实的成本曲线，再决定要不要为固定负载自建。反过来先买卡再标定，很容易为一条并不高频的链路付出一整年的固定成本。

## 九、分层路由的决策树

把快慢双模落到工程里，需要一条明确的路由链，而不是靠工程师每次临场判断：

```text
请求进入
   |
是否命中规则（关键词、长度、上游标注）？
   |                        |
  是                        否
   |                        |
直接指定模式          取同类历史任务的默认模式
   |                        |
   +-----------+------------+
               |
        该任务是否需要中间步骤
          |                |
         否                是
          |                |
       快思考            慢思考
          |                |
   收紧输出上限       放宽输出上限
          |                |
          +-------+--------+
                  |
        记录 token 用量与质量抽检结果
                  |
        按周回看分流比例与返工率
                  |
        调整规则，而不是逐个改调用点
```

这条链的要点是最后一环：调整发生在规则层，而不是散落在各个调用点。分流规则一旦分散，成本看板就无法解释开销变化，也谈不上治理。

## 十、部署与接入检查清单

上线前按这个清单逐项确认：

1. 确认模型名、上下文长度与输出上限，以服务侧模型列表为准，不写死猜测值；
2. Key 从环境变量或密钥管理服务读取，确认仓库与日志里不出现明文；
3. 接入地址固定为 HTTPS，禁止把 base_url 散落在业务代码里；
4. 快慢模式给出默认值，关键链路默认慢思考，降档必须经过抽检；
5. 用 usage 记录输入与输出 token，并按模式分组统计；
6. 为每类任务设定输出 token 上限与请求超时，防止慢思考无限展开；
7. 自建部署先算显存：权重按总参算，再叠加 KV cache 与激活峰值；
8. 压测并发下的吞吐与首 token 延迟，确认延迟敏感场景的实际表现；
9. 快思考降档前做 A/B，用抽检结果而不是直觉决定是否保留；
10. 配置用量告警与限流，账号级额度留出波动空间。

## 十一、成本与风险提示

- 显存与吞吐的数字是工程估算，用于判断可行性，实际值受量化方案、批处理策略与硬件差异影响；
- 快思考误用是多步任务的隐性成本来源，返工一次的开销常常超过慢思考直接做对的差额；
- 慢思考的输出 token 膨胀同样需要约束，缺少输出上限时，简单任务的费用会被中间推理文本抬高；
- 自建部署的隐性成本容易被低估，包括人力、电力、闲置卡与版本升级带来的持续投入；
- 量化到 INT4 能显著降低显存门槛，但精度损失必须在真实任务上验证，不能只看通用评测；
- 走中转接入时，模式控制参数、输出上限的覆盖范围以服务侧为准，切换前先小流量验证；
- 数据边界需要事先确认，涉及敏感数据的链路要明确数据流向与留存策略，并保持合规；
- 模型与单价迭代很快，把模型名与价格做成配置项，而不是硬编码在业务逻辑里。

## 结论

Hunyuan-A13B 的成本结构可以拆成三层：80B 总参决定能力上限，13B 激活参数决定单位算力成本，快慢双模式思维链决定的推理深度决定单任务成本。三层是乘法关系，任何一层选错，另外两层的优化都会被吃掉。

工程上的动作也就三个：把任务按"是否需要中间步骤"分流，把输出 token 上限按模式分别设定，把用量按模式分组统计并定期回看。三件事都不复杂，但收益直接体现在费用曲线和返工率上。

在 4sapi（https://4sapi.com）上先把分流比例和 token 分布跑出来，再决定自建还是继续走托管，比反过来更省钱。欢迎在评论区聊聊手头任务里快思考与慢思考的分流比例，或者踩过的输出 token 失控的坑。
