# 【大模型API中转站】[第06期] 个人 Agent 搭建实录｜996 份问卷启示

个人 Agent 没有想象中复杂。一组文件管上下文，一些工具管能力，再接到 agentic 工具上，就能跑通日常任务。

作为 4sapi 团队的接入实战记录，我从一份 996 票的问卷出发，用一个周报 Agent 的完整搭建过程说明这套结构。

## 一、开篇：我该不该搭一个个人 Agent

"个人 Agent"这个词被炒了很久，但真正用过的人不多。

我在一份面向从业者的问卷里（996 票）看到，大多数人并没有把个人 Agent 用在日常——不是不想，是不知道从哪下手。大家卡在同一个问题：**个人 Agent 到底长什么样？要不要写一大套框架？**

这一期把我的实测结论先摆出来：**个人 Agent 不复杂，本质就是"一组文件 + 一些工具"，接到任何一个 agentic 工具上**。把邮件、日程、电脑操作这些日常活拆成文件与工具，就是完整的个人 Agent。

## 二、原理速览：个人 Agent 的三件套

一个最小可用的个人 Agent 只需要三样东西：

```text
① 文件层：任务描述、配置、记忆（Markdown / JSON / 脚本）
② 工具层：能做的动作（收发邮件、读写文件、跑脚本、查日程）
③ 执行层：agentic 工具（接上模型，把文件和工具串起来）
```

没有"重框架"，也没有"通用大脑"。每个文件负责一段上下文，每个工具负责一个动作，执行层负责调度。

### 文件层

```text
agent/
├── memory/          # 记忆：偏好、历史决策、常用命令
│   ├── prefs.md
│   └── decisions.md
├── tasks/           # 任务：每个任务一个文件
│   └── weekly-report.md
├── tools/           # 工具：可执行脚本或 API 封装
│   ├── fetch_mail.py
│   └── gen_report.py
└── config.json      # 模型、网关、默认参数
```

### 工具层

工具是个人 Agent 能力的边界。最常见的几类：

| 工具 | 用途 | 示例 |
| --- | --- | --- |
| 读写文件 | 知识库、模板、记录 | `read_file` / `write_file` |
| 执行脚本 | 定时任务、批处理 | `run_python` |
| 外部 API | 邮件、日历、OA | `send_mail` / `list_calendar` |
| 检索 | 本地文档问答 | `search_docs` |

## 三、方案：从零搭一个"周报 Agent"

用一个完整案例演示：周报 Agent，每周一把上周数据汇总成 Markdown。

### 3.1 准备文件与工具

```text
agent/tasks/weekly-report.md      # 任务说明（输出格式、数据源）
agent/tools/fetch_data.py         # 拉取数据
agent/tools/gen_report.py         # 生成报告
agent/memory/prefs.md             # 偏好（要包含健康度指标）
```

`weekly-report.md`：

```markdown
# 周报任务
数据源：agent/data/week-*.csv
输出：agent/reports/weekly-YYYY-MM-DD.md
格式：本周概览、关键指标、风险项、下周计划
偏好：只写有变化的指标，不罗列全部数字
```

### 3.2 工具实现

```python
# tools/gen_report.py
import csv
import json
import sys

def main(week: str):
    rows = list(csv.DictReader(open(f"data/week-{week}.csv", encoding="utf-8")))
    # …… 计算指标
    md = f"# 第 {week} 周概览\n"
    md += f"- 完成项: {len([r for r in rows if r['status']=='done'])}\n"
    open(f"reports/weekly-{week}.md", "w", encoding="utf-8").write(md)
    print(json.dumps({"ok": True, "file": f"reports/weekly-{week}.md"}))

if __name__ == "__main__":
    main(sys.argv[1])
```

工具输出结构化状态（`{"ok": true, ...}`），agentic 工具能直接读懂。

### 3.3 接入执行层

把文件与工具接到执行层（我用统一网关模型，见后文），prompt 只需要一句：

```
读 tasks/weekly-report.md 的任务说明，调用 fetch_data.py 拉数据，
再用 gen_report.py 生成报告，最后校验输出文件存在。
```

模型负责编排，文件负责上下文，工具负责执行——每一层都薄，但合起来能干活。

## 四、把 Agent 接入日常：多任务与调度

周报跑通后，第一步是让 Agent 进入日常节奏：

```text
定时触发（每周一 09:00）
   ↓
读取本周任务清单 tasks/
   ↓
按任务调用对应工具
   ↓
输出产物写回 reports/
   ↓
失败重试（幂等 + 有限次数）
```

### 4.1 定时与触发

```python
import schedule
import time

def weekly_job():
    run_agent("tasks/weekly-report.md")

schedule.every().monday.at("09:00").do(weekly_job)

while True:
    schedule.run_pending()
    time.sleep(60)
```

### 4.2 任务清单即待办

每个新活加一个任务文件，Agent 只认 `tasks/*.md`：

```markdown
# 任务：合并月度账单
数据源：data/bills-*.csv
输出：reports/bill-summary-YYYY-MM.md
依赖：需先运行 tools/fetch_bills.py
```

任务文件是 Agent 的"需求文档"，工具是它的"执行手段"，别让模型自由发挥超出任务文件的范围。

## 五、成本和风险：个人 Agent 也要算账

- **模型费**：周报这类任务，一次完整推理成本可控，但每天高频任务要留意；
- **工具误操作**：能跑脚本 = 能改文件，个人 Agent 要在受限目录运行，别给系统级权限；
- **记忆漂移**：文件记忆久了会过时，定期清理 tasks 与 memory；
- **合规**：涉及公司数据、同事信息的任务，先确认权限边界。

### 我的成本控制

1. **优先小模型**：周报、格式化、抽取这类任务直接走小模型（见第 03 期）；只有复杂推理才上大模型；
2. **请求走统一网关**：多模型路由、限流、计费集中于一处，账单可拆分（https://4sapi.com 就是我用于统一管理的网关）；
3. **任务级预算**：每个任务设 token/费用上限，超限熔断；
4. **缓存结果**：同一数据源的中间结果落盘，重复任务不重复付钱。

## 六、安全与权限：能跑脚本就能改文件

个人 Agent 能执行脚本，就意味着它能改文件、发请求、删东西。权限边界必须在接入前划清：

- **工作目录隔离**：只允许 Agent 读写 `agent/` 目录，禁止系统级路径；
- **只读优先**：破例前先用只读版本跑通流程；
- **动作白名单**：所有写操作（发邮件、删文件、改配置）一律人工确认；
- **敏感操作禁用**：不把云凭证、支付信息交给 Agent 的脚本。

```text
工具调用 -> 权限检查（目录/动作白名单）
           ├── 只读操作 -> 直接执行
           ├── 可回滚写入 -> 写入 agent/ 内
           └── 外发/删除 -> 请求确认后才执行
```

个人 Agent 的定位是"提高效率"，不是"代替判断"。越靠近真实资金和他人数据，越要保持人的参与。

## 七、泡了三天实测排错清单

搭建过程中踩过的坑，整理成清单：

1. 工具输出不结构化 → 脚本统一输出 JSON，执行层好解析；
2. 文件路径硬编码 → 全部相对 agent/ 目录，换机器不碎；
3. 模型把任务文件当上下文塞爆 → 任务文件控制在一页以内，长文档放 tools 里按需读；
4. 记忆文件越来越大 → 按主题分文件，别全堆一个 prefs.md；
5. 断电重跑失败 → 工具幂等：生成报告前先删旧文件；
6. 多模型切换参数不兼容 → 用 OpenAI 兼容格式统一请求，网关层做转换。

## 八、进阶：从"脚本编排"到"记忆驱动"

个人 Agent 用顺了之后，可以加一层"决策记忆"：

```text
memory/decisions.md
# 2026-08-24 决定：周报改用双指标视图
# 2026-08-10 决定：日报停用，信息已并入周报
```

执行时让模型先读 `decisions.md` 再动手，避免重复踩坑。这比"重新训练"便宜得多——**记忆是文件，不是参数**。

## 九、个人 Agent 的适用边界

搭前先问自己三个问题，别为搭而搭：

| 场景 | 结论 |
| --- | --- |
| 每周固定、模板化任务 | ✅ 值得搭，收益直观 |
| 高频、低难度、重复查询 | ✅ 值得，小模型也能扛 |
| 一次性、探索型、高变化 | ⚠️ 收益低，维护成本高 |

个人 Agent 的本质是把"固定流程 + 少量决策"交给代码与模型，不是把一次性脑力活自动化。边界不清时，先跑两周再决定要不要长期维护。

## 十、总结

个人 Agent 没有想象中神秘：**文件层管上下文，工具层管能力，执行层管编排**。从周报这种单任务开始，跑通后再加记忆、加工具、加多任务调度。成本方面，小模型 + 统一网关 + 任务预算 + 结果缓存四件套足够日常使用。我的经验是：先搭最小闭环，再按需扩展，别一上来就想要"通用助手"。
