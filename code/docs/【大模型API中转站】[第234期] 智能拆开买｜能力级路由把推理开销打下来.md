# 【大模型API中转站】[第234期] 智能拆开买｜能力级路由把推理开销打下来

大模型应用正在发生一次安静的架构转向：从"所有环节都调旗舰"转向"按能力拆开买"——判断、排序、搜索、验证各自交给便宜一个数量级的专精系统，旗舰只接住少而难的部分。

这轮转向的推手是成本曲线的分化。我在自己的 agent 流水线里完成了这次改造，核心链路的开销降到改造前的两成左右。这篇文章把能力级路由的架构、实现和标定方法完整写下来。

## 一、痛点：旗舰调用量里的大多数是"低价值调用"

复盘任意一个 agent 任务的调用明细，会发现一个稳定的比例：真正的难题（规划、编码、复杂推理）只占调用量的一小截，剩下的大多数是判断类、分类类、格式类的小调用——判断一次工具返回是否有效、从十个候选里排个序、把非结构化文本转成 JSON。

这些调用用旗舰模型，就像用精密机床削铅笔。能削，但每一次都在烧预算。更麻烦的是这类调用频率极高：一个跑几十轮的 agent 任务，判断类调用的数量往往数倍于生成类调用。

## 二、原理速览：智能的"拆包"逻辑

应用层正在变成"智能编译器"：把一个任务编译成对不同能力档位的调用序列。

```text
传统单体调用：
  任务 -> 旗舰模型（一个会话包办一切）

能力级路由：
  任务 -> 意图分解
          |-> 检索/搜索   -> 便宜档或专精检索
          |-> 判断/校验   -> 专精判断模型（本地或低价档）
          |-> 排序/分类   -> 嵌入或小模型
          |-> 生成/规划   -> 旗舰档（少而难）
          |-> 验证       -> 独立验证调用
```

两个 recent 的标志性信号值得写进判断依据：一是"只输出判断"的专精模型路线跑通了——专门处理是非题、多选题和评分，输出校准概率，本地就能跑，成本比通用模型低几个数量级；二是 if-then 决策原语的专精化——把最简单的条件判断交给专门优化的小系统后，测试中这类调用的开销降了 99%，准确率反而从 47% 提到 80% 以上。

第二个数字尤其值得咀嚼：准确率提升的原因不是"小模型更聪明"，而是任务边界被切干净之后，评测和优化都有了明确的靶子。通用模型做简单判断的 47%，有相当一部分败在上下文干扰而非能力不足。

## 三、四层路由架构

我把生产环境的路由器做成四层：

| 层 | 覆盖能力 | 典型执行者 | 相对开销 |
| --- | --- | --- | --- |
| L0 规则层 | 格式校验、白名单、正则抽取 | 确定性代码 | ≈0 |
| L1 判断层 | 是非题、评分、路由决策 | 本地专精判断模型 | ≈0 |
| L2 轻量层 | 分类、摘要、改写、抽取 | 低价 API 档 | 低 |
| L3 旗舰层 | 规划、编码、复杂推理、创作 | 旗舰档 | 高 |

设计原则：**能在下层解决就不升级**，每层只把"自己搞不定"的流量上报。路由器本身要足够笨、足够快、足够确定——它不是智能组件，是成本闸门。

## 四、4sapi 接入实现

在 4sapi（https://4sapi.com）上，L2/L3 都是 OpenAI 兼容接口，路由器统一调度。核心代码骨架：

```python
import re, json
from openai import OpenAI

client = OpenAI(api_key="sk-4sapi-填入key", base_url="https://4sapi.com/v1")

LIGHT = "gpt-6-luna"
HEAVY = "gpt-6-sol"

def l0_rules(text):
    """确定性能解决的绝不进模型：格式、枚举、正则。"""
    if re.fullmatch(r"\d{4}-\d{2}-\d{2}", text.strip()):
        return "date"
    return None

def l1_should_escalate(text):
    """判断层：这条请求需要旗舰吗？本地小模型输出校准概率。"""
    prompt = f"判断以下请求是否需要复杂推理才能回答，输出 0 到 1 的概率：\n{text[:200]}"
    r = client.chat.completions.create(
        model=LIGHT, temperature=0,
        messages=[{"role": "user", "content": prompt}],
    )
    return float(r.choices[0].message.content.strip() or 0)

def route(text, threshold=0.6):
    hard = l0_rules(text) is None and l1_should_escalate(text) > threshold
    model = HEAVY if hard else LIGHT
    r = client.chat.completions.create(
        model=model,
        messages=[{"role": "user", "content": text}],
    )
    return r.choices[0].message.content, model
```

三个工程细节：

1. **判断层输入截断**。判断"需不需要旗舰"不需要全文，前 200 字符加任务类型足够，这一步自身的 token 开销趋近于零；
2. **阈值按任务族分设**。编码任务的升级阈值要低于闲聊——错放旗舰的代价不对称；
3. **全链路记录路由决策**。每条调用记录"进了哪层、为什么、开销多少"，月度复盘调阈值。

## 五、判断层的能力边界

专精判断模型不是缩小版的旗舰，它的能力面刻意做窄：

| 能做 | 不能做 |
| --- | --- |
| 是非判断、置信度输出 | 开放式生成 |
| 多选一、排序 | 长上下文理解 |
| 评分、分级 | 多步推理 |
| 意图分流 | 知识性问答 |

边界之外的任务必须上报，判断层的输出永远带置信度，低置信度直接升级而不是硬猜。**校准**是这一层的关键词：输出 0.9 的判断就要在 90% 的情况下正确，校准曲线偏离对角线的模型不能上岗。

验证方法很简单：拿 500 条历史判断类请求，让候选模型输出概率分桶，统计每个桶的实际正确率。曲线贴对角线才可信，偏了就重新标定或在路由层做补偿。

## 六、收益核算：改造前后的开销对比

以我的文档处理 agent 为例（日均 8 万次调用），改造前后对比：

| 环节 | 改造前 | 改造后 | 降幅 |
| --- | --- | --- | --- |
| 格式校验/抽取 | 旗舰 | L0 规则 | ~100% |
| 意图判断/路由 | 旗舰 | L1 本地判断 | ~99% |
| 摘要/分类/改写 | 旗舰 | L2 Luna 档 | ~85% |
| 规划/编码/复杂推理 | 旗舰 | L3 不变 | 0% |
| 整体调用开销 | 100 | 约 20 | 80% |

旗舰调用量降到改造前的六分之一，但 L3 的预算一分没省——省出来的全是"低价值调用"。这正呼应了行业侧的判断：旗舰模型未来处理的是更少但更难的任务，判断、排序、搜索、验证这些环节会被拆给更便宜的系统。

## 七、风险与反模式

能力级路由有三个典型的翻车姿势：

1. **过度拆分**。为了省一点开销把任务切成七层，每层引入新的延迟、错误和运维负担，链路复杂度吃掉全部收益。四层是我在实践里的舒适区，超过五层就该警惕架构洁癖；
2. **判断层漂移**。任务分布会变，判断模型半年前标定的阈值可能已经失准，校准验证必须周期化；
3. **错误向上漏斗**。下层误判导致的错答会以"旗舰背锅"的形式出现在监控里，日志必须记录完整路由链，否则排障是灾难。

还有一个战略层面的风险：专精路线的先发窗口很短。通用平台的低价档正在快速蚕食专精小模型的生存空间——Luna 的 $0.10/$0.50 已经把"便宜"的门槛拉到了本地部署都要犹豫的高度。自建判断层的理由从"省钱"逐渐转向"可控与低延迟"，这个动机的变化值得写进架构决策记录。

## 八、落地检查清单

1. 拉出最近一周的调用明细，统计"判断/分类/格式"类占比；
2. 把占比最高的三类低价值调用列为首批拆分对象；
3. L0 规则层先上线，这一步零风险；
4. 判断层候选模型做校准验证，曲线不贴对角线不上岗；
5. 阈值按任务族分设，默认从严（宁可多进旗舰）；
6. 路由决策全量落日志，月度复盘；
7. 灰度 10% 流量一周，质量与开销双指标验收后再全量。

## 九、成本与风险提示

- 能力级路由的收益依赖任务分布，判断类占比低的场景（比如纯写作流水线）收益有限，先测占比再动手；
- 本地判断模型有部署与维护成本，日调用量低于万次的场景未必划算，低价 API 档可能是更简单的选择；
- 校准漂移是长期风险，验证任务集要固定并周期重跑；
- 专精模型的供应商风险高于旗舰平台，接口抽象层要保留随时替换的实现自由度；
- 通过 4sapi 聚合调用时，路由层与中转层的重试策略要协调，避免下层误判被重试放大成双重开销。

## 结论

智能拆开买不是省钱的技巧，是应用架构的代际切换：应用层成为把任务编译成能力调用的路由器，旗舰模型回归"少而难"的本位。四层架构、校准判断层、阈值周期标定，这三件事构成了改造的全部骨架，而收益直接体现在调用明细里——我的核心链路开销降到了原来的两成。

价格越便宜，"什么任务值得调旗舰"就越值得想清楚。欢迎在评论区聊聊各自流水线里判断类调用的占比，以及拆分改造中踩到的坑。
