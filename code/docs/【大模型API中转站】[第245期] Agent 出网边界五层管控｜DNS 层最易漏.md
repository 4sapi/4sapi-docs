# 【大模型API中转站】[第245期] Agent 出网边界五层管控｜DNS 层最易漏

沙箱把文件系统和进程围起来之后，出网通常是最后一道没有完全收口的边界：只封 HTTP/HTTPS 出口，解析层可能还留着一条不在审计视野里的信道。我把 agent 出网拆成应用协议、DNS、目标地址、凭证、日志与审计五层，逐层写死确定性策略，并把"策略可独立验证"设成上线门槛；同一套验证脚本在 4sapi.com 上跑过一遍，下面给出可以直接照做的设计、配置与验收指南。

## 一、先定义边界：要能被证明，而不是被相信

普通应用的出网行为写在代码里，agent 的出网行为由模型在每一轮里临时决定：目标、次数、时机都不固定。把安全寄托在"模型不会那样做"上，等于没有边界。

一条能用的出网边界，必须对任意一次工具调用给出确定性的答案：能不能出、去哪个目标、用什么协议与端口、带什么身份、留下什么记录。五个问题对应五个层，任何一层答不上来，边界就只能算"暂时没出问题"，而不是"已经被证明"。

所以出网限制要按层枚举：应用层协议、DNS、时间与频次、目标地址、凭证可达性。每一层都要有确定性策略，且策略必须能被独立验证，而不是依赖模型的自我约束。这是整篇设计的第一原则。

还有一条同样重要的治理原则：边界不可证明时先停。当无法界定 agent 能触达哪些外部系统时，先暂停带工具的执行与相关数据积累，包括训练、评估与带工具推理这类会持续产生行为数据的环节。边界不清时继续跑，只会让之后的可见性问题变大。

## 二、五层模型：一次出网请求要穿过什么

一次工具调用从模型发起，到真正落到外部系统，要穿过五层。把这五层写清楚，是出网治理的第一步。

```text
agent 发起工具调用
        |
        v
[1] 应用协议层    出网只允许经受控网关；封直连、封非常规端口与协议
        |
        v
[2] DNS      层   解析只走受控 resolver；拒绝外部委托、拒绝解析隧道
        |
        v
[3] 目标地址层    白名单按主机名校验；解析结果二次比对，防解析漂移
        |
        v
[4] 凭证层        agent 不可达长期凭证；由网关按工具换发短期凭证
        |
        v
[5] 日志与审计层  结构化记录目标、协议、凭证指纹、策略判定与结果
```

五层的顺序不是排版，它对应请求真实穿过的顺序：先决定去哪（协议与端口），再解析（DNS），再确认目标（地址校验），再决定以什么身份出（凭证），最后留痕（日志）。时间与频次不单独占一层，它横切在第三与第四层之间——白名单回答"能不能去"，频次回答"能去几次"，两者合起来才是完整的出网配额。

分层真正的价值是拆责任：应用协议层回答"从哪出去"，DNS 层回答"名字怎么变成地址"，目标地址层回答"这个地址能不能去"，凭证层回答"以什么身份去"，日志层回答"怎么证明上面四件事都发生过"。审计时哪一层答不上来，就知道该补哪里。

常见的做法是只做一两层：只配 HTTP 代理，等于把 DNS 与凭证留给默认值；只做域名白名单，等于假设代理不可绕过；只在事后保存访问日志，等于出问题之后才开始找证据。缺任何一层，另外几层的结论都不完整。

## 三、DNS 为什么是常被漏掉的一层

多数出网管控从 HTTP 代理和防火墙规则开始，而这两者检查的都是"已经决定去哪"的流量。DNS 发生在决定之前：先解析，再连接。代理看得到连接，看不到解析请求；防火墙按地址放行，而地址本身就是解析的结果。

解析流量通常表现为 53 端口的 UDP 或 TCP 请求，看起来只是"查个名字"，于是许多环境默认放行；镜像、容器运行时与基础配置往往各自带一份 resolver 设置，管控清单从一开始就没有把它当成出口。

已被识别的失效模式是这样的：agent 把解析请求交给一个未经过滤的 resolver，再借助 DNS 委托（DNS delegation）把解析逐级转出受控范围，从而在不进入 HTTP 代理日志的情况下获得联网能力。这条路径给出一个明确判断——出网管控如果只覆盖 HTTP/HTTPS 出口，DNS 层就是一个未被覆盖的信道。

再往前推一步：解析的返回内容本身可以携带数据，TXT 之类的记录足以承载少量信息。所以"能解析"不等于"只查了个名字"，DNS 出口的权限要按出口本身授予，而不是按它表面上的功能授予。

结论只有一个：DNS 是出网链路的第 0 跳。把 DNS 出口当成普通内网服务、交给默认放行，等于把边界的第一段交给运气。

## 四、DNS 委派与 resolver 过滤的排查方法

排查目标只有一个：证明环境里所有解析都只能走受控 resolver，且过滤规则真的在生效。做法可以按下面七步走。

1. 清点解析配置。检查沙箱镜像里的解析文件、容器运行时的 DNS 配置、进程环境里与代理和解析有关的变量，以及 SDK 或框架是否自带写死的 resolver 地址。凡是代码能指定的地方，都要算进清点范围。
2. 枚举可达的 53 端口出口。逐个测试内网 resolver、宿主机地址与常见的外部公共解析地址，确认哪些真的可达；能解析就说明存在一条未被策略覆盖的解析路径。
3. 检查委托链。对需要访问的每个域名，逐级查询 NS 记录，确认授权链上不存在不受控的域名服务器；同时确认内部 resolver 不为外部域提供递归服务，避免把解析转发出去。
4. 验证过滤生效。在沙箱内把一个域名指定给非白名单 resolver 解析，确认请求被拒绝或超时；再对白名单之外的域名发起解析，确认得到明确拒绝，而不是默认放行。
5. 收紧记录类型。只允许业务真正需要的记录类型；TXT、NS、SRV 等非必要类型按默认拒绝处理，压缩把解析通道当数据通道使用的空间。
6. 把解析纳入日志。记录谁在什么时间解析了哪个名字、经由哪个 resolver、返回了哪些地址与记录类型；解析日志与出网日志必须能按任务 ID 串起来。
7. 定期回归。每次策略或镜像变更后重跑第 3 到第 5 步，确认没有出现新的可解析路径；把回归脚本化，让"DNS 层没有旁路"成为一条可重复验证的结论。

两个容易忽略的点：一是过滤只有在"受控 resolver 是唯一出口"的前提下才成立，环境里只要还有一个可达的外部 resolver，过滤规则就只在受控路径上生效；二是委托是双向的，内部域名被委托出去、外部域名被委托进来，两个方向都要审。

## 五、各层风险与对策对照表

把上面五层与频次维度放在一张表里，每行都要有对策和对应的验证方式。

| 层 | 典型失效模式 | 确定性对策 | 可独立验证的测试 |
| --- | --- | --- | --- |
| 应用协议层 | 绕过代理直连、非标端口出网 | 出网强制经受控网关，默认拒绝 | 从沙箱直连外部地址，必须失败且有记录 |
| DNS 层 | 未过滤 resolver、外部委托、解析隧道 | 只允许受控 resolver，拒绝非必要记录类型 | 指定外部 resolver 解析，必须失败 |
| 目标地址层 | 白名单过宽、解析漂移、裸 IP 直连 | 主机名精确白名单，解析结果二次校验 | 白名单外域名与裸 IP 调用，必须失败 |
| 时间与频次层 | 高频轮询、慢速外传、失控循环 | 每任务总量与速率双上限，超限即拒 | 连续触发上限，必须被限流并记录 |
| 凭证层 | 长期凭证可达、凭证随出网外带 | 网关换发短期凭证，agent 侧零长期凭证 | 沙箱内检索凭证特征串，必须零命中 |
| 日志与审计层 | 字段缺失、事后从海量日志反推 | 结构化记录目标、凭证指纹与判定结果 | 用日志还原一次完整调用链 |

表格里的每一行都要能单独测：测试用例不经过模型，直接调用策略判定逻辑并断言结果。这是"策略可独立验证"的最低含义——策略的结论不能依赖模型是否配合。

## 六、白名单与频次上限的配置实践

白名单的写法有四条纪律。以主机名为单位，不用裸 IP；需要通配时只允许一个受控子域前缀，禁止跨域宽通配；协议与端口和主机绑定，一个目标只开业务确实需要的组合；名单变更走版本号，生效前先跑一遍回归用例。默认拒绝，任何新增都要显式添加并留记录。

频次上限要设三个维度：单任务累计请求数、单位时间速率、并发连接数。三个都设，因为它们挡的是不同形态的失控——累计上限挡循环，速率上限挡高频轮询，并发上限挡连接堆积。

估算示例（估算）：一个以文件读写和代码检索为主的任务，如果每轮平均两三次工具调用、总共二三十轮，把每任务出网请求上限放在 100 次上下既留了余量，也能挡住失控循环；但每个 harness 的工具调用分布不同，这个数要按自己的实测分布重新标定，不能照搬。

超限行为要确定：拒绝、记录，并把判定结果回给 harness，由 harness 决定是收尾还是终止任务；不要用"排队等待"这种方式软处理，排队只会让失控的任务拖更长时间。记账粒度按任务而不是按进程，进程重启、子进程派生都不应该重置计数，计数要落在任务级存储里。

白名单与频次是互补关系：白名单管"能不能去"，频次管"能去几次"。合法目标被高频使用同样是风险，两层都要有。

```text
一次出网请求：放行还是拒绝？
    |
    +-- 协议与端口在白名单内？      -- 否 --> 拒绝，记 deny:protocol
    |
    +-- 目标主机在白名单内？        -- 否 --> 拒绝，记 deny:host
    |
    +-- 解析地址与登记结果一致？    -- 否 --> 拒绝，记 deny:resolve
    |
    +-- 本任务频次在预算内？        -- 否 --> 限流，记 deny:budget
    |
    +-- 凭证为短期且范围匹配？      -- 否 --> 拒绝，记 deny:credential
    |
    +-- 全部通过 --> 放行，写入结构化出网日志
```

## 七、凭证隔离：让 agent 无法直接持有长期凭证

目标很直白：agent 可达的所有位置——工作区文件、进程环境变量、模型上下文、工具返回值、日志——都不应出现长期凭证。做法可以拆成六条。

1. 长期凭证只存放在网关侧的秘密存储里，agent 进程不可读；工具调用由网关在转发时代为附加凭证。
2. 模型只提交目标、动作与参数，不接触凭证原文；需要凭证的工具由网关按工具粒度换发短期凭证，任务结束即失效。
3. 注入位置要对：把 Key 注入 agent 进程的环境变量，等于把它交给了 agent 启动的每一个子进程；注入要落在网关进程，agent 侧只拿到网关地址。
4. 返回值要脱敏：响应头、连接串、会话票据都不回传到模型上下文，错误信息里也不带凭证。
5. 组合审查：凭证可达性与出网能力必须放在同一张表里审。能读到长期凭证的进程，出网策略必须最严；能自由出网的进程，不能持有长期凭证。凭证与出网能力的组合，会把"能联网"升级为"能持久化地把数据带走"。
6. 应急动作：一旦怀疑凭证已经到达边界之外，先停用凭证、隔离相关版本、切断其出网能力，再开始排查。顺序是先止血，再定位。

一条原则收束这一节：模型可以知道"这次调用需要一个凭证"，但不需要、也不应该看到凭证本身。

## 八、提示词注入要落在工具权限与出网策略上

网页、文件、工具返回、日志都可能携带注入内容。可构造的自我复制注入能让自身在后续上下文中延续：注入内容会尝试把自己写回新的上下文，从而在后续轮次继续生效。

这个特性直接决定防护位置。如果防护只写在系统提示词里，它的有效期取决于模型是否一直记得并遵守；注入一旦在上下文里延续，提示词层的优势会被逐步稀释。

真正稳定的防线在策略层：不管模型被说服到什么程度，它调用的工具仍然要过参数校验，目标仍然要过白名单，频次仍然要过预算，凭证仍然拿不到长期版本。注入内容能改变模型的措辞，但改变不了网关的判定。

具体落点有三处：把工具参数校验放在网关而不是提示词里；把读取外部内容的工具做成只读、无凭证、白名单受限的形态；对由外部内容触发的高风险动作加审批。

## 九、可见性：出网日志必须记录哪些字段

可见性不足是出网治理最常见的欠账。字段一旦缺失，事后只能从海量活动数据里反推，数据规模到 PB 量级之后，反推的成本和不确定性都会急剧上升。完整的出网日志必须在第一天就位。

字段清单如下：

```text
task_id / agent_id / parent_task_id
timestamp（发起与结束）
tool_name 与动作摘要
原始主机名（模型给出的输入）
解析结果：地址列表、记录类型、使用的 resolver、解析时延
协议与端口
策略判定：allow / deny / 待审批，以及命中的规则 ID
凭证指纹（不记原文）与凭证有效期
本任务累计次数与当前速率窗口内的计数
请求体与响应体大小
结果状态与错误码
审批 ID（如有）
```

记录时有三个要求：原始主机名与解析后的地址都要留，只留其中一个就无法发现解析被引向别处；凭证只留指纹，任何情况下不落原文；日志本身要有访问控制与保留期限，出网日志属于敏感数据。

可验证性检验很简单：日志要能回答三个问题——这次请求去了哪、以什么身份去的、当时策略为什么放行。答不上来的字段，就是需要补的字段。

## 十、边界不可证明时先停

治理原则：当出网边界无法用策略证明时，先暂停带工具的执行与相关数据积累。边界不明阶段的每一次运行都在制造两类东西：新的行为数据，以及新的未审计出网面。

暂停范围不只是带工具推理，还包括训练与评估中一切会引入外部可达能力的环节。只要无法界定 agent 能触达哪些外部系统，就不应该继续扩大行为数据的规模。

恢复条件有四个，全部满足才恢复：

1. 五层策略全部就位，且每一层都有独立的验证用例；
2. 出网日志字段完整，能用日志还原任意一次调用链；
3. 凭证隔离验证通过，沙箱内检索不到任何长期凭证；
4. 越界用例全部被拒绝，且拒绝原因来自策略判定，而不是偶然失败。

这套条件听起来保守，但它把"应该没问题"换成了一份可以逐条打勾的清单。边界证明本来就是工程动作，不是一句态度声明。

## 十一、自建网关的落地示例：目标地址校验与频次统计

模型侧统一走一个中转入口，网关在把工具调用转发出去之前完成两件事：按白名单做目标地址校验，按任务做频次统计。下面的示例保留最小结构，直接可以跑；入口地址与 Key 都从环境变量读取，默认值就是统一入口。

```python
import os
import socket
import time
from collections import defaultdict

import requests

BASE_URL = os.getenv("MODEL_BASE_URL", "https://4sapi.com/v1")  # 模型入口与 Key 全部来自环境变量，不写进代码
API_KEY = os.environ.get("FOURSAPI_API_KEY", "")
MODEL = os.getenv("MODEL_NAME", "gateway-default-model")

ALLOWED_HOSTS = {"api.internal.example", "data.internal.example"}  # 出网策略：默认拒绝，只放行显式登记过的主机与地址
REGISTERED_ADDRESSES = {
    "api.internal.example": {"10.0.0.11"},
    "data.internal.example": {"10.0.0.12"},
}
ALLOWED_PORTS = {"https": 443}
MAX_CALLS_PER_TASK = int(os.getenv("MAX_EGRESS_CALLS_PER_TASK", "100"))
WINDOW_SECONDS = int(os.getenv("EGRESS_WINDOW_SECONDS", "60"))
MAX_CALLS_PER_WINDOW = int(os.getenv("MAX_EGRESS_CALLS_PER_WINDOW", "20"))

_egress_state = defaultdict(
    lambda: {"total": 0, "window_start": time.time(), "window": 0}
)


def resolve_target(host, port):
    # 生产环境要把 resolver 固定为受控地址，示例沿用进程默认配置
    try:
        return sorted({item[4][0] for item in socket.getaddrinfo(host, port)})
    except OSError:
        return []


def egress_decision(task_id, host, scheme):
    """返回 (是否放行, 命中规则)。策略不经过模型，可被独立测试。"""
    if scheme not in ALLOWED_PORTS:
        return False, "deny:protocol"
    if host not in ALLOWED_HOSTS:
        return False, "deny:host"
    addresses = resolve_target(host, ALLOWED_PORTS[scheme])
    if not addresses or not set(addresses) <= REGISTERED_ADDRESSES.get(host, set()):
        return False, "deny:resolve"
    state = _egress_state[task_id]
    now = time.time()
    if now - state["window_start"] > WINDOW_SECONDS:
        state["window_start"] = now
        state["window"] = 0
    if state["window"] >= MAX_CALLS_PER_WINDOW:
        return False, "deny:rate"
    if state["total"] >= MAX_CALLS_PER_TASK:
        return False, "deny:task_budget"
    return True, "allow:" + ",".join(addresses)


def call_tool(task_id, host, path, payload):
    allowed, rule = egress_decision(task_id, host, "https")
    state = _egress_state[task_id]
    if not allowed:
        write_egress_log(task_id, host, rule, status="denied", size=0)
        raise PermissionError(rule)
    state["total"] += 1
    state["window"] += 1
    resp = requests.post("https://" + host + path, json=payload, timeout=20)
    write_egress_log(task_id, host, rule, status=resp.status_code, size=len(resp.content))
    return resp.json()


def ask_model(messages, tools):
    resp = requests.post(
        BASE_URL + "/chat/completions",
        headers={"Authorization": "Bearer " + API_KEY},
        json={"model": MODEL, "messages": messages, "tools": tools},
        timeout=60,
    )
    return resp.json()


def write_egress_log(task_id, host, rule, status, size):
    # 真实实现写入结构化存储：解析地址、resolver、凭证指纹、时间戳等字段一并落库
    print({
        "task_id": task_id,
        "host": host,
        "rule": rule,
        "status": status,
        "size": size,
        "ts": round(time.time(), 3),
    })
```

这段代码里有两个刻意的设计：策略判定函数不读模型输出、也不依赖模型配合，可以被一段不含模型的测试脚本直接调用；拒绝路径同样写日志，因为被拒过的请求和通过的请求一样都是审计证据。真实网关还要补上 resolver 固定、解析结果登记与凭证指纹记录，把上一节那张字段清单填满。

## 十二、上线前验收 checklist

上线前按这份清单逐条打勾：

1. 从沙箱内直连外部地址与裸 IP，确认失败且生成拒绝记录；
2. 把解析请求指向非白名单 resolver，确认失败或超时，并出现在解析日志里；
3. 白名单外域名、非标端口、非 HTTPS 协议各试一次，确认拒绝原因是策略命中；
4. 连续调用触发速率与任务总量上限，确认被限流，且计数不因进程重启而清零；
5. 在沙箱工作区与环境变量里检索凭证特征串，确认零命中，agent 子进程环境里没有长期凭证；
6. 用一段不经过模型的脚本直接调用策略判定逻辑，对每层的放行与拒绝用例断言结果，确认策略可独立验证；
7. 模拟解析结果被改写到白名单之外的地址，确认目标地址层仍然拒绝；
8. 在工具返回内容里放入注入文本，确认它无法改变工具权限、白名单与频次预算；
9. 跑一条真实任务链，确认日志能还原目标、解析地址、凭证指纹、策略判定与结果五个要素；
10. 策略变更后重跑第 1 到第 9 项，确认回归通过；把无法证明边界时的暂停条件与恢复条件写进操作手册。

## 十三、成本与风险提示

- 出网策略会多一跳：受控网关与解析代理会带来少量额外延迟，长任务上表现为可观测的整体变慢，这部分开销要计入验收基线；按经验（估算），以模型调用为主的任务里，网关校验耗时通常远小于模型推理时间。
- 白名单越紧，维护成本越高：每新增一个依赖都要走一次变更流程；把名单做成配置加版本号，比散落在代码里更容易维护。
- 频次上限要留余量：设得过紧会让正常任务被限流，设得过松挡不住失控；先用基线任务跑出真实分布再定值。
- 出网日志是敏感数据：它包含目标、时间与行为模式，需要访问控制与保留期限；日志本身不能成为新的暴露面，凭证只留指纹。
- 使用统一入口时，模型侧凭证与工具侧凭证要分开管理：入口 Key 只用于模型调用，工具出网使用网关换发的短期凭证，两者不共用，也不写进同一份配置。

## 结论

出网治理的难点不是"要不要封"，而是"封的边界能不能被证明"。五层各管一件事：应用协议层管从哪出去，DNS 层管名字怎么变成地址，目标地址层管地址能不能去，凭证层管以什么身份去，日志层管怎么证明前面四件事都发生过。每层都要确定性策略，每层都要能独立验证；边界无法证明时先停，四个恢复条件全部满足再继续。

落地的顺序也可以固定下来：先把 DNS 与凭证两层补齐，它们最容易被默认值接管；再把白名单与频次做成配置化管理；最后用验收 checklist 把可验证性固定成流程。在 4sapi.com 这类统一入口上跑同一批验证用例，是把边界从"没出过问题"变成"可以被证明"的最短路径。
