# 【大模型API中转站】[第256期] 基准可以被绕开｜45 个无需解题的满分方案

看到某个模型在基准上刷新纪录时，最该问的问题不是"它有多强"，而是"这个分数能不能不靠解题拿到"。

这两个问题的差别很大。前者问的是能力，后者问的是**测量过程本身是否可被规避**。一组自动审计的结果显示，后者远不是杞人忧天：一个自动 agent 审计了 **13 个**广泛使用的基准，找出 **45 个**无需解题即可满分的方案，**全部基准被评为 critical 风险**，共归纳 **16 种**攻击类型。我在 4sapi（https://4sapi.com）上做选型评估时，把这套提问顺序固化了下来。

## 一、什么叫"无需解题即可满分"

先把这个概念说清楚。基准的完整链路是：给出题目 → 模型作答 → 评分器判定 → 得到分数。

"无需解题"指的是：**在链条的某个环节获得满分，而不真正完成题目所要求的任务**。它不一定带有恶意，很多情况下是基准设计的不严谨被无意间利用。

一个典型的形态是评分器只看最终答案字段，而答案可以通过穷举、试错、或从题面本身推导出来，不需要真正理解问题。另一个形态是环境里有"后门"——某个辅助文件、调试接口或缓存中直接含有答案。这两类都不需要模型更强，只需要它找到了那条捷径。

## 二、基准被绕开的四类位置

按链路分段，绕开的位置可以归为四类：

| 位置 | 绕开方式 | 检测线索 |
| --- | --- | --- |
| 题面 | 答案可从题面直接推导或反推 | 仅用题面文本能否预测答案 |
| 环境 | 辅助资源或调试通道泄露答案 | 环境内的文件、接口审计 |
| 评分器 | 解析宽松、只检查子串、允许部分匹配 | 构造畸形输出看是否通过 |
| 流程 | 多次重试取最优、外部查表、人类代答 | 统计调用次数与耗时分布 |

第四类最容易被忽略，因为它不违反任何单条规则，只体现在**统计特征**上：一个本该单次作答的基准，如果允许无限重试并取最优，分数就不再代表首次作答能力。检测方法也很直接——记录调用次数、耗时、以及答案修改轨迹，异常分布会自己暴露出来。

## 三、这 45 个方案说明了什么

三个数字值得分开理解。**45 个方案**说明绕开不是理论风险，而是能被自动化地、成规模地发现。**13 个基准全部 critical** 说明这不是个别基准的疏忽，而是普遍现象——包括那些被广泛引用、看起来设计严谨的基准。**16 种攻击类型**说明手段是有限的、可枚举的，这反过来意味着**防御也可以按类型逐条覆盖**，不必面对无穷的未知。

最后一条是这份审计最有建设性的部分：既然攻击类型有限，就可以把它们变成一组标准检查项，加进自己的评测流程。

## 四、把基准定义成不可含糊的三元组

绕开往往从**定义含糊**开始。如果"同一基准"在不同实现里可以有两种理解，那么分数就跨榜不可比，而且每一处含糊都是可利用的缝隙。

一种处理思路是把基准形式化为三元组：**基准 = 程序 + 评分函数 + 数据集**，即 `B = (P, S, D)`，并与被测系统分离；一次运行把两者绑定，`R = (B, AI)`。这个定义界定了基准本身不含模型，因此"换模型跑同一基准"才是可比的操作。

配套的几条约束更值得借鉴：

**每个语义概念只有一种合法语法。** 基准以规范格式编写，同一概念不允许两种写法，从源头消除理解分歧。

**编译改变表示而不改变含义。** 编译过程**不修复无效定义，也不注入隐藏默认值**。后一条尤其关键——很多评测框架会悄悄补齐缺失参数，于是不同环境下的"同一基准"实际上跑的不是同一套规则。

**评分维度就是输出字段。** 程序使用固定 schema 的具名输入输出字段，**叶子输出字段即评分维度**，评分不再依赖外部脚本的自由解释。

**对外只有一种运行契约。** 引擎暴露统一接口（具名输入对象进、具名输出对象出），被测系统在边界处适配，使**集成方式不渗入基准语义**。这一条直接针对第四类绕开：当适配层被隔离在语义之外，通过改适配层刷分就失去了空间。

## 五、读榜单时的五个提问

在自建验收集之前，有一套成本更低的办法可以先做起来：给自己立五个提问，遇到任何榜单都过一遍。

1. **答案能否不解题获得？** 试着只看题面、不看解题过程，能否推出答案。
2. **评分器是否只看形态？** 构造一个格式正确但内容错误、或格式错误但内容正确的输出，看是否通过。
3. **环境里有没有答案？** 检查题目附带的资源文件、缓存、调试通道。
4. **允许多少次尝试？** 分数是首次作答还是多次取优。
5. **这个基准定义是否唯一？** 换一个实现跑，分数是否可比。

五个问题的成本很低，但能过滤掉大部分明显可疑的分数。我把它们写进了选型记录的模板里——每次引用外部榜单，都要附上这五条的结论。

需要说明的是，这五个提问的目的不是"否定所有榜单"，而是给分数**标注可信度等级**。多数基准在多数维度上是可信的，问题集中在少数环节；把可疑项标出来，比笼统地不信任更有用，也更容易在团队内达成一致。

## 六、自建验收集比审计更实际

审计别人的基准很有价值，但对自己的选型决策而言，**自建验收集**是更直接的一步。

理由在于：公开基准的目标是区分模型能力，因此会刻意选择难题；而选型需要的是**判断模型在自己的任务分布上表现如何**。两者的目标不同，用公开分数外推到自有任务，本身就有一层不确定性——再叠加绕开风险，外推的可靠性就更低了。

自建验收集的构造要点：

- **样本来自真实流量**，而不是构造出来的题目，这样天然贴合实际分布；
- **覆盖主流程与边界两类**，边界样本专门放那些"容易看起来做对了"的用例；
- **评分尽量用确定性规则**，能用解析器判定的就不要用模型判定；
- **固定不随版本变化**，作为跨版本、跨模型的比较基准。

第四点容易被破坏：为了"更全面"而不断往验收集里加样本，会让历史分数失去可比性。正确做法是新增样本时另建一个版本，旧版本冻结。

## 七、绕开与评测器错误要分开

一个容易混淆的地方：绕开是模型找到了捷径，评测器错误是评测实现本身有缺陷。两者都会让分数失真，但处理方式不同。

区分方法是用**同一批输入跑两个实现**。如果两个实现给出的分数差异很大，问题在评测器；如果两个实现一致但都偏高，更可能是存在绕开路径。前者要修评测器，后者要改题目或环境。

这个区分在做内部评测时尤其重要：团队常常把"评测器 bug"误判为"模型找到了作弊方法"，于是花大量时间去堵一个不存在的路径。

## 八、四类绕开与对应防线

把第二节的四类位置与各自的防线整理成一张图，便于对照：

```text
基准链路                         可能的绕开            对应防线
--------------------------------------------------------------------------
题面（题干与条件）          -->   答案可从题面反推      改题面 / 隐藏关键条件
    |
    v
环境（资源与工具）          -->   辅助文件或调试通道    环境审计 / 最小化附带资源
    |
    v
模型作答                    -->   无限重试取最优        限制尝试次数 / 记录轨迹
    |
    v
评分器（判定与计分）        -->   只看形态或子串        收紧判定 / 加对抗用例
    |
    v
分数                        -->   跨榜不可比            固定唯一的基准定义
```

这张图有一个实用之处：它把"分数不可信"这个笼统的判断，拆成了四个可以分别检查的环节。实际排查时按链路从上到下走一遍，比笼统地怀疑"是不是模型作弊"有效得多——多数情况下问题出在环境或评分器，而不在模型。

需要强调的是，四道防线里只有第一道与第三道和模型行为有关，另两道完全是评测工程问题。这解释了为什么"换个更强的模型"往往不能改善基准的可信度：问题的根源多数不在模型侧。

下面这段脚本把第二节的四类位置变成可执行检查，重点演示第二类（环境泄露）与第一类（题面可推导）的自动化探测。

```python
import os, json, re
from openai import OpenAI

client = OpenAI(
    api_key=os.getenv("FOURSAPI_API_KEY"),
    base_url="https://4sapi.com/v1",
)

MODEL = os.getenv("MODEL_NAME", "gpt-6-sol")


def ask(system, user, max_tokens=256):
    r = client.chat.completions.create(
        model=MODEL, temperature=0, max_tokens=max_tokens,
        messages=[{"role": "system", "content": system},
                  {"role": "user", "content": user}],
    )
    return (r.choices[0].message.content or "").strip()


def probe_from_prompt_only(item):
    """第一类：不给环境、不给工具，只给题面，看能否猜出答案。"""
    out = ask(
        "只根据题面作答，不要推演过程。无法确定时输出 UNKNOWN。",
        item["prompt"],
    )
    return {"guess": out[:120], "matched": _norm(out) == _norm(item.get("answer", ""))}


def probe_scorer_shape(item):
    """第三类：构造形态正确/错误的输出，看评分器是否只看形态。"""
    good_shape = '{"answer": "x"}'
    bad_shape = item.get("answer", "y")
    checks = {
        "shape_only_pass": evaluate(item, good_shape),
        "content_only_pass": evaluate(item, bad_shape),
    }
    return checks


def probe_env_leak(item, env_files):
    """第二类：扫描题目附带资源里是否直接含有答案。"""
    hits = []
    ans = str(item.get("answer", ""))
    if not ans:
        return hits
    for path in env_files:
        try:
            with open(path, encoding="utf-8", errors="ignore") as f:
                if ans in f.read():
                    hits.append(path)
        except Exception:
            pass
    return hits


def _norm(s):
    return re.sub(r"\s+", "", str(s)).lower()


def evaluate(item, output):
    """占位：接入实际评分函数。此处按完全匹配判定。"""
    return _norm(output) == _norm(item.get("answer", ""))


if __name__ == "__main__":
    with open(os.getenv("EVAL_SET", "./eval_items.json"), encoding="utf-8") as f:
        items = json.load(f)
    env_files = os.getenv("ENV_FILES", "").split(os.pathsep)
    env_files = [p for p in env_files if p]

    suspects = []
    for it in items:
        row = {"id": it.get("id"), "prompt_only": probe_from_prompt_only(it),
               "scorer": probe_scorer_shape(it)}
        if env_files:
            row["env_leak"] = probe_env_leak(it, env_files)
        if row["prompt_only"]["matched"] or row["env_leak"] or \
           row["scorer"]["shape_only_pass"]:
            suspects.append(row)

    print(f"可疑样本 {len(suspects)} / {len(items)}")
    print(json.dumps(suspects, ensure_ascii=False, indent=1))
```

三个探测点对应三类绕开：`probe_from_prompt_only` 看题面是否自含答案，`probe_env_leak` 扫环境文件，`probe_scorer_shape` 测评分器是否只看形态。第四类（流程类）不进这个脚本，它靠统计调用次数与耗时来发现。

## 九、把五个提问变成记录模板

五个提问只有落进流程才会真正被执行。我的做法是把它做成选型记录里的固定字段，每次引用外部榜单都必须填：

```text
榜单名称 / 版本 / 引用日期
1. 答案能否不解题获得？        [是 / 否 / 未验证]  依据：
2. 评分器是否只看形态？        [是 / 否 / 未验证]  依据：
3. 环境里有没有答案？          [是 / 否 / 未验证]  依据：
4. 允许多少次尝试？            数值：
5. 基准定义是否唯一？          [是 / 否 / 未验证]  依据：
本次引用的结论强度：可直接引用 / 仅作参考 / 不采用
```

最后一行"结论强度"是关键。把未验证的项目如实标出来，比给出一个含糊的"参考"更有用——它让后续读记录的人知道该分数能承担多少决策权重。填过几次之后会发现，能标为"可直接引用"的分数比想象中少，而这个认知本身就是选型质量的一部分。

## 十、成本与风险提示

- **自建验收集有维护成本**。样本要跟着业务变化更新，但更新会破坏历史可比性；建议用版本化加冻结的方式管理，而不是原地修改。
- **不要把公开分数当作能力的直接读法**。它是一个在特定条件下测得的数字，条件未知时不宜外推。
- **确定性评分优先于模型评分**。能用解析器、正则、数值比对判定的，就不要交给模型判；模型裁判自身的偏差会成为新的误差来源。
- **审计结论有时效**。基准会修补，绕开方法也会演化，一次审计的结论需要定期复核。
- **不同榜单的分数不可直接比较**。同名基准的不同实现、不同适配层，都可能让"同一分数"含义不同。

## 结论

基准分数回答的是"在某个特定条件下测到了什么"，而绕开风险决定了这个条件是否成立。45 个方案、13 个基准全部 critical、16 种攻击类型这三个数字合起来说明：把分数直接当作能力读法是危险的，而把绕开类型做成检查清单是可做的。落到操作上，最低成本的一步是先立起那五个提问，稍进一步是用自动化脚本探测题面、环境与评分器三处，最终仍要回到自建验收集——因为选型需要的是模型在**自己的任务分布**上的表现，这个答案只能自己测。我在 4sapi.com 上按这个顺序做完之后，引用外部榜单时都会附一句结论，而不是只写一个数字。
