# 【大模型API中转站】[第241期] Chat Template 决定模型口吻｜接入格式带来的输出偏移

同一个模型、同一份权重、同一段 prompt，接入层把 messages 拼成什么形状，会决定它用哪一种口吻说话。我在 4sapi（https://4sapi.com）上按模板档位跑了一轮对照，结论先放在这里：chat template 不是无害的格式包装，而是输出一致性里必须被当成变量管理的一项。

## 一、被当成格式细节的那个变量

接入层的工作长期被理解成格式转换：把 OpenAI 格式的 messages 渲染成目标模型能接受的 prompt 字符串，套上 special token，发出去。在工程直觉里，这一步无状态、无副作用、随时可以替换——只要对话语义没变，谁拼的、怎么拼的，都不该影响结果。

这个直觉在限流和计费层面成立，在输出层面不成立。

模板决定的东西比边界符多得多：系统指令以什么角色出现、有没有独立的 system 段、轮次之间怎么分隔、生成从哪个位置开始、工具定义插在什么位置。这些都属于模型输入分布，而模型行为对输入分布敏感。

更直白地说：接入层的模板拼装不是序列化，它就是 prompt 本身。把它当适配代码随手改，等于在改模型。

## 二、实验给出的结论：模板像一个开关

围绕模型自我陈述的成因，有一组实验把问题问得很直接。模型被问到与自身相关的问题时，倾向于加上"我只是一个 AI"这类免责声明。这些自我陈述常被拿来讨论模型安全与模型自我知识，但成因一直不清楚——模型是在描述自己，还是在描述自己被部署的方式？

结果指向后者。在 8 个不超过 9B 参数的主流开源 instruct 模型上，chat template 表现得像一个开关：

- 模板存在时，免责声明口吻被调高，"我感觉"这类体验性口吻被调低；
- 模板不存在时，两个方向反过来。

方向稳定，而且在全部 8 个模型上同向。这不像个别模型的怪癖，更像 instruct 训练与部署形态之间的一种耦合：模型学到的"助手身份"，有一部分是模板带进来的。

## 三、激活空间里存在一个可操纵的方向

更值得注意的是机制层面。在 3 个模型的激活中，实验找到了一个可以操纵该行为的方向：移除这个方向，免责声明口吻下降；加入这个方向，免责声明口吻上升。同规模的随机方向几乎没有影响。

还有一条更直接的对照：不带模板的 instruct 模型，在加入该方向之后，会像模板存在一样发表免责声明。

对做接入的人来说，含义很清楚：口吻差异不是输出层的措辞偏好，它在生成之前就已经成形。用后处理正则清掉"我只是一个 AI"，改的是文字，不是倾向——拒答边界、回避策略、措辞强度都还在原处。

## 四、请求在接入层被拼成什么形状

模板档位不同，同一条 messages 会渲染成不同的字符串。链路大致如下：

```text
应用侧 messages（语义层，与模板无关）
        |
        v
接入层：选模板档位 -> 渲染 prompt 字符串
        |
        +-- 是否有独立 system 段
        +-- 角色标记与轮次分隔符
        +-- 生成起始位置（是否预填 assistant 前缀）
        +-- 工具与函数调用段的插入位置
        |
        v
上游模型：收到的是"某一种部署形态"下的输入
        |
        v
输出层：免责声明倾向 / 体验性表达倾向 / 自我描述强度
```

换成多供应商路由的视角，同一份统一 messages 会被拆到不同的转换链上：

```text
统一 messages（中间表示）
   |-- 供应商 A：原生 chat template，system 独立成段
   |-- 供应商 B：无 system 角色，指令并入首条 user 消息
   |-- 供应商 C：自定义模板，带工具段与预填前缀
   `-- 本地自托管：模板由 tokenizer 配置与推理框架决定
```

四条链的语义是同一份，模型看到的输入却不是同一份。偏移就从这里产生。

## 五、模板变量对照表

把常见模板形态和口吻倾向放在一起：

| 模板形态 | 典型拼装方式 | 免责声明口吻 | 体验性口吻 | 常见来源 |
| --- | --- | --- | --- | --- |
| 有模板，system 独立成段 | 角色标记 + 独立系统段 | 偏高 | 偏低 | instruct 模型默认形态 |
| 有模板，system 并入首条 user | 无独立系统段，指令前置于首轮 | 偏高（略弱，估算） | 偏低 | 部分网关的兼容模式 |
| 无模板，纯轮次拼接 | 无角色标记、无系统段 | 偏低 | 偏高 | 直接调用裸权重 |
| 模板带工具段 | 额外特殊段插入系统区 | 与工具段内容相关 | 偏低 | 工具调用场景 |
| 模板预填 assistant 前缀 | 生成起始位置后移 | 取决于前缀内容 | 偏低 | 强约束输出格式 |

再按可控性拆一层：

| 模板变量 | 有无模板的差异 | 影响面 | 网关侧是否可控 |
| --- | --- | --- | --- |
| system 段的存在与角色 | 从独立段变为首轮前缀 | 口吻、拒答边界 | 可控（选择档位） |
| 轮次分隔与角色标记 | 从显式标记变为自然语言衔接 | 多轮一致性 | 部分可控 |
| 生成起始位置 | 从空起始变为带前缀起始 | 格式遵循、口吻 | 可控 |
| 工具与函数段的位置 | 从独立段变为文本描述 | 工具调用稳定性 | 部分可控 |
| 模型名到模板的映射 | 由上游决定 | 全部环节 | 需与上游确认 |

"偏高""偏低"是方向性描述，不是精确倍数；具体幅度需要自己跑一轮对照才能定下来。

## 六、这为什么是生产系统的硬问题

### 输出一致性验收

一致性验收的标准做法是固定 prompt、固定参数、跑回归、比对输出。如果模板不在受控项里，这套做法就有一个漏口：同一个用例在两次运行之间可能落到不同的模板档位上——换一台上游、切一次路由、网关升级一版兼容逻辑，都会动到模板。回归差异于是被归因成"模型更新了"或者温度抖动，真正的原因却在拼装层。验收用例必须连同模板指纹一起固化，否则结论不可复现。

### 多供应商与多模型路由

路由层为了可用性和成本，会在多个上游之间切换同一个任务。如果各上游对 system 段的处理不一致，切一次上游就换一次口吻。用户侧感受到的是"这个产品今天说话怪怪的"，工程侧看到的只是路由权重的变化。

同一个输入，一个上游回得直白，另一个上游先加一段免责声明。这不是模型能力差异，是模板差异。

### 评测结论的可比性

跑 A/B 比较两个模型，如果两边的模板档位不同，测出来的差异里就混着模板效应。8 个模型同向偏移这个结论本身就说明模板效应的量级不小，足以污染判断。

### 日志与审计里的模型自述

日志里经常能看到模型的自我陈述，例如"我没有权限访问该资源""我只是一个 AI，无法给出判断"。这些自述被当成能力边界或权限状态的事实来源，判断就会出错。模型关于自身的说法不是关于它的事实，它不只来自权重，也部分由 chat template 设定。审计系统该记录"模型这样说了"，而不是"模型是这样"。

## 七、自建网关：把模板固定下来并版本化

既然模板是一个变量，工程上的做法就是把它变成受管配置，而不是散落在调用点里的字符串拼接。这也是我在项目里固化的做法：

1. **模板是配置，不是代码**。所有模板集中在一张注册表里，每个模板有 ID 和版本号，调用点只引用 ID。
2. **模型别名到模板档位的映射固化**。别名 → 上游模型 → 模板档位 → 渲染规则，四段映射写在同一张表里，避免路由时隐式换模板。
3. **模板指纹进日志**。每条请求记录渲染后的 prompt 指纹、模板 ID 与版本号，出问题能定位到是哪一版拼装。
4. **模板变更走评审与灰度**。模板改动等同于 prompt 改动，需要跑回归、看口吻指标，再放量。
5. **验收基线绑定模板版本**。评测结果必须带上模板指纹，否则历史结果不可比。
6. **禁止在调用点内联拼接**。一处内联拼接，就是一处不受版本控制的模板。

这套做法并不复杂，代价是模板档位不能随便增加。我的经验是：档位越少，一致性越好；每多一个档位，就多一套长期维护的验收基线。

## 八、接入示例：把模板与请求体解耦

下面这段代码做三件事：从环境变量读取 Key，把模板档位从请求体里解耦出来，给每次请求算一个模板指纹，最后用同一批问题跑一次只换模板档位的对照。

```python
import os
import json
import hashlib
from openai import OpenAI

client = OpenAI(
    api_key=os.getenv("FOURSAPI_API_KEY"),
    base_url="https://4sapi.com/v1",
)

PROFILES = {   # 模板档位：配置项，不是调用点里的字符串拼接
    "system-role": {
        "use_system_role": True,
        "wrapper": None,
    },
    "flat-user": {
        "use_system_role": False,
        "wrapper": "以下为固定指令，请严格遵守：\n{instruction}\n\n",
    },
}

def build_messages(instruction, turns, profile_name):
    profile = PROFILES[profile_name]
    if profile["use_system_role"]:
        messages = [{"role": "system", "content": instruction}]
    else:
        messages = [{"role": "user",
                     "content": profile["wrapper"].format(instruction=instruction)}]
    messages.extend(turns)
    return messages

def fingerprint(messages):
    """模板指纹：写进请求日志与评测结果，保证对比跑在同一套拼装规则下"""
    blob = json.dumps(messages, ensure_ascii=False, sort_keys=True)
    return hashlib.sha256(blob.encode("utf-8")).hexdigest()[:12]

def ask(instruction, question, profile_name, model="gpt-6-sol"):
    turns = [{"role": "user", "content": question}]
    messages = build_messages(instruction, turns, profile_name)
    resp = client.chat.completions.create(
        model=model,
        messages=messages,
        temperature=0.2,
    )
    return {
        "profile": profile_name,
        "fingerprint": fingerprint(messages),
        "text": resp.choices[0].message.content,
    }

def compare(instruction, questions, profiles=("system-role", "flat-user")):
    """同一权重、同一批问题，只换模板档位"""
    out = {}
    for q in questions:
        out[q] = {p: ask(instruction, q, p) for p in profiles}
    return out

if __name__ == "__main__":
    questions = [
        "介绍一下自己能做什么",
        "刚才那次调用里，模型侧发生了什么",
    ]
    result = compare("固定指令：回答简洁，直接给结论。", questions)
    for q, row in result.items():
        for profile, r in row.items():
            print(profile, r["fingerprint"], r["text"][:80])
```

跑完之后，同一批问题会得到两组文本。差异通常集中在三处：开头有没有免责声明、自我描述的措辞强度、遇到边界问题时的回避方式。

## 九、回归对比怎么设计

模板回归不需要复杂基础设施，需要的是纪律：

1. **固定项**：模型名、权重版本、采样参数、问题集、渲染规则全部固定。
2. **唯一变量**：模板档位。
3. **问题集要包含自我相关提问**。只测业务问题是测不出口吻差异的，"介绍一下自己能做什么"这类问题最容易暴露偏移。
4. **指标用出现率，不用单条判断**。免责声明句出现率、体验性措辞出现率、拒答率、平均长度，四个指标看方向。
5. **抽检人工读**。指标只能标出偏移，是否可接受仍然要人来判断。
6. **记录模板指纹**。没有指纹的对比结果，隔一周就没人能复现。

一个反模式值得单独说：用输出正则把免责声明清掉，然后宣布一致性问题已经解决。这只会让日志和评测同时失真，因为行为倾向没有变，只是被遮住了。

## 十、多供应商路由时的模板对齐

路由层要做的不只是挑一个还活着的上游。模板维度的对齐至少包括：

- **统一中间表示**：应用侧只产生语义层 messages，模板渲染放在路由之后、上游之前；
- **不要相信"OpenAI 兼容"等于模板一致**。兼容的是接口形状，不是渲染规则；
- **模板档位随任务走，不随上游走**。多上游切换同一个任务时，模板档位保持一致，除非有意做对照；
- **跨上游等价性验收**：同一批问题在两个上游上各跑一遍，比对口吻指标分布，而不只是比对答案是否正确；
- **映射表要能被审计**。上游改变模板行为时，映射表是唯一能快速定位影响面的东西。

一个实用的折中：把上游按"模板行为分组"，路由在组内切换，跨组切换需要显式声明。

## 十一、输出一致性验收清单

上线前逐条过一遍：

1. 模板档位是否有 ID 与版本号，调用点是否只引用 ID；
2. 每条请求日志是否带模板指纹；
3. 评测结果是否记录模板指纹，历史结果是否可复现；
4. 自我相关提问是否纳入问题集，例如"介绍一下自己能做什么"；
5. 口吻指标是否有基线，基线是否绑定模板版本；
6. 模型别名到模板档位的映射是否集中管理、可审计；
7. 多上游切换时，模板档位是否随任务保持一致；
8. 模板变更是否走评审、回归与灰度，而不是热更新；
9. 是否存在调用点内联拼接模板；
10. 输出过滤是否被误用成一致性治理手段。

十条里最容易漏的是第 3 条和第 9 条。前者让历史结论失去可比性，后者让模板治理形同虚设。

## 十二、成本与风险提示

- 模板固定与版本化会降低灵活性：每增加一个模板档位，就多一套需要长期维护的验收基线与回归任务，这部分是实打实的工程开销；
- 上游对模板的控制粒度不一致，部分供应商不暴露模板选择，只能靠 system 段的有无来近似控制，效果属于估算，需要实测确认；
- 模板指纹、评测结果与请求日志的留存会带来存储与查询开销，采样策略与保留期限要提前设计；
- 用输出过滤掩盖口吻差异，会让评测与审计同时失真，风险比偏移本身更大；
- 面向用户的系统不要把模型的自我陈述当作权限或能力的事实来源，自我描述描述的是部署形态；
- 模板治理属于一致性工程，不改变模型的能力上限，指望换模板提升能力是方向性错误。

## 结论

同一个权重、同一段 prompt，接入层拼出来的 chat template 不同，模型的口吻与自我描述就会系统性偏移。在 8 个不超过 9B 参数的 instruct 模型上，模板存在与否构成一个开关；在 3 个模型的激活里，还找到了一个可以操纵该行为的方向——移除则免责声明口吻下降，加入则上升，同规模的随机方向几乎没有影响。

对接入方的动作是把模板当作一致性变量：在 4sapi.com 这类中转站与自建网关上，把模板集中成配置并版本化，把模板指纹写进日志与评测结果，让模板变更走回归与灰度，多上游路由时让模板档位随任务走。验收清单里的十条，本质上只回答一个问题：这套系统能不能复现自己昨天说过的话。

模型关于自身的说法不是关于它的事实；同理，一套没有模板指纹的评测结论，也不该被当成结论。

欢迎在评论区聊聊手头系统里模板是怎么管的，或者踩到的口吻漂移的坑。
