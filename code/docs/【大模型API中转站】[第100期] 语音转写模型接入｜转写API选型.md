# 【大模型API中转站】[第100期] 语音转写模型接入｜转写API选型

语音转写赛道又来了一个新选手：Microsoft 发布 MAI-Transcribe-2，主打说话人分离、可配置转写风格和词级时间戳。

在它面前的是 Gemini 3.5 Transcribe、GPT-Transcribe 和 Whisper V3-Large 这些老牌模型。语音转写 API 怎么选？这篇我拆开讲清楚选型维度和接入方式。

## 一、开篇痛点

语音转写看起来简单，实际坑很多：会议录音有多个人说话，转出来分不清谁是谁；同声传译要实时，字幕要时间戳，转写风格还要能配置。

选错转写模型，轻则返工重转，重则下游任务全错。而市面上的转写模型各有侧重，比单纯看"准确率"复杂得多。

## 二、原理速览：转写模型在做什么

语音转写（ASR）把音频转成文本，但现代转写模型的能力远超"听写"：

```text
音频输入
    |
    v
语音识别（声学模型 + 语言模型）
    |
    +----> 转写文本
    |
    +----> 说话人分离（谁在说）
    |
    +----> 词级时间戳（每词对齐时间）
    |
    +----> 转写风格（逐字稿 / 整理稿）
```

MAI-Transcribe-2 的核心卖点就是把后三项做成了可配置能力，而不是固定输出。

## 三、选型维度：别只看准确率

我对比转写模型时按四个维度：

| 维度 | 说明 | 重要场景 |
| --- | --- | --- |
| 转写准确率 | 字错误率 | 所有场景 |
| 说话人分离 | 区分不同说话人 | 会议、访谈 |
| 词级时间戳 | 每词对齐时间 | 字幕、配音 |
| 转写风格 | 逐字稿/整理稿可配置 | 会议纪要、内容创作 |

单项能力强的模型不一定全能。选型先明确主要场景，再按维度加权对比。

## 四、接入示例：Python 转写

我用统一接入层做语音转写，音频上传后返回带时间戳和说话人标签的文本：

```python
from openai import OpenAI

client = OpenAI(api_key="4sapi-key", base_url="https://4sapi.com/v1")

with open("meeting.mp3", "rb") as f:
    resp = client.audio.transcriptions.create(
        model="mai-transcribe-2",
        file=f,
        response_format="verbose_json",
        timestamp_granularities=["word"],
    )

for seg in resp.segments:
    print(f"[{seg.get('start'):.1f}s-{seg.get('end'):.1f}s] "
          f"说话人{seg.get('speaker')}: {seg.get('text')}")
```

`verbose_json` 返回完整结构：每段文本、起止时间、说话人标签。字幕和会议纪要都能直接生成。

接入时的几个工程细节：音频格式建议统一转成 16kHz 单声道 wav，兼容性最好；长音频分段转写再拼接时，注意段与段之间可能丢字；说话人标签在不同分段里可能不连续，拼接后要做一次说话人 ID 归一化。这些细节不处理，转写结果看着能用，落到下游就出问题。

## 五、风格配置：逐字稿 vs 整理稿

MAI-Transcribe-2 支持可配置的转写风格。同一段音频，两种风格输出完全不同：

```text
逐字稿：嗯，那个，我觉得这个方案，呃，可行。

整理稿：我认为这个方案可行。
```

字幕和质检要逐字稿，会议纪要和内容创作要整理稿。接入时把风格作为参数传入，而不是在文本上二次加工。

```python
resp = client.audio.transcriptions.create(
    model="mai-transcribe-2",
    file=audio_file,
    prompt="输出整理稿风格，去除口头语，保留关键信息。",
)
```

风格可配置意味着一条链路服务多种下游需求。

## 六、成本与风险提示

- 长音频成本：转写按音频时长或 token 计费，长录音要估算；
- 说话人分离不完美：同音色说话人可能被误判为同一人；
- 专业术语：医学术语、产品名可能转错，需要术语表；
- 多语言混说：中英混杂场景要确认模型支持；
- 隐私：会议录音可能含敏感信息，注意数据链路合规。

## 七、术语表与后处理

转写质量提升最快的手段是术语表和后处理。我先给模型传术语提示，再对输出做规则校验：

```python
GLOSSARY = {"4sapi": "4sapi", "LLM": "大语言模型", "Astra": "Astra"}


def post_process(text: str) -> str:
    for src, dst in GLOSSARY.items():
        text = text.replace(src, dst)
    return text
```

术语表解决模型不懂的专业词，规则后处理兜底固定格式，两者配合成本最低。

## 八、接入检查清单

1. 明确主要场景：会议、字幕、访谈还是质检；
2. 按准确率、说话人分离、时间戳、风格四维度打分选型；
3. 用真实音频样本测试，不要用官方 demo 音频；
4. 配置术语表，处理专业术语；
5. 确认多语言与口音支持范围；
6. 检查长音频的成本与超时限制；
7. 敏感音频走合规链路，评估数据留存策略。

## 九、我的结论

语音转写选型的关键是场景先行：会议纪要要说话人分离，字幕要词级时间戳，内容创作要风格配置。MAI-Transcribe-2 把这三项做成可配置能力，接入体验比固定输出的模型好一截。选型时用真实音频做对照，比看参数表可靠。

## 总结

MAI-Transcribe-2 在说话人分离、转写风格和词级时间戳上做出差异化，语音转写 API 的选型要从场景出发按维度对比。我在 4sapi（https://4sapi.com）上把转写接入统一管理，术语表和后处理补齐模型短板。欢迎在评论区聊聊语音转写的踩坑经历。
