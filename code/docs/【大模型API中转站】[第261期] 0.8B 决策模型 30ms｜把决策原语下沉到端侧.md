# 【大模型API中转站】[第261期] 0.8B 决策模型 30ms｜把决策原语下沉到端侧

在成本优化的讨论里，注意力通常集中在"换更便宜的模型"或"优化提示词"上。但有一类成本几乎没人动：**决策本身**。

一次路由判断、一次分类、一次"该不该继续"的二选一——这些动作在高频链路里每天发生数百万次，而它们目前大多由大模型完成。把这类判断下沉到小模型，边际成本可以趋近于零。我在 4sapi（https://4sapi.com）上做链路成本治理时，这是收益最直接的一步。

## 一、先识别哪些是"决策原语"

决策原语指的是这样一类动作：**输入结构简单、输出空间有限、判定规则稳定**。它们的共同特征是——不需要生成能力，只需要判断能力。

典型例子：

- 请求该走哪个档位的模型（路由）；
- 输入属于哪一类任务（分类）；
- 两个候选中哪个更优（排序/选择）；
- 当前是否应该继续（收敛判断）；
- 输出是否满足格式约束（校验）。

识别方法也很直接：**如果这个动作的输出可以用一个枚举值或一个分数表示，它就很可能属于决策原语**。反过来，如果输出是自由文本、需要组织语言、或者需要多步推理链条，就更适合留给大模型。

这一步的清理价值常被低估。一条链路里真正需要生成能力的环节通常只有少数几个，其余多数是判断类动作。

## 二、0.8B 与 30ms 意味着什么

一组公开数据给出了这个方向的量级参考：一个 **0.8B** 规模的决策模型系列，与既有的决策模型家族兼容，**在家中训练**，推理延迟约 **30ms**。

三个数字各有含义：

**0.8B** 意味着它可以在消费级硬件上运行——不必部署到有加速卡的机器上，可以直接放进应用进程或本地服务。

**30ms** 意味着它可以落在请求链路的关键路径上。相比之下，一次云端大模型调用的首 token 延迟通常在数百毫秒量级；如果每个请求都要先做一次"该走哪条路"的判断，这个判断的延迟会直接叠加到总延迟上。

**在家中训练**说明训练门槛同样不高。决策类模型不需要海量通用语料，只需要**本领域的高质量标注对**——而这类数据往往可以从线上的历史调用日志里自动构造（例如：同一输入下用户最终选择了哪个分支）。

对成本敏感的高频链路，把这些原语下沉到 0.8B 级模型的收益，通常大于在旗舰模型上做提示词优化。后者的优化空间受限于模型自身的推理开销，而前者直接把每次判断的成本压到可以忽略。

## 三、成本锚点：三条曲线

把成本放进同一坐标系，选择就清楚了。当前可参考的三个锚点是：

| 层次 | 典型成本 | 延迟量级 | 适用动作 |
| --- | --- | --- | --- |
| 本地决策模型 | 边际成本趋近于零 | 约 30ms | 路由、分类、校验 |
| 中端模型 | 按任务计费，低档 | 数百 ms 起 | 结构化生成、简单推理 |
| 旗舰模型 | 排名靠前档位 | 秒级 | 多步推理、长链条任务 |

中间一行的具体数字可以看 agent 场景的实测：某一个中端档位在真实智能体会话上取得 **+1.6%** 的净提升，**单任务成本 $0.05**；而排名靠前的旗舰档位取得 **+12.15%** 的净改进，成本比上一代旗舰低 **56%**。

把三行放在一起，这条链路的合理分工就出来了：**决策用本地模型，执行按难度选中端或旗舰，只有真正困难的任务才上旗舰**。三类动作的成本差达几个数量级，因此分工带来的节省远大于在单一档位内做参数调优。

整条链路的形态可以画成三级：

```text
请求进入
    |
    v
[第一级] 本地决策模型（约 30ms，边际成本趋零）
    |        路由 / 分类 / 校验 / 选择
    |
    +-- 判定为简单 -> 本地直接给出结果，链路结束
    |
    +-- 判定为复杂 或 校验不通过
             |
             v
        [第二级] 中端模型（按任务计费，低档）
             |
             +-- 顺利 -> 返回
             |
             +-- 超规格 / 多步 / 长链条
                      |
                      v
                 [第三级] 旗舰模型
                      |
                      v
                 返回 + 记录所在层级
```

图里最后一行"记录所在层级"是这套结构能否持续优化的前提。没有层级标记，就不知道成本花在哪一级，也就无法判断下一轮的优化方向是"更多下沉"还是"更多升级"。

## 四、端侧这一层的真实约束

把决策下沉到端侧很有吸引力，但端侧有一个比"变慢"严重得多的约束。

在旗舰移动设备上的实测发现：**持续的端侧生成会让 GPU 推理运行时变得不稳定，在连续几次查询后崩溃或静默卡死**。失效点位于当前工具链（kernel 编译与移动 GPU 上的长 prompt prefill），**即使设备是凉的也会复现**，且对长生成最严重。

这个约束对决策模型的影响相对小——决策原语的输出很短（一个枚举值或一个分数），不涉及长生成。但它提示了一条边界：**适合端侧的是"短输出、高频、可校验"的动作**，而不是需要长输出的生成任务。

由此得到端侧部署的三条实践要求：

- **限制输出长度与连续调用次数**，把它保持在工具链稳定的区间内；
- **在客户端加看门狗**，静默卡死必须能被检测并重启，而不是让请求挂起；
- **预设备用路径**，端侧失败时降级到下一层，而不是重试同一条路径。

第三条尤其重要。没有降级路径时，端侧的不稳定会直接变成端到端的不稳定；有了降级路径，端侧的价值（数据不出设备、离线可用）得以保留，而它的失效被限制在局部。

## 五、奖励函数里必须给本地项留位置

三级路由如果按"质量、延迟、成本"三个目标优化，会得到一个反直觉的结果：**最优策略会把每一次查询都卸载到云端**。

原因很简单——在这个目标集里，本地执行的价值（数据不出设备、离线可用、单次零成本）**没有位置**。云端模型在质量与延迟上通常都更优，成本在优化目标里又是可以权衡的一项，于是本地这一层被完全放弃了。

修正办法是在奖励里加一项**本地性奖励**，明确褒奖端侧执行。加上之后，策略才会在"质量与延迟可接受"的前提下优先选本地。

这是一个很典型的工程陷阱：**用单一维度的成本指标去优化多目标系统，会系统性地牺牲掉未被计入的那些目标**。同样的错误在别处也常见——例如只按 token 用量优化提示词，会牺牲掉可维护性与可读性；只按延迟优化批处理，会牺牲掉吞吐与成本。判断方法是在写下优化目标时反问一句：**哪些真正在乎的性质没有被写进去**。

## 六、路由的收益在哪：延迟与覆盖，而非质量

还有一处容易误判的地方：**分层路由的收益不在质量上**。

实测对比很说明问题：始终使用端侧执行的方案，在**可服务的查询上与路由方案的每次查询质量持平**；差别在于它**慢 3 到 6 倍，且长查询会失败**。

所以路由的价值是三维的：

- **延迟**：把一部分负载留在本地，整体响应更快；
- **可靠性**：长查询或超规格请求能自动升级，不会失败；
- **覆盖率**：本地处理不了的请求也有去处，系统能服务的输入范围更宽。

这说明评估路由方案时，质量指标不是主要判据——它是**准入条件**（质量必须达标），而收益要按延迟、可靠性与覆盖率来衡量。如果只对比质量，会得出"路由没有必要"的错误结论。

## 七、路由器怎么训练与验收

路由器本身也是一个小模型，训练与验收有几点值得注意。

**状态设计**：决策依据应当包含**双方的能力边界**，而不只是输入特征。例如端侧路由需要考虑设备当前的热余量与可用资源——同一台设备在不同状态下能承担的任务量是不同的。

**离线训练、在线执行**：路由器用历史数据离线训练（例如 Q-learning 类方法），线上只做一次前向推理。这样延迟可控，也不会因在线学习引入不稳定。

**冷启动**：初始策略可以先用规则代替，收集一段时间真实数据后再训练。直接用规则长期运行也可以接受——规则的优势是可解释、可审计。

**验收要对比基线和启发式**：一个可参考的验收方式是让学到的策略与**两个手工调的启发式**对比，看质量与成本是否同时更优。如果只是不差于启发式，收益不足以支撑引入一个学习组件。

**覆盖率的定义要提前定**：什么是"可服务"、什么算"失败"，需要在验收前明确，否则容易把失败样本排除在统计之外，得出过于乐观的结论。

## 八、端侧可跑的规模在下探

支撑"决策下沉"这一判断的，还有一组基础设施侧的进展：小模型在端侧的可行规模正在持续下探。

浏览器里已经可以试跑多个极小模型；更极端的例子是在 **ESP32S3 集群**上运行 **1.58-bit** 量化语言模型——把模型压到了微控制器级别。同时，面向计算机使用的 agent 模型也在往小尺寸铺：一个系列同时提供 **27B 密集版**与 **35B-A3B 稀疏版**，另有更小的 Nano 档位。

这些方向合起来说明：**"能跑在哪"这条边界正在快速下移**。对做端侧方案的团队，这意味着今天需要云端兜底的任务，可能在下一次迭代里就能落到端侧。设计上应当预留这种迁移能力——把任务按"当前落在哪一层"做成配置，而不是把层级选择硬编码在业务逻辑里。

## 九、接入示例：两级决策与路由

下面这段脚本实现一个两级结构：用轻量规则（可替换为本地决策模型）做首轮判断，判定为复杂或校验失败时升级到云端模型。

```python
import os, re, json
from openai import OpenAI

client = OpenAI(
    api_key=os.getenv("FOURSAPI_API_KEY"),
    base_url="https://4sapi.com/v1",
)

LOCAL_ENDPOINT = os.getenv("LOCAL_MODEL_URL", "http://127.0.0.1:8081/decide")
MID_MODEL = os.getenv("MODEL_MID", "claude-sonnet-5-5")
TOP_MODEL = os.getenv("MODEL_TOP", "claude-opus-5-5")

PRIMITIVES = {   # 判定为决策原语的任务类型：短输出、可校验"route", "classify", "validate", "pick"}

HARD_HINTS = re.compile(r"逐步|推演|对比.*方案|先.*再.*最后|多步")


def local_decide(payload):
    """本地决策模型（或无依赖时的规则兜底）。返回 (label, score)。"""
    import urllib.request
    try:
        req = urllib.request.Request(
            LOCAL_ENDPOINT,
            data=json.dumps(payload).encode("utf-8"),
            headers={"Content-Type": "application/json"},
        )
        with urllib.request.urlopen(req, timeout=0.5) as r:
            obj = json.loads(r.read().decode("utf-8"))
            return obj["label"], float(obj.get("score", 0.0))
    except Exception:
        # 兜底规则：出现多步线索即判为复杂
        return ("complex" if HARD_HINTS.search(payload["text"]) else "simple"), 0.0


def needs_top(payload):
    if len(payload["text"]) > int(os.getenv("TOP_LEN", "4000")):
        return True
    return bool(HARD_HINTS.search(payload["text"]))


def cloud_call(model, text, max_tokens=512):
    r = client.chat.completions.create(
        model=model, max_tokens=max_tokens, temperature=0,
        messages=[{"role": "user", "content": text}],
    )
    return r.choices[0].message.content or ""


def handle(payload):
    """payload: {"task": "route"|"classify"|..., "text": "..."}"""
    task = payload["task"]

    # 第一级：决策原语走本地
    if task in PRIMITIVES:
        label, score = local_decide(payload)
        if label == "simple":
            return {"layer": "local", "label": label, "score": score}

    # 第二级 / 第三级：按难度选档
    model = TOP_MODEL if needs_top(payload) else MID_MODEL
    out = cloud_call(model, payload["text"])
    return {"layer": "top" if model == TOP_MODEL else "mid",
            "model": model, "text": out[:200]}


if __name__ == "__main__":
    demo = [
        {"task": "classify", "text": "把这封邮件归类到投诉或咨询。"},
        {"task": "generate", "text": "逐步推演：先解释 KV 缓存，再对比三种推理优化方案。"},
    ]
    for d in demo:
        print(json.dumps(handle(d), ensure_ascii=False))
```

三个设计要点：`local_decide` 带**超时**（0.5 秒）与**规则兜底**，保证本地不可用时不会拖慢链路；`needs_top` 把"是否必须上旗舰"的判断独立出来，便于单独调整；`handle` 的返回里始终带 `layer` 字段，让后续统计能按层级归因成本与延迟。

## 十、成本与风险提示

- **决策原语的边界要谨慎划定**。判定为原语就必须可校验，校验覆盖不到的动作不要下沉，否则错误会静默通过。
- **端侧必须有限制与降级**，连续调用次数、单次长度、看门狗、备用路径四项缺一不可。
- **奖励函数要显式列出非成本目标**，否则本地执行、离线可用这类价值会被成本目标挤掉。
- **路由方案的质量指标是准入门槛而非收益来源**，收益要按延迟、可靠性与覆盖率衡量。
- **覆盖率的定义要在验收前定死**，否则失败样本容易被排除在统计之外。
- **层级选择要做成配置**，端侧可跑的规模在持续下探，预留迁移能力比一次做到最优更重要。

## 结论

成本优化里收益最直接的一步，是把**决策**从大模型手里接过来。一次路由、一次分类、一次校验，输出空间有限、规则稳定，用 0.8B 级模型在约 30ms 内完成，边际成本趋近于零——而这类动作在链路里出现的频率远高于生成。落地时有四处要点：先识别哪些动作属于决策原语，端侧部署必须配限制与降级，奖励函数里必须显式给本地执行留权重，以及把路由的收益按延迟、可靠性与覆盖率而不是质量来衡量。最后一条判断尤其值得记住：**只按成本优化多目标系统，会牺牲掉未被计入的那些目标**；这与我在 4sapi.com 上做链路治理时得到的经验一致——先写清在乎哪些性质，再决定优化什么。
