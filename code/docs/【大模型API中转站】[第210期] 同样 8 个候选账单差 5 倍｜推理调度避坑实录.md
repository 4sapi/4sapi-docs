# 【大模型API中转站】[第210期] 同样 8 个候选账单差 5 倍｜推理调度避坑实录

同样生成 8 个候选，执行方式不同，GPU 能耗和 P95 延迟可以差出 5 到 6 倍。候选数 N 只回答"生成多少"，从不回答"怎么执行"，而账单恰恰由后者决定。

## 一、先说结论：账单差在调度，不在候选数

多候选采样（best-of-N、self-consistency）是公认的提分利器：固定候选预算 N=8，让模型回答 500 道 GSM8K 数学题，N 从 1 提到 8，Phi-3-mini 准确率提升 8.4 个百分点，Qwen2.5-1.5B 提升 18.4 个百分点。分数涨得实实在在，这确实是推理时最划算的换分手段之一。

但痛苦来得同样实在。我在 4sapi（https://4sapi.com）做 API 接入支持的日常里，最常遇到的一类问题是"同样跑 8 个候选，为什么这个月的延迟告警和算力开销一起翻倍"。排查到最后，十有八九不是模型变了、不是题目变了，而是调度方式变了：有人把 8 个候选写成 for 循环串行调用，有人用 asyncio 一次并发发出全部 8 个请求。候选数一模一样，token 消耗几乎一样，执行层面的差距却被完整地记进了延迟曲线和能耗账单。

这一期就把"调度决定账单"这件事拆开讲清楚：一组实测数据、一张调度对比表、一张时序图，再落到接入侧可以直接抄的 asyncio 改造方案和避坑清单。

## 二、一组实测数据：N=8 下的四种调度

先给数据。一组关于 test-time scaling 系统成本的实测是这样的：固定候选预算 N=8，比较四种生成调度——1x8、2x4、4x2、8x1。记法 axb 表示 a 次调用、每次 b 个候选。在 A100 GPU 上，8 次串行调用（8x1）比 1 次批式调用（1x8）多耗 4.64–4.86 倍 GPU 能量，P95 延迟高出 5.77–6.12 倍。

实验模型是 Phi-3-mini 与 Qwen2.5-1.5B，任务是 500 道 GSM8K 数学题。同样的模式在 3 个独立调度的 A100 节点上复现，也在短输出的 SciQ/V100 实验里复现——换节点、换数据集、换卡，量级差距依然在那里。

四种调度放在一起看：

| 调度 | 调用次数 | 每次候选数 | 执行形态 | P95 延迟 | GPU 能耗 |
| --- | --- | --- | --- | --- | --- |
| 1x8 | 1 | 8 | 单次批式并发 | 基准（1x） | 基准（1x） |
| 2x4 | 2 | 4 | 两波批式 | 介于基准与串行之间 | 介于基准与串行之间 |
| 4x2 | 4 | 2 | 四波小并发 | 更靠近串行一侧 | 更靠近串行一侧 |
| 8x1 | 8 | 1 | 纯串行 | 5.77–6.12 倍 | 4.64–4.86 倍 |

说明两点：倍数区间是 A100 上 8x1 相对 1x8 的实测范围；2x4 与 4x2 落在两者之间，具体位置取决于单次调用的固定开销占比和波次之间的等待，不宜脱离环境拍脑袋填数。这张表最重要的读法是第一列和最后一列的对照——候选数完全相同，成本结论完全不同。

## 三、原理速览：N 管生成多少，调度管怎么执行

test-time scaling 的思路是用推理时的额外计算换准确率：一道题不够笃定，就生成多个候选答案，然后挑最好的一个（best-of-N），或者让多数票说话（self-consistency）。这一步只规定了候选数 N。

但"生成 8 个候选"在系统层面至少有四种执行方式，就是上面那张表的四行。四种方式的 token 总量几乎一样，模型看到的上下文也一样，差异全部来自执行层：

- 纯串行（8x1）：每次调用只带一个候选，GPU 大部分时间在等上一个请求收尾，请求解析、调度排队、KV cache 预填、解码启动这些固定开销被重复支付 8 次；
- 单次批式（1x8）：一次调用带 8 个候选，8 条序列共享同一次调度与预热，GPU 按批次吞吐，空闲时间被压缩到最低；
- 中间态（2x4、4x2）：批次换来了部分固定开销共享，但波次之间仍然串行等待，波数越多越接近纯串行。

一句话总结：候选数决定分数上限，调度决定把这笔分换算成多少延迟和能耗。N 是算法参数，调度是系统参数，混在一格表格里，成本问题就永远找不到责任人。

## 四、调度时序图：串行的账是怎么滚起来的

把两种极端调度画在同一条时间轴上，差距一目了然：

8x1 纯串行（for 循环，一次只发一个请求）

候选7                          ████
候选8                              ████

总耗时 ≈ 各段延迟依次叠加，P95 被尾部逐段放大

图上画的是理想叠加形态，实测 P95 是 5.77–6.12 倍而不是满额的 8 倍，说明并非每一段都完全串行满叠加，但量级没有任何争议。还有一个容易被忽略的细节：两种方式都要等最后一个候选才能汇总投票，差别在于"最后一个候选"什么时候到——串行链路里它是第 8 段延迟的终点，批式链路里它只是同一个批次里最慢的那一条。

## 五、为什么 8 次串行会贵这么多

把 4.64–4.86 倍能耗和 5.77–6.12 倍 P95 拆到机制层面，主要是四笔账：

- 固定开销重复支付：每次调用都要走一遍请求解析、排队、预填、解码启动。批式调用把这些成本摊给 8 个候选，串行调用则原价支付 8 次。候选越短，固定开销占比越高，串行越亏——SciQ 这类短输出任务上模式依然成立，就是这个原因。
- GPU 利用率断崖：单候选的小请求撑不满 A100 的批次容量，大量算力在空转。能耗按时间照付，产出却没有对应增加，这笔浪费在账单上不可见，在功耗计上很诚实。
- 尾部延迟叠加：P95 看的是整体分布，串行把 8 段分布卷在同一条链上，任何一段慢，整体就慢。批式把 8 段分布压进同一个批次，整体只取决于最慢的一条。
- 失败重试更疼：串行链路里任何一个候选失败重试，都要重新走完剩下的整条链；批式里重试只影响自己那一条，其他 7 个照常返回。

## 六、评测报告里缺的那几列

很多评测表格只有两列：候选数 N、准确率。同样的 N=8、同样的准确率，背后可能是 1x8，也可能是 8x1，账单差 5 倍这件事被完全隐藏了。这也是这组实测最重要的结论：评测不应只报告候选数与准确率，还应报告生成调度与 GPU 级系统指标（延迟、吞吐、GPU-hours、能耗）。

一份能让别人复现、能横向比价的评测，至少应该包含：

- 生成调度：1x8、2x4、4x2 还是 8x1，用统一记法写清楚；
- GPU 级指标：P95 延迟、吞吐、GPU-hours、能耗；
- 硬件与环境：A100 还是 V100，节点是否独立调度；
- 模型与任务：Phi-3-mini 还是 Qwen2.5-1.5B，500 道 GSM8K 还是短输出的 SciQ。

同一份数据换一个调度复测，准确率大概率还在原位，成本结论可能整个翻转。只抄准确率的评测，恰好省掉了最贵的两列。

## 七、API 接入侧怎么选调度

把结论落到 API 接入侧，我的默认建议只有一条：能用批式并发，就不要 for 循环串行。

常见接入形态与调度的对应关系：

| 接入形态 | 对应调度 | 建议 |
| --- | --- | --- |
| for 循环逐个 await | 8x1 | 改造为 asyncio 并发 |
| asyncio.gather 一次发 N 个 | 1x8 | 多数场景的默认选择 |
| Semaphore 限流 + 分波 gather | 2x4 / 4x2 | 触发限流或超长输出时的折中 |
| 网关侧统一编排 | 由网关决定 | 按配额路由，客户端不再手工控波 |

还有一个和记法直接对应的接口细节：OpenAI 兼容协议里，请求体的 n 参数就是"每次调用带几个候选"中的 b。n=8 的一次调用对应 1x8，循环里 n=1 跑 8 次对应 8x1。调度记法不是抽象概念，它就落在请求参数和循环结构上。

以 4sapi（https://4sapi.com）为例，接入是标准的 OpenAI 兼容流程：控制台创建令牌，base_url 指向中转地址，其余代码与官方 SDK 写法完全一致。多候选采样这种高频并发场景，中转网关侧的并发配额、超时策略和预算熔断会直接决定调度方式能不能跑稳，这一点在后面的网关一节展开。

## 八、用 asyncio 把串行循环改成批式并发

下面是可以直接改改就用的批量并发版本：每个问题生成 8 个候选，带并发上限、超时、指数退避重试和多数票汇总。

```python
import asyncio
import random
from collections import Counter

from openai import AsyncOpenAI

client = AsyncOpenAI(
    api_key="sk-xxxx",                    # 中转站控制台创建的令牌
    base_url="https://4sapi.com/v1",      # OpenAI 兼容地址
)

N = 8                  # 候选预算：固定 N=8
MAX_CONCURRENCY = 8    # 并发上限：对应 1x8 调度
TIMEOUT_S = 60         # 单次调用超时
MAX_RETRIES = 2        # 失败重试上限

sem = asyncio.Semaphore(MAX_CONCURRENCY)

async def one_candidate(question: str) -> str | None:
    """生成一个候选答案，带超时与指数退避重试。"""
    for attempt in range(MAX_RETRIES + 1):
        try:
            async with sem:
                resp = await asyncio.wait_for(
                    client.chat.completions.create(
                        model="model-name",        # 按中转站模型列表填写
                        messages=[
                            {"role": "user", "content": question}
                        ],
                        temperature=0.7,           # 多候选采样需要温度大于 0
                        max_tokens=512,
                    ),
                    timeout=TIMEOUT_S,
                )
            return resp.choices[0].message.content
        except Exception:
            if attempt == MAX_RETRIES:
                return None
            await asyncio.sleep(0.5 * (2 ** attempt) + random.random())
    return None

def majority_vote(answers: list[str | None]) -> str | None:
    """self-consistency：数学题建议先抽取最终数值再投票。"""
    valid = [a for a in answers if a]
    if not valid:
        return None
    return Counter(valid).most_common(1)[0][0]

async def best_of_8(question: str) -> str | None:
    answers = await asyncio.gather(
        *(one_candidate(question) for _ in range(N))
    )
    return majority_vote(list(answers))

async def main() -> None:
    questions = ["1.2 与 0.9 相加等于多少？"]  # 替换为批量题目列表
    results = await asyncio.gather(
        *(best_of_8(q) for q in questions)
    )
    for q, r in zip(questions, results):
        print(q, "->", r)

if __name__ == "__main__":
    asyncio.run(main())
```

改造前的样子，也就是要避开的 8x1 调度：

```python
# 串行版本：同样的 8 个候选，延迟按链路逐段叠加
answers = []
for _ in range(N):
    answers.append(await one_candidate(question))
```

两个版本的 token 消耗几乎相同，差别全在执行层：串行版本的 P95 由 8 段延迟相加决定，批式版本由最慢的一条候选决定。生产环境的数学题投票建议在 majority_vote 之前先从答案里抽取最终数值（比如等号后面的数字或最后一个数值），让投票落在数值层面而不是文本层面。

## 九、重试与超时：并发之后才真正重要

串行时代，重试无非是多等一轮；改成批式并发之后，重试设计不当会把并发优势全部吃掉，甚至放大成事故：

- 客户端超时要小于网关超时：反过来就会出现"客户端还在等，服务端已经放弃"的悬空请求，能耗照记、结果没有；
- 重试必须带抖动（jitter）：8 个候选同时失败、同时重试，等于亲手制造一次流量尖峰，触发限流之后再集体失败一次；
- 重试次数要有上限：MAX_RETRIES=2 足够覆盖偶发抖动；N=8 的乘数之下，无限重试会把一次抖动放大成 8 倍的连锁反应；
- 失败的候选按缺失处理：示例里的 majority_vote 已经把 None 过滤掉，宁可 7 个候选投票，也不要为了凑满 8 个把重试打满。

这四条的共同点是确定性：超时、退避、上限、缺失处理都应该是代码里的显式参数，而不是"到时候再说"的运行时行为。

## 十、压测看 P95，不看平均值

平均值会撒谎。串行调用的平均延迟可能看起来"还在可接受范围"，但 P95 会把链路叠加完整暴露出来：

- 平均延迟描述"一般情况"，P95 描述"最慢的那批请求"，而超时告警和用户流失都挂在尾部；
- 串行调度的问题恰恰集中在尾部：任何一段慢，整条链慢，分布的长尾被逐段拉长；
- 压测要按调度分别压：1x8 和 8x1 的 P95 必须分开记录，混在一张均值表里等于没压；
- 实测里 5.77–6.12 倍这个数字本身就是 P95 口径，如果只看平均值，这个差距会被平滑掉一大截。

接入侧的落地动作很简单：给批量任务加一个最简单的耗时统计，记录每个批次完成时间的 P50 和 P95，跑两种调度各一遍，账单差异会自己浮出水面。

## 十一、把调度参数写进评测报告

第六节说的是"应该报告什么"，这一节落到操作层面：把调度当成实验参数管理，和 temperature、max_tokens 同级对待。每条评测记录长这样：

```text
n_candidates : 8
schedule     : 1x8          # 换成 8x1 时整条记录都要重测
hardware     : A100（独立调度节点复现）
model        : Phi-3-mini / Qwen2.5-1.5B
task         : GSM8K x 500
accuracy     : ...
p95_latency  : ...
throughput   : ...
gpu_hours    : ...
energy       : ...
```

两条纪律：

- 换调度就换记录：1x8 的结论不能外推给 8x1，哪怕候选数、模型、题目完全相同；
- 系统指标与准确率同表呈现：把延迟、吞吐、GPU-hours、能耗放进同一张表，成本问题才藏不住，调度差异才有人负责。

## 十二、网关侧：并发配额与预算熔断

多候选采样是典型的"瞬时并发放大器"：一道题乘 8 个候选，100 道题的批任务瞬间就是 800 个在途请求。这种形状的流量，光靠客户端自觉是不够的，网关侧需要四件套：

- 并发配额：按 API Key 限制同时在途请求数，防止一个批任务占满整个通道，影响同 Key 下的其他业务；
- 预算熔断：累计消费或 GPU-hours 达到阈值自动降速或暂停，而不是等账单出来再复盘；
- 排队与削峰：超配额的请求进队列而不是直接报错，配合客户端的重试抖动形成缓冲；
- 指标透出：P95、在途数、失败率按 Key 可查，调度问题才有得诊断。

4sapi（https://4sapi.com）网关侧的并发配额与预算熔断就是为这类场景准备的。接入侧要做的事是让两端对齐：客户端的并发上限、超时、重试参数与网关配额匹配，而不是各自为政——两边各跑各的，超时和账单都会失控。

## 十三、调度避坑清单

上线一个多候选采样任务之前，按这张清单过一遍：

- [ ] 调度记法明确：1x8 / 2x4 / 4x2 / 8x1，写在配置和评测记录里；
- [ ] 客户端并发上限用 Semaphore 控制，而不是裸 gather 打满；
- [ ] 单次调用超时小于网关超时，重试带指数退避和抖动；
- [ ] 重试次数有上限，失败候选按缺失参与投票；
- [ ] 批量任务的 P50/P95 分调度记录，不混平均值；
- [ ] 评测报告包含生成调度与 GPU 级指标（延迟、吞吐、GPU-hours、能耗）；
- [ ] 网关侧并发配额与客户端并发上限对齐；
- [ ] 预算熔断阈值已设置，超限自动降速而不是继续打满。

## 十四、成本与风险提示

- 计费模式决定差距落在哪：按 token 计费时，串行与批式的 token 账单接近，差距主要体现在 P95 延迟、限流占用和超时重试上；按 GPU-hours 或包月算力计费时，4.64–4.86 倍的能耗差距会直接落到账单上；
- 并发不是免费的：批式并发把压力推给了配额与队列，N=8 的批任务要先确认配额再放量，避免挤占同 Key 的其他业务；
- 准确率收益有边界：N 从 1 到 8 的提升（Phi-3-mini +8.4 个百分点、Qwen2.5-1.5B +18.4 个百分点）是这组实验的观察，换模型、换任务后需要重新实测，不要把候选数当成无脑堆叠的旋钮；
- 结论可复现优先：调度、硬件、任务规模任何一个变量变化，成本结论都要重测，不要跨环境搬运倍数。

## 结论

候选数 N 决定多候选采样能换回多少准确率，生成调度决定这笔交换的真实价格。同样 N=8，1x8 与 8x1 的 GPU 能耗差 4.64–4.86 倍、P95 延迟差 5.77–6.12 倍，而这两列在太多评测报告里根本不存在。

把调度写成显式参数，用 asyncio 批式并发替代串行循环，重试与超时显式化，压测盯 P95，把延迟、吞吐、GPU-hours、能耗和准确率放进同一张表，再让网关侧的并发配额与预算熔断兜底——这套组合拳不改变模型，却能实打实改变账单。接入侧的具体配置项，4sapi（https://4sapi.com）的接入文档里有对应的并发与预算说明；跑完自己的实测之后，欢迎在评论区聊聊各自的调度参数和账单数字，看看同样的 8 个候选在不同的场景里各值多少钱。
