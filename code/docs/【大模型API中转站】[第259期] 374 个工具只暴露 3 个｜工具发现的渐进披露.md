# 【大模型API中转站】[第259期] 374 个工具只暴露 3 个｜工具发现的渐进披露

接入 MCP 工具时，最先撞上的成本不是调用，而是**发现**。

每个工具都要占一份定义：名称、描述、参数 schema、返回值说明。工具少的时候这不是问题；一旦接入几十台服务器、上百个工具，光是把这些定义放进上下文就已经是一笔固定开销——每次请求都要重发一遍。我在 4sapi（https://4sapi.com）上做工具层治理时，第一件要解决的就是这件事。

## 一、先把这笔开销量化

一组实测给出了很具体的对照：在 **22 台服务器、374 个工具**的部署中，一次 top-5 的发现交互在全目录口径下需要 **42,450 个 token**；改成渐进披露之后，同样的发现过程只需要 **475 个 token**。

```text
全目录遍历：42,450 token
渐进披露：    475 token
降幅：约 89 倍
```

这个对比的前提要说明清楚：42,450 是"把全部工具定义都放进上下文"的口径，这在工具数量增长后是常见做法，因为简单、无需额外机制。而它的代价是**每一次请求都在为整个目录付费**，哪怕本次只用到一个工具。

475 的口径则是"只暴露与当前查询相关的少量工具定义"。两者的差距不是优化了多少，而是**成本模型不同**：一个是随目录规模线性增长，一个是与查询相关、与目录规模基本无关。

## 二、从 O(n) 到 O(k)

把这个改造说清楚：原来的模式是**目录遍历**，复杂度记作 O(n)，n 是目录里的工具总数。改造后是**渐进披露**，复杂度记作 O(k)，k 是本次查询实际需要涉及的工具数。

两者在工程上的差别不只是常数大小。O(n) 模式下，接入第 400 个工具会让**每一次请求**都变贵；O(k) 模式下，接入第 400 个工具只让**检索空间**变大，请求成本基本不变。前者会随规模增长而恶化，后者可以持续扩展。

两种模式的差异随规模变化如下：

| 目录规模 | 全量加载每请求开销 | 渐进披露每请求开销 | 主要瓶颈 |
| --- | --- | --- | --- |
| 20 个工具 | 约 2 千 token | 约 4 百 token | 差异不明显 |
| 100 个工具 | 约 1.1 万 token | 约 5 百 token | 开始影响成本 |
| 400 个工具 | 约 4.2 万 token | 约 5 百 token | 成为主要开销 |

这个性质决定了：当目录规模还小的时候，两种做法的差距不明显；一旦工具数量过百，O(n) 模式的成本增长就会开始吞噬其他优化的收益。所以这类改造越早做越省事——等到成本成为瓶颈再改，接口形态和调用方习惯都已经固化了。

## 三、两阶段检索：先服务器，后工具

渐进披露的具体实现通常分两阶段：**先对服务器排序，再在选中的服务器里对工具排序**。

为什么分两阶段而不是直接对工具平铺检索？因为工具之间高度同质。同一台服务器下的工具往往服务同一个领域、共享相似的描述措辞，直接平铺会让召回的候选集中在同一台服务器上，覆盖面变窄。先定位服务器，能在有限的名额里覆盖更多来源。

实测的检索质量可以作参考：在一个 49 条查询的基准上，两阶段方案的 **R@5 达到 0.816**，对比关键词基线的 **0.592**。这个对比说明方案本身的有效性，但更值得注意的是**基准规模很小**（49 条，作者自建），所以这个数字应当作为方向性参考，而不是可以外推到任意目录的性能承诺。

## 四、能力卡由谁签名

渐进披露的一个副作用需要提前处理：如果披露的内容被压缩成一句摘要，那么**这句摘要的可信度就决定了整个发现的准确度**。摘要写错，后面排序再准也没用。

一个值得借鉴的设计是：能力卡由**部署运营方签名**（例如用 Ed25519），而不是直接采信发布方提供的排名文案。

这个区别在治理上很重要。**发布方提供的描述天然带有自我推荐倾向**——它希望自己被选中，因此描述会向"适用范围广、能力强"的方向写。而运营方签名的描述，责任主体变成了**部署这套系统的人**，它有动机把描述写准，因为描述不准导致的选错工具，后果由它承担。

配套的做法是把签署与验证做成链路的一部分：登记工具时由运营方生成并签名，检索时验证签名，签名不匹配则拒绝该条目。这样"谁能往目录里加东西"和"加进去的描述由谁背书"就分开管了。

## 五、可混淆簇：描述相近的工具会互相干扰

工具描述之间还有一个更隐蔽的问题：**描述过于接近的工具会互相混淆**。

当两个工具的描述在语义上高度相似、参数结构也接近时，模型（以及检索器）会难以判断该用哪一个。这类问题在工具数量增长后会集中出现，因为新工具往往是在已有工具基础上扩展而来，描述措辞自然接近。

有一类分析方法专门处理这个：三层可混淆簇分析，包含**密度聚类**（找出描述高度密集的区域）、**查询边际分析**（找出哪些工具在典型查询下难以区分）与 **token 诊断**（定位描述中导致混淆的具体表述）。

在一组部署中，这类分析识别出 **49 个可混淆簇**，其中包含 **4 个高风险簇**。高风险的含义是：这些簇内的工具在常见查询下几乎无法区分，模型选错的概率很高。

这条的实践含义是，**工具治理不只是清理无效工具，还包括拆分和改写描述相近的工具**。具体动作有三类：合并语义重叠的工具、在描述里显式写出彼此的适用边界、或者把某个工具的参数约束收紧到只会命中它自己的场景。

## 六、描述来源要可追溯

还有一项容易被忽略的记录要求：**为每次查询记录用于排序的描述来源**。

原因是描述会变。同一个工具的能力卡可能被更新过多次，如果排序时用了哪个版本没有记录，那么事后复核"为什么这次选了工具 A"就无从下手——检索结果看着没问题，但依据已经找不到了。

记录来源的成本很低（在排序结果里带上描述版本号），收益是在排障时能把"选错工具"这件事拆成两个可验证的问题：**描述当时写错了**，还是**检索逻辑有缺陷**。两者的修法完全不同，而缺少版本记录时只能笼统地怀疑。

这一点与之前讨论过的评测可信度问题是同一个道理：**可追溯性是所有自动化决策的基础设施**，不只是审计需求。

## 七、延迟代价

一个自然的担心是：多了一层代理与检索，延迟会不会显著上升？

十次试验的网关测量给出的结果是：相比直接调用，代理层**平均只增加 5ms 延迟（0.8%）**。这个增幅相对于它带来的上下文节省（89 倍）可以忽略。

值得说明的是为什么代价这么低。检索本身是轻量操作（向量或关键词匹配），而它省下的是**大量 token 的处理**——按 token 计费的口径下，多花 5ms 省下几万 token，在任何合理的成本模型里都是划算的。这也说明一个更一般的判断：**在推理链路上，用少量计算换大量上下文通常是正收益**，因为上下文成本在整个链路里占的比重远高于一次轻量检索。

## 八、在受治理数据上加一层中介

工具发现的另一类场景是**跨组织的受治理数据**。这里的矛盾更尖锐：语言模型是概率式的交互方式，而数据治理是策略式的——两者直接对接，会让治理规则退化成提示词里的一句请求。

可行的架构是在中间加一层**协议中介**：把数据空间的能力翻译成**结构化、schema 驱动的工具**，供 agent 发现与调用，同时把治理约束留在中介层。

这个设计的关键性质是**不需要修改既有的数据空间组件**。中介层叠加在现有系统之上，通过协议对接，数据平台方无需为接入 agent 而改造自身。对于已经跑着一套治理体系、不可能为 AI 接入而重构的组织，这个性质决定了方案是否可落地。

原型验证覆盖了三个环节：目录发现、元数据检索、数据服务调用。三者对应 agent 与数据交互的完整路径——先知道有什么，再了解细节，最后取用。治理约束在每一环都生效，而不是只在最后一环把门。

## 九、接入示例：按需披露的工具注册表

下面这段脚本实现一个最小的工具注册表：登记工具、按查询检索出 k 个候选、记录所用描述版本。

```python
import os, json, hashlib, re
from openai import OpenAI

client = OpenAI(
    api_key=os.getenv("FOURSAPI_API_KEY"),
    base_url="https://4sapi.com/v1",
)

TOP_K = int(os.getenv("TOP_K", "5"))
REGISTRY_PATH = os.getenv("REGISTRY", "./tools_registry.json")


def load_registry():
    with open(REGISTRY_PATH, encoding="utf-8") as f:
        raw = json.load(f)
    # 为每个工具的当前描述计算版本指纹，便于追溯
    for t in raw:
        t["desc_version"] = hashlib.sha256(t["description"].encode("utf-8")).hexdigest()[:10]
    return raw


def score(query, tool):
    """轻量相关性打分：查询词与描述/名称的重合度。生产环境可换向量检索。"""
    q = set(re.findall(r"[\w\u4e00-\u9fff]+", query.lower()))
    d = set(re.findall(r"[\w\u4e00-\u9fff]+",
                       (tool["name"] + " " + tool["description"]).lower()))
    if not q:
        return 0.0
    return len(q & d) / len(q)


def discover(query, registry, k=TOP_K):
    """两阶段：先对 server 聚合打分，再在入选 server 内对工具排序。"""
    by_server = {}
    for t in registry:
        by_server.setdefault(t["server"], []).append(t)

    server_score = {s: max(score(query, t) for t in ts) for s, ts in by_server.items()}
    top_servers = sorted(server_score, key=server_score.get, reverse=True)[:max(1, k // 2)]

    cands = [t for s in top_servers for t in by_server[s]]
    ranked = sorted(cands, key=lambda t: score(query, t), reverse=True)[:k]

    return [{"name": t["name"], "server": t["server"],
             "desc_version": t["desc_version"], "score": round(score(query, t), 3)}
            for t in ranked]


def expose(selected, registry):
    """只把入选工具的定义拼进上下文，其余不出现。"""
    index = {t["name"]: t for t in registry}
    return [{"name": s["name"], "description": index[s["name"]]["description"],
             "parameters": index[s["name"]]["parameters"]} for s in selected]


if __name__ == "__main__":
    reg = load_registry()
    q = os.getenv("QUERY", "查询订单退款状态")
    picked = discover(q, reg)
    print("候选:", json.dumps(picked, ensure_ascii=False, indent=1))
    print("暴露定义数:", len(expose(picked, reg)), "/ 全目录:", len(reg))
```

三个设计点值得单独说明：`desc_version` 让每次发现都能追溯到具体描述版本；`discover` 的两阶段结构保证候选来源分散；`expose` 只返回入选工具的定义，是节省 token 的关键——**未入选的工具完全不占上下文**。

## 十、工具治理清单

1. 工具定义是否按需披露，而不是全量加载；
2. 检索是否分两阶段（先定位来源，再在来源内排序）；
3. 能力卡是否由运营方签名，而非采信发布方自述；
4. 是否做过可混淆簇分析，高风险簇是否已拆分或改写描述；
5. 是否记录每次发现所用的描述版本；
6. 代理层增加的延迟是否实测过；
7. 涉及受治理数据时，治理约束在哪一层生效，是否可独立于 agent 验证；
8. 新工具登记的流程是否包含描述质量检查，而不是只做技术接入。

第八条是最容易松动的一环：工具数量增长后，登记流程往往退化成"填个 schema 就算接入"，而描述质量直接决定发现准确度。

## 十一、成本与风险提示

- **检索质量决定整体可用性**。披露的是摘要，摘要不准则后续排序无意义；描述的维护优先级应与代码同级。
- **小样本基准上的检索指标不可外推**。自建基准规模有限，上线前应用真实查询分布验证。
- **可混淆簇会随目录增长而增加**。建议把簇分析做成定期任务，而不是一次性的清理。
- **签名机制带来运维成本**（密钥管理、轮换、失效处理），需要评估是否与组织的密钥管理能力匹配。
- **代理层是新增的单点**。它虽然延迟代价很小，但可用性要求高，需要冗余设计。

## 结论

工具发现的成本随目录规模线性增长，这在工具数量过百后会成为主要开销。渐进披露把复杂度从 O(n) 降到 O(k)，一组实测中把一次发现交互从 42,450 token 压到 475，延迟代价只有 0.8%。但真正的长期价值在两个治理设计上：**能力卡由部署运营方签名**解决了描述的可信来源问题，**记录排序所用的描述版本**提供了可追溯性。再补上可混淆簇的定期分析，以及受治理数据场景下的中介层，一套工具治理才算完整。我在 4sapi.com 上按这个顺序做下来，最明显的收益其实是"接第 400 个工具时不再需要评估对现有请求的影响"——这个可预期的性质，比省下的 token 更有价值。
