# 【大模型API中转站】[第214期] 家庭 Agent 独立账号隔离｜共享日程接入设计

个人 Agent 服务一个人，账号和权限围绕一个人设计就够了；当同一个 Agent 要同时服务一家人，主体、数据边界和隐私全都要重新设计。Google 一个刚开放的实验项目把这个问题最完整的一版参考答案摆上了台面，我把它的工程逻辑拆开，再落到 4sapi（https://4sapi.com）场景下的多租户接入设计。

## 一、开篇痛点：个人 Agent 好做，共享 Agent 难做

过去两年，大部分 Agent 产品都在解决"一个人用"的问题：一个会话、一个账号、一份历史、一套权限，出了问题停掉会话就能止损。

把服务对象从一个人换成一家人或一个小团队，问题立刻变形：

- **身份问题**：Agent 到底是谁？寄生在创建者的账号里，还是拥有独立身份？它发出的每封邮件、代填的每个表单，署名和责任算谁的？
- **数据问题**：读日历时读的是谁的日历？全家的合并成一份，还是按人分区？一个成员不想让 Agent 接触的私人日程，会不会因为 Agent 挂在另一个成员账号下而被顺带读走？
- **权限问题**：替人代填表单时，授权人是谁？是发起对话的那个人，还是表单归属的那个人？
- **归因问题**：Agent 多发了一封邮件、订错了活动场地，费用算谁的、责任算谁的、日志记在谁头上？

这些问题在多租户 API 接入里几乎一模一样：一个中转服务同时服务多个业务方时，隔离是第一设计原则，其次才轮到速度和价格。家庭 Agent 是这个问题最极端的样本——成员彼此熟悉、数据高度交叉、信任度极高，但工程上依然不能共用身份。信任解决不了审计，审计解决不了撤销，这两件事只有架构能解决。

## 二、原理速览：一个家庭 Agent 的四个关键事实

直接陈述这个刚开放的实验项目做了什么：

1. **独立的运行环境和身份**：家庭 Agent 运行在自己的云电脑上，使用一个独立的 Google 账号，不寄生在任何家庭成员的个人账号里。
2. **共享上下文聚合**：把家庭共享的邮件、文件和日历转化为每日简报和更新的计划，产出物是"一份全家都能看的摘要"，而不是把原始数据摊开给每个人。
3. **替人行动**：可以为最多 6 人代填表单、协调活动——行动对象明确圈定在家庭成员名单之内。
4. **行动边界与发布形态**：在超出家庭范围行动之前会先征得同意；目前是美国范围内的实验项目，采用候补名单制。

四条事实背后是三个工程决策：主体隔离（它有自己的云电脑和账号）、上下文聚合（多源数据汇成简报）、同意机制（敏感动作先审批）。下面逐个拆开，再映射到多租户接入的通用方案。

## 三、为什么是独立云电脑 + 独立账号

给 Agent 单独配一台云电脑、一个独立账号，是最费钱也最正确的决策。

**主体隔离**。Agent 拥有一个自己的身份，它以"家庭助理"这个主体的名义连接 Gmail、日历和文件，而不是冒用某个成员的登录态。授权关系因此变得清晰：谁授权了它、授权了什么范围、什么时候可以撤销，都是一条条可以单独操作的记录。反过来，如果 Agent 挂在某个成员的账号下运行，它的每个动作在服务端看来都是那个成员本人做的——权限过宽、审计混淆、出了事说不清。

**数据边界**。独立账号意味着 Agent 读到的数据落在自己的空间里，与成员个人数据物理分开。一个成员的私人邮件不会因为 Agent 寄生在另一个成员账号下而被间接暴露。数据边界划在账号层，而不是靠提示词里的约束语句——提示词能被注入改写，账号边界不能。

**凭证生命周期**。独立账号带来独立的 OAuth 授权链路和独立的 token 生命周期。撤销授权时，撤销的是"它"这一个主体，不影响任何成员的账号安全；token 泄露时，泄露的是家庭共享范围内那一份授权，不是全家六个人的个人凭证。

**可停机性**。云电脑是一个可重启、可重置、可销毁的沙箱环境。Agent 行为异常时，直接重置环境即可，不用动任何成员的设备。这是把运行环境和身份都独立出来之后才有的运维自由度。

## 四、共享上下文聚合：多源数据怎么变成每日简报

第二个决策是把家庭共享的邮件、文件、日历汇聚成每日简报和更新的计划。这里有几个容易被忽略的工程要点。

**多源异构**。邮件、文件、日历是三种完全不同的数据源：读取频率不同、变更粒度不同、格式不同。聚合层要为每个源维护独立的拉取节奏和失败隔离——日历挂了不应该连累简报里的邮件部分。

**聚合而非全量复制**。简报是"与家庭计划相关的增量摘要"，不是把所有原始数据倒进一个池子。聚合层做的是过滤、去重和摘要，原始数据留在各自的服务里，Agent 侧只保存派生结果。这样即使 Agent 环境被攻破，暴露的也是摘要而非全量原始数据。

**两种输出形态**。每日简报是给人读的（被动阅读），更新的计划是结构化的（可以被后续动作引用，比如协调活动时直接引用日程字段）。混在一起做，检索和引用都会变糊涂。

**冲突合并**。两个成员同时改了同一个日程、同一个文件，聚合层需要一个确定的合并策略——按时间戳、按来源优先级或标记冲突交给简报提示。没有合并策略的聚合层，会在第一次并发修改时产出自相矛盾的简报。

这套聚合逻辑对中转站同样成立：多租户场景下，每个业务方的用量、日志、限流状态也是"多源数据"，4sapi 在控制台里把它们聚合成按 Key 拆分的报表，而不是把所有租户的原始请求混在一个池子里。

## 五、行动边界：先同意，再行动

第三个决策是同意机制：可以为最多 6 人代填表单、协调活动，但超出家庭范围行动前会先征得同意。

把它翻译成动作分级，就是一条清晰的策略链：

- **读取家庭共享范围内的数据**：在授权范围内默认允许，保留审计记录。
- **替人行动（代填表单、协调活动）**：允许，但必须携带目标主体 ID，且目标必须在最多 6 人的名单内——"替谁办事"是动作的必填参数，不是可以从上下文里猜的字段。
- **超出家庭范围的对外动作**：先征得同意，再执行；同意记录本身要落库。
- **不可逆动作**：默认拒绝或升级到更强的确认流程。

关键设计在于"同意"是有记录、有主体、有范围的一次授权，而不是聊天框里的一句"好的"。谁在什么时间、批准了什么动作、批准的动作最后执行成什么结果，必须能还原。这也是后面审计日志一节的基础。

## 六、个人 Agent 与共享 Agent 的设计差异

把前面的分析压成一张对照表，这也是判断一个"共享 Agent"方案是否认真做过设计的速查表：

| 设计维度 | 个人 Agent | 共享 Agent（家庭/小团队） |
| --- | --- | --- |
| 运行身份 | 用户本人账号下的会话 | 独立服务账号 + 独立运行环境（云电脑/沙箱） |
| 凭证管理 | 一套 OAuth 授权 | 按数据源、按主体的多套授权 |
| 数据模型 | 单用户数据空间 | 个人区 + 共享区的双层结构 |
| 可见性控制 | 全量可见 | 按角色、按来源、按分区过滤 |
| 动作授权 | 用户本人确认即可 | 需要目标主体或家庭管理员的审批记录 |
| 上下文归属 | 单会话历史 | 按主体分区的历史，禁止跨主体串联 |
| 审计 | 按会话记录 | 按人归因 + 按动作分级记录 |
| 失效影响 | 个人会话中断 | 必须支持撤销单人授权而不影响其他成员 |
| 计费与配额 | 单账户用量 | 按主体拆分的配额、用量与账单 |

对照的结论很直白：共享 Agent 不是把个人 Agent 多开几份，也不是把所有人的账号塞给一个 Agent，而是在主体、数据、动作三个层面各自独立建模后再聚合。

## 七、多主体账号体系：服务账号 vs 个人账号代理

落到接入方，多主体共享 Agent 的账号体系有两种基本模式，实际系统几乎都是混合使用。

**服务账号模式**：为 Agent 建立独立账号（正如实验项目里那个独立的 Google 账号），各成员把共享数据授权给它。优点是主体清晰、撤销简单——删掉服务账号的授权就等于整个 Agent 下线；缺点是授权链路多一层，成员需要在各自服务里完成"授权给服务账号"的动作。

**个人账号代理模式**：Agent 以每个成员的身份访问各自的数据，技术上是成员分别完成 OAuth 授权码流程，Agent 持有按人区分的刷新令牌。优点是数据边界天然对齐个人账号，一个人能看到什么，Agent 以其身份行动时就能看到什么，不会更多；缺点是授权数量随人数线性膨胀，撤销和续期都要按人管理，审计时必须额外标注"以谁的身份执行"。

混合策略：共享数据（家庭共享的邮件、文件、日历）走服务账号，个人私有数据走成员委托授权，且个人区数据只在明确授权的任务里短暂可用。

映射到 4sapi 的场景，这套逻辑有一个非常直接的对应物：中转站的 API Key 本质上就是一种主体凭证。多租户接入时，为每个主体（家庭里的每个成员、团队里的每个业务方）发独立 Key，而不是共用一把 Key——只有这样，配额、限流、计费、审计才有"归因单位"。4sapi（https://4sapi.com）控制台支持多 Key 管理和按 Key 的用量报表，正好对应服务账号 + 按主体授权的组合：主 Key 管总配额，子 Key 按主体分配，一个主体的 Key 泄露或滥用，轮换它即可，不影响其他主体。

## 八、数据分区与可见性控制

账号体系定了，下一步是数据怎么摆。多主体共享 Agent 的数据架构是一个双层结构：

```text
家庭成员 A ─┐                          ┌─> 个人区 A（仅 A 授权的任务可访问）
家庭成员 B ─┼─ OAuth 委托授权 ────────┐  ├─> 个人区 B（仅 B 授权的任务可访问）
家庭成员 C ─┤                          |  └─> 个人区 C（仅 C 授权的任务可访问）
    ...6 人 ┘                          |
                                       v
                家庭 Agent（独立云电脑 + 独立服务账号）
                                       |
                 共享区（家庭共享邮件 / 文件 / 日历的授权接入）
                                       |
              聚合层：过滤、去重、冲突合并 -> 每日简报 + 更新的计划
                                       |
              审批网关：L2 及以上动作 -> 先征得同意 -> 生成审批记录
                                       |
              审计日志：按主体归因（替谁 / 经谁同意 / 动了哪个分区）
```

三条实现要点：

- **可见性在存储层和检索层同时过滤**，不依赖提示词。提示词是模型可见的文本，能被注入改写；分区过滤是代码路径上的确定性判断，注入改写不了。
- **个人区数据只进一次性任务**。聚合层只消费共享区数据；个人区数据在被授权的单次任务里短暂可用，任务结束即从 Agent 上下文中清除，不进入长期历史。
- **共享区有明确的成员名单**。"最多 6 人"这样的边界要在名单层实现——动作的目标主体先查名单再执行，而不是靠模型自己记得名单内容。

## 九、敏感动作审批链

审批链是把"先同意，再行动"变成代码的关键组件。动作按风险分级：

- **L0 只读共享区**：读取共享邮件、文件、日历的摘要信息，默认允许，保留审计。
- **L1 替人行动**：代填表单、协调活动。允许执行，但动作参数里必须携带目标主体 ID，且主体在家庭成员名单内。
- **L2 超出家庭范围的对外动作**：向外部服务发送、提交、预约等。先征得同意，审批记录落库后才执行。
- **L3 不可逆或高危动作**：删除共享数据、支付类操作等。默认拒绝，或要求更高级别确认。

审批请求必须说清楚具体内容，而不是一句抽象的"是否继续"：动作是什么、目标主体是谁、影响范围多大、数据来自哪个分区、如何回滚。审批记录至少包含审批人、时间、动作摘要和最终执行结果。这套分级在接入侧同样适用——对接入 4sapi 的多租户系统来说，涉及外部副作用的动作（发送、下单、通知全员）都应该走 L2 以上流程，只读的模型调用走 L0。

## 十、审计日志按人归因

家庭场景里，"Agent 干了什么"必须能还原成"替谁、经谁同意、动了哪个分区的数据"。审计日志的最小字段集：

```text
event_id
principal_id        # 目标主体：替谁办事
actor               # 执行者：Agent 实例 / 服务账号
invoker_id          # 触发人：谁发起的这次任务
action_type         # 动作类型：read / fill_form / schedule / send ...
risk_level          # 风险分级：L0-L3
data_scope          # 数据分区：personal:A / shared
approval_id         # 审批记录 ID，L2 及以上必填
timestamp
result_status
```

按人归因的价值在两端：对家庭场景，出了问题能定位到具体动作和责任人，而不是一句"Agent 干的"；对中转站场景，计费与限流争议同样靠归因仲裁——4sapi 的用量记录按 Key 拆分到主体，哪个 Key 消耗了多少 token、触发了哪些限流，一条条可查。没有按主体归因的日志，多租户系统的账永远是糊涂账。

## 十一、接入教程：用 4sapi 构建按主体隔离的会话层

把前面的设计落成代码。目标是一个多主体共享 Agent 的会话层：每个主体独立 Key、独立历史、独立数据范围，敏感动作先审批。4sapi 提供 OpenAI 兼容接口，接入只需替换 base_url 和 Key。

**环境准备**：

1. 注册 4sapi（https://4sapi.com），在控制台创建主 Key 与多个子 Key，每个主体（成员）一把独立子 Key；
2. 记录中转地址 `https://4sapi.com/v1`，作为所有主体的统一 base_url；
3. 安装依赖：`pip install openai`。

**核心实现**：

```python
import threading
import uuid
from dataclasses import dataclass, field
from openai import OpenAI

BASE_URL = "https://4sapi.com/v1"

@dataclass(frozen=True)
class Principal:
    """一个可被服务的主体的声明"""
    principal_id: str           # 稳定主体 ID，如 "family:member_a"
    api_key: str                # 该主体自己的中转站子 Key，绝不共用
    allowed_scopes: frozenset   # 允许的数据分区，如 {"shared", "personal:A"}

@dataclass
class Approval:
    approval_id: str
    principal_id: str
    action_type: str
    risk_level: str
    decided_by: str
    approved: bool = False

class PrincipalSessionManager:
    """多主体共享 Agent 的会话层：按主体隔离 Key、历史与权限"""

    def __init__(self):
        self._clients = {}     # principal_id -> OpenAI 客户端
        self._history = {}     # principal_id -> 会话历史（按主体分区）
        self._usage = {}       # principal_id -> 累计 token
        self._approvals = {}   # approval_id -> Approval
        self._lock = threading.Lock()

    def client_for(self, p: Principal) -> OpenAI:
        """每个主体一个客户端实例，绑定它自己的 Key"""
        if p.principal_id not in self._clients:
            self._clients[p.principal_id] = OpenAI(
                api_key=p.api_key,
                base_url=BASE_URL,
            )
        return self._clients[p.principal_id]

    def check_scope(self, p: Principal, data_scope: str) -> bool:
        """数据分区校验：代码层判断，不依赖提示词"""
        return data_scope in p.allowed_scopes

    def request_approval(self, principal_id: str, action_type: str,
                         risk_level: str) -> str:
        """L2/L3 动作生成待审批记录，等待管理端确认后置为 approved"""
        ap_id = str(uuid.uuid4())
        self._approvals[ap_id] = Approval(
            approval_id=ap_id,
            principal_id=principal_id,
            action_type=action_type,
            risk_level=risk_level,
            decided_by="family_admin",
        )
        return ap_id

    def chat(self, p: Principal, user_text: str,
             data_scope: str = "shared", risk_level: str = "L0",
             action_type: str = "read"):
        if not self.check_scope(p, data_scope):
            raise PermissionError(f"{p.principal_id} 无权访问分区 {data_scope}")

        if risk_level in {"L2", "L3"}:
            ap_id = self.request_approval(p.principal_id, action_type, risk_level)
            if not self._approvals[ap_id].approved:
                raise PermissionError(f"动作 {action_type} 等待审批，审批号 {ap_id}")

        with self._lock:
            history = self._history.setdefault(p.principal_id, [])
            history.append({"role": "user", "content": user_text})
            snapshot = list(history)

        resp = self.client_for(p).chat.completions.create(
            model="gpt-4o",  # 示例模型名，按中转站实际可用模型替换
            messages=snapshot,
        )

        with self._lock:
            history.append({"role": "assistant",
                            "content": resp.choices[0].message.content})
            self._usage[p.principal_id] = (
                self._usage.get(p.principal_id, 0) + resp.usage.total_tokens
            )
        return resp

    def usage_report(self) -> dict:
        """按主体拆分的用量报表，对应审计与计费归因"""
        return dict(self._usage)
```

**调用示例**：

```python
mgr = PrincipalSessionManager()

alice = Principal(
    principal_id="family:member_a",
    api_key="sk-4sapi-member-a",          # 成员 A 自己的子 Key
    allowed_scopes=frozenset({"shared", "personal:A"}),
)

bob = Principal(
    principal_id="family:member_b",
    api_key="sk-4sapi-member-b",          # 成员 B 自己的子 Key
    allowed_scopes=frozenset({"shared", "personal:B"}),
)

# L0 只读共享区：直接放行
mgr.chat(alice, "汇总今天全家的日程，生成简报", data_scope="shared")

# 越权尝试：A 请求访问 B 的个人区，代码层直接拒绝
# mgr.chat(alice, "查看 B 的私人日程", data_scope="personal:B")  # -> PermissionError

# L2 对外动作：先生成审批记录，管理端确认后才可执行
# mgr.chat(alice, "向活动场地发预约确认", data_scope="shared",
#          risk_level="L2", action_type="send_external")
```

四个设计点对应前文的架构：

- **每主体独立 Key**：4sapi 控制台按 Key 出用量与账单，天然支持按主体计费归因；某成员的 Key 异常，轮换该 Key 即可，其他成员不受影响。
- **分区校验在代码层**：`check_scope` 是确定性判断，注入任何提示词都无法绕过。
- **历史按主体分区**：`_history` 以 `principal_id` 为键，A 的上下文永远不出现在 B 的请求里。
- **审批先行**：L2/L3 动作在调用模型之前先过审批网关，等待期内动作不执行。

## 十二、成本与风险提示

- **成本**：多主体意味着多份会话历史、多份凭证管理和多份 Key 配额。简报类任务建议低频批量生成（每日一到两次），而不是每个成员各自高频轮询；上下文历史按主体分区后要设置保留期限，避免存储无限膨胀。4sapi 按量计费，按 Key 拆分后每个主体的成本清晰可见，便于把简报、协调这类高频轻量任务路由到便宜的模型档位。
- **风险**：家庭与小团队场景的数据敏感度高于普通单用户场景，授权范围务必最小化——只授权共享区所需的读取范围，个人区按需临时授权。实验项目目前是美国范围内、候补名单制，形态还会变，接入设计要把底层模型和上层会话层解耦，保留随时更换模型的余地。
- **合规**：只做合法授权范围内的数据接入与自动化，不抓取他人数据、不绕过平台限制；审批与审计记录按业务和安全要求设定保留期限，不做无限期留存。

## 十三、上线前清单

多主体共享 Agent 上线前，至少逐项确认：

1. 每个主体持有独立 Key 与独立配额，系统中不存在共用 Key 的调用路径。
2. 数据分区校验在代码层执行，构造任何提示词都无法越权访问其他分区。
3. L2/L3 动作默认拒绝执行，审批记录包含审批人、时间、动作摘要与执行结果。
4. 撤销或轮换单个主体的授权，不影响其他主体的会话与任务。
5. 审计日志能完整回答"替谁、经谁同意、动了哪个分区、结果如何"。
6. 用量报表按主体拆分，成本与限流可归因到具体 Key。
7. 断网、限流、模型失败时，动作不重复执行（写入类动作携带幂等键）。
8. Key 与刷新令牌不进日志、不进模型上下文原文，泄露时可在分钟级轮换。

## 总结

这期的核心是一个转折：个人 Agent 的账号、权限、隐私方案，在服务多个人时全部要重新设计。一个刚开放的实验项目给出的参考答案是三件事——给 Agent 独立的云电脑和独立账号，让"它"成为一个明确的主体而不是混在某个成员的身份里；把家庭共享的邮件、文件、日历聚合成每日简报和更新的计划，聚合派生结果而不是复制原始数据；在超出家庭范围行动前先征得同意，让敏感动作走有记录的审批链。落到接入方，就是服务账号与个人账号代理的组合、个人区与共享区的双层分区、按风险分级的审批网关、按人归因的审计日志，再配上按主体拆分的 Key 管理与用量报表——4sapi（https://4sapi.com）的多 Key 体系正好承载这套设计。多主体共享 Agent 的工程难点从来不是模型能力，而是身份、数据和责任的边界画在哪里。有正在做多租户 Agent 或家庭共享场景的读者，欢迎在评论区聊聊各自的隔离与审批方案。
