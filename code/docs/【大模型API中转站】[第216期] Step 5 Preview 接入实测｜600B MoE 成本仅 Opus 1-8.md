# 【大模型API中转站】[第216期] Step 5 Preview 接入实测｜600B MoE 成本仅 Opus 1/8

一个新旗舰把总参数堆到 600B，激活却只有 27B，还把单任务成本压到 Claude Opus 5 的 1/8，并且承诺 10 月 15 日交出开源权重。

这就是 Step 5 Preview 的基本盘：稀疏 MoE 架构、100 万 Token 上下文、文本与视觉双输入，在 Artificial Analysis Intelligence Index 拿到 44 分、位居全球开源模型前三。我在第一时间把它接进了手头的评测管线，这篇拆开讲三件事：MoE 的成本结构为什么支持这个价位、百万上下文在计费上有哪些坑、以及怎么用 4sapi（https://4sapi.com）把这条新旗舰稳稳接进现有系统。

## 一、开篇痛点

我面对的选型困境很典型：

- 旗舰模型能力强，但单任务成本高，跑批量任务时账单不可控；
- 开源模型便宜，能力却经常在 Agent 型任务上掉链子；
- 长上下文是刚需（长文档审阅、大仓库分析），但很多模型一过 128K 价格就翻着涨；
- 新模型发布后，接入文档滞后、SDK 适配慢，往往要等一两周才能稳定用上。

Step 5 Preview 恰好同时打了这四个点：能力进开源前三、成本压到旗舰的零头、上下文直接给到 100 万、并且预告了开源时间表。对我来说，问题只剩一个：它的真实接入体验和成本曲线，值不值得现在就切一部分流量过去。

## 二、原理速览：稀疏 MoE 的成本账

先看架构参数：

```text
Step 5 Preview（稀疏 MoE）
    总参数量:    600B
    激活参数量:  27B  (约 4.5%)
    上下文:      1,000,000 Token
    输入模态:    文本 + 视觉
    综合评测:    Artificial Analysis Intelligence Index 44 分
    权重计划:    2026-10-15 开源
```

MoE 的经济性来自"路由"：每个 Token 只被路由到少数专家，实际参与计算的参数是激活的 27B，而不是全部 600B。这意味着推理算力成本接近一个 27B 稠密模型，而能力上限向 600B 的知识容量靠拢。

我把这层关系画成请求流：

```text
请求 (prompt + 多模态输入)
    |
    v
路由层：为每个 Token 选择专家
    |
    v
计算层：仅激活 ~27B 参数
    |
    v
输出：能力对标 600B 级容量，算力账单按激活规模走
```

对比一下三个量级的成本定位：

| 模型档位 | 能力定位 | 相对单任务成本 | 适用场景 |
| --- | --- | --- | --- |
| 闭源旗舰（Opus 5 级） | 天花板 | 8x（基准） | 高难度推理、关键决策 |
| Step 5 Preview | 开源前三 | ~1x（Opus 的 1/8） | 日常生产、Agent 主力 |
| 开源中档 | 够用 | 更低 | 简单分类、批量粗筛 |

这里"1/8"是官方口径的单任务相对成本，我的用法是把它当锚点而非承诺：真实账单取决于任务构成、上下文长度和输出量。

## 三、百万上下文的计费坑位

100 万 Token 上下文是双刃剑。我在测试里踩到三个坑：

**坑一：输入费随上下文线性涨。** 一次塞 80 万 Token 的仓库分析，即使输出只有两千 Token，输入费也是账单大头。上下文给得越宽，越要有意识地控制"每次到底喂多少"。

**坑二：缓存与重复前缀。** 多轮会话里系统提示和前面的对话每轮都重算一遍输入费。百万窗口放大了这个问题——前缀越长，重复计费越疼。接入层必须做前缀缓存。

**坑三：隐性截断。** 窗口给到 100 万不代表中间内容都被有效利用，超长文档里的检索质量要单独验证，不能默认"窗口大=看得全"。

我在计费层加了一个前置检查：估算本次请求的输入 Token 数，超过阈值就先走检索压缩，而不是硬塞。

## 四、能力定位：44 分意味着什么

Artificial Analysis Intelligence Index 的 44 分放在"开源模型前三"的语境里，含义是：它已经能接住过去只有闭源旗舰才能稳定完成的任务类型——多步推理、工具调用、代码生成这一档。

我的实测感受是，这类"准旗舰"模型最好的用法不是替代旗舰，而是重新切分流量：

| 任务类型 | 切流建议 |
| --- | --- |
| 代码审查、文档生成、常规 Agent 任务 | Step 5 Preview 主力承接 |
| 高难度架构决策、复杂调试 | 保留旗舰兜底 |
| 批量分类、摘要、粗筛 | 更便宜的中档模型 |

## 五、接入教程：通过 4sapi 直连

新模型发布后最麻烦的是接入适配。我通过 4sapi（https://4sapi.com）接入，好处是接口协议统一、不用自己折腾 SDK 兼容，Python 侧三行配置：

```python
from openai import OpenAI

client = OpenAI(
    api_key="4sapi-key",
    base_url="https://4sapi.com/v1",
)

resp = client.chat.completions.create(
    model="step-5-preview",
    messages=[
        {"role": "system", "content": "按结构输出风险结论的代码审查助手。"},
        {"role": "user", "content": "审查以下变更，给出风险清单。"},
    ],
    max_tokens=2048,
)
print(resp.choices[0].message.content)
```

接入后我建议先跑三步验证：

1. **协议验证**：确认多模态输入的字段格式（视觉输入走标准消息结构即可）；
2. **长上下文冒烟**：用一段 10 万 Token 的真实文档测一次，核对回传用量与计费口径；
3. **回归对比**：拿过去一周的真实任务样本，在旧模型与 Step 5 Preview 上各跑一遍，对比质量与账单。

## 六、成本核算：一次真实任务的对账

按"Opus 5 的 1/8"做相对测算（设 Opus 5 单任务成本为 1 个单位）：

| 任务 | Opus 5（基准） | Step 5 Preview | 节省 |
| --- | --- | --- | --- |
| 单次代码审查（20K 输入 / 2K 输出） | 1.0 | ~0.125 | 87.5% |
| 批量 1000 次同类任务 | 1000 | ~125 | 87.5% |
| 长文档审阅（300K 输入） | 1.0（同任务口径） | ~0.125 | 87.5% |

账单下降是按比例的机械换算，真实数字要用自己的任务回归验证。我给自己定的切换门槛是：质量回归不回退、成本下降超过 50%，两个条件同时满足才切主力流量。

## 七、场景切分：它在 Agent 流水线里的位置

单点接入只是第一步，真正让新旗舰产生收益的是流水线里的岗位安排。我的切分方案：

| 流水线环节 | 岗位安排 | 理由 |
| --- | --- | --- |
| 任务理解与拆解 | Step 5 Preview | 长上下文吃得下完整需求 |
| 代码/文档产出 | Step 5 Preview 主力 | 成本与能力的平衡点 |
| 跨仓库大型分析 | Step 5 Preview + 检索 | 百万窗口的分段利用 |
| 最终裁决与合并 | 旗舰模型兜底 | 关键决策不留成本妥协 |

这套切分的核心思路是"把旗舰从流水线工位上换下来，只留在裁判席"。过去我的账单里六成花在了不需要旗舰能力的环节上，切分之后这部分全部由低成本档承接。

## 八、监控与对账看板

切流之后，我固定盯四条曲线：

```text
质量曲线:   人工抽检通过率 / 回归样张得分
成本曲线:   单任务平均成本 / 日总账单
延迟曲线:   P50 / P95 响应时间
异常曲线:   错误率 / 截断率(撞 max_tokens)
```

四条曲线必须放在同一时间轴上看：成本下降如果伴随质量曲线下探，就是切流过头的信号；延迟上浮通常先于错误率爆发。我给自己定的告警规则是质量曲线连续两天低于基线就自动回切两成流量，宁可贵一点，不让劣化扩散。

## 九、风险提示

- **Preview 后缀**：预览版行为可能随版本调整，Prompt 敏感的业务要做版本锁定与回归；
- **开源时间表**：10 月 15 日是承诺日期，权重规模、许可条款落地前不影响 API 决策，但影响"要不要本地再部署一份"的中期规划；
- **榜单≠业务**：44 分是综合口径，我的具体任务（比如特定语言的代码生成）要单独实测；
- **多模态计费**：视觉输入的 Token 折算口径要先确认，图片密集任务的成本模型和纯文本完全不同；
- **合规**：接入走正规渠道（如 4sapi），不碰来路不明的共享 Key。

## 十、检查清单：新旗舰接入验收

1. 协议兼容：SDK 调用、流式输出、工具调用全部通过；
2. 长上下文：10 万 Token 冒烟 + 回传用量核对；
3. 质量回归：真实任务样本对比不回退；
4. 成本对账：按相对成本锚点核算，误差可解释；
5. 降级路径：主模型异常时自动切备用模型；
6. 监控告警：错误率、延迟、单任务成本三条曲线看板。

## 总结

Step 5 Preview 用"600B 总参、27B 激活"的稀疏 MoE 把开源前三的能力做进了旗舰 1/8 的成本区间，100 万上下文和视觉输入补齐了接入场景。我的结论是：它可以当生产主力养起来，旗舰留作兜底，开源权重落地后成本还能再降一档。通过 4sapi（https://4sapi.com）接入时，我按"协议验证、长上下文冒烟、质量回归"三步走，切流前先对账。欢迎在评论区聊聊新旗舰的切流策略和踩坑经历。
