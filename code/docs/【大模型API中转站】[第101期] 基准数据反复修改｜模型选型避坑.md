# 【大模型API中转站】[第101期] 基准数据反复修改｜模型选型避坑

一个模型的幻觉率在几天内从 4.2% 变成 2%，又改回原值。基准数字如此反复，选型该怎么信？

这篇记录我观察到的基准数据波动现象，拆解评测口径差异，并给出我实际在用的多模型选型方法：自建评测集，通过 4sapi（https://4sapi.com）统一接入后逐模型跑分对比。

## 一、开篇痛点

新旗舰发布，宣传页上的数字总是一大串：幻觉率、推理得分、编程通过率、长上下文准确率。看起来都很硬，但真实情况是这些数字随时可能变。

我记录到一个典型案例：某旗舰模型发布公告里的幻觉率，先是 4.2%，之后被改成 2%，最后又改回接近原值。几天之内同一个指标出现三种口径，宣传页没有任何解释。对按这些数字做选型的开发者来说，这就是一个真实的坑。

更麻烦的是另一个现象：老基准正在失效。标准翻译基准接近饱和，SOTA 模型已经刷到顶，排行榜第一和第二之间只差零点几个百分点。分数失去区分度之后，排行榜反而变成噪声源。

## 二、基准数字为什么会变

### 评测本身是一个过程，不是一个快照

一个基准分数由四部分决定：

```text
测试集（测什么）
    |
    v
评测脚本（怎么算分）
    |
    v
运行环境（模型版本、温度、采样）
    |
    v
后处理（滤除无效输出、重跑失败项）
```

任何一环变化，分数都会变。发布当天先跑一遍、随后补跑更全的测试、再修掉脚本里的 bug，都是正常流程。问题在于这些过程通常不透明，用户只看到数字在变，不知道是哪一环变了。

### 幻觉率的测量口径尤其敏感

幻觉率不是一个固定值，它取决于：

- 问什么类型的问题（事实问答、代码、还是开放写作）；
- 判定"幻觉"的标准（与事实库比对、人工标注、还是模型裁判）；
- 采样次数与温度（同一条提示词跑多次，幻觉次数不一样）；
- 是否排除格式类错误。

同一个模型，用不同口径测，幻觉率可以从个位数跳到两位数。把 4.2% 改成 2%，很可能只是换了判定标准，而不是模型本身变好了。

## 三、我记录到的数字波动

我以某个旗舰模型为样本，记录下它发布后的指标变化：

| 指标 | 发布当天 | 第二天 | 第三天 |
| --- | --- | --- | --- |
| 幻觉率 | 4.2% | 2.0% | 4.0%（改回） |
| 综合推理分 | 169 | 169 | 169 |
| 智能指数 | 61 | 61 | 61 |

观察结论有两条：

- 单项指标（幻觉率）最容易反复，因为它口径最主观；
- 综合指标相对稳定，因为它由几十个子项加权，单项波动被稀释。

对选型来说，盯着单个数字没有意义，要看多个口径的交叉验证。

## 四、基准饱和：分数失去区分度

翻译基准是典型的饱和案例。模型逐年变强，标准翻译测试集很快被刷满：

```text
旧基准：BLEU 35 -> 40 -> 45 -> 48 -> 49.5（接近上限）
新需求：测试 SOTA 的极限与失败案例
```

分数接近上限之后有两个后果：

- 排行榜排序随机化，第一和第二的差距在误差范围内；
- 评测失去诊断价值，看不出模型具体在哪类句子上犯错。

应对方式是换"边界型"基准：专门构造长句、歧义句、专业术语密集的句子，让模型暴露失败案例，而不是继续在饱和集上比小数点。选型时如果只看老排行榜，很可能在两个实际上差不多的模型之间浪费大量对比时间。

## 五、方案一：官方直连逐个测

官方直连的优点是数据最新，缺点是要为每个模型单独申请 Key、单独写对接代码、单独对账。

```python
from openai import OpenAI

client = OpenAI(api_key="sk-xxx", base_url="https://api.openai.com/v1")

resp = client.chat.completions.create(
    model="gpt-6-astra",
    messages=[{"role": "user", "content": "翻译：The quick brown fox jumps over the lazy dog."}],
)
print(resp.choices[0].message.content)
```

跑三四个模型就要维护三四个 client 实例和三四个账单，选型期一过这些代码就变成废代码。

## 六、方案二：4sapi 统一接入跑分

我日常选型用的方式是统一接入层：一个端点、一套 OpenAI 格式、Key 集中管理，切换模型只改 `model` 字段。

```python
from openai import OpenAI

client = OpenAI(
    api_key="4sapi-key",
    base_url="https://4sapi.com/v1",  # 统一接入端点
)

models = ["gpt-6-astra", "claude-fable-5", "gemini-3.8-flash", "muse-spark-1.3"]

for m in models:
    resp = client.chat.completions.create(
        model=m,
        messages=[{"role": "user", "content": EVAL_PROMPT}],
        temperature=0,
    )
    print(m, "->", resp.choices[0].message.content[:100])
```

这样选型代码只需要写一遍，换模型就是换列表里的一项。评测集、温度、判定逻辑全部固定，只有模型在变，对比才公平。

## 七、自建评测集的步骤

我建议选型期做一套自己的最小评测集，二十到三十条就够：

1. **从真实任务取材**：收集过去一个月生产环境里最常问的 20 类问题；
2. **混合难度**：包含简单事实题、需要多步推理的题、长文档问答、代码生成各一组；
3. **固定判定标准**：每题预写答案要点，人工比对输出，避免用模型裁判造成二次偏差；
4. **固定运行参数**：temperature 固定为 0，同题跑两次取一致结果；
5. **记录失败案例**：把每题的错误类型归类，比总分更能指导选型。

这套评测集不用很大，重点是把口径锁死。锁死口径之后，即使宣传页数字再变，我的对比结论也不会被带偏。

## 八、成本与风险提示

- 别为宣传数字付溢价：数字会改，选型前先用自己的评测集验证；
- 单项指标警惕反复：幻觉率、安全分这类主观指标波动最大；
- 饱和基准慎用：接近上限的排行榜区分度低，别据此下结论；
- 多模型成本对比：统一接入层下每个模型按实际 token 计费，跑分成本可控；
- 合规接入：只走合法渠道，不绕官方限制，评测数据不涉及敏感信息。

## 九、选型检查清单

1. 收集真实任务样本，建立 20-30 条评测集；
2. 固定判定标准与运行参数，口径锁死；
3. 通过统一接入层批量跑分，切换模型只改字段；
4. 记录每个模型的失败案例类型，而非只看总分；
5. 对照宣传数字与自测结果的差异，差异大的模型重点怀疑；
6. 一周后再复测一次，观察数字是否稳定。

## 十、我的选择

我现在的做法是不再看单一排行榜，而是每季度用自己的评测集把所有候选模型重跑一遍，把结果存在统一接入层的路由配置里。宣传页数字只当作初步筛选，真正决定默认模型的是自测数据。

## 总结

基准数字会反复修改，饱和基准会失去区分度，唯一可靠的是自己锁死口径的评测集。通过 4sapi（https://4sapi.com）统一接入后，多模型跑分只是改一个字段的事，选型决策回归到真实任务表现。欢迎在评论区聊聊遇到过的基准数字翻车经历。
